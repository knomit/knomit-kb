# Bridge seeding: a model-less cross-cluster shared-token detector; discovery never feeds on its own output

A bridge is a structural token (entity or domain) shared by ≥2 facts living in DIFFERENT cluster communities — a connection across regions the clustering says are otherwise unrelated (D4). bridgeSeeds ranks candidates by strength = (1/token-freq) × distinct-communities × member-count and hands the {A..D} seed set to the connected MCP agent. The engine is MODEL-LESS: it only ranks and bounds; the agent is the sole reasoner.

Which axis counts (domain/entity/both) comes from DiscoveryConfig.Bridge via BridgeKindFromString — BOTH directions honor it. Both directions also cluster with the SAME knob the rest of the system uses — RepoInstance.ClusterResolution() / ClusterMinCommunitySize(), nothing hardcoded — so forward (review, scoped subgraph) and backward (hypothesize, whole-corpus CachedClusterFacts) share one partition and reuse the warm cluster cache. IDEMPOTENCY (§7): facts with origin=discovered are NEVER selected as seeds, so discovery cannot drift off the human-authored substrate. A seed absent from both clusters and the noise list is given a synthetic NEGATIVE community id, so it never collides with real community 0.
