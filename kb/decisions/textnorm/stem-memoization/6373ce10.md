# Stem is memoized IN PROCESS as a pure function — not a content-addressed cache, not persisted — because a remembered pure answer has no invalidation story at all, and a persisted one could outlive the library that wrote it

THE CHOICE: `textnorm.Stem` keeps a process-lifetime `sync.Map` of token → singular form. Warm cost drops from ~25µs to tens of nanoseconds at 0 allocations; `GET /lenses/all/motifs` over five mounts went 126.8ms → 8.6ms.

OPTIONS CONSIDERED AND WHY THEY LOST:

1. **A content-addressed cache of each mount's motif vocabulary, keyed on the mount's branch-head commit.** This was the originally specified design. Rejected once the cost was located: the expensive thing is not the union, it is a PURE STRING FUNCTION, and caching at the primitive needs no key, no branch, no commit and no invalidation. It also fixes every caller at once — groupingKey, domain matching, the motif-term query tiers, the motif subject-word strip — rather than one surface, which is what the house rule about making surfaces agree BY CONSTRUCTION asks for.
2. **Persisting stems (e.g. in control.db).** Rejected on two grounds. Entries are recomputable in microseconds, so persistence buys almost nothing beyond the first request of a process. More seriously, a persisted stem OUTLIVES the go-pluralize version that produced it: an upgrade that changes one singularization would leave stale stems on disk, and because Tokens feeds `store.groupingKey`, a changed stem silently re-keys motif clusters — a spelling joins, or stops joining, a different cluster, with no error anywhere. In-memory state dies with the process and cannot drift that way, which is the same posture as "git is the only source of truth; everything else is rebuildable cache".
3. **A bounded/LRU memo.** Rejected because any capacity would be a fixed constant encoding a guess about how big a corpus is — the forbidden anti-pattern. Unbounded matches the existing house precedent, `store.branchCache` (map + RWMutex, no eviction).

PURITY IS ENFORCED BY US, NOT BY THE LIBRARY — state this precisely, because the convenient short version is wrong. go-pluralize v0.2.1 DOES export rule mutators: `AddPluralRule`, `AddSingularRule`, `AddUncountableRule`, `AddIrregularRule`. What makes `Singular` a pure function here is that knomit calls NONE of them: the only references to the package in the whole tree are `pluralize.NewClient()` in textnorm.go and one in its test. **Calling any Add*Rule at runtime would silently invalidate every memo entry minted before it, and nothing would report the divergence.** If a future change needs custom rules, they must be installed before the first Stem call and treated as part of the binary, not applied dynamically.

WHAT BOUNDS THE MEMO — not only the corpus. Request-supplied tokens reach it: `?domain=` flows through `splitCSV` → `SearchOptions.Domain` → `store.canonicalizeDomain`/`domainTokens`, and `?motifs=` through the motif-term tiers, both landing in `textnorm.Tokens`. So a caller can mint entries. Free-text search is NOT one of these paths — `opts.Text` goes to the embedder and never through textnorm.

CONSEQUENCE OF THAT BOUND — the buffer-pinning one, which is why the code clones. `Tokens` hands `Stem` a `strings.FieldsFunc` substring, which SHARES the canonicalized input's backing array. Storing it as-is would pin the whole canonical string for the entry's life, and `Singular` returning its argument unchanged (the common case, for an already-singular word) would pin it through the VALUE too. So `Stem` clones the key AND singularizes the clone. One token off a long `?domain=` would otherwise hold that entire value forever. The clone costs one allocation on a miss; the hit path stays at 0.

WHAT THIS DOES NOT MEAN: not that caching in general is now sanctioned at this layer — the argument turns entirely on Stem being pure, and does not carry to anything that reads corpus state. Not that the memo may be persisted later for a speed-up; that is option 2, rejected on correctness. And not that a benchmark's exact warm ns/op is a contract — that figure moves run to run, and an earlier revision of this work recorded run-to-run noise (21 vs 14 ns/op) as if it were a result; the benchmark comment now records orders, with the ALLOCATION counts as the part pinned exactly.
