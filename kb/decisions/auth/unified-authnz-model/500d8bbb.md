# Decided (user, 2026-11-09): replace every current authn/z mechanism with ONE model — authenticated principal → instance-wide roles (fixed seeded set) → materialized permission policy, every gate is policy.Has(perm); no trust by peer address or Via, one HTTP port, single-tenant owner = server's own uid/SID on the socket

STATUS: design APPROVED, NOT YET BUILT. As of this decision the code at HEAD 8024d51b still implements the OLD model (loopback anonymous trust, Via gates, per-permission grants, separate [oauth].addr listener). Do not read this fact as describing current behaviour; it records what was chosen and why. It supersedes, once built, the earlier phased-auth decisions (phase-order-core-socket-first, third-listener-401-is-narrow). Design doc: .claude/plans/2026-11-09-unified-auth-design.md with its cited inventory .claude/plans/2026-11-09-authz-obsolete-inventory.md (local working files).

OPTIONS CONSIDERED: (1) keep the third OAuth listener because loopback TCP carries anonymous admin (loopback_default) and a same-host proxy looks local; (2) all HTTP authenticated, socket/pipe identified by kernel peer creds, so OAuth can share the main port; (3) split API into admin/non-admin with non-admin open by default — rejected as default because anonymous kb:write through a proxy lets anyone plant facts agents trust; (4) a per-connection ceiling / step-down / step-up 'permission mode' for same-uid processes — rejected: a same-uid process can read the data dir anyway, and kb exposes only kb:read/kb:write MCP tools; (5) multi-user accounts with linked identities — rejected: knomit is single tenant; (6) user-defined roles in config — rejected.

RATIONALE: today access is two systems mixed — permissions and trust-by-how-you-connected — and the second leaks into the first (socket callers skip admin, push needs a cert regardless of grants, fleet ignores permissions, read is unchecked on the main port, merge:main enforced nowhere). Peer-address trust is what forced a separate OAuth listener; removing it lets every channel share one port.

THE CHOICE (all components, none optional):
- Principals: os:uid:<n>/os:sid:<SID> (socket/pipe peer creds); token:<id> + label (each PAT or OAuth family is its own principal with EXACTLY ONE role); node:<fp> (mTLS); anonymous.
- Owner = the os principal whose uid/SID equals the server's; implicit, all permissions, unrevocable, no modes. Other uids INCLUDING root/SYSTEM: authenticated, no roles until bound. Anonymous: nothing by default (bindable, e.g. reader for a public demo). Socket stays owner-only for now.
- Roles fixed, seeded in DB at boot (Go, not SQL migration): owner, admin, operator, contributor, reader, node. Bindings instance-wide.
- Permissions are a code registry, every route/MCP tool declares one, undeclared = denied: kb:read, kb:write, repo:push (node only), repo:manage, repo:origin, ops:run, secret:manage, auth:manage, fleet:manage; merge:main and push:own removed.
- Chat: a reader CAN chat (routes need kb:read) but every MCP tool call inside chat is checked against the caller's own policy.
- TLS certificates are for nodes only: a fleet-root-signed INSTANCE cert (agent email SAN) = node role on every member; any other root-signed cert (former operator cert) is refused.
- Browser: web UI is an OAuth client of knomit's own AS; login by socket handoff link, pairing (variant B: new browser shows a code, owner approves from a logged-in session or the CLI over the socket), optional passkeys. No OS-password login. Social/OIDC login deferred; the existing GitHub-IdP approval path ([oauth.idp], idpflow) is REMOVED; the 2026-11-08 GitHub-account project is revised after this model is built.
- Agents: socket locally; remote via OAuth (scopes are role names, never admin) or personal access tokens (required expiry).
- CLI: knomit oauth + knomit grants merge into knomit auth (pending, approve, deny, link, sessions, tokens, roles); no aliases; roles go through the server, not control.db.
- No config switch disables auth; tests bootstrap over the socket.

NON-SCOPE: does not authorize per-repo/lens role bindings, multi-user accounts, user-defined roles, or opening the socket to other uids — all deferred. Does not mean a same-uid process is restricted: owner is total by design.
