# The loopback Host check sits INSIDE AuthMiddleware's anonymous branch, not in a separate middleware in front of it — a second classifier of 'is this plain TCP, not a peer, not TLS' would drift from AuthMiddleware's own

OPTIONS (#281 RCA, item 5; the issue text itself proposed 'one middleware installed above AuthMiddleware'):
- (a) inside apiRouter;
- (b) a separate middleware in Server.Handler() above AuthMiddleware;
- (c) inside AuthMiddleware's anonymous branch, before auth.WithPrincipal.

CHOICE: (c). The user approved it on 2026-09-25, as a deviation from the issue text that the master put to the user.

RATIONALE:
- One Handler() serves the plain, socket and TLS listeners. A check placed in front of AuthMiddleware (b) would have to re-derive which listener the request came in on, i.e. not a kernel peer and not TLS, duplicating AuthMiddleware's first two branches. Two classifiers of the same thing drift: a new listener or principal kind added to one is missed by the other, and the check then fires on a socket client (`knomit oauth` sends Host: knomit.local) or misses a new path to anonymous.
- Inside the branch, the classification is already done, and the check runs exactly when anonymous@none is about to be minted.
- (a) was rejected outright. It misses /git, /docs and the SPA on the outer router, and it runs on the OAuth listener, where a same-host TLS proxy legitimately sends the public issuer Host from loopback.

NON-SCOPE: this does not make AuthMiddleware the home for other request validation. The check belongs there only because it is a precondition of minting that one principal. CSRF (#287) is a different mechanism and is not decided here.
