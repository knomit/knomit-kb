# Windows's local authenticated listener is a NAMED PIPE, not AF_UNIX — Windows does accept net.Listen("unix"), but AF_UNIX there has no SO_PEERCRED equivalent, so it could vouch for nobody

The local authenticated listener on Windows is a named pipe at `\\.\pipe\knomit-<8 bytes of SHA-256 of the data root>`, opened by auth.ListenLocal and dialled by auth.DialLocal.

Options considered and rejected:

- **AF_UNIX on Windows.** Windows 10 1803+ genuinely accepts net.Listen("unix", ...), and it would have needed no new dependency and no per-platform listener. REJECTED because there is no SO_PEERCRED equivalent for AF_UNIX on Windows: the socket would have carried NO verified identity while the code looked cross-platform. THE TRAP WORTH REMEMBERING: the transport ports, the CREDENTIAL does not.
- **A token file in the data root.** REJECTED: it reintroduces a stored secret, which the socket path exists to avoid, and its ACL would do the pipe ACL's job with an extra thing to leak.
- **A named pipe.** CHOSEN. ImpersonateNamedPipeClient plus GetNamedPipeClientProcessId give a kernel-verified SID and pid — the same SHAPE of answer SO_PEERCRED gives on Linux, which is what lets one Principal type cover both.

Consequence: on Windows a local bridge is `bridge:sid:<SID>@pipe`, and nothing is stored or presented to earn it.
