# ON UNIX, whether the local socket's owner is alive is decided by an exclusive flock on <path>.lock held for the listener's life, NEVER by dialing the socket, because a saturated live listener refuses connects exactly like a stale file — Windows needs none of this and has no lock file

SCOPE: everything below is the UNIX half of auth.ListenLocal (internal/auth/listen_unix.go). The Windows half needs none of it — see the last paragraph.

CONTEXT: after F19 phase 1c, BOTH `knomit serve` (cmd/serve.go) and the desktop app (tools/desktop/boot.go) open the same unix socket path, `<data root>/knomit.sock`, through `auth.ListenLocal`. Something has to decide, before binding, whether the thing already at the path belongs to a LIVE instance or is a leftover.

OPTIONS CONSIDERED:
1. Unconditionally remove the path before listening — what phase 1 did inline in cmd/serve.go.
2. Dial the path first and treat ECONNREFUSED or ENOENT as stale.
3. Take an exclusive non-blocking flock on `<path>.lock`, held for the listener's life.

WHY NOT (1): once both binaries open the same path, a second knomit process silently unlinks a live instance's socket and every bridge that dials afterwards lands on the thief. Nothing fails; bridges just move.

WHY NOT (2): a dial cannot tell a SATURATED live listener from a stale file. A live listener whose accept backlog is full refuses new connects with ECONNREFUSED on darwin (EAGAIN on linux) — the same answer a crashed server's leftover socket gives (reproduced on darwin 2026-09-22). A probe therefore steals exactly the busiest server's socket. And the stale set is not enumerable anyway: a regular file or a directory at the path dials ENOTSOCK, a live socket this uid cannot reach dials EACCES, so every error needs its own ruling and each ruling is a guess.

CHOSEN: (3). The kernel releases a flock on ANY exit of the holder, graceful or crash, so "lock held" is exactly "owner alive" and "lock acquired" is exactly "whatever sits at the path is a leftover — remove it". Lock held -> `ErrSocketInUse`, the path is untouched, and the caller logs WARN and serves TCP only (never fatal on that ground alone; see the require-needs-a-bound-listener invariant for the one case that does fail the boot). Any other error from open or flock is a real error.

LOAD-BEARING DETAILS, ALL UNIX-ONLY, each of which a tidy-up would break:
- `syscall.Flock`, NOT fcntl `F_SETLK`. fcntl locks are per PROCESS, so a second `ListenLocal` in the same process would succeed; flock locks belong to the open file description, so it is refused. The in-process live-owner tests only mean something because of this.
- Cleanup NEVER unlinks `<path>.lock`; it only closes the descriptor. Unlink-and-recreate lets two processes each lock a DIFFERENT inode and both believe they own the socket. The leftover .lock file is inert without a holder.
- Cleanup releases the lock LAST, after unlinking the socket, so a successor that acquires the lock can never have its fresh socket unlinked by the departing owner.
- The cleanup closure is what keeps the lock file reachable. A caller that drops it lets the GC finalizer close the descriptor and release the lock while the listener is still serving. Conversely a caller that never CALLS it keeps the lock after its listener is gone: the desktop's `server.shutdown` must call `closeSocket`, because `http.Server.Shutdown` alone unlinks the socket file but does not release the lock, and a relaunch (`RestartApp`) would then find it held and serve TCP only.

TESTS THAT PIN IT — all now in internal/auth/listen_unix_test.go, which is build-tagged `!windows`; internal/auth/listen_test.go holds only the platform-neutral `TestListenLocal_EmptyPathIsNoop`. `TestListenLocal_RefusingLiveOwnerIsNotStolen` — the owner keeps its lock (cleanup not called), closes its listener with `SetUnlinkOnClose(false)` so the file stays and every dial is refused (asserted, as a fixture check), then a second ListenLocal must return `ErrSocketInUse` and the path must be the SAME inode via `os.SameFile`. This is what a dial probe sees from a saturated server, reproduced deterministically on every unix. It replaced an earlier fixture that SATURATED the accept backlog by dialing: that only works where somaxconn is small (darwin 128) and failed on linux (4096), and a dial failing with EMFILE could pass it for the wrong reason — the platform-specific-fixture shape. `TestListenLocal_LiveSocketIsNotStolen` asserts the same inode for an accepting owner. Making `lockExclusive` always succeed fails both live-owner tests. `TestListenLocal_StaleSocketIsReplaced` proves replacement by BEHAVIOUR — before, a dial gets ECONNREFUSED; after, the new listener's Accept receives a dial with PeerCred ok — NOT by comparing inodes, because ext4 reuses the freed inode for the new socket (see the inode-reuse gotcha). The desktop's `TestBootServer_OpensLocalSocketWithPeerCreds` (now tools/desktop/boot_socket_unix_test.go) takes the path with a successor ListenLocal after `shutdown()`, and deleting `s.closeSocket()` fails it.

THE WINDOWS COUNTERPART, added by knomit#245: there is no lock file and nothing to restore, because a pipe NAME cannot outlive its owner — the kernel reaps it with the process — and winio.ListenPipe creates the first instance with the FILE_CREATE disposition, so the OS itself refuses a second listener on a live name (ERROR_ACCESS_DENIED, mapped to the same `ErrSocketInUse`). Do not go looking for `<path>.lock` on Windows, and do not port these details there.

NON-SCOPE, the misreading to avoid: this does NOT make the socket path, or the .lock file, a general mutex between knomit processes. It protects ONE path from two listeners and nothing else — two instances still both run, both serve TCP, and share the data root exactly as before. Do not reach for the .lock file to serialise anything else.
