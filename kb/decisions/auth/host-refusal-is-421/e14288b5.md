# A loopback request refused for its Host gets 421 Misdirected Request, not 403 — the 403 titles 'Authentication required' and 'Permission denied' are what clients key on, and a wrong authority is neither

OPTIONS:
- (1) 421 Misdirected Request with a problem+json body titled 'Misdirected Request';
- (2) 403 with a new, third title.

CHOICE: (1). The user approved it on 2026-09-25 with the #281 proposal.

RATIONALE:
- AuthMiddleware's contract (its doc comment) is that knomit's 403s are told apart by TITLE: 'Authentication required' when there is no principal, 'Permission denied' when a principal lacks the permission. Clients and tests key on those titles.
- A request naming a Host this server does not answer for is not an authorisation outcome; no principal was ever considered. 421 (RFC 9110 §15.5.20) says what is true: the server is not able to produce a response for that authority.
- The detail names the refused Host and the fix: add it to [auth].loopback_hosts, knowing that anyone reaching knomit through that name then holds loopback_default.

COST ACCEPTED: the phase-3b approval gate still answers 403 for the Host classes only it refuses (a non-arrival port, other loopback IP literals), because that is a permission decision. So two statuses exist for 'bad Host' depending on which check fires. Five TestBrowserGate_EachMissingProofRefuses rows therefore expect 421.

NON-SCOPE: this does not change any existing 403; the TLS listener's and require=true's refusals stay 403 'Authentication required'.
