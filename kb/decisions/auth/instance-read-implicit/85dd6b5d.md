# An instance certificate that chains to the fleet root holds `read` and `push:own` IMPLICITLY and nothing else — the chain is admission (push:own added by the F11 ruling) — while every further permission, and everything an operator certificate holds, is a grants row keyed by the full-fingerprint principal

DECIDED (master ruling 5, F19 phase 2, 2026-09-22); AMENDED for `push:own` by the user's F11 ruling (2026-09-28). A certificate chained to the fleet root is fleet ADMISSION — it replaces F10's admitted-fingerprint list — so an instance that presents one holds `read` with no grants row, and, since F11, `push:own` too. It holds nothing else by default: `write`, `merge:main`, `operator`, `admin` are grants rows for `instance:<64-hex fp>@cert`, added with `knomit grants add`.

THE F11 AMENDMENT. Asked "Does every enrolled instance get to push its own branch to this one, or only instances you grant it to?" — with the reversal of this decision named — the user answered "1. A" (every enrolled instance, automatically). The line ruling 5 drew was that the chain is admission, not authorisation to act; `push:own` crosses it deliberately because the only thing it lets a peer do is update ITS OWN agent branch on this host (receive-pack refuses everything else), and a per-peer grant was a step every operator would always take. The rejected alternative was a per-peer `knomit grants add instance:<fp>@cert push:own`. Consequence for tests: like the implicit `read`, the implicit `push:own` makes the receive-pack path's push:own check unobservable as a separate refusal for instance principals; `TestFleetOrigin_PeerPushesOwnBranchOverKnomitHTTPS` pins the wiring (drop PushOwn from CertGrants and it goes red).

HOW, and why this shape: `auth.CertGrants{Store}` returns `{read, push:own}` merged with the store's rows for `KindInstance` + `ViaCert` + non-empty ID, and the store's rows alone for everyone else. `Server.grants()` builds `loopbackGrants{anon: …, store: CertGrants{Store: s.Grants}}`, so BOTH enforcement points (writeGate and the MCP gatePermission/permissionFilter) consult the same answer, and `auth.Allowed` stays the only check (kb/invariants/auth/one-principal-one-check). It is deliberately NOT a shortcut in AuthMiddleware: the middleware decides WHO, never WHAT.

COMPOUND CONDITIONS worth stating in full:
- Only an INSTANCE via a CERTIFICATE gets it. An operator-role certificate maps to `operator:<fp>@cert` (pki.IdentityOf reads the role from the SAN) and holds exactly its rows — no implicit read. `instance:<fp>@token` would not get it either.
- A grants STORE ERROR denies even the implicit read (CertGrants returns the error; Allowed denies), matching default-deny-on-error.
- There is nothing to revoke on this side: a revoked certificate never reaches a Grants lookup because the TLS handshake refused it. Hence `knomit grants revoke <instance> read` is refused with an explanation pointing at `knomit identity revoke`.

CONSEQUENCE a consumer must act on: in phase 2 NOTHING enforces `read` — a request that reached the server has passed the transport boundary — so no HTTP or MCP test can observe a missing CertGrants. `TestServerGrants_WrapTheStoreInCertGrants` pins the wiring directly (sabotage-checked). If a later phase adds the first `read` enforcement point, this implicit read is what keeps enrolled instances from being locked out.

MISREADING TO AVOID: 'the TLS listener serves reads to instances' is true but is not what this fact grants — the TLS listener refuses any request with no certificate principal regardless of grants (never anonymous); CertGrants answers what a principal that got in may DO.
