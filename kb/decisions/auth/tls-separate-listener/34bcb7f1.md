# Mutual TLS runs on a SEPARATE port with its own http.Server over the same handler, off until [tls].addr is set and a certificate is installed — not on the plaintext port, not by protocol sniffing — and only `knomit serve` opens it; the desktop app does not

OPTIONS (master ruling 1, F19 phase 2, 2026-09-22): (a) turn the existing TCP port into TLS once a certificate is installed; (b) sniff TLS vs plaintext on one port; (c) a separate TLS listener on its own port. CHOSEN: (c).

WHY: (a) breaks every plaintext client on the port the day a certificate lands — the bridge's TCP fallback (`knomitapi/dial.go` speaks http://), the desktop lockfile consumers, the web UI, and every `curl` and `git clone http://…/git` in docs. (b) is more machinery for no gain. (c) is purely additive: nothing about the plaintext port changes, which the end-to-end test asserts as its positive control.

SHAPE: `[tls].addr` (env KNOMIT_TLS_ADDR, default EMPTY = off) and `[tls].dir` (env KNOMIT_TLS_DIR, default `<home>/pki`, set in config.Load after tilde expansion — the one definition of that default). `cmd/serve_tls.go` `openTLSServer` returns a SECOND `http.Server` sharing the plaintext server's Handler, timeouts and BaseContext, with `ConnContext: auth.TLSConnContext` and a zerolog-backed ErrorLog; `serve.go` serves it and shuts it down beside the plaintext one. Three outcomes: addr empty → off silently; addr set but no instance.crt → WARN 'run `knomit identity install`' and plaintext only (so configuring early is harmless); certificate installed but unloadable (CRL missing/malformed, older than crl.number, certificate for another key) → FATAL, fail closed. The certificate must wrap the key `App.KeyPath()` returns — the same file app.New resolved.

WHY A SECOND SERVER rather than a second listener on the same server: the marker that tells AuthMiddleware a request came in on the TLS listener comes from the server's ConnContext, and wrapping the conn instead breaks r.TLS (see the linked gotcha). Measured by sabotage: giving the TLS server the plaintext ConnContext made a LOOPBACK peer the anonymous principal, and its POST reached the handler past the write gate — the listener's 'never anonymous' rule depends on this wiring.

DISTINCT FROM the unix-socket rule (kb/invariants/auth/local-listener-single-site): that one says BOTH binaries must open the socket; this listener is deliberately opened by `knomit serve` ONLY. `tools/desktop/boot.go` builds its own server and binds loopback only, so it is never a peer's target; whether the desktop should ever be a fleet peer is a product question left to the user. auth.ListenTLS is the shared helper so wiring it into bootServer later is one call. MISREADING TO AVOID: 'phase 2 adds mTLS' does not mean a desktop-served machine accepts peers — it does not.
