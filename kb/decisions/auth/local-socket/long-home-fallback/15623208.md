# A data root too long for sun_path gets /tmp/knomit-<euid>/<8 hex of sha256(Clean(root))>.sock — the LITERAL /tmp, never TMPDIR/XDG_RUNTIME_DIR/os.TempDir, computed in config.localListenerName so server and bridge cannot disagree

knomit#253: a `KNOMIT_HOME` long enough that `<home>/knomit.sock` does not fit in `sockaddr_un.sun_path` made every listen EINVAL, and `knomit serve` was fatal on it.

THE RULE, in `config.localListenerName(home)` on unix: `p := filepath.Join(home, "knomit.sock")`. If `len(p) < auth.SunPathCap()` it returns `p`, byte-identical to before. Otherwise it returns `filepath.Join(auth.FallbackSocketDir(), hex(sha256(filepath.Clean(home)))[:8] + ".sock")`, i.e. `/tmp/knomit-<euid>/xxxxxxxx.sock`, about 30 bytes.
- `auth.SunPathCap()` is `len(syscall.RawSockaddrUnix{}.Path)`: 104 darwin, 108 linux, never typed. `>=` is exactly where Go's `net.Listen` refuses on BOTH platforms, which is the right boundary because knomit listens through `net.Listen`. `TestListenLocal_PathLengthBoundaryIsTheSunPathCap` asks `net.Listen` on every run, which is what makes a mistyped cap fail in either direction.
- TWO LAYERS, and they differ on BOTH platforms. The KERNEL would bind an unterminated path of exactly `len(sun_path)`: 104 bytes on darwin (a raw C bind(2) on macOS 26.6.2 succeeds and stat shows the socket under the full name) and 108 on linux (raw C bind(2) in golang:1.26 linux/arm64). Both measurements were made by the #268 reviewer. Go refuses that length before any syscall, in `syscall_bsd.go` (`n >= len`) and `syscall_linux.go` (`n == len` for a non-abstract name), and net reports it as "bind: invalid argument". So a path of exactly the cap never binds through Go on either platform, before this PR or after, and the fallback costs nothing there.
- HOW BOTH SIDES GET HERE: the server's `config.Load` and the bridge's `config.SocketPath` both start from `config.homeAndConfig` (ResolveHome, then expandTilde, then filepath.Abs, then `<home>/knomit.toml`). They then call `config.socketFor(home, fromTOML, os.Getenv("KNOMIT_SOCKET"))`. This function is socketFor's DEFAULT layer, reached only when neither KNOMIT_SOCKET nor the knomit.toml `socket` key is set. See the listener-layering invariant. `knomitapi.SocketPath` only delegates to `config.SocketPath`.

OPTIONS REJECTED (worker D7, reviewer B5/B6, master ruling E3, 2026-09-23):
- `os.TempDir()` or `$XDG_RUNTIME_DIR`: environment-dependent. The bridge can run with a filtered environment (an MCP host spawns it), so the server and the bridge would compute DIFFERENT paths and the bridge would silently fall back to TCP, losing the verified identity. No single-process test can see that.
- Failing the boot on a long root: the old behaviour, which the issue exists to remove.

CONSEQUENCES:
- /tmp is shared, so the directory is used only under the private-dir invariant (0700, owned by euid, checked on both sides). A squatted `/tmp/knomit-<euid>` therefore makes a long-root server serve TCP only, and REFUSE TO BOOT under `[auth].require = true`. That is the intended fail-closed trade. The remedy is a shorter root or an explicit `socket`.
- The root is `filepath.Clean`ed before hashing, so `home`, `home/` and `home/.` share a socket. Since knomit#274 (PR #293) the root that reaches this function is also ABSOLUTE: homeAndConfig makes it so. A relative KNOMIT_HOME therefore hashes its absolute form, resolved against the reading process's cwd.
- An EXPLICIT `socket` (knomit.toml) / `KNOMIT_SOCKET` bypasses this function on both sides. It must be absolute, or socketFor refuses it on both sides. An overlong explicit path reaches `ListenLocal`, which refuses it with `ErrPathTooLong` (WARN, TCP only). Since knomit#271 the bridge honours those overrides too; before it, the bridge ignored them.
- Windows is untouched: a pipe name has no length cap.

WHAT THIS DOES NOT MEAN: not that `SunPathCap` is the KERNEL's limit on either platform. It is `net.Listen`'s. A measurement names the layer it went through: an EINVAL seen through `net.Listen` reports Go's check, not bind(2). During #268 a `net.Listen` measurement was briefly misread as "the linux kernel refuses 108"; the review caught it with a raw C bind(2).
