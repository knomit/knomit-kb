# Decided (knomit#265, 2026-09-27): on Windows the local listener's pipe names its owner in the SDDL (O:<user SID>) and auth.DialLocal verifies the pipe's OWNER from the dialled handle before a byte is written, accepting the caller's SID, SYSTEM and BUILTIN\Administrators; anything else is ErrForeignListener, which the bridge treats as a FAILURE, not as 'no listener' with a TCP fallback; the server token-user route and a certificate were rejected for this step

**Context.** \\.\pipe\ is world-creatable, so another local process can hold knomit-<hash> before knomit boots. The server notices (ErrSocketInUse) but with [auth].require=false serves TCP only, and the bridge that dialled the squatter gets no signal. Measured (worker, 2026-09-26): in every squat scenario the squatter accepted the connection and read the full HTTP request, `Authorization: Bearer` included; what flows is every MCP tool call and fact body, the client identity header, and, back, whatever the squatter answers goes to the agent's stdout and gets injected as facts by the hooks client. `knomit oauth approve|deny` on the same pipe could be faked. There are exactly two production dial sites: tools/bridge/knomitapi/dial.go and cmd/oauth.go. This decision is the WINDOWS dial-side counterpart of the unix rule in kb/invariants/auth/local-socket/fallback-dir-private (DialLocal refuses a fallback socket directory the user does not own): on unix the DIRECTORY vouches for the server, on Windows the pipe's OWNER has to. The listen side (liveness lock, single open site, the two require checks) is unchanged.

**Options.** (a) Owner check from the handle: `GetSecurityInfo(handle, SE_KERNEL_OBJECT, OWNER_SECURITY_INFORMATION)` returns the pipe's owner atomically on the conn we already hold; READ_CONTROL is inside the GENERIC_READ DialLocal asks for, so a squatter that withholds it makes the dial itself fail. CHOSEN. (b) Server token user: GetNamedPipeServerProcessId -> OpenProcess(PQLI) -> OpenProcessToken -> GetTokenUser; works, even unelevated client to elevated server, but has a PID-reuse race and more handles; rejected for now. (c) A certificate: the thorough answer, phase 2 material; not this step. (d) Do nothing: leaves the exposure above.

**Why O: in the SDDL.** Without an O: part the pipe's owner is the creating token's TokenOwner, which for a UAC-elevated server (the desktop on an admin account) is BUILTIN\Administrators, the same as #301's directory finding; a naive 'owner == my SID' check would reject the real desktop. A token may always assign its own user SID as owner, so `O:<sid>` is accepted from an elevated token and yields the user (measured).

**Why the accepted set is {own SID, SYSTEM, Administrators}.** A knomit run as a service produces a SYSTEM-owned pipe; a pre-upgrade elevated server produces a BA-owned one. A non-admin other user can produce neither (setting an owner you do not hold needs SeRestorePrivilege or SE_GROUP_OWNER on that group), and local admins are out of scope by the project's stated threat model. A same-user squatter cannot be told apart by any SID check; that is the unix same-uid boundary.

**Why no TCP fallback on ErrForeignListener.** The bridge's existing fallbacks are for a MISSING listener (debug) and an UNREACHABLE one (one warning): both mean 'no server on the pipe'. A foreign owner means an active process on our name; falling back would hand the same traffic to TCP, where the server's identity is not verified either. The request fails with a message naming the owner and the escape hatch (an explicit URL argument or KNOMIT_BASE_URL skips the pipe) for the one legitimate case, a server under a non-SYSTEM service account.

**What this does NOT mean.** It does not defend against a squatter running as the same user, nor against a local Administrator. The cross-user owner outcome is inferred from how the kernel assigns owners (measuring it needs a second account; the session's permission did not allow staging a LOCAL SERVICE probe). Unix is unchanged beyond the existing fallback-dir check: the socket's directory (privdir 0700 root, or the owner-checked 0700 fallback dir) gates creation, so no owner check is needed there; a client-side SO_PEERCRED check would be parity polish.
