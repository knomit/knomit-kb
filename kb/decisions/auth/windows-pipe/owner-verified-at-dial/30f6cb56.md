# Decided (knomit#265, 2026-09-27): on Windows the local listener's pipe names its owner in the SDDL (O:<user SID>) and auth.DialLocal verifies the pipe's OWNER from the dialled handle before a byte is written, accepting the caller's SID, SYSTEM and BUILTIN\Administrators; anything else is ErrForeignListener, which the bridge treats as a FAILURE, not as 'no listener' with a TCP fallback; the server token-user route and a certificate were rejected for this step

**Context.** \\.\pipe\ is world-creatable, so another local process can hold knomit-<hash> before knomit boots. The server notices (ErrSocketInUse) but with [auth].require=false serves TCP only, and the bridge that dialled the squatter gets no signal. Measured (worker, 2026-09-26): in every squat scenario the squatter accepted the connection and read the full HTTP request, `Authorization: Bearer` included; what flows is every MCP tool call and fact body, the client identity header, and, back, whatever the squatter answers goes to the agent's stdout and gets injected as facts by the hooks client. `knomit oauth approve|deny` on the same pipe could be faked. There are exactly two production dial sites: tools/bridge/knomitapi/dial.go and cmd/oauth.go. This decision is the WINDOWS dial-side counterpart of the unix rule in kb/invariants/auth/local-socket/fallback-dir-private (DialLocal refuses a fallback socket directory the user does not own): on unix the DIRECTORY vouches for the server, on Windows the pipe's OWNER has to. The listen side (liveness lock, single open site, the two require checks) is unchanged.

**Options.** (a) Owner check from the handle: `GetSecurityInfo(handle, SE_KERNEL_OBJECT, OWNER_SECURITY_INFORMATION)` returns the pipe's owner atomically on the conn we already hold; READ_CONTROL is inside the GENERIC_READ DialLocal asks for, so a squatter that withholds it makes the dial itself fail. CHOSEN. (b) Server token user: GetNamedPipeServerProcessId -> OpenProcess(PQLI) -> OpenProcessToken -> GetTokenUser; works, even unelevated client to elevated server, but has a PID-reuse race and more handles; rejected for now. (c) A certificate: the thorough answer, phase 2 material; not this step. (d) Do nothing: leaves the exposure above.

**Why the primitive is sound (review, 2026-09-27).** NPFS keeps the security descriptor on the pipe's FCB (the NAME), not per instance, and the client's open handle pins that FCB, so there is no dial/verify race and the server cannot swap it. go-winio sets the SD only on the FIRST NtCreateNamedPipeFile (FILE_CREATE); later instances (every Accept) use FILE_OPEN with no SD and inherit the FCB's: measured with a multi-accept listener and five dials, every instance read the same `O:<me>` descriptor. A NULL owner cannot occur (the object manager defaults it from TokenOwner) and is rejected anyway. A squatter can only set an owner its token may own: its own user, or BA when it is an elevated admin (SeRestorePrivilege is admin-equivalent).

**Why O: in the SDDL.** Without an O: part the pipe's owner is the creating token's TokenOwner, which for a UAC-elevated server (the desktop on an admin account) is BUILTIN\Administrators, the same as #301's directory finding; a naive 'owner == my SID' check would reject the real desktop. A token may always assign its own user SID as owner, so `O:<sid>` is accepted from an elevated token and yields the user (measured; see kb/gotchas/testing/windows/uac-token-owner-discriminator for which test sees it).

**Why the accepted set is {own SID, SYSTEM, Administrators}.** BA: a pre-#265 elevated server produced a BA-owned pipe, and only an elevated admin can produce one. SYSTEM: NOT because a knomit run as a service would be reachable (its pipe's DACL grants only its own SID and SY, so a user client gets access denied before any owner check), but because only admin-equivalent code can produce a SYSTEM-owned pipe, so accepting it costs nothing. Local admins are out of scope by the project's threat model. A same-user squatter cannot be told apart by any SID check; that is the unix same-uid boundary.

**Why no TCP fallback on ErrForeignListener, and its honest limit.** The bridge's existing fallbacks are for a MISSING listener (debug) and an UNREACHABLE one (one warning): both mean 'no server on the pipe'. A foreign owner means an active process on our name; falling back would hand the same traffic to TCP, where the server's identity is not verified either. The request fails, with one warning, and the BRIDGE (not auth) appends the escape hatch: name the server — kb's server argument, or KNOMIT_SERVER (which the hooks read too) — and the default-path pipe is skipped. (Until 2026-10-02 the hatch was the URL argument or KNOMIT_BASE_URL for the hooks client; that variable was retired with no alias. A NAMED local listener — KNOMIT_SERVER=npipe:////./pipe/<name> — is dialled through the same auth.DialLocal, so ErrForeignListener on it fails the request too, and it never falls back to TCP at all.) LIMIT (measured in review): a squatter that denies us READ_CONTROL or all access makes DialLocal fail with access denied, which is the existing 'unreachable' path and DOES fall back to TCP. So the no-fallback rule is a SIGNAL for the squatter we can see, not a boundary; the security property, that no byte reaches a foreign-owned pipe, holds either way. Treating access denied as suspicious was left optional: a server legitimately running as another account is also access denied, and today that falls back to TCP on purpose.

**What this does NOT mean.** It does not defend against a squatter running as the same user, nor against a local Administrator. The cross-user owner outcome is inferred from Windows semantics (measuring it needs a second account; the session's permission did not allow staging a LOCAL SERVICE probe). Unix is unchanged beyond the existing fallback-dir check: the DEFAULT socket under the data root (privdir 0700) and the owner-checked /tmp fallback gate creation, so no owner check is needed there; an operator-named KNOMIT_SOCKET or toml `socket` is only required to be absolute and is never owner-checked, the operator's choice. A client-side SO_PEERCRED check would be parity polish.
