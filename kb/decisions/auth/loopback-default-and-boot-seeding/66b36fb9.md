# A nil LoopbackDefault falls back to the defaults (a test convenience), and boot seeds the server's own socket uid ONCE PER PERMISSION — asking EverGranted, not For, so a restart never revives what an operator revoked

Two coupled choices about how a fresh knomit instance ends up usable.

ONE: a NIL `Auth.LoopbackDefault` in a `web.Server` literal falls back to `config.Defaults().Auth.LoopbackDefault`. The alternative — nil means deny — was rejected because 73 test files build a `Server` literal with no config, and there is exactly ONE production literal (`internal/app`). Touching 73 files would have bought no security. The COST of the fallback is real and has to be guarded: if the production literal ever stopped carrying `cfg.Auth`, every instance would silently fall back to the full default set and nothing would notice. `TestApp_AuthConfigReachesMiddleware` is that guard — it boots a real App and asserts BOTH halves of `[auth]` arrived, each through the handler. It needs two boots because the halves are mutually exclusive: with `require = true` there is no anonymous principal for a loopback default to apply to. Delete that test and the fallback becomes a hole.

Note the asymmetry deliberately: an EMPTY but present list (`loopback_default = []` in TOML) is honoured as "anonymous holds nothing". Only NIL falls back. An operator who writes an empty list means it.

TWO: boot grants the server's OWN socket principal (`bridge:uid:<server uid>@socket`) each permission in `loopback_default`, via `seedOwnUID`. That is what makes the local bridge work with zero configuration — it dials the socket, the kernel reports the uid, and the grant is already there. The OS user running the server is treated as its operator.

THE LOAD-BEARING DETAIL: seeding asks `EverGranted`, which counts rows live OR revoked, NOT `For`, which returns only live ones. A revoked row is HISTORY, not absence. Seeding on liveness would mean every restart silently undid an operator's revocation — the permission would look revocable and be unrevokable in practice, which is worse than having no revocation at all. This is why `grants.revoked_at` is a timestamp and a revoke is an UPDATE rather than a DELETE: the row has to survive to say "this was taken away on purpose".

A seed failure STOPS the boot rather than logging. A server that came up without its seed would look healthy and refuse every local write, which is harder to diagnose than not starting.
