# knomit's local auth credential is the unix socket itself: the kernel reports the peer uid, so nothing is stored, presented, or forgeable — and `require` defaults FALSE so loopback TCP behaves exactly as before

OPTIONS considered for authenticating the LOCAL bridge to the server: (a) issue the bridge a client certificate, (b) mint a bearer token at init and bake it into the scaffolded MCP config, (c) have the bridge dial a unix domain socket and read the peer credential from the kernel.

CHOSEN: (c), for phase 1. The rationale is that (a) and (b) both create a SECRET that has to be generated, stored somewhere on disk, rotated, and revoked — and whose leak is the whole compromise — to prove something the operating system already knows for free. On a unix socket the kernel answers "which uid is on the other end" and the answer cannot be forged by the peer, because the peer never says it. The file mode on the socket (0600) and the data root above it are then the entire access control.

MECHANICS worth knowing before touching this. The credential is readable only while the `net.Conn` is in hand, which is exactly once per connection, so it is captured in `http.Server.ConnContext` — before any request is read — and every request on that connection inherits it via `r.Context()`. Linux reads uid AND pid from one `SO_PEERCRED` getsockopt; darwin needs TWO calls, `LOCAL_PEERCRED` for the uid via `GetsockoptXucred` and a separate `LOCAL_PEERPID` for the pid, and a failure of the second is NOT fatal — the uid is the credential, the pid is only for the session trail. A non-unix connection yields ok=false, and callers must treat that as "no credential", NEVER as uid 0.

WHAT ELSE THIS DECIDED, and it is the part that makes the upgrade uneventful: `[auth].require` defaults FALSE. A loopback TCP caller with no credential becomes the ANONYMOUS principal holding `[auth].loopback_default`, which is every permission a local operator already had. Nothing an existing user does changes. Turning `require = true` is what makes the socket the only way in.

THE MISREADING TO AVOID: the socket is not "more secure transport". It is an IDENTITY source. A TCP loopback caller is still served — it just becomes anonymous rather than a named principal, and with `require = true` it is refused outright.

A side consequence that has already bitten once in this repo's history: the bridge must resolve the socket path through `config.SocketPath` rather than computing it. A bridge that derives a DIFFERENT path does not fail loudly — it finds no socket, falls back to TCP, and silently loses the verified identity, which is the entire feature.
