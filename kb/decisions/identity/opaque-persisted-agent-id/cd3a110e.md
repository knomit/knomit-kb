# The agent id is OPAQUE and persisted at first boot; the gate finds a signer's record by the commit author's id and requires the signing key to be on it; nothing parses the fp8 in the id

DECISION (F09 PR 5, user rulings 2026-09-27; D1 of the design).

USER, VERBATIM: "no, not magic parsing - the agent name should be considered opaque. Fetching the agent key should be based on the git commit author and/ or signer".
On a revision that claimed rotation leaves the id unchanged: "the agent id 'fp8' part currently is derived from the key, wouldn't rotation actually change it ? Therefore, how can we make the claim rotation will not change it ?"
D1: "re-creating control.db will be like a fresh start - set the agent id in control db, and so on".

OPTIONS REJECTED:
- Parsing the fp8 out of the author id and comparing it with the signer's fingerprint (PR 3's authorClaimRe). A 32-bit prefix, and it ties identity to one key.
- Option A: keep the fp8 comparison and let the id and branch change with every rotation (one branch per key, the record accumulating keys). Review found a rotated instance could not find its own record.
- Option B: pin the id to the FIRST key's fp8 and adapt the check to 'the record at the author's id holds the signing key'.
- Persisting the id at first REGISTRATION rather than first boot; and keeping today's re-derivation at every boot.

CHOICE: at first boot on the new binary the id is computed as before and written to control.db instance_identity; every later boot reads it (kb/invariants/identity/persisted-agent-branch/b05bdf65.md). The author id is the persisted agent_id, passed to every store (SetAgentID); no code derives it from the branch (PR #513, D18). The gate looks up the ONE active record at the author's id and requires the FULL signing key to equal its current key.

NON-SCOPE: the fp8 still appears in ids built at first boot (app.newIdentity); it is decoration, and nothing may start relying on it again. Deleting control.db is a fresh start: the instance re-registers.

UPDATE (PR #514, user ruling, verified at the merge commit): opaque still means never parsed, but the persisted id must be a VALID id: pki.ValidAgentID refuses an empty id, '+', '@', white space, control characters and any UPPER-CASE letter. repos.resolveIdentity validates a fresh id before it writes anything and validates a stored one at every boot; a stored id that fails stops boot with repos.ErrStoredAgentIDInvalid (a fresh start: stop knomit, delete control.db, start again; the instance mints a new lower-case id and re-registers). The stored id is NEVER rewritten or lowercased. The id is compared EXACTLY everywhere it meets another identity (the gate's record lookup, the leaf lookup, the audit, the fleet reader); nothing is case folded (kb/invariants/pki/agent-id-binding/efad10db.md). MISREADING: 'opaque' does not mean 'any string'.
