# Writes are gated by a branch write-eligibility classification (RepoInstance.WritableBranch) — v1 allowed only the repo's own agent branch; experiments widened it in PR #235, at that method and nowhere else

**Options considered:** (a) honor the URL/lens branch for writes unconditionally (symmetric with the Phase 0 read fix); (b) lens carries a WriteBranch setting; (c) hard-wire writes to the repo's own agent branch and strip branch from the write path; (d) keep the write plumbing branch-parameterized and gate writes behind a per-branch eligibility CLASSIFICATION.

**Rationale (stress test + user ruling 2026-07-16):** store.factIndex.writeFile mechanically commits to ANY branch, but two branch classes must never be authored directly: the consensus branch (bypasses reconcileAgentMerge and the watermark model) and other machines' agent/* branches (corrupts their watermarks). Option (a) is a correctness trap. Option (c) — the first draft of this decision — was overturned because it forecloses EXPERIMENTS: the planned future flow of forking a working branch from the agent branch, authoring facts there, reviewing, and merging back. The danger was never 'non-agent branch' per se — it is specific branch classes. So the policy is a classification, and the classification (not the plumbing) is the extension point.

**The choice:** classify each branch: own agent branch → writable; experiment branches forked from it → writable; consensus branch and foreign agent/* → NEVER. Write tools on a non-writable binding fail with a clear read-only-view error (the MCP twin of internal/web/readonly.go's non-live-views-are-read-only invariant). writeFile KEEPS its branch parameter. Reads honor any branch.

THE SEAM: there is no free function `writableBranch(ri, branch)`. The classification is the EXPORTED method `RepoInstance.WritableBranch(branch) bool` (internal/repos/instance.go), and the binding-level gate is `Binding.writeOK`, set at construction from it and read via `Binding.WriteOK()`. Grepping for the lowercase free function and finding nothing does NOT mean the classification was never built.

**THE PROMISE WAS KEPT (PR #235, 2026-09-20).** Experiments widened `WritableBranch` itself — one added class, an `exp/*` branch whose recorded parent is this instance's current agent branch — and touched NO call site, which is what this decision predicted the extension point would buy. See invariants/repos/experiment-eligibility for the widening's own trap (both sides of the parent comparison must be guarded non-empty, or a subscription makes every experiment writable) and invariants/repos/write-branch-threading for the companion question this decision did NOT answer: WriteOK says whether a write may happen, and `Binding.WriteBranch()` now says where it LANDS.

**THE LENS HALF (PR #236).** v1 said named lenses write to the write repo's agent branch with no WriteBranch column. That rule STANDS, and the PR-2 work is deliberately narrow around it: a lens may pin its write member at the consensus branch FOR READS and stay writable at that member's agent branch, so `writeOK` and `WriteBranch` consult the pin ONLY when it is an experiment that member may author — `NewBindingOfLensOnExperiment` re-pins that one ReadTarget and leaves every other mount byte-identical. Deriving `writeOK` from the pin unconditionally would turn every read-pinned lens silently read-only, which is the regression this narrowness exists to prevent; a test for it is unreachable unless the write member is pinned EXPLICITLY in Reads, because Lens.normalize gives an unpinned write member the agent branch and the obvious test then passes for the wrong reason. There is still no WriteBranch COLUMN on a lens: the redirect comes from the caller's handle or from the URL, never from the lens definition.

**Still out of scope here:** the experiment lifecycle itself (fork, commit, sync, rollback, expiry) — that is the store's, recorded in its own facts.
