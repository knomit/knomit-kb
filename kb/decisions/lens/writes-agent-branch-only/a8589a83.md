# Writes always target the write repo's OWN agent branch; no write-branch config; non-agent-branch bindings are read-only views

**Options considered:** (a) honor the URL/lens branch for writes too (symmetric with the Phase 0 read fix); (b) lens carries a WriteBranch setting (RFC revision 3 as first drafted); (c) writes always go to the write repo's own agent branch — no write-branch configuration anywhere; bindings on non-agent branches are read-only views.

**Rationale (stress test 2026-07-16):** store.factIndex.writeFile mechanically commits to ANY branch, but the sync model does not tolerate it: agent watermarks (writeAgentBase) and reconcileAgentMerge assume facts are authored on the repo's own agent branch. Authoring directly on main bypasses reconciliation into consensus; authoring on another machine's agent/* branch corrupts that machine's watermarks. So option (a) is a correctness trap and option (b) is dead config that could only ever hold one safe value.

**The choice:** Write tools (learn/update/retract/hypothesize/review) always operate on b.write @ ri.AgentBranch(). Lens has NO WriteBranch field (schema: lenses table has no write_branch column). Binding carries writeOK: for a lens-of-one, writeOK = (urlBranch == ri.AgentBranch()); when false, write tools fail with a clear read-only-view error — the MCP twin of the web UI's non-live-views-are-read-only invariant (internal/web/readonly.go precedent). Reads honor any branch (the Phase 0 branch-honoring fix applies to reads). Bridge compatibility unaffected: knomit-bridge already discovers and pins the agent branch in the URL it builds.

**Non-scope:** Does not restrict which branches can be READ — any branch remains a valid read view; only authoring is pinned.
