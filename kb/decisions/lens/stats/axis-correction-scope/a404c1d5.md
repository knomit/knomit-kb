# The lens stats axis correction is a SECOND fan-out, it fires in the normal case, and only Highlights is axis-dependent — so it must re-fetch highlights alone

`GET /lenses/{lens}/stats` fans out TWICE. The second pass is correct and stays: store.Stats cuts each mount's top-N by NormalizeAxis(requested, THAT MOUNT's own default), so when the caller names no axis and mounts disagree about theirs, every mount's highlights were cut by a different ruler than the union ranks by; pinning them all to the resolved POOLED axis and re-fetching is the fix for that. Both conditions in full: (1) the caller sent no axis= AND (2) the mounts' default axes differ.

Two things about it are easy to get wrong.

FIRST — it is the NORMAL case, not an edge case. Mounts disagreeing is ordinary (in the reference corpus core and agentic-engineering default to impact; knomit-kb, knomit-io-kb and test to confidence) and the UI sends no axis. Every lens open paid it, and it grows with mount count exactly like the pass it duplicates.

SECOND — only `Highlights` and `HighlightsFallback` are axis-DEPENDENT. The count, average confidence, both json_each histograms, the type counts and the separation counters are axis-independent and already summed from the first pass. Re-running the whole Stats recomputed all of them to use none of them: instrumented on a 5-mount lens, pass 1 (Stats+Activity) was 43.2 ms, pass 2 was 37.0 ms (44% of an 84 ms request), and the highlights inside pass 2 were 10.6 ms.

Decision: a narrow provider method — `FactQuery.Highlights` — that calls the SAME `fq.highlights` implementation Stats calls (one query, two callers, agreement by construction; a second full fan-out fails the stub-counter test). Do NOT give it its own implementation. A parallel implementation would be free to drift in the one place nothing would notice, because the corrected rows ARE the rows the reader sees.

Unlike Stats, the narrow call uses the axis it is GIVEN and does not fall back to the branch's own default — the caller asks precisely to pin a mount to an axis it did not choose, so re-deriving one would undo the correction. Normalising is the caller's job. Dropping NormalizeAxis on that path is safe because AxisFromSeparation returns only recognized axis constants.

To tell whether the corrective pass is what you are measuring, pass an explicit `?axis=`: that skips it entirely, and is the control (48.7 ms against 87.6 ms bare, before the fix). Post-fix the bare request is 52.4 ms and the pinned one is unmoved — a change that speeds up the pinned-axis number is measuring something else.

WHAT THIS DOES NOT MEAN: it does not make the correction free (it is still a second highlights fan-out), and `?axis=…` requests skip the correction entirely.
