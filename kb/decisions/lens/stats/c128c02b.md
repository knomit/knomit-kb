# The lens stats axis correction is a SECOND fan-out, and it must fetch only highlights — mounts disagreeing on default_axis is the normal state, not an edge case

GET /lenses/{lens}/stats with no explicit axis runs the per-mount Stats+Activity fan-out, elects a lens-wide rank axis, and — when mounts DISAGREE about their own default_axis — runs a corrective second pass at the elected axis. Both conditions in full: (1) the caller sent no axis= AND (2) the mounts' default axes differ. At any realistic mount count some mounts default to impact and others to confidence, so the correction fires on essentially every lens open — it is the NORMAL state. (In the reference corpus: core and agentic-engineering elect impact; knomit-kb, knomit-io-kb and test elect confidence.)

The correction consumes ONLY st.Highlights/st.HighlightsFallback (highlights are the one axis-dependent block), but it originally re-ran the WHOLE Stats per mount. Instrumented on a 5-mount lens: pass 1 (Stats+Activity) 43.2 ms, pass 2 (the same Stats again) 37.0 ms of an 84 ms request, where the highlights inside pass 2 were 10.6 ms. Every other field it recomputed — count, average confidence, both json_each histograms, type counts, separation counters — is axis-INDEPENDENT and was already summed from pass 1.

Decision: a narrow provider method — FactQuery.Highlights — that calls the SAME fq.highlights implementation Stats calls (one query, two callers, agreement by construction; a second full fan-out fails the stub-counter test). The dropped NormalizeAxis on that path is safe because AxisFromSeparation returns only recognized axis constants; the narrow call deliberately uses the axis it is GIVEN rather than re-deriving a default, since re-deriving one would undo the very correction it exists for.

What this does NOT mean: it does not make the correction free (it is still a second highlights fan-out), and ?axis=… requests skip the correction entirely — the control measurement for any future regression is that an explicit-axis request must not pay it. Concrete baseline for that control, pre-fix: ?axis=impact 48.7 ms against 87.6 ms for the bare request; post-fix the bare request is 52.4 ms and the pinned one is unmoved. A change that speeds up the pinned-axis number is measuring something else.
