# The lens stats axis correction is a SECOND fan-out, and it must fetch only highlights — mounts disagreeing on default_axis is the normal state, not an edge case

GET /lenses/{lens}/stats with no explicit axis runs the per-mount Stats+Activity fan-out, elects a lens-wide rank axis, and — when mounts DISAGREE about their own default_axis — runs a corrective second pass at the elected axis. Both conditions in full: (1) the caller sent no axis= AND (2) the mounts' default axes differ. At any realistic mount count some mounts default to impact and others to confidence, so the correction fires on essentially every lens open — it is the NORMAL state.

The correction consumes ONLY st.Highlights/st.HighlightsFallback (highlights are the one axis-dependent block), but it originally re-ran the WHOLE Stats per mount: 37 ms of an 84 ms request where 10.6 ms of highlights-only work was needed. Decision: a narrow provider method — FactQuery.Highlights — that calls the SAME fq.highlights implementation Stats calls (one query, two callers, agreement by construction; a second full fan-out fails the stub-counter test). The dropped NormalizeAxis on that path is safe because AxisFromSeparation returns only recognized axis constants.

What this does NOT mean: it does not make the correction free (it is still a second highlights fan-out), and ?axis=… requests skip the correction entirely — the control measurement for any future regression is that an explicit-axis request must not pay it.
