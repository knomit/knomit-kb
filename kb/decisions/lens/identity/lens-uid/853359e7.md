# Lenses gain a uid primary key and their name becomes display-only — the same three-identifier model repos already have, driven by wanting lens rename

**The choice.** The `lenses` table is re-keyed from `name` (today's PRIMARY KEY) onto a new `uid` PRIMARY KEY, with a UNIQUE index preserving name uniqueness, and `lens_reads.lens_name` becomes `lens_uid`. A lens name then means what a repo name already means: display only. This is what makes lens rename possible at all, and it is the reason it was done — a name that is a primary key and a foreign-key target cannot be changed without rewriting rows that point at it.

**Options considered.** (a) Re-key onto a uid, mirroring repos. (b) Leave lenses name-keyed and implement rename as a cascading UPDATE of `lenses.name` plus every `lens_reads.lens_name` row. (c) Leave lenses name-keyed and do not support lens rename.

**Rationale.** (b) works mechanically but leaves the name load-bearing, so every future feature that wants a stable lens handle re-opens the question — and it does nothing for the cursor-pin problem, where a *recreated* lens with the same name is indistinguishable from the original. (a) makes lens identity behave like repo identity, which the codebase already documents as uid=membership / root-commit-id=addressing / name=display, so there is one model rather than two.

**THE MIGRATION IS THE RISK, AND IT HAS A DOCUMENTED TRAP.** `OpenLensRegistry` CANNOT perform this upgrade: its `CREATE TABLE IF NOT EXISTS` is a no-op against a control.db whose `lenses` table already exists, so a legacy-shaped table survives the open unchanged and every query against the new column fails at runtime. That exact failure mode is already recorded in `lens.go`'s own comment from the previous lens re-keying (member names → uids). `migrate-registry` owns lens schema upgrades and performs them by DROPPING and recreating from `LensSchemaSQL`, carrying rows across. A second migration path there — or a schema probe on the open path — is required; adding the column to `lensSchema` alone is the plausible-looking change that silently does nothing to an existing install.

**Companion decision.** The MCP §7.3 cursor binding pin moves onto these ids at the same time (see the cursor-pin-on-ids decision under kb/decisions/mcp/sessions/): `lens:<uid>` is what closes the delete-and-recreate gap that `lens:<name>` would leave open.

**Non-scope.** This does not give lenses a root-commit-style content identity — a lens has no tree of its own, so uid is its only stable handle. It does not change how lens MEMBERS are keyed (already uid). It does not make `/lenses/{lens}` uid-addressed: the REST surface stays name-addressed exactly as `/repos/{repo}` does, with rename as a custom action.
