# A lens merges motif clusters by shared cluster_key OR shared member spelling, and keys the merge on the SMALLEST constituent key

# Cross-mount motif cluster identity

`/lenses/{lens}/motifs` had to answer "when are two mounts' clusters the same cluster?". A motif `cluster_key` is a MECHANICAL function of a spelling (`store.groupingKey`: canonicalize → tokenize → sort → join), so the same key names the same shape in every repo — but a judge merge is PER-BRANCH, so one mount can file `quiet-degradation` under key `fallback-silent` while another still keys it `degradation-quiet`.

## Options considered

1. **Merge by `cluster_key` only** — the obvious reading of "the key is mechanical, so it is comparable". Rejected: it puts ONE spelling in TWO rows of one vocabulary, and the two rows pivot to different lists from names the reader cannot tell apart.
2. **Merge by key OR any shared member spelling, transitively** (chosen). Within a mount a spelling belongs to exactly one cluster, so a shared spelling is evidence the two clusters are one shape.
3. **Recompute clusters lens-wide from scratch** — rejected: the alias tables and judge verdicts are per-branch state the web layer cannot re-derive, and it would discard every merge decision a mount has recorded.

## The choice

Union-find over per-mount clusters, unified on shared key OR shared spelling. The merged identity:

- `cluster_key` = the LEXICOGRAPHICALLY SMALLEST constituent key. Not the highest-df mount's: a cluster key is what definitions and URLs hang off, and the store's own rule is that it must be STABLE UNDER DF CHANGE. min() is stable, deterministic, independent of mount order, and for a lens of one is the repo's own key.
- `canonical` = the representative of the highest-df constituent, ties lexicographic (mirrors `store.electCanonical` at the granularity the wire gives).
- `members` = the sorted union — and this list IS the `motifs=` CSV the detail's `_links.facts` pivot sends, so each mount expands the union against its own alias table. That is what makes the merge correct for mounts that have not merged the same shapes yet.
- `df` / `df_total` = per-mount SUMS, carrying the same accepted fork over-count as the `/lenses/{lens}/stats` histograms.
- `definition` = freshest across mounts (current > stale > missing), ties write-mount-first then binding order.

## Non-scope

This does NOT authorize inventing lens-wide cluster STATE. Nothing is written back: no lens-scoped alias table, no lens-scoped definitions, no persisted merged key. The union is computed per request from what each mount already holds, and a mount added or removed changes the merged key — which is correct, because the vocabulary is a property of the read set.

It also does not extend to `/lenses/{lens}/stats`: motifs stay out of stats on both surfaces.

The cluster DETAIL deliberately does not accept `repo=`, unlike every other lens union read: a cluster is addressed by identity there, and narrowing the mounts would change the merged key under the reader. The collection does accept it.
