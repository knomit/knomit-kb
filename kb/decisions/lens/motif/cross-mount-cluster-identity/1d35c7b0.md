# A lens merges motif clusters by shared cluster_key OR shared member spelling, and keys the merge on the SMALLEST constituent key

# Cross-mount motif cluster identity

`/lenses/{lens}/motifs` had to answer "when are two mounts' clusters the same cluster?". A motif `cluster_key` is a MECHANICAL function of a spelling (`store.groupingKey`: canonicalize → tokenize → sort → join), so the same key names the same shape in every repo — but a judge merge is PER-BRANCH, so one mount can file `quiet-degradation` under key `fallback-silent` while another still keys it `degradation-quiet`.

## Options considered

1. **Merge by `cluster_key` only** — the obvious reading of "the key is mechanical, so it is comparable". Rejected: it puts ONE spelling in TWO rows of one vocabulary, and the two rows pivot to different lists from names the reader cannot tell apart.
2. **Merge by key OR any shared member spelling, transitively** (chosen). Within a mount a spelling belongs to exactly one cluster, so a shared spelling is evidence the two clusters are one shape.
3. **Recompute clusters lens-wide from scratch** — rejected: the alias tables and judge verdicts are per-branch state the web layer cannot re-derive, and it would discard every merge decision a mount has recorded.

## The choice

Union-find over per-mount clusters, unified on shared key OR shared spelling. The merged identity:

- `cluster_key` = the LEXICOGRAPHICALLY SMALLEST constituent key. Not the highest-df mount's: a cluster key is what definitions and URLs hang off, and the store's own rule is that it must be STABLE UNDER DF CHANGE. min() is stable, deterministic, independent of mount order, and for a lens of one is the repo's own key.
- `canonical` = the representative of the highest-df constituent, ties lexicographic (mirrors `store.electCanonical` at the granularity the wire gives).
- `members` = the sorted union.
- `df` / `df_total` = per-mount SUMS, carrying the same accepted fork over-count as the `/lenses/{lens}/stats` histograms. The pooled `health` counts carry it too — documented in openapi, and deliberately no longer paired with `count` in the UI, since the two are different populations.
- `definition` = freshest across mounts (current > stale > missing), ties write-mount-first then binding order.
- Alias attribution on the detail reads a PER-MOUNT key set, never the union's `keys`. A key one mount coined can name an unrelated cluster on another — same mechanical-key argument as above, one level down.

## The merged member list is the FILTER, not just a link

This is the part that is easy to under-read, and it shipped broken once. The store's exact tier is per-branch canonical equality (`store.expandMotifQuery`): a term resolves through THAT branch's alias table, and a mount carrying the shape under a different spelling resolves the term to itself, matches no member, and contributes ZERO facts. So a merged row reading `df 7` pivoted to a list of 5 — on a surface whose whole promise is that the count and the list are one query.

The fix is `expandLensMotifs`, which widens every caller-supplied motif term to its merged cluster's member list BEFORE the `/lenses/{lens}/facts` and `/lenses/{lens}/search` fan-out. Fixed at the endpoint, not in the callers: a chip minted anywhere — vocabulary block, filter picker, hand-typed `motif:`, a script — is correct because the endpoint resolves it, not because the caller remembered to send members.

The widening runs over the FULL read set and ignores the query's own `?path=` and `?repo=`: those narrow the LIST, never what a term MEANS. Resolving through a narrowed union re-runs the same bug, because the narrowed mount is the one spelling it differently.

## Non-scope

This does NOT authorize inventing lens-wide cluster STATE. Nothing is written back: no lens-scoped alias table, no lens-scoped definitions, no persisted merged key. The union is computed per request from what each mount already holds, and a mount added or removed changes the merged key — which is correct, because the vocabulary is a property of the read set. There is no cache; the union costs a `Clusters` read per mount per call, which is why the expansion path skips the definitions and health reads it does not use.

It also does not extend to `/lenses/{lens}/stats`: motifs stay out of stats on both surfaces.

The cluster DETAIL deliberately does not accept `repo=`, unlike every other lens union read: a cluster is addressed by identity there, and narrowing the mounts would change the merged key under the reader. The collection does accept it — and a narrowed row's `self` link therefore opens the FULL merged cluster, with a larger `df` and more members than the row promised. It cannot 404 (a narrowed component's smallest key is always in the full union's key set), and openapi says so.
