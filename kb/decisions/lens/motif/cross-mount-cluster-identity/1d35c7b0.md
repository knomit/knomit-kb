# A judge merge on ANY mount changes what a motif term returns for the WHOLE lens (reads only) — the union merges clusters by shared key OR shared spelling

# Cross-mount motif cluster identity

## The consequence a hurried reader needs

**A judge merge on ANY mount changes what a motif term returns for the WHOLE lens.** Read through a lens, the mounts share ONE motif vocabulary, exactly as one repo's folders share one — that is what "a lens answers like a single repo" comes to when the question is about motifs.

It is **READ-ONLY**. No mount's alias table, canonical election or verdict history is touched, and the same repo read DIRECTLY still answers with its own vocabulary alone.

Two boundaries that are easy to lose in compression:
- A lens over ONE mount is left alone entirely, so it answers exactly as that repo does. This is a semantic requirement, not an optimisation — see "the one-mount skip" below.
- Over two or more mounts a term can reach spellings a single UNREBUILT repo's exact tier would not, because the union groups mechanically-equal spellings that per-branch canonicals keep apart. That is the shared vocabulary, not a leak in the tier.

## Why the merge rule is what it is

A motif `cluster_key` is a MECHANICAL function of a spelling (`store.groupingKey`: canonicalize → tokenize → sort → join), so the same key names the same shape in every repo — but a judge merge is PER-BRANCH, so one mount can file `quiet-degradation` under key `fallback-silent` while another still keys it `degradation-quiet`.

### Options considered

1. **Merge by `cluster_key` only** — the obvious reading of "the key is mechanical, so it is comparable". Rejected: it puts ONE spelling in TWO rows of one vocabulary, and the two rows answer different queries from names the reader cannot tell apart.
2. **Merge by key OR any shared member spelling, transitively** (chosen). Within a mount a spelling belongs to exactly one cluster, so a shared spelling is evidence the two clusters are one shape.
3. **Recompute clusters lens-wide from scratch** — rejected: the alias tables and judge verdicts are per-branch state the federation layer cannot re-derive, and it would discard every merge decision a mount has recorded.
4. **Keep per-mount resolution** (the pre-lens rule, which two tests had fossilized) — rejected: it makes a lens's answer depend on which mount the reader's vocabulary happened to come from, which is the shape a merged vocabulary exists to remove.

### The merged identity

- `cluster_key` = the LEXICOGRAPHICALLY SMALLEST constituent key. Not the highest-df mount's: a cluster key is what definitions and URLs hang off, and the store's own rule is that it must be STABLE UNDER DF CHANGE. min() is stable, deterministic, independent of mount order, and for a lens of one is the repo's own key.
- `canonical` = the representative of the highest-df constituent, ties lexicographic.
- `members` = the sorted union.
- `df` / `df_total` = per-mount SUMS, carrying the same accepted fork over-count as the lens `/stats` histograms. The pooled `health` counts carry it too — documented in openapi, and deliberately NOT paired with `count` in the UI, since the two are different populations.
- `definition` = freshest across mounts (current > stale > missing), ties write-mount-first then binding order. A web rendering concern, so it lives in the handlers, not in the union.
- Alias attribution reads a PER-MOUNT key set (`MotifGroup.ContributedKey`), never the union's keys. A key one mount coined can name an unrelated cluster on another — the same mechanical-key argument, one level down.

## The merged member list is the FILTER, not just a link

The part that is easy to under-read, and it shipped broken TWICE. The store's exact tier is per-branch canonical equality (`store.expandMotifQuery`): a term resolves through THAT branch's alias table, and a mount carrying the shape under a different spelling resolves the term to itself, matches no member, and contributes ZERO facts. A merged row reading `df 7` then answered with 5.

`federate.ExpandMotifTerms` widens every caller term to its merged cluster's members BEFORE the fan-out. It lives in `internal/federate` because TWO surfaces answer motif queries against a lens — the REST lens reads and the MCP `knomit_query` fan-out — and the first fix landed in the web package only, leaving the most-used motif path (recall) still dropping mounts. One definition is what makes that impossible to repeat; a second implementation kept in step is the failure this demonstrated.

Expansion runs over the FULL read set: `path=` and `repo=` narrow the LIST, never what a term MEANS. Resolving through a narrowed union re-runs the same bug, because the excluded mount may be the one spelling it differently.

### The one-mount skip

Skipped at one mount, and this is a SEMANTIC choice. Widening a single mount would not be a no-op: `ClustersUnder` groups mechanically-equal spellings into one cluster while the exact tier resolves a bare term through per-spelling canonicals, so a widened term would reach a sibling the same repo read directly does not. A lens over one repo must answer exactly like that repo.

### The failure coupling it accepts

Because a term's meaning is lens-wide, a mount EXCLUDED by `repo=` is still read to resolve it — so that mount failing fails the request. That follows from RFC §9.1 (a lens never answers from a shrunken read set), but it is a coupling a narrowed query did not have before.

## Non-scope

Does NOT authorize inventing lens-wide cluster STATE. Nothing is written back: no lens-scoped alias table, no lens-scoped definitions, no persisted merged key. The union is computed per request from what each mount already holds, and adding or removing a mount changes the merged key — correct, because the vocabulary is a property of the read set. There is no cache; the union costs a `Clusters` read per mount per call.

Does not extend to lens `/stats`: motifs stay out of stats on both surfaces.

The cluster DETAIL does not accept `repo=` — a cluster is addressed by identity, and narrowing would change the merged key under the reader. The collection does, and a narrowed row's `self` link therefore opens the FULL merged cluster, with a larger `df` and more members than the row promised. It cannot 404 (a narrowed component's smallest key is always in the full union's key set), and openapi says so.
