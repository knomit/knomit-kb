# Lens create/update rejects two mounts sharing a repo ID (ErrReplicaInLens) — UPDATE: true replicas are now unreachable by construction; the check survives for the 12-hex prefix-collision case

**Options considered:** (a) tolerate replica mounts (a repo and its clone/fork, sharing a root-commit ID) with a deterministic precedence order for ID→alias resolution and duplicate-path reads (RFC revision 2 working assumption); (b) reject same-ID members at lens create/update.

**Rationale (user ruling 2026-07-16):** Replicas in one read set produce duplicated results, version confusion (the copies evolve and merge independently), and ambiguous ID→alias resolution — a mess with no benefit. Preventing it at creation time is cheap and makes ID→alias BIJECTIVE within any valid lens, which the qualified-path/kb:// machinery can then rely on.

**The choice:** Lens create/update resolves each member alias → RepoInstance.ID() and fails with ErrReplicaInLens if two members share an ID. The check lives ABOVE the registry — in the Manager-level validation helper used by the REST create path (`checkMemberIDCollision`, called from `validateLensLocked`) — because the registry stores membership by uid and has no Manager dependency to resolve IDs itself.

**UPDATE (repo-registry-in-control.db, 2026-08): a true replica match is now UNREACHABLE BY CONSTRUCTION.** `repos_active_repo_id` (the one-local-copy-per-knowledge-base DB constraint, see kb/invariants/repos/one-local-copy-per-knowledge-base) makes a given root-commit knowledge base unique among ACTIVE repos, and lens membership can only name active repos — so two DISTINCT lens members can never resolve to the exact same full repo ID anymore. `checkMemberIDCollision`'s doc comment in internal/repos/manager.go states this explicitly: "The ErrReplicaInLens name now covers only ONE reachable case. A true replica — two members with the SAME full repo ID — is unreachable by construction through the validated path". **What the check still does, and why it is retained rather than deleted:** `checkMemberIDCollision` dedups on the 12-hex ROOT-COMMIT PREFIX that `Binding.ByID` routes on (RFC §6.1), not the full ID — because lens membership is keyed by registry uid but fact ADDRESSING is keyed by (prefix of) repo ID, and it is the addressing namespace, not the identity-uniqueness namespace, that can still collide: two DISTINCT knowledge bases whose full root commits happen to share the same first 12 hex characters would be misrouted by the addressing layer, and that case the registry's identity constraint does nothing to prevent. So the sentinel `ErrReplicaInLens` (internal/repos/manager.go) is retained and still reachable, but its live trigger today is a coincidental prefix collision between two different repos, not an actual replica.

VERIFIED AT HEAD 2026-08: `ErrReplicaInLens` is declared in internal/repos/manager.go (NOT in lens.go). Note the load-bearing dependency this ban has on repo-ID uniqueness: the ban is only meaningful because root-commit IDs are collision-free at the FULL-ID level, which required the `knomit-repo-nonce` fix historically and is now additionally enforced by the `repos_active_repo_id` DB constraint. See kb/decisions/lens/qualified-path-repo-identity/10a3bcc0.md.

**Non-scope:** Does not forbid cloning/forking repos in general, nor mounting a repo and its fork in two DIFFERENT lenses — only coexistence within a single lens. Does not forbid a DISJOINT-HISTORY origin connect (Manager.SwapStore) from later making two previously-distinct member repos' IDs collide at some future validation call — that is exactly the 12-hex-prefix (or, pathologically, full-ID-after-a-swap-races-ahead-of-registry-update) case the retained check still guards.
