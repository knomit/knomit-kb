# Lens create/update rejects two mounts sharing a repo ID (ErrReplicaInLens) — replicas are never tolerated in one lens

**Options considered:** (a) tolerate replica mounts (a repo and its clone/fork, sharing a root-commit ID) with a deterministic precedence order for ID→alias resolution and duplicate-path reads (RFC revision 2 working assumption); (b) reject same-ID members at lens create/update.

**Rationale (user ruling 2026-07-16):** Replicas in one read set produce duplicated results, version confusion (the copies evolve and merge independently), and ambiguous ID→alias resolution — a mess with no benefit. Preventing it at creation time is cheap and makes ID→alias BIJECTIVE within any valid lens, which the qualified-path/kb:// machinery can then rely on.

**The choice:** Lens create/update resolves each member alias → RepoInstance.ID() and fails with ErrReplicaInLens if two members share an ID. The check lives ABOVE the registry — in the Manager-level validation helper used by the REST create path — because the registry stores aliases and has no Manager dependency, so it cannot resolve IDs itself.

VERIFIED AT HEAD 2026-07-22: `ErrReplicaInLens` is declared in internal/repos/manager.go (NOT in lens.go — the Manager-level placement this decision called for is exactly what shipped). Note the load-bearing dependency this ban has on repo-ID uniqueness: the ban is only meaningful because root-commit IDs are collision-free, which required the `knomit-repo-nonce` fix — before that, two repos created in the same second shared an ID and would have FALSELY tripped this check. See kb/decisions/lens/qualified-path-repo-identity/10a3bcc0.md.

**Non-scope:** Does not forbid cloning/forking repos in general, nor mounting a repo and its fork in two DIFFERENT lenses — only coexistence within a single lens.
