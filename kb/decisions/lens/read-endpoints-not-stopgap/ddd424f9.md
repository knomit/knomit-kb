# Lens browsing UI reads through real lens REST endpoints — the client fan-out stopgap is rejected, not deferred

**Options considered:** (A) add lens-scoped REST read routes — `GET /api/v1/lenses/{lens}/facts`, `/search`, `/completions`, `/facts/{path}` — behind LensMiddleware, reusing the union machinery already built for MCP in internal/mcp/federate.go (readTargetsFor fan-out, fuseRRF search fusion, mergeRecent recency merge, first-mount-wins dedupe, kb://<id12>/ path qualification), extracted to a shared package; (B) an interim client-side fan-out where web/src/api.ts queries each mount's existing repo endpoints and merges in JavaScript, migrating to A later (the design handoff explicitly offered B as a stopgap).

**Rationale:** the union logic already exists server-side — A is extraction plus four thin handlers, not new algorithm work, which removes B's only advantage (schedule). B costs one request per mount per screen, a merge/dedupe layer that is deleted when A lands, and — decisive — client-side score interleaving cannot reproduce RRF, so humans and agents would see different result orderings for the same lens.

**The choice:** build A first; B is never built. Responses carry each fact's path in canonical form (bare = write repo, kb://<id12>/… = read mount) plus a `source: {repo, id, branch}` convenience field; a `repo=` filter param and a `repo` completions category power source filtering. Routes are read-only-gated exactly like repo reads (the /mcp subtree stays the only gate bypass).

**Non-scope:** this decision does not add lens-scoped history or write endpoints — per-fact history uses the existing repo endpoints anchored at the fact's source mount, and writes use the existing repo endpoints on the write repo's agent branch.
