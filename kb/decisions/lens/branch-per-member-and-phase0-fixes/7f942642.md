# A lens pins a branch per member repo (default: agent branch); Phase 0 first fixes branch-honoring and hard-coded maxCandidates

**Options considered:** (a) branch segment in the lens URL applied lens-wide; (b) no branch semantics (revision 1 was silent); (c) branch pinned per member repo in the lens definition, defaulting to each repo's agent branch.

**Rationale:** Branch names are per-repo — a single branch name across heterogeneous repos cannot work. Pinning branches in the lens definition keeps capability in endpoint identity. Revision 1's silence hid a pre-existing bug: MCP handlers ignore the URL {branch} and always use ri.AgentBranch() (e.g. internal/mcp/query.go agentBranch := ri.AgentBranch()). Per user ruling: ALL HTTP handlers MUST honor the branch parameter — this is a bug, not a convenience. A second pre-existing fix: knomit_query snapshots a hard-coded maxCandidates=500 regardless of caller wishes.

**The choice:** Lens.Reads is []LensRead{Repo, Branch, Source} with Branch "" = agent branch; Lens.WriteBranch likewise; lens URL carries no branch segment; lens-of-one inherits the URL branch for write and read. A new Phase 0 (before any lens code) fixes branch-honoring across handlers and adds an explicit `max_results` argument to knomit_query controlling snapshot depth — **default 500 (today's behavior), larger requests clamped to a server-side ceiling** (ruled 2026-07-16; a hidden multiplier of `limit` was rejected as invisible magic). `limit` keeps meaning page size; the snapshot must stay deeper than one page or the cursor has nothing to page into. Binding carries a branch per member (ReadTarget{ri, branch}).

**Non-scope:** Phase 0's branch fix intentionally changes observable behavior for callers who passed a non-agent branch expecting it to be ignored — bug-fix semantics, not a compat break to engineer around.
