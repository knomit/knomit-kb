# Lens facts use ONE canonical form everywhere — kb://<root-commit-hash>/path on REST and MCP; the API is faithful, name mapping is UI-only

**Options considered:** (a) extra `repo` argument on MCP tools; (b) attribution as a side-channel metadata field with unqualified paths; (c) qualified paths with repo names; (d) dual-form: repo-name-qualified paths on the wire, kb://<id> refs at rest, server translating at the boundary (revision 2); (e) one canonical kb://<repo-id> form everywhere, no server-side mapping — faithful API.

**Rationale:** A repo argument reintroduces argument-value misrouting; a metadata field doesn't survive copy-paste; names in durable content break on rename and differ across machines. The root commit hash (`init: create knowledge base` commit, store.InitRepo) is clone-stable, rename-safe, and needs zero migration. Option (d) — server-side name↔ID translation — was briefly chosen, then rejected by user ruling 2026-07-16: hidden rewriting makes the API unreliable, callers end up maintaining the mapping themselves anyway.

**CORRECTION (Phase 2 implementation, 2026-07-16):** the original "collision-free because the init signature includes creation time" premise was FALSIFIED — git timestamps are second-precision and the init commit was otherwise fixed content, so two repos created in the same second produced byte-identical init commits → identical root hashes → identical IDs (reproduced 3/3 in tests; would also falsely trigger the replica ban, decision 18). Fix: the init commit MESSAGE now carries a per-repo nonce (`knomit-repo-nonce: <uuid>`) at both creation sites (InitRepoWithUpstream, initFromEmptyRemote in internal/store/repo.go) — message entropy changes the SHA without touching the tree, kb.md (rendered verbatim as repo description in the UI), or any product surface. Pre-nonce repos keep their root identity; the same-second collision risk for repos created before the fix is accepted as vanishingly rare.

**The choice:** Repo ID = root commit hash (RepoInstance.ID(), 40-hex; lazy-once cached via store.Service.RootCommit first-parent walk). ONE form everywhere on REST and MCP: read-mount facts are `kb://<repo-id-12>/kb/...` in query results, tool arguments, AND refs stored inside facts; unqualified paths = the write repo; lens-of-one stays unqualified byte-for-byte. The server NEVER maps IDs to repo names in API payloads. Friendly names are presentation: UI maps ID→name; agents get the mount table via AfterInitialize instructions and knomit_repos. Tools route kb:// paths via Binding.ByID; update/retract on a non-write ID → read-only error; unmounted ID → not-mounted error.

**Non-scope:** Does not authorize semantic cross-repo lineage machinery (walking kb:// refs) — only the syntax ships in v1. Error MESSAGES may name repos (prose, not addressing). The lens registry still stores repo names (machine-local config).
