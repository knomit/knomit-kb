# Lens facts are addressed by alias-qualified paths on the wire and kb://<root-commit-hash> refs at rest — never by repo name in durable content

**Options considered:** (a) extra `repo` argument on MCP tools; (b) attribution as a side-channel metadata field with unqualified paths; (c) qualified paths (mount-namespace model) with repo names; (d) qualified paths with a stable repo ID for durable refs.

**Rationale:** A repo argument reintroduces argument-value misrouting and leaks federation into the single-repo tool schema. A metadata field doesn't survive copy-paste into explain/update/refs and leaves replica paths ambiguous. Names in durable refs break on rename and differ across machines (each clone names its mounts locally). The root commit hash (`init: create knowledge base`, store.InitRepo) is clone-stable, rename-safe, collision-free (init signature includes creation time), and needs zero migration — every existing repo already has one. A committed UUID was rejected: needs backfill and is human-editable.

**The choice:** Within a lens, wire-surface paths are `alias:kb/...` (unqualified = write repo, the "current directory"); refs persisted inside facts use `kb://<repo-id-12>/...`. Boundary rule: **names never persist, IDs never surface** — learn/update canonicalize alias→ID on write, query/explain resolve ID→alias on read; unresolvable IDs display raw as honest dangling refs. Lens-of-one stays unqualified byte-for-byte. Replica mounts (shared ID) resolve write-first-then-alias-sorted.

**Non-scope:** Does not authorize semantic cross-repo lineage machinery (walking kb:// refs) — only the syntax ships in v1. The lens registry still stores aliases (it is machine-local config; Manager updates it on rename).
