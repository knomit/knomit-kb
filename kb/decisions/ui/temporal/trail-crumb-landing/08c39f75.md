# A trail crumb for a fact the reader LEFT from its timeline lands on that fact LIVE (oldest entry of the same-fact run), not back in the timeline — a deliberate choice the tests assert

Since PR #506 entering a timeline pushes the fact's live entry, so navStack can hold [.., A live, A history] while the reader has hopped on to B. selectTrail collapses that adjacent same-fact run into ONE crumb; when the run does not contain the current view it keeps the OLDEST entry, which is A live, with pops = 2. Jumping to that crumb therefore lands on A live with the timeline closed. Before #506 the crumb was A at the timeline commit (pops 1), so the jump now drops the reader out of the timeline they had left.

Options: (1) oldest entry of the run (chosen): the trail shows each fact once and a jump returns to the fact itself; (2) newest entry of a non-current run: preserves the old landing in the timeline commit, but the crumb then points at a different state than the one that opened the fact. The code-review verdict recorded this as fix-later and noted that the new test (web/src/state_asof.test.ts, 'keeps the trail one crumb per fact and each crumb jumpable by its pop count') asserts the live landing, so it is a decision, not an accident. A run that includes the current view keeps the current view (pops 0).

CONSEQUENCE: if product wants a jump to restore the timeline commit, change the non-current-run choice in selectTrail AND that test together; do not treat the live landing as a bug to patch in jumpTrail. WHAT THIS DOES NOT MEAN: not that timeline state is lost: Back (NAV_BACK one step at a time) still restores each intermediate entry.
