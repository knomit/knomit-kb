# The in-app console panel was deleted, not repaired — user-facing lines went to SET_NOTICE and the rest to the browser console via App's `diag`

Console.tsx, consoleStore.ts, the 500-entry ring buffer and the whole CONSOLE_LOG / CONSOLE_TOGGLE / CONSOLE_SET_HEIGHT action family are GONE. The bottom rail survives as web/src/StatusFooter.tsx: temporal position, active task, build version — and it is no longer a control (no chevron, no entry counts, no click target).

WHY DELETED RATHER THAN KEPT. Nothing addressed to a USER was ever routed there. The traffic was SSE retry chatter, bootstrap attempts that retry themselves, a background status refresh that failed, and per-task progress that SET_TASK already renders in the footer. A panel whose every line is developer diagnostics is a panel nobody opens, and its existence made "log it to the console" look like a user-facing outcome when it was not.

WHERE THE LINES WENT — this is the part that matters, because deleting them outright was the alternative and it was rejected:
- Addressed to a person → `SET_NOTICE`, the amber auto-clearing banner. Two sites moved: FilterBar's parse warnings, and FilterBar's "open a fact first — time anchors are per-fact in a lens".
- Everything else → `diag(level, message)` in App.tsx, a two-line helper over console.error / console.info.

`diag` exists specifically so the SSE outage lines survive. An EventSource that silently stops leaves a STALE HEAD PILL and no other signal anywhere in the app — that failure was the reason the outage logging was written, and dropping it would have made the one thing this app cannot otherwise show undiagnosable. The flap-suppression logic (FLAP_WINDOW_MS / FLAP_LIMIT, one summary line per storm) is unchanged and still tested; only its destination moved.

CONSEQUENCES A CONSUMER ACTS ON:
- New code has no in-app log to write to. Ask who the message is for: a user → SET_NOTICE or a banner; anyone else → `diag`.
- Tests that used to read rendered console rows now spy on console.error / console.info (App.sse.test.tsx, App.resilience.test.tsx). The behavioural assertions — which lines, how many, at what level — are unchanged.

WHAT THIS DOES NOT MEAN:
- Not "the footer was removed". It stayed; it stopped being expandable.
- Not "diagnostics were dropped". They moved destination. A claim that some failure is now silent has to name a line that reaches neither `diag` nor SET_NOTICE.
- Not "SET_NOTICE is the new log". It is a transient ~6s banner and holds ONE message; routing chatter there would destroy it as a signal.
