# Ref display shortening is computed server-side because splitting a ref is parsing — the client only renders `display || raw`

THE CHOICE. Abbreviating a citation for display (`src://7b4887ce51d9/x.go@<40hex>:<40hex>` → `src://core/x.go@8cba88ff…:c451fd99…`) is computed in Go and shipped as `RefView.Display`, NOT derived in FactBody from `raw`.

THE OPTION NOT TAKEN, and why. The client alternative was real and cheaper on paper: /api/v1/repos already returns each mounted repo's 12-hex `id` alongside its name, so the browser could build the id→name map itself and slice the hashes in a few lines — no Go signature changes at all. It was rejected because it requires the client to split a ref into repo / path / commit / blob, and that is ref PARSING. internal/fact.ClassifyRef is the single parsing authority; the Go guard test TestRefClassification_HasNoSecondImplementation enforces that, and it cannot see into TypeScript. A second parser in the browser is exactly the class of bug the kind-branching invariant was written to stop, one step removed.

A middle option — server sends parsed COMPONENTS, client formats — was also rejected: it still puts a src:// grammar in the client (which fields exist, which are optional, how a legacy ref differs), and it would have needed the repo-name map threaded into AppState and down through RightPanel to FactBody anyway.

WHAT IT COST. `RepoNamer func(id12 string) string` threads through BuildRefViews → BuildFactView → five handler constructors (fact read, create, update, commit-anchored, lens fact), wired from `storeProviders.repoNamer`, defaulted in `withDefaults(m *repos.Manager)` to `m.NameByID`. That is the honest price: five constructor signatures rather than zero. The handlers hold a `*repos.RepoInstance` from context but NOT the Manager, so there was no cheaper seam.

CONSEQUENCES A CONSUMER ACTS ON:
- Adding a ref kind that needs a label: extend fact.Ref.Display, not FactBody.
- A nil RepoNamer is legal (a Server with no Manager, a test) and means no id resolves. BuildRefViews must stay nil-safe — `nameOf` exists for that.
- Display is MOUNT-dependent, not anchor-dependent. Never persist it, never assert on it across instances.

WHAT THIS DOES NOT MEAN:
- Not "all ref presentation belongs on the server". Which glyph, which colour, whether a kind is clickable, where raw goes (title vs body) are client decisions and stay in FactBody. Only the STRING DECOMPOSITION moved.
- Not a general rule that the client may never read a ref field. Reading `r.path` or `r.kind` is consuming the server's parse; regexing `r.raw` is re-doing it.
