# Ref label shortening lives in FactBody, not the server — formatting an already-classified ref is not the parsing the ref-scheme invariant reserves

The References rail shortens a repo-qualified ref for display in `refLabel` (web/src/FactBody.tsx), CLIENT-side. `src://7b4887ce51d9/web/src/EdgesRail.tsx@<40hex>:<40hex>` renders as `src://7b4887ce51d9/web/src/EdgesRail.tsx@b27972ca…:f08b5ecf…`, with the full raw citation in the element's `title`. The `(source)` marker is gone — `src://` in the label already says it.

WHERE THE INVARIANT LINE ACTUALLY FALLS. kb/invariants/ui/factbody/ref-scheme-branching forbids the CLIENT deciding what a ref IS: kind, existence at the viewed commit, clickability — questions whose answers it cannot know. It does NOT cover formatting a string whose kind the server has already decided. `QUALIFIED_REF` is applied only INSIDE an already-chosen `source_code` / `foreign` case, never to choose one, and a non-match falls back to `raw` verbatim. The worst a wrong match can do is render an ugly label; it cannot make a ref clickable, hoppable, or resolvable. That asymmetry is the entire justification — a client-side regex feeding ROUTING would still be forbidden.

THIS WAS BUILT SERVER-SIDE FIRST AND REVERTED. The server version (fact.Ref.Display → RefView.Display, plus a RepoNamer threaded through BuildRefViews / BuildFactView and five handler constructors) was rejected on two grounds: a cosmetic change should not require a server rebuild to appear in a hot-reloading dev loop, and its repo-name lookup could never fire — see the src-id-vs-kb-id gotcha. Do not re-propose moving it back without a source-repo registry to justify the trip.

THE NAME OVERLAY, AND WHAT IT REALISTICALLY DOES. `repoNames` maps 12-hex KB-STORE id → mounted repo name, built in App from /api/v1/repos (which already returns `{name, id}`), memoized on `repos`, passed through RightPanel to FactBody. A `kb://<other-mounted-id>/…` foreign fact ref therefore renders as `kb://knomit-kb/…`. A `src://` id belongs to the source-code namespace and is LEFT AS WRITTEN — by design, not omission. NOTE the live corpus contained no foreign refs at all when this landed, so the naming path is covered by unit test, not by observation.

CONSEQUENCES A CONSUMER ACTS ON:
- Do not extend QUALIFIED_REF to influence anything but the label string.
- An unknown id keeps its id; an older server omitting `RepoInfo.id` degrades to exactly that, so no extra fallback branch is needed.
- The stored ref keeps full 40-hex hashes. Never let a shortened label reach anything that resolves, copies, or persists a ref.

WHAT THIS DOES NOT MEAN:
- Not "the client may parse refs now". It may FORMAT one the server classified. Deriving `kind`, `path`, or hop targets from `raw` remains forbidden, and `refTarget` still prefers the server's `path`.
- Not "the label is the citation". `raw` must stay reachable wherever a label shows — the title attribute is the minimum.
- Not "src:// refs will get names later". That needs a registry knomit deliberately does not have.
