# Back across a repo or lens switch returns to the context left, on its re-read branch, with its fact: a rail pick pushes, NAV_BACK only asks (navReturn), and App enters, re-reads and lands in that order

User ruling (2026-11-08): "back should restore the proper context". Before this, a context switch dropped the back stack (SET_CONTEXT set navStack: []), so Back after a rail pick was disabled; NAV_BACK's old "repo changed" arm was unreachable, and had it been reached it set `repo` without `context`. The reported symptom (a red 404 after Back across a switch) did NOT reproduce at dev 70826ce6: the Back button was disabled. The real gap was that the switch was not on the history at all, and that a chat's landing in another repo left Browse on that repo after Back.

HOW IT WORKS NOW (web/src/state.ts, web/src/App.tsx):
- NavEntry carries `context` (repo or lens). `SET_CONTEXT {push: true}` pushes the place left (only when a repo and branch are known), and only `onSelectTarget` passes push: a rail pick, a Mounted-in lens, a chat's landing. Every other SET_CONTEXT (a fallback off a deleted repo, boot restore, a create landing, a rename) still drops the stack: it is not the reader's move.
- NAV_BACK to an entry from another context applies NOTHING of it: it pops, sets `navReturn: {entry, entered: false}` and `chatReturn`. While navReturn is set, NAV_BACK is a no-op (one Back at a time). Any SET_CONTEXT clears navReturn, so a pick meanwhile cancels the return.
- App, layout effect 1: does the context still exist (repo listed, repoAvailable, not the fleet; lens listed and not broken)? Gone: NAV_RETURN_GONE, the reader stays where they are, and every trailing entry of that context is dropped, so Back is not a run of dead steps. There: SELECT_CONTEXT_TARGET (unless the entry returns to a chat still open) and NAV_RETURN_ENTER, which reduces through SET_CONTEXT but keeps the stack.
- App, layout effect 2, once the context has a branch (and a lens its doc): if the entry's branch is the one on screen, NAV_RETURN_LAND at once; otherwise api.status(repo, entry.branch), then statusAction + NAV_RETURN_LAND in ONE flushSync (the row-0 race, kb/gotchas/web/chat/browse-landing-row-zero/63b5b413.md). 404: BRANCH_GONE, Browse's normal view on the repo's own branch, as #790 does for a return to a chat. Any other failure: NAV_RETURN_DROP, the context's normal view, nothing landed. A late answer is ignored unless navReturn and repo are still the ones asked about.
- NAV_RETURN_LAND restores view, factPath, asOf, filters, freeText, sort, lensSources, and since-fork only if the re-read branch is an experiment. Head, experiment and write gate come from the fresh status, never from the entry.
- A chat's landing into another context is ONE entry: the switch pushes it with fromChat, and the landing's APPLY_NAV carries `departed` so it does not push again. One Back returns to the chat AND puts Browse back in the repo it left.
- selectTrail stops at an entry from another context: a crumb is a hop inside one repo or lens.

Does NOT mean: Back inside one context changed. It did not: the same-context NAV_BACK arm is untouched, including #790's fromChat branch restore and branchRecheck. Does NOT mean the entry's head is restored: it is re-read. Tests: the 'NAV_BACK across a repo switch' describe in state.test.ts and 'Back across a repo switch' plus 'a landing in another repo' in App.facets.test.tsx.
