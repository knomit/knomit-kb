# Back across a repo or lens switch returns to the context left, on its re-read branch, with its fact: a rail pick pushes, NAV_BACK only asks (navReturn), and App enters, re-reads and lands in that order

User ruling (2026-11-08): "back should restore the proper context". Before this, a context switch dropped the back stack (SET_CONTEXT set navStack: []), so Back after a rail pick was disabled; NAV_BACK's old "repo changed" arm was unreachable, and had it been reached it set `repo` without `context`. The reported symptom (a red 404 after Back across a switch) did NOT reproduce at dev 70826ce6: the Back button was disabled. The real gap was that the switch was not on the history at all, and that a chat's landing in another repo left Browse on that repo after Back.

HOW IT WORKS NOW (web/src/state.ts, web/src/App.tsx):
- NavEntry carries `context` (repo or lens). `SET_CONTEXT {push: true}` pushes the place left (only when a repo and branch are known), and only `onSelectTarget` passes push: a rail pick, a Mounted-in lens, a chat's landing. Every other SET_CONTEXT (a fallback off a deleted repo, boot restore, a create landing, a rename) still drops the stack: it is not the reader's move.
- NAV_BACK to an entry from another context applies NOTHING of it: it pops, sets `navReturn: {entry, entered: false}` and `chatReturn`. While navReturn is set, NAV_BACK is a no-op (one Back at a time) and canGoBack is false, so the Back control is disabled rather than dead.
- A pending return YIELDS TO THE READER: any SET_CONTEXT clears it, and so does every reader move, through `reducer`'s READER_MOVES drop (NAVIGATE, GO_UP, filters, free text, APPLY_NAV, FOCUS_LENS_SOURCE, PIVOT_MOTIF, EXIT_SEARCH/EXIT_MOTIF, sort, lens sources, since-fork, SET_AS_OF) and enterBranch's NAV_RETURN_DROP. NOT AMEND_NAV or RESTORE_LIST: those are the app's own (a list selecting its first row, a reload), and dropping on them would cancel every return into a Recent list. A new reader action added to the reducer must be added to READER_MOVES, or a late landing will overwrite it.
- A pick before the last switch has a branch (still opening) keeps the stack as it is: there is nothing of its own to push, and dropping would lose the history behind it.
- App, layout effect 1: does the context still exist (repo listed, repoAvailable, not the fleet; lens listed and not broken)? Gone: NAV_RETURN_GONE, the reader stays where they are, and every trailing entry of that context is dropped, so Back is not a run of dead steps. There: NAV_RETURN_ENTER, which reduces through SET_CONTEXT but keeps the stack. The return NEVER touches the view (facets.ts): Back only fires with Browse on screen and nothing pinned, so the context is the displayed target and its facets follow it at render (shownFacet); a return to a chat still open has just been pinned by chatReturn, and a SELECT_CONTEXT_TARGET would unpin it. Do NOT add a rail dispatch there.
- App, layout effect 2, once the context has a branch (and a lens its doc): if the entry's repo is not the context's repo now (a lens entry pushed before the lens resolved names the repo on screen then; a lens whose write repo changed), NAV_RETURN_DROP: the context's normal view, no branch asked about, stack untouched. If the entry's branch is the one on screen, NAV_RETURN_LAND at once; otherwise api.status(entry repo, entry.branch), then statusAction + NAV_RETURN_LAND in ONE flushSync (the row-0 race, kb/gotchas/web/chat/browse-landing-row-zero/63b5b413.md). 404: NAV_RETURN_BRANCH_GONE, Browse's normal view on the branch on screen, keeping that branch's own experiment and since-fork, and dropping only the trailing entries left on the dead branch of that context. NOT #790's BRANCH_GONE, which clears every entry and the experiment (right there only because the agent branch's status follows it). Any other failure: NAV_RETURN_DROP, the context's normal view, trail kept. A late answer is ignored unless navReturn and repo are still the ones asked about.
- Entering a lens applies the lens doc's write_branch status (resolveLens), so a lens return usually lands on the agent branch without a re-read; the re-read runs when the doc has none and SET_LENS kept the write repo's branch on screen.
- NAV_RETURN_LAND restores view, factPath, asOf, filters, freeText, sort, lensSources, and since-fork only if the re-read branch is an experiment. Head, experiment and write gate come from the fresh status, never from the entry.
- A chat's landing into another context is ONE entry: the switch pushes it with fromChat, and the landing's APPLY_NAV carries `departed` so it does not push again. One Back returns to the chat AND puts Browse back in the repo it left.
- selectTrail stops at an entry from another context: a crumb is a hop inside one repo or lens.

Does NOT mean: Back inside one context changed. It did not: the same-context NAV_BACK arm is untouched, including #790's fromChat branch restore and branchRecheck. Does NOT mean the entry's head is restored: it is re-read. Tests: 'NAV_BACK across a repo switch' and 'a pending return to another context' in state.test.ts; 'Back across a repo switch', 'a landing in another repo' and 'a landing in another repo whose chat has since ended' in App.facets.test.tsx; 'Back to a lens' in App.listUrl.test.tsx. Each App test passes alone (-t): the helper sets everything the fact view reads.

Review asked for a test failing when that check became `!!fromChat`; none could, because the dispatch changed nothing visible (the facet is derived at render). 85fcde79 removed the dispatch and the check.
