# The filter picker becomes a wide two-pane facet browser with NO counts — values sorted only where the server has no order to preserve, marked by the glyph each value already owns, and entity takes back the dashboard blue by evicting the type chip's single hue

The "+" picker was a 212px two-pane flyout that looked nothing like the ranked facet panel PR #70 gave the summary. Four treatments were mocked; the user chose the two-pane one (rail + browser), then explicitly dropped counts from it.

**Options considered**
- **A — facet sheet**: the picker becomes the dashboard's three ranked columns wholesale. Rejected as too heavy for a filter bar.
- **B — rail plus browser (CHOSEN)**: keeps the category rail, restyles the value pane as the facet browser — wide sheet, three columns, dashboard palette.
- **C — type-ahead sheet**: no menu; one ranked cross-category result list. Rejected — fastest to use, worst for browsing a corpus you don't know.
- **D — restyle only**: rejected as fixing the look and none of the substance.

**Counts were considered and DROPPED by the user** — "I don't necessarily want the counts, just the layout and the colors". This matters because it removes the whole cost driver: counts would have needed the stats histogram plumbed into FilterBar (RightPanel's fetch bails with `if (factPath) return`, exactly when the picker is used), or a `GROUP BY` added to the completions query. Without them the change is pure presentation over data the picker already fetches.

**The choice**
- 600px sheet, 132px rail, three columns, FIXED height so the panel never resizes under the cursor (same reason FacetBrowser fixed its own).
- **Sorting is per-category, not global.** Open sets (domain, entity, path) are sorted alphabetically because the server gives them NO order — `SELECT DISTINCT … LIMIT` with no ORDER BY, and the path arm iterates a Go map, so its order is random per call. Curated enums (type, kind, origin) keep server order: types arrive grouped epistemic-then-pragmatic and alphabetising would destroy a meaning that is already there. Repo keeps binding order (write mount first).
- **Every row carries a mark: the glyph the value already owns elsewhere, or a dot in the facet hue when it owns none.** Never both — a glyph is already drawn in the value's colour, so a dot beside it repeats the only thing it says. Type → `typeStyles[t].icon`; origin → `originGlyphs`; repo → its `repoHue` dot; domain/entity/path/kind → facet-hue dot. Kind is the only category with no mark anywhere in the app (a text `pragmatic` badge on the fact body, nothing for `epistemic`).
- The search field is hidden for sets of ≤8 values unless something has been typed — a search box over Kind's two rows is furniture.

**Chip hues — entity blue forced the type chip to move.** Entities were pink as a chip (`chipColors.entity #f8a`) and blue everywhere else (`FacetPanel` and the fact body's tag cloud both use `136,170,255`). The user confirmed blue is correct. But `#88aaff` IS `#8af`, which `chipColors.type` already used, so entity could not take it while type held it. Resolved by making TYPE CHIPS PER-VALUE: a type chip takes that type's own colour, background and glyph from `typeStyles`, which is what the dashboard's Types column and every Library row already do. Entity then takes the vacated slot verbatim. Nothing shares a hue afterwards.

**Non-scope**
- No counts, and therefore no ranking — alphabetical is not a stand-in for rank, it is what you use when there is no rank to show.
- Episode is NOT a picker category and is deliberately not added: `FACT_CATEGORIES` holds six (domain, entity, kind, type, origin, path) plus the lens-only repo. The `ep:` filter does work end-to-end if typed (parseFilterQuery accepts it, the server honours it — measured 1146 → 417 facts for ep=learn) but the user's position is that episode filtering is not a feature; it stays out of the UI.
- No date/time filtering exists anywhere in the API (the complete param surface has nothing temporal; `before`/`after`/`from` on the commit-log endpoints are commit-hash cursors). Separate work.
