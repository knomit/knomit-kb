# The fact panel's timestamp is the FACT VERSION's commit date, not the anchor's — and it is chosen by first-parent walk, never by ORDER BY committed_at

**The choice.** The fact panel shows the date of the newest commit that touched THIS fact at or before the view's anchor. Live: "this fact last changed 3d ago". History (scrubbed to commit C): the date of the version on screen. One rule, both modes, one code path — the resolver is called with the resolved head sha for HEAD anchors and the pinned sha for commit anchors, so the two modes agree by construction rather than by two branches being kept in step.

**Options considered.** (a) The fact version's own commit date. (b) The anchor commit's date — cheapest, one commit object read. (c) Both, side by side.

**Rationale.** (b) was rejected because in LIVE mode the anchor is the branch tip, so its date means "when the repo last changed" — a number with no relationship to the fact on screen, and one that ticks every time an unrelated fact is written. It is only correct in history mode, where it coincides with (a). (c) adds a second temporal number to a band that already carries a version chip, for information the reader can get by opening the timeline.

**THE TRAP — this is the load-bearing part.** `commit_log` carries the index `commit_log_path_time ON commit_log (path, committed_at DESC)`, which makes `SELECT commit_hash, committed_at FROM commit_log WHERE path = ? ORDER BY committed_at DESC LIMIT 1` both the easiest query to write and exactly wrong. It orders by WALL CLOCK, which the first-parent invariant forbids: a sibling-branch commit that touched the path with a later timestamp and was then merged back in would win, where first-parent ancestry correctly stays on the merged-into line. `readFileLastCommit` already had to be fixed for this precise bug class in PR #77.

The rule: **first-parent ancestry CHOOSES the commit; `committed_at` is read only to DISPLAY the date of the commit already chosen.** Implement as a sibling of `resolveActiveCommitForPath` that selects `cl.committed_at` alongside `cl.commit_hash` from the row the first-parent CTE already lands on. Any implementation that sorts candidate commits by `committed_at` is wrong even when it returns the right answer on a linear history — the merge case is the test that distinguishes them, and it must exist.

**Wire + placement.** `FactView.AsOf` gains `date` (RFC3339, `omitempty` so an unresolvable commit degrades to no-date, never to 1970). `BuildFactView` is the single serializer for both repo and lens fact reads, so lenses need no lens-specific work. In the UI the date renders in the fact band's action group, left of the `[in | out | version]` control strip: relative in live, absolute and amber in history. Placement was chosen over three alternatives — inside the control strip (every cell there is a control; a date is a readout), in the dot-separated meta line (already wraps on a narrow panel, and carries two extra parts in a lens), and under the title (scrolls away, which is the problem the band exists to solve).

**Non-scope.** This does not authorize showing the ANCHOR commit's date anywhere, and it does not authorize removing `VersionWalker`'s index-0 fallback for a live anchor — that fallback becomes unnecessary but stays, as a separate change with its own tests.
