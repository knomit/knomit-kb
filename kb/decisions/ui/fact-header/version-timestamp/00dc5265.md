# The fact panel's timestamp is the FACT VERSION's commit date, not the anchor's — and it is chosen by first-parent walk, never by ORDER BY committed_at

**The choice.** The fact panel shows the date of the newest commit that touched THIS fact at or before the view's anchor. Live: "this fact last changed 3d ago". History (scrubbed to commit C): the date of the version on screen. One rule, both modes, one code path — the resolver is called with the resolved head sha for HEAD anchors and the pinned sha for commit anchors, so the two modes agree by construction rather than by two branches being kept in step.

**Options considered.** (a) The fact version's own commit date. (b) The anchor commit's date — cheapest, one commit object read. (c) Both, side by side.

**Rationale.** (b) was rejected because in LIVE mode the anchor is the branch tip, so its date means "when the repo last changed" — a number with no relationship to the fact on screen, and one that ticks every time an unrelated fact is written. It is only correct in history mode, where it coincides with (a). (c) adds a second temporal number to a band that already carried a version chip, for information the reader can get by opening the timeline. (The chip's 'vN' count was removed in PR #793, squash-merged as b7a34667; the button is now a bare ↺. See kb/decisions/ui/fact-header/history-button-no-count/6d7214a4.md.)

**AS BUILT — corrected after implementation.** An earlier revision of this fact said to implement a new store method, a sibling of `resolveActiveCommitForPath` selecting `cl.committed_at`. That was wrong: the primitive ALREADY EXISTED. `store.RevisionsBefore(ctx, branch, path, anchorCommit, limit)` (`internal/engine/store/internal/vcs/revisions_before.go`, reachable as `svc.Search().RevisionsBefore`) walks the shared `firstParentChainCTE`, filters to `action IN ('added','modified')`, orders by `fpc.depth ASC`, and additionally joins `branch_commits` so off-branch lineage never surfaces — something `resolveActiveCommitForPath` does NOT do. Called with `limit=1` it returns the version commit and its `CommittedAt`. The shipped code is `versionDateFromService` in `internal/edge/web/fact_version_date.go`, a thin wrapper. **Look for an existing primitive before adding one here; this area already has three overlapping first-parent walkers.**

**THE TRAP — still the load-bearing part, and reuse is what defuses it.** `commit_log` carries the index `commit_log_path_time ON commit_log (path, committed_at DESC)`, which makes `SELECT commit_hash, committed_at FROM commit_log WHERE path = ? ORDER BY committed_at DESC LIMIT 1` both the easiest query to write and exactly wrong. It orders by WALL CLOCK, which the first-parent invariant forbids: a sibling-branch commit that touched the path with a later timestamp and was then merged back in would win, where first-parent ancestry correctly stays on the merged-into line. `readFileLastCommit` already had to be fixed for this precise bug class in PR #77.

The rule: **first-parent ancestry CHOOSES the commit; `committed_at` is read only to DISPLAY the date of the commit already chosen.** Reusing `RevisionsBefore` satisfies this by construction — the correct implementation became "call the existing function" rather than "write a new query".

**The guard, and why it needed strengthening.** `TestRevisionsBefore_MergeAnomalyPicksFirstParent` pins this. Note what the first attempt got wrong: mutating only the trailing `ORDER BY` leaves the `parent_order = 0` CTE join intact, so the merged-in sibling can never enter the candidate set and the test only discriminated via a `committed_at` tie-break (Unix SECONDS — all writes in one test land in the same second). The guard that actually holds is a tie-break-independent ABSENCE assertion: after the merge, the feature commit must not appear anywhere in the revision list, because `branch_commits` is populated by full reachability and only the first-parent CTE excludes it. Verify a guard here by replacing the whole query with the naive `commit_log`⋈`branch_commits` form, not by tweaking the sort.

**Wire + placement.** `FactView.AsOf` gains `date` (RFC3339, `omitempty` so an unresolvable commit degrades to no-date, never to 1970). `BuildFactView` is unchanged in signature; the stamp happens after construction at exactly three READ sites (repo HEAD, commit-anchored, lens) — create/write responses are deliberately NOT stamped, so a just-written fact shows no date until the next read. At the lens site the path passed must be the mount-relative `rel`, never `view.Path`, which is rewritten to the `kb://<id12>/…` wire form immediately after and would match no `commit_log` row. In the UI the date renders in the fact band's action group, left of the `[in | out | version]` control strip: relative in live, absolute and amber in history.

**Non-scope.** This does not authorize showing the ANCHOR commit's date anywhere. (It used to also protect `VersionWalker`'s index-0 fallback for a live anchor; that fallback only positioned the 'vN' label, and went with the label in PR #793. VersionWalker no longer takes the current commit at all: it opens history at the newest entry of the fact's /commits list.)
