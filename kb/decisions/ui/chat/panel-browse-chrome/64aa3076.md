# The chat's side panel renders a fact with Browse's fact view, the one component (FactView): the same fact shows the same thing in both, except that the panel has a × in its top-right corner and no retract button; band menus open in place and a pick from them lands in Browse, and Back returns to the chat

User decision (2026-11-07), in the user's words: "we already have a perfectly functional component that renders facts EXACTLY how we want them... in the right hand panel for chat view, when we have to render a fact, use that component."

So there is no separate chat fact rendering. FactView (web/src/FactView.tsx, extracted whole from RightPanel) is the fact view. Browse mounts it inside RightPanel; the chat's side panel mounts it through PanelFact in ChatSidePanel. What it reads is a FactReading, a Pick of AppState (which fact, from where, at which commit, whether it can be written), and the state selectors (selectAnchorCommit, factHistoryAnchor, edgeAnchorCommit, isReadOnly and the rest) take a FactReading, so both go through the same rules. Browse hands its app state; the panel builds a reading for its fact. Everything else the view can do is a prop. ChatFactView was deleted. A reader sees and can do the same on a fact in both: version, cited by, cites, same motif, materialize, retracted badge, history and anchored reads, tags, references.

THE TWO DIFFERENCES FROM BROWSE, and the only two. (1) A visible × in the view's top-right corner (cornerAction, inside the band's 28px right padding), which Esc also does. Until the chat review of 2026-11-08 it sat at the end of the band's action row (bandAction), beside history and materialize where Browse draws retract, and the user moved it out so it cannot be confused with retract. (2) No retract button (hideRetract), the user's decision: Browse keeps its retract button. Both are inputs on the one component, not a variant. Consequence: do NOT add a chat rendering, a chat band or a chat copy of any control. A new difference goes through a prop on FactView, and only if the user asks for it. Do NOT bring the user questions about how a fact renders in the panel: it renders as in Browse.

Also around the component, not in it: no path/Open in Browse row, since the path is in the band; no back or forward arrows and no back stack in the panel (the reader selects from the chat; from a fact opened out of a commit, the way back to the commit is its chip in the answer). The corner × is drawn in every state (the fact, loading, an error, no version at the commit); in the materialize view it sits at the end of that view's own toolbar instead (barAction), so × never disappears. The view's own Loading and error lines are Browse's.

What navigates goes to Browse, and Back returns to the chat: the version; a PICK from the cited by, cites or motif menu (since the chat review of 2026-11-08 these menus open IN PLACE in the panel, exactly as in Browse; the onOpenPanel hand-over that switched the app to Browse just to show the menu is deleted, with the factPanel / factPanelRequest / FACT_PANEL_SERVED landing plumbing it alone fed. An edge pick hops to that fact at its pinned commit through onHopEdge; a motif's "Open all N carriers" dispatches PIVOT_MOTIF, which the panel turns into BrowseFactRequest.motif and resolveNavRequest lands as the pivot would leave it, motif chip with the path as returnPath, in ONE APPLY_NAV so one Back step returns to the chat. Does NOT mean clicking the cell navigates: only the pick does.); a tag or origin chip (it lands in Browse with that filter on, in one Back step; it does what a tag click does in Browse, which keeps the fact only if the demoted list holds it, kb/gotchas/web/chat/browse-landing-row-zero/63b5b413.md); a reference in the body (Browse on that fact at the edge's pinned commit). A fact read at a commit lands at that commit. A fact read live lands live, except the version, which lands at the newest version as Browse's walker does. Materialize opens in place and uses Browse's view; materializeInUrl={false} keeps its options out of the query string, which Browse reads at mount, so a chat cannot leave Browse opening materialized. Focus does what it does in Browse, through the same attribute: data-mat-focus hides the rail and tabs, and materialize.css folds the chat column and its splitter and footer so the panel takes the window. It is scoped to the chat being on screen (materializeFocus.hidden, from ChatFacet's onScreen): the chat stays mounted behind Browse, and a hidden chat's Focus has no effect on the shell or the keyboard, whichever way the reader left. It is remembered, so the chat comes back as it was. Does NOT mean Focus ends on leaving. Retracted handling is the view's own: an anchored read always uses ?fallback=before, so the panel entry has no `removed` flag, and the badge shows as in Browse.

How the landing works: APPLY_NAV with fromChat stamps the departure entry it pushes (NavEntry.fromChat); NAV_BACK popping it sets state.chatReturn, and App then pins that chat (SELECT_PINNED). One route for the keyboard, the Library's chevron and the timeline's back, because they all dispatch NAV_BACK. The chat stays mounted while Browse shows, so it returns with its scroll and panel as they were. A chat that has since ended is not pinned: the reader stays in Browse on what back restored, and if the landing was into another repo or lens, Browse goes back to that context as a rail pick of it would (facet rule included: the facets follow the context at render, with no rail dispatch on the return). selectTrail stops at a fromChat entry, so what Browse held before is not a crumb. A landing that moves the branch pushes its entry BEFORE the branch moves, and NavEntry holds the branch with its head, experiment and write gate, and since-fork, so a return to the chat restores what the reader left: Browse's own fact on its own branch, in the experiment, with since-fork as it was. Moving the branch first paired the new branch with the old fact, which was a 404 back in Browse. ONLY a return to a chat (a fromChat entry) does this: Back inside Browse does not touch the branch or since-fork (kb/invariants/ui/navigation/nav-entry-captures-ways-of-looking/06e6b0af.md), and only a reveal from a chat clears since-fork. The entry is only what the app knew when the reader left: the experiment can be committed or rolled back meanwhile, by an agent too. So NAV_BACK raises the one-shot branchRecheck and App reads the branch's status. It answers: statusAction applies it, which refreshes the head, write gate and experiment. 404: the branch is gone, so BRANCH_GONE closes the fact and clears the filters and trail, and the reader is on the agent branch in Browse's normal view, not an error. Any other failure says nothing about the branch, and the reader keeps it. LIMITS of the re-read (App.tsx, as merged): an answer is applied only while Browse is still on the repo and branch it asked about (still()), so a late answer after the reader moved on changes nothing, a late 404 included. And on a 404, if the agent branch or its status cannot be read either, the reader STAYS on the dead branch: BRANCH_GONE is dispatched only from this one-shot re-read, never by the status poll, so nothing else moves them off it. Does NOT mean a return always lands on a readable branch. A branch deleted AFTER the return, while the reader stays in the chat, is not rechecked: that is not a restore, and Browse left on any branch has the same shape. Across repos or lenses (since fix/back-restores-repo) the switch itself pushes the departure entry stamped with the chat, and the landing does not push again (APPLY_NAV departed): one Back returns to the chat AND puts Browse back in the context it left, on its re-read branch, with its fact (kb/decisions/ui/navigation/back-across-context/135b2e49.md). Before #794 the switch emptied navStack and Back left Browse on the new repo; it no longer does. APPLY_NAV carries factPanel, FactView serves state.factPanelRequest once and clears it (FACT_PANEL_SERVED), or a later return to the fact would reopen the panel.

A test renders one fact through RightPanel and through ChatSidePanel, live, at a commit and retracted at it, and compares the DOM with only the × and the retract button removed: web/src/FactView.shared.test.tsx. It is what fails if the panel stops using the component.
