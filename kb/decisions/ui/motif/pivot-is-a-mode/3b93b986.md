# The motif pivot is the FOURTH library mode — DERIVED like relevance, which is why its ≈ segment is an EXIT and why PIVOT_MOTIF must never write librarySort

Settled in PR #180 (merged 2026-08-31). A motif pivot is a PEER of ontology / chrono / search — not a place, not a moment, not a ranking, and above all NOT a sort axis. It gets a `≈` segment in the mode strip that appears only while a pivot is on, exactly as the relevance radar appears only while searching. Three claims, all load-bearing:

**1. It is DERIVED, like relevance.** The motif chip is what MAKES the list a pivot; there is no stored mode, and nothing in the strip can ENTER either derived mode — a search box and a motif cell do that. Two of the four segments are therefore EXITS: pressed while lit, each LEAVES. `EXIT_MOTIF` is `EXIT_SEARCH`'s twin by construction — read them as a pair and change them as a pair. The `≈` segment carries `aria-label="Leave this motif"` and needs its `onExitMotif`: without one, an enabled segment would fall through to `onSortChange` and dispatch `'motif'`, which is not a `LibrarySort` and which every list effect early-returns on, so it is disabled in that case — a dead segment misleads less than a panel-blanking one.

**2. `PIVOT_MOTIF` MUST NOT WRITE `librarySort`.** The pivot already ARRIVES in Recent by derivation — a motif chip is a content filter and the tree cannot honour one — so writing the sort stored the derived value over the remembered one and erased the only record of where the reader came from. An ontology browser who pivoted could only ever be dropped back into a flat feed; leaving a pivot can now put them back in the ontology. This is the EXACT failure `EXIT_SEARCH`'s own comment already described for relevance, hit a second time in a second mode. The lesson generalises further than the code does: **a rule stated about one instance of a pattern does not generalise itself.** The first mode's write-up did not stop the second mode from repeating it. If a third derived mode arrives, state the rule for it explicitly rather than trusting this one to carry.

**3. A derived mode DISABLES the rest of the strip** — not because it is a mode, but because it FORCES THE ORDERING. While searching, order is relevance; while pivoting, the list is one motif's carriers newest-first and the tree cannot hold a shape at all. An enabled button whose entire effect is overridden is worse than a disabled one — it gives no feedback and the reader keeps clicking — and in a pivot Recent is exactly that: it would write the axis the list already has and clear the open fact (`SET_LIBRARY_SORT` nulls `factPath`) for nothing.

**WHAT THIS DOES NOT MEAN.**

- *Not* that the pivot has a stored value in `librarySort`. It has none, and adding one recreates the bug this decision fixed.
- *Not* that a content chip alone disables the strip. A chip with no search and no pivot disables PATH ALONE — the tree cannot honour a filter so Library borrows Recent, and Recent stays LIVE because the reader may want to say explicitly that that is what they are in before removing the chip. Distinct case; do not merge it with the derived-mode rule.
- *Not* that `EXIT_MOTIF` is a general 'clear the filters'. Only the motif chip goes — a domain the reader added to narrow the pivot survives — and the folder the pivot displaced comes back from a `returnPath` stashed ON the chip. See kb/decisions/ui/motif/exit-restores-place/655c7804.md.
