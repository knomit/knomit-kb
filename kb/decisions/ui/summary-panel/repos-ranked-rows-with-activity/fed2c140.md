# The lens summary's Repos section becomes ranked borderless rows carrying a facts share bar AND the 7/30/90d change meter — the card-per-mount, the repo-as-fourth-facet, and the chip-rail options were all rejected

Four treatments were mocked against the real panel and the user chose C.

**Options considered**
- **NOW (rejected)** — the shipped LensRepoRow: one bordered, filled card per mount, ~51px each (~330px for six). After PR #70 replaced the facet clouds with ranked columns (hairline share bars, tabular counts, no box chrome), this section was the only boxed thing left in the panel and read as imported from another design. Nothing encoded relative size: a 1377-fact mount and a 9-fact mount were the same visual weight.
- **A (rejected as the whole answer, kept as the base)** — ranked borderless rows in the FacetPanel grammar: dot + mono name, a share bar under the name carrying the mount's slice of the corpus, then right-aligned tabular columns for facts / confidence / top domains / recency. ~185px.
- **B (rejected)** — fold Repos into FacetPanel as a fourth column beside Domains/Entities/Types. Costs zero vertical space and deletes the section entirely, but has nowhere to put confidence, top domains, recency or the write marker, and squeezes the other three columns from a third to a quarter of the width.
- **C (CHOSEN)** — A, plus the mount's `changes_7d` / `changes_30d` / `changes_90d` rendered as a three-tick activity meter. ~229px measured.
- **D (rejected)** — repos as a wrapped rail of source-badge chips with inline counts, ~60px. Counts stop being comparable (no bar, no alignment) and a fifteen-mount lens wraps into a hue soup.

**Rationale**
C wins on the same ground A does — the section stops looking foreign because it is built from the same three parts as the facets above it (name, hairline share bar, tabular count) — and additionally spends data the panel already fetches and throws away: `LensRepoStats` has carried changes_7d/30d/90d since the union-stats endpoint shipped and `LensRepoRow` rendered none of them. That turns the list from an inventory into a pulse. B lost because a mount is not a peer of a domain string — it has an identity (write target, sync state, its own recency) that the facet grid would silently delete. D lost on scale.

**The choice**
Ranked rows, sorted total DESC then name ASC (the same tie-break `FacetPanel.ranked` uses, and for the same reason: JSON object order must not decide which of two equal mounts leads). Per row: hue dot, mono name, write marker, ONE top domain, share bar of `total / max(total)`; then facts, confidence, a 3-tick meter, relative last_commit. A zero-fact mount renders dimmed, with `—` rather than a claimed 0.00 confidence.

The name cell is capped at 380px even though it sits in a `1fr` track: at full panel width the leading mount's bar stops reading as a measure and starts reading as a horizontal rule, and the cap also keeps it near facet-bar length, which is the scale the eye was just calibrated on.

**Picking a mount drives the SOURCES selection, not a `repo:` chip** — corrected after the first implementation shipped the chip. Both narrow the union and the two INTERSECT in the Library, so a chip would have left two controls over one scope that can silently disagree; the sources dropdown is the one the left panel already displays ("1 of 6 mounts"). The pick also dispatches `SET_LIBRARY_SORT 'recent'`, because path mode lists the mount's topic FOLDERS and deliberately starts un-selected — the flat list is the mode that auto-selects its first row, so a pick from a facts-and-confidence table lands in the facts.

**Non-scope**
This authorizes THREE ticks, not a sparkline: the payload carries three cumulative buckets, not a time series, and drawing a curve through them would invent data. It does not authorize dropping the second top domain everywhere — the domain column narrows to one value only because the meter takes its width in this layout. And it does not make `repo:` chips dead: the chip category still exists and still intersects with sources; this decision only says the REPOS SECTION does not mint them.
