# The facet browser CLOSES on a pick, and structurally cannot do otherwise — the chip flips path→Recent, the refetch opens row 0, and RightPanel draws the summary only when no fact is open

**The choice.** Picking a value in the summary panel's overflow facet browser closes the browser — and closes the summary with it, because the reader lands on a fact. This is intended behaviour, not a limitation, and it matches what a facet pick means everywhere else in the app: the three ranked columns below do it, and so does picking a mount in the repo summary.

**Why the alternative was never actually available.** `FacetBrowser` claimed in a code comment that it "stays open after a pick". It could not have: adding the chip flips a path-sorted view to Recent, the list refetches, the refetch `AMEND_NAV`s row 0 open, and `RightPanel` renders the summary ONLY when `!factPath`. Four independent steps each of which the browser does not control. The comment was corrected rather than the behaviour; nothing was built and reverted.

**Consequence to act on.** Treat the browser as the way to REACH one value among hundreds, not a mode the reader stays in. Selecting a second value means opening it again — which is the honest cost, and is why the browser is a full-width overflow view with search rather than an inline expansion. Anyone proposing "keep it open for multi-select" is proposing to change the facet-pick contract app-wide (a pick would have to stop opening a fact), not to tweak one component; that is a much larger change than it looks and should be argued at that level.

**Not a claim about the FILTER BAR's picker.** That sheet is a different surface with a different lifecycle; this decision governs the summary panel's overflow browser only. Related: [[picker-facet-browser]] for the filter-bar sheet, whose fixed height solves the same do-not-resize-under-the-cursor problem for a different reason.
