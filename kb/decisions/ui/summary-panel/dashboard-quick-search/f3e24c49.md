# The filter bar hides on the clean dashboard; search reopens as a BARE input expanded inside the stats strip, committing on enter — chosen over a slot-level input because the panel must not slide down

The filter bar duplicated the facet columns' job on the summary panel, so it comes off the dashboard. It is also the app's ONLY free-text search, so it needed a way back.

**Options considered (placement)**
- **Magnifier at the end of the stats strip, bar reopens in its own slot** — rejected: opening pushes the whole dashboard down 34px, so the numbers being read move as the reader reaches for the box.
- **Bar collapsed to a 28px strip in its own slot** — rejected: no layout shift, but it keeps a strip on screen and gives back none of the space.
- **Floating round button** — rejected: a shape this interface uses nowhere else, and it puts the click and its result in opposite corners.
- **CHOSEN: the magnifier at the end of the stats strip expands LEFTWARD into an input, inside the strip.** Nothing moves, because the strip is already that tall.

**Options considered (what opens)**
- The full bar — rejected by the user: "there is no reason to have the whole + selection because as soon as I type a text, it will search". On a dashboard whose facet columns ARE the picker, the `+` has no job.
- **CHOSEN: a bare box — magnifier, text, cancel.** The `+`, chips and autocomplete appear only once there are results to describe, i.e. in the dressed bar on the fact view.

**Options considered (when it fires)**
- Live, on the bar's existing 300ms debounce — rejected. Search flips the list to relevance, which auto-opens the first result, which REPLACES the dashboard: live search would delete the panel mid-word and force the input to survive that transition with its cursor.
- **CHOSEN: commit on enter.**

The two chosen halves reinforce each other: the known cost of expanding inside the strip is that the query cannot stay there — it must move to the bar when results arrive. With enter-commit that move happens exactly once, at the moment the whole panel is being replaced by the result view, so the jump is absorbed by a transition that was already happening. With live search it would have been a jump in the middle of typing.

**Keys**: `/` opens and focuses, `esc` closes, plus an × in the box — a keyboard-only exit strands whoever opened it by clicking. Both hints ride the bottom rail (StatusFooter) beside the `h now` it already carries, and the hint SWAPS to `esc close` while open, so the rail describes what the key does now.

**The rule that governs hiding**: the bar hides only when there is NOTHING TO SHOW — no free text and no non-path chips. A filter you cannot see is a filter you cannot remove. The load-bearing case is a search that returned zero results: freeText is set but no fact auto-opens, so the dashboard is still on screen and the bar MUST be visible or the query that emptied it is invisible. A lone `path:` chip does not keep the bar, because the left panel's header already shows and navigates the location.

**Non-scope**: this does not hide the bar on the fact view, and does not touch the not-live branch (an anchored view renders TrailBreadcrumb instead of the bar, unchanged).
