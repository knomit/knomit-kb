# macOS CFBundleVersion = HEAD committer epoch seconds (monotonic, for upgrade ordering)

The macOS app bundle's `CFBundleVersion` (in `tools/desktop/macos/Info.plist`, filled by the Makefile's `{{BUILD_VERSION}}` sed substitution) is the **HEAD commit's committer epoch seconds** — `git show -s --format=%ct HEAD`, e.g. `1782160423`. Definition in the Makefile:

    BUILD_VERSION := $(shell git show -s --format=%ct HEAD 2>/dev/null || echo 0)

`CFBundleShortVersionString` stays the marketing semver `{{SHORT_VERSION}}` = `$(VERSION)` (e.g. `0.5.0`).

**The hard requirement (overturns the prior decision):** macOS / LaunchServices use `CFBundleVersion` to ORDER builds for upgrade detection, so it MUST increase monotonically across releases — the user confirmed "I need upgrades to work." This invalidates the earlier rationale ("no auto-updater consumes CFBundleVersion, so non-monotonicity is harmless").

**The core conflict:** Apple requires `CFBundleVersion` to contain ONLY digits 0-9 and periods (≤3 integer components). A single legal integer can encode EITHER commit identity (the decimal SHA — unique but unordered) OR time-ordering (monotonic) — NOT both. The resolution is to stop overloading the field: `CFBundleVersion` carries the monotonic number; commit IDENTITY lives in `GIT_COMMIT` / `internal/version.Commit` (reported by `knomit version`, the REST `/api/v1/version`, and the UI badge) — not in the bundle version.

**Options considered** (resolved via AskUserQuestion):
1. *Decimal value of the short SHA* (`printf '%d' 0x<sha>`) — PREVIOUSLY CHOSEN, now REJECTED: legal and identity-preserving but UNORDERED, so upgrades can go backwards.
2. *Commit count* (`git rev-list --count HEAD`) — REJECTED: not monotonic across branches (feature-branch count can exceed master, then drop after a squash-merge), and collapses to `1` on shallow CI clones (`depth=1`).
3. *Build wall-clock timestamp* (`date -u +%s`) — REJECTED: bulletproof-monotonic but non-deterministic (same commit rebuilt → different version), fully decoupling the bundle version from any commit.
4. *Manual build counter* — REJECTED: easy to forget to bump.
5. *HEAD committer epoch* (`git show -s --format=%ct HEAD`) — CHOSEN. Monotonic by commit time, deterministic per commit (reproducible), survives shallow clones, a single legal integer ~1.78e9 (well under 2^32 — legal until ~2106). Caveat: cross-machine clock skew or rebuilding an OLD commit can invert ordering — negligible for this effectively-solo repo.

**Transition safety:** epoch values (~1.78e9) are always GREATER than any previously-shipped 7-hex decimal-SHA value (≤ 0xFFFFFFF = 268435455 ≈ 2.68e8), so a decimal-SHA→epoch upgrade is correctly seen as newer.

**Makefile gotcha (still relevant):** avoid POSIX `case` (and any unparenthesized-but-paren-containing syntax) inside Make `$(shell ...)` — Make's balanced-paren matching closes `$(shell` at the first bare `)`. The chosen form uses only `... || echo 0`, no parens.

**History:** PR #93 set `{{BUILD_VERSION}}` to `$(VERSION).$(GIT_COMMIT)` (illegal) → `40dbdb8` restore → `ff03b02` commit-count → `888e0b1` decimal-SHA → committer-epoch (THIS decision, supersedes decimal-SHA). The Makefile change for this decision is currently in the working tree atop `888e0b1`.
