# macOS CFBundleVersion = decimal-encoded short commit SHA (not the commit count)

The macOS app bundle's `CFBundleVersion` (in `tools/desktop/macos/Info.plist`, filled by the Makefile's `{{BUILD_VERSION}}` sed substitution) encodes the short git commit SHA as its DECIMAL value, e.g. short SHA `ff03b02` -> `267401986` (= `0xff03b02`). Definition in the Makefile:

    BUILD_VERSION := $(shell if [ "$(GIT_COMMIT)" = unknown ]; then echo 0; else printf '%d' 0x$(GIT_COMMIT); fi)

`CFBundleShortVersionString` stays the marketing semver `{{SHORT_VERSION}}` = `$(VERSION)` (e.g. `0.5.0`); only `CFBundleVersion` carries the build/commit distinguisher.

**Why the literal SHA can't be used (the hard constraint):** Apple/LaunchServices requires `CFBundleVersion` to contain ONLY digits 0-9 and periods, as <=3 period-separated integers. A git short SHA is hexadecimal (`a`-`f` letters), so it is fundamentally illegal there. Also note the broader binary version string `0.5.0.<sha>` has FOUR dotted components AND a hex tail -> doubly illegal as a CFBundleVersion. So the in-app/REST/CLI version (`internal/version.String()` -> `0.5.0.ff03b02`) and the macOS bundle version necessarily diverge in format.

**Options considered** (resolved in conversation during PR #93 review):
1. *Put the literal short SHA in CFBundleVersion* — REJECTED: illegal (hex letters), LaunchServices rejects it.
2. *Commit count* (`git rev-list --count HEAD`) — a legal single integer, claimed 'monotonically increasing'. REJECTED: it is NOT actually monotonic across branches (a feature branch count can exceed master then drop after a squash-merge), and it loses commit identity — you can't recover which commit a build came from.
3. *Decimal value of the short SHA* (`printf '%d' 0x<sha>`) — CHOSEN. A single legal integer, and the hex->dec map is unique and reversible (`printf '%x'` recovers the SHA), so the bundle version again identifies the EXACT build commit.

**Rationale for choosing decimal-SHA:** the user explicitly wanted commit IDENTITY back in the bundle version, prioritizing identity over update-ordering. Neither the count nor the decimal-SHA is truly monotonic, and there is no auto-updater (Sparkle/installer) consuming CFBundleVersion for upgrade comparison, so the non-monotonicity is harmless. For a 7-hex short SHA the decimal value is <= 0xFFFFFFF = 268435455 (< 2^32), comfortably within range. `unknown` (outside a git checkout) falls back to `0`.

**Makefile gotcha encountered:** the first attempt used a shell `case "$(GIT_COMMIT)" in unknown) ... ;; esac` inside `$(shell ...)`. Make does balanced-paren matching for `$(...)`, so the bare `)` after `unknown` PREMATURELY CLOSED the `$(shell` call, leaving `BUILD_VERSION` expanding to literal garbage (`echo 0;; *) printf ... esac)`). Fix: use an `if [ ... ]; then ...; else ...; fi` form, which has no bare `)` inside the shell text. Lesson: avoid POSIX `case` (and any unparenthesized-but-paren-containing syntax) inside Make `$(shell ...)`.

**History:** original PR #93 set `{{BUILD_VERSION}}` to `$(VERSION).$(GIT_COMMIT)` (illegal) -> commit `40dbdb8` 'restore macOS bundle version' -> commit `ff03b02` switched to commit-count `BUILD_NUMBER` -> commit `888e0b1` switched to decimal-SHA `BUILD_VERSION` (this decision). Supersedes the commit-count approach.
