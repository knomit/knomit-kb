# The native-lib cache is keyed per platform by GOOS-GOARCH — and GitHub scopes entries BY REF, so the first dev run after any key change is cold on every platform

`.github/actions/native-toolchain` caches `dist/<goos>-<goarch>/lib` on all three platforms (it was Windows-only until #226). Key: `native-libs-<goos>-<goarch>[-<rust target>]-<hashFiles('tools/fetchlibs/spec.go')>`.

GOOS-GOARCH rather than `runner.os`/`runner.arch` because it is the same pair that NAMES the directory being cached, so the key cannot drift from its contents.

THE RUST TRIPLE IS IN THE WINDOWS KEY ONLY, and that asymmetry is deliberate rather than an oversight. Windows BUILDS libtokenizers.a with cargo because upstream publishes no Windows artifact; ubuntu and macos download a published one and never run cargo, so there is no target to pin there. This is why "Read pinned native-lib versions" stays Windows-only. An MSVC-target .lib and a GNU-target .a are both called libtokenizers.a and only one links against mingw's ld, which is why the triple is named explicitly even though it is redundant with the spec.go hash.

TWO PATH SPELLINGS, ON PURPOSE. `LIBDIR` is absolute (cygpath -m converted on Windows) and is what the calling jobs' LD_LIBRARY_PATH/ORT_LIB_PATH consume. `LIBDIR_REL` is workspace-relative and is what the cache `path` uses, because that is the spelling actions/cache keys entries on and it is identical on all three runners. "Resolve native lib dir" MUST run before the restore: the cache path is `${{ env.LIBDIR_REL }}`, and a var written to $GITHUB_ENV only reaches the expression context of LATER steps.

CACHE ENTRIES ARE SCOPED BY REF — observed, not assumed. `gh cache list --json ref` at 2809e531 shows the same three keys existing TWICE, once on `refs/pull/226/merge` and once on `refs/heads/dev`. A PR can read the base branch's entries but saves its own, so a key that a PR warmed does NOT warm dev: the first dev run after any key change pays a cold save on every platform. Plan for that when changing the key or spec.go, and do not read a PR's green warm run as evidence that dev will be warm.

`make setup` STILL RUNS AFTER A HIT. The cache saves the download (and, on Windows, the cargo build) — not the step. fetchlibs is what decides the libs are present, and it prints "already present … skipping" on a hit.

NOT COVERED: the macOS-only `desktop` and `embed-smoke` jobs use inline steps rather than this composite action, so they still download both libs on every run. That is a known gap, not an oversight.
