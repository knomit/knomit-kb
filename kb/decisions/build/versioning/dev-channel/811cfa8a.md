# Dev builds version as <next patch>-dev.<committer epoch> via RELEASE_CHANNEL=dev; ordered for a future update channel but self-update stays OFF

The Makefile's `RELEASE_CHANNEL` (default `stable`) selects what `VERSION` means, and nothing else in the file branches on it:

    BASE_VERSION := 0.5.1                # last RELEASE; still the single source of truth
    RELEASE_CHANNEL ?= stable
    ifeq ($(RELEASE_CHANNEL),dev)
      VERSION := $(shell echo $(BASE_VERSION) | awk -F'[.]' '{print $$1"."$$2"."$$3+1}')-dev.$(BUILD_VERSION)
    else
      VERSION := $(BASE_VERSION)
    endif

`.github/workflows/release.yml` sets `RELEASE_CHANNEL: dev` at WORKFLOW level (not per step) so both build jobs, the Docker tag, and the release-notes step that shells out to `print-version`/`print-semver` cannot disagree about the version they are naming.

**The problem it fixes:** `VERSION` was a static constant and `dev-latest` is a ROLLING tag, so every dev build reported the same version as the last stable release — indistinguishable in `knomit version`, `GET /api/v1/version`, the UI badge, Finder Get Info, and artifact filenames, which collided outright with the real release's assets.

**Why next patch, not BASE_VERSION:** semver orders a prerelease BELOW its own release, so `0.5.1-dev.N < 0.5.1` would sort a dev build behind the release it was cut after. Bumping the patch first gives `0.5.1 < 0.5.2-dev.N < 0.5.2`. Still correct if the next release is a minor: `0.5.2-dev.N < 0.6.0`.

**Why BUILD_VERSION as the counter:** it is already the monotonic, deterministic, shallow-clone-safe HEAD-committer-epoch integer used for CFBundleVersion (see [[macos-cfbundleversion]]), and semver compares dot-separated NUMERIC prerelease identifiers numerically, so `dev.1000 > dev.999` rather than the lexical reverse. One notion of "which build is newer", not two that can disagree. Verified against `golang.org/x/mod/semver`, which `pkg/updater/internal/semver.Compare` thinly wraps.

**What this does NOT mean — the foreseeable misreading:** this did NOT turn on self-update for dev builds. Dev builds still ship an EMPTY `UPDATE_PUBLIC_KEY`, and that emptiness is precisely what makes `updaterConfig` in `tools/desktop/update.go` return `enabled=false`. The ordering exists so a dev channel COULD be built later. Adding `UPDATE_PUBLIC_KEY` to release.yml without also publishing a SIGNED dev appcast feed is strictly worse than no key, because pkg/updater's verification fails OPEN on releases carrying no verification block — see [[appcast-ed25519-single-provider]].

**Constraints a future editor must not break:**
- `print-semver` on the default stable channel must keep printing the bare `BASE_VERSION`, or `release-stable.yml`'s verify-version tag check fails on every tag.
- `awk -F'[.]'` not `-F.` (a bare `.` is a regex to some awks), and brackets not parens (Make closes `$(shell` at the first bare `)` regardless of quoting).
- `CFBundleShortVersionString` now carries the full `$(VERSION)`, so a dev bundle reads `0.5.2-dev.<epoch>` in Get Info. Apple documents that key as three period-separated integers, but it is a DISPLAY string; upgrade ordering is `CFBundleVersion`'s job and stays the bare epoch integer on both channels.

A live dev update channel would also change the risk profile: today a broken dev build is a manual download, but an auto-installing dev channel applies KB migrations that do not reverse.
