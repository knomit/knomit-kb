# fetchlibs retries 5xx, 429 and transport errors on a FIXED TOTAL BUDGET — Retry-After redistributes that budget, it never adds to it

A single 500 from the GitHub release CDN used to fail `make setup` and with it a whole CI job (job 105443136472). `httpGet` now retries: 4 attempts, doubling from 2s, so `retryBudget()` is 2+4+8 = 14s of waiting in the worst case.

RETRIED: transport errors (dial/TLS/response-header-timeout/reset), 5xx, and 429. NOT RETRIED: every other 4xx. The predicate is literally `>= 500 || == 429`, not `>= 400 && != 404`. A 404 means `spec.go` pins a release that does not exist — a wrong pin is not going to become right — while a rate limit is transient by definition.

THE BUDGET IS A CEILING ON THE TOTAL, NOT A PER-ATTEMPT CAP, and that is the part a hurried reader gets wrong. `nextWait(attempt, advice, spent)` takes the doubling backoff as a FLOOR, raises it to a server-supplied `Retry-After` when that is longer, then clamps to `retryBudget() - spent`. So the header cannot extend the total wait; it can only spend it sooner.

NON-OBVIOUS CONSEQUENCE, verified at 2809e531 by a test against an httptest server answering `Retry-After: 3600` on every request: a hostile rate limiter gets TWO attempts, not four. The first wait consumes the entire budget, the second failure finds nothing left, and `nextWait` returns a non-positive value which `httpGet` reads as "stop". That is correct — the alternative breaches the under-a-minute bound — but it is invisible from reading `nextWait` alone, so do not assume `fetchAttempts` attempts will actually be made.

A negative or unparseable `Retry-After` falls back to the normal backoff and NEVER to zero. `time.Sleep` returns immediately on a negative duration, so a zero would turn the backoff into a hot loop burning every attempt instantly against the rate limiter it was meant to back off from — the exact inverse of the intent.

THE RETRY IS ENTIRELY INSIDE `httpGet`, before any byte of a body is read. That is what keeps it compatible with the skip-if-present invariant: no partial write can occur, and the `writeFile` temp-then-rename discipline is untouched. The tests assert WHICH body came back for the same reason — a 500's error page is a perfectly well-formed file, and an atomic rename cannot catch it.

The bound test walks the whole schedule against a hostile header rather than computing the worst case from `backoffFor` alone: a `Retry-After` never passes through `backoffFor`, so a bound checked there stays green while a real job sleeps an hour.
