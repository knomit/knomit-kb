# The `frame` pragmatic type ships ALONE first (user rulings 2026-10-28): knomit adds the type and the same-subject candidate skip, mirroring signal; no-dedup and the `frames/` topic come from the mission template, which has no status key (abandoned = retracted); a frame's parents are the frames it refs (playbooks #11)

DECISION (user, 2026-10-28), for the arena design's frame (a mission's thinking-process node: kind pragmatic, type frame). The user asked for a PR that adds ONLY the type; materialize is a separate, later call.

RULINGS (each put to the user with options):
1. NO-DEDUP — mirror signal (CHOSEN) over a type check in learn.go. Knomit code adds the `frame` type and makes the same-subject refusal skip EXISTING frames as candidates (the one switch a topic setting cannot give, as for signal). Never deduplicating an INCOMING frame, and never letting it merge into or settle a nearby fact, comes from the mission template's `frames/` topic setting `learn_dedup: off`, not from the type.
2. WHERE `frames/` LIVES (and, as first ruled, a `status` key; see ruling 4) — the mission template (knomit-playbooks), like annotations (CHOSEN) over built into knomit. Knomit ships only the type.
3. PARENT RULE — first ruled as waiting for materialize, then settled (user, 2026-10-28, knomit-playbooks #11): a frame's parents are the frames it refs (any ref whose target is a frame, read at the commit its edge pins), and a frame may have several. materialize (#675) implements this: the frame you are at is the child; in a same-commit mutual pair the frame you are at is the child and no cycle-detection code exists (see the last UPDATE). No `context.parent` key, no 'the first frame ref is the parent', and the template does not require a frame to have a parent. Rejected: a `context.parent` key enforced at write; 'the first frame ref is the parent'.
4. STATUS REMOVED; ABANDONED = RETRACTED (user, 2026-10-28, knomit-playbooks #11). The question 'abandoned = retract (spec 09) vs D31 (abandoned/stalled, abandoned/budget are not retractions)' was first left open, as belonging to the template's status key. The user then ruled that a retracted frame IS the abandoned one and removed `context.status` from the template, because nothing reads it. A frame has no status; do not add one to express abandonment.

CONSEQUENCES. Being pragmatic already keeps a frame out of synthesis seeding and review dedup, and every type is revisable in place and retractable, so the type adds no code for those. Without the template's `learn_dedup: off`, frames under `frames/` WILL be merged by the in-category dedup (two sibling frames, or an observation folded into a frame) and an incoming frame can settle a nearby hypothesis: the type alone does not protect them.

MISREADINGS. 'Frames are never deduplicated because of their type' — only the CANDIDATE side of the same-subject refusal is type-based; the rest depends on the topic setting. 'A frame's first frame ref is its parent' — no such rule; every ref whose target is a frame makes that frame a parent, and there may be several.

UPDATE (user, 2026-10-28, knomit-playbooks PR #9): the mission template's `frames` topic sets `learn_dedup: off`, carries a validation that only `fact.type === 'frame'` may be written under `frames/` (the signal topics' pattern), and declared `context.status` as an enum open/resolved/abandoned that was NOT required (superseded: playbooks #11 removed the status key, see the last UPDATE). Frames become writable only once BOTH the knomit type (PR #668) and the template (playbooks #9) have shipped, plus a knomit submodule bump.

UPDATE: shipped in #668, merged to dev as 1eb481b6. The type half is as ruled: `Frame Type = "frame"` is in PragmaticTypes and AllPragmaticTypes in internal/domain/fact/pragmatic_type.go; findSameSubjectCandidates skips an EXISTING frame candidate by type, beside the signal and hypothesis skips, in internal/edge/mcp/learn_same_subject.go; the schema gloss is the factTypeDocs entry in internal/edge/mcp/factschema.go, which says an incoming frame is NOT exempt from dedup or merge unless its topic sets learn_dedup: off; the UI has a typeStyles entry in web/src/utils.ts and a TypeIcon case in web/src/icons.tsx; the pragmatic type table in spec/mbekg.md has a frame row. Nothing in the type changes how an INCOMING frame is handled.

The template half shipped in knomit-playbooks #9 (merged 2026-10-28): the mission template's `frames` topic sets `learn_dedup: off`, and validates `fact.type === 'frame'` for everything written under frames/. A frame is therefore protected from merge, same-subject refusal of the incoming write and hypothesis settlement only in a repo whose ontology comes from that template; a frame written under any other topic gets the type's behaviour alone.

UPDATE (user, 2026-10-28, knomit-playbooks #11, merged): the template's `frames` topic no longer declares `context.status`, and its README and ontology comment now say a frame's parents are the frames it refs (any ref whose target is a frame), and a frame may have several. User rulings: a retracted frame IS the abandoned one; status is removed because nothing reads it; a parent is any ref to a frame. The template change is in playbooks #11; this fact does not say which template revision any knomit build pins. Frames are writable in a mission repo only from a build that has the `frame` type (#668) AND a template copy that has the `frames` topic.

UPDATE (parent rule as merged in #675, materialize): materialize is the only code that uses the parent concept; the type, the template and learn enforce nothing about it. A frame's parents are the frames it refs; the frame you are at is the child. Each ref is read at the commit its DERIVED_FROM edge pins (the latest version under unpin), so a cited version precedes or shares the commit of the citing one, and there can be SEVERAL parents; nothing validates them. materialize orders a frame's ancestors by a depth-first post-order from the starting frame over its frame refs in refs order (every parent before the frames that cite it); a breadth-first pass decides only inclusion and the fact cap. In a same-commit mutual pair the frame you are at is the child and the other frame is its parent; no cycle-detection code exists, a ref to an already-visited frame is a back-reference. The full ruling is kb/decisions/materialize/rulings/16ccefe6.md; the code is `ancestors` in internal/corpus/materialize/frames.go at the #675 merge.

DOES NOT MEAN: the older frame is the parent, or that a frame must ref a parent to be valid.
