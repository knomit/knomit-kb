# The `frame` pragmatic type ships ALONE first (user rulings 2026-10-28): knomit adds the type and the same-subject candidate skip, mirroring signal; no-dedup, the `frames/` topic and the `status` key come from the mission template; the parent rule waits for materialize; abandoned-vs-retract stays open

DECISION (user, 2026-10-28), for the arena design's frame (a mission's thinking-process node: kind pragmatic, type frame). The user asked for a PR that adds ONLY the type; materialize is a separate, later call.

RULINGS (each put to the user with options):
1. NO-DEDUP — mirror signal (CHOSEN) over a type check in learn.go. Knomit code adds the `frame` type and makes the same-subject refusal skip EXISTING frames as candidates (the one switch a topic setting cannot give, as for signal). Never deduplicating an INCOMING frame, and never letting it merge into or settle a nearby fact, comes from the mission template's `frames/` topic setting `learn_dedup: off`, not from the type.
2. WHERE `frames/` AND `status` LIVE — the mission template (knomit-playbooks), like annotations (CHOSEN) over built into knomit. Knomit ships only the type.
3. PARENT RULE ('every non-root frame refs a parent frame') — defined with materialize (CHOSEN): no parent concept and no enforcement in the type PR. Rejected for now: a `context.parent` key enforced at write; 'the first frame ref is the parent'. Reason: a frame also refs sibling frames and ancestor decisions, so 'the parent' is ambiguous until the code that needs it (materialize) exists.
4. ABANDONED = RETRACT (spec 09) vs D31 ('abandoned/stalled', 'abandoned/budget' are not retractions) — LEFT OPEN; it belongs to the template's status key, not to the type.

CONSEQUENCES. Being pragmatic already keeps a frame out of synthesis seeding and review dedup, and every type is revisable in place and retractable, so the type adds no code for those. Without the template's `learn_dedup: off`, frames under `frames/` WILL be merged by the in-category dedup (two sibling frames, or an observation folded into a frame) and an incoming frame can settle a nearby hypothesis: the type alone does not protect them.

MISREADINGS. 'Frames are never deduplicated because of their type' — only the CANDIDATE side of the same-subject refusal is type-based; the rest depends on the topic setting. 'A frame's first frame ref is its parent' — no such rule exists yet.

UPDATE (user, 2026-10-28, knomit-playbooks PR #9): the mission template's `frames` topic sets `learn_dedup: off`, carries a validation that only `fact.type === 'frame'` may be written under `frames/` (the signal topics' pattern), and declares `context.status` as an enum open/resolved/abandoned that is NOT required. The user kept both the type rule and the optional status. Still open: what `abandoned` implies; no parent key or rule in the template. Frames become writable only once BOTH the knomit type (PR #668) and the template (playbooks #9) have shipped, plus a knomit submodule bump.
