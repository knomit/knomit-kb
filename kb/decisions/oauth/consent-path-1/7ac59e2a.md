# OAuth consent without accounts, path 1: /oauth/authorize PARKS the request and shows only its id; an operator decides with `knomit oauth approve <id> --as <subject> [--scopes …]` or `deny`; the browser's /wait long-poll wakes on the decision and collects the code once

CHOSEN (F19 phase 3a, plan Global Constraints + master rulings D12/D13, 2026-09-23; extended in 3b, 2026-09-24): knomit has no user table, so consent is an operator act on the instance, not a login form. Path 3 (external IdP) is 3c.

FLOW: /oauth/authorize validates everything, then stores a PENDING row (10 min) carrying WHO ASKED — client id and name, requester RemoteAddr and User-Agent, redirect_uri, requested scopes, resource — and renders a page naming the id (no form, no auto-approval) that refreshes to /oauth/authorize/{id}/wait. /wait long-polls (30 s) and is woken in-process the moment Approve or Deny runs; on approval it mints the code and 302s to the redirect_uri with code, state and iss; on denial or expiry it sends access_denied. A second /wait on a completed request is 410.

THREE WAYS TO DECIDE (all end in Issuer.Approve / Issuer.Deny, so grants, ceiling and the waiter wake-up are identical):
1. `knomit oauth pending|approve <id> --as <subject> [--scopes …]|deny <id>` over the local socket/pipe (3a).
2. The web UI's Manage → Authorizations tab (3b), which calls the same REST endpoints from the browser with the same-origin proof (kb/decisions/oauth/browser-approval-proof); decided_by anonymous@none. The tab exists only where the server has an issuer (GET /api/v1/oauth/pending 404 hides it); the desktop never opens the OAuth listener and builds NO issuer (app.Options.NoOAuth, set by desktopAppOptions), so it never shows the tab.
3. Consent path 2 (3b): a master-key signed statement delivered to the public POST /oauth/approve, from the operator's own machine (`knomit oauth approve|deny <id> --sign …`, `approve --signed`); decided_by master:<root fp8> (kb/invariants/oauth/signed-approval-statement). The public GET /oauth/pending/{id} gives the signer the requester-supplied fields and their digest.
All three were exercised live against Claude Code 2.1.281 on 2026-09-24 (phase 3b Task 5).

WHY THE REQUESTER FIELDS: a URL client_id proves domain ownership, not which local process is asking (kb://bc6eac5f37df/kb/gotchas/ai/agents/tools/mcp/security/client-identity/066a9dad.md). The operator judges the requester, and PKCE binds the code to whoever started the flow. The panel and the --sign printout show the redirect HOST first; the RemoteAddr/User-Agent are those of the BROWSER that opened the link, not of the client program.

APPROVE: the operator names the subject (1–128 chars of letters, digits and . _ @ + -, starting alphanumeric); the principal is host:<subject>@token (oauth.TokenPrincipal, keyed in grants by String()). CEILING = --scopes when given (any of read, write, push:own, merge:main, operator — NEVER admin; an empty list is refused), else requested ∩ {read, write}, else read (oauth.DefaultCeiling), in one canonical order. Clients ask for everything advertised (Claude Code requests all five), so the panel pre-checks the default, never the requested set, and --sign signs the default explicitly. Approve writes grants for the principal for every ceiling permission, granted_by = the approving principal, BEFORE recording the decision: a decision that loses a race leaves grants the operator intended, never a token with nothing behind it. A revoked token loses everything at once; the grants stay for the next token of that subject (operator choice).

BOUND: /oauth/authorize is unauthenticated on a proxied listener, so at most 100 undecided unexpired requests may wait (temporarily_unavailable beyond); expired rows are purged at each create. There is deliberately NO per-IP rate limit on /oauth/token: behind a same-host proxy every caller is 127.0.0.1 and one bucket is a lockout tool (master ruling D14).

MISREADING TO AVOID: approve/deny/pending being CLI commands does not make them loopback-only by themselves. What restricts them is the gate on their REST endpoints (local socket/pipe principals, or the proven browser holding admin) and, for path 2, the master key's signature.
