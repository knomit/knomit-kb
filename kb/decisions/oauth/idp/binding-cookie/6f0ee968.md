# knomit's FIRST cookie is a per-request browser BINDING for consent path 3, not a session: set by /oauth/authorize only when [oauth.idp] is configured, named knomit_idp_<hash of the pending id>, HttpOnly, SameSite=Lax, Secure on https, Path = <issuer path>/oauth/idp/, 10 min; its SHA-256 sits on the request; nothing reads it as identity

OPTIONS (F19 phase 3c; worker W1 + reviewer B1, master rulings 2026-09-24): (a) no cookie, the pending id alone keys the provider sign-in (the plan as drafted); (b) a nonce cookie set at /oauth/idp/start (reviewer); (c) a binding cookie set at /oauth/authorize, the moment the browser that asks is known (worker).

CHOSEN: (c), replacing (b). With (a) anyone holding the pending id — the requester, i.e. a possible attacker — can hand the start link to someone else. With (b) a forwarded start link still works in the victim's browser (it would get its own nonce at start). With (c) start, callback and the decide POST all require the cookie that PARKED the request, so a forwarded start link fails in every other browser before GitHub is contacted, and a GitHub callback URL started in one browser fails in another (login CSRF, RFC 6749 §10.12's binding of state to the user agent).

ATTRIBUTES AND WHY:
- Name per request (knomit_idp_ + 16 hex of sha256(pending id)): one fixed name let a second authorize in the same browser overwrite the first — Claude Code with two knomit MCP servers does exactly that (test: two parked requests in one jar both complete).
- SameSite=Lax, not Strict: the provider callback is a cross-site top-level GET and must carry it.
- Path = issuer path + /oauth/idp/: the path the BROWSER sees. With issuer https://h/knomit the proxy strips /knomit before the listener (3a deployment rule), but the browser matches the unstripped path.
- HttpOnly; Secure iff the issuer is https (an http issuer is loopback-only by config); Max-Age = the request's 10 min; cleared by the decide POST.
- Stored as hex SHA-256 in oauth_pending_idp (a side table: the control migration chain admits idempotent CREATE only), compared constant-time.

WHAT THIS DOES NOT MEAN: the cookie is not authentication and not a session — the identity is proven at the provider each time, and kb://bc6eac5f37df/…/security/sessions ('sessions are never authentication') still holds. It does not change the plain listener's browser-approval proof, which relies on knomit setting no AUTHORITY-bearing cookies: cookies are not port-isolated, so on a localhost setup the plain listener also receives this one, but only under /oauth/idp/, which it does not serve, and it grants nothing there. And it does not defend a victim who opens an attacker's authorize URL themselves — that browser gets a valid cookie; the consent page is that case's defence.
