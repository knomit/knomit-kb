# Replay of a signed OAuth approval is refused by the PENDING ROW (decide only an undecided row) as the real guard; the in-memory table of statement hashes is a bounded, pruned belt that a restart may empty

OPTIONS (phase 3b Task 3; reviewer S3):
- (a) persist a replay table in control.db;
- (b) keep it in memory only and rely on the pending row;
- (c) no table.

CHOSEN: (b).

WHY THE ROW IS ENOUGH:
- Approve and Deny decide a request only while its decision is empty, in one UPDATE … WHERE decision = '' (Store.Decide).
- So a second statement for the same id gets ErrNotPending (409), whatever any table says. That includes after a restart: TestSignedApprove_Replay empties the table and still gets ErrNotPending.
- A pending request lives 10 minutes, and a statement's window ends at most 10m + 5m ahead. A statement cannot outlive the row it decides by more than the skew.

WHY A TABLE AT ALL: it answers an honest double delivery with a clearer error (ErrReplayed) and refuses before any row lookup.

THE TABLE:
- It is keyed by sha256 of the statement BYTES, not the signature. Ed25519 signatures are deterministic, but keying on the bytes makes the table independent of the signature encoding.
- An entry is forgotten at expires + skew.
- It is capped at replayTableMax (1024). When full after pruning it answers ErrReplayTableFull (503).
- Inserting needs a VALID master-key signature, so the cap is not an unauthenticated-growth defence. It keeps a leaked master key from also being a memory lever.

MISREADING TO AVOID: the table is not what makes replay safe. Removing it would weaken nothing but the error message. Removing the WHERE decision = '' guard would make replays work.
