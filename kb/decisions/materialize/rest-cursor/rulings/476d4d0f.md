# Decided (user, 2026-10-29): REST materialize pages through the SAME server-side cursor as MCP knomit_materialize (human audience) — order frozen on the first call, a cursor refuses every other argument, pages are whole facts under the 32 KiB budget, the payload is the MCP human page unchanged, cursors are owned by endpoint + principal; the agent-document route is the Export, sent as an attachment

The user's final rulings for the REST paging route the materialize UI streams from (branch feat/materialize-rest-cursor, stacked on PR #680):

1. SAME CURSOR AS MCP. Server-side cursor streaming exactly like knomit_materialize. A materialization never comes back in one shot through the paging route, because it can overrun a model's context; the UI streams it with infinite scroll.
2. ORDER FROZEN ON THE FIRST CALL. The walk and the render order are computed once, on the first call, and stored as a cursor (tool_sessions + tool_queue). Later calls take ONLY the cursor; a cursor plus any other argument is refused, so changing options means a new first call. The freeze is load-bearing because cross_kb foreign targets and unpin refs resolve to LATEST versions, which move: every page must come from one snapshot.
3. PAGES ARE WHOLE FACTS, under the same ~32 KiB budget MCP uses (materialize.PageCap); a fact larger than the budget is sent alone; a page never splits a fact.
4. SAME PAYLOAD AS MCP: the REST page JSON is the MCP human-audience page with the same field names and structure (the UI's TypeScript types are written against it). Fields missing for the UI are added to BOTH surfaces identically; one shared builder is preferred over two copies.
5. FIRST-CALL PARAMETERS: depth (default 4, max 10), max count (default 200, max 500), cross_kb, unpin, and the commit or branch being viewed (materialize as of the viewed commit).
6. OWNERSHIP: cursors are owned by endpoint + principal (the #680 model); another owner reads the cursor as expired and the refusal consumes nothing. Reach as in #675: a caller cannot materialize what it cannot read, cross_kb follows only repos the caller reaches, and unauthorized and nonexistent repos answer the same.
7. EXPORT: the existing REST agent-document route sends Content-Disposition: attachment with filename `<slugged title, up to 48 chars>-<id8>.md`. Export is always the whole materialization at the chosen depth and count; building it in memory is acceptable (about 2 MB at 500 facts).
8. OpenAPI documents the new route and the header.

SECOND ROUND (user, 2026-10-29, on the PR #683 open questions):
9. PAGE SIZE: `limit` (1-5, default 3) is accepted on the FIRST call only and frozen in the cursor; a later REST call passing `limit` is still a 400. knomit_materialize (human audience) takes the same limit and keeps the first call's on every resume, so REST and MCP pages stay byte-identical for the same input at every limit.
10. COMPRESSION: text/markdown is a compressible content type, so the export is gzip-compressed.
11. STATUS: every cursor that cannot be served stays a 404, never a 410: a 410 would say that the cursor once existed.
12. PAGE 1 TEXT: REST page 1 keeps the `instructions` text (byte identity with MCP).

WHAT THIS DOES NOT MEAN: the agent-document route is NOT the streaming source (it is the one-shot export, for saving a file), and the pages route is not a second, REST-specific payload: a field renamed or added on one surface only breaks the UI's types.
