# FactSet fact identity = 64-bit FNV-1a FactHash(repo id12, path), the anchor f-<16 hex>; a collision is DETECTED by a second independent 64-bit check hash stored beside each key (8 bytes), not by storing (repo, path), to keep the cache inside its per-FactSet budget

The plan (PR C, factset-streaming-plan.md section 2) said the written set maps hash -> (repo, path) so a collision fails the call with a 500 instead of dropping a subtree. As built (factset_plan.go: factHash, factCheck; factset.go applyUnit and reserve; fsState.lookup), every map keyed by FactHash (results, reserved, written) stores factCheck(repo, path), FNV-1a over path, 0xff, repo, beside its value; a lookup or insert whose check differs returns ErrFactIdentity (500) and logs. Reason: (repo, path) costs about 60 bytes per entry and the written set reaches 250k entries at the rulings' maxima (500 units x 500 facts), past the 16 MiB per-FactSet cache target; the check hash costs 8. An undetected collision now needs both independent 64-bit hashes to collide.

The written set also keeps blob64 (the first 64 bits of the written blob) so a back link's different_version is computed server-side without holding the blob.

CONSEQUENCE: a test that forces a collision must replace FactHash only (SetFactHashForTest); the check hash is deliberately not replaceable. F22 pins it.

WHAT THIS DOES NOT MEAN: anchors are not unique per appearance: every appearance of a fact shares f-<16 hex>, so only a written (or unavailable) section emits <a id> in the export.
