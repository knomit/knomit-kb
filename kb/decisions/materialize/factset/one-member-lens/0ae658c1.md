# Decided (user, 2026-11-02, #709 M1, then fix/one-member-lens-shape): a one-member lens is a LENS for FactSets: cross_kb=true is refused, the no-filter title is "All in lens <lens>", and since fix/one-member-lens-shape the engine serves it through the lens facade over a single sub, so its pages have a multi-member lens's shape

Question (review of #709, M1): a one-member lens is not Binding.IsLens (it federates across nothing), so FactSetFirstPage served it on the repository path; there cross_kb=true was ACCEPTED and its title was the write repo's ("All facts in <repo>"), while the OpenAPI text and facts 19eda5cd / 4d18d5a0 said cross_kb on a lens is always a 400.

OPTIONS:
(a) treat it as a lens: refuse cross_kb and give it the lens title, like a multi-member lens;
(b) let it act like its repo: accept cross_kb and keep the repo title, and correct the docs to say "a lens of two or more members".

CHOICE: (a). RATIONALE: the user's principle that a lens is a virtual repo whose UX is as close to a repo's as possible; and that the lens SURFACE stays uniform: whether a lens has one member or five must not change what the lens accepts or how it names itself. A caller who adds a second member to a lens must not see cross_kb start failing or the title change.

AS BUILT (#709, merged at 3f4a8b84): FactSetFirstPage refuses CrossKB when the binding IsLens() || FromLens(), BEFORE the IsLens dispatch, with the one text "cross_kb is not accepted on a lens factset" (the check moved out of lensFactSetFirstPage, so it is defined once); the repository path uses FactSetLensTitle(..., Binding.Name()) when FromLens(). The units, sections and pages stay the write repo's (still the repository path; pin lens:<uid>).

SUPERSEDED IN PART (user ruling 2026-11-02, verbatim: "lens HAS TO BE consistent, no matter how many repos are in it."; #727, squash-merged at 1ffc89bd): the 'AS BUILT' paragraph's repo path is gone. FactSetFirstPage dispatches on materialize.LensFactSet(b) = b.FromLens() || b.IsLens(), so a one-member lens goes to lensFactSetFirstPage: a facade over ONE sub, v2 row, the fused lens search, env.anchors {write id12: anchor}, repo_name on every unit root. cross_kb is refused inside that branch, before any read. The repo path no longer checks FromLens at all (no lens title, no checkRepoNarrowing: that function is deleted; a repository refuses any repo= with "repo is only accepted on a lens"). The edges wire the lens list's embedder (REST lensEmbed + lensMotifClusters, MCP fanoutQueryVec) on the same predicate. Tests: TestLensFactSet_OneMemberLensHasTheMultiMemberShape (REST), TestLensFactSet_OneMemberLensRESTIsTheMCPFactSetInTheMultiMemberShape (REST == MCP, export), TestFactSet_Contract_OneMemberLensIsTheLensFacadeWithTheLensPin (MCP); review additions TestLensFactSet_OneMemberLensNonTopicPathAgreesWithTheLensList, TestLensFactSet_OneMemberNeverSyncedWriteIsEmptyAsAMultiMemberLens and the white-box wiring tests TestFactSetRequest_OneMemberLensGetsTheLensWiring / TestFactSetSearchWiring_OneMemberLensGetsTheLensEmbedder. (Refs re-pinned to 1ffc89bd.)

WHAT THIS DOES NOT MEAN: IsLens is not redefined; it still means breadth (gotcha 5b18e905) and session instructions for a lens-of-one stay single-repo. LensFactSet is the FactSet-only predicate. A repository's own FactSet still accepts cross_kb.
