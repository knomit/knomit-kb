# Decided (user, 2026-11-02, #709 M1): a one-member lens is a LENS for FactSets: cross_kb=true is refused (400 on REST, the same tool error on MCP) and the no-filter title is "All in lens <lens>", although the engine still serves it on the repository path with the write repo's units

Question (review of #709, M1): a one-member lens is not Binding.IsLens (it federates across nothing), so FactSetFirstPage served it on the repository path; there cross_kb=true was ACCEPTED and its title was the write repo's ("All facts in <repo>"), while the OpenAPI text and facts 19eda5cd / 4d18d5a0 said cross_kb on a lens is always a 400.

OPTIONS:
(a) treat it as a lens: refuse cross_kb and give it the lens title, like a multi-member lens;
(b) let it act like its repo: accept cross_kb and keep the repo title, and correct the docs to say "a lens of two or more members".

CHOICE: (a). RATIONALE: the user's principle that a lens is a virtual repo whose UX is as close to a repo's as possible; and that the lens SURFACE stays uniform: whether a lens has one member or five must not change what the lens accepts or how it names itself. A caller who adds a second member to a lens must not see cross_kb start failing or the title change.

AS BUILT (feat/lens-factset-rest, after #707/#708): FactSetFirstPage refuses CrossKB when the binding IsLens() || FromLens(), BEFORE the IsLens dispatch, with the one text "cross_kb is not accepted on a lens factset" (the check moved out of lensFactSetFirstPage, so it is defined once); the repository path uses FactSetLensTitle(..., Binding.Name()) when FromLens(). The units, sections and pages stay the write repo's (still the repository path; pin lens:<uid>).

WHAT THIS DOES NOT MEAN: a one-member lens does not go through the lens facade (no anchors map, no fused search); IsLens still means breadth (gotcha 5b18e905), and FromLens is the provenance test used here. A repository's own FactSet still accepts cross_kb.
