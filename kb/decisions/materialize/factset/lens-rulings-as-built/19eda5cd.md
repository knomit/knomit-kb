# Lens FactSet rulings Lens 1-7 as built in F3: the not-followed leaf is {path kb://<member>/..., reason lens_repo, repo_name}; cross_kb=true is ErrInvalid; no blob dedupe; env.anchors; 'All in lens <lens>'; since_fork = write member only; search.repo narrowing; repo_name on unit roots

The user's lens rulings (2026-11-01, factset-lens-design section 8) and the wording rulings S1-S6 (2026-11-01), as implemented (F3 #706, strings in #708, REST routes and the one-member-lens ruling in #709):

- Lens 1: a ref from a sub into ANOTHER lens member is never followed and nothing of it is read. classify (factset_plan.go) checks planner.lensRepos (every member id12 -> repo name, frozen in the v2 row) BEFORE the cross_kb gate and emits not_included {"path":"kb://<member id12>/<rel>" (or the bare path when the member is the lens write repo, the canonical wire form), "reason":"lens_repo", "repo_name":"<member's repo name at creation>"}. The reason token is lens_repo (S1). The agent export renders the leaf exactly "<repo name> `<rel path>`" with nothing after it (S2). A ref to a repo OUTSIDE the lens is the plain cross_kb_off omission, as on a repo FactSet. The leaf does not count toward the N.k reservation (subs run CrossKB off).
- Lens 2: cross_kb=true on a lens FactSet of ANY size (a one-member lens included, user ruling 2026-11-02, kb/decisions/materialize/factset/one-member-lens/0ae658c1.md) is ErrInvalid "cross_kb is not accepted on a lens factset" (S3; MCP tool error; REST 400 "Invalid request" with this text), before any read. Checked in FactSetFirstPage on IsLens() || FromLens() before the IsLens dispatch.
- Lens 3: no blob dedupe; the same path is write-first through federate.WriteFirstWinners; the same blob at two paths stays two roots (TestLensFactSet_NoBlobDedupeAcrossForks).
- Lens 4: lens pages carry env.anchors {member id12: anchor} for the members the search read; env.anchor stays the write member's. Keyed by id12, not name (10a3bcc0: ids on the wire; names only as labels beside them).
- Lens 5: the no-filter title is "All in lens <Binding.Name()>" (FactSetLensTitle) for a lens of ANY size (the repo path uses it too when FromLens()); filtered titles follow the repo rules.
- Lens 6: since_fork reads ONLY the write member's leg, with the edge's PathsIn; other members' legs return nothing (NoResults makes every leg empty). repo= is FactSetSearch.Repos (JSON "repos", MCP search key "repo", whose tool description is "Lens endpoints only: search only these member repos, by name (the lens list's repo filter)." (S6)), passed as FusedQuery.Repos, so the FactSet equals the narrowed lens list; an unknown name is the lens list's own UnknownRepoError text as ErrInvalid. The search line spells the narrowing "in <names>", comma-separated, e.g. "in alpha, beta" (S5). On the repo path: a one-member lens accepts only its write repo's name (any other is the UnknownRepoError text); a binding that is not a lens refuses any repo with exactly "repo is only accepted on a lens" (S4). A one-member lens stays on the repo path (its units and pages are the write repo's), but is a lens there: no cross_kb, the lens title.
- Lens 7: every unit root of a lens page carries "repo_name" (frozen); node.repo (id12) was already on every node.

CONSEQUENCE: all six visible strings are ruled; change none without asking. Tests pin them exactly: TestLensFactSet_RefIntoAnotherMemberIsANotFollowedLeaf (S2 export line, S3), TestFactSet_RepoNarrowingOnTheRepoPath (S4), TestSearchLine_LensNarrowing and TestLensFactSet_TitleNarrowingAndSinceFork (S5).

WHAT THIS DOES NOT MEAN: MCP does not accept since_fork in factset mode (it never did); the REST lens route (#709) does, ONLY when the lens pins its write member to an experiment branch (exp/...): it then reads that experiment's changes since its fork, and the other members contribute nothing. A lens whose write member sits at its agent branch answers since_fork with the repo route's 400 "Not an experiment" (TestLensFactSet_SinceForkReadsTheWriteMembersExperiment).
