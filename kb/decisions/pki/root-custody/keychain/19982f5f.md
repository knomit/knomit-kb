# The fleet root key lives in the OS keychain under service "knomit", account "fleet-root/<RootID>" (RootID = fingerprint of the root's OWN Ed25519 key, read from root.crt), with the passphrase-encrypted <dir>/root.key as the fallback; export-root MOVES the key by default and is CLI-only

Fleet design D9, built in internal/pki/custody.go (branch feat/pki-root-custody).

SCHEME. One keychain item per root: service `knomit`, account `fleet-root/<RootID>`. RootID is `pki.RootID(root.crt)` = `pki.Fingerprint` of the root certificate's Ed25519 public key (64 hex, SSH wire encoding) — the same value the CRL watermark is keyed by and `identity install --root` takes. It is computed from the key, never parsed from any name. The item holds the root key UNENCRYPTED as OpenSSH PEM (~400 bytes). Library: github.com/zalando/go-keyring v0.2.8 (MIT; macOS `security -i` over stdin, Windows Credential Manager, Linux Secret Service).

OPEN. `OpenRoot(dir, kc, pass)` reads `<dir>/root.crt` FIRST (it names the item), tries the item, and returns the source (`keychain` | `file`). It falls back to `<dir>/root.key` + passphrase when the keychain errors in ANY way (not found, locked, no Secret Service). It does NOT fall back when an item EXISTS but holds another key — that is an error. Neither present → `ErrNoRootKey`, naming the item and the file. The passphrase callback is called only for the file path.

CREATE. `CreateRoot` (init-master) writes root.crt O_EXCL, then `kc.Set`; on any Set error it writes the encrypted root.key (needs a passphrase) or removes root.crt and fails. With a keychain, NO root.key is written: the operator's only copy is the keychain until `export-root --keep`.

EXPORT/IMPORT. `export-root --out <file>` writes the encrypted key (root.key format) followed by the root cert PEM, O_EXCL 0600, reads it back and decrypts it, and only then (unless --keep) deletes the keychain item AND root.key. It refuses without --out and without a terminal on stdin. `import-root <file>` stores into the keychain (file fallback), writes root.crt if missing, refuses a dir holding a DIFFERENT root. No HTTP route or UI exists for either.

CLI. init-master/enroll/revoke/oauth sign go through OpenRoot; --dir defaults to `<home>/master`; --passphrase-file is needed only for file custody (oauth sign still reads it first, as its consent step).

CONSEQUENCES. To find the key you need root.crt; a master dir without root.crt cannot open a keychain-held root. After a default export the machine can no longer enroll/revoke — that is the point (no two masters by accident).

MISREADING. 'Keychain first' does not mean a bad keychain item is skipped: a mismatched item fails closed. And the fallback file is not a backup made automatically: with a working keychain there is no file.
