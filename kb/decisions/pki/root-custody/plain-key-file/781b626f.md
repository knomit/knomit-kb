# The fleet root key is a plain, unencrypted OpenSSH-format file <home>/fleet/root.key (mode 0600, in an owner-only directory), like ~/.ssh/id_ed25519: no OS keychain, no passphrase, no prompt; since PR #525 the key moves between machines only by the master switch, GET then PUT /api/v1/fleet/root on the LOCAL listener (no other export or import); a lost or replaced key is a fresh fleet

Fleet design 1.8, built in PR #519 (merge 72919aa0). It REPLACES the keychain custody of PR #512 (OS keychain item with a passphrase-encrypted root.key fallback, export-root/import-root, --passphrase-file), which was deleted whole (internal/pki/custody.go, go-keyring).

THE DECISION. The fleet root's Ed25519 private key is <home>/fleet/root.key: OpenSSH private-key format (ssh.MarshalPrivateKey), UNENCRYPTED, created O_EXCL with mode 0600, in a directory made owner-only (privdir.Ensure, then privdir.Verify; see the privdir.Verify invariant). root.crt sits beside it. The model is the SSH private key: whoever can read the file can sign for the fleet, exactly as with ~/.ssh/id_ed25519.

WHAT IT MEANS, stated in full:
- NO keychain, NO passphrase, NO prompt for the key. Every root operation (identity init-root, enroll, revoke, and oauth approve|deny --sign) reads the file directly through pki.LoadRoot(dir) and asks for nothing. (The y/N on --sign is consent to ONE approval, not custody; --yes skips it.)
- THREAT MODEL = the operating system's file permissions on the owner-only directory and the 0600 file. It is not protection against code running as the same user, against root/Administrator, or against a backup or copy that is made world-readable. Windows has no meaningful file mode: there the directory's protected DACL is the only protection (kb/gotchas/windows/filesystem/mode-bits-and-dacl-inheritance/81f38acc.md).
- The key NEVER leaves custody through any route: export-root and import-root do not exist, no HTTP route, MCP tool, UI or desktop binding reads, loads or exports it (only cmd/identity.go and cmd/oauth_sign.go call LoadRoot, both CLI). One route WRITES a fresh key: POST /api/v1/fleet/create, since PR #518 (merge 537f2019), local listener only (RequireLocalVia); see the UPDATE paragraph. An operator who copies the directory by hand (cp -r, a backup) is outside the product; LoadRoot then refuses a copy that landed wider than 0600/0700 (see the privdir.Verify invariant).
- A key that is lost or replaced is a FRESH FLEET START: a new root orphans every certificate the old one issued, so there is no recovery path, no re-keying and no migration. NewRoot refuses to run over an existing root.key OR root.crt ("refusing to replace the fleet root"). Back up by copying the directory somewhere only you can read.
- Older material is not migrated: a passphrase-encrypted root.key from an older build is refused with an error naming `ssh-keygen -p -N '' -f <path>`; a key held in an OS keychain is simply not read.
- A missing root.key is pki.ErrNoRootKey = this machine is not the fleet root. Other instances hold root.crt alone.

STILL TRUE AFTER THIS DECISION: manual `identity enroll`, `install` and `revoke` remain until the fleet membership verbs land; `identity show` is unchanged.

OPTIONS REJECTED: keep the keychain (the master's unattended duties, renewal and CRL re-sign, cannot answer a prompt, and a keychain adds a platform matrix of failure modes); a passphrase on the file (same unattended problem, and a passphrase file beside the key guards nothing); export-root/import-root (every export is a second copy of the one secret that ends the fleet).

MISREADINGS. 'Plain file' does not mean 'any permissions': the 0600 file in an owner-only directory is the whole protection and is enforced on create and on load. 'No export' does not mean the key cannot be backed up: it means no knomit command moves it. 'Unencrypted' does not mean the key is exposed to other local users.

UPDATE (PR #518, merge 537f2019): a SECOND CALLER OF NewRoot. Besides `identity init-root`, Manager.CreateFleet (internal/repos/fleet_create.go) calls pki.NewRoot, but on the STAGING directory <home>/fleet.creating, not on <home>/fleet, and renames the staging directory to <home>/fleet only near the end of the create (an EMPTY <home>/fleet is removed first). NewRoot's Ensure-then-Verify therefore runs on the staging directory; the owner-only mode or DACL travels with the rename (stated by the review follow-up; Windows CI was green; not re-measured here), and LoadRoot verifies <home>/fleet again afterwards. The key is regular-file 0600 in both places. A create that fails or dies removes the root it made, and only when <home>/fleet's root.crt carries the root id on the create marker, so it never deletes an operator's own root. The create refuses any NON-EMPTY <home>/fleet (root_present), so 'a lost or replaced key is a fresh fleet' still means: move the old directory away yourself, then create. MISREADINGS: 'No route touches the key' is now 'no route reads or exports it'; the create route writes it and answers with the fleet's status, never the key. 'LoadRoot is called by create': it is not; create keeps the minted root in memory (the staging directory's files are read as PEM only) and the master test (isFleetMaster) later only Stats root.key (a regular file) and reads root.crt; it never opens the key.

UPDATE (PR #525, verified at merge commit fd991d4f): THE KEY NOW MOVES, BY ONE ROUTE PAIR, AND `identity init-root|enroll|revoke` ARE GONE. 'The key NEVER leaves custody through any route' and 'no HTTP route reads or exports it' (above) are FALSE: `GET /api/v1/fleet/root` returns the contents of <home>/fleet (root.key, root.crt, crl.pem, issued.jsonl, revoked.jsonl) in the response body, `Cache-Control: no-store`, and `PUT /api/v1/fleet/root` writes them on another instance. Both are served on the local authenticated listener only (RequireLocalVia: unix socket or named pipe; 403 for an mTLS peer and a loopback browser page, tested for every route including a check that no key appears in any refused body) and both take fleetOpMu. The sequence is the master switch: GET on the old master, PUT on the new one (refused with 409 `root_present` while <home>/fleet holds ANY entry; also `unknown_file`, `root_incomplete`, `root_invalid`; the files land in a private staging directory <home>/fleet.receiving, pki.LoadRoot checks key and certificate are one root, then a rename), then the new master points its copy at the forge or becomes the hub, then DELETE /fleet/root on the old one (stand-down: deletes <home>/fleet, keeps the membership, refused with `hub` while the copy has no origin). The new instance is the master only once the root.crt it installed equals the root on the fleet's main; nothing checks the other side, and one master at a time is the operator's job (kb/decisions/fleet/two-masters-unsupported/daea77c9.md). Decommission deletes <home>/fleet, root key included. The production readers of the key are now pki.LoadRoot in enroll, revoke and the PUT's staging check (internal/repos/fleet_membership.go) and in cmd/oauth_sign.go; fleet create still mints it (NewRoot on the staging directory). MISREADINGS: 'no export means the key cannot be copied by knomit' is false for GET /fleet/root; a client of that route holds the one secret that ends the fleet, so it is a trusted-local-process route by design (issue #521 would add a second factor before it may be remote). The 'STILL TRUE' line about manual `identity enroll`, `install` and `revoke` above is obsolete: they are the enroll, join and revoke routes.
