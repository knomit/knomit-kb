# The fleet root key is a plain, unencrypted OpenSSH-format file <home>/fleet/root.key (mode 0600, in an owner-only directory), like ~/.ssh/id_ed25519: no OS keychain, no passphrase, no prompt, and no export or import — the key never leaves custody by any route; a lost or replaced key is a fresh fleet

Fleet design 1.8, built in PR #519 (merge 72919aa0). It REPLACES the keychain custody of PR #512 (OS keychain item with a passphrase-encrypted root.key fallback, export-root/import-root, --passphrase-file), which was deleted whole (internal/pki/custody.go, go-keyring).

THE DECISION. The fleet root's Ed25519 private key is <home>/fleet/root.key: OpenSSH private-key format (ssh.MarshalPrivateKey), UNENCRYPTED, created O_EXCL with mode 0600, in a directory made owner-only (privdir.Ensure, then privdir.Verify; see the privdir.Verify invariant). root.crt sits beside it. The model is the SSH private key: whoever can read the file can sign for the fleet, exactly as with ~/.ssh/id_ed25519.

WHAT IT MEANS, stated in full:
- NO keychain, NO passphrase, NO prompt for the key. Every root operation (identity init-root, enroll, revoke, and oauth approve|deny --sign) reads the file directly through pki.LoadRoot(dir) and asks for nothing. (The y/N on --sign is consent to ONE approval, not custody; --yes skips it.)
- THREAT MODEL = the operating system's file permissions on the owner-only directory and the 0600 file. It is not protection against code running as the same user, against root/Administrator, or against a backup or copy that is made world-readable. Windows has no meaningful file mode: there the directory's protected DACL is the only protection (kb/gotchas/windows/filesystem/mode-bits-and-dacl-inheritance/81f38acc.md).
- The key NEVER leaves custody through any route: export-root and import-root do not exist, there is no HTTP route, MCP tool, UI or desktop binding that touches it (only cmd/identity.go and cmd/oauth_sign.go call LoadRoot, both CLI). An operator who copies the directory by hand (cp -r, a backup) is outside the product; LoadRoot then refuses a copy that landed wider than 0600/0700 (see the privdir.Verify invariant).
- A key that is lost or replaced is a FRESH FLEET START: a new root orphans every certificate the old one issued, so there is no recovery path, no re-keying and no migration. NewRoot refuses to run over an existing root.key OR root.crt ("refusing to replace the fleet root"). Back up by copying the directory somewhere only you can read.
- Older material is not migrated: a passphrase-encrypted root.key from an older build is refused with an error naming `ssh-keygen -p -N '' -f <path>`; a key held in an OS keychain is simply not read.
- A missing root.key is pki.ErrNoRootKey = this machine is not the fleet root. Other instances hold root.crt alone.

STILL TRUE AFTER THIS DECISION: manual `identity enroll`, `install` and `revoke` remain until the fleet membership verbs land; `identity show` is unchanged.

OPTIONS REJECTED: keep the keychain (the master's unattended duties, renewal and CRL re-sign, cannot answer a prompt, and a keychain adds a platform matrix of failure modes); a passphrase on the file (same unattended problem, and a passphrase file beside the key guards nothing); export-root/import-root (every export is a second copy of the one secret that ends the fleet).

MISREADINGS. 'Plain file' does not mean 'any permissions': the 0600 file in an owner-only directory is the whole protection and is enforced on create and on load. 'No export' does not mean the key cannot be backed up: it means no knomit command moves it. 'Unencrypted' does not mean the key is exposed to other local users.
