# The CRL rollback watermark is kept PER ROOT, keyed by pki.Fingerprint of the root key — not globally (breaks moving to another fleet) and not reset on a root change (lets an old bundle roll a root back by bouncing through another fleet)

CONTEXT. An instance refuses a CRL whose Number is lower than one it already accepted, so a validly signed OLD crl.pem cannot un-revoke a serial. The first cut of F19 phase 2 kept ONE number in `crl.number` and in the reloader's memory. The review of #252 reproduced the failure: `knomit identity install --replace-root` (moving an instance to another fleet) deleted crl.number on disk, but the RUNNING server's in-memory watermark still held the old fleet's number, so the new fleet's CRL #1 was rejected as a 'rollback' and the server silently kept trusting the OLD root — admitting every certificate it ever signed — until a restart, while the CLI said the change was live.

OPTIONS (decided by the master session, 2026-09-22):
1. Global watermark. Breaks root replacement: every new fleet's numbering starts at 1 and is a 'rollback'.
2. Reset the watermark on any root change, unkeyed (the first fix proposed). Reopens rollback by a BOUNCE: install fleet A's CRL #7, move to fleet B, then re-install an OLD fleet-A bundle carrying CRL #3 — the reset on each move forgets A's #7, and #4..#7's revocations are undone.
3. Per-root keying. CHOSEN.

SHAPE: `crl.number` is a JSON object `{RootID: "<decimal Number>"}`. `pki.RootID(root)` = `pki.Fingerprint` of the root's Ed25519 key — the one fingerprint definition, NEVER the CommonName (two unrelated roots may share one; the test fleets all do). `AcceptedNumber(dir, root)` reads that root's entry; `RecordAcceptedNumber` only ever RAISES it and keeps every other root's entry. The reloader's effective watermark is max(in-memory for that root, on-disk for that root), so a failed persist still protects the running process. An install (`pki.InstallBundle`) checks the bundle's CRL against the BUNDLE's root entry and deletes nothing when it moves an instance to another root. A garbled crl.number, including the old single-number format, fails closed.

UPDATE (PR #525, verified at merge commit fd991d4f): the `knomit identity install --replace-root` verb is gone with the whole identity enroll/install CLI. In the product an install of ANOTHER root no longer exists: POST /api/v1/fleet/join passes `InstallOptions{}` and refuses with `trust_installed` while ANY of root.crt, crl.pem or instance.crt is present in [tls].dir, and the way to another fleet is leave (or decommission) first, which runs `pki.Uninstall`. `Uninstall` removes only instance.crt, crl.pem and root.crt and KEEPS crl.number, which is filed per root, so a later install of the SAME root (a rejoin) is still checked against that root's old watermark and cannot roll the CRL back; a different root is unaffected. MISREADING: uninstall does not reset the watermark, and a leave-then-rejoin is not a way to un-revoke by presenting an older CRL. The only writer of the local revocation copies is now `pki.RecordRevocation` (the directory wrapper `pki.Revoke` was deleted).

TESTS, each red under the named sabotage: `TestServerConfig_ReplaceRootWhileRunningMovesToTheNewFleet` (a running server moves to B with no restart and refuses A's certificate server-side) and `TestServerConfig_WatermarkIsPerRootSoABounceCannotRollBack` (A #7 → B #1 → A #3 refused → A #8 adopted) go red under a global key and under a CN key; `TestIdentity_InstallRefusals` goes red when install restores the unkeyed reset or checks the INSTALLED root's entry instead of the bundle's.

MISREADING TO AVOID: per-root does not mean 'a new root is trusted automatically' — the new set must still verify internally (certificate chains to the new root, CRL signed by it) and arrives only by an operator writing the pki dir. And it does not weaken rollback protection within a root: the same root with a lower Number is refused exactly as before.
