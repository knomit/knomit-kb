# A knomit instance's CRL is fail-closed when MISSING or malformed, ENFORCED-and-warned when stale, never adopted when older than the highest Number already accepted — and that Number is persisted in crl.number so a restart cannot roll a revocation back

Four CRL states, four different answers, decided with the master session for F19 phase 2 (2026-09-22).

1. MISSING or MALFORMED: fail closed. `ServerConfig` returns ErrCRLMissing / ErrCRLInvalid and `knomit serve` does not open the TLS listener; `VerifyInstanceChain` with a nil CRL refuses every peer. An instance that cannot tell whether a peer is revoked must not admit it.
2. STALE (NextUpdate passed): adopted, ENFORCED, and warned (`tls_crl_stale`). Refusing it would turn 'the operator has not published lately' into 'every peer is refused'; accepting it but ignoring its list would un-revoke everything. Enforcing the last known list is the only reading that is safe in both directions.
3. OLDER (Number lower than the highest accepted): NOT adopted; the previous list stays in force and the attempt is logged as ErrCRLInvalid '... (rollback)'. A validly-signed old CRL is exactly what an attacker with write access to the pki dir, or a careless copy, would put in place to un-revoke a serial.
4. NEWER: adopted on the next handshake without a restart; its Number is written to `<dir>/crl.number` (0600, atomic).

WHY crl.number EXISTS: without it the rollback guard lives only in memory and a restart forgets it — the restarted server would accept the older file in state 3 as if it were fresh. `TestServerConfig_RestartRemembersTheCRLNumber` pins that. A GARBLED crl.number is an error, not 'none': resetting to accept-any is the rollback it exists to stop. If persisting fails, the newer list is enforced anyway and the operator is warned (`tls_crl_number_unpersisted`); only the restart protection is lost.

MASTER SIDE: `revoked.jsonl` is the revocation list and `crl.pem` is a PROJECTION of it; `Revoke` appends, then reissues from the whole log with Number+1, so a reissue can never drop an earlier revocation.

RELOAD MECHANICS: the reloader reads the three files (instance.crt, root.crt, crl.pem) on EVERY handshake and compares BYTES with the current set — a few KB, and immune to mtime granularity and inode reuse — and adopts a changed set only WHOLE: if any part fails, the previous set stays, so the listener never runs a new root with an old CRL. Revocation also reaches RESUMED TLS 1.3 sessions, because crypto/tls calls VerifyConnection on the PSK path too (handshake_server_tls13.go ~1033); the test asserts DidResume was actually true on the refused handshake.

MISREADING TO AVOID: 'stale is accepted' does NOT mean stale is ignored, and 'missing is fatal' applies to the SERVER listener and to every verification — there is no fallback to 'no revocation checking', the HTTPS twin of the SSH known_hosts rule that forbids an insecure fallback.
