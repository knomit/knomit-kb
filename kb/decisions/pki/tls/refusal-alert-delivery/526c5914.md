# A refused mTLS handshake is made to DELIVER its bad_certificate alert (server half-closes and drains before closing) plus one client redial on a post-handshake Windows reset/abort; a reset is never itself counted as a refusal (#543, user choice a+c)

CONTEXT (#543). On a Windows CLIENT, the TLS 1.3 refusal alert of knomit's mTLS listener could be lost: the client finishes its handshake before the server judges its certificate and writes its HTTP request; the server's VerifyConnection refuses, crypto/tls sends bad_certificate, and net/http's failed-handshake path closes the socket at once (no closeWriteAndWait). Closing with the client's request unread, or receiving it after close, makes the server's stack send RST, and Windows drops the queued, not-yet-read alert: wsarecv 10054 (WSAECONNRESET) or 10053 (WSAECONNABORTED) at the first read. Measured on Win10: ~1-3 per 2000 naturally, 100% with a 20 ms client delay after the handshake.

OPTIONS CONSIDERED.
(a) Server side: wrap the raw TCP listener UNDER tls.NewListener; a connection whose handshake VerifyConnection refused closes by CloseWrite (FIN after the alert), a bounded drain, then Close, so the RST never races the alert.
(b) Client side, Windows only: count a reset/abort right after the handshake (no application data yet) as ErrRefusedByPeer.
(c) Client side: on such a reset, redial ONCE before returning the error.
(d) combinations.

CHOICE: (a) + (c).

RATIONALE. (a) keeps "refusal = the bad_certificate alert" true, so the refusal-classes invariant (kb/invariants/fleet/sync/refusal-classes/7c861da6.md) is untouched and there is no new false-`revoked` risk (a false revoked stops a healthy member's sync). Measured: 0 resets in 2000 parallel probes and 100% alert even with the 20 ms delay. (c) covers version skew: a host that predates (a) still resets, but the alert wins ~99.9% of single attempts, so one redial makes a lost alert rare; a reset is still never named a refusal.

WHY (b) LOST. classifyFleetRefusal needs the "tls: bad certificate" text for `revoked`, so (b) alone yields `other` and no sync stop; making it yield revoked means changing invariant 7c861da6. It names crashes, restarts and middlebox resets as refusals (false positives, and a false revoked halts sync until restart). It contradicts joinReachErr's documented choice (a reset after the handshake is `unreachable`, 502, not bundle_refused) and ClassifyPeerError's rule that a bare EOF/drop is never mapped to a refusal.

NON-SCOPE. No change to error classification, ErrRefusedByPeer mapping, the refusal classes or invariant 7c861da6. The #258 sweep's NetConn().Close() of an established connection stays a HARD close (only handshake-refused connections linger). The redial is at most one, only before any application data is received (never mid-transfer).
