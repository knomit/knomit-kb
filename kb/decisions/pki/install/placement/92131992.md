# Enrollment install and show orchestration lives in internal/pki (InstallBundle, PreviewBundle, InstalledRoot, SplitBundle, Status), not in cmd and not in internal/app: both the CLI and the desktop's Settings bindings call it, it needs no server, and pki stays import-free by taking (dir, keyPath) instead of a config

`knomit identity install` and `identity show` used to do their work in package `cmd` (`installBundle`, `splitBundle`, `showIdentity`, `writeAtomic`). The desktop app ships without the `knomit` CLI and cannot import `cmd`. So knomit#256 moved that orchestration into `internal/pki`:
- `InstallBundle(dir, keyPath, raw, InstallOptions{ExpectInstalledRoot})` (since knomit#299; it was `replaceRoot bool` before)
- `PreviewBundle(keyPath, raw)` (knomit#299): the checks that read only the bundle and the key, returning the root and principal to show for confirmation
- `InstalledRoot(dir)` (knomit#299): the installed root as a caller reads it to show and to pass as ExpectInstalledRoot — none for a missing root.crt, an error naming the file for an unreadable one
- `SplitBundle(raw)`
- `Status(dir, keyPath)`

Both `cmd/identity.go` and the desktop's Wails bindings call them. There is therefore ONE set of install checks: key match, chain, the installed root is the one the caller expected, and the per-root CRL watermark. Since knomit#299 the installed-root check and the writes run under a cross-process lock beside the pki dir; see kb/invariants/pki/install/expected-root-under-lock/eac8d325.md and the decision kb/decisions/pki/install/expected-root-under-lock/b86086b2.md.

Why `pki` and not `internal/app`: the orchestration needs no server, handler or boot state, only the pki directory and the key path. `pki` imports no knomit package, and it stays that way by taking strings, not a `config.Config`. (That is also why the cross-process file lock, `pki.LockFile`, lives in pki and the bridge imports it, rather than pki importing a shared lock package.) Consequence for a caller: resolve `[tls].dir` and the key yourself (`cfg.TLS.Dir`, `app.ResolveKeyPath(cfg)`). Anything that depends on `[tls].addr` stays in the caller, such as the CLI's "add [tls] addr" hint and its `tls_listener:` line. Collecting the user's consent to a root (the desktop's root_unconfirmed / root_differs confirmation, the CLI's --root / --yes / prompt) is also the caller's; pki takes only the root the caller saw.

REFUSALS ARE CLASSIFIED, so a UI can name the problem without showing the bundle:
- `ErrMalformedBundle`
- `ErrKeyMismatch`
- `ErrRootDiffers`, as `*RootDiffersError` carrying the root found installed (empty RootInfo when none) and the bundle's, each with CommonName and RootID fingerprint
- `ErrCRLRollback`
- `ErrCRLInvalid`
- a `VerifyInstanceChain` sentinel

`RootDiffersError.Error()` names only fingerprints and no CLI flag. The CLI formats its own messages from the typed error. For every other class, `Error()` is the text the CLI printed before the move.

THE WRITE GUARANTEE IS SCOPED to verification: a VERIFICATION failure leaves `<pki>` exactly as it was. That covers its bytes, file modes, mtimes and the directory's own mode, and on a fresh home the directory is not created at all. This is why `MkdirAll`/`Chmod(0700)` run after every check. The install lock file is `<pki>.lock`, a SIBLING, precisely so this still holds; only `<pki>`'s parent may be created (0700) to hold it, which means that parent must be writable.

This ordering was the #256 move's one declared behaviour change. Before it, the CLI created or re-moded the directory before the same-root and CRL checks. `TestIdentity_RefusedInstallLeavesThePKIDirAlone` is red on the pre-move code.

An I/O failure BETWEEN the three renames can still leave a mixed set. The reloader adopts only a set that verifies together, and the next install repairs it. So do NOT read the guarantee as "install is atomic".

An installed `root.crt` that exists but does not load (or is not Ed25519) FAILS CLOSED, always (since knomit#299; before, replace mode let it through), and both front ends refuse it via InstalledRoot before asking anything. Only a missing file means "no root installed". The way out is removing the file, which the error names.

The writes use pki's own `writeFileAtomic`, which writes a uniquely named temp file per target and renames it into place. The old cmd `writeAtomic` used a fixed `<name>.tmp` that a concurrent CLI and desktop install could collide on. It was deleted rather than moved, so pki keeps a single atomic writer.

Misreadings to avoid:
- `Status` is not a verifier. It reads the certificate with `IdentityOf`, which checks neither the chain nor the CRL, so it must never decide trust. Nor is it the way to read the root to pass as ExpectInstalledRoot: it reports an unreadable root.crt as absent. Use `InstalledRoot`.
- `PreviewBundle` passing does not mean the install will: it reads nothing installed (no root comparison, no CRL watermark).
