# Enrollment install and show orchestration lives in internal/pki (InstallBundle, SplitBundle, Status), not in cmd and not in internal/app: both the CLI and the desktop's Settings bindings call it, it needs no server, and pki stays import-free by taking (dir, keyPath) instead of a config

`knomit identity install` and `identity show` used to do their work in package `cmd` (`installBundle`, `splitBundle`, `showIdentity`, `writeAtomic`). The desktop app ships without the `knomit` CLI and cannot import `cmd`. So knomit#256 moved that orchestration into `internal/pki`:
- `InstallBundle(dir, keyPath, raw, replaceRoot)`
- `SplitBundle(raw)`
- `Status(dir, keyPath)`

Both `cmd/identity.go` and the desktop's Wails bindings call them. There is therefore ONE set of install checks: key match, chain, same root unless replacing, and the per-root CRL watermark.

Why `pki` and not `internal/app`: the orchestration needs no server, handler or boot state, only the pki directory and the key path. `pki` imports no knomit package, and it stays that way by taking strings, not a `config.Config`. Consequence for a caller: resolve `[tls].dir` and the key yourself (`cfg.TLS.Dir`, `app.ResolveKeyPath(cfg)`). Anything that depends on `[tls].addr` stays in the caller, such as the CLI's "add [tls] addr" hint and its `tls_listener:` line.

REFUSALS ARE CLASSIFIED, so a UI can name the problem without showing the bundle:
- `ErrMalformedBundle`
- `ErrKeyMismatch`
- `ErrRootDiffers`, as `*RootDiffersError` carrying both roots' CommonName and RootID fingerprint
- `ErrCRLRollback`
- `ErrCRLInvalid`
- a `VerifyInstanceChain` sentinel

`RootDiffersError.Error()` names only fingerprints and no CLI flag. The CLI formats its own `--replace-root` message from the typed error. For every other class, `Error()` is the text the CLI printed before the move. A differential run of the old and new `knomit` binaries through one install/show/refusal flow gave byte-identical output and identical pki files.

THE WRITE GUARANTEE IS SCOPED to verification: a VERIFICATION failure leaves `<pki>` exactly as it was. That covers its bytes, file modes, mtimes and the directory's own mode, and on a fresh home the directory is not created at all. This is why `MkdirAll`/`Chmod(0700)` run after every check.

This ordering was the move's one declared behaviour change. Before it, the CLI created or re-moded the directory before the same-root and CRL checks. `TestIdentity_RefusedInstallLeavesThePKIDirAlone` is red on the pre-move code.

An I/O failure BETWEEN the three renames can still leave a mixed set. The reloader adopts only a set that verifies together, and the next install repairs it. So do NOT read the guarantee as "install is atomic".

An installed `root.crt` that exists but does not load FAILS CLOSED unless replacing. Only a missing file means "no root installed". Treating a garbled one as absent would skip the same-root check and admit any fleet's bundle.

The writes use pki's own `writeFileAtomic`, which writes a uniquely named temp file per target and renames it into place. The old cmd `writeAtomic` used a fixed `<name>.tmp` that a concurrent CLI and desktop install could collide on. It was deleted rather than moved, so pki keeps a single atomic writer.

Misreading to avoid: `Status` is not a verifier. It reads the certificate with `IdentityOf`, which checks neither the chain nor the CRL, so it must never decide trust.
