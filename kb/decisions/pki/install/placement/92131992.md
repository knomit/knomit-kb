# Enrollment install and show orchestration lives in internal/foundation/pki (InstallBundle, PreviewBundle, InstalledRoot, SplitBundle, Status), not in cmd and not in internal/app: the fleet create and join call it (the CLI and the desktop bindings did when it was moved), it needs no server, and pki stays import-free by taking (dir, keyPath) instead of a config

`knomit identity install` and `identity show` used to do their work in package `cmd` (`installBundle`, `splitBundle`, `showIdentity`, `writeAtomic`). The desktop app ships without the `knomit` CLI and cannot import `cmd`. So knomit#256 moved that orchestration into `internal/pki`:
- `InstallBundle(dir, keyPath, raw)` (first-install only; it took `InstallOptions{ExpectInstalledRoot}` from knomit#299 until PR #536 removed the parameter, and `replaceRoot bool` before that)
- `PreviewBundle(keyPath, raw)` (knomit#299): the checks that read only the bundle and the key, returning the root and principal to show for confirmation
- `InstalledRoot(dir)` (knomit#299): the installed root as a caller reads it to show (it was also the value passed as ExpectInstalledRoot until #536) — none for a missing root.crt, an error naming the file for an unreadable one
- `SplitBundle(raw)`
- `Status(dir, keyPath)`

When #256 moved it, `cmd/identity.go` and the desktop's Wails bindings called InstallBundle; at present its only callers are the fleet create (internal/corpus/repos/fleet_create.go) and the fleet join (internal/corpus/repos/fleet_membership.go), pinned by test/archtest TestInstallBundleHasOnlyTheListedCallers. There is therefore ONE set of install checks: key match, chain, no root installed (any installed root refuses), and the per-root CRL watermark. Since knomit#299 the installed-root check and the writes run under a cross-process lock beside the pki dir; see kb/invariants/pki/install/expected-root-under-lock/eac8d325.md and the decision kb/decisions/pki/install/expected-root-under-lock/b86086b2.md.

Why `pki` and not `internal/app`: the orchestration needs no server, handler or boot state, only the pki directory and the key path. `pki` imports no knomit package, and it stays that way by taking strings, not a `config.Config`. (That is also why the cross-process file lock, `pki.LockFile`, lives in pki and the bridge imports it, rather than pki importing a shared lock package.) Consequence for a caller: resolve `[tls].dir` and the key yourself (`cfg.TLS.Dir`, `app.ResolveKeyPath(cfg)`). Anything that depends on `[tls].addr` stays in the caller, such as the CLI's "add [tls] addr" hint and its `tls_listener:` line. Collecting any consent to a root is also the caller's (the desktop root_unconfirmed / root_differs confirmation and the CLI --root / --yes / prompt that once did it are gone; the join's supplying of the bundle is the consent).

REFUSALS ARE CLASSIFIED, so a UI can name the problem without showing the bundle:
- `ErrMalformedBundle`
- `ErrKeyMismatch`
- `ErrRootDiffers`, as `*RootDiffersError` carrying the root found installed (empty RootInfo when none) and the bundle's, each with CommonName and RootID fingerprint
- `ErrCRLRollback`
- `ErrCRLInvalid`
- a `VerifyInstanceChain` sentinel

`RootDiffersError.Error()` names only fingerprints and no CLI flag. The CLI formats its own messages from the typed error. For every other class, `Error()` is the text the CLI printed before the move.

THE WRITE GUARANTEE IS SCOPED to verification: a VERIFICATION failure leaves `<pki>` exactly as it was. That covers its bytes, file modes, mtimes and the directory's own mode, and on a fresh home the directory is not created at all. This is why `MkdirAll`/`Chmod(0700)` run after every check. The install lock file is `<pki>.lock`, a SIBLING, precisely so this still holds; only `<pki>`'s parent may be created (0700) to hold it, which means that parent must be writable.

This ordering was the #256 move's one declared behaviour change. Before it, the CLI created or re-moded the directory before the same-root and CRL checks. `TestIdentity_RefusedInstallLeavesThePKIDirAlone` is red on the pre-move code.

An I/O failure BETWEEN the three renames can still leave a mixed set. The reloader adopts only a set that verifies together, and the next install repairs it. So do NOT read the guarantee as "install is atomic".

An installed `root.crt` that exists but does not load (or is not Ed25519) FAILS CLOSED, always (since knomit#299; before, replace mode let it through), and both front ends refuse it via InstalledRoot before asking anything. Only a missing file means "no root installed". The way out is removing the file, which the error names.

The writes use pki's own `writeFileAtomic`, which writes a uniquely named temp file per target and renames it into place. The old cmd `writeAtomic` used a fixed `<name>.tmp` that a concurrent CLI and desktop install could collide on. It was deleted rather than moved, so pki keeps a single atomic writer.

Misreadings to avoid:
- `Status` is not a verifier. It reads the certificate with `IdentityOf`, which checks neither the chain nor the CRL, so it must never decide trust. Nor is it the way to read the root to pass as ExpectInstalledRoot: it reports an unreadable root.crt as absent. Use `InstalledRoot`.
- `PreviewBundle` passing does not mean the install will: it reads nothing installed (no root comparison, no CRL watermark).

UPDATE (PR #518, merge 537f2019): THE THIRD CALLER. Manager.CreateFleet installs this instance's own leaf, the fresh root and an empty CRL through the same pki.InstallBundle, with InstallOptions{} (ExpectInstalledRoot "" = it expects NO root installed). It does not use PreviewBundle, InstalledRoot or any confirmation: the material was minted a moment earlier by the same call, so there is nothing for a user to confirm. Its own pre-flight (trust_installed) refuses when root.crt, crl.pem or instance.crt exists in [tls].dir, by Lstat of the three files, not through InstalledRoot; if another install lands in between, InstallBundle's own check under the lock refuses with RootDiffers and the create rolls back, leaving the foreign files alone (TestCreateFleet_ForeignInstallIsLeftAlone). The caller list is pinned by test/archtest TestInstallBundleHasOnlyTheListedCallers (kb/invariants/desktop/fleet/install-surface/a46bbb69.md). MISREADING: 'the install is only for operators who confirm a root': the create route is the one caller that never asks, because it is the root's origin.

UPDATE (PR #525, merge fd991d4f): `cmd/identity.go` no longer calls anything here (the `knomit identity install` verb, `installBundle` and `showIdentity`'s install half were deleted; `knomit identity show` stays and reads pki.Status). The callers are the desktop bindings, the fleet create and the fleet join (internal/repos/fleet_membership.go), which runs SplitBundle and PreviewBundle first and then InstallBundle with InstallOptions{}. The package gained the inverse, `pki.Uninstall(dir)`: it removes instance.crt, crl.pem and root.crt under the SAME install lock, treats an absent file as fine, keeps crl.number (per-root watermark) and the instance key, and is what leave, decommission, a refused join's undo and the create rollback's fresh-trust removal call. Its effect on a running listener: kb/invariants/pki/established-connections/9928b5a7.md. MISREADING: 'verification failure leaves <pki> exactly as it was' does not extend to a join that fails AFTER the install (clone, root, record or push refusal): that one is undone by Uninstall, which removes the three files but not the lock file or crl.number.
