# pki.InstallBundle takes InstallOptions{ExpectInstalledRoot} instead of a replaceRoot bool and decides the install against the root the CALLER SAW, under a cross-process file lock kept OUTSIDE <pki>; a first install (expected "") is shown and confirmed like a replace, in the desktop binding and in the CLI (--root / --yes / tty prompt) — issue #299

Issue #299 (follow-up to #256/#296) reported two gaps in fleet enrollment. Verified at dev b3a9ec46: (1) a FIRST install is decided by the mere absence of root.crt (internal/pki/install.go:176-177) and nothing is shown to the user before the write: the desktop binding with an empty confirm pair goes straight to pki.InstallBundle (tools/desktop/identity.go:243) and the CLI prints the principal only AFTER installing (cmd/identity.go:244); (2) with replaceRoot=true the root comparison at install.go:182 is SKIPPED entirely, the only comparison lives in the desktop binding BEFORE the call (identity.go:229-240), the binding's installMu is in-process only (its own comment at :214-215 says a concurrent CLI install "gets pki's atomic renames"), and pki holds no lock, so a `knomit identity install --replace-root` landing between the binding's read and its InstallBundle call is silently overwritten with the bundle the user confirmed against a root that is no longer installed. The same check-then-act gap exists without replace between :176 and the writes at :214-218. Also, replace mode tolerated an UNREADABLE installed root (install.go:179-181).

OPTIONS CONSIDERED
1. Leave it: the desktop-vs-CLI window is seconds wide and the atomic renames keep the files consistent.
2. Pass the expected installed-root fingerprint into InstallBundle and compare at install.go:176, no lock: closes the confirmed-pair gap, leaves a millisecond TOCTOU.
3. Option 2 plus a cross-process file lock (flock / LockFileEx, lifted from tools/bridge/knomitapi/credlock_{unix,windows}.go) held across read-compare-write; the lock file outside <pki> so a refused bundle still leaves <pki> absent.
4. Keep the replaceRoot bool alongside the expected fingerprint.

RATIONALE (the designer's, 2026-09-26)
Option 3. "Compare under its own lock" in the issue presumes a lock that does not exist; it must be added, and about forty lines of the bridge's credlock already do it portably. Making the expected root the ONLY input makes replace a consequence rather than a mode: expecting the current root while supplying a different bundle root IS the replace, so option 4's bool is redundant and its skip-the-compare behaviour is exactly the bug. Empty expected means "no root installed", which lets a first install go through the same confirmation shape as a replace: the binding refuses with a new class root_unconfirmed carrying the bundle root fingerprint and the instance principal (kind:fp@cert from IdentityOf, no free text), and the confirm call sends ("", bundleFP). The CLI cannot prompt when the bundle is on stdin, so it gets --root <fp> for the out-of-band value, --yes to accept what is printed, a y/N prompt only on a terminal with a file bundle (os.Stdin ModeCharDevice, no x/term dependency), and otherwise refuses naming the fingerprint and the flags. Unreadable root is always refused now: reading it as "none" under replace would admit any fleet's bundle.

THE CHOICE
InstallBundle(dir, keyPath, raw, InstallOptions{ExpectInstalledRoot}) under a cross-process lock; callers are the desktop binding and cmd/identity.go only (pinned by test/archtest/install_callers_test.go). Renewal under the same root passes the current root read via pki.Status. The race test is deterministic with no goroutines: install A, expect A, install C directly (the "concurrent CLI"), install B expecting A → RootDiffersError and C intact.

WHAT THIS DOES NOT MEAN
- It does not make `knomit identity install --replace-root` work unattended any more: scripts need --yes or --root. That break is deliberate and named in the PR.
- The lock protects the DECISION (which root the caller confirmed), not just file integrity; the atomic renames still do the latter.
- It does not move enrollment onto an HTTP route; invariant a46bbb69 stands.
- Foreseeable misreading: "first install needs no confirmation because there is nothing to compare". There IS something to compare: the operator's out-of-band fingerprint, and the clipboard is writable by any window or local process.

UPDATE (PR #525, merge fd991d4f): the CLI half of this decision no longer exists. `knomit identity install` and its `--root`, `--yes`, `--replace-root` and tty prompt were deleted, so 'in the CLI' in the title and the CLI paragraphs are history; the decision's core (InstallOptions{ExpectInstalledRoot}, the lock, no replaceRoot bool) stands and is still what InstallBundle does. The surviving callers are the desktop binding (which still shows and confirms the root), the fleet create and the fleet join (both pass InstallOptions{}, after a trust_installed pre-flight, and show nothing; the join's supplying of the bundle is the consent). A replace of one root by another no longer has a product path: the join refuses while trust is installed, and moving to another fleet is leave then join.

SUPERSEDED (fleet PR8, branch feat/fleet-tick-duties): `InstallOptions` and `ExpectInstalledRoot` were removed with the parameter (`pki.InstallBundle(dir, keyPath, raw)`). With the desktop confirm flow gone (PR7b) every caller expected "no root", so the decision's surviving core is the cross-process lock and fail-closed unreadable root, and an install is now first-install only: any installed root refuses (RootDiffersError for another root, ErrAlreadyInstalled for the bundle's own). See kb/invariants/pki/install/expected-root-under-lock/eac8d325.md. MISREADING: 'expecting the current root while supplying another bundle root IS the replace' is history; there is no replace.
