# ScopedCluster's neighbour search and joinCousinsForPrune pass store IncludeKinds from ONE configurable list that defaults to [epistemic]; dedupCluster is NOT on the config and never merges a pair whose kinds differ — hard-coding was rejected so clustering can one day include pragmatic facts; the seed filter is unchanged — issue #308

Issue #308: the kind exclusion (convention 8b26a25d) was enforced on SEEDS only. The three neighbour searches passed no kind filter: ScopedCluster's expansion (internal/synthesize/cluster.go:78), dedupCluster's candidate search (dedup.go:189, restricted to cluster members at :203) and the corpus-wide joinCousinsForPrune (cousins.go:152, whose comment at :174 deliberately matched ScopedCluster). The reviewer reproduced at dev e4175f7b: an observation and a policy in one directory were clustered together and dedupCluster deleted the observation into the policy mechanically, with no judge; with confidences reversed (dedup.go:45) the policy would have been deleted. Of ScopedCluster's five callers, the prune plan (review_strategy.go:166) merges or deletes, the RAPTOR follow-up (:1062) feeds the WHOLE cluster including neighbours into a distill item's FactsJSON (:1075), and the three bridge callers (bridge.go:482, bridge_report.go:86, bridge_motif_report.go:234) never cite a neighbour but a pragmatic one shifts Louvain community boundaries; the issue's claim that bridges could cite signals was inaccurate. The store already had IncludeKinds/ExcludeKinds (store/search_query.go:270-271) and the kind column is NOT NULL and normalised on every write, so legacy facts are safe.

OPTIONS CONSIDERED
1. Prune-only filter (neighbours, dedup, cousins under the prune plan).
2. IncludeKinds [epistemic] hard-coded inside ScopedCluster (all five callers), cousins and dedup.
3. One configurable kind list, default [epistemic], driving ALL THREE searches including dedup.
4. One configurable kind list driving ScopedCluster and joinCousinsForPrune only; dedupCluster hard-coded to epistemic AND refusing any pair whose kinds differ.
5. ExcludeKinds [pragmatic] or an ExcludeTypes list of the pragmatic types at each site.
6. A new store default / "synthesis search" mode.

RATIONALE (the designer's, 2026-09-26)
The filter must cover every route: option 1 leaves RAPTOR feeding policies into distill and bends bridge topology. Option 5 fails OPEN when a new kind or pragmatic type is added (as Signal was); IncludeKinds fails closed. Option 6 hides the rule in the store, whose other readers legitimately want pragmatic facts. The designer rejected option 2 (hard-coding): the filter must be CONFIGURABLE because clustering may one day need to include pragmatic facts. Option 3 was then rejected on the reviewer's finding that a widened list would put dedup.go:189 straight back to the reproduced corruption: a mechanical, judge-less merge of a policy with an observation, one config edit away. Hence option 4: the knob governs CLUSTERING (neighbours, cousins, and through them bridges and topology); mechanical dedup is an INVARIANT, not a setting. The seed filter (SeedQuery IncludeKinds plus AcceptSeed on both scan paths, gotcha 0bc8c031) is untouched, so with a widened list pragmatic facts can join a cluster around an epistemic seed but never seed one. Search Limit is NOT raised to compensate for k-window thinning: raising it would change output on corpora with no pragmatic facts and break the byte-identical normal-effort guarantee.

THE CHOICE (PR #314)
One configuration list of kinds, `[cluster_cache] neighbor_kinds` / KNOMIT_CLUSTER_CACHE_NEIGHBOR_KINDS (that section already holds ScopedCluster's resolution and min size; there is no [synthesize] section), value literals "epistemic" / "pragmatic" validated in config without importing fact (config.ValidateNeighborKinds, following the config.go:702 precedent that mirrors synthesize.Effort as literals to avoid a config→synthesize cycle), default [epistemic], empty/unknown/duplicate refused, threaded to ScopedCluster as a parameter (all five callers inherit it via RepoInstance.ClusterNeighborKinds or an explicit parameter; the calibrate tool gets --neighbor-kinds) and to joinCousinsForPrune, passed as store.SearchOptions.IncludeKinds. dedupCluster keeps IncludeKinds [epistemic] hard-coded on its search (dedupSearchKinds) AND runs sameKnownKind at pair formation, which fails CLOSED on an empty Kind ("" vs anything, including "" vs ""); factForLLM gained a Kind field filled at every construction site. The kind-equality check is the load-bearing half: with a widened list, dedup searches FROM every cluster member, so a search from a pragmatic member returns its epistemic neighbours through the epistemic-only filter and forms the mixed pair anyway.

HOW DEDUP ACTUALLY HARMS A MIXED PAIR (for the record; the reviewer corrected the first draft)
dedupCluster never goes through mergedFact: it re-parses the WINNER from its own file, keeping its kind, writes it back, and deletes the loser. So a policy that loses is DELETED, and a policy that wins has the observation deleted into it. Nothing is "rewritten as epistemic" on this route. Consequence: convention 8b26a25d says the seed filter may go once mergedFact carries Kind; sameKnownKind must NOT go with it, because dedup deletes across kinds whatever mergedFact does.

KNOWN LIMIT OF WIDENING (documented on the config field ClusterCacheConfig.NeighborKinds and RepoInstance.ClusterNeighborKinds; the repo has no config reference page or example toml)
mergedFact and distillFact still drop Kind, so with a widened list a JUDGED prune merge or a RAPTOR distill over a mixed cluster can still act on a policy. Widening is a future hook to be used knowingly, not a supported production setting, until those carry Kind.

OUT OF SCOPE
- discovery.go:574 isDuplicate: a pragmatic twin there causes a false "duplicate" (a missed discovery), not corruption; same distinction as gotcha b05bb21a; separate issue if wanted.

WHAT THIS DOES NOT MEAN
- It does not make pragmatic facts seeds under any setting.
- It does not put dedupCluster on the config; a PR that does reopens #308.
- It does not tie sameKnownKind's lifetime to the seed filter's: they guard different routes.
- Foreseeable misreading: "the config lets you run prune over policies safely". It lets a policy be a NEIGHBOUR; the judge can then act on it, and that is on the operator.
