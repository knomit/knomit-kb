# Derived-writer rules for motifs (MN11): mechanical merge unions winner-first and trims at the cap; LLM writers carry over; nothing mechanically stamps seed motifs onto discovered facts

Every path that writes a fact it did not receive from a human obeys these, and they are deliberately different for mechanical and LLM writers.

**Mechanical (dedup-merge).** `fact.MergeMotifs` unions the operands WINNER-FIRST and trims deterministically at `MaxMotifs` = 3. Winner-first is what decides which axis survives an overflow, so operand ORDER is load-bearing, not cosmetic — swapping the operands drops the winner's whole axis. Bound by `TestMotifDynamics_ReviewMergeTrimsToTheCapWinnerFirst` (the overflow case) alongside the pre-existing ordering test.

**LLM writers (prune / distill / discover).** Output schemas gain `motifs` with a carry-over instruction; `factForLLM` shows the members' motifs so the model can carry them; all output flows through `SerializeFact`, so MN4's single validation entry point covers them with no per-path code.

**Two deliberate NOTs.** (1) Keystones stay motif-less via the ORDINARY subject strip — there is no strip exemption for them. (2) There is NO mechanical stamping of seed motifs onto discovered facts: a discovered fact gets motifs only if the model wrote them.

**Consequence for anyone adding a write path.** The mechanical rule and the LLM rule are not interchangeable. A new mechanical path must union-and-trim explicitly (nothing infers it); a new LLM path needs only the schema field, because serialization already validates.

**Caught before it shipped:** backfill originally parsed a fact's INDEXED BODY rather than its source, so writing it back would have replaced real facts with husks carrying only the new motifs — up to 8 authored facts per session, and the damage would have looked like success.
