# Dedup merge tiebreak: non-hypothesis always wins; then confidence; then sources. Union domains+entities

mergeFacts (internal/corpus/synthesize/dedup.go) tie-breaks merge pairs in this strict order: (1) non-hypothesis ALWAYS wins over hypothesis regardless of confidence (hypotheses carry uncertainty, can't beat observed/derived facts); (2) within same category: higher Confidence wins; (3) Confidence tie: higher Sources wins. After the winner is chosen: Domain and Entities are merged as UNION via fact.UnionStrings (dedupes and orders); Sources = a.Sources + b.Sources (sum both). applyGreedyMerges sorts candidate pairs by similarity DESC and enforces 'each fact participates in AT MOST ONE merge per pass' — preventing transitive merges within a single dedup round (transitivity would require re-running dedup until fixpoint, which we explicitly don't).

Anti-pattern: implementing your own merge ordering somewhere — always go through mergeFacts.

WHAT THIS DOES NOT MEAN — THE THRESHOLD IS NOT A CONSTANT (corrected 2026-07-22): this fact previously said `defaultDedupThreshold = 0.92`. There is NO such constant in internal/corpus/synthesize at HEAD, and 0.92 is the WRONG number for the active model. The dedup cutoff is CALIBRATED PER EMBEDDING MODEL and read at call time via `store.EmbedderThresholds(emb).Dedup` — for the current model that value is 0.905 (nomic fallback 0.95), set in internal/domain/modelparams/thresholds.go; it was 0.82 until #638 re-derived it. Every live consumer sources it that way: internal/edge/mcp/learn.go, internal/corpus/synthesize/review_strategy.go, and internal/corpus/synthesize/discovery.go (DedupThreshold field).

Why this matters operationally: 0.92 was nomic's cutoff, and the per-model thresholds were deliberately ported DOWN by preserving the percentile each occupied on nomic. Hardcoding 0.92 against a model calibrated to 0.82 sets the bar roughly a tenth too high — near-duplicates sail through and dedup silently stops merging almost anything. The failure is invisible: no error, just a corpus that quietly accumulates duplicates. Never write a literal similarity cutoff; always read it from EmbedderThresholds for the embedder in hand.

UPDATE (#638, merge 231e5711): the tiebreak above is review's (mergeFacts in synthesize/dedup.go) and is unchanged. Learn's merge no longer uses newFactWins alone: the incoming fact takes the identity (title and body) only when it is the SAME statement and newFactWins (incomingIdentityWins = sameStatement && newFactWins in internal/edge/mcp/learn.go). Otherwise the existing title and body are kept, and confidence, sources, refs, domains and entities are still pooled; statementNotAppliedNotes tells the caller the incoming statement was not applied. Why: a more confident SIBLING decision used to overwrite the existing one at its path (incidents/mcp/learn/dedup-merge-overwrote-sibling-decision).

UPDATE (#642, merge 77896f0a): learn's merge now agrees with this fact's rule (1) in one direction. When the incoming fact is a HYPOTHESIS and the stored fact is not, learn keeps the stored fact's whole identity AND its confidence (absorbedHypothesis in internal/edge/mcp/learn.go), because a hypothesis's confidence is a prediction probability, not evidence. See kb/decisions/mcp/learn-hypothesis-report/91e88bb3.md. This does NOT make learn's tiebreak the same as review's: between two non-hypotheses learn still uses incomingIdentityWins (same statement AND newFactWins), and the cases where another type can still win are listed in kb/gotchas/mcp/learn-hypothesis-report/99e43740.md.

UPDATE (#643, merge a20152c9): the last sentence of the #642 update ('the cases where another type can still win are listed in 99e43740') is superseded for learn: learn's merge never changes a stored type, kind or (on differing types) origin, whichever side wins the identity tiebreak (kb/decisions/mcp/learn-hypothesis-report/489f36ae.md). Review's tiebreak above is unchanged.
