# Corpus structure (declared + mined anchors, ref targets, constants) goes into the property graph as first-class nodes, not per-feature side tables

**Options considered:** (a) per-feature SQLite side tables (fact_terms for tf-idf terms, fact_ref_targets for refs, a numbers class) feeding separate detectors; (b) an Anchor node kind in the existing property graph (edges/node_props_text) with MENTIONS/CITES/TAGGED edges, where declared entities/domains and mined identifiers/terms/collocations/constants/ref-targets are one node model distinguished by class + provenance (declared|mined|promoted).

**Rationale:** One substrate makes every detector a graph query: TokenDF becomes node in-degree; bridge enumeration, co-citation, missing-hub detection, and shared-origin checks read the same structure; blast radius of a src:// FILE is native once ref targets sit inside the derivation graph (which also closes the false-independence hole in confluence detection — two facts derived from the same file share an ancestor). Anchor promotion (mined identifier → declared entity) is a provenance transition, not a migration. Side tables were the minimum-change option and were rejected under the pre-release principle. Bodies live in git blobs, so anchor extraction happens on the index write path where embeddings are already computed; a hybrid lexical index (FTS/BM25-class) is part of the same pillar and anchor mining falls out of its term statistics.

**The choice:** Design the anchor node/edge schema once for all anchor classes (proposals 01-03), then absence queries (05) and graph analytics (07) run over it. Status: proposed direction, pre-refinement; no implementation yet.
