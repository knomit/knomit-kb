# Concurrent-caller tests accept the three benign loser refusals (completed / being applied / moving to its next phase) through ONE shared test-only helper used by both the review and hypothesize tests — not typed error sentinels, which would change production error construction to fix a test flake — issue #305

Issue #305: TestReviewer_ConcurrentContinuations_ApplyOnce failed once in CI (PR #302's macOS slow-tests leg) because a losing concurrent caller received `session %q is moving to its next phase for another caller; retry shortly, or start with takeover:true to abandon the session`, the errAdvancing refusal added by the #291 `advancing` guard (pipeline.go:282-284, raised at :1133-1135 on a lost phase CAS and at :1253-1254 in completeSession), and requireOnlyBenignErrors' regex at review_claim_test.go:219 predates it. Verified at dev b3a9ec46 by the reviewer: the loser only reaches it AFTER losing the item claim (:604, :620-630), so nothing is applied twice and no work is lost; it happens only in the window between the phase CAS setting advancing=1 (store/pipeline_index.go:405) and FinishPipelineSessionAdvance clearing it (:424), so it is a flake, reproduced 1 in 50 with -race locally. review_phase_test.go:196 already accepts "retry shortly" (#291 updated that test and missed this one). TestHypothesizer_ConcurrentDiscoverSubmission_WritesOnce (hypothesize_engine_test.go:327) discards ALL errors with `_, _ =`, so it has no regex gap but also checks no loser path, and the comment at review_claim_test.go:207-209 claiming it "makes the same tradeoff" is stale.

OPTIONS CONSIDERED
1. The issue's fix: append `|is moving to its next phase for another caller` to the regex in requireOnlyBenignErrors.
2. One shared test-only benign pattern/helper in the synthesize test package, used by requireOnlyBenignErrors AND by the hypothesize test, which starts collecting its errors and checking them.
3. Typed error sentinels in production (errors.Is) that the tests match on.

RATIONALE (the designer's, 2026-09-26)
Option 2. Option 1 works (200 -race runs green in a throwaway worktree, the one-fact apply-once assertion reached) but leaves the hypothesize test blind and lets two lists drift apart again the next time a refusal is added. Option 3 is rejected because every engine refusal is a plain errf string (pipeline.go:110) and nothing in production branches on these messages; introducing sentinels would change production error construction to fix a test flake. If MCP ever needs to classify refusals as retryable, that is its own issue.

THE CHOICE
Option 2, test-only, no production change. The helper's comment names the `advancing` guard and the window in which a loser sees it.

WHAT THIS DOES NOT MEAN
- It does not say the advancing refusal is a bug; it is the correct "handled by someone else" outcome.
- It does not make the 4-caller test the apply-once anchor; per its own comment it is the loser-path guard, and the one-fact assertion is the anchor.
- Foreseeable misreading: "add the new message to the regex" the next time a fourth refusal appears. Add it to the SHARED helper, or both tests drift again.
