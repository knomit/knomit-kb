# Work-item ids are echoed on the wire so a continue call can CAS on the item it was actually rendered for

ReviewItem and HypothesizeItem carry an `id`, and both tools accept an OPTIONAL `item_id` on continue. When supplied and it does not match the peeked item, the call is rejected WITHOUT consuming the item — the client is answering a stale item and its response must not be applied to a different one. When omitted, behaviour is exactly as before, so this is backward-compatible for existing callers.

WHY: the response-IS-NULL CAS (see invariants/synthesize/work-item-claim-protocol) closes the double-APPLY race, but not the MISMATCH window — between rendering item A and receiving its response, a higher-priority item can be inserted, so the peek returns B and A's response would be applied to B. This is reachable today, not theoretical: a distill apply enqueues RAPTOR follow-up items, which is exactly an insert between render and continue.

NOT WHAT THIS MEANS: item_id is not a session token or an auth check, and supplying it does not reserve the item. It is a staleness guard only.
