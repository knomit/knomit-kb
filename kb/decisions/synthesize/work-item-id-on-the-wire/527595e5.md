# Work-item ids are echoed on the wire so a continue call can CAS on the item it was actually rendered for

ReviewItem and HypothesizeItem carry an `id`, and continue calls take `item_id`. When it is supplied and does not match the peeked item, the call is rejected WITHOUT consuming the item: the client is answering a stale item, and its response must not be applied to a different one.

REQUIRED OR OPTIONAL, per tool (as of PR #291): knomit_review REQUIRES `item_id` with every response; the handler refuses a response without it. knomit_hypothesize still takes it OPTIONALLY, and when it is omitted the answer applies to whatever item is current. In-process callers (ContinueSession with itemID 0, used by RunAll) skip the check.

WHY: the response-IS-NULL CAS (see invariants/synthesize/work-item-claim-protocol) closes the double-APPLY race, but not the MISMATCH window. Between rendering item A and receiving its response, a higher-priority item can be inserted, so the peek returns B and A's response would be applied to B. This is reachable, not theoretical: a distill apply enqueues RAPTOR follow-up items, which is exactly an insert between render and continue. Resume made it more reachable still, since two callers can now answer one session.

A caller that names its item and loses the claim is refused ("already answered ... nothing was applied by this call"), as is one naming an item when none is outstanding; see the start-resumes-live-session decision.

NOT WHAT THIS MEANS: item_id is not a session token or an auth check, and supplying it does not reserve the item. It is a staleness guard only.
