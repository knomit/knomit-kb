# Review's mechanical dedup may merge across ontology topics and keep only the winner's body — the loser stays reachable through history via knomit_explain; the ONLY defect in issue #280 is the survivor citing itself instead of only the subsumed fact

Issue #280 reported that knomit_review's mechanical dedup (dedupCluster in internal/synthesize/dedup.go) merged an incident into a gotcha: (1) the loser's unique body paragraph was not carried into the winner, (2) the incident vanished from kb/incidents/ at HEAD because pair selection checks cluster membership only and never the topic, (3) the survivor cited itself because dedupMergeRefs unioned the loser's kb://<id>/<winner> ref onto the winner and marked it carried, which the refs.go self-ref check exempts.

OPTIONS CONSIDERED
(a) Never merge mechanically across ontology topics; route such pairs to the prune judge as a work item.
(b) Body-containment check before a mechanical merge keeps only the winner's body, falling back to the judge.
(c) Drop any ref that canonicalises to the winner's own path in dedupMergeRefs, keeping the ref to the subsumed loser.

RATIONALE (the designer's, 2026-09-25)
knomit is a temporal graph. A merge removes the loser from HEAD but never from history: its full body is retrievable through knomit_explain at any earlier commit, and the winner deliberately cites the loser's path as the record of the merge (dedup.go, "the record of the merge, not a dead ref"). So neither "the body was lost" nor "the incident record vanished" is a defect: the content is one explain away, and the merge honours dedup-not-append (kb/principles/philosophy/dedup-not-append/adf1c4a5.md). Topic-blind candidate selection is acceptable for the same reason. (a) and (b) were rejected as fixes for a non-problem; (b) additionally has no non-brittle mechanical signal and would introduce a corpus-property constant.

THE CHOICE
Only (c). The survivor must cite the subsumed fact and must not cite itself. dedupMergeRefs (dedup.go:91) gets the winner's path and filters from the WRITTEN list every ref whose canonical form equals the winner's own path (the loser's ref may be in kb://<id>/ form while winnerFact.File is bare kb/..., so compare canonical forms as learn.go's mergeFacts does), leaving the carried set derived from the operands. The stale comment at refs.go:204-206 ("mergeFacts no longer emits a self-ref by either route") must be corrected: it was true only of mcp.mergeFacts; synthesize.mergeFacts/dedupMergeRefs is a separate function.

WHAT THIS DOES NOT MEAN
- It does not endorse hand-repairing a merged winner to re-add the loser's paragraphs as routine; the designer's position is that the history holds it.
- It does not say cross-topic merges are always desirable in principle, only that they are not a defect worth a mechanical guard today. Revisit with data if a merge is ever shown to be wrong on CONTENT, not location.
- It does not touch the two-commit write/delete non-atomicity of mechanical dedup (winner written at dedup.go:340, loser deleted at :358); that is a separate observation and no issue was filed for it here.
- Foreseeable misreading: "#280 wants topic-scoped dedup". It does not; a PR adding a cross-topic skip contradicts this decision.
