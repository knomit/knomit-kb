# Cross-cluster restatements reach prune's EXISTING judge as ordinary prune work items — no prompt, schema, or apply-path change was needed

**The gap.** Prune IS consolidation with a judge, but its work items are built per Louvain cluster, so a restatement whose halves cluster apart is judged by nothing, forever.

**Options considered.**
1. *Loosen the mechanical dedup threshold.* REJECTED — the problem is a SCOPE gap, not a threshold problem; loosening destroys data without closing it.
2. *A new cross-cluster judge with its own prompt and apply path.* REJECTED — duplicates the fidelity contract that `MergeEntry` already enforces, and doubles the surface where consolidation semantics can drift apart.
3. *Feed the existing judge a bounded cross-corpus shortlist.* CHOSEN.

**Why (3) was nearly free.** The prune prompt ships facts BESIDE itself rather than interpolating them into the text, so a two-fact work item is shape-identical to a cluster work item. No prompt change, no schema change, no apply-path change — the candidates are just more `prune` items.

**How selection avoids asserting anything about a corpus.** Ranking is by title cosine, and the cut is a percentile of THIS repo's own pair-similarity distribution — never an absolute value. Pairs at or above the model's calibrated dedup threshold are dropped (those belong to `mergeFacts`), as are pairs this session's clusters already co-present. Enforcement is the corpus's own judge verdicts, not a configured rate. Identical code prints an operating point of 0.783 on knomit-kb and 0.884 on core; the number is a fingerprint, not a setting.

**Bounded, not suppressed, on flood corpora.** A high candidate rate costs at most the judge-slot cap per session (8 measured on core), after which that corpus's verdicts decide.
