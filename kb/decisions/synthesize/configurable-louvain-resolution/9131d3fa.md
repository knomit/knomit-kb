# Louvain resolution is config-driven (default γ=4.0) and threaded as single-source-of-truth to checker + read path

DECISION (PR #70): the Louvain clustering resolution (γ) and min community size are configurable, defaulting to γ=4.0 / min_community_size=2 — was a hardcoded γ=1.0 + a hardcoded 'len(c) > 1' filter.

DEFAULT γ HISTORY: originally 2.0 (γ=1.0 produced an over-large mega-cluster; γ=2.0 broke it up, largest community 54->26, top-3 share 25%->14%). RECALIBRATED to 4.0 for the SIMILAR_TO scoped graph in commit bd3bffc — the denser graph needed a higher γ to keep communities from re-merging into a mega-cluster. Higher γ = more, smaller communities.

CONFIG: config.ClusterCacheConfig carries Resolution float64 + MinCommunitySize int (TOML [cluster_cache] resolution / min_community_size; env KNOMIT_CLUSTER_CACHE_RESOLUTION / KNOMIT_CLUSTER_CACHE_MIN_COMMUNITY_SIZE).

SINGLE-SOURCE-OF-TRUTH THREADING (load-bearing, verified in sync at HEAD): the SAME (resolution, min_community_size) must reach BOTH the cluster checker AND the synthesize read path. Path: config -> RepoInstance.ClusterResolution()/ClusterMinCommunitySize() -> synthesize.ScopedCluster(... resolution, minCommunitySize ...). BOTH default-fallback constant pairs are 4.0/2 and MUST stay in sync: synthesize defaultScopedResolution=4.0 / defaultScopedMinCommunitySize=2 (internal/synthesize/cluster.go — plain consts because synthesize must NOT import repos) and repos defaultClusterResolution=4.0 / defaultClusterMinCommunitySize=2 (internal/repos/cluster_config.go). Both are used ONLY when a caller passes a non-positive value. filterSmallClusters takes minCommunitySize so the category-fallback paths drop the same small communities the Louvain path does.

WHAT THIS DOES NOT MEAN (corrected 2026-07-22):

1. The reason to keep the two pairs in sync is NOT 'cache thrash'. There is no cluster cache to thrash: PR #98 deleted store.ClusterFacts / CachedClusterFacts and migration 000013 dropped the `cluster_cache` TABLE; clustering is now in-process gonum Louvain over a scoped subgraph (see kb/decisions/synthesize/bridge-clustering-source-in-process-scoped/b922c8d0.md). The surviving `[cluster_cache]` TOML section name and the `ClusterCacheConfig` Go type are back-compat labels, not storage. The reason the pairs must still match is plainer and just as load-bearing: two code paths computing communities at DIFFERENT γ produce DIFFERENT partitions, so the checker's view and the read path's view disagree about which facts are in which community.

2. The doc comment on RepoInstance.ClusterResolution still says 'default 2.0' and mentions warming a 'cluster_cache key'. Both are stale in the CODE COMMENT; the actual default is 4.0 (cluster_config.go). Trust the constant, not that comment.
