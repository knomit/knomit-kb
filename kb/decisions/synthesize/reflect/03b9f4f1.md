# Reflect on a deleted (settled or retracted) hypothesis transition reinforces the live facts written in the deleting commit that cite it, and warns and skips when there is none (user ruling, #648)

THE RULING (user, on #648 review r1 finding B2, option (a)). A reflect reinforce entry names TRANSITION facts. After #648 a transition fact can be a hypothesis that a settle deleted, so the path no longer exists. ApplyReflectDecisions therefore does this per transition path: if the fact is live, reinforce it as before; if it is deleted, reinforce the LIVE facts that were written by the commit that deleted it AND whose refs cite it (livingCiters); if there are none, emit ONE warning ('transition ... was deleted and no live fact written with its deletion cites it; skipped') and skip that transition. Reflect no longer fails the whole call on a deleted transition path.

WHY. The settling fact is the natural carrier of the lesson: it cites the hypothesis and was written in the same commit. Failing the whole reflect over one deleted path (the r1 repro) threw away every other reinforce in the response.

OPTIONS REJECTED: failing the call (the old behaviour, B2), and reinforcing any fact that ever cited the path (unbounded; the cite filter is what stops an unrelated sibling written in the same commit from being reinforced).

THE REPORT SIDE. findHypothesisTransitions reports a deleted hypothesis as `confirmed` or `refuted` when the session's commits carry a Knomit-Outcome for it, otherwise `retracted`. If reading the outcomes fails it logs a warning and reports `retracted` rather than failing.

WHAT THIS DOES NOT MEAN. It does not mean a deleted transition is always reinforceable: delete, re-create, delete again takes the LATEST deleting commit, and a plain retract with no citer warns and skips. See kb/architecture/store/facts/settlements-since/ for the walk it relies on.
