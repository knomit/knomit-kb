# Distill work items will PAGE over CLUSTERED input — paging removes the transport cap, clustering is what stops it being replaced by an arbitrary context cap

A review session's distill work items exceeded the client's MCP tool-result cap and were spilled to disk, so the agent never saw them. Direction decided 2026-07-28; AMENDED the same day (see "Amendment" below) after the ordering was challenged.

**The framing that decided it:** the MCP cap bounds ONE TOOL RESULT, not the conversation. The model can hold a 26-fact cluster; we simply cannot hand it over in a single envelope. Every option that shrinks the work item solves the transport problem by shrinking what the model SEES — solving the wrong problem with the only lever available.

**Options considered:**

1. *Lower maxDistillChunkBytes only.* Smallest change. Rejected as sufficient: it trades a loud transport failure for a quiet quality loss. Each distill would see ~9-17 facts instead of ~26-38, and the compensating mechanism (enqueueRaptorFollowups) only recurses over facts a round ACTUALLY WROTE and needs ClusterMinCommunitySize>=2 to form a cluster at all — so a narrower window produces fewer writes, which produces fewer follow-ups. Shrinking breaks the very thing that was supposed to repair shrinking. SHIPPED ANYWAY as an interim delivery fix (commit 34f0f553), because an undeliverable item is worse than a narrow one.
2. *Cluster the depth-0 distill input.* Deferred at first. NOW A PREREQUISITE — see the amendment.
3. *Snippets + on-demand body fetch.* Rejected: the incident reporter did exactly this by hand and documented the failure mode — synthesis coverage became bounded by titles, and a pattern living only in an unread body was invisible.
4. *Paging with an accumulate-then-respond contract.* CHOSEN.

**The choice:** one work item holds the full cluster. The server serves it in pages; the agent accumulates every page into its context and answers ONCE at the end.

**Why it is cheap here specifically:** PipelineWorkItem.FactsJSON already holds the entire payload, so a page is a deterministic slice of an existing column — paging needs NO new state, NO new column, and is idempotent under re-serve (an agent that dies mid-page simply restarts when NextPipelineWorkItem re-serves the unanswered item). Paging is a pure read that happens entirely BEFORE the claim CAS, so invariants/synthesize/work-item-claim-protocol is untouched: the CAS still fires exactly once, on the final response. The addressing precedent already exists — item_id is an echo-back parameter today.

**What paging costs, accepted knowingly:** it is NOT cheaper in turns (3 pages + 1 response = 4 round trips vs 3 small items = 3). The purchase is coherence — one decision over the whole cluster instead of three decisions over thirds of it — not throughput.

**The enforcement requirement is load-bearing, not advisory.** The last page carries a completion token the agent can only hold by having received that page, and the response must echo it; a response for a multi-page item without a valid token is REJECTED loudly, naming what is missing, in the same position as requireResponseKey (before the claim, so the item stays retryable). Direct application of invariants/synthesize/response-envelope: a stated requirement that nothing probes for is inert. Merely instructing the agent to page until exhausted would let it answer on page 1 and be accepted — trading a loud transport failure for a silent quality loss, strictly worse than the bug being fixed.

**The token travels as an MCP PARAMETER (completion_token), a sibling of item_id — not as a key inside the response JSON.** Four reasons: item_id is the precedent and the same kind of protocol concern (the response object is the agent's DECISIONS; a delivery receipt is not a decision); one enforcement site in ContinueSessionForItem instead of four parsers, so step types added later cannot escape it; embedding it would grow each schema's `required` list, the exact construct that was inert until fef554d1; and decisively for a PAGING protocol, a response_schema key lives inside the very payload this feature exists to keep deliverable — during the incident the reporter had to extract response_schema from a spilled-to-disk file with a script to read it at all.

**AMENDMENT (same day): depth-0 clustering moved from out-of-scope to PREREQUISITE.**

The original record said "paging RAISES the ceiling; it does not remove it," and kept two caps: a page size (transport) and an item size (model context). Challenged with: if we page, shouldn't the total limit be gone rather than merely larger? Substantially correct, and the correction sharpens the design.

What paging genuinely removes is the TRANSPORT cap on one decision's input. Today maxDeliveredItemBytes does double duty — it bounds the response AND, because an item is delivered in one response, it bounds the item. Paging severs that permanently.

What does not vanish is a bound on what the model must ACCUMULATE. Two independent reasons: the package explicitly accommodates small local models (extractJSON strips <think> blocks for them), whose context cannot hold what a 1M-context model can regardless of page size; and — decisively — DEPTH-0 DISTILL'S INPUT IS THE ENTIRE SEED POOL, not a cluster. review_strategy.go passes llmSeeds (every epistemic fact in the corpus) to chunkFacts, with ClusterKey "distill-all-N". Removing the total cap without clustering therefore pages an ENTIRE KNOWLEDGE BASE into one decision — precisely the behaviour chunking was introduced to stop (d8f69f60: "marshalling it into one item put an entire knowledge base into a single prompt"). At ~2.5 KB a fact, a 500-fact corpus is ~1.2 MB, ~400k tokens, ~40 pages, for one synthesis.

So the cap changes NATURE rather than disappearing: from "what fits in one HTTP response" (arbitrary, client-dependent, and the thing that broke) to "what the model can hold and reason over at once" (real, model-dependent, and legitimately a per-deployment config knob).

And clustering is what makes that cap stop mattering. If depth-0 distill clustered its input the way prune already does, item size would be bounded BY THE CLUSTER — by the corpus's own structure — and the cap would degrade to a backstop against a pathological mega-community rather than a routine constraint. That is the property actually wanted: not "a larger arbitrary limit" but "no meaningful limit, because nothing is arbitrarily grouped in the first place."

**Revised ordering: cluster depth-0 → page each cluster → keep a generous item cap purely as a backstop.** Paging alone buys "no transport limit." Paging over clustered input buys "no meaningful limit at all."

**WHAT THIS DOES NOT MEAN.** It does not mean the item cap can be deleted — the backstop is what prevents a mega-community or a small-model deployment from regressing to the original failure by another route. It does not mean depth-0 chunking can simply be deleted before clustering exists; until then chunkFacts is the ONLY thing standing between a first run and a whole-corpus prompt. It does not make paging distill-specific: prune clusters are unchunked and unbounded today, so a generic per-render paging path would give prune a safety net it currently lacks. And it does not bless raising MAX_MCP_OUTPUT_TOKENS as a fix — that is a per-user harness setting usable as a stopgap, never something knomit can require.

**Status.** The interim delivery fix shipped on branch fix/review-payload-delivery (34f0f553): maxDeliveredItemBytes now names the binding budget and derives maxDistillChunkBytes from it, and facts moved out of the prompt string into a structural `facts` field — a prerequisite for paging, since facts embedded in a prompt STRING cannot be sliced. Verified end to end against two live servers driving real Claude Code instances: the old build spilled a 67,943-byte distill item to disk (38 facts, facts inside the prompt), the new build delivered 31,504 bytes inline (17 facts, separate `facts` field). Clustering and paging are not yet built.
