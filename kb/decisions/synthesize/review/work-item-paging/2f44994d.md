# Distill work items will PAGE over CLUSTERED input — paging removes the transport cap, clustering is what stops it being replaced by an arbitrary context cap

A review session's distill work items exceeded the client's MCP tool-result cap and were spilled to disk, so the agent never saw them. Direction decided 2026-07-28; AMENDED the same day after the ordering was challenged; SHIPPED COMPLETE the same day.

**The framing that decided it:** the MCP cap bounds ONE TOOL RESULT, not the conversation. The model can hold a 26-fact cluster; we simply cannot hand it over in a single envelope. Every option that shrinks the work item solves the transport problem by shrinking what the model SEES — solving the wrong problem with the only lever available.

**Options considered:**

1. *Lower maxDistillChunkBytes only.* Smallest change. Rejected as sufficient: it trades a loud transport failure for a quiet quality loss. The compensating mechanism (enqueueRaptorFollowups) only recurses over facts a round ACTUALLY WROTE and needs ClusterMinCommunitySize>=2 to form a cluster at all — so a narrower window produces fewer writes, which produces fewer follow-ups. Shrinking breaks the very thing that was supposed to repair shrinking. Shipped anyway as an interim delivery fix.
2. *Cluster the depth-0 distill input.* Deferred at first, then promoted to PREREQUISITE — see the amendment.
3. *Snippets + on-demand body fetch.* Rejected: the incident reporter did exactly this by hand and documented the failure mode — synthesis coverage became bounded by titles, and a pattern living only in an unread body was invisible.
4. *Paging with an accumulate-then-respond contract.* CHOSEN.

**The choice:** one work item holds the full cluster. The server serves it in pages; the agent accumulates every page into its context and answers ONCE at the end.

**Why it was cheap here specifically:** PipelineWorkItem.FactsJSON already holds the entire payload, so a page is a deterministic slice of an existing column — no new state, no new column, idempotent under re-serve (an agent that dies mid-page restarts when NextPipelineWorkItem re-serves the unanswered item). Paging is a pure read that happens entirely BEFORE the claim CAS, so invariants/synthesize/work-item-claim-protocol is untouched: the CAS still fires exactly once, on the final response.

**The enforcement requirement is load-bearing, not advisory.** The last page — and only the last — carries a completion token derived from (item id, payload), so holding it is equivalent to having received that page, and the response must echo it. A multi-page item answered without it is REJECTED before the claim, so the item stays retryable. Direct application of invariants/synthesize/response-envelope: a stated requirement that nothing probes for is inert. Merely instructing the agent to page until exhausted would let it answer on page 1 and be accepted — trading a loud transport failure for a silent quality loss, strictly worse than the bug being fixed.

**The token travels as an MCP PARAMETER (completion_token), a sibling of item_id — not as a key inside the response JSON.** item_id is the precedent and the same kind of protocol concern (the response object is the agent's DECISIONS; a delivery receipt is not a decision); one enforcement site instead of four parsers; embedding it would grow each schema's `required` list, the exact construct that was inert until fef554d1; and decisively for a PAGING protocol, a response_schema key lives inside the very payload this feature exists to keep deliverable.

**Enforcement is reached through an OPTIONAL pagedStrategy interface, not the required Strategy interface.** Only strategies that ship a payload beside the prompt can page; hypothesize ships one fact per item and has nothing to page, so widening Strategy would force a meaningless implementation on it.

**Paging lives at the TRANSPORT boundary (reviewResultPage), not in Strategy.Render.** The engine's in-process consumers — RunAll and the web synthesis job — want the whole item, and only the MCP wire has a per-result limit. Slicing in Render would have handed RunAll page 1 and silently dropped the rest.

---

**AMENDMENT: depth-0 clustering was a PREREQUISITE, not a follow-on.**

The original record said "paging RAISES the ceiling; it does not remove it," keeping both a page size and an item size. Challenged with: if we page, shouldn't the total limit be gone rather than merely larger? Substantially correct.

What paging genuinely removes is the TRANSPORT cap on one decision's input — maxDeliveredItemBytes had been doing double duty, bounding the response AND, because an item shipped in one response, bounding the item. What does not vanish is a bound on what the model must ACCUMULATE: this package accommodates small local models whose context cannot hold what a long-context hosted model can regardless of page size; and — decisively — DEPTH-0 DISTILL'S INPUT WAS THE ENTIRE SEED POOL, not a cluster. Removing the total cap without clustering would page an ENTIRE KNOWLEDGE BASE into one decision, precisely what chunking was introduced to stop.

So the cap changed NATURE rather than disappearing: from "what fits in one HTTP response" (arbitrary, client-dependent, the thing that broke) to "what the model can hold and reason over at once" (real, model-dependent, legitimately a per-repo knob). Clustering is what makes it stop mattering: item size is now bounded by the community's own size, leaving the cap as a backstop against a pathological mega-community.

**WHAT THIS DOES NOT MEAN.** It does NOT mean the item cap can be deleted — the backstop is what prevents a mega-community or a small-model deployment from regressing by another route. It does NOT mean chunkFacts can be deleted; it still splits a group that exceeds maxItemBytes. It does NOT make paging universal — prune, reflect and discover interpolate their payloads into the prompt and are single-page by construction, so prune clusters remain unchunked and unbounded, the latent version of the same bug. And it does NOT bless raising MAX_MCP_OUTPUT_TOKENS as a fix — a per-user harness setting, usable as a stopgap, never something knomit can require.

**STATUS: COMPLETE.** Branch fix/review-payload-delivery, three commits.

- 34f0f553 — maxDeliveredItemBytes names the binding budget and derives the fact budget from it; facts move out of the prompt string into a structural `facts` field (a prerequisite: facts embedded in a prompt STRING cannot be sliced). RunAll recombines prompt and facts, since the headless and web-job paths take one message and have no second channel.
- eeb2bd9e — depth-0 distill groups by cluster via distillGroups. Two ScopedCluster properties made the naive version wrong: filterSmallClusters DROPS communities below minCommunitySize (so grouping straight off it would silently lose seeds), and clusters contain NEIGHBOURS pulled in by search with no ExcludeTypes on the review path (so a pragmatic fact AcceptSeed refuses could reach distill and be rewritten as epistemic on commit). Groups are cluster SEEDS only; unclustered and lone seeds fall to a trailing remainder rather than being dropped.
- f61989c7 — paging, token, enforcement, MCP `page` and `completion_token` parameters. maxPageBytes (transport, ~24.5 KiB) and maxItemBytes (cognition, 256 KiB) are now separate constants.

**Verified end-to-end over real MCP**, live servers driving Claude Code instances, not only unit tests. Delivery: the pre-fix build spilled a 67,943-byte distill item to disk (38 facts, facts inside the prompt); the fixed build delivered 31,504 bytes inline (17 facts, separate `facts` field). Grouping: with clusters=4, prune_clusters=3, seeds=38, distill items came out as distill-c0-0/c1-0/c2-0 at 4/2/2 facts — exactly the communities prune received — plus distill-rest-0/1 at 17/13, totalling 38 fact slots across 38 distinct paths with zero duplication. Paging: a 7-page item delivered 46 distinct facts with no gap or overlap, token on page 7 only, prompt on page 1 only, progress frozen through every page fetch. Enforcement: a deliberate early answer to a 4-page item returned "work item 16 spans 4 pages and no completion_token was supplied…", the item survived, and the corrected resubmission completed the session.
