# Distill work items will PAGE (accumulate-then-respond) rather than shrink, because the MCP cap bounds one tool result and not the conversation

A review session's distill work items exceeded the client's MCP tool-result cap and were spilled to disk, so the agent never saw them. The fix direction was decided in conversation on 2026-07-28.

**The framing that decided it:** the MCP cap bounds ONE TOOL RESULT, not the conversation. The model can hold a 26-fact cluster; we simply cannot hand it over in a single envelope. Every option that shrinks the work item solves the transport problem by shrinking what the model SEES — solving the wrong problem with the only lever available.

**Options considered:**

1. *Lower maxDistillChunkBytes only.* Smallest change (~15 lines). Rejected as sufficient: it trades a loud transport failure for a quiet quality loss. Each distill would see ~9 facts instead of ~26, and the compensating mechanism (enqueueRaptorFollowups) only recurses over facts a round ACTUALLY WROTE and needs ClusterMinCommunitySize>=2 to form a cluster at all — so a narrower window produces fewer writes, which produces fewer follow-ups. Shrinking breaks the very thing that was supposed to repair shrinking.
2. *Cluster the depth-0 distill input.* Today depth-0 distill does NOT use clusters: review_strategy.go passes the whole flat seed pool to chunkFacts, so an item is an arbitrary byte slice of the corpus in scan order (ClusterKey "distill-all-N"). Clustering it would mirror prune. Deferred, not rejected — it fixes slice incoherence but still caps what one decision can see.
3. *Snippets + on-demand body fetch.* Ship path/title/metadata for all N, let the agent pull bodies via knomit_explain. Rejected: the incident reporter did exactly this by hand and documented the failure mode — synthesis coverage became bounded by titles, and a pattern living only in an unread body was invisible.
4. *Paging with an accumulate-then-respond contract.* CHOSEN.

**The choice:** one work item holds the full cluster. The server serves it in pages; the agent accumulates every page into its context and answers ONCE at the end.

**Why it is cheap here specifically:** PipelineWorkItem.FactsJSON already holds the entire payload, so a page is a deterministic slice of an existing column — paging needs NO new state, NO new column, and is idempotent under re-serve (an agent that dies mid-page simply restarts when NextPipelineWorkItem re-serves the unanswered item). Paging is a pure read that happens entirely BEFORE the claim CAS, so invariants/synthesize/work-item-claim-protocol is untouched: the CAS still fires exactly once, on the final response. The addressing precedent already exists — item_id is an echo-back parameter today.

**What paging costs, accepted knowingly:** it is NOT cheaper in turns (3 pages + 1 response = 4 round trips vs 3 small items = 3). The purchase is coherence — one decision over 26 facts instead of three decisions over 9 — not throughput. It also accumulates the full payload into the agent's context for one decision, which is real cumulative pressure across a 36-item session.

**The enforcement requirement is load-bearing, not advisory.** The last page carries a completion token the agent can only hold by having received that page, and the response must echo it; a response for a multi-page item without a valid token is REJECTED loudly, naming what is missing, in the same position as requireResponseKey (before the claim, so the item stays retryable). This is a direct application of invariants/synthesize/response-envelope: a stated requirement that nothing probes for is inert. Merely instructing the agent to page until exhausted would let it answer on page 1 and be accepted — trading a loud transport failure for a silent quality loss, which is strictly worse than the bug being fixed.

**Consequence for the budget constants:** the single maxDistillChunkBytes must split into TWO honestly separate numbers, because conflating them is the original defect. A *page size* bounds one tool result (client-side; the current constant is mis-derived from a model-context-window rationale and measured on compact fact JSON while the delivered payload is 1.13-1.14x larger). An *item size* bounds what the model must hold at once (model-side, and genuinely per-repo — this package accommodates small local models where a 74 KB accumulation will not fit even when every page does). Paging RAISES the ceiling; it does not remove it.

**Non-scope.** This decision does NOT authorize removing the item-size cap, does NOT settle whether depth-0 distill should cluster its input (option 2 remains open and desirable), and does NOT make paging distill-specific — prune clusters are currently unchunked and unbounded, so a generic per-render paging path would give prune a safety net it lacks today. It also does not bless raising MAX_MCP_OUTPUT_TOKENS as a fix: that is a per-user harness setting usable as a stopgap, never something knomit can require.
