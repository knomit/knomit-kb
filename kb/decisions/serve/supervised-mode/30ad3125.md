# `knomit serve --supervised` is the desktop-as-parent mode: stdin EOF is a clean stop, the local socket/pipe is mandatory, a held TCP/TLS/OAuth/diagnostics address is a WARN, exit 2 means no retry will help (config, trust, unwritable server.json), exit 3 means the local listener is held by another live process, anything else is a crash

OPTIONS for the desktop's attach/spawn decision (design Q2, user accepted 2026-10-12): (a) always spawn and let the child fail; (b) probe the socket first and attach if a knomit answers; (c) lockfile-pid based. CHOSEN: (b), with (a)'s exit code as the race backstop - which is why exit 3 exists. Landed in knomit#493 (merge 9860c726).

WHAT --supervised MEANS, and only this: (1) stdin EOF = graceful shutdown, exactly as SIGTERM (the parent dying on any OS closes the pipe), exit 0, server.json removed; (2) the local socket/pipe is MANDATORY; (3) availability failures warn and serve without that listener: held plaintext TCP port, held [tls].addr, held OAuth or diagnostics address (availabilityOnly = supervised && app.IsAddrInUse); (4) exit codes returned as an ExitCodeError from RunE (never os.Exit mid-flight, so the crash marker's defers run): 2 = configuration or trust failure, an app.ListenerConfigError, 'do not retry'; 3 = auth.ErrSocketInUse, the local path is held, 'attach instead'; anything else = crash, a supervisor may restart with backoff.

USER-VISIBLE BEHAVIOUR UNCHANGED WITHOUT THE FLAG: plain `knomit serve` exits 0 or 1 only; a held TCP/TLS/OAuth/diagnostics address fails the boot (exit 1); a held socket serves TCP only with a WARN; stdin EOF is ignored (TestServe_StdinEOFIsIgnoredWithoutSupervised). See kb/decisions/desktop/tls/bind-conflict for why the policy is chosen by the flag.

NOT MEANT: (a) exit 2 does NOT mean 'bad TOML' - any non-benign ListenLocal error under --supervised (permission denied on the home, path too long, unsafe socket dir) and an unwritable server.json also exit 2, because retrying cannot fix them; (b) exit 3 REQUIRES stdin to be open: `knomit serve --supervised </dev/null` exits 0 at once even when the socket is held, because EOF wins before any listener binds - a supervisor must hold the pipe; (c) supervised + held socket + [auth].require = true reports exit 3, not the require refusal (a test pins it); (d) a trust failure is never downgraded to a warning, supervised or not; (e) a supervised serve that warned is not a fleet peer (no TLS) and may have no TCP, so a client must read server.json or the socket, not assume the configured port.

READINESS is the supervisor's job (dial the socket and GET /api/v1/version); the process says 'knomit ready' only after every listener it will have is bound.
