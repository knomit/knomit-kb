# A running `knomit serve` re-applies config only through a signal/event loop (SIGHUP, Windows named event, `knomit reload`): plaintext http/host/port, [tls].addr/[tls].dir and [log].level change live, every other changed key is only LISTED in server.json restart_needed, and there is no HTTP route or pipe message for it

DECISION (knomit#497, merge 4a9018c4): `Listeners.Reload(load)` / `Listeners.Apply(newCfg)` in internal/app/listeners_reload.go are called only from the reload trigger installed by cmd/serve.go. The trigger is SIGHUP on unix and a session-local named event on Windows; `knomit reload` is the CLI that fires either. Reload re-reads knomit.toml and runs the same loader closure as boot (so config.Validate runs and the environment still wins over toml, see the env gotcha), then diffs against the RUNNING config.

WHAT RELOADS LIVE: the plaintext TCP listener (`http`, `host`, `port`), the mTLS listener (`[tls].addr`, `[tls].dir`: a listener that was off for lack of a certificate is started, an up one is dropped or rebound), and `[log].level`. WHAT NEEDS A RESTART: every other key that differs, found by a reflection diff of config.Config over toml names (examples seen: auth.require, auth.loopback_hosts, oauth.issuer, llm.api_key, runtime.addr, socket), plus `host` when the new bind host is a DNS name the boot Host-header allowlist lacks. The names go to server.json `restart_needed` and a WARN per key; values are never written (a secret value must not reach the file; pinned by a test with a positive control). The local socket/pipe listener is never touched by Apply.

ORDER AND FAILURE: the new listener is bound BEFORE the old is closed, so a failed bind (port held) keeps the previous listener serving and records the reason in `listeners.*.reason`; the one exception is a same-port respelling (different host spelling, same port), which must close first and re-binds the old one on failure. `http = false` is refused when this process holds no local listener (nothing would be left to serve). A config that does not load or validate keeps the running config, logs ERROR and writes `reload_error`. Reload errors are logged and returned, never fatal.

RETIRING A LISTENER ENDS ITS IN-FLIGHT STREAMS: the plaintext http.Server is shared with the local socket and cannot be Closed for one listener, so each reload-bound listener is a `trackedListener` whose retirement closes the listener AND the connections it accepted. An SSE stream on a port that is switched off or moved ends (the browser reconnects to the address in server.json); the socket path is unaffected. Reason: a stream on an all-interfaces port must not outlive the setting that turned external listening off.

WHY NO HTTP ROUTE OR PIPE MESSAGE: every route on the app handler is served on every listener, including the mTLS one, so a reload route would be callable by enrolled remote peers; listener config that opens a port must change only through operator-controlled front ends (see kb/invariants/desktop/fleet/install-surface/a46bbb69.md). A signal or event is delivered by the OS only to same-user processes and carries no payload, so it can only ask the server to re-read files the operator or Settings already wrote. Enforced by test/archtest TestListenersApplyHasOnlyTheSignalLoopAsCaller, which pins callers by method name and by file: cmd/serve.go may call Reload/Apply, so a route registered inside serve.go that did would pass (a known looseness; tighten to the enclosing function).

SIGHUP NO LONGER TERMINATES `knomit serve`: it used to die on SIGHUP (default action, e.g. closed terminal); now it keeps running and reloads. Anyone scripting `kill -HUP` as a stop must use SIGTERM. Protection for the reverse hazard, a hand-sent `kill -HUP` at an OLD server binary that predates reload (it WOULD die): `knomit reload` refuses unless server.json says `reload: true`; a person typing kill -HUP at an old server is not protected.

NOT MEANT: (1) Reload does not re-read the process environment: the server's env is the one it started with. (2) `restart_needed` is relative to the running config, so it persists until restart. (3) `knomit reload` and `kill -HUP` are one trigger, not two features. (4) For the desktop's own in-process boot (until PR 5) nothing changed: it still decides at boot.
