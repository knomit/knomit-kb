# A fleet listener that is configured but waits for this instance's certificate is NOT a reload failure, and only while NOTHING is listening: serveraddr.ListenerWaitsForCertificate = reason no_certificate AND Listening empty; `knomit reload` exits 0 with a waiting line, the log says Info, and a still-bound listener with that reason stays a failure (#545)

DECISION (PR #545, merged into dev at 7ce30154; read there). Before it, `no_certificate` was one of the exit-1 reasons of `knomit reload` (kb 6679f9ff), so the step BEFORE a fleet create (set the Fleet port, reload) looked broken: red Settings line, exit 1, though the create installs the certificate and starts the listener (kb 7a1bd4ee).

RULE. `serveraddr.ListenerWaitsForCertificate(l)` is `l.Reason == "no_certificate" && l.Listening == ""`: configured, no certificate yet, and nothing serving meanwhile. Four places use that one rule: (1) `ReloadListenerFailures` does not count a waiting listener, so `knomit reload` exits 0 and the desktop ack is `applied`; (2) `knomit reload` appends `, ` + `serveraddr.TLSWaitingForCertificate` to that listener's line, so the output is `  tls: off (no_certificate), waits for this instance's certificate: it starts when this instance creates or joins a fleet`; (3) cmd/serve.go `reloadItemWaits` (item `tls`, reason no_certificate, nothing bound) logs the reload at Info, not ERROR ("reload: the mTLS listener waits for this instance's certificate; a fleet create or join starts it"); (4) the desktop `ackLine` (SettingsForm.tsx) shows the neutral FLEET_PORT_WAITING note only when `tlsReason === 'no_certificate' && !tlsListening`. An attached older server that answers `listener_failed` only for the waiting Fleet port gets the same note; a held HTTP port beside it is still the red error.

THE `Listening` CONDITION IS LOAD-BEARING (review finding F1). `Listeners.Apply` also reports no_certificate when a reload moves `[tls].dir` to a directory with no certificate, or a member's certificate was deleted, while the previous listener keeps serving (state Configured X, Listening X, Reason no_certificate). That is a requested change that did NOT happen. With the reason alone as the test it was reported as waiting, exit 0, and the desktop printed "Saved and applied". With the extra `Listening == ""` it stays a failure: exit 1 and a red error. Pinned by TestReloadListenerFailures_OnlyAFailedListenerCounts (bound row), TestReloadItemWaits_OnlyTheUnboundFleetListenerWithoutACertificate and the desktop bound-no_certificate test; sabotage of each rule turns its test red.

STILL FAILURES: addr_in_use, bind_failed, tls_failed, refused (and no_certificate with a listener bound). `off` is still a state the user asked for.

CONSEQUENCE. `knomit reload && next` is now safe on a fresh instance that only set the Fleet port; exit 0 does NOT mean the Fleet port is open, only that nothing the reload asked for failed: the create or join opens it. Nothing new calls Reload or Apply; test/archtest/reload_callers_test.go still passes.

MISREADINGS. "no_certificate never fails a reload": it fails when a listener is still bound. "exit 0 means members can connect": the listener is not up until the create or join. A port held by another program also reads as waiting before the certificate exists (see the gotcha on a held Fleet port before a certificate).
