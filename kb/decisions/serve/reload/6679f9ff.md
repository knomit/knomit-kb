# `knomit reload` signals only a server whose server.json says `reload: true`, for the same data root, and whose local listener answers; it exits 0 only when every requested listener change applied, 1 on a refused config or a failed bind, and 1 on a 5 s timeout with no acknowledgement

BEHAVIOUR (cmd/reload.go, knomit#497 merge 4a9018c4). Resolves the data root (KNOMIT_HOME), reads that root's server.json and REFUSES to signal unless: the file exists; its `home`, when present, equals this root; `reload` is true (an older server or a file from before reload is refused with 'does not listen for reload: restart it'); and, when the file names a `socket`, the local listener answers a dial (2 s). Reason: SIGHUP's default action ends a process, so a stale file whose pid was reused, or a server from before reload existed, must never be signalled. The dial is a refusal check on the file's claim, not a liveness decision (liveness stays the flock, kb/decisions/auth/socket-liveness-flock/b27c556d.md). KNOWN GAP: when server.json has no `socket` the dial check is skipped, so a stale `reload: true` file with a reused pid would get the signal; only a server configured with an empty socket produces such a file.

THEN it signals (kill -HUP, or sets the Windows event) and polls server.json every 50 ms for up to `--wait` (default 5 s; 0 = fire and do not wait, prints 'reload requested'). Poll order: (1) same pid and generation higher than before: print 'reloaded (generation N)' plus each listener's state and any needs-a-restart list, then evaluate reloadOutcome; (2) same pid and `reload_error` differs from the value read BEFORE signalling: fail with 'reload refused, the running configuration is unchanged: <error>' immediately, without waiting out the timeout; (3) deadline: fail with 'did not acknowledge within 5s (generation still N); its log says why'.

EXIT CODES: 0 = generation advanced and no listener has a reason other than empty, `off` or (#545) a fleet listener waiting for its certificate with nothing bound (`off` is a state the user asked for). 1 = reloaded but a listener reason is a failure (addr_in_use, bind_failed, tls_failed, no_certificate WITH A LISTENER STILL BOUND, refused; but see the #545 update at the end: no_certificate with nothing listening is not one): the outcome is printed first and the error says the previous listener keeps serving where there was one; or config refused (reload_error); or timeout; or any pre-signal refusal. So `knomit reload && next` is safe, and a generation advance is NOT by itself success.

NOT MEANT: the timeout does not prove the signal was lost (a parked reload before the server is ready, or a hung server, look the same); a refused config is distinguishable only because the server writes reload_error.

WINDOWS: the trigger is the session-local event described in the Windows reload event fact; when the event does not exist, missingEventError says 'probably running in a different Windows session' if the pid in server.json is alive, and 'no running knomit serve' only if it is dead.

MOVED (knomit#504, merge 1c6a0934): the logic described above no longer lives in cmd/reload.go. It is `serveraddr.RequestReload(ctx, home, wait)` and `serveraddr.SignalReload` in internal/serveraddr/reload.go (+ reload_unix/windows/other.go), with the typed errors ReloadRefusedError, ReloadTimeoutError and ReloadListenerError; `runReload` in cmd/reload.go is a thin wrapper that prints the same messages and keeps the same exit codes (the strings were compared line by line against the old file; the reload tests moved with the code to internal/serveraddr/reload_test.go). Reason: the desktop's Settings binding is the second caller and cannot import cmd (TestDesktopLinksNoServer). The 'known gap' and exit-code semantics are unchanged. Callers are pinned: kb/invariants/serve/reload/reload-client/6ba726a8.md. Where this fact says `cmd/reload.go` read `internal/serveraddr/reload.go`; `signalReload` is now exported as SignalReload.

UPDATE (PR #545, merged into dev at 7ce30154, re-read there): `no_certificate` is no longer an exit-1 reason when the fleet listener is merely WAITING for this instance's certificate, i.e. reason no_certificate AND nothing listening (`serveraddr.ListenerWaitsForCertificate`). `ReloadListenerFailures` skips such a listener, so `knomit reload` exits 0 and prints the extra text `waits for this instance's certificate: it starts when this instance creates or joins a fleet` on that listener's line; the server logs it at Info. no_certificate with a listener STILL BOUND (a reload moved [tls].dir to a directory with no certificate, or a member lost its certificate) is still a failure, exit 1. Where the EXIT CODES paragraph above lists no_certificate as a failure, read this update. Full decision and pins: kb/decisions/serve/reload/waiting-for-certificate/1e14e1f4.md. MISREADING: exit 0 does not mean the Fleet port is open; the create or join opens it.
