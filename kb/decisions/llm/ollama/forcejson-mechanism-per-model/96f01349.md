# ForceJSON picks its mechanism from the model's thinking capability — grammar for non-reasoning models, prompt for reasoning ones

CompletionOptions.ForceJSON states a REQUIREMENT ("the caller needs parseable JSON") and no longer names a mechanism. OllamaAdapter probes /api/show at construction and branches: a model advertising the "thinking" capability is sent NO `format` field and carries the JSON demand in its system prompt; a model without it keeps `format:"json"`.

**Options considered**
1. Keep `format:"json"` always (status quo).
2. Disable thinking (`think:false`) on ForceJSON calls, keeping the grammar.
3. Send `format` as a full JSON schema object instead of the string "json".
4. Keep thinking on and drop the grammar constraint for reasoning models (chosen).

**Rationale**
`format:"json"` is a decoding constraint the runner must suspend for the reasoning phase and resume for the answer, and that seam is where output breaks. Measured on gemma4:26b-mlx via ollama 0.32.5, each response run through internal/corpus/synthesize's extractJSON:
- `think:true` + `format:"json"` → 1/4 parsed
- `think:true`, no `format` → 4/4 parsed
- `think:true` + `format:<schema>` → 2/4 parsed
- `think:false` + `format:"json"` → 3/3 parsed

Failures were NOT recoverable fenced JSON (extractJSON already strips fences): one response opened with a bare literal `json` before the fence, another returned YAML-ish key/value pairs. Option 2 was rejected by the user on purpose grounds — reasoning quality is the reason for running a local reasoning model at all, and a non-thinking gemma4 answered a trap riddle wrong. Option 3 measured worse than dropping the constraint and the MLX backend ignored the schema entirely on a separate probe.

**The choice**
Branch on the server-reported capability, not on a config knob and not on the model name. A failed/unanswered probe is NOT fatal — it falls back to the grammar path, which is the pre-existing behaviour.

**Non-scope**
This does NOT mean "ollama should never send format:json". For a model without the thinking capability the grammar is a hard guarantee where a prompt is only a strong convention, and those models never exhibited the failure — the constraint stays for them. It also does NOT authorise disabling thinking to make parsing easier. It says nothing about non-ollama providers, whose thinking support is a separate mechanism with its own budget semantics.

STATUS AFTER PR7 (chore/remove-synthesis-job): the mechanism this fact decides is DELETED. `CompletionOptions` (and its ForceJSON field), the v1 `OllamaAdapter` and its `jsonStrategy` are gone with the whole v1 Complete path; the refs pin the code before the deletion (same blobs at ddb66b59, the last commit that has them). The in-process harness's Ollama adapter (`OllamaChat` in internal/engine/llm/ollama_v2.go) sends tool-calling chat requests and has no ForceJSON or `format` field; it still probes /api/show at construction (that probe was COPIED into ollama_v2.go by PR3, which is what allowed the v1 file to be deleted), but for capabilities and the trained context, not to pick a JSON mechanism.

The MEASUREMENT above (gemma4:26b-mlx on ollama 0.32.5: `think:true` + `format:"json"` parsed 1/4, `think:true` without `format` 4/4) is still the evidence to read before anyone adds a `format` constraint to a reasoning model's request. DOES NOT MEAN: that the decision is in force; nothing in the tree sends `format` any more, so there is no code to branch.
