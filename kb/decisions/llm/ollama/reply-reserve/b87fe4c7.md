# Ollama's reply length defaults to min(8192, num_ctx/4) and is sent as num_predict; the loop reserves Caps().MaxOutput against the EFFECTIVE window min(num_ctx, trained), or window/4 when MaxOutput is <= 0 or >= that window, so the two can differ

Decision (user, 2026-11-04): num_ctx covers prompt and reply together, so the loop must reserve reply room. OllamaOptions.MaxOutput 0 now means min(8192, NumCtx/4) (withDefaults in internal/engine/llm/ollama_v2.go); negative means uncapped. 8192 is a quarter of the default 32768 window, chosen from the window, not a measurement; reasoning tokens count against num_predict on Ollama, so the figure leaves room for thinking as well as the answer.

The same value is sent as options.num_predict (a positive MaxOutput; a negative one sends -1, no cap), so generation normally stops at the reserved length instead of running into the window: with shift:false an overrun of num_ctx ends done_reason length (ErrTruncated), and num_predict -1 (the earlier default) let a reply fill the window exactly. The loop's replyReserve (agent.go) is Caps().MaxOutput, or ContextWindow/4 when MaxOutput <= 0 or >= ContextWindow, so a misconfigured model never refuses every request. The two values are NOT always the same number: the default MaxOutput is computed from NumCtx (withDefaults), but Caps().ContextWindow is the effective window min(NumCtx, the model's trained context from /api/show). When the trained length is below NumCtx, MaxOutput can be >= that window, the loop reserves window/4, and num_predict stays at the NumCtx-derived default. With a negative MaxOutput (uncapped) the loop also reserves window/4 while num_predict is -1.

Consequence: a reply that spends its whole budget thinking ends as 'The reply hit the output limit', with no text; the turn is dropped if it was the first request. Does NOT mean Anthropic is affected: its MaxOutput comes from ModelProfile (default 64000).
