# Ollama sends no reply cap by default (num_predict -1); the loop still reserves window/4 of the EFFECTIVE window min(num_ctx, trained) as a pre-send check only, or the explicit MaxOutput (request first, then model) when one is set

Decision (user, 2026-11-04, superseding the same day's earlier min(8192, num_ctx/4) default): num_ctx covers prompt and reply together, so the loop must reserve reply room, but the reserve must not limit the reply. OllamaOptions.MaxOutput 0 (or negative) means NO cap: options.num_predict is -1. A positive MaxOutput, from config max_output or a request's StreamOptions.MaxOutput, is sent as num_predict and is also what the loop reserves. There is no code constant for a default reply length (the former 8192 is removed).

The loop's replyReserve (agent.go) is the reserve used by checkBudget: StreamOptions.MaxOutput when > 0, otherwise Caps().MaxOutput; and ContextWindow/4 when that is <= 0 or >= ContextWindow, so a misconfigured model never refuses every request. Caps().ContextWindow for Ollama is the effective window min(NumCtx, the model's trained context from /api/show). With no configured cap the reserve is therefore window/4 while num_predict is -1: the reserve is a check made before sending, it does not stop generation.

A reply that reaches the window end still ends done_reason length (shift:false), which is ErrTruncated, never success. Consequence: a reply that spends the whole remaining window thinking ends as truncated with no text; the turn is dropped if it was the first request. Config validation (PR5): Ollama max_output must be below min(num_ctx, trained length); the trained length is only known at probe time, so the registry refuses the model then.

Does NOT mean Anthropic is affected: its MaxOutput comes from ModelProfile (default 64000). Does NOT mean the reply is unbounded in practice: it is bounded by the window, not by a derived cap.
