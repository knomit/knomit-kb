# A missing LLM API key is a configuration, not a fault: the registry wraps llm.ErrNoCredentials when a provider's key cannot be resolved, so a caller can tell a configuration gap from a fault

HISTORY: every first-mission instance once logged `WRN LLM adapter init failed: GEMINI_API_KEY ... required` plus `WRN synthesis disabled`, though none needed a key: knomit_review and knomit_hypothesize hand the LLM work to the calling agent. #412 (merge 55a47911) made an absent key ONE info line (`logLLMSetup` in internal/app/llm_log.go, over the v1 server adapter).

SUPERSEDED BY PR7 (chore/remove-synthesis-job): the server-side synthesis job (web RunAll), the v1 LLMAdapter/NewAdapter/ResolveProvider path, `NewGeminiAdapter` and `logLLMSetup` with its "synthesis enabled" / "synthesis disabled" lines are all deleted, so those log lines no longer exist. The sentinel stays: PR7 moves its declaration from resolver.go to internal/engine/llm/credentials.go, and `Registry` (registry.go, as of ddb66b59) returns `fmt.Errorf("%w: provider %q has no api_key_file, api_key_env value or api_key", ErrNoCredentials, provider)` when a configured provider's key cannot be resolved; TestRegistry_MissingKeyIsErrNoCredentials pins it. The refs pin ddb66b59, the last commit before the deletion.

CONSEQUENCE for a new provider: wrap ErrNoCredentials when its key is absent, so a caller can tell a configuration gap (errors.Is) from a fault.

WHAT THIS DOES NOT MEAN: it is not a boot failure or a log line any more; the only consumer is whoever lists or opens a model. A bad or rejected key is still a provider error, not ErrNoCredentials.
