# Anthropic v2 places at most three cache breakpoints: 1h on the last hook-3 system block (tools+system+instructions), 1h on the last hook-4 frame block when present, 5m rolling on the last cacheable block of the last message; hook 5 gets none

renderAnthropic (internal/engine/llm/anthropic_v2.go) maps hooks onto the API's cache order tools → system → messages: tools = hook 1 in name order; system = text blocks of hooks 2, 3, 4, 5 in that order (empty texts skipped, the API rejects them); messages = hook 6 then hook 7, each entry ReplayFor("anthropic", model), consecutive same-role items merged into one message. Breakpoints: cache_control{ephemeral, ttl 1h} on the LAST block of hooks 2-3 (normally system[1], the instructions), which caches the whole per-permission-set prefix; a second 1h on the last hook-4 block when a frame exists; the rolling cache_control ttl 5m on the last block of the last message, skipping back over thinking/redacted_thinking blocks, which cannot carry cache_control. Hook 5 (working set) is deliberately uncached. Max three of the API's four, and every 1h precedes the 5m one in render order, as the API requires for mixed TTLs.

Pinned by TestRenderAnthropic_BreakpointsAtHookBoundaries (exact JSON paths: $.system[1] 1h and $.messages[2].content[0] 5m; with a two-item frame also $.system[3] 1h) and by TestAnthropicChat_StreamMapsEventsAndUsage, which asserts the same paths in the body the httptest server received.

NOTE: the marshalled JSON puts "messages" before "system" (SDK struct field order); byte position in the JSON is not render order, so never check TTL order by string index.
