# While a repo indexes (or after its index was cancelled or failed) search answers from the PARTIAL index and the status says so (index_state, index_reason) — this degradation is accepted and must NOT be fixed by making requests wait for index readiness

Issue #411, rule 8. The Open stage attaches the store before Index starts, so a repo serves reads at once and its vector index fills in behind. A query during that window, or after CancelIndex / a failed heal, can miss facts that exist. That is the accepted cost; the remedy is visibility, not blocking: every repo row and branch status carries index_state (ready|indexing|error) and index_reason, the repo-events stream carries the same, and the UI chip shows it on every row.

Do NOT: add a wait on index readiness to any request path (query, explain, write, origin changes, the create job's register step), add a 'block until indexed' option, or retry a search until the index is ready. Each turns a background job into a foreground stall — the class of bug the lifecycle machine exists to remove — and the index can take minutes.

What this does NOT mean: it is not 'index errors are fine'. An error state is shown and Rebuild re-indexes; the create job still reports done only once the state left indexing (it observes; it does not gate the repo).

MOVED (14b, PR #631, merge 37dc65d5, re-read there): the IndexStatus named in the entities is now events.IndexStatus {State, Done, Total, Reason} in internal/corpus/repos/events/status.go, part of the public events.Status that Machine.Status() returns. The rule is unchanged: the degradation is visible through index_state and index_reason, never fixed by waiting.
