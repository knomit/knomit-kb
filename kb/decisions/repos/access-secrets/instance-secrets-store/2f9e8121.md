# Store forge credentials as per-instance secrets in control.db, additive to the per-repo pasted credential

Describes the agreed design for feat/access-secrets, not shipped behaviour (the code does not exist yet).

Options considered: (1) replace the per-repo pasted credential with secrets; (2) add secrets alongside it; plus, separately, a helper that matches existing repo tokens by value and migrates them.

Rationale: the goal is to rotate one credential once per instance and have every linked repo pick it up with no reconnect. Replacing the per-repo credential would break every existing repo and force a migration; value-matching migration was judged not worth its risk and complexity, and the user prefers to relink repos by hand once.

Choice: a per-instance secrets store in control.db, encrypted with the existing instance Crypt (AES-256-GCM, key derived from the instance SSH key file). Each secret has a stable internal ID (what repos link to) and a renameable friendly name, a type (token, username/password, or SSH private key with optional passphrase) and an optional expiry. Repos link to a secret as an additional option; the pasted per-repo credential stays the default and unchanged. No automatic migration and no find-repos-holding-this-token matching.

Non-scope: does not remove or deprecate the pasted credential; does not share secrets across instances; replacing the instance key file still makes stored secrets undecryptable, as it does for repo tokens today.
