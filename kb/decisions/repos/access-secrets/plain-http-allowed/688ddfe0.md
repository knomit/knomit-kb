# Stored token and basic secrets may be linked to plain http:// remotes; the secret's hosts list, not the scheme, is the guard

Options considered (raised in the review of the linking PR): (A) allow token and basic secrets only on https:// remotes, with an exception for loopback hosts so local test and dev forges still work; (B) allow them on http:// and https:// alike, as checkSecretFits does.

Rationale: the user chose to keep plain http allowed. A stored secret is already bound to an explicit hosts list that the operator wrote and that is re-checked at link time and at every resolution, so the secret only ever goes to a host the operator named; an https-only rule would add a second, scheme-based policy with its own exception for loopback, and would refuse self-hosted forges an operator deliberately runs on http.

Choice: (B). checkSecretFits (internal/corpus/repos/secret_auth.go, with isHTTPURL in origin_method.go) accepts token and basic secrets for http:// and https:// URLs; ssh_key needs an ssh URL.

Non-scope: this does not loosen host binding (the hosts list still decides every send), it does not make plain http safe against an on-path observer (that risk is the operator's, by naming an http host), and it says nothing about fleet origins, which require https on their own (refuseFleetOrigin).
