# A sync round that force-updated the consensus branch re-records the repo's identity at once (reidentifyAfterRewind -> recordIdentity, Identify's rule on the read branch's root), so after a replace_main attach HeldByAnotherActiveRepo names the repo from that first round, not its next mount; recording the origin's root ahead, at attach, was rejected because the store does not always end up with it

CONTEXT (branch fix/origin-attach-followups, PR #682; PR #676 review, found-not-fixed item 1). After an attach with replace_main, repos.repo_id kept the repo's OLD root until the next mount's Identify, while its main (and, after the replay, its agent branch) carried the origin's root. In that window HeldByAnotherActiveRepo did not name the repo for the origin's knowledge base, so a second local copy could be created; at the next mount Identify hit the unique index (repos_active_repo_id) and the repo went Unavailable (identityConflict). Reproduced by TestOriginEscalation_ReplaceMainReidentifiesAtOnce with the fix removed: the copy is created and the remount lists x unavailable with cause identity_conflict.

OPTIONS. (a) Record the origin's root (the guard's ProbeBranchHistory Root) in applyAttach, before the git remote moves. Built first and REJECTED: it predicts what the reconcile will do, and the prediction is wrong when the agent branch has nothing to replay onto a DISJOINT upstream (observed: the first unrelated origin of a repo whose main holds no fact; replayOntoUpstream keeps the branch, the known gap in kb/gotchas/store/remote-reconcile/rewind-residual-leaks/cd3a2bbf.md, issue #541): the agent branch keeps its old root, and the next Identify would flip repo_id back, freeing the origin's root. It would also be a second identity rule (probe root vs read-branch root). (b) Rewind the machine to Identify after the round: one site, but it re-enters Index/Serve/Sync and needs a stage to drive its own machine. (c) CHOSEN: after a successful fetch round whose remotesync result has Main.Mode == ModeRewound, runReconcileLoop calls its `rewound` callback, which the Sync stage (and OriginRoundForTest) sets to RepoInstance.reidentifyAfterRewind: RootCommit of the read branch, then recordIdentity. recordIdentity is now the ONE RecordRepoID call for a mounted repo, shared with identifyStage.Enter, so the identity rule (root of the read branch, unique among active repos) stays in one place and reads the store's truth.

WHAT IT DOES NOT DO. It does not change the in-memory RepoInstance.ID() (kb:// addressing) or reload the ontology: those still change at the next Identify. A conflict found by the round (another active repo registered the root between the attach guard and the round) cannot make the repo Unavailable mid-life: it is logged, and the next mount's Identify does so as before. The attach guard's root layer (HeldByAnotherActiveRepo on the probed root, before replace_main is consulted) is what refuses a root that is already held, up front; pinned for replace_main by TestOriginEscalation_ReplaceMainOntoAnotherReposRootIsRefused.

RESIDUAL (accepted, point-in-time like the rest of the attach checks): between the attach and the end of its first successful round the old root is still recorded; in production that round starts as Sync re-enters. If no round succeeds before a restart, Identify records what the store holds (the old root), which is correct for that store.

COVERS MORE THAN replace_main: any round that rewinds the consensus branch re-derives the root, including PATCH /origin/upstream with replace_main and a forge-side rewrite of main (trusted as fetched, kb/decisions/fleet/trust-the-forge-main/3a19b2d3.md). A rewind that keeps the knowledge base records the same id again, a no-op.

PINNED BY (sabotage at c3c214cb): `if false && rewound != nil ...` in runReconcileLoop -> TestOriginEscalation_ReplaceMainReidentifiesAtOnce red at the repo_id assertion, and with that assertion skipped, at the create refusal and then at the remount (identity_conflict); drop the guard's root-layer `return alreadyLocal(holder)` -> TestOriginEscalation_ReplaceMainOntoAnotherReposRootIsRefused and _OperatorRefusedAnotherReposKBByItsRoot red.

NOT COVERED (PR #682 review N3 and N5; both follow-ups, neither a fail-open):
- N3, a round that replays and then fails. The callback fires only when the fetch round returns no error (internal/corpus/repos/sync.go, `rewound != nil && syncResult.Main.Mode == merge.ModeRewound` in the success branch). remotesync Index.sync can return an error AFTER reconcileAgent has already replayed the agent branch onto the new main (for example when recordOriginIdentity fails). The next round's main is then not Rewound, so the repo is NOT re-identified until its next mount. It needs a control-plane write failure, so it is rare. A later fix would trigger on 'the read branch's root differs from the recorded repo_id' instead of on the rewind.
- N5, an empty repo attached to an unrelated origin WITHOUT replace_main (admitted because its main holds no fact). main takes the origin's root, but the agent branch, the read branch, keeps its seed root, because replayOntoUpstream keeps a branch on a disjoint upstream (kb/gotchas/store/remote-reconcile/rewind-residual-leaks/cd3a2bbf.md, issue #541). So repo_id never names the origin's knowledge base, not at this round and not at any mount, and once the origin moves ahead a second local copy of it can be created (the b27a57c6 clobber); later rounds also fail with 'no common ancestor'. Re-identify does NOT close this; it is the #541 shape, for the user to triage.
