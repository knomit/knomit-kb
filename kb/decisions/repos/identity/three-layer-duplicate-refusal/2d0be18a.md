# A duplicate knowledge base is refused at THREE layers, cheapest first — the origin's advertised knomit-repo-id, an advertised tip already held by an active local repo, and the root commit of the fresh clone before registration — with RecordRepoID after Add kept as the backstop; layer 2 is sufficient-only and never skips layer 3

Decided 2026-09-16 with the user (PR #208) after an incident: a subscribe to a peer knomit's cyberai-kb cloned 3254 commits, registered, started indexing, and only THEN was refused with "this knowledge base is already registered" (correct: the same KB was local under another name). The refusal came after minutes of work because Registry.RecordRepoID ran after m.Add, and its failure cancelled the background index heal (the "context canceled" in the log was a consequence).

Three layers now, each pinned by a test that fails when that layer alone is removed, plus a counterpart test that an UNRELATED remote is not refused (without which refuse-everything would satisfy all three):

1. A knomit origin advertises `knomit-repo-id=<40-hex root commit of its consensus branch>` as a capability (buildAdvRefs; empty root skips the capability rather than breaking the advertisement, since go-git rejects an empty capability argument). CreatePreflight reads it from the one advertisement ProbeInitialized already pays for (an unexported remoteProbe holds it so identity and ontology-shape are answered from one handshake) and refuses via HeldByAnotherActiveRepo naming the holder. Cost: the server sees only /info/refs.
2. For ANY origin, each advertised branch tip is checked against every active local store (Service.HasObject). A hit proves the same knowledge base (commits are unique to a history). A MISS PROVES NOTHING: the local copy may be behind. Layer 2 is sufficient-only and must never short-circuit layer 3.
3. Right after InitSubscription/InitFromRemote returns, before m.Add: svc.RootCommit(upstream) + HeldByAnotherActiveRepo, refusing with ErrKnowledgeBaseAlreadyLocal (HTTP 409 "Knowledge base already registered"). Also runs in initInitialize ABOVE its push, because that mode inherits the remote's root and refusing above the push leaves the remote untouched.

RecordRepoID after Add stays exactly as before as the backstop (the invariant b27a57c6 names it the real guard); with layer 3 disabled the story test still fails on the backstop's message.

Placement facts: ProbeOrigin is UNTOUCHED (it keeps remote.ListContext and its four-state classification, per 328dcc0f); the layers live in CreatePreflight. InitializedResult gained `already_local`, ORTHOGONAL to the three-state `initialized` (a remote can be a knowledge base AND already local); the wizard's branch step renders it as an advisory; CreatePreflight is the authoritative refusal.

Fixture trap that bit during implementation: a layer-1 test passed with layer 1 deleted because the local copy held the origin's tip and layer 2 answered. The fixtures now move the origin AHEAD of the local copy and assert tipHeldLocally is empty before asking layer 1.

Misreadings: "layer 2 said no duplicate" is never a verdict; only layer 3 (or the backstop) clears a clone. Layer 1 trusts the origin's claim only to REFUSE early; identity is never recorded from it.
