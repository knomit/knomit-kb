# User ruling (PR 646): trigger `if` sandbox setup gets no limit of its own; its cost grows with the fact's element count and facts are realistically small

USER RULING on PR #646 (merge ff045df3): there is NO separate limit on the time CompiledTrigger.EvalIf (internal/domain/fact/triggers.go) spends in setup (bindGlobals: sandboxGlobals, i.e. marshal, JSON.parse and deepFreeze of the globals). The 100ms ifBudget() starts after setup and bounds the condition only.

OPTIONS PUT TO THE USER: a separate setup bound, a cap on the fact's node count, or nothing. CHOSEN: nothing. REASONS: setup cost scales with the number of array and object elements, not bytes (review measurements on one dev machine, not a property of the code: about 0.5s of freeze at 1M entities, about 66ms at 100k, a few ms for a 16MiB body of one string); facts are realistically small; the same writer already pays O(size) in parse, index and embed.

CONSEQUENCE. A fact with a huge entity, domain or ref list costs roughly 0.6s of serial, non-cancellable time per active matching trigger in the dispatcher's phaseB (EvalIf takes no ctx). An if-timeout still means the condition was slow, never that setup was. Do not reintroduce setup into the budget to bound it (that was the pre-#646 bug), and do not add a constant for it without a new ruling.

WHAT THIS DOES NOT MEAN. It is not a claim that setup is cheap in general or a guarantee for any machine. It says nothing about runSandboxed in script.go, which keeps its own 5s ScriptEvalTimeout armed before setup.
