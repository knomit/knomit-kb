# The trigger dispatcher reaches back into the repos instance through exactly four injected funcs (acquire, syncWake, indexReady, bind); about five is the ceiling, and a sixth upward call means the code belongs in the parent

User ruling Q1 on PR #632 (14c, merged as ee850fd6; re-read there). The dispatcher holds no *RepoInstance. Its only ways back into the instance are four funcs given to trigger.New by Manager.newInstance: acquire (ri.Acquire, the store lease), syncWake (ri.wakeSync, the push action's non-blocking wake of the sync loop), indexReady (a closure that calls ri.Status() and compares Index.State with ready; evaluated at CALL time, never captured once) and bind (builds a FRESH WithBinding(ctx, NewBindingOfRepo(ri, agentBranch)) per call, reading ri at call time, so nothing goes stale on a rename). serverAddr (Manager.ServerAddress) was already a func, so there are five func values in all. The repo's *events.TaskPublisher is a constructor parameter held in an unexported field (f6d5c104); ontologyRoot is a value fixed at instance construction and never reassigned.

CEILING. About five. Rejected: a struct-of-funcs or an interface standing in for the instance (it re-creates the *RepoInstance coupling under another name). CONSEQUENCE: if a change needs a sixth func into the instance, the code belongs in the parent (or the contract needs a ruling), not in the child with one more closure.

MISREADINGS. Func values are not a license to capture state once: indexReady and bind are evaluated per call on purpose. And 'the dispatcher reads RepoInstance state' is true only through these funcs; the dispatcher's no-write allowlist (TestTriggers_RepoCallsAreAllowlisted) names d.acquire, d.syncWake, d.Kick and d.bind as its only upward keys.
