# The dispatcher's two tables (migration 000029): trigger_fires keeps the newest 10,000 rows per repo with exactly ONE run row per run and no if-false rows; phase C is WRITE-BEHIND — tx1 (fire rows + run rows) then tx2 (watermarks + rowid-range prune) flushed only after the writer has been quiet for 20 ms, at a size bound, or at shutdown — because flushing after every run cost a busy writer 5–7 ms per write

internal/store/triggers.go (TriggerIndex: RecordTriggerRuns, AdvanceTriggerWatermarks, RecentTriggerFires) and internal/repos/triggers.go (pendingFlush, buffer, settle, flush, flushOnStop); migration 000029_triggers — it was 000028 on the branch until F09 PR 5 (#334, drop verify_context) merged first and took that number; a merged migration is never renamed, so the trigger tables moved to 000029 before 1b was pushed.

TABLES. trigger_fires(id AUTOINCREMENT, trigger, branch, path, episode, source, commit_hash, trace, outcome, error, nonlinear, range_from, range_to, evaluated, paths, fires, fires_not_logged, duration_ms, diff_ms, change_ms, fired_at). One row per emitted fire or error outcome (emitted | unparseable | if-error | if-timeout); `if-false` evaluations are COUNTED in the in-memory statistics and never written, so the cap holds real fires (M2). Exactly ONE run row per dispatcher run (trigger '', outcome 'run') with the coalesced range_from/range_to, paths, evaluated, fires, fires_not_logged, duration_ms, diff_ms, change_ms — one row however many triggers exist (TestDispatch_OneRunRowPerRun). range_from/range_to on every row are the coalesced W → H. fired_at is local Unix seconds, the only clock in F07 PR 1: written for the operator, never read for ordering. RETENTION: tx1 inserts at most TriggerFireRetention (10,000) rows per run — the newest paths, the rest counted in fires_not_logged (TestRecordTriggerRun_Tx1Bounded: 12,000 fires → 10,000 rows + run row with fires_not_logged 2000; statistics count all 12,000) — and tx2 prunes with `DELETE WHERE id <= MAX(id) - 10000` (a rowid range on the primary key), so the log holds exactly the newest 10,000 rows including run rows (TestTriggerFires_PrunesToRetention). The log is operator cache, not the audit trail (the trail is the trace trailers in git). CREATE TABLE IF NOT EXISTS: upWithRecovery re-runs bodies.

WRITE-BEHIND (the one place 1b deviates from 'phase C per run'). The repo DB runs every transaction as BEGIN IMMEDIATE (the process-wide write lock) with a 5 s busy timeout, and SQLite's busy handler sleeps in 1, 2, 5, 10… ms steps. A fact write takes that lock several times per commit. Flushing phase C right after every run put two dispatcher transactions in the middle of the NEXT write, and each collision cost the writer at least one busy-handler step: measured 10.2 → 17.1 ms median write latency with 50 matching triggers (the kick alone: none; 50 non-matching triggers: 15.5 ms; phase C skipped: 12.4 ms). So a run BUFFERS its phase C (pendingFlush: the runs with their rows, the watermark moves, the deletes) and the actor flushes when no kick has arrived for triggerFlushGrace (20 ms), when the buffer reaches TriggerFireRetention rows or maxBufferedRuns (256), or at shutdown (flushOnStop, store still attached). Under a burst the fire rows and watermarks of several runs land in ONE tx1 and ONE tx2 after the burst (RecordTriggerRuns writes several runs in one transaction with multi-row INSERTs); a lone write flushes ~20 ms after its run. Measured with the deferral: 5.4 → 6.5 ms median (TestDispatch_WriteLatencyIndependentOfTriggers measures in ALTERNATING blocks, because write latency on this store also grows with the repo — 4.7 ms at 50 facts to 16 ms at 1,000 — so a first-then-second layout confounds the comparison).

WHAT THE BUFFER DOES NOT CHANGE: emits happen in phase B immediately; each run still yields one run row; tx1 always precedes tx2; phase A OVERLAYS the buffered watermarks on the stored ones, so a buffered advance is never diffed twice; a crash before the flush loses the buffered log rows and re-fires the range on restart — the at-least-once shape the proposal already states for a crash before tx1; a failed or PANICKING flush drops the buffer for the same reason (the tables are then the truth; TestDispatch_CrashBetweenFireAndWatermark panics between tx1 and tx2 and sees the rows logged, the watermark behind, and the range re-fired on restart); a buffer built against a previous store generation (SwapStore) is dropped. Consequence for readers: GET …/triggers overlays the buffer on the stored watermarks, but the fire log lags a burst by up to 20 ms plus the flush.

Misreading: 'one transaction would be simpler' — moving the watermark into tx1 is the crash test's SABOTAGE; the two-transaction order is what makes a crash re-fire rather than lose.
