# control.db owns origin URL, branch AND credential; the repo store's auth columns are emptied and never read

PR #61 made control.db authoritative for WHAT repos exist and re-clones a lost repo from its recorded origin. That promise was empty for private origins: the credential lived encrypted in the repo's own `remotes` table — inside the very file whose loss triggers the rebuild. PR #65 closes it.

**Options considered** (each resolved explicitly with the designer, not inferred):

1. *Recovery scope* — (a) same machine, lost repo `.db` [CHOSEN]; (b) new machine with control.db + agent key restored; (c) new machine with control.db alone. (c) was rejected because it requires abandoning key-derived encryption (passphrase / OS keychain / plaintext).
2. *Ownership* — (a) control.db owns intent, the store materializes it [CHOSEN]; (b) control.db only, the store stops storing config entirely; (c) both, with guaranteed bidirectional sync. (b) touches 11 call sites plus the store's internals for no extra safety; (c) keeps two writers and so keeps drift possible forever.
3. *Token location* — (a) control.db only, the store's auth columns stay empty [CHOSEN]; (b) materialize the token into the store as well; (c) (a) plus a store migration dropping the columns. (b) duplicates the ciphertext into every repo `.db` and forces two clear-points on disconnect; (c) was deferred, not rejected — the columns remain, unused.
4. *Migration of existing installs* — (a) boot backfill plus a read-fallback; (b) lazy migration on next origin write; (c) hard: refuse to serve a repo whose credential cannot be migrated [CHOSEN].

**Rationale.** `store.NewCrypt` derives its AES-256-GCM key from the agent SSH private key via HKDF with a fixed info string and NO per-repo salt, so a token encrypted by any repo's crypt decrypts with the registry's. That makes the migration a MOVE, not a re-key, and makes control.db exactly as strong a home as the store was — the objection that it concentrates secrets is answered by the key living outside every database either way. The recoverable unit is therefore **control.db + the agent key**, never control.db alone. The hard migration is what lets auth resolution read ONE place: with a fallback, `OriginAuth` would need "try control.db, else the store" indefinitely, hiding migration failures behind working syncs.

**The choice.** control.db's `repos` row owns `origin_url`, `origin_branch`, `auth_method`, `auth_token`. The store's `remotes` row keeps url, branch, intervals and the `last_*` status columns, with its auth columns emptied by the migration and never read again — `remoteAuthFromRecord` is deleted. Writes funnel through `Manager.SetOrigin`/`ClearOrigin`, control.db FIRST on every path. `Manager.OriginAuth` is the only resolver.

**Non-scope.** This does NOT make control.db self-sufficient — without the agent key the ciphertext is unusable, so backup guidance must name both. It does NOT remove the store's auth columns (a later release may). It does NOT cover a credential embedded in `origin_url` itself, which is stored and served in plaintext. And "the store's auth columns are never read" has exactly one exception by design: `migrateCredential` reads them once, via `LegacyAuth`, to move them.
