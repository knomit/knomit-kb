# A subscription refuses writes at TWO layers on purpose — the branch classification answers the client, the store flag is the structural backstop, and sync merges are deliberately outside both

The two layers are not redundant — they answer different questions, and removing either degrades a distinct property.

1. **`WritableBranch` + `refuseUnwritableBranch` (web/MCP)** — the SEMANTIC layer. It produces a 403 with a reason the client can act on, and the detail deliberately DIFFERS for a subscription: telling a subscription's client to "use the repo's own agent branch" names a branch that does not exist, and which the DTO deliberately omits for that reason.
2. **`repoHandler.readOnly` (store)** — the STRUCTURAL layer. It sits at the shared write seam (`writeFileExact`, `deleteFile`, `batchWrite`), so facts, root files and batch writes all inherit it from one place and no forgotten call site can leak a write. It returns `ErrRepoReadOnly`, which is not an answer a REST client can act on — that is the first layer's job.

**The sync merges are deliberately OUTSIDE the store gate.** A subscription must keep following its upstream, so `reconcileMain` writes git refs on a read-only repo by design. The flag refuses AUTHORED commits, not all ref movement.

**Consequence for a consumer:** adding a new fact-write door needs no new gate (the seam covers it), but adding a new *client-facing* write route DOES need `refuseUnwritableBranch`, or the caller gets an opaque store error instead of a 403. And never "tighten" the store flag to cover merges — that breaks following, which is the whole feature.
