# Repo lifecycle REST design: delete=archive (recoverable, a control.db state flip)+purge, single NDJSON create endpoint, top-level /archived

Design choices resolved for remote repo management (so they aren't re-litigated):

- Repo creation is API/UI-ONLY. The `knomit init` CLI command (and app.InitRepo/InitRepoOnDiskBytes/ResolveAgentBranch) were REMOVED (commit c4d52a6). The only ways to create a repo are POST /api/v1/repos and the web Repo Manager. The `knomit reset` and `knomit verify` CLI commands remain. **UPDATE (repo-registry-in-control.db, 2026-08): there is no more auto-created default/trunk repo** — that concept (isDefault, initDefaultGit, Manager.Start opening a privileged repo first) was removed separately; see kb/invariants/repos/no-default-repo. A fresh home boots with zero repos registered.
- Delete = archive, not hard delete. DELETE /repos/{repo} moves the repo to an archived STATE (recoverable); permanent deletion is a separate explicit Purge (DELETE /archived/{id}). Restore (POST /archived/{id}/restore) brings it back. Chosen for recoverability matching the 'no shell access' goal. **UPDATE: 'moves the repo to an archive holding area' described a real file move at the time this was written; it no longer does.** Archive/Restore/Purge are now control.db `repos` table UPDATEs/DELETEs (state flip active↔archived, or row delete) — the repo's `.db` file at `<home>/repos/<uid>.db` never moves, is never renamed, and there is no `repos/archive/` directory or JSON manifest anymore. See kb/architecture/repos/lifecycle/9c43d8bd.md for the current mechanics.
- ONE create endpoint, mode-driven. POST /repos takes a single body with a mode param (preset|custom|clone) and per-mode fields — NOT separate endpoints per creation kind.
- Create streams progress as newline-delimited JSON (Content-Type application/x-ndjson), NOT SSE. Each line is {type: progress|done|error, ...}; the terminal line carries the created repo or the error. Pre-stream rejections (bad name 400, name-active/in-flight/origin-in-use 409) are sent as problem+json BEFORE the stream starts, because once 200+stream begins the status can't change.
- Archived repos live under a TOP-LEVEL /api/v1/archived collection (sibling of /repos), NOT nested under /repos/{repo}, because 'archived' is a valid repo name ([a-z0-9_-]+) and would collide with the {repo} param; archived items also aren't resolvable by RepoMiddleware (they're not active repos).
- Origin-uniqueness: two active repos may not share an origin URL; enforced on clone-create and on restore (409). The deeper identity-uniqueness guard (same root commit / knowledge base) is a separate, authoritative DB constraint — see kb/invariants/repos/one-local-copy-per-knowledge-base.

Note: the restore action uses a slash route /archived/{id}/restore rather than the AIP colon-verb style (POST /collection:verb) used by the now-deleted /repos:rescan; this was a conservative default and is a candidate to align to :restore for consistency.
