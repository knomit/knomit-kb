# Repo lifecycle REST design: delete=archive (recoverable, a control.db state flip)+purge, ONE mode-driven create endpoint answering 202+poll, top-level sibling collections

Design choices resolved for remote repo management (so they aren't re-litigated):

- Repo creation is API/UI-ONLY. The `knomit init` CLI command (and app.InitRepo/InitRepoOnDiskBytes/ResolveAgentBranch) were REMOVED (commit c4d52a6). The only ways to create a repo are POST /api/v1/repos and the web Repo Manager. **UPDATE (2026-08-10): `knomit reset` is gone as well.** This sentence previously read "The `knomit reset` and `knomit verify` CLI commands remain"; only the `verify` half still holds. There is no `cmd/reset.go`, and `knomit --help` at HEAD lists exactly: completion, help, migrate-registry, serve, verify, version, warm-models. Carry forward the DIRECTION rather than that list — the CLI has been losing repo-mutating commands one at a time, so check `knomit --help` before trusting any doc or script that names one (`migrate-registry` is itself a stop-gap slated for removal). **UPDATE (repo-registry-in-control.db, 2026-08): there is no more auto-created default/trunk repo** — that concept (isDefault, initDefaultGit, Manager.Start opening a privileged repo first) was removed separately; see kb/invariants/repos/no-default-repo. A fresh home boots with zero repos registered.
- Delete = archive, not hard delete. DELETE /repos/{repo} moves the repo to an archived STATE (recoverable); permanent deletion is a separate explicit Purge (DELETE /archived/{id}). Restore (POST /archived/{id}/restore) brings it back. Chosen for recoverability matching the 'no shell access' goal. **UPDATE: 'moves the repo to an archive holding area' described a real file move at the time this was written; it no longer does.** Archive/Restore/Purge are now control.db `repos` table UPDATEs/DELETEs (state flip active↔archived, or row delete) — the repo's `.db` file at `<home>/repos/<uid>.db` never moves, is never renamed, and there is no `repos/archive/` directory or JSON manifest anymore. See kb/architecture/repos/lifecycle/9c43d8bd.md for the current mechanics.
- ONE create endpoint, mode-driven. POST /repos takes a single body with a mode param (preset|custom|clone|initialize) and per-mode fields — NOT separate endpoints per creation kind.
- **UPDATE (#67 / PR #162, merged 2026-08-26): create is 202 + POLL. The NDJSON stream is GONE.** This bullet previously read "Create streams progress as newline-delimited JSON (Content-Type application/x-ndjson), NOT SSE. Each line is {type: progress|done|error, ...}". It no longer does. POST /repos answers **202 Accepted** with a `Location` header and the job's first status snapshot; progress and the terminal outcome are read by polling **GET /api/v1/repo-creates/{id}**, which stays readable for CreateJobTTL (1h) after the job ends.

  **Why, and it is not a style preference.** The stream was the MECHANISM by which the request OWNED the work: the handler passed `r.Context()` into `Manager.Create`, so a client that closed its tab cancelled the create at its next step boundary — discarding, in clone mode, a network fetch that may already have completed. 202 removes the ownership rather than patching it: there is no window in which the client holds the work, because it never holds it at all. The create runs on `context.WithTimeout(m.ctx, …)` — parented to the MANAGER — and is bounded, not fire-and-forget, so it always reaches a terminal state and a failed create rolls back its partial `.db` and registry row before becoming terminal. Disconnect-safety became structural instead of a fixed bug, and the outcome now outlives the connection that asked for it.

  What was traded away, honestly: a poll reports a LATEST VALUE, not every event, so a create finishing in milliseconds may be observed once. The web client compensates by rendering the mode's known step list with the reported `step` as a cursor — see CreateProgress.tsx, whose CREATE_STEPS mirrors lifecycle.go's emit() calls.

  Pre-flight rejections are UNCHANGED and still matter: bad name 400, name-active/in-flight/origin-in-use/wrong-remote-shape 409 are sent as problem+json BEFORE the 202, because once the job has started its failures are poll results, not HTTP statuses. `CreatePreflight` runs on the REQUEST's context, correctly — it is the only part of a create the caller genuinely owns.
- **Long-running sub-resources are TOP-LEVEL SIBLINGS of /repos, never nested under it — this is now a house rule with two instances.** Archived repos live under /api/v1/archived and create jobs under /api/v1/repo-creates/{id}, NOT under /repos/{repo}, because repo names are `[a-z0-9_-]+` so both `archived` and `creates` are LEGAL REPO NAMES that would collide with the {repo} param. chi resolves a static segment in preference to a param edge and does NOT backtrack, so nesting would not merely shadow one URL — it would make a repo actually called that unreachable at EVERY route beneath /repos/{repo}. Pinned by `TestReposNamedCreatesStaysReachable`. Archived items also aren't resolvable by RepoMiddleware (they're not active repos). Apply this rule to any future collection hung off /repos.
- Origin-uniqueness: two active repos may not share an origin URL; enforced on clone-create and on restore (409). The deeper identity-uniqueness guard (same root commit / knowledge base) is a separate, authoritative DB constraint — see kb/invariants/repos/one-local-copy-per-knowledge-base.

Note: the restore action uses a slash route /archived/{id}/restore rather than the AIP colon-verb style (POST /collection:verb) used by the now-deleted /repos:rescan; this was a conservative default and is a candidate to align to :restore for consistency.

Known, NOT fixed by #67 and deliberately out of its scope: a create still in flight when `Manager.Close` runs fails with "database is closed" and rolls back as far as it can; a leftover registry row then surfaces on the next boot as a MISSING repo offering to rehydrate. Pre-existing behaviour — 202 makes the window easier to hit (the request no longer blocks) but does not create it. Filed as a separate follow-up.
