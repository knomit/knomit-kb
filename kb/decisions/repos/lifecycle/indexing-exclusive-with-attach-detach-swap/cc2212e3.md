# Attach, Detach and Swap are REFUSED with ErrIndexing (HTTP 409 with a cancel-index link) while the index job runs, checked before any guard or network read; CancelIndex is the way through and records index error "indexing cancelled"

Decided in issue #411 (implementation of the decision in kb/decisions/repos/lifecycle/state-machine/9514e759). Each of the three events exits Sync (Attach/Detach restart it; Swap rewinds to Populate — a no-op Populate under mount mode none — so Open, Identify, Index, Serve and Sync all re-enter). A sync round takes lockBranch(upstream), which the index heal holds for a whole branch, and lockBranch is not ctx-aware — so accepting one of these while the index runs would make the single driver goroutine wait behind the heal (the PR #230 'activating sync' park, now for every event of the repo). Refusing is the only option that keeps 'the driver never waits on background work'.

WHERE THE CHECK IS. Twice, both before anything else: Machine.Send answers ErrIndexing from the status snapshot without queueing, and handleExternal re-checks m.indexRunning() before the guard runs — so a refused Attach never probes the network and a refused Swap never opens the temp DB. indexRunning = the Index life exists AND its job has not posted indexDone.

HTTP. writeLifecycleProblem (internal/web/handlers_index.go) maps ErrIndexing to 409 "Repo is indexing" with `_links.cancel-index` {href: /api/v1/repos/{repo}/index:cancel, method: POST}. PUT/DELETE origin and the origin-session commit return it; the commit also accepts `{"cancel_indexing": true}`, which sends CancelIndex first and streams a `cancelling-index` phase. The web UI offers 'Cancel indexing' from that refusal.

CANCELINDEX. Exits the Index stage (cancel, drain — it lands after the in-flight embedding batch) and sets the verdict to ErrIndexCancelled: index_state 'error', index_reason 'indexing cancelled'. The repo stays usable with a partial index (kb/decisions/repos/index/accepted-partial-index-degradation). A no-op when nothing is indexing. Rebuild and the next Mount re-index.

Misreadings: NOT 'wait for the index then proceed' — nothing in a request path waits for index readiness. NOT 'Rebuild is refused too' — Rebuild targets Index itself and replaces or absorbs (kb/decisions/repos/lifecycle/rebuild-replaces-or-absorbs).
