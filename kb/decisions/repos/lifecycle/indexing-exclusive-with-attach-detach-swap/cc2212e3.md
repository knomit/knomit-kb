# Attach, Detach and Swap are REFUSED with ErrIndexing (HTTP 409 with a cancel-index link) while the index job runs, checked before every guard and network read — except a STANDING refusal (today only a subscription's Detach → ErrSubscriptionOrigin), which answers first; CancelIndex is the way through and records index error "indexing cancelled"

Decided in issue #411 (implementation of the decision in kb/decisions/repos/lifecycle/state-machine/9514e759). Each of the three events exits Sync (Attach/Detach restart it; Swap rewinds to Populate — a no-op Populate under mount mode none — so Open, Identify, Index, Serve and Sync all re-enter). A sync round takes lockBranch(upstream), which the index heal holds for a whole branch, and lockBranch is not ctx-aware — so accepting one of these while the index runs would make the single driver goroutine wait behind the heal (the PR #230 'activating sync' park, now for every event of the repo). Refusing is the only option that keeps 'the driver never waits on background work'.

WHERE THE CHECK IS. Twice, both before any guard: Machine.Send answers ErrIndexing from the status snapshot without queueing, and handleExternal re-checks m.indexRunning() before the guard runs — so a refused Attach never probes the network and a refused Swap never opens the temp DB. At BOTH sites the order is: closed / unavailable / not-open (handleExternal also handles Unmount inside that prefix; Send skips every check for Unmount), then MachineEvent.standingRefusal, then the index gate, then guard. indexRunning = the Index life exists AND the job's verdict is still unset (the driver sets it when it handles the job's indexDone).

HTTP. httpx.WriteLifecycleProblem (internal/edge/web/httpx/lifecycle.go; it was writeLifecycleProblem in web/handlers_index.go before the 12e route move) maps ErrIndexing to 409 "Repo is indexing" with `_links.cancel-index` {href: /api/v1/repos/{repo}/index:cancel, method: POST}. PUT/DELETE origin and the origin-session commit return it; the commit also accepts `{"cancel_indexing": true}`, which sends CancelIndex first and streams a `cancelling-index` phase. The web UI offers 'Cancel indexing' from that refusal.

CANCELINDEX. Exits the Index stage (cancel, drain — it lands after the in-flight embedding batch) and sets the verdict to ErrIndexCancelled: index_state 'error', index_reason 'indexing cancelled'. The repo stays usable with a partial index (kb/decisions/repos/index/accepted-partial-index-degradation). A no-op when nothing is indexing. Rebuild and the next Mount re-index.

Misreadings: NOT 'wait for the index then proceed' — nothing in a request path waits for index readiness. NOT 'Rebuild is refused too' — Rebuild targets Index itself and replaces or absorbs (kb/decisions/repos/lifecycle/rebuild-replaces-or-absorbs).

FIELD LOCATION (14b, PR #631, merge 37dc65d5, re-read there): the "status snapshot" that Machine.Send checks is the machine's snapshot, which embeds the public events.Status; Send's cheap refusal reads st.IndexRunning, an exported field of events.Status (internal/corpus/repos/events/status.go) filled from m.indexRunning() in computeStatus. The second check, m.indexRunning() in handleExternal, is unchanged. Behaviour is the same; only the type's home moved.

STANDING REFUSALS COME FIRST (decided by the user 2026-10-28, branch fix/subscription-detach-before-indexing). Problem: detaching a SUBSCRIPTION's origin while it indexed answered ErrIndexing (409 + cancel-index link); the user cancelled indexing, retried, and only then got the real, permanent ErrSubscriptionOrigin ('a subscription requires its origin'). A transient refusal masked a permanent one and sent the user down a way through that led nowhere. Ruling: the permanent reason is answered first.

Design: MachineEvent.standingRefusal(f lifeFacts) (internal/corpus/repos/events.go) holds refusals no wait can lift. Send's fast path and handleExternal both call it immediately before the index gate; the subscription case was MOVED there out of guard (not copied), so the logic lives once. Admission rule for a standing refusal, all four required: cheap; local (no network, no store or temp-DB read); reads state FIXED for the RepoInstance's whole life (Send calls it off the driver goroutine, so mutable state would race); and permanent for that instance. r.subscribed qualifies — set in Manager.newInstance and never written again.

r.subscribed IS READ OFF THE DRIVER GOROUTINE: standingRefusal runs in Machine.Send on the caller's goroutine, concurrently with the driver. That is safe ONLY because r.subscribed is written once, in the RepoInstance literal in Manager.newInstance, before the driver starts (the only other writer is the test constructor NewTestInstanceWithDeps, whose instance has no machine). A change that mutates it after mount becomes a data race and gives wrong refusals. Anything added to standingRefusal must read only state fixed for the instance's whole life, never the store or the Ontology (e.g. IsFleet()). CODE-SIDE GUARDS (follow-up to the #672 review, branch chore/standing-refusal-fixed-state, refs pinned to its commit 35f1f3ed — re-pin to the merge commit): (1) standingRefusal takes lifeFacts (events.go), a small value type holding only instance-life-fixed facts (today just subscribed), built by RepoInstance.lifeFacts() at both call sites in machine.go; it receives no *RepoInstance, so driver-owned or store-derived state (indexVerdict, Ontology(), IsFleet()) is unreachable from it and a check that wants them fails to compile. A field joins lifeFacts only if it is immutable after construction. (2) The comment on RepoInstance.subscribed (instance.go) states it is fixed for the instance's whole life, read off the driver goroutine by standingRefusal, and must never be mutated. Neither guard stops a writer of r.subscribed from racing: lifeFacts() copies the field on each call, so the immutability rule on the field is still what keeps the read safe. This keeps the index gate's rationale intact: nothing that probes the network or opens a DB moves ahead of it.

Options considered: (a) duplicate the subscribed check inline at both sites — rejected, two copies of one rule; (b) run the whole guard before the index gate — rejected, it would probe the network / open the temp DB while indexing, the very thing this decision forbids; (c) a per-event predicate of cheap state-only refusals evaluated before the gate — CHOSEN. Not moved: guardSwap's r.IsFleet() refusal (ErrFleetOntologyReserved) is similar in spirit but a different event, and IsFleet reads the store-derived Ontology(), which is not instance-fixed; it stays in guard. ValidateLocalOrigin in guardAttach is config policy over the request's URL, not repo state; it stays too.

Misreadings: NOT 'every refusal now precedes ErrIndexing' — only standingRefusal's (today exactly one: subscription Detach). A NON-subscription Attach/Detach/Swap still gets ErrIndexing first; tests that assert a guard's own verdict (probe failure, swap identity) on such events must still waitIndexSettled first (kb/gotchas/corpus/repos/machine/tests/8dbd4ad0). NOT 'standing refusals precede ErrNotOpen' — the not-open / closed / unavailable gates still answer before it (kept narrow to the user's ruling). HTTP: handleHALDeleteOrigin maps ErrSubscriptionOrigin and lifecycle refusals in independent switch arms, and the web UI hides Disconnect for subscriptions (lockOrigin), so no layer above depended on the old order. Tests: TestWalkthrough_SubscriptionDetachDuringIndexing (both sites, via sendPastFastPath for handleExternal) and the 'ready, index running' subtest of TestMachine_TransitionTable (non-subscription Attach/Detach/Swap still ErrIndexing at both sites).
