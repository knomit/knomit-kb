# Boot archives a refused repo on its own ONLY for a symlinked ontology (option B): missing, other-unopenable and conflict stay unavailable for the user to archive; every archive records a reason (source user|system) in repo_archive_reasons

User ruling 2026-10-09 ("archive, but we need a reason why - user archived should get a reason stating so, system archived should have a reason why", then "let's do 1" = option B). Built in PR #450.

THE CHOICE. Manager.Start, after every mount replied (boot.Wait), runs autoArchiveRefused ONCE: every Unavailable whose typed Cause is CauseOntologySymlink is archived with ArchiveReason{Source: system, Reason: <the refusal text>, Condition: "unopenable"}. Nothing else is archived on its own, and nothing is ever archived at runtime.

WHY ONLY THAT CAUSE — the three tests a cause must pass: (1) a property of the repo's own content, (2) cannot heal in place, (3) independent of which repo opened first.
- symlinked ontology: passes all three. A refused repo does not sync, so no fix can reach it; archiving frees its name and knowledge base for a re-add.
- missing / other unopenable (corrupt file, newer schema, I/O): can heal by themselves (file put back, binary upgraded, restart); archiving would turn a self-healing state into a manual restore.
- conflict: which of two copies of one knowledge base to keep is the user's call, and the loser at boot is decided by mount state, not intent.
Options rejected: A (never auto-archive — the symlink repo stays a dead row until the user acts) and C (archive every unavailable repo — auto-archives transient causes and picks conflict losers).

SAFETY / REVERSIBILITY. Archive deletes nothing (state flip + reason row; the .db stays at RepoPath(uid)). Restore re-runs Identify and is refused with the same text (422); the repo stays archived with its reason intact, because Restore clears the reason row ONLY after mountExisting succeeded — and BEFORE m.Set, so a DELETE that archives the freshly restored repo again cannot have its new reason deleted by a late clear (review N1; not testable deterministically without a seam between m.Set and the clear). Data safety is pinned by tests: the unopenable and conflict archive tests assert the store file's bytes are identical after the user archive and just before the purge, and the boot test asserts the file survives the system archive and the refused restore (sabotage "user archive removes the store" goes red at a996589b). A lens member is never auto-archived (archive refuses it with ErrRepoInUseByLens) — it stays unavailable with a WARN.

THE REASON RECORD. Table repo_archive_reasons (control migration 000014; a TABLE, not columns, because the control chain admits only CREATE ... IF NOT EXISTS): uid PK REFERENCES repos ON DELETE CASCADE, source (user|system), reason (system's why), note (user's free text, <=500 bytes), condition (state at archive time; "<reason>: <detail>" for one archived while unavailable). Written by Registry.Archive in ONE transaction with the state flip; an unknown source is refused. Purge removes it by cascade. An archived row with NO reason row is a pre-#450 archive: API reason null, UI "No reason recorded" — there was nothing to backfill.

WHO WRITES WHICH SOURCE: user = DELETE /repos/{repo} (optional {"note"}); Manager.Archive(name) is a user archive with no note (tests and storyboard use it). system = autoArchiveRefused, DeleteRepo(name, reason) for a cancelled create, and the two fleet removals — those purge right after, so their reason is seen only when the purge fails.

ON THE WIRE. GET /archived and GET /archived/{id} (added: it is every item's self link, which had no route) carry reason {source, reason, note, condition, summary}; summary is composed server-side (archiveSummary). A 404 for a name whose newest archived row has a reason appends that summary to the detail (RepoMiddleware), so an agent bound to an auto-archived repo learns why. The reason is NOT on GET /repos rows — archived repos are not in that collection.

FLEET: the fleet guard cannot see an UNAVAILABLE fleet repo (fleetRepo finds the fleet by a mounted repo's ontology), so archiving one is not refused and the fleet state is left as it was; accepted and documented on ArchiveWith. KNOWN DEAD END (not made worse by #450): a fleet row in state "unregistering" whose fleet repository is unavailable. Archiving that repository does not call fleetRemoved (wasFleet is false), so the row stays "unregistering" and RegisterFleet keeps refusing with "...it must finish (or the fleet repository be archived)" — a remedy that no longer clears it. Clearing it needs a way to recognise the fleet repository without mounting it.

NOT what this says: that boot archives every refused repo, or that a system archive is permanent (restore and purge both work on it).

FOLLOW-UPS filed after review (open at the merge, eb5a5554): #452 — the archived-name 404 scans the whole archive (LatestArchivedNamed → ListArchived, an origin query, a reason query and a stat per archived row on every 404 miss); #453 — openapi's note maxLength counts characters while the server counts bytes after trimming, and a body over 4096 bytes fails in decodeOptionalJSON instead of the documented 400; #454 — deleteRepo inherits archive's by-name fallback to an unavailable repo (unreachable today: active names are unique and m.unavailable is filled only at boot), and archive defaults an EMPTY source to user, so a future internal caller that forgets the source is recorded as a user archive.
