# /git was deliberately left unauthenticated in PR #205 pending ONE server-wide auth design, and it now inherits that design: phase 1 gates receive-pack by `write` and refuses unauthenticated clones under [auth].require, phase 2 serves /git to enrolled instances over mTLS, phase 2b lets a knomit subscriber fetch over it — but the PLAINTEXT port still serves fetches to anyone who can reach it unless require is on

Decided 2026-09-15 with the user (PR #205). Options: (A) no auth now, the network (tailnet, VPN, reverse proxy) gates access as it does for the API; (B) a static bearer token on /git only, via a git.token config value; (C) defer to a server-wide auth design. Chosen: A phrased as C — keep /git open, consistent with the rest of the server, and treat authentication as ONE design for the whole HTTP server later rather than a one-off on /git that the API would not follow.

THAT DESIGN HAS SINCE LANDED, and /git inherited it without a /git-specific mechanism (F19):
- Phase 1 (PR #243): `AuthMiddleware` sits on the OUTER router above the `/git` mount, so every /git request gets a principal; `writeGate` wraps the mount, so `git-receive-pack` needs `write` while `git-upload-pack` (clone/fetch) is exempt from the method gate. With `[auth].require = true`, both halves of a fetch answer 403 without a principal.
- Phase 2 (PR #252): the optional mTLS listener (`[tls].addr`) serves the SAME handler, /git included, to enrolled instances only — never anonymous, reads included. An instance holds `read` implicitly and needs a grants row for anything else.
- Phase 2b (F19 phase 2b PR): the CLIENT side caught up. A knomit subscriber names another instance as origin with `knomit+https://<host>:<tls port>/git/<repo>` and auth method `cert`, and go-git fetches over the phase 2 mutual-TLS client (kb/decisions/repos/remote/knomit-https-scheme). Fetches between two ENROLLED instances are therefore authenticated in both directions: the fetcher verifies the server against the fleet root and CRL, and the server's listener verifies the fetcher.

CONSEQUENCES NOW, stated in full: on the PLAINTEXT port with `require = false` (the default), anyone who can reach the port can still fetch every served repo and every advertised branch — reads are not enforced anywhere there, only the transport boundary is. So the original advice stands for the plaintext port: put it behind the network boundary. A subscriber that still uses an `http://` origin with auth method none against the plaintext port is still UNAUTHENTICATED; only a `knomit+https` origin is authenticated. The mTLS port is the one that needs no network boundary for authentication. Revocation on the mTLS port is checked at the handshake, so a revoked peer's kept-alive connection lasts until the server's idle timeout (60s in knomit serve and the desktop).

Misreading: this is NOT 'auth on /git was forgotten', and it is no longer 'no auth mechanism exists to reuse'. It is also NOT 'fetches are now authenticated' in general — only knomit+https fetches between enrolled instances are; on the plaintext port without require, they are not. Push to a knomit origin is still not served (receive-pack over /git is F11).
