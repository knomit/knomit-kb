# F24 plan rulings (user, 2026-10-07): listing description = template fact title plus its path; folder-without-fact creatable but unlisted, fact-without-folder neither, two facts refused; copy exactly README.md + .knomit/**; initialize + template follows today's initialize rules, no new collision rule (the ruling 'fleet template only via initialize' is SUPERSEDED: since PR #520 a fleet-id template is refused in every mode)

Context: the F24 worker's plan (create a repo from a template, PR #433) put open points to the user; the coordinating session condensed them into a numbered list and a fifth question raised by the reviewer (M1: initialize + template overwriting same-path files on the remote's branch).

OPTIONS CONSIDERED
1. Listing description: the fact's title vs its first body paragraph ("Template folder: ..."); optionally also return the fact's path.
2. Folder/fact mismatch: require the fact to create (one rule) vs folder-only creatable but unlisted; and what to do with two template facts for one name (skip/log vs first-wins vs refuse).
3. What is copied: the spec's ".knomit/** only" vs the plan's "root-level files + .knomit/**" vs reviewer M2's narrowest set, root README.md + .knomit/**, everything else refused by name.
4. Fleet: allow a fleet-id template as a local repo (like the preset does today) vs refuse it locally and allow it only with initialize (a local fleet-id repo becomes this instance's fleet and `fleet register` then answers already_registered).
5. initialize + template: a new collision rule (refuse when a template path exists with a different blob, ErrTemplateConflict) vs skip README.md vs today's initialize rules unchanged.

THE USER'S RULINGS (verbatim, from the F24 brief, section "User rulings on the plan (2026-10-07, verbatim)")
- "1. yes 2. yes 3. yes 4. yes" on the master's list:
  1. listing description = the template fact's title; the listing also returns the fact's path (`fact`).
  2. folder without a fact: not listed, creatable by name; fact without a folder: not listed, not creatable; two template facts for one name: refused with a named error.
  3. copy exactly the template's root `README.md` + `.knomit/**`; anything else in the template folder refused by name (reviewer M2).
  4. fleet-id template refused in local `template` mode and when a fleet repo is already mounted; allowed with `initialize`. The preset's local fleet behaviour is NOT changed here.
- 5 (initialize collisions): "why would this be any different than any other repo type - like one for general knowledge ? The same rules should apply as currently" -> NO new collision rule. initialize + template behaves as initialize + preset does today (lifecycle.go initInitialize): a remote whose branch already has an ontology is refused (ErrRemoteAlreadyInitialized); otherwise the template files are written onto the agent branch only, as one commit (signed, trailers), replacing same-path files there (e.g. the remote's README.md), visible in the agent-branch merge; nothing is written to the remote's consensus branch.

RATIONALE
- 1: the playbooks template-fact titles are written to say what the template is for; the path lets an agent knomit_explain the template directly.
- 2: the template IS its files, the fact describes it; a fact pointing at nothing must not be offered; which of two facts is right is not knomit's call.
- 3: the new write door goes around path lowercasing, so it takes the narrowest set that works (root LICENSE, .gitmodules or a readme.md case-duplicate are files knomit never writes); the playbooks templates hold only these.
- 4: initialize on the fleet's git URL sets the origin that a later `fleet register` of the same URL matches.
- 5 (user): a template is just another ontology source; the existing initialize rules already govern what lands where, and the agent-branch merge is where a person sees the replacement.

THE CHOICE (as built, merged 97e735ee): kb/architecture/repos/create/from-template, kb/invariants/repos/create/template-refusals, kb/architecture/repos/templates/listing.

NON-SCOPE: ruling 4 does not change mode `preset` with `fleet` locally; ruling 5 does not authorize a template-specific overwrite check later without a new decision; ruling 3 does not widen WriteSystemTree for any other caller.
