# Seeding an empty remote gets its OWN create mode ("seed") that hard-fails on a non-empty remote — and unlike clone it PUSHES, because initFromEmptyRemote only writes locally

# Context

The best onboarding workflow is: create an EMPTY repo on a git host, then point knomit at it. Local and remote then share a root commit from birth and are never disjoint. Creating locally and attaching a remote later leaves histories with no commits in common; connecting them runs `store.Replay`, which carries every fact across (deduped by path, latest version only) but NOT each fact's earlier revisions.

That workflow was the one case the backend forbade: `initClone` hardcoded `fact.DefaultOntology()` as the empty-remote seed, and `rejectOntologySpecForClone` refused `ontology_preset`/`ontology_yaml` in clone mode outright.

# The choice

`CreateSpec.Mode` gains `"seed"`. It requires BOTH `Origin.URL` and an ontology, runs `initClone`'s path with the CHOSEN ontology as `initFiles`, and **fails with `ErrRemoteNotEmpty` if the remote turns out to have refs**.

Rejected alternatives: relaxing `rejectOntologySpecForClone` to honour an ontology "when the remote is empty", and a `SeedOntologyIfEmpty` boolean. Both reintroduce the silent-drop the rule exists to prevent — the request would be obeyed only sometimes, and the caller could not tell which. Mode `seed` never half-obeys: the ontology is used, or the request is refused. `clone` mode is untouched.

# The non-obvious half: seed MUST push, clone does not

`Service.initFromEmptyRemote` writes the root commit, the consensus branch and the agent branch **LOCALLY ONLY — it never pushes**. Left there, the remote stays ref-less, so `ActivateSync`'s first reconcile calls `fetchOrigin`, gets `transport.ErrEmptyRemoteRepository`, and `repoBuilder`'s startSync returns that error BEFORE `go runReconcileLoop(...)` — meaning **no background sync loop starts for the rest of the process lifetime**, with `Create` logging only a warning. Only a daemon restart starts one, and `Push` force-pushes the agent ref alone, so the consensus branch never reaches the remote at all.

For clone that is a corner case. For seed it would be EVERY invocation, silently defeating the mode's entire premise ("your knowledge is backed up from the first commit"). So `initSeed` explicitly pushes BOTH the consensus branch and the agent branch after `InitFromRemote` succeeds, before returning. This is the one place a push of the consensus branch is legitimate; steady-state sync still never pushes main.

A partial seed — consensus push succeeds, agent push fails — leaves the remote holding `main` while the local repo is rolled back, so every later seed of that URL hits `ErrRemoteNotEmpty`. The error names that state and the recovery.

# Five mode sites, not two

`internal/repos/lifecycle.go` gates on mode in FIVE places: preflight, origin reservation, the dispatch switch, origin persistence into control.db, and ActivateSync. A `CreateSpec.hasRemote()` predicate covers all of them. Missing the persistence site produces a repo whose remote was initialised but which has NO origin record — the failure surfaces much later as "my facts never push".

# What this does NOT mean

It does not change `clone` mode. It does not authorise trusting a client-supplied `empty` flag — `Create` re-asserts emptiness itself, because a remote can gain refs between probe and create; the preflight probe is a fail-fast affordance only, which is why seed deliberately probes twice. And `clone` OF AN EMPTY REMOTE still has the original no-push/no-sync-loop defect; only `seed` was fixed.

See also the four-state probe rule, which is what routes a request to this mode in the first place.
