# Seeding an empty remote with a chosen ontology gets its OWN create mode ("seed") that hard-fails on a non-empty remote — rejectOntologySpecForClone stays untouched for "clone"

# Context

The best-outcome onboarding workflow is: create an EMPTY repo on a git host, then point knomit at it so it is initialised in place. Local and remote then share a root commit from birth, so they are never disjoint histories. Creating locally and attaching a remote later leaves two histories with no commits in common; connecting them runs `store.Replay`, which carries every fact across (deduped by path, latest version only) but NOT each fact's earlier revisions.

That ideal workflow was the one case the backend forbade. `initClone` hardcodes `fact.DefaultOntology()` as the empty-remote seed, and `rejectOntologySpecForClone` refuses `ontology_preset`/`ontology_yaml` in clone mode entirely.

# Options considered

1. **Relax `rejectOntologySpecForClone`** to accept an ontology in `clone` mode and use it only when the remote turns out empty. REJECTED — this is precisely the half-obeyed request the rule exists to prevent: honoured for an empty origin, silently dropped otherwise.
2. **Add a boolean to CreateSpec** (`SeedOntologyIfEmpty`). REJECTED — same silent-drop failure mode wearing a different name; the caller still cannot tell which branch ran.
3. **A new mode `"seed"`** — CHOSEN.

# The choice

`CreateSpec.Mode` gains `"seed"` alongside `preset` / `custom` / `clone`:

- Requires BOTH `Origin.URL` and an ontology (`OntologyPreset` or `OntologyYAML`).
- Runs `initClone`'s path but passes the CHOSEN ontology as `initFiles` rather than the hardcoded default.
- If the remote turns out to have refs, fails with a new `ErrRemoteNotEmpty` directing the caller to `clone`.

# Rationale

Mode `seed` never half-obeys: the ontology is either used, or the request is refused outright. That preserves the exact property `rejectOntologySpecForClone` was written to protect, while making the good workflow expressible. `clone` mode keeps `rejectOntologySpecForClone` unchanged, so the blast radius of this change is zero for existing callers.

The UI probes the remote before asking for an ontology, so the ambiguity never reaches the user either — but the probe is a UX affordance, NOT the authority. A remote can gain refs between probe and create, so the emptiness check MUST be re-asserted inside `Create`.

# Non-scope

This does NOT make ontologies editable after creation — see the sibling decision. It does NOT change `clone` mode's behaviour in any way. And it does NOT authorise trusting a client-supplied `empty` flag: the server re-checks.
