# Decided (2026-11-03, #395): Manager.Create's double store.Open of the new DB is NOT fixed: a ~300 ms per-create slowdown on Windows is acceptable; closed won't fix

**Options considered:**
- (a) Hand-over: populate keeps its open *store.Service and, only after it succeeds, hands it to the Open stage, so openStage.Enter adopts it instead of calling store.Open. Prototyped on Windows 10: preset create went from 619-712 ms to 343-387 ms in production durability (about 45% less), and from about 435 to 300 ms under the test durability switch.
- (b) Seed the DB inside Open.Enter for a fresh DB.
- (c) Make the close or reopen cheaper (skip the checkpoint or fsync).
- (d) Create the session sidecar lazily.
- Do nothing.

**Choice: do nothing.** Issue #395 is closed as won't fix.

**Rationale:**
- It is a slowdown, not a bug. Every create mode (preset/custom, template, clone, initialize, subscribe) does 2 store.Open and 1 Close of the new DB: the mode's init function (lifecycle.go initLocal/initTemplate/initClone/initInitialize/initSubscribe, each store.Open plus defer svc.Close) and then openStage.Enter (stages.go, store.Open(r.dbPath)).
- The cost is paid only when a repo is CREATED: about 600 ms instead of about 300 ms per preset create on Windows. It is not paid when an existing repo opens, at boot, or on reads and writes.
- The user judged 600 ms per create acceptable.
- Option (a) touches the repo lifecycle Machine's ownership rules and the 'Open.Enter is the ONE wiring function' invariant (kb/invariants/store/lifecycle/reopen-rewire/a3f07a9a.md) for a saving nobody needs. That risk outweighs the benefit.
- Test-suite cost (about 135 ms per create under the test durability switch of ffef3411, hundreds of creates per run) was weighed and judged not significant. It does not cause timeouts; the #725 timeout had a different cause.

**Non-scope (what this does NOT mean):**
- It does NOT forbid fixing the double open later. If create latency becomes a real user or CI problem, the measured design for (a) and its ownership analysis are on issue #395 and can be picked up as they are.
- It says nothing about option (d), the lazy session sidecar (about 110 ms on EVERY store.Open, including boot and swaps). That was not decided here.
- It does not cover Create's cleanup ignoring os.Remove errors, which would silently leave .db/-wal/-shm/sessions files behind on Windows if a handle ever leaked. That was noted on #395 but not acted on; no leak exists today.
- It is not the #365 test-durability decision (ffef3411), which covers how tests make SQLite cheap and is unaffected.
