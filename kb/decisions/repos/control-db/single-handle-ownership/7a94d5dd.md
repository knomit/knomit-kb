# control.db is opened ONCE, with Registry keeping ownership and LensRegistry/Origins borrowing the handle

**Options considered.** (a) One handle: `Manager.Start` opens control.db once and all three tenants share it. (b) Keep the two existing handles and run the migrator on the Registry handle only.

**Rationale.** Under (b) two `SetMaxOpenConns(1)` pools contend on one file, and LensRegistry acquires a silent dependency on Registry having migrated first — invisible at the call site. (a) also matches what Origins already does: it shares Registry's handle so its foreign key into `repos(uid)` is enforced on the same connection. With one migrator over the file, "who migrates" stops being ambiguous.

**The choice.** `Registry` KEEPS ownership of the handle. Only `LensRegistry` moves off its own handle: `NewLensRegistry(db)` is a non-owning wrapper whose `Close()` is a no-op, and `Manager.Start` gives it `repoReg.DB()`. `Origins` continues to borrow the same handle.

No `NewRegistry(db)` constructor is added. `OpenRegistryNoSchema`, `Registry.SchemaExisted()`, `OpenRegistry`, `OpenLensRegistry` and `OpenOrigins` all keep their signatures. `OpenLensRegistry(path)` is retained as an OWNING wrapper that runs the same bring-up as every other opener (`controlUp`: conditional `upgradeLensSchema`, then `migrate.Control`). As of merge 1cc5413c, `Registry.SchemaExisted()` has no caller at all, production or test — its only reader was the legacy-home boot check that merge removed; it was kept deliberately rather than deleted in that PR.

**Correction to an earlier reading of this decision.** There was never a double close to fix. `Manager.Close` calls `Close()` on both `m.registry` and `m.reg`, but before this change those were two DIFFERENT handles, so closing both was correct. After the change it stays correct for a different reason: the lens wrapper is non-owning and its `Close()` does nothing. The no-op `Close` is what PRESERVES the existing shape of `Manager.Close`, not a repair of a latent bug.

**Non-scope.** Retaining the path-taking constructors is a test-ergonomics concession, not a sanctioned second way to open control.db in production. Nothing outside tests should call them once `Manager.Start` holds the shared handle.

**Allowed exception (PR #515): a short-lived read-only open.** "Opened ONCE" and "nothing outside tests should call the path-taking constructors" govern the server's read-write handle. A separate CLI-owned handle opened with SQLite `mode=ro` for a single read (repos.StoredAgentID, behind `knomit identity show`) is not a second owner: it does not take part in handle sharing, never migrates, and coexists with the server's live WAL handle (it returns the committed value, does not block on an open write transaction, and creates no files while the server runs). It is allowed only while read-only, short-lived and closed by its caller. It does NOT license a second READ-WRITE handle, and it does not mean the path-taking constructors (OpenRegistry etc.) are fine for display commands. See kb/architecture/identity/stored-agent-id and kb/gotchas/store/sqlite/readonly-wal-sidecars (quiescent-home sidecar caveat).
