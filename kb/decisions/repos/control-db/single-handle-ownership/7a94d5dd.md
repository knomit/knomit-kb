# control.db is opened ONCE and shared by all three tenants; OpenRegistry/OpenLensRegistry survive as owning wrappers for tests only

**Options considered.** (a) One handle: `Manager.Start` opens control.db once and passes the `*sql.DB` to Registry, Origins and LensRegistry. (b) Keep the two existing handles and run the migrator on the Registry handle only.

**Rationale.** Under (b) two `SetMaxOpenConns(1)` pools contend on one file, and LensRegistry acquires a silent dependency on Registry having migrated first — invisible at the call site. (a) also matches what Origins already does: it shares Registry's handle so its foreign key into `repos(uid)` is enforced on the same connection. With one migrator over the file, "who migrates" stops being ambiguous.

**The choice.** `Manager` owns the handle. `NewRegistry(db)` / `NewLensRegistry(db)` are non-owning constructors that run no DDL and whose `Close()` is a no-op. This also fixes a latent double-close: `Manager.Close` currently closes both `m.registry` and `m.reg`, which would be the same handle once shared.

`OpenRegistry(path)` and `OpenLensRegistry(path)` are RETAINED, because ~37 test call sites use them. They open their own handle, mark themselves owning, and reproduce the boot sequence minus the guard — `OpenLensRegistry` still calls `upgradeLensSchema` before `migrate.Control`. `OpenRegistryNoSchema` also stays: it is the guard's entry point.

**Non-scope.** Retaining the path-taking constructors is a test-ergonomics concession, not a sanctioned second way to open control.db in production. Nothing outside tests should call them once `Manager.Start` holds the shared handle.
