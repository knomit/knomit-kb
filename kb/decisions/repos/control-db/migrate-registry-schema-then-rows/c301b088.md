# migrate-registry splits into migrator-then-rows: DATA stays atomic, tables no longer do — and that is the accepted trade

`applyControlDB` built all three tenants plus every row in ONE transaction, so an abort left no half-built registry. golang-migrate opens its own transactions and cannot nest inside a caller's, so something had to give.

**Options considered.** (a) Migrator first, then rows in one tx. (b) Keep the tx untouched using the exported `*SchemaSQL` constants, then run the migrator after it commits purely to stamp `schema_migrations`. (c) Keep the constants but generate them from the embedded .sql at init.

**Rationale.** (b) preserves abort semantics exactly but leaves the DDL in two places — constants and .sql files — which is precisely the drift the exported constants were created to prevent. (c) avoids drift but forces the baseline to be sliced per-tenant across separate files just to keep three constants distinct, shaping the migration layout around a one-shot tool. (a) keeps one source of truth and the simplest layout.

**The choice.** (1) drop legacy `lens_reads`/`lenses` outside the tx, (2) `migrate.Control(db)`, (3) one tx for all row inserts plus `DROP TABLE repo_settings`. `RegistrySchemaSQL`, `OriginsSchemaSQL` and `LensSchemaSQL` are deleted.

**What changed and why it is acceptable.** A failed run now leaves empty-but-correct tables rather than no tables. That state is indistinguishable from a fresh home, `control.db.bak` still provides full rollback, and the existing abort tests assert on rows and on the backup file — not on table absence.

**Non-scope.** This weakens the SCHEMA half of the atomicity guarantee only. The row-insert half stays in a single transaction and must not be split further; a partially-populated registry is a different and much worse failure than an empty one.
