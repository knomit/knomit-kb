# Breaker schedule (decision 7, "ok, approved"): open at the 3rd consecutive failure for 2× the loop interval, double per failed probe, cap 30 min as a code constant, separate fetch and push breakers

User, verbatim (2026-10-01), after the schedule was explained (normal pace for failures 1–2, open at the 3rd with 2× the interval, doubling per failed probe, cap 30 min, separate fetch/push breakers): "ok, approved".

AS BUILT (PR #363, merge 252efbe1, internal/repos/breaker.go + sync.go):
- breakerTripAfter = 3; the open period is breakerOpenFor(base, opens), base = the loop interval (min(interval, push_interval), 300 s default). Waits are 10, 20, 30 min at 300 s; 6, 12, 24 s … at a 3 s base. breakerOpenFor saturates (doubles only while below the cap, never shifts), so it cannot overflow.
- breakerMaxOpen = 30 min, a code constant.
- Two breakers per origin loop: fetch (auth resolution + Sync) and push (Push). An auth-resolution failure counts against the fetch breaker when the fetch is due; while the fetch breaker is open it counts against nothing (no broadcast, no push charge; review F1) — it is never a push failure.
- Every round consults them, the woken ones included. A skipped step makes no request, writes no status row and broadcasts nothing. One success closes a breaker; the probe's success is the existing recovery edge.

OPTIONS REJECTED
- A toml key for the cap: the user said "a predefined max time", and instance config stays limited to what belongs to the instance.
- One shared breaker for the round: a refused push (read-only token, branch protection) would also stop pulls, and a failing fetch would stop pushes of this instance's own branch, which is still a correct force-push.
- rev 2's doubling wait alone: woken rounds bypassed it.

NON-SCOPE: the cap is not per-repo or tunable; the breaker state is in memory (a loop or server restart starts closed, which is deliberate: a changed origin or credential gets an immediate attempt).
