# Per-repo sync mode: a root ontology option `sync: {push, pull}` where realtime push is the do: push mechanism for every commit and realtime pull is a full sync round every [git].realtime_pull_interval (3 s default, toml) (user request, 2026-10-01)

**The user's request, verbatim (2026-10-01):** "hmm... I actually want an ontology option which will describe how pushes and pulls should be handled. So, when we're in real time mode for push, use the "do: push" mechanism (commit triggers 1s window triggers push) but for all commits. When we are in real time for pull, actively do a git sync every whatever configured real time pull interval is - let's say 3s by default, configurable in the knomit toml file."

**Options considered (design rev 3):**
- Key shape: an object `sync: {push, pull}` (chosen), two flat keys `sync_push`/`sync_pull` (two registry entries for one concern), or one scalar `sync: realtime` (loses "push fast, no pull").
- Where push realtime lives: PR 4's existing commit wake (`ri.wakeSync`, 1 s countdown) for every agent-branch commit, gated by a cached atomic the loop publishes, because onCommit runs under the writer's branch lock and must never read the store.
- Sync-made merge commits under push: realtime: wake on them too and accept one bounded idle round per consensus advance (chosen), or suppress them with a "tick in progress" flag that could also swallow a real write landing mid-round (rejected).
- Pull: a toml key, per instance, as the user asked; the per-repo `remotes.interval` column still has no writer.

**The choice:** root attribute `sync: {push: realtime|interval, pull: realtime|interval}`, absent = today, read by the sync loop at the consensus branch's tip; `[git].realtime_pull_interval` default 3 s, below 1 s a boot error. Built in PR #382 (merged d5d91dfc).

**Non-scope:** it does not change what a round writes, only when rounds run; it pushes nothing but this instance's own agent branch; it adds no writer for the 300 s interval of repos without `sync`.
