# Every push and pull, today's interval mode included, passes through a circuit breaker, and a push no longer blocks writes: it pushes a snapshot of the branch tip (user ruling, 2026-10-01)

User ruling, verbatim (2026-10-01): "push and pull mechanisms - including the current ones, not realtime - should pass through a circuit breaker, I do not want to continuously lock the repo for consistent, repeated failures. The circuit breaker can have an exponential backoff with a predefined max time. Also, are you saying that during a push we're completly blocking for writes ? Why, can't we do bookmark based push, like when a push triggers, fetch the current commit, then push up until that commit ? Since history is read only there should not be any conflicts."

OPTIONS CONSIDERED
- Retry handling: (a, chosen) a circuit breaker consulted by every round; (rejected) rev 2's doubling wait alone, which only lengthened the timer arm, so a wake-started round (do: push, knomit.push(), a commit under realtime) bypassed it (review M2), and it coupled fetch and push (M3).
- Push locking: (a, chosen) a snapshot push — the write lock only for the tip read, a per-branch push mutex for the push, and the tip pushed by hash; (rejected) keep holding the agent-branch write lock across the network push. With that, a breaker would bound only how OFTEN writes are blocked, and every push would still block them for up to network_timeout.

RATIONALE
The user asked for both outright. The lock had held across the network only so that the ref read and the ref pushed were the same, and to serialize this instance's pushes; a hash refspec gives the first, and pushMu gives the second, without blocking writes. The rebase-fallback rewrite (history is NOT always read-only) is safe because the loop's Sync runs before its Push on the same goroutine, and a cross-caller push's older snapshot is force-overwritten by the loop's next push.

CHOICE (as built, PR #363, merge 252efbe1)
- See kb/architecture/repos/sync/circuit-breaker and kb/architecture/store/remote-sync/snapshot-push.

NON-SCOPE
- This is not the `sync` ontology key (realtime push/pull): that is PR S2.
- The breaker gates the origin loop's rounds only. One-shot calls (startup recovery, ActivateSync's Sync, the create-time and fleet pushes) neither consult nor change it.
- pushMu does not stop a timed-out push being applied late on the server; that guard is the host's compare-and-set.
