# The ontology moved to .knomit/ontology.yaml (private namespace); .domains/ is now the legacy read fallback, and the preset refresh writes back to whichever path it read from

`ontology.yaml` is configuration, not knowledge, so it belongs in a private directory under the dot-path rule (see the sibling `private-dot-paths` decision).

**Options considered**, for what an unmigrated repo should do (there is no migration — repos are updated by hand): (a) detect the legacy path and log at ERROR while still defaulting; (b) refuse to open the repo entirely; (c) read the legacy path silently as a fallback; (d) leave today's warn-and-default behaviour untouched.

**Rationale.** (c) was chosen. The behaviour on a missing ontology at the time was `warn + DefaultOntology()`, which meant a missed repo would silently start validating new facts against the WRONG taxonomy — the failure this decision exists to prevent, and only reading the legacy path actually prevents it. (b) was rejected because it also breaks any third-party KB repo that legitimately ships without an ontology. (a) and (d) both leave the wrong-taxonomy window open. (Since then the open path no longer substitutes the default at all: a repo with no usable ontology opens readable but unwritable.)

**Layout today.** knomit's private data lives under `fact.PrivateRoot` (`.knomit/`). THREE ontology rungs are read, newest first, by `fact.OntologyPathsNewestFirst()` in `internal/domain/fact/private.go`: canonical `.knomit/ontology.yaml` (`fact.OntologyFile`), `.domains/ontology.yaml` (`fact.LegacyOntologyFile`, the previous canonical path) and the pre-dot `domains/ontology.yaml` (`fact.PreDotOntologyFile`, the original location; it was dropped once and later restored, because an unmigrated repo is likeliest to hold it). None is written by a migration; both seed sites in `lifecycle.go` write the canonical path. The constants live once in `fact` because `internal/corpus/repos` and `internal/domain/okf/source` both need them and neither imports the other; `repos.OntologyPath` / `LegacyOntologyPath` / `PreDotOntologyPath` (manifest.go) are defined in terms of them.

**How the open path reads it.** `RepoInstance.loadOntology` (`internal/repos/stages.go`, the identify stage; it used to live in builder.go, which no longer exists) reads through `store.Service.OntologyFileAt`, which returns the FIRST rung PRESENT and its path, the same rule as every other ontology reader (OntologyAtCommit, the range verifier in engine/store/verify, the probe, okf). Since #439 (merge a8ef3d02): an EMPTY first rung is the error "ontology at <path> on <branch> is empty" rather than falling through to a later rung, and a SYMLINK at the first rung present is fact.ErrSymlinkNotFollowed naming it (kb/invariants/repos/ontology/symlinks/1ac1e8f3.md). A later rung never stands in for the first one present. The two errors are treated differently since #444 (merge ec3406df): an EMPTY (or missing, or unparseable) ontology leaves the repo MOUNTED, readable but unwritable, with the error as its OntologyError; a SYMLINK refuses the repo outright (identifyStage.Enter returns it; the repo is listed "unopenable" and not mounted).

**Where a reader sees it.** For a mounted repo with no usable ontology, GET /api/v1/repos rows and GET /api/v1/repos/{repo} carry `ontology_error` (the error text: "no ontology at <rungs> on <branch>", "ontology at <path> on <branch> is empty", "ontology at <path> does not parse: ..."), via RepoInstance.IdentifiedOntologyError, which drops the not-yet-identified placeholder so a repo being created never shows one; the field is omitted when the repo has an ontology. The web UI shows a "read-only" chip with the message as tooltip on the Overview table and the top-bar switcher, a compact lock chip (same tooltip; #443's rule that a rail row's name yields last) on the Manage rail, and a banner on the repo page's branch block. A symlinked ontology never appears in ontology_error: its repo's row is state "unopenable" with the message as `detail`.

**The non-obvious consequence.** `loadOntology` must REMEMBER which path it read (`srcPath`), because the boot-time preset refresh rewrites the ontology file when an embedded preset has moved ahead of the stored copy. If that write always targeted the canonical path, a legacy repo would grow a SECOND ontology file while the stale one stayed behind — two files, one in force, no indication which. Writing back to the path that was read keeps a legacy repo internally consistent until it is migrated by hand. This is the regression most worth a test.

**Non-scope.** The fallback is READ-only and is not an invitation to keep the old layout indefinitely; it exists so a hand-migration miss degrades safely rather than silently. It also does not make 'always add a fallback' the rule — the sibling README decision deliberately takes a clean break, because the cost of a miss there is only a blank description.
