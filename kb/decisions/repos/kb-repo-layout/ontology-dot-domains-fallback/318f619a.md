# The ontology moved to .domains/ontology.yaml and DOES keep a legacy read fallback — and the preset refresh writes back to whichever path it read from

`domains/ontology.yaml` is configuration, not knowledge, so it belongs in a private directory under the dot-path rule (see the sibling `private-dot-paths` decision).

**Options considered**, for what an unmigrated repo should do (there is no migration — repos are updated by hand): (a) detect the legacy path and log at ERROR while still defaulting; (b) refuse to open the repo entirely; (c) read the legacy path silently as a fallback; (d) leave today's warn-and-default behaviour untouched.

**Rationale.** (c) was chosen. The pre-existing behaviour on a missing ontology is `warn + DefaultOntology()`, which means a missed repo would silently start validating new facts against the WRONG taxonomy — that is the failure this decision exists to prevent, and only reading the legacy path actually prevents it. (b) was rejected because it also breaks any third-party KB repo that legitimately ships without an ontology. (a) and (d) both leave the wrong-taxonomy window open.

**The choice.** `OntologyPath = ".domains/ontology.yaml"` canonical; `LegacyOntologyPath = "domains/ontology.yaml"` read as fallback, in both `repoBuilder.loadOntology` and the OKF source loader. Both seed sites in `lifecycle.go` write the canonical path.

**The non-obvious consequence.** `loadOntology` must REMEMBER which path it read, because the boot-time preset refresh rewrites the ontology file when an embedded preset has moved ahead of the stored copy. If that write always targeted `.domains/`, a legacy repo would grow a SECOND ontology file while the stale one stayed behind — two files, one in force, no indication which. Writing back to the path that was read keeps a legacy repo internally consistent until it is migrated by hand. This is the regression most worth a test.

**Non-scope.** The fallback is READ-only and is not an invitation to keep the old layout indefinitely; it exists so a hand-migration miss degrades safely rather than silently. It also does not make 'always add a fallback' the rule — the sibling README decision deliberately takes a clean break, because the cost of a miss there is only a blank description.
