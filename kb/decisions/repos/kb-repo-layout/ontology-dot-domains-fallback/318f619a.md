# The ontology moved to .knomit/ontology.yaml (private namespace); .domains/ is now the legacy read fallback, and the preset refresh writes back to whichever path it read from

`ontology.yaml` is configuration, not knowledge, so it belongs in a private directory under the dot-path rule (see the sibling `private-dot-paths` decision).

**Options considered**, for what an unmigrated repo should do (there is no migration — repos are updated by hand): (a) detect the legacy path and log at ERROR while still defaulting; (b) refuse to open the repo entirely; (c) read the legacy path silently as a fallback; (d) leave today's warn-and-default behaviour untouched.

**Rationale.** (c) was chosen. The pre-existing behaviour on a missing ontology is `warn + DefaultOntology()`, which means a missed repo would silently start validating new facts against the WRONG taxonomy — that is the failure this decision exists to prevent, and only reading the legacy path actually prevents it. (b) was rejected because it also breaks any third-party KB repo that legitimately ships without an ontology. (a) and (d) both leave the wrong-taxonomy window open.

**Superseded layout (as of Task 6 of the knomit-private-namespace plan).** knomit's private, knomit-owned data was consolidated under `fact.PrivateRoot` (`.knomit/`). The ontology moved a second time as part of that consolidation: `OntologyPath = ".knomit/ontology.yaml"` is now canonical; `LegacyOntologyPath = ".domains/ontology.yaml"` (the PREVIOUS canonical path from this decision's original choice) is read as the fallback. The older pre-dot `domains/ontology.yaml` path — the original fallback described when this decision was first made — was dropped entirely; it is no longer recognized anywhere. Both seed sites in `lifecycle.go` write the canonical (`.knomit/`) path, in both `repoBuilder.loadOntology` and the OKF source loader.

The two path literals now live once, as `fact.OntologyFile` / `fact.LegacyOntologyFile` in `internal/fact/private.go` — shared by `internal/repos` and `internal/okf/source`, neither of which imports the other, which is exactly why the constants sit in the common `fact` package rather than being owned by either. `repos.OntologyPath`/`repos.LegacyOntologyPath` and OKF's `okfOntologyFile`/`okfOntologyFileLegacy` are now defined in terms of those `fact` constants rather than duplicating the literal — okf/source previously carried its own duplicated copies, which was a real drift risk this consolidation closes.

**The non-obvious consequence (unchanged by the Task 6 move).** `loadOntology` must REMEMBER which path it read (`srcPath`), because the boot-time preset refresh rewrites the ontology file when an embedded preset has moved ahead of the stored copy. If that write always targeted the canonical path, a legacy repo would grow a SECOND ontology file while the stale one stayed behind — two files, one in force, no indication which. Writing back to the path that was read keeps a legacy repo internally consistent until it is migrated by hand. This is the regression most worth a test, and `internal/repos/builder.go`'s `loadOntology` logic was left byte-for-byte untouched by the Task 6 move — only the constants it reads (`OntologyPath`/`LegacyOntologyPath`) changed underneath it.

**Non-scope.** The fallback is READ-only and is not an invitation to keep the old layout indefinitely; it exists so a hand-migration miss degrades safely rather than silently. It also does not make 'always add a fallback' the rule — the sibling README decision deliberately takes a clean break, because the cost of a miss there is only a blank description. Exactly two ontology paths exist after Task 6: canonical `.knomit/ontology.yaml` and legacy `.domains/ontology.yaml`.
