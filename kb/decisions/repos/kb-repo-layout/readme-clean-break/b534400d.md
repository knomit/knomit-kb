# kb.md became README.md with NO legacy fallback — deliberately asymmetric with the ontology move, which does keep one

The repo root manifest moved from `kb.md` to `README.md` because every major git provider already renders README.md at the repo root as the repository description — which is exactly what this file is.

**Options considered.** (a) Clean break: read and write README.md only. (b) Read kb.md, write README.md — description survives an unmigrated repo and the first UI edit migrates it. (c) Read and write whichever exists, full symmetry with the ontology decision.

**Rationale.** (a) won on cost-of-a-miss. A repo that still has kb.md shows an empty description card — the existing 'no manifest' state: visible in the UI, harmless, self-correcting the moment the file is renamed. It also keeps the write path unambiguous, so the UI editor always commits to README.md. (b) leaves a stale kb.md behind as a decoy and shows GitHub nothing until someone edits. (c) lets a repo stay on kb.md forever and never gain a provider-rendered description, which was the entire motivation.

**The choice.** `ReadmePath = "README.md"`; `ReadKBManifest`/`WriteKBManifest` renamed to `ReadReadme`/`WriteReadme`. No code reads `kb.md` anywhere. There is no migration — existing KB repos are renamed by hand.

**The trap this decision walks into.** `factIndex.writeFile` lowercases every path unconditionally, so `WriteFact(…, "README.md", …)` commits `readme.md`. That lowercasing is a FACT-PATH rule (it prevents case-duplicate topics like `AI` vs `ai`), and it never mattered before because `kb.md` is already lowercase. Writing the manifest therefore requires a case-preserving path — `WriteRootFile`, root-level only so it cannot become a way around fact-path normalization. A rename that overlooks this silently produces a lowercase readme and defeats the decision.

**Non-scope.** This does NOT establish 'no fallbacks' as a layout-migration rule. The sibling ontology decision (same `kb-repo-layout` category) deliberately keeps one, because a missing README costs a description whereas a missing ontology costs correct fact-path validation. Cost-of-a-miss decides each case, not consistency.
