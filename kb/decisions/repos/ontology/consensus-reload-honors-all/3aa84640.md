# An ontology change arriving through consensus is applied live in full, not filtered

Decision (user ruling on knomit/knomit#429): when the ontology file at a repo's read branch changes by a means other than a local write (a sync round, origin attach/swap, rebuild, a merge into the read branch), knomit re-reads it and applies it AS-IS.

Options considered:
1. Additive-only: apply the new ontology only when old ⊆ new (topics/categories only added), otherwise keep the old one.
2. Additive plus non-security attributes: allow additions and attribute changes except security-relevant ones such as verify_signatures.
3. Apply everything consensus delivers.

Choice: option 3, apply everything. That covers added topics and categories; changed or added attributes of every kind, verify_signatures included; removed or renamed topics and validations.

Rationale (the user's words, paraphrased): the main branch is consensus. Anything on main that is signed was approved at the consensus gate (signing, review, merge), and knomit must honour it in full. An additive-only filter, a subset check, or a security guard that refuses consensus content downstream is "fixing the security in the wrong place": security belongs at the gate that admits commits, not in the consumers of main.

Non-scope / what this does NOT mean:
- It does not loosen the consensus gate itself (signing, review, merge admission are unchanged). If you think a consensus ontology change is dangerous, the fix goes in the gate, never in a reload-time filter.
- An UNUSABLE ontology file at the new tip (missing, empty, unparseable, or a symlink) is not applied: the previously loaded ontology stays in force and the error is reported in the repo's status. 'Apply everything' is about content that parses, not about files that cannot be used at all.
- It is not the boot-time preset refresh (knomit's own release overwriting the stored preset file); that path keeps its own rules, including its no-attribute-change rule.
