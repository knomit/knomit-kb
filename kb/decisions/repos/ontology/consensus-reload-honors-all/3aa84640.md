# An ontology change arriving through consensus is applied live in full, not filtered

Decision (user ruling on knomit/knomit#429): when the ontology file at a repo's read branch changes by a means other than a local write (a sync round, origin attach/swap, rebuild, a merge into the read branch), knomit re-reads it and applies it AS-IS.

Options considered:
1. Additive-only: apply the new ontology only when old ⊆ new (topics/categories only added), otherwise keep the old one.
2. Additive plus non-security attributes: allow additions and attribute changes except security-relevant ones such as verify_signatures.
3. Apply everything consensus delivers.

Choice: option 3, apply everything. That covers added topics and categories; changed or added attributes of every kind, verify_signatures included; removed or renamed topics and validations.

Rationale (the user's words, paraphrased): the main branch is consensus. Anything on main that is signed was approved at the consensus gate (signing, review, merge), and knomit must honour it in full. An additive-only filter, a subset check, or a security guard that refuses consensus content downstream is "fixing the security in the wrong place": security belongs at the gate that admits commits, not in the consumers of main.

Non-scope / what this does NOT mean:
- It does not loosen the consensus gate itself (signing, review, merge admission are unchanged). If you think a consensus ontology change is dangerous, the fix goes in the gate, never in a reload-time filter.
- An UNUSABLE ontology file at the new tip (missing, empty, unparseable, or a symlink) is not APPLIED, and — since decision 1 below — neither is the previous one KEPT: the repo becomes unwritable until consensus fixes the file. 'Apply everything' is about content that parses, not about files that cannot be used at all.
- It is not the boot-time preset refresh (knomit's own release overwriting the stored preset file); that path keeps its own rules, including its no-attribute-change rule.

FOLLOW-UP DECISIONS (user, on the review of PR #761, 2026-11-05).

DECISION 1 — what an UNUSABLE consensus ontology does.
Options: (a) keep the previously loaded ontology in force, the repo stays writable, the error is reported (what the PR first built); (b) the repo becomes UNWRITABLE until consensus fixes the file.
Choice: (b). Unusable means exactly what readOntology refuses: missing at every rung, a symlink (fact.ErrSymlinkNotFollowed), an empty first rung present, a fatal ParseOntology error. The repo has no ontology in force (OntologyError), WritableBranch refuses every authored write, and the store refuses EVERY FACT MUTATION by any in-process writer — writes, empty writes, DELETES and retracts (review prune, dedup losers), batches, and carried-over replay writes (Service.SetOntologyUnusable -> facts.Repo.refuseWhileOntologyUnusable in all three write cores: writeFileExact, deleteFile, batchWriteLocked). validateWrite itself also refuses on an unparseable or empty tip instead of skipping validations. Only a write that touches no fact path (the ontology's own repair) passes. 'Unwritable' is literal for every WRITER: no in-process or authored write, delete or retract changes a fact until consensus fixes the file.
NOT GATED (by design): MERGES are not the store's write cores, so they still change facts while the ontology is unusable — the sync merge or fast-forward of main into the read branch (which is how the fix itself arrives, and which the gate must not block), the consensus merger merging pushed branches, and an experiment commit. Those have their own gates (validation of the merge result, the push judges), not this one. When consensus fixes the file, the next reload makes the repo writable again under the NEW ontology, with no restart. Status reports it (OntologyStatus.Error; GET /repos ontology_error; GET /repos/{name} ontology.usable=false + ontology.error).
Rationale: it matches what a restart gives today; the repo cannot run on content it cannot read; keeping a stale ontology would silently diverge from consensus.
A READ error (ontologyReadError: the tip, tree or blob could not be read) is NOT unusable: it is 'unknown, retry' — it changes nothing, records nothing, and the next round or commit reads again.

DECISION 2 — the reserved fleet id arriving by consensus on a repo that is NOT the fleet repository.
Options: (a) the repo becomes UNAVAILABLE with cause fleet_conflict; (b) apply it as the fleet repository. (The PR's first build — refuse it while keeping the repo writable — was a downstream filter, which the ruling forbids, and is removed.)
Choice: (a). The repo is made unwritable at once, then Manager.retireFleetConflict (on a goroutine Manager.Close tracks and waits for, whose Unmount is bounded by the machine's unmountDrainBound like Close's own) unmounts it FIRST and, only once that unmount has completed (its store closed), removes it from the live maps and lists it unavailable (reason unopenable, cause fleet_conflict), re-checking the instance by uid and publishing it under its current name (a rename during the unmount is followed, not stranded) — unless a later reload has already applied a fixed, non-fleet tip. If the bounded unmount times out, nothing is published: the repo stays mounted, unwritable and winding down until Close or its next mount (which refuses it with fleet_conflict).
Rationale: it matches mount (admitFleetOntology at Identify).

NON-SCOPE of both: neither decision filters or refuses USABLE consensus content. A usable ontology on a repo that is not the fleet repository is applied in full; a fleet repository's usable consensus ontology is applied in full, including one that drops the fleet id.
