# Renaming a live repo re-keys Manager.repos in place rather than Remove+Add — the store must not close to change a display string

**The choice.** `Manager.RenameRepo` validates the new name, reserves it, checks the lens-name conflict, does `Registry.Rename(uid, newName)`, then re-keys in place under `m.mu`: `m.repos[new] = m.repos[old]; delete(m.repos, old); ri.setName(new)`. `byUID` is untouched — the uid does not change.

**Options considered.** (a) Re-key in place. (b) `Remove(old)` + `Add(new, uid, path, origin)`, which is what `Restore` already does and is therefore the proven path.

**Rationale.** (b) is correct but `Restore` is opening a repo that was closed anyway. Here the store is LIVE: `Manager.Remove` calls `ri.shutdown()`, which closes the store, drops SSE subscribers mid-stream and forces an index re-warm — a large amount of destruction to change a display string. A repo's name is display-only: the store file is `<home>/repos/<uid>.db` (name-independent), lens membership is uid-keyed, and the lens REST wire format derives its `name` field, so a rename is genuinely a control.db UPDATE plus a map key move.

**The cost this incurs.** `RepoInstance.name` is currently a plain `string` field read without a lock from several sites, mostly logging. In-place rename introduces the only write it has ever had, so it becomes an `atomic.Pointer[string]` behind the existing `Name()` accessor — reads stay lock-free, the single write is safe. This is the one part of rename that is not already-existing machinery; everything else (`Registry.Rename`, `reserveNameAndOrigin`, `lensNameConflict`) already exists and is already exercised by `Restore`.

**HTTP shape.** `POST /api/v1/repos/{repo}/rename`, not `PATCH /repos/{repo}` — `repoView` re-reads the repo through the name in the URL, and a rename invalidates the identifier the request was addressed by. The slash form matches the existing resource-level action `POST /archived/{id}/restore`. It is deliberately NOT the colon form: the AIP colon convention (`/repos:rescan`) is scoped to COLLECTION-level actions with no `{repo}` segment. Registered INSIDE the `RepoMiddleware` group, unlike Archive — Archive sits outside because it resolves through `m.Archive` and attributes its own not-found errors, whereas rename's `{repo}` must exist (so the middleware 404 is the right answer) and every error rename raises concerns the NEW name, which the middleware never sees.

**UI.** Danger zone, below Archive, with typed confirmation of the CURRENT name. The warning names the real consequence — agent MCP endpoint URLs embed the repo name and stop resolving — rather than saying "this is dangerous"; nothing is deleted and the rename is freely reversible.

**Non-scope.** This does not make the name an identity: uid remains membership, root-commit id remains fact addressing. It does not narrow `isValidRepoName`, so a user can still type a ksuid-shaped name and widen the known migrate-registry false-positive class — accepted, because it fails loudly and narrowing the grammar would affect create too.
