# Renaming a live repo re-keys Manager.repos in place and commits durably via a compare-and-swap — the store must not close, and neither the forward write nor its compensation may be unconditional

**The choice.** `Manager.RenameRepo` renames without closing the store: a registry write plus an in-place re-key of `m.repos`. `Remove`+`Add` (what `Restore` does) was rejected — it calls `ri.shutdown()`, closing the store, dropping SSE subscribers and forcing an index re-warm, all to change a display string. A repo's name is display-only: the .db is `<home>/repos/<uid>.db`, lens membership is uid-keyed, and the lens wire format derives its name field.

**AS BUILT — two review rounds changed the mechanism. The naive version of this shipped and was wrong twice; do not simplify back toward it.**

*Round 1 — the guards were not enough.* Validating outside `m.mu` and then writing the map raw is racy: `reserveNameAndOrigin` only gates paths consulting `m.creating` (Create/Restore/CreateLens) and reserves the NEW name only — `Archive` and `Remove` consult neither. An `Archive` completing between the guards and the registry write meant the rename landed on the now-ARCHIVED row and the map write resurrected a shut-down instance with no `byUID` entry. Fix: **revalidate `m.repos[oldName] != ri || m.repos[newName] != nil` UNDER `m.mu`**, in the same critical section as the map write, and compensate the durable half on failure.

*Round 2 — the compensation had to be a CAS, and then so did the forward write.* An unconditional compensating revert clobbers a concurrent winner: the loser can only reach the revalidate AFTER the winner's map swap, and the winner's registry write strictly precedes that, so the loser's own straggling revert is chronologically last and the durable revert becomes the MODAL outcome, not a rare interleaving — a rename that returned `nil` silently reverts at the next restart. Making only the compensation conditional does not fix it, because the losing call's own forward write is still the last one to land. **Both writes are compare-and-swap:** `Registry.RenameIfNamed(uid, from, to) (bool, error)` — `UPDATE repos SET name = ? WHERE uid = ? AND name = ?`. The forward CAS means a loser matches zero rows, learns it lost at the registry layer, and never touches the map or needs compensating at all.

**Ordering that matters:** `controlHandles()` BEFORE `m.mu.Lock()` (it takes `m.mu.RLock()` and RWMutex is not reentrant); `ri.setName` INSIDE the critical section, not after — outside it there is a window where `Get` returns an instance whose `Name()` matches neither key, and `setName` is a lock-free atomic Store so moving it in costs nothing.

**`RepoInstance.name` became `atomic.Pointer[string]`** because this introduced the only write it has ever had. Every construction site must `setName` after building — an atomic cannot be set in a struct literal — including `repoBuilder.build()`, which the plan missed and a grep for `RepoInstance{` found.

**A consequence the doc comment must keep stating:** the loser of a lost race gets `ErrRepoNotFound` wrapping the OLD name, which the HTTP layer maps to **409, not 404** — the middleware already proved the repo existed, so "not found" would be a lie.

**Tests that must exist, because their absence let bugs through here:** a DURABLE assertion (an implementation that skipped the registry write entirely passed all five original tests), and a CONCURRENT one (all five were single-goroutine, so `-race` proved nothing about the atomic field this design introduced).

**Non-scope.** This does not make the name an identity: uid remains membership, root-commit id remains fact addressing. `Restore`'s three unconditional compensations (`lifecycle.go`) are the same class of bug and remain OPEN — one conditional-rename method should cover all four, and when `Restore` migrates, DELETE `Registry.Rename`: it and `RenameIfNamed` have different zero-row semantics (`ErrRegistryNotFound` vs `(false, nil)`), which is a trap for the next caller.
