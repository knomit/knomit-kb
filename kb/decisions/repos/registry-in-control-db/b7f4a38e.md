# The repo registry moved from the filesystem (glob repos/*.db + JSON archive manifests) into <home>/control.db, so a lost .db is re-clonable from a record that outlives it

**What existed before:** repo existence and identity were derived entirely from the filesystem. `Manager.Start` globbed `<home>/repos/*.db` (sorted, skipping session sidecars and invalid names) and registered whatever it found; the repo's NAME was its filename. Archive moved the file to `<home>/repos/archive/<name>.<unix>.db` plus a sibling `.json` manifest; Restore/Purge moved or deleted those files. Remote connection config (url/branch/auth_method/auth_token) lived inside each repo's own `remotes` row, so it traveled (or was lost) WITH the .db file. `POST /api/v1/repos:rescan` existed because the glob was the only way to pick up a repo that appeared out-of-band (a restored backup, a .db copied in by hand). `repo_settings(repo_id, profile)` was a second control.db tenant keyed by the mutable root-commit hash.

**Options considered:** (a) keep the filesystem as source of truth and patch around its gaps (the rescan endpoint, careful archive-directory glob exclusion, dangling-lens-ref guards at the Archive/Purge choke points only); (b) move repo existence, identity, state, profile, and remote connection config into `<home>/control.db`, keyed by a newly-minted, permanent, path-independent uid (ksuid), with the .db file's on-disk location derived from that uid rather than from the repo's (mutable, user-facing) name.

**The choice: (b).** `internal/repos/registry.go` adds a `repos` table (`uid` PK, `name`, `state`, `profile`, `repo_id` nullable+unique-among-active, `created_at`, `archived_at`) and `internal/repos/origins.go` adds `repo_origins` (`repo_uid` PK/FK→repos, `url`, `branch`, `auth_method`, `auth_token`) as a second control.db tenant sharing the registry's `*sql.DB` handle. Repo databases now live at the path-independent `<home>/repos/<uid>.db` — the repo NAME never appears in any path. `Manager.Start` reads `repos` rows (`List(StateActive)`) instead of globbing; `Manager.Rescan` and the glob-discovery loop are DELETED because there is no longer a filesystem state to reconcile against — the registry IS the state. Archive/Restore/Purge became registry UPDATE/DELETE state flips; the .db file never moves, so `repos/archive/` and its JSON manifests are gone. Migration `000017_remotes_drop_connection` dropped the four connection columns from each repo's own `remotes` table; `repo_settings` was folded into `repos.profile`, re-keyed from the mutable `repo_id` to the permanent `uid` (fixing a real bug — profile silently reverting to "code" after a disjoint-history connect, see kb/decisions/mcp/profile-per-repo). Lens membership was similarly re-keyed from repo NAME to registry `uid` (`lenses.write_uid`, `lens_reads.repo_uid`), closing the whole class of dangling-lens-ref bugs that existed when membership was keyed by a value (name) that Restore-under-new-name or a future rename could silently invalidate (see the retracted lens-registry-integrity gotcha).

**Rationale — durability is the load-bearing reason:** with connection config living inside the .db file itself, a corrupted or lost database was unrecoverable — nothing durable outside it remembered where to re-clone from. Moving the origin record into control.db means a lost/corrupted repo .db is re-clonable from a record that outlives it (internal/store/remote.go's Origin doc comment: "This is what makes a lost repo recoverable: the .db file holds the knowledge base, control.db holds the address to re-clone it from"). A second reason: a filesystem-derived registry cannot represent 'this repo is registered but broken' — a missing or corrupt .db file simply vanished from the glob. The control.db registry is authoritative independent of whether the file opens, so a registered repo that fails to open now stays VISIBLE (states `missing`/`unopenable`/`conflict`, surfaced via `Manager.Unavailable()`) with its endpoints answering 409, instead of silently disappearing from the API.

**Accepted consequences:** (1) a legacy (pre-registry) home cannot boot until converted — `Manager.Start` refuses when `Registry.SchemaJustCreated()` is true (this OpenRegistry call created the table fresh) and a stray `.db` is found in `repos/`, pointing the operator at `knomit migrate-registry`; the guard is keyed on schema-freshness, not registry-emptiness, because a fully-migrated-then-fully-purged home is also empty and must still boot. (2) the one-shot conversion tool (`cmd/migrate_registry.go`) had to be built carrying its own ordering invariant (raw-SQL reads before any `store.Open`, see kb/invariants/repos/migrate-registry-ordering) because the very schema migration this move requires (000017) destroys the data the tool needs to carry forward — a sharp, self-inflicted edge that is the direct cost of moving connection config out of the file it used to live in.
