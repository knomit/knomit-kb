# Instance-to-instance git fetches use a custom go-git scheme knomit+https with a rewriting wrapper over pki.HTTPClient, not DNS/IP SANs with go-git's ClientCert/CABundle and not a global https override

Decided in F19 phase 2b (2026-09-22, plan .claude/plans/2026-09-22-f19-phase2b-gogit-mtls.md, master and reviewer rulings). UPDATE (PR #526, merge 0488c05d): the scheme below is now an INTERNAL key. The user types and stores plain `https://<host>:<tls port>/git/<repo>`; knomit classifies the origin once when it is set (pki.ClassifyOrigin) and stores auth method `cert`; only pki.GitURL and the derived .git/config spell knomit+https, and a typed or stored knomit+https URL is refused (kb/decisions/repos/remote/plain-https-origins/07cc1cef.md, D1 to D4). Option (c) below stays true as the mechanism and options (a) and (b) stay rejected; the naming of an origin with the scheme does not.

An instance names another instance as its git origin by an https URL that classifies as a fleet peer and auth method `cert` (before #526: by typing `knomit+https://<host>:<tls port>/git/<repo>`). Every fetch, clone and probe then goes through the phase 2 mutual-TLS client: fleet-root-only chain verification, CRL, URI SAN, named refusals.

OPTIONS CONSIDERED:
(a) Put DNS/IP SANs in instance certificates and use go-git's ClientCert/ClientKey/CABundle options. REJECTED: an address change would force a re-issue (certificates are renewed without re-key and carry only the knomit:// URI SAN). Go's hostname check cannot express the URI SAN. CABundle appends to the SYSTEM pool, so any publicly trusted certificate would verify. And ClientKey goes through tls.X509KeyPair, which cannot read the OpenSSH key without a second on-disk copy (kb/gotchas/pki/openssh-key-is-not-x509keypair-input).
(b) `client.InstallProtocol("https", …)` with the fleet client. REJECTED: process-global, so it would carry every forge (GitHub) clone as well, and the verifier would need a system-verification fallback for non-fleet hosts. That is exactly the kind of fallback the no-insecure-skip invariant forbids.
(c) CHOSEN: a separate scheme, registered ONCE, whose wrapper copies the endpoint with Protocol "https" and delegates to go-git's http transport over pki.HTTPClient. The `https` entry is never touched; `TestGitTransport_HTTPSProtocolEntryUntouched` pins pointer equality.

SHAPE THAT FOLLOWS: `cert` is a fifth remote auth method meaning 'the credential is the client certificate on the transport'. resolveAuth returns no go-git AuthMethod for it. Since #526, resolveAuthWithOrigin no longer forces cert from the URL: cert is keyed on the STORED method (decided at set time by ResolveOrigin), a credential typed for a peer is refused (ErrPeerCredential) and cert as an input is refused (ErrCertNotAnInput) by the edge (validateURLAuth and the wizard's urlAuthMismatch, same words, same table) and by ResolveOrigin. (Before #526: for a knomit+https URL resolveAuthWithOrigin FORCED cert and errored on an explicit token/basic.) Scheme checks stay case-insensitive because go-git lowercases the scheme.

OUT OF SCOPE BY DESIGN: push (knomit's /git exposes no receive-pack until F11), F09 signature verification on fetch, F10 peers, per-repo trust roots, cross-scheme redirects.

MISREADING TO AVOID: this is not 'knomit replaced go-git's https'. Forge clones use go-git's stock https transport and never see the fleet client.
