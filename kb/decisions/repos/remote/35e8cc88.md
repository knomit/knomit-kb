# HISTORICAL (true from #82 until fix/no-hardcoded-consensus-branch): Clone/InitFromRemote preferred 'main' over a remote agent-branch HEAD as the consensus upstream. Superseded by store.ChooseConsensusBranch, which skips an agent-branch HEAD without preferring any name

WHAT WAS TRUE: when a repo was cloned with no explicit upstream branch, store.InitFromRemote resolved the consensus upstream by PREFERRING 'main' whenever the remote had it (remoteHasBranch on refs/remotes/origin/main after the wildcard fetch). It fell back to the remote's symbolic HEAD (detectRemoteUpstream) only when there was no 'main', and then to 'main' as a last resort. The reason was real: a knomit remote's GitHub default branch can be an agent branch (knomit-kb's HEAD was agent/mindev.local-8ef0cd32). The pre-#82 code adopted that HEAD, which made another machine's agent branch the local consensus, and that triggered the reconcile force-reset data-loss bug (gotchas/repos/remote-sync).

SUPERSEDED under the ruling "Hardcoded values are never good": kb/decisions/store/consensus-branch/remote-rule-head-not-name. The #82 hazard is now handled by the ROLE of the HEAD branch, not the NAME of another. store.IsRoleBranch skips an agent/*, exp/* or okf HEAD, and the one remaining branch is adopted. A remote with several remaining branches is refused (ErrNoConsensusBranch). A remote with main and trunk and HEAD on trunk now resolves to trunk.
