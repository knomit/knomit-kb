# On a restored/copied home, adopt the previous agent branch as seed and retain the orphan

When a knomit home is restored onto a different machine (or a repo DB is copied), the fresh SSH key yields a different agent branch name (derived from the key fingerprint), so the configured agent branch is ABSENT in the copied database. ensureBranch (internal/repos/builder.go) must seed it via CreateBranch from a source that exists; seeding from itself (the old CreateBranch(agent, agent)) failed and broke every write path (issue #32).

**Options considered** for the seed source: (a) adopt the repo's current HEAD branch — the previous machine's agent branch; (b) seed from the upstream consensus branch (main/master). For the orphaned previous branch: retain, adopt, or garbage-collect.

**Rationale**: Seed = HEAD (option a), NOT upstream main. For local-only repos (the dominant case, including knomit's own memory) main sits at the init commit, so seeding from main would DISCARD every accumulated fact. HEAD points at the previous agent branch, which carries all knowledge; CreateBranch already clones git ref + branch_commits + branch_facts, so adoption inherits everything. This mirrors how a fresh clone bootstraps its agent ref from origin/main. The orphaned previous branch is RETAINED (not GC'd): nothing writes to it and it is outside the fetch refspec so it is never pushed; GC risks deleting the only copy of data.

**The choice**: seedSourceForAgentBranch() returns the agent branch when present (CreateBranch no-ops), else the HEAD/DefaultBranch when it differs, else falls back to the agent branch itself (so CreateBranch fails loudly on a detached/broken HEAD rather than seeding from a broken source). ensureBranch also now runs BEFORE loadOntology in manager.openOne so the restored instance loads the adopted branch's ontology on first boot instead of the default. A missing sync watermark on the adopted branch self-heals via reconcileAgentRebase's MergeBase fallback.

**HEAD == THIS MACHINE'S AGENT BRANCH IS AN INVARIANT.** Every repo-creation path establishes it — store.InitRepo, InitFromRemote, initFromEmptyRemote, plus the runtime lifecycle paths (Manager.Create's initLocal/initClone) which route through them. Nothing else writes HEAD, and no config lets an operator choose a different one (the name derives from the local key fingerprint). A restored/copied home is precisely the case that violates it.

So ensureBranch calls alignHeadWithAgentBranch() after any successful CreateBranch: if HEAD is not the agent branch, repoint it. This is load-bearing, NOT cosmetic — two earlier revisions of the fix got it wrong in different ways.

1. The FIRST revision left HEAD on the orphan entirely, reasoning that reads/writes address branches by name. But seedSourceForAgentBranch READS HEAD as its adoption source, so HEAD stayed pinned to the machine that first created the repo: a home restored, used, and restored AGAIN adopted the original branch on the second hop and silently discarded everything the intervening machine wrote. No error, no warning.
2. The SECOND revision moved HEAD only on the boot that adopted. That made the repair un-retryable — once the agent branch exists no further adoption fires, so one failed SetDefaultBranch pinned HEAD wrong permanently and re-armed the same data loss.

Repairing the invariant on ANY boot (not only the adopting one) is what makes it self-healing; it also fixes a detached HEAD for free. The check runs only AFTER CreateBranch reports success, so HEAD is never pointed at a missing ref — that would dangle it and fail the next OpenRepo (which, for the default repo, falls through to initDefaultGit). Regression tests: TestEnsureBranch_ChainedRestoreAdoptsMostRecentBranch (three machines in sequence), TestEnsureBranch_RepairsHeadWhenAgentBranchAlreadyExists (damaged state, no adoption fires).

**Non-scope**: The orphan branch is still not garbage-collected — only the HEAD pointer moves off it. No explicit agentBase seeding for origin repos (the reconcile MergeBase fallback covers it). Push/sync never consult HEAD (they address the agent ref by name), so moving it has no remote-facing effect. Note that DropBranch does not guard HEAD, so deleting a branch HEAD points at would dangle it and fail OpenRepo; DropBranch has no API/CLI/MCP caller today, so this stays latent.
