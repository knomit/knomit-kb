# A create job's `done` means INDEXED, not registered: after m.Add the job mirrors RepoInstance.IndexStatus() until it leaves `indexing`, and an index error is `done` with index_state=error, never a failed job — the transfer phase is indeterminate and the status body carries NO pct while it is

Decided 2026-09-16 (PR #208). Before: progress was a constant per step (subscribe emitted 40% and the next emit was 70% after the whole clone), and the job reported `done` right after m.Add while the index heal continued in the background (the open-serves-immediately model of fa0ea608), so a repo looked ready in the create flow while it was still indexing.

Now: CreateStatus carries Phase (validate|transfer|index|register|done), Indeterminate, IndexState. InitSubscription and InitFromRemote take a `progress func(string)` and forward the remote's sideband lines as transfer-phase events with Indeterminate=true. After m.Add succeeds (and the RecordRepoID backstop), the job MIRRORS ri.IndexStatus() every 250 ms on the job goroutine — done/total become the job's pct — until the state leaves `indexing`. `ready` → done. `error` → done with index_state=error: the repo exists and is registered, so failing the job would misdescribe it; its row shows the error chip. The repo open path itself is unchanged: it still serves immediately with the heal in the background; only the CREATE JOB waits for the heal before calling itself done. The mirror is placed AFTER Add on the instance Add registered; ri.markIndexing() runs synchronously inside openOne before Add returns, so the placement is race-free.

WHAT THE INFERENCE NOW RESTS ON (updated 2026-09-18, PR #221). "The state left `indexing`, therefore the heal finished" depends on TWO things, not one:

1. The ORDERING above — markIndexing runs synchronously inside openOne before m.Add returns — which guarantees the heal has claimed the state before this loop first reads it. This is what makes the first read safe.
2. The 409 REFUSAL of a manual rebuild while the state is `indexing` (handleStartRebuild). This is what makes every LATER read safe, and it did not exist when this fact was written.

The second became load-bearing when the manual rebuild endpoint began marking the same cell. Before #221 a rebuild never touched index state, so the heal was the only writer as a fact about the code; now it is the only CONCURRENT writer as a matter of policy. Without the 409, a rebuild could finish first while a heal was still in flight, flip the cell to `ready`, and make mirrorIndexing return `ready` — and this job would emit done/100%/index_state=ready over a half-built index, which is exactly what this fact promises cannot happen.

A THIRD WRITER OF THE CELL BREAKS THE INFERENCE AGAIN unless it is serialised the same way. Do not derive safety from the ordering paragraph alone: it establishes who claims the state first, not who may change it afterwards.

Wire contract: `indeterminate:true` → the "pct" KEY IS OMITTED from the status body; otherwise pct is present. Do NOT zero pct instead: createStatusBody wrote it unconditionally and a zero would run the latest value 5 → 0 → 70, sending a monotonic client bar backwards mid-create (caught in review before it shipped). Both UI components treat a missing pct as "draw indeterminate", pinned on both sides.

Test trap: DisableBackgroundSync (set by most repos/web tests) takes an open path that heals synchronously and marks ready before Add returns, so a "done arrived while ready" test passes with NO mirror at all. A test of this property must run WITHOUT that flag and assert unconditionally that it observed a Phase==index status with total > 0; and it should collect events from the emit callback rather than sample job.Status(), whose 25 ms polling can miss a short index phase (a flake fixed this way).

Deliberately left: the commit-parents backfill inside openOne emits no progress of its own (openOne takes no context or callback by design, part of the clone-create-index-stuck incident's repair); the index mirror covers that period with the heal's real counts.
