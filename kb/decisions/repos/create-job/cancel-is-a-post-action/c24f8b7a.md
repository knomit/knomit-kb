# Cancel is an ACTION on the job — POST /api/v1/repo-creates/{id}:cancel answering 202 with the snapshot in the non-terminal state `cancelling` — never blocking, idempotent while cancelling, 409 once failed/cancelled, 404 unknown; GET /repo-creates omits cancelled jobs while GET /repo-creates/{id} still serves them until TTL; the in-memory Err is ErrCreateCancelled while the wire body carries no `error`

Options considered in PR #230: (a) reuse DELETE /repo-creates/{id} with a flag; (b) a colon-suffixed POST /repo-creates/{id}:cancel matching /repos:probe-origin; (c) a synchronous cancel that returns only once the repo is gone. Chosen: (b), never blocking. Rationale: dismiss (DELETE) refuses a running job by design — a list operation must not roll back a half-clone — and cancel exists exactly for a running job, so the two must stay distinct routes. The handler returns 202 + createStatusBody rather than 204 because a running create stops at its next step boundary, not on the request, and a transfer in flight is not interruptible (go-git fetch), so the honest answer is "accepted, poll to cancelled"; a finished job's delete also runs on a goroutine so the HTTP caller is never held for Archive's shutdown. `cancelling` is a NON-terminal CreateState introduced because the UI kept drawing the last progress line after the click ("everything is frozen"); record() never writes j.state so a progress event cannot clobber it; runningCreates/anyRunning in the UI count cancelling as activity so the list keeps its 2s poll rate. CreateJobs() omits CreateCancelled so the rail drops the row on its own (the user: "what's the point, I KNOW it was cancelled"); failed jobs stay listed because their error is worth reading; CreateJobByID still answers for cancelled jobs until CreateJobTTL so a poller sees the terminal state. This amends the earlier visibility decision (pending-rows-and-indicator), which predates cancel and described only list/dismiss. In memory a cancelled job's Err is ErrCreateCancelled (distinct from context.Canceled, which shutdown produces) so Result() is consistent across the running and done paths; on the wire createStatusBody writes `error` only for failed — do not "fix" that asymmetry, it is the contract the UI relies on. The handler has NO ErrRepoInUseByLens branch: the delete happens after the response, so a lens refusal lands on the job as a failed state with the reason. Misreading to avoid: 'cancelled' is terminal and never goes back to 'running'; 'cancelling' after 'done' IS legal (done job being deleted) and the UI's adoptStatus guard must allow it.
