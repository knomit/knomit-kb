# Repo description = verbatim README.md read at HEAD, exposed on the single-repo GET only, rendered collapsible in the detail pane — with LICENSE as its read-only sibling

NOTE ON THIS FACT'S PATH: the slug says `description-from-kbmd`. The manifest is `README.md` and has been since PR #68; the slug is a historical artifact of when this decision was taken, not a claim. It was kept rather than retracted-and-rewritten because the DECISION recorded here is unchanged — only the filename it names moved — and a retract would sever this fact's revision history and inbound refs for no gain.

Repos gained a "description" sourced from the repo's root manifest (PR #91).

**Options considered (resolved via AskUserQuestion):**
1. *Extraction* — (a) first paragraph after the H1 title, (b) a YAML frontmatter `description:` field with fallback, (c) the WHOLE file verbatim. → chose (c) whole file.
2. *UI placement* — (a) list + detail pane subtitle, (b) detail pane only, collapsed. → chose (b).

**Rationale:** The user wants the entire manifest rendered, not a parsed/extracted summary, so no first-paragraph/frontmatter heuristic. Showing it only in the detail pane (not the /repos collection items) keeps embedded collection items minimal per the HAL hard rule (§3 #7: embedded items carry only _links.self + minimal display fields) and avoids N git reads on the list endpoint. Collapsing it keeps a manifest that routinely runs to several pages from taking over the pane.

**The choice / implementation (verified at 54290347):** `handleHALRepo` reads the manifest per-request — always fresh, no caching on RepoInstance — via `readReadme` → `ri.ReadReadme` → `svc.Facts().ReadFact(ctx, branch, repos.ReadmePath, nil)` on the AGENT BRANCH, which is where HEAD points. The field is OMITTED when nothing is readable (nil store / missing file / empty branch) so the UI shows it only when available. The /repos collection endpoint is unchanged. Web: `api.getRepo()` hits the single-repo GET; `RepoManager` renders it through the shared `DescriptionCard` — react-markdown inside a collapsed-by-default `Disclosure`, with inline markdown editing that PATCHes back through `WriteReadme` (capped at `MaxRepoDescriptionBytes` = 64 KiB). OpenAPI's Repo schema documents `description`, `license`, and the previously-undocumented `agent_branch`.

**The kb.md → README.md rename (PR #68).** Clean break, no legacy fallback: nothing reads `kb.md`, and an unmigrated repo shows an empty description card until the file is renamed by hand. See `kb/decisions/repos/kb-repo-layout/readme-clean-break/b534400d.md` for why this move is deliberately asymmetric with the ontology's `.domains/` move, which DOES keep a read fallback. Writes go through `store.WriteRootFile` rather than the fact-write path, because `factIndex.writeFile` lowercases every path — a fact-path rule that never mattered for `kb.md` but would have committed `readme.md`.

**LICENSE, the read-only sibling.** PR #68 added `LICENSE` on this SAME endpoint and with the same scoping — single-repo GET only, omitted when absent — but read-only: no write path, no seeding, no OKF export, and rendered as PREFORMATTED text rather than markdown, because a markdown renderer reflows a licence's newlines away. See `kb/decisions/repos/kb-repo-layout/license-read-only/2b569af1.md`.

**Why both files sit at the TREE ROOT, not under `kb/`:** anything under the ontology root with an ordinary name is a fact by location — see `kb/invariants/store/indexing/ontology-root-scope/1b35d56b.md`. Indexing the manifest as a fact is exactly the bug that invariant exists to prevent.
