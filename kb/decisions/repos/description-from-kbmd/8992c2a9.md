# Repo description = verbatim README.md read at HEAD, exposed on the single-repo GET only — with LICENSE as its sibling field (UI since moved from a collapsed card to an open SettingsPage section; LICENSE gained a write path too, see below)

NOTE ON THIS FACT'S PATH: the slug says `description-from-kbmd`. The manifest is `README.md` and has been since PR #68; the slug is a historical artifact of when this decision was taken, not a claim. It was kept rather than retracted-and-rewritten because the DECISION recorded here is unchanged — only the filename it names moved — and a retract would sever this fact's revision history and inbound refs for no gain.

Repos gained a "description" sourced from the repo's root manifest (PR #91).

**Options considered (resolved via AskUserQuestion):**
1. *Extraction* — (a) first paragraph after the H1 title, (b) a YAML frontmatter `description:` field with fallback, (c) the WHOLE file verbatim. → chose (c) whole file. **Still true.**
2. *UI placement* — (a) list + detail pane subtitle, (b) detail pane only, collapsed. → chose (b). **The "detail pane only" half still holds; the "collapsed" half has since been reversed — see UI SINCE CHANGED below.**

**Rationale:** The user wants the entire manifest rendered, not a parsed/extracted summary, so no first-paragraph/frontmatter heuristic. Showing it only in the detail pane (not the /repos collection items) keeps embedded collection items minimal per the HAL hard rule (§3 #7: embedded items carry only _links.self + minimal display fields) and avoids N git reads on the list endpoint. Collapsing it kept a manifest that routinely runs to several pages from taking over the pane — a constraint that was real when the pane was a boxed dialog about two cards deep.

**The choice / server implementation (verified at 54290347, re-verified at HEAD 9702a283):** `handleHALRepo` reads the manifest per-request — always fresh, no caching on RepoInstance — via `readReadme` → `ri.ReadReadme` → `svc.Facts().ReadFact(ctx, branch, repos.ReadmePath, nil)` on the AGENT BRANCH, which is where HEAD points. The field is OMITTED when nothing is readable (nil store / missing file / empty branch) so the UI shows it only when available. The /repos collection endpoint is unchanged. `api.getRepo()` hits the single-repo GET; inline markdown editing PATCHes back through `WriteReadme`, capped at `MaxRepoDescriptionBytes` = 64 KiB (`internal/repos/manifest.go:29`). OpenAPI's Repo schema documents `description`, `license`, and the previously-undocumented `agent_branch`. **All of this is unchanged.**

**UI SINCE CHANGED (PR #77 and the SettingsPage rework).** The shared `DescriptionCard` and its collapsed-by-default `Disclosure` are GONE — neither symbol exists in `web/src/` any more. The manage surface is now `SettingsPage`, which explicitly "replaces a stack of collapsed `Disclosure` cards": the page is the window rather than a boxed dialog, so a README renders **open**, and the fold that the original decision's option (b) called for no longer exists. What replaced the fold is a bounded band — the rendered body scrolls within `minHeight: 120` / `maxHeight: 360` so a long manifest cannot push the wiring blocks off the page.

The block is now contributed as a section descriptor `{ id: 'description', title, hint, action, body }`, split across two components that share one `useDescriptionEditor` hook: `DescriptionActions` (the heading's right-aligned control — pencil, or Save/Cancel + byte counter while editing) and `DescriptionBody` (markdown, or a textarea over the raw markdown). A lens's **Note** is the same pair against `noteEditor`. The pencil moved into the heading because a bounded scroller reserves a flex sibling's column for its whole height — see `kb/decisions/ui/manage-page/block-affordance-in-heading/b9176d5e.md`.

**The kb.md → README.md rename (PR #68).** Clean break, no legacy fallback: nothing reads `kb.md`, and an unmigrated repo shows an empty description block until the file is renamed by hand. See `kb/decisions/repos/kb-repo-layout/readme-clean-break/b534400d.md` for why this move is deliberately asymmetric with the ontology's `.domains/` move, which DOES keep a read fallback. Writes go through `store.WriteRootFile` rather than the fact-write path, because `factIndex.writeFile` lowercases every path — a fact-path rule that never mattered for `kb.md` but would have committed `readme.md`.

**LICENSE — NO LONGER read-only.** PR #68 added `LICENSE` on this SAME endpoint and with the same scoping — single-repo GET only, omitted when absent — and originally shipped read-only, rendered as PREFORMATTED text rather than markdown (a markdown renderer reflows a licence's newlines away). A LATER decision (`kb/decisions/repos/kb-repo-layout/license-write-path/401a296b.md`) gave it a write path mirroring README's: `WriteLicense`/`patchRepoRequest.License`, same 64 KiB cap now enforced as an INPUT check too, same skip-on-byte-identical. The UI (`RepoManager.tsx`) reuses `useDescriptionEditor`/`DescriptionActions`/`DescriptionBody` for the license editor — with parameterised testids (`testIdPrefix`, `containerTestId`/`textareaTestId`) so the license block doesn't collide with the description block's — but the READ view stays `<pre data-testid="repo-license">`, never the markdown branch `DescriptionBody` uses for description/note. See `kb/decisions/repos/kb-repo-layout/license-read-only/2b569af1.md` for the now-superseded original read-only decision and its still-true rendering rule.

**Why both files sit at the TREE ROOT, not under `kb/`:** anything under the ontology root with an ordinary name is a fact by location — see `kb/invariants/store/indexing/ontology-root-scope/1b35d56b.md`. Indexing the manifest as a fact is exactly the bug that invariant exists to prevent.
