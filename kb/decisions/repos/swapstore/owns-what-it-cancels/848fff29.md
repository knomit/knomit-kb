# Decided (user, 2026-10-02; issue #400): SwapStore is NOT teardown — it may still cancel the initial heal, but must then start the repo's lifetime components (dispatcher, merger, sweep) if activate() never ran; the post-swap rebuild marks the index state; a failed swap restarts the sync it stopped

Problem (verified at b6f71ded): Manager.SwapStore cancels indexCtx (ebd96069 classified it as 'real teardown' with shutdown/Close so the heal drains before the old DB closes). openOne's heal goroutine returns on indexCtx.Err() WITHOUT b.activate() and WITHOUT markIndexReady/Failed — correct for teardown (repo going away), wrong for SwapStore (repo stays live and observed). activate() has only two call sites, both in openOne, so a skipped activation is permanent for the process. Result when the origin-session commit (the only production SwapStore caller, disjoint-history branch, handlers_origin_session.go:976) lands during an initial heal: index state pinned at 'indexing' (the handler's inline Rebuild builds a correct index but marks nothing), handleStartRebuild 409s 'Index is busy' so the UI cannot recover, and the trigger dispatcher, consensus merger and experiment sweep never start. The reconcile loop IS restarted by the handler's ActivateSync. Second form: on a SwapStore error the handler returns before ActivateSync, so the sync loop SwapStore cancelled stays dead.

Options considered:
(1) SwapStore waits for the heal instead of cancelling — rejected: blocks the wizard for minutes on large repos, and the heal's work lands on a store about to be discarded.
(2) The heal's cancelled exit distinguishes swap from teardown and calls activate() — rejected: activate()'s first half (ensureLocalUpstream, recoverFromOrigin, startSyncLoops(b.syncCtx)) is bound to the build-time store and the just-cancelled syncCtx; it would do work (possibly network) against the discarded store while SwapStore waits on indexWg.
(3) SwapStore owns what it cancels — CHOSEN.

Choice: (a) activate() records an 'activated' flag on the RepoInstance; dispatcher/merger/sweep start become idempotent. (b) After the new store is attached, if not activated, SwapStore starts dispatcher, merger and sweep (they reach the store via Acquire, so they are swap-safe). It does NOT run the store-bound half; starting sync remains the caller's contract (documented on SwapStore). (c) The origin-session handler brackets its post-swap Rebuild with MarkIndexRebuildStart/MarkIndexRebuildDone — single-writer holds because SwapStore has already drained the heal. (d) On SwapStore error the handler restarts the previous sync mode (ActivateSync with the prior origin, else StartLocalSync) before reporting. (e) Regression test via the index heal gate: hold heal, SwapStore, release, assert state leaves 'indexing' and the three components run.

Non-scope: does not change teardown (shutdown/Close still cancel the heal and skip activation). Does not fix ActivateSync's initial-reconcile failure leaving no loop, nor handleStartRebuild's 409 turning any stuck 'indexing' into an unrecoverable UI state — tracked separately.
