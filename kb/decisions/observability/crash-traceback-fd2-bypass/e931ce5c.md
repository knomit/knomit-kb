# Runtime/CGO fatal tracebacks bypass zerolog (write straight to fd 2); persist via GOTRACEBACK=crash + opt-in fd-2 redirect

**The gotcha:** The Go runtime writes its fatal traceback — and a CGO/ONNX SIGSEGV traceback — DIRECTLY to file descriptor 2, bypassing zerolog and the lumberjack file sink entirely. A Go `recover()` cannot catch a C-level SIGSEGV either. Since ONNX native embedding inference runs on essentially every fact write, an ONNX crash is the most probable hard-down failure and would otherwise leave NO trace in the configured log file.

**The choice:** (1) `debug.SetTraceback("crash")` in `main` so unrecovered panics and runtime-fatal/CGO crashes dump all goroutines to fd 2 and abort into a core where the OS permits. (2) An OPT-IN fd-2 redirect, `crashdump.RedirectStderr` (gated by `KNOMIT_CRASH_LOG`/`[log].crash_file`), points fd 2 at an append-only file so those tracebacks persist WITHOUT the launcher needing `2>>file`. Implemented with stdlib `syscall.Dup3` on Linux (all arches; `Dup2` is absent on linux/arm64) and `syscall.Dup2` on darwin, build-tagged; cross-compiles linux amd64+arm64.

**Daemon layout that falls out of this:** fd 1 = structured JSON logs (stdout/lumberjack), fd 2 = crash file → the two never interleave because zerolog writes fd 1 and the runtime writes fd 2. Redirecting fd 2 also redirects anything writing to `os.Stderr` (the ConsoleWriter), so it is daemon-only; in containers leave it OFF (the log driver already captures fd 2). The Go-panic class is additionally covered by `crashdump.Guard` writing a JSON bundle then re-panicking.
