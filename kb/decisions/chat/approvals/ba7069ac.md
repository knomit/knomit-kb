# A chat's session grant on knomit_learn also covers deletions made through learn's retract argument: the grant key is (pin, tool, action), learn with a retract is the action learn, and the user decided on 2026-11-04 not to split it

Decision (user, 2026-11-04, taken at PR5 review): chat.Decide keys a session grant on (binding pin, tool, action). mcp.ClassifyCall gives knomit_learn the single action learn whatever its arguments. knomit_learn accepts a retract argument (the atomic move: write facts and retract paths in one commit), so after the person chooses 'Allow for session' on a knomit_learn call into repo A, later knomit_learn calls into A run without a prompt even when they retract (delete) facts through that argument.

Options considered: (a) leave learn as one action; (b) classify a learn call with a non-empty retract as its own action (for example move), so a grant for plain learn never covers deletion. The user chose (a). No code changed.

MISREADING TO AVOID: 'a learn grant never deletes' is FALSE. What still asks: a separate knomit_retract call (its own tool and a destructive row), a review answer or takeover, an experiment rollback, and every call into a different repo or lens. The approval card for a learn call shows the tool, the action learn and the arguments, so the person can see a retract in the call they grant from, but a LATER learn call is covered without being shown again.

Consequence: anyone changing the grant key or the classification table must keep this in mind: splitting learn-with-retract into its own action is a behaviour change that needs a new decision, not a bug fix.
