# An adaptive chat always has knomit_bind and knomit_query in its window (mcp.ChatCoreTools): loaded from the opening, never evicted, never a preload pick, still listed in the catalogue, chosen because a 4B model did not call load_tools in the live run

Live acceptance: on turn 3 the preload missed knomit_query and the model never called load_tools (0 calls in three runs), so it looped on knomit_bind. The window now takes ToolWindowSpec.Core: those catalogue tools are loaded by NewToolWindow, skipped by evictOrder (not by pressure, not to make room for a load), skipped by Preload (it only loads what is not loaded, so they are not picks and not PreloadHits), and a call to one goes to the host (Handles is false). A core name the principal was not shown is ignored. The chat's list is mcp.ChatCoreTools = knomit_bind, knomit_query: the two tools nearly every turn needs; the justification and the list are policy, not usage data. Every other tool stays adaptive (preload plus load_tools); the catalogue in the loader description still lists all tools, core included.

Measured on the real tools, system prompt and server instructions of a writer against a 32K model (U = 24576, P = U/8 = 3072): the opening is 8181 tokens (33.3% of U): tools hook 2577 (core 2183, loader with catalogue about 394), system 282, instructions 5264. The core set costs 2183, under P at 32K ONLY: at 16K, P is 1536 (default reserve) or 1024 (MaxOutput 8192), and the core is not under it. The measurement is a bytes/4 estimate of this build, not a property of the code (the test asserts only under half of U).

The page shows the core tools from the first turn: openWindow calls Window.Observe on the builder's snapshot so the first user item says 2 loaded with their size, with no tools event (the opening is not a change). Does NOT mean the model is told the other tools are loaded: the catalogue still says they are not. A static chat (Anthropic, adaptive_tools off) has no window and no core.

UPDATE (PR 5 v3, stubs). The core is no longer the only way a tool is reachable: every other catalogue tool is in the first request as a stub (7d36bd78), because the live re-test showed the 4B model still never called load_tools (S4 failed, knomit_learn unreachable). The loader's catalogue is now the names only. The opening is therefore core in full PLUS the stubs: on the real writer tools the stubs of the 11 non-core tools cost 468 tokens, the tools hook 2866 (loader, core 2183, stubs), and the whole opening 8470 tokens (system 282, instructions 5264). That is 34.5 percent of U at 32K (U = 24576). The earlier 8181 figure and the claim 'core 2183 under P' were 32K-only and counted neither stubs nor a small window.

CORRECTED FIT CHECK (review N1). openWindow no longer checks only that the tool names fit P. It refuses a chat at open, with the approved C7 sentence, when the projected opening (loader, core in full, a stub per other tool, system prompt, instructions) is more than U minus P (P = U/8, kept free for the first guess and the message). 16K CAVEAT: at 16K with the default reserve (4096, U = 12288) the 8470-token opening fits (68.9 percent); at 16K with an explicit MaxOutput of 8192 (U = 8192) the opening alone exceeds U and the chat is refused at open instead of failing on its first turn. The core is unevictable, so in a small window the history is what grows; a window whose U is under about 9700 (opening plus P for this toolset) cannot open an adaptive chat. These sizes are bytes/4 estimates of this build, not properties of the code.
