# An adaptive chat always has knomit_bind and knomit_query in its window (mcp.ChatCoreTools): loaded from the opening, never evicted, never a preload pick, still listed in the catalogue, chosen because a 4B model did not call load_tools in the live run

Live acceptance: on turn 3 the preload missed knomit_query and the model never called load_tools (0 calls in three runs), so it looped on knomit_bind. The window now takes ToolWindowSpec.Core: those catalogue tools are loaded by NewToolWindow, skipped by evictOrder (not by pressure, not to make room for a load), skipped by Preload (it only loads what is not loaded, so they are not picks and not PreloadHits), and a call to one goes to the host (Handles is false). A core name the principal was not shown is ignored. The chat's list is mcp.ChatCoreTools = knomit_bind, knomit_query: the two tools nearly every turn needs; the justification and the list are policy, not usage data. Every other tool stays adaptive (preload plus load_tools); the catalogue in the loader description still lists all tools, core included.

Measured on the real tools, system prompt and server instructions of a writer against a 32K model (U = 24576, P = U/8 = 3072): the opening is 8181 tokens (33.3% of U): tools hook 2577 (core 2183, loader with catalogue about 394), system 282, instructions 5264. The core set costs 2183, under P. The measurement is a bytes/4 estimate of this build, not a property of the code (the test asserts only under half of U).

The page shows the core tools from the first turn: openWindow calls Window.Observe on the builder's snapshot so the first user item says 2 loaded with their size, with no tools event (the opening is not a change). Does NOT mean the model is told the other tools are loaded: the catalogue still says they are not. A static chat (Anthropic, adaptive_tools off) has no window and no core.
