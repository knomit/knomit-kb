# An adaptive chat sends every catalogue tool that is not loaded as a stub (real name, approved one-line purpose, permissive schema) because a 4B model never calls load_tools; a call to a stub is not run, loads the tool and is answered with NotLoadedCallResult

WHY. The live re-test of PR 5 v2 passed S1 (12 of 12 turns at 32K) and failed S4: the 4B model never called load_tools in 8 runs, so knomit_learn was never in its tool set and no learn approval card appeared; it said it would use knomit_learn and re-called knomit_bind instead. A tool the model must load first is a tool it never uses, and the core set (ed942141) cannot hold every tool. So the model must SEE every tool.

WHAT. For an adaptive provider (Loop.Window != nil), ToolWindow.Project sends hook 1 as: the loader (load_tools), every loaded tool (core, preloaded or loaded by the model) with its full definition, and for every other catalogue tool a STUB: the real tool name, the approved one-line purpose from mcp toolPurposes as its description (a tool with no row, a script tool, gets the first sentence of its own description capped at 160 bytes, so no new copy is written), and the schema {"additionalProperties":true,"properties":{},"type":"object"} (no required field; Ollama parses parameters into type/required/properties and ignores the rest, llama.cpp compiles any JSON schema; NOT exercised against a live server in this change). A call to a stub takes the existing not-loaded path (ToolWindow.runStale): the call is NOT run, is never offered to the approval gate, loads the tool, and is answered with NotLoadedCallResult; the next request carries the full definition, and the model's second call is an ordinary loaded-tool call that reaches CallGate.Decide (a card for a write) and runs only after Allow. Same-batch rules are unchanged: a stub call in the batch of a load of the same tool is not run either. Pairing holds because every stub call is answered. The Builder still holds only full definitions; the stub is a view made by Project. Anthropic has no Window and is untouched.

EVICTION. Evicting a loaded tool turns it back into a stub, it does not remove it. Free room is measured on a view that already carries every stub, so loading a tool costs its GROWTH (full definition less its stub, ToolWindow.growth), eviction frees the growth, and Preload counts growth too.

LOADER. load_tools stays. Its description now carries the tool NAMES only (mcp.BuildNameCatalogue), not the name-and-purpose lines: the purposes are in the stubs, and the loader keeps the list of valid names its names argument takes. On the real writer toolset the names-only catalogue is 218 bytes against 939 for the lines, about 180 tokens saved, with nothing lost because each purpose is one stub away. The name-and-purpose line builder (mcp.BuildCatalogue) no longer exists: the purposes live only in mcp.StubPurposes.

COST (bytes/4 estimates of this build on the real writer tools, a measurement of this build and not a property of the code). The stubs of the 11 non-core tools cost 468 tokens (about 43 each); the loader, core (2183) and stubs make a tools hook of 2866; with the system prompt (282) and the repo instructions (5264, which dominate) the opening is 8470 tokens. At 32K (reserve 8192, U = 24576, P = 3072) that is 34.5 percent of U. At 16K with the default reserve (a quarter, 4096; U = 12288, P = 1536) it is 68.9 percent and the chat opens. At 16K with an explicit MaxOutput of 8192 (U = 8192) the opening alone is more than U, so that chat is refused at open (review N1). The test bounds are only: stubs under a tenth of U at 32K, opening under half of U at 32K.

OPENING CHECK. openWindow refuses a chat at open, with the approved C7 sentence (OpeningTooBigAdaptiveMessage), when the projected opening (loader, core in full, a stub per other tool, system prompt, repo instructions) is more than U minus P; the figure shown as needed is opening plus P. P (U/8) is a policy fraction kept free for the first guess and the first message, not a measurement. The check counts the core AND the stubs; the earlier check counted only the tool names. The names-only catalogue still has to fit P (CatalogueTooBigError).

Does NOT mean: a stub is callable (it is never run; its schema constrains nothing because its arguments are never used); loading a tool by calling its stub approves anything (14f7949c); the model is told the stubs are stubs (the first call teaches it through NotLoadedCallResult, approved copy). The C7 sentence still says 'the tool catalogue' for what is now the loader plus stubs; the wording is the user's and is unchanged. Consequence for a reader: do not re-add purposes to the loader's catalogue, and do not estimate a load as the full definition size, it is the growth.

Stub-call bookkeeping in Loop.runCalls: an identical stub call already answered in the same response is answered with AlreadyLoadedResult instead of a second NotLoadedCallResult, and a stub call neither extends nor breaks the repeat-failure streak (the tool is loaded and the call is to be made again).
