# A {body} resolution is a FACT WRITE and goes through the whole update chain in ONE shared function both MCP and REST call — and what lands is SerializeFact's output, never the caller's bytes

**Options considered:** (a) validate at each surface; (b) validate in the store's merge; (c) one shared `internal/resolutions.Normalize` that both doors call and neither surface duplicates.

**Rationale.** (b) is impossible: the merge sees bytes and has no ontology. (a) is what shipped for review and was wrong in both directions at once — REST validated NOTHING (accepting prose with no frontmatter, and the empty-`# `-title shape that gotchas/mcp/learn/empty-title-unvalidated records as invisible to query and repairable only by retract+relearn), while MCP ran `ParseFact` + `ValidateFact` only. That is the LENIENT half: `ParseFact` is the READ side and waves through malformed `kb://` and `src://` refs that `SerializeFact` rejects, and the refs gate — documented to cover EVERY write path — never ran at all. Two doors onto one action disagreeing about what is acceptable is the failure a shared function removes by construction.

**The choice:** `ParseFact -> ValidateFact -> refs.Gate.Apply -> SerializeFact`, in update.go's order, in one place.

**WHICH BYTES LAND: SerializeFact's output.** A raw body that differs from its own serialization — a canonicalized ref, a stripped motif, reordered frontmatter — would otherwise enter the tree in a form no write path produces, having skipped the gate that produces it. Same choice `knomit_update` makes.

**Local refs resolve against EITHER side of the merge**, because the merged tree holds both; checking only the parent would refuse a body citing a fact this very merge is bringing in.

**Non-scope:** the subject-motif gate is NOT a step here. `SerializeFact` applies it internally, so reaching SerializeFact IS being gated — copying the REST raw-editor PUT's explicit call into this path was surplus and tripped internal/fact's MN4 conformance test.
