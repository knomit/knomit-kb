# Knomit experiments are serialized per MCP session: subagents of one Claude Code session never open, commit or roll back an experiment while another subagent's is live; the coordinator gates knomit writes

CONTEXT (2026-10-01): two subagents of one Claude Code session wanted parallel knomit experiments, for #384 and #375.

MECHANISM (verified at origin/dev 68ba3853):
- On a URL-scoped bridge (--repo/--lens in .mcp.json) the open experiment is stored per (Mcp-Session-Id, mount_uid) in mount_experiments. SetMountExperiment is INSERT ... ON CONFLICT(session_id, mount_uid) DO UPDATE, so a second `open` silently SWITCHES every agent on that connection to the new experiment.
- Commit and rollback both call clearMountExperiment, which clears it for every agent on that connection, whichever experiment they believed they were in.
- Write tools take no experiment argument; the destination is read off the binding (describeWriteDestination).
- (SUPERSEDED by PR #664, 2026-10-27: at the time of this decision knomit_bind failed on a URL-scoped endpoint, so no per-agent handle was available there. Now it works on a default-branch scoped endpoint and changes only the branch: each agent can bind its own handle on the same --repo/--lens connection. See kb/decisions/mcp/session-binding/scoped-endpoint-bind.)
- `open` on an existing name RESUMES it without error (store OpenExperiment returns the existing record), so switching back is safe.
- Only an UNSCOPED bridge (neither --repo nor --lens) gives per-agent isolation: knomit_bind returns a fresh handle per call and every tool takes `binding` per call.

OPTIONS:
(1) Serialize experiments: code work runs in parallel, but only one agent writes knomit facts at a time. Switching experiments is safe while the others are idle, because open-by-name resumes.
(2) Add an unscoped bridge entry to .mcp.json and give each agent its own binding handle.
(3) Run a separate Claude Code session per parallel issue.

CHOICE (user, 2026-10-01): (1), for now. It was used successfully: #375's experiment was opened, committed and switched back while #384's stayed open. (2) is worth revisiting if parallel experiments become routine; (3) was not needed.

CONSEQUENCE FOR AGENTS: subagents of one session must never open, commit or roll back an experiment while another subagent's experiment is live. The coordinator gates knomit writes: one writer at a time, and the coordinator re-opens (by name) the experiment a writer needs before handing over.

NON-SCOPE: this does not forbid parallel CODE work or parallel read-only subagents (reviewers); it constrains only experiment open/commit/rollback and fact writes on one shared URL-scoped connection. It does not apply to separately started Claude Code sessions (own Mcp-Session-Id) or to an unscoped bridge with per-agent bindings. Related policy: kb/meta/methodology/multi-agent/knomit-binding/b8a4802a.md, which states the one-writer rule; this fact records the mechanism and the options weighed.

RE-VERIFIED at origin/dev b352cb79 (2026-10-20): the session holds ONE current experiment per (session_id, mount_uid): SetMountExperiment (internal/foundation/clientsessions/bindings.go) is the same upsert; knomit_experiment's actions are only list, open, commit, rollback, sync (internal/edge/mcp/experiment.go), and only commit and rollback call clearMountExperiment, so nothing but those two puts the session back on the agent branch.

PRACTICAL CONSEQUENCES for an agent that writes facts: (1) before EACH batch of writes, re-open your own experiment by name (open resumes, it is safe and cheap) because any other agent's open, commit or rollback on the same connection may have moved or cleared the shared session since your last call, and a learn or update lands wherever the session currently points; (2) never run two experiment-writing agents concurrently on one connection; (3) to READ another experiment's facts you must switch the shared session onto it with open, and switch back afterwards, so a reader is a writer for coordination purposes; (4) the call that follows a commit or rollback lands on the agent branch.

WHAT THIS DOES NOT MEAN: experiments do not fork from each other. Every experiment forks from the agent branch (parent in `list`), so opening B while inside A does not carry A's facts into B and does not make B depend on A; two open experiments that edit the same fact only collide at commit time, which refuses and names the paths.

UPDATE 2026-10-27 (PR #664): option (2) no longer needs a second, unscoped bridge entry. On a --repo/--lens bridge each agent calls knomit_bind and passes its handle; handle-routed calls ignore the connection's session-keyed experiment, so the serialization rule above is needed only for agents that pass no handle. The mechanism paragraphs describe the handle-less path and remain accurate for it.

UPDATE 2026-10-29 (#685, PR #686): the MECHANISM paragraphs above are now HISTORICAL. A URL-scoped connection no longer has a session-keyed experiment at all: `open` without a handle returns a new handle inside the experiment and leaves the connection default on the agent branch; commit/rollback/sync need `name` or a handle and are refused with neither; mount_experiments is unused. So a second `open` can no longer switch other agents, and an unnamed rollback can no longer destroy someone else's experiment. The serialization rule is no longer needed for isolation: each agent keeps the handle its own `open` returned (or binds one) and passes it on every call. Calls without `binding` always land on the agent branch, so an agent that forgets its handle writes outside the PR gate; the rule is now "always pass your handle", not "one writer at a time" (kb/invariants/mcp/session-binding/scoped-default-never-moves).
