# Experiment commit merges into its RECORDED PARENT (equal to the agent branch whenever an owner is recorded) and DELETES the experiment on success; a conflict is settled by the repo's `conflicts` setting when it is on (read at the consensus branch's tip, parent = consensus side) and otherwise REFUSES, changes nothing, and returns per path the three commits to read; the retry passes `resolutions {path: ours|theirs|{body}}` applied inside the SAME merge ("ours" = the experiment, the reverse of git), overlaid per path on the setting; sync is catch-up only, never the exit; rollback also clears an orphan ref

**Options considered:** (a) merge-back with experiment-wins (auto-resolve); (b) refuse on conflict, agent resolves by rolling back only; (c) refuse on conflict PLUS a `sync` primitive (agent-branch-wins merge INTO the experiment) as the exit, after which the agent re-applies its edit; (d) refuse on conflict and accept per-path RESOLUTIONS on the retry, applied inside the same three-way merge (chosen 2026-09-21, PR #239); also (e) merge keeps the experiment branch vs (f) merge deletes it.

**Rationale:** The agent branch keeps moving while an experiment is open, so experiment-wins would clobber a peer's update silently. Refuse-alone is a trap: the merge base is the fork point, so any path edited on both sides stays in conflict whatever the agent writes next. (c) was the first answer and was withdrawn: sync overwrites the experiment's version of exactly the flagged paths before the agent has read it, so "re-apply your edit" is unactionable (the user rejected that instruction as such) and the operation is two-phase. (d) keeps one atomic branch merge and lets the resolver decide per conflicting fact with all three versions in hand; it is the same mechanism a UI would use, so the surfaces cannot drift. Merge-then-delete is transaction semantics. No archive of dropped experiments (designer call left open). The user also ruled: NO merge UI, no Sync in the UI, and NO record of any kind (decision, meta observation) of a merge-time conflict resolution — conflicts leave no trace beyond the merge commit.

**The choice:** `commit` = mergeIntoBranch(exp → recorded parent, StrategyRefuse with an explicit `resolutions` input) under the parent's lock, then teardown (ref, branch tables, experiments row, name-keyed pipeline_watermarks and meta rows). On conflict the refusal carries, per path, the merge BASE commit (the actual `MergeBase(dst, src)`, NOT experiments.fork_commit, which diverges after a sync), the experiment head and the parent head, or "NO BASE VERSION" for a dual-add; the agent reads them with knomit_explain at those commits. Retry: `resolutions {<path>: "ours" | "theirs" | {body}}` — "ours" is the EXPERIMENT (the merge SOURCE), the opposite of git's convention; "ours" on the Delete arm is absence. Every conflicting path without a resolution still refuses (by construction inside every merge arm, never by falling through to a default); a resolution for a non-conflicting path is refused and named, checked up front so it is also reachable on the noop and fast-forward returns; a NEW conflict after the parent moved is listed alone; resolving everything to the parent's side yields ModeNoop with no merge commit and the summary says so. A `{body}` goes through internal/resolutions.Normalize — the FULL update chain (ParseFact → ValidateFact → refs gate → SerializeFact) shared by the MCP and REST surfaces — and what lands is SerializeFact's bytes, not the caller's. Auto vs interactive resolution is agent behaviour described in the tool and the skill, not a tool flag. `sync` = mergeIntoBranch(parent → exp, StrategyRemoteWins; the parent is src on that direction) remains for plain catch-up only and is never the first move after a refusal. Commit and sync compare the recorded parent to AgentBranchOwner() and refuse on mismatch; an EMPTY owner is UNKNOWN, not a mismatch. `rollback` deletes, is never gated by the parent check, and also clears an orphan `exp/<name>` ref that has no experiments row; `open` REFUSES such an orphan rather than adopting it. The mechanics (refuse strategy's dual-add strictness, empty-owner rule, the orphan shape rollback cannot clear, the resolutions design) are in their own facts, cited below; this fact records WHY the lifecycle has this shape.

**Non-scope:** does not change steady-state origin reconcile (still StrategyLocalWins at its single call site) and does not add ancestry checks or GC for experiments beyond the expiry sweeper.

UPDATE (#412, merge 55a47911, 2026-10-03): THE REPO'S `conflicts` SETTING NOW APPLIES TO THE COMMIT. The user ruled (2026-10-02, verbatim): "6) agreed, experiment merging should honor the repo configuration." Before, every first-mission experiment merge ran `(refuse)` even in a `conflicts: merge` repo.
- WHERE IT IS READ: the tip of the consensus branch (`rh.consensusBranch` = Service.UpstreamBranch, the function hostConflictStrategy uses), NEVER the experiment's or the parent's own ontology — an experiment cannot vote itself a merge policy (TestCommitExperiment_SettingReadAtTheConsensusBranchOnly).
- With it on: the parent is the consensus side (factConsensus = dst), an `off` key falls back to Refuse, so whatever the setting leaves is refused with the three-commit guide as before. With no setting, or both keys off, the commit is plain StrategyRefuse.
- CONSEQUENCE: under `consensus: auto` an absent `conflicts` reads facts: merge / state: consensus, so every auto repo now FIELD-MERGES experiment commits by default.
- Caller `resolutions` are OVERLAID on the setting per path (`mergeOpts.overlayResolutions`, set ONLY by CommitExperiment; every other site still refuses resolutions alongside a `conflicts:` strategy). A retry that names only the paths the refusal listed therefore keeps the setting for the rest. A caller side resolution is recorded `Knomit-Conflict … reason=chosen`.
- The result's `Settled []SettledPath` (from the merge commit's Knomit-Merge/Knomit-Conflict lines) and the MCP summary name each settled path and say when the experiment's version was DROPPED.
WHAT THIS DOES NOT MEAN: "commit never refuses any more" — it still refuses whatever an off key leaves, and every conflict in a repo without the setting.
