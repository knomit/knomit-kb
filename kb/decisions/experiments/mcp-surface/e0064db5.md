# Experiments get their own knomit_experiment tool (not folded into knomit_bind) and the active experiment rides on the BINDING HANDLE, never on the MCP session id; URL-scoped bridges carry it in the URL and knomit_bind {experiment} only RESUMES

**Options considered:** (a) fold start/commit/rollback into `knomit_bind` (the user's first preference: fewer tools); (b) a dedicated `knomit_experiment {list|open|commit|rollback|sync}` tool; for WHERE the active experiment lives: (c) per MCP client session, keyed (Mcp-Session-Id, write repo uid) in client_sessions — the master's first plan; (d) on the binding handle (a sibling table handle_experiments keyed by handle); (e) an `experiment:` argument on every write tool.

**Rationale:** (a) fails the requirement "experiments are for everyone": `knomit_bind` is refused on URL-scoped mounts (`--repo`, `--lens` bridges) by design, so folding lifecycle into it would exclude those bridges. (c) is the design the 2026-09-17 cross-binding incident removed: two jobs on one connection share a session id, so session-keyed state serves whichever bound LAST; here it would be worse because both branches share an ontology, so a misrouted learn looks like a success; and "nothing in client_sessions may gate". (e) relocates the destination into tool arguments the way a `repo:` argument would, and an agent that forgets it silently writes to the agent branch. (d) keys on the one thing that already distinguishes two logical callers on one connection. A column on binding_handles was impossible: the control migration chain is replayed as one script and admits only CREATE ... IF NOT EXISTS, never ALTER TABLE, so it is a sibling table.

**The choice:** `knomit_experiment` with actions list/open/commit/rollback/sync on all three mounts. On the unscoped mount, `open` records the experiment on the caller's handle; ResolveSessionBinding reads it and builds the binding at `exp/<name>` (repo pin) or re-pins only the write member (lens pin); commit/rollback clear that handle eagerly and every other handle heals LAZILY on next resolution when the experiment no longer exists or fails eligibility (covers the sweeper, REST/UI rollback, another session committing a shared experiment), and the tool result says so; sync does not clear. A handle carrying both a branch pin and an experiment is UNREPRESENTABLE (refused at write and at read), not ranked. On URL-scoped mounts the experiment is in the URL — `/repos/{repo}/branches/exp:<name>/mcp` and the new `/lenses/{lens}/experiments/{name}/mcp` — with no per-session state anywhere; `open` there creates the experiment and RETURNS THE URL to reconnect on, stating that the live session is not inside it. `knomit_bind` gains an optional `experiment: <name>` that resumes an EXISTING experiment only (unknown name → error naming knomit_experiment open); creation stays in the tool. knomit_repos marks the active experiment by name only.

**Non-scope:** does not add per-handle branch switching in general (binding_handles.branch stays inert), and does not make a handle survive a reconnect — a fresh bind is on the agent branch, re-entry is one call. This fact is the EXPERIMENT decision; the handle model itself and the tool catalogue are described by their own facts.
