# `expires` is a plain frontmatter date, searchable and filterable, that knomit NEVER acts on — the F03 design's automation (reconcile-tick signal collection, due seeds via pipeline_watermarks, type-keyed hiding) was rejected by the user

Options considered (F03, 2026-09-26):
1. The fleet design document's F03, and the worker's refined option B′ from the RCA: expired signals deleted by any instance on the reconcile tick (with a new `expire` commit op and signal immutability); due hypotheses and other epistemic facts fed once into review's seed set through a `due_until` column on pipeline_watermarks; expired facts hidden from default queries (all of them in the design, signals only in B′), with `include_expired` to see them.
2. `expires` as a plain optional frontmatter date on any fact, searchable and filterable through REST and MCP (`expired`, `expires_before`, `expires_after`), with an `expired` marker on results, and knomit never deleting, hiding or retracting anything because of it.

The choice: option 2 (built in PR #311, merged as d6926514).

Rationale (the user's): "keeping expired facts in the KB is the correct way; humans decide when to discard." Expiry is information for a reader, not a trigger for the system; a human or an agent searches (for example, all expired hypotheses) and decides to keep, update or retract. The automation would also have carried costs the RCA surfaced: hidden-but-kept hypotheses vanishing from readers, clock skew making the fastest collector delete fleet-wide early, extend-vs-collect modify/delete conflicts, and new pipeline state to keep consistent across forks.

Non-scope: this does not forbid a consumer (a skill, a future executor recipe, a human) from retracting expired facts it finds; it forbids knomit itself from doing so automatically. It does not introduce a default expiry: absent means never. It does not decide the fleet's later trigger mechanism (F07), which may still offer an explicit, declared action on expiry if the user asks for one.
