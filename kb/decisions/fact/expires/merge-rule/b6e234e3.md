# A merge never invents, inherits or pools an `expires`: learn's dedup merge and review's pairwise dedup keep the WINNER's own value; a prune merge writes a NEW fact carrying none and names every dropped member date in a warn; distill, reflect and discovery outputs inherit nothing

The rule (F03 ruling): a surviving fact keeps its OWN expires; a merge never invents, inherits, or drops one silently.

- knomit_learn dedup `mergeFacts`: `merged.Expires = winner.Expires` (type follows the winner too, so a hypothesis's settlement date never lands on an observation). When the EXISTING fact wins and the caller sent an explicit `expires`, it is NOT applied, and the learn result says so: `existing fact kept; expires not applied; set it with knomit_update on <path>` (expiresNotAppliedNotes).
- Review's pairwise dedup (dedupCluster) re-reads and re-serializes the winner file, so the winner keeps its own value by construction; the loser's is never taken.
- Prune merge (ApplyPruneDecisions): the LLM's output is written at a fresh UUID path (normalizeFactPath, #107a) and EVERY member is retracted in the same commit, so there is NO survivor. The merged fact carries no expires; memberExpiries reads the members before the commit and a warn progress event names each `<path> (expires <value>)` not carried. The dates remain in history with the retracted members.
- Distill, reflect-propose and discovery build NEW claims with fact.NewFact and inherit nothing from their inputs, which stay alive with their own dates.
- The store's three-way merge is blob-level and needs no rule; replay's resolveDeadRefs parses and re-serializes and keeps expires because fact.Fact carries it end to end.

WHAT THIS DOES NOT MEAN: it does not mean an incoming explicit expires is always honoured on learn — only when the incoming fact wins the dedup merge; otherwise use knomit_update. It does not mean a prune merge 'drops' dates silently: the warn is the audit.
