# Fact bodies may not carry `[[...]]` outside code: every write is judged on the RESULTING body, so a create with one is refused and an update of a fact that still holds one is refused, whatever it changes; refs are the only link channel; artifacts are exempt

**Decision (user, 2026-11-08).** Wiki-style `[[...]]` in a fact body is NOT rendered and is now refused on write. Reasons: (1) prompt injection — a body is free text that agents read, so an inline link notation becomes an instruction channel that bypasses the refs gate; (2) refs are the ONLY link channel: they are gated on write (a local ref must resolve), canonicalised, versioned and turned into graph edges, while a body `[[...]]` gets none of that; (3) nothing renders or resolves them (the forms are ambiguous: an 8-hex id, a kb/ path, a category, a bare slug — see the wikilinks gotcha in refs). Rendering was considered and rejected.

**Rule as built (branch fix/no-wikilinks-in-bodies; SHA ddd1a6dc is pre-merge and must be re-pinned at the merge).** fact.WikiLinks(body) finds, in PROSE only, a `[[` up to the first `]]` after it on the same line, with a non-blank inner; single brackets inside count (`[[the [x] fact]]`). A lone `[[` without `]]` on its line is ignored, and so is `[[  ]]`.
- Code is exempt; `[[oauth.client]]` (TOML) and `[[:space:]]` (regex) are legitimate there. Code means:
  - fenced blocks, ``` or ~~~, found AFTER stripping blockquote `>` and list markers (`-`, `*`, `+`, `1.`, `1)`), so a fence opened on `- ```toml` or `> ~~~` counts (review F2). A block closes on a run of the same character at least as long; an unclosed block runs to the end of the body;
  - indented blocks (4+ columns, a tab = 4) that do not continue a paragraph and are not inside a list item; an indented line inside a list is judged as prose (the strict direction);
  - inline code spans, a backtick run closed by a run of equal length within one paragraph, which a blank line, an ATX heading line or a fence ends. A backtick escaped by an odd run of backslashes does not OPEN a span; inside a span a backslash is literal, so an escaped-looking backtick can CLOSE one, as in CommonMark.
- This is NOT CheckFenceEdit's fence rule (fenceLines counts ``` lines only, any indentation and length, ignores ~~~ and list markers). Harmless: a line read as a fence here and not there can only hide text, so it can only make a body pass, never refuse one.
- Known limits, left as they are: HTML `<code>`/`<pre>` is prose; fullwidth brackets are not brackets; an unclosed fence hides the rest of a NEW body (CommonMark).
- A NEW body must hold none (fact.CheckWikiLinks): knomit_learn (facts only), REST POST /facts, and the review pipeline's distill (warn and skip), reflect propose (the whole apply fails) and discovery (warn and skip).
- An UPDATE is judged on the RESULTING body only, with no comparison to what the fact held (fact.CheckWikiLinksUpdate; its error adds "An update must leave no [[...]] outside code, including ones the fact already had."). User ruling (2026-11-08): "regardless if [[...]] was there or not, if someone tries to update that fact, force them to replace or remove [[..]]. Then get rid of the crappy counting crap". So: knomit_update runs it on EVERY update, a refs-only or confidence-only one included (a fact holding `[[x]]` cannot be updated at all until the update removes it); REST PUT runs it (a PUT that creates gets the create text); a prune merge's body must hold none, whatever its members held; an experiment commit's `{body}` resolution must hold none, whatever the fork, parent and experiment versions held (internal/corpus/resolutions normalizeOne, shared by knomit_experiment and REST; found by review F1); and a knomit_learn that dedup-merges into an existing fact is refused when the merged body holds one (the kept body may be the existing one).
- An earlier build on this branch had a "no more than before" count rule (CheckWikiLinkEdit, max over the merge versions). It was removed at the user's ruling above; do not reintroduce a before/after comparison.
- The roughly 226 existing facts that hold them (survey in the wikilinks gotcha) are left as they are: no cleanup job runs. Consequence: each is frozen against updates until someone's update removes its `[[...]]` or moves them to refs, the same latent-until-touched shape as legacy facts that fail an ontology validation (kb/gotchas/fact/validation/legacy-invalid-facts/f33a1b95.md).
- NOT checked, deliberately left as they were: the review pipeline's system rewrites of existing facts that do not author a body (a prune `update` that changes only confidence, a settle, reflect's reinforce appending a ref to transition facts, and the mechanical dedup merge). They are not someone updating the fact; refusing them would stall review over legacy bodies. This was reported to the user as an open question.
- Artifacts (artifacts/<area>/...) are exempt everywhere: they are a job's bookkeeping, not knowledge, and the crawl job's state files discuss `[[link]]` in prose. Triggers/scripts and the in-app chat reach the same MCP handlers, so they get the rule too.

**Scope of the guidance vs the enforcement (copy approved by the user, 2026-11-08).** The stated rule covers EVERY reference: another fact's path AND an external source such as a URL go in refs, never in the body text. Only `[[...]]` is ENFORCED. A bare URL in a body, or a `[text](url)` markdown link, is NOT refused: that part is guidance in the descriptions, not a gate.

**The rule is now in the server's own copy**, not only the Claude Code knomit-remember skill (commit 7847a228 put it only there). It is in the knomit_learn and knomit_update body field descriptions (shared const bodyLinkRule: "There is no link syntax in a body: every reference, whether another fact's path or an external source such as a URL, goes in refs."; the tests pin the approved strings byte for byte), the ops description, the "Writing Fact Bodies" section of the server instructions, the OpenAPI POST/PUT /facts docs, and both knomit-remember SKILL.md copies. The tool descriptions are part of the chat's cached prefix, so this shipped as one change: one cache break.

**Errors say what to send instead**: every reference, to another fact or to an external source, in refs; the fact's path in refs, a plain-text body, and code spans or fenced blocks to show `[[...]]` literally. They name each occurrence with its line number (up to three, then "and N more").

**What this does NOT mean.** It does not mean `[[...]]` is now a recognised syntax: the server still resolves nothing. It does not mean the existing ones are scheduled for removal: they stay until an update touches their fact, and then that update must remove them. Swapping one occurrence for another (`[[a]]` to `[[b]]`) is refused. `[text](path)` markdown links are NOT refused: they are stored as literal text and resolve to nothing. And the rule is not checked at git entry paths (receive-pack, verify): a fact pushed through git bypasses it, like the fence gate.
