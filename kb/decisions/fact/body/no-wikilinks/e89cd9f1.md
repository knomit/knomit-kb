# Fact bodies may not carry `[[...]]` outside code: a create with one in prose is refused, and an edit is refused only when it ADDS one (no more than the body already had); refs are the only link channel; artifacts are exempt

**Decision (user, 2026-11-08).** Wiki-style `[[...]]` in a fact body is NOT rendered and is now refused on write. Reasons: (1) prompt injection — a body is free text that agents read, so an inline link notation becomes an instruction channel that bypasses the refs gate; (2) refs are the ONLY link channel: they are gated on write (a local ref must resolve), canonicalised, versioned and turned into graph edges, while a body `[[...]]` gets none of that; (3) nothing renders or resolves them (the forms are ambiguous: an 8-hex id, a kb/ path, a category, a bare slug — see the wikilinks gotcha in refs). Rendering was considered and rejected.

**Rule as built (branch fix/no-wikilinks-in-bodies; SHA 87f15659 is pre-merge and must be re-pinned at the merge).** fact.WikiLinks(body) finds, in PROSE only, a `[[` up to the first `]]` after it on the same line, with a non-blank inner; single brackets inside count (`[[the [x] fact]]`). A lone `[[` without `]]` on its line is ignored, and so is `[[  ]]`.
- Code is exempt; `[[oauth.client]]` (TOML) and `[[:space:]]` (regex) are legitimate there. Code means:
  - fenced blocks, ``` or ~~~, found AFTER stripping blockquote `>` and list markers (`-`, `*`, `+`, `1.`, `1)`), so a fence opened on `- ```toml` or `> ~~~` counts (review F2). A block closes on a run of the same character at least as long; an unclosed block runs to the end of the body;
  - indented blocks (4+ columns, a tab = 4) that do not continue a paragraph and are not inside a list item; an indented line inside a list is judged as prose (the strict direction);
  - inline code spans, a backtick run closed by a run of equal length within one paragraph, which a blank line, an ATX heading line or a fence ends. A backtick escaped by an odd run of backslashes does not OPEN a span; inside a span a backslash is literal, so an escaped-looking backtick can CLOSE one, as in CommonMark.
- This is NOT CheckFenceEdit's fence rule (fenceLines counts ``` lines only, any indentation and length, ignores ~~~ and list markers). Harmless: a line read as a fence here and not there can only hide text, so it lowers the count.
- Known limits, left as they are: HTML `<code>`/`<pre>` is prose; fullwidth brackets are not brackets; an unclosed fence hides the rest of a NEW body (CommonMark).
- A NEW body must hold none (fact.CheckWikiLinks): knomit_learn (facts only), REST POST /facts, and the review pipeline's distill (warn and skip), reflect propose (the whole apply fails) and discovery (warn and skip).
- An EDIT may not hold MORE than the body it replaces (fact.CheckWikiLinkEdit, judged on the edit like CheckFenceEdit): knomit_update (updates.body and ops str_replace/append alike, only when the body changed), REST PUT (before = the stored body; a PUT that creates has none, so the create rule applies), prune merges (before = the members' bodies, snapshotted before the call's retracts), and an experiment commit's `{body}` resolutions (internal/corpus/resolutions normalizeOne, shared by knomit_experiment and REST; before = whichever of the fork, parent-tip and experiment-tip versions holds the most, in line with carriedRefs/carriedVersions; a path on none of them is a fresh body; added after review finding F1, since the package's contract is that a resolution bypasses no rule another write path enforces).
- Why "no more than before": roughly 226 existing facts written before the rule carry them (survey in the wikilinks gotcha). The user decided (2026-11-08) to leave them exactly as they are: no cleanup job runs. So they must stay editable, and an edit that keeps them passes. An edit that happens to remove some also passes, but nothing is expected to remove them.
- Artifacts (artifacts/<area>/...) are exempt everywhere: they are a job's bookkeeping, not knowledge, and the crawl job's state files discuss `[[link]]` in prose. Triggers/scripts and the in-app chat reach the same MCP handlers, so they get the rule too.

**Scope of the guidance vs the enforcement (copy approved by the user, 2026-11-08).** The stated rule covers EVERY reference: another fact's path AND an external source such as a URL go in refs, never in the body text. Only `[[...]]` is ENFORCED. A bare URL in a body, or a `[text](url)` markdown link, is NOT refused: that part is guidance in the descriptions, not a gate.

**The rule is now in the server's own copy**, not only the Claude Code knomit-remember skill (commit 7847a228 put it only there). It is in the knomit_learn and knomit_update body field descriptions (shared const bodyLinkRule: "There is no link syntax in a body: every reference, whether another fact's path or an external source such as a URL, goes in refs."; the tests pin the approved strings byte for byte), the ops description, the "Writing Fact Bodies" section of the server instructions, the OpenAPI POST/PUT /facts docs, and both knomit-remember SKILL.md copies. The tool descriptions are part of the chat's cached prefix, so this shipped as one change: one cache break.

**Errors say what to send instead**: every reference, to another fact or to an external source, in refs; the fact's path in refs, a plain-text body, and code spans or fenced blocks to show `[[...]]` literally. They name each occurrence with its line number (an edit names only the ADDED ones).

**What this does NOT mean.** It does not mean `[[...]]` is now a recognised syntax: the server still resolves nothing. It does not mean an edit must remove existing ones, or that they are scheduled for removal; an edit only must not add one. Swapping one occurrence for another (`[[a]]` to `[[b]]`) keeps the count and passes, which is accepted as the price of a count rule. `[text](path)` markdown links are NOT refused: they are stored as literal text and resolve to nothing. And the rule is not checked at git entry paths (receive-pack, verify): a fact pushed through git bypasses it, like the fence gate.
