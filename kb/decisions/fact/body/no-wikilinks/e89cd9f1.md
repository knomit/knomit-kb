# Fact bodies may not carry `[[...]]` outside code: a create with one in prose is refused, and an edit is refused only when it ADDS one (no more than the body already had); refs are the only link channel; artifacts are exempt

**Decision (user, 2026-11-08).** Wiki-style `[[...]]` in a fact body is NOT rendered and is now refused on write. Reasons: (1) prompt injection — a body is free text that agents read, so an inline link notation becomes an instruction channel that bypasses the refs gate; (2) refs are the ONLY link channel: they are gated on write (a local ref must resolve), canonicalised, versioned and turned into graph edges, while a body `[[...]]` gets none of that; (3) nothing renders or resolves them (the forms are ambiguous: an 8-hex id, a kb/ path, a category, a bare slug — see the wikilinks gotcha in refs). Rendering was considered and rejected.

**Rule as built (branch fix/no-wikilinks-in-bodies; SHA fb02a10e is pre-merge and must be re-pinned at the merge).** fact.WikiLinks(body) finds `[[x]]` with both halves on one line, no bracket inside and a non-blank inner, in PROSE only. A lone `[[` without `]]` is ignored, and so is `[[  ]]`.
- Code is exempt: fenced blocks (``` or ~~~, any indentation, closed by a run of the same character at least as long; an unclosed block runs to the end of the body) and inline code spans (a backtick run closed by a run of equal length within the same paragraph). `[[oauth.client]]` (TOML) and `[[:space:]]` (regex) are legitimate there.
- A NEW body must hold none (fact.CheckWikiLinks): knomit_learn (facts only), REST POST /facts, and the review pipeline's distill (warn and skip), reflect propose (the whole apply fails) and discovery (warn and skip).
- An EDIT may not hold MORE than the body it replaces (fact.CheckWikiLinkEdit, judged on the edit like CheckFenceEdit): knomit_update (updates.body and ops str_replace/append alike, only when the body changed), REST PUT (before = the stored body; a PUT that creates has none, so the create rule applies), and prune merges (before = the members' bodies, snapshotted before the call's retracts).
- Why "no more than before": about 240 facts written before the rule still carry them (survey in the wikilinks gotcha), and they must stay editable. A cleanup that removes them is allowed and is being done by a separate job.
- Artifacts (artifacts/<area>/...) are exempt everywhere: they are a job's bookkeeping, not knowledge, and the crawl job's state files discuss `[[link]]` in prose. Triggers/scripts and the in-app chat reach the same MCP handlers, so they get the rule too.

**The rule is now in the server's own copy**, not only the Claude Code knomit-remember skill (commit 7847a228 put it only there). It is in the knomit_learn and knomit_update body field descriptions (shared const bodyLinkRule), the ops description, the "Writing Fact Bodies" section of the server instructions, the OpenAPI POST/PUT /facts docs, and both knomit-remember SKILL.md copies. The tool descriptions are part of the chat's cached prefix, so this shipped as one change: one cache break.

**Errors say what to send instead**: the fact's path in refs, a plain-text body, and code spans or fenced blocks to show `[[...]]` literally. They name each occurrence with its line number (an edit names only the ADDED ones).

**What this does NOT mean.** It does not mean `[[...]]` is now a recognised syntax: the server still resolves nothing. It does not mean an edit must remove existing ones; it only must not add one. Swapping one occurrence for another (`[[a]]` to `[[b]]`) keeps the count and passes, which is accepted as the price of a count rule. `[text](path)` markdown links are NOT refused: they are stored as literal text and resolve to nothing. And the rule is not checked at git entry paths (receive-pack, verify): a fact pushed through git bypasses it, like the fence gate.
