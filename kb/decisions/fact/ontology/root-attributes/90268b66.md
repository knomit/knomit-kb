# The ontology has a ROOT `attributes:` block for repository-level settings (verify_signatures, verify_signers); a key in the wrong scope or a bad root value is a WARNING on the open path and FATAL only for a new ontology (ParseNewOntology)

`Ontology.Attributes` (yaml `attributes` at the document root) holds REPOSITORY-level settings. They do NOT inherit into topics and are not resolved by `Ontology.Attr` (that is the topic walk).

KEYS: `verify_signatures` is exactly "off", "log" or "enforce"; "off" is the absent value, and absent means off. `verify_signers` is a yaml LIST of authorized-key lines, each of type ssh-ed25519 (full keys, not fingerprints, because a git allowed_signers file needs the key). Both are registered in `attributeRegistry` with `scope: scopeRoot`. `learn_dedup` is `scopeTopic`.

STRICTNESS DEPENDS ON THE READER:
- Open path (`ParseOntology`, used by repos/builder.go, initialized.go, okf): a key in the wrong scope (a root key on a topic, a topic key at root) or a bad value for a ROOT key is a SeverityWarning with `Diagnostic.newOnly` set. The ontology still parses. Why: a parse failure on the open path makes the repo refuse every write (builder.go loadOntology), so a hand-edited typo must not brick an existing repo.
- Create path (`ParseNewOntology`, used by lifecycle.go resolveOntology for custom/initialize): any error OR any newOnly warning is refused, because a new ontology can still be fixed.
- A bad value for a TOPIC key (learn_dedup: maybe) stays FATAL everywhere, unchanged from F02.
- An UNKNOWN root key is a plain warning and is PRESERVED in the map, so Serialize writes back what a newer knomit wrote.

DOES NOT MEAN: that a misplaced or invalid verify key is silently "off". It is never read as a setting; F09's verifier treats an unreadable setting as UNKNOWN (keep the previous mode), never as off. And it does not mean the ontology became user-editable: the file is still immutable except by the preset refresh or a hand commit.
