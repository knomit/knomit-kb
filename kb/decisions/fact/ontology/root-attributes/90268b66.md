# The ontology has a ROOT `attributes:` block for repository-level settings (verify_signatures, and consensus since F08 PR B); a key in the wrong scope or a bad root value is a WARNING on the open path and FATAL only for a new ontology (ParseNewOntology)

`Ontology.Attributes` (yaml `attributes` at the document root) holds REPOSITORY-level settings. They do NOT inherit into topics and are not resolved by `Ontology.Attr` (that is the topic walk).

KEYS: `verify_signatures` is exactly "off", "log" or "enforce"; "off" is the absent value, and absent means off. It is registered in `attributeRegistry` with `scope: scopeRoot`; `learn_dedup` is `scopeTopic`. It is the ONLY verification setting in an ontology: who may sign comes from the fleet repository's member records (F09 PR 5), never from a KB's ontology. `verify_signers` was REMOVED (it never shipped): a dev-built ontology that still carries it has an UNKNOWN root key, a warning on open and on create, preserved but never read.

`consensus` (F08 PR B) is exactly "off" or "auto", absent = off, scope root. Its reader `fact.ReadConsensus` (read at the consensus branch's tip by the consensus merger) reads any OTHER value as off with one warning per blob, rather than as unknown-and-refusing like verify_signatures: off is the safe reading for consensus, so a later value (e.g. a recipe reference, ruling R5's future) is ignored by an older binary, never acted on.

STRICTNESS DEPENDS ON THE READER:
- Open path (`ParseOntology`, used by repos/builder.go, initialized.go, okf): a key in the wrong scope (a root key on a topic, a topic key at root) or a bad value for a ROOT key is a SeverityWarning with `Diagnostic.newOnly` set. The ontology still parses. Why: a parse failure on the open path makes the repo refuse every write (builder.go loadOntology), so a hand-edited typo must not brick an existing repo.
- Create path (`ParseNewOntology`, used by lifecycle.go resolveOntology for custom/initialize): any error OR any newOnly warning is refused, because a new ontology can still be fixed.
- A bad value for a TOPIC key (learn_dedup: maybe) stays FATAL everywhere, unchanged from F02.
- An UNKNOWN root key is a plain warning (open AND create) and is PRESERVED in the map, so Serialize writes back what a newer knomit wrote.

DOES NOT MEAN: that a misplaced or invalid verify key is silently "off". The acceptance gate (store.CheckRange) reads verify_signatures at main's tip through fact.ReadVerifySettings; an unknown value makes the gate fail to run (exit 2), never a pass. And it does not mean the ontology became user-editable: the file is still immutable except by the preset refresh or a hand commit.
