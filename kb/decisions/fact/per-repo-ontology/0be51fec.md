# Each repo loads its OWN ontology once, at the lifecycle machine's identify stage, from its READ branch (the agent branch when hosted, the upstream branch when subscribed) — Manager has no shared ontology, and the snapshot is what every write-time validation uses until the repo is re-identified; an ontology that changes on the consensus tip or arrives by sync is not seen

Each repo loads its own ontology from .knomit/ontology.yaml (legacy rungs .domains/ontology.yaml and domains/ontology.yaml still open) on its READ branch, once, at the lifecycle machine's identify stage, via RepoInstance.loadOntology (internal/repos/stages.go). It NEVER falls back to fact.DefaultOntology(): a missing, empty or unparsable ontology is an error, ri.Ontology() is nil and the repo opens readable but unwritable. The result is stored on the instance and exposed via ri.Ontology(). There is no shared/global ontology (Manager has none). The ontology is captured at identify time — if the ontology file changes in git after that, the in-memory ontology is stale until the repo is re-identified (remount).

HISTORY AND DETAIL (first written 2026-04 against the old repoBuilder; re-verified 2026-10-14 at origin/dev c9c599de). The sections below carry the detail:

- WHERE: `RepoInstance.loadOntology` (internal/repos/stages.go) runs inside `identifyStage.Enter`, after `ensureBranch`. There is no `repoBuilder` any more.
- WHICH BRANCH: it reads `r.ReadBranch()` — the agent branch for a hosted repo, the upstream (consensus) branch only for a subscription — walking `fact.OntologyPathsNewestFirst()` (`.knomit/ontology.yaml`, then `.domains/ontology.yaml`, then `domains/ontology.yaml`).
- NO FALLBACK: it NEVER substitutes `fact.DefaultOntology()`. A missing, empty or unparsable ontology is returned as an error, `ri.Ontology()` is nil and the repo opens readable but unwritable (the error is on GET /repos as `ontology_error`). A SYMLINKED ontology is the exception: since #444 (merge ec3406df) Identify refuses the repo, which is not mounted (kb/invariants/repos/ontology/symlinks/1ac1e8f3.md). Because the snapshot is taken only here, an ontology that becomes a symlink after open is not noticed until the next mount, which then refuses the repo. (The embedded-preset refresh in place, for a stored ontology that is a strict subset of its preset, is unchanged; a subscription never refreshes.)
- WHERE IT LIVES: an atomic `identity{ontology, ontologyErr}` on the instance; `identifyStage.Exit` forgets it. The only way the in-memory ontology changes is the identify stage running again (mount, remount, a lifecycle walk that re-enters it).

CONSEQUENCE: every ontology-dependent decision at write time — `ValidatePath`, per-topic `validations`, `ValidateContext`, `learn_dedup`, attributes — uses this snapshot. An ontology edit committed on main by a peer and carried in by sync, or one placed on the agent branch after open, changes nothing until the repo is re-identified; and a HOSTED repo validates against its agent branch's copy, not the consensus tip's. Readers of "the ontology is read at the consensus branch" (said of `consensus`/`conflicts` root attributes, which the sync code re-reads per merge) must not generalise it to the validation ontology.

UPDATE (PR #520, verified at merge commit 1a6c03f7): Identify now ALSO decides, right after loadOntology reads the snapshot, whether a fleet-id ontology may be mounted (admitFleetOntology): only with the fleet door, which at boot belongs to the repo recorded in control.db instance_fleet_repo. CONSEQUENCE of the snapshot rule: a repo whose upstream switches its ontology id to `fleet` and receives it by sync is NOT noticed until the next re-identify (restart or remount); at that point it is refused and listed unavailable with cause fleet_conflict, not mounted as the fleet repository (kb/invariants/fleet/baked-ontology/reserved-id/4cdcf99e.md). loadOntology also sends a fleet-id ontology to refreshFleetOntology instead of the preset refresh (master only, wholesale).
