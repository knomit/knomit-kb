# A knomit repo has three roots, one writer rule each: kb/ facts (fact tools by topic/category), .knomit/ the system (people through git, knomit's own code; CLOSED to every fact tool with every dot path, reads included), artifacts/<area>/ agents' untyped working files (fact tools by explicit path; never indexed, queried, listed, exported or trigger-visible)

The user's framing (2026-10-04), verbatim: "we have really three categories of data: - "kb" : where knowledge goes, all agents need R/W - system: like the "system" part of a database, that describes how the kb operates, ontology, etc - state / artifacts: non-fact type artifacts that agents should be allowed to R/W". The name (2026-10-04): "why not artifacts, as long as they're keeping the same kind of data - "untyped" ? ones are system artifacts, the others are "regular" artifacts". Approved 2026-10-05 ("1. yes."). Design: F25-three-roots in the fleet proposals.

WHY. Before F25 the agent-writable `.knomit/<area>/` shared a folder with the system: knomit_learn/update/PUT could add files under `.knomit/skills/` (served by knomit_skill to every later session) and, once F23 lands, `.knomit/guidance/`. On a repo with no origin the local reconcile fast-forwards main to the agent tip every 30 s, so an agent write became trusted repo content within a round — data becoming instructions (F23's review finding R1). Two writers, one path rule: the root cause was the shared folder.

OPTIONS. (a) Reserve system areas in `reservedPrivate` (a deny-list inside the agents' folder — every new system area would need a release to protect it, and a forgotten one fails open). (b) Keep one folder and check content type (a fact file can be a valid SKILL.md: ParseFact ignores unknown keys). (c) Split by location: system and agents' files in different roots. (c) won: discovery already keys on location, so a folder beside kb/ needs no new filter, and closing all of `.knomit/` fails closed for every future system file.

THE CHOICE, as built (PR #422, merge commit 74fa6cd3 on dev):
- `.knomit/` and every path with a dot segment: refused by learn (`path`, `retract`), update, retract, explain (plain/commit/history_cursor), query `path`, REST GET/PUT/DELETE (sub-resources included, percent-encoding judged), and experiment resolutions of every kind. `fact.IsWritablePrivatePath` was deleted.
- `artifacts/<area>/<name>`: `fact.IsArtifactPath` — ≥1 folder deep, no empty segment, no dot segment at any depth, no `..`. NormalizePath keeps it at the repo root (case-insensitive root segment). No ontology rule, no dedup, a `context` is refused.
- config refuses `ontology_root` = "artifacts" or nested under it (Load fails, naming the setting).

COORDINATOR'S CHOICES ON OPEN DETAILS (not ruled by the user; conservative): an artifact keeps the fact file format the tools build; trigger SCRIPTS stay fact-only and may not write artifacts/ (the host refuses); existing `.knomit/<area>/` files are left in git, unreachable through the tools, moved by hand if needed; the #381 bookmark and the route for editing `.knomit/` on an origin-less hosted repo are out of scope.

WHAT THIS DOES NOT MEAN: knomit itself still reads `.knomit/` by exact name at the consensus tip (ontology, skills, recipes, trigger scripts, templates); the rule binds the fact tools only. And "artifacts" here is the repo-root folder — F24's `.knomit/artifacts/` in a recipes repo is SYSTEM artifacts, written through git.

UPDATE (2026-10-06, #424 merged into dev at 37033359). User ruling, verbatim: "No, we should not limit writes only to the folders we own - I am OK with integrators writing into their own roots, if they choose to do so. We just reserved two top level "kb" and "artifacts", as well as a private folder ".knomit"". So knomit RESERVES exactly three roots and does not refuse others: REST PUT/DELETE keep writing any other dotless repo-root path verbatim (for example `notes/x.md`) — the integrator's folder, never indexed, never a fact, never trigger-visible. The MCP tools still stay inside knomit's roots (a non-root path gets the ontology-root prefix; `knomit_learn`'s `path` accepts only `artifacts/<area>/…`). Also in #424: trigger scripts may write `artifacts/` ("triggers should write to artifacts"; see kb/invariants/repos/triggers/script-private-path/b1c7ee9c.md), and REST DELETE of ANY missing path now returns 404 (it returned 500 for every missing path, not only encoded ones; the store wraps ErrPathNotFound and the handler maps it).
WHAT THIS DOES NOT MEAN: a stray top-level folder in a KB repo is not corruption, and knomit does not manage it.
