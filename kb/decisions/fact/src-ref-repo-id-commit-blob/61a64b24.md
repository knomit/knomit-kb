# src:// refs carry repo id, commit AND blob hash (full 40-hex) — the blob makes the citation retrievable byte-exact without knomit

The old form `src://<source-name>/<path>@<commit>` makes an assertion that can be FALSE: the file may not have existed at that commit, the path may have been renamed, the commit may be unreachable after a force-push. It also identifies the repo by a bare name, which collides across forks, renames, and host migrations.

**Options considered:** (a) keep the commit only; (b) replace the commit with a blob hash; (c) carry BOTH commit and blob; (d) adopt fully-qualified SWHID (`swh:1:cnt:<blob>;origin=...;anchor=swh:1:rev:<commit>;path=...`) as the storage format.

**Rationale:** (b) alone loses the temporal anchor — no ordering, no as-of date. (c) wins because the two components cover each other's failure modes: a shallow clone loses the blob but keeps commit+path; a rewritten history loses the commit but the blob is still fetchable (verified: GitHub's `GET /repos/{owner}/{repo}/git/blobs/{sha}` returns it with no clone at all). The pair is also self-checking — `git rev-parse <commit>:<path>` must equal the blob, and a commit is immutable, so a mismatch means the ref was generated wrong. (d) was rejected for STORAGE because SWHID identifies a repo by `origin=<URL>`, the unstable identifier we deliberately replaced with the root commit; but SWHID is EMITTED on demand, since its `cnt` hash IS git's blob id and its `rev` hash IS git's commit id.

Verified against git: `git cat-file blob <sha>` retrieves exact bytes with no commit involved and still works for a file deleted several commits ago; `git diff <blobA> <blobB>` diffs without commits; `git log --find-object=<blob>` recovers the commits; partial clones (`--filter=blob:none`) lazily fetch by blob sha; shallow clones (`--depth 1`) do NOT have the object.

**The choice:** `src://<repo-id12>/<path>@<commit40>:<blob40>[#L<start>-L<end>]`. The repo id is the first 12 hex of the SOURCE repo's root commit, matching the width already canonical for kb:// (RepoInstance.ShortID). Commit and blob are stored FULL 40-hex — expanding an abbreviation needs the source object database, which knomit does not have, so abbreviated storage would make SWHID emission impossible for exactly the foreign repos where interop matters. Display abbreviates; storage does not. Parsing disambiguates by component count: one component after `@` is the legacy form, two is the new form, so legacy refs keep resolving permanently.

**Non-scope:** knomit CANNOT verify any component of a src:// ref — its object database holds fact blobs only, never source. Server-side checking is SHAPE ONLY (parseable; new-form hashes are full 40-hex). Existence is the authoring client's obligation, carried by the MCP instructions and the knomit-* skills: `git rev-parse <commit>:<path>` failing IS the check. Do not add a server-side existence check for src:// refs, and do not treat a src:// ref as an edge — it is terminal-external, exactly like https://.
