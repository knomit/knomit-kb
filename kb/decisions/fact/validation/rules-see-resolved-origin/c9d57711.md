# Ontology rules see the RESOLVED origin, not the raw field — and ref_warnings stays hidden on purpose

`factToJS` (internal/fact/validation.go) built the `fact` object ontology rules
evaluate against, and exposed only nine of the Fact struct's thirteen fields:
kind, type, domain, entities, refs, title, body, path, confidence. `sources`,
`origin`, `evidence_weight` and `ref_warnings` were invisible — an omission,
not a design, and spec/mbekg.md §3.4 froze it as "exactly … Nothing else".

Three choices were made when closing it.

**Options considered**

1. Field set: (a) add sources + origin + evidence_weight; (b) add those plus
   ref_warnings, for literal completeness.
2. Origin representation: (a) resolve the default via `defaultOriginForType`
   when `f.Origin == ""`; (b) pass the raw field, empty string included.
3. Recurrence guard: (a) a reflection test over the Fact struct; (b) a doc
   comment in factToJS and the spec.

**The choice** — (1a), (2a), (3a): expose sources, origin and evidence_weight;
resolve origin through `defaultOriginForType(f.Type)` when unset; add a
reflection test asserting every exported Fact field maps to a factToJS key
unless named in an explicit opt-out list.

**Rationale**

Origin must be RESOLVED because the two write paths disagree on whether it is
set at validation time. knomit_learn deliberately leaves `f.Origin` empty when
the caller omitted it (internal/mcp/learn.go), so SerializeFact/ParseFact can
apply the default; knomit_update parses the fact off disk first, so origin is
already resolved by the time ValidateFact runs. Exposing the raw field would
make `fact.origin === 'authored'` false on every learn write and true on the
equivalent update — the same parse/serialize drift that once round-tripped
authored synthesis facts into distilled, and that `defaultOriginForType` exists
to centralise. Resolving means a rule sees the value that will actually land on
disk.

ref_warnings is excluded because it is derived on read, never stored, and is
unusable from a rule in BOTH directions. On the learn path it is structurally
always empty: the fact was built in memory, and SerializeFact refuses to write
a malformed ref anyway, so no warning can exist. On the update path it is
STALE: ParseFact computes it from the on-disk refs, the handler then replaces
`fact.Refs` wholesale with the caller's new refs, and only then does
ValidateFact run — so a rule would judge refs that are no longer being written
and ignore the ones that are. A rule like `fact.ref_warnings.length === 0`
would therefore pass vacuously on every write.

The reflection test exists because this omission was silent: fields were added
to Fact and nobody updated factToJS. A comment cannot fail CI.

**Non-scope**

This does NOT establish "rules see every field" as a rule — ref_warnings is a
standing exception, and the opt-out list is the place to record the next one
with its reason. It also does not make `origin` mutable or rule-settable: rules
are pure boolean predicates over a read-only snapshot, and origin remains
immutable after write.
