# User ruling 2026-10-16, item 3: "yes, fix - what's the point in supporting enforcements in the ontology definitions if they are not honored" — ontology validations bind every writer and every entry path (BUILT by PR #533)

THE QUESTION. Ontology `validations` ran only on knomit_learn, knomit_update and experiment {body} resolutions; REST fact writes, the review pipeline, pushes and merges never evaluated them, so a validation was a guard on one door, not a property of the corpus. The question was whether to enforce them everywhere. The answer, verbatim: "yes, fix - what's the point in supporting enforcements in the ontology definitions if they are not honored".

THE DECISION, as built (PR #533, squash commit 6f241959 on dev):
1. At the SOURCE, option (a): validateWrite in both store write cores (kb/invariants/store/fact-write/validate-write), so REST (422), the review pipeline, fleet code, trigger scripts and MCP are all refused with the rule's own message.
2. At every ENTRY path, judged on the branch's NET change (kb/invariants/store/verify/validation-net-change): receive-pack, the fleet fetch judge, `knomit verify ci`, and the master's own range; the pushed-branch merges (MergePushed, MergeConsensus) judge the merge RESULT.
3. In every verify_signatures mode (off included) and in every repository, because the write path it mirrors refuses in every mode.
Option (b) alone (net-change judging at the entry paths without source validation) was the alternative put to the user. The first build judged per commit at the entry paths; review showed a per-commit judge strands a branch on a commit that was valid when written but is refused once main's ontology tightens, and a later fix cannot unstick it. The coordinator then decided the entry paths judge the NET change. The source validation (a) stays, so both exist.

WHAT IS DELIBERATELY NOT COVERED: reconcileMain following an origin's main (trust-the-forge, kb/decisions/fleet/trust-the-forge-main/3a19b2d3.md; the forge's own CI is `verify ci`), subscriptions (read-only), a local reconcile of a non-fleet knowledge base (its writes were validated at the source), deletes, unchanged content, InitRepo's seeds.

CONSEQUENCE: a topic's validations ARE now an invariant of every fact a writer or an entering branch adds or changes. They are still not an invariant of the whole corpus: untouched legacy facts are never judged (kb/gotchas/fact/validation/legacy-invalid-facts).
