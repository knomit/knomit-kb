# Confidence/sources bounds validated at the fact serialize/parse chokepoint, not MCP handlers or ontology rules

Numeric fact-field invariants — confidence in [0,1] and sources >= 0 — are enforced by validateBounds(), called by BOTH SerializeFact and ParseFact, symmetric with the existing validateKindAndType chokepoint (see [[single-validation-entry-point]]).

**Options considered** (resolved via AskUserQuestion): (A) fact serialize/parse chokepoint; (B) explicit checks in the MCP learn + update handlers only (what the PR #69 review literally suggested); (C) an ontology root-level JS validation rule.

**Rationale** — A won: it enforces the invariant on EVERY write path (MCP, synthesize, web factWriter) and on read, so an out-of-range fact can neither be persisted nor silently loaded, and it cannot be bypassed. It matches the documented single-validation-entry-point invariant (validate in both directions; validating one direction only is the anti-pattern). B lost: localized to MCP, duplicated across two handlers, and leaves synthesize/web write paths uncovered. C lost: `sources` is not exposed to rules (factToJS omits it), the rule would be per-ontology-preset rather than universal, and a numeric range check is a universal fact invariant — not designer policy — so the ontology layer is the wrong semantic home.

**The choice** — validateBounds() in internal/domain/fact/kind.go, invoked from SerializeFact and ParseFact in internal/domain/fact/format.go. Blast-radius verified before adopting: synthesize already rejects propose confidence outside [0,1] (internal/corpus/synthesize/validation.go); no production path emits out-of-range values; boundary values 0 and 1 are accepted (inclusive).
