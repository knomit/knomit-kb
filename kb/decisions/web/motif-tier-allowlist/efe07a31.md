# Web REST accepts motif tiers exact/stem/token-2 only, validated by an allowlist that never names the loose tiers — and the MN6 AST guard now scans internal/edge/web

Options considered: (1) exact + stem + token-2, the same ladder MCP exposes for automation (chosen); (2) all tiers except soft, letting a human explore token-1 from the UI, requiring a looseTierRefusers exemption; (3) exact only.

Rationale: MN6 doctrine — loose tiers exist for a caller who TYPES them, never as anything automation selects; the web surface feeds programmatic re-issue (chips, links), so it stays on the automation ladder. The validation in motifParams is an ALLOWLIST switch over the accepted tier constants, so the identifiers MotifMatchToken1/MotifMatchSoft and the strings "token-1"/"soft" appear NOWHERE in internal/edge/web non-test code — which is what let the guard extend without any looseTierRefusers entry. TestMotifMatch_LooseTiersAreNeverReachedByAutomation's dirs list gained "../web".

Verified by sabotage, not trust: temporarily defaulting motifParams to the loose tier made the guard fail naming ../web/params.go.motifParams, then reverted.

Consequence for future web code: rejecting a loose tier must stay phrased as an allowlist ("accepted: exact, stem, token-2") — writing the rejected tier's name into a validation case or an error string will fail the MN6 guard, and the fix is rewording, never a refuser exemption for web.
