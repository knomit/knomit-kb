# FactSet back stack + Top tool group (user, 2026-11-03; PR #744, supersedes the #736 Back pill and its one-origin rule): every in-document link PUSHES an origin; the back arrow inside Top's ModeFlyout POPS one and returns exactly; Top goes to unit 1 AND clears the stack; an option change clears it; no cap

SOURCE (user, 2026-11-03, verbatim intent): "remember multiple jumps, in a stack like fashion"; "change the to top button to use the same Adobe toolset style as we have for materialize search results"; "when both back and top are available, when I hover on top button expand to the left and show a side arrow as well"; "clicking on the side arrow will pop one pointer from the local reference follow stack"; "clicking on top will go to the top, and clear the stack". The report behind it: the #736 pill kept ONE origin, stayed until clicked, and the Top button was hidden meanwhile.

AS BUILT (PR #744, branch feat/factset-back-stack):
- STACK: FactSetView keeps `stack: Origin[]` (useState). Following a forward stub, a back stub or a builds-on link PUSHES the origin recorded exactly as #736 (takeOrigin: clicked section else the section at the pane top, its offset from the pane top; a stub is named by the nearest written section above it). The Unit stepper, a path item and Top push nothing.
- POP: the back arrow returns to the TOP entry with #736's machinery unchanged (in-run: restoreStep; else seek(unit, undefined, n, back=true); restoreStep reads above/below until the offset fits; recover() after a 404 lands on backTarget; Retry after another failure is retryBack). The entry leaves the stack only when that return has LANDED (popIf(o): removed only if it is still the top), so a refused or failed Back keeps it.
- TOP: goes to unit 1 (scroll to 0 when unit 1 heads the run and no seek is in flight, else seek(1), which also supersedes a Back seek in flight) AND clears the stack and any pending restore.
- OPTION CHANGE (depth, references, Cross-KB, Unpin): clears the stack (a restart can renumber (unit, n)).
- NO CAP: the user named none, so there is no constant; the stack lives as long as the FactSet view (one per search, RightPanel keys it).
- UI: the floating pill is GONE. Top is the results header's ModeFlyout reused (decision 9fcadb32), testid fs-tools, class .k-fs-tools at the old Top spot: at rest only Top (ArrowUpIcon, 'Back to top'); the 4px corner triangle ONLY while the stack is non-empty; hover or focus opens the back arrow (ChevronLeftIcon, fs-stack-back) INLINE TO THE LEFT on the same surface. Its tooltip and aria-label are 'Back to <title>' of the entry it pops (stubLabel rule minus 'see '), the user's ruled wording; final copy. 250 ms collapse, Esc, blur, Left/Right, only Top tabbable, Safari press-blur guard: all ModeFlyout's own.
- VISIBILITY: Top is hidden ONLY at the start of the FactSet with an empty stack: shown when scrolled past FS_NEAR_PX, OR the stack is non-empty, OR the run starts past unit 1 (a jump lands near the top of its run, where the old scrolled-only rule hid it: the reported bug).

SHARED-COMPONENT CHANGES (ModeFlyout): optional testid (strip/hint ids derive from it), className, style, stripStyle, iconSize; FlyoutItem.toggle=false drops aria-pressed (actions, not modes); open = wantOpen && others.length > 0 (the same rule PR #742 carries), so a group with nothing to open is never open, never draws a strip and never carries data-keeps-esc (with an empty stack, Esc on a focused Top still closes the view); hint and aria-haspopup/expanded only when there are other items; an ACTING current icon with an enabled other opens on a touch/pen tap that finds the group closed (no hover to reach it) and acts on the next tap or any mouse click; while open the group carries data-keeps-esc="true" and useMatFocus returns early for focus inside it, so Esc collapses the flyout instead of closing the FactSet view.

CONSEQUENCE: a new jump kind in the FactSet view must decide whether it pushes; a new navigation must decide whether it clears the stack (Top and an option change do; the stepper and path items do not). Never pop an entry before its return has landed. Do not put a second implementation of the flyout in the FactSet view; extend ModeFlyout.

WHAT THIS DOES NOT MEAN: it is not browser history (the browser Back button is untouched) and it does not survive closing the FactSet. Top's 'clear' is the user's rule, not a side effect: Top is not a pop. The touch-tap-opens rule does NOT change the results header (its derived-mode exits have only disabled others, so a tap still exits).
