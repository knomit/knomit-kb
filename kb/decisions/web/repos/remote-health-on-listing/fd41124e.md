# Per-repo remote health reaches the client as GET /repos remote:{sync,push} plus an edge-only remote kind on /repo-events, not as a GET /origin per repo

The target rail and its toggle dot need every repo's remote health all the time. The old ManageOverview fanned out one `getOrigin` per repo when it opened. Polling N origins forever was rejected as the minimum-change path, and /repo-events' own contract already named "its origin failing at the repo level" as a kind it should carry.

Instead:
- Each `GET /repos` row carries `remote: {sync, push}`, each `ok | error | ""` (`""` = that half never ran), read from `remotes.last_status` / `last_push_status` through the same `originProvider` `GET /origin` uses.
- The `remote` kind on `/repo-events` carries `{repo, sync, push}`. The payload is the row's whole new value, not a delta. It is an edge-only event (see the invariant on persisted-row edges).

The key is ABSENT (`omitempty` on a pointer) when the repo has no origin, when its store cannot be read (an unavailable row, a repo still populating), or when the read fails. A consumer must read absence as "nothing to show", NEVER as healthy, and must read `""` as "never ran", not as ok.

WHAT THIS DOES NOT MEAN: the `remote` kind does not carry error text, and it does not replace the per-branch `sync_*`/`push_*` events. Those still drive the active repo's banner, together with `syncRemoteError`'s `GET /origin` read. App patches `repos[i].remote` from the event and dispatches nothing to AppState. Membership follows the repo-events scope test: origin health is a whole-repo state shown per row.

Consequence: new UI that wants a repo's remote health reads `RepoInfo.remote` from the listing (kept current by the stream); it must not add a per-repo `GET /origin` loop.

DECISION RECORD (confirmed by the user on 2026-10-12, 'ok'): this is a deliberate Go change, not a client-side shortcut. Options, from facets plan section 7, item 1 and the status card: (1) a client fan-out of one `GET /origin` per repo, polled; (2) a server field on the listing plus an edge-only `remote` kind on `/repo-events`, and the lens `uid` on the lens JSON (kb/invariants/web/lens/wire-format/0b63a068.md) so Activity can filter by `lens:<uid>`. Chosen: (2). Reasons: the rail and toggle dots need every repo's status all the time; today only ManageOverview fanned out, once, on open; polling N origins forever is the minimum-change path the pre-release principle rejects; the repo-events contract already named a repo-level origin failure as a kind it should carry; filtering sessions by lens name client-side would break across a rename and on redacted rows. Pinned to PR A (#461).
