# Manage-panel gating uses two flags: serverReadOnly locks every mutation; a DISPLAYED subscription locks only that repo's content (description, licence, facts) and leaves its admin/registry operations open — never the browsed repo's state

CONTEXT (#324): RepoManager took one `readOnly = isReadOnly(state)` = serverReadOnly || repoReadOnly || !branchWritable || !isLive, all but the first describing the BROWSED repo/branch/anchor. So landing on a subscription (pickRepo falls back to the first sorted repo on a fresh origin) disabled + repo / + lens and hid the Logs tab; and every OTHER repo's settings page, every lens and every archived repo inherited the browsed repo's state (browse a subscription → a writable repo's rename/archive/description locked; browse a writable repo → a subscription's description editor enabled and failing).

OPTIONS CONSIDERED:
1. Composite flag as before (status quo) — rejected: mixes instance-level and browse-context reasons; the bug itself.
2. Two flags with ALL admin AND content operations open on a subscription — rejected: README/LICENSE writes on a subscription always fail (no agent branch; store read-only flag), so the UI would ship controls that cannot work.
3. Two flags: content locked, admin open — CHOSEN.

THE CHOICE:
- `serverReadOnly` (instance accepts no mutations) is the ONLY instance gate in RepoManager and ManageOverview, a REQUIRED prop on both: create repo/lens, CreateBlocked, Logs tab, Authorizations tab + OAuth probe, archived restore/purge, lens edits, and every RepoDetail control.
- A repo is read-only when the DISPLAYED repo's own mode === 'subscribe' (RepoDetail reads it from its own details) — NEVER the browsed repo's state. Read-only means nothing IN the repo can change: description and licence are locked in Manage; facts are locked in the browse surface by isReadOnly. Its admin/registry operations stay available: rename, archive, rebuild, and changing the upstream branch.
- UNKNOWN MODE: until the displayed repo's details answer (or if the read fails), RepoDetail treats the mode as unknown and withholds the same controls a subscription withholds, so a subscription's page never flashes an affordance that would 409/503. Registry operations do not wait on the mode.
- ORIGIN (sub-decision, option A of three): the server keeps refusing origin DELETE and connect-session re-pointing for a subscription (409), so RemoteCard (`lockOrigin`) withholds Reconnect and Disconnect for one. Rejected: (B) make disconnect convert the subscription to a local writable repo by rebuilding the instance — a new product behaviour needing Go work; (C) add a URL/credential editor over PUT /origin (which already carries Mode) — a new feature. Both left to the user as follow-ups.
- `isReadOnly(state)` survives unchanged in state.ts and gates only fact authoring in the browse surface (RightPanel factReadOnly). branchWritable and the non-live anchor never reach Manage.

RATIONALE: a read-only repo means its CONTENT is immutable, not its registry configuration. Instance-scoped actions cannot depend on which repo happens to be browsed, and a repo's settings page must describe that repo, not the one behind it. The origin exception exists because a subscription's mode lives only on its origin record (manager.go builds `subscribed` from origin.Mode; Origins.Delete drops repo_subscriptions): detaching it would leave the running instance subscribed while the next restart builds it as a writable repo — a silent runtime/restart divergence.

NON-SCOPE: does not authorize making the server accept content writes on a subscription, nor lifting the origin DELETE / connect-session refusals — that is option B, a separate decision.

UPDATE (facets stack, merged 2026-10-12): the rule is unchanged; its landing sites moved because Manage was dissolved (kb/decisions/web/shell/facets/manage-dissolved/9b39ed67.md). `RepoManager` and `ManageOverview` are deleted; `RepoDetail` is now `RepoSettings` (web/src/RepoSettings.tsx), and `LensSettings`, `ArchivedSettings`, `UnavailableSettings` and `PendingCreateSettings` are siblings. `serverReadOnly` is a REQUIRED prop on each `*Settings` component, on TargetRail (the `+` buttons and the create wizard's `CreateBlocked`) and on SettingsFacet; the server tabs are gated by `serverPagesFor(state.serverReadOnly, oauth.available)` (Logs and Authorizations never appear read-only, and the OAuth probe does not run). The subscription-mode lock is still read by RepoSettings from its own details, with the unknown-mode withholding. Wherever this fact names RepoManager.tsx, ManageOverview or the 'Logs tab', read the components above; `isReadOnly(state)` still reaches only RightPanel.
