# Manage-panel gating uses two flags: serverReadOnly locks every mutation; a DISPLAYED subscription locks only that repo's content (description, licence, facts) and leaves its admin/registry operations open — never the browsed repo's state

CONTEXT (#324): RepoManager took one `readOnly = isReadOnly(state)` = serverReadOnly || repoReadOnly || !branchWritable || !isLive, all but the first describing the BROWSED repo/branch/anchor. So landing on a subscription (pickRepo falls back to the first sorted repo on a fresh origin) disabled + repo / + lens and hid the Logs tab; and every OTHER repo's settings page, every lens and every archived repo inherited the browsed repo's state (browse a subscription → a writable repo's rename/archive/description locked; browse a writable repo → a subscription's description editor enabled and failing).

OPTIONS CONSIDERED:
1. Composite flag as before (status quo) — rejected: mixes instance-level and browse-context reasons; the bug itself.
2. Two flags with ALL admin AND content operations open on a subscription — rejected: README/LICENSE writes on a subscription always fail (no agent branch; store read-only flag), so the UI would ship controls that cannot work.
3. Two flags: content locked, admin open — CHOSEN.

THE CHOICE:
- `serverReadOnly` (instance accepts no mutations) is the ONLY instance gate in RepoManager and ManageOverview: create repo/lens, CreateBlocked, Logs tab, Authorizations tab + OAuth probe, archived restore/purge, lens edits, and every RepoDetail control.
- A repo is read-only when the DISPLAYED repo's own mode === 'subscribe' (RepoDetail reads it from its own details) — NEVER the browsed repo's state. Read-only means nothing IN the repo can change: description, licence, ontology, facts. Its admin/registry operations stay available: origin, rename, archive, rebuild, upstream.
- `isReadOnly(state)` survives unchanged in state.ts and gates only fact authoring in the browse surface (RightPanel factReadOnly). branchWritable and the non-live anchor never reach Manage.

RATIONALE: a read-only repo means its CONTENT is immutable, not its registry configuration. Instance-scoped actions cannot depend on which repo happens to be browsed, and a repo's settings page must describe that repo, not the one behind it.

NON-SCOPE: this does not authorize making the server accept content writes on a subscription, nor removing the server's subscription refusals on origin DELETE / connect-session — those have integrity reasons (subscription mode lives only in control.db; deleting the origin row demotes the repo to writable on the next restart) and are a separate decision.
