# At a viewport of 640px or narrower the app shell stacks the repositories rail above the page and the top bar keeps a 96px target label while its tab strip scrolls inside itself; above 640px nothing changes

PR #534 (merge 59813b66) fixed the two 375px defects the earlier gotcha recorded (the Connect form squeezed to ~69px by the open 236px rail, and the top bar tabs clipping). The fix is one `@media (max-width: 640px)` block in web/src/App.css, the same breakpoint the Connect grid uses, acting on shared shell class hooks:

- RAIL: `.k-shell-body` (App.tsx) becomes a column and `.k-rail` (TargetRail.tsx) goes full width, max-height 40%, with its border on the bottom instead of the right. The rail STACKS above the page; it does not overlay. Reason: `railShown` forces the rail open over a repository or lens draft, and an overlay would hide the very page being filled in.
- LABEL: `.k-bar-label` has min-width 96px and `.k-bar-name` min-width 3ch; the label carries a `title` with the full name ("fleet (master)" for a fleet) because the visible name truncates with an ellipsis.
- TAB STRIP: the facet tab strip is flexShrink 1 with overflowX auto, so it scrolls sideways INSIDE itself (about 1.5 tabs visible at 375px, "Acti" cut by the scroll edge: the decided behaviour, not a bug). Tab buttons are flex-shrink 0 with 8px padding; `.k-bar-sep` and `.k-bar-divider` margins tighten.
- The rules are CSS classes with !important because the shell styles are inline objects, and an inline style beats a class unless the class says !important; inline styles cannot carry media queries.

At 641px and wider the rail is still the 236px pushing column (the breakpoint is exact: 640 stacks, 641 does not). Measured in real Chromium at 375x740: no horizontal scroll on Browse, Activity, Settings, server pages, fleet pages, with the rail open or closed; the Connect form is 311px wide with the rail open (was ~69px).

CONSEQUENCE: new shell chrome that must survive a phone width gets a class hook and a rule in this block, not an inline style.

WHAT THIS DOES NOT MEAN: (1) the rail is not an overlay at any width. (2) The stacked rail costs up to 40% of the height, so the page below it is short on a small screen; that is accepted. (3) This is not a container query: the rules key on the viewport, so a tablet width (641px up) still gives the page only ~405px beside the rail, unchanged from before. (4) The Browse page's own dense stats columns at 375px were not touched.
