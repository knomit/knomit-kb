# Boot collapses from four dependent round trips to two by EMBEDDING the read-branch root in GET /repos/{repo} (and the write-branch root in GET /lenses/{lens}) and fetching the remembered context speculatively in parallel with the repo list — not via a boot endpoint; the boot screen shows phase, attempts and errors and ends once repo AND branch are known, with a pre-React splash in index.html covering the bundle download

**Context (2026-09-18, after PR #223 made bytes cheap).** Cold boot still needed four dependent round trips before `state.branch` existed: repos list → repo GET (read-only flag) → repo GET again (`getAgentBranch`, for `agent_branch`) → branch root GET (head, index watermark) → `SET_STATUS`. Until then `App.tsx` rendered a bare centred "Loading…" with no chrome, no phase and no retry feedback (`bootstrapStatusWithRetry` logged attempts only to the console), and before React ran the page was blank for the whole bundle download (8 s on the user's link) and, on desktop, for the `config.js` block. At 100 ms RTT that chain was ~0.5 s of pure latency that compression could not touch.

**Options considered.** (1) Embed the branch root in the existing single-repo and single-lens resources (HAL `_embedded`), and fire the remembered context's GET in parallel with the list because localStorage already knows it before any request goes out. (2) A dedicated `GET /api/v1/boot?repo=&path=` returning version, repos, lenses, resolved context, branch root and the first panel wave in one response. For the boot screen: (a) end it when repo and branch are known, panels keep their own placeholders; (b) end it only after the first panel wave has rendered.

**Rationale.** (1) reuses resources that already exist, adds one embedded sub-resource to each (a single resource embedding one child is in scope of the HAL rules; the "minimal embedded items" rule is about collections), and the two bodies agree BY CONSTRUCTION through one shared branch-root builder. The speculative fetch costs nothing in the common case and one extra hop only when the remembered repo is gone. (2) is one hop faster but duplicates four section endpoints inside a new resource, teaches the server what the client's first screen contains, and must be mirrored on every panel change. The user chose (1) and (a): the boot screen's job is to get the user to a usable chrome quickly and honestly, not to hide the panel wave.

**The choice.** Server: `GET /repos/{repo}` gains `_embedded.branch` = the READ branch's root (same `ri.ReadBranch()` the body advertises as `read_branch`), built by the same function `handleHALBranch` uses; omitted, never an error, when the store is unreadable. `GET /lenses/{lens}` gains `_embedded.write_branch` likewise. Repo LIST untouched. Client: `bootstrapStatusWithRetry` takes `getRepo` and uses the embedded root when present (one request), falling back to the branch call when absent; `App` reads `loadLastContext()` synchronously and fires the remembered repo/lens GET in the same wave as `repos`/`lenses`/`version`, applying the speculative result only after `pickRepo` confirms it. UI: a pre-React inline splash inside `#root` in `web/index.html` (no JS, no fonts, no external CSS), replaced by `BootScreen` with a determinate phase bar (connecting → opening <repo|lens> → branch), an elapsed counter after 2 s, per-attempt retry text, and a terminal error state with Retry. Plan: .claude/plans/2026-09-18-boot-sequence-and-progress.md.

**Non-scope.** The panel wave (topics/stats/activity/motifs) and its placeholders are unchanged. No boot endpoint. The no-repos empty state, not the boot screen, is what a fresh install shows.
