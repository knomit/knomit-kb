# Boot collapses from four dependent round trips to two by EMBEDDING the read-branch root in GET /repos/{repo} (and the write-branch root in GET /lenses/{lens}) and fetching the remembered context speculatively in parallel with the repo list — not via a boot endpoint; the boot screen shows phase, attempts and errors and ends once repo AND branch are known, with a pre-React splash in index.html covering the bundle download

**Context (2026-09-18, after PR #223 made bytes cheap).** Cold boot still needed four dependent round trips before `state.branch` existed: repos list → repo GET (read-only flag) → repo GET again (`getAgentBranch`, for `agent_branch`) → branch root GET (head, index watermark) → `SET_STATUS`. Until then `App.tsx` rendered a bare centred "Loading…" with no chrome, no phase and no retry feedback (`bootstrapStatusWithRetry` logged attempts only to the console), and before React ran the page was blank for the whole bundle download (8 s on the user's link) and, on desktop, for the `config.js` block. At 100 ms RTT that chain was ~0.5 s of pure latency that compression could not touch.

**Options considered.** (1) Embed the branch root in the existing single-repo and single-lens resources (HAL `_embedded`), and fire the remembered context's GET in parallel with the list because localStorage already knows it before any request goes out. (2) A dedicated `GET /api/v1/boot?repo=&path=` returning version, repos, lenses, resolved context, branch root and the first panel wave in one response. For the boot screen: (a) end it when repo and branch are known, panels keep their own placeholders; (b) end it only after the first panel wave has rendered.

**Rationale.** (1) reuses resources that already exist, adds one embedded sub-resource to each (a single resource embedding one child is in scope of the HAL rules; the "minimal embedded items" rule is about collections), and the two bodies agree BY CONSTRUCTION through one shared branch-root builder. The speculative fetch costs nothing in the common case and one extra hop only when the remembered repo is gone. (2) is one hop faster but duplicates four section endpoints inside a new resource, teaches the server what the client's first screen contains, and must be mirrored on every panel change. The user chose (1) and (a).

**AS MERGED (PR #227, dev 444be652).**
- Server: `branchRootBody` (internal/web/handlers_branches.go) builds the branch root for both `handleHALBranch` and the embeds; branch name is an explicit parameter — repo embed passes `ReadBranch()`, lens embed passes `AgentBranch()`; a lens whose write member is a subscription omits `_embedded.write_branch` (named test). `_embedded` on the lens is a `map[string]any` with `omitempty`, set only by the single-lens GET; list/create/patch never carry it. **Embed gate:** `defaultBranchRootReader` returns a ZERO `branchRootInfo` with nil error when the store is unopened (WithRead skips its callback), so "omit on error" was not enough — the embed is omitted whenever `info.Head == ""`, which conflates an unopened store with an empty branch in the SAFE direction (client falls back to the branch GET; one extra hop, never a wrong head). Embed size on the fixture: repo GET 276 → 1,500 B raw, 160 → 434 B gzipped.
- Client: `bootstrapStatusWithRetry` takes `getRepo`; uses `details.branch` when present (one request), else falls back to `getStatus(repo, bootBranchOf(details))` which prefers `read_branch`. `App` reads `loadLastContext()` synchronously and fires the remembered repo/lens GET in the same wave as repos/lenses/version; the speculative result is applied only after `pickRepo` confirms it (mutation-verified: removing the guard boots beta on alpha's branch). The read-only effect WAITS for the boot response instead of racing its own `getRepo`; a later context switch refetches.
- Progress: inline `#boot-splash` + `<style>` inside `#root` in `web/index.html` (no JS/fonts/external CSS), removed by React's first `createRoot().render` (render-tested; note the test cannot distinguish createRoot from hydrateRoot on React 19, which recovers from hydration mismatch by client-rendering). `BootScreen` + `boot.ts` reducer: phase → FRACTION (not index/total, so the one-hop path reaches 1.0 and the conditional `branch` phase appears only on fallback); monotonic (a stale `onPhase` after done is a no-op by object identity); elapsed after 2 s; per-attempt retry text; terminal error with Retry. The no-repos empty state precedes the BootScreen.
- Windows CI exposed a fixture leak: `Manager.Set` orphans the replaced instance and `Manager.Close` tears down only the map; fixed by restoring the instance in `t.Cleanup` (see the Manager.Set gotcha).

**Non-scope / follow-ups.** The panel wave and its placeholders are unchanged. No boot endpoint. A context switch after boot still fetches the new repo twice (read-only effect + bootstrap) — the conspicuous redundant hop left. Plan: .claude/plans/2026-09-18-boot-sequence-and-progress.md.
