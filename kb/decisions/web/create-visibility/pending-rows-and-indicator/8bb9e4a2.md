# Create jobs are visible from every view: GET /api/v1/repo-creates lists running and recently finished jobs newest first, DELETE dismisses a FINISHED job (409 while running), repo rows carry index_state/done/total, and the UI merges jobs into the repo list with a top-bar running-count indicator — chosen over locking the UI

Decided 2026-09-16 with the user (PR #208). The incident: a subscribe was at "40%" when the user navigated to Logs; on return there was no trace of it anywhere. Creates were already detached (a job registry with a poll endpoint), so nothing was cancelled — but there was no list endpoint, so a client that lost the job id had no way back to a running or failed job.

Options considered: (A) pending rows in the repo list; (B) A plus a global activity indicator; (C) lock the UI until the create finishes. Chosen B. C rejected: worst to use and a browser refresh still shows nothing.

API: GET /api/v1/repo-creates (HAL collection `creates`, newest StartedAt first, running plus finished within CreateJobTTL); DELETE /api/v1/repo-creates/{id} dismisses a FINISHED job (204), answers 409 for a running one and 404 for unknown/expired; GET /api/v1/repos rows gain index_state, index_done, index_total from RepoInstance.IndexStatus(). The job model (detached, latest-value status, TTL, deadline) is unchanged; this only adds a list, a dismiss and richer status.

UI: one module-level poller (useRepoCreates) shared by TopBar and the lists, 2 s while any job is running or the list is non-empty, else 30 s; jobs merge into the repo list as rows where the name would sort — `creating` with step/message and an indeterminate bar during transfer, determinate during index; `create-failed` with the error and a dismiss control; a running row opens the existing CreateProgress view for that id rather than re-entering the wizard. TopBar shows a spinner with the running count and hides at zero. Active rows carry `indexing d/t` or `index error` chips.

Test note: the poller's shared timer clears on unmount and does NOT explain the pre-existing vitest flakes in RepoManager/Library under load (806a17af); those reproduce on dev with none of this code present. Adding test files raises concurrency and tips already-marginal tests sooner.
