# Issue #178 is fixed as three commits on one branch; the live-head repair is 404-retry PLUS a periodic re-poll, and edge anchoring stays commit-anchored

Resolved with the user before implementing the fixes for issue #178 (stale live head after a long post-merge index run; lens routes missing /incoming|/outgoing).

**Options considered — scope.** (a) All three defects on one branch; (b) Defect 1 only (the root-cause observer drop); (c) Defects 1+2, splitting the lens routing bug to its own issue.

**Options considered — the client repair for Defect 2.** (a) Both a 404-triggered head refresh + retry AND a periodic head re-poll; (b) the retry alone; (c) the re-poll alone.

**Rationale.** Scope: the three defects are small, independent, and were found in one investigation, so one branch with one commit per defect keeps the PR reviewable. Client repair: the two mechanisms cover different failure classes and neither subsumes the other — the 404-retry recovers the observed failure immediately, while the re-poll is the fallback for a lossy or dead SSE stream and would have masked Defect 1 entirely. The retry alone leaves any OTHER consumer of the stale head wrong; the poll alone still shows the raw error until the next tick.

**A third option was considered and rejected for Defect 2:** making the live repo-context edge anchor '' (as the lens context already does), so live edge fetches use the non-anchored /facts/{path}/incoming|outgoing route and no cached head can go stale.

**CORRECTION (2026-08-29, from the review of PR #179).** The reason first recorded here was WRONG, and is replaced rather than left standing. It claimed the HEAD-anchored handlers serve ExplainFact, "the CURRENT graph", rather than the version-aware IncomingAtCommit/OutgoingAtCommit primitives, and that the swap would therefore resolve ref hops against the target's latest version and violate historical-not-current. graphStore.ExplainFact does no such thing: it resolves the path's HEAD-active commit out of branch_facts and then calls IncomingAtCommit and OutgoingAtCommit itself, returning the same RefSummary.Commit — target_commit for outgoing. refCommits is read off those edge rows either way, so the swap would NOT have broken target_commit pinning.

The real difference is narrower: which commit THIS fact's own version resolves at — ExplainFact uses the HEAD-active commit, the anchored route uses resolveActiveCommitForPath(path, ≤ pinned). In a live view with a fresh head those coincide, which is exactly the scope the rejected option was limited to.

**Why the choice still stands, on reasons that are true.** (1) The observer fix and the head re-poll repair staleness app-wide; the anchor swap would have fixed only the edge fetch, leaving every other consumer of state.headCommit stale. (2) ONE anchored code path shared by live and history is simpler than a live-only special case that must be re-justified whenever someone reads it. The choice was right; the first justification for it was not.

**The choice.** One branch off dev, three commits: (1) commitObserver never discards a head notification — a timer firing while fn runs keeps `pending` and re-arms after the run, so the LAST head always broadcasts; (2) useFactEdges refreshes the head and retries once on a commit-anchored 404 while the view is LIVE, plus a periodic head re-poll in App; (3) the lens facts route dispatches fact sub-resources against the mount it already resolves.

**Non-scope.** The head refresh-and-retry is authorized ONLY while the view is live (isLive). It must never re-anchor a history or diff view: there the commit is the user's pin, and refreshing it would violate kb/invariants/ui/navigation/every-hop-is-path-plus-commit, which states that "the target still exists" is never a reason to drop the pin. This also does not authorize dropping the commit anchor from live edge fetches — see the rejected option above, which stays rejected on the corrected reasoning.

**Methodological note.** The wrong rationale was inherited from an imprecise comment in web/src/api.ts, believed rather than checked against internal/store/search_graph.go. A decision fact's rationale is the part future sessions reuse without re-deriving, so an unverified mechanism claim in one is worse than none — it is a written justification for the wrong side of exactly the invariant it cites. The api.ts comment was corrected in the same commit.
