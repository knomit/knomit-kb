# Issue #178 is fixed as three commits on one branch; the live-head repair is 404-retry PLUS a periodic re-poll, and edge anchoring stays commit-anchored

Resolved with the user before implementing the fixes for issue #178 (stale live head after a long post-merge index run; lens routes missing /incoming|/outgoing).

**Options considered — scope.** (a) All three defects on one branch; (b) Defect 1 only (the root-cause observer drop); (c) Defects 1+2, splitting the lens routing bug to its own issue.

**Options considered — the client repair for Defect 2.** (a) Both a 404-triggered head refresh + retry AND a periodic head re-poll; (b) the 404-triggered retry alone; (c) the periodic re-poll alone.

**Rationale.** Scope: the three defects are small, independent, and were all found in one investigation, so one branch with one commit per defect keeps the PR reviewable while still closing #178 in one go. Client repair: the two mechanisms cover different failure classes and neither subsumes the other — the 404-retry recovers the exact observed failure immediately (a raw error on a fact that reads fine at HEAD), while the re-poll is the belt-and-braces fallback for a lossy or dead SSE stream, and would have masked Defect 1 entirely had it existed. The retry alone leaves any OTHER consumer of the stale head wrong; the poll alone still shows the raw error for the window between the stale read and the next tick.

**A third option was considered and rejected for Defect 2:** making the live repo-context edge anchor '' (as the lens context already does), so live edge fetches use the non-anchored /facts/{path}/incoming|outgoing route and no cached head can go stale. Rejected: those HEAD-anchored handlers serve ExplainFact (the CURRENT graph) rather than the version-aware IncomingAtCommit/OutgoingAtCommit primitives the commit-anchored route uses. useFactEdges derives refCommits (outgoing edge → the target_commit the referrer actually reasoned over) from that response, so the swap would resolve ref hops against the target's latest version — exactly the HEAD-resolution that kb/principles/philosophy/historical-not-current forbids, and the bug kb/incidents/ui/ref-resolution/in-body-ref-target-commit already fixed once. Live edge anchoring therefore STAYS commit-anchored; the staleness is repaired at the head, not by dropping the anchor.

**The choice.** One branch off dev, three commits: (1) commitObserver never discards a head notification — a timer firing while fn runs keeps `pending` and re-arms after the run, so the LAST head always broadcasts; (2) useFactEdges refreshes the head and retries once on a commit-anchored 404 while the view is LIVE, plus a periodic head re-poll in App; (3) the lens facts route dispatches fact sub-resources against the mount it already resolves, instead of misparsing `<uuid>.md/incoming` as a fact path and 500ing.

**Non-scope.** The head refresh-and-retry is authorized ONLY while the view is live (isLive). It must never re-anchor a history or diff view: there the commit is the user's pin, and refreshing it would violate kb/invariants/ui/navigation/every-hop-is-path-plus-commit, which states that "the target still exists" is never a reason to drop the pin. This also does not authorize dropping the commit anchor from live edge fetches (see the rejected option above).
