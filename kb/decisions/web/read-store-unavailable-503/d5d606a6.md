# Every web read answers a store that cannot be reached with the one 503 "Repo not ready" (fixed detail), except the SSE stream and factVersionDate; a lens single-fact read on a READ mount answers its missing-fact 404 instead, and lens fan-out routes fail whole with the 503

DECISION (user rulings 2026-10-24, one PR; built in PR #620, merged as 1a860912 on dev, re-read there).

1. Every web read helper built on RepoInstance.WithRead returns WithRead's error as-is, and its handler answers it through writeStoreError (storeUnavailable first): 503, title "Repo not ready", fixed detail "the repo's store is not available; try again" (never the error text). The unreachable `svc == nil` branches are deleted. Two EXCEPTIONS stay best-effort on purpose: handleHALEvents (the SSE stream has already started; a store that cannot be reached opens it with head "") and factVersionDate (a missing date, not a failed request).

2. LENS single-fact reads (the fact itself, the /commits /incoming /outgoing sub-resource gate, and the `.knomit/` system-file read) split by the ROLE of the mount the path resolved to:
- the WRITE mount (a bare path, or kb://<id12>/ naming the write repo) answers the same 503 "Repo not ready" as every other route; every lens has a write mount, so this reveals no topology;
- a READ mount keeps the byte-identical missing-fact 404 (lensFactNotFound, echoing the REQUESTED path), because a 503 would let a caller iterating candidate ids read "mounted, store down" off the status (an unmounted id answers 404).
The role is decided ONCE, in resolveLensFactMount (readMount = rt.RI != bind.Write(), the instance and not whether the path was qualified); lensFactMount.answersNotFound(err) = errFactNotFound || (readMount && storeUnavailable(err)) is asked at both readFact exits and, as writeSystemFile's hideUnavailable argument, by the `.knomit/` read.

3. Lens FAN-OUT routes (facts, search, completions, motifs, motif cluster, stats, topics) fail the WHOLE request with the 503 when any selected mount's store is unavailable. That follows RFC 9.1 ("a lens must never silently shrink its read set"; kb/invariants/web/lens/eab51403.md, kb/invariants/web/lens/parallel-fanout-determinism/b9c7ab96.md, kb/decisions/lens/no-federation-metadata-in-responses/de09fac3.md). Before this PR they answered 200 and silently dropped the mount. Judged not an oracle: the detail names no mount, the lens's mounts are listed on GET /lenses/{lens}, an unknown repo= name is already a 422 and an unmounted kb:// path filter already a 400.

4. Every other store-unavailable answer is unified to that one 503: origin GET, PUT (prior-origin read), PATCH upstream; changes and the experiment diff (they no longer leak raw error text); experiment list/open/actions, pushed-branches, synthesis Pin and writeExperimentError. ErrNotOpen through writeLifecycleProblem is also the same 503: in production ErrNotOpen means the machine's Open stage is not live, which is exactly when Acquire refuses with ErrStoreUnavailable. (A bare test instance with no machine answers ErrNotOpen whatever its store; every instance a running Manager builds has a machine.) ErrClosed, ErrUnavailable and ErrManagerStopped are DIFFERENT conditions and keep their own answers ("Repo unavailable", "Server stopping", PATCH upstream 500).

5. The 403 eligibility message ("Read-only branch" on a write to a closed machine-backed repo) is OUT of scope and stays on triage (kb/gotchas/repos/lifecycle/write-403-before-store-503/624fcd06.md).

CONSEQUENCE: a new web read helper on ri.WithRead must return its error; a new lens route that ADDRESSES one mount by a client-supplied id must hide a storeUnavailable error behind its not-found answer when that mount is a READ mount, and a lens route that fans out must let the error fail the request.

DOES NOT MEAN: that every route can reach the 503 over HTTP (see kb/gotchas/web/store-unavailable-503-reachability for the unreachable and quirky edges), or that a bare lens fact path always 404s on store-down: on the write mount it is the 503. NOT CHANGED, flagged: the experiment sync's post-sync re-read (`_ = ri.WithRead` in handlers_experiments.go) still answers 204 if the store goes away, and the git smart-HTTP route answers text/plain 503 "repo store unavailable" (git protocol, not problem+json).
