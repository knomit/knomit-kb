# The 421 loopback-Host refusal says WHICH knomit.toml to edit ("this instance's") and drops the threat-model clauses; the config file's path is deliberately NOT in the body

**Context (2026-09-27).** The designer, on a two-machine tailnet, received the 421 from the knomit on machine B (behind `tailscale serve`, which connects from 127.0.0.1 and forwards Host unchanged), edited `~/.knomit/knomit.toml` on machine A, restarted A, and still got the 421. The check itself was correct (this refs the pre-fix middleware text at L135-L140); the message sent the operator to the wrong file. The choice of 421 over 403 and the placement of the check inside AuthMiddleware's anonymous branch are separate, earlier decisions and are unchanged here; this decision is about the TEXT of the detail only.

**Options considered.**
1. Keep the long detail as is: `…; a web page served from that name may not act as the local user. If this is your own proxy or tunnel, add the name to [auth].loopback_hosts in knomit.toml — anyone who reaches knomit through it then holds [auth].loopback_default`.
2. Shorten to the rule and the command, and say whose file: `this knomit instance does not answer loopback requests for Host "<host>". If this is your own proxy or tunnel, add the name to [auth].loopback_hosts in this instance's knomit.toml and restart it.`
3. Same as 2 but include the instance's actual config path (`<home>/knomit.toml`) so the operator can copy it.

**Rationale.** Option 1 failed in practice: "in knomit.toml" does not say which instance's, and the two threat-model clauses are reasoning, not instruction; they already live in full as the comment above `loopback_hosts` in the shipped knomit.toml template, which is where the operator lands anyway. The agent-facing-text convention (rule and command, never the threat model) applies to operator-facing error bodies for the same reason. Option 3 was rejected on security grounds: a DNS-rebound page is SAME-ORIGIN with this response (its name resolves to 127.0.0.1) and can read the body, so the data root and the username in it would leak to exactly the party the check exists to refuse. "This instance's" is the pointer that fixes the misdirection without the leak.

**The choice.** Option 2. Status 421, headers and branch structure unchanged. The diag port's shorter variant (server.go L142-L146) stays aligned. The host-guard test keeps asserting the body names the Host and `[auth].loopback_hosts`, and additionally asserts the body contains neither `loopback_default` nor a filesystem path.

**Non-scope.** This does not relax `hostguard.LoopbackHostOK` (exact names only, no port, no wildcard) and does not authorize putting `cfg.Home` or any path into ANY unauthenticated response body. It also does not change the knomit.toml template comment, which is the right home for the loopback_default warning.

**Misreading to avoid.** "The message is too terse now, add the reason back" re-creates option 1; the reason belongs beside the config key, not in a 421 a browser shows.
