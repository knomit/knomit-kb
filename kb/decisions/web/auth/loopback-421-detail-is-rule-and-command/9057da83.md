# The 421 loopback-Host refusal says WHICH knomit.toml to edit ("this instance's") and drops the threat-model clauses; the config file's path is deliberately NOT in the body

**Context (2026-09-27).** The designer, on a two-machine tailnet, received the 421 from the knomit on machine B (behind `tailscale serve`, which connects from 127.0.0.1 and forwards Host unchanged), edited `~/.knomit/knomit.toml` on machine A, restarted A, and still got the 421. The check itself was correct (this refs the pre-fix middleware text at L135-L140); the message sent the operator to the wrong file. The choice of 421 over 403 and the placement of the check inside AuthMiddleware's anonymous branch are separate, earlier decisions and are unchanged here; this decision is about the TEXT of the detail only.

**Options considered.**
1. Keep the long detail as is: `…; a web page served from that name may not act as the local user. If this is your own proxy or tunnel, add the name to [auth].loopback_hosts in knomit.toml — anyone who reaches knomit through it then holds [auth].loopback_default`.
2. Shorten to the rule and the command, and say whose file: `this knomit instance does not answer loopback requests for Host "<host>". If this is your own proxy or tunnel, add the name to [auth].loopback_hosts in this instance's knomit.toml and restart it.`
3. Same as 2 but include the instance's actual config path (`<home>/knomit.toml`) so the operator can copy it.

**Rationale.** Option 1 failed in practice: "in knomit.toml" does not say which instance's, and the two threat-model clauses are reasoning, not instruction. The reasoning's home is the Go doc comment on `AuthConfig.LoopbackHosts` (internal/config/config.go L345-L361); this repo ships NO knomit.toml template (an annotated one on the designer's machine is not from this repo; an earlier revision of this fact wrongly said the template carried the explanation). The agent-facing-text convention (rule and command, never the threat model) applies to operator-facing error bodies for the same reason. Option 3 was rejected on security grounds: a DNS-rebound page is SAME-ORIGIN with this response (its name resolves to 127.0.0.1) and can read the body, so the data root and the username in it would leak to exactly the party the check exists to refuse. "This instance's" is the pointer that fixes the misdirection without the leak. "Restart it" is correct because config is not hot-reloaded.

**The choice.** Option 2. Status 421, title "Misdirected Request", `instance` = r.URL.Path, headers and branch structure unchanged. The diag port's variant (server.go L142-L146) is ALIGNED to the same shape: it too drops its threat-model parenthetical ("shared with the main listener, where a loopback request carrying that Host is treated as the anonymous local user") and gains "in this instance's knomit.toml and restart it", staying text/plain via http.Error. The host-guard test keeps asserting the body names the Host and `[auth].loopback_hosts`, and additionally parses the problem body and asserts the `detail` field contains neither `loopback_default` nor '/' or '\' (the raw body always contains a slash in `instance`, so the negative check must be on `detail`; a real Host can never contain either character because net/http rejects it with 400 first).

**Non-scope.** This does not relax `hostguard.LoopbackHostOK` (exact names only, no port, no wildcard) and does not authorize putting `cfg.Home`, the loopback_hosts list, the bind address or any path into ANY unauthenticated response body. It does not add a knomit.toml template.

**Misreading to avoid.** "The message is too terse now, add the reason back" re-creates option 1; the reason belongs on the config key's doc comment, not in a 421 a browser shows.
