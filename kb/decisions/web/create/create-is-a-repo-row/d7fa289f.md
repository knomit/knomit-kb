# A create in flight IS a repository, not a bespoke surface: the rail draws it as a repo row with one chip (creating / cancelling / failed) and no inline controls, the repo details page renders in creating mode (progress + the one allowed action first; Remote, Danger zone, Rebuild and edit controls withheld), the wizard enters the repo's browse view as soon as the index phase is reached, and the running count lives in the status footer as a generic "N repositories being created"

Decided with the user across three review rounds of PR #230 (supersedes the earlier pending-rows + top-bar-indicator design). What was REJECTED, in the user's words: rail rows reading "knomit [creating] [details] [cancel]" ("all jumbled up and squished"); a lingering "[cancelled] [dismiss]" row ("I KNOW it was cancelled"); a footer reading "Creating…" beside "Cancelling…"; a separate create page while the Knowledge table opened the ordinary settings page with Archive/Rename for a repo on its way out; a "1" badge in the top bar; repo names in the footer status ("there could be multiple repos in progress — maybe a generic status"). What stands: (1) RAIL — PendingCreateRow renders with the rail's own listItem style, hue dot, name, ONE chip, whole row is the click target; once the repo is registered the repo's OWN row carries the chip (activeCreateByRepo in useRepoCreates), one row not two, and the create flag wins over the index chip; cancelled jobs are never drawn (server omits them, pendingCreates drops them too). (2) PAGE — the regular RepoDetail in creating mode: subtitle 'creating'/'cancelling', the CreateProgress block with "Cancel create" or disabled "Cancelling…" above Description; Description/License read-only, Agent branch, Agent access and Browse shown; Remote, Danger zone (rename/archive), Rebuild and every edit control withheld; the block disappears IN PLACE when the job turns done (verified in Chromium: same page read "repository settings" with Archive/Rename/Rebuild back, no navigation). Before registration the same page shows only header + progress. Failed before registration: error + Dismiss; failed after (index error): repo kept, normal page with the index chip in error. (3) ENTRY — the wizard calls onDone as soon as the job reports the index phase AND the repo exists (createRepoIsRegistered), landing on the browse view with the banner "Creating… search and lists may be incomplete until this finishes" (measured +0.3s after the server reported the index phase); a cancelling job never navigates. (4) FOOTER — StatusFooter shows "1 repository being created" / "N repositories being created" (cancelling counted), clickable to Manage, absent at zero; CreateIndicator and its top-bar badge are deleted. (5) The top-bar switcher carries the same chip but only renders as a dropdown with >1 repo or a lens, so with a single repo the banner and footer carry the state. Misreading to avoid: "flag the repo" does not mean a new section or view — every route (rail, Knowledge table, switcher) must land on the same page in the same state.
