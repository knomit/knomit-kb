# The review step asks join-or-subscribe with the Source step's segmented control, not radios or side-by-side compare cards

Context: the create-repository wizard's Review step (web/src/StepReview.tsx) offers join vs subscribe when the chosen branch is already a knowledge base. It shipped as two browser-default <input type=radio> at 16px under the "What will happen" caption, so an INPUT was filed as a consequence and looked like a heading.

Options considered (three mocks, PR #193):
- A. Segmented choice, then the plan: reuse StepSource's segment control (segGroup/segment/segDot/segSub) under its own caption "How to attach", a segDisclosure rule, then "What will happen" and the list for the chosen mode. Warning as a bordered amber box under Join only.
- B. Compare both modes side by side as selectable cards, each carrying its own consequence list, with the push warning living inside the Join card so the reader sees why Subscribe is safer before choosing. Most informative, most text.
- C. Receipt-style summary strip (name, remote, branch, mode toggle) then a shorter plan. Densest, but restates inputs, which the component's own contract (review states consequences, not inputs) forbids.

Choice: A. The designer's stated reason: it matches what the wizard already does for the local-vs-remote choice on the Source step. Two peer binaries asked with two different widgets would make the wizard look like two wizards. B was NOT rejected on merit (it was the implementer's recommendation); consistency with the existing control won.

Non-scope: this does not make segmented buttons the answer for every choice in the web UI. It applies to a wizard step that asks ONE binary and discloses what the answer means underneath. It also does not settle the accessibility question: the segment control uses role=group + aria-pressed buttons, which lose the radio semantics (mutual exclusion, arrow-key roving focus, one tab stop) the old markup had. That is known debt to be fixed in BOTH steps at once, not one.
