# The index-rebuild job routes read the repo's TaskHub and nothing else (the synthesis-run kind they once shared it with is deleted); the web JobRegistry (never constructed in production) is deleted; DELETE on a job CANCELS it and there is no pending state; TaskPublisher.PublishTask records a terminal before publishing it (TaskHub.Start and Cancel are deleted)

User ruling 2026-10-24 (web split step 12c0, PR #623). Before: Server.JobRegistry was never set in production (NewJobRegistry had no production caller; app.go built web.Server without it) and nothing called Register/Complete/SetProgress, so every registry branch was dead and API clients saw: list always 200 {count:0, jobs:[]} even while a job ran; GET {id} only via the hub fallback; DELETE always 204 deleting nothing (never the documented 409); GET {id}/events for an unknown id skipped its 404 (guarded by `jr != nil`) and opened a stream that never ended.

After: JobRegistry, NewJobRegistry, JobEntry, JobProgress, Server.JobRegistry and job_registry.go are gone. Every job route reads ri.TaskHub() through hubTask (hubOps: op `synth` for synthesis-run, `rebuild` for index-rebuild; an id of the other op is 404):
- list: TaskHub.Tasks(op) - the running task first, then the last terminal one; at most TWO, empty before the first run. The hub keeps nothing older.
- get: 200 for the running or last terminal task of that kind; anything else 404.
- DELETE CANCELS (user direction 2026-10-24: "we still need to cancel a running or pending job"; resolved: there is NO pending state). TaskHub holds only the running job and the last done job per op, so the only job DELETE can act on is the kind's running one. synthesis-run: TaskHub.Cancel(id) cancels the running Start task's context; 202 with the job still running; it stops at its next model call and usually ends in error with a cancellation message, but a run already finishing may end done. index-rebuild: the lifecycle machine's CancelIndex (same path as POST /repos/{repo}/index:cancel), 202 after the drain, job error "indexing cancelled". Finished job: 409 "Job already finished". Unknown or other-kind id: 404. Nothing is removed from the list. No queue exists to take a job out of: a second synth start is 409 (single-flight), a rebuild replaces or absorbs the running one.
- HUB ORDERING (review F1): TaskHub.Start's emit records a terminal (delete active and cancels entry, set lastDone) under h.mu BEFORE publishing it, as publishTask does. The old publish-first order let a Subscribe see the task running and miss its end, hanging a per-job stream. Regression: TestTaskHub_SubscribeRacingATerminalNeverMissesIt (a stress loop that must subscribe repeatedly; one Subscribe per iteration never hit the window).
- events: subscribe FIRST, then hubTask(id): 404 before any stream if not held; else write it and end if terminal, otherwise follow the channel to the terminal. With the ordering fix this has no window (the Subscribe snapshot is not used: it hides the last terminal while the op runs again).
- Job body is {id, kind, state: running|done|error, error?}: no created_at, updated_at, progress or _links.

CONSEQUENCES. A client polling a job must expect 404 once two newer jobs of the kind have finished, and after a restart (in-memory only). Progress is on the branch events stream, not in the job body.

MISREADINGS. "DELETE removes the job": no, it cancels the running job; the job stays listed as finished (error). "202 means it has stopped": for synthesis no (still running until the run sees the context); for a rebuild yes (CancelIndex drains). "The list is a job history": no, at most the running and the last finished job. "There is a pending/queued job to delete": no. "There is a registry fallback": no, the hub is the only record.

MOVED (12c, PR #627, merge 97ae7c19, re-read there): the handlers named above (handleListJobs, handleGetJob, handleDeleteJob, handleJobEvents, hubTask, hubOps) are unchanged but now live in internal/edge/web/api/jobs/handlers.go, mounted by jobs.Mount (see kb/architecture/web/api-jobs/1bd359b5.md). The contract tests (handlers_jobs_hub_test.go and siblings) stay in internal/edge/web and run through the full router; jobEnvelope there is a test-side copy of the wire shape.

MOVED (14b, PR #631, merge 37dc65d5, re-read there): TaskHub is now events.TaskHub in internal/corpus/repos/events/hub.go. The job routes still read the consumer hub only (Task, Tasks, Cancel via hubTask, unchanged in internal/edge/web/api/jobs/handlers.go); the publishing methods that could fabricate a running or done task (PublishTask, CancelTasks) are on events.TaskPublisher and uncallable from web, which is what keeps this contract (DELETE cancels the running job, 409 only for a finished one) from being broken by a handler. See kb/decisions/repos/events/hub-publisher-split/f6d5c104.md.

CHANGED BY PR7 (chore/remove-synthesis-job): the synthesis-run kind is gone, so everything above about it is history: hubOps is `{"index-rebuild": "rebuild"}` only (no `synth`), the synthesis DELETE branch (TaskHub.Cancel of the running Start task, 202 while it finishes its model call) and the "second synth start is 409" single-flight are deleted, and an id of the OTHER kind can no longer be 404 because there is one kind. DELETE is the lifecycle machine's CancelIndex path only. The contract that survives: the hub is the only record, a list is at most the running task and the last terminal one, DELETE cancels (202 after the drain) and never removes, a finished job is 409, an unknown id is 404, and events subscribe first then read. TaskHub itself is unchanged and still generic, but at PR7's HEAD `TaskHub.Start` and `TaskHub.Cancel` have NO production caller (only events/hub_terminal_order_test.go and the web job tests call them): the lifecycle machine records the rebuild through TaskPublisher, and the synthesis job was the last production Start. They were kept then as the hub's own contract; chore/taskhub-unused deleted them (see DELETED below). Tests that use op "synth" (now published through PublishTask, e.g. sse_bounded_test.go) use it as an arbitrary label, except where they read through a job route, which needs op "rebuild".

DELETED BY PR #791 (chore/taskhub-unused, merged as 02d41850, re-read there): `TaskHub.Start`, `TaskHub.Cancel`, the hub's `emit` helper, its `cancels` map, `counter` and task ctx, and `TaskPublisher.CancelTasks` are gone. CancelTasks only ever cancelled tasks Start had launched, so openStage.Exit's call to it was already a no-op and was removed with it. The hub now runs no work: every task is recorded through `TaskPublisher.PublishTask` (in production, only the lifecycle machine's index rebuild), and the consumer `*TaskHub` offers Subscribe, Task and Tasks only. HUB ORDERING above now lives in PublishTask: it records a terminal (deletes the active entry, sets lastDone) under h.mu BEFORE publishing, and TestTaskHub_SubscribeRacingATerminalNeverMissesIt now races a PublishTask terminal (verified to fail when PublishTask publishes first). The web job tests (handlers_jobs_hub_test.go, sse_bounded_test.go, api/jobs/keepalive_test.go) fabricate jobs through PublishTask, not Start. CONSEQUENCE: a job a consumer can see is one the repos parent published; nothing outside repos can start or cancel a hub task. MISREADING: "the job routes lost cancel": no, DELETE was already CancelIndex only (PR7). NOTHING GUARDS re-adding a consumer-side Start: a sabotage that restored Start on *TaskHub with a production caller in api/jobs passed archtest and every events and jobs test; TestEventPublishers_NotExposed guards only publisher exposure.
