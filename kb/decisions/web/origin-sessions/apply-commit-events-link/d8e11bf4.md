# Origin-session apply and commit: the POST starts the run and returns a link to its events, followed by a GET event stream

Issue #509. On the Windows desktop, Wails v3.0.0 GA buffers every asset-handler response until the handler returns, so streamApply/streamCommit (web/src/api.ts), which read SSE progress from the POST's own response body, showed progress only at the end. GET event streams are live on Windows because the desktop carries them over the knomit-sse Wails Stream.

**Options considered**
1. The POST starts the apply/commit and returns at once with a link to its progress events (HAL `_links`, plus a `Location` header if that fits the codebase's convention); the page follows the link with openEventStream (GET SSE). CHOSEN.
2. A GET that starts the action. Rejected: event streams auto-reconnect (EventSource and knomit-sse backoff), so a reconnect would re-run a write; commit is also behind the admin gate, and both take request bodies.
3. A second, desktop-only Wails Stream whose first frame carries the POST method, path and body. Rejected: a platform branch and a second transport to maintain.
4. Accept end-only progress on Windows. Rejected.
5. A separate synthesis-run-style job-id scheme. Rejected as unnecessary IF a session runs at most one apply/commit at a time: the link may then be session-scoped (`.../origin-sessions/{sessionID}/apply/events`, `/commit/events`). If that is not true, a per-run id is used instead.

**Rationale**: a GET that only reads (and replays) buffered events is safe to reconnect; the write happens exactly once on the POST. One design works on every transport, so there is no platform branch.

**The choice**: the POST validates and refuses as before, then starts the run detached from its request context and answers 202 with the events link; the run's events are buffered so a late or reconnecting GET gets the whole sequence from the start, then live events, then completion. Same design in browser, macOS, Linux and Windows desktop.

**Non-scope**: this does NOT change what apply and commit do, nor their pre-stream refusals (409 'Repo is indexing' with the cancel_indexing body, validation errors, the admin gate) which still come back on the POST itself before anything starts. It does NOT widen the knomit-sse adapter: its GET-only path check stays. It does NOT mean every POST that streams should become POST+link; it was chosen for these two routes because the desktop could not stream them.

**As built (PR #754, branch commit 91d72b34)**: the session-scoped link holds because a session runs at most one apply/commit at a time: the run holds the session's exclusive use (sessionManager.Use) for its life, and the run registry refuses a POST while the session has an unfinished run of either kind with 409 'Session busy' (carrying that run's events link) instead of letting it wait on the use and run again. Routes: POST .../apply and .../commit answer 202 + `_links.events` + Location; GET .../apply/events and .../commit/events. Dropping the session cancels an apply but not a commit. Mechanism and its consequences: kb/architecture/web/origin-sessions/runs/68ab1cec.md. The only production consumer of these routes is web/src/api.ts (streamApply/streamCommit, signatures unchanged).
