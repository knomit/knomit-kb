# A count taken from a truncated page renders as a LOWER BOUND ("2+") — never as the page size ("500+"), which would assert a different quantity that is not what the number means

Decided 2026-09-17 during the PR #217 review, after the bounded list made this reachable at all.

THE SITUATION. The Manage tab badge counts LIVE sessions out of a page the server now bounds at 500. Once the page can be cut, the badge's number stops being a total.

OPTIONS CONSIDERED

1. Leave the bare count. REJECTED, and it is the failure the bounding work exists to remove: it would read as exact, standing beside a table that openly says "showing the N most recent of more". A silently cut number is worse than an unbounded read, because it looks finished.
2. Render the PAGE SIZE with a plus — "500+". REJECTED. The badge counts live sessions WITHIN the page, so on a truncated page of 500 with two live it would read "500+" for a quantity that is two. It asserts something about the page size, which is not what the number means, and is a different false claim rather than a fixed one.
3. Render the count as a LOWER BOUND — "2+". CHOSEN. "At least two live" is exactly what a live count taken from a partial page supports.

SHAPE. `truncated` travels WITH the count rather than being inferred: `ManageSessions` passes it through `onLiveCount`, and `RepoManager`'s own read takes it off the response directly, because that path counts while the page is closed. The marker follows the data and does not latch — a `+` left from an earlier truncated read would claim there is more after the condition has gone — and a failed read clears it along with the count.

CHECKED, not assumed (reviewer, same round): the badge hides at zero, and a truncated page cannot be concealing live sessions beyond the cut, because the page is ordered `last_seen_at DESC` and liveness derives from that same column — so everything dropped is older than everything kept. There is no "0" that should have been "0+".

THE GENERAL RULE, which is the part worth carrying: any consumer of a bounded list must carry the truncation marker WITH the number. Bounding a read and marking it in one place while another consumer keeps rendering from the same page is how the silent failure comes back one component over.

WHAT THIS DOES NOT MEAN: it is not an argument for showing a plus whenever a limit exists. An exhausted page renders the exact number, and the test that asserts THAT is the control — without it, a badge that appended `+` unconditionally would satisfy every other assertion.
