# The Sessions UI goes live through a browser-side SSE change stream (GET /api/v1/sessions/events, id+kind pings only) that triggers a throttled list re-read; the 30 s poll stays as fallback — this does NOT reopen the bridge-side held-stream question

**Context (2026-09-15):** the maintainer reported "sessions are not refreshed live, so I have to reload/refresh the UI to see them." At HEAD d3a005be the Sessions page polled GET /api/v1/sessions every 30 s plus on window focus; the Manage tab badge read the live count once on open plus on focus; the Overview "N live sessions" line read once on mount. The 2026-09-14 client-session design plan (line "Refresh by polling every 30s while open, plus on window focus. No SSE.") is superseded by this report.

**Options considered:**
1. Poll faster (every few seconds) on the page, badge and overview. Cheap, but three readers hammering control.db (SetMaxOpenConns(1)) and still not instant.
2. Server-pushed SSE stream carrying full session rows. Instant, but duplicates the ReadOnly redaction logic on a second surface and patches UI rows from event data instead of the list.
3. Server-pushed SSE stream carrying ONLY change pings ({id, kind: touch|init|end|purge}); the UI re-reads the (already redacted) list on each ping; the existing 30 s poll stays as the fallback while the stream is down and as the clock that advances the ages.

**Rationale:** option 3 gives sub-second visibility with a payload that cannot leak operator details, keeps the list handler the single source of truth, reuses the goob observable pattern of internal/repos/hub.go and the SSE handler shape of internal/web/handlers_events.go, and matches the pattern the browser already uses (one branch-events SSE stream per tab). Option 1 was rejected as a load multiplier that is still not live; option 2 as a redaction and consistency liability.

**The choice:** a change hub inside internal/client/sessions.Store publishing after each successful Touch/SetClientInfo/End/Purge (End and Purge only when rows were affected); GET /api/v1/sessions/events (SSE; `ready` on connect; `session` pings; keepalive every 30 s; per-write deadline so a client that stops draining ends the subscription instead of growing goob's unbounded buffer; 503 when the store is nil; allowed under ReadOnly); `_links.events` on the sessions collection and an OpenAPI entry; a web hook that subscribes, throttles, and closes on unmount; the Sessions page keeps its poll; the Manage badge subscribes only while the Sessions page is NOT open so exactly one sessions stream exists per tab; ManageOverview takes the live count as a prop instead of fetching.

**Re-read policy BY KIND (added after the PR #197 review found a 30x load amplification):** `init`, `end`, `purge` re-read immediately (leading edge) because they are what makes a row appear or disappear; `touch` is trailing-only on a 5 s window because it only moves last_seen, request_count and idle→live. The FIRST `ready` per connection is ignored (both consumers already read on mount); a later `ready` is a reconnect and re-reads because events may have been missed. Bound to design against: one list read per 5 s per open Manage tab while any session is busy, plus one per appear/disappear. The comment in handleHALClientSessions that reasons about control.db serialisation must state this bound, not the old 30 s poll rate.

**Non-scope / named misreading:** kb/decisions/mcp/client-sessions/liveness-last-seen/6de8f3d9.md forbids a held stream, heartbeat or reconnect between the MCP CLIENT (bridge or direct HTTP caller) and the server for presence. This decision is about the BROWSER subscribing to the server and changes nothing about presence: last_seen_at remains the only source of live/idle/dead and the bridge is untouched. The old ManageSessions.tsx header comment ("No SSE by design", citing the liveness decision) was a misreading of that decision's scope and is corrected as part of this work. Do not read this fact as "knomit now streams presence": it streams change notifications to a UI that then reads the same list it always did. Do not read it as "every touch re-reads the list" either: that is the amplification the by-kind policy exists to prevent.
