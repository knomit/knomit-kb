# Esc in a chat: while a turn runs it is Stop and never closes the side panel; with no turn running it closes the panel unless focus is in a text field; Cmd/Ctrl+[ goes back from anywhere

Two window-level keydown listeners both see Escape in a chat: ChatPanel's (PR 2: Stop, only while state.running) and ChatSidePanel's (mounted only while the panel is open). They do not coordinate through preventDefault; the panel's listener reads the chat's `running` prop and returns early when a turn runs, so Stop always wins and the panel stays open. ChatPanel treats the side panel as part of the chat: its focus test is against the nearest [data-chat-scope] element (ChatFacet's chat-columns row, holding the column AND the panel), so Esc while a turn runs with focus on a panel tab or button is Stop too (before this, focus inside the panel made Esc do nothing). With no turn running, Esc closes the panel unless document.activeElement is a TEXTAREA, INPUT, SELECT or contentEditable (the composer), where Esc does nothing. A chat that is not on screen (Settings tab, display:none ancestor) ignores both. Cmd+[ (and Ctrl+[) goes back through the panel's history from anywhere including the composer and calls preventDefault so the browser's own history shortcut is suppressed. App.tsx's own Escape (CLEAR_FILTERS / return-to-now) and Cmd+[ (NAV_BACK) are gated by browseShown, so they never run over a chat. Consequence: a person who wants to close the panel during a running turn must stop it first (one Esc), then Esc again. Does NOT mean Esc is swallowed: after the turn ends the same key closes the panel. A dialog that listens on window without preventDefault is invisible to both listeners.
