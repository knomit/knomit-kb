# Esc in a chat: while a turn runs it is Stop and never closes the side panel; with no turn running it closes the panel unless focus is in a text field

Two window-level keydown listeners both see Escape in a chat: ChatPanel's (PR 2: Stop, only while state.running) and ChatSidePanel's (mounted only while the panel is open). The panel's listener reads the chat's `running` and returns early when a turn runs, AND ChatPanel calls preventDefault when its Esc was Stop, which the panel's listener honours. Both are needed: a browser runs microtasks between listeners, so React has already rendered running:false by the time the panel's listener runs, and without the mark the one key both stopped the turn and closed the panel. jsdom does not run them there, so only a real browser shows this. Stop always wins and the panel stays open. The panel's materialize Focus takes Esc in the capture phase, ahead of both (kb/gotchas/web/ui/materialize-focus/3fedfce6.md), and yields it while a turn runs (MatFocusScope.yieldsEsc): Focus stays on and the key is Stop. With no turn running in Focus, the first Esc leaves Focus and the next closes the panel. The chat column is folded rather than undisplayed in Focus, because ChatPanel reads display to know its chat is on screen. ChatPanel treats the side panel as part of the chat, the nearest [data-chat-scope] element (ChatFacet's chat-columns row, holding the column AND the panel), so Esc while a turn runs with focus on a panel tab or button is Stop too. Focus outside that scope refuses Stop only in a field (TEXTAREA, INPUT, SELECT, contentEditable) or inside a [role=dialog] or [role=menu], which have an Esc of their own. On a plain control out there (the gear) it is Stop: otherwise Focus yielded, ChatPanel returned and the panel returned, and the key did nothing. With no turn running, Esc closes the panel unless document.activeElement is a TEXTAREA, INPUT, SELECT or contentEditable (the composer), where Esc does nothing. A chat that is not on screen (Settings tab, display:none ancestor) ignores both. The panel has no history, so Cmd+[ does nothing there (kb/decisions/ui/chat/panel-browse-chrome/64aa3076.md). App.tsx's own Escape (CLEAR_FILTERS / return-to-now) and Cmd+[ (NAV_BACK) are gated by browseShown, so they never run over a chat. Consequence: a person who wants to close the panel during a running turn must stop it first (one Esc), then Esc again. Does NOT mean Esc is swallowed: after the turn ends the same key closes the panel. A dialog that listens on window without preventDefault is invisible to both listeners. LIMITS (as merged): the field, [role=dialog] and [role=menu] exemptions from Stop apply only to focus OUTSIDE the chat scope; inside the column or the panel a running turn's Esc is Stop wherever focus is, unless something already called preventDefault. The panel's close-Esc checks only typingIn (any field, anywhere on the page) and defaultPrevented, not dialogs or menus, so a menu that does not preventDefault its Esc also closes the panel. Both listeners skip a chat with a display:none ancestor (shown / isShown). The field test is one helper, typingIn in chatPanelState.ts, shared by both listeners; the menu and hidden-chat cases are covered by ChatSidePanel.test.tsx.
