# Every chat element that opens the side panel only OPENS it: clicking the item already shown leaves the panel open on it; the panel closes only by its × and Esc (user, 2026-11-09)

User, 2026-11-09: "clicking on something twice should not make the right panel close". The openers and their behaviour:
- a tool-call row (ChatToolGroup -> ChatFacet onSelect): USED TO TOGGLE (same callId dispatched `close`); now always dispatches `open` with the result entry. A second click keeps the same ChatResultPanel mounted, with no second fetch, and the row stays marked aria-current="true". It used aria-pressed while it toggled; an open-only selector of the panel's entry is not a toggle button, so it is aria-current now (review of #811).
- a fact chip (FactLink -> onOpenFact), a commit chip (CommitLink -> onOpenCommit), and a fact row in the panel's commit view (ChatCommitView onOpenFact): always dispatched `open`; unchanged.
- the panel's own band menus (cites, motifs, connections): they never open a panel entry; a pick lands in Browse (onBrowse).
Closing stays with the panel: its × (chat-panel-close) and Esc when no turn is running (see the Esc fact). panelReducer has no toggle action; a new opener must dispatch `open`, never `close` on a repeat click.

Does NOT mean a second click re-reads the entry: the same entry stays mounted, so nothing is fetched again.

**How the open entry is marked.** Every opener whose entry the panel shows carries aria-current="true" (absent otherwise): the tool row, and the fact and commit chips, which also keep data-open (the highlight hook; it is not drawn for fact chips). Several fact chips citing the open fact are all current. A new opener marks its open state the same way, never with aria-pressed.
