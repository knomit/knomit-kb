# A streaming chat answer draws its fact links as chips while it streams: the turn still running is resolved like a finished one, and only CLOSED inline-code spans are candidates

**Why they diverged (until 2026-11-09).** ChatPanel passed `null` to useTurnFacts for the last turn while `state.running`, and useTurnFacts never asks about a null answer. The renderer itself was the same for both (ReactMarkdown with remarkFactLinks appended after chatLivePlugins or chatPlugins), so a streaming answer's `kb/...md` spans had no resolved fact to mark and stayed plain code until turn_done, then all became chips at once (user screenshot t-fly). The exclusion was deliberate ("its text is still growing") but was not needed: the lookup does not depend on the text, only on its candidates.

**The rule now.** Every turn's answer is passed, the running one included. useTurnFacts' effect depends on the JSON of each turn's (prefer list, candidates), not on the text, so:
- a delta that closes no new inline-code span re-runs nothing and asks nothing;
- a delta that closes one asks for that handle only (cached and in-flight handles are skipped), one POST /facts/resolve per new candidate set, never per delta;
- a path whose closing backtick has not arrived is not a candidate (factCandidates' span regex needs the closing run) and remark does not parse it as inlineCode either, so it is shown as literal text, never as a chip or a broken link;
- a chip is not remounted by later deltas (the streamed text only grows at the end, so earlier hast positions are stable).

**Why the final rendering is identical.** A streaming turn's prefer list (turnPrefer) changes only when it makes another call, and a new call moves all the text before it into that call's group as its lead (ChatPanel blocksOf), out of answerOf. So the answer text a chip sits in is always read under the turn's final prefer list, and the cache entry it used mid-stream is the one the finished turn uses. A test compares the streamed turn's final chat-text HTML with a fresh mount of the same finished answer.

**Accepted cost.** A handle asked mid-stream that resolves to nothing is cached as null for the page (as for finished turns). Since a turn's own writes are tool calls that complete before the text after them, a fact the turn wrote is normally on the branch before the text naming it arrives.

**Does NOT mean** a fact link in a group's lead text (interstitial text before a tool call) is a chip: lead text is not part of answerOf and is never resolved, streaming or not.
