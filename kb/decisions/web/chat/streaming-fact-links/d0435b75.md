# A streaming chat answer draws its fact links as chips while it streams: the turn still running is resolved like a finished one, and only CLOSED inline-code spans are candidates

**Why they diverged (until 2026-11-09).** ChatPanel passed `null` to useTurnFacts for the last turn while `state.running`, and useTurnFacts never asks about a null answer. The renderer itself was the same for both (ReactMarkdown with remarkFactLinks appended after chatLivePlugins or chatPlugins), so a streaming answer's `kb/...md` spans had no resolved fact to mark and stayed plain code until turn_done, then all became chips at once (user screenshot t-fly). The exclusion was deliberate ("its text is still growing") but was not needed: the lookup does not depend on the text, only on its candidates.

**The rule now.** Every turn's answer is passed, the running one included. What keeps a stream from asking per delta is useTurnFacts' skip of handles already in the cache or in flight (`cache.has(k) || inFlight.has(k)`), not the effect's key:
- a delta that closes no new inline-code span asks nothing;
- a delta that closes one asks for that handle only, one POST /facts/resolve per new candidate set, never per delta.
The effect is keyed on the JSON of each turn's (prefer list, candidates), which only saves re-running it; a text-keyed effect would re-run per delta and still ask nothing (review of #811 confirmed by sabotage). The key is not pinned by a test; the skip is.
- a path whose closing backtick has not arrived is not a candidate (factCandidates' span regex needs the closing run) and remark does not parse it as inlineCode either, so it is shown as literal text, never as a chip or a broken link;
- a chip is not remounted by later deltas (the streamed text only grows at the end, so earlier hast positions are stable).

**Why the final rendering is identical, and the assumption it rests on.** The cache is keyed by the turn's prefer list (turnPrefer), and NOTHING in the code pins that list while an answer streams: it changes on each new call, and when a still-running call settles (a running call has isError false and counts; if it then fails it is dropped). It holds in practice only because of the ORDER models stream in: text after a tool call arrives after that call's result, and text before a call becomes the call's group lead (ChatPanel blocksOf), out of answerOf. So the answer text a chip sits in is read under the turn's settled list. If a provider ever streamed answer text while a call of the same turn was still running, a change of list would re-key its handles: they would be asked again and show as code until the new answer came back. (Excluding running calls from the list was considered and rejected: it rests on the same ordering, since a call that settles successfully still changes the list.) A test compares the streamed turn's final chat-text HTML with a fresh mount of the same finished answer.

**Accepted cost.** A handle asked mid-stream that resolves to nothing is cached as null for the page (as for finished turns). Since a turn's own writes are tool calls that complete before the text after them, a fact the turn wrote is normally on the branch before the text naming it arrives.

**Does NOT mean** a fact link in a group's lead text (interstitial text before a tool call) is a chip: lead text is not part of answerOf and is never resolved, streaming or not.
