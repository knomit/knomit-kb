# The web page opens ONE chat events stream (GET /chats/events) and routes by the `chat` tag, because a stream per chat exhausts the browser's 6 HTTP/1.1 connections per origin: 5 chats starved the page, 9 hung every fetch

Why: browsers allow 6 concurrent HTTP/1.1 connections per origin and http://localhost is HTTP/1.1. With one SSE connection per mounted chat a rail worker measured the page starved (blank transcript, no live rail) at 5 chats and every fetch, including the rail's DELETE, hanging at 9. The server therefore serves GET /chats/events for all the caller's chats, tagging each event with `chat`; web/src/chatEvents.ts opens it once on the first subscription, routes each event to the subscribers of its chat (drops events for chats nobody shows), and closes it one microtask after the last subscriber leaves (so StrictMode's effect replay keeps the connection). A page-level `ready` (every connect = every reconnect) goes to EVERY subscriber, and a chat subscribing after the stream's first ready is told once, so each ChatFacet reloads its snapshot; the snapshot stays authoritative. Browser-checked: 20 chats in one tab, one chats/events request, a turn streamed, DELETE 204 in ~40 ms with the rail updated by chat_end.

Choice, ready page-level not per chat: the server has nothing per-chat to say at connect, a per-chat ready would need a frame per chat plus one for every chat created later, and the client already knows what it shows.

Does NOT mean the stream is per chat or that a new chat needs a new connection; a feature that wants chat events subscribes through subscribeChatEvents, never openEventStream directly. A browser with many TABS still holds one stream per tab, so ~5 tabs on one origin can reach the 6-connection limit again.
