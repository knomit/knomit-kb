# A commit the repo does not hold is 404 with problem code commit_not_in_repo on every commit-anchored REST route and on the commit-log cursors, never 500; the web UI shows a no-version state for it and keeps asOf

RULING (user, 2026-11-03): a commit the repo does not hold is a 404, never a 500 (500 is only for internal errors). When a lens re-select moves the open fact to another mount while history is open, the view does NOT drop back to live. The server answers something the UI can recognise, and the UI shows that state.

WHAT WAS BUILT (PR #747):
- Server: problems keep `type: about:blank`. The distinguishing value is the RFC 9457 extension member `code: commit_not_in_repo`, following the existing `code` convention (fleet: auth_invalid, not_this_fleet...). Title is "Commit not found".
- refuseUnknownCommit (api/kb) runs on /commits/{sha}, /commits/{sha}/facts/* (fact, /incoming, /outgoing, /materialize[/pages], .knomit/ system files) and /commits/{sha}/topics[/*]. It runs AFTER the route's #718/#720 query-parameter refusal (so a malformed query is still 400 first) and BEFORE any read at the commit. It uses Service.HasCommit, which is true only for a full 40-hex hash the object store holds. A short hash, a non-hash and another repo's commit are all 404 with the code.
- model.ErrCommitNotFound is mapped by httpx.WriteStoreError to the same 404+code. Two places return it. The first is the commit-log cursors after/from/before on /commits and /facts/{path}/commits (the lens fact /commits shares that handler): there the storer returns storegit.ErrCursorNotInLog (no commit_log row), and vcs.CommitLogQuery wraps it because archtest forbids store/git importing model. vcs wraps it as ErrCommitNotFound ONLY when the object store lacks the commit. A held commit that changed no file has zero rows by design: it becomes model.ErrCommitNotInLog, 400 `code: commit_not_in_log`, never commit_not_in_repo (see kb/gotchas/store/commit-log/cursor-null/df24c26d.md). The second is vcs.ReadFileAtCommit for an unknown hash.
- Web: fetchJSON, the explain edge fetches and factDiff attach `status` and `code` to the thrown Error (the message is unchanged). isCommitNotInRepo(err) means status 404 AND that code. RightPanel's anchored read and FactDiffView render NoVersionAtCommit (copy is a PLACEHOLDER) and dispatch no asOf change.

CONSEQUENCES: a client must branch on `code`, not on the 404 alone. A missing FACT at a commit the repo holds is still 404 "Fact not found" WITHOUT the code. In factDiff a plain 404 side is still an absent side (null), and only the code-404 rejects. A new commit-anchored route must call refuseUnknownCommit after its param refusal, or it reintroduces the 500 (readFileAtCommit: object not found) or a misleading "Fact not found".

WHAT THIS DOES NOT MEAN: it does not mean every unknown-commit input is 404. /changes?since=<unknown> stays 400 "Unknown since" (model.ErrUnknownSince), and /fleet/drop-commit keeps its own invalid_commit 422. It does not mean the server checks that the commit is on the requested BRANCH: only that the repo's object store holds it.

BREADCRUMB (same PR, found while checking this state in a browser): the current crumb showed the PREVIOUS fact's title. RightPanel's CACHE_FACT_TITLE effect paired the new factPath with the stale `fact`, which the panel keeps until a new one loads. In this state no new fact ever loads. The cache now requires the loaded fact to belong to the open path (showFact / factLoadedFor). See kb/gotchas/web/ui/title-cache-stale-fact/0a617661.md.

RULING (user, 2026-11-03, after review): option (a) is approved. A commit-log cursor (after/from/before) naming a commit the repo HOLDS that has no commit_log row answers 400 `code: commit_not_in_log` ("Commit has no log position"). It does not answer commit_not_in_repo, and it is not positioned by the commit's timestamp.
