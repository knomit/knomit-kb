# The Content-Type rule on request bodies is PARTIAL defence in depth by decision: it covers body-carrying mutations only, and EVERY body-less mutation (deletes, repo-create cancel, archived restore and experiment actions sent with an empty body, origin-session commit, synthesis/index runs) stays protected by the loopback Origin check alone against a browser that omits Origin; a mutation-wide non-simple-request rule was considered and not chosen

CONTEXT. The loopback Origin check refuses any mutation that carries a foreign Origin. What still reaches a JSON handler cross-site is only a browser request with NO Origin header — browsers old enough to omit it on a cross-site form POST (Firefox before 70). A modern browser always sends Origin on these requests, so the second layer is defence in depth, not a fix for a live gap. (authDisabled also skips the check but is test-only, unexported, and has no config knob.)

OPTIONS.
1. Content-Type rule in a shared body decoder (chosen): 415 unless application/json, applied where a handler reads a body.
2. A mutation-wide non-simple-request rule in the anonymous branch: require application/json OR a custom header (e.g. X-Knomit-Client, which the OAuth approval gate already uses) on EVERY mutation, bodied or not. This closes the old-browser residual completely, but it changes every client that mutates without a body (the web UI's experiment commit/rollback/sync, curl in scripts, e2e fixtures), and was out of scope for the issue.

THE CHOICE (approved by the user). Option 1 only. A Content-Type rule cannot see a request with no body, so it is PARTIAL by construction.

THE NAMED RESIDUAL — do not re-litigate it as an oversight. Against a browser that sends no Origin, every body-less mutation remains protected by the Origin check alone. The complete list from router.go at the change:
- DELETE /archived/{id} (purge), and POST /archived/{id}/restore sent with an EMPTY body (its body is optional, so an empty-body POST still un-archives on the Origin check alone)
- DELETE /repo-creates/{id} (dismiss) and POST /repo-creates/{id}:cancel
- DELETE /repos/{repo} (archive), DELETE .../origin, DELETE .../origin-sessions/{id}, POST .../origin-sessions/{id}/commit
- experiment DELETE, commit, rollback and sync sent with an empty body (their body is optional)
- DELETE .../facts/*
- POST .../synthesis-runs (the handler ignores the body the SPA sends) and DELETE .../synthesis-runs/{id}
- POST .../index-rebuilds and DELETE .../index-rebuilds/{id}
- DELETE /lenses/{lens}
OAuth deny is body-less too, but browserProof already requires application/json on it from a browser. A NEW body-less mutation route joins this list automatically; a new route that reads a body must use decodeJSON (kb/conventions/web/http/json-request-body). Closing the residual means option 2, which is a separate decision needing the user and a client audit.

ALSO DECIDED. The malformed-body 400 title is unified to "Invalid request body" (previously also "Invalid body", "Invalid request", and "Invalid resolutions" for a non-JSON commit body); every oversize body answers 413 "Request body too large". Unknown fields stay accepted.

WHAT THIS DOES NOT MEAN. It does not say body-less mutations are unprotected — the Origin check refuses a foreign Origin on every method but GET/HEAD/OPTIONS. It does not rule out option 2 later; it records that it was weighed and not taken now.
