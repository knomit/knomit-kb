# SUPERSEDED 2026-09-17 — the original design for the unscoped /api/v1/mcp mount, which recorded a session's chosen repo or lens in a control.db table keyed by Mcp-Session-Id; the mount survives, the session key does not

**SUPERSEDED on 2026-09-17 by kb/decisions/mcp/session-binding/per-bind-handle (PR #215, merged b3cebeb4). Read that fact for the current design; read this one only for the history of how the mount came to exist.**

WHAT SURVIVED: the unscoped `/api/v1/mcp` mount itself, `knomit_bind` as the tool that selects a target, the uid PinID (`repo:<uid>` / `lens:<uid>`) as the stored value, the fail-closed rule for every tool but `knomit_repos`, and the refusal of `knomit_bind` on a URL-scoped mount.

WHAT WAS DELETED: option 3 below — the `session_bindings` table keyed by `Mcp-Session-Id`, and the middleware that resolved it. A client may share ONE connection, and therefore one session id, across several independent logical jobs; Claude Desktop does exactly that for Cowork sessions. On 2026-09-17 two jobs' binds overwrote each other seven times in half an hour and five writes were served from the wrong target. Binding is now named per CALL by an opaque server-minted handle, and nothing resolves a binding from `Mcp-Session-Id` at all. The initialize body-peek described below went with the lookup it existed to protect. The `session_bindings` table still exists in the schema but is abandoned and unread.

The reasoning below was sound on its own terms and is preserved unedited; what it got wrong was treating the MCP session id as an identifier of the caller. MCP revision 2026-07-28 removed protocol sessions outright for that reason (SEP-2567).

---

Decided 2026-09-16 (session with the designer) when adding dynamic repo switching to the MCP bridge. Shipped in PR #209 (merged 897e17ed); amended the same day by PR #210, which made knomit_repos the binding-free discovery tool (see the AMENDMENT below and kb/decisions/mcp/session-binding/catalog-tool).

OPTIONS CONSIDERED

1. Keep URL-scoped mounts only and have the bridge reconnect to a different URL on switch. Rejected: the MCP session id is minted per endpoint by initialize, so a switch would be a new session and lose the host's view of instructions and cursors; and it puts routing logic in the bridge, which by decision has no reconnect/recovery.
2. Store the selected binding as a column on client_sessions. Rejected: the standing invariant says every field of client_sessions is inferred from traffic and the row must never gate anything. A selected binding is deliberately client-ASSERTED routing state, and mixing it into an observational table would blur that line.
3. A separate `session_bindings` table in control.db keyed by Mcp-Session-Id, value in the existing PinID format (`repo:<uid>` / `lens:<uid>`), resolved by a middleware on a new unscoped mount `/api/v1/mcp`, set by a new tool. CHOSEN [and superseded 2026-09-17 — see the banner above].

Tool NAME options: knomit_use, knomit_switch, knomit_checkout, knomit_bind. Chose `knomit_bind` because the server-side object is literally a repos.Binding, its pin is the binding identity, and the planned experiments feature (a branch cut from the agent branch, later committed or merged on the user's say-so) changes only the WRITE branch inside the same binding — so the tool later grows an optional experiment argument rather than being replaced.

RATIONALE FOR THE SHAPE

- The value is the uid-based PinID, not a name, so a repo or lens rename never breaks a live session — the same reason tool cursors pin on PinID. [STILL TRUE: the handle maps to the same uid pin.]
- It is DURABLE (control.db, purged with the client_sessions retention) because the server's stateless session-id manager accepts ids across a restart, so a bridge that outlives a restart must keep its selection. [STILL TRUE of handles, which are durable and purged on their own last-used time.]
- Write eligibility needs NO new logic: the middleware builds the binding with NewBindingOfRepo(ri, "") which defaults to ri.ReadBranch() — the agent branch, or the followed upstream for a subscription — and writeOK comes from WritableBranch, false for a subscription or an ontology-less repo. Every write tool already gates on Binding.WriteOK(). Reads on a subscription work; writes fail with the read-only-view error. Lenses resolve through NewBindingOfLens as on the lens mount. [STILL TRUE: the handle gate resolves through the same constructors.]
- Unbound sessions fail CLOSED for every tool that operates on a binding: query, explain, learn, update, retract, review, hypothesize error with "no repo or lens bound to this session; call knomit_bind" via repos.RequireBinding(ctx), which replaced the panicking BindingFromContext in handlers. A stored pin that no longer resolves is surfaced as that tool error, not an HTTP 4xx, so JSON-RPC framing survives. AMENDMENT (PR #210): knomit_repos is the exception by design — it is the discovery tool, works unbound, and reports an unresolvable stored pin as `bound.status: "unresolvable"` rather than as an error, because it is precisely the tool an agent calls to find out what to bind to or what went wrong. [STILL TRUE, with the error text changed; note `bound.binding` is now `bound.name`.]
- The middleware skips lookup and resolution on an initialize request (bounded body peek, POST-only, fail open), because mcp-go mints a fresh id on every initialize and ignores the inbound Mcp-Session-Id, so any state keyed on the header belongs to a DIFFERENT session during initialize; the AfterInitialize hook returns the unbound instructions first on the session-scoped mount as a second barrier. [DELETED — there is no session lookup left for it to protect.]
- knomit_bind returns the mount table of the binding it just made (the `bound` section of knomit_repos — NOT the whole server catalogue) PLUS the full BindingInstructions text, because initialize on the unscoped mount can only carry the default ontology and MCP cannot re-send instructions mid-session — the chosen repo's topics and profile addendum must ride back in the tool result. [STILL TRUE, and it now returns the handle first.]
- On a URL-scoped mount knomit_bind REFUSES ("this endpoint is bound by its URL; connect to /api/v1/mcp"); the context carries a session-scoped marker set only by the new mount. [STILL TRUE, and a `binding` argument there is now refused too.]
- Once bound a session can be re-bound to another repo/lens but never returned to unbound: the designer chose no clear/unbind form. [CHANGED: re-binding now MINTS A SECOND HANDLE and leaves the first valid, rather than overwriting.]
- tools/list is per server, so write tools stay listed on a read-only binding and fail at call time — accepted.
- The bridge enters session-bound mode only when NEITHER --repo nor --lens was given; an explicitly empty flag exits 2, and a leading positional must parse as an http(s) URL with a host (a mistyped subcommand must not become a base URL).
- The read-only gate's route allowlist admits the bare /api/v1/mcp mount, so a read_only server still serves knomit_bind.

NON-SCOPE

The `claude init` and `antigravity init` scaffolders are unchanged — this decision does not add a no-scope scaffold form. Experiments themselves (branch cut/commit/merge) are future work; only the tool name was chosen with them in mind. This does not change the session-id manager (still stateless) and does not make session_bindings an authorization mechanism: anyone can already reach any repo by URL, so binding grants nothing new, but a known session id can redirect that session's writes — the network remains the boundary. [That last clause is precisely the hazard that was realised on 2026-09-17, by accident rather than by an attacker.]
