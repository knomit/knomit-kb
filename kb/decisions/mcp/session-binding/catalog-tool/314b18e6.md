# knomit_catalog is a separate binding-free MCP tool listing every repo and lens the server serves — knomit_repos was NOT overloaded to answer that question, and the catalogue is a cheap index that never reads README per repo

Decided 2026-09-16, right after the session-bound mount (knomit_bind) shipped in PR #209, when the designer observed that an MCP client had no way to learn which knowledge bases exist: knomit_repos reports the mounts behind the CURRENT binding, and on the unscoped /api/v1/mcp mount a fresh session has no binding, so an agent could not discover what names knomit_bind accepts. The catalogue existed only on REST (GET /api/v1/repos, GET /api/v1/lenses). Shipped in PR #210.

OPTIONS CONSIDERED

1. Make knomit_repos return the server catalogue when the session is unbound (or with an `all` flag). Rejected: knomit_repos answers "what is behind this binding", its output shape is pinned by tests and by the session instructions' mount table, and giving one tool two meanings depending on state is the one-name-many-referents trap; a bound session would still need a flag to reach the catalogue.
2. Make knomit_bind with no arguments return the catalogue instead of an argument error. Rejected: conflates a query with a mutation and hides the listing behind a tool whose name says it changes state.
3. A new read-only tool `knomit_catalog`, registered on EVERY mount with write=false (so a read-only demo server still has it), requiring no binding. CHOSEN.

SHAPE

- repos: name, 12-hex root-commit id (the kb://<id>/ addressing id, per the three-identifier gotcha — NOT the registry uid, which is membership and never typed by a user), mode (`subscribe`, `writable`, or `read-only` when the ontology could not be established), agent_branch when there is one, read_branch, ontology root, profile; registered-but-unopenable repos are listed too with their Unavailable reason and detail so the agent knows why a bind would fail, mirroring the REST list which keeps broken repos visible. An unavailable repo has NO id key at all (`json:"id,omitempty"`, the writedest.go precedent): the root-commit id only exists once the store has opened, and the uid must never be printed in its place.
- lenses: name, description, write repo name, mounts as repo name at branch (Manager.RepoLabel for a member with no live instance: registry name, uid only when the registry has no row).
- bound: the session's current binding as kind + name; omitted when unbound. When the stored pin no longer resolves, bound carries `status: "unresolvable"` and the error text, kind from the pin prefix, and a name ONLY when the registry still has a real one (looked up directly by uid, NOT through RepoLabel, whose fallback would print the uid). The pin reaches the tool through a Pin field on SessionBindingError, set at every construction site in ResolveSessionBinding; empty Pin means the failure was not about a specific pin (e.g. the store lookup itself failed).
- THE UID RULE, stated precisely because the slogan version misleads: a registry uid must never appear in a NAME or ID field an agent might feed back to knomit_bind (repos[].id, lenses[].write, mounts[].repo, bound.name). It MAY appear in error prose (bound.error, tool error text) describing what died, because with no registry row the uid is the only handle left — that prose comes from ResolveSessionBinding via RepoLabel's fallback and is correct #209 behaviour, not a leak. Tests assert on the fields, not on the prose.
- It is a CHEAP INDEX: no README read per repo. The REST layer deliberately keeps the repo LIST free of per-repo git reads (description and license are single-repo GET only), and the catalogue follows the same rule — the bound knowledge base's full instructions arrive in the knomit_bind result. (ri.ID() may still do one cached root-commit read on a miss; that is parity with the REST list, not a per-fact read.)
- Built from internal/repos accessors only (Manager.ForEach, Manager.Unavailable, LensRegistry.List, Registry.Get for profile), because internal/mcp cannot import internal/web. A LensRegistry.List failure is a logged tool error, never an empty `lenses` list an agent would read as "no lens exists".
- LOCK RULE, found by the review gate on the first cut: Manager.ForEach holds m.mu.RLock for the whole iteration, and sync.RWMutex is not reentrant, so NOTHING inside the callback may call another Manager method (Repos(), GetByUID, Get, RepoLabel — profileFor calls Repos()). A pending writer between the outer and inner RLock wedges the whole Manager permanently, from an unauthenticated tool call. Snapshot names and instances inside ForEach and do all per-repo work after it returns, exactly as handleHALRepos does. Both regression guards were mutation-verified: the concurrency test hangs to a timeout when the bad call is reintroduced, and the structural guard checks for `mgr` in any form (the first version checked `mgr.` and missed `profileFor(mgr, ri)`).
- The unbound instructions addendum and the knomit_bind description both point at knomit_catalog as the way to learn the names.

WEIGHED CONSEQUENCE, accepted: because the tool is registered on every mount, a read-only public demo now discloses agent_branch, read_branch, ontology_root, profile and full lens topology to any unauthenticated MCP caller, more than GET /api/v1/repos shows. This is consistent with the project's posture (the network is the boundary; /git is deliberately unauthenticated; the session-bound mount is not an authorization boundary), and it will be revisited only when server-wide auth is designed.

This is distinct from the architecture fact enumerating the registered tool set (kb/architecture/mcp/tool-catalog), which counts tools and must be updated as the count grows; this fact records why a tenth tool exists and what it must and must not do.

NON-SCOPE: no create/delete of repos or lenses over MCP; no README/description per repo in the listing; no filtering arguments in v1.
