# knomit_repos is the ONE discovery tool: it needs no binding, always returns {repos, lenses, bound?} listing every repo and lens the server serves, and knomit_catalog was folded into it before merge — a cheap index, no paging at tens of entries

Decided 2026-09-16 in two steps. First, right after the session-bound mount (knomit_bind) shipped in PR #209, the designer observed that an MCP client had no way to learn which knowledge bases exist: knomit_repos reported only the mounts behind the CURRENT binding, and on the unscoped /api/v1/mcp mount a fresh session has none. A separate `knomit_catalog` tool was designed and built (PR #210). Second, before #210 merged, the designer asked why two discovery tools existed, and the answer was that the distinction ("what is behind my binding" vs "what exists on the server") is one nested section, not a second tool. The two were MERGED into knomit_repos; knomit_catalog never existed on dev.

OPTIONS CONSIDERED (cumulative)

1. A separate knomit_catalog tool alongside knomit_repos. Built first, then REJECTED: two discovery tools cost the agent context on every session and hand it a choice it does not need; the shapes overlapped.
2. Make knomit_bind with no arguments return the catalogue. Rejected: conflates a query with a mutation.
3. knomit_repos absorbs the catalogue, keeps its name, and returns ONE shape fixed per STATE. CHOSEN. The earlier objection ("one name, two meanings") does not apply because each key's presence reports a fact about the world (is the session bound; did the lens lookup succeed), not a mode the tool is in. The name stays `knomit_repos` because the session instructions already say it lists every mounted repo's id and no rename ripples through prose, skills or hooks; its description says it lists lenses too.

SHAPE

- repos: every repo on the server: name, 12-hex root-commit id (the kb://<id>/ addressing id, NOT the registry uid), mode (`subscribe`, `writable`, or `read-only` when the ontology could not be established), agent_branch when there is one, read_branch, ontology root, profile; registered-but-unopenable repos listed with their Unavailable reason and detail and NO id key at all (`json:"id,omitempty"`, the writedest.go precedent).
- lenses: every lens with name, description, write repo name, mounts as repo name at branch (Manager.RepoLabel for a member with no live instance). On SUCCESS the key is always present, `[]` when the server has none. On a LensRegistry failure (not started, or List error) the key is ABSENT and `lenses_error` carries the text, with a log.Warn — repos and bound are still returned, so a URL-scoped caller never loses its own mount table over an unrelated control-plane error, and an agent can never read a failure as "no lens exists". The field is `*[]reposLens` with omitempty on purpose: encoding/json treats a nil slice and an empty slice identically, so a plain `[]T` + omitempty would omit the key for a server with zero lenses and collapse the two states; a nil POINTER omits, a pointer to an empty slice emits `[]`. A zero-lenses success test pins this.
- bound: present only when the session has a binding. Carries the pre-#210 knomit_repos contract — the binding name and the mount table with role (read / read+write, read+write only when rt.RI == b.Write() && b.WriteOK()), read branch, write_branch on the read+write row, source slug, mode — plus, when the stored pin no longer resolves, `status: "unresolvable"`, the error text, kind from the pin prefix, and a name only when the registry still has a real one (looked up directly by uid, never through RepoLabel's uid fallback). The pin reaches the tool through the Pin field on SessionBindingError. knomit_bind returns ONLY this bound section (built by the same shared function) plus BindingInstructions, never the whole catalogue.
- THE UID RULE, stated precisely because the slogan misleads: a registry uid must never appear in a NAME or ID field an agent might feed back to knomit_bind (repos[].id, lenses[].write, mounts[].repo, bound.name). It MAY appear in error prose (bound.error, lenses_error, tool error text), because with no registry row the uid is the only handle left. Tests assert on the fields, not on the prose.
- CHEAP INDEX: no README/LICENSE read per repo, same rule as the REST repo list. This is also the size guard.
- NO PAGING. At tens of repos and lenses the whole listing is ~150 bytes per row, so 50 repos + 20 lenses is ~12 KB, inside what a tool result carries and smaller than a query page. Paging would add cursor state for a list the agent scans in one go. If the listing ever grows past that, the intended growth path is a `match` argument (case-insensitive substring on names), NOT paging. Not added now.
- Built from internal/corpus/repos accessors only (Manager.ForEach, Manager.Unavailable, LensRegistry.List, Registry.Get for profile).
- LOCK RULE, found by the review gate on the first cut: Manager.ForEach holds m.mu.RLock for the whole iteration and sync.RWMutex is not reentrant, so NOTHING inside the callback may call another Manager method (Repos(), GetByUID, Get, RepoLabel). Snapshot inside ForEach; do all per-repo work after it returns, as handleHALRepos does. Both regression guards were mutation-verified (the structural guard checks for `mgr` in any form; the first version checked `mgr.` and missed `profileFor(mgr, ri)`).
- Registered on every mount with write=false (a read-only demo server still has it); requires no binding; never panics on an empty context. Every OTHER tool fails closed when unbound; knomit_repos is the deliberate exception — do not "restore consistency" by making it fail too. Tool count right after this merge was 9 tools, 4 read-only; that count has since moved (see the 2026-10-12 note at the end) and must be read from toolRegistrationsWith, not from this decision.
- The unbound instructions addendum and the knomit_bind description both point at knomit_repos as the way to learn the names.

WEIGHED CONSEQUENCE, accepted: because the tool is on every mount, a read-only public demo discloses agent_branch, read_branch, ontology_root, profile and full lens topology to any unauthenticated MCP caller, more than GET /api/v1/repos shows. Consistent with the project's posture (the network is the boundary; /git is deliberately unauthenticated; the session-bound mount is not an authorization boundary); revisited only when server-wide auth is designed.

This is distinct from the tool set itself: the authoritative list is `toolRegistrationsWith` in internal/edge/mcp/server.go (the former architecture fact kb/architecture/mcp/tool-catalog was merged into this one and retracted, so do not look for it).

NON-SCOPE: no create/delete of repos or lenses over MCP; no README/description per repo; no filtering or paging arguments in v1.

This decision's claims about knomit_repos (no binding, write=false, folded catalogue) still hold at HEAD: it is registered with gateOptional and write=false. The ref to the retracted fact kb/architecture/mcp/tool-catalog/e1986a28.md was removed and a HEAD-pinned ref to server.go added. Do NOT read '6 read-only' as 'six read tools need a handle': knomit_repos is gateOptional and knomit_bind is gateUngated.

Updated by PR #664 (2026-10-27): knomit_repos returns {repos, lenses, bound?, endpoint?}. `endpoint` ({kind, name, bind}) appears ONLY on a URL-scoped endpoint (endpointOf in repos.go): bind says either that knomit_bind there mints a handle that changes only the branch and that calls without `binding` use the URL's repo or lens, or, on a route naming a branch, "fixed to branch X by the URL; knomit_bind is not available here". On a scoped endpoint `bound` describes the handle when one is passed (or `unresolvable`), else the URL's binding; a failed handle is checked FIRST in boundOf because the scoped context still carries the URL's binding and would otherwise tell the caller its handle worked. knomit_repos still needs no binding and always answers on a scoped endpoint, including when it is given a bad one.
