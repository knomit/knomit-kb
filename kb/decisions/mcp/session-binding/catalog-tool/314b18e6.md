# knomit_catalog is a separate binding-free MCP tool listing every repo and lens the server serves — knomit_repos was NOT overloaded to answer that question, and the catalogue is a cheap index that never reads README per repo

Decided 2026-09-16, right after the session-bound mount (knomit_bind) shipped in PR #209, when the designer observed that an MCP client had no way to learn which knowledge bases exist: knomit_repos reports the mounts behind the CURRENT binding, and on the unscoped /api/v1/mcp mount a fresh session has no binding, so an agent could not discover what names knomit_bind accepts. The catalogue existed only on REST (GET /api/v1/repos, GET /api/v1/lenses).

OPTIONS CONSIDERED

1. Make knomit_repos return the server catalogue when the session is unbound (or with an `all` flag). Rejected: knomit_repos answers "what is behind this binding", its output shape is pinned by tests and by the session instructions' mount table, and giving one tool two meanings depending on state is the one-name-many-referents trap; a bound session would still need a flag to reach the catalogue.
2. Make knomit_bind with no arguments return the catalogue instead of an argument error. Rejected: conflates a query with a mutation and hides the listing behind a tool whose name says it changes state.
3. A new read-only tool `knomit_catalog`, registered on EVERY mount with write=false (so a read-only demo server still has it), requiring no binding. CHOSEN.

SHAPE

- repos: name, 12-hex root-commit id (the kb://<id>/ addressing id, per the three-identifier gotcha — NOT the registry uid, which is membership and never typed by a user), mode (`subscribe`, `writable`, or `read-only` when the ontology could not be established), agent_branch when there is one, read_branch, ontology root, profile; registered-but-unopenable repos are listed too with their Unavailable reason and detail so the agent knows why a bind would fail, mirroring the REST list which keeps broken repos visible.
- lenses: name, description, write repo name, mounts as repo name at branch.
- bound: the session's current binding as kind + name, so the agent sees where it is before switching; omitted when unbound.
- It is a CHEAP INDEX: no README read per repo. The REST layer deliberately keeps the repo LIST free of per-repo git reads (description and license are single-repo GET only), and the catalogue follows the same rule — the bound knowledge base's full instructions arrive in the knomit_bind result.
- Built from internal/repos accessors only (Manager.ForEach, Manager.Unavailable, LensRegistry.List, Registry.Get for profile), because internal/mcp cannot import internal/web.
- The unbound instructions addendum and the knomit_bind description both point at knomit_catalog as the way to learn the names.

This is distinct from the architecture fact enumerating the registered tool set (kb/architecture/mcp/tool-catalog), which counts tools and must be updated as the count grows; this fact records why a tenth tool exists and what it must and must not do.

NON-SCOPE: no create/delete of repos or lenses over MCP; no README/description per repo in the listing; no filtering arguments in v1.
