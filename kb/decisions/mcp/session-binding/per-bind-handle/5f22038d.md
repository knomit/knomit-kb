# Session-keyed binding was replaced by a per-bind opaque handle required as a `binding` argument on every call — chosen because the client will NEVER identify the logical session, so the only thing that can name the caller is a value the caller carries

Decided 2026-09-17 with the designer, after the cross-binding incident; shipped in PR #215 (merged b3cebeb4). It SUPERSEDES the session-keyed design in kb/decisions/mcp/session-binding/unscoped-mount.

OPTIONS CONSIDERED

1. Keep the `Mcp-Session-Id` key and have the client disambiguate. REJECTED as impossible, not merely undesirable: nothing on the wire identifies a Cowork session — no `_meta`, no header — and Claude Desktop consumes its own session id for permission gating and never forwards it. Waiting for a client fix would be waiting for something the protocol has moved away from.
2. Handle OPTIONAL, falling back to the session binding when absent. REJECTED: the fallback is the bug. A caller that forgets the handle gets the other job's target silently, which is the exact incident with an extra step. An absent handle must fail, not degrade.
3. Pass the REPO OR LENS NAME per call instead of a handle. REJECTED: a name is guessable and therefore hallucinable — a model that has seen `knomit_repos` output can produce a plausible-looking valid value and be routed somewhere it never bound. It also loses rename-safety, which the uid pin gives for free.
4. Scope by configuration — one bridge process per job, each with `--repo`/`--lens`. REJECTED as a fix, though it remains a legitimate deployment: it cannot be enforced server-side, and the failure it leaves is silent. The server must be correct on a connection that is shared, because it cannot tell whether it is.
5. A server-minted OPAQUE HANDLE, returned by `knomit_bind` and required as a `binding` argument on every other call. CHOSEN.

WHY IT WON. The handle is minted by the server, so it cannot be hallucinated into a valid one; it is carried by the caller, so it survives any amount of connection sharing; and MCP revision 2026-07-28, which removed protocol sessions outright, prescribes exactly this shape — "servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments" (SEP-2567). Every `knomit_bind` call mints a FRESH handle and old handles stay valid, so binding twice yields two working handles rather than one silently retargeted one.

TWO CALLS MADE DURING IMPLEMENTATION, both deliberate and both worth knowing:

- A non-empty branch on a LENS pin is REFUSED rather than ignored. A lens pins a branch per mount at resolve time, so a single branch names nothing coherent across its members, and ignoring it would serve a branch other than the one the handle names. Unreachable today (`knomit_bind` always stores `''`), which is precisely why it must fail loudly if it ever becomes reachable.
- `knomit_repos`' `bound.binding` was RENAMED to `bound.name`. `binding` now means the opaque handle everywhere on the surface; one key meaning a handle in one result and a repo name in another is the single most expensive ambiguity available here, because the agent that resolves it the wrong way sends the NAME as its handle and gets a hard failure it cannot read its way out of. `boundSection` already carried a `Name` field for the unresolvable state, so this collapsed two spellings of one thing rather than inventing a field.

NON-SCOPE: no authentication of handles to a principal (knomit has none), no expiry policy beyond the retention purge, and no change to the URL-scoped mounts' behaviour. Per-handle branch switching is future work — the column exists, the tool argument does not.
