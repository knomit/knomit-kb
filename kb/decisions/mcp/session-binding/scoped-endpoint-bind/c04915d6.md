# Decided (user, 2026-10-27): routes whose URL names a branch (main, a foreign agent branch, exp:<name>, /lenses/{l}/experiments/{n}) REFUSE knomit_bind and every handle, and do not advertise them — extending mount-eligibility-from-the-route from session state to handles

Decided with the user on 2026-10-27 (review of PR #664 raised it as a narrowing the user had not asked for; the user confirmed it).

OPTIONS. (a) Literal reading of "whatever an unbound kb can bind to": a `…/branches/main/mcp` connection could mint a handle and move around. (b) Treat every URL that names a branch as an ADDRESS: bind and handles are refused there. CHOSEN.

RULE. On a URL-scoped route that names a specific branch (main, a foreign agent branch, `…/branches/exp:<name>/mcp`, `/lenses/{l}/experiments/{n}/mcp`) knomit_bind is refused, EVERY non-empty `binding` handle is refused (errFixedEndpoint), tools/list does NOT list knomit_bind, and `binding` is described as not accepted. The predicate is the same mount-session marker as kb/invariants/mcp/experiments/mount-eligibility-from-the-route/711ae81d.md (MountSessionFromContext plain), so session state and handles cannot drift apart.

WHY. That invariant (711ae81d) is about SESSION state; applying it to handles is THIS decision, not a consequence of the invariant. Reasons: such URLs are addresses of one branch; `kb --repo/--lens` never produces them (the bridge discovers the agent branch); and the error is actionable. An advertised tool that always fails was the original bug.

WHAT THIS DOES NOT MEAN. Empty `binding` ("") still passes on these routes: it counts as absent. It does not change what these URLs serve.
