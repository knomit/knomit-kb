# Decided (user, 2026-10-27): a --repo/--lens (URL-scoped) MCP endpoint ALLOWS knomit_bind, but only to change the BRANCH; it behaves like the unscoped endpoint except that every bind, and every handle it accepts, is confined to the endpoint's own repo or lens

Decided with the user on 2026-10-27 and shipped in PR #664.

TRIGGER. A small local model (LFM2.5 2.6B via ollmcp) on `kb --lens knomit-dev` looped forever calling knomit_bind. On a scoped endpoint bind always failed and every tool refused any `binding` (even "", knomit_repos included), yet tools/list advertised knomit_bind and `binding` everywhere: an advertised tool that always fails.

OPTIONS CONSIDERED. (a) Leave bind refused on scoped endpoints and only fix the advertising (do not list it). Rejected: the real need is subagents that share ONE bridge connection and must each have their own experiment; the only per-caller key that survives connection sharing is a handle (kb/incidents/mcp/session-binding/cross-binding-overwrite), and the session-keyed row cannot separate them. (b) Allow bind on scoped endpoints with full repo/lens selection. Rejected: the URL already fixed the knowledge base, and letting a scoped connection move to another repo or lens is the 2026-09-17 incident. (c) Allow bind on scoped endpoints, changing only the BRANCH within the URL's repo or lens. CHOSEN.

THE USER'S RULINGS. 1. A kb started with --repo or --lens ALLOWS knomit_bind, only to change the branch; repo or lens stays the one in the URL, so subagents sharing one bridge each get their own experiment branch and their own handle. 2. Whatever an unbound kb can bind to is bindable here, within the connection's repo or lens. Today that is the default branch or an EXISTING experiment (`experiment:` resume); knomit_bind takes no branch argument. 3. On a lens only the WRITE repo moves; read mounts stay. 4. knomit_experiment open/commit/rollback/sync through a handle behave EXACTLY as on the unscoped endpoint (same code path, handle_experiments).

ALSO DECIDED. `binding` is optional on a scoped endpoint: absent or "" means the URL's own binding, and "" counts as absent on BOTH endpoint kinds. A handle minted on another endpoint, or for another repo or lens, is refused. knomit_repos always answers on a scoped endpoint. Tool schemas and `binding` texts are per endpoint kind, and errors are short and actionable ("…the user must restart the bridge with --repo <name>. Do not retry."). A handle belongs to the ENDPOINT (the --repo/--lens URL's mount), not to a connection or session: a handle minted by one `kb --repo X` bridge works in a second bridge for the same X. Harmless, handles are not authorization.

WHAT THIS DOES NOT MEAN. Not that a scoped endpoint may switch repos or lenses. Not that binding_handles.branch is live (it stays inert; the experiment rides on handle_experiments). Not that session state now routes handles: the handle is keyed on itself. Not that two callers who pass NO handle are separated: they still share the session-keyed row (the accepted hazard in kb/decisions/experiments/mcp-surface). Committing or rolling back another caller's experiment by name does not eject you (kb/invariants/mcp/experiments/commit-by-name-keeps-caller).
