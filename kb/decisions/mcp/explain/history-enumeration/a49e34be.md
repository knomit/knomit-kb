# knomit_explain history lists only the commits that changed the fact's content, as one linear list, newest change first by author date — never the first-parent line

CONTEXT. knomit_explain's `history` was built by RevisionsBefore, a first-parent walk. When writes reach a branch through PR merges (agent branch -> main, then the agent branch catches up), the walk listed one merge commit per PR and hid every write behind it, then ended with more_available:false. On the agentic-engineering crawl-state slot it showed 15 of 36 writes. First-parent is right for RESOLUTION (which version is live at C) and wrong for ENUMERATION (every version the fact has had).

OPTIONS CONSIDERED.
1. Git's TREESAME simplification in topological order, with the parent-0 side of a real branch point walked first (the agent's proposal). REJECTED by the user: it exposes topology tie-break rules to callers.
2. A linear list of content changes ordered by when each change was made. CHOSEN.
3. Keep first-parent and only document it. Rejected: the list stays silently incomplete.

THE CHOICE (precise definition).
- WALK: from the anchor, restricted to the branch's branch_commits, using git's history simplification for the path. At a merge whose blob for the path equals one of its parents' (TREESAME), only the first such parent is followed. A PR merge therefore leads into the writes it delivered, and the side of a LocalWins merge whose write was discarded is never visited: a discarded write was never content of this branch. At a merge equal to none of its parents, every parent is followed. (Refined during implementation: "reachable through ANY parent" would have listed LocalWins losers.)
- ENTRY: a walked commit C is an entry iff the path exists at C and the path's blob at C differs from its blob in EVERY parent of C (a parent without the path counts as different). So each entry introduces a blob none of its parents had. A merge that carries a parent's blob over (a PR merge, or a LocalWins merge) is never an entry. A conflict or evil merge that produces a new blob is an entry.
- REVERTS COUNT. A->B->A yields three entries. Uniqueness is per commit, relative to its parents, not global over the history. Rationale: the newest entry must be the content live at the anchor, and each entry's diff against the next older entry must be a real edit. Global blob dedup would drop the revert and misstate current content.
- ORDER (user decision, review round 2; SUPERSEDES pure author-date order): newest first by AUTHOR date, but a change is NEVER listed below a change it descends from, and revisions[0] is ALWAYS the content live at the anchor. Why: reconcileAgentRebase keeps orig.Author.When on a replayed commit (remote_reconcile_rebase.go), so a replayed A' dated T1 sorted below main's M at T2 and revisions[0] was not the live content.
  Implementation: a precomputed sort key per change. order_at = max(author date, order_at of every change it was edited from); gen = 1 + max gen of those. Sort by order_at desc, gen desc, commit asc.
  On any history without concurrent edits (every chain, every PR-merge history) this is exactly git --date-order. It differs from git only in how concurrent edits from the two sides of a composing merge interleave: a clamped change stays next to its descendant instead of being re-sorted by its own date.
- The displayed `date` is the change's own author date, not the clamped key.
- DIFF (user decision, round 2): each revision is diffed against the content it was EDITED FROM, i.e. its parent's blob on the followed edge. A composing merge is diffed against its first parent that has the path. NEVER against the list neighbour. Why: a side-branch entry was diffed against the other side's change and showed a fake revert.
- action per revision: `added` when no parent of C has the path, else `modified`.

PAGING (all in).
- The first explain call shows 3 revisions inline and returns `history_cursor` when more exist.
- A call with `history_cursor` returns a HISTORY-ONLY page: no body, no graph walk, and a larger page.
- Re-anchoring with commit=<oldest revision> is not the paging mechanism; it is unsound once history branches.

PERFORMANCE AND STORAGE (user decision, round 2: "all these explains need to be ms at most", "add links in the db").
- Per-path history is PRECOMPUTED when the commit log is built and appended to: tables path_changes (entries and carries, with blob, action, author date, message and sort key) and path_change_links (the edited-from link per parent).
- A page is a series of indexed lookups following links from the live change: no revwalk, and no commit loads.
- KEYSET pagination: the cursor carries the frontier of the link walk, not an offset.
- The rows are content-addressed (keyed by commit, derived only from git objects), so no rewind, purge or rebuild can make them stale. A derivation-version key recomputes them if the derivation ever changes.

CURSOR RULES (review round 2).
- The cursor is bound to the binding (PinID plus read-set fingerprint) and to the NORMALIZED path.
- It is accepted only for fact paths (an ontology fact or a .knomit/<area>/ slot) that are readable at the anchor.
- A cursor from another binding, or one that cannot be decoded, is refused as unknown.
- If the anchor has left the branch, or a frontier change is no longer on it or no longer indexed, the page is refused with "history changed, restart". It never returns a silently short or empty page.

NON-SCOPE.
- RevisionsBefore stays first-parent and keeps serving resolution and as_of.date (the fact panel's version timestamp, kb/decisions/ui/fact-header/version-timestamp, is unchanged).
- explain's root `commit` (rootCommit) stays the first-parent resolved commit. Seen-keys and edge pins depend on it.
- This does NOT mean first-parent is wrong elsewhere: kb/decisions/store/resolver/first-parent-vs-committed-at stands for resolution.
- Author-date ordering applies only to this list. It is not licence to order resolution by the clock.

DERIVE AT INDEX TIME (user decision, review round 3; SUPERSEDES the round-2 self-healing sync):
- A commit's path_changes rows are derived in the SAME transaction that records it in the commit index (branch_commits), parents first. A commit is never visible without its rows.
- This applies to every entry into the index: our own writes, merges and fast-forwards from origin, experiment commits, the reconcile replay after a rewind, and :rebuild.
- The upgrade, a pathChangesVersion bump and :rebuild do a one-time BATCHED derivation while the repo opens: after backfillCommitParents, before the repo serves any request.
- knomit_explain NEVER derives, and there is no "history indexing" status. The read-path self-heal is deleted.
- The only error a history read may return is "history changed", on a cursor whose branch was rewound or purged between pages. "unknown history_cursor" stays distinct. A first page is never short and never silently empty.
- Why: round 2 derived after indexing. A commit derived before its parent was indexed got marked done with an unresolved link, and its history stayed truncated for good (review N1). And a read during a rewind or rebuild could return a short or empty first page with no error (N2).

GIT-ONLY DERIVATION (review round 4, same user rule: a commit is never visible in the index without its rows):
- Derivation depends on git objects alone, never on branch_commits membership. Deriving a commit first derives its underived ancestors, walking git parents-first; it never refuses because a parent is missing from branch_commits (review R1: a legacy gap made every populate and every WriteFact fail for good).
- A git read error fails the derivation, and nothing is recorded, so a later pass retries it. Only real absence counts as absent (R3).
- Derived rows are NEVER deleted on a rewind or a rebuild: they are immutable per hash. A pathChangesVersion bump is the only reset, done atomically before re-derivation.
- Rebuild and rewind derive whatever is missing in short batched transactions first, then swap branch_commits in one SHORT transaction (R2/R5: one long transaction made a concurrent writer wait more than 5 s).
- Scope: the resolver fast path (resolveActiveCommitForPath / OutgoingAtCommit) and switching the as_of date are a follow-up, not this PR.
