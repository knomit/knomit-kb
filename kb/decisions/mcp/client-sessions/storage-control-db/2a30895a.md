# MCP client-session rows live in control.db (durable, global), NOT in the per-repo *.sessions.db sidecar — retention one week, configurable

**Options considered:**
1. Keep the registry in memory only.
2. Store rows in the existing per-repo `<name>.sessions.db` sidecar (the maintainer's first suggestion: 'store these in the sessions db').
3. A new table in `<home>/control.db`.

**Rationale:** the maintainer wants the rows to double as a longer-term audit trail (which sessions ran, and later what each pulled/added/dropped). Option 2 cannot do that for two verified reasons: the sidecar is PER REPO, while a bridge bound to a lens spans several repos and has no single repo to live in; and the sidecar is DISPOSABLE — its schema header states it is recreated empty on every Service.Open, so a server restart would wipe the trail. control.db is global, durable, and already owns the cross-repo registry and repo_origins, so a client-session row can reference a repo or lens by uid and survive restarts. This is OPERATIONAL state, not knowledge: it does not conflict with 'git is the only source of truth' any more than the registry does, and it must never be written as facts.

**The choice:** a `client_sessions` table in control.db. State (live/dead) is derived at read time from `last_seen_at`; nothing writes a status flip. Rows are purged by a reaper after a RETENTION setting — default ONE WEEK (the maintainer explicitly shortened it from a proposed 30 days: 'there will literally be hundreds of these'). Presence view hides rows silent >3h; deletion is the separate retention policy. All three thresholds (dead 1h, hidden 3h, purge 7d) are settings, not constants — they are operational policy, not corpus properties.

**Non-scope:** the row gets a stable primary key so a future per-session activity record can reference it, and a nullable principal column for future bridge authentication — neither is built by this decision.
