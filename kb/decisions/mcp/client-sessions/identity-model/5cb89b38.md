# A bridge instance identifies itself by a derived hash (host, user, cwd, parent app) plus pid for the run — sent as HTTP headers; direct HTTP callers get ip+User-Agent+clientInfo (NOT port) with the MCP session id as run id

**Context:** every knomit instance is ONE agent identity (agent branch = hostname + key fingerprint), but many knomit-bridge processes — several Claude Code windows, Cowork, Antigravity — all write under it. The server today sees only the host's `clientInfo` and an opaque session id; the bridge sends no User-Agent and nothing about itself.

**Options considered:**
1. Per-project stable id minted by `knomit-bridge init` and baked into the scaffolded MCP config (enrollment point for future auth).
2. Per-process ephemeral id (pid + start time).
3. Derived key with no stored state: hash of hostname, user, cwd, parent app.

**Rationale / choice (maintainer):** a COMBINATION — 3 for the stable instance id, PLUS pid so two bridges on the same project are distinct runs, PLUS declared metadata: transport (`stdio` vs `http`), parent app name and ppid (read from the OS; the host's own `clientInfo` from `initialize` is recorded alongside so a mismatch is visible), pid, hostname, bridge version, bound repo-or-lens and branch. The bridge sends these as request headers on every request plus a real `User-Agent`; headers are transport-native, never touch the host's `initialize` payload, and a direct HTTP client may send the same headers voluntarily.

**Direct HTTP callers:** the maintainer first proposed hashing remote ip+port. Port was REJECTED: a client opens new TCP connections during one MCP session and each gets a new ephemeral port, so ip+port splits one session into many instances. Substitute (accepted): instance id = hash(remote IP, User-Agent, declared clientInfo name/version); run id = the server-minted MCP session id; transport tag `http`.

**What this is NOT:** none of this is authentication. Every field is self-declared or derived from unverified request data, consistent with the existing invariant that session handles are correlation, not identity. The `principal` slot for future verified identity stays empty. Option 1 (init-time enrollment) was not chosen now but remains the natural place to add a credential later.
