# MCP client-session liveness is last_seen_at per request — NO held GET stream, NO heartbeat, NO bridge-side reconnect

**Options considered** (2026-09-14, designing live tracking of knomit-bridge instances and MCP sessions):
1. Exact real-time liveness: the bridge holds the MCP standalone GET stream open for its whole life; the server records open/close, so process death is detected within seconds. Verified feasible in mcp-go v0.45.0 (a GET on a POST-created session is accepted and the bookkeeping would live in knomit's dispatch wrapper).
2. Approximate liveness: every MCP request bumps `last_seen_at` on the session row; 'dead' is DERIVED at read time from last_seen age.
3. A hybrid: 2 as baseline, 1 as an optional upgrade for bridges.

**Rationale:** the maintainer rejected 1 and 3 twice, firmly. Direct HTTP MCP callers must be first-class, and a mandatory or even optional long-lived connection breaks over the internet and through proxies that cut idle streams. A held stream would also re-open the retry/reconnect question that the bridge no-recovery decision closed. Last-seen needs nothing from the client beyond ordinary requests, so it works identically for bridges and direct HTTP callers.

**The choice:** on `initialize` the server records the session id, the client's identity hash and declared metadata; on EVERY later MCP request it updates `last_seen_at`. No process anywhere holds a connection for presence. Liveness thresholds are settings: silent >1h ⇒ shown as dead, hidden from the presence view after 3h.

**What this does NOT authorize:** do not propose a held stream, heartbeat endpoint, or bridge-side reconnect 'to make presence exact' — the approximation is the accepted cost. If an MCP session id is the same across two requests hours apart (it is: the bridge captures it once from `initialize` and reuses it for the process lifetime), that is what makes last-seen sufficient.
