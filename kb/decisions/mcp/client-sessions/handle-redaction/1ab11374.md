# ReadOnly redacts the HANDLE and the branch inside each session's binding row while leaving the target visible — because read-only keeps /mcp and four read tools reachable, so a leaked handle is a CAPABILITY a visitor can use, not information about the operator

Decided 2026-09-17 in the PR #216 review. `GET /api/v1/sessions` gained a `bindings` array (every handle a session has presented). Under `ReadOnly` — the unauthenticated public demo — each entry's `handle` and `branch` come back empty, while `kind`, `uid`, `name`, the timestamps and the request count stay.

`branch` IS THE EXISTING RULE, not an extension. The standing redaction decision already names `branch` among the fields ReadOnly strips, because an agent branch embeds the operator's hostname by construction. Here it is the same field, having moved into a nested object.

`handle` IS A DIFFERENT KIND OF FIELD FROM EVERYTHING ELSE ON THAT LIST, and this is the whole argument. Every other redacted value — host, user, cwd, pid, parent app, remote address, User-Agent, branch — is INFORMATION about the operator's machine. A handle is a CAPABILITY: possession changes what the holder can do.

AND IT IS USABLE, which was checked rather than assumed. `internal/web/readonly.go` deliberately exempts the `/mcp` routes from the read-only method gate — `initialize` and `knomit_bind` are POSTs, and gating them would make a read-only instance unreachable — and `enabledTools` keeps four tools registered when `readOnly` is true: `knomit_query`, `knomit_explain`, `knomit_repos`, `knomit_bind`. So a visitor who lifts a handle off the unauthenticated sessions page can call `knomit_query` and `knomit_explain` against that binding and get answers.

WEIGHED CONSEQUENCE, accepted: this is NOT an escalation and NOT an authorization boundary. A demo instance's repos are reachable by URL anyway, and the handle invariant says explicitly that a handle grants nothing new. The rejected framing was the first one written — "redacting costs the demo nothing" — which is true but undersells it; the reason to redact is the information/capability asymmetry, not the cheapness.

WHAT THIS DOES NOT MEAN. It does not make ReadOnly an authentication mechanism for the endpoint, and a NON-demo instance still serves handles to anyone who can reach the API, exactly like every other field. Bridge authentication remains the eventual answer. It also does not mean handles are secret in general: they travel in ordinary tool arguments and appear in logs. The claim is narrower — an unauthenticated PAGE should not hand one to a stranger who was not going to have it otherwise.
