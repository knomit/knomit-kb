# GET /api/v1/sessions under ReadOnly (the read-only DEMO) redacts operator details — host, user, cwd, pid, parent app, branch, remote IP, user-agent — plus the handle and branch inside each binding row, and keeps only presence, client name and what each binding points at

**Context (2026-09-14, PR #192 review, finding 3):** the sessions endpoint is unauthenticated, and `ReadOnly` is documented in both internal/config/config.go and internal/web/server.go as 'a read-only demo'. The original handler comment said 'it is a read, so read-only mode changes nothing' — which would have served an anonymous demo visitor the operator's hostname, OS username, absolute cwd, pid, parent process name, git branch and IP for every bridge connected to the demo instance.

**Options considered:**
1. Serve the full rows regardless of mode (as first implemented).
2. Hide the endpoint entirely under ReadOnly (404).
3. Redact under ReadOnly: bridge.{host,user,cwd,pid,parent,parent_pid,version}, branch, remote_addr, user_agent all empty/zero; keep id, instance_id, state, transport, binding, client name/version, timestamps, request_count.

**Choice:** option 3, made by the master session as the safe default with the maintainer able to override; the reviewer explicitly deferred it ('whether the demo is expected to have live bridges at all is your decision'). Rationale: presence ('two Claude Code sessions are live against this KB') is harmless and is the feature; the per-operator fields are the leak, and redacting them is a one-liner that keeps the page working in demo mode.

**EXTENDED 2026-09-17 (PR #216).** The response gained a `bindings` array — every handle a session has presented. Two of its fields are redacted too:

- `branch` inside each entry, which is the SAME rule as the row-level branch above: an agent branch embeds the hostname. The field moved into a nested object, the rule did not change.
- `handle`, which is a DIFFERENT kind of field from anything in the original list. Everything above is INFORMATION about the operator's machine; a handle is a CAPABILITY, and possession changes what the holder can do. Verified rather than assumed: readonly.go deliberately exempts the /mcp routes from the method gate (initialize and knomit_bind are POSTs, and gating them would make a read-only instance unreachable), and enabledTools keeps knomit_query, knomit_explain, knomit_repos and knomit_bind registered under readOnly — so a visitor who lifts a handle off this page can query and explain against that binding.

What each binding POINTS AT (kind, uid, name), the timestamps and the counts all stay: that is the presence story, and the pin and name are already public on the row above. See kb/decisions/mcp/client-sessions/handle-redaction for the full argument.

**What this does NOT mean:** ReadOnly is not authentication for the endpoint in normal mode — a non-demo instance serves the full rows, including handles, to anyone who can reach the API, exactly like every other endpoint. Layer 4 (bridge authentication) is the eventual answer, not this flag. Nor does redacting the handle here make handles secret in general: they travel as ordinary tool arguments and appear in logs. The narrow claim is that an unauthenticated PAGE should not hand one to a stranger.
