# No knomit_motifs MCP tool — agents get cluster_key + member_count on knomit_explain's motif block (siblings capped at 8); vocabulary listing is REST-only

Options considered: (1) a new knomit_motifs tool (list clusters + inspect one, per-repo); (2) extend knomit_explain only (chosen); (3) REST-only with no MCP change.

Rationale: knomit_query already pivots (motifs + motif_match params), so the only agent gap was going from a fact's motif to its cluster identity. explainMotif gained cluster_key (the stable identity, usable against GET /motifs/{key}) and member_count (spelling count, 1 = no aliasing, computed from AliasRows fetched once per explain call, degrading to 1 on an unrebuilt corpus). explainMotifsShown rose 5 → 8 because member_count now tells a reader the sibling list is a preview. Members stay a COUNT on MCP, not a list — member spellings are intrinsically few (judge merges are capped per session) but unbounded, and the full list is one REST detail call away. A new tool was rejected to avoid growing the tool count for a browse task agents rarely need (choice-count degrades selection).

Non-scope: does not preclude a future knomit_motifs tool if agents demonstrably need vocabulary listing; does not change knomit_query.
