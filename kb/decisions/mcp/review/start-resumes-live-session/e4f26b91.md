# A knomit_review start RESUMES a live, planned session on its branch when effort and scope match; refuses one still planning, one opened in-process, or one with another scope unless takeover:true; displaces one idle longer than session.pipeline_resume_window (default 10m). An item being applied holds the phase, only an active session completes, every answer carries item_id, and ownership is never decided by caller identity

CONTEXT: review sessions are keyed per (tool, branch). Every binding of one repo resolves to that repo's agent branch: a --repo bridge, a --lens bridge, and knomit_bind on the unscoped mount alike. Only an experiment binding gets its own branch. Before this change a start abandoned whatever session was active on the branch, so two parallel callers on one repo displaced each other. Nothing ends a pipeline session when its client disconnects: HTTP DELETE, stdio close and bridge exit touch only client_sessions. A session stays active until a start displaces it or the reaper deletes it after pipeline_idle_ttl (default 60m).

OPTIONS CONSIDERED:
1. Plain refuse while a session is active. Rejected: a crashed caller would lock the same user out for up to the 60m idle TTL.
2. Owner-based takeover (same principal takes over automatically). Rejected: created_by holds a per-process Mcp-Session-Id, and the auth principal is the same for every local bridge of one OS user (bridge:uid:<uid>@socket), so it cannot tell a restarted bridge from a concurrent task.
3. Per-caller sessions. Rejected: two reviewers on one branch race on the same facts; the work-stealing design assumes one active session per tool and branch.
4. CHOSEN: resume.

THE START RULE (Pipeline.StartOrResumeSession, used by the knomit_review handler). When the tool and branch have an active session:
(0) takeover:true: abandon it and start a new session (abandoned_session names it).
(1) Still PLANNING: refuse ("still planning; retry shortly, or start with takeover:true to abandon it"). EVERY create is planning, including StartSession's for RunAll and the web job. The mark clears, with a heartbeat bump, only after planning has rendered the first item. A planning session is never stale by the window; only takeover or the reaper displaces it.
    - On BOTH start paths, planSession abandons its session if planning fails by error or panic, and only while it is still planning (AbandonPlanningPipelineSession: AND planning = 1). The abandon can therefore never hit a session someone resumed.
    - Clearing the mark reports whether it matched. A no-match re-reads the row: completed during its own planning is a normal done result; abandoned means displaced by takeover, and the planner is told so at start; missing means reaped.
(2) last_used_at is older than the window: displace. The create re-checks that staleness under the write lock (the idleBefore cutoff), so a session used again since the read is not abandoned.
(3) Fresh, and start_key matches: RESUME, returning its session_id and current item with resumed:true. start_key is the effort plus the domain and entity lists, folded exactly as the scope filter compares tags (store.CanonicalizeTag, textnorm.Fold), deduped, sorted and JSON-encoded as lists.
(4) Fresh and opened in-process (start_key ''): refuse with "an in-process review is running on this branch; wait for it to finish, or start with takeover:true". No session_id is offered.
(5) Fresh, with a different start_key: refuse, naming session_id, who opened it ("an unattributed caller" when created_by is empty), last_used_at and takeover:true.
The create runs under BEGIN IMMEDIATE and abandons only the session the caller decided to replace, else ErrPipelineSlotChanged and a re-read.

THE SESSION RULES, for everyone who continues a session:
- MARKS ARE ALWAYS FINISHED BY A DEFERRED CALL. The `applying` mark on a claimed item, and the `advancing` mark on a session whose phase advance was won, are each cleared explicitly on the normal path, and by a deferred call (context.WithoutCancel) armed the moment the claim or the advance is won, on every other way out, a panic included. A mark left set would hold the session for good, and each refusal's heartbeat would keep it from ever going stale. Any new mark added to this engine needs the same pattern.
- An item is `applying` from its claim until its apply returns.
- A won phase advance marks the session `advancing` in the same UPDATE, until the strategy's OnPhaseAdvance returns. Until that hook has queued the new phase's work (the reflect item, above all), the new phase only LOOKS empty.
- The phase advance is one guarded UPDATE (AND status = 'active'). It refuses while any item is unanswered or applying, or while the session is advancing. A refused caller is served an item queued meanwhile, or told "retry shortly, or start with takeover:true to abandon the session" ("item N is being applied by another caller" / "is moving to its next phase for another caller").
- Only an ACTIVE session that is not mid-advance completes (CompletePipelineSession: AND status = 'active' AND advancing = 0). A session completed by a concurrent caller reports done without moving the watermark again; a displaced one is an error with nothing completed.
- item_id is required with every knomit_review response.
- A lost claim is refused: "already answered (by another caller or an earlier attempt of this call); nothing was applied by this call; if you sent this answer before, it was applied".
- An answer naming an item when none is outstanding is refused.
- Pipeline.activeSession is the single not-found / not-active / still-planning check for continue, page and Current.
- knomit_review: session_id with no response returns the current item, and may advance the session when nothing is outstanding. knomit_hypothesize, where an empty response is a real answer, uses session_id with current:true for the same fetch. Every refusal names the fetch.
- Every result carries a short `next` line. reviewResultPage sets its longest form before the runtime size check, and the page envelope test measures the same; see kb/architecture/synthesize/review/page-envelope-reserve.

WHY THE WINDOW IS 10 MINUTES: the heartbeat is bumped whenever the session serves an item, and when planning completes. 10m is far above an agent's per-item think time and far below the 60m reaper, so a crashed caller's session is displaced within minutes. Resume covers the same user restarting with the same arguments. Config: session.pipeline_resume_window, env KNOMIT_SESSION_PIPELINE_RESUME_WINDOW. It must be positive and shorter than pipeline_idle_ttl, and Manager.Start refuses to boot otherwise; it is parsed once and handed to every instance. Left empty it is 10m, clamped to half of pipeline_idle_ttl when that TTL is 10m or less.

RESIDUAL, by design: only a process that DIES mid-apply or mid-advance leaves a mark set; panics are covered by the deferred finish. A left mark holds the session until takeover or the reaper. Both marks live in the ephemeral sessions DB, which is recreated empty on every server open.

NON-SCOPE: resume is for knomit_review only. knomit_hypothesize and in-process runs (Pipeline.StartSession: RunAll, the web job) still displace an active session silently on start, by design, so two parallel hypothesize tasks can still displace each other. knomit_hypothesize did get the fail-closed rule, the `next` line and the current:true fetch; its item_id stays optional. Resume does not make created_by an identity; start_key compares arguments, not callers.
