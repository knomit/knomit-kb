# A knomit_review start RESUMES a live session on its branch when effort and scope match, displaces one idle longer than session.pipeline_resume_window (default 10m), and otherwise refuses unless takeover:true; ownership is never decided by caller identity

CONTEXT: review sessions are keyed per (tool, branch). Every binding of one repo resolves to that repo's agent branch: a --repo bridge, a --lens bridge, and knomit_bind on the unscoped mount alike. Only an experiment binding gets its own branch. Before this change a start abandoned whatever session was active on the branch, so two parallel callers on one repo displaced each other and the loser's next continue failed with "abandoned, not active". Nothing ends a pipeline session when its client disconnects: HTTP DELETE, stdio close and bridge exit touch only client_sessions. A session stays active until a start displaces it or the reaper deletes it after pipeline_idle_ttl (default 60m).

OPTIONS CONSIDERED:
1. Plain refuse while a session is active. Rejected: a crashed or disconnected caller leaves its session active, so the same user's next start would be locked out for up to the full 60-minute idle TTL.
2. Owner-based takeover (same principal takes over automatically). Rejected: created_by holds a per-process Mcp-Session-Id, so a restarted bridge is a stranger. The auth principal is the same string for every local bridge of one OS user (bridge:uid:<uid>@socket), so it cannot tell "my restarted bridge" from "my other concurrent task", and would reintroduce the displacement in exactly the parallel case.
3. Per-caller sessions. Rejected: two reviewers on one branch race to prune and merge the same facts, and the work-stealing design assumes one active session per tool and branch.
4. CHOSEN: resume.

THE CHOICE (Pipeline.StartOrResumeSession, used by the knomit_review handler). When the tool and branch have an active session:
(i) last_used_at is older than the window, or takeover:true: abandon it and start a new session, named in abandoned_session.
(ii) Fresh, and start_key matches (the effort plus the sorted scope domain and entities): RESUME. The result carries that session's session_id and current item, with resumed:true. The session is marked shared, and from then on every answer must carry item_id, so one caller's answer cannot land on the item another caller just advanced to.
(iii) Fresh, and start_key differs: refuse with an error naming session_id, created_by and last_used_at, plus takeover:true as the override.
The create is a compare-and-swap on the slot (CreatePipelineSessionReplacing abandons only the session the caller decided to replace, else ErrPipelineSlotChanged), so a concurrent start cannot slip in between the read and the write.

WHY THE WINDOW IS 10 MINUTES: last_used_at is bumped every time the session serves an item (the NextPipelineWorkItem heartbeat). 10m is far above an agent's per-item think time between calls, and far below the 60m reaper, so a crashed caller's session is displaced within minutes. Because resume covers the same user restarting with the same arguments, the window matters only for mismatched starts. Config: session.pipeline_resume_window, env KNOMIT_SESSION_PIPELINE_RESUME_WINDOW. It must be positive and shorter than pipeline_idle_ttl (a boot error otherwise). Left empty it is 10m, clamped to half of pipeline_idle_ttl when that TTL is 10m or less.

NON-SCOPE: this is the MCP start policy for knomit_review only. Pipeline.StartSession (RunAll, knomit_hypothesize) still displaces unconditionally. Resume does not make created_by an identity; the start_key compares arguments, not callers.
