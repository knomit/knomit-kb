# A knomit_review start RESUMES a live, planned session on its branch when effort and scope match; refuses one still planning; displaces one idle longer than session.pipeline_resume_window (default 10m); otherwise refuses unless takeover:true. Every answer carries item_id, and a lost or stale answer is an error. Ownership is never decided by caller identity

CONTEXT: review sessions are keyed per (tool, branch). Every binding of one repo resolves to that repo's agent branch: a --repo bridge, a --lens bridge, and knomit_bind on the unscoped mount alike. Only an experiment binding gets its own branch. Before this change a start abandoned whatever session was active on the branch, so two parallel callers on one repo displaced each other. Nothing ends a pipeline session when its client disconnects: HTTP DELETE, stdio close and bridge exit touch only client_sessions. A session stays active until a start displaces it or the reaper deletes it after pipeline_idle_ttl (default 60m).

OPTIONS CONSIDERED:
1. Plain refuse while a session is active. Rejected: a crashed caller leaves its session active, locking the same user's next start out for up to the 60m idle TTL.
2. Owner-based takeover (same principal takes over automatically). Rejected: created_by holds a per-process Mcp-Session-Id, and the auth principal is the same for every local bridge of one OS user (bridge:uid:<uid>@socket), so it cannot tell a restarted bridge from a concurrent task.
3. Per-caller sessions. Rejected: two reviewers on one branch race on the same facts; the work-stealing design assumes one active session per tool and branch.
4. CHOSEN: resume.

THE CHOICE (Pipeline.StartOrResumeSession, used by the knomit_review handler). When the tool and branch have an active session:
(0) It is still PLANNING (pipeline_sessions.planning = 1): refuse with "session <id> is still planning; retry shortly", unless takeover:true. A planning session is never stale by the resume window; only takeover or the reaper displaces it. The mark is set by the resumable create and cleared (with a heartbeat bump) once Plan has queued the work. Continue, page and current-item calls on a planning session are refused too. A start whose planning fails abandons its own session. WHY: before planning finishes, the row has a matching start_key and a fresh heartbeat but an empty queue. A resumer would advance it to done, complete it, and on an unscoped session move the watermark past seeds nobody had served.
(i) last_used_at is older than the window, or takeover:true: abandon it and start a new session, named in abandoned_session.
(ii) Fresh, and start_key matches: RESUME. The result is that session's session_id and current item, with resumed:true. start_key is the effort plus the scope's domain and entity lists, folded the way the scope filter compares tags (store.CanonicalizeTag, textnorm.Fold), deduped and sorted.
(iii) Fresh, and start_key differs: refuse with an error naming session_id, created_by and last_used_at, plus takeover:true.
The create runs under BEGIN IMMEDIATE and abandons only the session the caller decided to replace, else ErrPipelineSlotChanged and a re-read. A DEFERRED transaction failed the loser of a concurrent start with SQLITE_BUSY_SNAPSHOT ("database is locked") instead.

ANSWERS, for every knomit_review session, resumed or not:
- item_id is required with every response (the MCP handler refuses one without).
- A caller that names its item and loses the claim is refused ("answered by another caller; nothing was applied") instead of being handed the next item.
- An answer naming an item when none is outstanding is refused instead of advancing the session.
- session_id with no response serves the current item again (Pipeline.Current), and every stale-answer refusal says so.
- Every result carries a short `next` line naming session_id and item_id. That line, plus the start result's identity and abandoned_* fields, is measured inside the page envelope reserve, which is now 12.5 KiB.

WHY THE WINDOW IS 10 MINUTES: last_used_at is bumped whenever the session serves an item, and when planning completes. 10m is far above an agent's per-item think time and far below the 60m reaper, so a crashed caller's session is displaced within minutes. Resume covers the same user restarting with the same arguments, so the window matters only for mismatched starts. Config: session.pipeline_resume_window, env KNOMIT_SESSION_PIPELINE_RESUME_WINDOW. It must be positive and shorter than pipeline_idle_ttl, and Manager.Start refuses to boot otherwise. It is parsed once at start and handed to every instance. Left empty it is 10m, clamped to half of pipeline_idle_ttl when that TTL is 10m or less.

NON-SCOPE: resume is for knomit_review only. knomit_hypothesize got the fail-closed rule (an answer without session_id is refused) and the `next` line, but NOT resume. Its start, like Pipeline.StartSession for RunAll, still displaces unconditionally, and its item_id stays optional. Resume does not make created_by an identity; start_key compares arguments, not callers.
