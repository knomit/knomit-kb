# The §7.3 cursor binding pin moves from names to ids — `repo:<uid>` / `lens:<uid>` — because renaming a repo silently orphaned every in-flight cursor

**The trigger.** Adding repo rename exposed a latent defect. `tool_sessions.binding` stores `Binding.Name()`, and `queryResume`/`explainResume` reject a resume when the stored value no longer matches. `Binding.Name()` is the lens name for a lens and the REPO NAME for a lens-of-one — so once a repo can be renamed, every open `knomit_query`/`knomit_explain` cursor against it dies on its next page. The pin was always the wrong shape (the codebase already says repo names are display-only); rename merely made the latent bug reachable.

**The choice.** The pin becomes a PREFIXED ID: `repo:<uid>` for a lens-of-one, `lens:<uid>` for a lens. Prefixed, not bare, because once one side stops being a name the two value spaces are no longer self-evidently disjoint — and a legal repo name can parse as a ksuid, which is a documented false-positive class elsewhere. The prefix removes the question rather than arguing about probabilities.

**Options considered.** (a) Prefixed ids on both sides. (b) `repo:<uid>` plus `lens:<name>`, deferring lens uid. (c) Leave the pin on names and accept orphaned cursors, documenting it in the UI warning. (d) Migrate `tool_sessions.binding` rows during a rename so cursors survive.

**Rationale.** (c) was rejected once it was clear the pin was already wrong rather than newly broken. (d) couples the repo layer to the session store and buys little — cursors idle out in 15 minutes by default. (b) was rejected on sequencing: it writes the same comparison twice, and `lens:<name>` leaves the delete-and-recreate gap open. (a) closes BOTH holes — a renamed repo keeps its pin, and a deleted-and-recreated lens gets a fresh uid, so a stale cursor no longer resumes against the new lens. (a) depends on lenses having a uid, which is the companion decision under kb/decisions/lens/identity/.

**What this supersedes.** `ErrLensNameConflictsRepo` (manager.go) was added to keep the pin sound by forcing repo and lens names to be disjoint — it cites `kb/gotchas/lens/cursor-binding-pin` in its own comment. Once the pin is id-based, that guard is no longer load-bearing for cursor correctness and survives only as a UX nicety. Do not remove it on those grounds without a separate decision; DO stop citing it as the reason the pin is sound.

**Migration: none, deliberately.** Existing rows hold bare names; new code compares prefixed values, mismatches, and returns "session expired — omit cursor to start a new query." That is the designed-safe failure, already specified as byte-indistinguishable from expiry, and tool sessions idle out after 15 minutes (`defaultToolIdleTTL`).

**Non-scope.** The write-mount-branch term of the fingerprint is unchanged. This does not make cursors survive a mount-set change, a re-pinned read branch, or a lens redefinition that alters the read set — all of those still and should diverge the pin.
