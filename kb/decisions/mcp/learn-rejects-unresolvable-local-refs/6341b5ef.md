# Unresolvable local fact refs are REJECTED at write time — forbidding the broken state replaces an entire observability subsystem; the gate now lives in internal/refs and covers EVERY write path

derived_from.go silently skipped any ref that failed to resolve (`if !ok { continue }`). Nothing recorded that it happened, so a typo, a wrong scheme, and a deliberate forward-reference were indistinguishable at every surface.

**Options considered:** (a) keep the skip but record it — an unresolved_refs table, a third `unresolved` bucket in knomit_explain, a warnings channel on knomit_learn, a UI error state, and a verify sweep; (b) warn at learn time without failing; (c) REJECT the write outright.

**Rationale (user ruling 2026-08-02):** (a) was fully planned and then deleted as over-engineering — it builds a reporting apparatus for a state that should never be written, and a persisted table of failures is derived state that is not knowledge (git-is-the-only-source-of-truth). (b) fails because a warning nobody is required to read is a warning agents learn to ignore: the authoring workflow is write-many-facts-then-leave, so no pull surface (knomit_explain, a UI badge) would ever be consulted. (c) is cheapest and strictest.

The objection that killed earlier drafts of (c) — "agents write interlinked facts and cannot order them" — does not survive contact with the code: `BatchWriteFacts` commits every fact in ONE knomit_learn call as a single atomic commit. So the gate checks corpus-at-branch-head UNION the current batch, and facts written together may cite each other in any order, including circularly. Only citations ACROSS calls must point backwards, which is the natural direction.

**The choice, as implemented at HEAD:** the check lives in package `internal/refs` as `refs.Gate` (`New`, `CheckBatch`, `Apply`). It rejects a write in which any newly added `fact.RefLocalFact` ref is neither in the batch nor resolvable in the corpus. The error names the citing fact, the ref, and the three fixes. Only local fact refs are RESOLVED: foreign `kb://` refs may name an unmounted repo, `src://` refs name source objects knomit never holds, external URLs are opaque — none is resolvable. Since knomit#249 the same gate also checks the FORM of a newly added `src://` ref (it must be the full 12-hex/40-hex/40-hex form), under the same newly-added-only rule; see decisions/refs/src-ref-gate-new-refs-only. The derived_from.go skip stays but becomes a logged warning, since with the gate it should only be reached by writes that bypassed the gate (direct git push, remote reconcile, history rewrite).

**This reverses the 2026-08-01 request document**, which stated "a ref to a not-yet-written or retracted fact must never fail a write." That premise is precisely what made the observability apparatus necessary.

**WHAT THIS DOES NOT MEAN.**

- *Not* "this is a knomit_learn rule." The gate is package-level and EVERY write path routes through the same `refs.Gate`, so a ref cannot be laundered past it by choosing a different API: `internal/mcp/learn.go` (CheckBatch), `internal/mcp/update.go`, `internal/web/handlers_fact_create.go`, `internal/web/handlers_fact_write.go` (both via `writerGate(...).Apply`), `internal/resolutions` (experiment {body} resolutions, both MCP and REST), and the synthesize pipelines (`discovery.go`, `decision.go`, `dedup.go`, `discovery_reinforce.go`). The package doc says this explicitly — a copy in internal/web would be the ninth copy of a rule the codebase just finished collapsing into one.
- *Not* "`checkLocalRefsResolve` is the function to look for." That symbol no longer exists anywhere in the tree. Grep for `refs.New` / `CheckBatch` / `Apply` instead.
- *Not* "citing a RETRACTED fact is rejected." The gate's predicate is `store.FactQuery.FactExistsAt` (with an empty commit), which walks BACK THROUGH retractions on purpose — a retracted fact still has a navigable last-valid blob, renders as a live link in the UI, and follows correctly in knomit_explain. A narrower "is it live right now" check would reject writes whose refs the rest of the system resolves perfectly well, enforcing a stricter reality than the graph implements. Plain `FactExists` is NOT the gate's predicate.
- *Not* "every ref on the fact is re-checked on every edit." Only NEWLY ADDED refs are gated; refs the fact already carried are passed as `prior` and never re-litigated. They resolved at their own commit, and that is a fact about the past. Without this, editing a title would re-judge citations written months earlier against today's corpus, and one retraction would make every fact that ever cited it uneditable. Getting `prior` right is each CALLER's job, and a writer that carries refs forward from existing versions (a resolution, a prune-merge) must pass them — the per-caller rule is in decisions/refs/src-ref-gate-new-refs-only.
- *Not* "an empty repo id fails closed." `refs.New` with an empty `localRepoID` treats every `kb://` ref as foreign, so nothing is gated and nothing is qualified — deliberately under-enforcing rather than stamping a wrong id into stored bytes.

**Non-scope:** the gate evaluates the commit BEING WRITTEN, which is commit-time resolution for that fact — it is not a HEAD policy. Retraction does NOT dangle existing edges: nodes are keyed by (path, blob_hash) and edges carry (source_commit, target_commit), so an edge to a retracted fact still resolves to the cited version and knomit_explain reports `deleted:true`. Do not add a repair pass, a verify sweep, or a dangling-ref table on the theory that retraction breaks something.
