# knomit_learn REJECTS a call citing a local fact that will not exist — forbidding the broken state replaces an entire observability subsystem

derived_from.go silently skipped any ref that failed to resolve (`if !ok { continue }`). Nothing recorded that it happened, so a typo, a wrong scheme, and a deliberate forward-reference were indistinguishable at every surface.

**Options considered:** (a) keep the skip but record it — an unresolved_refs table, a third `unresolved` bucket in knomit_explain, a warnings channel on knomit_learn, a UI error state, and a verify sweep; (b) warn at learn time without failing; (c) REJECT the learn call outright.

**Rationale (user ruling 2026-08-02):** (a) was fully planned and then deleted as over-engineering — it builds a reporting apparatus for a state that should never be written, and a persisted table of failures is derived state that is not knowledge (git-is-the-only-source-of-truth). (b) fails because a warning nobody is required to read is a warning agents learn to ignore: the authoring workflow is write-many-facts-then-leave, so no pull surface (knomit_explain, a UI badge) would ever be consulted. (c) is cheapest and strictest.

The objection that killed earlier drafts of (c) — "agents write interlinked facts and cannot order them" — does not survive contact with the code: BatchWriteFacts commits every fact in ONE knomit_learn call as a single atomic commit. So the gate checks corpus-at-branch-head UNION the current batch, and facts written together may cite each other in any order, including circularly. Only citations ACROSS calls must point backwards, which is the natural direction.

**The choice:** before BatchWriteFacts, `checkLocalRefsResolve` rejects the whole call if any fact.RefLocalFact ref is neither in the batch nor present via store.FactIndex.FactExists. The error names the citing fact, the ref, and the three fixes. Only local fact refs are gated: foreign kb:// refs may name an unmounted repo, src:// refs name source objects knomit never holds, external URLs are opaque — none is checkable, none is gated. The derived_from.go skip stays but becomes a logged warning, since with the gate it should only be reached by writes that bypassed MCP (direct git push, remote reconcile, history rewrite).

**This reverses the 2026-08-01 request document**, which stated "a ref to a not-yet-written or retracted fact must never fail a write." That premise is precisely what made the observability apparatus necessary.

**Non-scope:** the gate evaluates the commit BEING WRITTEN, which is commit-time resolution for that fact — it is not a HEAD policy and it never re-evaluates refs in previously-written facts. Retraction does NOT dangle existing edges: nodes are keyed by (path, blob_hash) and edges carry (source_commit, target_commit), so an edge to a retracted fact still resolves to the cited version and knomit_explain reports deleted:true. Do not add a repair pass, a verify sweep, or a dangling-ref table on the theory that retraction breaks something.
