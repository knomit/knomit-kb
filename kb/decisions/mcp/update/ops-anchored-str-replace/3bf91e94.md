# knomit_update gains `ops` (anchored str_replace + append, body XOR ops) and optional `if_commit` — chosen over unified diff, append-only, and structural addressing; no result echo, no shrink guard, no dry_run; structural checks (roundtrip parse, fence balance, ontology rules) are the only hard rejects

**Context.** A periodic job (agentic-engineering) keeps a ~65KB private slot under `.knomit/jobs/<job>/`. `knomit_update` only replaced the whole body, so the job never rewrote the slot to retract a wrong claim: resending 62KB reconstructed from memory was too costly and too risky, and the wrong claim stayed in place run after run. The job asked for a patch primitive.

**Options considered.**
1. Unified/line diff — rejected: line-addressed formats assume the writer tracks positions, and `patch`-style fuzz turns a wrong anchor into a silently misplaced hunk in a durable file.
2. Append-only — rejected as the primitive: safe but cannot retract; the wrong sentence stays at the top and the correction lands 600 lines below it (stratified archaeology). Kept as a secondary op.
3. Structural addressing by markdown heading — rejected: couples the server to a document convention the job invented and keeps drifting.
4. Anchored string replace (`old_str`/`new_str`, exactly one match) — CHOSEN.

**The choice.** `knomit_update` accepts `ops` as an alternative to `updates.body`; body XOR ops, both present is rejected. Ops: `str_replace {old_str,new_str}` (empty new_str deletes) and `append {text}`. Uniqueness is the contract: 0 matches rejects, >=2 matches rejects with the count and offsets. No regex, no replace_all, no whitespace normalisation, no fuzz, no occurrence index. Ops apply to `fact.Body` only (frontmatter fields keep their own update keys), sequentially against the evolving buffer, all-or-nothing in one commit. Diagnostics may be heuristic (longest matching prefix, offset, first divergent char on both sides) but application never is. Ops work on ANY fact, public or private; not restricted to `.knomit/` slots.

**if_commit is CONTENT equality, not commit equality, and it is atomic.** Optional `if_commit` (the commit the caller read the fact at — what knomit_explain returns) is honoured on BOTH the body path and the ops path. Absent, null and "" all mean no guard (some MCP clients send null or "" for an unset optional); any other value must be a full 40-hex lowercase string or the call is refused, so a number or array never silently switches the guard off. The update proceeds iff the file's bytes at `if_commit` equal its bytes at the write-branch tip. An unknown commit, or a path absent at that commit, rejects. The check is made atomic with the write by a compare-and-swap: the handler commits through `FactIndex.WriteFactIfUnchanged` with the blob it read, re-checked inside the branch write lock, so two callers holding the same if_commit cannot both land. A refusal returns `current_commit` = the WRITE-BRANCH TIP and never the body. The tip is chosen, not git's last commit touching the path, because the guard compares bytes and the tip's bytes are by definition the file's bytes now, so a retry that re-reads at current_commit and sends it back as if_commit passes; a per-path git log walk can name a commit whose bytes differ from the tip after a merge (e.g. an experiment committed with a {body} resolution), which would make that retry loop. Strict commit-hash equality was a viable alternative and was NOT chosen because the guard exists to protect the bytes the caller's anchors were computed against, which a hash compare only approximates: content equality passes wherever hash equality would, and also when an unrelated or byte-identical revision (A→B→A) landed in between, where the caller's anchors are still valid.

**Guards (hard rejects).** After applying: serialise and re-parse must roundtrip; an edit must not unbalance the body's triple-backtick fences (even count before, odd after — a body already odd, which valid CommonMark can be, stays editable); ontology validation rules run on public facts exactly as before. Nothing else blocks.

**As built (differences from the design brief, all reviewed by master).** The roundtrip gate runs on the FINAL serialised bytes on every update, frontmatter-only ones included, after the refs gate, and names the differing field; order in code is fences → ontology → refs → roundtrip → CAS write. (A newline in a title was first refused by this gate; since PR #333, fact.ValidateTitle refuses it earlier, with the other argument checks — see write-gates.) The fence gate runs only when the body changed and judges the edit, not the result. Every update is a CAS on the blob it read, with or without if_commit. Title and body edge whitespace, which the file format cannot store, is trimmed rather than failing the roundtrip, and `ops[].delta` counts stored bytes. `updates` is no longer schema-required: a call sends updates, ops, or both. Unknown keys on an op are refused. Overlapping occurrences count as separate matches ("aa" in "aaa" is 2). append inserts only the newlines needed for one blank line before `text`.

**Explicitly NOT built.** No echo of the edited neighbourhood in the response (user decision). No shrink guard: every revision is a commit so truncation is recoverable, and a fixed percentage is a corpus-property constant. No `dry_run`. No soft-heuristic rejects (anchor mid-word, large shrink). The fence and roundtrip gates are not moved into SerializeFact (follow-up).

**Non-scope.** This does not change what reaches the agent branch, does not add a new tool name, and does not make `.knomit/` slots discoverable. The read-side overflow the job complained about (tool result persisted to a JSON file) is the client harness's cap, not knomit's, and is not addressed here.

Updated 2026-10-12 (drift sweep against HEAD 2104fd6d): the Context paragraph's `.knomit/jobs/<job>/` slot and the phrases 'private slot' and 'not restricted to `.knomit/` slots' describe a layout that is gone. A periodic job's bookkeeping now lives in `artifacts/<area>/<name>` (fact.IsArtifactPath; a malformed artifacts/ path is refused by notAnArtifactPath, lines 248-250), and ops and if_commit work on such an artifact exactly as on a kb/ fact. Two differences for artifacts: ontology validation is SKIPPED for them (update.go:460, `!factpkg.IsArtifactPath(file)`), and a `context` on one is refused (lines 464-468, ErrContextWithoutOntology), so 'ontology validation rules run on public facts exactly as before' means kb/ facts only. CONSEQUENCE: a job that still writes `.knomit/jobs/...` through knomit_update will be refused; the patch primitive itself (str_replace, append, if_commit as content-equality CAS) is unchanged.
