# knomit_update gains `ops` (anchored str_replace + append, body XOR ops) and optional `if_commit` — chosen over unified diff, append-only, and structural addressing; no result echo, no shrink guard, no dry_run; structural checks (roundtrip parse, balanced fences, ontology rules) are the only hard rejects

**Context.** A periodic job (agentic-engineering) keeps a ~65KB private slot under `.knomit/jobs/<job>/`. `knomit_update` only replaced the whole body, so the job never rewrote the slot to retract a wrong claim: resending 62KB reconstructed from memory was too costly and too risky, and the wrong claim stayed in place run after run. The job asked for a patch primitive.

**Options considered.**
1. Unified/line diff — rejected: line-addressed formats assume the writer tracks positions, and `patch`-style fuzz turns a wrong anchor into a silently misplaced hunk in a durable file.
2. Append-only — rejected as the primitive: safe but cannot retract; the wrong sentence stays at the top and the correction lands 600 lines below it (stratified archaeology). Kept as a secondary op.
3. Structural addressing by markdown heading — rejected: couples the server to a document convention the job invented and keeps drifting.
4. Anchored string replace (`old_str`/`new_str`, exactly one match) — CHOSEN.

**The choice.** `knomit_update` accepts `ops` as an alternative to `updates.body`; body XOR ops, both present is rejected. Ops: `str_replace {old_str,new_str}` (empty new_str deletes) and `append {text}`. Uniqueness is the contract: 0 matches rejects, >=2 matches rejects with the count and offsets. No regex, no replace_all, no whitespace normalisation, no fuzz, no occurrence index. Ops apply to `fact.Body` only (frontmatter fields keep their own update keys), sequentially against the evolving buffer, all-or-nothing in one commit. Diagnostics may be heuristic (longest matching prefix, offset, first divergent char on both sides) but application never is. Ops work on ANY fact, public or private; not restricted to `.knomit/` slots. Optional `if_commit` (the commit knomit_explain returns) is honoured on BOTH the body path and the ops path; mismatch returns the current commit, never the body.

**Guards (hard rejects).** After applying: serialise and re-parse must roundtrip; the body must sanitise as markdown by good practice (at minimum balanced triple-backtick fences); ontology validation rules run on public facts exactly as before. Nothing else blocks.

**Explicitly NOT built.** No echo of the edited neighbourhood in the response (user decision). No shrink guard: every revision is a commit so truncation is recoverable, and a fixed percentage is a corpus-property constant. No `dry_run`. No soft-heuristic rejects (anchor mid-word, large shrink).

**Non-scope.** This does not change what reaches the agent branch, does not add a new tool name, and does not make `.knomit/` slots discoverable. The read-side overflow the job complained about (tool result persisted to a JSON file) is the client harness's cap, not knomit's, and is not addressed here.
