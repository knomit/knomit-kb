# knomit_update's ops items are an anyOf of two closed, const-discriminated branches (str_replace: op+old_str+new_str; append: op+text), shipped together with cross-op error copy that names the fields to send, in ONE release so the chat's cached tool prefix breaks once

**Cause (2026-11).** A live chat run made three byte-identical knomit_update calls; each failed with `op 0: str_replace does not take text`, and the agent loop's repeat-failure guard (same tool, byte-identical args, same error, RepeatFailureLimit = 3) ended the turn. Three things combined: (1) the served `ops.items` schema was ONE flat object with `required: [op]` only, so `{"op":"str_replace","text":...}` was schema-valid (additionalProperties:false refuses only unknown keys, not the other op's fields); (2) the error named the mistake but not the fix, so the model had nothing new to send; (3) resending the same arguments is exactly what the repeat guard counts. The transcript was never found; the likeliest shape, `{op: str_replace, text}`, is inferred from code.

**Options weighed.** (a) Copy only: rewrite the errors and property descriptions. (b) Schema only: split ops.items per op. (c) Both. The user chose (c), in ONE release: the tool schema is hook 1 of the chat's cached prefix (kb/decisions/mcp/tools/display-metadata/6a87f692.md), so any change to its bytes, copy or structure, invalidates every cached chat prefix once at deploy; shipping copy and schema separately would break it twice.

**As built (branch fix/update-op-guidance).**
- internal/domain/fact/bodyops.go applyBodyOp: E1 (str_replace with text) now reads `str_replace takes old_str and new_str, not text: ... text belongs to append ...` with both JSON shapes; E2 (append with old_str/new_str) names text and the str_replace shape; E3 (empty old_str) says what old_str must be. The other op errors are unchanged. The text check still runs before the old_str/new_str checks, so a `{op: str_replace, text}` caller gets E1, which already names both anchors.
- internal/edge/mcp/update.go: `ops.items` is `{anyOf: [str_replace branch, append branch]}` built by opsItemSchema() through the existing raw-map `mcpgo.Items` path (no mcp-go change). Each branch is `type: object`, `additionalProperties: false`, a `const` on op, and requires every field it declares. The four property descriptions say which op each field belongs to; opsDescription gains "The two shapes do not mix: str_replace refuses text, and append refuses old_str and new_str."

**Why anyOf, not oneOf.** The branches are disjoint on op's const, so anyOf and oneOf accept exactly the same instances; anyOf is the combinator more tool-schema consumers accept. It is the first combinator in internal/edge/mcp and internal/engine/llm.

**Providers do not validate tool input, so the server error is the real gate.** anthropic.go passes the schema as raw bytes (param.Override, no strict tool use); ollama.go passes it as json.RawMessage into the request, where Ollama only renders it into the chat template. The schema split is guidance a model may or may not follow (local models follow nested combinators inconsistently); fact.ApplyBodyOps refusing the mixed op is what actually stops it, which is why the copy change matters most. Server-side decoding is unchanged: unmarshalArgStrict still decodes ops into []fact.BodyOp with DisallowUnknownFields, and rejectUnknownArguments reads only top-level properties.

**Consequences.** Editing the op descriptions or the schema again is another cache break: batch such edits. A schema walker added later must handle anyOf under items (none exists today: traceTools and rejectUnknownArguments read top-level properties only; the adaptive ranker tokenizes name+description; stubs use their own schema). Tests: TestUpdateTool_ServesOpsAndIfCommit (two branches, required fields, nothing beside anyOf), TestUpdateTool_OpsSchemaValidatesOpShapes (valid/mixed ops against the tools/list and chat schemas, with a keyword-subset validator because the module has no JSON Schema validator dependency), TestProviders_PassAnyOfItemsSchemaThroughUnchanged, TestApplyBodyOps_CrossOpFieldErrorsSayWhatToSend.

**NOT meant:** this does not make the schema a gate; a client that ignores anyOf can still send a mixed op and gets E1/E2 from the server. It also does not change what the server accepts: every op the server accepted before is still accepted, and every op the schema now refuses was already refused by the server.
