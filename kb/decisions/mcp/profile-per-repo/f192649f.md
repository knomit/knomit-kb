# Profile is a column on the control.db repos row (repos.profile, keyed by uid), not a separate repo_settings table keyed by repo_id

**STATUS: implemented and live at HEAD.** Verified against internal/repos/registry.go, internal/mcp/server.go, and internal/web/server.go.

**Options considered:** (a) keep profile as a caller choice (`?profile=` query param, bridge `--profile`, 3 server instances — the status quo); (b) store profile per lens (RFC revision 1 had `Lens.Profile`); (c) store profile per repo, git-backed (kb.md frontmatter or sibling of domains/ontology.yaml); (d) store profile per repo in the machine-local control-plane DB `control.db`.

**Rationale:** Investigation showed profile's ONLY effect is a one-paragraph authoring addendum appended to session instructions (internal/mcp/instructions.go `profileAddenda`) — three server instances existed for one string. Authoring guidance describes the repo, not the caller: `profile=code` against a general-knowledge repo is nonsense the caller-choice design permits. Per-lens placement was wrong for the same reason, one level up. Git-backed storage (option c, briefly chosen) was overturned by user ruling 2026-07-16: profile is SERVING configuration — how the MCP server instructs agents — i.e. control-plane state, not knowledge content, so it lives in `control.db`.

**UPDATE (repo-registry-in-control.db, 2026-08): `repo_settings(repo_id, profile)` was FOLDED INTO the `repos` table.** The choice originally shipped as a standalone `repo_settings(repo_id TEXT PRIMARY KEY, profile TEXT NOT NULL)` table keyed by the repo's root-commit hash, opened via `OpenRepoSettings`. That table and that accessor are GONE. Profile is now a plain column — `repos.profile TEXT NOT NULL DEFAULT 'code'` — on the same `repos` row the registry uses for name/state/repo_id, keyed by the registry's `uid` (a stable, immutable identifier minted at Create) rather than by `repo_id` (the root-commit hash). `Registry.SetProfile(uid, profile)` and the `RepoRecord.Profile` field are the read/write surface; `ProfileCode`/`ProfileChat`/`ProfileGeneric` constants and `ErrInvalidProfile` live in internal/repos/registry.go. Absent/unrecognised values still read as "code" (ProfileCode), so no migration is forced.

**Why the re-key from repo_id to uid matters (the bug this fixed):** repo_id is MUTABLE — a disjoint-history origin connect calls Manager.SwapStore, which replaces the repo's root commit with the remote's (see the one-local-copy-per-knowledge-base invariant). Under the old repo_id-keyed repo_settings table, a divergent connect silently orphaned the profile row (the old repo_id no longer matched anything) and the repo's profile reverted to "code" with no warning. Keying by the registry uid — which never changes across a swap — makes profile survive a disjoint-history connect. `knomit migrate-registry` (cmd/migrate_registry.go, planProfiles) performs the one-time fold for legacy homes: it reads the old repo_id-keyed repo_settings rows, matches each to a repo by root commit, writes the profile onto the corresponding repos.profile column, and the table is dropped (`DROP TABLE IF EXISTS repo_settings`) inside the same control.db transaction that rebuilds the registry.

ONE MCP server instance, built by `Server.buildMCPHandler()` (singular); `AfterInitialize` selects the addendum from the context repo's profile via `profileFor` → now reads `RepoRecord.Profile` off the registry rather than calling into a settings package. `?profile=` and bridge `--profile` are deprecated: accepted, logged at debug, and ignored. A lens authors under its WRITE repo's profile (the addendum is entirely about writing facts).

**Accepted consequence:** profile does not travel with clones — each machine sets it locally; a fresh clone serves as "code" until configured.

**Non-scope:** readOnly stays a NewServer constructor flag gating write-tool registration — the server collapse does not remove it.

NOTE: the constructor is `buildMCPHandler` (singular). The plural `buildMCPHandlers` named in this decision's original text was the pre-collapse function and no longer exists.
