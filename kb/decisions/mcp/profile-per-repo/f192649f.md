# Profile becomes a per-repo git-backed attribute; the three profile-keyed MCP server instances collapse to one

**Options considered:** (a) keep profile as a caller choice (`?profile=` query param, bridge `--profile`, 3 server instances — the status quo); (b) store profile per lens (RFC revision 1 had `Lens.Profile`); (c) make profile a per-repo, git-backed attribute.

**Rationale:** Investigation showed profile's ONLY effect is a one-paragraph authoring addendum appended to session instructions (internal/mcp/instructions.go profileAddenda) — three server instances exist for one string. Authoring guidance describes the repo's content/ontology, not the caller: `profile=code` against a general-knowledge repo is nonsense the caller-choice design permits. Per-lens placement was wrong for the same reason, one level up.

**The choice:** Profile lives in the repo (git-backed, versions and syncs with the knowledge; storage location — kb.md frontmatter vs sibling of domains/ontology.yaml — decided in Phase 2; absent → "code" so no migration). One MCP server instance; AfterInitialize selects the addendum from the context repo's profile. `?profile=` and bridge `--profile` are deprecated: accepted and ignored. A lens authors under its WRITE repo's profile (the addendum is entirely about writing facts).

**Non-scope:** readOnly stays a NewServer constructor flag gating write-tool registration — the server collapse does not remove it.
