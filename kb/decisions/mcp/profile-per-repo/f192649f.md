# Profile becomes a per-repo attribute stored in control.db repo_settings; the three profile-keyed MCP server instances collapse to one

**Options considered:** (a) keep profile as a caller choice (`?profile=` query param, bridge `--profile`, 3 server instances — the status quo); (b) store profile per lens (RFC revision 1 had `Lens.Profile`); (c) store profile per repo, git-backed (kb.md frontmatter or sibling of domains/ontology.yaml); (d) store profile per repo in the machine-local control-plane DB `control.db`.

**Rationale:** Investigation showed profile's ONLY effect is a one-paragraph authoring addendum appended to session instructions (internal/mcp/instructions.go profileAddenda) — three server instances exist for one string. Authoring guidance describes the repo, not the caller: `profile=code` against a general-knowledge repo is nonsense the caller-choice design permits. Per-lens placement was wrong for the same reason, one level up. Git-backed storage (option c, briefly chosen) was overturned by user ruling 2026-07-16: profile is SERVING configuration — how the MCP server instructs agents — i.e. control-plane state, not knowledge content, so it lives in `control.db`.

**The choice:** `control.db` table `repo_settings(repo_id TEXT PRIMARY KEY, profile TEXT NOT NULL)`, keyed by repo ID (root commit hash — rename-proof). Absent row → "code" (today's default), so no migration. One MCP server instance; AfterInitialize selects the addendum from the context repo's profile. `?profile=` and bridge `--profile` are deprecated: accepted and ignored. A lens authors under its WRITE repo's profile (the addendum is entirely about writing facts).

**Accepted consequence:** profile does not travel with clones — each machine sets it locally; a fresh clone serves as "code" until configured.

**Non-scope:** readOnly stays a NewServer constructor flag gating write-tool registration — the server collapse does not remove it.
