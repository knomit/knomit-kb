# knomit_explore merged into knomit_query as sort=recent; explore tool deleted

knomit_explore was removed; its browse-by-recency capability now lives in knomit_query via a new `sort` parameter (`relevance` default, `recent`). Rationale: the two tools didn't compose — query filtered (type/domain/path) but only ranked by relevance, while explore ordered by recency but couldn't filter. Now `knomit_query {type:[...], sort:"recent"}` filters AND orders by recency in one call.

Implementation: `sort=recent` routes to the store's existing `RecentFacts` (already filtered + `committed_at DESC`; it predates this change and was used only by the web layer). `queryRecent` enqueues ALL ordered entries into a tool_session queue and serves the first page through the SAME `queryResume` path the relevance branch uses, so body hydration and pagination are uniform — only the ordered source list differs (RecentFacts vs Search). Because RecentFacts rows carry no body, every recent row is hydrated from its pinned commit via readNode (no single-page fast path — a deliberate uniform-code-path choice).

Every query result row now exposes `committed_at` in its frontmatter, on all paths (relevance fast-path, snapshot/resume, recent). This required adding a `commit_log` LEFT JOIN to BOTH of Search's SQL branches — Search did NOT previously populate CommittedAt (only RecentFacts did). RecentFactEntry also gained `commit_hash` so recent rows can be version-pinned in the queue.

Validation relaxed: a query is accepted when {any filter: text/entities/domain/applies_to/path/type/min_confidence} OR `sort=recent`. So `sort=recent` with no filter reproduces explore's bare whole-base browse; a no-filter relevance query still errors; an unknown sort value errors. The dead WalkChangedFiles store method and its transitive git-layer chain (commitLogWalkChanged, Storer.CommitLogWalkChanged, CommitLogFileRecency, store.FileRecency) were deleted with explore.

CORRECTION (#657, merge da40f11d): `sort=recent` is newest-first only WITHOUT text. With text, store recentFactsSearch sorts by relevance score, then committed_at desc, then path, and queryRecent fuses per-mount lists with RRF; recency only breaks ties (pinned by TestRecentFacts_WithQuery_SortsByRelevanceNotDate). To get the newest facts about X, use a text-less sort=recent with a structural filter (path, domain, entities, context). The sort parameter, tool description and server instructions say this since #657. Several `domain` values are ANDed.
