# Out-of-range min_similarity is REJECTED, not rescaled, and text-search failures become errors — both ship in ONE PR (#372)

DECISION (issue #372, branch fix/372-text-search-silent-empty): `min_similarity` is a raw cosine and must lie in [0, 1]. A value outside that range is refused with an error that names the parameter and the valid range, on knomit_query (MCP), the repo REST /search, and the lens REST /search and /facts twins. It is NOT rescaled: a 45 is not treated as 0.45.

Options weighed. (1) Reject vs rescale values above 1. Rescaling would make the displayed `score` (cosine x 100) pass-back 'just work', but it guesses intent, hides that the parameter's scale is cosine, and makes 1 ambiguous (cosine 1.0 or score 1?). Rejecting makes the misuse visible at the moment it happens; the maintainer chose reject. (2) One PR vs two (validation first, error propagation later). Both come from the same root cause, a text query that yields nothing without saying why, and they touch the same functions, so they ship together.

RATIONALE. Make misuse visible, and never let a failure masquerade as an honest empty result. Along with the range check: (a) when the caller's own cutoff removes every candidate, the response says so (best cosine seen, cutoff applied) in an optional `notice` field on MCP and REST; (b) store.Search returns an error, instead of nil/nil, when a text query's embedder errors, yields no query vector, or the KNN query fails (a store opened with NO embedder at all keeps its documented empty-result behaviour, now logged at Warn: app.New never starts a service that way, and erroring broke tests that rely on it); (c) one Info log per relevance query records text-present, min_similarity, the per-mount cutoff and per-mount counts after the vector step and after the cutoff.

WHAT THIS DOES NOT MEAN. It does not make the default (min_similarity=0, the model's calibrated SearchFloor) stricter, and it does not touch text-less queries (path prefix, entities, domain filters), which never use the vector step and still work with a dead embedder. fanoutQueryVec keeps its fall-back to per-mount embedding; only the store-level failure now reaches the caller. It SUPERSEDES the sentence in the per-mount-embedding gotcha saying a failed inference should fall back to keyword-only search and never fail a read: there is no keyword fallback for text, and a failed embedding now fails the read.
