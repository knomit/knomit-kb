# The same-subject anchor excludes generic entities via the MOTIF df ceiling — reused for its shape, and measured on the entity axis before being trusted

An entity can anchor a same-subject refusal only if its document frequency on the branch is at or below `synthesize.DFCeiling(n)` = `max(motifDFCeilingFloor, motifDFCeilingPerCent% of n)` — the derivation the motif df band already used, extracted and shared rather than restated. It encodes no fixed corpus property: it is a RATIO of the corpus's own size with a small-corpus floor, so it resolves to a different df on every corpus.

THE TRANSFER IS THE RISK, AND IT WAS MEASURED, NOT ASSUMED. Both of that rule's justifications in `bridge_motif.go` are about MOTIF recurrence, and the file itself notes the three axes (motif/entity/domain) have different df distributions. Entities are more numerous and longer-tailed — every fact carries entities, not every fact carries motifs — so reusing the rule is reusing its SHAPE, not inheriting a validated cutoff.

Measured on the core KB before merge: N=2122 live facts, ceiling 42. Only 15 of 3724 entities exceed it, and they are exactly the big-tech names (Anthropic, OpenAI, Google, Microsoft, Nvidia, Meta, Apple, Claude, Cursor, Claude Code, Hugging Face, DeepSeek, CISA, ChatGPT, GitHub). The known collision pairs' anchors sit at df 1–11. The transfer holds at this operating point.

KNOWN LIMIT, from the same measurement: entity anchors miss SPELLING VARIANCE. The TPUv7 pair names its subject three ways (TPU / TPUv7 Ironwood / Google TPU), so its only shared entity is `Google`, which the ceiling excludes — that pair cannot be caught by this gate at all, and prune remains the backstop.

CONSEQUENCE: if the entity df distribution shifts (a corpus dominated by one vendor, or a bulk import), re-measure before trusting the ceiling; a green test suite says nothing about whether the cutoff is right, because the tests assert the mechanism, not the outcome on real data.

df comes from `TokenDF(…, "entity")` so there is one definition of df. NOTE the two folds do NOT fully agree: `TokenDF` counts over a `COLLATE NOCASE` column (ASCII-only) while `EntityTagMatches` folds full Unicode, so `Café`/`CAFÉ` is one entity to the match and two to the count. The df lookup is keyed exactly as the count was requested, which confines the disagreement to that non-ASCII case rather than spreading it. Reconciling the folds is open work.
