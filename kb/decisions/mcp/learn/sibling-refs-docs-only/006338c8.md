# knomit_learn gets no caller-chosen handles for citing siblings in the same call; the docs stop promising same-call citation, and interlinked new facts are written by learning first, then adding refs with knomit_update

# Options considered

(a) Caller-chosen handles: an optional `id` per fact in knomit_learn, with refs written as `@<id>` and rewritten server-side to the sibling's generated path before the ref gate, so one call can interlink new facts (including circularly). About 40 lines plus tests; dedup merge must map a handle to the merged-into path.

(b) Docs only: stop promising same-call sibling citation in the knomit_learn `refs` description (internal/edge/mcp/learn.go:142), the ref gate's comment and rejection text (internal/corpus/refs/refs.go:142-143, :349-350), and the knomit-decided / knomit-remember / knomit-update skill templates (tools/bridge/skills/templates/) and their .claude/skills copies.

# Rationale

Knomit's graph is temporal: each fact version is frozen with its refs pinned to the version of the target at the commit that wrote it. What matters is that each fact version points at a reference version with the proper CONTENT. Whether an interlinked set is written in one commit or in a hundred does not matter (user, 2026-11-03). Learning facts first and then adding refs with knomit_update yields correctly pinned refs to versions whose content is right, so handles would only save calls, at the cost of input-schema and dedup-merge complexity. A caller cannot write a same-call sibling ref today in any case: fact.BuildFactPath (internal/domain/fact/paths.go:51) names knowledge facts with a random 8-character id that is only returned after the commit, so the promise is one the API cannot keep.

# Choice

(b). The docs say a `kb/` ref's target must already exist, and that to interlink NEW facts you learn them first and then add the refs with knomit_update. The ref gate keeps accepting a ref to a path written in the same call (harmless, and artifact facts, whose paths are caller-chosen, can still use it); only the promise to callers changes.

# Non-scope

This does NOT mean the multi-call result is a lossy or degraded graph, and it does NOT forbid a future handle feature if call count ever matters; it rejects handles as a correctness fix, because there is no correctness problem. It also does not change how refs are pinned (see kb/decisions/store/derived-from-time-aware-edges/a5222e48.md).
