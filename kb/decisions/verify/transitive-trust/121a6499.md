# F09 trusts transitively like git: repository access is the trust boundary and a breach is handled forensically with `knomit verify audit`, not prevented by host hardening

DECISION (F09, user ruling 2026-09-27; D3 of the PR 5 design). F09 builds capabilities; it does not harden the hosts, the fleet or the operator. A compromised key is investigated after the fact by listing everything that key signed.

USER, VERBATIM: "I think you're going overboard in general with all these proposals to tighten everything up. Remember, we're just building the capabilities, it does not mean we need to start using them right away. We're operating also under a trust model, like git is, so we do not need to verify the world each and every time - for example, the kb repos in github are all locked for external commits, you MUST have a token or a key in the repo settings in order for your commits to be accepted. So that's transitive trust - we assume agents will be careful with their access tokens, and are not compromise. If they are, we can look at all commits signed by that agent from the day we detect the breach backwards."
And: "the plan describes an ellaborate workflow to verify the merges into main in github for the existing repos. That is NOT needed ATM, I am not planning to turn verification on for any of those repos".
D3 (ship the audit command): "Yes to the audit - add it".

OPTIONS REJECTED:
- GitHub hardening per KB repo: rulesets on main with a required knomit-verify check, merge-only, a pull_request_target workflow, a required check pinned to a dedicated GitHub App whose key sits in an environment secret restricted to main.
- The gate alone with no audit command (M1).

CHOICE: `knomit verify audit` (kb/decisions/store/verify/audit/e4caa34f.md) re-checks a whole branch against every version of the fleet's member records; `--key` lists every commit a key signed.

CONSEQUENCE FOR REVIEW: RCAs and gates verify that a capability does what its proposal says and fails closed where it says so. They do not threat-model the host, and reviewers do not escalate hardening beyond the approved proposal.

NON-SCOPE: not a claim that the gate is optional when a KB turns verification on; it is the capability. It means no procedure is imposed on KBs that leave it off.
