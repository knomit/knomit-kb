# F09's accept list is per INSTANCE in control.db (verify_accepted, control migration 000013), not in each repo's database, because E4 refuses during a clone, before the repo DB exists; since the fleet model (PR 5) E4 is its ONLY reader

DECISION (user ruling on F09 PR 4): the operator's accept list lives in control.db, one per instance, as table `verify_accepted(commit_hash PK, repo_uid NULLABLE, note, accepted_at)` (control migration 000013; it was 000012 until PR 5 took that number for instance_identity). repos.VerifyAccepts owns it. Each Service gets it as a store.AcceptList bound to its repo uid (builder, SwapStore's rewire, the lifecycle stores, the origin wizard's clone store). A NULL repo_uid applies to that commit in ANY repository; commit hashes are content-addressed, so a global waiver by hash is precise.

OPTIONS CONSIDERED:
- (a, chosen) Instance-level list in control.db. `knomit verify accept <commit>` works before any clone exists and survives SwapStore and repo re-create.
- (b, rejected) A repo-DB table plus CreateSpec.Accept to carry hashes into a create. It needs a CLI/UI path into create that the wizard lacks, and the list dies with a SwapStore.

WHY: E4 (the clone-time own-lineage check) refuses DURING a create, when the repository's database is brand new, and a failed create discards it. E4's remedy is 'accept the commits, clone again', so the accept must live somewhere that exists before the repository does.

SCOPE (since the fleet model, F09 PR 5): E4 is the ONLY reader (repoHandler.acceptedCommit in verify_walk.go). An accept lets a clone adopt origin's copy of this instance's own agent branch although it holds that commit, which this instance did not sign (typically commits from before signing existed). The acceptance gate (store.CheckRange / knomit verify ci) never reads it, and nothing else is waived. The repo-database table verify_accepted from repo migration 000027 is never read or written (migrations are immutable, so it stays, empty); TestRepoVerifyAcceptedTableIsNeverUsed guards that. E4's ForeignLineageError prints a ready `knomit verify accept <full hash>` line per refused commit.

UPDATE (E7a, PR #584, merged into dev as 32414d74; re-read at 32414d74): the type `store.AcceptList` no longer exists (the model.AcceptList interface was deleted; internal/store/model/accept_list.go now holds only the `Accept` row type). `repos.VerifyAccepts.For(repoUID)` returns `func(commit plumbing.Hash) (model.Accept, bool)` (internal/repos/verify_accepts.go) and `Service.SetAcceptList` takes that func (internal/store/service_verify.go, forwarding to vcs.Repo.SetAcceptList); where the text above says each Service gets it 'as a store.AcceptList', read 'as this func'. The call sites (Manager.acceptListFor in the builder, SwapStore's rewire, the lifecycle stores and the origin wizard's clone store) are unchanged. A nil VerifyAccepts gives a nil func, and the E4 check reads a nil lookup as the empty list: the reader is now `acceptedCommit(rh *vcs.Repo, h)` in internal/store/verify/walk.go (it was repoHandler.acceptedCommit in verify_walk.go), which returns false when rh.AcceptList() is nil. The reason for the func value is a package edge: vcs holds the lookup, and vcs cannot import repos. The decision itself (per-instance list in control.db, E4 the only reader) is unchanged.
