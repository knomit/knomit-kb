# DECISION (user ruling, #524 S1): TRUST THE FORGE. The fleet master adopts the forge's `main` as fetched, rewinds included and unjudged; a direct write to the forge's main is the forge admin's business (branch protection), not knomit's

QUESTION (review S1): should the master judge what it adopts from the forge's `main` when it fetches, given that anyone with write access to the forge can put commits on main directly, and a rewound or force-pushed main is adopted by the master's reconcile?

OPTIONS: (a) judge the forge's main too (each fetched main commit, rewinds refused or flagged): not built, it would turn the master into a gate for the forge's own branch protection; (b) TRUST THE FORGE: CHOSEN, a stated assumption. Branch protection on the forge's main is the forge admin's job.

WHAT IS TRUE (verified at merge commit 9db8c106). The master's reconcile adopts the origin's main as fetched, on the fleet master too, rewinds included, without judging it (a one-line stated-assumption comment sits at the reconcileMain adoption point in remote_sync.go). The fetch-time judge covers `agent/*` tips only, never main. The master itself publishes main WITHOUT force, so a non-fast-forward is an ordinary push error and the next round converges onto the forge's main (TestFleetMaster_TrustsTheForgesMainAndNeverForcesItsPush pins both: main is trusted, and the master's push is never forced).

CONSEQUENCE: a forge admin or anyone with write access to the forge's main can change the fleet's membership and certificates outside knomit's judge; knomit does not detect it. If that is not acceptable, protect main on the forge.

MISREADING: 'every commit that reaches the fleet's main is judged' is true only for commits that arrive through the master's merger or receive-pack; it is not true of a direct write to the forge's main. Consistent with the git trust model of kb/decisions/store/verify/acceptance-only/14ef5ebb.md (verify once, where a change enters main).
