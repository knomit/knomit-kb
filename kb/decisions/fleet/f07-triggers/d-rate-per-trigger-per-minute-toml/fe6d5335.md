# F07 PR 3 (D-rate): the script brake is script runs per trigger per minute, with the default in knomit.toml `[triggers].script_rate_per_minute` (built-in 60, must be ≥ 1) and NO per-trigger `rate:` ontology key; fires beyond it are dropped as `rate-limited`, never retried

Rulings, verbatim (maintainer, 2026-09-28), one per question:
- unit: "keep the brake per minute, per trigger."
- default: "no, with default but should be configurable in toml."
- per-trigger key: "Toml is enough"

Context the user asked for: on first seeing the cap, the maintainer said "what's this 'rate' thing? was not aware of it". The explanation given: the cap is the ONLY brake on cross-trigger chains. The loop guard stops a trigger re-firing on its own write, but two triggers whose scripts write each other's paths would otherwise run forever, each hop being a new commit and a new dispatcher run. A per-run cap bounds a burst (one advance bringing many matching paths), not a chain, because a chain crosses runs. So the unit has to be time-based.

Options considered and rejected:
- cap per dispatcher run (bounds a burst, not a chain);
- a built-in default with no knomit.toml key;
- a per-trigger `rate:` ontology key (an older binary reads an unknown key as an invalid trigger and freezes it in a mixed fleet);
- no brake at all.

The choice: a sliding window of run instants per trigger, in memory, per machine (config.TriggersConfig.ScriptRatePerMinute; env KNOMIT_TRIGGERS_SCRIPT_RATE_PER_MINUTE; Load refuses < 1, so there is no "unlimited"). Fires beyond the cap are DROPPED for good on this machine: the bookmark moves past them, each is a `rate-limited` row plus a counter, and there is one WARN per cap episode. Only runs that would start are counted: an `if-false` or an emit trigger is never capped.

Non-scope: this is not a queue and not a delay. A burst above the cap loses fires on that machine by design; anything that must not be dropped needs a different mechanism.
