# D-window: a push fire starts a FIXED 1 s countdown from the FIRST fire (a code constant, not a debounce); later fires are batched into it; at the end ONE round fetches, merges and pushes everything on the branch at that moment; fires during the round start the next countdown — one running, one pending

User ruling (2026-09-28, verbatim): "2) agreed, but we need to queue and batch - like we do now with SSE events. Meaning, once a new commit comes in, a 1s countdown starts. Once it completes, it fetches everything up to the moment it fires, and sends it."

Options considered:
- CHOSEN — 1 s fixed window as a code constant (pushWakeWindow), countdown from the first fire, not restarted or extended by later fires; one round at its end; at most one round running plus one pending, never a queue of N.
- REJECTED — a 5 s window: batches more of a slow agent's bursts but adds 4 s to every push.
- REJECTED — no window (the 1-slot channel only): a burst spread across two dispatcher runs becomes two rounds.
- REJECTED — a debounce that restarts on every fire: a steady writer would postpone the push indefinitely.
- REJECTED — any config or ontology key for the window (simplest-shape rule; the window is a constant).

Why fixed-from-first: 'visible elsewhere in seconds' must hold under a steady write stream; a debounce breaks that. The window is also the lever on Risk 6 (each push round holds the agent-branch write lock for the push).

'Like we do now with SSE events' was implemented as the SSE batcher's one-running-one-pending half only: the SSE batcher (commitObserver) is itself a debounce and was deliberately not reused (see the SSE decision in this folder).
