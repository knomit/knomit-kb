# `.knomit/` is NEVER trigger-visible, now or in the future (D5): a `match` naming a dot path is refused at ontology load; inboxes are ordinary paths; rejected explicit `.knomit/` matching (the design's own earlier 'own inbox' example was a slip)

OPTIONS (decision D-c in the PR 1 RCA). (1) Refuse any `.knomit/` (or dot-segment) pattern in `match`, in PR 1 and for good. (2) A second, unfiltered diff over `.knomit/` so a trigger can match private state when it names it explicitly — which the approved design's example ('the agent's own inbox') seemed to want, contradicting 02-rejected-alternatives (dot paths are discovery-invisible at seven walkers by design) and 00-goal (inboxes at inbox/<agent>/, a normal path).

RATIONALE (the user, verbatim, 2026-09-27 ~12:15): "no, not now not in the future .knomit is for data and code only." Private paths are machinery, not knowledge; a trigger over them would make one machine's private state an episode for others.

CHOICE: option (1). compileGlob refuses a dot segment; F05's isFactPath filter already keeps `.knomit/` out of the diff; the design's 'own inbox under .knomit' sentence is superseded (inboxes are `inbox/<agent>/`). A change under `.knomit/` (a script or a recipe, later PRs) reloads compiled code and is never an episode.

NON-SCOPE: this does not restrict what `.knomit/` HOLDS (scripts, recipes, private bookkeeping keep living there); it restricts what a trigger may OBSERVE.
