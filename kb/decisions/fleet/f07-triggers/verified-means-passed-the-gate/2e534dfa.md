# `change.author.verified` means "this change has already passed the acceptance gate": verification is on (verify_signatures log|enforce at the observed head) AND the originating commit is already in upstream main; a master ruling after F09 PR 5 removed the anchor and fold; rejected signature re-verification or a fleet lookup in the dispatcher, and always-false

OPTIONS (round 2 of the #335 gate, 2026-09-27 ~23:30). The proposal defined `verified` as 'the commit is below F09's verified anchor', with a once-per-run history walk when F09's in-memory cache was empty (R2-1). F09 PR 5 (#334) then merged first and made verification ACCEPTANCE-TIME (the user's redirect, verbatim: "I think we're overly complicating this, why don't we inspire ourselves from how git itself works - meaning, changes are verified when they're accepted, not every time when a branch is merged."), deleting the fold, the anchor ref and the cache — see kb/decisions/store/verify/acceptance-only. Options for F07: (1) always false until a later PR redefines it; (2) re-verify the originating commit's signature in the dispatcher, with a fleet lookup for admission; (3) treat reachability from the local upstream (main) tip as the acceptance mark, since main is trusted once the gate accepted it.

RATIONALE: nothing re-verifies history — the gate did it; (2) would duplicate the gate's logic in a hot path and reintroduce the per-instance judgement PR 5 removed; (1) throws away a real signal. (3) keeps every stated consequence: off ⇒ false, own unmerged writes ⇒ false until they come back through main, `source` (signer-based) independent of `verified`.

CHOICE (master ruling, told to the user with a veto option, not vetoed): verified = (mode log|enforce at the observed head's ontology) && (the toucher commit is an ancestor of the upstream main tip); NO signature re-verification and NO fleet lookup in the dispatcher. Built as TriggerIndex.UpstreamTip + AncestorSet (F09's walkHistory), one walk per run per tip, cached by tip; tests: off → false, on + reachable from main → true, on + own unmerged → false; documented in the OpenAPI description of GET …/triggers.

NON-SCOPE: `verified` says nothing about WHO signed (that is `fp`/`source`) and nothing about log-mode failures main accepted with a report — main contains them, so they read verified.
