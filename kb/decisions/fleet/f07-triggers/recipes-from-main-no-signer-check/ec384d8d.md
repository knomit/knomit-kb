# Repo recipes run only from main, with NO signer, certificate, last-writer or author check (D1): `.knomit/recipes/<name>.js` at the tip of the consensus branch wins, else the machine's <home>/recipes, else unbound; rejected every operator-identity scheme

THE EXCHANGE (user, 2026-09-29, verbatim, in order).
1. "ideally operator would be a human, not an agent. So is there a way to verify the commit came from a human and not from an agent from the fleet ? I guess yes, if the commit is signed, but not signed by any agent from the fleet. Stress test this."
2. The stress test (reviewer, .claude/plans/2026-09-29-F07-pr5-rca-review.md, "D1 stress test"): the rule U "signed, and the signer is not any fleet member's key" does not identify a human — it admits anyone: a throwaway ssh-keygen key, a second key a fleet agent generates for itself, a removed member's key, every old key after a rotation, and EVERY signed commit when no fleet repo is mounted (it fails open). GitHub's web-editor signature is GPG, which knomit's SSHSIG verifier does not read. The only positive marker available was an F19 operator certificate carried in the commit (rule P, the proposal's D1(d)), and no rule can tell a human from an agent using that human's key.
3. "let's say I am going to add the recipe by hand in github in the repo, then in that case it will be signed, but not with any agent key. I DO want that recipe to run. Let's discuss"
4. "A, recipes run only from main. No enforcement on who actually adds the recipes in main for now"

OPTIONS CONSIDERED, all REJECTED except the last:
- an F19 operator-role certificate carried in the recipe's commit (`Knomit-Operator-Cert` trailer, VerifyInstanceChain against this machine's root and CRL) — the rev 2.1 recommendation;
- "signed but not by a fleet key" (the user's first idea; the stress test showed it admits anyone);
- that rule combined with the certificate;
- GitHub web-flow signature plus a non-agent author;
- a per-machine approval of recipes in the UI;
- recipes read from the agent branch;
- CHOSEN (A): recipes run only from main, and how a file reached main is main's business.

RATIONALE. The user wants a recipe they add by hand in the forge's web editor to run; none of the identity schemes admits that commit without new infrastructure, and the trust model (maintainer ruling 2026-09-27) already treats repo access as the boundary. Main is the acceptance point: what reaches it is what the fleet agreed to.

THE CHOICE, as built in #346: resolution per fire is `.knomit/recipes/<name>.js` at UpstreamTip(UpstreamBranch()) (a repo with no main has no repo tier), else <home>/recipes/<name>.js, else unbound (counted, no row). The main recipe wins and shadows the local one of the same name. A main recipe that does not compile is recipe-error with no fall-back. Cached by the blob at main's tip; recipe_rev = that blob.

NON-SCOPE. This does not say recipes are verified or safe: nothing checks who wrote the file or that main's gate ran. "No enforcement ... for now" leaves an identity check open for later; it does not make the agent branch, an experiment or a peer's branch a recipe source.
