# Changed trigger code or recipes MUST reload: declarations, `if` programs, scripts and recipes are read from the observed branch's head tree and compiled programs are cached by source blob hash, so a new blob recompiles before the next evaluation — no restart, no manual step, and never an episode

OPTIONS (D-b in the PR 1 RCA). (1) Keep the open-time ontology snapshot (`ri.Ontology()`, set once at build and never re-read): a changed trigger takes effect after a restart. (2) Read the trigger set from the ontology at the new head of the agent branch on every advance, cached by the ontology file's blob hash (the F09 settingsAt pattern), so a trigger merged from a peer works immediately.

RATIONALE (the user, verbatim, 2026-09-27 ~12:15): "if a loaded trigger or recipe is changed in the repo, then knomit must reload that trigger / recipe goja VM". A different blob at the new head means a recompiled program before the next evaluation; the old program is discarded. For repo recipes (PR 5) the operator-signature check is redone on the new blob's commit before it is trusted.

CHOICE: option (2), built as 1a's single-entry blob-keyed TriggerCache and 1b's per-advance read of the head's ontology (TestDispatch_ReloadOnHeadOntology; an unparseable head keeps the last good set). Validations and every other ontology use keep the open-time snapshot — a user editing both at once sees the trigger change first.

NON-SCOPE: the reload is the dispatcher's own bookkeeping; a change to a script or recipe under `.knomit/` fires nothing (D5).
