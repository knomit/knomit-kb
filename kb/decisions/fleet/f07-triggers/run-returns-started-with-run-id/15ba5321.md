# knomit.run() and `do: run` return `started` at once with a minted run id (run-<32 hex>) that the start row and the later result row share (D5); rejected waiting for the recipe's result and reusing the trace id

RULING (user, 2026-09-29, verbatim): "yes, started, and hopefully with a task id which we can use to correlate the results later on".

OPTIONS CONSIDERED:
- CHOSEN: answer at once {ok: true, status: "started", id, source} (or {bound: false}, {ok: false, status: "busy"}, {ok: false, status: "recipe-error", error}); the recipe's own result is a second fire-log row carrying the same run id.
- REJECTED: return the recipe's result synchronously to the script (R3's literal wording) — a script's budget is 5 s and goja cannot interrupt a native wait, so every recipe longer than 5 s (the sample's Claude session included) would be killed, or phase B would block for the process.
- REJECTED: wait up to the script budget and fall back to started — two return shapes and a race at the edge.
- REJECTED: reuse the causal trace (Knomit-Trace) as the run id — a trace is a story shared by every fire and re-fire in it, so two runs in one story (a retry, a second trigger on the same task, the crash re-run) could not be told apart.

THE CHOICE, as built in #346: the id is minted in phase B when the job is accepted, `run-` + 16 random bytes in hex, and carried by the `started` row, the result row (column run_id, migration 000031), the recipe's `run.id`, the child's KNOMIT_RUN and knomit.run's answer; GET /api/v1/repos/{repo}/branches/{branch}/triggers?run=<id> returns the two rows. Both rows also carry the trace, which leads to the rest of the story.

NON-SCOPE. The id is not stamped as a commit trailer, and writes made by a session the recipe started do not carry it (MCP-side forwarding of KNOMIT_TRACE/KNOMIT_RUN is out of scope; D-mint stands). Scripts have no fire-log read: a later fire looks a result up through the API.
