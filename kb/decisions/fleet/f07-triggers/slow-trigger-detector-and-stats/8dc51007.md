# A slow-trigger detector modelled on the slow-call detector, and per-repo per-trigger statistics (fires, min/max, p95): the user's requirement, timed as the trigger's own work (`if` + action) only

OPTIONS. (1) No instrumentation: read the fire log. (2) A slow-trigger WARN on the same mechanism as the slow-request log (`[log].slow_request_ms` / `metricsMiddleware`), with a trigger-specific threshold beside it, plus in-memory per-trigger counters and durations. (3) Time everything a fire costs, including knomit's own change build (the history walk, the signature check) — rejected in review (R2-2) because that walk reaches 72 ms on real knomit-kb merges and would blame an innocent trigger.

RATIONALE (the user, verbatim, 2026-09-27 ~11:05): "we should have a 'slow trigger' detector, like we have a slow call detector. There should be somewhere a way to get statistics per repo per trigger - how many times fired, min/max, p95". Same log level, same `elapsed` key and message shape ("slow trigger") as "slow request", so one filter finds both; the threshold is config (default 50 ms, structural: the sandbox caps an `if` at 100 ms), never a constant.

CHOICE: option (2): `[log].slow_trigger_ms` (env KNOMIT_LOG_SLOW_TRIGGER_MS, 0 disables); per trigger evaluations, fires, outcomes by kind, slow, and duration count/min/max exact plus p95 over the last 1,024 (labelled p95_window); the run's own diff_ms and change_ms reported separately. Where the statistics show is decision D-d (the triggers endpoint only).

NON-SCOPE: statistics are in memory since instance start and reset on restart; the fire log is the durable record.
