# #349: the AGENT attaches `trace` entries to each MCP write (learn/update/retract/review/hypothesize), named `trace`; only Knomit-Trace/-Cause/-Run are agent-settable (Reading A); knomit stamps Knomit-Run on recipe writes; rejected env/header forwarding, server-side stitching, automatic stamping, the name `story`, and Reading B

Issue #349: a session started by a `do: run` recipe wrote untraced results. Built in PR #385, merged into dev as 9f731d09 (2026-10-01).

**User rulings, verbatim (brief 2026-10-01-rca-brief-349-session-trace):**
- Direction (on rev 1's multi-task problem): "what if the session is long running and does multiple tasks in parallel"; then "so this is what I'm thinking: I don't think currently in the CUD MCP operations (learn, update, retract, synthesis, hypothesis) is any way for the agent to add anything into the git log. If we add that support (allow agents to add "headers") then all this stitching what header to add where could be passed on to the agent themselves, as part of the prompt / tasks."; then "yes, send it back with agent-supplied trailers - but I don't want to call them "trailers", find a better name to match mission, task, experiment, etc"
- The Knomit- ruling: "everything prefixed "Knomit-" is ours, reserved, and well known - agents cannot use anything like that. No for trigger entry if it can cause non-deterministic loops. Validation - whatever is "Knomit-*" must be on the list we support, anything else must match git rules - not long names, short values, etc; these are used for stamping and context carrying, not for verbose notes and descrptions. Automatic stamping - correct. Gap - accepted"
- Decisions 1-3: "1) I prefer trace, since  I'm assuming could be something we could pass cross fleet - like we start a new mission, the mission creates a task, the task will create one or multiple operations which can belong to the same trace id. What do you think ? 2) a indeed, what I meant agents cannot invent new "Knomit-" prefixed names. 3) Agreed, if they need anything else they can either save facts or they can save state. This feature is only for context."
- Decision 4: "sure, stamp."

**Options considered and REJECTED:**
- Rev 1, env/header forwarding: the `kb` bridge reads KNOMIT_TRACE/KNOMIT_CAUSE/KNOMIT_RUN from its env and sends them as request headers. Rejected because the values are fixed at session start, which is wrong for a long-running or multi-task session (the user's 'multiple tasks in parallel').
- Server-side stitching: the recipe registers its run with the server, or a bind-style 'set my trace' call, and the server stamps the session's writes. Rejected: it is session state, it goes stale, and it cannot tell which write belongs to which of several parallel tasks.
- Automatic stamping of ordinary writes: rejected ('Automatic stamping - correct', which confirms D-mint, "D-mint: agreed, no."). knomit stamps nothing an agent did not pass.
- The name `story`, which the rev 2 proposal recommended, and alternatives thread/waypoint/docket/stamps: rejected for `trace` (decision 1), because one trace id should follow mission -> task -> operations across the fleet.
- Reading B: no Knomit-* from agents at all, with recipe-named keys such as Task-Trace. Rejected (decision 2, 'a indeed'). It would hide the session's lines from knomit (deriveTrace would not continue the story) and force readers to grep two spellings.

**The choice (Reading A):**
- The five MCP write tools take an optional per-call `trace` object.
- Agents may pass only Knomit-Trace, Knomit-Cause and Knomit-Run, each in knomit's exact form. They may never pass Knomit-Trigger, because it switches the loop guard.
- Own keys are short git trailer tokens; the limits are key <=32, value one line <=128 bytes, and <=8 own entries.
- Any bad entry refuses the whole call.
- knomit's own set on script and recipe writes always wins: an agent trace there is refused.
- moment_name must be one line.
- Recipe writes carry Knomit-Run (decision 4).
- The accepted gap: an agent that forgets to pass `trace` leaves its write untraced.

**Cost accepted with Reading A:** any agent can join any story by naming its Knomit-Trace. This is correlation only and gates nothing.

**Non-scope:**
- This does NOT authorize knomit minting or forwarding traces on its own.
- It does NOT make `trace` session state.
- It does NOT extend to REST, the web UI or git push writes.
- Anything larger than context belongs in facts or state (decision 3).
