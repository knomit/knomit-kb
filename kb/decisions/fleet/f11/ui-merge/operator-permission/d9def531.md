# Merging a peer's pushed branch requires the `operator` permission — the first route that enforces it (user ruling D1, F11 UI merge)

USER, VERBATIM (2026-09-29, answering the F11 UI-merge proposal's four open decisions): "1) agreed 2) agreed 3) agreed 4) no, no warnings - remember the principle, we should operate like a chain of trust ? If I trust this agent A and  agent A trusted agent B and it accepted its commits then we should trust them." This fact records answer 1.

OPTIONS (open decision 1, 'who may press Merge?'): (a) anyone holding `operator`; (b) anyone holding `write`; (c) `merge:main`.

CHOICE: (a). POST /repos/{repo}/branches/{branch}/merge sits behind Require(operator) (requireOperator, off only with authDisabled like writeGate); writeGate still adds `write`. It is the FIRST enforcement point for `operator` anywhere.

RATIONALE: the merge is the host's operator acting on the host. The shipped [auth].loopback_default (read, write, push:own, operator, admin) and the socket uid seed already hold it, so the web UI and desktop app need no setup; a peer's instance certificate ({read, push:own}) cannot hold it, so a peer can never merge itself in.

REJECTED: `write` as the merge permission (any writer could merge, dropping R1's 'operator-only'); `merge:main` (misnamed for a target that is not main, and absent from loopback_default, so every host would need a config edit).

NON-SCOPE: not hardening. The local socket principal also holds operator by default, so a local agent could call the REST endpoint by hand; no MCP tool exposes it, and the trust ruling says no hardening.

UPDATE (PR #525, verified at merge commit fd991d4f): on the FLEET repository, `operator` is necessary but no longer sufficient. After the operator check, the merge handler calls `RepoInstance.FleetMergeRefusal` inside its existing read, before `MergePushed`: a MEMBER (an instance that is not the fleet's master) is refused 409 `not_master`; the MASTER's merge is re-judged against main NOW with `svc.JudgePeerBranch(branch, own, expected_tip, nil)` (tip minus main, the core the master's merger uses), and a refusal is 409 `judge_refused` with the reason (for example `not-owner`), so a branch admitted at push time and refused since (a revocation, an edit of another member's folder) is not merged by hand either. This closes the #524 residue 'the manual web merge does not re-judge'. Any other repository: unchanged (nil). MISREADING: 'an operator can force a fleet branch in by hand' is false at fd991d4f; the by-hand merge is the same gate as the merger. A route-level test of a refused branch on the master must tolerate 404, because the master's background merger re-judges the same branch and demotes (deletes) a refused one (kb/invariants/fleet/fetch-judge/88eb5593.md).

UPDATE (PR #676, merge dd73ed85): the merge is no longer the only route that enforces `operator`. PUT and DELETE /repos/{repo}/origin, PATCH /origin/upstream, every /origin-sessions route, /repos:probe-origin, /repos:probe-initialized and POST /repos whose body carries an `origin` now require it too (kb/invariants/repos/remote/attach-identity/545ae852.md; decision kb/decisions/repos/remote/origin-operator-gate-and-attach-identity/b5ed2af2.md). 'The FIRST enforcement point for operator' above stays true as history; do not read it as 'the only one'. The loopback_default and socket-seed rationale is unchanged: local callers hold operator, so the UI and desktop need no setup, while a repo-scoped bearer token needs `operator` in its approved scopes.
