# Chain of trust: no E4 warning in the UI, and E4 adopts commits an own-signed merge brought in (user ruling D4, F11 UI merge)

USER, VERBATIM (2026-09-29): "1) agreed 2) agreed 3) agreed 4) no, no warnings - remember the principle, we should operate like a chain of trust ? If I trust this agent A and  agent A trusted agent B and it accepted its commits then we should trust them." This fact records answer 4.

OPTIONS (open decision 4, the re-clone consequence): the proposal recommended saying in the merge dialog, every time, that a re-clone of the host refuses the merged peer commits until the forge merges them, plus an 'In main on origin' column per branch; remedies were a forge merge or `knomit verify accept` per commit.

CHOICE: no warning anywhere (D4a), and instead the E4 own-lineage check trusts transitively (D4b): a commit neither own-signed nor accepted is adopted when it is reachable from a NON-FIRST parent of a merge commit that is in the range and signed by an own key — exactly what the UI merge writes. Everything else is refused as before. See kb/decisions/store/verify/first-contact for the rule and its tests.

RATIONALE: if this instance trusts itself and it signed a merge accepting a peer's commits, a re-clone of it should trust those commits too; without D4b, removing the warning would have left every re-clone of a host failing after its first UI merge.

REJECTED: the E4 warning in the merge dialog; the 'in main on origin' column; `knomit verify accept` as the remedy for UI merges.

NON-SCOPE: does not vouch through the first parent of an own merge, through an own non-merge commit, through a merge signed by anyone else or unsigned, or through an accept-list entry.
