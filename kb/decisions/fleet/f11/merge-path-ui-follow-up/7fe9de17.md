# Pushed peer branches are merged by a human through a UI feature in the web app, built as a SEPARATE follow-up after F11 — not a CLI command, not plain git outside knomit (user ruling "2. b - but I want a UI feature, not command line.")

CONTEXT: with F12 (librarian) postponed to a human, the F11 RCA found knomit has NO merge surface: nothing merges a pushed agent/<peer> branch on the host into anyone's main, so pushed work is visible and searchable on the host but stops there.

OPTIONS (F11 RCA open decision 2): (a) outside knomit with git — fetch the branch from the host's /git with a client certificate, merge, push to the forge's main (needs a git that presents an Ed25519 client certificate; unverified); (b) a small follow-up after F11: an operator-only "merge branch X into this host's agent branch", reusing the existing merge code and the chokepoint, after which the host's normal sync carries it upstream; (c) nothing yet, F11 for visibility only.

CHOICE (user, verbatim): "2. b - but I want a UI feature, not command line."

CONSEQUENCES the follow-up's RCA must carry: it is its own RCA and PR, not part of F11 (#340 ships the transport only); it is a web-app UI feature; merging peer commits into the host's agent branch meets F09's E4 lineage check — a re-clone of the host fails with ErrForeignLineage while the origin's copy of the host's agent branch holds commits beyond origin's main that the host did not sign, until the human merges on the forge (a merge into MAIN on an origin-less host avoids it but needs `merge:main`, which has no enforcement point yet).

REJECTED: merge outside knomit with plain git; no merge path at all; a CLI merge command.
