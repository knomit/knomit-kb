# DECISION (user rulings 2026-10-16): the master switch is 'the old master stands down FIRST, then the new master takes the role'; no handover protocol, no flush, no contact between the two; the only safety check is the new master's own synced main (the master marker), with an explicit loss confirm

WHAT WAS DECIDED (PR #531 rework). After a review found the first fix incomplete, the user ruled in four steps the same day: (1) first 'flush, freeze, then hand over' (a handover state on the old master, the new master verifying its final main); (2) OVERRIDE: 'It could be as simple as A stops accepting changes and stops acting as master (no more merges). Then, C sets the role master and starts merging. There is no reason for A to talk to C or the other way around.'; (3) CLARIFICATION: a master that stood down must be able to become master again by the same steps (A -> C -> A); 'must not act as master once it stood down' means it never RESUMES by itself; (4) FINAL: only a marker naming the acting master (artifacts/fleet/master), replacing a stood-down line in the host record; explicitly NOT a root-signed record, NOT 'master: none', NO isFleetMaster change, NO new judge rule beyond adding the path to the host-record rule.

OPTIONS REJECTED: the handover/flush protocol (state, cancel, drain of in-flight pushes, a git capability advertising the final main) was partly built and removed before any commit: more machinery than the problem needs. An authoritative master record (isFleetMaster requires it; the judge refuses master-only writes from non-named agents; root-signed) was analysed and stopped: commit signatures are instance keys, so 'signed by the root holder' needs a root-signed artifact; 'delete the record' collides with legacy fleets; isFleetMaster reading main blocks the new master's own Host here.

CONSEQUENCES: see kb/invariants/fleet/master-marker/13dcd692.md and kb/invariants/fleet/root-move/b41b75ed.md. KNOWN RESIDUE: a master replaced while it was down (confirmed takeover) cannot learn it was replaced until it points at the new host; if it stands down BEFORE pointing, its marker deletion is a host-record-rule change the new host refuses for good (last_error_commit_refused; that test is gone at the merge, see the UPDATE below for TestFleetMasterSwitch_FallbackHostRecordRewriteIsRefusedForGood). On a forge-hosted fleet nothing checks the marker: importing the root makes the new master work at once, and its round claims the marker only once the old one is gone.

MISREADING: 'two masters at once is now detected': no, it is still unsupported (kb/decisions/fleet/two-masters-unsupported/daea77c9.md); the marker only lets the new master see, on its own main, whether the old one stood down.

UPDATE (rulings 6 and 7, 2026-10-16; verified at c86b0d6e). (6) "If each puts their own key in their own branches, it means they're both candidates. Whoever the merge sets in main, that is the true master, and the second one will be demoted to a member." The marker on main now DECIDES the master on every hosting (isFleetMaster requires it); root holders main does not name do no master work; while main names no master they claim, and git decides (the first claim published to main wins; the loser keeps nothing and is a member). This supersedes FINAL's 'no isFleetMaster change'. (7) "Decommission in forge it means the master is gone from the fleet repo data ... IF somehow some other instance has the keys, it should be able to take over the fleet just fine." A forge decommission publishes the marker's deletion first. RESIDUES REVISED: the stand-down-before-pointing trap and the legacy returned-master claim are gone (a rewind replay drops marker-only commits); the forge two-masters window after an import is gone (the importer does nothing while main names the old master). What remains: a master that is down cannot know it was replaced and acts on its own stale hub main until it points at the new host; a host-record rewrite it made meanwhile is refused for good after pointing (TestFleetMasterSwitch_FallbackHostRecordRewriteIsRefusedForGood; way out: leave, revoke, enroll, join).

VERIFIED AT THE MERGE (PR #531, squash commit 8ca72760 on dev, 2026-10-16). The rulings quoted above are the user's words from the rework brief (OVERRIDE, CLARIFICATION, FINAL) and from the second fix round (rulings 6 and 7); the code at the merge implements the UPDATE, not the first four steps' 'no isFleetMaster change': StandDown (DELETE /fleet/root) needs nothing before it, deletes the marker as its last act as master and then <home>/fleet; Host here checks only its own main's marker (old_master_active, confirm_loss); the hub refuses member pushes once its master stood down (FleetPushRefusalStoodDown). TestFleetMasterSwitch_StandDownFirst runs the switch end to end.

VERBATIM RULINGS NOT QUOTED ABOVE (user, 2026-10-16). RULING 7: "Decommission a fleet when knomit hosted means the repo is gone - and that is acceptable. Decommission in forge it means the master is gone from the fleet repo data, and since no one has the master key anymore, the fleet is abandoned. This is acceptable if it works like this. IF somehow some other instance has the keys, it should be able to take over the fleet just fine." The user's request behind FINAL: "I'm assuming the fleet repo already has a record somewhere that is saying who the master is, and standing down will remove that record, so others can check the repo is a 'master-less' fleet." The CLARIFICATION in the user's words as relayed: "A must not act as master once it stood down" means A does not RESUME master duties BY ITSELF (after a restart, or coming back online after C took over without its marker); it does NOT mean A can never be master again, and switching back uses the same protocol (C stands down, A hosts the fleet here exactly as C did; the end-to-end test includes the round trip A to C to A).
