# A YAML comment in a fact version's frontmatter does NOT make the version lossy: the merge proceeds and drops the comment; the commented version stays readable at its own commit

THE USER (2026-09-30, verbatim): "I don't really care much about the comments in the header, the user can read them using explain or something"

OPTIONS:
(a) keep PR 1 review round 2's rule (N1): a comment is lossy, so the fact falls back to a side-pick;
(b) let the merge proceed and drop the comment.

THE CHOICE: (b). `knownKeysOnly` no longer checks comments (`hasComment` was removed). The version that carried the comment is one parent away from the merge commit and readable with knomit_explain at that commit. Every knomit_update rewrite already drops comments.

Pinned by TestMergeVersions_Lossless (the comment case merges and the output has no comment) and by TestPeerSync_StateConsensus's comment.md case. Sabotage S3, making comments lossy again, turns both red.

RATIONALE: a comment is not part of the fact's content, and refusing a merge over it forces a side-pick that drops a real edit to preserve an annotation.

NON-SCOPE: other losses stay lossy: an unknown frontmatter key, a ref/motif/expires ParseFact drops, or an output that does not round-trip. Those go to the `state` rule with the reason recorded. MergeVersions' 'never drop what a side wrote' still holds for everything except comments.
