# `conflicts` and `consensus` are SET ONCE AND FORGOTTEN: documented, not engineered for mid-flight changes. Under `consensus: auto` an absent `conflicts` key reads facts: merge / state: consensus

THE USER (2026-09-30, verbatim), on the matrix follow-ups: "1) ok, 2) NO, people do not go and randomly change the ontology on the fly. The pattern we want to encourage is set it once, and forget. Document. 3) ok 4) ok 5) ok."

OPTIONS (follow-up 2): engineer for a setting that changes while instances are merging, for example version the setting or have both sides agree on one value; or document that it is set once.

THE CHOICE: document only. The AttrConflicts doc comment carries 'SET IT ONCE AND FORGET IT', and the schema description served to agents ends with 'set it once when the repository is created and leave it'. Every merge site reads the value at its own copy of the consensus branch's tip. An instance whose copy lags reads the older value for one round, and that is accepted, not handled.

Follow-up 1 ('ok') is the default. When `consensus: auto` is set and `conflicts`, or one of its keys, is absent, the missing key reads `facts: merge` / `state: consensus`. It keys on the ATTRIBUTE alone, whether or not the repo has an origin. An explicit `off` stays off, and a bad value reads off, never the default. Pinned by TestReadConflicts, TestReadConflicts_AutoDefaultIsTheAttributeAlone, TestPeerSync_AutoDefault and the matrix's 'absent' row. Sabotages S1 (drop the default), S7 (explicit off overridden) and S8 (a bad value reads the default) all turn red.

RATIONALE: a repo whose host merges every pushed branch by itself should not leave each conflict for a human, or let the peer override it a round later (the F1 gotcha). Settings are repository policy chosen at creation, so machinery for changing them live would buy nothing users do.

REJECTED: engineering for settings that change mid-flight.

NON-SCOPE:
- This does not forbid changing the ontology. It says a change is not coordinated, so the two sides of a conflict may apply different rules for one round.
- The auto default does not turn a repo with an origin into an auto-merging one: the merger still ignores auto there.
