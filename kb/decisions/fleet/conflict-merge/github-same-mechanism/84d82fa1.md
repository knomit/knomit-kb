# The conflict merge runs in the PEER's sync, before its push, so a GitHub-hosted KB gets it with no workflow change. That answers the user's point that the problem is the same when GitHub is the host

THE USER (2026-09-30, verbatim), on hearing that the host refuses a conflict and the peer's own LocalWins sync then lands its version: "but if this is true, then it is true even today when I use github"

CONFIRMED: the GitHub workflow (knomit-kb merge-agent-branches) behaves the same way. It does not resolve conflicts. The agent's next sync merges main into its branch with LocalWins, and the retry merges cleanly with the agent's version.

CHOICE: resolve where the peer syncs (the reconcileAgent call site in remote_sync.go, strategy from `conflicts` read at the consensus branch's tip), not only on a knomit host. With `conflicts: merge` in a GitHub-hosted KB's ontology, read at the peer's local main (= origin's main), the peer writes the merged fact and its Knomit-Merge trailer and pushes. The workflow then only performs a git-level merge that is already clean. There is zero workflow change. With `conflicts` off it stays exactly as today, except that the peer's merge commit now records the dropped version.

REJECTED: a GitHub-side merge step (a workflow that resolves conflicts itself). It would need a second implementation of the rule outside knomit, and two resolvers could disagree.

NON-SCOPE: this does not make GitHub merges signed by knomit. Chain of trust is unchanged: the peer signs its merged commit.
