# Conflict-merge rulings 1-5: confidence is the default both-changed rule (upstream, renamed merge:consensus in PR 2, the second); a retraction beats a concurrent edit; a per-repo `conflicts` root attribute (absent = today, now recorded; an object {facts, state} since PR 2); title/body never spliced; two PRs

THE USER (2026-09-30, verbatim): "1) yes 2) delete wins, with the edit staying visible in the comit's other parent 3) yes 4) yes 5) yes"

WHAT EACH ANSWER CHOSE (from the proposal's open decisions):
1. A field both sides changed differently is settled by the `confidence` rule: dedup's rule made symmetric (higher confidence, then more sources, then non-hypothesis, then the smaller blob hash). `upstream` is a second value. `trusted` is reserved and not built (no member rank exists). `newest` was rejected: concurrent versions have no causal order, and ordering by commit time is forbidden (decisions/store/resolver/first-parent-vs-committed-at).
2. Modify/delete: the retraction wins and is recorded (`Knomit-Merge: … out=none dropped=<side>-modify decided=delete`). The edit stays visible in the merge commit's other parent. `edit-wins` was not built.
3. Root ontology attribute `conflicts`, read at the tip of the consensus branch. Absent = off = today's side-picking, but every side-picked conflict is now recorded (`Knomit-Conflict`).
4. Title and body are taken whole from one side, never spliced, until an LLM merger exists.
5. Two PRs. PR 1 is store + fact: MergeVersions, StrategyMergeFacts at the peer sync, the rebase fallback, MergePushed and MergeConsensus, both trailers, and the attribute. PR 2 is the UI `resolution: "merge"` value.

ACCEPTED DURING IMPLEMENTATION, UNDER RULING 1: the value set is CLOSED as `off | merge | merge:upstream` (`merge` = the confidence rule). `upstream` ships now so no new key is ever needed for it. Any other value (e.g. a future merge:trusted) reads as off with one warning, like `consensus`. The reviewer accepted both.

REJECTED: `trusted`/`newest` now; edit-wins on modify/delete; splicing bodies; an instance-wide setting (nothing here belongs to the instance).

NON-SCOPE: ruling 3's 'absent = today' does not mean 'unrecorded'. It also does not mean the host auto-merges when `conflicts` is absent: it still refuses.

SUPERSEDED IN PART BY CONFLICT-MERGE PR 2 (#356, merged at b9cdf382):
- The scalar value set above (`off | merge | merge:upstream`) is gone. `conflicts` is an OBJECT, `facts: off|merge|merge:consensus|consensus` and `state: off|consensus`. `upstream` is renamed `merge:consensus`. The PR 2 UI `resolution: "merge"` value was dropped: MergePushed with no side already applies the setting. See decisions/fleet/conflict-merge/conflicts-object.
- 'Absent = today' still holds EXCEPT under `consensus: auto`, where an absent key reads `facts: merge` / `state: consensus`. The NON-SCOPE line 'the host still refuses when conflicts is absent' is true only without auto.
- INVALID VALUES, as built: 'reads as off with one warning' is the merge-site reader's half. A bad value (the scalar form, an unknown inner key, a value outside a key's set, a null) is handled exactly as for `consensus`: a WARNING when an existing repo opens (it keeps opening), FATAL only for a new ontology (ParseNewOntology), and ReadConflicts reads it as off for BOTH keys, never as the auto default, with one warning per ontology blob at the merge site.
