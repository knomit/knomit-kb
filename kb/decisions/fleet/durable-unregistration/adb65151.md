# Fleet unregistration is durable: write `left` locally, push, retry on the sync loop until success or a manual archive, unmount only on success, refuse any new registration meanwhile; every state and error is explicit in the API and Fleet tab

DECISION (F09 PR 5, user rulings 2026-09-27, design revisions 6.2-6.6).

USER, VERBATIM:
- "during fleet unregistration (DELETE /api/v1/fleet) to update the fact locally, then push the agent branch to the origin so origin knows to process it"
- "it should keep on trying to push until it succeeds or the user manually archives the repo. If the sync eventually succeeds, the repo should be gone. While this unregistration is pending, the user should not be able to register with any other fleet"
- "obviously the REST API and the UI for the fleet should properly reflect this state machine along with any possible errors"

OPTIONS REJECTED, in order:
- DELETE only drops the local membership row; the fleet sees nothing and a human sets `left` by hand; the fleet repo stays mounted.
- Push failure fails the unregistration outright.
- Three states (standalone|registered|unregistering) with errors left unlisted.
- (master ruling, rev 6.6) A failed CLONE entering `registering` and retrying: it would need the URL of an unmounted repo stored somewhere, against 'no URL in control.db'. A failed clone fails the PUT; the user retries.

CHOICE: fleet_state standalone|registering|registered|unregistering in control.db; record state pending|active|left|revoked; GET carries last_error/last_attempt; refusals are 409/422 with machine-readable codes; the UI disables forbidden actions and says why. Only a failed first push after a successful clone enters `registering` and retries. Mechanics: kb/architecture/fleet/registration/05e5af16.md.
