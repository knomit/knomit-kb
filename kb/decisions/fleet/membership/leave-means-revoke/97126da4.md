# Leave means revoke (user ruling R6; BUILT by PR #532): the acting master revokes a leaver's leaf automatically once the member's `left` record, naming that leaf, is on main; a left record naming no leaf, or one that never reached main, is revoked by hand (POST /fleet/revoke)

CURRENT STATE (PR #532, squash commit a1b0ca5d on dev, verified there; read this first, the paragraphs below are the history of how it got built and their 'not built' / 'does not revoke' sentences are SUPERSEDED): the duty IS built. The fleet's acting master (actsAsFleetMaster: root key AND main's master marker names it AND not paused) revokes a leaver's leaf in its first round after the member's `left` record is on main, when that record names the leaf (leaf_serial), main's current leaf for the id has exactly that serial, and main's CRL does not list it (kb/invariants/fleet/leave/master-revokes-left/d2132d6b.md; ruling in kb/decisions/fleet/membership/leave-must-revoke/e9e7bab2.md). A rejoin then needs no manual revoke. STILL MANUAL: a left record that never reached main (the leave's push failed), and a left record naming no leaf (written before leaf_serial existed, or by an instance with no certificate installed). MISREADINGS: 'Leave itself revokes' (the master does, later); 'every left record is auto-revoked' (see above).

The decision: a member leaving the fleet is a revocation of its certificate, so the old leaf is on the CRL and a later same-key rejoin is admitted by rule A only on a FRESH leaf the master issues after the leave; that fresh leaf is the approval. OPTION considered: let a left record's leaf stay valid (a rejoin then needs no new approval, so a leaving member could return unapproved): rejected by the ruling.

SCOPE: the duty belongs to the master reconcile (P5), not to the judge and not to PR #514. The judge only reads the CRL at the fleet revision. CONSEQUENCE for a reader of the code at #514: a member whose record is `left` but whose leaf is not on the CRL still has a valid leaf; rule B refuses its commits only because the record rules refuse an inactive record first. MISREADING: 'leaving revokes the leaf automatically' is wrong until P5 builds it.

UPDATE (PR #523, verified at merge commit 3ac59b57): once the master (or anyone) lands a CRL that lists the leaf, readers (FleetStatus.record_state, GET /fleet/members) now show the member as `revoked`, derived from the CRL at the same main (FleetPKI.Revoked); the record itself is not changed and the judge does not read the derived state (kb/decisions/fleet/derived-revoked/504782ff.md). The duty to revoke on leave is still not built by this PR. MISREADING: 'a `left` record with an unlisted leaf reads revoked' is false: it reads left; `revoked` appears only when the CRL lists the leaf.

UPDATE (PR #525, verified at merge commit fd991d4f): POST /api/v1/fleet/leave is built, but the duty is STILL not automatic. Leave writes `left`, pushes once, deletes the repository and runs `pki.Uninstall`; it revokes nothing (a member cannot revoke its own leaf, and revoke is master-only). The leaf is revoked only when the master calls POST /api/v1/fleet/revoke {agent_id}, a manual step until the master's reconcile (P5, PR 8) does it from a `left` record. What changed is the rejoin: POST /fleet/enroll refuses an id whose leaf on main is not on main's CRL (409 `enrolled`: revoke it first), so a left member cannot come back on its old leaf; a rejoin needs the master's revoke, then a fresh enroll of the SAME key, which issues the fresh leaf that is the approval. A different key under an id that already has a leaf is refused outright (409 `rekey_unsupported`; a lost or rotated key is a new agent id). The check reads MAIN only (the forge-master gap: kb/gotchas/fleet/enroll/2dfa0b97.md; the rule: kb/invariants/fleet/enroll/5c5a3bef.md). MISREADING: 'leave revokes' is still false; 'the leaving member's old leaf stays usable until the master revokes' is the operational consequence, and the leaver's own listener stops admitting the fleet because it uninstalled, which does nothing for OTHER members' listeners that still trust the unrevoked leaf.

UPDATE (PR #533, squash commit 6f241959 on dev, verified there): (1) The master's automatic revoke (fleetLeaveRound -> revokeLeaf writes the CRL and the revocation statement on the master's branch) is a commit of the master's OWN range, so the next publish judges it (kb/invariants/store/verify/own-range); the CRL change is a `replace` under crl-newer and the statement a write-once pki revocation, and both pass. A `left` record carrying leaf_serial passes validation (writeRecord writes pragmatic/policy; leaf_serial is in the body, which no validation reads). Pinned end to end by TestFleetJudgeOwn_LeaveAutoRevokeAndRejoinPassTheJudge: join, leave, automatic revoke (CRL Number 2, authored by the master), re-enroll, rejoin, with last_error empty and no fetch-judge refusal at every step. (2) A merge of a member's leave branch by the master used to be refused by its own judge when the master had revoked another leaf since the branch forked; fixed by the artifact-rules narrowing (kb/invariants/store/verify/artifact-rules/fd3ab8ab.md). (3) A member whose OWN commit the host refuses (the member 'commit refused' notice) is NOT revoked by the duty: its Leave push carries the same refused commit, so it is refused too, the left record never reaches main, and the duty only revokes for a left record on main (leftLeafDue). The operator must revoke that certificate by hand (POST /api/v1/fleet/revoke) before enrolling it again. The notice (fleet-commit-refused-notice) says this and the openapi text of last_error_commit_refused names POST /fleet/revoke. MISREADING: 'leave always ends in an automatic revoke': not when the leaver's branch holds a commit the host refuses.
