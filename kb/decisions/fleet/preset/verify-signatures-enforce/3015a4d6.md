# The embedded fleet preset DECLARES verify_signatures: enforce in its own ontology (user ruling R7: 'everything is explicit'); the judge's behaviour is never inferred from the preset id, and a fleet repository at off or log gets no enforcement or only logging by its OWN declaration

OPTIONS: (a) leave the preset without verify_signatures, so a new fleet repository is unjudged (off) until its creator writes the attribute (the pre-#514 preset): REJECTED, because the fleet's trust files would then be unprotected by default; (b) make the fleet id imply enforcement in code: REJECTED, because the behaviour of a repository would be read from a name instead of from its own policy; (c) the preset declares `attributes: { verify_signatures: enforce }` in its ontology text: CHOSEN, the user's reasoning being that everything is explicit: the policy a repository runs under is the text in its .knomit/ontology.yaml and nowhere else.

CONSEQUENCES. A NEW fleet repository judges every change that enters main (record rules, rules A/B once there is a root, and the artifact rules) from its first push. An EXISTING fleet repository keeps its stored ontology: the boot refresh treats root attributes and the artifacts section as policy (refreshDivergence) and never adds them, so it stays at its own setting until someone commits the attribute to that KB's main. The knomit-playbooks fleet template carries the same text (byte for byte; editing it makes create-from-template refuse it).

MISREADING: 'upgrading knomit turns on enforcement for an existing fleet repository' is wrong. MISREADING: 'enforce on the preset means artifact rules run everywhere' is wrong; they run only in a repository whose own ontology has verify_signatures log or enforce AND declares an artifacts: section.
