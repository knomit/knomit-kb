# The fleet repository stores issuance and revocation as per-operation, root-signed files (issued/*.pem = the issued leaf; revocations/*.txt = a signed statement) instead of append-only issued.jsonl/revoked.jsonl ledgers; there are no ledgers in the fleet repository; a replacement crl.pem must list a superset of the old CRL's serials; file names carry no meaning

Ruling (PR #514 round 3, 2026-10-14). OPTIONS: (1) append-only ledgers in the fleet repository (the original P3 design; D7 planned them as fleet artifacts): REJECTED; (2) drop the ledgers and keep nothing: withdrawn early, because RevokeSerial built each CRL from the prior revocations parsed from revoked.jsonl; (3) one write-once, root-signed file per operation: CHOSEN. Why (1) lost: a ledger had a permanent size ceiling (review F3: 16KiB is about 65 issuances, then every legitimate append is refused for ever), could not be merged when two appends raced (F9), and its lines were signed by nothing, so any member could append a plausible line. A per-operation file is root-signed content (the leaf itself, or a statement), so it is verified on its own when added, is bounded by a per-file cap, and two operations never touch the same path. The CRL stays the enforcement artifact; the superset rule (revoked_set: superset) makes a reissue unable to un-revoke, and pki.RevokeSerial builds each new CRL from the CURRENT CRL plus the serial so the rule holds by construction.

Names: any unique name (ksuid or timestamp prefix) is fine; nothing may derive order or meaning from it (D18). The fleet root directory (the master's machine) still keeps its LOCAL issued.jsonl/revoked.jsonl as its own audit log; that is not the fleet repository. Master-side tooling that writes these files into the fleet repo is P5 scope: nothing writes them automatically yet.

CONSEQUENCE: the CRL grows without bound and carries no max_size; the reader bounds its read at 64MiB as a memory guard only. MISREADING: 'there are no ledgers anywhere' is wrong; only the fleet repository has none.
