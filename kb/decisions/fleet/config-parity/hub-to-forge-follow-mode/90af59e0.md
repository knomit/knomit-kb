# The hub-to-forge move ships as a mode of POST /fleet/follow on the hosting master, atomic and e2e-tested, with the push BEFORE the attach: the user's 'point to a remote, push everything, then turn sync on; everything else works the same'

DECIDED (user, 2026-10-16, PR #529 audit). QUESTION: a self-hosted fleet (the hub) has no generic equivalent of 'connect this repo to a remote'; DELETE origin is POST /fleet/host and attach is POST /fleet/follow, which only took peers. Should the hub be able to move onto a forge, and by what route? OPTIONS: (a) never, a fleet is created on a forge or on a hub for life; (b) a separate route (POST /fleet/move); (c) a mode of POST /fleet/follow on the hosting master. CHOSEN (c), by user ruling: 'point to a remote, push everything, then turn sync on; everything else works the same'. Atomic (a failed host-record write restores the previous origin) and pinned by an e2e test, cmd TestFleetHubMovesToAForge, in which a member's unmerged change is merged by the fetching master after the move.

WHAT WAS BUILT DIFFERENTLY FROM THE WORDING: the ruling's order 'set the origin, then push' became PUSH FIRST, then attach, because the attach's first origin round trusts the forge's main and could force-update local main on a diverged forge (kb/gotchas/fleet/move/attach-trusts-forge-main/c0e1a84b.md); the worker flagged the deviation in its PR report. The invariant: kb/invariants/fleet/move/onto-forge/d83bd272.md. The same semantics (including the host record) apply to a forge-to-forge move by the master.

MISREADING: 'follow on the master is always a move': the stored forge URL (or none) is a credential change (kb/invariants/fleet/follow/credential-vs-move/7b230fe8.md).
