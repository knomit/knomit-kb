# consensus: off|auto is a per-repo root ontology attribute for USER knowledge bases; auto makes the no-origin host merge every pushed peer branch into its OWN agent branch (the consensus branch follows), never on a repo with an origin; the FLEET repository is the exception (since #524 its merger is gated by the master predicate, with or without an origin, and `consensus` is not read); richer values such as a JavaScript recipe are future (user ruling R5, F08)

## The ruling (R5, user, 2026-09-29, verbatim)

"If the repo is hosted remotely (github, gitlab, etc) then the merge to main is their problem. If the repo is hosted by a knomit instance, then it will be that instance's problem. Since we very all commits for a fleet, I think I am comfortable with the knomit repo owner to actually merge the other agent's branches maybe blindly to begin with" → "if I have a repo that belongs only to me (no origin) and if I accept other agents to commit their branches into it, then I should be able to turn on this feature which will automatically merge agent's work into main. Let's bring in a new "consensus" option per repo, for now with only one possible valu e - "auto". In the future this could become something more fancy like "consensus" could point to a javascript recipe or something. But "auto" and "off" will do for now."

Addendum (user, 2026-09-29): "main" means the repo's configured consensus branch, never a hardcoded name.

## Options considered

1. Merge a pushed peer branch DIRECTLY into the consensus branch. Rejected: the local reconcile only fast-forwards the consensus branch from the host's agent branch and skips when it is not an ancestor; a merge written there would stop it following the host's agent branch, so the host's own facts would never reach it again.
2. Merge into the host's AGENT branch and let the consensus branch follow through the local reconcile. CHOSEN.
3. Let auto act on a repo WITH an origin. Rejected by the ruling itself: with a remote host "the merge to main is their problem". Auto is inert there, and the instance warns once naming the origin.
4. A JavaScript consensus recipe now. Deferred ("In the future … "auto" and "off" will do for now"). The reader treats any value other than off/auto as off, with one warning per blob, so a future value is ignored by an older binary, never acted on.

## The choice (as built in #353)

- `consensus: off | auto` in the ontology's ROOT attributes; absent = off; read at the tip of the consensus branch (svc.UpstreamBranch()).
- auto: an async per-repo merger merges every pushed peer branch into the host's agent branch with a host-signed merge commit, kicked by a peer push and by the consensus branch advancing. It never runs inside the push.
- It is "blind" as ruled: it merges whatever receive-pack accepted (verification stays the existing push gate). But it never picks a side in a conflict: a conflict is refused, warned once and left for a human UI merge. See the F1 gotcha: the peer's own sync can make the retry clean; the user has since approved a fact-level conflict merge to replace that, not yet shipped.
- None on a read-only server or a subscription.

## Not a user ruling

The (b′) no-ff skip rule (MergeConsensus no-ops a peer tip whose new commits are all merge commits and whose merge changes nothing) was the master's call under the implementation brief ("if (b) ping-pongs … fix it"). It is not part of R5 and can be revisited without re-opening R5.

## Non-scope

R5 does not authorize auto-resolving conflicts, merging into the consensus branch directly, or acting on origin-backed repos. "Blindly" means without a human click, not without the push gate.

## UPDATE (PR #524, verified at merge commit 9db8c106): the fleet repository is the exception

R5 above ("if hosted remotely the merge to main is their problem") was written for user knowledge bases and still describes them: `consensus: auto` + no origin. The FLEET repository no longer follows it:

- Its merger runs only where `RepoInstance.isFleetMaster` holds (fleet door, fleet repo, and this instance is the master: the root key file is here and its certificate is the root on main), on EVERY hosting, with or without an origin. The origin is transport only. `consensus` is not read for it, and the built-in fleet ontology (`ontology_fleet.yaml`) no longer declares it. A non-master fleet copy (a member) merges nothing.
- Fleets created before #524 keep a `consensus: auto` line on their main until the master's wholesale ontology refresh rewrites it. Until then the `conflicts` default it implies (merge/consensus) is read at main by the merger's merge, harmless and self-healing.
- The `conflicts` auto-default no longer applies to a fleet created or refreshed after #524: a member branch whose merge would conflict is refused and left behind, never settled by the master.
- For every other repository nothing changed: the gate is `consensus: auto` at the consensus branch AND no origin (consensusMerger.mayMerge).

Misreading: 'consensus: auto is how the fleet merges' is now false; and 'the master merges only on a knomit-hosted (no-origin) fleet' is false: on a forge-hosted fleet the master also merges (see kb/architecture/fleet/master-merges for the forge route).
