# Skills are read from the tip of the repo's CONSENSUS branch (UpstreamTip(svc.UpstreamBranch())), like recipes — never the agent branch, never a hardcoded "main" (D2)

**User ruling, verbatim.** D2: "2) yes, from main". Clarified by the user: "when you say "main" what are you referring to, the branch that is marked as the consensus per repo, correct ? Not something hardcoded "main"" — so "main" means the repo's configured consensus/upstream branch, resolved by svc.UpstreamBranch().

**Options considered.**
1. CHOSEN: the tip of the consensus branch, like recipes. A skill tells every session how to act on the shared repo, so it is what the repo has agreed; a subscription (no agent branch) can serve skills too.
2. REJECTED: the agent branch (or the binding's read branch / an experiment). A session's own unmerged edit would change what every later session on that machine is told, and subscriptions could not serve skills.

**The choice as built (#351).** skillSource.loadFrom reads UpstreamTip(svc.UpstreamBranch()); no branch name is spelled in the new code. Tests use a repo whose origin names "develop" so a hardcoded "main" turns T-C1 red, and T-C2 shows an agent-branch-only skill is not served until the consensus branch advances.

**Consequence / non-scope.** A new or edited skill reaches sessions only once it is on the consensus branch (on a no-origin host, within the local reconcile interval; on an origin repo, after the forge merge). This does not authorize reading anything else from the consensus branch by default.
