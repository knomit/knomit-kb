# Repo skills are ALSO served by a model-invocable read-only tool, knomit_skill, because MCP prompts are user-typed slash commands a model cannot run by itself ("add the knomit_skill tool too")

**User ruling, verbatim.** "add the knomit_skill tool too" — given after the master explained that MCP prompts are user-invoked slash commands the model cannot see or run by itself, while a tool is model-invocable, so a session told "follow the work-task skill" (including a recipe-started `claude -p` session) can fetch it itself.

**Options considered.**
1. Prompts only (R8 as first specified). REJECTED as insufficient: a model cannot invoke a prompt.
2. `knomit.skill(name)` on the recipe/script host (the RCA's named fallback if `claude -p` did not expand MCP prompts). NOT BUILT: it serves only recipes, and it needed its own ruling.
3. CHOSEN: an MCP tool, knomit_skill, beside the prompts, from the same source.

**The choice as built (#351).** knomit_skill {} → name + description per skill; knomit_skill {name} → body + bundled files (same 256 KiB total inline rule), or a named error. Read-only, not a write tool, no new permission. Same binding resolution as the prompts (repo mount → that repo; lens → write repo only), same consensus-branch source, same malformed handling.

**Master's ruling, not the user's:** on the unscoped mount knomit_skill behaves like knomit_query — no binding handle is the gate's error, a handle serves that binding. The brief's "unscoped → none" was the master's wording, and the master clarified it; the user did not rule on it. The prompts on the unscoped mount still list none.

**Non-scope.** The tool does not substitute $ARGUMENTS; the model applies the body. The hand check showed `claude -p "/mcp__…"` does expand MCP prompts on Claude Code 2.1.284, which does not make the tool redundant.
