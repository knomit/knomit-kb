# The mission template's claim window X = 15 s is derived, not tuned: floor = N (3 s pull) + 1 s push countdown + 1 s host fast-forward (the merger's own push wake) + N (one due tick) = 8 s, X >= 1.5x floor, enforced by TestMissionTemplate_TimingRule from knomit's constants — and it holds ONLY while every participant runs F21 with a healthy origin

Under `sync: {push: realtime, pull: realtime}` (F21 S2), examples/mission sets WINDOW_SECONDS = 15 (was 360). The rule (README "The timing rule"): X >= the LARGEST round interval of any participant + push countdown + host merge/fast-forward + one due tick, plus margin.

Where each term comes from in code:
- N = config.DefaultRealtimePullInterval (3 s): under pull: realtime every round, the host's local round included, waits N. Claimers see a task up to one round apart.
- push countdown = pushWakeWindow (internal/repos/sync.go, 1 s): under push: realtime ri.onCommit wakes the loop for every agent-branch commit.
- host fast-forward = pushWakeWindow AGAIN, not a separate constant: the consensus merger calls m.ri.wakeSync() after merging a pushed branch (internal/repos/consensus.go), so the host's local round runs after the same 1 s countdown regardless of the sync setting.
- due tick = N: the on: due sweep rides the round, which fetches before it sweeps.
Floor = 3+1+1+3 = 8 s; X = 15 s (~1.9x); 2X = 30 s > the winner's due latency 2N = 6 s.

TestMissionTemplate_TimingRule (internal/repos/mission_protocol_test.go) reads WINDOW_SECONDS from the shipped claims.js, computes the floor from config.DefaultRealtimePullInterval and repos.PushWakeWindowForTest (export_test alias of pushWakeWindow), requires X >= 1.5x floor and 2X > 2N, and pins floor == 8 s so a constant change forces the README arithmetic to be revisited. Sabotage WINDOW_SECONDS = 5 went red at 691e8a84. Shipped in #383, merged at c6c2625b (a true merge; the template and test blobs are identical to the branch head).

WHEN THE 15 s DOES NOT HOLD (the backstops — losers' re-arm and dup-check — cover these, the window does not):
- a failing origin: one round can take 240 s (2 x the 120 s network_timeout), and after 3 failures the breaker skips for 2N doubling to 30 min — both far above 2X, so a slow live winner can be presumed dead and two peers take the same task;
- a peer on a knomit older than F21: it ignores `sync` (one warning) and syncs every 300 s;
- a host with local_reconcile_interval = 0: no local rounds at all, so no timed due sweep and no timed fast-forward;
- a forge-hosted mission: the forge's merge of agent branches dominates and must be added to X;
- any participant with a larger realtime_pull_interval: X >= 1.5 x (2N + 2 s) for everyone.

MISREADING: "15 s is safe because the breaker protects us" — no. The breaker protects the ORIGIN from being hammered; it makes the failing participant slower, not the window safer. Also: dropping `sync` on GitHub to save requests removes the ONLY fast path, since the template no longer has do: push triggers; X must go back to ~360 s.

THE RULING, VERBATIM. The user's request (2026-10-01): "hmm... I actually want an ontology option which will describe how pushes and pulls should be handled. So, when we're in real time mode for push, use the "do: push" mechanism (commit triggers 1s window triggers push) but for all commits. When we are in real time for pull, actively do a git sync every whatever configured real time pull interval is - let's say 3s by default, configurable in the knomit toml file." F21 decision 5 was "Ship the F08 template follow-up (X → 15 s, healthy origin only) after this design merges"; the user's answer to decisions 1–6: "1) yes. 2) yes 3) yes 4) explain 5) yes. 6) yes." (see kb/decisions/repos/sync/sync-mode-decisions-1-6/7e598594.md and kb/decisions/repos/sync/sync-mode-request/2e670e78.md).

REJECTED OPTIONS (ruled out by approving decision 5):
- Keep X = 360 s with `sync` on: correct but about 24x the 15 s the realtime rounds support; every claim would still wait six minutes, which is the latency the request set out to remove.
- Keep the four `do: push` triggers beside `push: realtime`: redundant (realtime push already opens the same 1 s countdown for every agent-branch commit), and they would hide a missing or mistyped `sync` — the template would still push fast while pull fell back to 300 s, so X = 15 s would silently be wrong. Removing them makes `sync` the single source of the fast path, pinned by TestMissionTemplate_Settings.

LIVE CHECK (reviewer, post-merge acceptance of #383): claims reached the host in 1.5–2.1 s; 5 races each had exactly one taker, within 23 s; the control without `sync` took over 10 s.
