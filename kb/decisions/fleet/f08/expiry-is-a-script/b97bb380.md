# Expiry is a trigger script (on: due + do: script + knomit.retract), not a built-in action — and a due fire dropped for capacity (rate-limited, busy) is now retried at the next sweep

User ruling R2 (2026-09-29, verbatim): "A) a script." → confirmed "A) ok": expiry is a trigger script (`on: due` + `do: script` + `knomit.retract`), no built-in retract action.

OPTIONS CONSIDERED
- (A) expiry as a trigger script (CHOSEN); a built-in retract action on due (REJECTED: R1 asks for generic operations composed, not specific implementations).
- What happens when the script rate cap drops a due fire (the F08 RCA measured: the due mark was written in phase A regardless, so the fact NEVER expired):
  - keep dropping it (REJECTED: measured loss);
  - retry only fires dropped for CAPACITY — outcomes `rate-limited` (script cap) and `busy` (a `do: run` recipe at its `concurrent` limit) — by not writing their mark, so the next sweep fires them again (CHOSEN);
  - also retry `script-error` / `script-timeout` (REJECTED: usually deterministic, so it would re-fire every tick for the life of the fact; for claims the losers' re-arm covers a transient error, and for expiry every instance expires the task).

RATIONALE
A due fire is a STATE re-derived every sweep, so re-evaluating it is not a replay of an event; learn/update/retract fires stay dropped for good. The retry is bounded by the tick, never a hot loop. With R9 the expiry trigger is one line: `js: "knomit.retract(change.path)"`.

Consistent with kb/decisions/fact/expires/never-acted-on/a2a8fe01.md: knomit ITSELF still never acts on `expires`; a repo's own trigger script does, which is the composition R1 asks for.

THE CHOICE
Merged in PR #348 (merge commit 53d102e9): runState.dueRetry, marks skipped in buffer(). Details: kb/invariants/repos/triggers/due-marks/db770fa9.md.

NON-SCOPE: no built-in retract action, no timers other than `due`, and no retry of non-due fires.
