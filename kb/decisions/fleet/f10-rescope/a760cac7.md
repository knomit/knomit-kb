# F10 re-scoped to: the admitted set IS the fleet repo (already done), signer policy DROPPED, and each member record carries operator-declared addresses plus host-detected capabilities, refreshed at every boot; probe-before-use left to its consumers F13/F16

The original F10 proposal (.claude/future/fleet/proposals/F10-peers-admitted-set-signer-policy.md) bundled an admitted set of peers, a signer policy for protected paths, and peer addressing. F09 PR 5 had already made the fleet repository's member records the admitted set (who may sign is kb/decisions/fleet/source-of-truth/6ddfdd1a.md, unchanged here). The user then ruled the remainder in a series of messages, quoted verbatim below (brief .claude/plans/2026-09-28-brief-F10-member-addresses.md, rulings table). The work shipped in PR #336, merge 013dbe01.

RULINGS (user, verbatim):
1. F10 scope: "1. ok. 2. drop. 3. ok, makes sense" (admitted set = the fleet repo, done; signer policy for `.knomit/**`/`principles/**` DROPPED; addresses and capabilities live on the member record; probe-before-use goes with its consumers F13/F16).
2. "In the fact registration I think we should automatically add the loopback_hosts as well, so they know where to connect to the agent" → "how would knomit know for example what protocol and port tailscale is using ?" → "I don't think blindly adding the loopback hosts is valid" → "no, no magic guesses. could we instead have this defined in knomit.toml ? like 'external addresses' or something".
3. "I want the registration to be automatically updated at start time, for example, if knomit starts and the external address from the fleet registration is outdated, it should be updated. Same for all the other capabilities."
4. F09 design (rev 6.6): member record = CURRENT state + CURRENT key, history via the fact's versions; registration = own agent branch + merge into the fleet's `main`; fleet membership state in control.db; no fleet in any KB ontology.
5. Trust model: build the capability, no hardening; a member's own record is its own claim.
6. "I want to add os and platform detection (arm, x64) to the capabilities" (the claude/agy PATH part withdrawn: "ignore the claude and agy request. everything else stays").

OPTIONS CONSIDERED AND REJECTED:
- Signer policy for `.knomit/**` / `principles/**` (restricting who may sign commits touching those paths): dropped by ruling 1.
- A separate `peers` topic per KB: rejected. Fleet data lives only in the fleet repo, and no KB ontology names a fleet (ruling 4).
- Invented capabilities (lanes, concurrency caps, a subscribe-only flag that does not exist at instance level): rejected. Capabilities are only what knomit detects on its own host: os and arch from the Go runtime, the version string, read_only.
- Deriving addresses from auth.loopback_hosts plus the listen port: rejected by ruling 2 ("no magic guesses"). knomit cannot know the protocol and port a proxy such as tailscale exposes.
- A self-probe at registration (checking that an address answers): rejected. Probe-before-use belongs to its consumers F13/F16 (ruling 1).
- An override field in the register request (PUT /api/v1/fleet carrying addresses): rejected. knomit.toml `external_addresses` is the one place the operator declares them.
- Manual re-registration as the only refresh path: rejected by ruling 3. The record is reconciled at every boot as well as on re-registration.
- claude/agy PATH detection as capabilities: requested, then withdrawn by the user (ruling 6).

THE CHOICE (as built):
- A top-level knomit.toml `external_addresses` list (scheme://host[:port], validated at boot), copied verbatim into the member record.
- `git: /git` only when the instance mounts /git.
- `capabilities: os arch version read_only`.
- At boot, a registered, non-read-only instance compares its own record on its agent branch with the current config and binary. It writes at most one compare-and-swap version and never touches state. The update reaches the fleet's main by the operator's merge like any agent-branch commit.

NON-SCOPE: this does not make addresses trusted or reachable; nothing validates or uses a peer's addresses yet. It is not a signer policy of any kind. It does not refresh the record automatically outside boot and re-registration.
