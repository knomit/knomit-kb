# `knomit fleet` gets thin verbs for every mutating fleet route (user ruling 2026-10-27): each verb only calls the existing RequireLocalVia REST route over the local socket/pipe and prints the answer; the CLI never does fleet work itself

DECISION (user, 2026-10-27). Trigger: the web UI on a non-local page says 'Not in a fleet — create or join from the desktop app', and the user wanted to run fleet operations from a terminal against a running instance, as `knomit fleet ...`.

OPTIONS PUT TO THE USER: (a) thin named verbs — create, enroll, join (+ join:check), leave, revoke, decommission, root get/put/delete — each a client of the existing local-socket route: CHOSEN. (b) one generic passthrough (`knomit fleet api POST /fleet/join < body.json`), which keeps the letter of the 2026-10-15 ruling: NOT TAKEN. (c) status only, operators curl the socket: NOT TAKEN.

SCOPE CHOSEN: every route in the RequireLocalVia fleet group in one PR (not only the join/enroll path).

WHAT IT SUPERSEDES: the 'no new `knomit fleet ...` CLI verbs' half of kb/decisions/fleet/create/rest-first-local-only/b001bb23.md. WHAT IT KEEPS: that fact's other half — every fleet operation is a REST endpoint first, the gate is the RequireLocalVia group on the server, and a CLI that does the work itself (mints keys, writes control.db, installs a bundle in-process — the pre-#525 `identity init-root|enroll|install` shape) is still not allowed.

CONSEQUENCES: the verbs dial the same local listener `knomit fleet status` uses, so they work only where a server is running and only on its own machine; the authorization is the socket's, unchanged. A new mutating fleet route still goes inside the server's RequireLocalVia group first; its CLI verb, if any, follows.

MISREADING: 'the CLI may now do fleet operations' — it may only REQUEST them from the running server; with no server running, every verb fails rather than acting offline.
