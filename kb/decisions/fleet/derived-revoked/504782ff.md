# `revoked` is derived for READERS only (FleetStatus.record_state, GET /fleet/members) from the CRL at the same main, never written and never fed to the judge, so the judge's input stays exactly what is on main and rule B keeps its own `revoked` refusal; the leaf's key is not compared with the record's key

Decided and built in PR #523 (merge commit 3ac59b57), design item M6.

WHAT. store.FleetPKI.Revoked(id) (internal/store/fleet_read.go) is true when the leaf at certs/<id>.pem chains to this revision's root AND its serial is on the CRL the root signed (pki.ErrRevoked from verifyLeaf, the chain check shared with leafFor). repos.Manager.fleetMembersAtMain (internal/repos/fleet.go) sets State = revoked on each member for which that holds. Only the READERS use it: FleetStatus.record_state and GET /fleet/members. The record on main still says what its owner wrote (usually active); `revoked` is never written to a record, and fact.ParseMember still accepts the word.

WHY THE JUDGE DOES NOT GET IT. The judge's input (FleetAtMain) stays exactly what is on main: the records as written. And rule B keeps its own refusal reason: a revoked leaf is refused `revoked` because of the CRL, not because of a record state. Deriving the state into the judge's input would change which rule names the refusal and make the judge read something that is not on main, for nothing gained.
THE WRONG REASON, which must not be repeated: 'deriving it in the judge would flip mayRegister and let rule A re-admit a revoked id'. That is FALSE: rule A (selfRegistration -> leafFor -> verifyLeaf) re-checks the same CRL, so a revoked leaf is still refused `revoked` by rule A itself.

WHAT Revoked DOES NOT DO. A missing, unreadable or foreign leaf, or an unusable root or CRL, is NOT 'revoked' (nothing the root signed says so); the judge refuses those on its own terms (rule B: no-cert). It does NOT compare the leaf's key with the record's key: whatever leaf sits at certs/<id>.pem decides. That is display-only. Example: a record rotated to key K2 over a revoked K1 leaf reads `revoked` to readers while the judge says key-mismatch. It is not exploitable, because only the artifact rules (a root-signed leaf, leaf-renewal) can change certs/<id>.pem.

MISREADINGS. 'A revoked reader state means the gate refuses the member's commits for state reasons' is false: the gate refuses by rule B from the CRL, and the reader state is a view of the same CRL. 'The record says revoked' is false: the record on main still says active.

PINNED BY: internal/repos TestFleet_RevokedIsDerivedFromTheCRLAtMain (revoked at the CRL revision; another member stays active; the record on main still says active). Sabotage (no derivation; revoked for any leaf that chains) red.
