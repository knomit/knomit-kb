# Backup is a warm-start CACHE for cold boot — it must never refuse a boot, and never be protected as if it were durable state

PURPOSE, stated by the project owner: the backup tool exists to help containers and the server BOOT FASTER FROM A COLD BOOT. It is not a durability mechanism.

This follows from [[git-is-the-only-source-of-truth]]: the SQLite databases the replica holds are rebuildable cache. A repo with an origin can be re-cloned; losing the replica costs boot TIME, never data.

OPTIONS CONSIDERED:
(a) Treat the replica as durable state to be protected — the shape the feature was originally built in. Refuse the boot when a restore fails (ErrRestoreIncomplete), refuse when a registered repo has no DB and no origin (StrictMissing), refuse when the replica's TXID is ahead of local (Preflight/ErrDiverged), fail the boot when backup.Open cannot reach the object store, and ship `knomit restore` to overwrite a corrupt database from the replica.
(b) Treat the replica as a cache — every failure degrades to a slower boot, and git/origin is the recovery path.

CHOSE (b). Rationale: every refusal in (a) protects the replica, and under the source-of-truth principle there is nothing there to protect. Worse, the refusals convert a cache miss into an OUTAGE — the failure mode is strictly worse than the one being prevented. Recovering a corrupt database is 'point the repo at its origin and re-clone', which the repo registry already records the origin for.

CONSEQUENCES a consumer must act on:
- A backup failure NEVER fails the boot. backup.Open failing, a restore failing, or a replica being absent all log loudly and continue.
- Do not add divergence/two-writer detection back. A stale or contended replica is a cache-coherency annoyance; the answer is to re-clone, not to refuse.
- Do not add an operator command that overwrites a live database from the replica.
- The repo registry (control.db `repos` table) SURVIVES and is load-bearing: it records each repo's origin URL/branch, which is what makes 'rebuild from origin' possible on an empty disk. It is not part of what was cut.

NON-SCOPE — the boundary this decision does NOT cross: knomit stores git objects INSIDE the SQLite file (internal/store/git, the storegit Storer). For a repo created WITHOUT an origin (preset/custom create mode), that .db is the only copy of its git history, so for those repos the replica is genuinely durability rather than cache. The ruling above was made for the container/server deployment where repos clone from origins. It does not license treating a local-only repo's database as disposable; that case gets a loud warning, and if it ever needs stronger handling the decision must be revisited rather than assumed.
