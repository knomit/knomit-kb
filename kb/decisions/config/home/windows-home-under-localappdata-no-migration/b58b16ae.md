# On Windows the knomit data root defaults to %LOCALAPPDATA%\knomit\home for ALL binaries (knomit, kb, knomit-desktop), with no ~/.knomit fallback and no migration

Decided 2026-09-20 by the project owner after the C:\.knomit incident (see kb/gotchas/config/home/windows-drive-root/63dbce31.md).

Options considered:
1. Auto-migrate an existing %USERPROFILE%\.knomit to the new location on first launch (move or copy; must not run under a live server; breaks hand-made PATH entries to the old bin/).
2. Honour %USERPROFILE%\.knomit if it exists, default only NEW installs to LOCALAPPDATA (two populations forever; the answer to "where is my data" depends on filesystem state).
3. Require KNOMIT_HOME explicitly on Windows (breaks download-and-run; a tray app cannot prompt for it).
4. Keep ~/.knomit on Windows and only fix the dropped-error bug.

Rationale: Windows support has NOT been released, so there is no installed base to migrate and no reason to carry a second resolution branch. The owner's hard requirement is that the path be PER USER and IDENTICAL whether the server is started from PowerShell (`knomit serve`), through the bridge (`kb`), or by the desktop app; any scheme where two launch paths could resolve different roots means re-downloading the 617 MB models and re-initialising identity and repos, which is exactly what options 1 and 2 risk. %LOCALAPPDATA%\knomit is already where the desktop keeps its state (server.json, logs, update.json), with a written Local-not-Roaming rationale; the `home` subdirectory keeps the data root (control.db, repos/, models/, keys, bin/, knomit.toml) out of the folder the desktop's "reveal logs" menu opens.

Choice: config.Defaults()/Load() resolve Home on Windows to %LOCALAPPDATA%\knomit\home, via ONE exported helper that tools/desktop/internal/paths also uses for the parent, so the two cannot disagree. UserHomeDir/LOCALAPPDATA lookup failures are errors that stop startup with an actionable message, never a drive-root path. KNOMIT_HOME still overrides everything (kb/conventions/config/knomit-home-single-root/2549af57.md unchanged). No code path consults %USERPROFILE%\.knomit on Windows. Linux and macOS defaults are unchanged.

WHERE THAT HELPER LIVES (the paths above are unchanged by this; only the location of the code moved). It was briefly a package of its own, internal/apppaths, which is now DELETED and split in two:
- internal/config — config.DefaultHome / config.StateDir / config.LockfilePath, plus the only spellings of "knomit" and "home". This is the exported helper the paragraph above means.
- internal/platform/userdirs — the OS half: which directory Windows/macOS/Linux designate, the %LOCALAPPDATA% reconstruction, and the never-guess-a-drive-root rule. It joins no app name and knows no application.
See kb/gotchas/architecture/internal-package-layout/platform-tier-parameterise-limit/86953386.md for why the split lands there.

Non-scope: this does not move macOS to ~/Library/Application Support or Linux to XDG_DATA_HOME; it does not authorise any migration code; and it does not change the desktop's state dir. If Windows support later ships and the location must change again, THAT is when a migration decision is needed.
