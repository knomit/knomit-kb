# Machine-local operational state lives in one control-plane database <home>/control.db; lenses are its first tenant

**Options considered:** (a) a dedicated `<home>/lenses.db` just for the lens registry (RFC revision 2 as first published); (b) a general machine-local configuration/state database hosting lenses as one table set among future tenants. Name candidates for (b): control.db (chosen), local.db, system.db, knomitd.db.

**Rationale:** More machine-local operational concerns are coming (authentication, settings); one DB per concern proliferates files and lifecycle wiring. A single control-plane DB gives them one home and one Manager open/close point. The name `control.db` encodes the architectural split: knowledge repos are the DATA plane (git-backed, synced, shared across machines); `control.db` is the CONTROL plane (per-machine operational config and state, never synced, not git-backed). Avoids collision with the existing `core.db` (the default repo's store).

**The choice:** `<home>/control.db`, opened in Manager.Start and closed in Manager.Close. Each concern owns a namespaced table set created with CREATE TABLE IF NOT EXISTS; lenses (`lenses`, `lens_reads`) are the first tenant; future tenants add tables without touching existing ones.

**Non-scope:** Does not put knowledge or anything shareable in control.db — anything that needs provenance, sync, or sharing belongs in a git-backed repo (the git-is-the-only-source-of-truth tension is accepted only for per-machine operational state).
