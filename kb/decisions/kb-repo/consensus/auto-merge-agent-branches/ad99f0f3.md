# knomit/knomit-kb on GitHub auto-merges every push to an agent/* branch into main through a workflow-opened, workflow-merged pull request (merge commit); conflicts fail the run and leave the PR open until the agent's next local-wins sync pushes a clean branch

**Context (2026-09-15):** the maintainer asked for GitHub to merge changes from any `agent/*` branch into `main` automatically, as a merge commit, as they arrive, for the knomit-kb repository (the origin of the knomit-dev lens's write repo). Until then agent branches were merged by hand as PRs #10–#13. This is the consensus half of the agent-branches principle: each agent writes its own branch, main is reached by merge.

**Options considered:**
1. Workflow merges locally and pushes main with GITHUB_TOKEN. Rejected in practice: main carries a repository RULESET (id 19773107) requiring every change to arrive through a pull request, no bypass actors, 0 required approvals; the direct push is refused (GH013). Rewriting the ruleset to add a bypass was not wanted.
2. Workflow opens (or reuses) a PR from the agent branch and merges it via the API with the merge method. CHOSEN. Produces the same "Merge pull request #N from knomit/agent/…" commit the manual flow did, and the ruleset is satisfied rather than bypassed.

**The workflow** (`.github/workflows/merge-agent-branches.yml` on main, landed by PR #14): triggers on push to `agent/**` and on workflow_dispatch with a branch input; one run at a time (concurrency group, never cancelled) so two agents land one after the other; resolves the branch tip by sha; uses the compare API `main...tip`: `ahead_by == 0` ⇒ already in main, skip; `files == 0` ⇒ the branch only absorbed main, skip (no empty merge commit); otherwise open or reuse a PR and poll mergeability (GitHub computes it asynchronously) up to five times, then `gh pr merge --merge`. First real run: PR #15 merged agent/mindev.local-8ef0cd32 (20 commits, 19 files); a push-triggered run for agent/h1v302 correctly skipped as already in main.

**Conflict policy:** NOT resolved by the workflow. A CONFLICTING PR fails the run and stays open. The knomit server's steady-state reconcile (internal/store/remote_reconcile_merge.go) then merges main into the agent branch with StrategyLocalWins and force-pushes, which re-triggers the workflow on a branch that now merges cleanly. So conflicts self-heal on the agent's next sync; GitHub never picks a winner.

**Why no ping-pong:** after the merge commit M on main, the agent tip is an ancestor of M, so the server's reconcile fast-forwards the agent branch to M (no new commit); only real local commits produce a new push.

**Required repo setting:** Settings → Actions → Workflow permissions → "Allow GitHub Actions to create and approve pull requests" (API: `can_approve_pull_request_reviews: true`). Without it `gh pr create` fails with "GitHub Actions is not permitted to create or approve pull requests"; this was the first failure and was enabled on 2026-09-15.

**Misreading to avoid:** this does not mean agent branches are deleted or rebased on merge; they are long-lived and force-pushed by their owning machine, and the workflow never touches them. It also does not mean main accepts direct pushes: it does not, for humans or bots.
