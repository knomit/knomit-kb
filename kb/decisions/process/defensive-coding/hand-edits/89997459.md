# Don't add docs, validations or tests whose only job is to stop someone deliberately hand-removing or hand-editing something (user ruling 2026-10-28: 'enough defensive coding'); guards against the project's OWN accidental regressions are a different thing and stay

DECISION (user, 2026-10-28). Offered a one-line addition to the knomit-playbooks mission template README saying the `frames` topic must be kept (the ruling 'missions keep frames like inbox, acks and annotations' lived only in two playbooks KB facts), the user declined: "no, leave it - enough defensive coding. If people go and remove by hand stuff, it's their problem".

RULE. Do not propose extra docs, warnings, validations or tests whose ONLY purpose is to protect against a person deliberately deleting or editing something they chose to touch (a template topic, a config key, a generated file). The ruling can live where it already is (here: the KB facts).

WHAT IS STILL WANTED. A regression guard against the PROJECT itself accidentally losing a shipped behaviour is not 'defensive coding' in this sense: the same day the user asked for TestMission_FramesTopicNeedsDedupOff (knomit PR #669), which fails if the shipped template's frames topic loses learn_dedup: off.

MISREADING. 'Never add protective tests' — wrong: tests that pin what the project ships stay. The line is who causes the change: a deliberate manual edit by a user is theirs to own; an accidental change in the project's own code or templates is a regression worth catching.
