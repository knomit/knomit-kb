# Windows test slowness is fixed by a test-only SQLite durability switch (synchronous=OFF, WAL kept), not by raising go test -timeout

Context (#365): on Windows CI internal/web takes ~281s (42s ubuntu, 61s macos) and once hit go test's 10-minute default (600s, a 1s test running at the cutoff: slow, not hung). Per-PR CI wall-clock is median 24 min, max 44 min, critical path always slow-tests (windows synthesize).

Measured root cause (local Windows 10, 737s package): ~400 tests each build a repos.Manager and create real repos; each repo create costs ~0.8s, almost all SQLite WAL file creation plus checkpoint/close syncs, plus initLocal opening a store, closing it, and Add reopening it. Raw migrate.All: WAL default sync 170-400ms, WAL sync OFF 130-150ms, journal MEMORY + sync OFF 11ms. With main-DB sync OFF, session DB journal MEMORY, control.db sync OFF, the package went 737s -> 278s, all 830 tests passing.

Options considered:
1. Raise -timeout on the web step (Windows 20m), following the existing contract-timeout/slow-tests pattern. REJECTED: it normalises 30-minute PRs; the goal is fast tests, not a higher ceiling.
2. Test-only SQLite durability switch set from TestMain. CHOSEN.
3. Stop initLocal's close+reopen (production change). DEFERRED to its own ticket: changes create-path ownership and rollback.
4. t.Parallel on fixture-heavy tests. REJECTED for now: some tests swap globals (log.Logger, timeNow), and Windows has a runtime-fault history (#279).

Choice: one switch in store/repos, enabled only from a test package's TestMain (never an env var, never production code; archtest guards that production never calls it), that sets synchronous=OFF on every DB the tests open (main store DB, session sidecar, control.db, and the OAuth web fixture's control.db). WAL is KEPT by default: leaving WAL changes locking semantics that concurrency tests depend on (e.g. TestPathHistory_RebuildDoesNotBlockWriters, #366). Moving the session DB to journal MEMORY is allowed only if measured gain over WAL+sync OFF is large and the user sees the numbers first. The switch is then measured on internal/synthesize, repos and store, since synthesize is the PR critical path.

Non-scope: this does NOT mean tests may skip durability-sensitive behaviour, or that a test of crash recovery or fsync ordering may run under the switch; such tests must opt out. It does NOT authorize lowering durability in production, nor raising the per-step -timeout as an alternative fix for any other slow package.

OUTCOME (PR #398, merged as f05522da on 2026-10-02):
- Shipped as store.SetTestFastDurability, enabled only in internal/web's TestMain (main_test.go).
- The switch is applied inside the sqlite3_knomit ConnectHook, because the hook would override a DSN value (kb/gotchas/store/sqlite/dsn-vs-connect-hook/3546d60c.md). control.db gets store.SyncDSNParam().
- Guards: internal/store/test_durability_test.go, internal/repos/control_durability_test.go, and archtest TestFastDurabilityOnlyReferencedFromTests.
- The session DB stays WAL. Moving it to journal MEMORY would bring internal/web from 389 s to 240 s locally; it was not shipped.
- Measured locally (Windows 10, quiet box): internal/web 706 -> 389 s. Measured but not enabled: store 588 -> 342 s, repos 1364 -> 775 s.
- Windows CI: 216 s and 275 s on the PR, against a baseline of 15 runs with median 329 s, range 234-602 s. That suggests a gain but does not prove one: the runner's own variance is about 2.4x, and slow runs also slow down storytests in the same step. #365 stays open until post-merge dev runs confirm the tail is clear of 600 s.

EXTENDED (PR #441, merged as 19a6a6da on 2026-10-08): the TestMain of internal/synthesize, internal/repos, internal/store and test/storytests (each a main_signer_test.go) now also calls SetTestFastDurability(true), so all five test binaries named above run with synchronous=OFF and WAL kept. internal/store/migrate is a separate test binary without a TestMain and still runs at production durability.

WHICH TESTS STILL SEE REAL FSYNC: exactly two observe synchronous. They are TestSetTestFastDurability_SyncOffWALKept (internal/store/test_durability_test.go) and TestControlDB_HonoursTestFastDurability (internal/repos/control_durability_test.go). Each one sets the switch for each of its cases and restores the previous value in t.Cleanup. Their "off (production)" case therefore runs at synchronous=NORMAL even under a fast TestMain. Sabotage at the #441 head proved it: deleting the per-case SetTestFastDurability(tc.fast) call makes both "off" cases fail with expected 1, actual 0, while the "on" cases still pass. The other crash-named tests construct the crash state inside the process (an injected swap error, a hand-inserted stage row, then a reopen), for example TestRebuild_FailedSwapLeavesNothingStaged. They cannot observe synchronous, which decides only when bytes reach the platter.

MEASURED (Apple Silicon, median of 3 interleaved runs): store 22.5 -> 22.1 s and repos 131.1 -> 129.4 s, which is no gain. macOS fsync without F_FULLFSYNC is cheap, so the switch cannot show locally. On ubuntu PR CI: store 67.5 -> 66.6 s and repos 184 -> 190 s, one sample each. The expected gain is on Windows, and it is first measurable on the dev push after #441, because PRs no longer run Windows tests (#440).

NOT MEANT: a new test that asserts fsync or crash-ordering behaviour in any of these five packages is not covered automatically. It must turn the switch off for its own duration, the way the two guards do, and it must not be t.Parallel.
