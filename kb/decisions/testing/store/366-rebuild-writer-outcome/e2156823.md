# TestPathHistory_RebuildDoesNotBlockWriters asserts the OUTCOME (a write succeeds at each rebuild pause point, via deriveObjectHook) instead of 'worst concurrent write < 5 s'; test-only, no production change

Context (#366): the test flaked on Windows CI with a 6.8 s write against its 5 s limit while the rebuild took 3.06 s. The RCA found no lock contention; the 6.8 s had two other sources.
- Fixture artifact: clearDerived wipes commit_fp/path_changes and branch `writer` shares main's 2000-commit history, so the writer's FIRST WriteFact re-derives the whole closure itself (deriveBeforeAdvance), in parallel with the rebuild. It takes about as long as the rebuild.
- The first commit after the rebuild pays the WAL auto-checkpoint of the rebuild's backlog (gotcha under kb/gotchas/store/sqlite/wal-checkpoint-after-bulk-write/).
The 5 s duration cannot tell either of these from the guarded regression (derivation moving inside the swap transaction). The test's stated intent ('a writer never sees database is locked') is already asserted by require.NoError(werr).

Chosen (per kb/meta/methodology/measure-outcome-not-the-race/eae2bb22.md):
- Pause the rebuild mid-derive and mid-stage through the existing test-only deriveObjectHook, outside any transaction, and at each pause require a WriteFact on `writer` to succeed. A derivation inside the swap would make it fail deterministically with 'database is locked' (busy_timeout 5 s).
- Keep swap < elapsed/4. Drop worst < 5 s.
- Stop the writer re-deriving the history (orphan branch, or a warm-up write).
- Prove it: forcing derivation into the swap turns it red; it passes under disk load.

Rejected:
- widening the limit (the tail reached 6.8 s idle and 26 s loaded);
- timing only writes inside the rebuild window (a 14.6 s mid-rebuild write was seen under load);
- a production checkpoint as the fix: split out to #403, which the test fix does not depend on.

Non-scope: no production code changes for #366. If deriveObjectHook cannot pause where needed, that is escalated, not worked around in production code.

OUTCOME (PR #405, merged as c079a828): shipped as designed.
- writer is an ORPHAN branch. A warm-up write would not work, because clearDerived also wipes that write's rows.
- The rebuild pauses three times: 'derive', 'derive-end' and 'stage'. The gate is a deriveObjectHook trigger: a hash match plus a callerIs stack check for rebuildCommitLog plus the phase's frame.
- Reaching 'stage' needs the test to drop svc.rh.changes at derive-end. Staging normally reuses derivation's cached change lists and reads nothing from git. The drop mirrors changeLists.put's overflow reset.
- A pause that is never reached fails the test loudly. Verified by renaming the stage frame.
- Forced failures:
  - a tx held across derive+stage+swap fails 3/3 at the first pause with 'database is locked';
  - a tx held across stage+swap only fails 3/3 at the stage pause.
- 5/5 under disk load. -race is clean. Idle cost is unchanged at about 12 s.
- Residual risk: swap < elapsed/4 still times the swap's COMMIT, which can pay a checkpoint (0.5% idle, 7% loaded). #403 would remove it.

SUPERSEDED IN PART by #661 (merge 3abc5c6c): the `swap < elapsed/4` ratio gate (the "Keep swap < elapsed/4" choice and the residual-risk line above) is gone. It put one transaction against the whole unpaused rebuild, and one preemption inside the swap on a loaded runner could break it. The pause-point write checks stay. The property is now checked structurally: the same vcs.DeriveObjectHook (it runs before every derive-path object read) counts each read made while vcs RebuildCommitLog is on the goroutine's stack, split by whether storegit's CommitLogApply (whose transaction runs the swap's Before and Derive callbacks) is also on the stack (`onStack("knomit/internal/engine/store/git.", "CommitLogApply")`). The test requires zero reads inside the swap and a positive count outside (about 14,000 on the 2000-commit fixture, which also proves the hook was reached). LastSwapDuration is only logged now.

Sabotage, against a commit (reviewer): a fresh deriver commit() read at the top of RebuildCommitLog's swap `before` callback turns it red ("Should be zero, but was 1"; the author's own run with one indexItems read gave "was 5"); moving staging into the swap turns red through the pause write (busy timeout).

KNOWN LIMITS, stated in the test's comment: the check does NOT see (1) a read on ANOTHER goroutine started inside the swap (the reviewer made one and the test stayed green: neither RebuildCommitLog nor CommitLogApply is on that stack), (2) a read that bypasses deriver.readGuard (a direct rh.repo object read), and (3) a read deeper than onStack's 128 frames. A flag set for the swap's duration would not close (1): the only hook inside the swap, vcs.SwapHook, runs AFTER the rebuild's own swap callback, which is where a stray read would most likely go. Reads in the Derive half of the swap are refused in production anyway (readGuard returns ErrReadInApply before the hook runs, so the hook never counts them); the new check adds coverage mainly for the Before callback. Do not read a green run as "nothing reads git during the swap" for code that fans out to goroutines.
