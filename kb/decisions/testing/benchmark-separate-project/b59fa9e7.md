# knomit-bench (the fact-quality benchmark) is a separate top-level project, not an in-repo test package

**Options considered**

1. In-repo package: `test/mcpbench` + a `knomit bench` subcommand sharing the engine (the initial draft of proposal 21).
2. Separate top-level project: `knomit-bench`, its own repo/module, shipping one binary that takes the knomit binary under test as a target argument (`knomit-bench run --target <knomit-binary> --mode mechanical|model`).

**Rationale**

The benchmark's core principle is measurement at the MCP boundary — the real interface every agent uses. As an in-repo package that principle holds only by review discipline; as a separate module with no knomit import it holds by construction (the bench physically cannot reach internals). Taking the target binary as an argument additionally enables cross-version scoring (v(N) vs v(N−1) scorecard diffs in release notes) and keeps a path open to a public benchmark others run against their own corpora. The user chose option 2 explicitly ("benchmark is the perfect name; I am willing to make that a separate top level project"). Known cost: the `test/testenv` git-fixture helpers must be extracted into a shared library or vendored, since hermetic repo construction is the bench's core need; bootstrap order (extract-first vs vendor-then-extract) is an open question in the proposal.

**The choice**

knomit-bench is a standalone top-level project — a pure MCP protocol client, two modes (mechanical: scripted agent, deterministic, gates knomit CI; model: pinned model, nightly, tracked), four ground-truth mechanisms (golden task sets, git-history replay, mutation testing, planted-structure corpora), reporting a three-axis scorecard (Actionable / Trustable / Discovery) that defines per-phase exit criteria for the refinery roadmap. Full design: `.claude/future/21-benchmark.md`; roadmap integration: `.claude/future/ROADMAP.md` ("The measurement workstream").
