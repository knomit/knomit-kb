# Phase C write-behind is asserted by COUNTING flushes through TestHooks.BeforeFlush (TestDispatch_PhaseCFlushesABurstOnce), not by a latency ratio (#419, #654)

TestDispatch_WriteLatencyIndependentOfTriggers no longer gates on a median ratio. Its old max(1.5x, +3ms) bound passed its own regression (a flush after every run measured 1.46x on a loaded laptop). The ratio is now logged only.

The write-behind property is asserted by TestDispatch_PhaseCFlushesABurstOnce: Settle's quiet-gap timer is held off with FlushGrace = 1h (that only means it never fires inside the test; it is not a speed bound); N=20 writes are made, each awaited until its run completes; TestHooks.BeforeFlush (called once per flush with the run count; it ALSO fires with 0 for a flush that has no run rows, so count calls, do not assume runs>0) must have fired 0 times; restarting Serve flushes exactly once, holding all 20 runs, and the log gains exactly 20 run rows.

Sabotage (d.flush instead of d.maybeFlush at the end of runOnce) gives "20 flushes for 20 runs", red 3 of 3, independent of machine speed.

Consequence: a test of "work X is batched, not per-event" counts the batches through a seam; it never infers them from latency.
