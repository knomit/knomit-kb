# TestCancelCreate_DuringIndexLandsWithoutWaitingForTheIndex drops `elapsed < fullCreate` and its baseline create and asserts state instead (terminal IndexState still "indexing"); a 120 s bound is a hang detector only; the original sawSync/ActivateSync guard no longer exists since #411, and the deterministic coverage is now TestCreate_StageEnterDoesNotParkBehindTheIndexRebuild — test-only, no production gate

CORRECTION (2026-10-22, PR #586, re-read at 8a96c89b). This fact was written at PR #407 and went stale with #411. STALE, no longer true: (1) "the regression stays caught by sawSync (e2e) and TestCreate_CancelledDuringIndexSkipsSyncActivation (deterministic)" -- that unit test does not exist; (2) ActivateSync and indexHealGate are gone, removed by the lifecycle machine in #411; (3) the create has NO "sync" step since #411 (the production steps are clone, done, index, init-git, ontology, ontology-write, persist-origin, probe, push, register, subscribe, template, template-write, validate), so sawSync could never fire and #586 deleted it; (4) the "parks on step 'sync' for the whole remaining index" mechanism is gone. The CURRENT form of that bug is different: the mount walk's Sync.Enter parked on lockBranch(upstream) and the job sat on step "register" (kb/incidents/repos/create-job/sync-enter-parks-on-index-lock). STILL TRUE: the relative timing check (`elapsed < fullCreate`) and its baseline create were deleted (#368/#407); the 120 s bound is a hang detector only; the terminal IndexState == "indexing" postcondition proves the cancel landed before the index finished. The deterministic coverage of "a running create narrates its index, and the driver is not parked behind the index's lock" is now TestCreate_StageEnterDoesNotParkBehindTheIndexRebuild (internal/repos/stage_enter_index_lock_test.go, #586).

ORIGINAL CONTEXT (#368, still accurate as history): the test failed on Windows CI (run 36590870983) with 'a 17.5 s cancel is not less than a 1.88 s full create'. The relative timing check compared two durations taken about 10 s apart on a runner whose disk slowed about 23x in between: the same 202-commit commit-log phase took 0.3 s for the reference create and 7.0 s for the cancelled one. The cancel itself behaved correctly. No sleep, retry or poll exists in CancelCreate, DeleteRepo, Archive, Purge, shutdown or closeFn.

Decisive measurement (at the time, against the since-removed ActivateSync): with the original regression re-injected, `elapsed < fullCreate` still PASSED 3/3 (cancel 0.63 s against create 2.65-3.02 s). The check was blind to the bug it was written for, and a source of flakes.

Options:
1. Delete the timing check and the baseline create, keep the CreateCancelled terminal state and the no-trace checks (then also sawSync, since deleted). CHOSEN by the user. Test-only.
2. Add a second nil-in-production gate (same pattern as indexHealGate, now removed) to hold the heal mid-index under the branch lock. REJECTED: it needs a production hook.
3. Loosen to a multiple of a baseline. REJECTED: still a machine-speed assertion, and shown blind to the regression.

OUTCOME (PR #407, merged as eaf36ca1): shipped as chosen. Review hardening added a postcondition: the terminal IndexState must still be 'indexing'. The anti-vacuity guard runs before CancelCreate, so this proves the index had not finished when the cancel landed. 10/10 pass locally, with cancels at 67-205 ms; the Windows repos leg passed in 12m48s.

WHAT #586 ADDED. The e2e test flaked on the #584 merge for a different reason than #368: the product really parked (Sync.Enter behind the index lock), visible only when the scheduler let the index job win the lock. The fix made the losing interleaving deterministic in its own test (an embedder released only by cancel, a hook on (StageServe, enter)) rather than hoping the e2e hits it. Misreading: this does not mean the e2e cancel test is redundant; it still pins the cancel-lands-before-the-index-finishes outcome end to end.
