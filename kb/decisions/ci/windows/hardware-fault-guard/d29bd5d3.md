# Decided (knomit#279, 2026-09-25): mitigate golang/go#81238 by removing real hardware faults from Windows test processes and guarding for the class in CI, a real Manager in the read-only router tests plus a Windows-only 'no recovered nil dereference' step, rather than skipping the test on Windows, pinning Go, or disabling Green Tea

**Context.** Five Windows build-test runs died of `found pointer to free object`, all right after TestReadOnlyRouter_FactRouteBypassRegression took two nil-*repos.Manager access violations. The cause is golang/go#81238 (kernel exception dispatch overruns the 4 KiB Windows stack reserve on AMX hosts), open with no released fix.

**Options considered.** (a) `t.Skip` the test on windows/amd64: loses the regression coverage on the platform that ships a desktop build, and leaves every OTHER real fault in the suite free to corrupt the heap. (b) Pin go-version: every 1.26.x and 1.27.x is affected; nothing to pin to. (c) GOEXPERIMENT=nogreenteagc on Windows: the stack overrun still happens, only the symptom moves off the inline mark bits into whatever else sits under the stack; it hides, it does not fix. (d) Wait for CL 828724: unmerged as of 2026-09-07, not shown upstream to be the complete fix, no backport issue, and the flake was costing a re-run on ~1 in 40 Windows attempts meanwhile. (e) CHOSEN: give the tests the dependency they dereferenced (an empty real Manager in the read-only router tests, exact 404/503 asserted; an error return from runRows on a nil ONNX session so the embeddings serialize test recovers nothing), AND capture every go test step's `-json` stream through .github/scripts/go-test-capture.sh so a Windows-only guard (.github/scripts/go-test-fault-guard.sh, in build-test and slow-tests) fails on any recovered `invalid memory address or nil pointer dereference`, AND print the runner CPU in the Windows probe so a recurrence can be correlated with an AMX host.

**Rationale.** The tests were never asserting what a recovered-panic gave them; the real dependency makes them better tests on every OS, so the trigger removal is not a Windows special case. The guard covers the CLASS of fault a log can see. `-json` rather than a tee of plain output was forced by review: plain `go test` discards a passing package's output, so the first version of the guard could only ever have fired after the package had already crashed. The CPU line is the one cheap measurement the two incident logs were missing.

**What this does NOT mean.** (1) It does not catch a bare `recover()` that swallows a panic silently; that is a review rule (on Windows a test must never reach a nil dependency), not something a grep can enforce. (2) It does not make production safe: the server recovers handler panics too, and a real fault in a handler on a Windows AMX host corrupts the heap identically. The only production fix is a Go release carrying a fix for golang/go#81238; bump when it lands. (3) It does not mean every `panic:` line is a fault: deliberate `panic("handler exploded")` tests are software panics and the guard deliberately ignores them.
