# Decided (knomit#279, 2026-09-25): mitigate golang/go#81238 by removing real hardware faults from Windows test processes and guarding for the class in CI, a real Manager in the read-only router tests plus a Windows-only 'no recovered nil dereference' step, rather than skipping the test on Windows, pinning Go, or disabling Green Tea

**Context.** Five Windows build-test runs died of `found pointer to free object`, all right after TestReadOnlyRouter_FactRouteBypassRegression took two nil-*repos.Manager access violations. The cause is golang/go#81238 (kernel exception dispatch overruns the 4 KiB Windows stack reserve on AMX hosts), open with no released fix.

**Options considered.** (a) `t.Skip` the test on windows/amd64: loses the regression coverage on the platform that ships a desktop build, and leaves every OTHER real fault in the suite free to corrupt the heap. (b) Pin go-version: every 1.26.x and 1.27.x is affected; nothing to pin to. (c) GOEXPERIMENT=nogreenteagc on Windows: the stack overrun still happens, only the symptom moves off the inline mark bits into whatever else sits under the stack; it hides, it does not fix. (d) Wait for CL 828724: unmerged as of 2026-09-07, no backport issue, and the flake was costing a re-run on ~1 in 40 Windows attempts meanwhile. (e) CHOSEN: give the test the dependency it dereferenced (an empty real Manager, so the non-gated routes answer 404, and tighten the assertion to 'not 403 AND not 500'), AND add a Windows-only CI step that fails on any recovered `invalid memory address or nil pointer dereference` in any go test step's output, AND print the runner CPU in the Windows probe so a recurrence can be correlated with an AMX host.

**Rationale.** The test was never asserting what a recovered-panic 500 gave it; a real Manager makes it a better test on every OS, so the trigger removal is not a Windows special case. The guard covers the CLASS: a sixth Windows fatal of a different shape (internal/embeddings serialize_test.go:124, an onnxruntime nil-deref sigpanic followed by a closechan crash, job 106148265186) is the same 'real fault inside a Windows test process' and would be named by it. The CPU line is the one cheap measurement the two incident logs were missing.

**What this does NOT mean.** It does not make production safe: the server recovers handler panics too, and a real fault in a handler on a Windows AMX host corrupts the heap identically. The only production fix is a Go release carrying CL 828724; bump when it lands. It also does not mean every `panic:` line is a fault: deliberate `panic("handler exploded")` tests are software panics and the guard deliberately ignores them.
