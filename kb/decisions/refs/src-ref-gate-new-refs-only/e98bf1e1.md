# refs.Gate refuses a NEWLY ADDED src:// ref unless it is the full <12-hex>/<path>@<40-hex>:<40-hex> form; legacy refs a fact already carries stay readable and writable; each caller's `prior` is derived by a stated rule; the existence check is deferred

Decided 2026-09-24 for knomit#249 (a placeholder src:// blob landed through knomit_update), by the user via the master session; refined by the PR #282 review the same day; merged as 08d9528b.

**What was wrong.** fact.ValidateRefs (via SerializeFact) holds only the NEW src form to 40-hex hashes, and "new form" meant a 12-hex repo id AND a non-empty blob. Anything shorter classified as Legacy and was accepted unconditionally, so a placeholder repo id, a dropped `:blob` or a whole legacy-form ref got through. "SRC://" in any other case was not even classified as source, so it skipped every rule. Nothing checks existence anywhere.

**Options considered.**
- Syntactic layer, always on, rejecting every non-full src ref including legacy ones: REJECTED. Measured on knomit-kb main on 2026-09-24: 712 legacy src refs in 279 of 825 facts (513 name+short commit, 108 name+full commit, 74 name with no commit, 17 a 12-hex repo with a commit but no blob). knomit_update resends the whole refs list, so this would make 279 facts un-editable.
- The gate rule for NEWLY ADDED refs only: CHOSEN.
- Where the rule lives: in refs.Gate (which already takes `prior` and skips carried refs), not in fact.ValidateRefs (which has no notion of prior and also runs on the read side as warnings).
- For the nil-prior callers: (A) give each a real prior, (B) accept that they refuse or skip legacy-citing facts, (C) apply the rule only in learn/update/REST. CHOSEN A. B breaks "carried refs are never re-judged" for resolutions and merges. C makes two rules.

**The choice.**
1. refs.Gate.CheckBatch refuses any src ref not in prior unless fact.Ref.IsFullSource() holds. The scheme is matched in ANY case (fact.HasSrcScheme, per RFC 3986 §3.1), but IsFullSource requires the canonical lowercase `src://`, so a mixed-case scheme classifies as source and is then refused. The error names each ref and gives the three git commands (rev-list --max-parents=0 | cut -c1-12, rev-parse HEAD, rev-parse <commit>:<path>). Self-refs, src-form problems and unresolvable local refs are all reported in ONE error, each in its own section.
2. PRIOR DERIVATION PER CALLER. This is the part the next person will get wrong: the src rule makes `prior` load-bearing for src refs, so a caller that passes nil while carrying refs forward refuses its own inheritance.
   - knomit_update, REST PUT: the fact's current refs (unchanged).
   - knomit_learn creating a fact, REST create: nil. The fact is new.
   - Experiment {body} resolution (resolutions.Normalize → carriedRefs): the UNION of that path's refs at the experiment's fork commit, on the parent tip and on the experiment tip. Each version was accepted when written, and a resolution that keeps their refs is merging, not authoring. store.ErrPathNotFound means the version is absent; any other read error fails the resolution, because a smaller prior would refuse legitimate refs and blame the resolver. THIS ALSO EXEMPTS LOCAL kb/ REFS: a ref any of the three versions carried is not existence-checked again, even if both tips have dropped it and its target resolves nowhere. With prior = nil every local ref in the body used to be checked; the exemption is historical-not-current applied to the merge.
   - Review prune-merge (ApplyPruneDecisions → memberRefs): the UNION of the member facts' refs, SNAPSHOTTED BEFORE the decision loop. Read at the tip inside the merge loop, a member already deleted by a retract decision, or by an earlier merge in the same call, contributed nothing, and its kept legacy ref read as new, which was exactly the symptom being fixed. computeTransfer still reads members at the tip. That is left as is, because snapshotting it would start pooling the sources of members the judge chose to retract, which is a behaviour change.
   - Distill and discovery: nil ON PURPOSE. They author a new claim that CITES its sources and inherits none of their refs. Both call sites carry a comment saying not to "fix" this.
   - Dedup (carriedRefs), reflect and reinforce: already passed a real prior.
3. Agent-facing wording states the rule and the command only, per conventions/tools/bridge/skills/agent-facing-text. The skill templates say: a src ref you add is the full form, all three values computed with git, never typed or abbreviated; leave refs already on a fact as they are. The gate error and the knomit_learn refs description say the same. The ValidateRefs error calls a ref with a name and no blob "short form: leave it where a fact has it; never add one". The templates' own example src ref named the WRONG blob (storer.go's for service.go) and was fixed. TestTemplates_SrcRefExamplesNameTheRealBlob checks every full-form example against git, and TestTemplates_CarryNoIssueReferences fails on any issue reference in a template.
4. DEFERRED, a separate decision: the semantic existence check (blob == rev-parse <commit>:<path>). Measured against the knomit checkout: 1370 of 1425 new-form refs verify, 3 cited blobs that exist nowhere (fabricated), 1 had a wrong path, and 51 refs cite commits absent from the local clone (orphaned branch/squash commits). So such a check may REFUSE only when the commit is present and the blob differs; an absent commit must come back as unverified. Two candidate designs: (a) a server-side registry mapping source repo-id → local checkout, read with go-git (no git on PATH needed; it is a new config surface, and there is deliberately no registry today — see the src-repo-id gotcha); (b) a bridge-side pre-check, since the `kb` bridge runs in the author's checkout and could verify src refs before forwarding learn/update, with no registry.

**Non-scope.** This does NOT make any src ref trustworthy: an invented well-formed 40-hex hash still passes, which is why computing refs with git remains the rule. It does NOT authorize rewriting or "upgrading" legacy refs, and it does NOT re-check refs a fact already carries. It also does NOT mean every Gate caller should pass the cited facts' refs as prior: only a writer that REPLACES or MERGES existing versions inherits their refs. And it takes effect only where the lens server runs a build containing 08d9528b: a server built earlier still accepts the short forms.
