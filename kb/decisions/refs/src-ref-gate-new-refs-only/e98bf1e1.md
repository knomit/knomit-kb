# refs.Gate refuses a NEWLY ADDED src:// ref unless it is the full <12-hex>/<path>@<40-hex>:<40-hex> form; legacy refs a fact already carries stay readable and writable; each caller's `prior` is derived by a stated rule; the existence check is deferred

Decided 2026-09-24 for knomit#249 (a placeholder src:// blob landed through knomit_update), by the user via the master session.

**What was wrong.** fact.ValidateRefs (via SerializeFact) holds only the NEW src form to 40-hex hashes, and "new form" meant a 12-hex repo id AND a non-empty blob. Anything shorter classified as Legacy and was accepted unconditionally, so a placeholder repo id, a dropped `:blob` or a whole legacy-form ref got through. Nothing checks existence anywhere.

**Options considered.**
- Syntactic layer, always on, rejecting every non-full src ref including legacy ones: REJECTED. Measured on knomit-kb main on 2026-09-24: 712 legacy src refs in 279 of 825 facts (513 name+short commit, 108 name+full commit, 74 name with no commit, 17 a 12-hex repo with a commit but no blob). knomit_update resends the whole refs list, so this would make 279 facts un-editable.
- The gate rule for NEWLY ADDED refs only: CHOSEN.
- Where the rule lives: in refs.Gate (which already takes `prior` and skips carried refs), not in fact.ValidateRefs (which has no notion of prior and also runs on the read side as warnings).
- For the nil-prior callers: (A) give each a real prior, (B) accept that they refuse or skip legacy-citing facts, (C) apply the rule only in learn/update/REST. CHOSEN A. B breaks "carried refs are never re-judged" for resolutions and merges. C makes two rules.

**The choice.**
1. refs.Gate.CheckBatch refuses any src:// ref not in prior unless fact.Ref.IsFullSource() holds. The error names each ref and gives the three git commands (rev-list --max-parents=0 | cut -c1-12, rev-parse HEAD, rev-parse <commit>:<path>). It is reported in the same error as unresolvable local refs.
2. PRIOR DERIVATION PER CALLER. This is the part the next person will get wrong: the src rule makes `prior` load-bearing for src refs, so a caller that passes nil while carrying refs forward refuses its own inheritance.
   - knomit_update, REST PUT: the fact's current refs (unchanged).
   - knomit_learn creating a fact, REST create: nil. The fact is new.
   - Experiment {body} resolution (resolutions.Normalize → carriedRefs): the UNION of that path's refs at the experiment's fork commit, on the parent tip and on the experiment tip. Each version was accepted when written, and a resolution that keeps their refs is merging, not authoring. The two tips fail loudly on a read error; the fork read treats any failure as absent, which errs strict.
   - Review prune-merge (ApplyPruneDecisions → memberRefs): the UNION of the member facts' refs. The merged fact replaces them.
   - Distill and discovery: nil ON PURPOSE. They author a new claim that CITES its sources and inherits none of their refs. Both call sites carry a comment saying not to "fix" this.
   - Dedup (carriedRefs), reflect and reinforce: already passed a real prior.
3. Wording: the ValidateRefs error, knomit_learn's refs description and the skill templates now say the legacy form is kept where carried and refused when added, not "still accepted".
4. DEFERRED, a separate decision: the semantic existence check (blob == rev-parse <commit>:<path>). Measured against the knomit checkout: 1370 of 1425 new-form refs verify, 3 cited blobs that exist nowhere (fabricated), 1 had a wrong path, and 51 refs cite commits absent from the local clone (orphaned branch/squash commits). So such a check may REFUSE only when the commit is present and the blob differs; an absent commit must come back as unverified. Two candidate designs: (a) a server-side registry mapping source repo-id → local checkout, read with go-git (no git on PATH needed; it is a new config surface, and there is deliberately no registry today — see the src-repo-id gotcha); (b) a bridge-side pre-check, since the `kb` bridge runs in the author's checkout and could verify src refs before forwarding learn/update, with no registry.

**Non-scope.** This does NOT make any src ref trustworthy: an invented well-formed 40-hex hash still passes, which is why computing refs with git remains the rule. It does NOT authorize rewriting or "upgrading" legacy refs, and it does NOT re-check refs a fact already carries. It also does NOT mean every Gate caller should pass the cited facts' refs as prior: only a writer that REPLACES or MERGES existing versions inherits their refs.
