# The desktop webview reaches the server ONLY through the Wails asset handler (an /api/ reverse proxy dialing the local socket/pipe) plus ONE Wails Stream, knomit-sse, for the six event streams — not through the server's TCP port, and not through a loopback proxy listener with a token

Decided 2026-10-12 (the desktop-as-separate-process design, Q9 superseded after two spikes); built in PR #488 (merge 2104fd6d), on Wails v3.0.0-beta.28 (PR #487).

OPTIONS CONSIDERED
1. Keep what it was: the webview's API base is the server's TCP port, with the wails origins in the CORS allow-list. Rejected: the design makes the server a separate process that listens on the socket/pipe by default, so the UI must not depend on a TCP port or on a CORS exception.
2. A loopback proxy listener (with a token) that the webview talks to. Verified-correct on Windows by source, but it adds a listener and a credential. Was kept as the FALLBACK for Windows only; the 2026-10-12 Windows run of Streams did not disappoint (kb/gotchas/desktop/transport/windows/d7e80a3e), so it stays unbuilt and is not needed.
3. Asset handler for everything, SSE included, on macOS/Linux, and the loopback proxy on Windows. Rejected: two transports kept in step is the cd92bf55 failure shape (two construction paths), and Wails Streams already work on macOS.
4. CHOSEN: the asset handler for every request/response call (a ReverseProxy mounted on /api/ in front of the SPA handler) and Wails Streams for the six event streams, on every platform. No listener, no token.

RATIONALE: Wails' Windows response writer buffers a response until the handler returns, so SSE cannot go through the asset handler there; a Wails Stream is a held poll whose every response completes, so it works with that writer (see the Windows-writer gotcha). One transport, three platforms.

CONSEQUENCE for a consumer: nothing on the webview's path may dial TCP (archtest TestDesktopUIPathNeverDialsTCP pins it); a new long-lived response for the UI must be a Wails Stream, not a streamed asset-handler response; a new event source in web/src must be opened through openEventStream (web/src/eventStream.ts), never `new EventSource`, or it silently stops working on the desktop (the seam test web/src/eventStreamSeam.test.ts fails on a stray `new EventSource` in logStore.ts).

WHAT THIS DOES NOT MEAN: it does not mean the server has no TCP port (it still binds one; Settings' effective-port readout and every non-desktop client use it); it does not mean the UI uses Wails IPC bindings for data (bindings stay the Settings window's NativeService; data goes through /api); it does not mean Windows is unverified any more, nor fully verified: the Streams carrier was measured on Windows on 2026-10-12 (kb/gotchas/desktop/transport/windows/d7e80a3e) and the loopback fallback is not needed, but the fetch-streamed POSTs streamApply/streamCommit were measured as delivering progress only at the END of the response, with the real wizard not run and the Streams-or-accept decision pending (kb/gotchas/desktop/transport/06f9a76c); and the webview's origin (wails://localhost, http://wails.localhost on Windows) is no longer a CORS client of the server, although the desktop still passes it as CORSOrigins.
