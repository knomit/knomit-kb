# The desktop window is Hidden at creation, and /config.js answers IMMEDIATELY — flagging __KNOMIT_BOOTING__ rather than blocking — because a first launch spends minutes downloading models

Two coupled choices in tools/desktop/app.go. The first is unchanged; the second was REVERSED, and the old form is now a documented trap.

**The window is Hidden at creation** (`Hidden: true` in the WebviewWindowOptions). Knomit is a tray app: the menu bar is the entry point and the window opens only when asked, including on the login-item launch.

**/config.js no longer blocks on the booting server.** It used to: `configInjectingHandler` called `serverBoot.wait` with a 90s `apiBaseWaitTimeout`, on the reasoning that the webview should take a moment longer to paint rather than load against an address that does not exist. That is a good trade for a two-second boot and a bad one for a FIRST launch, which spends minutes fetching ~640 MB of model artifacts (`EnsureModel`, called from `app.New` BEFORE `bootServer` ever listens).

Why blocking was worse than slow: web/index.html loads config.js with a plain `<script src="./config.js">` tag, so holding that request holds the whole DOCUMENT — the user watched a static splash with no way to learn what was happening. And the wait was CAPPED: past 90s config.js 503'd, the page loaded with no `__KNOMIT_API_BASE__`, and `apiBase()` then resolved every request against the webview origin, where the handler's own SPA fallback takes it.

**WHAT THE FALLBACK ACTUALLY DOES — corrected.** An earlier revision of this fact said it "answers 200 with index.html". That is WRONG for API paths and leads to the wrong fix (teaching the client to detect HTML). Measured against the real handler:

| request | result |
|---|---|
| `/` | 200, the app |
| `/toplevel` | 301 -> `./` -> `/` -> 200, one hop |
| `/api/v1/repos` | 301 -> `./` -> `/api/v1/` -> 301 -> … **redirect loop** |

The fallback rewrites to `/index.html` and re-dispatches to `http.FileServer`, which 301s any path ending in index.html to `./` — and `./` resolves against the REQUEST path, so a NESTED path lands on its own parent and repeats. A Go client gives up after 10 hops; a browser reports a redirect error. EVERY `/api/v1/…` path is nested, so every API call taken by this fallback dies this way. This is the same trap as kb/gotchas/web/spa/fileserver-index-redirect-loop/68987070, which the SERVER-side handler already fixed with http.ServeContent; the desktop handler still has it, and the gate below is what keeps anything from reaching it.

The conclusion is unchanged either way: the UI cannot distinguish that from a server that is merely unwell, so it retried forever and never recovered even once the server was up.

WHAT IT DOES NOW: /config.js answers immediately and says which world the client is in — `__KNOMIT_API_BASE__` when the server is up, `__KNOMIT_BOOTING__ = true` when it is not (and NO base, deliberately: the absence is what makes the client's gate unmissable). The client polls `GET /boot/status`, served by the same desktop handler, and adopts the base from it with no reload. `apiBaseWaitTimeout` is deleted.

**THE GATE IS PER-EXIT, NOT PER-CALL, and that distinction cost a review round.** Gating the repo list was not enough: a cold launch still sent `api.listLenses` once, `fetchVersion` TWICE (useVersion plus the read-only effect) and constructed an EventSource for `/api/v1/repo-events`. Two properties make these silent rather than noisy:
- An **EventSource resolves its URL at construction** and its effect was mounted once, so a stream opened against the webview origin stays pointed there for the whole session — index chips freeze and the `reconnect` refetch never fires.
- Every one of these callers has a **swallowing catch**. `fetchVersion`'s failure path leaves the app WRITABLE, so an early call against a read-only server silently unlocks it for the session.

So anything in App that can reach the network must early-return on `serverBooting` AND list it in its dependency array, or it will never re-run once the server arrives. The regression test counts every exit — `fetch` calls and EventSource constructions — rather than naming individual API functions, so a newly added call is caught without anyone remembering to extend it.

CONSEQUENCE for the Go side: nothing serving an HTTP REQUEST may call `serverBoot.wait`. Use `serverBoot.status()`, which is non-blocking and whose non-blocking select is also what preserves the struct's no-mutex synchronisation (apiBase/err are read only on the branch where `done` is already closed). `wait` survives for run()'s tray-badge/fatal-dialog goroutine, which genuinely wants to sleep until the boot settles.

The phases are a WIRE FORMAT shared with web/src/boot.ts: starting, installing-tools, downloading-models, starting-engine, starting-server, ready, failed. An unknown value degrades to a generic "Starting…" there rather than breaking, so change both sides together.

WHAT THIS DOES NOT MEAN: the Hidden-window rule is untouched, and so is the invariant that bootKnomit runs on its own goroutine and never touches Wails. Serving /boot/status adds no listener and no main-thread work.
