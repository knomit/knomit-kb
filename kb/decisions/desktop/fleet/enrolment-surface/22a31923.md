# A desktop-only user enrols as a fleet peer from a Settings "Fleet identity" section over window-gated Wails bindings — not by leaving enrolment to users who already have the CLI, and never through an HTTP route (the bundle also ships the knomit binary since #500, but that is not the enrolment surface)

**Decision 3 of the knomit#256 proposal.** The user chose this on 2026-09-25, and it was built in PR #296, merged as dc28adda.

**Superseded in part by desktop PR 4 (#500, merged 2026-10-12, user ruling).** The bundle now DOES ship the `knomit` server binary beside `knomit-desktop` (one build copied from `make build`, not recompiled). The enrolment-surface decision below is unchanged and still stands: the Settings section and its window-gated bindings remain THE enrolment path for a desktop-only user, and option (b)'s rejection reason (the target user has no terminal habit) is untouched. What changed is only the factual premise "the bundle ships no knomit binary". Read every "ships no CLI" statement below as the state at the time of #296 (2026-09-25), not as current state. Shipping the binary does NOT make `knomit identity install` the desktop's enrolment story, and does not remove the need for the Settings bindings.

**The gap (as of #296).** The desktop bundle shipped no `knomit` binary: only `knomit-desktop`, `kb` and `knomit-okf`. So a desktop-only user could not run `knomit identity install` or `show` at all, even after PR 1 (#290) gave the desktop its mTLS listener.

**Options considered**
- **(a) CHOSEN: a Settings "Fleet identity" section**, backed by Wails bindings on `NativeService`: copy the public-key line, install a pasted or picked bundle, and show enrolment and listener state. This required moving the install orchestration out of `cmd` into `internal/pki`, so the CLI and the desktop run ONE implementation of the checks.
- **(b) Ship the `knomit` CLI inside the bundle**, via `installBundledTool`, as `kb` and `knomit-okf` already are. This was much smaller: no bindings, no UI, no code move. REJECTED as the answer because the issue's target user has no terminal habit. (b) did not block (a); it was offered only as a cheap interim.
- **(c) PR 1 alone.** It served only users who already had the CLI. REJECTED because it leaves the issue's target user with nothing.

**Why install is not an HTTP route** (a structural reason, not a preference). Every route on the app handler is ALSO served on the mTLS listener and by `knomit serve`. An install or replace-root route would therefore be reachable by enrolled remote peers, and on the plaintext port by any loopback process. Bindings avoid that.

Bindings alone are still too wide, because the main window shares the Wails origin. So the trust-changing bindings (`InstallBundle`, `PublicKeyLine`, `SaveSettings`) also check that the caller is the Settings window. See `kb/invariants/desktop/fleet/install-surface`.

**Non-scope**
- This does not add master-side operations to the desktop (`init-master`, `enroll`, `revoke`).
- It does not add CSR-based or online enrolment.
- It does not distribute CRLs automatically.
- It does not add a fleet panel to the shared `web/` UI.
- It did not rule out shipping the CLI later for other reasons; #500 did, for the desktop's server child (PR 5), not for enrolment.
