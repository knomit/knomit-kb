# Self-update needs a NEW semver release channel and a Linux AppImage — the rolling dev-latest tag and the Linux directory tarball are both structurally incompatible with the updater

**Options considered** (2026-07-28 design session).

Versioning: (a) add real semver tags/releases alongside the untouched rolling `dev-latest` — CHOSEN; (b) keep `dev-latest` only and write a custom provider comparing commit SHA / `published_at`; (c) both channels from day one.

Linux packaging: (a) macOS first, Linux in phase 2; (b) AppImage plus a target override — CHOSEN; (c) publish a bare `knomit-desktop` binary as the update asset.

**Rationale — why the current release shape cannot work at all.**

Both providers gate on `semver.IsNewer(tag, req.CurrentVersion)`. knomit's only git tag is `dev-latest`, deliberately deleted and recreated on every run, and the build version is `VERSION.GIT_COMMIT` (e.g. `0.5.0.2a7ae9d`) from the Makefile. NEITHER SIDE PARSES AS SEMVER, so the update check can never fire. This is not a tuning problem; it is a hard block. Semver releases were chosen over a custom SHA-comparing provider because they use the stock code path with zero custom comparison logic and give users release notes that mean something. Conveniently `version.Version` is ALREADY the bare semver (`0.5.0`) — `version.String()` is the one that appends the commit — so `Config.CurrentVersion` needs no new plumbing.

The updater replaces EXACTLY ONE path: `target := bundleTarget(selfExecutable())`, not configurable, and `maybeExtractInto` rejects archives with more than one top-level entry. The macOS `.app.zip` is `ditto --keepParent`, so its single top-level entry is `Knomit.app` and `bundleTarget` swaps the whole bundle — works as-is. The Linux desktop tarball's top-level entry is a DIRECTORY holding `knomit-desktop` + `knomit-bridge` + `knomit-okf` + `lib/`, while the Linux swap target is the bare executable path — so it cannot work. A bare-binary asset was rejected because `lib/` (ONNX Runtime) would never update, so any release bumping the ORT version would silently break Linux self-updaters. AppImage is the only shape that is both one file and complete.

**Two costs the AppImage decision brings, both mandatory work, not nice-to-haves.**

1. **`pkg/updater` is AppImage-unaware** — grepping the whole Wails `pkg/` tree for `APPIMAGE` returns zero hits. Inside a mounted AppImage `os.Executable()` resolves into the FUSE mount (`/tmp/.mount_xxxx/...`), so the swap targets the mount rather than the `.AppImage` file. The fix belongs upstream in `pkg/updater/spawn.go` (honour `$APPIMAGE` in `selfExecutable`); `selfExecutable` is a package var reassignable only from inside the package, so knomit cannot patch it locally. Plan: upstream PR plus a temporary `replace` directive. Removing the `replace` is the acceptance criterion.
2. **`tools/desktop/bundled.go` breaks under AppImage, independently of the updater.** `installBundledTool` resolves `os.Executable()` and symlinks `<home>/bin/<tool>` at the sibling binary. Inside an AppImage that target is inside the FUSE mount, which VANISHES when the app quits — every MCP client wired to `<home>/bin/knomit-bridge` would find a dangling link. Fix: COPY on Linux instead of symlinking, refreshing when the shipped version differs. macOS keeps the symlink, because the `.app` lives at a stable path and the updater replaces the bundle in place.

Also: the AppDir must place ONNX libs at `usr/bin/lib/`, not `usr/lib/`, because knomit resolves native libs from `<exe>/lib`. Keeping them beside the binary preserves that resolution and avoids an `LD_LIBRARY_PATH` dance in `AppRun`.

**Non-scope.** The existing `release.yml` and the rolling `dev-latest` pre-release are UNTOUCHED — this adds a second channel, it does not replace the dev one. Dev builds must never self-update (they carry no pinned key). This does not authorize an opt-in "dev" update channel, though `sparkle:channel` support makes that cheap later. Windows is not a release target.
