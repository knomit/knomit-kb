# Desktop self-update uses Wails pkg/updater's appcast provider with Ed25519 and NO fallback provider, because verification fails open on unsigned releases

**Options considered** (2026-07-28 design session, `.claude/plans/2026-07-28-desktop-self-update-design.md`):

1. Sparkle (the Objective-C framework) via cgo/go-sparkle — the user's opening instinct.
2. `providers/github` + a `SHA256SUMS` checksum sidecar — simplest, no keys, no feed to host.
3. `providers/appcast` + Ed25519, single provider, no fallback — CHOSEN.
4. `providers/appcast` primary with `providers/github` as an availability fallback.

**Rationale.**

Sparkle lost because `github.com/wailsapp/wails/v3` is ALREADY a knomit dependency and ships `pkg/updater`, whose `providers/appcast` speaks Sparkle's own feed vocabulary natively in Go and cross-platform. The ObjC framework buys nothing and costs cgo plus macOS-only scope.

The GitHub provider lost because it CANNOT carry a signature — it populates `Release.Verification` only from a checksum sidecar, SHA-256 only (`providers/github/github.go` `Check`). A digest that ships from the same GitHub release as the artifact protects against a truncated download, not against anyone who can write to the releases. That matters more for knomit than for most apps: the macOS `.app` is unsigned and un-notarized (the release notes tell users to `xattr -dr com.apple.quarantine`), so there is no Developer ID signature underneath. The Ed25519 signature on the artifact is the ONLY integrity guarantee.

The appcast+github fallback lost because of the fail-open behaviour below.

**The load-bearing discovery: `pkg/updater` verification FAILS OPEN on unsigned releases.** `runVerification` in `pkg/updater/verify.go` returns nil when `Release.Verification` is absent. It rejects a signature when no key is pinned, and it checks a digest when one is present — but a release carrying NEITHER installs regardless of whether `Config.PublicKey` is set. There is no "require a signature" flag anywhere in `Config`.

Two consequences a consumer MUST act on:

1. `Config.Providers` holds EXACTLY ONE provider, the appcast one. A GitHub fallback behind it is a downgrade path: take the feed host offline and clients silently accept unsigned artifacts. Availability is deliberately traded away for the guarantee that unsigned artifacts never install.
2. An empty pinned key MUST disable the updater entirely — `configureUpdater` returns before `Updater.Init` when `version.UpdatePublicKey == ""`. "No key" must mean "no updater", NEVER "an updater that skips signature checks". This guard gets its own unit test precisely because it looks like dead weight to anyone simplifying the function.

**Also non-obvious: the signature covers the DIGEST, not the file.** `ed25519Verifier.verify` calls `ed25519.Verify(pub, digest, sig)` where `digest` is the SHA-256 computed while streaming the download (`digestHasher` defaults to SHA-256 on an empty `DigestAlgo`). Sparkle's own `sign_update` signs file CONTENTS. **The feed format is Sparkle's; the signatures are NOT interchangeable** — a genuine Sparkle-generated `sparkle:edSignature` will not verify here. knomit generates its own via `tools/appcast sign`, computing `ed25519.Sign(priv, sha256(file))`.

**MEASURED 2026-07-29 — a self-installed update does NOT re-trigger Gatekeeper.** This was previously an INFERENCE (Go's `net/http` does not set `com.apple.quarantine` the way a browser download does), flagged in the verification checklist as the assumption in this design most likely to be wrong. It is now an observation: an unsigned, un-notarized `Knomit.app` in `~/Applications` updated 0.5.0 → 0.5.1 through the in-app updater and relaunched itself with NO Gatekeeper dialog of any kind. Conditions: macOS (Darwin 25.5.0), arm64, single machine, artifact fetched over plain HTTP from a local staging feed.

**What that measurement does NOT license.** It does NOT mean the app escapes Gatekeeper generally. The FIRST install still arrives by browser download, which DOES apply `com.apple.quarantine` — so the release notes' `xattr -dr com.apple.quarantine` step remains necessary for a manual install and must not be removed on the strength of this result. The scope of the finding is exactly: quarantine is not re-applied by the updater's own download path, so a user who got past Gatekeeper once is not asked again on subsequent self-updates. It also does not generalize to a notarized/stapled future build, where the mechanism differs entirely.

**Non-scope.** This does NOT mean "knomit distrusts GitHub Releases" — the artifacts still live in GitHub releases; only the trust ANCHOR moved to a pinned key. It does NOT authorize adding a fallback provider later for availability reasons without re-litigating the fail-open analysis. It does NOT cover the server/CLI tarball, the `knomit` binary, or Docker — desktop only. And it does NOT remove the need to sign/notarize the macOS `.app`, which remains separately worth doing — see the unsigned-bundle notification gotcha, where the missing signature demonstrably costs the update banner.
