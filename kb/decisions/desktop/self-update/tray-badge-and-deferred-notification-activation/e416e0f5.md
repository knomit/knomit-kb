# Notification setup deferred to ApplicationStarted; tray badge is the persistent surface and the banner a once-per-version event

**Amends [[kb/decisions/desktop/self-update/windowless-notification-flow]]**, which named unverified notification delivery on an unsigned .app as "the assumption most likely to be wrong" and left the banner as the ONLY update surface. Code review of PR #48 turned that from a risk into three defects, fixed together in 80cf99e6.

## Defect 1 — the setup ran before the application existed

`configureUpdater` was called from `run()` before `wapp.Run()`. Inside it, `RequestNotificationAuthorization()` and `RegisterNotificationCategory()` reach the OS notification centre. Two consequences, both verified against the vendored wails v3.0.0-alpha.98-tui:

- Wails runs service startup from INSIDE `Run` (`application.go` `startupService`, after `newPlatformApp`). `darwinNotifier.Startup` is where the guards live — `isNotificationAvailable`, `checkBundleIdentifier`, `ensureDelegateInitialized`. Calling in earlier does not merely skip them: `[UNUserNotificationCenter currentNotificationCenter]` raises rather than returns when the main bundle is not yet resolvable, and an ObjC exception through cgo takes the process. The app would DIE AT LAUNCH where it was supposed to log "self-update unavailable".
- `RequestNotificationAuthorization` is synchronous with a **180-second** timeout (`notifications_darwin.go`), waiting on a completion handler that cannot arrive without a run loop. On the startup path that is three minutes with no window and no tray icon.

**Choice:** split `configureUpdater` by what each half touches, not by tidiness. It returns `(start func(), err error)`. Pure-Go wiring — `Updater.Init`, `OnNotificationResponse`, `Event.On(updater.EventError)` — stays eager and pre-`Run`. Everything platform-touching moved into `activateNotifications`, called from the returned closure, which `app.go` registers on `events.Common.ApplicationStarted` and runs **on its own goroutine** so a slow authorization prompt cannot stall the event handler. The category is registered even when authorization was REFUSED: permission can be granted later without a restart, and a banner naming an unregistered category still delivers, silently losing the button that is the only thing able to install.

## Defect 2 — no surface survived a dead notification centre

`pkg/services/notifications` documents "Your app must be packaged and signed for this feature to work" and knomit's .app is unsigned. With the banner as the only UI, a user whose authorization is denied or unavailable had a running updater, a published release, and no way to learn either existed — the tray item only posted another banner.

**Options considered** (2026-07-29): (a) tray icon badge plus an install-capable tray item — CHOSEN; (b) badge only, informational; (c) a fallback updater window. (b) lost because a flag you cannot act on does not fix the defect, only its visibility. (c) lost because it re-introduces exactly the window the windowless design removed.

**Choice, as shipped:**
- `updateAnnouncer` is a narrow interface called on EVERY check; `checkAndNotify` calls `AnnounceUpdate(rel)` **BEFORE** `notifyUpdateAvailable` and never gates it on the banner. The two surfaces have opposite reliability — the tray is in-process and cannot fail, the notification centre can refuse the app outright — so announcing second would make the reliable surface contingent on the unreliable one.
- `pendingUpdate` holds the newest release found and is **never cleared**: `Check` returns nil both for "you are current" and for a feed that is briefly empty or unreachable, and clearing on the second would turn a transient feed problem into an update that silently vanished.
- One tray item is both surfaces: "Check for Updates…" until a release is found, then "Install Knomit X & Restart…". `updateMenuAction` dispatches on `pendingUpdate`. This is the only install path that does not route through the notification centre, and it still requires a deliberate click.
- `trayIconState` composites a badge onto the tray art (`withUpdateBadge`, pure Go image/draw, no new assets). The per-platform files were refactored from `applyTrayIcon(app, tray)` to `baseTrayIcon(app)` + `watchTrayAppearance(app, apply)` so theme and badge are two inputs to ONE `apply()` — the macOS ApplicationStarted boot-timing gotcha from [[kb/decisions/desktop/icons/per-platform-strategy]] is preserved, and a theme change can no longer drop the badge.

## Defect 3 — nothing surfaced for six hours, then nagged forever

`pollForUpdates` created its ticker and blocked on `t.C`, so the FIRST check was at T+6h — survivable when the banner was a one-shot interruption, not when a passive badge is the primary surface. Meanwhile the banner used a fixed notification ID with no memory, so an unclaimed update re-posted **every interval forever**.

**Options considered** (2026-07-29, `AskUserQuestion`): (a) banner once per version, tray carries it thereafter — CHOSEN; (b) once per version, retried ~daily while undelivered; (c) re-banner daily regardless. (c) lost because it is the same nagging four times slower. (b) lost as unnecessary once MarkNotified was made conditional on delivery (below), which covers its motivating case for free.

**Choice, as shipped:** `initialCheckDelay = 30 * time.Second`; `pollForUpdates(ctx, …, first, every)` checks once after `first`, then enters the ticker loop, honouring ctx cancellation DURING the initial delay so a fast quit fires no request. The banner is gated on a new `notifyLog` interface — NOT on the announcer's return, because the two surfaces have different lifetimes and must not share one decision.

The division that results: **tray = persistent STATE, refreshed on every check; banner = one-time EVENT, fired on the transition.** A genuinely newer version banners once more.

## Where the memory lives

`<StateDir>/update.json` — `~/Library/Application Support/knomit/update.json` on macOS, XDG state dir on Linux — beside the server lockfile, via `paths.UpdateStatePath()` and the new `tools/desktop/internal/updatestate`. Shape: `{"last_notified": "0.5.1"}`, a struct not a bare string so a second field does not invalidate files on disk.

**NOT `internal/config`**, which is load-at-startup TOML/env with no writer at all. This is runtime state.

**Placed under `internal/` deliberately:** CI's cross-platform `build-test` job runs `./tools/desktop/internal/...`, whereas `tools/desktop` itself is only compiled by the macOS-only `desktop` job.

**Every failure degrades, none propagates.** `updatestate.Load` NEVER errors — missing, unreadable and corrupt all yield the zero State, because the only cost of losing this memory is one redundant banner and refusing to announce an update over an unreadable JSON file would be strictly worse. An unresolvable state dir leaves `persistentNotifyLog.path` empty, which makes `MarkNotified` a no-op and degrades to the previous session-scoped behaviour instead of erroring on every check. An unwritable file still leaves `checkAndNotify` returning nil — the banner WAS delivered.

**`MarkNotified` runs only after the banner was ACCEPTED.** A send that failed reached nobody, so recording it would burn the one announcement that version gets; leaving it unmarked means a user who grants notification permission afterwards still gets told. The retry is silent either way — a rejected send posts nothing — so this cannot become nagging. (This supersedes an earlier revision of this fact which listed "a banner that fails to deliver is not retried" as an accepted cost. It is no longer a cost.)

**Keyed on VERSION, not pointer identity.** Every poll builds a fresh `*updater.Release`; a pointer comparison would report each check as new and restore the every-interval banner. Guarded by `TestPendingUpdateReportsNewVersionsOnly`.

**Save is write-then-rename at 0600**, mirroring `lockfile.Write` in the same directory. Note `json.Unmarshal` validates the whole document before assigning, so a truncated file leaves the destination untouched — `Load`'s explicit zero-value return on unmarshal error is unobservable today and is belt-and-braces for a future streaming `Decoder`.

## GOTCHA — MenuItem.SetLabel is not main-thread-safe

`SystemTray.SetIcon` / `SetTooltip` / `SetMenu` wrap themselves in `InvokeSync`. `MenuItem.SetLabel` (and `SetEnabled`/`SetHidden`/`SetChecked`) call `m.impl.setLabel` — straight into AppKit on the CALLING goroutine. `trayUpdateAnnouncer.AnnounceUpdate` runs on the update poll goroutine, so it wraps its menu mutations in `application.InvokeSync` explicitly. Anything else mutating a menu off the main thread needs the same.

## Non-scope

This does NOT change the macOS-only guard, the single-provider decision, the pinned-key gate, or `WindowNone` / `CheckInterval: 0` — the reasoning in [[kb/decisions/desktop/self-update/windowless-notification-flow]] stands, and the once-per-version banner is a refinement of it, not a reversal. It does NOT add a SKIP: a user can leave a version pending, not dismiss it, and dismissing a banner remains an unobserved no-op — the badge returns on every launch because the update genuinely is still pending. "Defer to ApplicationStarted" applies to the OS notification centre specifically; the updater's own `Init` and Go-side callback registration are fine before `Run` and were deliberately left there. And `initialCheckDelay` is not a promptness guarantee — a machine asleep or offline at T+30s waits for the next interval.

## Verification status

`go vet -tags desktop`, the desktop suite under `-race`, and the full `go test ./...` all pass; the new guards were mutation-tested (recording an undelivered banner, rewriting an unchanged file, never reading the file back on startup, and dropping the initial check are each caught by a named test). STILL UNVERIFIED on real hardware: the deferred-activation fix targets a launch path only a real bundled `.app` exercises, and `trayicon_others.go` is not compiled by CI at all (the desktop job is macOS-only).
