# Notification-centre setup is deferred to ApplicationStarted, and a tray badge + install-capable menu item make the update reachable when notifications never deliver

**Amends [[kb/decisions/desktop/self-update/windowless-notification-flow]]**, which named unverified notification delivery on an unsigned .app as "the assumption most likely to be wrong" and left the banner as the ONLY update surface. Code review of PR #48 turned that from a risk into two concrete defects.

## Defect 1 — the setup ran before the application existed

`configureUpdater` was called from `run()` at `app.go` line ~146; `wapp.Run()` is line ~201. Inside it, `RequestNotificationAuthorization()` and `RegisterNotificationCategory()` reach the OS notification centre. Two consequences, both verified against the vendored wails v3.0.0-alpha.98-tui:

- Wails runs service startup from INSIDE `Run` (`application.go` `startupService`, after `newPlatformApp`). `darwinNotifier.Startup` is where the guards live — `isNotificationAvailable`, `checkBundleIdentifier`, `ensureDelegateInitialized`. Calling in earlier does not merely skip them: `[UNUserNotificationCenter currentNotificationCenter]` raises rather than returns when the main bundle is not yet resolvable, and an ObjC exception through cgo takes the process. The app would DIE AT LAUNCH where it was supposed to log "self-update unavailable".
- `RequestNotificationAuthorization` is synchronous with a **180-second** timeout (`notifications_darwin.go`), waiting on a completion handler that cannot arrive without a run loop. On the startup path that is three minutes with no window and no tray icon.

**Choice:** split `configureUpdater` by what each half touches, not by tidiness. It now returns `(start func(), err error)`. Pure-Go wiring — `Updater.Init`, `OnNotificationResponse`, `Event.On(updater.EventError)` — stays eager and pre-`Run`. Everything platform-touching moved into `activateNotifications`, called from the returned closure, which `app.go` registers on `events.Common.ApplicationStarted` and runs **on its own goroutine** so a slow authorization prompt cannot stall the event handler.

## Defect 2 — no surface survived a dead notification centre

`pkg/services/notifications` documents "Your app must be packaged and signed for this feature to work" and knomit's .app is unsigned. With the banner as the only UI, a user whose authorization is denied or unavailable had a running updater, a published release, and no way to learn either existed — the tray item only posted another banner.

**Options considered** (2026-07-29): (a) tray icon badge plus an install-capable tray item — CHOSEN; (b) badge only, informational; (c) a fallback updater window. (b) lost because a flag you cannot act on does not fix the defect, only its visibility. (c) lost because it re-introduces exactly the window the windowless design removed.

**Choice, as shipped:**
- `updateAnnouncer` is a new narrow interface; `checkAndNotify` calls `AnnounceUpdate(rel)` **BEFORE** `notifyUpdateAvailable` and does not gate it on the banner's error. The two surfaces have opposite reliability — the tray is in-process and cannot fail, the notification centre can refuse the app outright — so announcing second would make the reliable surface contingent on the unreliable one.
- `pendingUpdate` holds the newest release found. It is **never cleared**: `Check` returns nil both for "you are current" and for a feed that is briefly empty or unreachable, and clearing on the second would turn a transient feed problem into an update that silently vanished.
- One tray item is both surfaces: "Check for Updates…" until a release is found, then "Install Knomit X & Restart…". `updateMenuAction` dispatches on `pendingUpdate`. This is the only install path that does not route through the notification centre, and it still requires a deliberate click, so the rule that nothing installs unprompted is intact.
- `trayIconState` composites a badge onto the tray art (`withUpdateBadge`, pure Go image/draw, no new assets). The per-platform files were refactored from `applyTrayIcon(app, tray)` to `baseTrayIcon(app)` + `watchTrayAppearance(app, apply)` so theme and badge are two inputs to ONE `apply()` — the macOS ApplicationStarted boot-timing gotcha from [[kb/decisions/desktop/icons/per-platform-strategy]] is preserved, and a theme change can no longer drop the badge.

## GOTCHA — MenuItem.SetLabel is not main-thread-safe

`SystemTray.SetIcon` / `SetTooltip` / `SetMenu` wrap themselves in `InvokeSync`. `MenuItem.SetLabel` (and `SetEnabled`/`SetHidden`/`SetChecked`) call `m.impl.setLabel` — straight into AppKit on the CALLING goroutine. `trayUpdateAnnouncer.AnnounceUpdate` runs on the update poll goroutine, so it wraps its menu mutations in `application.InvokeSync` explicitly. Anything else mutating a menu off the main thread needs the same.

## Non-scope

This does NOT add a check at startup — the first poll is still at T+6h, so the badge cannot appear before then; that was raised and deliberately left alone. It does NOT add per-version dismissal state, so an ignored update still re-banners every interval. It does NOT change the macOS-only guard, the single-provider decision, the pinned-key gate, or `WindowNone`/`CheckInterval: 0`. And "defer to ApplicationStarted" applies to the OS notification centre specifically — the updater's own `Init` and Go-side callback registration are fine before `Run` and were deliberately left there.
