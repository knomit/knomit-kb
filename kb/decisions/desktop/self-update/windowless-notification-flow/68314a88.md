# Desktop self-update NEVER opens a window: WindowNone + our own Check ticker + an OS notification whose Install action is the only thing that installs

**Supersedes the window configuration in [[kb/decisions/desktop/self-update/appcast-ed25519-single-provider]]'s sibling design.** The original wiring set BOTH `CheckInterval: 6*time.Hour` AND `Window: &updater.BuiltinWindow{}`. Code review (PR #48) established those two are incompatible.

**The load-bearing discovery: `CheckInterval` + any window = an uninvited panel every interval, forever.** `pkg/updater`'s `periodicCheckLoop` calls **`CheckAndInstall`, not `Check`**. `CheckAndInstall` calls `openSession` — which reaches `updaterHost.OpenWindow` → `win.Show()` — *before* it runs the Check, so the window appears before the app knows whether an update exists. It then DELIBERATELY leaves the window open on the up-to-date path (upstream comment: closing it "caused a flicker on every check"). On an app that lives in the tray for weeks that is a "You're Up to Date" panel the user must dismiss every six hours. `pkg/updater`'s own doc comment on `CheckAndInstall` says apps wanting silent background polling should use `Config.Window = updater.WindowNone` or call `Check()` directly.

**Options considered** (2026-07-29, resolved by `AskUserQuestion`):

What the notification click does: (a) an **Install & Restart** action button on the banner — CHOSEN; (b) informational banner only, install via the tray item; (c) stage the install silently and apply on next launch.

What a manual tray check does when already current: (a) notify "You're up to date"; (b) **stay silent** — CHOSEN.

**Rationale.** (c) lost because it installs without a click, contradicting the standing policy that nothing installs unprompted (an update may migrate the knowledge base, and migrations do not reverse). (b) lost because with no window the banner is the ONLY update UI, so routing the install through a second surface makes it a two-step flow for no gain. Silence-when-current won because the banner is the only channel: a "nothing to do" notification every six hours reproduces, in Notification Centre, exactly the recurring interruption the windowless design exists to remove.

**The choice, as shipped.** `updaterConfig` sets `Window: updater.WindowNone` and leaves `CheckInterval` at ZERO. `pollForUpdates` runs knomit's own ticker on `updateCheckInterval` calling `Check`, which reports without installing. On a non-nil release `checkAndNotify` posts a notification in the `knomit.update.available` category, whose single registered action `install` is wired by `configureUpdater` to `installAndRestart` → `CheckAndInstall` then `Restart`. Restart runs ONLY after a successful install (`Restart` returns `ErrNotReady` with nothing staged, and quitting the app on a failed install is indistinguishable from a crash). Any response that is not the install action is a deliberate no-op. The tray's "Check for Updates…" shares `checkAndNotify`, so it also cannot install directly.

The two interfaces `updateChecker` (Check only) and `updateInstaller` (CheckAndInstall + Restart) exist to make that split structural: the polling path is handed something with no method that can install.

**Consequence for registration order.** `updaterConfig(runtime.GOOS)` is now resolved in `app.go` BEFORE `application.New`, because the notifications service is only added to `Options.Services` where self-update can actually run — a Linux or dev build should not take on a notification-daemon dependency for a feature it does not have.

**Non-scope / foreseeable misreadings.** This does NOT mean "never set `CheckInterval`" in general — it means `CheckInterval` is unusable *together with* this updater's window semantics, and headless (`WindowNone` + `CheckInterval`) is WORSE still, because `CheckAndInstall` then installs with no prompt whatsoever. It does NOT mean the app has no update UI: the OS banner is the UI. It does NOT change the macOS-only guard, the single-provider decision, or the pinned-key gate. And notification delivery is best-effort — `pkg/services/notifications` documents "packaged and signed" as its requirement and knomit's `.app` is unsigned, so an authorisation refusal degrades the channel to log-only rather than breaking the app; this remains UNVERIFIED on a real machine and is now the assumption most likely to be wrong.
