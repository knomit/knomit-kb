# A held [tls].addr is an AVAILABILITY failure the desktop survives (WARN, serve without TLS) while `knomit serve` stays fatal; a TRUST failure (certificate installed but unloadable) fails both — app.ErrTLSAddrInUse is how the caller tells them apart

OPTIONS (knomit#256, user ruling 2026-09-25): when the desktop cannot bind [tls].addr, (a) fail the boot, for parity with `knomit serve`; (b) WARN and serve without the TLS listener. CHOSEN: (b) for the desktop only.

WHY: a bind conflict is an availability failure — failing 'open' means NO TLS listener, fewer doors, not more — the same shape as auth.ErrSocketInUse, which both binaries already treat as benign. The desktop and `knomit serve` on one machine share <home>, hence the key, [tls].addr and <home>/pki, so whichever starts second finds the port held; under (a) the desktop user would lose the knowledge UI and MCP server because the other knomit is already serving the fleet. `knomit serve` is a fleet node, and one asked to serve the fleet that cannot must not come up looking healthy, so cmd's startTLSServer stays fatal on every error (pinned in a subprocess by TestServeTLS_BindConflictIsFatal).

MECHANISM: OpenTLSServer wraps a listen error that is address-in-use as ErrTLSAddrInUse (isAddrInUse: syscall.EADDRINUSE on unix, windows.WSAEADDRINUSE on Windows, where the two are NOT the same errno). Every other error — CRL missing or malformed, older than crl.number, certificate for another key — is returned unwrapped and fails the desktop's boot too. TestOpenTLSServer_AddrInUseIsTypedAndTrustFailureIsNot asserts both directions.

MISREADING TO AVOID: 'the desktop tolerates TLS errors' is false. It tolerates exactly one, a held address; a trust failure is fatal on both binaries. Consequence for operators: a desktop that logs 'serving without the mTLS listener' is NOT a peer, even though [tls].addr is set.
