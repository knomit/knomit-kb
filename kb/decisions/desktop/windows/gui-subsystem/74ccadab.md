# knomit-desktop.exe is linked into the Windows GUI subsystem (-H windowsgui) and the CLIs deliberately are not — a CONSOLE-subsystem tray app is owned by the terminal that launched it

Go's default PE subsystem is CONSOLE (3). A CONSOLE-subsystem binary launched from a terminal is attached to that terminal's console, so closing the terminal window delivers CTRL_CLOSE_EVENT and KILLS the process — a tray app that dies when you close the shell you started it from. It also pops up a console window when launched any other way.

`DESKTOP_LDFLAGS` in the Makefile adds `-H windowsgui` under `ifeq ($(GOOS),windows)`, giving subsystem 2 (WINDOWS GUI). Measured before/after on dist/windows-amd64/knomit-desktop.exe: **3 -> 2**. Wails' own Windows task files pass the same flag. It is defined with `=`, not `:=`, so it tracks a later `VERSION_LDFLAGS +=` rather than snapshotting that variable at parse time.

SCOPED TO THE DESKTOP BINARY ONLY. `knomit`, `kb` and `knomit-okf` stay at subsystem 3 and must: they are CLIs whose entire job is writing to the terminal that ran them. Verified after the change — the three CLIs still read 3.

CONSEQUENCE: a GUI-subsystem process gets no console, so `knomit-desktop.exe version` / `--version` would print nowhere. `tools/desktop/console_windows.go` repairs that on the version path only, and must guard per stream rather than attaching unconditionally. It also cannot repair PowerShell's native `>`, which drops a GUI child's output regardless of what the program does. Both traps are written up in the console-subsystem gotcha; read it before touching that file.

WHERE THE MANIFEST COMES FROM — corrected, and not what it looks like. The binary carries a 710-byte manifest (asInvoker + five supportedOS GUIDs), but it is NOT Go's doing. Measured: a pure-Go `-H windowsgui` binary has NO .rsrc and no manifest at all, while a minimal CGO one carries the byte-identical manifest. It comes from mingw-w64's `default-manifest.o`, which the MinGW linker adds to everything it links, and the desktop build reaches that external-link path only because it is CGO. It would disappear if the desktop app ever stopped needing cgo.

That manifest sets no `dpiAware`, which is exactly why the committed `rsrc_windows_*.syso` carries an icon and NO manifest: Wails v3 sets per-monitor-v2 DPI awareness itself at runtime (`setupDPIAwareness` in pkg/application/application_windows.go), Windows permits that only ONCE per process, and a manifest entry would be a second author for a setting that already has one. The .syso is generated by `make desktop-winres` with go-winres PINNED to v0.3.3 — pinned because the target regenerates a committed artifact, and verified to reproduce the checked-in bytes exactly.

CI COVERAGE: the `desktop` job in .github/workflows/tests.yml runs on macos-latest, so it does NOT compile the `//go:build desktop && windows` files. The windows-2025 leg of `build-test` carries a compile+vet gate for them (`CGO_ENABLED=1 go build -tags desktop -o NUL ./tools/desktop`). Build only — that leg already costs ~30 minutes — so the desktop TESTS still run on macOS alone and the Windows-only tests run only on a developer's machine.
