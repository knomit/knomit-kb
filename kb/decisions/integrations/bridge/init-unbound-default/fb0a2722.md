# A flagless `kb claude init` / `kb antigravity init` scaffolds an UNBOUND server: the directory name may appear in the KEY (`knomit-repo-<sanitized dir>`) but never in `args` (`[]`); hooks bind from args only; a re-init keeps an existing scope

Decided 2026-09-28 by the designer (issue #341, relayed via the master session) after an RCA showed three layers: both init commands defaulted `--repo` to the directory basename (so a flagless init in `ingestion` bound to repo `ingestion`, and one in `My Project` failed validation on a name the user never typed); the unbound server mode (bridge with neither flag, PR #209) had explicitly left the scaffolders out of scope; and the hooks on BOTH hosts mis-handled an entry with neither flag — Claude's mcpBinding fell back to the directory basename (a silent read of whatever repo shares the directory's name), Antigravity's pluginBinding returned no_binding and told the user every conversation to "Re-run init".

OPTIONS CONSIDERED AND CHOSEN

1. The server KEY for an unbound entry. Proposed: a neutral constant (`knomit-unscoped`). REJECTED by the designer in favour of keeping today's naming: a flagless init in `ingestion` writes key `knomit-repo-ingestion` with `"args": []`. The directory name may appear in the KEY, never in ARGS. `knomitapi.ServerKey` semantics are unchanged; the unbound case gets its own key-from-directory helper. Accepted cost: the key is no longer injective across bound/unbound — `--repo ingestion` and a flagless init in `ingestion` produce the same key. That is tolerable only because of rule 3 (re-init keeps the existing scope) and rule 4 (nothing reads the scope from the key). The bare legacy key `knomit` was never an option: decision init-merge (b9284197) forbids touching it, and a flagless re-init over it must leave it byte-identical.

2. Directory names that are not valid knomit names. CHOSEN: sanitize for the key only — ASCII-lowercase, every character outside the name grammar becomes `-`, truncated so the key fits MaxServerKeyLen. Init must NEVER fail because of the directory name; `My Project` and a 60-character directory both succeed. Name validation and the key-length refusal apply only to an explicit --repo or --lens value.

3. Re-init with no flags over an existing bound config. Options were (i) overwrite to unbound and print what changed, (ii) keep the existing scope and say so, (iii) a new --unbound flag. CHOSEN (ii) on BOTH hosts: unbound applies only to a fresh scaffold. For Claude this matters because the unbound key equals the old repo key (`knomit-repo-<dir>`), so the merge's same-key path would otherwise silently rewrite `--repo <dir>` to `[]`. To go unbound deliberately, remove the entry (or mcp_config.json) and re-init.

4. Hooks. CHOSEN: fix in the same PR. A hook's binding comes from the entry's ARGS only — never from the key, never from the directory. An entry with neither flag is UNBOUND even when its key looks bound (`knomit-repo-ingestion`). Claude: no directory-name repo read for an unbound entry. Antigravity: no "Re-run init" notice. Both hosts inject one line telling the agent to call knomit_repos, then knomit_bind, and pass the binding on every call; the text is shared from knomitapi so the hosts cannot drift.

5. DEFERRED (C3): Claude's directory-basename fallback for a project with NO knomit entry at all (no .mcp.json, or no kb server in it) stays as it is; narrowing it would regress users whose knomit server is configured at user scope.

WHAT THIS DOES NOT MEAN: it is not "the key names the scope" — a key containing a repo name proves nothing about the binding; read the args. It does not make flagless init mean "rebind to unbound" for an existing install.
