# knomit-bridge does NOT auto-recover an MCP session on server failure; the consumer owns restart

**The choice:** knomit-bridge will NOT silently re-resolve the server from the lockfile and replay the MCP handshake when a forwarded request fails at the transport level. On a dead/refused port the bridge returns the transport error to the client and stays out of the recovery business. Deciding when (or whether) to re-initialize is left to the MCP consumer/client. PR #83 (branch feat/bridge-lockfile-recovery), which implemented lazy request-driven recovery via a bridgeProxy type, is being dropped.

**Options considered:**
1. Bridge-side lazy recovery (PR #83): on a transport error against an auto-discovered target, re-read server.json, probe liveness, replay the cached initialize/initialized to mint a fresh session against the relaunched server, swallow the replayed responses, and retry the original request once.
2. No bridge-side recovery (chosen): surface the transport failure; the consumer decides if/when to restart the session.

**Rationale (why recovery loses):** An MCP session is server-process-local state (negotiated protocol version, client capabilities, subscriptions, in-flight requests, progress tokens) keyed by the Mcp-Session-Id header. There is no protocol primitive to *restore* a session to a different/restarted server process — the only spec-sanctioned move is to discard the dead session id and send a fresh `initialize` (the server returns 404 for an unknown session and the client re-initializes). So 'recovery' is necessarily a silent *reset*, not a resume. Having the bridge perform that reset transparently (a) hides a state-losing event from the consumer that, for a stateful MCP server, would silently drop subscriptions/in-flight work, and (b) usurps a decision the spec assigns to the client. The transparent re-init only looked free because knomit's request/response tools carry no durable session state — that is not a safe general assumption. Re-initialization policy belongs to the consumer.

**Implication:** Do not re-add bridge-side recovery/retry. If a dead-port error surfaces, that is by design — the client owns the restart decision.
