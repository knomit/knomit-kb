# knomit-bridge re-resolves the server from server.json on transport failure (lazy recovery)

How knomit-bridge survives the knomit server moving/dying.

**Problem:** the bridge pinned its server URL once at startup (explicit base-url arg > server.json > default :19278) and never re-resolved, so when the server quit or relaunched on a new port (e.g. quitting the desktop app, which writes server.json) it kept POSTing to a defunct port until the MCP client was restarted.

**Design (lazy, request-driven — the bridge does nothing between stdin lines):** forwarding lives in a `bridgeProxy` type (tools/bridge/proxy.go). On a TRANSPORT-level failure (`client.Do` returns err — dead/refused port) AND the target was auto-discovered (`pinned == false`), `forward` makes ONE recovery attempt via `recoverTarget()`: re-read server.json (`resolveBaseURL`), `buildServerURL` (which probes liveness via the agent-branch GET, so a stale lockfile pointing at a dead port fails here), then `reinit()` replays the CACHED `initialize` (and `notifications/initialized`) to mint a fresh session, then retry the original request once. The replayed initialize RESPONSE is swallowed — never written to the client — because the client already completed its handshake; leaking it would corrupt the JSON-RPC stream. If no live server is reachable, write a clean `knomit server unavailable` JSON-RPC error and STAY ALIVE so the next request recovers once the server returns.

**Scope decisions:** recovery trigger is transport-error only (side-effect-safe: a refused connection never reached the server, so retrying can't double-apply a tool call). An explicit `base-url` arg is a deliberate pinned target and disables recovery. We did NOT enforce single-instance across `knomit serve` + the app; instead documented 'run one or the other' (the app falls back to an ephemeral port when :19278 is taken, producing two servers and an ambiguous server.json).
