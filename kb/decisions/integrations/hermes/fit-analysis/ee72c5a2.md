# A knomit–Hermes integration is complementary in BOTH directions: Hermes's memory gaps are knomit's core mechanics, and Hermes's turn hooks (prefetch, on_memory_write, sync_turn) close knomit's measured write-path non-use — the recommended shape is a memory provider whose centerpiece is server-side compiled per-turn context

Product assessment written 2026-09-13 (full report at the artifact URL in refs; local copy .claude/plans/2026-09-13-knomit-hermes-assessment.html). This is the analyst's conclusion, NOT yet a user-ratified decision — record a /knomit-decided fact when the maintainer confirms or amends it.

Gap-for-gap mapping. Hermes → knomit: bounded 800-token MEMORY.md with no read → unbounded relevance-queried facts; contradictions accumulate → learn-twice subsumes, conflicts surface at merge; consolidation is a prompt → prune/distill pipelines with a review gate; 'forget' leaves a summary → retraction is a signed commit leaving the active corpus; 'never share one home between processes' → branch per profile, merge to main; agent-created skills have no dedup/lineage → skill as methodology fact. knomit → Hermes: write path taken only 10–37% of the time under Claude Code → on_memory_write mirrors every built-in write and sync_turn fires every turn, so capture no longer depends on the model choosing knomit; no per-turn injection → prefetch(query) before every turn; zero distribution → 245k-star host with a plugin catalog and skills hub; chat/generic MCP profiles (internal/mcp/instructions.go profileAddenda) have never had a host → Hermes personas exercise them.

Ranked use cases: (1) compiled per-turn context — prompt assembled from facts by direction of travel (principles → invariants → decisions → gotchas, applies-to scoped, confidence filtered, token budgeted, cached by normalized query), built as a knomit SERVER endpoint/MCP tool so Claude Code (UserPromptSubmit) and Antigravity (PreInvocation) reuse it; (2) skills as facts with SKILL.md rendered back from main; (3) silent capture from memory-write mirror + turn sync with conservative confidence; (4) shared memory across profiles/devices/kanban workers; (5) research monitoring on stateful cron using the hypothesize pipeline; (6) real retraction + explain through the gateway; (7) coding via ACP with the code profile.

Shape: Phase 0 MCP entry + skills + docs (`knomit-bridge hermes init`); Phase 1 context endpoint + general plugin (pre_llm_call) coexisting with any provider; Phase 2 memory provider (mirror, sync, pre-compress checkpoint, skills round-trip); Phase 3 distribution (provider listing, Docker bootstrap for VPS users, version pinning). Route every call through knomit-bridge as a spawned stdio subprocess — same auth-chokepoint rationale as the OpenClaw decision. Map Hermes profile → knomit agent branch via initialize()'s hermes_home; non-primary agent_context (cron, subagent) reads but does not extract.

Conditions that flip the verdict: prefetch p95 cannot get under ~1 s (then inject on topic shift, or make Claude Code the first host for compiled context); Hermes ships structured shared memory itself; Phase 0 draws no installs in a month (then the blocker is knomit's install story, not host coverage). Biggest execution risk is the shelved-adapter pattern: the OpenClaw adapter was complete in July and never merged (see the integrations/openclaw/status fact written alongside this one).

WHAT THIS DOES NOT MEAN: it does not mean knomit should model the user — USER.md/Honcho's theory-of-mind job stays theirs; mirror USER.md writes as preference facts and stop. It does not mean the memory-provider slot is required for value — the general-plugin path delivers compiled context even to users who keep mem0 in the slot.
