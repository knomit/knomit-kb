# `knomit-bridge claude init` MERGES into an existing .claude/settings.json and REPLACES the versioned CLAUDE.md block in place — the companion file survives only for .mcp.json under a different knomit key and for a CLAUDE.md block with a heading but no marker

`knomit-bridge claude init` MERGES into an existing .claude/settings.json and REPLACES the versioned CLAUDE.md block in place; the companion-file-plus-"merge manually" path survives ONLY for .mcp.json when a knomit-bridge entry under a DIFFERENT key already exists, and for a CLAUDE.md whose block has a heading but no version marker.

Decided 2026-09-17 by the designer after a deployment gap from PR #211 (memory-guard hook). Re-running `knomit-bridge claude init --lens knomit-dev` on the knomit checkout itself left .claude/settings.json WITHOUT the memory-guard PreToolUse hook: init wrote the gitignored companion `.claude/settings.json.knomit` and printed one "WARNING: … exists — merge from … manually" line per file; the designer merged CLAUDE.md and .mcp.json by hand and never saw the settings companion. Net effect was the exact half-merged state the memory-guard decision names as unguarded: block marker v4, no PreToolUse entry. As of this decision the change is DISPATCHED, not shipped — verify against tools/bridge/claude/init.go before assuming init merges.

OPTIONS CONSIDERED

1. Keep the companion + warning for all three merge-required files (the status quo: runInit's writeOne drops companionPath(dst) whenever the destination exists). Rejected: the companion is gitignored, there are three of them, each announced by one line, and the failure it produces is SILENT — a missing hook never announces itself; the project just goes unguarded.
2. Overwrite merge-required files outright. Rejected: destroys user hooks, permissions, other MCP servers and the rest of CLAUDE.md.
3. A per-file STRUCTURAL merge, with the companion kept only where a merge could produce a wrong result. CHOSEN.

THE RULES, PER FILE

- .claude/settings.json — parse the existing JSON. For each hook event in the template, append the template entries whose hook COMMAND string is not already present anywhere under that event. Idempotence is keyed by command, NOT by matcher: a user who registered `knomit-bridge claude hook post-edit` under their own matcher already has it, and init must not add a second copy under the template's matcher. "Present" is NOT an exact-string compare: a command whose binary is path-prefixed (`${CLAUDE_PROJECT_DIR:-.}/dist/knomit-bridge claude hook post-edit`, the form .mcp.json already uses for the bridge) counts as the same hook as the bare `knomit-bridge claude hook post-edit`; match on the `claude hook <name>` suffix or normalise the binary path, otherwise every re-init appends a duplicate for such a user. Every user entry, the `permissions` object and every other key are preserved; key order and indentation are preserved where feasible. Print `Updated: .claude/settings.json (+PreToolUse memory-guard)` naming each event/hook added; print nothing to add when nothing changed. No companion. A settings.json that does not parse is left BYTE-IDENTICAL and init fails with an error naming the file — never clobbered, never companioned.
- CLAUDE.md — the block is delimited by `<!-- knomit:integration vN -->` … `<!-- /knomit:integration -->`. Marked block with an older marker: replace the whole delimited region in place, everything outside it byte-identical; print `Updated: CLAUDE.md knomit block v3 → v4`. Marker current: no change. No block at all (neither marker nor the `## Working with knomit memory` heading): APPEND the block, blank-line separated, and print `Updated: CLAUDE.md (+knomit block)`; no companion. Heading present but NO marker (pre-marker installs, or a user who stripped the HTML comments — claudeMdBlockNote's middle case): there is no end delimiter to replace up to, so this keeps today's companion + "replace the whole block, not just parts" warning. That is the only CLAUDE.md case that still writes a companion.
- .mcp.json — parse. An entry under the derived key (knomitapi.ServerKey, `knomit-lens-<lens>` / `knomit-repo-<repo>`) exists: refresh ONLY its `args` to the derived scope and PRESERVE its `command` and every other key the user set; print an update only when args actually changed. AMENDED 2026-09-17 during PR #213 review: the first cut rewrote the whole entry value, which replaced a customised `command` (`${CLAUDE_PROJECT_DIR:-.}/dist/knomit-bridge`, the form this repo uses) with the bare `knomit-bridge` that does not resolve outside the macOS .app (see the bridge-path gotcha) — a refresh that silently stops the MCP server loading. `command` is deployment-specific and belongs to the user; `args` are scope-derived and belong to init. No knomit-bridge entry at all: add one under the derived key, other servers untouched. A knomit-bridge entry under a DIFFERENT key (the legacy literal `knomit`, or another scope): keep today's companion + two-scopes warning, because side-by-side entries naming two scopes is the state that makes the hooks disable themselves (see the scaffolding gotcha). This is the LIVE case for the knomit checkout itself: the committed .mcp.json at 2eed2b99 still carries the legacy key `knomit`. Init must never migrate or rename that key — existing installs keep it on purpose, and renaming would reintroduce the clobbering removed in caaeac09/d7141821.
- .claude/skills/** stay owned and overwritten, unchanged.

TESTS THE DECISION REQUIRES (init_test.go): a second run is a no-op on all three files (byte-identical); the no-op and preserve fixtures START FROM a realistically pretty-printed settings.json (one key per line, like the knomit checkout's own), not from init's compact template output — otherwise a first run that reformats the user's whole file passes the byte-identical check on the second run; a path-prefixed knomit hook command is recognised as present and not duplicated; user hooks and permissions survive a settings merge; a v3 block is replaced and a v4 block is not touched, with content outside the block byte-identical; a no-block CLAUDE.md gets the block appended exactly once; a settings.json with a syntax error is left byte-identical and init returns an error; .mcp.json same-key update, no-entry add, different-key companion. The existing companion tests for .mcp.json (different key) and heading-only CLAUDE.md remain valid; the settings companion test becomes a merge test.

WHAT THIS DOES NOT MEAN: init does not edit arbitrary user content — only the marked CLAUDE.md region, the knomit-bridge entry under its own key, and the hook arrays, by appending. It does not mean a removed knomit hook stays removed: idempotence is keyed by presence of the command string, so a user who deliberately deleted a knomit hook gets it back on the next init; the README should say so. It does not change the antigravity scaffolder, whose files are all owned.
