# The rule "notes go in knomit, not Claude Code auto-memory" ships in the PRODUCT — the scaffolded CLAUDE.md block, a knomit-bridge `claude hook memory-guard` PreToolUse subcommand, and the settings template — never as a per-checkout edit

Decided 2026-09-16 by the designer after three separate sessions (master, worker, reviewer) each wrote team-relevant lessons into Claude Code's private auto-memory directory (~/.claude/projects/<cwd>/memory/) instead of knomit. That directory is per session owner and invisible to every other agent, so a lesson written there is lost to the team.

OPTIONS CONSIDERED

1. Edit THIS checkout's CLAUDE.md and .claude/settings.json and drop a shell hook under .claude/hooks/. Built first, then REJECTED and reverted: it fixes one instance. CLAUDE.md's knomit block and .claude/settings.json are GENERATED by `knomit-bridge claude init` from templates, so a local edit is outside the generated block, ships to nobody, and diverges from what init writes.
2. Put the rule and the enforcement in the scaffolding templates and the bridge binary, so every project that runs `knomit-bridge claude init` (or antigravity init) gets it, and re-init refreshes it. CHOSEN.
3. A knomit principle authored by the designer with /knomit-principle, injected as a PROJECT PRINCIPLE at every session start. Complementary, designer-only.

THE SHAPE

- tools/bridge/claude/templates/CLAUDE-md-block.txt gains the rule inside the generated block: anything another agent could use (lesson, gotcha, convention, environment limit, decision) goes into knomit via /knomit-remember or /knomit-decided, never into auto-memory; auto-memory is only for `type: user` facts about the person; a hook enforces it. The block version marker is bumped (blockMarkerPrefix / blockMarkerCurrent in init.go) so init reports existing blocks as outdated.
- tools/bridge/claude/hook.go gains a fifth subcommand `memory-guard` beside session-start, post-edit, post-ask, pre-compact. It reads the PreToolUse JSON on stdin. Write/Edit/MultiEdit under any `.claude/projects/*/memory/` path: allow only MEMORY.md or a file whose frontmatter has `type: user` (content for Write, the existing file for Edit); otherwise emit a PreToolUse deny whose reason points at /knomit-remember. Bash: deny only when the command references that directory AND contains a write OPERATOR (>, >>, tee, sed -i, rm, mv, cp) — match operators, not words, because the shell prototype matched `echo` and blocked a plain read.
- tools/bridge/claude/templates/settings.json.tmpl registers it: PreToolUse, matcher "Write|Edit|MultiEdit|Bash", command `knomit-bridge claude hook memory-guard`.
- tools/bridge/antigravity gets the same rule in its scaffolded rules and the same guard in its pre-invocation hook if that surface can deny a tool call.

WHY A BRIDGE SUBCOMMAND RATHER THAN A SCRIPT FILE: the other four hooks are already subcommands, so there is no script to copy, no chmod, no path to get wrong, and the same binary serves every project.

NON-SCOPE: this does not migrate memories already written to auto-memory in any checkout; that is a per-user cleanup. It does not touch knomit's server or MCP tools.
