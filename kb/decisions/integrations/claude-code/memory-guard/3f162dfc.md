# The rule "notes go in knomit, not Claude Code auto-memory" ships in the PRODUCT — the scaffolded CLAUDE.md block, a knomit-bridge `claude hook memory-guard` PreToolUse subcommand, and the settings template — never as a per-checkout edit

Decided 2026-09-16 by the designer after three separate sessions (master, worker, reviewer) each wrote team-relevant lessons into Claude Code's private auto-memory directory (~/.claude/projects/<cwd>/memory/) instead of knomit. That directory is per session owner and invisible to every other agent, so a lesson written there is lost to the team. Shipped as PR #211.

OPTIONS CONSIDERED

1. Edit THIS checkout's CLAUDE.md and .claude/settings.json and drop a shell hook under .claude/hooks/. Built first, then REJECTED and reverted: it fixes one instance. CLAUDE.md's knomit block and .claude/settings.json are GENERATED by `knomit-bridge claude init` from templates, so a local edit is outside the generated block, ships to nobody, and diverges from what init writes.
2. Put the rule and the enforcement in the scaffolding templates and the bridge binary, so every project that runs `knomit-bridge claude init` (or antigravity init) gets it, and re-init refreshes it. CHOSEN.
3. A knomit principle authored by the designer with /knomit-principle, injected as a PROJECT PRINCIPLE at every session start. Complementary, designer-only.

THE SHAPE (as shipped)

- The scaffolded rules block (tools/bridge/claude/templates/CLAUDE-md-block.txt and its Antigravity twin) gains ONE HOST-NEUTRAL paragraph, byte-identical in both: anything another agent could use (lesson, gotcha, convention, environment limit, decision) goes into knomit via /knomit-remember or /knomit-decided, never into the host's private per-session memory, which is invisible to every other agent and is only for facts about the person. The concrete path (~/.claude/projects/<cwd>/memory/) and the hook name do NOT appear in the block: TestRulesBlockMatchesClaude requires the two copies to be byte-identical apart from marker lines and TestRulesBlockIsHostNeutral bans "Claude Code", "CLAUDE.md", ".claude/" from the shared prose. Host-specific wording would mean splitting the fork, which is its own change. The specifics live where host-specific text is allowed: the bridge README and the hook's own deny reason — the text an agent reads at the moment it is blocked.
- The block version marker is bumped v3→v4 ONLY in the template. init.go computes blockMarkerCurrent off the embedded template via templateBlockMarker() (a test enforces it) precisely so the marker cannot drift two ways; a hand-written constant would reintroduce that drift. init_test asserts that a v3 block is reported as "from an older version" against the bumped template.
- tools/bridge/claude/hook.go gains a fifth subcommand `memory-guard` beside session-start, post-edit, post-ask, pre-compact. It reads the PreToolUse JSON on stdin. Write/Edit/MultiEdit under any `.claude/projects/*/memory/` path: allow only MEMORY.md or a file whose frontmatter has `type: user` (content for Write, the existing file for Edit); otherwise emit a PreToolUse deny whose reason names the directory, says it is private per-session memory invisible to other agents, and points at /knomit-remember (or /knomit-decided, /knomit-update). Bash: deny only when the command references that directory AND contains a write OPERATOR or write-capable command matched as a TOKEN — >, >>, tee, sed -i, rm, mv, cp, dd, install, truncate, heredoc, subshell redirection, python/perl/ruby/node -e — never words, because the shell prototype matched `echo` and blocked a plain read; cat, sed -n, grep, ls and echo-of-a-read are allow-side test cases. A malformed payload exits 0 silently.
- tools/bridge/claude/templates/settings.json.tmpl registers it: PreToolUse, matcher "Write|Edit|MultiEdit|Bash", command `knomit-bridge claude hook memory-guard`.
- Antigravity gets the rule text ONLY. Its sole hook event, PreInvocation, emits {} or an injected message and has no deny path (hook_pre_invocation.go, templates/hooks.json), so there is nothing to enforce with and no guard was invented.

WHY A BRIDGE SUBCOMMAND RATHER THAN A SCRIPT FILE: the other four hooks are already subcommands, so there is no script to copy, no chmod, no path to get wrong, and the same binary serves every project.

NON-SCOPE: this does not migrate memories already written to auto-memory in any checkout; that is a per-user cleanup. It does not touch knomit's server or MCP tools. It does not split the shared rules block into host-specific forks.

DEPLOYMENT: an existing project gets the guard only after rebuilding the bridge AND re-running claude init. Before PR #213 init dropped a companion next to an existing settings.json and the operator had to merge by hand, which is how this very checkout ended up with a v4 block and no PreToolUse entry — NOT guarded. Since PR #213 (merge 2a25012b) init merges the PreToolUse entry into the existing settings.json in place and replaces the CLAUDE.md block in place (see kb/decisions/integrations/claude-code/init-merge), so the half-merged state can no longer be produced by init itself; it can only persist in a project that has not been re-inited since. A project whose CLAUDE.md block is v4 but whose settings.json has no PreToolUse entry is still NOT guarded — re-run init.
