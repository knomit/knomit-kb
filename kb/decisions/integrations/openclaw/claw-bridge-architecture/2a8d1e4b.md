# OpenClaw integration is a thin plugin proxying through knomit-bridge, not a native MCP or direct-HTTP plugin

OpenClaw (open-source agent gateway) has no MCP client. To give an OpenClaw agent knomit's full power we add a `knomit-bridge claw` subcommand (parallel to `claude`) that scaffolds an OpenClaw integration.

**Options considered:**
- A — Skills + CLI shell-out: bridge grows `claw query/learn/...` verbs; skills tell the agent to shell out. Zero Node, but tools aren't first-class and auth/credentials are awkward in shell argv. OpenClaw's own guidance calls shell-driven the 'workaround' path.
- B — Native TS/JS plugin calling knomit HTTP directly: most 'native', but BYPASSES the bridge — no chokepoint for future auth.
- C — Thin generic OpenClaw plugin that forwards every tools/call back through knomit-bridge (its existing stdio-MCP mode). First-class typed tools, all logic stays in Go, matches the existing 'no client-specific code' Cowork decision.

**Rationale / choice:** C. The user requires everything to route through the bridge so future AUTH is a single Go-side chokepoint — this eliminates B. OpenClaw's official criterion ('use a plugin when the capability has code, credentials, lifecycle hooks') points to a plugin over skills for the callable tools, so A loses. Skills are still reused for the WORKFLOW layer (the existing knomit-* AgentSkills files, adapted to bare OpenClaw tool names).

**Key sub-decisions:**
1. Plugin<->bridge link = a PERSISTENT stdio-MCP session (registerService start/stop holds one `knomit-bridge` subprocess; one initialize+tools/list handshake; low latency across dozen-turn review loops). Multi-turn correctness does NOT depend on it — review/hypothesize session_id and query/explain cursor are arg-carried and stored server-side in knomit — so persistence is a latency/robustness optimization.
2. Tools are SNAPSHOTTED at `claw init` into a local knomit-tools.json and registered SYNCHRONOUSLY at plugin load (register(api)), NOT dynamically after an async tools/list — to dodge OpenClaw's known bug (#47683/#61790, closed 'not planned') where late-registered tools don't surface to the agent. Re-run `claw init` to refresh the manifest.
3. Long-running knomit_review (60-120s, only tool with MCP TaskSupportOptional) handled via variant 2b = AGENT-VISIBLE task polling: plugin issues review in MCP task mode, returns {status:working, resume:taskId} sub-second, review skill instructs the agent to re-call with resume until a work item arrives. Every execute() is sub-second so it beats any OpenClaw tool timeout. No knomit changes (tasks already implemented). Chosen over 2a (internal poll loop hidden in execute()) which still blocks ~90s and does NOT beat OpenClaw's timeout.
4. Per-profile MCP `initialize` Instructions (no OpenClaw equivalent channel) are re-injected via a scaffolded knomit-guidance skill.
