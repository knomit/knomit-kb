# Deletes drop folders they empty, and a delete inside a missing folder is a no-op (#375 option b); existing empty trees are not swept

PROBLEM (#375): knomit's deleteFromTree re-inserted every child subtree after recursing, so deleting the last fact in a folder left an EMPTY tree entry behind. Git, a GitHub merge or a hand commit simply has no folder there.

OPTIONS CONSIDERED:
(a) Drop emptied folders and KEEP the old `deleteFromTree: subtree %q not found` error for a delete whose folder is missing.
(b) Drop emptied folders AND make a delete inside a missing folder a no-op, matching the long-standing no-op for a missing leaf in an existing folder.
In both options, existing empty trees in installed repos are not swept.

CHOICE: (b), approved by the user and merged as PR #389 (merge commit fa1b6d03). There is ONE fix point, deleteFromTree in internal/store/plumbing.go, which every knomit delete passes through: DeleteFact, BatchWriteFacts, the merge's src-delete, and the src-delete conflict resolution.

RATIONALE: "Nothing is there, so there is nothing to delete." Under (a), dropping folders would have turned a REPEAT delete into an error as soon as its folder had emptied. Today that repeat delete is a silent no-op, and callers rely on that: the synthesize prune merge, and learn's subsumed-hypothesis deletes. A caller that needs the target to exist already checks for itself: DeleteFact's existence check under the lock, BatchWriteFactsMustExist / RetractMissingError for the F04 move, and dstHas in the merge. An audit at merge time found no production caller that depended on the missing-subtree error. Only one test used it, as a failure injector, and it was replaced by an injected storage failure (TestBatchWriteFacts_DeleteFailureCommitsNothing).

REJECTED: (a), for the repeat-delete regression. A one-off sweep of legacy empty trees, because the fix only needs to change new writes, and rewriting trees in installed repos is a separate decision.

NON-SCOPE: this does NOT make deletes unchecked. A storage failure reading a subtree still errors and fails the whole batch. It does NOT change DeleteFact, which still refuses an absent path with "does not exist". And "no sweep" is only approximately true: a delete whose path WALKS THROUGH a pre-existing empty folder drops that folder as a side effect. That is spelled out in the invariant "deleteFromTree is the single funnel for every knomit tree deletion" (kb/invariants/store/git-trees/delete-drops-empty-folders/).
