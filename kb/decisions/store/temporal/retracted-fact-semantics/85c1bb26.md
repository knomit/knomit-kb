# Commit-anchored reads: retracted = gone (404) by default; ?fallback=before resolves the last-valid version + its edges

As of a commit, a fact's state RESPECTS deletions: once retracted it is GONE for the commit-anchored fact read, /incoming, and /outgoing alike. A retracted fact's past content is reachable ONLY by following another fact's historical ref, which is pinned to the exact target_commit where that version existed — never by 'fall forward to a later commit'. Two modes:

- DEFAULT (no fallback): respects deletes. fact read + /incoming + /outgoing all 404 when the most-recent commit_log event for the path in the first-parent ancestry is a deletion. Gate: FactLiveAtCommit (internal/engine/store/index/derived_from.go since #557) — same first-parent CTE as resolveActiveCommitForPath but WITHOUT the action filter: it takes the most-recent event and is live ONLY if it is added/modified. The web handlers call factPresentAtCommitOr404 (handlers_fact_sub.go) before fetching edges.
- ?fallback=before (explicit opt-in, fact read AND /incoming /outgoing): steps OVER the deletion to the last added/modified version and serves it + its edges; 404s ONLY if the path never existed in the ancestry. Gate for edges: FactExistsAt (the step-over-delete predicate). Edge effective-commit resolution (IncomingAtCommit/OutgoingAtCommit) already uses resolveActiveCommitForPath, which steps over deletes, so the edges line up with the fallback fact read. ExplainView's api.explain appends ?fallback=before to the commit-anchored edge fetches so the view's edges follow its fallback:'before' fact read.

LOAD-BEARING DISTINCTION — two existence predicates with OPPOSITE deletion semantics, do not confuse them:
  • FactLiveAtCommit  → 'is the fact present (un-retracted) AS OF X' — used to 404 the no-fallback path.
  • resolveActiveCommitForPath / FactExistsAt → 'what is the last NAVIGABLE (added/modified) version ≤ X', steps over retractions — used for ref-kind classification, edge resolution, and the fallback-before content.
Using the step-over predicate as a no-fallback existence gate is the bug that made /incoming /outgoing return an empty 200 for a fact that the fact read 404'd (PR #77). Both read the SAME index (commit_log + commit_parents first-parent chain), which faithfully mirrors git — the 'divergence' was these two semantics, never an index error.

WHERE THEY LIVE (corrected 2026-07-22): both predicates are methods on the **factQuery** sub-service — `Service.FactQuery().FactLiveAtCommit(...)` / `.FactExistsAt(...)`, not on `store.SearchIndex`. They moved in the P1.3 read-surface split (see kb/architecture/store/240a44f5.md). `resolveActiveCommitForPath` did NOT move in the P1.3 split — it stayed on repoHandler (since hier-07 it is vcs.Repo.ResolveActiveCommitForPath in internal/engine/store/internal/vcs/revisions_before.go), co-owned by FactQuery existence checks and GraphStore commit-scoped queries.

AT W0g2 (PR #614, merged as 99e0d3a5; re-read there): the gate logic above is unchanged. factPresentAtCommitOr404 in handlers_fact_sub.go lost its provider parameter and calls the package functions factLiveAtCommit (no fallback) and factExistsAt (?fallback=before) at the ANCHOR commit, never at the branch head. TestCommitAnchoredSub_GateIsEvaluatedAtTheAnchor pins both: kb/r.md live at x1 and retracted at head answers 200 at x1 without fallback, and at x0 (before r existed) with ?fallback=before answers 404.
