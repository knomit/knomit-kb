# The commits a push brings are found by a walk that stops at a commit the host already holds (on the FLEET repository: only at a held commit reachable from main or an admitted agent/* branch) — not by walkHistory with a precomputed stop set of every host ref's history

`quarantine.newCommits(tip)` (internal/store/receivepack_quarantine.go) returns reachable(new tip) ∖ reachable(host refs) by descending only into commits that arrived in THIS push (are in the quarantine) and skipping any commit the host store holds. Cost is proportional to the push. The obvious alternative — `walkHistory(overlay, tip, stop, …)` with `stop` = every commit reachable from the host's refs — gives the same set but walks the host's whole history on every push (F11 review N9); CheckRange pays that for Main because it runs once per merge job, a push path runs per push.

The two definitions differ only for commits the host holds that no ref reaches (e.g. objects left by a crashed promotion). Those are already present, so neither judging nor promoting them again is right either way.

The same held/not-held test bounds `reachableNew`: a tree the host already has is not descended (the host has everything under it), and a referenced object that is neither in the quarantine nor on the host fails the push ('incomplete') rather than promoting a tip with a hole in it. `newCommits` reports `visited`, which equals the number of new commits exactly when the walk never entered host history; TestReceivePack_NewCommitWalkIsProportionalToThePush pins it on a 31-commit host with a 2-commit push.

## UPDATE (PR #524 B1, verified at merge commit 9db8c106): on the fleet repository a held commit does not end the walk unless it is admitted

The rule above rested on an assumption: a commit the host holds was judged or written here. On the FLEET repository that is false. A master with an origin FETCHES every member's agent/* branch, refused tips included (they stay as remote-tracking refs), and a member clone made before #524 copied every agent/* branch of the forge. Once such a copy receives a push (a hub that was a forge copy, or a pre-#524 clone promoted), a clean merge M(X, main) of a refused, held tip X would be the only commit the walk returned; M carries no content of its own, so it is admitted and X is laundered into main.

The rule since #524: `quarantine.newCommits(tip, admitted)`. On the fleet repository (`repoHandler.heldAdmitted`: the ontology at the upstream is the fleet ontology, and the strict rule also applies when it cannot be read) a held commit ends the walk ONLY when it is reachable from the consensus branch (main) or from a local `refs/heads/agent/*` branch; any other held commit is descended and judged as if new. Remote-tracking refs are NOT admitted. Every other repository keeps `admitted == nil`: stop at any held commit, exactly as above.

INVARIANT, stated at the walk (comment on signerIsPusher): every commit the walk skips must be reachable from main or from a ref that was itself admitted. Pinned by TestFleetMaster_HubJudgesAHeldRefusedCommitAsNew and TestFleetMaster_HubJudgesACommitItsMemberCloneHeld (cmd, over mTLS: the push is refused naming the held commit X, and X never reaches main).

Cost note: a frontier commit that is a head tip is answered at once; any other held frontier commit builds, once per push and lazily, the set of commits reachable from main and the agent heads (O(fleet history), fleet repository only). The walk is still O(push) on every other repository.

Misreading to avoid: 'a held commit has been judged' is FALSE on the fleet repository (a fetch or a pre-#524 clone stores unjudged objects), and 'the walk is always O(push)' is false there. Also: this is in addition to, not instead of, the web-edge refusal of any push to a fleet copy with an origin (repos.Manager.FleetPushRefusal; see kb/invariants/fleet/push-refusal/882f738f.md), which is defence in depth.
