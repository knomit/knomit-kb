# ref_edges is the flat per-BLOB mirror of the DERIVED_FROM edges in the AUTHOR's refs order and THE read path for references in both directions (outgoing, incoming, blast radius, highlights); rows are derived from the edges inside the claim transaction, cross-KB refs get unresolved rows, the edges remain for Verify's drift check

PR B (#694, merged into dev at b208d5ed, on top of #693). Table ref_edges(source_blob, ord, target_repo, target_path, target_blob, target_commit), PRIMARY KEY (source_blob, ord), WITHOUT ROWID (migration 000035).

SEMANTICS:
- source_blob = the citing version's blob (node identity = blob, #693). ord = the ref's 0-based position in the version's frontmatter refs, counting EVERY ref (URLs, src://, .knomit/ too), so ord == json_each(facts.refs).key; gaps are normal; a (repo, path) cited twice keeps its first position (refSpecsOf). It is NOT edge-id order (edge ids are misordered for ~4% of facts, kb/gotchas/store/graph/derived-from-order).
- A LOCAL row (target_repo '') exists iff the blob's DERIVED_FROM edge to that path exists, with the edge's target blob and target_commit. So the real-blob invariant carries over: no row from a source blob missing from objects, none for a ref whose target blob is missing, none for an unresolved local ref.
- A CROSS-KB row (kb://<other-repo-id>/<path>) has target_repo set and target_blob/target_commit NULL, enforced by CHECK (target_repo = '' OR (target_blob IS NULL AND target_commit IS NULL)) in migration 000035 (review round 3, R3-N2; the incoming read and the reverse walk probe idx_ref_edges_target with no target_repo filter and rely on it): it is NOT resolved at write time, because the FactSet design resolves cross-KB refs against the other repo's tip frozen at FactSet creation. The row exists so a walk never parses frontmatter to find cross-KB refs. A version citing ONLY other KBs therefore also gets a refs_commit claim now (it goes through graphAddDerivedFromAtCommitTx with zero local refs).

WRITE: applyBlobRefs (index/derived_from.go) calls writeRefRowsTx in the SAME transaction as the claim and the edges, after the edges: the rows are recomputed from the edges now on the claim node plus the refs (expectedRefRows) and REPLACE the blob's rows when they differ. So a claim move or a void claim re-claimed replaces rows atomically with edges; a fill-in (Sync pass 2, rebuild phase B) adds rows with the edges; a COW hit writes nothing (the no-op check also compares rows, so a same-node revisit opens no transaction when rows are current).

EXISTING STORES: BackfillRefEdges (index/ref_edges.go), called once at the heal AFTER the branch rebuilds/syncs (corpus/repos/stages.go healIndexBranches, meta sentinel ref_edges_backfilled; after, so a pre-v8 store is not backfilled from the old union edges its v8 rebuild is about to reset), rewrites (a) every blob RefEdgeDrift names and (b) every Fact-node blob whose bytes contain 'kb://' and that has no row; order from the blob parsed out of objects. Batches of 500 blobs per transaction, sentinel last: an interrupted backfill just runs again. The #693 v8 reset (resetBlobRefsOnce) also deletes ref_edges.

VERIFY / REBUILD: fsck category ref-edges = RefEdgeDrift: the edge set vs the local row set compared as (source blob, target path, target blob, target commit), 'missing' and 'orphan'. rebuildGraph runs repairRefEdges after phase B' (failure logged, not fatal). The drift check costs ~8 s on a 750k-edge store and runs in every Verify and every rebuild: ACCEPTED by the user (PR #694).
- STRAY EDGES ARE DROPPED (user ruling, PR #694: an edge that should not be there should not be there): an edge out of any node of the blob whose target path is not a local ref of the source blob's parsed refs, or that is off the blob's refs (claim) node, or that is a SECOND edge to a path the refs node already has (the first by edge id is kept: the one expectedRefRows builds the row from) is reported by Verify as drift until a rebuild, and the rebuild's repair (repairRefBlobs with dropStray, dropStrayRefEdgesTx) DELETES it in the same transaction that rewrites the blob's rows, leaving drift 0. None of these is producible by the write path (corruption only): the resolver ignores the branch (vcs/revisions_before.go ResolveActiveCommitForPath, `_ = branch`), the claim fixes the source commit, and graphDerivedFromEdgeExists dedups on (src, tgt, source_commit, target_commit), so one claim resolves each path once.
- EMPTY REPO ID GUARD (PR #694 review F1): with localRepoID unresolved, kb://<self>/ refs classify as cross-KB, so (a) the repair is SKIPPED entirely (it would drop valid kb://self edges; BackfillRefEdges refuses the same state), and (b) the write path still writes edges but neither checks nor rewrites rows (rowsOK=false in graphAddDerivedFromAtCommitTx). rowsOK comes from the SAME repo-id lookup the specs were built with (callers pass that id into graphAddDerivedFromAtCommitTx): a second lookup could succeed where the first failed and store a kb://self ref as a cross-KB row naming this repo, which no drift check sees (review round 2, R2-F1). localRepoID no longer caches a failure (mutex, not sync.Once): a transient RootCommit error is retried on the next call instead of disabling repair and backfill for the life of the process.
- READ FALLBACK BEFORE THE BACKFILL (PR #694 review N2): the heal is a background job and the repo serves meanwhile. Until the sentinel ref_edges_backfilled is set, every reference read falls back to the DERIVED_FROM edges and answers the same before and after the backfill (tested): OutgoingAtCommit reads the edges sorted into the author's order (blob parsed from objects); RefEdgesOfBlobs derives the rows exactly as the backfill would (expectedRefRows); IncomingAtCommit reads the edge candidates in the same defined order; BlastRadius/ReverseDependentPaths walk the edges (that walk's recursive step is pinned with CROSS JOINs: unpinned it scanned every DERIVED_FROM edge per frontier row and never finished on a large store); the highlights out-degree counts the edges. The fallbacks do not fail when the repo id is unresolved: they LEARN this repo's id (review round 3, R3-N1): a candidate is the repo R of a kb://R/p ref whose blob has an edge to p and NO explicit local ref to p (else the edge is the local ref's, and kb://R/p may be another KB's fact at the same path); with exactly one candidate over the batch (else per blob), every spec of R becomes local, so a kb://self ref whose edge was dropped as dangling gets no row, as in the table; with none or several candidates nothing is converted, and a kb://self ref then reads as cross-KB, the best the blob tells (selfCandidates, withSelfRepo). Every rebuild runs BackfillRefEdges at its end when the sentinel is unset, so a reset spent by an explicit full rebuild does not leave the readers on the fallback until the next heal. Migration 000035 sets the sentinel on a store with no Fact node (a new store), and the v8 reset CLEARS it (so the next backfill restores cross-KB rows of versions on no branch, which the drain cannot re-create: review N4). The heal's backfill does NOT drop edges, and a blob that is missing from objects or does not parse drops nothing (its refs are unknown; missing-blob edges are dropDanglingRefEdges's job).
- Cross-KB rows are NOT checked by Verify (they mirror no edge; checking them would need every blob parsed): ACCEPTED by the user (PR #694).
- A version citing ONLY other KBs gets a refs_commit claim like any other (its rows are written in the claim transaction): ACCEPTED by the user (PR #694); pinned by TestRefEdges_CrossKBRowsAreUnresolved.

READERS (user ruling, PR #694 scope addition: ref_edges is THE read path for references in BOTH directions; the DERIVED_FROM edges are kept only for Verify's drift check, the write path's own bookkeeping, and the reads before the backfill):
- Outgoing: OutgoingAtCommit (Connections, explain outgoing, materialize pins) reads ref_edges (refEdgesOutOfBlob), joining the target Fact node by (target_path, target_blob) for title/type/deleted; the one intended change vs the edge read is the author's order. GraphStore.RefEdgesOfBlobs(blobs) is the batched level read for the FactSet: all rows of a set of blobs in (source_blob, ord) order, one IN statement per chunk of 4000 sorted blobs.
- Incoming: IncomingAtCommit reads ref_edges through the partial index idx_ref_edges_target ON ref_edges(target_blob) WHERE target_blob IS NOT NULL (refEdgesIncomingRows): the citing blobs of the target blob, each described by every Fact node of the citing blob; 'own' = the citing blob's claim node, chosen in Go as the lowest node id carrying refs_commit (readBlobClaim's rule) from a per-node LEFT JOIN; the source commit = the claim's refs_commit. The probe is a COVERING read of idx_ref_edges_target with no target_repo filter (only local rows carry a target_blob), and the join order is pinned (defensively: with this query shape SQLite picks the same plan without the pin, so no test catches its removal); measured warm at parity or better than the edge read (2,000 citers: 19.7-19.9 ms vs 19.8-20.2 ms; 200 citers on a knomit-kb copy: 2.28-2.31 ms vs 2.41-2.42 ms; before review round 2 the table read was 29.6-30.5 ms vs 20.3-20.7 ms). #693's semantics are unchanged (held-blob visibility now or in history via blobHoldings, one row per held path at the same hop commit, retracted citers listed as deleted, every version that ever cited kept: kb/decisions/store/graph/incoming-visibility-held-blob). The ORDER is now defined and rebuild-stable for both the table and the edge read (sortIncomingCandidates): the citing version's source commit in commitEarlier's total order (committed_at, same-second ancestors, hash), then the citing blob, then the path. Cross-KB incoming is NOT read (other KBs' tables are not consulted).
- Blast radius / ReverseDependentPaths: the reverse walk follows ref_edges target_blob -> source_blob (reverseDependentsByRowsSQL), same liveness through branch_facts. The edge walk's recursive step can scan every DERIVED_FROM edge per frontier row (plan SEARCH e USING INDEX idx_edges_type): on a 750k-edge store it did not finish in 37 minutes, while the table walk takes ~2-7 ms.
- Highlights out-degree: COUNT(DISTINCT target_path) of a blob's local rows (liveFactNodeCTE byRows).
- No other production reader of DERIVED_FROM edges remains outside Verify (RefEdgeDrift, DanglingRefEdges), the rebuild (dropDanglingRefEdges, repair) and the write path (graphDerivedFromEdgeExists, expectedRefRows, refsNodeOfBlob).

No target node id column: the FactSet joins blob to blob, and node ids are no more stable than edge ids; the outgoing read finds the target node by (path, blob) through idx_node_props_text_key_value.

WHAT THIS DOES NOT MEAN: ref_edges is not a second source of truth. It is derived from the edges; when they disagree the edges win (repair rewrites rows from edges). Cross-KB rows are NOT checked by Verify (they mirror no edge). Do not read target_blob of a cross-KB row as 'unresolved local ref': local refs that did not resolve have no row at all.

MEASURED 2026-10-31 (Apple Silicon laptop, load average 2-3 from other work, OS page cache NOT purged, so 'first after open' is SQLite-cold only). These are dated observations of that build and machine, not properties to derive constants from.
- Worst case 500 roots x 499 distinct refs (250k facts, 748,500 rows, 3.1 GB store): first level RefEdgesOfBlobs 0.21-0.22 s vs the edge-EAV set join 0.44-0.45 s (warm and first-after-open alike); per level (each root's 499 children, one set read per unit) 1.74 ms vs 2.61 ms per unit. The flat read is dominated by scanning 250k rows into Go, so the gain is ~2x, not an order of magnitude.
- Getting rows into an existing store: backfill 26.6 s for 250k blobs vs 9 m 08 s for the forced v8 rebuild of the same store; drift check (Verify, and every rebuild's repair) 8.0 s over 748,500 edges; table 122 MiB (VACUUMed page delta) for 748,500 rows.
- Real KBs (copies of the live knomit-kb and core stores, v7 upgraded by the v8 rebuild): backfill == write path row for row (15,769 and 3,176 rows), drift 0; backfill 0.57 s / 0.11 s vs v8 rebuild 22.7 s / 7.6 s; OutgoingAtCommit vs edge read identical on every live version (per-call time unchanged, dominated by the path@commit -> blob resolution).
- Write path: a fact citing 20 facts, 60 writes, base 866eb303 vs branch: median 27.24-27.37 ms vs 27.44-27.45 ms (about +0.1-0.3 ms, ~1%).
