# ref_edges is the flat per-BLOB mirror of the DERIVED_FROM edges in the AUTHOR's refs order: rows are derived from the edges inside the claim transaction, cross-KB refs get unresolved rows, outgoing reads use it, incoming stays on the graph

PR B (branch feat/ref-edges-v2, on top of #693). Table ref_edges(source_blob, ord, target_repo, target_path, target_blob, target_commit), PRIMARY KEY (source_blob, ord), WITHOUT ROWID (migration 000035).

SEMANTICS:
- source_blob = the citing version's blob (node identity = blob, #693). ord = the ref's 0-based position in the version's frontmatter refs, counting EVERY ref (URLs, src://, .knomit/ too), so ord == json_each(facts.refs).key; gaps are normal; a (repo, path) cited twice keeps its first position (refSpecsOf). It is NOT edge-id order (edge ids are misordered for ~4% of facts, kb/gotchas/store/graph/derived-from-order).
- A LOCAL row (target_repo '') exists iff the blob's DERIVED_FROM edge to that path exists, with the edge's target blob and target_commit. So the real-blob invariant carries over: no row from a source blob missing from objects, none for a ref whose target blob is missing, none for an unresolved local ref.
- A CROSS-KB row (kb://<other-repo-id>/<path>) has target_repo set and target_blob/target_commit NULL: it is NOT resolved at write time, because the FactSet design resolves cross-KB refs against the other repo's tip frozen at FactSet creation. The row exists so a walk never parses frontmatter to find cross-KB refs. A version citing ONLY other KBs therefore also gets a refs_commit claim now (it goes through graphAddDerivedFromAtCommitTx with zero local refs).

WRITE: applyBlobRefs (index/derived_from.go) calls writeRefRowsTx in the SAME transaction as the claim and the edges, after the edges: the rows are recomputed from the edges now on the claim node plus the refs (expectedRefRows) and REPLACE the blob's rows when they differ. So a claim move or a void claim re-claimed replaces rows atomically with edges; a fill-in (Sync pass 2, rebuild phase B) adds rows with the edges; a COW hit writes nothing (the no-op check also compares rows, so a same-node revisit opens no transaction when rows are current).

EXISTING STORES: BackfillRefEdges (index/ref_edges.go), called once at the heal AFTER the branch rebuilds/syncs (corpus/repos/stages.go healIndexBranches, meta sentinel ref_edges_backfilled; after, so a pre-v8 store is not backfilled from the old union edges its v8 rebuild is about to reset), rewrites (a) every blob RefEdgeDrift names and (b) every Fact-node blob whose bytes contain 'kb://' and that has no row; order from the blob parsed out of objects. Batches of 500 blobs per transaction, sentinel last: an interrupted backfill just runs again. The #693 v8 reset (resetBlobRefsOnce) also deletes ref_edges.

VERIFY / REBUILD: fsck category ref-edges = RefEdgeDrift: the edge set vs the local row set compared as (source blob, target path, target blob, target commit), 'missing' and 'orphan'. rebuildGraph runs repairRefEdges after phase B' (failure logged, not fatal). The drift check costs ~8 s on a 750k-edge store and runs in every Verify and every rebuild: ACCEPTED by the user (PR #694).
- STRAY EDGES ARE DROPPED (user ruling, PR #694: an edge that should not be there should not be there): an edge out of any node of the blob whose target path is not a local ref of the source blob's parsed refs, or that is off the blob's refs (claim) node, or that is a SECOND edge to a path the refs node already has (the first by edge id is kept: the one expectedRefRows builds the row from) is reported by Verify as drift until a rebuild, and the rebuild's repair (repairRefBlobs with dropStray, dropStrayRefEdgesTx) DELETES it in the same transaction that rewrites the blob's rows, leaving drift 0. None of these is producible by the write path (corruption only): the resolver ignores the branch (vcs/revisions_before.go ResolveActiveCommitForPath, `_ = branch`), the claim fixes the source commit, and graphDerivedFromEdgeExists dedups on (src, tgt, source_commit, target_commit), so one claim resolves each path once.
- EMPTY REPO ID GUARD (PR #694 review F1): with localRepoID unresolved, kb://<self>/ refs classify as cross-KB, so (a) the repair is SKIPPED entirely (it would drop valid kb://self edges; BackfillRefEdges refuses the same state), and (b) the write path still writes edges but neither checks nor rewrites rows (rowsOK=false in graphAddDerivedFromAtCommitTx). localRepoID no longer caches a failure (mutex, not sync.Once): a transient RootCommit error is retried on the next call instead of disabling repair and backfill for the life of the process.
- READ FALLBACK BEFORE THE BACKFILL (PR #694 review N2): the heal is a background job and the repo serves meanwhile. Until the sentinel ref_edges_backfilled is set, OutgoingAtCommit reads the DERIVED_FROM edges sorted into the author's order (blob parsed from objects) and RefEdgesOfBlobs derives the rows exactly as the backfill would (expectedRefRows), so both answer the same before and after the backfill (tested). Migration 000035 sets the sentinel on a store with no Fact node (a new store), and the v8 reset CLEARS it (so the next backfill restores cross-KB rows of versions on no branch, which the drain cannot re-create: review N4). The heal's backfill does NOT drop edges, and a blob that is missing from objects or does not parse drops nothing (its refs are unknown; missing-blob edges are dropDanglingRefEdges's job).
- Cross-KB rows are NOT checked by Verify (they mirror no edge; checking them would need every blob parsed): ACCEPTED by the user (PR #694).
- A version citing ONLY other KBs gets a refs_commit claim like any other (its rows are written in the claim transaction): ACCEPTED by the user (PR #694); pinned by TestRefEdges_CrossKBRowsAreUnresolved.

READERS: OutgoingAtCommit (Connections, explain outgoing, materialize pins) reads ref_edges (refEdgesOutOfBlob), joining the target Fact node by (target_path, target_blob) for title/type/deleted. The ONE intended change vs the edge read: rows come in the author's order. GraphStore.RefEdgesOfBlobs(blobs) is the batched level read for the FactSet: all rows of a set of blobs in (source_blob, ord) order, one IN statement per chunk of 4000 sorted blobs, no git, no graph nodes. IncomingAtCommit stays on the graph (no target_blob index; visibility semantics unchanged).

No target node id column: the FactSet joins blob to blob, and node ids are no more stable than edge ids; the outgoing read finds the target node by (path, blob) through idx_node_props_text_key_value.

WHAT THIS DOES NOT MEAN: ref_edges is not a second source of truth. It is derived from the edges; when they disagree the edges win (repair rewrites rows from edges). Cross-KB rows are NOT checked by Verify (they mirror no edge). Do not read target_blob of a cross-KB row as 'unresolved local ref': local refs that did not resolve have no row at all.

MEASURED 2026-10-31 (Apple Silicon laptop, load average 2-3 from other work, OS page cache NOT purged, so 'first after open' is SQLite-cold only). These are dated observations of that build and machine, not properties to derive constants from.
- Worst case 500 roots x 499 distinct refs (250k facts, 748,500 rows, 3.1 GB store): first level RefEdgesOfBlobs 0.21-0.22 s vs the edge-EAV set join 0.44-0.45 s (warm and first-after-open alike); per level (each root's 499 children, one set read per unit) 1.74 ms vs 2.61 ms per unit. The flat read is dominated by scanning 250k rows into Go, so the gain is ~2x, not an order of magnitude.
- Getting rows into an existing store: backfill 26.6 s for 250k blobs vs 9 m 08 s for the forced v8 rebuild of the same store; drift check (Verify, and every rebuild's repair) 8.0 s over 748,500 edges; table 122 MiB (VACUUMed page delta) for 748,500 rows.
- Real KBs (copies of the live knomit-kb and core stores, v7 upgraded by the v8 rebuild): backfill == write path row for row (15,769 and 3,176 rows), drift 0; backfill 0.57 s / 0.11 s vs v8 rebuild 22.7 s / 7.6 s; OutgoingAtCommit vs edge read identical on every live version (per-call time unchanged, dominated by the path@commit -> blob resolution).
- Write path: a fact citing 20 facts, 60 writes, base 866eb303 vs branch: median 27.24-27.37 ms vs 27.44-27.45 ms (about +0.1-0.3 ms, ~1%).
