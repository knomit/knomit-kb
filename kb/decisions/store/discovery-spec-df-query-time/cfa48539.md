# Discovery spec df is computed live at query time (SearchIndex.TokenDF), not a materialized token_df table

Options considered: (a) a materialized `token_df` table maintained on ingestion + rebuild with a rebuild≡ingest parity test; (b) compute df live at query time via an indexed COUNT over the junction tables joined to branch_facts, memoized per session; (c) a branch-scoped materialized table also maintained on every branch_facts change.

Rationale: a LIVE document-frequency is inherently branch-scoped — liveness lives in `branch_facts`, which changes on sync/merge/retract, NOT on the fact-ingestion path — so a table maintained only on ingestion+rebuild would silently drift from live df. df is needed only for candidate bridge tokens that survive the cheap coh/sep gates (bounded by the effort budget: <=12 medium / <=48 high per session), each one an indexed point COUNT, memoized like gap — tens of ms against the ~68s clustering the pipeline already does. Materializing trades a migration + dual choke-point maintenance + parity tests to save noise-level time AND is less correct (version-level, not live). All needed indexes already exist (fact_domain_tokens_token, fact_entities_entity, branch_facts_fact). It is merge-safe because the junctions it counts are maintained in `upsert` (search_crud.go), which runs on merges too (Sync→indexFile→upsert).

CRITICAL framing: `spec` is the document-frequency of the bridge's DOMAIN/ENTITY TAG — it is NOT TF-IDF over fact body text; nothing reads or tokenizes bodies for it.

Choice: `TokenDF(ctx, branch, token, kind)` returns COUNT(DISTINCT branch_facts.path) joined to fact_domains (domain; canonical-form exact match) or fact_entities (entity; COLLATE NOCASE), branch-scoped and live, memoized per session in the consumer. No materialized table, no migration. Mirrors BlastRadius's liveness pattern. Supports the mechanism in decisions/synthesize/bridge-quality-mechanism.

WHERE IT LIVES (corrected 2026-07-22): the method is on the **graphStore** sub-service — `Service.GraphStore().TokenDF(...)`, NOT `SearchIndex.TokenDF`. It moved in the P1.3 read-surface split (internal/store/token_df.go; see kb/architecture/store/240a44f5.md).
