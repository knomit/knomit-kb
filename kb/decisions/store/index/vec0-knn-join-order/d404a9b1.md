# Decided (user, 2026-11-02, #725): every vec0 KNN joined to a table is written so vec0 is the OUTER loop (CROSS JOIN in written order, or a MATERIALIZED CTE), with an EXPLAIN QUERY PLAN guard test; not a test-only fixture, not a timeout bump

Options considered:
1. Pin the join order in SQL so the vec0 virtual table drives (CROSS JOIN, or a MATERIALIZED CTE where CROSS JOIN cannot express it), and add an EXPLAIN QUERY PLAN guard that fails if the outer loop is not the vec0 table.
2. Test-only: write TestLensQuery_EpSelectsBeforeTheWindow's 501-fact fixture on a store with no embedder, so no similarity edges are built.
3. Raise go test -timeout for the web step, or split the package.

Rationale: SQLite planned `facts_vec fv JOIN facts f ON f.id = fv.rowid WHERE fv.embedding MATCH ? AND fv.k = ?` as `SCAN f` outer and re-ran the whole vec0 KNN once per facts row. graphBuildSimilarityEdges runs on every indexed fact write, so each write costs (facts rows, all versions) x one KNN (~4 ms each on the Windows dev host) and a batch of n facts is quadratic: 501 facts took 9 min 12 s, against 5.9 s with vec0 outer. That is a product bug that users hit on every write, not test cost. Option 2 hides it. Option 3 was rejected before for the same class of failure (decision ffef3411: fix the cause, not the ceiling), and this one test alone needs more than 9 minutes on Windows.

Choice: option 1, for graphBuildSimilarityEdges, rebuildGraph's KNN, the vector-search KNN joins in search_query.go, and every other vec0 MATCH query in the store joined to a table (methodology, vocab abstraction, ...), with the guard test over the exact SQL each runs.

Non-scope: this changes JOIN ORDER only. It does not change k, any overfetch, any WHERE filter or the KNN window semantics: vec0's k window still applies before the join and before every filter (gotcha fbb0d36d), so the result sets must be identical before and after. It does not authorize CROSS JOIN as a general style rule outside queries whose plan was measured wrong.
