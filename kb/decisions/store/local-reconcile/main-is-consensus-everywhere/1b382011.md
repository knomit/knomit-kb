# main is a real consensus branch on EVERY repo: an origin-less repo advances refs/heads/<upstream> from its own agent branch through a polled local reconcile, never through the write path — chosen over 'HEAD follows the agent branch' so a peer needs no host-specific rule

Decided 2026-09-15 with the user (PR #205). The problem: a repo with no origin never started a reconcile loop (runReconcileLoop returned when GetRemote("origin") was nil), so its main stayed at the root commit forever while every fact lived on the agent branch. A peer subscribing to that repo's main would have seen one commit.

Options: (A) on origin-less repos serve HEAD → agent branch and have a knomit subscriber trust HEAD when the origin identifies as knomit via the agent capability; (B) origin-less repos advance main themselves; (C) leave it, subscribers name the agent branch. Chosen B, with an adjustment: main is advanced by a RECONCILE step (Service.AdvanceLocalUpstream, driven by runLocalReconcileLoop), not inside batchWrite. Rationale: under A main is a lie papered over by a client-side special case that disappears the moment knomit is a true origin; under B main means the same thing on every host. Advancing in a reconcile step rather than the write path keeps the invariant that an agent writes only its own branch, and it is the same step the future "host merges other agents' branches into main" needs — with one agent it is a fast-forward, with several it is a merge. This is consistent with kb/invariants/store/branch-roles: the consensus role still comes from the explicit record (Remote.Branch, else the local-init default), never inferred from a git-level signal.

Shape: polled on GitConfig.LocalReconcileInterval (toml local_reconcile_interval, env KNOMIT_GIT_LOCAL_RECONCILE_INTERVAL, default 30s, 0 disables), runs once at loop start, each tick compares tips and does nothing when equal, so a burst of writes costs one advance and main is EVENTUALLY consistent by design (the user explicitly accepted lag to keep sync off the hot path). The loop and the origin-backed reconcile loop are mutually exclusive by the same fact (origin row present or not). The advance reuses reconcileMain's fast-forward shape: EnsureBranch → SetReference → populateCommitLog → notifyCommit under the upstream's branch lock. EnsureLocalUpstream additionally bootstraps a missing refs/heads/<upstream> from refs/remotes/origin/<upstream> at open for origin-backed stores (a store moved between machines had no local main).

Misreadings: main advancing does NOT mean main is written by facts — nothing on the write path touches it. "Eventually" is real: a read of main right after a write may lag up to one interval. Repos WITH an origin are unchanged; their main follows origin/<upstream>.
