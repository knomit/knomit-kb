# commit_log SQL operations live on storegit.Storer, NOT on git.Store

All commit-index SQL operations are owned by storegit.Storer as named methods: CommitLogAvailable() bool, CommitLogSync(branchName, iter) error, CommitLogQuery(branchID, path, cursor, limit), CommitLogFileCounts(hashes), CommitLogActivity(path, cutoffs), CommitLogWalkChanged(prefix, seen, limit). The storer owns SQL; git package retains go-git walk logic only (populateCommitLog builds an iterator over commits using gogit.Log, calls changedFilesInCommit per commit, passes the iterator to s.storer.CommitLogSync). git.Store NO LONGER has a *sql.DB field — it accesses commit_log via the storer's named methods.

CommitLogSync's iterator signature (post PR #67): `func() (hash string, parents []string, entries []CommitLogEntry, err error)`. The `parents` return was added when commit_parents was introduced (see [[three-table-commit-index]] and [[commit-parents-table]]) — the iterator yields parents alongside per-path entries so all three tables (commit_log, branch_commits, commit_parents) can be populated atomically inside the same transaction per commit. Sentinel for done is `('', nil, nil, nil)`. Dedup: stops processing a hash already in branch_commits but CONTINUES iterating (skip-and-continue, not short-circuit) so merge DAGs index correctly — see [[commitlog-sync-walks-dag-not-shortcircuit]]. Sets the internal commitLog atomic on first successful write. Used identically for startup backfill (many commits) and per-write append (single-commit iterator).
