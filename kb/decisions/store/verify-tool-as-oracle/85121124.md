# Verify is production debugging tool AND test oracle for 8 store integrity categories

Service.Verify(ctx, opts) returns an IntegrityReport that BOTH the knomit-verify CLI and the invariant test suite use. EIGHT categories (constants in internal/store/verify.go, verified present at HEAD): (1) git-reachability — full walk from each branch ref, every tree entry resolves; (2) commit-log — bidirectional parity between git history and the commit index; (3) facts-coherence — three-way branch_facts/facts/tree blob_hash triangle; (4) embeddings-coverage — every facts row has a facts_vec row and vice versa; (5) branches-table — SQLite branches table has exactly one row per git branch ref; (6) branch-facts-table — branch_facts integrity (added since the original 7-category design); (7) fact-format — Warning severity, Deep:true only; (8) graph-coherence — every facts row has a cypher Fact node keyed by (path, blob_hash) and vice versa (catches graphSyncFact silent failures).

WHAT THIS DOES NOT MEAN (corrected 2026-07-22 — both of these were stated backwards or stale):

1. "Verify is NEVER atomic across branches — it locks per branch and releases before the next" is FALSE and is the DANGEROUS reading. Verify acquires `lockBranchRead(br)` for EVERY branch up front and `defer`s every unlock, so ALL branch read locks are held SIMULTANEOUSLY for the ENTIRE run (internal/store/verify.go). That is deliberate — it is what makes the report a consistent cross-branch snapshot instead of a torn one. The operational consequence is the opposite of the old wording: a Verify on a busy repo BLOCKS EVERY WRITER on every branch it covers until it finishes, and a concurrent index Rebuild (which holds the write side of the same per-branch RWMutex) BLOCKS Verify. Do not treat Verify as a cheap incremental probe you can fire on a live repo — budget for it, or take the repo offline. See kb/invariants/store/index/branch-locking/f4911495.md and kb/invariants/repos/verify-holds-read-lock/9b737b05.md.

2. The commit-log category does NOT check a TWO-table index. The commit index is THREE tables — commit_log (per-path) + branch_commits (visibility) + commit_parents (DAG edges) — see kb/invariants/store/three-table-commit-index/0d26d859.md. A parity check written against the old two-table mental model would miss commit_parents drift entirely.

3. embeddings-coverage is NOT unconditional: `checkEmbeddingsCoverage` returns early with zero issues when no embedder is configured. A no-embedder store reports clean because it was never checked — see kb/invariants/embeddings/mandatory/f34da09a.md.
