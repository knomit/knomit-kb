# Sync and replication code is designed as snapshot-then-reconcile: record immutable commit hashes, recompute every decision from them on each round, converge eventually — never chase individual failure paths with modes or flags

USER RULING (2026-10-17), verbatim: "there is absolutely no way to enfoce everything to behave as the happy path all the time. You cannot prevent all failures. For distributed systems, you account for failures: you do snapshotting (in our case the commit hash), then you detect changes and see if you can account for them or not. You bulid for eventual consiustency, not consistency 100% of the time - this is not an ACID database, its is a distrivuted system. Failure is expected." And: "No more chasing different paths - we're always looking to snapshot and reconcile. Add this as a guideline."

OPTIONS CONSIDERED. (1) What PR #544 had become through three review rounds: an in-progress mode flag (origin_position_forgotten), a destructive step (delete the watermark and tracking refs at the first sync with a new URL), a signing-based filter, then — for each failure window a reviewer found (failed fetch, failed push, crash, a retry taking a different code path) — one more patch (a ref copy, forcing a code path while the flag is set). Every new failure point was a new hole. (2) Snapshot-then-reconcile: keep only immutable facts (commit hashes and the identity of the origin they came from), never destroy them mid-operation, and recompute the decision from scratch on every round as a pure function of reachability between those hashes and what was just fetched. Chosen: (2).

THE RULE. For any code that syncs, replicates, rewinds or hands state between copies (store reconcile/replay, origin changes, fleet sync, master switches, experiments across rewinds):
- Snapshot: record the last state that was FULLY reconciled as immutable values (commit hashes, plus the origin identity they belong to). Replace a snapshot only after a round fully succeeds; never delete it as a first step.
- Detect: each round, fetch, then compare current state against the snapshot by reachability.
- Reconcile: classify every difference into (a) can be accounted for automatically → act, or (b) cannot → leave it untouched and surface it (no silent default; see issue #541).
- A failure anywhere leaves the snapshot as it was; the next round recomputes the same answer from the same hashes. The system converges; there are no partial-progress modes whose meaning depends on which step failed.

CONSEQUENCE. Briefs and reviews of such code ask "what is the snapshot, and is every decision a pure function of it and the fetched state?" — not "which failure window is still open?". A design that needs a new flag or code-path special case per discovered failure window is the anti-pattern; redesign instead of patching.

FORESEEABLE MISREADING. This does NOT mean ignoring failures or accepting data loss: unclassifiable differences must be kept and surfaced, not dropped. It does NOT mean every operation must be retried blindly — reconcile decides from the snapshot what is safe. It does NOT forbid locks for local atomicity (one round's own writes); it forbids correctness that depends on a multi-step operation never being interrupted.

NON-SCOPE. Single-process local operations with an atomic commit (one git ref update, one SQLite transaction) are not distributed and need no snapshot machinery.
