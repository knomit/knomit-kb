# Control-character paths are refused by ONE check in store.validatePath, not by per-field checks at learn/REST/synthesize

**Problem (#384).** A caller-supplied segment holding a control character (knomit_learn `category: "a\nb"`) became a tree path that go-git refuses to READ but happily WRITES. The read runs in notifyCommit's im.Sync after SetReference, so the write committed, reported failure, and every later write on the branch did the same while the index froze.

**Options considered.** (A+B) a store backstop in store.validatePath PLUS boundary checks in learn, REST create/PUT and synthesize that name the offending field (`fact 0: category contains a control character`); (A only) the store backstop alone, its error quoting the path with %q so the character is visible; (B only) boundary checks alone.

**The choice: A only** (user decision, 2026-10-01). store.validatePath, which writeFileExact, deleteFile and batchWrite all run before the branch lock and before the ref moves, refuses any byte < 0x20 and 0x7f, wrapping store.ErrInvalidPath: `invalid path "kb/architecture/a\nb/x.md": contains a control character`. fileExists applies the same helper so learn's exists check on an explicit `path` answers in the same words; writeStoreError maps ErrInvalidPath to HTTP 400.

**Rationale.** The user wanted a single check. B's only advantage was naming the field; its cost was NOT the reason it lost. B-only was never viable: it leaves every future write door unguarded.

**Non-scope.** This does not authorize adding per-field control-character checks at the boundaries later 'for a better message' without revisiting the decision. It does not cover empty segments (`x//y`), which were explicitly not approved. It does not repair a branch already holding such a commit. The rule must stay a strict SUBSET of go-git's ValidTreePath; it does not license store.validatePath to absorb the private-path rule (see kb/decisions/fact/kb-repo-layout/private-dot-paths/b3425b43.md, which forbids that for a different reason).
