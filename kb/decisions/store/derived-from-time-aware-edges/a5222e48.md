# DERIVED_FROM edges carry (source_commit, target_commit) and are written ONCE per source blob: at the commit that introduced the blob; a later arrival of the same blob adds none

CORRECTED 2026-10-30 (user ruling; PR fix/graph-blob-edges, GraphSchemaVersion 8). The original decision, 'one edge per ref-event: every commit asserting a ref is its own ref-event', is SUPERSEDED. It made the COW-hit path re-resolve a blob's refs at every commit the blob arrived at. Reads match by version, so they returned the union: on knomit-kb, 2,053 duplicate groups and 507 refs pinned to several target versions (see kb/incidents/store/graph/reference-edges-re-pinned-per-commit).

THE RULE NOW:
- Node identity for references = the blob. A blob's refs become DERIVED_FROM edges ONCE, resolved at the commit that FIRST introduced it (the earliest introduction in the order below), wherever it is first seen.
- Each edge keeps two text properties: source_commit (that introducing commit) and target_commit (the target's write commit, as resolveTargetCommit finds it from there).
- A blob arriving anywhere else adds NOTHING: a merge carrying it unchanged, another branch, an experiment commit, a rename (same bytes at a new path), a restore after retraction. A merge that RESOLVES a conflict produces a new blob, hence a new node and new edges resolved at the merge commit.
- Mechanism: the node that carries the blob's edges holds node prop refs_commit (the claim), even when no ref resolved. The claim and the edges are written in ONE transaction (applyBlobRefs); the claim is decided outside it (claimBlobRefs, which may read git) and re-checked inside it.
  - Only a strictly EARLIER introduction seen later moves the edges. The order (commitEarlier) is TOTAL, a per-commit key compared lexicographically: committed_at FIRST (commit_log's, else the git committer time; with clock skew a descendant can come out earlier), then the number of ancestors committed in that same second (so a same-second ancestor comes first), then the hash. It is NOT 'ancestor first': ancestry only decides inside one second.
  - Every arrival, claimed or not, is resolved at the earliest introduction at that path (introducingCommit: path_changes entries reachable from an indexed branch, plus the passed commit when it holds the blob and a branch reaches it); for a claimed blob the claim then decides. It is never resolved at a commit that does not hold the blob (no edges instead), and a merge or branch tip holding it is used only when no introduction is recorded yet.
  - A claim whose commit no branch reaches (rolled-back experiment, rewound branch) is VOID: it counts as no claim, and the next arrival replaces it and deletes its edges in the same transaction (kb/invariants/store/graph/introducing-commit-holds-blob).
  - Rebuild == incremental holds because of four things together: the order is total (so the claim converges to one minimum whatever order arrivals come in); every arrival picks the earliest reachable introduction directly; claims at unreachable commits are void (so an orphaned claim never outlives the history a rebuild sees); and the GraphSchemaVersion 8 reset re-resolves EVERY row of `branches`, not only the rebuilt one. Before those fixes (PR #693 review B1) an experiment-only blob lost its edges on upgrade and came back pinned at the merge commit.
- Edges stay physically on that first (path, blob) node. Readers key by blob_hash (graphDerivedFromNeighbours, blast radius, highlights), so a rename's node reads them. Incoming: an edge is visible on a branch iff the CITING BLOB is held there (now or in its history), NOT iff its source_commit is on that branch (user ruling, PR #693 round 4). One row per node of the citing blob whose path holds it on the branch (a rename f->g lists kb/g.md live and kb/f.md retracted), each with a commit of that branch, ordered by edge id then node id. Option 1: refs stay resolved once, even across branches that never merge, so a branch can show the target as another branch resolved it, flagged as changed since cited (kb/decisions/store/graph/incoming-visibility-held-blob).

The two insert helpers still differ, and that still matters: DERIVED_FROM uses graphInsertEdgeReturningID (plain INSERT INTO, returns the id for the props), never graphInsertEdge (INSERT OR IGNORE).

WHAT THIS DOES NOT MEAN: edges are not per (path, commit) any more. Do not expect an edge per commit, and do not 'fix' a missing re-pin after a merge: a merge carrying a blob is meant to add nothing.
