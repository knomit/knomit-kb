# F05 `knomit_changes` is the NET tree difference between commit `since` and head — not a per-event replay of the commit log; `since` is a commit hash and no clock is involved anywhere

**Options considered** (RCA proposal `.claude/plans/2026-09-26-F05-rca-proposal.md`, reviewed and amended A1–A3, presented to the user by the master session on 2026-09-26):
- A. Per-event rows from the commit log (`CommitLogQuery`), ordered by commit time with a row tiebreak, each row carrying path, op and author — the original F05 design-set draft.
- B. The net difference of two trees: the folder at commit `since` vs the folder at head, each path added/modified/deleted, plus head.
- C. A `since` mode on `knomit_query`.

**Rationale.** A cannot be ordered the same way on two machines and can lose deletions: commit time is committer-set; equal seconds are common (on live knomit-kb main 419 seconds hold more than one commit, one holds 68) and ties break on each instance's local SQLite rowid; a fast-forward of main over an agent's merge puts an OLDER deleting commit behind the reader's bookmark, so a time-ordered read never reports that deletion even with honest clocks (reviewer probe P3d, reproduced through AdvanceLocalUpstream); GitHub merge commits re-list what they merged (201 merges carry 2190 duplicate rows, op `""` or `github-actions[bot]`); CommitLogQuery folds per commit and returns no path or action. C cannot show a deletion at all — query rows are index rows, and a deleted fact has none. B is a pure function of the two commits, identical on every machine, and reports deletions natively; the codebase already made the same call for experiments (`since_fork` is "a git diff from the recorded fork commit, never a timestamp comparison").

**The choice.** B. The user approved it on 2026-09-26. The user's confirmation, as relayed by the master session (the user's verbatim words were not available to the worker that recorded this): "F05 is APPROVED by the user: net difference (tree at `since` vs tree at head), the agent keeps the bookmark (a commit hash), knomit writes nothing, no clock anywhere." Shipped in PR #315 (merge 7cd2b28c); the rules that implement it are in the invariant this fact cites.

**Consequence a consumer must take away.** It is the NET difference: something added and removed between two reads is not reported, because it is no longer there — right for a reader of state (a task pool, an inbox). Nothing in F06–F08 or F15 needs an event this drops; F07 triggers consume the commit observer, not `changes`. Per-row op and author are not provided — read the fact for them.

**Non-scope.** This does not forbid a per-event history surface for humans (the REST commit list already exists) and does not decide F16's branch parameter. It does not authorise ordering or filtering anything in `changes` by commit time.
