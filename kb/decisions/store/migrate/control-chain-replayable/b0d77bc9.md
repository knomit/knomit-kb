# repo_subscriptions is a PRESENCE TABLE, not a column, because the control migration chain must stay replayable with IF NOT EXISTS statements only

A subscription's persistence is the PRESENCE OF A ROW in `repo_subscriptions` (repo_uid PRIMARY KEY, FK to repos with ON DELETE CASCADE), not a `mode` column on `repo_origins`. `Origin.Mode` (`OriginModeSync` / `OriginModeSubscribe`) is DERIVED from that row at read time.

The reason is a property of the control chain, not a preference: `knomit migrate-registry` replays the whole control schema text inside its own transaction, so every statement in the chain must be safe to re-run — `IF NOT EXISTS`-only. `ALTER TABLE ... ADD COLUMN` has no such form in SQLite and would break the replay. A test now enforces that property for EVERY control migration, so this constraint is checked rather than remembered.

**Consequence for a consumer:** when adding state to control.db, reach for a new table before a new column, and expect the migration test to reject a non-idempotent statement. This is specific to the CONTROL chain — it is not a claim about the per-repo store schema, which is migrated differently.

**Second-order effect:** because the mode is a joined row rather than a column on the origin, an origin writer that rewrites `repo_origins` without carrying Mode silently demotes a subscription to sync. Both origin write paths were changed to carry it.
