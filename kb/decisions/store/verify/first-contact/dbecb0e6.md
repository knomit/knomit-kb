# F09 first contact sets refs at origin's tips (no fold, since PR 5); E4 still adopts origin's copy of the own agent branch only if every commit beyond origin's main is signed by an own key (current key, plus every key the own fleet member record has held), accepted, or brought in by an own-signed merge commit (reachable from its non-first parent, F11 UI merge D4), and otherwise FAILS the create, never starting a fresh lineage

Since F09 PR 5 (user ruling: verify once, at acceptance), first contact (InitFromRemote, InitSubscription, CloneFrom) no longer folds history: local refs are set at origin's tips, which are trusted as fetched.

E4 (checkOwnLineage) stays, because it IS acceptance: it is the point where this instance adopts origin's copy of its OWN agent branch, whose commits it will push again under its own identity. Every commit reachable from that branch and not from origin's main must be signed by an own key or be on this instance's accept list (control.db verify_accepted, control migration 000013, since #330; E4 is its only reader: see kb/decisions/verify/accept-list-location/f6c03f1f.md). E4's refusal prints a ready `knomit verify accept <full hash>` line per refused commit. Own keys = the store's commit signer, plus (Service.SetOwnKeys, wired by the Manager next to SetSigner) every key this instance's fleet member record has held (Service.FleetKeysOf over the record's versions), so a key rotation does not make earlier own commits foreign. Standalone: the current key only. Otherwise the create FAILS with ForeignLineageError naming each refused commit; it never starts a fresh lineage (that would overwrite the remote branch on the first push and silently discard its commits).

Tests: verify_e4_test.go (own key adopted; unsigned, another key, no signer refused; pre-signing commits refused then adopted once accepted; an old record key adopted only with the record).

TRANSITIVE TRUST (F11 UI merge, user ruling D4 2026-09-29, verbatim: "4) no, no warnings - remember the principle, we should operate like a chain of trust ? If I trust this agent A and  agent A trusted agent B and it accepted its commits then we should trust them."): a commit that is neither own-signed nor accepted is ALSO adopted when it is reachable from a NON-FIRST parent of a merge commit that is itself in the range and signed by an own key — the shape the web UI's peer merge writes (merge commit [host tip, peer tip], host-signed). checkOwnLineage collects the whole range first and judges second, because walkHistory is post-order (parents before children) and would reach a merged-in commit before the merge that vouches for it.

WHAT THIS DOES NOT MEAN: an own-signed NON-merge commit vouches for nothing below it; the FIRST parent of an own merge is not vouched (that is this instance's own line and is judged commit by commit); a merge signed by another key, or unsigned, vouches for nothing; an accept-list entry waives only its own commit and vouches for nothing. A peer commit set directly onto origin's copy of the agent branch is still refused. Tests: verify_e4_transitive_test.go (TestE4_TransitiveTrust: one positive with two peer commits plus a peer merge, and five refusals, each asserting WHICH commits are refused).

Observation (reviewer2's gate plan): after a force-rewind of origin main, old main commits that reached the agent branch through this instance's own reconcile merge (second parent = main at the time) are now vouched where they were refused before. That is consistent with the chain-of-trust ruling.

TEST GAP (reviewer2, #352 gate, N2): no test pins that an ACCEPT-LISTED merge commit vouches for nothing. The code keeps them apart (an accepted commit is recorded with ownSig false, and only ownSig merges vouch), but a change that let an accepted merge vouch for its non-first parents would pass today's suite. Add the case before relying on that distinction.

'Beyond origin's main' is exact (PR #442, merged as 3291e2f8). E4 judges only commits reachable from origin's agent tip and NOT from origin's main. An agent tip that is itself on main — e.g. the instance's sync fast-forwarded its agent branch onto a forge web merge, GPG-signed by the forge — holds nothing beyond main and is adopted whoever signed it. This does NOT relax E4 for foreign commits: a commit beyond main that is not own-signed, accepted, or vouched by an own-signed merge still fails the create. Before #442 such a tip was wrongly refused because walkHistory never checked its stop set for the start commit (kb/gotchas/store/verify/e4-start-commit-not-stopped/e56919a1.md).

WHERE E4 LIVES NOW (re-pointed at the PR C merge ba59d2b2): checkOwnLineage is the exported verify.CheckOwnLineage in internal/store/verify/e4.go (formerly store/verify_e4.go); the parent's repoHandler.checkOwnLineage forward is gone. Create-time E4 is called from remotesync.InitFromRemote in internal/store/remotesync/bootstrap.go; InitSubscription and CloneFrom are in the same file. The history walk is vcs.WalkHistory (internal/engine/store/internal/vcs/history_walk.go; verify/walk.go keeps KeyFingerprint and the accept-list lookup). Own keys are set through Service.SetOwnKeys (service_verify.go), which forwards to vcs.Repo.SetOwnKeys. The tests named above still sit in package store (verify_e4_test.go, verify_e4_transitive_test.go, verify_e4_upstream_test.go). Older text naming checkOwnLineage or verify_e4.go describes the pre-split names.
