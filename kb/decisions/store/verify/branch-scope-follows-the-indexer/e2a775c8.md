# Verify checks parity only for branches the indexer maintains; every other refs/heads ref is reported once as informational, never as ERROR

# Verify's branch scope follows the indexer, not refs/heads

**Measured problem.** Run against a byte copy of a live 5-repo home (2026-08-12), `knomit verify --all` produced 8128 issues and ALL 8128 were on branches this instance does not index — 6762 on legacy `refs/heads/okf/*` export residue, 1366 on another machine's agent branch (`agent/Alexs-MacBook-Air-6.local-60def18b`) in `core`. Zero issues on any branch it does index. Exit code 1, permanently.

**Cause.** `listBranchRefsForVerify` enumerates EVERY `refs/heads/*` and demands full SQLite parity for each. `repoBuilder.setupIndex` maintains a strictly smaller set: `agentBranch` plus `upstreamMain`, and nothing else. Verify's model of "must be indexed" was strictly wider than the indexer's, so every correctly-unindexed ref became a wall of ERRORs.

**Options considered.**
1. Widen the indexer to index every local branch — rejected: the two-branch scope is deliberate (see `dropUnresolvableBranches`, and the per-branch schema-version heal), and foreign agent branches arriving by fetch would make index work unbounded.
2. Special-case `okf/*` in verify — rejected: treats the symptom. The foreign-agent-branch class is not legacy, does not age out, and would still produce false errors.
3. **Chosen:** make verify's branch scope follow the indexer's. Parity checks run only for maintained branches; every other `refs/heads/*` ref is listed once as informational, naming it, so an operator can still see it exists.

**Rationale.** An integrity tool that always reports failure gets ignored, which is strictly worse than not having one. Parity between SQLite and git is only an invariant for branches the index claims to maintain — asserting it elsewhere is asserting something the system never promised.

**Non-scope.** This does NOT mean unindexed branches are healthy or uninteresting. It means their SQLite parity is not an ERROR. A branch that IS maintained and shows drift is still an ERROR, and the `branches`-table check still fires both directions for maintained branches. It also does not authorize dropping the branches-table check's second direction (a `branches` row with no git ref remains an ERROR).
