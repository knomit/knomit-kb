# A knomit host does NOT re-judge a pushed branch's commits when MergeConsensus merges it on a USER knowledge base (user ruling R5, review F4 dropped): following git's trust model, a change accepted once at the gate is trusted; revocation is prospective there. The FLEET repository is the exception since #524: its master re-judges each local agent/* branch against the CURRENT main before every merge

The review's F4: a commit admitted at fleet revision R1 can reach main after the CRL lands at R2, because the pushed branch merges later (for example after a conflict is resolved). OPTIONS: (a) re-run judgeCommit for the branch's new commits inside MergeConsensus against the CURRENT fleet, moving authority to merge time as the D10 amendment did for dot paths: REJECTED by the user; (b) do nothing at merge time: CHOSEN, per the git trust model recorded in kb/decisions/store/verify/acceptance-only/14ef5ebb.md (a change is verified ONCE, where it advances a KB's main; nothing re-verifies history). Do not touch MergeConsensus for this.

CONSEQUENCES. Revocation is prospective: a commit signed while its leaf was valid is honestly signed, and the gate judges at the fleet revision it reads when the commit is received. On a forge `knomit verify ci` at merge time judges against the fleet revision it is given (--fleet-rev), which closes the window only if the workflow does not pin an old revision. The window on a knomit host is unbounded in time.

MISREADING: 'revoking a certificate stops every already-pushed branch' is wrong; it stops commits judged after the CRL is at the fleet revision the gate reads.

## UPDATE (PR #524, verified at merge commit 9db8c106): the fleet repository re-judges at merge time

On the fleet repository the consensus merger's gate (consensusMerger.runOnce with `admit`, fleetPeers.mayMerge) re-judges each local agent/* branch's `tip ∖ main` against the CURRENT main before merging it, memoised per (branch, tip, main). Main moving (a revocation, an issuance) changes the verdict: a branch admitted earlier and now refused is recorded (`last_refusal`, in memory) and DEMOTED (its local refs/heads/agent/<x> dropped, only while it is still at the judged tip) instead of merged; one refused earlier and now admissible is admitted. This holds on both hostings. It was added because the fleet master is the one process that merges (user ruling: the master merges), and because receive-pack judges only what a push SENDS: after a revocation, M(revoked member's admitted unmerged tip, main) pushed before demotion would show receive-pack only M. The merger's re-judge is what refuses it.

What stays true: for a USER knowledge base MergeConsensus still does not re-judge, and, as of PR #524, the operator's web merge (store.MergePushed) did not re-judge on the fleet repository either. SINCE PR #525 (verified at merge commit fd991d4f) it does: the merge route calls RepoInstance.FleetMergeRefusal, which refuses a non-master (409 `not_master`) and on the master re-judges the branch against the current main (JudgePeerBranch, tip minus main) and refuses with 409 `judge_refused`, so the window in which an operator could merge a head refused at the current main is closed. For a USER knowledge base the web merge still does not re-judge. For the fleet, 'revocation is prospective' now means: it applies to commits already on main; an admitted-but-unmerged branch is stopped at merge time.

Misreading: 'the master re-verifies history' is false; it re-judges `tip ∖ main` of branches that are not yet in main.
