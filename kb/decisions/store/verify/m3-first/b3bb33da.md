# Every two-parent merge runs checkM3 BEFORE the record rules, and a clean merge (tree equals the three-way merge of its parents) is admitted unsigned, with a verifying signature, or with a present-but-INVALID signature (user ruling H4/S2: it has no content of its own); a merge that fails M3 is judged like any commit when signed and refused `merge` when unsigned

Decided in PR #523 (merge commit 3ac59b57), design item H4 plus the user's ruling on review finding S2 (2026-10-15).

THE DECISION. judgeSigner (internal/store/verify_range.go) runs checkM3 first for every commit with two or more parents, before the signature check, the record rules, rule B and the owner rule. If M3 is clean (no error and verdict OK) the commit is ADMITTED in any signature state: unsigned, signed with a signature that verifies, or carrying a signature that is present but does NOT verify. If M3 is not clean: an unsigned commit is refused with rule `merge`; a signed one falls through to the signature check and the ordinary record rules, rule B and the owner rule, like any other commit. (The artifact rules still run after judgeSigner for every admitted commit, including a clean merge.)

WHY (user ruling): a clean merge's signature is not verified because the merge carries no content of its own beyond its parents, and stripping the signature would give the same verdict, so verifying it would protect nothing. The consequence the user accepted: a merge whose signature is corrupt is admitted exactly like an unsigned one. It is pinned so it is not forgotten: TestM3_CleanMergeWithABadSignatureIsAdmitted (CheckRange: the bad signature is asserted to be ErrBadSignature and the merge is admitted; control: the same broken signature on a DIRTY merge is refused `signature`) and TestReceivePack_CleanMergeSignatureStates (receive-pack: bad signature admitted and the branch created; a VERIFYING signature by boss pushed by rogue is `not-pusher`). Sabotage (refuse a clean merge whose signature does not verify) turns both red.

WHY M3 COMES FIRST (H4). A member's routine 'merge main into my branch' brings other members' changes in against main's side. Judged by the record rules and the owner rule it would be refused no-record or not-owner every time. M3 shows it adds nothing beyond its parents, so those rules have nothing to judge.

WHAT checkM3 GUARANTEES: the merge commit's tree equals the path-level three-way merge of its two parents over their single merge base (exactly one merge base is required; none or several mean a signature is needed). It compares EVERY non-tree entry on hash and mode: files, symlinks and gitlinks (submodule entries); an empty directory is skipped. A path both sides changed needs a signature.

WHAT IT DOES NOT GUARANTEE: it does not judge the PARENTS. In CheckRange (`knomit verify ci`) the parents are judged on their own because the fold walks candidate minus main. In receive-pack only commits the host does not already hold are judged (newCommits stops at held commits), so a clean merge of a held-but-unadmitted parent would pass. That is safe only while 'held by the host' means 'admitted', which holds on a knomit host because a refused push writes nothing (the receive-pack all-or-nothing invariant). Anything that lets a host hold objects the gate refused (for example fetched-and-refused tips, served by a receive-pack whose walk stops at them) breaks that assumption.

MISREADINGS. 'M3 means the signature does not matter for merges' is false for a merge that fails M3: it is judged like any commit and must verify. 'A clean merge needs no pusher check' is half true: a clean merge with NO verifying signature has no signer to compare, so signerIsPusher passes it, but a VERIFYING signature on a clean merge must still be the pusher's (`not-pusher`). 'M3 admits any merge whose content comes from its parents' is false for a malformed tree: judgeCommit refuses malformed-tree before M3, and checkM3's flatten fails on one (an error, never an early end).
