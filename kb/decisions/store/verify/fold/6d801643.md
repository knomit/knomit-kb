# F09's fold decides verification per commit from the repo's OWN history: a stricter policy change reaches every range commit except its own ancestors, a looser one reaches all, the final mode is never exempted, and merges are judged in the final context

`verifier.fold(anchor, actx, tip)` (internal/store/verify_fold.go) judges `tip ^anchor`, or the whole history from the root when anchor is ZeroHash (first contact). It is the design of proposal revision 5 section 7.2, as built and as corrected in review (#319):

1. SETTINGS come from each commit's own tree (`settingsAt`), through fact.OntologyPathsNewestFirst, via fact.ReadVerifySettings (root attributes only, through the registry validators). Unreadable or invalid is UNKNOWN, never off.
2. EACH COMMIT IS JUDGED AGAINST THE CONTEXT OF ITS OWN ANCESTRY: the anchor's context with the accepted changes among its ancestors applied in walk order (`inherited`, a sorted index list per commit). NOT one running context across the range: a change on one branch then makes a concurrent commit on a sibling look like it undoes it, and a legitimate log to enforce was refused depending on merge-parent order (review R3-1). NOT "differs from every parent": a merge could adopt a pre-enable ontology unjudged, leaving a file that says off while the fold enforces. A commit whose file disagrees with its ancestry context is a POLICY CHANGE, unless a parent carries the same file under the same context (then nothing new happened).
3. The CHANGE RULE: an enable, a relaxation and any verify_signers change need the OPERATOR (RootOfTrust); log to enforce needs an admitted signer or the operator. With no operator configured, a change needing one is UNROOTED: its commit is refused and the advance closes before it in every mode.
4. A REJECTED change refuses its whole commit when the final mode is enforce (RulePolicyChange), and is a Reported note otherwise, so no stranger can stall a repo that does not enforce.
5. REACH: a stricter accepted change (enable, log to enforce, signer removal) reaches every range commit except its own ancestors; a looser one reaches all. With an off anchor, a commit is CHECKED only if it is not an ancestor of an accepted enable. The MODE is never exempted: the final mode applies to every checked commit.
6. A non-merge is accepted when its SSHSIG verifies, its signer (full fingerprint) is admitted for that commit, and an author email fp8 claim, if any, matches CASE-INSENSITIVELY (review R3-2). The OPERATOR is always an admitted signer; an instance's OWN key never counts unless listed, so every instance computes the same anchor.
7. MERGES are judged in the final context: signed by an admitted signer or the operator, or M3 over parents that were accepted or are below the anchor.
8. --accept (verify_accepted) waives a failing SIGNATURE, or an unsigned merge that fails M3 (the criss-cross auto-merge shape, user decision D3-1 (a)). It never waives an unaccepted parent, a policy change or an author claim.
9. The NEW ANCHOR is the furthest first-parent commit whose whole range was accepted.

DOES NOT MEAN: that log mode lets a failing commit count as accepted. Modes differ only in where the local upstream goes (verify_gate.go); a failing commit is never accepted and the anchor never passes it.
