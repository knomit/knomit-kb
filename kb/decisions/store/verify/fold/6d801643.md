# F09's fold decides verification per commit from the repo's OWN history: a stricter policy change reaches every range commit except its own ancestors, a looser one reaches all, the final mode is never exempted, and merges are judged in the final context

`verifier.fold(anchor, actx, tip)` (internal/store/verify_fold.go) judges `tip ^anchor`, or the whole history from the root when anchor is ZeroHash (first contact). It is the design of proposal revision 5 section 7.2; the rules as built:

1. SETTINGS come from each commit's own tree (`settingsAt`), through fact.OntologyPathsNewestFirst, via fact.ReadVerifySettings (root attributes only, through the registry validators). Unreadable or invalid is UNKNOWN, never off.
2. A POLICY CHANGE is a commit whose settings differ from EVERY parent's. Each component is judged by the CHANGE RULE: an enable, a relaxation and any verify_signers change need the OPERATOR (RootOfTrust); log to enforce needs an admitted signer or the operator. With no operator configured, a change needing one is UNROOTED: its commit is refused and the advance closes before it in every mode.
3. A REJECTED change refuses its whole commit when the final mode is enforce (RulePolicyChange), and is a Reported note otherwise, so no stranger can stall a repo that does not enforce.
4. REACH: a stricter accepted change (enable, log to enforce, signer removal) reaches every range commit except its own ancestors; a looser one reaches all. The ancestor test uses git reachability, never the author's chosen parent alone, because ancestry is chosen by the author (a fork cut before an enable is checked; a key holder's commits merged before its removal stay valid).
5. With an off anchor, a commit is CHECKED only if it is not an ancestor of an accepted enable (the ancestors are the baseline). The MODE is never exempted: the final mode applies to every checked commit (a log-era failure is refused once enforce arrives).
6. A non-merge is accepted when its SSHSIG verifies, its signer (full fingerprint) is admitted for that commit (anchor signers + additions - removals it is not an ancestor of), and an author email fp8 claim, if any, matches. The OPERATOR is always an admitted signer. An instance's OWN key never counts unless listed: otherwise instances would compute different anchors.
7. MERGES are judged in the final context: signed by an admitted signer or the operator, or M3 over parents that were accepted or are below the anchor.
8. --accept (verify_accepted) waives a failing SIGNATURE only; the policy-change judgement runs first and is never waived.
9. The NEW ANCHOR is the furthest first-parent commit whose whole range was accepted.

DOES NOT MEAN: that log mode lets a failing commit count as accepted. Modes differ only in where the local upstream goes (verify_gate.go); a failing commit is never accepted and the anchor never passes it.
