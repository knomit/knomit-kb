# A remote's consensus branch is chosen by store.ChooseConsensusBranch: the request, else the remote's HEAD unless it is an agent/exp/okf branch, else the ONE other branch, else refuse. It replaced "prefer main, else HEAD, else main", and the clone, the subscription and the probe all call it

Decided under the user's ruling "Hardcoded values are never good" (fix/no-hardcoded-consensus-branch). Before, store.resolveUpstream preferred a remote branch named main whenever one existed (the #82 guard against a forge whose default branch was an agent branch). Otherwise it took the remote's HEAD, and then "main" when detection failed. repos/probe.go kept a hand-copied twin of that rule.

Now one pure function, store.ChooseConsensusBranch(requested, head, branches):
1. A requested name wins.
2. Otherwise HEAD, if HEAD names a fetched branch and store.IsRoleBranch(HEAD) is false. IsRoleBranch is true for agent/*, exp/* and generated okf refs.
3. Otherwise the single fetched branch with no other role.
4. Otherwise "": several candidates, or none.

The store (resolveUpstream, after the wildcard fetch, from refs/remotes/origin/* plus an ls-remote for HEAD) refuses "" with ErrNoConsensusBranch, naming HEAD and the candidates. The probe (repos/probe.go resolveUpstream) calls the same function on its ref listing, so the wizard shows what the create adopts (subscribeInspectBranch). For an EMPTY remote the probe answers requested-else-DefaultConsensusBranch, mirroring the seed path.

BEHAVIOUR CHANGES, stated:
- A remote holding main and trunk with HEAD on trunk now resolves to trunk (git's own meaning of the default branch). The old rule picked main.
- A remote whose HEAD is an agent branch and which holds two or more other branches is refused until a branch is named. The old rule picked main if present.
- The #82 case (agent-branch HEAD, one other branch) is unchanged.

Tests: TestChooseConsensusBranch (table), TestResolveUpstream_HeadNotMainByName (a bare remote with main+trunk, HEAD→trunk, clone and subscription both land on trunk with a non-zero tip), TestResolveUpstream_UndecidableIsRefused, TestProbeOrigin_HeadNotMainByName. lifecycle_subscribe_test's distinguishing fixture is now seedBareRemoteHeadIsAgentBranch (HEAD agent/other-host without an ontology, trunk is the KB), because a HEAD-on-develop, main-is-KB remote is no longer a case where the two rules differ.

Sabotage: restore the prefer-main step in the store or the probe, and the main+trunk tests go red.

MIXED-VERSION FLEET (reviewer N2, non-blocking, #362): the rule decides only when a repo is CREATED from a remote, and the result is recorded. A peer that cloned or subscribed with an older binary adopted main (the prefer-main rule). A peer that clones now with no branch named follows the remote's HEAD. On a remote holding both main and another branch with HEAD on the other one, the two peers therefore track different consensus branches, and nothing reconciles them. Existing repos never re-resolve: their recorded or origin branch stands. CONSEQUENCE: on such a remote, name the branch explicitly when a new peer joins (OriginSpec.Branch / the wizard's branch step), or set the forge's default branch to the one the existing peers use.
