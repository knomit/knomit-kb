# OKF bundles regenerate lazily during ref advertisement, for main plus the local agent branch only

Options considered for the trigger: lazy on fetch; eager on every fact write; explicit CLI/API only; lazy plus an explicit rebuild command. Options considered for branch coverage: main only; every local branch; main plus the local agent branch.

Rationale: eager generation hooks the fact write path and does work nobody may ever fetch. Explicit-only hands an external consumer a clone URL that silently serves stale knowledge — a bad artifact given the whole point is external consumption. Lazy generation is never stale, touches no write path, and at knomit's object counts costs sub-second work only on the first fetch after a burst of writes; a stored marker makes the common case one comparison and zero work. The separate explicit-rebuild command was rejected as unnecessary surface once the marker keys on mapper version as well as source SHA, since a mapper change then invalidates and regenerates automatically. Every local branch was rejected because it publishes half-finished agent knowledge to anyone who clones and makes each advertisement check N bundles; main alone was rejected because a local user pointing a tool at their own live knowledge needs their own agent branch.

The choice: EnsureOKF runs from the path in internal/store/httphandler.go that already calls AdvertisedReferencesContext before every fetch, covering `main` and the local agent branch. The marker lives in internal/store/git/kv.go keyed as (source SHA, mapper version) → OKF SHA.

Critical failure behavior: EnsureOKF returning an error is logged and metered, then advertisement PROCEEDS — serving the previously generated OKF ref if one exists, or omitting it if none was. A broken mapper must never make a knomit repo unclonable.

Non-scope: lazy generation is not a promise of freshness for consumers who never fetch, and covering the local agent branch does not authorize publishing other machines' agent branches.
