# OKF refs use snapshot+stable-parent-chain, built on a deterministic per-commit mapper so mirror mode is an added caller

Options considered: (a) a single snapshot commit regenerated per fetch — cheapest, but every regeneration is a fresh root commit, so pulling twice yields unrelated histories and forces downstream force-pushes; (b) snapshot chained onto the previously generated OKF commit — clones fast-forward cleanly, requires storing the last generated commit; (c) mirror knomit's history by replaying each source commit as an OKF commit — highest fidelity `git log`/`blame` and the best log.md.

Rationale: CPU is not the obstacle to mirroring. Measured on the largest local store (core.db): 2062 commits, 8438 trees, 1679 blobs, 12179 objects — an incremental oldest→newest replay applying per-commit tree deltas is a seconds-to-minutes one-time, resumable backfill. The real obstacle is knomit's own history semantics: branch_merge.go produces merge commits (mappable) and remote_reconcile_rebase.go rewrites history, which orphans mapping entries and forces a non-fast-forward rebuild for every downstream consumer. Entangling the first OKF release — judged on bundle conformance, not on git log — with rebase-reconcile edge cases is the wrong risk to take first.

The choice: ship (b), with the mapper factored as a deterministic commit-scoped function (fixed author/committer identity `knomit okf-mapper`, timestamps taken from the source commit, never time.Now()), so the same source commit and mapper version always yield a byte-identical bundle and identical OKF commit SHA. Mirror mode later is turning on a history walk over that same function, not a redesign. Accepted cost, to be announced if taken: flipping snapshot→mirror chains parents differently and therefore rewrites the OKF ref once.

Non-scope: determinism here is per mapper version, not forever — a mapper change legitimately changes the output SHA, which is why the marker stores the mapper version.
