# OKF export is per-repo and export-only in v1; lenses are explicitly out of scope

Options considered: (a) export only, knomit→OKF; (b) export now with a deliberately round-trippable mapping so an OKF→knomit importer is a later non-breaking addition; (c) both directions in v1; (d) import first. Separately for the unit of export: per-repo only vs also exporting a lens as an OKF bundle (flat merge of the lens's write repo + N read repos, with knomit_repo provenance and cross-repo slug collision handling).

Rationale: the stated bar is that a real OKF ingester (Google's knowledge-catalog tooling) accepts our bundle unmodified, with conformance as the checkable proxy. That bar is fully satisfied by a per-repo bundle. Exporting a lens would require inventing lens-as-a-git-repo — a capability knomit does not have — through the OKF door, letting an OKF-shaped decision silently become knomit's answer to "what is a lens, materialized?". Lens-as-git-export deserves its own design (clone URL, object storage, behavior when a read mount is removed). Dropping lenses also dissolved the storage-location question entirely: with repos only, generated bundles live in the repo's own store and the existing /{repo} git endpoint serves them unchanged — no sidecar stores, no new routing, no merge/collision policy, no provenance frontmatter.

The choice: v1 exports a single knomit repo to an OKF bundle. The mapper is written to take a set of facts at a tree rather than a repo, so a lens caller is an added entry point later, not a redesign. Import is not built, but the mapping is kept round-trippable (see okf/frontmatter-mapping) and a round-trip test guards that promise before an importer exists.

Non-scope: this does not decide that lenses will never be exportable, nor that import will never be built. It decides only that neither ships in v1, and specifically that OKF must not be the feature through which lens-as-git-repo gets invented.
