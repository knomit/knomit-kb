# OKF type maps from the topic, not the leaf fact.Type

In the OKF exporter, the OKF `type` frontmatter field (OKF v0.1's ONLY required key — 'what this document is') maps from the fact's TOPIC (the first path segment under kb/), singularized, NOT from the fact's leaf `fact.Type`. Options considered: (a) map from leaf fact.Type verbatim — faithful but knomit's leaf types are a thin controlled vocabulary (observation, concept, process, principle, pattern, reference, synthesis, insight, hypothesis, methodology, policy, heuristic) dominated by 'observation'/'policy', producing a conformant-but-useless required field where ~80% of docs read 'observation'; (b) map from the topic (invariant, decision, gotcha, convention, principle, incident, architecture, meta) — knomit's real primary classification and legible to an external OKF consumer, matching the spec's category-of-thing example ('BigQuery Table'); (c) a composite like 'decision/principle' — non-obvious value no consumer predicts. Chose (b). The leaf fact.Type is preserved verbatim in a `knomit_type` frontmatter key for round-trip; the importer treats knomit_path (topic) and knomit_type (leaf) as authoritative and NEVER re-derives the leaf from OKF `type`. Singularization is an explicit table over the eight known topics (architecture and meta unchanged), with a strip-trailing-'s' fallback for unknown future topics. This does NOT mean the leaf type is discarded — it is round-trip-preserved in knomit_type; and it does NOT mean OKF `type` is free text — it is a deterministic function of the immutable topic path. Decision made 2026-07-24 during implementation when fact.Type was found to be a validated enum (epistemic/pragmatic leaves), invalidating the earlier design examples that listed decision/invariant/gotcha as `type` values. Implemented in internal/okf/concept.go (okfType + singularTopic). Relates to [[okf-frontmatter-mapping]].
