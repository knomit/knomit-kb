# OKF frontmatter carries meaning in standard keys, knomit specifics in knomit_* — type maps from the TOPIC, leaf type preserved in knomit_type

CORRECTION (2026-07-24, superseded by [[okf-type-from-topic]]): this fact originally stated OKF `type` maps from knomit's leaf `type` verbatim. That was WRONG. fact.Type is a validated enum (epistemic leaves observation/concept/process/principle/pattern/reference/synthesis/insight/hypothesis/methodology; pragmatic leaves policy/heuristic) — 'decision'/'invariant'/'gotcha' are TOPICS, not leaf types. OKF `type` maps from the singularized TOPIC; the leaf fact.Type is preserved in knomit_type for round-trip. The rest of this fact stands.

Options considered for the required OKF `type` field: the singularized topic (invariant/decision/gotcha/...) vs knomit's leaf `type` (observation/policy/...) vs knomit's `kind` (epistemic/pragmatic) vs a namespaced value like "knomit:decision". For knomit-specific metadata: encode into tags/body, drop it, or use OKF's explicitly permitted custom frontmatter keys. For the recommended `description` key, which has no source field in knomit: synthesize from the body's first sentence; omit it; duplicate the title into it; add a first-class summary field to knomit's fact format; or keep first-sentence guarded by a discourse-marker blocklist. For file naming: flatten the trailing <slug>/<uuid8>.md into <slug>.md with the uuid8 appended only on collision; or preserve the directory structure and name the file from the truncated title + uuid8; or from the category slug + uuid8; or uuid8 alone.

Rationale: OKF's `type` is a descriptive string for the kind of thing a document is (the spec's example is "BigQuery Table") — the topic (invariant/decision/gotcha) matches that far better than the thin leaf vocabulary dominated by 'observation'/'policy'. epistemic/pragmatic is an axis describing how a fact is USED, not what it is, so it belongs in tags and knomit_kind. The spec permits producer-defined keys and requires consumers to tolerate unknowns, which makes knomit_* the correct channel for the leaf type plus confidence/sources/origin/kind/evidence_weight/domain/entities/refs/path — and that same block is what makes the deferred OKF→knomit importer possible, since a foreign bundle lacking it still imports with defaults. knomit refs are code anchors (file:line) and the spec has a named `# Citations` section for exactly that, so putting them there also means a human reading the bundle on GitHub sees them (the machine round-trip copy is knomit_refs).

On `description` specifically: its job in OKF is progressive disclosure — it is the one line in index.md that a reader or ingester uses to decide whether to open a document — so a wrong value routes consumers wrong. Synthesizing it from the body's first sentence fails structurally, not occasionally: the /knomit-decided skill mandates an "Options considered: ..." opening, so every fact under the decisions/ topic would advertise itself with a list of mostly REJECTED options, conveying roughly the opposite of what it decided. Duplicating the title was rejected because identical title and description in index.md reads as broken tooling; a guarded first-sentence heuristic was rejected as unpredictable per fact with a fragile marker list. The genuine gap is that knomit facts have no authored summary distinct from the title; adding one is the right long-term fix and would serve knomit's own UI and search too, but it changes the core fact format and the learn path and must not gate OKF export.

On file naming: the flatten-and-collide scheme was proposed first and rejected as defective on two counts. It destroyed a real ontology level — a category directory like lens/reject-replica-mounts/ can legitimately hold more than one fact, since nothing in BuildFactPath reserves the last path segment for a single fact — and it made a document's filename CONDITIONAL ON ITS SIBLINGS: adding an unrelated second fact to a category would rename the first one, breaking every external link to it. Identity in a published artifact must never depend on what else exists around it. Title-slug was chosen over the immutable category slug because the filename then carries information the parent directory does not, which is what makes the bundle readable on GitHub; the accepted cost is that titles are mutable (knomit_update accepts a new title while the topic/category path is immutable), so rewording a title renames the exported file — internal bundle links regenerate together and stay correct, but external references to the old path break.

The choice: type←the singularized TOPIC (NOT the leaf fact.Type — see [[okf-type-from-topic]]); leaf fact.Type←knomit_type (round-trip); title←the body's `# Heading`; description←OMITTED in v1 (recommended, not required, so omission is fully conformant — index.md entries carry title + type, and knomit titles are already serviceable one-liners); resource←`knomit://<repo-id>/<fact-path>`; tags←domain + entities + kind; timestamp←authoring commit time; knomit_* ←type(leaf), kind, confidence, sources, origin, evidence_weight, domain, entities, refs, path. Refs render as a `# Citations` section in the body, with knomit_refs as the machine round-trip copy.

Tree shape: kb/ is dropped as the bundle root and every topic and category segment below it maps one-to-one — the knomit directory structure is preserved verbatim. Only the filename changes: slugified truncated title + `-<uuid8>.md`, with the uuid8 ALWAYS present, never conditionally. Slugification is a pure function of the title with no collision-dependent branching (the uuid8 already guarantees within-repo uniqueness): lowercase, fold to ASCII, collapse runs of non-[a-z0-9] to a single hyphen, trim hyphens; truncate to 60 chars at the last hyphen boundary at or before 60, never mid-word, hard-cutting at 60 only if the first word alone exceeds it; append -<uuid8>.md; if the slug comes out empty (a title of pure punctuation or non-Latin script) fall back to the category's last path segment, and to the uuid8 alone if that is empty too.

resource deliberately uses repo ID, not repo name (names are per-machine aliases) and deliberately is not an HTTP URL: baking the request host into blobs would make identical knowledge produce different commit SHAs on localhost versus a hosted instance, breaking the determinism the marker depends on.

Non-scope: this does not authorize inventing further knomit-flavored extensions beyond the knomit_* block — every standard OKF key must carry its standard meaning, because the acceptance bar is a foreign ingester. Omitting description is a v1 call justified by the absence of a summary field, NOT a claim that descriptions are unwanted: if knomit facts ever gain an authored summary, it maps straight to description. And preserving the directory structure verbatim does not mean exported filenames are stable — they track the title.
