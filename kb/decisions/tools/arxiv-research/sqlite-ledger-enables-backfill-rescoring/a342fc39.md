# arxiv-research keeps every harvested abstract in a SQLite ledger keyed by profile_version, so changing the interest profile re-scores the back catalogue offline

**Options considered.** (a) Plain Python with file targets — implement Luigi's one load-bearing idea ("output exists, skip the stage") in ~15 lines. (b) Luigi. (c) Prefect. (d) Plain Python with a SQLite ledger.

**Rationale.** Luigi and Prefect were rejected on cost/benefit: the DAG is linear with one fan-out at fetch, Luigi is maintenance-only upstream, and Prefect's value (UI, scheduling, run history) wants a server this job does not need. The real contest was between file targets and a ledger.

The ledger wins on a capability file targets cannot offer. The funnel's known weakness is a keyword blind spot: work phrased unexpectedly never reaches stage 2, and there is no way to tell what was missed. Because every abstract ever harvested is retained in `papers` and every score is stamped with `profile_version` (a hash of `profile.toml`), changing the profile allows re-scoring the entire back catalogue with no network access and diffing against what the old profile caught:

    "what would today's profile have caught that last month's missed?"  -> one SELECT

That removes the need for a periodic full-firehose audit pass, which was the alternative mitigation. Rejections become queryable for the same reason: why was a paper dropped, and under which profile version.

**The choice.** SQLite at `$WORKDIR/ledger.db` with tables `papers`, `scores` (PK paper_id+profile_version+stage), `fetches`, `verdicts`, `runs`. Stdlib `sqlite3`; schema migrations are owned by the job.

**Non-scope.** The ledger is PIPELINE state only. The agent has no tool that can reach it, and knowledge facts never live there — they go to knomit via MCP. The ledger is not a second corpus.
