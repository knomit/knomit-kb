# Bridge-quality tuning is a `calibrate bridges` cobra subcommand (dev-only), not runtime telemetry

Options considered: (a) a new standalone tools/ binary for the bridge eval; (b) reuse+enhance tools/calibrate into a cobra+viper root with subcommands (`calibrate embeddings` = today's threshold porting, `calibrate bridges` = new); (c) a subcommand on the shipped knomit binary.

Rationale: both operations DERIVE a tunable from the corpus distribution — `calibrate` ports retrieval thresholds by preserving percentiles, and `calibrate bridges` derives cohFloor/qualityFloor from the corpus cohesion/Q distribution the same way — so bridges genuinely IS calibration, which is why it belongs under `calibrate` rather than a separate 'eval' binary. The project keeps dev/diagnostic tools in tools/ (not cmd/, the shipped binary); tools/drone is the existing cobra+viper precedent. `calibrate bridges` needs NO ONNX/ORT libs because it reads precomputed SIMILAR_TO/clusters, unlike `calibrate embeddings`. An earlier idea — runtime outcome telemetry in a persisted `bridge_outcomes` table — was REJECTED: the sessions DB is ephemeral so it has no durable home, and the data only serves development (no real knomit consumer), making it dev scaffolding, not a product feature.

Choice: restructure tools/calibrate into a cobra+viper root; migrate the existing threshold logic to `calibrate embeddings`; add `calibrate bridges` (per-bridge component report + cohFloor/qualityFloor derivation). Dev-tool only — no runtime telemetry, schema, or storage added to the product. Tunes the mechanism in decisions/synthesize/bridge-quality-mechanism.
