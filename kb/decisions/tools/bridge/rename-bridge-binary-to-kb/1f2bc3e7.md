# The bridge EXECUTABLE is named `kb`; `knomit-bridge` stays as the program's descriptive name (header, User-Agent, log file) — no compatibility alias

## Options considered

1. Keep `knomit-bridge` as the binary name.
2. Rename to `kb` and ship `knomit-bridge` as a compatibility alias for at least one release: both names in dist and in the desktop app's bin link, `IsKnomitCommand` accepting both basenames, init rewriting or tolerating old commands in existing .mcp.json / settings.json.
3. Rename everything — executable, help, User-Agent, log file, error prefixes — to `kb` in one step.
4. Rename ONLY the executable file to `kb` and keep `knomit-bridge` as the descriptive program name everywhere that nobody types.

## Rationale

`kb` won because the binary is the user-facing entry of every integration, and the catchiness pays exactly where the name is typed or copied: the MCP `command` in .mcp.json, the hook commands in settings.json, `kb claude init` in install instructions. "bridge" names an implementation detail. `kb` also matches the corpus root `kb/`, the `kb://` ref scheme and the knomit-kb repo.

The compatibility alias (option 2) was rejected by the designer on 2026-09-18: there is one primary user who owns every installed configuration and updates them by hand; a compat window would double the surface in `IsKnomitCommand`, the desktop bin-link installer and the init merge for nobody's benefit.

The full rename (option 3) was narrowed by the designer to option 4: "the header and everything else can stay knomit-bridge, including the help printed from the command line. I just want the name to be more catchy." The one refinement accepted on top of that: usage LINES in help show `kb` because a user copies them, while the header may still say the program is knomit-bridge.

What cannot stay: anything that names the file on disk. The templates `init` writes, `IsKnomitCommand` (init's idempotence check — compares the command basename, so a stale name makes a re-run of init ADD a second server and duplicate hooks), `bridgeExecName` in the desktop app (the bundle lookup and the <home>/bin link name), the Makefile outputs/codesign/package copies and `.gitignore`.

Known consequences accepted:
- Existing installs' configs spelling `knomit-bridge` stop launching and stop being recognised by init. The fix is to update the configs, not the code.
- `kb` is a two-letter name on a global PATH; a Python package also installs a `kb` command. Accepted.
- "the kb" already means the corpus in facts and docs; the tool now shares the word. Accepted.
- Repos outside this one (OpenClaw plugin, docs site, knomit-kb facts) still spell `knomit-bridge` and need a separate sweep.

## The choice

The executable is `kb` (`kb.exe` on Windows). MUST follow the file: Makefile build outputs, symlink_tool, macOS bundle path + codesign, server package, AppImage, `.gitignore`, `bridgeExecName`, `IsKnomitCommand`, all six claude/antigravity templates, this repo's committed `.mcp.json` and `.claude/settings.json`, and the tests asserting on those strings. SHOULD follow: usage lines and examples in `main.go` help and the `usage:` strings of the hook subcommands, plus the READMEs. STAYS `knomit-bridge`: the help header's descriptive name, User-Agent, `bridgelog` default file name, error prefixes, comments, Go identifiers, Makefile target names, the `tools/bridge/` directory.

## Non-scope

Does not rename `knomit`, `knomit-okf`, `knomit-desktop` or the `tools/bridge` directory. Does not authorise init to migrate existing user configs. Does not authorise renaming the User-Agent or log file later "for consistency" — the designer explicitly kept those.
