# Decided (knomit#301, 2026-09-26): the data root is made PRIVATE TO THE USER at boot on every platform by one helper (internal/platform/privdir.Ensure): unix creates it 0700 and warns if wider; Windows sets a protected owner+SYSTEM DACL with inheritance when the existing DACL is purely inherited, warns and continues when it cannot; per-file ACLs at each write site and refusing to boot were rejected

**Context.** knomit.toml (can hold an LLM API key) had no Windows permission test, and the survey behind knomit#301 showed the class: nothing in the tree sets a file or directory ACL on Windows, every 0600/0700 is a no-op there except the read-only bit, and a KNOMIT_HOME outside the profile inherits Users:RX and Authenticated Users:M onto the instance's unencrypted SSH private key, the bridge's OAuth tokens, known_hosts and control.db backups as well. The unix '0700 data root' that config.go and paths_unix.go cite was never enforced either; it was a side effect of ensureKeyPair's MkdirAll at first boot. This is about WHO CAN READ the root once it is resolved; kb/gotchas/config/home/windows-drive-root is about WHERE the root resolves to, a different question on the same directory.

**Options.** (a) Per-file security attributes at every secret write site: many sites, and the tree's temp-file-plus-rename pattern REPLACES the target's DACL with the temp file's inherited one (measured), so each site would also have to protect its temp file; brittle and incomplete. (b) Refuse to boot when the root is not private: a FAT/exFAT volume or a share without ACL support would brick a previously working install over a filesystem quirk. (c) Do nothing outside the profile and document it: leaves the private key world-readable on exactly the installs that chose a custom root. (d) CHOSEN: one boot-time helper on the DIRECTORY, called from the shared boot wiring (app.New: serve, verify, desktop) and from the bridge's credentials-directory creation (kb login can run before any server boot). Windows applies `D:P(A;OICI;FA;;;<user>)(A;OICI;FA;;;SY)` with PROTECTED_DACL_SECURITY_INFORMATION only when the current DACL is NOT protected (an already-protected DACL is treated as deliberate and left alone); OICI inheritance makes every child, temp files included, owner+SYSTEM only, which is what closes the rename problem for every write site at once. Failures are logged warnings, not errors. Unix: MkdirAll 0700, warn on a wider existing directory, never chmod what the user set.

**Why owner+SYSTEM and not Administrators.** The owner must be in the DACL or keeps only READ_CONTROL|WRITE_DAC and cannot read its own data; SYSTEM is needed for services, backup and AV; Administrators can take ownership regardless (SeTakeOwnershipPrivilege), so listing them buys nothing and omitting them costs nothing. No DACL defends against a local Administrator; that is out of scope and stated.

**What this does NOT mean.** The atomic writes (writeConfigFile, SaveCredentials, pki.writeFileAtomic) are unchanged and still set POSIX modes that Windows ignores; their privacy on Windows comes from the root's inheritance, not from the mode. A client_secret_file placed OUTSIDE <home> is still the user's responsibility on Windows (the gated mode check in oauth_idp.go stays gated). A Windows test of file privacy must use a parent with a deliberately BROAD DACL: t.TempDir() is under the profile and inherits owner-only, so a naive test is green on code that does nothing.
