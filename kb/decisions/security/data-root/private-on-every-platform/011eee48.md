# Decided (knomit#301, 2026-09-26): the data root is made PRIVATE TO THE USER at boot on every platform by one helper (internal/platform/privdir.Ensure), called at each entry point before the first write and again in app.New as the backstop: unix creates it 0700 and TIGHTENS an existing wider root it owns (warns when it does not own it); Windows sets a protected owner+SYSTEM DACL with inheritance when the existing DACL is purely inherited, leaves a protected one alone but WARNS if it grants anyone else or is owned by someone else, and never rewrites when running as a service SID; per-file ACLs at each write site and refusing to boot were rejected

**Context.** knomit.toml (can hold an LLM API key) had no Windows permission test, and the survey behind knomit#301 showed the class: nothing in the tree sets a file or directory ACL on Windows, every 0600/0700 is a no-op there except the read-only bit, and a KNOMIT_HOME outside the profile inherits Users:RX and Authenticated Users:M onto the instance's unencrypted SSH private key, the bridge's OAuth tokens, known_hosts and control.db backups as well. The unix '0700 data root' that config.go and paths_unix.go cite was never enforced either: review found the root is created 0755 BEFORE app.New on every fresh serve (crashdump marker, marker.go:39) and desktop install (installBridgeTool's <home>/bin, bundled.go), and by warm-models and the Docker COPY; ensureKeyPair's 0700 MkdirAll only ever found it already there. This is about WHO CAN READ the root once it is resolved; kb/gotchas/config/home/windows-drive-root is about WHERE the root resolves to.

**Options.** (a) Per-file security attributes at every secret write site: many sites, and the tree's temp-file-plus-rename pattern REPLACES the target's DACL with the temp file's inherited one (measured), so each site would also have to protect its temp file. (b) Refuse to boot when the root is not private: a FAT/exFAT volume or a share without ACL support would brick a working install. (c) Do nothing outside the profile: leaves the private key world-readable on exactly the installs that chose a custom root. (d) Warn-only on unix (the first draft): review showed it would warn on EVERY boot of every existing macOS/Linux install and every Docker container, forever, because their roots are 0755 from the writers above. (e) CHOSEN: one helper on the DIRECTORY, called at each entry point before the first write (serve before the crash marker, desktop before installBridgeTool, warm-models before the download, the bridge before its credentials dir) and in app.New as the backstop. Unix: MkdirAll 0700; an existing wider root OWNED by the current euid is chmod'd to 0700 with one Info line on the boot that changes it (knomit's own directory, and the contract the comments already claimed); a wider root NOT owned by us is warned about and left alone. Windows: `D:P(A;OICI;FA;;;<user>)(A;OICI;FA;;;SY)` with PROTECTED_DACL_SECURITY_INFORMATION when the DACL is purely inherited; OICI makes every existing and future child, temp files included, owner+SYSTEM only (propagation to existing children measured), which closes the rename problem for every write site at once. Failures are logged warnings, not errors.

**Guards added by review (Windows).** (1) A PROTECTED existing DACL is left alone but WARNED about when it grants any SID other than the user and SYSTEM, or holds an ACE type whose SID cannot be read: the attack is a KNOMIT_HOME under C:\ pre-created by another local user with a protected DACL naming themselves; silent acceptance would hand them the key files. (2) The OWNER is checked: not the user, SYSTEM or BUILTIN\Administrators → warn (an owner keeps implicit WRITE_DAC and can re-grant themselves whatever the DACL says). (3) Running as a service SID (S-1-5-18/19/20) never rewrites: a SYSTEM-only DACL would lock the interactive user out of a home they share with the service; that was the one real lockout path.

**Why owner+SYSTEM and not Administrators.** The owner must be in the DACL or keeps only READ_CONTROL|WRITE_DAC and cannot read its own data; SYSTEM is needed for services, backup and AV; Administrators can take ownership regardless (SeTakeOwnershipPrivilege), so listing them buys nothing. No DACL defends against a local Administrator; out of scope and stated.

**Behaviour changes to know.** Windows first boot re-propagates the DACL to every existing child synchronously inside boot (repos/, models/), a one-time cost proportional to the tree; any account other than the user and SYSTEM (another admin, a backup agent's service account, a second account sharing a KNOMIT_HOME) loses DACL access on that boot. Unix: an existing 0755 root owned by the user becomes 0700 on the next boot with one log line.

**What this does NOT mean.** The atomic writes (writeConfigFile, SaveCredentials, pki.writeFileAtomic) are unchanged and still set POSIX modes that Windows ignores; their privacy on Windows comes from the root's inheritance. A client_secret_file placed OUTSIDE <home> is still the user's responsibility on Windows. The desktop's state dir under %LOCALAPPDATA%\knomit (outside <home>) and the master root key's directory are not covered. A Windows test of file privacy must use a parent with a deliberately BROAD DACL: t.TempDir() is under the profile and inherits owner-only, so a naive test is green on code that does nothing. And a test that calls privdir.Ensure itself proves the mechanism, not that a call site applies it: the call sites have their own tests.
