# Components that are unit-correct fail as a SYSTEM on the second session, or the fifth, or the one after an edit — test the SEQUENCE, not the function

**The claim.** For any component holding state across invocations — a cache, a budget, a throttle, a watermark — unit correctness of every function is compatible with total system failure, and the failure shows up on session N, not session 1.

**The evidence.** EVERY blocking defect found in the Phase-0 review lived in cross-session behaviour rather than in any single function: a budget scaled by the wrong quantity, a cache frozen by a premature coverage marker, a throttle that latched shut. Three MORE were found by the dynamics suite while it was being written. Not one was reachable from a single-call test.

**The practice.** Write tests that drive 4–6 real sessions with partial budgets, judge verdicts, and fact edits interleaved between them — and assert on the state at the END of the sequence, not after each step. The point is to let a premature marker or an unconsumed counter accumulate until it is visible.

**What it catches that unit tests structurally cannot.** Any bug whose precondition is "a previous session already wrote state". A unit test constructs its own preconditions, so it can only exercise the states the author thought of; a session sequence produces the states the CODE actually reaches.

**Scope.** This is for stateful, multi-invocation components. It is not a blanket demand that every test become a sequence.

Applied again in the motif phases (`motif_dynamics_test.go`): a motif written in session N surviving dedup-merge in N+1, df counting live paths rather than edit churn, the subject strip holding on every write rather than the first.
