# A src:// ref is server-unverifiable, so a fabricated one rots silently — compute every component with git, never transcribe from memory, and `git cat-file -e` is the free check

The knomit server holds no source objects, so it CANNOT check that a `src://<repo-id>/<path>@<commit>:<blob>` ref names a real object. Local `kb/` refs are checked on write and a bad one rejects the whole call. For src refs, refs.Gate checks only FORM (knomit#249): a newly added src ref must be the full 12-hex/40-hex/40-hex form, so a placeholder, a dropped `:blob` or an abbreviated hash is refused. An invented but WELL-FORMED 40-hex hash is still accepted silently — that is exactly the fabrication below, and exactly what no syntactic check can catch. It then rots with no signal: the next reader's `git cat-file` fails, and nothing says whether the file moved, the commit was rewritten, or the hash was never real. (A 2026-09-24 audit of knomit-kb found three such invented blobs in two facts, e.g. `b1cff6b5b8ba9bd8b2b0e1a9a0c8c0e0e0b0a0d0` — a pattern no git object has — plus one ref with the wrong path. All four were repaired.)

**The rule.** Compute all three components with git, in the checkout you are citing, at the moment you write — `git rev-list --max-parents=0 HEAD | cut -c1-12` (repo id), `git rev-parse <commit>` , `git rev-parse <commit>:<path>` (blob). Never transcribe one from memory, from an earlier fact, or from a nearby ref that 'looks right'. Then verify: `git cat-file -e <hash>` costs nothing and is the whole check.

**The observed failure (knomit, 2026-08-26, #67 close).** Writing a decision update, I ran `git rev-parse` for three of four files and INVENTED the fourth blob hash. Nothing rejected it. It was caught only by re-reading my own tool call afterwards; `git cat-file -e` confirmed the object had never existed, and the refs list was corrected in a follow-up revision. I then re-verified ALL five cited objects — including the three I believed I had computed — because at that point my belief about which ones I had computed was exactly the thing that had just proven unreliable. It recurred on 2026-09-22 (knomit#249) while re-pinning the F19 phase 1 experiment: a placeholder typed where a blob belonged, caught only by mechanically re-verifying all 17 refs.

**Why it happens, and where else to expect it.** The fabrication rode in on a batch where most refs WERE computed; being mostly-right is what made the gap invisible. This is the same shape as the cheap-check-skipped-under-confidence family: the moment you feel settled is the moment the free verification gets dropped. Expect it specifically when writing several refs at once, when updating a fact whose other refs you are copying forward, and when the fact is otherwise finished and the refs feel like paperwork.

**What the #249 gate does NOT mean.** It does not mean a src ref that got through is real. The gate cannot see the source repo; an existence check was deferred (decisions/refs/src-ref-gate-new-refs-only). `git cat-file -e` is still the only check that catches an invented hash.

**Scope note.** `refs` on knomit_update REPLACES the entire list rather than merging, so a partial resend silently DROPS refs you meant to keep — read the current refs first and resend the full merged list. That is a second way a refs edit fails quietly, and it fails in the opposite direction: not a bad ref added, but good ones removed.
