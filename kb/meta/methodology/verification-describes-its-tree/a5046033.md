# A verification result describes the TREE it ran against, not the branch — any revert, amend or partial stage AFTER the run silently invalidates it, so verify at the pushed SHA in a clean tree and quote that SHA beside the output

A green suite certifies the bytes on disk at the moment it ran. It says nothing about the commit you push afterwards, and nothing in the output carries the identity of the tree it saw — so a report quoting real, honest, green output can describe a tree that was never pushed and no longer exists.

CONSEQUENCE to act on, on both sides of a review:

- AS AUTHOR: run the verification at the PUSHED SHA, in a clean tree, and quote that SHA next to the outputs. If anything touches the working tree after the run — a revert of one file, an amend, a rebase, a stash pop, a partial `git add -p` that leaves half a change behind — the previous result is void and the run must be repeated. Order matters more than effort here: verifying last is the whole discipline.
- AS REVIEWER: a verification claim with no SHA is unverified. Re-run it yourself at the head the PR actually points at, taken from `gh pr view --json headRefOid` and the remote ref.

THE INCIDENT (knomit PR #217, first round, 2026-09-17). The author ran the full suite green, then ran a commit step that BEGAN with `git checkout HEAD -- internal/mcp/client_sessions_hook_test.go`, to keep that file's pre-existing gofmt difference out of the commit. That revert ran AFTER the green suite and discarded three `store.List` call-site fixes along with the formatting. The pushed head failed `go vet ./internal/mcp/` on the first command a reviewer ran — "assignment mismatch: 2 variables but store.List returns 3 values" — while the report said build and vet clean, 46 packages green. Both statements were true about a tree that was never pushed. Nothing in the process compared the verified tree with the pushed one, because nothing was watching for a difference.

WHY IT WAS ARMED, which is the part worth generalising: that file had been excluded from THREE consecutive PRs, each time to keep its pre-existing gofmt noise out of a diff. The workaround became reflex, and the reflex ran after the tests. The repair was not to re-add the three-value form but to make the file gofmt-clean in a commit of its own, so there is nothing left to exclude. A workaround applied three times is a signal to fix its cause; carried a fourth time it will eventually run at the wrong moment.

THE SAME FAMILY, and the discipline is one discipline: a verification claim must rest on something the other side can independently reach. An intermediate commit from your own rebase proves nothing to a reviewer who cannot fetch it, and a SHA quoted from your own earlier scrollback is stale the moment you amend. Beware a shared checkout here — `git rev-parse` can resolve an unpushed commit for a reviewer whose worktree shares an object store with the author's, which makes an unreachable ref LOOK reachable and hides exactly this class of error; a reviewer on another machine would fail immediately.

THIS FACT'S OWN REFS DEMONSTRATE IT: the incident commit was force-pushed away and is now reachable from no branch, so it is named above as history only, and every ref below is anchored on the merge commit that is permanently reachable. Citing the broken commit would have been the error this fact is about.

THE MISREADING TO AVOID: this is not "never use `git checkout -- <file>`", and not a rule about reverts specifically. The rule is about ORDER — any mutation of the tree between the verification and the push voids the verification, whatever produced it. Re-running the suite is cheap; a report that certifies the wrong tree costs a review round and, if the reviewer trusts it, ships.
