# A guard whose value is "nothing has been written yet" must be tested through the ENTRY POINT with the sibling files seeded — a unit test on the guarded function cannot express ordering or cross-file atomicity, however wide its input table

Observed 2026-09-17 reviewing PR #213 (`knomit-bridge claude init` merges instead of dropping companion files). The merge functions were correct and their unit tests were sound and green. Two defects lived entirely in the CALLER, and no test of `mergeSettingsJSON` at any input could have seen either:

1. A settings.json whose top-level value is a JSON scalar (`null`, `42`, `true`, a bare string) indexed to a node with span offsets of -1, which the splice helpers took literally — `panic: slice bounds out of range [:-1]` in lineIndent. Reachable only by driving the entry point; calling the merge function is what the author had already done.
2. The panic fired DURING the template walk, and the walk reaches CLAUDE.md and .mcp.json before settings.json. So the run left a half-landed scaffold: two of the operator's files rewritten, the third untouched, the process dead. That is a property of ORDERING ACROSS FILES. A single-function test has no walk, no sibling files and no ordering, so the defect is not merely unobserved there — it is outside what that test can express.

THE RULE. Verify a guard by driving the ENTRY POINT the operator actually runs (`runInit`, not `mergeSettingsJSON`), in a temp directory seeded with the OTHER files that run touches, and assert THREE things, naming all three every time:
- the target file is byte-identical;
- the error names the file;
- every SIBLING file the run would have written is still absent or unchanged.

The third assertion is the one that catches half-landing and the one that gets omitted, because the first two feel like the whole requirement. Omitting it is how a test passes on both sides of the fix that matters.

WHY PLACEMENT IS THE WHOLE VALUE HERE. The repair was not the shape check itself but WHERE it runs: `checkSettingsShape` called from `preflightSettings`, before any file is written, rather than from the merge at the point of use. A test asserting only "init returns an error" passes identically whether the check runs before the walk or halfway through it. Only the sibling-file assertion distinguishes a guard that prevents the damage from one that merely reports it afterwards.

OPERATIONAL CONSEQUENCE. When reviewing or writing a guard, ask: at what point in the run does this fire, and what has already been written by then? If the answer is "something", the guard needs an entry-point test with the siblings seeded — a unit test on the guarded function cannot certify it, however thorough its input table.

WHAT THIS DOES NOT MEAN: it does not mean unit tests on the merge functions were wasted or should be replaced. They are where the byte-splicing correctness lives, they caught real defects, and they are far cheaper to run over a wide input table. The claim is narrower and only about SCOPE: a unit test cannot certify ordering or cross-file atomicity, so a guard whose value is "nothing has been written yet" needs BOTH — the input table at the unit level and one entry-point test that proves the siblings are untouched.

Distinct from the green-under-sabotage pair: there, the guard's own test is vacuous (nothing reaches its call site, or another line silently provides the guarantee). Here the guard's test is sound at its own level and the defect simply lives at a level the test does not span — so mutation-testing the merge function would not have surfaced it either.
