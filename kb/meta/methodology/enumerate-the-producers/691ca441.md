# To forbid a state, enumerate its PRODUCERS — and at least one usually has no syntactic marker to grep for, because it creates the state by changing the MEANING of code that was already correct

**The rule.** A fix that says "state S must never exist" is only as complete as its list of the things that PRODUCE S. Enumerate them before writing the fix, and do not enumerate them by grepping for an operation — the operation is how you find the producers that ADD S, and it is blind to the ones that create S by changing what already-correct code MEANS.

**How it presented (knomit #132, PR #166).** The state forbidden: a fact whose refs contain its own path. The obvious producer was an explicit append in knomit_learn's dedup-merge — `AppendUnique(union, existingPath)` — greppable, and the whole approved plan was to delete it.

The second producer had nothing to grep. The merge RETARGETS an incoming near-duplicate onto the existing fact's path. An incoming fact may legitimately cite the very fact it merges into — an ordinary "B cites A" — and the retarget silently turns that into "A cites A". No append, no new ref, no line that mentions self-reference: the ref was already there and correct, and only its MEANING changed when the fact's identity moved underneath it. The complete fix is therefore to FILTER the merged ref set against the merged path, not merely to stop adding to it.

**What caught it: running the suite, not reviewing the plan.** After the append was removed and the write gate added, a wholly unrelated test — `TestLearnHandler_OriginDefaultsAuthored`, about origin defaulting — went red, because its second write dedup-merged into the fact it cited and was then rejected by the new gate. That is a real behavioural consequence, not a test artifact: a legitimate authored write, citing a genuine other fact, would have been refused in production. Reading the plan could not surface it; only building the thing and running everything did.

**The generalisable tell.** Look for a meaning-changing producer wherever a fix's subject is a RELATIONSHIP between two identities and the code can move one of them: a retarget, a rename, a merge, a reparent, an alias. Anything that relocates identity converts existing references without touching them. Ask: after this operation, which previously-valid relations now describe something else?

**What this does NOT mean.** It is not "grep harder" — the second producer contains no token the first shares. It is also not the same as repair-recursion, which asks what a landed fix does to its NEIGHBOURS: both producers here are inside the one function being fixed, and the miss was in enumerating them, not in looking one level out. Sibling of removal-completeness-triad, generalised from removing CODE to removing a STATE.
