# A semantic merge conflict — two branches each valid on its own base, incompatible combined — is caught only by building the MERGE RESULT, never either branch

When two branches are queued for merge and both touch a SHARED SIGNATURE — one changes it, the other adds a call site to it — each can be independently correct: green on its own base, cold-reviewed clean, and text-mergeable (git has nothing to conflict on — different lines, different files). The COMBINED tree still fails to compile. Both branches can be current, correct, and mutually incompatible.

TWO halves, because the failure has two owners and a fact that names only one lets the other reader skip their check:

1. MERGER / coordinator, at merge time: build the MERGE RESULT. Run this AFTER each merge, and as a TRIAL MERGE before merging the second of two queued branches that touch a shared signature. Use `go vet ./...` (or `go test -run XXX ./...`, which compiles tests without running them) — NOT `go build ./...` alone. `go build` ignores `_test.go` files, so when the incompatibility is in test call sites the product builds fine the whole time and the breakage is invisible to build; only a test-compile sees it. 'Re-assert the base before every commit' does NOT cover this: it proves a branch sits on current dev, and says nothing about a second queued branch changing a signature that branch calls.

2. IMPLEMENTER, before handing the branch over: when you add call sites to (or otherwise depend on) an API that a sibling branch is actively changing the signature of, ASK what else is queued against that signature. It is answerable from your side before the branch is ever merged — you know which API you are calling and can check what other in-flight work touches it. Skipping that question is the other half of how the conflict reaches the merge.

WHEN TO SPEND THE TRIAL MERGE — the operative test, and the half that makes the rule followable: **does either branch DEPEND on a package the other CHANGED?** That is answerable in one step from the two diffs plus the import graph, and it is what turns a vague 'these could conflict' into a named mechanism worth ten minutes. When there is no import edge in either direction, disjoint file sets really are close to sufficient. When there is one, build the merge result even though nothing textually overlaps.

This matters because the alternative framings both fail in practice. 'Always build the merge result' gets ignored on the hundredth trivial merge — a rule nobody follows protects nothing. And 'the branches touch disjoint files, so they cannot conflict' is TEXTUAL reasoning applied to a SEMANTIC question: it is exactly the fallacy this fact exists to kill, and it is seductive enough that it was offered by the coordinator who was citing this fact at the time (knomit, 2026-08-26).

Concrete (knomit, 2026-08-26), the shape that produced the rule: #123 added a `createdBy` parameter to `CreatePipelineSession` and swept every call site that existed ON ITS BRANCH. #117b (merged first) added five NEW call sites its sweep could not have seen (its branch was cut before #123 merged), into a package it knew #123 was changing the signature of, without asking what else was queued. Both PRs were green on their own bases and merged cleanly at the text level; the combined dev did not compile (`not enough arguments in call to CreatePipelineSession` in two test files), which silently made `go test ./internal/synthesize/` unrunnable — so anything reporting that package green after the merge had not actually run it. The coordinator also never built the merge result. Both checks were skipped; either one alone would have caught it.

Concrete (knomit, 2026-08-26), the import-edge test doing its job: #125 (bridge lineage + signal, `internal/synthesize` + `internal/fact` + `tools/`) was queued behind #67 (bounded detach of repo creation, `internal/repos` + `internal/web` + `web/src`). ZERO file overlap — and the file-disjointness argument was made explicitly. But `internal/synthesize` IMPORTS `internal/repos`, and #125 threaded `*repos.RepoInstance` through four new projection sites (`fact.ID12(d.RI.ID())`, plus `ClusterResolution()`, `QualityConfigFromRepo(ri)`, `NewTestInstanceWithDeps` in its tests) while #67 changed repo CREATION lifecycle. A RepoInstance created asynchronously, or whose `ID()` populated later, would have broken that threading with both branches individually green and no file in common. The trial merge was built for that reason and came back clean — the mechanism did not fire — but the point stands: only the merge result could answer it, and the import edge is what said to ask.

What this does NOT mean: it is not caught by re-reviewing either branch (each is correct in isolation), it is not a git merge conflict (no textual overlap), and it is not solely a merge-time problem (the implementer's 'what else is queued against this API?' is the earlier catch). A clean trial merge is also not durable — it proves composition against the dev tip it was run against, so if dev moves again before the merge lands, it must be re-run. Sibling of repair-recursion (a change's effect shows up one step away from the change) applied to the merge boundary.
