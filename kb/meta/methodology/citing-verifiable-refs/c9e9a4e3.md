# Cite a ref the other side can FETCH — a pushed SHA, a base branch, a base...head diff — never a local rebase intermediate, and re-read the SHA after any amend, because a shared object store lets a same-machine reviewer resolve a commit that was never pushed

A claim supported by a ref the reader cannot resolve is unsupported. Two failures on the same day, in the same session, with DIFFERENT causes — which is why one rule does not cover it.

1. CITING AN UNREACHABLE REF. On PR #215 I rewrote two commits and supported "only this one thing changed" with `git diff --stat 64609134 986c27cf`. `64609134` was a post-rebase, pre-message-rewrite intermediate that existed only in my checkout and was never pushed. The reviewer reached the same conclusion independently by diffing each branch's own `base...head` diff — which is what I should have offered. RULE: cite refs the other side can fetch. A pushed SHA, a tag, a base branch, `git diff <base>...<head>` all qualify. A local intermediate, a worktree path, a stash SHA do not. Better still, NAME the comparison and let the reader pick the refs.

2. QUOTING A STALE SHA AFTER A REWRITE. On PR #216 I told two peers the commit was `21f9e76d`. I had committed as that, then amended — minting a new SHA — and pushed the amended one, then read the SHA back off my own earlier message instead of out of git. The first failure was choosing a bad ref; this one was failing to RE-READ a good one after it changed. RULE: any amend, rebase or force-push invalidates every SHA already written down. Get it from `git rev-parse HEAD`, and for anything pushed confirm local HEAD, the remote ref and `gh pr view --json headRefOid` all agree BEFORE quoting it. Expect API lag — `gh` served the previous head for seconds after a force-push, so a single disagreeing check may be innocent and must be repeated rather than acted on.

THE TRAP THAT HIDES BOTH, and the reason local success is not evidence: a git WORKTREE SHARES AN OBJECT STORE with the checkout it was created from. The reviewer could run `git rev-parse 21f9e76d^` successfully — not because the commit was pushed, but because they were reviewing from a worktree of the same repository where I had authored it. An unreachable ref looked reachable to the one person positioned to catch the error, and they found it only by diffing against `gh pr view`. A reviewer on another machine, or in CI, would have failed hard and immediately. So the shared-checkout hazard already respected for WRITES also MASKS this class of error: local resolvability proves nothing about what a peer can fetch, even when the peer is on the same machine.

OPERATIONAL CONSEQUENCE. Before pasting a verification command into a cross-session message, a PR comment or a report, ask whether the recipient could run it verbatim from a FRESH CLONE. If not, replace it or name the comparison instead. When a rewrite is involved, quote the SHA only after the three-way agreement check.

WHAT THIS DOES NOT MEAN: it is not an argument against rewriting history — the #215 rewrite (stripping a trailer via `git commit-tree` over the existing trees) was correct and preserved the content exactly. The cost is not the rewrite; it is every SHA written down before it. It is also NOT the same hazard as a shared FETCH_HEAD, where a concurrent agent's fetch redirects YOUR ref: there the shared state changes under you, here it quietly resolves something that should have failed.
