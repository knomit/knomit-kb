# When a fix lands, ask what it does to its NEIGHBOURS — the same class of bug reappears one level out, and this applies to cleanups MORE than to fixes

**The claim.** A fix frequently re-creates its own bug class one level out, in the code the fix reaches into.

**Three instances from one phase.** (1) Requeuing a changed fact's PARTNERS repaired the asymmetric-KNN pair loss — and destroyed the partners' own pairs by the identical mechanism. (2) Not-marking-uncovered fixed the premature coverage marker — and still lost pairs that had been scanned against a partial axis. (3) Deleting a declined pair stopped it recurring — and let a later neighbour rescan re-mint it.

**The practice.** After a fix, name the neighbours it touches and ask the ORIGINAL failure question about each one. Not "does the test pass" — the test was written for the first instance and will pass.

**The corollary, learned the hard way: this applies to CLEANUPS more than to fixes.** Two of three self-review findings in the phase were in changes made because a reviewer had called them non-blocking tidying. That is precisely the category that receives less scrutiny — it is labelled safe, so nobody re-derives its blast radius, and the label is doing the reasoning.

**The named misreading.** This is not "write more tests around the fix". It is a question about SCOPE: which other code now behaves differently, and does the reason the original code was wrong apply there too? A test cannot ask that, because the neighbour was not the subject of the test.
