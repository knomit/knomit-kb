# A fix that adds a FIELD something else must populate needs TWO tests — one for the gate that reads it, one for the wiring that fills it — and only sabotage tells them apart

When a fix introduces a new FIELD and some other code must fill it, the fix has two independent failure modes and a test suite naturally covers only one. A test that constructs the struct literal itself — setting the field by hand and then asserting the consumer behaves correctly — proves the GATE works. It says nothing about whether anything in production ever populates that field, and it stays green when the population is deleted. The field silently sits at its zero value, the consumer reads the zero, and every test passes.

SO WRITE BOTH: (1) a gate test that hands the value in and asserts the reader's behaviour; (2) a POPULATION test that drives the real producer — the projection function, the builder, the call site — from an input carrying the raw form, and asserts either the field's resulting value or a behaviour only a correctly-filled field can produce. Only the second survives deleting the assignment.

AND ONLY SABOTAGE SEPARATES THEM. Reading the suite does not reveal the gap: both kinds of test mention the field, both look like coverage, and the missing one is invisible because nothing is absent from the file — the assertion that would have failed was simply never written. Deleting the population line and watching the suite stay green is what exposes it. This is why the rule is stated as a sabotage target rather than a review checklist item.

FOUR INSTANCES (knomit, 2026-08): #117a — a wiring test called applyEmissionOutcome DIRECTLY, so it passed under a sabotage deleting its call site; rewritten to drive planRestatementShortlist. #125 part 1 — factForLLM gained LineageRefs, populated at the projection sites via localFactRefPaths; every test built factForLLM by hand, so replacing the normalized population with the raw refs passed THE ENTIRE FIRST DRAFT of the suite, and the whole lineage exclusion would have shipped green and excluded nothing. #125 part 2 — enumeratedMotif gained entOverlap, assigned once in buildMotifBridgesWithRows; every rank test set it by hand, so deleting that one assignment passed all of them and the tiebreaker would have shipped permanently inert at zero with green tests proving the comparator worked. #67 — the same shape on the incident oracle. Two of the four occurred in ONE ticket, in both of its halves, which is what moved this from coincidence to rule.

WHAT THIS DOES NOT MEAN: it is not 'always add an end-to-end test'. The population test can be small — call the projection function and assert the field — and the gate test remains worth having, because it is the one that localises a failure to the reader rather than the producer. Nor is it satisfied by a test that calls the producer and asserts the CONSUMER's final output only: if the consumer's output is identical whether or not the field is filled (a rank tie, a no-op branch), that test is inert for the same reason. Choose an input where the filled and unfilled field give DIFFERENT answers, and assert the fixture makes them different (fixture-discrimination-precondition). Sibling of 'a test that calls the helper is not a test of the wiring' generalised from call sites to struct fields.
