# Count and delta checks certify the number, not the content — they pass green while individual elements are silently rewritten; only exact per-element comparison against the intended payload catches it

A batch operation verified by counts and deltas can be fully green while individual elements were changed in ways the counts cannot see. Aggregate invariants (N in / N out, delta equals the expected count, zero residual of the target defect) are real checks, but they measure the SHAPE of the change, not its CONTENT.

Concrete case that earned this: repairing 42 facts by re-sending each fact's reference list minus one self-ref, under a promise that every OTHER ref stayed byte-identical. Every count-based check passed — 195 refs before, 153 after, delta exactly 42, one per fact, zero residual self-refs. Meanwhile the write path silently canonicalized 6 facts' bare refs (bare form to kb://<repo-id>/ form). Only an exact-string-and-order comparison of each fact's stored refs against the STAGED payload that was supposed to be written revealed it. Had verification been the count-based version originally proposed, this would have shipped as a flawless batch.

Two consequences to act on:
(1) Verify a batch at the granularity of the property you actually guaranteed. A promise of 'every other ref byte-identical' is checked by a per-element exact comparison against the intended output, not by counting refs. A coarser check certifies only a coarser claim.
(2) A proof of YOUR half of an operation is not a proof of the whole operation. The repair logic provably could not canonicalize (it sliced around an index); the canonicalization happened downstream in the write path, which the repair never controlled. When an uncontrolled transform sits between your input and the stored result, verify the STORED result, not your input — the guarantee has to be proven end-to-end, or it is only proven where you happened to be looking.

Does NOT mean 'counts are useless'. Count and delta checks catch whole error classes (dropped elements, duplicated writes) that content comparison alone can miss. The rule is that they are necessary and not sufficient: pair them with an exact comparison against the intended payload whenever a write path you do not fully control sits downstream.
