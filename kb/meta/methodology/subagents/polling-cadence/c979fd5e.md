# A subagent waiting on CI must NOT poll and must NOT wait for the whole run: start ONE background shell loop that returns on the FIRST failed job (or on completion), read that job's log at once while the run is still going, fix a real failure immediately, and rerun a known flake once only after the run completes; the sleeping shell costs no tokens

Learned during the 2026-10 multi-session work (fleet specs, F22–F24, the KB audit), when the operator was at the weekly quota ceiling and every wasted turn counted. A subagent told "wait until <file> exists", "wait for the PR to merge" or "wait for CI" tends to write `sleep` loops or re-check on every turn. Each re-check is a full model turn: it re-sends the whole conversation (100–200k tokens for a worker deep in a PR) and spends output tokens, while the thing it waits for changes on a scale of minutes.

RULE 1, never poll (operator, 2026-10-07, verbatim: "yes, do that - I mean I'm seeing my tokens evaporating waiting on a stupid CI job to complete"). Start ONE background command and make NO further tool calls until the harness wakes the agent on that command's exit. The same holds for long local suites (run once in the background) and for any other slow external state: one blocking command, with an upper bound so a dead producer does not hold the session forever. Write the handoff (what you need, where you will look) to a file before waiting.

RULE 2, fail fast (operator, 2026-10-08, verbatim: "WTF is the other session waiting for, the rest of them to fail ?"). This replaces `gh run watch <id> --exit-status`, which waits for EVERY job even after one has already failed. The background command is a loop that returns on the FIRST failed job or on completion, whichever comes first:

`ID=<run>; R=<owner/repo>; until [ "$(gh run view $ID -R $R --json status -q .status)" = completed ] || gh run view $ID -R $R --json jobs -q '.jobs[].conclusion' | grep -qx failure; do sleep 60; done; gh run view $ID -R $R --json status,conclusion,jobs`

When it returns with a failed job, read that job's log AT ONCE. The run may still be in progress; a finished job's log is already available: `gh api --allow-escape-sequences repos/<owner/repo>/actions/jobs/<jobid>/logs`, then strip ANSI codes and grep for `--- FAIL|^FAIL|panic:`. A REAL failure is fixed now, without waiting for the other jobs. A KNOWN FLAKE waits for the run to complete (start the same loop again; it returns on completion) and is then rerun ONCE with `gh run rerun <id> --failed`.

WHY RULE 2 DOES NOT BREAK RULE 1: the loop's `sleep 60` runs in a background shell, not in the model. It costs no tokens and wakes the agent exactly once. Polling that RE-ENTERS THE MODEL is what rule 1 forbids; a sleeping shell is not that.

PRACTICAL NOTE: some agent harnesses (worktree-isolated agents) refuse a compound command containing `gh ... | grep`, because they cannot prove it is not git. Put the loop in a script file and run `bash <script> <run-id>` in the background.

WHAT THIS DOES NOT MEAN: not that a subagent should block indefinitely. After the bound, report what is still missing and stop. It is not a ban on the coordinator reading a run's state ONCE when it needs a fact (e.g. which head merged). It is not a rule about the SERVER's own loops (sync, reconcile, triggers), whose intervals are config and cost no model turns. And 'fail fast' does not mean cancelling the run or rerunning before it completes: a flake is rerun only once the run has finished, and only once.
