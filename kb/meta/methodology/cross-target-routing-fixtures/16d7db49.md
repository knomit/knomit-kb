# A routing test must make the WRONG target accept the call too — give the two repos disjoint ontologies and a misrouted write is refused by validation, so the test goes green without ever exercising routing

When a test asserts that a call reached the RIGHT target, the fixture's targets must be INTERCHANGEABLE with respect to every check the call passes through before the routing effect becomes observable. If the wrong target would refuse the call for its own reasons, the misroute is caught by an unrelated guard, and a green test says nothing about routing.

CONSEQUENCE to act on: a cross-repo routing regression test whose two repos have DISJOINT ontologies cannot fail for the real reason. A write aimed at the wrong repo dies on topic validation, so the test would pass on a build whose routing is completely broken. Build the fixture so every call is valid in EITHER target — in knomit's incident test, `newE2EMount` gives both repos `fact.CodeOntology()`, so `architecture` resolves in both and a misrouted `knomit_learn` COMMITS. The assertion on `written_to.repo` is then the only thing that can catch it, which is exactly the property wanted.

This is not hypothetical, and the real incident is the proof. On 2026-09-17 two Claude Cowork jobs shared one MCP session id and their `knomit_bind` calls overwrote each other; four `knomit_learn` calls ran against the wrong knowledge base and FAILED — `unknown topic technology` / `unknown topic incidents` — only because those two ontologies happened to share no topic. That loud failure was a NEAR MISS, not a safeguard: the corpus was one shared topic away from silent cross-writes. A regression test built with disjoint ontologies reproduces the near miss instead of the incident.

THE ACCEPTANCE CHECK, and it is cheap: run the test against the broken build and read WHY it goes red. It must fail on the routing assertion. If it fails on a validation error, a permission refusal, or anything else that happens before routing is observable, the fixture is wrong even though the test is red. This is the rule that a regression test never seen RED is unverified, taken one level further in: red is necessary, red for the RIGHT reason is the actual bar.

The ontology is only the instance. The same trap is any pre-routing guard that the two targets do not share: a read-only subscription would refuse a misrouted write for the wrong reason, which is why the incident fixture makes both mounts writable (`subscribed=false`) rather than accepting whatever the helper defaults to. Before trusting a routing test, list what could refuse the call at the wrong target and confirm the fixture removes each one.

THE MISREADING TO AVOID: this is not "make the fixture's targets identical". They must differ in the ONE dimension the assertion reads — here the repo name that comes back in `written_to.repo` — and be alike in every dimension that could refuse the call earlier. Identical targets would make the assertion itself unable to discriminate, which is the fixture-discrimination rule seen from the other side: a fixture only discriminates if the values it must distinguish are asserted to differ.
