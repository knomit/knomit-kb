# Measuring merge latency for facts written inside knomit experiments: time from the EXPERIMENT COMMIT (the merge into the agent branch) to the fact's arrival on the host's main — timing from the fact's own commit inside the experiment folds the whole session's duration into the number (first mission F-R5: a 35 s median and a 396 s p95 that were session length, not sync delay)

From the first mission's real run (2026-10-02). The measure script took, for each fact on the mission KB's main, the interval between the commit that first wrote the fact and the commit that landed it on the host's main. For the mission REPO that is right: tasks are written straight on the agent branch. For the mission KB it is wrong: every session writes its facts inside a per-task experiment, and the experiment is merged into the agent branch only at the end of the session, so the interval is dominated by how long the session kept working after its first fact. The report's "R median 35 s, p95 396 s" for the KB was session duration; the same instrument gave 0–4 s for the mission repo, which is the real sync figure over the tailnet.

RULE: when the writer uses experiments (any `exp/<name>` branch, mission or not), the sync-latency clock starts at the merge commit on the agent branch (`merge: exp/<name> into <agent branch> (...)`, authored by the owning agent since #396), not at the fact's first commit. The fact's first-commit time still matters for a different question (how long the knowledge was invisible to peers), and the two must be reported as two numbers.

MISREADING TO AVOID: "the KB syncs 10x slower than the mission repo" — both are carried by the same sync loop; the difference in the report was the instrument. The user ruled the measure script is the only thing to change (post-run ruling 8), so this is a measurement convention, not a knomit change.
