# A test anchor asserted as require.Contains(rendered, "<word>") pins a SPELLING, not the rule it guards — a decoy occurrence elsewhere in the same file satisfies it, and the obvious repair (pin the full phrase) fails on line wrapping, where the tempting fix manufactures the original defect

Found in review of PR #188 (2026-09-14), on a test that pins PROMPT TEXT rather than parsed source. This is `kb/meta/methodology/conformance-whitelist-not-blacklist/ef85a3c0.md`'s mechanism on a second surface: that fact says a conformance check forbidding NAMED identifiers pins a spelling, not a property. The same is true of an assertion that pins a WORD of a rendered prompt.

**FORM A — the anchor matches an unrelated occurrence.** `methodology_load_test.go` pinned the distill prompt's forcing language with `require.Contains(t, content.Prompt, "Always")`. `distill_user.txt` contains "Always" TWICE: once in the methodology rule the assertion exists to guard, and once at the end of the hypothesis-handling section in the unrelated sentence "Always use a path under `<ontology-root>/meta/reasoning/` for methodology-type output". The pin was satisfied by the second whatever the first said.

Measured, not inferred: replacing the methodology rule's "Always — its title is not enough to judge whether it applies." with "Its title is not enough...", leaving the unrelated sentence standing, left one "Always" in the file and `TestRenderDistillWorkItem_HeaderAppearsWhenSectionPresent` returned ok. Two contrast mutations in the same worktree confirmed the instrument was working: renaming "Read the top-ranked candidate above:" FAILED, and removing `reflect_user.txt`'s single "Always" FAILED. So the reflect pin was sound and only the distill one was vacuous — one file having a decoy and the other not is the whole difference.

**This is a new surface for the second cause in `green-under-sabotage-has-two-causes`** — "a DIFFERENT line is quietly providing the guarantee you attributed to it". There the different line was code; here it is prose in the same asset.

**FORM B — the anchor matches nothing, and the obvious repair manufactures Form A.** The fix for Form A is to pin the full phrase, "Always — its title is not enough". In `reflect_user.txt` that phrase was split across a newline by the file's wrapping ("...its title is not\nenough"), so the pin matched zero times and the test failed. The tempting repair at that point is to SHORTEN the pin until it matches the wrapping — which reproduces Form A exactly. The correct order is to reflow the source so the phrase is contiguous, THEN pin it.

Form B is why "pin the full phrase, not the bare word" is insufficient advice on its own, and it is the part a reader will not derive: a failing pin looks like an honest red, and shortening it looks like fixing a test rather than deleting a guard.

**Both forms present as a green suite, and both are invisible to reading.** A plausible anchor in a plausible place reads as protective — the same sentence MN13 uses about corpus-property constants. The reviewer who found Form A proposed the fix that walked into Form B; the implementer caught it. Recorded because a competent reader taking the tempting path is the evidence that the path is tempting.

**CONSEQUENCE — what to do.** When an assertion binds to text in a rendered artifact, assert the anchor occurs EXACTLY ONCE, not at least once. That catches Form A outright (a decoy makes the count 2 and reddens) and converts Form B from tempting into loud (a wrapped phrase makes the count 0 with a message that says so). This is the same move as `ForModel` returning `(Thresholds, bool)` rather than a silent default, and the same move as ef85a3c0's "read the permitted set from the DECLARATION": make the ambiguous case unrepresentable instead of relying on the author to notice it. A helper for this was deliberately NOT added in #188 — it widens the change beyond the review and needs a decision about which anchors may legitimately repeat.

**WHAT THIS DOES NOT MEAN — exactly-once is not right for every anchor.** Some assertions legitimately match text that repeats (a heading rendered per section, a token deliberately restated). The rule is that a pin guarding a SPECIFIC RULE must bind to something unique to that rule; it is not a blanket ban on anchors with multiple occurrences. Applying exactly-once blindly turns correct tests red.

**WHAT THIS DOES NOT MEAN — this is not about mutation technique.** `kb/meta/methodology/testing/sabotage-must-delete-not-replace/101f516e.md` covers mutations that REPLACE rather than delete, where the mutation itself asks the wrong question. Here the mutation was correct and did its job; what was wrong was what the assertion BOUND TO. Anchor validity and mutation validity are separate failures and a fix for one does not address the other.

**METHOD.** Inspection accepted this pin — it reads as protective. It was caught only by mutating the anchor, keeping the decoy, and asserting the test FAILED, per `field-population-needs-its-own-test` ("only sabotage tells them apart"). A pin added to a rendered artifact should be mutation-proven at every site it is added to, because the decoy is a property of the FILE, not of the assertion: the identical pin was sound in one prompt and vacuous in another.
