# A sabotage that REPLACES a guard instead of deleting it tests a different program — so its green AND its red are both true answers to a question nobody asked

`prove-the-regression-test-fails` says construct the broken implementation and watch it fail. `green-under-sabotage-has-two-causes` says how to read a green. Both assume the mutation you performed was the one you described. THIS FACT IS UPSTREAM OF BOTH: establish that first, because the common way to get it wrong is invisible in the diff you wrote.

One PR produced the same error twice, from the same author, both times reported as a completed proof:

- `if emb == nil { return }` was "deleted" by writing `modelID := "none"; if emb != nil { modelID = emb.ID() }` — re-supplying the guard's nil-safety in another shape.
- `if !ok { warn; return }` was "deleted" by writing `if th.Dedup == 0 { th = EmbedderThresholds(emb) }` — substituting a different policy.

Neither is the guard removed. Each is a THIRD program, so each result was a true statement about something nobody asked.

**THE RULE: delete the guard and nothing else, then read WHY it went red.** Three ways that goes wrong, in the order they bite:

1. **Repairing the wreckage.** A true deletion often will not compile, or panics. The reflex is to make the mutant run again — and every way of doing that re-supplies the guard's effect under another name. THE URGE TO MAKE THE MUTATED PROGRAM WORK IS THE URGE TO PUT THE GUARD BACK.
2. **Red for the wrong reason.** A mutation can fail for reasons unrelated to what the guard protects. Miss 2 turned the gate ON; that fails loudly while proving nothing about a guard whose job is turning it OFF. The bar is not "it went red" but "it went red on the property the guard exists to protect" — read the failure MESSAGE, not the exit status. RED IS NOT SELF-VALIDATING, which is the half `green-under-sabotage-has-two-causes` does not cover.
3. **Grading your own experiment.** The author knows the answer they want. Both misses were caught only when the REVIEWER ran the mutation independently. So write the mutation INTO the test comment, precise enough to run verbatim, and expect that someone will.

**THREE OUTCOMES, NOT TWO.** Deletion will not COMPILE → the guard is structurally required; the compiler is the guard and no test is needed. Deletion compiles and goes red ON THE GUARD'S PROPERTY → the test pins it; this is the target. Deletion compiles and stays GREEN → the test does not pin it, whatever its name or comment claims; now apply `green-under-sabotage-has-two-causes` to find which cause. The first and third both feel like "no useful test here" and are opposites.

**ASSERT THE SIDE EFFECT WHEN THE SIDE EFFECT IS THE VALUE.** A guard whose only unique contribution is a log line cannot be pinned by asserting behaviour that is already correct without it. Measured: with the `!ok` guard deleted, the captured log showed the fact was STILL WRITTEN (`upsert: using donated embedding`, index sync +1). The outcome was correct without the guard, so no outcome assertion could have caught it even in principle — only asserting the warning fires.

**CONSEQUENCE:** before concluding anything from a sabotage, diff your mutation against the original and confirm it is a pure deletion. If you had to add or change a line to make it build or run, you did not test the guard.

**REFINES `green-under-sabotage-has-two-causes`:** its consequence says that on a green you must NOT conclude "my sabotage was wrong". That is right once the mutation is valid, and wrong before — here the sabotage genuinely WAS wrong, twice. Rule out the invalid mutation FIRST, then that fact's two causes are exhaustive.

**WHAT THIS DOES NOT MEAN — not "any mutation that turns the test red proves the guard".** That is miss 2 exactly, and it is the more dangerous of the two because it presents as success.

**WHAT THIS DOES NOT MEAN — not "check your guards are reachable".** One of the two cases here was a dead branch, but the other was a LIVE guard that fired correctly and whose only unique contribution was a log line. Collapsing both into a reachability check loses the second entirely — and the second is the one no outcome assertion can catch.
