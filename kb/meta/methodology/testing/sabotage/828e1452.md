# A negative test whose forbidden commit is the branch TIP cannot catch an over-broad vouching rule — E4's transitive trust needs a foreign commit placed BELOW an own-signed commit (a non-merge, and the first parent of a merge) for 'vouch everything under any own-signed commit' to turn red

When a rule VOUCHES for commits by their position under another commit (E4's D4b rule: adopt what an own-signed merge brought in through a non-first parent), the obvious negative test — a foreign commit set directly as the branch tip — is below nothing, so every candidate vouching rule refuses it, the correct one and the laxest wrong one alike. The laxest wrong rule is 'anything reachable from ANY own-signed commit, first parents included'. It is caught only by negatives that place the foreigner UNDER an own-signed commit: once under an own-signed NON-merge commit, and once under the FIRST parent of an own-signed merge.

Measured on feat/f11-ui-merge at f791493b: sabotage S9 (the laxest rule) turned exactly those two cases red and left the tip-only negative green; S7 (a merge vouches whatever its signer) was caught by the foreign-signed-merge and unsigned-merge cases; S8 (vouch the first-parent chain only) was caught by the positive case (two peer commits plus a peer merge) and by the first-parent case.

Consequence for anyone adding a trust or vouching rule: for each way the rule could be too broad, write the negative that places the untrusted object where that broader rule would reach it, and prove it by sabotaging the rule to exactly that breadth. A sabotage that does not model the broader rule faithfully proves nothing: the first S9 attempt here inverted a condition, went red for the wrong reason, and would have been reported as coverage. Read the sabotage's diff before crediting its red.

NON-SCOPE: this is about test design for positional trust rules. It does not say E4 is under-tested elsewhere.
