# A mutation must produce an OBSERVED, NAMED failure — "not green" is not a result and neither is "no output": three distinct ways a sabotage run proves nothing all present as silence, and asserting the anchor matched catches only the first

Before you may ask what a sabotage RESULT means, establish that there IS one. A mutation run counts only when it produces the failure you expected, NAMED — the assertion text, the offending item, the line. Anything else is an unfinished run.

THREE WAYS IT PROVES NOTHING, all of which look like a clean pass:

1. **The edit never APPLIED.** The anchor did not match — a renamed symbol, different indentation, a `sed` pattern that silently matched zero times. The test then runs against UNMODIFIED code and passes correctly.
2. **The edit applied but did not COMPILE.** The mutation is real and the code is not: it referenced a field that does not exist. `go test` reports a build failure, and a grep looking for a FAIL line matches neither the failure nor the build error.
3. **The edit compiled but the harness never REACHED the assertion.** An earlier fatal, a skipped subtest, a filter that matched no test.

ASSERTING THE ANCHOR MATCHED — `assert s.count(old) == 1` before writing — catches ONLY the first. It is a good habit and it is not the rule; case 2 passes that assertion with room to spare.

THE OPERATIONAL FORM, which is what to actually adopt: classify every run into exactly one of

```
NAMED FAILURE  |  BUILD FAILED  |  PASSED  |  SILENT
```

Mutually exclusive and exhaustive, so a build break cannot be misread as a discriminating test and "matched neither pattern" cannot be absorbed by a tired human hoping to be finished. The minimum viable version is grepping for the expected failure AND for `FAIL|build failed`, or simply reading the whole output — but the classifier is better precisely because it removes the judgement call at the moment you least want one.

TWO ANCHORS, ONE SESSION (2026-09-18, PR #224). A `{branch}` sabotage printed nothing because the `sed` anchor missed the real registration — case 1, caught, and written up. Then, in the SAME session, with that warning already written, a `/domains` sabotage printed "applied" and the test printed nothing: it had applied, it referenced `p.domainsLister` which does not exist, the package failed to compile — case 2, in a variant the just-written rule did not cover. The reviewer, who had been asserting the anchor for a week as an unstated habit, confirmed it would not have caught that one either.

HOW IT SITS WITH THE OTHER SABOTAGE FACTS. It is UPSTREAM of "green under sabotage has two causes": that fact classifies a run that came back GREEN and asks which of two reasons explains it; this one is the precondition for asking, because silence is not green. It is ORTHOGONAL to "sabotage must delete not replace", which is about choosing a mutation that tests the right program — a well-chosen mutation can still be silent, and a badly-chosen one can produce a perfectly named failure about nothing. And it does NOT cover the shared-premise case, where a suite and its code rest on the same assumption: those runs are genuinely green, not silent, and no mutation reaches them.

THE GENERAL SHAPE, worth more than the procedure: an unstated habit protects only the person who has it, and a rule generalises only as far as the instance that produced it unless you deliberately push it further. Both were demonstrated here by the person who wrote the rule, twice, within an hour.
