# A guard test can be vacuous because its own SETUP completed the hazardous work before the hazard could occur — the fixture must be chosen so the guarded window is still open, and that must be asserted

**The rule.** A test that guards against "X must not damage in-flight work Y" is vacuous whenever its own setup causes Y to FINISH before X happens. The assertion is then made about completed work, is correct under both the sound and the broken implementation, and reads as coverage forever. The defect is not in the assertion and not in the values — it is in the TIMING the fixture produces. So: choose the fixture that leaves the guarded window OPEN at the moment the hazard fires, and assert that the window was open, as a precondition, in the test itself.

**How it presented (knomit #67, PR #162).** The fix detaches repo creation onto a bounded context, and the load-bearing safety property is that this new deadline must never cancel the background search-index heal — reinstating incident kb/incidents/repos/clone-create-index-stuck-indexing, where a cancelled heal returns without markIndexReady/markIndexFailed and pins IndexStatus at 'indexing' forever. The oracle: run a real create, let StartCreate's `defer cancel()` fire, require IndexStatus to reach 'ready'.

Written on CLONE mode it was inert. Clone-mode Create ends in `ActivateSync`, whose synchronous reconcile blocks on the branch lock the heal holds — so Create cannot return until the heal has already finished. Measured: IndexStatus was already `"ready"` at job completion, 5 runs out of 5. The cancel landed on completed work, and the test passed under the exact sabotage it existed to catch (threading the create context into `openOne`'s builder).

Rebuilt on PRESET mode, which has no ActivateSync, so Create returns while the heal is still running: `"indexing"` at job completion, 50 runs out of 50. That condition is now an explicit `require.Equal(t, "indexing", state)` with a message saying the fixture no longer discriminates — so a future change that makes the heal finish first FAILS LOUDLY instead of quietly disarming the guard. Under the same sabotage the rebuilt test is the only failure in either package.

**Why this is a sibling of, not the same as, fixture-discrimination-precondition.** That fact is about two VALUES coinciding: the things the test must tell apart happen to be equal in the fixture. This one is about ORDERING: the values would differ fine, but the hazardous moment has already passed when the assertion runs. Both are found the same way — by sabotage plus MEASUREMENT, never by reading — and both are fixed the same way, with a precondition assertion. Look for this one specifically whenever a test's setup path is allowed to complete asynchronous or background work, and whenever the code under test SERIALISES against that work (a shared lock, a WaitGroup, an inline reconcile): serialisation is what silently converts "during" into "after".

**What this does NOT mean.** It is not an argument for the most realistic fixture. Clone mode is the more production-shaped path and is precisely the one that cannot express this test; the discriminating fixture won, and the test carries both measurements plus the reason, so nobody "improves" it back to vacuity. It also does not mean adding sleeps or timing hacks — preset mode is deterministic, and the precondition assertion, not a delay, is what enforces the ordering.
