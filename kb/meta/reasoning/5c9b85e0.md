# A check that CANNOT see the defect returns the same green as one that looked — nine distinct structural blindnesses, one question that finds them all, and sabotage is the only instrument that answers it

Nine separately-earned methodology facts describe the same failure at the level above their own subjects: a check whose inputs cannot reach the defect returns the reassuring answer whether or not the defect is present. In every one, the ASSERTION was correct, the code under it was correct, nobody wrote anything wrong — and the check still could not have detected the defect it existed to detect. It returned the reassuring answer, and it would have gone on returning it for the lifetime of the code, reading as coverage to every later reviewer.

**THE ONE QUESTION.** *Could this check produce the answer it just produced if the defect WERE present?* Reading a check tells you what it claims. Only that question tells you whether its inputs can reach the claim, and the only reliable way to answer it is mechanical: **introduce the defect and watch the check notice.** Break the implementation the specific way the test guards against, and see it RED before trusting it (`prove-the-regression-test-fails`). Disable the sanitiser and re-run. Remove the drain and count red runs. Every one of the nine was found that way or by an independent re-measurement; none was found by reading.

**NINE DISTINCT BLINDNESSES — the checklist for when sabotage is not available.** Each is a different relationship between the check and the phenomenon, and they are NOT interchangeable; the remedy for one is the failure mode of another.

1. **Same side of the transformation.** An instrument comparing two values both produced BY the lossy step reports zero loss. Ask: which side of the lossy step does each of my two values come from? Same side = measures nothing. (`instrument-reads-truncated-values`)
2. **Shared provenance.** Two sources agreeing corroborate only if verified INDEPENDENTLY against ground truth. A corpus fact and a code doc-comment descending from one design note agree by inheritance and can be wrong together — a knowledge base manufactures this the more it documents an intent. Verify one against the code, never against its sibling. (`corroboration-needs-independent-provenance`)
3. **Wrong granularity.** Counts and deltas certify the SHAPE of a change, not its CONTENT: 195→153 refs, delta exactly 42, zero residual — while the write path silently canonicalized six facts' refs. Verify at the granularity of the property you actually guaranteed, against the STAGED payload, and remember that a proof of YOUR half is not a proof of the whole operation when an uncontrolled transform sits downstream. (`batch-verification-granularity`)
4. **The window already closed.** A guard against "X must not damage in-flight Y" is vacuous when its own SETUP finishes Y first — measured: IndexStatus already `ready` 5/5 in clone mode, `indexing` 50/50 in preset mode. Serialisation (a shared lock, a WaitGroup, an inline reconcile) is what silently converts "during" into "after". Choose the fixture that holds the window open and ASSERT it was open. (`guard-setup-outruns-hazard`)
5. **Coinciding values.** When two things a test must tell apart hold the SAME value in the fixture, it passes under both implementations. The enforcement is a PRECONDITION ASSERTION that they differ, written in the test — not the author's care. (`fixture-discrimination-precondition`)
6. **The bug moves the measured variable.** Widening a timing margin cannot fix a timing assertion when the bug's own effect changes how long the measured thing takes — measured red rates 27/30, 28/30, then **20/30 on the largest fixture**, because `Close` BREAKING the create is what made the create finish fast. THE TELL: if widening makes it worse, stop tuning the fixture and re-choose the QUESTION — ask about the OUTCOME, which is not a race. (`measure-outcome-not-the-race`)
7. **Sample read as population.** A remediation silently inherits the scope of the observation that found it: '6 observed self-refs' repaired, 42 actually present. Only an independent full enumeration closes the class, and it carries information ONLY when it DISAGREES — agreement is indistinguishable from re-finding what you already had. (`remediation-completeness`)
8. **The anchor binds a spelling, not the rule — or the fixture measures a value production never emits.** A pin on a WORD of a rendered artifact is satisfied by an unrelated occurrence of that word (a decoy) whatever the guarded sentence says; the tempting repair for a pin that matches nothing — shortening it until it matches the file's wrapping — manufactures the decoy case again; and a fixture that passes a test-only label as data measures a payload the system cannot produce and reports a number about itself. The remedy has two halves: a pin guarding a SPECIFIC RULE must bind to something unique to that rule and assert it occurs EXACTLY ONCE, not at least once; and every field of a measuring fixture that reaches the wire must carry its production value, with test-only labels held in fields that do not. This is `guarantee-provided-elsewhere` on a new surface — the different line quietly providing the guarantee is prose in the same asset rather than code. (`anchor-binds-spelling-not-rule`)
9. **Both sides of the inequality share a derivation.** A safety check written as requirement-versus-budget is unsatisfiable, not conservative, when the budget was itself computed from the requirement: the comparison asks a question the sizing step already answered, and reports whatever that step decided rather than an independent fact about the machine. Its monotonicity test passes VACUOUSLY over a condition that is false everywhere it is sampled — a check that never fires never fails. THE DIAGNOSTIC: SWEEP THE SAFETY CONSTANT; when tuning a safety parameter barely moves the behaviour, the parameter is not in the binding path and the condition is probably degenerate. The two sides of a safety inequality must come from different sources. This is the self-satisfying sibling of the proxy-inverts-against-property failure: both are the gate's input not being independent of what the gate is supposed to judge. (`tautological-check`)

**Where 4 and 6 diverge, because merging them is the available mistake.** Both are about timing, and their remedies are opposite. The distinguishing question is **who moves the timing**: if it is the SETUP, re-choose the fixture and assert the window is open; if it is the BUG, re-choose the question and assert an outcome. Keep the in-flight precondition assertion either way — it is what makes a fixture that stops discriminating fail loudly instead of going quiet.

**Where 2 and 9 diverge, because merging them is the other available mistake.** Both are about inputs that are not independent. In 2 the two sources are supposed to CORROBORATE and cannot, because they inherit from one origin; the remedy is to verify one against ground truth. In 9 the two sides are supposed to be COMPARED and cannot, because one was computed from the other; the remedy is to take one side from a different source entirely (the machine, not the resolved budget) and to sweep the constant to prove the comparison binds. Reading 9 as 2 sends you to verify the derivation — which was sound — instead of noticing that a sound derivation on both sides is exactly the problem.

**A corollary that generalises past tests.** A harness is itself a check. A first run reporting '0 near, 0 far' on every corpus READ as a finding about the corpora and was a finding about the harness (`MaxMembers` left at 0). RE-DERIVE a re-verification harness; never trust one from a path — a stale script reporting five greens is telling you it is stale, and one measured case scripted 5 sabotages where 7 existed. And **verify by EXIT CODE, never by a message printed beside one**: a commit landed red because the command printed '(green)' unconditionally after a grep that had matched nothing. Read that example for what it actually shows, because the printed-message-versus-exit-code framing is only its surface: the grep EXAMINED nothing and matched nothing, and the harness reported success regardless. **An exit code is honest about whether a command SUCCEEDED and is never a claim about whether it EXAMINED anything.** A command whose input set is empty — a grep over nothing, a type-check over zero files, a test filter that matched no test — exits clean and means nothing, and a reader who has correctly learned to trust the exit code over the message is walked straight into it. This is shape 7 at zero: the independent enumeration that closes the class is the enumeration of what the command actually read, and it is informative precisely when it returns nothing.

**WHAT THIS DOES NOT MEAN.** It is not that counts, timing assertions, cosine filters, agreement between sources, realistic fixtures, text anchors, or derived budgets are bad — each is the right instrument in its own place: counts catch dropped and duplicated elements that content comparison misses; the timing assertion in case 6 was KEPT as a free secondary check; agreement across INDEPENDENTLY-verified sources is real evidence; deriving a budget from measurements was sound and stayed — the defect in 9 was reusing the SAME derivation on both sides of a comparison meant to test it. It is not 'always sweep before fixing anything' — a fix explicitly scoped to specific known instances is honest. It is not an argument for the most production-shaped fixture: in case 4 the realistic path is precisely the one that cannot express the test. Exactly-once is not right for every anchor: some assertions legitimately match text that repeats (a heading rendered per section, a token deliberately restated); the rule in 8 is that a pin guarding a SPECIFIC RULE must bind to something unique to that rule, and applying exactly-once blindly turns correct tests red. A conservative measurement error in 8 is not harmless: a gate that over-measures stays safe, but the recorded figure is what the next author trims against, and 'it errs in the safe direction' justifies not treating it as urgent, not leaving the number. Shape 8 is not about mutation technique — anchor validity and mutation validity are separate failures and a fix for one does not address the other. And sabotage is scoped to checks pinning a NAMED regression, guard or property — it is not a blanket ritual for every assertion in the suite.
