# NO STATIC ROUTE may be registered as a sibling of a `{param}` that holds a USER-CHOSEN NAME — it shadows the entity called that. Today that is /repos/{repo}, /lenses/{lens} and /branches/{branch}; the enforcing test covers only /repos/, which is a known gap

THE RULE, in its general form: a static segment must not be registered as a SIBLING of a `{param}` whose value is a user-chosen NAME. Such a segment is also a legal value for that param, chi prefers the static route, and the entity called that becomes unreachable there — with nothing about it diagnosable from the outside by whoever owns it. A new server-wide collection goes at a TOP-LEVEL path (`/repo-events`, `/repo-creates`) instead.

WHERE IT BITES TODAY — three subtrees, not one:

- `/repos/{repo}` — repo names, `[a-z0-9_-]` via `repos.IsValidName`.
- `/lenses/{lens}` — lens names, validated by the SAME function (`validateLensLocked`, `CreateLens`, `UpdateLens` all pass `l.Name` to `isValidRepoName`), so identical character set and identical collision property.
- `/repos/{repo}/branches/{branch}` — branch names, which the user also chooses.

The other ten `{param}` subtrees in the router are NOT in scope, because their params are not user-chosen names: `{id}` on `/archived`, `/repo-creates`, `/index-rebuilds`, `/synthesis-runs` and `/origin-sessions` is server-minted; `{sha}` is a commit hash; `{name}` on `/ontologies/presets` and `/domains`, and `{key}` on `/motifs`, are ours or derived rather than chosen. A static sibling there cannot collide with something a user named. **That distinction is the rule** — not the list, which will change.

AS OF bb1c5217 there are ZERO static siblings under any of the thirteen, so nothing is broken. This is a rule against reintroduction.

WHY BLUNT RATHER THAN CASE BY CASE. The cost of a collision is NOT uniform: a static LEAF costs exactly one method+path because chi backtracks, while a static segment with a PARAM CHILD costs the whole subtree below it, because the greedy child param matches the next segment and wins. That difference is invisible from "static beats param", and asking each new route's author to work out which case they are in is precisely how `GET /repos/events` shipped at 594b551a. The rule does not ask.

ENFORCEMENT, AND ITS KNOWN GAP — read this before trusting the test. `TestRouter_NoStaticChildrenUnderRepos` walks the router the server actually serves and fails on any static child, naming it. It is an EXCLUSION test: no list of known-bad names, cannot go stale as routes are added, catches a name nobody anticipated. **But it cuts on the `/repos/` prefix ONLY.** A static child added under `/lenses/` or under `/branches/` reproduces `/repos/events` exactly and NEITHER this fact's enforcer NOR anything else notices. Generalising it — loop the prefix check, or derive the prefixes from the walk by finding every `{param}` parent whose param is a user-chosen name — is scheduled work, not done. Until it is, treat `/lenses/` and `/branches/` as governed by this rule but unenforced.

Its companion `TestRouter_APIRootHasNoParamChild` pins what makes a top-level destination safe — shadowing needs a `{param}` SIBLING, and the API root has none. If a top-level `{param}` route is ever added, that test fails and every top-level static collection needs re-examining.

THE REJECTED ALTERNATIVE, recorded because it is the one that gets re-proposed: a reserved-name GUARD, refusing to create or rename an entity to a name that collides with a static route. Built to spec and overruled. A guard taxes every future static route with a permanent, USER-FACING prohibition — a list of names nobody may use, growing forever, each entry needing justification to whoever wanted it. Moving the route removes the possibility instead, and leaves a test that needs no maintenance. Prefer removing the possibility over prohibiting the collision.

AND WHERE A NEW SERVER-WIDE STREAM GOES is settled by the repo-event stream's membership test — is this about the entity as an entry in a list, or about content inside it? — not by adding a top-level path per feature. "Top-level" is where such a collection lives, not a licence to create one.

WHAT THIS DOES NOT SAY: it does not govern routes BELOW a param (`/repos/{repo}/branches`, `/lenses/{lens}/motifs`). Those sit under the param and shadow nothing. The rule is about SIBLINGS of the param, at that one level.

NOTE ON THIS FACT'S PATH: the category slug says `no-static-children-under-repos`, which is narrower than the rule. The slug is fixed; the title and this body are the claim. It was written for `/repos/` and generalised once the reviewer observed that the scope rule had been written as a membership test to decide unlisted cases while this one had been written as an enumeration of one.
