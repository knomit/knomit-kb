# NO STATIC ROUTE may sit beside a `{param}` whose value A USER CAN CAUSE TO EXIST — it shadows the thing named that. Six subtrees qualify today; the test derives them from the router and FAILS on an unclassified one

THE RULE: a static segment must not be registered as a SIBLING of a `{param}` whose value a user can cause to exist. Such a segment is also a legal value for that param, chi prefers the static route, and the thing named that becomes unreachable there — undiagnosably, from the outside, by whoever owns it. A new server-wide collection goes at a TOP-LEVEL path (`/repo-events`, `/repo-creates`) instead.

THE MEMBERSHIP TEST: **can a user cause a value with that name to exist — NOT does a user own it.** Ownership tracks how BAD a collision would be; only the first question decides whether one can happen, and that is what guarding turns on. A domain tag is owned by nobody and is still authored by whoever writes `domain: [stats]` in a fact's frontmatter, so `/domains/stats` would shadow something real.

THE SIX, as of 2d36336c:

```
/repos                                    {repo}    repo names
/lenses                                   {lens}    same validator as repo names
/repos/{repo}/branches                    {branch}  chosen at branch creation
/repos/{repo}/branches/{branch}/domains   {name}    authored domain tags
/repos/{repo}/branches/{branch}/motifs    {key}     authored motif keys
/lenses/{lens}/motifs                     {key}     the lens-scoped view of those
```

The two `/motifs` entries are DISTINCT parents, not one: a branch-scoped and a lens-scoped view, each shadowable in its own scope. Counting by last segment gives five and silently drops one. `/ontologies/presets/{name}` is deliberately OUT — those are our shipped preset names, which no user adds to.

CLASSIFIED BY PARENT PREFIX, NOT BY PARAM SPELLING, because one spelling holds two truths: `{name}` is product-fixed at `/ontologies/presets` and author-written at `/domains`. A table keyed by spelling cannot state both, and the first version hedged in prose instead of deciding. **An UNCLASSIFIED parent FAILS the test** — a new param subtree must force a decision, since defaulting to guarded would quietly forbid legitimate routes and defaulting to unguarded would quietly reopen the hazard.

WHY BLUNT RATHER THAN CASE BY CASE. The cost of a collision is NOT uniform: a static LEAF costs exactly one method+path because chi backtracks, while a static segment with a PARAM CHILD costs the whole subtree below it. That difference is invisible from "static beats param", and asking each new route's author to work out which case they are in is precisely how `GET /repos/events` shipped at 594b551a.

ENFORCED BY `TestRouter_NoStaticSiblingsOfUserNamedParams`, which walks the router the server actually serves, derives the `{param}` parents (nested ones included), and fails on any static sibling of a user-named one, naming it. It also asserts all six parents are FOUND — a tripwire on the DERIVATION, not its definition: without it, a refactor that renamed those routes would leave the test passing while guarding nothing. Its companion `TestRouter_APIRootHasNoParamChild` pins what makes a top-level destination safe: shadowing needs a `{param}` sibling, and the API root has none.

THE ANCHOR THAT SHOWS THIS IS NOT TIDINESS: at df8918cd the classification read `{name} → not user-named`, so `GET /repos/{repo}/branches/{branch}/domains/stats` would have PASSED the guard and shipped, shadowing an author-written domain tag. After the prefix-keying it fails by name. The scope correction bought real coverage.

THE REJECTED ALTERNATIVE, recorded because it gets re-proposed: a reserved-name GUARD refusing to create or rename an entity to a colliding name. Built to spec and overruled. A guard taxes every future static route with a permanent, USER-FACING prohibition — a list of names nobody may use, growing forever. Moving the route removes the possibility instead. Prefer removing the possibility over prohibiting the collision.

AND WHERE A NEW SERVER-WIDE STREAM GOES is settled by the repo-event stream's membership test — about the entity as an entry in a list, or about content inside it? — not by adding a top-level path per feature.

WHAT THIS DOES NOT SAY: it does not govern routes BELOW a param (`/repos/{repo}/branches`, `/lenses/{lens}/motifs` as PATHS). Those sit under the param and shadow nothing; they appear above only because they are themselves parents of a further param. The rule is about SIBLINGS of a param.

TWO NOTES FOR A READER WITH grep. `/repos/creates/{id}` appears in `router.go` ONLY IN COMMENTS — the `repo-creates` rationale and the measured chi table — and has never been a live route; a bare grep suggests otherwise. And this fact's category slug still says `no-static-children-under-repos`, which was accurate when it covered one subtree and is now too narrow; the slug is fixed, the title and body are the claim.
