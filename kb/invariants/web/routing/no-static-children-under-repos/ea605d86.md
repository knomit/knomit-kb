# NOTHING STATIC may be registered under /api/v1/repos/ — every static segment there is also a legal repo name and shadows the repo called that; a new collection goes at a TOP-LEVEL path, and the rule is blunt because the cost is not uniform

THE RULE: no static segment may be registered under `/api/v1/repos/`. A new server-wide collection goes at a TOP-LEVEL path — `/repo-events`, `/repo-creates` — never `/repos/<something>`.

WHY: repo names are `[a-z0-9_-]` (`repos.IsValidName`), so any static child of `/repos/` is ALSO a legal repo name. chi prefers the static route, and the repo of that name becomes unreachable there, with nothing about it diagnosable from the outside by the repo's owner.

WHY BLUNT RATHER THAN CASE BY CASE — the part that keeps the rule from being negotiated away. The cost of a collision is NOT uniform: a static LEAF costs exactly one method+path because chi backtracks, while a static segment with a PARAM CHILD costs the whole subtree below it, because the greedy `{id}` matches the next segment and wins. That difference is invisible from "static beats param", and asking each new route's author to work out which case they are in is precisely how `GET /repos/events` shipped at 594b551a. The rule does not ask.

PRECEDENT: `/repo-creates` was already a sibling collection for this reason — "creates" is a legal repo name — so this generalises an existing decision rather than inventing one.

ENFORCED BY `TestRouter_NoStaticChildrenUnderRepos`, which walks the router the server actually serves and fails on any static child, naming it. It is an EXCLUSION test: it needs no list of known-bad names, cannot go stale as routes are added, and catches a name nobody anticipated. Its companion `TestRouter_APIRootHasNoParamChild` pins what makes the destination safe — shadowing needs a `{param}` SIBLING, and the API root has none. If a top-level `{param}` route is ever added, that test fails and every top-level static collection needs re-examining.

THE REJECTED ALTERNATIVE, recorded because it is the one that gets re-proposed: a reserved-name GUARD, refusing to create or rename a repo to a name that collides with a static route. It was built to spec and overruled. A guard taxes every future static route with a permanent, USER-FACING prohibition — a list of names nobody may use, growing forever, each entry needing justification to whoever wanted it. Moving the route removes the possibility instead, and leaves a test that needs no maintenance. Prefer removing the possibility over prohibiting the collision.

AND WHERE A NEW SERVER-WIDE STREAM GOES is settled by the repo-event stream's membership test — is this about the repo as an entry in the repo list, or about content inside a branch? — not by adding a top-level path per feature. "Top-level" is where such a collection lives, not a licence to create one.

WHAT THIS DOES NOT SAY: it is not a claim about `/repos/{repo}/...` sub-routes, which are fine — they sit BELOW the param and shadow nothing. The rule is about siblings of `{repo}`, at that one level.
