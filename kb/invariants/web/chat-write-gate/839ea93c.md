# The chat routes (/chats and below) are exempt from writeGate's and readOnlyGate's POST/DELETE rule, like the MCP dispatch, because per-TOOL permission is enforced when a chat's call reaches the MCP server; a ReadOnly server does not mount them at all, so the exemption never reaches a demo instance

isMutatingRequest treats POST/PUT/PATCH/DELETE as writes except the MCP dispatch routes, a factset close and now chatRoutePattern, ^/api/v1/chats(/|$). Without the exemption a principal holding only Read gets 403 on POST /chats and on answering approvals, which would contradict the decision (Q2) that read-only principals chat and see only the tools the permission gate exposes to them.

The exemption widens nothing: a chat's side effects all pass the ordinary MCP tool path (gateBinding, gatePermission), so a read-only principal's knomit_learn is a permission tool error and nothing is written (TestChat_ReadOnlyPrincipalCanChatReads). The pattern is anchored: /api/v1/chatsfoo, /api/v1/chat-providers (a GET-only route) and any path that merely contains /chats stay gated.

A ReadOnly (demo) server mounts no chat route (Server.chatRouter returns nil), so POST /chats is a 404 there, not a 403.

Does NOT mean any chat route is safe to make write-capable: a new chat route that mutates knowledge directly would bypass the per-tool gate; chat never calls a handler or corpus API except through the InProcessSession.
