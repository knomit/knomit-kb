# A parallel lens fan-out reports the LOWEST-INDEXED failing mount — binding order, not completion order, and a panic does not outrank a lower-indexed error

RFC §9.1 says any mount error fails the whole lens request. Concurrency adds the question §9.1 never had to answer: WHICH error, when several mounts fail? A lens error names the failing mount's branch, so the answer must be deterministic — the LOWEST-INDEXED mount in binding order wins, regardless of which goroutine finished first and regardless of failure KIND: a panic in a higher-indexed mount does not outrank a lower-indexed ordinary error. Racing goroutines would otherwise make the user-visible error message a coin flip between runs.

Implementation shape (fanOutMounts, internal/web/lens_fanout.go, mirroring internal/mcp/query.go): results and errors land in per-mount indexed slots; the request goroutine checks slots in order only after wg.Wait(); panics are recovered into their slot as errors.

The sharp edge inside it: the recover handler must not itself be able to panic. It originally built its diagnostic from t.RT.RI.Name() — a field access — so a mount that panicked BECAUSE its RepoInstance was gone (nil) re-panicked the handler on the same nil and took the process down: the exact input class the recover was written for. The label is now built before the goroutine, behind a nil guard; reverting that one line makes the test binary segfault (sabotage-verified).

What this does NOT mean: it does not order SUCCESS results by completion — those are always assembled by slot index — and it does not apply to the still-serial /lenses/{lens}/facts fan-out, where errors surface in loop order naturally.
