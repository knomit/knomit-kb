# Lens REST identifies members by registry uid ONLY on input; responses carry {uid, name} and name is read-only

On `POST /api/v1/lenses` and `PATCH /api/v1/lenses/{lens}`, a member repo is named by an OBJECT carrying `uid` — the `repos(uid)` registry key — and by nothing else. `write` is `{"uid": ...}`; each entry of `reads` is `{"uid": ..., "branch": ..., "source": ...}`. Responses add a `name` field to the same objects, resolved server-side.

Three request spellings are each a 400 (`Unknown repo uid` / `Invalid request body`), never a 422:

1. `"write": "core"` — a bare name string. `lensMember.UnmarshalJSON` intercepts a JSON string and returns an error naming the fix; the stock decoder's "cannot unmarshal string into Go struct field" said nothing actionable.
2. `{"uid": "core"}` where no registered repo has that uid — `checkLensMembers` runs `Registry.Get` per named member before the manager sees the request.
3. `"reads": [{"repo": "beta"}]` — the pre-uid mount shape, which carries no uid at all. This is checked EXPLICITLY (empty read uid is a 400) because `Lens.normalize()` silently drops a read with an empty RepoUID: without the check the lens would be created quietly missing that mount.

An empty `write` uid is deliberately NOT covered by that check — it falls through to `ErrLensWriteEmpty` → 400 "Lens write repo required", a better message.

RESPONSE ORDER: `reads` is sorted by RESOLVED NAME, not by the uid the rows are stored under (`readsOf` is `ORDER BY repo_uid`, and uids are ksuids whose order within a second is arbitrary). This matches the mount order `NewBindingOfLens` already sorts to for the federation tie-break, so the editor's list and the lens's own results agree. Names for a whole response are resolved with ONE `Registry.List(StateActive)` into a uid→name map — never a `Get` per member, which on a listing was L×(M+1) reads on a `SetMaxOpenConns(1)` control DB.

CONSEQUENCE for a client: the only place a uid comes from is `GET /api/v1/repos`, whose rows now carry `uid` alongside `name` and `id`. A UI must hold uids internally and never show one; the lens editor (`web/src/CreateLensForm.tsx`, `LensSettings.tsx`) works in repo NAMES throughout and translates to uids at submit via a name→uid map built from the repo listing.

WHAT THIS DOES NOT MEAN: it does NOT mean the whole lens surface is uid-keyed. Only MEMBERSHIP is. The lens read endpoints' repeatable `repo=` narrowing parameter (`/lenses/{lens}/facts`, `/search`, `/stats`, `/browse`) still takes mount NAMES matched against `Binding` mount names, and `state.lensSources` in the web UI holds names for exactly that reason. Fact ADDRESSING is a third namespace, the root-commit `kb://<id12>/…` form.

It also does NOT mean `repos.ErrRepoNotFound` → 422 is dead. That arm survives for the race the handler check cannot close: a member archived between `checkLensMembers` and `Manager.validateLensLocked`. The split is 400 = "that is not a repo uid", 422 = "that IS a registered repo but cannot be a lens member".

RESPONSES ALSO CARRY THE LENS'S OWN UID (facets PR A, 2026-10): `GET /api/v1/lenses` items and `GET /api/v1/lenses/{lens}` carry `uid`, the lens's registry identity (`lenses.uid`, `lensView.UID`), minted at create, never reused and unchanged by a rename. It is the spelling session bindings use (`lens:<uid>`), which the web UI's Activity facet needs to filter sessions with `?binding=lens:<uid>`; filtering by name would break across a rename. Do not confuse it with `write.uid` or `reads[].uid`, which are MEMBER repo uids (the lens-uid test asserts it differs from its write member's). `decodeJSON` accepts unknown fields, so a client that echoes a lens view (`uid` included) into a PATCH body is not refused; membership input is still the object form above.

ALSO "Unknown repo uid" (PR #680): a NEW member — one the lens does not already have — whose repo the caller's credential does not reach by name gets exactly the same 400 body as a uid no repo has, so a confined token cannot probe which uids exist. See kb/invariants/lens/membership/add-needs-reach/bc6a8362.md.
