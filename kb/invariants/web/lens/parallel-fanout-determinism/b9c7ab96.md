# A parallel lens fan-out reports the LOWEST-INDEXED failing mount, reduces in binding order, and must never let naming a mount be the thing that panics

A concurrent lens fan-out must produce a response that is a function of the REQUEST, never of which mount finished first. Three rules, each with a failure that is invisible in ordinary testing.

1. REDUCE IN BINDING ORDER. Goroutines write only their own indexed slot; the reduction runs afterwards on the request goroutine, walking targets in order. Never append from inside a goroutine — a mount's INDEX is its identity to federate.FuseRRF and federate.WriteFirstWinners, so collecting results as they arrive re-maps every row's mount, changing both the fused order and which copy of a cross-mount duplicate wins.

2. REPORT THE LOWEST-INDEXED FAILURE, not the first to arrive. RFC §9.1 (any mount error fails the whole request) was already satisfied by a serial loop; what parallelism ADDS is the question of WHICH error a caller sees when several mounts fail. A lens error names the offending mount's branch, so first-to-fail makes that message a coin-flip between runs. Lowest index is what the serial loop would have hit. This ordering is by INDEX, not by failure KIND: a panicking high-index mount must not outrank a lower-indexed ordinary error.

3. NAMING A MOUNT MUST NOT BE ABLE TO PANIC. Build the mount's label BEFORE the goroutine and without dereferencing anything that may be absent. `RepoInstance.Name()` reads a field, so it panics on a nil instance — and a nil instance is the archive/shutdown race the recover exists to survive. Building the recover's message from it meant the handler failed on precisely the input it was written for, and the second panic escapes the goroutine and kills the PROCESS (net/http recovers panics on the request goroutine only, so a panic in a bare fan-out goroutine is not one connection but the server).

WHAT THIS DOES NOT MEAN: byte-identical captures are not evidence for any of this. A single capture per binary samples nondeterminism once. The evidence is forced-delay tests that INVERT completion order against binding order — the slowest mount placed first, the write mount made slowest while sharing a path with a read mount that finishes first.

WHERE IT LIVES NOW (PR #704, re-read at the merge 8f34e391): the concurrent fan-out is ONE function, `federate.FanOut` in internal/corpus/federate/fused.go. It reduces in index order, reports the lowest-indexed failure as `*MountError{Mount, Err, Panicked}`, and builds a nil-safe label before the goroutine.
- The fused lens read (`FusedSearch`/`FusedRecent`) runs on it. That read serves REST /lenses/{lens}/search and MCP knomit_query, relevance and sort=recent alike.
- REST `fanOutMounts` (lens_fanout.go) is now a thin wrapper that adds the problem title ("Mount failed" on a panic).
- MCP's own goroutine loops and `recoverFanout` are gone. They violated rule 3: `defer recoverFanout(mountLabel(t.RT), ...)` evaluated `rt.RI.Name()` before the recover was armed.
- Exception: REST /lenses/{lens}/facts still reads its mounts SERIALLY (`FusedOptions{Serial: true}`), as it always has. There the first failure stops the loop, which is also the lowest index, and a panic is not recovered.
- The forced-delay evidence this fact asks for is in the fused-search goldens on both edges (kb/conventions/testing/lens/fused-search-goldens/6eaab660.md) and in TestFusedSearch_LowestIndexedFailureWins.
