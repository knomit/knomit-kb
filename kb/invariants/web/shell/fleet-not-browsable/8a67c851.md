# The fleet repository is never a browse context: GET /repos rows carry `fleet: true`, browsableRepo excludes them everywhere a context is picked, and the fleet's only page is the fleet rail target

Built in PR #528 (verified at merge e417fd76). The server marks the instance's fleet repository on GET /repos with `fleet: true` (absent on every other row). The web app uses `browsableRepo` (repoAvailable && !fleet, web/src/repoSelection.ts) in pickRepo, resolveLens and refreshContextAfterChange, so a remembered or default context never names the fleet repository; an effect in App moves a context that does name it to a browsable repository (or none) and shows the fleet target. `noRepos` is `reposLoaded && !repos.some(r => !r.fleet)`: a fleet-only instance is the ZERO-REPOSITORY shell (the repository draft is the page and the rail is forced open only while that draft is on screen, `railShown(view, noRepos && displayed.kind === 'draft')`), and the rail never lists the fleet repository as a repository row.

WHY: the fleet repository has no generic page (browse, settings and every mutation are refused or meaningless; the fleet repository is changed only through /fleet), so a context on it 404s or shows a dead end. Before the fix, after Leave a remembered context named the fleet repository and the console 404'd until the shell recovered.

CONSEQUENCE: any new code that picks a repository from GET /repos must use browsableRepo (or r.fleet) rather than repoAvailable alone. MISREADING: the fleet is not hidden from the UI; it is a rail TARGET of its own with Members, Activity and Settings tabs (see the facets decisions).
