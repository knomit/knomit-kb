# App re-reads GET /repos (list-only, never refreshLists) when a create job is registered or done AND its repo is not in `repos`, at most once per (create_id, point) for the two points registered and done; cancelled and failed jobs never trigger it

App.tsx has an effect over `creates` (the shared 2 s creates poll) and `repos`, gated on `reposLoaded`. A job triggers it only if all of these hold: it is NOT cancelled; it is NOT failed; it is registered (createRepoIsRegistered: it has an index_state, or its step is index or done; or its state is done); and its repo is not listed (createListedIn from useRepoCreates.ts: name OR repo uid in `repos`, the very test pendingCreates applies). This is what turns a create started by ANOTHER client (another tab, the CLI, a peer) from a pending 'created' rail row into a real repo row, and puts it in the lens draft's mounts, with no click (#469).

The trigger is REGISTRATION, not only done. A foreign create is listed (with its 'creating' chip, via activeCreateByRepo) while it is still indexing, exactly like one started in this tab.

The re-read is LIST-ONLY: api.repos() then setRepos, nothing else. It must NOT be refreshLists. refreshLists runs refreshContextAfterChange, which is a context re-sync. During boot, reposLoaded is set before boot dispatches SET_CONTEXT, so a refreshLists fired then dispatched SET_REPO for the first readable repo; that landed after boot's SET_CONTEXT, replaced the remembered or URL context, and was written to localStorage (reproduced in review of #755). In a lens context it also re-resolves the lens (SET_LENS) and dispatches the write branch's statusAction with no guard against the reader having left it. Lenses are not re-read either: a create adds no lens, and a late lens list landing after a rename's refreshLists would bring the old name back and let the auto-unpin effect drop a renamed brokenLens pin. A lens whose broken mount is this repo is repaired by `repos` alone (brokenLensMember reads repos).

The read is guarded by TWO counters, both SNAPSHOT when it starts and NEITHER bumped by starting it (bumping repoListGen there used to retire a reconnect read already in flight). repoFullGen moves on every write of a WHOLE repo list: boot's setRepos, refreshLists' setRepos, the repo-events reconnect re-read, and this read when it replaces. repoListGen moves on every stream event patch (index state, remote health). When the answer lands: (1) repoFullGen moved -> DROP the answer entirely, because a newer whole list landed and anything written from the older answer, even 'add the missing rows', can bring back a repo that list removed (purged, archived, deleted and seen by a reconnect) or put a renamed repo's old name beside its new one; the done point is the retry if that list still lacked the new repo. (2) Only repoListGen moved -> ADD the rows the list lacks (mergeMissingRepos, matched by name OR uid like createListedIn), in the server's order, keeping every held row exactly as the events made it; not dropped, because index events for the new repo itself arrive all through its index and would void nearly every read. (3) Neither moved -> REPLACE `repos` and bump repoFullGen. Consequence: any NEW code path that writes a whole repo list must bump repoFullGen, or a held foreign-create read can overwrite or resurrect against it; a path that patches rows bumps repoListGen instead. Added rows go in server order, not appended, because pickRepo falls back to the first readable repo.

The once-per-(create_id, point) guard: a ref holds the keys already tried, the points being 'registered' and 'done'. A job first seen already done claims both in one read. The done point is the retry for a registered-point read that failed (the catch swallows it) or answered before the repo was listable. The cap exists because 'registered and not listed' can stay true across polls: the list may lag the job, and a server that predates the done-job pruning (create_job.go omits a done job whose repo uid is no longer registered) keeps a deleted repo's job listed for about an hour. Without the cap each of those is a /repos read every 2 s. Consequence: do not drop the guard, and do not key it on create_id alone. If you change pendingCreates' listed test, change createListedIn: they are one function so the rail and this effect cannot disagree about which jobs are pending.

WHAT THIS DOES NOT MEAN: the repo-events stream does NOT announce new repos. It still only patches rows already in `repos` (index state, remote health) and re-reads the list on reconnect. A new repo reaches `repos` through this effect, refreshLists or the draft callback. It also does NOT remove a repo a foreign create registered and then cancelled: the server omits cancelled jobs from the list and this effect skips them, so such a row stays until the next refreshLists or reconnect. And it does NOT mean a foreign read that replaced the list is final: refreshLists still writes its own answer without any generation check, so a refreshLists answer that was in flight when the foreign read replaced the list overwrites it, and if that answer predates the registration the new repo drops out again. The done point then restores it (it is unlisted when the job reaches done), EXCEPT for a job first seen already done: it claimed both points in its one read, so it stays a pending 'created' row until the next refreshLists or reconnect.

Pinned `pending` targets: the auto-unpin effect has no `pending` case, so the re-read does not unpin it. PendingCreateSettings checks /repos itself and hands over via onCreateRegistered, as before this change.
