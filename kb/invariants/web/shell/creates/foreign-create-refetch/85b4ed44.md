# App re-reads the lists (refreshLists) when a create job is registered or done AND its repo is not in `repos`, at most once per (create_id, point) for the two points registered and done; cancelled and failed jobs never trigger it

App.tsx has an effect over `creates` (the shared 2 s creates poll) and `repos`, gated on `reposLoaded`. For every job that is NOT cancelled, NOT failed, is registered (createRepoIsRegistered: it has an index_state, or its step is index or done; or its state is done) AND whose repo is not listed (createListedIn from useRepoCreates.ts: name OR repo uid in `repos`, the very test pendingCreates applies), it calls refreshLists() to re-read repos, lenses and archived. This is what turns a create started by ANOTHER client (another tab, the CLI, a peer) from a pending 'created' rail row into a real repo row, and puts it in the lens draft's mounts, with no click (#469).

Trigger is REGISTRATION, not only done: a foreign create is listed (with its 'creating' chip, via activeCreateByRepo) while it is still indexing, exactly like one started in this tab.

The guard: a ref holds the (create_id, point) keys already tried, points being 'registered' and 'done'. Each fires at most once per create; a job first seen already done claims both in one refetch. It exists because the condition can stay true forever: a done job outlives its repo on the server (about an hour), so a repo deleted or renamed elsewhere leaves a job that is 'registered and not listed' on every poll. Without the guard that is a refetch every 2 s for an hour. Consequence: do not drop the guard, and do not key it on create_id alone (the done point is the retry for a registered-point read that refreshLists swallowed). If you change pendingCreates' listed test, change createListedIn: they are one function so the rail and this effect cannot disagree about which jobs are pending.

WHAT THIS DOES NOT MEAN: the repo-events stream does NOT announce new repos. It still only patches rows already in `repos` (index state, remote health) and re-reads the list on reconnect; a new repo reaches `repos` through this effect, refreshLists or the draft callback. It also does NOT remove a repo a foreign create registered and then cancelled: the server drops cancelled jobs from the list and this effect skips them, so such a row stays until the next refreshLists or reconnect.

Pinned `pending` targets: the auto-unpin effect has no `pending` case, so the refetch does not unpin it; PendingCreateSettings checks /repos itself and hands over via onCreateRegistered (one more refreshLists, harmless).
