# A chat target's tabs are Chat and Settings and come only from facetsFor (CHAT_FACETS); TopBar has no chat tab logic, only a label and an icon

facetsFor({kind:'chat'}) returns exactly CHAT_FACETS = ['chat','settings']; a repo target's tabs stay ['browse','activity','settings'] and never contain 'chat'. TopBar draws whatever facetsFor returned through FACET_LABEL ({chat:'Chat', settings:'Settings'}); the only chat-specific code in TopBar is the crumb's label colour and icon (TargetLabel kind 'chat'), never which tabs exist. The icon is the provider's mark picked by the provider's kind (ProviderIcon, from target.provider {name, kind}, which targetLabelFor looks up in GET /chat-providers); a chat's crumb has no chip, and the configured provider name is only the mark's accessible name and tooltip. A kind with no mark, or a provider not yet listed, keeps the generic chat glyph. A chat has no store to browse and no sessions page of its own, so a missing facet is omitted, never disabled.

The facet rule in facets.ts handles the move: landingFacet sends a target whose first facet is 'chat' to 'chat', and sends a reader leaving the chat's 'chat' facet to a target with Browse to 'browse'. The 'chat' facet is not persisted (useViewState skips it, like 'members'), so a reload never lands on a Chat tab the stored value cannot name.

Consequence: to add or remove a chat tab, change CHAT_FACETS in facets.ts and nothing in TopBar. Misreading to avoid: Settings on a chat is the CHAT's Settings (its approval grants, GET /chats/{id}/grants), not the repo's SettingsFacet; App renders ChatFacet for a chat and excludes kind 'chat' from the Browse, Activity and repo Settings bodies.
