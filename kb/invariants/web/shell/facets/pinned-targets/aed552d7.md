# A pinned pending-create target carries its own name, because the server omits cancelled jobs from the creates list and the top-bar label cannot look the job up afterwards

PinnedTarget {kind:'pending'} is {createId, name}. TargetRail sets name from the job when pinning. targetLabelFor reads job?.name ?? target.name: the live job still supplies the chip, but the name must come from the pin once the job has left the shared creates list. The server omits a cancelled job from GET /repo-creates (only GET by id still serves it), so after a cancel the job is not in the list while the pin remains; PendingCreateSettings refetches by id for the same reason. Consequence: any new construction of a pending pin must pass the name; do not derive the label from the creates list alone. Pins are never persisted, so no old pin without name can be read back. Does NOT mean the chip persists after cancel: createFlag('cancelled') is null by design.
