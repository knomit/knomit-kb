# A pinned target must be in its backing list (archived, lenses, repos, fleet.fleet_repo) no later than the render it is set or renamed, or App's auto-unpin effect drops it at once

App.tsx has an effect that unpins any pinned target its backing list does not hold: an archived pin whose id is not in `archived` (once `archivedLoaded`), a brokenLens pin whose name is not in `lenses` (once `reposLoaded`), an unavailable pin whose repo is not an unavailable entry of `repos`, a fleet pin once GET /fleet names no `fleet.fleet_repo`. The effect runs after every render where the pin or a list changed, so the list must hold the pin's subject no later than the render the pin is set or renamed in (the same render, or an earlier one: the archive fix seeds the list one render before the pin). Two ways to break that, both bugs fixed in #476:

1. Setting a pin whose row only exists if a re-read succeeded. `refreshLists` swallows a failed `api.listArchived()` while `archivedLoaded` is already true from boot, so `onUnavailableArchived` pinned an id the stale list lacked and the effect removed it immediately. Fix: merge the row the server returned into `archived` (replace by id, else add) BEFORE refreshing; a successful re-read still replaces the whole list and holds the row. The archived Settings page (SettingsFacet) also looks the row up in `archived`, so without the merge it would render nothing even if pinned.

2. Changing the list so the pin's key disappears. A rename re-reads `lenses` without the old name. Re-pinning before the new list lands makes the new name look gone against the old list; re-pinning after lets the effect unpin first. Fix: `refreshLists` dispatches `RENAME_PINNED_LENS {from, to}` in the same synchronous block after the await as `setLenses`, so React 18 batches them into one render.

Consequence: any new code that pins a target, or that mutates a list a pin is keyed on (rename, re-read, purge), must never let the pin get ahead of the list, either by seeding the list with the server's row first or by dispatching the view change next to the setState with no await between them. Do not 'fix' such a race with a timing exception in the effect (e.g. skipping the gone check for a just-set pin); the issue suggested that and it was rejected.

Also: re-pinning by SELECT_PINNED is not neutral. It is a pick: it closes the server pages (server: null) and runs the facet rule. A rename uses RENAME_PINNED_LENS, which changes only the brokenLens pin's name (and the pin held in returnTo for a draft's Cancel) and matches on `from` in the reducer, so a late rename for a pin the reader has since left changes nothing.

Not meant: this does not say the effect is wrong to unpin; a pin whose subject really vanished elsewhere (purged, deleted) must still be unpinned.
