# origins.Mount takes an optional *sync.WaitGroup and still returns nothing: Mount Adds one and marks it Done only after the manager's close has finished, so 'released' means every session store closed and folder removed, the run dir and lock file removed with the lock handle closed, and the startup sweep finished

Mount (mount.go) calls released.Add(1) synchronously, then registers a context.AfterFunc on ctx that runs sm.close() and then released.Done(). Internally the signal is sessionManager.released, closed in shutdown after every session is finalized (store closed, folder removed), the run dir and lock file are removed with the lock's handle closed, and the startup sweep has finished (shutdown waits on staleDone right after sm.live.Wait() and BEFORE it removes the run and closes the lock, because that sweep holds handles in the base while it runs: the ReadDir, and a lock file it probes; so the sweep and shutdown are never two removers of one lock file, and on Windows a probed file cannot be unlinked. It is not the last step of shutdown). close() is a sync.Once and a concurrent caller returns only when the first call has finished, so Done always follows a complete shutdown.

Removal after ctx ends is still asynchronous. The WaitGroup is how an owner that deletes the sessions dir (or the temp dir a '' manager uses) waits for that removal. While ctx is live no goroutine waits on it. Today only web's tests wait on it, through Server.originSessionsReleased, which is unexported on purpose. A first attempt that made Mount RETURN a channel was refused by the archtest (TestWebAPI_ExportsOnlyMount: Mount has no results).

App.Close does NOT wait. Waiting would make `knomit serve`'s exit block on a handler still running after the 5 s Shutdown grace (cmd/serve.go serveUntil). That is safe: process exit frees the handles and the next start reclaims the dead run (kb/invariants/web/origin-sessions/8bab8ef0.md).

DOES NOT MEAN that App.Close returns with the origin-session files gone. Also: when a Server has no Lifetime, originSessionsRouter passes Mount a nil WaitGroup (Mount skips the Add and the AfterFunc), so Server.originSessionsReleased stays at zero and Wait returns at once. That does NOT mean the manager was released: with no Lifetime the manager never releases and holds its files for the process's life. A return from Wait on such a Server proves nothing about files.

Test: TestSessionManager_ReleasedMeansNothingIsHeld holds the startup sweep, with the dead run's lock file open, on a gate the test owns (runHooks.reclaimOpened, through newSessionManagerHooked), not on the 50 ms runProbeWait timer, so the sweep is still running when the lifetime ends however slow setup is. Removing the staleDone wait from shutdown fails it 20 of 20 runs under -race with a concurrent `go test -race ./internal/corpus/repos/...` load. The one timed wait is a 1 s window in which a shutdown that skipped the sweep would close released; it is a window, not a synchronisation sleep, and the gate is opened only after it.
