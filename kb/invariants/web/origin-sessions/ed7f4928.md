# The origin-session map is a plain map under ONE mutex, and every eviction is decided and applied in the same critical section, so a sweep or Delete removes exactly the session instance it examined, never a newer one that reused the repo key

BEFORE. The map was a sync.Map and Create did LoadAndDelete, then MkdirTemp, then Store, so two Creates could both store and orphan a folder; runCleanup deleted by key after an unlocked check, so it could evict a newer session that had reused the repo key. The sweeper's flag lived under a separate sweepMu.

NOW. sessions is a plain map[string]*originSession under sm.mu together with the sweeping and closed flags. Create replaces and stores in one critical section; Delete removes only if the session in the map is the exact ID named; runCleanup finds and evicts the expired instances in the same section. Dropped sessions are retired AFTER mu is released (no IO under mu). ensureSweeperLocked runs under mu after the store, and the sweeper's exit check (stopIfEmpty) is under mu too, so a session stored concurrently with the sweeper's exit is always swept.

DOES NOT MEAN: that session folders may be made under mu. They are made before it is taken precisely so no IO happens under it.

TEST. TestSessionManager_ConcurrentLifecycleLeavesNoOrphanFolder (-race -count=50): the folders on disk must be exactly the held sessions' folders. Sabotage results: unlocking between replace and store, red 49-50/50; evicting by key after the folder removal, red 50/50; evicting by key right after re-locking, red about 30/50, caught only across many runs.
