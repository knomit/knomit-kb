# Every REST read route of the knowledge base (/search, /facts, topics, changes, commits, activity, completions, domains, motifs, stats, events, triggers, the fact reads; the lens reads) and, since #728, of the management API (repos, branches, experiments, origin, templates, lenses, archived, repo-creates, fleet, ontologies, repo-events) answers 400 to an undeclared or malformed query parameter, from ONE declared set per route (httpx.DeclaredParams) pinned against openapi.yaml

User ruling 2026-11-02: a REST list route answers 400 to a query parameter it does not declare, never ignoring it silently. Since PR #718 (merged as 18fa59a6), the four list routes enforce it through internal/edge/web/api/kb/params_declared.go:
- One declaredParams per route: repoSearchParams, repoFactsParams, lensSearchParams, lensFactsParams. Each lists the route's openapi.yaml query parameters, aliases (q/query, entity/entities) and paging (limit, offset) included. A name spelled `context.<key>` declares the context.* family.
- Each handler calls refuseUnknown first (since #728 spelled httpx's (DeclaredParams).RefuseUnknown; see EXTENDED (PR #728) below). It parses r.URL.RawQuery with url.ParseQuery; a malformed query string (a bad %-escape, a `;` separator) is a 400 "Invalid parameter" with detail `malformed query string: <parse error>`, because r.URL.Query() would drop such a pair silently. It then answers the first undeclared parameter in name order with 400, title "Invalid parameter", detail `unknown parameter "<name>"`. That is the FactSet routes' text (factsetRequest), so the five routes refuse alike.
- TestListRouteParams_MatchOpenAPI (kb) compares each set with the route's spec parameters. TestListRoutes_UnknownParamIs400_DeclaredParamsAccepted (web) sends every spec-declared parameter to each route and gets 200, except since_fork, which is accepted but refused "Not an experiment" on a non-experiment branch. It also sends an unknown one and gets the 400.
- web/src/listRouteParams.test.ts reads each route's declared set from openapi.yaml. It captures the real requests of api.search, api.recent, lensSearch and listLensFacts (mocked fetch, every option set) and checks that every name sent is declared.
- since_fork is declared as string enum ["true", "1"], what the handler turns on; any other value leaves the list unnarrowed.

What the switch-on found:
- since_fork was read by repo /search and /facts but not declared. The web client sends it inside an experiment. It is declared now.
- sort=recent was sent to repo /facts by the web client (api.recent) and by the bridge (tools/bridge/knomitapi/facts.go), but not declared. It is declared now with enum [recent]. Any other value is 400 `sort must be "recent"`. `sort=recent` does NOT force date order: the order is newest first, but with `q` the list is ranked by relevance, recency breaking ties (recentFactsSearch), with or without sort. So the value is validated but changes nothing. The user ruled (2026-11-02, #718 review M2) to keep `sort` declared on repo /facts, accepting only `recent`. The two 400 details, `sort must be "recent"` and `malformed query string: <parse error>`, are ruled final copy: do not reword them without asking.
- The branch HAL template advertised search{?q,limit,cursor}, but /search never took cursor. The template is now {?q,limit}.

RULE: to add a parameter to any of these routes, add it to its declared set AND to openapi.yaml in the same change; the test fails on either alone. Clients (web, bridge, knomit.io's vendored api.ts) must not send speculative parameters.

EXTENDED (PR #720, merged as 543c66f8; user ruling 2026-11-02): every OTHER knowledge-base GET route refuses the same way, from one declared set per route in internal/edge/web/api/kb/params_declared_kb.go:
- Repo branch routes: topics and topics/{path} (with their /facts and /stats sub-resources), changes, commits, commits/{sha}, commits/{sha}/facts/{path}, commits/{sha}/topics[/{path}], activity, completions, domains, domains/{name}, motifs, motifs/{key}, stats, events, triggers, and the fact read GET /facts/{path}.
- Lens routes: facts/{path}, completions, motifs, motifs/{key}, stats, topics[/{path}].
- Same texts as the four list routes; TestKBRouteParams_MatchOpenAPI pins each set to the spec; TestKBRoutes_UnknownAndMalformedAre400_DeclaredAccepted checks every route; web/src/listRouteParams.test.ts checks every web client call to them against the spec: the api.ts reads, api.factDiff, materializeApi.page (first and cursor calls) and exportMarkdown, and App's branch /events stream, whose URL is built by branchEventsUrl.
- The fact routes (repo, commit-anchored, lens) pick the set by what the path addresses (refuseUnknownFactPath): the fact read and its /incoming and /outgoing take none (fallback at a commit), /commits takes limit/after/from/before, and the /materialize and /materialize/pages terminals keep their own older unknown-parameter text ("unknown parameter X; valid parameters are …"), with the malformed-query 400 (refuseMalformed) in front.
- The check runs BEFORE the raw .knomit/ system-file read and the private-path refusal, so those paths refuse unknown parameters too. A raw system file (fact.IsSystemFilePath, bare or kb://-qualified on the lens: isSystemFileRequest) is decided FIRST and takes factReadParams (none), whatever its last segment is. So `.knomit/x/commits?limit=5` and `.knomit/x/materialize?bogus=1` are 400 on the repo, commit-anchored and lens routes (TestKBRoutes_SystemFilePathTakesTheFactReadSet). Checking the sub-resource suffix first would hand such a file the /commits or /materialize set.

EXTENDED (PR #728, merged as 0db5b76f; user ruling 2026-11-02): every GET route of the management API (internal/edge/web/api/manage) refuses the same way, with the same two texts.
- The mechanism MOVED: api packages export only Mount, so manage cannot import kb. The type, its builder and both refusals now live in internal/edge/web/httpx/params_declared.go as httpx.DeclaredParams, httpx.DeclareParams, (DeclaredParams).RefuseUnknown, httpx.RefuseMalformed and (DeclaredParams).Names (the OpenAPI spelling, for the spec tests). kb's declaredParams/declare/refuseUnknown/refuseMalformed no longer exist. kb keeps its per-route sets in params_declared.go and params_declared_kb.go and calls the httpx helpers. A source-scanning allowlist names the call: internal/engine/store/changes_guard_test.go lists changesParams.RefuseUnknown.
- Manage sets: internal/edge/web/api/manage/params_declared.go, one per GET route. Each handler calls RefuseUnknown first (the handlers are not wrapped, so route_table.golden is unchanged). The 23 routes are /repo-events, /fleet, /fleet/members, /fleet/activity, /fleet/root, /archived, /archived/{id}, /repos, /repo-creates, /repo-creates/{id}, /ontologies/presets, /ontologies/presets/{name}, /ontologies/schema, /templates, /repos/{repo}, /repos/{repo}/templates, /repos/{repo}/origin, /repos/{repo}/branches, /repos/{repo}/pushed-branches, /repos/{repo}/experiments, /repos/{repo}/branches/{branch}, /lenses and /lenses/{lens}. Only /fleet/activity declares a parameter (limit); every other set is empty.
- Ordering: middleware runs first. /fleet/root's RequireLocalVia 403, RepoMiddleware's unknown-repo 404 and the fleet-repo gate all answer before the parameter check does.
- Tests:
  - manage.TestManageRouteParams_MatchOpenAPI pins each set to the spec and requires a GET for each route in openapi.yaml. GET /repo-creates and GET /repos/{repo}/experiments had no spec entry and were added.
  - web.TestManageRoutes_UnknownAndMalformedAre400_DeclaredAccepted drives all 23 routes through the real router over the local listener. It also fails if any GET whose handler is in package manage has no row (walkFull), so a new manage GET route without the check is caught.
  - web/src/listRouteParams.test.ts checks every web client read of a manage GET (api.status for the branch root included), plus subscribeRepoEvents' URL, against the spec. Each manage row also asserts that the request path matches the spec route it is checked against, so a function pointed at another route fails instead of being checked against the wrong parameter list.
- openapi.yaml's top-level info.description note on the two 400s names the manage GET routes alongside the knowledge-base ones. Update it with any route added to either set.
- Caller survey at the switch-on found that no client sends a parameter to a manage GET: web, tools/desktop, tools/bridge, `knomit fleet` and e2e. So nothing was declared for compatibility. The only casualty was a test that sent GET /fleet?local=true as a spoof; that request is now a 400.

WHAT THIS DOES NOT MEAN: the write routes (POST/PUT/PATCH/DELETE, on kb and manage alike), the jobs routes (synthesis-runs, index-rebuilds, in api/jobs), the MCP endpoints, and the routes outside the api packages (e.g. /sessions, /logs/events, /version, registered directly in internal/edge/web) still ignore undeclared parameters silently.
