# Commit indexing uses THREE tables: commit_log (per-path) + branch_commits (visibility) + commit_parents (DAG edges)

Commit indexing is split into THREE tables matching git's separation of commit facts, branch visibility, and DAG structure:

(1) **commit_log** — branch-agnostic per-path log. One row per (commit_hash, path), records timestamp/message/operation/author/action. Immutable once written. PK = (commit_hash, path). Used for activity aggregates and per-path history queries.

(2) **branch_commits** — branch visibility. Many-to-many, one row per (branch_id, commit_hash). Records which branches see which commits. ON DELETE CASCADE on branch_id so dropping a branch reclaims visibility rows. Branch creation clones the parent's visibility set via one INSERT OR IGNORE … SELECT — O(rows) at creation, zero copying afterward. All read paths JOIN through this table.

(3) **commit_parents** — DAG edges. One row per (commit_hash, parent_order, parent_hash). parent_order = 0 is the first parent (git's 'ours' side on a merge). Powers the recursive-CTE walk in resolveActiveCommitForPath and resolveTargetCommit. Replaced the first_parent_chain virtual table (retired in PR #67) whose Go-side cursor callback re-entered the *sql.DB pool and deadlocked under concurrency.

All three are populated atomically per commit inside Storer.CommitLogSync's transaction — there is exactly one chokepoint for commit indexing. commit_log entries can be empty (visibility-only commits) but branch_commits + commit_parents rows are always written. Anti-pattern: writing to any of the three outside CommitLogSync — the transactional grouping is what guarantees consistency.

ORIGINAL DESIGN WAS WRONG: PK on commit_log was (commit_hash, path) with a branch_id column — shared commits could only carry ONE branch_id, so INSERT OR IGNORE silently dropped rows for the second branch. Discovered 2026-04-08 (commit 4fd7d4d). Two-table split was the first fix; commit_parents was added 2026-05-25 as part of the vtable retirement.
