# Every branch-ref mutation MUST call vcs.Repo.NotifyCommit (rh.NotifyCommit from the parent) while holding the branch lock

Every mutation that advances a branch ref MUST call NotifyCommit(ctx, branch, hash) — vcs.Repo.NotifyCommit in internal/store/internal/vcs/branch_commit.go since hier-07, reached from the parent as rh.NotifyCommit through the embedded *vcs.Repo (formerly repoHandler.notifyCommit) — while still holding the per-branch write lock. NotifyCommit does four things in order: (1) AppendCommitLog(ctx, branch, hash) — branch-agnostic commit_log row + branch_commits visibility row; (2) im.Sync(ctx, branch) — brings branch_facts / facts_vec / graph in sync with the new tree (skipped when no index manager is set); (3) touchExperimentActivity(ctx, branch); (4) onCommit(branch, hash) external observer (e.g. SSE). The index manager and onCommit are injected by the parent as values (SetIndexManager, SetOnCommit); the child never calls up. Mutation paths that call it (at dev tip d4fbf2fb): facts.Index.writeFileExact / deleteFile / batchWrite in internal/store/facts/fact_write.go (the facts child; rh there is the same shared vcs.Repo), merge.Repo.MergeIntoBranchLockedOpts in internal/store/merge/branch_merge.go (the fast-forward and the 3-way merge; reconcileAgentMerge in remote_reconcile_merge.go reaches it through rh.MergeIntoBranchLocked and has no NotifyCommit call of its own), remote_reconcile_rebase.replayOntoUpstream. Skipping notifyCommit leaves SQL stale relative to git — trips Verify's facts-coherence check. The list above is not exhaustive: at d4fbf2fb rh.NotifyCommit is also called from internal/store/merge/experiment_rewind.go (the rebuilt experiment), httphandler_receivepack.go, peer_admit.go, remote_reconcile.go, service_sync.go and service_facts.go (Service.WriteSystemTree, which calls facts.Index.BatchWriteLocked under rh.LockBranch and then rh.NotifyCommit itself). Anti-pattern: advancing a ref via storer.SetReference without immediately calling NotifyCommit.
