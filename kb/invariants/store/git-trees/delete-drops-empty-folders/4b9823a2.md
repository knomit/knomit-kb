# deleteFromTree is the single funnel for every knomit tree deletion: it drops a folder the delete empties (cascading, never the root), never stores the dropped empty tree, and treats a missing path as a no-op

Every knomit delete builds its new tree through deleteFromTree in internal/store/plumbing.go. The callers are:
- deleteFileFromStore, used by DeleteFact
- batchWriteLocked, used by BatchWriteFacts, BatchWriteFactsMustExist, learn's retract and the F04 move
- mergeTreesWithStrategy's src-delete
- applyResolution's src-delete

Since PR #389 (merged as fa1b6d03), deleteFromTree behaves as follows:

1. DROP, NOT EMPTY. A folder left with no entries is removed from its parent, and the removal cascades: deleting kb/x/y/only.md drops kb/x/y, then kb/x if y was its only entry. The ROOT is never dropped; an empty root tree is stored and is legal git.
2. NEVER STORE THE DROPPED TREE. The recursion (deletePath) reports `empty` and does NOT store an empty tree for a level its parent is about to drop. A first cut stored it and then discarded it, which left an unreachable object. Verify reports that as orphan-objects, and nosignertest/TestSignedWrite_LeavesNoUnsignedPreImage fails on it. Anything that builds trees on this path must keep that property; TestDeleteFact_LastFactDropsFolder asserts Verify is strictly clean after a cascading drop.
3. MISSING PATH = NO-OP ON THE TREE. A missing leaf in an existing folder and a missing FOLDER (#375 option b) both return the tree unchanged, with no error. The `subtree %q not found` error no longer exists. Delete errors now come only from storage, such as a subtree object the store does not hold.

CONSEQUENCES:
- A BatchWriteFacts delete of an absent path never fails the batch. A delete-only batch of that shape still MINTS A COMMIT whose tree equals its parent's.
- DeleteFact is different: it checks existence itself under the branch lock and refuses an absent path with "does not exist". That is unchanged.
- Callers that need "the target existed" must use BatchWriteFactsMustExist; a failed batch never signals it.

WHAT THIS DOES NOT MEAN:
(a) "Existing empty folders are never touched." FALSE. There is no sweep, but a delete whose path WALKS THROUGH a pre-existing (legacy, pre-#389) empty folder drops that folder. This happens even when the target itself is missing, so a "no-op" delete can change the tree. Mechanism: at plumbing.go L265-266, a missing child under an empty `existing` returns empty=true, and a leaf removal that leaves no entries does the same, so the parent drops the legacy folder. Legacy empty folders that no delete walks through stay forever.
(b) "Knomit trees never contain empty folders now." FALSE for history and for untouched legacy folders, so tree readers must still accept BOTH shapes: present-but-empty and missing. ChangesUnder's subtreeOrEmpty handles the missing shape, which it needs anyway because a lane folder does not exist before its first post. The present-but-empty shape has no dedicated test since PR #389 removed it from TestChangesUnder_MissingFolderIsEmptyTree.
(c) "Write paths can create empty folders." They cannot: buildTree and upsertEntry only add entries.
