# refs → [:DERIVED_FROM] edges are driven from rec.Refs through Upsert, written POST-COMMIT as immutable time-aware historical edges (callers cannot bypass)

Every fact's LOCAL refs (rec.Refs filtered to non-http/https) become [:DERIVED_FROM] graph edges. The write is driven from the Upsert path and callers cannot inject edges another way: there is NO public 'add edge' API — the sole writer is the UNEXPORTED graphAddDerivedFromAtCommitTx (internal/store/derived_from.go), reached only via si.writePostCommitDerivedFrom. GraphAddDerivedFrom was removed from the synthesize/SearchIndex interface, so bypass is structurally impossible.

MECHANISM (this is the CORRECTED version — the 2026-03-26 explain-view design that seeded this fact has since been replaced; the old 'clean-and-rebuild inside graphSyncFactTx' model is GONE):
- Edges are written POST-COMMIT, NOT inside graphSyncFactTx. graphSyncFactTx handles only current-state edges (TAGGED / IN_DOMAIN / UNDER / SIMILAR_TO) and does NOT touch DERIVED_FROM. writePostCommitDerivedFrom runs after tx.Commit on BOTH the COW-hit path (search_crud.go:123) and the COW-miss path (search_crud.go:258), and again in rebuildGraph Phase B / Pass 2 (search_index.go:304, :1165). Post-commit is required because graphAddDerivedFromAtCommitTx needs target node IDs only visible after the source Fact's MERGE has committed.
- Edges are TIME-AWARE and IMMUTABLE. Each edge carries source_commit + target_commit; every commit that asserts a ref is its OWN ref-event, so edges ACCUMULATE across a fact's history. graphAddDerivedFromAtCommitTx has a dedup guard that makes repeated writes idempotent, but distinct ref-events at distinct commits produce distinct edges.
- Edges are NEVER deleted on retraction. graphDeleteFactTx deletes only TAGGED / IN_DOMAIN / UNDER and incoming SIMILAR_TO (search_graph.go:305); DERIVED_FROM (incoming AND outgoing) is preserved as immutable historical lineage. /explain hides retracted endpoints at query time via NOT f.deleted = true.

WHAT THIS DOES NOT MEAN (documented misreadings):
- NOT 'a fact's DERIVED_FROM out-edges are a clean mirror of its CURRENT refs.' FALSE — the out-edge set is the UNION of every (path, commit) ref-event in the fact's history; a fact whose refs changed over commits still has edges for the OLD refs. To read current refs, read the fact record, never the graph. There is no 'no extras' guarantee (the deleted TestDerivedFromInvariant that once asserted it no longer exists).
- NOT 'retracting or updating a fact cleans up its DERIVED_FROM edges.' FALSE — they are immutable; both directions survive retraction ON PURPOSE (removing them would erase the temporal lineage rail). No cleanup runs; the query layer hides deleted nodes instead.

Anti-pattern: do NOT add a public 'add edge' API, and do NOT move DERIVED_FROM writes into graphSyncFactTx — the post-commit two-pass order is load-bearing. Current pinning tests: derived_from_test.go, edge_props_test.go, search_graph_query_test.go (two-commit time-aware edge semantics).
