# knomit_changes (and GET …/branches/{branch}/changes) is a read of TWO TREES — tree at `since` vs tree at head under one folder — with no clock, no commit_log, no write; `since` must be head or its ancestor, a missing folder is the empty tree

`store.ChangesUnder` answers "what is different under this folder since commit C" by diffing the tree at `since` against the tree at head (subtrees at the prefix) with go-git `object.DiffTree`. The answer is a pure function of (tree(since), tree(head), prefix), so two machines holding the same two commits return byte-identical rows. It reads NO timestamp, NO commit_log row and NO index row, and it WRITES NOTHING — the caller keeps `head` in its own state and passes it back as `since` (the user's F05 decision, 2026-09-26). Shipped in PR #315, merge 7cd2b28c.

Load-bearing rules, each pinned by a test in internal/store/changes_test.go with a sabotage that fails it:
1. `since` must be head or an ANCESTOR of head (`commit.IsAncestor`), else `ErrSinceNotBehind` (MCP tool error / REST 409). A reversed or sideways diff reports paths as DELETED that nobody removed — in a task pool, a fabricated take. Honest callers hit it with a bookmark from a machine whose main was further ahead, a head taken from the agent branch (REST twin) and replayed at main (MCP), or a reconfigured Remote.Branch.
2. A prefix folder MISSING at either end is the EMPTY tree (`subtreeOrEmpty` maps object.ErrDirectoryNotFound to nil) — a lane's first post reads as `added`, its last removal as `deleted`. Never an error, never "no change". Since PR #389 (fa1b6d03, #375), knomit's own deletes DROP an emptied folder exactly as git does, so a lane emptied by DeleteFact, a GitHub merge or a hand commit is MISSING at head, and TestChangesUnder_MissingFolderIsEmptyTree now reaches the missing-folder branch through knomit alone. The other shape, a folder PRESENT BUT EMPTY, still occurs in pre-#389 history and in legacy folders no later delete walked through. It diffs correctly, because DiffTree of an empty tree lists no files, but since #389 it has NO dedicated test. Do not assume heads never contain it.
3. The prefix is relative to the ontology root, lowercased, stripped of leading/trailing `/`, never given `.md`, refused on `..` or any dot segment (`NormalizeChangesPrefix`). It must NOT go through `fact.NormalizePath`, which appends `.md` and turns `tasks/a` into the single file `kb/tasks/a.md` — every read then silently returns nothing.
4. Rows are filtered with `repoHandler.isFactPath` — the indexer's own membership rule (under the ontology root, `.md`, no dot segment) — so changes and the index agree on what a fact is, with one copy of the rule. They sort bytewise; a rename/move is `deleted` + `added` (DiffTree does no rename detection).
5. Paging is a STATELESS cursor carrying (repo, branch, since, head, prefix, last path), shared by MCP and REST; page 2 re-diffs the SAME pinned head of the SAME repo and branch. A pinned head must be on the branch's history (else ErrInvalidChangesCursor). The last path stays repo-relative even when the MCP rows are kb://-qualified. A cursor carrying only one of repo and branch is invalid; one with neither is a LEGACY cursor (minted before #364) and means the write repo's consensus branch on MCP, the URL's repo and branch on REST.
6. An unknown or malformed `since` is `ErrUnknownSince`, an unknown branch `ErrBranchNotFound` (404) — never an empty page, because an empty page reads as "nothing changed".

Anchor (since #364, decision kb/decisions/store/changes/repo-branch-addressing/47cfc650.md): the MCP tool reads ONE repo at ONE branch per call. `repo` is a 12-hex id routed through Binding.ByID (a name is refused: "repo must be a 12-hex id from knomit_repos"; an id not mounted: "repo X is not mounted in this binding"); omitted, it is the write repo. `branch` omitted is the branch the BINDING reads that repo at — for the write repo Binding.WriteMountBranch(), which is the agent branch or, while the session is in an experiment, exp/<name> (the binding is already re-pinned, on both the unscoped handle and URL-scoped mounts, so the handler needs no experiment lookup of its own); for a read mount its pinned ReadTarget.Branch (a subscription's followed branch). `consensus: true` is that repo's Service.UpstreamBranch() (origin branch, else the recorded consensus — not a hardcoded main) and is refused together with `branch`. A branch the repo lacks is "repo X has no branch Y" (ErrBranchNotFound from resolveRef), never an empty page. The response names `repo` (12-hex), the RESOLVED `branch`, the raw `head`, and `bookmark` = `<repo12>:<head>`; `since` takes the bookmark or a bare hash (meaning the repo being read), and a bookmark naming another repo is refused by name — the repo is never inferred from it. Rows are kb://<id>/… iff the repo is not the write repo (wirePath). CONSEQUENCE: the default answer is machine-local (two synced machines differ on their agent branches); only consensus:true gives the byte-identical cross-machine answer, so coordination readers must pass it. The REST twin reads the repo and branch in its URL, refuses a cursor minted for another repo or branch, and accepts the bookmark form of since for its own repo only.

No-write guard: `TestChanges_CallsAreAllowlisted` (internal/store/changes_guard_test.go) is an ALLOWLIST of every call the three files make, keyed receiver.method; any other call fails, and an allowlist entry nothing calls fails too. A denylist of known writers was tried first and let `rh.CreateBranch` / `svc.Branches().CreateBranch` through. Behavioural backstops: `TestChangesUnder_WritesNothing` snapshots every ref, the branches table and the commit_log / branch_commits row counts around every kind of call; `TestChangesHandler_WritesNothing` (internal/mcp) snapshots every branch ref and branches row around the MCP handler.

Misreadings to avoid: (a) "changes is an event log" — it is the NET difference; an add-then-delete between two reads is invisible by design, and op/author are not on the rows (read the fact for them). (b) "extend it with commit_log ordering for per-event rows" — commit time is committer-set, ties break on the instance-local SQLite rowid, and a fast-forward over an agent's merge puts an older deleting commit behind the bookmark (TestChangesUnder_DeletionSurvivesFastForwardOverOlderCommit fails under a time-ordered replay, reporting `t2 added` and missing `t1 deleted`). (c) "a missing since or folder can just return empty" — see rules 2 and 6. (d) "add a call to the guard's allowlist to make CI pass" — only after checking it writes nothing and reads no clock or commit log.

Measured on a backup of live knomit-kb (2465 commits on main): IsAncestor 27 µs one commit back, ~10 ms to the root, ~75 ms on the refusal path (full walk); a first page from the root 48–71 ms, one-commit incremental 14–28 ms.
