# Sync reads refs/remotes/origin/<main> BEFORE fetchOrigin and seeds a MISSING agent watermark from it; the position must be read pre-fetch (go-git keeps no reflog) and an existing watermark is never overwritten

RULE (PR #542, verified at merge 637960bc on dev, 2026-10-17). remoteIndex.sync does three things in this order. (1) Inside the configMu-read-locked closure, immediately BEFORE fetchOrigin, it reads refs/remotes/origin/<upstreamMain> into lastOrigin (zero when there is no such ref). (2) After a successful fetch, when there is an agent branch distinct from the upstream, it calls seedMissingWatermark(agentBranch, lastOrigin). (3) Only then reconcileNow. seedMissingWatermark, under lockBranch(agentBranch), writes the watermark refs/knomit/agent-base/<branch> at lastOrigin ONLY when the branch has NO watermark (readAgentBase returned ErrReferenceNotFound); any other read error is returned, not downgraded. Every reconcile then advances the watermark, so the seed is used for one sync.

WHY: a repo made before the watermark existed (or never synced since) has none; the rewind replay then stops at the merge base, and strictlyAhead without a watermark is the upstream-is-an-ancestor test alone, so an origin reset to an ancestor of the branch read as 'the branch is ahead' and the commit the origin removed was kept and pushed back (the R5 leak, gotcha kb/gotchas/store/remote-reconcile/rewind-residual-leaks/cd3a2bbf.md). Where the origin was at the last fetch is the signal git's pull --rebase --fork-point reads from the remote-tracking reflog.

CONSEQUENCES. (a) The position MUST be read before the fetch: fetchOrigin moves the ref to the new upstream and go-git keeps no reflog, so reading it after reads the new upstream and re-opens the leak. Do not move the read below fetchOrigin or into reconcileNow. (b) An EXISTING watermark must never be overwritten by the seed: the seed can sit beyond what the branch consumed (a fetch whose reconcile failed), and overwriting would turn that into the leak for every repo that has a watermark, not only legacy ones. (c) With no tracking ref (a truly first sync) nothing is written and the merge-base fallback stays; do not 'complete' it by seeding from local main or from the agent branch tip.

MISREADINGS. 'The watermark is the branch's first commit': no, and it must never be; seeding at the branch tip counts every unsynced own commit as consumed and drops it on the next rewind (sabotage S2). 'The watermark is only consulted on a rewind, so a seed is harmless': the seed is written on every sync of a legacy repo, and what it changes is the rewind's stop point. 'Sync seeds it, so reconcileAgentRebase never sees a missing watermark': it still does on a truly first sync or from a caller that does not fetch.

PINNED BY (store, internal/store/remote_watermark_fallback_test.go, full Sync against a real bare file:// remote): TestSync_NoWatermarkResetToAnAncestorDoesNotKeepTheRemovedCommit (subtests nothing_else and an_own_unsynced_write_on_top_is_kept; also asserts the watermark is written and a Push does not send the removed commit back), TestSync_ExistingWatermarkIsNotOverwritten (watermark s, tracking ref moved past it to x, own write b, origin reset to r: b kept, s unreachable), TestSync_NoWatermarkGenuinelyAheadDropsNothing and TestSync_FirstSyncEverKeepsTheMergeBaseFallback (guards: they pass at the pre-#542 code too, each pinned by a sabotage instead). Sabotaged against the branch heads and red: S1 never seed (both NoWatermarkReset subtests); S2 seed at the branch tip (own_unsynced_write, GenuinelyAhead); S3 with no tracking ref seed from local main (FirstSyncEver); S4 read the tracking ref after the fetch (both NoWatermarkReset subtests); R1 the seed overwrites an existing watermark (ExistingWatermarkIsNotOverwritten only, and it survived the whole store suite before that test existed).

See kb/invariants/store/remote-reconcile/replay-stop/5482c3ab.md (the stop rule and the C1/C2 limits of the seed).

UPDATE (PR #544, merge 8a01d3ca on dev, read there): the seed and the watermark are consulted only on the rewind path, and a round with a DIFFERENT origin no longer takes that path (the ordinary merge path runs; the seed is still written when the watermark is missing, harmlessly). The 'stale watermark after a URL change' limit therefore no longer drops own commits on a switch; it only matters for a same-origin rewind. The ordering rule above (read the tracking ref BEFORE fetchOrigin) is unchanged, and the switch check reads the recorded origin identity after the fetch without touching it. See kb/decisions/store/remote-reconcile/origin-switch/5269d61e.md.
