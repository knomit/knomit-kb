# The rewind replay (replayOntoUpstream) never re-submits a commit the new upstream's history holds: the first-parent walk stops at the watermark OR at the first commit reachable from upstreamTip (its WHOLE history, every parent), whichever comes first; an empty walk is a no-op only when equal or strictly ahead (watermark at or below the upstream) or disjoint, fast-forwards when behind, and otherwise rebuilds the branch on the upstream (#539)

RULE (branch fix/fleet-switch-replay, verified at b25765bd; re-pin at the merge commit). On the rewind path (reconcileMain reported ModeRewound, so reconcileAgent routes to reconcileAgentRebase -> replayOntoUpstream), unpushedCommits walks the agent branch's first-parent chain from its tip and stops at EITHER of two points, whichever it meets first: (1) the stop point it was given (the watermark refs/knomit/agent-base/<branch>, or the merge base when there is none), or (2) the first commit that upstreamTip's history holds. 'Holds' is ONE walkHistory of the upstream over EVERY parent (skipped when the two histories are disjoint), not its first-parent chain: in a fleet a member's commits reach main through the SECOND parent of the master's merge. Merge commits on the way are still skipped. So a commit already upstream is never replayed, whatever the watermark says. Stopping at a held commit can never skip a local commit: ancestry is closed, so everything below a held commit is held too.

EMPTY WALK (HISTORY; #539 changed it, see the last UPDATE): as it was before #539. local == upstream: no-op; local an ancestor of upstream: fast-forward; anything else: no-op, the branch stays as it stands and the caller's force-push sends it. An earlier version of this branch moved a diverged branch with only merges beyond upstream onto upstream ('shape 3'); the PR #531 review (B1) showed it silently drops a committed experiment: CommitExperiment writes a merge commit and deletes the experiment, so on a rewind that merge is the only reference to the experiment's work. Shape 3 was removed; TestReconcileAgentRebase_ExperimentMergeSurvivesARewind pins it.

WHY THE STOP: the watermark can lie arbitrarily far behind. A copy with NO origin (a hub, or any local-only repo) never advances it: only InitRepo/InitFromRemote seed it and only the origin reconcile (reconcileAgentMerge/reconcileAgentRebase) advances it; the local reconcile never touches it. So the first rewind after such a copy attaches an origin used to replay its WHOLE history since InitRepo onto the new main, local side winning every conflict (StrategyLocalWins), re-signed by this copy. That is #528 N1: the old master's create-time host record and a re-enrolled member's first leaf were replayed over the new main's and refused by the new host's judge on every retry.

CONSEQUENCES. (a) A former hub that follows a new host replays only its own non-merge commits the new main lacks; its consensus merges of members' branches are skipped (members push their own branches to the new host). After a stand-down-first switch (kb/invariants/fleet/root-move/b41b75ed.md) the new main holds everything the old master wrote as master, so nothing of that is replayed. (b) Do not 'fix' a stale watermark by re-seeding it at attach time instead: the walk rule already bounds the replay.

MISREADINGS. (1) 'The replay now uses the merge base instead of the watermark': no, the watermark still stops the walk when it comes first (G6 scrub semantics on a disjoint rewind are unchanged). (2) 'Nothing of the old master's own is replayed any more': its own commits that the new main lacks ARE replayed; a master-only write among them (made after the new host's last sync from it: the dead-master fallback, where the old master was the ONLY master when it wrote; this is not the two-masters mode) is judged by the new host and can be refused for good (last_error_commit_refused). (3) 'An empty walk on a diverged branch moves it onto upstream': that was true of #531's shape 3, false from #531 to #538, and TRUE AGAIN from #539 for shared history with the exceptions in the last UPDATE; the known gap that such a branch is force-pushed as it stands, merges included, is kb/gotchas/store/remote-reconcile/merges-only-pushed-as-is/75e0108b.md.

UPDATE (verified at c86b0d6e): a repository may name paths a rewind replay never carries (Service.SetReplaySkipPaths; the fleet repository names artifacts/fleet/master): a non-merge commit that changes only those paths is dropped from the walk, and when the walk dropped one, the empty-walk shapes do NOT keep the branch as it stands: the replay rebuilds it on upstream with what is left (unpushedCommitsDropping). Pinned by store TestReconcileAgentRebase_DropsCommitsThatChangeOnlySkippedPaths. The stop rule is exercised end to end again by cmd TestFleetMasterSwitch_DeadMasterFallback (#531 re-review N6): dropping it there replays the create-time host record and is refused.

VERIFIED AT THE MERGE (PR #531, squash commit 8ca72760 on dev, 2026-10-16). Re-read against that commit: the stop rule (watermark or first commit reachable from upstreamTip through every parent), the empty-walk shapes (equal no-op, fast-forward, otherwise the branch stays as it stands) and the skip-paths drop (unpushedCommitsDropping; a rebuild on upstream when the walk dropped a commit) are all as written above, and every test named above exists at the merge. The fleet repository names the skipped path in stages.go (svc.SetReplaySkipPaths(fact.FleetMasterPath)). EDGE (reproduced by the #535 gap probe, shape A): when the walk dropped a marker-only commit AND the rest of the divergence is merges only whose side holds none of this instance's own commits, the branch is rebuilt on upstream with nothing left, so those merges are not kept. In a FLEET this is NOT data loss: the content behind a hub master's consensus merges is members' commits (they push their own branches to the new host, and the old master could not deliver them anyway: re-pushed inside its branch, the new host's receive-pack refuses them under signer-is-pusher, not-pusher) or old main (which a rewind exists to leave behind), and the fleet repository refuses experiments, so no experiment merge can be there; the master's own writes are plain first-parent commits and are replayed. Dropping the merges is the replay's general rule, not a fleet defect. Residual, reasoned and not probed: a member that left, was revoked or lost its copy after the old master merged it and before the new host last synced loses those commits from the fleet; no log line names them. The no-drop twin is kb/gotchas/store/remote-reconcile/merges-only-pushed-as-is/75e0108b.md.

UPDATE (PR #535, verified at merge 48e7d8d5): the walk no longer ignores what a merge brought in. At each merge it looks behind the merge's non-first parents (sideOf) and replays the INSTANCE's own work found there: a clean own-only side is replayed as the merge itself (one commit, its change against its first parent, so a CommitExperiment resolution survives), a mixed side only as its own non-merge commits, one by one, with a Warn. Foreign commits are never replayed as commits; the exceptions, the own-key filter, the held set and the instance-key misreading are in kb/invariants/store/remote-reconcile/side-replay/7c9af34f.md, and the incident (a committed experiment lost on a rewind after one later write) is kb/incidents/store/remote-reconcile/experiment-merge-lost/23318e68.md. CONSEQUENCES: (a) the EMPTY WALK paragraph above is about an empty walk only; a diverged branch whose only extra commits are a clean own experiment merge no longer has an empty walk, so in an ordinary repository it is rebuilt on upstream with the merge replayed (ModeRebase), not kept as it stands (ModeNoop). The empty-walk no-op itself is unchanged. (b) A commit the upstream holds under a different hash (squash-merged) is replayed again, local side winning, and can revert a later upstream edit to that path (existing first-parent class). (c) An own commit that edits a foreign file re-adds that file's content (re-review S1: the side's foreign commit is not replayed, but the own edit applied where it is absent lands the whole file). MISREADING: 'merges are never replayed' was true before #535 and is false now.

UPDATE (#538, merge 3f254262): the rewind (reconcileAgentRebase) now also RECORDS, before replayOntoUpstream runs (so also for a rewind that then moves nothing; the next commit or sync finds nothing removed and drops the record), the agent's pre-rewind tip for each experiment of that branch (refs/knomit/experiment-rewound/<name>, first record kept), under lockBranch(agent). The replay itself is unchanged; the experiments' own rebuild happens at their next commit or sync: kb/invariants/store/experiments/open-across-rewind/a854b8f9.md. WHAT THIS DOES NOT MEAN: the replay does not touch experiment branches, and it does not make an experiment safe by itself; a rewind that ran before #538 recorded nothing.

UPDATE (#539 merge 266f96f5, nits #540 merge ba40165b; read at ba40165b): THE EMPTY-WALK NO-OP IS GONE FOR SHARED HISTORY. After unpushedCommitsDropping returns no commits and dropped nothing, replayOntoUpstream decides: local == upstream: no-op; local an ancestor of upstream: fast-forward; STRICTLY AHEAD (strictlyAhead: the upstream is an ancestor of local AND the watermark, when there is one, is the upstream or its ancestor): no-op, the caller's force-push fast-forwards origin; DISJOINT (no common ancestor): no-op, kept (attach identity; residual, see the gotcha); EVERYTHING ELSE: the branch is REBUILT on the upstream with nothing to replay (ModeRebase, NumReplayed 0). Also: unpushedCommitsDropping no longer returns early whenever the upstream is an ancestor of local; it asks strictlyAhead, so a watermark BEYOND the upstream (the origin moved back past what the branch consumed, reset HEAD~1 plus force-push) runs the walk, own write on top or not. An own experiment merge is still not lost: the side collection (#535) makes the walk non-empty. THE RULE THIS MAKES EXPLICIT (user-accepted 2026-10-17, kb/decisions/store/remote-reconcile/consumed-own-work-dropped/): a rewind drops EVERY CONSUMED commit (at or below the watermark) that the new upstream lacks, own work included, idle branch or not; before #539 an idle branch kept such commits only through the no-op, and one write on top already dropped them. MISREADINGS: 'no own work is lost by a rewind' covers only work ABOVE the watermark; a consumed own experiment merge the upstream lacks is dropped too; an origin that LAGS (a mirror or backup, a dead-master fallback) looks the same as one that scrubbed. NOT COVERED: a disjoint upstream (issue #541), a repo with no watermark (PR #542 in progress), an own edit of a removed file above the watermark (accepted): kb/gotchas/store/remote-reconcile/rewind-residual-leaks/.
