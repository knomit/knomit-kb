# store.validatePath is the place for storage-integrity path rules (bytes git cannot read back) — and only those; knowledge-layout rules like the private-path rule stay out

Every store write door runs store.validatePath BEFORE taking the branch lock, so a refusal there leaves the ref, the commit_log and the index untouched. The doors are:
- writeFileExact (WriteFact, WriteFactIfUnchanged, WriteRootFile)
- deleteFile (DeleteFact)
- batchWrite (BatchWriteFacts, BatchWriteFactsMustExist)

That makes it the right home for a rule that is true of EVERY file the store could write. A path git itself cannot read back poisons the branch whatever the file is. Since #384 the rule is go-git's own ValidTreePath, asked through gitReadablePath, not restated.

It is the WRONG home for a rule about what may hold a FACT. The same doors also write README.md, LICENSE, .domains/ontology.yaml and .knomit/ slots. A knowledge-layout rule there breaks the server's own writes; the private dot-path rule is the documented example.

Consequence for a consumer: before adding a check to validatePath, ask whether it holds for README.md and .domains/ontology.yaml too. If yes, it belongs here; if it is about facts only, it belongs at the fact-write boundaries. A leading dot is NOT a go-git refusal: `.knomit/`, `.domains/` and `.github/` all pass. Only `.git` and its disguises are refused, for example `git~1`, `.git.`, `.git ` or a zero-width-joined `.git`.

Misreadings to avoid:
- validatePath is not exactly go-git's rule plus nothing. It also refuses `..` as a SUBSTRING (`a..b`), which is stricter than git's component rule (older design), and the empty path.
- It does not refuse empty segments (`x//y`). go-git's whole-path rule drops them, and gitReadablePath skips them on purpose.
- Do not replace gitReadablePath with a hand-written copy of the rule: it asks go-git so the two cannot drift on an upgrade.
