# store.validatePath is the place for storage-integrity path rules (bytes git cannot read back) — and only those; knowledge-layout rules like the private-path rule stay out

Every store write door — writeFileExact (WriteFact, WriteFactIfUnchanged, WriteRootFile), deleteFile (DeleteFact) and batchWrite (BatchWriteFacts, BatchWriteFactsMustExist) — runs store.validatePath BEFORE taking the branch lock, so a refusal there leaves the ref, the commit_log and the index untouched. That makes it the right home for a rule that is true of EVERY file the store could write: a path git itself cannot read back (control characters, since #384) poisons the branch whatever the file is.

It is the WRONG home for a rule about what may hold a FACT. The same doors also write README.md, LICENSE, .domains/ontology.yaml and .knomit/ slots, so a knowledge-layout rule there (the private dot-path rule is the documented example) breaks the server's own writes.

Consequence for a consumer: before adding a check to validatePath, ask whether it holds for README.md and .domains/ontology.yaml too. If yes, it belongs here; if it is about facts only, it belongs at the fact-write boundaries.

Misreading to avoid: this does NOT mean validatePath mirrors all of go-git's ValidTreePath. It mirrors only the control-character clause today; '..' it refuses as a substring (stricter than git's component rule, by older design); .git-name variants and empty segments are not checked here.
