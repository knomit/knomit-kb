# A reopened store.Service must be re-wired with ALL per-store process-level config — rewireStore is that checklist, and its silent-failure member is the ORIGIN, not the Crypt

`store.Open` restores NONE of the per-store wiring `repoBuilder` applies. Any path that reopens a `Service` (SwapStore, reattach, future reopen helpers) MUST re-apply that wiring, or the reopened store behaves differently from a freshly built one. `repos.Manager.rewireStore` (`internal/repos/swapstore.go`) is the single place that does it, and it is called from BOTH SwapStore branches and from `reattach`.

**The set at HEAD, named in full:** `SetEmbedder` (only when `m.deps.Embedder != nil`), `SetSigner`, `SetNetworkTimeout` (from `m.deps.Cfg.Git.NetworkTimeout`), `SetOntologyRoot` (from `m.deps.Cfg.OntologyRoot`), and `reinjectOrigin` — a lookup of the control.db `Origins` row for `ri.uid`, re-applied via `svc.SetOrigin`. None of these are persisted in the repo database; they are process-level config derived from `m.deps`.

**The member whose omission is silent is the ORIGIN.** rewireStore's list previously read as complete while omitting it, and the omission only bit on the RECOVERY paths: on success the caller re-injects, but a failed copy/reopen/git-open goes `reattach(reopenLocal())`, the handler returns, and nothing re-injects. The repo came back live with `origin == nil`, the reconcile loop hit sync.go's `if remote == nil { return }` and exited WITH NO LOG LINE — a repo that looks healthy and has quietly stopped syncing. That is the failure shape to expect from any future omission: not an error, a repo that stops doing something.

**Operational consequence:** adding any new piece of per-store wiring to `repoBuilder` means adding it to `rewireStore` too. Treat rewireStore as the checklist that must mirror repoBuilder's wiring, and read its doc comment — it declares itself COMPLETE, which is the claim that has to stay true.

**WHAT THIS DOES NOT MEAN.**

- *Not* "a reopened Service needs its Crypt restored." This fact previously said so and it is FALSE at HEAD. Since migration 000017 the store holds no credentials, so there is no per-store Crypt to restore: control.db's `Origins` tenant owns the token AND its Crypt, and both outlive the swap. `configureCrypt` and `Service.SetCrypt` no longer exist anywhere in the tree — do not go looking for them, and do not re-introduce per-store credential encryption to "fix" a reopen. The historical failure (`SetRemote` refusing to persist an auth token with "encryption unavailable" after a disjoint-history origin apply) is no longer reachable by that route.
- *Not* "rewireStore literally applies everything a reopened store needs." `SetOnCommit` is applied by each call site immediately after — `if ri.onCommit != nil { svc.SetOnCommit(ri.onCommit) }` in the in-memory branch and again in `reattach`. A new reopen path that calls only rewireStore gets a store that commits without notifying.
- *Not* "the set is a fixed list." It has already changed twice (network timeout and ontology root added; Crypt removed). The invariant is "ALL per-store process-level config", not any enumeration — including this one, which is accurate as of commit 4baae4ed and should be re-read from the code, not from here.
- *Not* "re-injecting the origin re-reads it from the repo database." Since 000017 the repo's own `remotes` row carries sync/push STATUS only; the connection identity comes from control.db's Origins, which is why `reinjectOrigin` returns quietly (with a warn, sync inactive until next boot) when that lookup fails.
