# Any code that reopens a store.Service must re-apply embedder + Crypt + signer

store.Open restores NONE of the per-store wiring the repoBuilder applies: the embedder, the credential-encryption Crypt (configureCrypt from the agent key), and the commit signer. lifecycle.go re-runs configureCrypt after opening; SwapStore originally re-applied only the embedder, so after the disjoint-history origin apply swapped the clone in, the reopened store had no Crypt -> SetRemote refused to persist the auth token ("refusing to store credential ... encryption unavailable") and post-swap commits were unsigned.

Invariant: any path that reopens a Service (SwapStore, future reopen helpers) MUST re-apply the per-store process-level config so the reopened store behaves identically to a freshly built one. Fixed via repos.Manager.rewireStore (internal/repos/swapstore.go), called in both SwapStore branches. Crypt/signer are NOT persisted in the DB; they are process-level config derived from m.deps (KeyPath, Signer).

WHAT THIS DOES NOT MEAN: the re-applied set is NOT frozen at 'exactly three (embedder + Crypt + signer)'. As of HEAD, rewireStore ALSO re-applies the network timeout (SetNetworkTimeout from m.deps.Cfg.Git.NetworkTimeout) — store.Open does not restore that either. The true invariant is 'a reopened Service must re-apply ALL per-store process-level config', not a fixed list of three. Adding any new piece of per-store wiring to repoBuilder means adding it to rewireStore too, or the swapped-in store silently loses it. Treat rewireStore as the single checklist that must mirror repoBuilder's wiring.
