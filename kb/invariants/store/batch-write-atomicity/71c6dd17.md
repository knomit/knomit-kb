# BatchWriteFacts(files, deletes) is the ONLY way to retract a fact atomically with the write that supersedes it

`FactIndex.BatchWriteFacts(ctx, branch, files map[string]string, deletes []string, message, operation)` applies BOTH the writes in `files` and the retractions in `deletes` to one running git tree inside a single `lockBranch` critical section, producing exactly ONE commit.

This exists because a write and a retraction that belong together MUST NOT be two commits. The learn subsume path (internal/mcp/learn.go) is the motivating case: an incoming observation that subsumes an existing hypothesis writes the observation with a ref to the hypothesis path AND retracts that hypothesis. As two commits, either half can land alone — a failed retraction leaves an observation referencing a live hypothesis it claims to have subsumed (dangling ref plus the duplicate it claimed to remove), and a failed write leaves a fact retracted for nothing.

CONSEQUENCE: if you are writing fact A *because* fact B should go away, pass B in `deletes` on the same BatchWriteFacts call. Never follow a BatchWriteFacts with a separate DeleteFact (or vice versa) and call the pair atomic — it is not.

Mechanics that matter:
- Deletions are applied AFTER the writes, against the same running tree, so a path in both sets ends up deleted. Keep the two sets disjoint.
- The running root tree is seeded from the parent commit's tree, so a delete-only batch (`files` nil, `deletes` non-empty) is valid and commits parent-minus-deletions.
- A delete naming a path absent from the tree FAILS THE WHOLE BATCH — the writes are not committed either. That is deliberate: the caller asked for both or neither.
- Both sets are lowercased and run through `validatePath`.
- An all-empty call (`files` and `deletes` both empty) is a no-op returning an empty commit hash — no commit is minted.

WHAT THIS DOES NOT MEAN: this is not a general transaction over the store. It is one git commit. The SQLite index is still synced afterwards by `rh.notifyCommit` inside the same branch lock, and index sync handles the deletions via `DiffFiles`' `deleted` set — not via anything BatchWriteFacts does itself.
