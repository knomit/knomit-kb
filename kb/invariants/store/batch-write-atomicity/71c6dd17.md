# BatchWriteFacts(files, deletes) is the ONLY way to retract a fact atomically with the write that supersedes it

`FactIndex.BatchWriteFacts(ctx, branch, files map[string]string, deletes []string, message, operation)` applies BOTH the writes in `files` and the retractions in `deletes` to one running git tree inside a single `lockBranch` critical section, producing exactly ONE commit.

This exists because a write and a retraction that belong together MUST NOT be two commits. The learn subsume path (internal/mcp/learn.go) is the motivating case: an incoming observation that subsumes an existing hypothesis writes the observation with a ref to the hypothesis path AND retracts that hypothesis. As two commits, either half can land alone — a failed retraction leaves an observation referencing a live hypothesis it claims to have subsumed (dangling ref plus the duplicate it claimed to remove), and a failed write leaves a fact retracted for nothing.

CONSEQUENCE: if you are writing fact A *because* fact B should go away, pass B in `deletes` on the same BatchWriteFacts call. Never follow a BatchWriteFacts with a separate DeleteFact (or vice versa) and call the pair atomic — it is not.

Mechanics that matter:
- Deletions are applied AFTER the writes, against the same running tree, so a path in both sets ends up deleted. Keep the two sets disjoint.
- The running root tree is seeded from the parent commit's tree, so a delete-only batch (`files` nil, `deletes` non-empty) is valid and commits parent-minus-deletions. A delete against a branch with NO tree at all errors out.
- Both sets are lowercased and run through `validatePath`.
- An all-empty call (`files` and `deletes` both empty) is a no-op returning an empty commit hash — no commit is minted. Note this is a check on the two INPUT SETS, not on the resulting tree: a call whose tree ends up identical to the parent still mints a commit.

WHERE THE ATOMICITY ACTUALLY ENDS (verified at HEAD, 2026-08-07): it is one git commit, not a transaction over the store. Tree construction, commit creation, signing, and the branch-ref move all happen in `batchWriteLocked`; `batchWrite` then calls `rh.notifyCommit` to sync the SQLite index, inside the same branch lock. Index sync handles deletions via `DiffFiles`' `deleted` set — not via anything BatchWriteFacts does itself.

WHAT THIS DOES NOT MEAN (misreadings verified false at HEAD, 2026-08-07):

1. "It is atomic, so if BatchWriteFacts returns an error nothing was written." FALSE, and this is the most convenient and most damaging inference. `batchWriteLocked` already did `SetReference(branchRefName, cHash)` — the branch ref has MOVED — before `batchWrite` calls notifyCommit. If notifyCommit fails, batchWrite returns `("", nil, err)`: an error AND an empty commit hash, while the commit is durable in git. Callers propagate this as a plain write failure (learn.go reports `write error: %v`), so the user concludes nothing landed while the facts are in fact committed and will surface on the next successful index sync, heal, or Rebuild. Do NOT retry such a call blindly and do NOT report it as "no change". Errors raised EARLIER — validatePath, tree construction, a failed delete — do leave nothing behind, because they all precede the commit.

2. "A delete naming a path absent from the tree fails the whole batch." FALSE as stated — it depends on WHICH component is missing (internal/store/plumbing.go). A missing DIRECTORY component fails the batch: deleteFromTree recurses per path segment and errors `subtree %q not found`, so the writes are not committed either. A missing LEAF is silently tolerated: `removeEntry` just rebuilds the tree filtering on name, matches nothing, and returns the identical tree hash with NO error. So retracting an already-retracted fact from a directory that still exists SUCCEEDS quietly — and a delete-only batch in that shape mints a commit whose tree equals its parent. If you depend on "the target existed", check with FactExists first; the batch will not check for you.

3. "One commit, so a multi-fact learn call is all-or-nothing end to end." TRUE for git, NOT for what the caller observes — see (1). The all-or-nothing property that IS load-bearing is the ref gate: learn.go runs `gate.CheckBatch` BEFORE BatchWriteFacts, and because the whole call is one commit, facts written together may cite each other in any order, including circularly (internal/refs/refs.go). That ordering freedom is a consequence of the single commit; durability across the index sync is not.
