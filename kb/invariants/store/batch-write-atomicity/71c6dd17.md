# BatchWriteFacts(files, deletes) is the ONLY way to retract a fact atomically with the write that supersedes it

`facts.Index.BatchWriteFacts(ctx, branch, files map[string]string, deletes []string, message, operation)` (reached as svc.Facts().BatchWriteFacts; the store.FactIndex interface it used to be declared on was deleted in PR #575) applies BOTH the writes in `files` and the retractions in `deletes` to one running git tree inside a single `lockBranch` critical section, producing exactly ONE commit.

This exists because a write and a retraction that belong together MUST NOT be two commits. The learn subsume path (internal/edge/mcp/learn.go) is the motivating case: an incoming observation that subsumes an existing hypothesis writes the observation with a ref to the hypothesis path AND retracts that hypothesis. As two commits, either half can land alone — a failed retraction leaves an observation referencing a live hypothesis it claims to have subsumed (dangling ref plus the duplicate it claimed to remove), and a failed write leaves a fact retracted for nothing.

CONSEQUENCE: if you are writing fact A *because* fact B should go away, pass B in `deletes` on the same BatchWriteFacts call. Never follow a BatchWriteFacts with a separate DeleteFact (or vice versa) and call the pair atomic — it is not.

Mechanics that matter:
- Deletions are applied AFTER the writes, against the same running tree, so a path in both sets ends up deleted. Keep the two sets disjoint.
- The running root tree is seeded from the parent commit's tree, so a delete-only batch (`files` nil, `deletes` non-empty) is valid and commits parent-minus-deletions. A delete against a branch with NO tree at all errors out.
- Both sets are lowercased and run through `validatePath`.
- An all-empty call (`files` and `deletes` both empty) is a no-op returning an empty commit hash — no commit is minted. Note this is a check on the two INPUT SETS, not on the resulting tree: a call whose tree ends up identical to the parent still mints a commit.

WHERE THE ATOMICITY ACTUALLY ENDS (verified at HEAD, 2026-08-07): it is one git commit, not a transaction over the store. Tree construction, commit creation, signing, and the branch-ref move all happen in `batchWriteLocked`; `batchWrite` then calls `rh.vr.NotifyCommit` (the vcs.Repo method; formerly rh.notifyCommit) to sync the SQLite index, inside the same branch lock. Index sync handles deletions via `DiffFiles`' `deleted` set — not via anything BatchWriteFacts does itself.

WHAT THIS DOES NOT MEAN (misreadings verified false at HEAD, 2026-08-07):

1. "It is atomic, so if BatchWriteFacts returns an error nothing was written." FALSE, and this is the most convenient and most damaging inference. `batchWriteLocked` already did `SetReference(branchRefName, cHash)` — the branch ref has MOVED — before `batchWrite` calls notifyCommit. If notifyCommit fails, batchWrite returns `("", nil, err)`: an error AND an empty commit hash, while the commit is durable in git. Callers propagate this as a plain write failure (learn.go reports `write error: %v`), so the user concludes nothing landed while the facts are in fact committed and will surface on the next successful index sync, heal, or Rebuild. Do NOT retry such a call blindly and do NOT report it as "no change". Errors raised EARLIER — validatePath, tree construction, a delete that fails on storage — do leave nothing behind, because they all precede the commit.

2. "A delete naming a path absent from the tree fails the whole batch." FALSE, in every shape, since PR #389 (fa1b6d03, #375 option b). A missing LEAF and a missing FOLDER are both silent no-ops in deleteFromTree (internal/engine/store/internal/vcs/plumbing.go), and the `subtree %q not found` error no longer exists. Note that knomit now drops a folder its delete empties, so a repeat delete usually hits the missing-folder case. Retracting an already-retracted fact therefore SUCCEEDS quietly, and a delete-only batch of that shape mints a commit whose tree equals its parent's. A delete fails the batch only on a storage error, such as an unreadable subtree object; that is the case where the writes are not committed either. If you depend on "the target existed", use BatchWriteFactsMustExist (F08 PR A): it checks the named paths INSIDE the branch lock and refuses the whole batch with *RetractMissingError. A FactExists check before BatchWriteFacts is outside the lock and can go stale between the check and the commit (kb/invariants/mcp/learn/atomic-move/e4fff5d1.md).

3. "One commit, so a multi-fact learn call is all-or-nothing end to end." TRUE for git, NOT for what the caller observes — see (1). The all-or-nothing property that IS load-bearing is the ref gate: learn.go runs `gate.CheckBatch` BEFORE BatchWriteFacts, and because the whole call is one commit, facts written together may cite each other in any order, including circularly (internal/corpus/refs/refs.go). That ordering freedom is a consequence of the single commit; durability across the index sync is not.

RE-VERIFIED at the PR #575 merge f41adda1: facts.Index.BatchWriteFacts and BatchWriteFactsMustExist are in internal/engine/store/facts/fact_write.go and both call the unexported batchWrite, which takes fi.rh.vr.LockBranch, calls batchWriteLocked and then fi.rh.vr.NotifyCommit inside the same lock; deletes go through vcs.DeleteFromTree (internal/engine/store/internal/vcs/plumbing.go); the invariant is unchanged. The refs pinned at fa1b6d03 point at the pre-split internal/engine/store layout (store/fact_write.go, store/plumbing.go) and are historical.
