# A single-file store write (WriteFact, WriteFactIfUnchanged, WriteRootFile) whose final content is byte-identical to the blob at that path on the branch tip makes NO commit, moves no ref and fires no commit notification; it returns WriteFactResult{Unchanged: true, CommitHash: <the tip>}. Batch writes are not covered (#432)

RULE (#432, fix/432-noop-write-no-commit). writeFileExact (internal/engine/store/facts/fact_write.go), the one core behind WriteFact, WriteFactIfUnchanged and WriteRootFile, reads the blob at path on the branch tip under the branch lock and, AFTER the compare-and-swap precondition (a stale expectBlob is still refused with ErrFactChanged, even when the bytes match) and BEFORE validateWrite or any object write, compares it with plumbing.ComputeHash(BlobObject, content). Equal: nothing is written (no blob, tree or commit object), the ref does not move, DeriveBeforeAdvance and NotifyCommit are not called (so no index sync, no trigger kick, no realtime push, no consensus kick), and the result is Unchanged=true, CommitHash = the tip that was compared against, BlobHash = the existing blob. knomit_update answers {file, unchanged: true, written_to, summary: "no change: <file> already has this content on branch ..."} with NO commit field; REST PUT /facts/{path} answers 200 with unchanged: true.

CONSEQUENCES. (1) A caller must never treat a returned CommitHash as "the commit this write made" without checking Unchanged: on a no-op it is an older commit that may belong to someone else's write. (2) A re-save is never an event: nothing may use an identical rewrite to fire a trigger, bump a watermark, renew a lease or signal liveness. Nothing does today: tree-episode triggers and knomit_changes read tree diffs (DiffFacts, ChangesUnder), due fires key on the expires instant, and every lease re-arm in the mission template writes a new expires (now + window), so it is a real write. To make an event, change the content (e.g. expires). (3) Tests that assert "no commit" must compare the branch tip or rev-list --count (kb/gotchas/testing/git/commit-counting).

MISREADINGS. (a) "Re-sending what I sent last time is a no-op": no, the comparison is of the FINAL bytes the store is handed, after the caller's normalisation (knomit_update trims, normalises context, canonicalises bare kb/x.md refs to kb://<id>/kb/x.md, SerializeFact orders fields; REST PUT rewrites only when a gate changed something). A fact stored with a bare ref therefore commits ONCE on an unchanged re-save, then is a no-op. (b) "Every store write skips no-ops": batchWriteLocked (BatchWriteFacts, BatchWriteFactsMustExist, so knomit_learn, dedup merges, distill) is NOT covered; an all-identical batch with no deletes still makes an empty commit (follow-up). (c) "Unchanged means valid": the no-op returns before validateWrite, so an identical rewrite of a legacy invalid fact is reported unchanged rather than refused; nothing is written either way.
