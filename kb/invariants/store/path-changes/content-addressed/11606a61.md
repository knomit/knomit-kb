# path_changes rows are derived from GIT ALONE, parents first, and committed no later than the transaction that records a commit in branch_commits — so an indexed commit is never visible without them; rows are immutable per hash and never deleted (a pathChangesVersion bump is the only reset)

RULE (user, #347 review rounds 3-4): an indexed commit is NEVER visible in branch_commits without its history rows (path_changes, path_change_links, and commit_fp: depth plus packed jump pointers).

HOW IT HOLDS:
1. Derivation depends on GIT ALONE: the commit's trees and its parents' trees, plus the rows of its ancestors. It never depends on branch_commits or commit_log. The changed paths ALWAYS come from derivation's own tree diff against the first parent (diffTrees). That diff prunes equal-hash subtrees without reading them and shares a tree cache, so upgrade opens stay at 1.0 s (agentic-engineering) and 2.85 s (knomit-kb). Using commit_log's recorded rows (round 4) made a tampered or drifted row lose a revision for good (review A1). commit_log is consulted only when a tree is MISSING and git cannot list the changes, and the commit is then marked degraded (see kb/invariants/store/path-changes/never-fails-a-write). deriveClosure derives any underived ancestors first, walking git parents-first, and stops at derived commits and at objects genuinely absent from the store (a shallow boundary). It NEVER refuses because a parent is missing from branch_commits: that refusal (round 3) made one legacy gap fail every populate and every WriteFact for good (R1). TestPathHistory_LegacyGapDerivesFromGit, TestPathHistory_VersionBumpOverDeletedSideBranch.
2. Every commit is derived BEFORE the ref that makes it visible advances (deriveBeforeAdvance), or in the transaction that records it. The recording transaction's hook refuses a commit without its commit_fp mark (errNotDerived). CommitLogApply is the only writer of branch_commits for new commits: CommitLogSync is deleted, and Derive is REQUIRED. CreateBranch derives the source tip's closure (a lookup when derived) before copying its set.
3. A git READ ERROR fails the derivation; nothing of it is recorded, and a later pass retries. Only plumbing.ErrObjectNotFound for a commit, or ErrPathNotFound for a path, counts as absent (R3). TestPathHistory_ReadErrorRecordsNothing uses deriveObjectHook to inject one.
4. Rows are IMMUTABLE per hash. Nothing deletes them on a rewind or a rebuild, and another branch's history survives a rebuild. Exceptions are DEGRADED rows (commit_fp.degraded > 0), which :rebuild replaces once the objects are back.
   A pathChangesVersion bump, or an upgraded database with no key, derives every branch tip into SHADOW tables (path_changes_next and siblings; resumable), then flips them in with the version key in ONE short transaction (drop + rename). A failed pass keeps the old history served (review A3, TestPathHistory_FailedVersionPassKeepsServing). A branch ref that fails to resolve, other than not-found, blocks the flip and is logged (A6).

LOCKING, PREPARE OUTSIDE AND APPLY INSIDE (learned twice on #347): the repo DB opens transactions with BEGIN IMMEDIATE, from a pool of 4 connections with a 5 s busy timeout.
- deriver.prepare does every git read, carry detection and diff BEFORE any transaction. deriver.apply is SQL ONLY, with no object-read fallback.
- A transaction that waits for a pool connection (an object read) while other writers hold the rest in BEGIN IMMEDIATE starves until the timeout.
- Rewind (repopulateBranch) and rebuild (rebuildCommitLog) derive whatever is missing in short batches (pathChangeBatch = 250 commits per transaction).
- Then swapBranch runs ONE SHORT transaction PROPORTIONAL TO THE CHANGE: it deletes the dropped commits and records the new ones, both computed outside the lock.
- Rebuild stages its commit_log rewrite in commit_log_stage outside the lock and swaps it in with bulk statements: 132 ms at 10k commits, about 0.9 s extrapolated to 70k (review A4).
- apply refuses any git read, cache hits included (errReadInApply). Readers see the old branch or the new one, never a mix (TestPathHistory_RewindIsAtomic and TestPathHistory_RebuildIsAtomicAndKeepsOtherBranches pause inside the swap via swapHook and read from another connection; both fail if the clear is committed separately).
- Never add a git read, or a bare-pool query, inside CommitLogApply's Before or Derive.

CONSEQUENCES:
- ANY change to what a row contains (the entry rule, the sort key, the diff, the JSON shape, the depth or jump layout) must bump pathChangesVersion.
- path_changes has a row for every commit_log add/modify row of a .md path; a case-only rename is a carry (markdownChanges mirrors commit_log's first-row-wins). LiveRevision depends on this.
- Rows of commits on no branch are never garbage-collected (a follow-up candidate). Reads scope candidate rows to the branch, so such rows are never scanned at read time. Derivation's liveChange is unscoped by design (git-only); it rejects off-line candidates in keyset pages, costing O(log depth) per orphan row of that path below the parent.

COST, measured 2026-09-29 on this machine's shared disk:
- Opening an upgraded live copy, including the one-time pass: 0.90 s (agentic-engineering) and 2.3 s (knomit-kb).
- Bulk-indexing 10,000 commits: about 11 s.
- Rebuild of a 10,000-commit branch with history already derived: 2.7 s. The worst concurrent write on another branch meanwhile was 1.0 s, with no lock error (TestPathHistory_RebuildDoesNotBlockWriters also checks a rebuild that re-derives 2,000 commits).
- Per append: the derive hook itself is about 0.6 ms. With the extra pages the transaction commits, append costs 11.7 ms against 4.6 ms without derivation (+3 to +7 ms; noisy).

WHAT THIS DOES NOT MEAN: not 'the rows are the source of truth'. They are a rebuildable cache (kb/architecture/store/f6db3a49); :rebuild derives rows that are missing, and a version bump regenerates all of them.
