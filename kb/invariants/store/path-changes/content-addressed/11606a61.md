# path_changes rows are derived IN the transaction that indexes a commit (branch_commits), parents first — an indexed commit is never visible without its rows; the rows are content-addressed, knomit_explain never derives, and any change to the derivation MUST bump pathChangesVersion

RULE (user decision, #347 review round 3): a commit's path_changes rows — plus its commit_fp depth mark and commit_fp_up jump pointers — are written in the SAME transaction that records the commit in branch_commits. They are written by storegit.CommitLogApply's Derive hook, after the commit's commit_log and commit_parents rows. Commits are fed PARENTS FIRST. An indexed commit is therefore never visible without its rows, and knomit_explain never derives anything.

Consequences a maintainer acts on:
- EVERY path into branch_commits must go through CommitLogApply with the hook, fed parents first. populateCommitLog collects the commits the branch has not recorded and orders them with parentsFirst, because go-git's log order is children first. AppendCommitLog falls back to populateCommitLog when a parent was never indexed. CreateBranch copies branch_commits from an already-derived branch, so it needs no hook. A new entry path that inserts into branch_commits directly breaks the invariant.
- The hook REFUSES a commit whose parent object exists but is not derived: errParentUnderived, and the whole transaction rolls back. Never "derive with an empty link". That is review N1: a commit derived before its parent was marked done with an unresolved link, and its history stayed truncated forever. TestPathHistory_TipFirstIndexingNeverTruncates.
- Replacing a branch's visibility is ATOMIC. A rewind and the rebase replay use repopulateBranch (purge + populate in one transaction). rebuildCommitLog clears the branch's commit_log, path_changes, links, jump pointers and marks, then re-populates, in one transaction. It re-populates WITHOUT the one-time pass: that pass would re-derive commits shared with other branches before their commit_log rows are back, and mark them done with no rows. Readers keep the old rows until commit, so there is never an empty or short first page (review N2). TestPathHistory_RebuildIsAtomicAndRepairs, TestPathHistory_RewindIsAtomic.
- An upgraded database, or a pathChangesVersion bump, is derived by deriveUnderived: batched, 1000 commits per transaction, parents first. It runs at the start of populateCommitLog. OpenRepo runs backfillCommitParents BEFORE populate (review N4).
- ANY change to what a row contains — the entry rule, the sort key, the diff algorithm, the RevisionDiff JSON shape, or depth and jumps — must bump pathChangesVersion. Otherwise old rows are served forever.
- Rows are content-addressed: keyed by commit and computed from git objects plus the rows of the commit's ancestors. Branch visibility is applied at READ time: every PathHistory and LiveRevision lookup joins branch_commits or filters by first-parent line.
- path_changes has a row for EVERY commit_log add/modify row of a .md path. A case-only rename becomes a carry. That one-to-one match is what lets liveChange replace first-parent walks (LiveRevision, and resolveActiveCommitForPath's fast path); keep it if you change what gets a row.

COST, measured 2026-09-29:
- Opening an upgraded live copy, including the one-time pass: 1.1 s (agentic-engineering) and 3.1 s (knomit-kb), down from 2.6 s and 8.9 s with per-commit transactions.
- Bulk indexing 10,000 commits: 10.7 s. Jump pointers are packed into commit_fp.ups, one row per commit; one row per level cost 15.4 s.
- Per append, 3k to 10k-commit repos: the derive hook itself is about 0.6 ms. The indexing transaction's commit grows by a few extra B-tree pages, measured at +3 to +7 ms on this machine's disk (BenchmarkPathHistoryDeep: AppendOneCommit 11.7 ms against AppendOneCommitWithoutDerive 4.6 ms). An earlier "inside the noise" reading compared against a baseline that fell back to a full populate; it was wrong.

LOCKING — PREPARE OUTSIDE, APPLY INSIDE (learned twice on #347): the repo DB opens every transaction with BEGIN IMMEDIATE, from a pool of 4 connections with a 5 s busy timeout.
- A transaction that reads git objects — each read takes a POOL connection — while holding the write lock starves. Other writers wait in BEGIN IMMEDIATE holding the remaining connections, so the lock holder cannot get one for its read until the busy timeout. The first round-3 build did exactly that: "database is locked" in the storytests concurrency tests, and synthesize timed out.
- So deriver.prepare does every blob read, carry detection and diff BEFORE the transaction; deriver.apply writes depth, jump pointers and rows with SQL on the transaction only.
- The same applies to the commit_log payload (DiffTree): CommitLogApply receives fully prepared items.
- Rewind (repopulateBranch) and :rebuild prepare everything first, then run their purge or clear and the re-record as one short transaction.
- Never add a git-object read, or a bare-pool query, inside CommitLogApply's Before or Derive.

WHAT THIS DOES NOT MEAN: not 'the rows are the source of truth'. They are a rebuildable cache like every SQLite index (kb/architecture/store/f6db3a49), and :rebuild repairs them.
