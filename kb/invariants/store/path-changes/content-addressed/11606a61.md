# path_changes rows are content-addressed derived state: keyed by commit, derived only from git objects and the rows of the commit's ANCESTORS, parents before children — so no purge, rewind or commit_log rebuild may delete them, and any change to the derivation (including the stored diff format) MUST bump pathChangesVersion

The three tables of migration 000032 hold the per-path change history knomit_explain reads:
- path_changes: entries and carries, with blob, action, author date, message, sort key and the precomputed RevisionDiff JSON
- path_change_links: the edited-from entry per parent
- path_change_commits: which commits are derived

A row depends only on (a) the commit's own tree and its parents' trees, which are immutable for a hash, and (b) the rows of its ANCESTORS. So a row is valid for as long as the commit exists, regardless of which branches can see it.

Consequences a maintainer acts on:
- NEVER delete these rows on purgeBranchCommits, a reconcileMain rewind or rebuildCommitLog. Branch visibility is applied at READ time (every PathHistory lookup joins branch_commits); the rows themselves are branch-agnostic. TestPathHistory_ContinuationAfterPurgeIsHistoryChanged pins that a purged position reports ErrHistoryChanged and that the SAME position continues correctly once the branch is repopulated.
- Derive parents before children. syncPathChanges orders pending commits with Kahn over commit_parents (pendingTopoOrder), because an entry's links and sort key read its ancestors' rows. Deriving out of order silently produces empty links ('' from_commit) and a wrong key.
- ANY change to what a row contains — the entry rule, the sort key, the diff algorithm or the RevisionDiff JSON shape — must bump pathChangesVersion. ensurePathChangesVersion then empties all three tables and the next sync recomputes them. Without a bump, old rows are served forever, because nothing else ever revisits a derived commit.
- Derivation is a self-healing cache. populateCommitLog runs a full pending sync; AppendCommitLog derives the new commit (or falls back to the full sync when a parent is underived); both only LOG a failure, because the ref has already moved. The first PathHistory page re-runs syncPathChangesFor on an underived anchor so a failed derive cannot make the history start at an older change.
- The derivation reads commit_log (the commit's changed .md paths vs parent 0). It must therefore run AFTER CommitLogSync for that commit: both hook sites call it at the end.

- LOCKING (learned the hard way on #347): the repo DB opens every transaction with BEGIN IMMEDIATE (_txlock=immediate, busy_timeout 5 s, a pool of 4). So the derivation (1) does ALL reads, git object loads and diffs OUTSIDE any transaction, then writes one commit's rows in a short transaction; and (2) does NOTHING when the context carries a caller's transaction (storegit.TxFromContext): a call on the bare pool would wait out the caller's own write lock. The first version broke both rules. Other branches' writes failed with "database is locked", and because the version row was never set, every append paid a 5 s wait, which timed internal/synthesize out at 40 min.

COST: one-time derivation measured on 2026-09-29 at 2.6 s (agentic-engineering) and 8.9 s (knomit-kb, ~4k commits) on first open after upgrade. That is dominated by one short transaction per commit, the price of never blocking other writers. Per append it adds a few tree lookups, one diff per changed fact, and one short transaction.

WHAT THIS DOES NOT MEAN: not 'the rows are the source of truth'. They are rebuildable cache like every SQLite index (kb/architecture/store/f6db3a49); emptying the tables is always safe, just slow once.
