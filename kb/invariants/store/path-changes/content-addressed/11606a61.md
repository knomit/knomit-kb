# path_changes rows are derived from GIT ALONE, parents first, and committed no later than the transaction that records a commit in branch_commits — so an indexed commit is never visible without them; rows are immutable per hash and never deleted (a pathChangesVersion bump is the only reset)

RULE (user, #347 review rounds 3-4): an indexed commit is NEVER visible in branch_commits without its history rows (path_changes, path_change_links, and commit_fp: depth plus packed jump pointers).

HOW IT HOLDS:
1. Derivation depends on GIT ALONE: the commit's trees and its parents' trees, plus the rows of its ancestors. It never depends on branch_commits or commit_log. The changed paths ALWAYS come from derivation's own tree diff against the first parent (diffTrees). That diff prunes equal-hash subtrees without reading them and shares a tree cache, so upgrade opens stay at 0.91 s (agentic-engineering) and 2.29 s (knomit-kb). Using commit_log's recorded rows (round 4) made a tampered or drifted row lose a revision for good (review A1). commit_log is consulted only when a tree is MISSING and git cannot list the changes, and the commit is then marked degraded (see kb/invariants/store/path-changes/never-fails-a-write). deriveClosure derives any underived ancestors first, walking git parents-first, and stops at derived commits and at objects genuinely absent from the store (a shallow boundary). It NEVER refuses because a parent is missing from branch_commits: that refusal (round 3) made one legacy gap fail every populate and every WriteFact for good (R1). TestPathHistory_LegacyGapDerivesFromGit, TestPathHistory_VersionBumpOverDeletedSideBranch.
2. Every commit is derived BEFORE the ref that makes it visible advances (deriveBeforeAdvance, run under context.WithoutCancel): every write, merge, fast-forward, rewind, the rebase fast-forward AND replay, upstream advances and CreateBranch. TestRefMoves_DeriveBeforeTheRef injects a read error at four of them and checks the ref did not move. Otherwise a commit is derived in the transaction that records it. The recording transaction's hook refuses a commit without its commit_fp mark (errNotDerived). CommitLogApply is the only writer of branch_commits for new commits: CommitLogSync is deleted, and Derive is REQUIRED. CreateBranch derives the source tip's closure (a lookup when derived) before copying its set.
3. A git READ ERROR fails the derivation; nothing of it is recorded, and a later pass retries. Only plumbing.ErrObjectNotFound for a commit, or ErrPathNotFound for a path, counts as absent (R3). TestPathHistory_ReadErrorRecordsNothing uses deriveObjectHook to inject one.
4. Rows are IMMUTABLE per hash. Nothing deletes them on a rewind or a rebuild, and another branch's history survives a rebuild. Exceptions are DEGRADED rows (commit_fp.degraded > 0), which :rebuild replaces once the objects are back.
   An upgraded database (no key) or a pathChangesVersion change is handled ONLY AT OPEN (openHistory, user decision round 6), before the repo serves anything: every git read is prepared first, then ONE SQL-only transaction rebuilds the rows IN PLACE and writes the key. If it fails, it rolls back and the repo does not open; the next open retries (TestOpenHistory_FailedPassKeepsRepoClosed). Round 5's shadow tables and flip are gone: they lost a write committed between the pass and the flip (B1) and served an empty history after a failed pass (B2). With the version current, the same pass derives only what a branch tip is missing. A branch ref that fails to resolve, other than not-found, is SKIPPED and logged; nothing is derived or served for it (TestOpenHistory_UnresolvableBranchIsSkippedAndLogged). The bootstraps run the same pass before they return: InitRepo, InitFromRemote, InitSubscription, and Replay's raw clone target. It assumes one process on the DB while it opens (kb/gotchas/store/path-changes/open-time-migration).

LOCKING, PREPARE OUTSIDE AND APPLY INSIDE (learned twice on #347): the repo DB opens transactions with BEGIN IMMEDIATE, from a pool of 4 connections with a 5 s busy timeout.
- deriver.prepare does every git read, carry detection and diff BEFORE any transaction. deriver.apply is SQL ONLY, with no object-read fallback.
- A transaction that waits for a pool connection (an object read) while other writers hold the rest in BEGIN IMMEDIATE starves until the timeout.
- Rewind (repopulateBranch) and rebuild (rebuildCommitLog) derive whatever is missing in short batches (pathChangeBatch = 250 commits per transaction), because live writers can contend. The open-time pass is NOT batched: nothing writes during open.
- Then swapBranch runs ONE SHORT transaction PROPORTIONAL TO THE CHANGE: it deletes the dropped commits and records the new ones, both computed outside the lock.
- Rebuild stages its commit_log rewrite in commit_log_stage outside the lock (with an empty-path sentinel row per reachable commit) and swaps it in with bulk statements. Like dev's rebuild, it replaces EVERY commit_log row of the branch's commits: a commit that changed nothing keeps none, and a dropped commit on no other branch loses its rows. A dropped commit still on another branch keeps them (B8, TestRebuild_ReplacesEveryCommitLogRowOfTheBranch). The swap deletes only rows that DIFFER from the stage (NOT EXISTS an identical stage row, compared with IS so NULLs match), and INSERT OR IGNORE fills the gaps. An unchanged branch's swap therefore writes no commit_log row (round 7, C3; TestRebuild_UnchangedBranchWritesNoCommitLogRow counts writes with a trigger). The stage is deleted after the swap, OUTSIDE its lock, whether the rebuild succeeded or failed (B9); open clears what a crash left. Swap at 10k commits for an unchanged branch: 41-115 ms, down from 220-238 ms when it rewrote every row (round 6). TestPathHistory_SwapIsProportional counts branch_commits inserts and deletes with a trigger: 0 for an unchanged rebuild, k for a rewind by k (B5; a delete-all revert gives 82).
- Readers see the old branch or the new one, never a mix (TestPathHistory_RewindIsAtomic and TestPathHistory_RebuildIsAtomicAndKeepsOtherBranches pause inside the swap via swapHook and read from another connection; both fail if the clear is committed separately).
- apply refuses any git read, cache hits included (errReadInApply).
- Never add a git read, or a bare-pool query, inside CommitLogApply's Before or Derive.

CONSEQUENCES:
- ANY change to what a row contains (the entry rule, the sort key, the diff, the JSON shape, the depth or jump layout) must bump pathChangesVersion.
- path_changes has a row for every commit_log add/modify row of a .md path; a case-only rename is a carry (markdownChanges mirrors commit_log's first-row-wins). LiveRevision depends on this.
- Rows of commits on no branch are never garbage-collected (a follow-up candidate). Reads scope candidate rows to the branch, so such rows are never scanned at read time. Derivation's liveChange is unscoped by design (git-only); it rejects off-line candidates in keyset pages, costing O(log depth) per orphan row of that path below the parent.

COST, measured on this machine's shared disk (round 5 on 2026-09-29, round 6 on 2026-09-30):
- Bulk-indexing 10,000 commits: 17.7 s in round 6 (median of 3 alternating runs, against 19.3 s in round 5). commit_log's payload now REUSES derivation's tree diff (changeLists, filled by prepare, taken by indexItems), so a commit is diffed once (TestIndex_OneDiffPerCommit). ONLY a deriver whose commits are recorded next keeps its lists: newIndexingDeriver is used by deriveBeforeAdvance, recordCommits, swapBranch and rebuild's closure. The open-time pass and rederiveDegraded keep none (round 7, C1; TestOpenHistory_KeepsNoChangeLists). Otherwise their lists piled up per repoHandler to the 200k-entry cap, and the wholesale drop at the cap cost a concurrent write its one diff. TestCommitChanges_EqualsGitDiff pins that diff to go-git's DiffTree under commit_log's first-row-wins rule. Round 4's shortcut through commit_log rows was faster and wrong.
- Upgrade open (round 6, one transaction): 0.91 s (agentic-engineering) and 2.29 s (knomit-kb).
- Open-pass memory (round 7, C2): derivation carries a commitMeta (hash, tree, parents, author time, first message line) instead of *object.Commit. The open pass drops its walk and the object caches before the transaction. Peak heap over the base during an upgrade open: 4.8 MB at 2k commits and 15.6 MB at 10k, down from 8.3 MB and 32.6 MB. Open time is unchanged at about 1.2 s and 6.6 s, so extrapolated to 100k commits it is roughly 160 MB and 65 s. Still ONE transaction by decision: no staging table.
- Rebuild of a 10,000-commit branch with history derived (round 7, 2 runs): 1.3-1.6 s, of which the swap transaction is 41-115 ms. The worst concurrent write was 0.75-1.21 s, against 0.68-0.70 s for the same writer with no rebuild. TestPathHistory_RebuildDoesNotBlockWriters asserts the swap stays under a quarter of a 2,000-commit re-deriving rebuild, measured at about 10 ms of 1.3 s.
- Per append at 10k commits (round 6, median of 3 alternating 300-iteration runs): 14.4 ms, against 16.5 ms before the single diff. That difference is within this disk's noise: recording without derivation alone ranged 8-13 ms across the same runs.

WHAT THIS DOES NOT MEAN: not 'the rows are the source of truth'. They are a rebuildable cache (kb/architecture/store/f6db3a49); :rebuild derives rows that are missing, and a version bump regenerates all of them.
