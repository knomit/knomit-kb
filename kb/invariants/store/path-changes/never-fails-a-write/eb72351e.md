# History derivation never fails a write: a missing parent commit is a history boundary, a missing blob or tree on the path is a content_unavailable revision, and derivation runs BEFORE the ref advances, so a write never ends with its ref moved and its call failed

RULE (user decision, #347 review round 5): nothing about history derivation ever fails a write.

How it holds:
1. DEFINITIVE ABSENCE never fails a derivation. Only plumbing.ErrObjectNotFound, or ErrPathNotFound for a path in a tree, counts:
   - A missing PARENT COMMIT is a history boundary, like a shallow clone's: the child is `added`, with no link below it, and depth restarts. commit_fp.degraded = 2, which propagates to descendants because their depths are cut too.
   - A missing BLOB, or a missing TREE on the path, still records the revision and its links, but with content_unavailable = 1: blob '' when unknown, and no diff. This covers the revision whose content is missing AND the revision edited from it, whose diff base is missing. degraded = 1.
   - A tree missing from the DIFF itself means git cannot list the changed paths. That is the one case where commit_log's recorded rows are used, and the commit is degraded.
2. Derivation runs BEFORE a ref advances: deriveBeforeAdvance runs at every write (writeFile, deleteFile, batchWrite), merge (fast-forward and merge commit), advanceBranchTo (create, fast-forward, rewind), the rebase fast-forward (round 6, B3) and replay, upstream advance, and CreateBranch. TestRefMoves_DeriveBeforeTheRef pins four of them: a read error there leaves the ref unmoved. The bootstraps and a version change derive at OPEN instead (openHistory), before anything is served; a transient failure there fails the OPEN, never a write, and missing objects still become boundaries or content_unavailable. A transient read error, which still fails and retries (R3), therefore fails the call before the ref moves, never after. Round 4 failed every write after its ref had moved (review A2).
3. Degraded rows are NOT frozen. :rebuild (rederiveDegraded) re-derives every degraded commit once its objects are back, parents first and replacing its rows in one transaction; a version change re-derives everything at the next open. TestPathHistory_RestoredObjectsAreRederived covers both a blob and a commit.
4. Damage is REPORTED by Verify (CategoryGitReachability), not by history; knomit_explain only shows content_unavailable on the revision.

Consequences:
- A new code path that moves a branch ref to a new commit must call deriveBeforeAdvance first. Otherwise AppendCommitLog derives after the move, and a transient failure there reintroduces the torn write.
- Never map a transient read error to absence: that records a permanent wrong row (R3). TestPathHistory_TreeAndParentReadErrorsFail and TestPathHistory_ReadErrorRecordsNothing inject them through deriveObjectHook.
- The commit_log payload reuses derivation's tree diff (commitChanges; round 6, B7). Where derivation had no complete diff (a tree missing), building the payload still needs the commit's trees and fails. That is pre-existing indexing behaviour, not history derivation.

WHAT THIS DOES NOT MEAN: not 'derivation swallows errors'. It turns only definitive absence into recorded, repairable state; everything else fails loudly and early.

**Caller cancellation is not a derivation failure.** `deriveBeforeAdvance` runs under `context.WithoutCancel(ctx)`, as `notifyCommit` does. A write that has already built its commit must complete even when the caller's ctx is cancelled (`fact_write_cancel_test.go`: `TestWriteFact_/TestDeleteFact_CancelledContext_KeepsGitAndIndexConsistent`). Honouring cancellation there failed the write with `path changes: mark: context canceled`, the first full-suite run of round 5 caught it, and 9c1edc8b fixed it. Anti-pattern: passing the caller's ctx straight into any new pre-advance step.
