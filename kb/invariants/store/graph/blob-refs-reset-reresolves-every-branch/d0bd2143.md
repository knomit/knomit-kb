# The GraphSchemaVersion 8 reset drops EVERY branch's reference edges, so the rebuild that spends it must re-resolve EVERY row of `branches` (open experiments included), not only the branches the heal rebuilds

resetBlobRefsOnce (index/derived_from.go) deletes every DERIVED_FROM edge and every refs_commit claim in the store ONCE (meta sentinel derived_from_per_blob), inside the first rebuild's phase-A transaction. The heal (planIndex) rebuilds only the read branch and upstream, so a blob that lives only on another indexed branch (an open experiment) would stay edgeless, and later come back pinned at a merge commit (PR #693 review B1).

THE RULE: in the SAME transaction as the reset, every row of `branches` gets a meta mark derived_from_per_blob_pending:<branch>. After its own phase B, rebuildGraph runs reResolvePendingBranches: phase B over each pending branch's commit_log events (reResolveBranchRefs, skipping (commit, path) events already resolved), then deletes that branch's mark, but ONLY if none of that branch's edge writes failed (the rebuilt branch included); a failed write keeps the mark and un-marks the event, so the next rebuild re-resolves it, as after a cancellation. The rebuild itself still succeeds: failing it would turn a permanent per-blob failure into a full re-index on every boot (the PR #73 lesson in kb/architecture/store/graph-schema-version). ANY rebuild drains whatever marks it finds.

Crash safety: the reset, the sentinel and the marks commit together; a mark is cleared only after its branch was re-resolved; the rebuilt branch's per-branch schema version is bumped by Rebuild only after rebuildGraph returns. An interrupted drain therefore leaves marks AND an un-bumped branch, the next boot rebuilds that branch, and its rebuild drains the remaining marks.

The drain takes NO other branch's LockBranch (nesting branch locks under a rebuild could deadlock against writers that lock in another order). It is safe because phase B only adds edges and claims, and each blob's claim and edges are written in one transaction that re-checks the claim (applyBlobRefs).

OPERATIONAL CONSEQUENCE: any future one-time, store-wide reset of shared graph state (edges and node props are shared by all branches) must also schedule the re-derivation of every branch, crash-safely, before the triggering branch's version is bumped.

WHAT THIS DOES NOT MEAN: it does not make every branch's FULL index rebuild on upgrade; only reference edges are re-resolved for branches the heal does not rebuild. And it does not lock those branches: a branch written concurrently still resolves its own new blobs through its own index sync.
