# A blob's reference edges are resolved only at a commit that HOLDS the blob and that a branch reaches: the earliest introduction (path_changes) wins whether or not the blob is claimed, and a claim at a commit no branch reaches is VOID

introducingCommit (index/derived_from.go) picks the commit a blob's refs are resolved at. The commit the indexer passes comes from LastCommitForPath (the latest NON-merge commit touching the file, which can misattribute: kb/gotchas/store/git/last-commit-for-path) or a rebuild/drain commit_log event, so it may not hold the blob, may not be its earliest introduction, or may be on no branch any more.

THE RULE (whether or not the blob is claimed):
- the answer is the EARLIEST, in commitEarlier order, of (a) path_changes rows with entry = 1 for (path, blob) whose commit is in some branch's branch_commits, each re-checked to hold the blob, and (b) the passed commit if it holds the blob AND some branch reaches it;
- none of those and the blob has a LIVE claim: "" (write nothing);
- none of those and no live claim: the branch tip's live version, or the tip, IF it holds the blob (a merge being indexed before branch_commits names it); then, last, a passed commit that holds the blob but that no branch reaches; "" if the branch itself is gone;
- never a commit that lacks the blob.
For a claimed blob, claimBlobRefs then compares that answer with the claim: an earlier introduction the claim missed moves it (PR #693 round-2 m4).

VOID CLAIMS: a refs_commit claim whose commit is in no branch_commits row (RollbackExperiment drops the branch and its branch_commits; a rewind drops commits) is void wherever claims are read: readBlobClaim (blobClaim.void), claimBlobRefs, the re-check inside applyBlobRefs, and blobRefsClaimed. The next arrival re-claims the blob, and applyBlobRefs deletes the void claim's edges in the same transaction (PR #693 round-2 B3: a rolled-back experiment's claim made R's incoming on the agent branch empty and broke rebuild == incremental).

Why branch_commits: path_changes rows and claims are immutable or global and survive rewinds and rollbacks; a rebuild never visits an orphaned commit, so using one breaks rebuild == incremental, and readers filter source_commit by the branch.

OPERATIONAL CONSEQUENCE: never prefer a merge carrying the blob, a tip holding it, or an orphaned commit over the reachable commit that wrote it; never trust a claim without checking that its commit is still reachable.

WHAT THIS DOES NOT MEAN: the earliest introduction is per path; it does not search other paths for the same bytes. A rename or a copy at another path resolves to its own (later) introduction there, and the claim on the original path refuses it.
