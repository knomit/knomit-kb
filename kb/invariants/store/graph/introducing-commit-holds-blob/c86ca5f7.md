# A blob's reference edges are resolved only at a commit that HOLDS the blob at that path: an unclaimed blob goes to its earliest introduction (path_changes), never to the passed commit or the branch tip when they do not hold it

introducingCommit (index/derived_from.go) picks the commit a blob's refs are resolved at. The commit the indexer passes comes from LastCommitForPath (the latest NON-merge commit touching the file, which can misattribute: kb/gotchas/store/git/last-commit-for-path) or a rebuild's commit_log event, so it may not hold the blob.

THE RULE:
- blob already claimed: the passed commit if it holds the blob at the path (the claim then decides whether it is an earlier introduction), else "" (write nothing);
- blob NOT claimed: the earliest, in commitEarlier order, of (a) path_changes rows with entry = 1 for (path, blob) whose commit is in some branch's branch_commits, each re-checked to hold the blob, and (b) the passed commit if it holds the blob;
- only when neither exists (a merge commit being indexed before branch_commits names it): the branch tip's live version, or the tip, IF it holds the blob;
- otherwise "": no edges. Never a commit that lacks the blob.

Why branch_commits: path_changes rows are immutable and survive rewinds and rollbacks, so an orphaned commit (a rolled-back experiment) is still listed; a rebuild never visits it, and picking it would break rebuild == incremental.

OPERATIONAL CONSEQUENCE: a merge that carries a blob, or a tip that holds it, must never be preferred over the commit that wrote the blob: that pinned F to the agent branch's newer R2 after a merge-mode experiment commit (PR #693 review B1, probe E).

WHAT THIS DOES NOT MEAN: it does not search other paths for the same blob (a rename's new path); the earliest introduction is per path, and the rename case is already claimed.
