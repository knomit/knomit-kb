# resolveActiveCommitForPath walks first-parent, NEVER wall-clock

When resolving 'what was the active commit for path X at commit Y', the walk MUST follow first-parent ancestry, not wall-clock timestamp ordering. The merge anomaly: if a sibling-branch commit touches X with a later wall-clock time than our local branch's last write to X, then gets merged back in, wall-clock SQL would pick the sibling commit. First-parent ancestry correctly stays on the merged-INTO line and picks the local commit. Deletions are STEPPED OVER (write events in the path's sparse history, not stop conditions) — the walk continues to the previous add/modify.

factIndex.readFileLastCommit (the fact read's ?fallback=before / ReadFactOpts.BeforeCommit path) ALSO obeys this now. It previously VIOLATED the invariant: it walked go-git history with gogit.LogOrderCommitterTime (wall-clock) starting from the first parent, which both ordered by committer time AND — because go-git's file-log lands on the most recent change — returned ErrPathNotFound when that change was a deletion, so fallback-before 404'd at any commit AFTER a retraction instead of stepping back to the last valid version. PR #77 rewrote it to resolve via fi.rh.resolveActiveCommitForPath (first-parent, steps over deletes) and read the blob at the resolved commit, keeping 'before' exclusive by starting from firstParentCommit(beforeCommit). This is also what made the fact read agree with /incoming and /outgoing, which resolve the same way. Per the 'git is the only source of truth, everything else is rebuildable cache' principle, history navigation reads the index (commit_log + commit_parents), not a live go-git walk; resolveActiveCommitForPath lives on repoHandler so both searchIndex and factIndex share it.
