# Tree-shape rule: judgeCommit FIRST checks (checkTreeShape) the commit's tree and every parent's tree, in every repository, refusing `malformed-tree`; receive-pack's closure runs the same check in EVERY verify_signatures mode (off included), and checkM3 and the member loader fail on a malformed tree instead of ending early

Built in PR #523 (merge commit 3ac59b57; found by the follow-up review as a pre-existing blocker, fixed in b2ef014f and pinned in 4f0f7ce3 on the branch).

THE RULE. judgeCommit (internal/store/verify_range.go) calls commitTreeShape first, before M3 and before every record, owner and artifact rule, in EVERY repository (not only the fleet). commitTreeShape runs checkTreeShape (internal/store/verify_tree.go) over the commit's tree AND over every parent's tree. A failure is refused with rule `malformed-tree` (RuleMalformedTree), the reason naming the path, and `parent <hash>:` when the parent's tree is the bad one. CheckRange (`knomit verify ci`), receive-pack verify and any fetch-time judge reach it because they all call judgeCommit.

WHAT 'WELL FORMED' MEANS (checkTreeShape walks entries by hand, not with go-git's walkers): every Dir entry resolves to a tree; every file and symlink entry resolves to a blob; the objects exist; names pass go-git's ValidTreePath (this excludes .git, its HFS/NTFS variants, '.', '..' and control characters), hold no '/', and appear once per tree; depth is at most 1024 (go-git's own limit). A gitlink is not looked up (its name is still checked), consistent with reachableNew and M3. Tree decoding canonicalises every mode (an unknown mode reads as a gitlink), so there is no 'other mode' branch. Results are memoised per tree hash within one judge or push.

WHERE ELSE IT IS ENFORCED. (1) receive-pack's privatePathClosure calls commitTreeShape for each new commit in EVERY verify_signatures mode, off included, refusing with `knomit: commit <h> refused: malformed-tree: <path>`. The closure needs it because quarantine.reachableNew trusts any object the host ALREADY holds, so a Dir entry naming a held blob passed the completeness walk; before the fix such a push moved the ref and then failed at populateCommitLog ('a tree is missing'). (2) checkM3's flatten runs checkTreeShape first: a malformed tree is an error, never an early end. (3) loadMembersOfTree fails the load. Each of the four has its own sabotage-red test.

WHY. go-git's walkers truncate silently at a malformed directory entry (see the go-git TreeWalker gotcha), so every gate walk would judge a prefix of the tree: an unsigned merge could add content after the bogus entry (M3 OK), and a member could make every member sorting after its own folder vanish from the loader.

NOT COVERED: the closure's merge-base trees are not shape-checked (privateChangeFromBase); a truncated base only drops changes or makes paths look added (more refusals), and the merge-time private-path guard stays the authority. Only the immediate parents are shape-checked, not all ancestors.

MISREADINGS. 'verify_signatures: off means a push is not checked for shape' is false: the closure refuses in every mode. 'reachableNew already refuses bogus trees' is false for objects the host holds. 'A real git client can send such a tree' is false in practice: git never writes one and a go-git client omits the objects, so the host answers 'incomplete'; the test builds the pack by hand.
