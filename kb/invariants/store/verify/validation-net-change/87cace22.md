# RuleValidation judges a branch's NET change, not each commit: a fact is judged only when its content at the tip differs from main AND from the content at EVERY merge base; enforced in every verify_signatures mode and every repository at receive-pack, the fetch judge, `knomit verify ci` and the master's own range, and on the merge RESULT in MergePushed/MergeConsensus; a later fix or delete unsticks a branch, and the refusal names the commit that WROTE the failing content

RULE (PR #533, squash commit 6f241959 on dev, verified there; ruling: kb/decisions/fact/validation/enforced-everywhere/338656ce.md). store.branchFactsValid(tip, main, ont, root) validates, with fact.ValidateFact on the fact's topic path (the typed context gate, then root, topic and declared-child rules), every fact path under the fact root (a .md, no dot segment) that satisfies BOTH: (1) its blob at the tip differs from main's, and (2) it is NOT equal to its blob at every merge base of tip and main. The ontology is the one at MAIN (receive-pack and the fetch judge: upstream's tip; the merge guards: the destination's tip), never the pushed branch's own tree, so a pushed ontology cannot choose its own rules. Deletes are never judged, a file that does not parse as a fact is skipped as the index skips it, and main nil (no consensus branch yet) judges every fact at the tip.

WHERE IT RUNS: receive-pack on any knowledge-base host (incomingValid, before the mode check), the fleet fetch judge (AdmitPeerBranch / JudgePeerBranch, which the merger's re-judge and the fleet UI merge also use), `knomit verify ci` (CheckRange, new --kb-root flag), and the master's own range (kb/invariants/store/verify/own-range). The pushed-branch merges (MergePushed, MergeConsensus) instead validate the merge RESULT against the destination (validateFacts); they answer *ValidationRefusedError (the merger remembers it per tip; the UI answers 409). Every OTHER rule (signature, record, ownership, artifact, host-record, not-pusher) stays per commit.

WHY NET CHANGE. The first build judged each commit. A commit valid when written but refused once main's ontology tightens (an owner adds a validation; the master's refreshFleetOntology after an upgrade adds a rule) stayed in tip minus main forever, and a later commit fixing the fact did not help, for a plain knowledge-base member with no way out. Net change judges the fact as fixed. The merge-base condition (2) keeps a stale branch that never touched a fact from being judged for main's newer version of it (TestValidation_AStaleBranchIsNotJudgedForWhatMainChanged).

EVERY merge base, not one. With several best common ancestors (a criss-cross), git's ort merge builds a VIRTUAL base from all of them, while go-git answers them newest first by a committer date the pusher sets. Skipping a fact that equals ONE base lets a merge that resolves it back to invalid content through (TestValidation_ACrissCrossCannotSmuggleAnInvalidFact, both date orders).

THE REFUSAL NAMES THE WRITER. Text `knomit: commit <hash> refused by the ontology's validations: validation: <reason>` where <hash> is introducedBy: the commit of tip minus main that wrote the failing blob, preferring a NON-merge commit (a merge cannot be dropped), and among several the latest by topology (a writer that is not an ancestor of another writer), never by committer date. It is NOT necessarily the tip. This is the commit a fix or Drop must address.

A HELD TIP IS STILL JUDGED. Under net change the host holds the invalid intermediates of branches it admitted fixed, so receive-pack loads a tip it already holds and judges it; a ref forced back onto such an intermediate is refused (TestValidation_APushOntoAHeldInvalidIntermediateIsRefused). Holding a commit is not admitting it.

CONSEQUENCES / MISREADINGS. (1) 'A branch with an invalid commit is stuck': false, a later commit that fixes or deletes the fact unsticks it (TestValidation_AFixedBranchIsAdmittedAfterMainTightensItsOntology). (2) 'Every commit in main's history satisfies the ontology': false by design, admitted branches can carry broken-then-fixed intermediates. (3) 'An untouched legacy invalid fact blocks a push': false; only a fact the branch changed against main and a base is judged. (4) 'It runs in verify_signatures=enforce only': false, every mode. (5) A merge that reverts a fact to an older invalid parent version is caught, because the tip's content is what is judged (an earlier draft's known gap, closed by this rule). (6) The merge-time result check on hosts and `verify ci`'s merge-result check cover what merging LANDS; this rule covers the tip: kb/invariants/store/verify/ci-merge-result.
