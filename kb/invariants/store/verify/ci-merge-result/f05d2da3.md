# `knomit verify ci` also judges what MERGING the candidate into main lands: git merge-tree --write-tree (git 2.38+, main's attributes via attr.tree on 2.42+) in every mode; facts in the result that differ from main are validated against main's ontology, a conflict is `merge-conflict` (blocks in every mode), and a git that cannot run the merge is exit 2, never a pass

RULE (PR #533, squash commit 6f241959 on dev, verified there). store.mergeResultValid(kbDir, kb, mainC, candC, ont, root) runs in CheckRange (`knomit verify ci`) in EVERY mode, right after branchFactsValid passes (kb/invariants/store/verify/validation-net-change). It runs `git -C <checkout> -c attr.tree=<main> merge-tree --write-tree --no-messages <main> <candidate>`:
- main already an ancestor of the candidate: nothing to do (the merge is the tip, already judged);
- exit 0 (clean): the first output line is the result tree; every fact in it that differs from main is validated against MAIN's ontology (newFactPaths + invalidAmong). A failure is RuleValidation on the candidate tip with the reason 'merging the branch into main would land a fact that the branch and main each keep valid apart: ...; bring main into the branch and fix it there';
- exit 1 (conflicted): not admitted; RuleMergeConflict = `merge-conflict`, which blocks in every mode like `validation` (ExitCode);
- any other git failure (git older than 2.38, unrelated histories, a shallow checkout missing the merge bases): an error, so the gate exits 2 ('could not run'), never a pass (TestValidation_AGitThatCannotMergeIsNeverAPass, a PATH shim that prints merge-tree usage and exits 129; skipped on Windows). CI needs fetch-depth: 0 for the merge bases (tools/ci/verify-signatures.yml has it).
- ATTRIBUTES: `-c attr.tree=<main>` (git 2.42 or later) reads .gitattributes from MAIN's tree, not from the checkout's work tree, which CI checks out at the candidate, so a candidate's `*.md merge=union` cannot choose how its own merge is judged (TestValidation_ACandidatesGitattributesDoNotChooseItsMerge). A git 2.38 to 2.41 ignores the unknown key and reads the work tree's attributes: a divergence in the safe direction (a union driver only touches hunks that would conflict on the server).
- Side effect: the result's objects are written into the checkout's object store; no ref, index or work tree changes.

WHY. git merges a fact hunk by hunk, so two sides that each keep a cross-field rule (main shortens the title, the branch raises the confidence; rule `fact.confidence < 0.95 || fact.title.length > 3`) can merge cleanly into a fact that breaks it, and judging only the candidate's tip passes it. For a GitHub-hosted knowledge base `verify ci` IS the gate (kb/decisions/verify/forge-ci/fda838bb.md; it merges with `gh pr merge --merge`, git's ort strategy). The shipped hypothesis 'Settlement:' rule and kind/type rule are cross-field, so this needs no adversary, only two agents editing different lines of one fact while the candidate is behind main (TestValidation_TwoValidSidesThatMergeIntoAnInvalidFactAreRefused, with a control where the branch merges main in and fixes the title).

MISREADINGS. (1) 'The hub and knomit's own merges run this': no. They validate their own merge RESULT in-process (validateFacts in MergePushed and MergeConsensus); only verify ci shells out to git. (2) 'A merge-conflict refusal means the content is invalid': it means the merge cannot be judged; the fix is to bring main into the branch and resolve there. (3) 'verify ci passing means the merge lands valid': only if main has not moved since the check (kb/gotchas/verify/forge-ci/main-moves-after-verify). (4) 'It needs git on a runner that has it': the gate fails closed (exit 2) where git is old or absent from the path.

PINNED BY TestValidation_ACandidateThatConflictsWithMainIsRefused (a clean valid candidate behind main is admitted; both sides rewriting the title line is refused merge-conflict), and the three tests above. Cross-checked in CI: the ubuntu runner's git is new enough.
