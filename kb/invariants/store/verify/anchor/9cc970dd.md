# The verified anchor never moves past a failing commit in ANY mode, never moves on a rewind, and its context comes from the fold (verify_context cache, recomputed from the root on a miss) — never from the anchor commit's own ontology file

`refs/knomit/verified/<upstream>` is the anchor: the furthest first-parent commit whose whole history the fold accepted. Rules (verify_anchor.go, verify_gate.go):
- It moves ONLY to a fold's NewAnchor. It never passes a failing commit in any mode (in log the upstream moves to origin but the anchor stays, so the report repeats every tick), and a REWIND (origin no longer contains the anchor) never moves it, in every mode.
- It is written only while verification is on. An off repository keeps an off-scan watermark in meta (`verify_scan:<upstream>`) instead, and a verified disable RETIRES the ref.
- The context in force AT the anchor lives in the `verify_context` table (migration 000027), keyed by commit. A miss is recomputed by folding from the root. It is NEVER read from the anchor commit's ontology file, which may carry a policy change the fold rejected and ignored.
- The ref is under refs/knomit/, so no fetch refspec, /git advertisement or push touches it.

WHERE THE LOCAL UPSTREAM GOES (verifyAdvance, called by reconcileMain before any SetReference): off and log move to origin; enforce, or an unrooted policy change, moves to the anchor (refs advance up to the last good commit and stop there); never backwards; a rewind holds in enforce. Sync returns ErrVerifyFailed (VerifyFailedError with the report) after the agent step when the advance was blocked.

CONSEQUENCE: anything that moves the anchor by hand (PR 4's re-anchor) must also drop the in-memory history cache (repoHandler.verifyBelow), or the next tick folds against a stale set.
