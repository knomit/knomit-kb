# 'Derived state is safe to lose' holds only at the layer whose producing computation is the one that will re-run — on the abstraction axis the title vectors are disposable, the restatement pair cache is NOT (asymmetric top-K), and a deleted verdict pair is a decision, not cache

Derived state is safe to lose only when the computation that produced an entry is the same computation that will run again to reproduce it; in a chain of caches each derived from the previous, that condition holds at one layer and silently fails at the next, so 'derived, therefore disposable' must be re-checked per layer rather than inherited from the base.

The three layers of the abstraction axis, where the rule flips:
- LAYER 1, `fact_titles_vec` — DISPOSABLE. One title vector per fact VERSION keyed by `facts.id` with `UNIQUE(path, blob_hash)`; an edited fact is a new row with no vector, so 'rows lacking a vector' IS the delta (`LiveFactsMissingTitleVector`), with no watermark and no bookkeeping. Code-managed at the active model's dimension (`ensureFactTitlesVec`), because vec0 cannot be ALTERed. Renames are NOT free (path is in the key), superseded versions are NOT self-cleaning (the delete trigger fires only on a facts DELETE), and a missing vector is NOT an error during backfill. It shares `facts_vec`'s embedding identity, so a model change invalidates it — and an identity MATCH does not prove the table is at the right width.
- LAYER 2, `restatement_pairs` — NOT DISPOSABLE. The cache is the union over every fact's top-K, and top-K is asymmetric: a pair may exist only because B's neighbourhood contained A. Dropping the pairs that touch a changed fact and rescanning that fact cannot re-mint them, because they were never in its top-K; the cache looks healthy and simply shrinks with every edit. The repair — requeue the PARTNERS (`PartnersOfFacts`) — reproduces the identical loss one level out if requeuing a partner also deletes the partner's pairs. Bound by `TestDynamics_PairsSurviveAnUnrelatedEdit`.
- LAYER 3, `restatement_verdicts` — DELETION IS THE RECORD. A judged pair is DELETED from `restatement_pairs` when its verdict lands; deletion is the re-offer exclusion, so `RestatementPairsByMatchKind` needs no verdict join. Verdicts are branch-scoped and their schema says losing them is safe only in the sense of optimistic cold-start: on a fresh agent branch or after DB loss, pairs are re-detected and re-judged. A pair retired WITHOUT a verdict stays standing and can be re-offered.

Where the vec0 substrate adds its own trap at every layer: vec0 applies its `k` window BEFORE any WHERE, so a KNN that asks for exactly k and then filters to live/branch/kind comes back short, or empty on a repo carrying many superseded revisions — `TopTitleNeighbours` over-fetches by `titleKNNOverfetch` and `graphBuildSimilarityEdges` pays `knnK+1`. Adding a predicate never makes vec0 look harder; it only discards matches already found.

WHAT THIS DOES NOT MEAN: it does not contradict the corpus-wide rule that derived SQLite state is regenerated from git rather than data-migrated — that rule is about regenerating from the SOURCE, and layer 2's source is a scan of OTHER facts, not the changed fact. Nor does it mean the axis needed a GraphSchemaVersion bump: an empty axis is the CORRECT state because the review pipeline fills it lazily. 'The pair query has no verdict join' does NOT mean judged pairs are re-offered — a reader auditing the SELECT alone draws exactly that false conclusion. The axis is epistemic-only, FORCED (prune does not carry Kind through mergedFact), not chosen.
