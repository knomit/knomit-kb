# MergePushed and MergeConsensus refuse a merge whose RESULT would change any dot path of the host's agent branch (*PrivatePathMergeError) — this, not receive-pack, is the authority that a pushed branch never changes the host's .knomit/

The only two routes from a pushed branch into the host's AGENT branch (which the upstream/main then follows) are `store.MergePushed` (the operator's web merge) and `store.MergeConsensus` (the consensus merger under `consensus: auto`). Both set `mergeOpts.guardPrivate`. In `mergeIntoBranchLockedOpts`, after the three-way tree is computed and before any commit is written, the merged tree is diffed against dst's tree. If any changed path satisfies `fact.IsPrivatePath` (any segment beginning with `.`: `.knomit/`, `.gitignore`, `.github/`, `kb/.drafts/`), the merge is refused with `*PrivatePathMergeError{Src, Dst, SrcTip, Paths}`, matched with `errors.Is(err, store.ErrPrivatePathMerge)`. Nothing moves. The check judges the RESULT, so an explicit side (ResolveSrc) or a `conflicts` setting that picks the peer's version of a dot path is refused too.

Surfacing:
- The consensus merger (`internal/corpus/repos/consensus.go` mergeOne) records it like a conflict: `m.refuse` remembers the refused tip, emits one warning naming the paths, and moves on to the other branches of the same round. The branch is retried as soon as its tip moves.
- The web merge (`writePushedMergeError` in internal/edge/web/handlers_pushed_branches.go) answers 409 "Merge would change system files" with extras `private_paths` (the sorted dot paths) and `peer_commit` (the refused src tip); pinned by TestPushedMerge_PrivatePathRefused, which also asserts the agent branch does not move.

Why merge time: receive-pack judges only the commits a push SENDS. A push whose tip the host already holds (another agent/* tip, an old tip of a rewound branch, a branch pushed before the push-time closure existed) brings no new commits and skips both the closure and the signer rule; a push-time-only rule also cannot reach branches already on the host. The guard judges current state, not history. That heals ONLY a branch that merely LAGS behind (its dot paths are an older upstream's, and merging the newest upstream makes them equal again; it then passes on the next round). A branch whose OWN history changed a dot path keeps that change through any merge of the upstream and passes only once the member REVERTS the change on its branch; merging upstream does not fix it. The consensus warning names both remedies.

WHAT IT DOES NOT MEAN: it does not stop the HOST's own writes to `.knomit/` (ontology edits, template init); it does not apply to the agent sync's own merges of the upstream (other mergeIntoBranch callers do not set guardPrivate); and receive-pack's closure is not redundant, but it is now only early feedback (kb/invariants/store/git-serve/receive-pack/content-closure/692bbe0d.md). Any NEW route that merges a pushed branch into the agent branch must set guardPrivate.

The guard runs after conflict detection and only when the merged tree differs from dst's tree; a tree-identical merge cannot change a dot path. Verified at merge commit 1441b044 (PR #511).
