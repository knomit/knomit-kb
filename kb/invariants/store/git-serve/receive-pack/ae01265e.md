# A receive-pack push is ALL OR NOTHING and writes NOTHING to the host until every rule and the signature judge have passed — then promotes in one transaction and registers on an uncancellable context

Three rules hold the receive-pack path (internal/engine/store/gitserve/httphandler_receivepack.go) correct; each has a test that a sabotage turned red.

1. ALL OR NOTHING across commands. A push naming the pusher's own branch AND anything else (a foreign ref, a second ref) is refused WHOLE: the own branch does not move. A per-command judge that applies the passing command and refuses the rest still returns an error to go-git naming the foreign ref, so only an assertion that the OWN ref is unchanged catches it (TestReceivePack_TwoRefsRefusedWhole).

2. NOTHING ON THE HOST BEFORE THE DECISION. The pack goes into an in-memory quarantine; the host's SQLite storer writes each object immediately (SetEncodedObject autocommits) and could not be rolled back. Only after the ref rules, the old-hash check and the verify_signatures judge does `storegit.PutObjects` copy the objects the new tip reaches, in ONE transaction. A refused push leaves the host's `objects` count unchanged (TestReceivePack_RefusesOutsideOwnBranch asserts the count).

3. REGISTRATION ON context.WithoutCancel. From the promote onwards the request context is replaced by context.WithoutCancel: both CreateBranch and advanceBranchTo move the ref BEFORE the context-bound SQL (EnsureBranch, then PopulateCommitLog, or RepopulateBranch on a force-update, then NotifyCommit) that describes it, and net/http cancels a request context whenever the client goes away (a timeout, Ctrl-C). A cancelled registration would leave the ref at the pushed tip while branch_commits and the index describe the old one — the torn state notify-commit-single-chokepoint forbids (TestReceivePack_CancelAfterAcceptStillRegistersWhole). Everything BEFORE the promote may honour cancellation: nothing has been written then.

MISREADING TO AVOID: rule 3 is not 'ignore the client'. The client may abandon the response; it may not abandon a registration that has begun. And advanceBranchTo carries the same obligation for ANY future request-path caller.

UPDATE (PR #524, verified at merge commit 9db8c106): rule 2 (a refused push leaves nothing on the host) is still true of receive-pack, which is exactly why the host can hold objects nobody admitted only through a FETCH or a CLONE, never through a push: a fleet master with an origin fetches member tips it then refuses, and a member clone made before #524 copied every agent/* branch. For that reason the fleet repository's new-commit walk does not trust 'held' (kb/decisions/store/git-serve/receive-pack/new-commit-walk/75ab4d9f.md), and a fleet copy with an origin accepts no push (repos.Manager.FleetPushRefusal). Misreading: 'a refused push writes nothing, so held means judged' is false for fetched objects.
