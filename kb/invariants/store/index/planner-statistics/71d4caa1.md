# Index.Sync refreshes planner statistics when the pass's indexed-fact count reaches 1, 2, 4, 8, ... and, only when sqlite_stat1 content changed, bumps the schema cookie with a no-op DDL so EVERY pooled connection reloads them; Open repairs stale on-disk statistics with the same PRAGMA after the migrations (#731)

Rule: planner statistics must not lag the data while a batch lands, and a refresh must reach every pooled connection. Three parts, all in internal/engine/store:

1. CHECKPOINTS. Index.Sync calls statsCheckpoint after every indexed file; it runs `PRAGMA analysis_limit=1000; PRAGMA optimize=0x10002` (index.OptimizeStatsSQL) when the number of facts indexed in THIS pass is 1, 2, 4, 8, ... (a power of two), plus the existing end-of-pass call. The cadence comes from optimize's own rule (it re-analyzes a table only when its size drifted 10x or more against the statistics the connection holds); doubling is a schedule, not a corpus-size constant, so none is to be introduced. It runs outside any transaction (under _txlock=immediate an open tx is the process-wide write lock, and the optimize can wait up to busy_timeout behind another writer) and is best-effort: failure is logged, never fails Sync.

2. PROPAGATION. ANALYZE/optimize reload statistics on the ONE connection that ran them and do not change the schema cookie, so the other pooled connections (pool size 4) keep what they last loaded until the process restarts. refreshPlannerStats compares a digest of the sqlite_stat1 rows before and after the statement and, only when it changed, runs `CREATE TABLE IF NOT EXISTS planner_stats_epoch(x); DROP TABLE planner_stats_epoch`, a schema change that makes every connection reload at its next statement. It takes the write lock briefly and invalidates prepared statements, hence only on change (the always-empty indexed tables, e.g. restatement_throttle_state and the vec0 shadow tables, are re-ANALYZEd by every optimize but write no rows, so they do not trigger it). Rebuild's closing ANALYZE goes through the same helper.

3. OPEN. store.Open runs the same PRAGMA AFTER migrate.All. The old plain `PRAGMA optimize` before the migrations used no table on its connection and had no 0x10000 bit, so it only analyzed never-analyzed indexes and never repaired size drift. No schema bump there: every connection opened afterwards loads the repaired statistics from disk.

Why: the first Sync ANALYZEs a 1-row store, and creating sqlite_stat1 is DDL, so the one-row statistics reach all connections. A batch then plans every write with them: inner SCANs under the five vec0 KNN reads, `SCAN edges` in graphMergeEdge, graphNodeIDByProps driven by `label=?`. Measured on darwin/arm64 (stub embedder): 1 existing fact + 2000 in one BatchWriteFacts 9.0 s before, 4.7 s after. Windows and Linux were not measured.

What this does NOT mean: the plan flip threshold (stat rows of 1-2 give scans on SQLite 3.51) is SQLite's cost model, not knomit's; never encode it. Checkpoints at 1, 2, 4 and 8 facts legitimately leave scans on those tiny tables (optimize re-analyzes only at 10x drift), so the guard asserts SEARCH plans from the 16-fact checkpoint on. The CROSS JOINs of the vec0 reads stay: they still prevent the catastrophic whole-KNN-per-row plan.

Guards: TestVecKNN_StalePlannerStatsRefreshed holds EVERY pooled connection and requires SEARCH inner loops for the five reads plus graphMergeEdge/graphNodeIDByProps mid-pass (hook after a checkpoint) and after the batch; TestOpen_RepairsStaleOnDiskStatistics plants stale on-disk statistics and checks all connections after reopen. Sabotages seen to fail: no checkpoint refresh (mid-pass fails), no schema bump (mid-pass and after-batch fail on the connections that did not run the optimize), Open's optimize back before migrate.All as a plain PRAGMA (reopen fails).
