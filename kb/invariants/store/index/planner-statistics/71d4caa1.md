# Index.Sync refreshes planner statistics when the pass's indexed-fact count reaches 1, 2, 4, 8, ... and, only when sqlite_stat1 content changed, bumps the schema cookie with a no-op DDL so EVERY pooled connection reloads them; Open repairs stale on-disk statistics through the same helper after the migrations (#731)

Rule: planner statistics must not lag the data while a batch lands, and a refresh must reach every pooled connection. Four parts, all in internal/engine/store:

1. CHECKPOINTS. Index.Sync calls statsCheckpoint after every indexed file; it runs `PRAGMA analysis_limit=1000; PRAGMA optimize=0x10002` (index.OptimizeStatsSQL) when the number of facts indexed in THIS pass is 1, 2, 4, 8, ... (a power of two). The end-of-pass call still runs, except when a checkpoint already ran at exactly that count (a one-fact write would otherwise run two optimizes). The cadence comes from optimize's own rule (it re-analyzes a table only when its size drifted 10x or more against the statistics the connection holds); doubling is a schedule, not a corpus-size constant, so none is to be introduced. Each optimize is NOT free: it re-ANALYZEs the always-empty indexed tables (restatement_throttle_state, fact_titles_vec_*) and takes the write lock briefly.

2. PROPAGATION. ANALYZE/optimize reload statistics on the ONE connection that ran them and do not change the schema cookie, so the other pooled connections (pool size 4) keep what they last loaded until the process restarts. index.RefreshPlannerStats compares a digest of the sqlite_stat1 rows before and after the statement and, only when it changed, runs `CREATE TABLE IF NOT EXISTS planner_stats_epoch(x); DROP TABLE planner_stats_epoch`, a schema change that makes every connection reload at its next statement. It takes the write lock briefly and invalidates prepared statements, hence only on change (the always-empty tables write no rows, so they do not trigger it). Only a 'no such table' error on sqlite_stat1 counts as 'no statistics yet'; any other digest error skips the bump. Its statements run on db's own pooled connections, so it REFUSES a ctx that carries a transaction (does nothing, logs at debug): under _txlock=immediate the tx holds the process-wide write lock and the helper's own connection would wait on it (measured 10.6 s, then 'database is locked'; the invisible-tx trap of kb/invariants/store/transactions/212e7e44.md). Outside a tx it can still wait up to busy_timeout behind another writer; failures are best-effort (Sync logs at debug, Rebuild at warn).

3. OPEN. store.Open runs the same helper AFTER migrate.All, so it also bumps if more than one pooled connection is already open. The old plain `PRAGMA optimize` before the migrations used no table on its connection and had no 0x10000 bit, so it only analyzed never-analyzed indexes and never repaired size drift.

4. REBUILD. Rebuild's closing ANALYZE goes through the same helper. KNOWN GAP: Rebuild's phases 1-3 get no in-pass checkpoints; they plan with whatever statistics the connections hold when Rebuild starts. In practice Rebuild's own DDL moves the schema version (by 14 in a test), so every connection reloads from disk after its closing ANALYZE even without the bump: reverting to a bare ANALYZE does not fail any test, the bump there is belt and braces.

Why: the first Sync ANALYZEs a 1-row store, and creating sqlite_stat1 is DDL, so the one-row statistics reach all connections. A batch then plans with them: inner SCANs under the five vec0 KNN reads and, in graphMergeEdge, `SCAN edges` per merged edge. Measured on darwin/arm64 (stub embedder): 1 existing fact + 2000 in one BatchWriteFacts 9.0 s before, 4.7 s after. Windows and Linux were not measured. graphNodeIDByProps is a different case: it walks node_labels (a `SCAN nl` or every node of the label via idx_node_labels_label (label=?)) only when node_labels' statistics ALONE are stale (the RCA's slowest state, since mixed staleness is not safer than all stale); the natural one-fact stale state does not produce that plan.

What this does NOT mean: the plan flip threshold (stat rows of 1-2 give scans on SQLite 3.51) is SQLite's cost model, not knomit's; never encode it. Checkpoints at 1, 2, 4 and 8 facts legitimately leave scans on those tiny tables (optimize re-analyzes only at 10x drift), so the guard asserts SEARCH plans from the 16-fact checkpoint on. The CROSS JOINs of the vec0 reads stay: they still prevent the catastrophic whole-KNN-per-row plan.

Guards: TestVecKNN_StalePlannerStatsRefreshed holds EVERY pooled connection and requires SEARCH inner loops for the five reads and no SCAN edges in graphMergeEdge, mid-pass (hook after a checkpoint) and after the batch (its graphNodeIDByProps check does not fire in this natural state). TestGraphNodeIDByProps_NodeLabelsOnlyStale plants node_labels-only stale statistics, requires the node_labels walk on every connection, then requires one refresh to repair every connection. TestOpen_RepairsStaleOnDiskStatistics plants stale on-disk statistics and checks all connections after reopen. TestRebuild_AnalyzeReachesEveryPooledConnection guards Rebuild's ANALYZE. TestRefreshPlannerStats_RefusesAContextWithATransaction guards the tx refusal. Sabotages seen to fail: no checkpoint refresh (mid-pass), no schema bump (mid-pass, after-batch and the node_labels-only test), Open's optimize back before migrate.All as a plain PRAGMA (reopen), Rebuild's closing ANALYZE removed, the tx check removed. Bare ANALYZE in Rebuild passes (see part 4).
