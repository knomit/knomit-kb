# The ep filter (SearchOptions.EpisodeOps) is ONE SQL clause, episodeOpsClause, applied per path and BEFORE the LIMIT on RecentFacts and on both Search paths

ep selects a fact by the operation that wrote THIS PATH's current version: `COALESCE(cl.operation, '') IN (...)` over `LEFT JOIN commit_log cl ON bf.commit_hash = cl.commit_hash AND f.path = cl.path`. Since PR #715 (review M1, merged as 31a99271), every read builds it with episodeOpsClause (internal/engine/store/index/search_query.go) and applies it in SQL before its row limit:
- RecentFacts (count and list);
- Search's text-less path, before `LIMIT ?`;
- Search's vector path, in the metadata query, before the trim to `limit`.

BEFORE the fix, Search post-filtered the rows it had already limited (filterByEpisodeOps, now deleted), using a per-COMMIT `SELECT commit_hash, operation FROM commit_log ... GROUP BY commit_hash`. Consequence: on a mount with more than the per-mount depth (500), a filterless or text `ep=update` saw only the updates inside the window. TestLensQuery_EpSelectsBeforeTheWindow (REST and MCP) pins this with 501 newer learn facts.

The per-commit vs per-path difference was NOT reachable through the write API: commit_log.operation comes from the commit's author email (`<agent>+<op>@agents.knomit.io`, CommitSigs), so every path in one commit carries the same operation. A batch commit cannot learn A and update B.

Rule: a new read honouring ep calls episodeOpsClause in SQL before its LIMIT; never filter ep in Go after a limit.

WHAT THIS DOES NOT MEAN: on the vector path the KNN window (kLimit) still comes before every filter, ep included, exactly as for type or context. ep is exact only within that window, like the other filters.
