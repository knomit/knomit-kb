# Every index Sync/Rebuild on a branch must hold lockBranch; bare Sync is the in-lock primitive, out-of-band callers use SyncLocked, Rebuild self-locks

Load-bearing invariant: ALL search-index mutations for a branch (branch_facts / facts_vec / graph + the last-commit watermark) must run while holding `lockBranch(branch)` (the per-branch RWMutex in repoHandler.branchMu). Otherwise two mutators interleave: Rebuild clears the watermark (setLastCommit "") then re-indexes, and a concurrent Sync seeing the empty watermark launches its OWN full re-index → double facts_vec inserts / corrupt branch_facts. This is the PR #82 background-index race.

The contract, made uniform in `searchIndex` (internal/store/search_index.go):
- `Sync(ctx, branch)` is the LOCK-FREE primitive. Its ONLY legitimate caller is `repoHandler.notifyCommit` (internal/store/branch_commit.go), which is itself always called INSIDE lockBranch by every write path (writeFile/deleteFile/batchWrite in fact_write.go, MergeBranch, remote reconcile). Calling bare Sync out-of-band is a bug.
- `SyncLocked(ctx, branch)` = `defer lockBranch(branch)(); Sync(...)`. Out-of-band Sync callers MUST use this: the commit observer (repoBuilder.build's observe.New callback) and the startup heal's incremental path (healIndexBranches).
- `Rebuild(ctx, branch, progress)` self-acquires lockBranch for its whole duration. Its three callers are all out-of-band (startup heal stale path in healIndexBranches, the rebuild job handleStartRebuild, and the connect/commit reindex in handlers_origin_session) — none holds the branch lock first, so self-locking does not deadlock TODAY.

WHAT THIS DOES NOT MEAN (misreadings verified false at HEAD, 2026-07-22):

1. "Rebuild self-locks, so Rebuild/SyncLocked is safe to call from anywhere." FALSE — lockBranch is a bare sync.RWMutex Lock (internal/store/branch.go), NOT reentrant. It is safe only because no CURRENT caller already holds the lock. Adding a Rebuild or SyncLocked call from anywhere inside a write path — i.e. anywhere reachable from notifyCommit, writeFile/deleteFile/batchWrite, MergeBranch, or remote reconcile — SELF-DEADLOCKS the branch. Before adding a caller, prove it is out-of-band; if it is in-band, call bare Sync.

2. "Holding lockBranch during a long re-embed still lets reads proceed — reads don't take branchMu." FALSE. store.Verify takes `lockBranchRead(br)` on EVERY branch it checks and holds it for the whole run (internal/store/verify.go, in the branch loop). Consequence, both directions: a minutes-long Rebuild BLOCKS Verify on that branch, and a long Verify blocks every writer on all branches it covers. What is actually true is narrower: ordinary fact READS (query/explain/search) do not take branchMu, and other-branch / other-repo writers are unaffected. Compose this with kb/invariants/repos/verify-holds-read-lock/9b737b05.md — ri.Verify additionally pins the store generation for its whole call, so a Verify racing a Rebuild stalls both, it does not merely snapshot around it.

3. "notifyCommit calls Sync, so the index is always current after a write." FALSE when sync is suspended. `searchIndex.syncSuspended` (atomic.Bool) makes Sync an unconditional early-return no-op; store.Replay sets it when ReplayConfig.SkipIndexSync is set (internal/store/replay.go) and the caller OWNS the follow-up Rebuild. It is instance-scoped — only that Service's searchIndex is affected — and is meant for a TRANSIENT store (the origin clone). NEVER leave a live store suspended: its per-branch tables drift from the git tree and trip Verify's facts-coherence check.

Reentrancy safety: Sync/Rebuild never internally re-acquire lockBranch (EnsureBranch is pure DB), so the wrappers are deadlock-free for the existing callers. lockBranch is independent of the SQLite write lock, so same-branch writers block cleanly instead of hitting 'database is locked'.

Why it kept getting mis-fixed: PR #82 deferred the reconcile loop to activate() but left the commit observer wired live in build() calling BARE Sync, and its comments overclaimed 'the observer never races the initial index build'. The real fix is serialization via lockBranch (regression test: TestRebuild_SerializedWithConcurrentSyncLocked in rebuild_concurrency_test.go), not deferral.

LOCKBRANCH IS NOT CTX-AWARE (added for issue #411). lockBranch is a plain sync.RWMutex Lock (internal/store/branch.go): a goroutine parked on it cannot be released by cancelling its own context. To stop such a goroutine (e.g. a sync round parked behind the index heal), cancel the lock HOLDER — the index job — first; it returns at its next batch boundary and releases the lock. The lifecycle machine's exitStages cancels every affected life before draining any for exactly this reason (kb/invariants/repos/lifecycle/exit-cancels-all-then-drains). The out-of-band callers named above are now the Index stage's job (heal or full rebuild; internal/repos/stages.go) and the commit observer wired in Open.Enter; handleStartRebuild and the origin-session commit no longer call Rebuild directly — they send Rebuild / SwapStore events.
