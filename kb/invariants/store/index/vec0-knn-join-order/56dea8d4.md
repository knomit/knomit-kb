# Every vec0 KNN read joined to another table names its join order with CROSS JOIN, the vec0 table first, so the KNN is not re-run per row of another table; TestVecKNN_JoinOrderKeepsVec0Outer guards the exact SQL of all five reads (outer loop in every statistics state, inner SEARCHes only without stale statistics — #731)

Rule: a query that has `<vec0 table> MATCH ? AND k = ?` AND joins that vec0 table to any other table (facts, branch_facts, branches, ...) writes EVERY join in the chain as `CROSS JOIN`, with the vec0 table leftmost. SQLite treats CROSS JOIN as a fixed order (left table outer). The five reads that do this live as package consts so the guard can EXPLAIN the exact string the code runs: index.similarityKNNSQL (graphBuildSimilarityEdges AND rebuildGraph), index.searchByPathKNNSQL and index.searchKNNSQL (FactQuery.search), index.methodologyKNNSQL (RelevantMethodologyForFact), all in internal/engine/store/index/vec_knn_sql.go, and vocab.titleKNNSQL (TopTitleNeighbours).

Why: with plain JOINs the planner may put a real table outer and the vec0 virtual table inner. The inner vec0 scan is the WHOLE KNN (no rowid constraint is pushed into it), re-run once per outer row, so the read costs (outer rows) x one KNN. The gotcha under kb/gotchas/store/vec0/knn-join-order/ has the measured cost.

Consequences:
- A new vec0 KNN read that joins a table must use the same CROSS JOIN form, be a package const, and be added to index.VecKNNQueriesForTest (or a vocab seam) so TestVecKNN_JoinOrderKeepsVec0Outer covers it.
- ONE plain JOIN anywhere in the chain is enough to break it: with `tv CROSS JOIN f CROSS JOIN bf JOIN branches b` the planner moved branches to the front, outer of the vec0 table.
- The guard checks three planner-statistics states (none, fresh ANALYZE, stale one-fact statistics planted from the #725 store) because the plain-JOIN plan depends on the statistics; a guard that checked only a fresh store would pass on the old SQL for the similarity read. With no statistics and after ANALYZE it also requires every inner loop (the QueryByPath subquery's included) to be an index SEARCH or a vec0 rowid point read (printed `SCAN fv2 VIRTUAL TABLE INDEX n:2!…`); under the stale statistics it asserts only the outer loop.
- The guard also requires each filtered read (search by path, search by vector, methodology, title) to return fewer rows than its k, so its k window straddles rows the filter drops, and compares the pinned and plain-JOIN rows in ORDER BY order.

What this does NOT mean: the reads are not now O(k). CROSS JOIN fixes only the OUTER loop: vec0 runs once, but the inner lookups into facts, branch_facts and branches are still the planner's choice. Under stale planner statistics (one-fact sqlite_stat1 rows, what the first Sync's PRAGMA optimize leaves before a large batch lands) the pinned plans keep vec0 outer while the inner loops degrade to full covering-index SCANs (`SCAN f USING COVERING INDEX sqlite_autoindex_facts_1`, `SCAN bf`, the subquery's `SCAN bf2`), costing about k x (|facts| + |branch_facts|) row visits per read. The guard's three states assert SEARCH inner loops only for no statistics and ANALYZE; the stale state is SQLite's cost model (stat rows of 1-2 flip the plans on SQLite 3.51), which the SQL cannot pin. What keeps production out of it is kb/invariants/store/index/planner-statistics/71d4caa1.md (#731; the one place it does NOT reach is Rebuild's phases 1-3, which get no in-pass checkpoints): Sync refreshes statistics at 1, 2, 4, 8, ... facts indexed and bumps the schema cookie so every pooled connection reloads them. Measured on darwin (stub embedder, 8k facts, one connection): stale one-row statistics cost a vec0 read +25% (similarity) to +52% (search, search by path); methodology showed no cost in the fixture; title was not timed (empty vec table). That is far below #725's (facts rows) x one whole KNN (~4 ms each on Windows). Stale statistics cost the graph WRITE statements more than the five reads: in the natural one-fact stale state graphMergeEdge falls back to SCAN edges (graphNodeIDByProps drove off label=? or scanned node_labels only when node_labels' statistics ALONE were stale, per the RCA), taking a 2000-fact batch from ~5 s to ~9 s, of which the five reads' share was ~0.6 s. Where the stale statistics come from: the first Sync ANALYZEs a 1-row store and creating sqlite_stat1 is DDL, so the one-row statistics are broadcast to ALL pooled connections; later refreshes reach only the connection that ran them. The guard now plants and EXPLAINs on every pooled connection (it used to pass only by database/sql's most-recently-used connection reuse). Windows and Linux were not measured.

Nor does it change the KNN semantics. The order changes the plan only, and the guard asserts the rows equal those of the same SQL with plain JOINs. vec0 still applies its k window BEFORE the join and before every WHERE filter (gotcha fbb0d36d), so the k overfetch (knnK+1, titleKNNOverfetch, the methodology whole-table k) is still required. Nor is it a general rule to CROSS JOIN ordinary SQL: that is only right where the plan was measured wrong (as in 7274d077).
