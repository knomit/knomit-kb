# A store transaction travels out-of-band in ctx and every BeginTx is BEGIN IMMEDIATE, so nothing at a call site shows it is executing inside SQLite's process-wide write lock — any slow work reachable through a tx-bearing ctx silently serializes every writer, and slow inputs must be resolved before the tx opens

The transaction is carried invisibly in the context and every transaction takes the process-wide write lock for its whole lifetime, so a call site cannot tell whether it is inside the lock; any slow operation reached through a transaction-bearing context therefore blocks every writer on every branch and repo sharing the database, and the remedy is to resolve slow inputs before the transaction opens, using a read-only probe that mirrors the in-transaction decision while leaving that decision authoritative.

The two halves and their consequence:
- THE CARRIER. `ctxKeyTx` is one private context key shared by the git storer and the index (both on the same `*sql.DB`): `WithTx` stores, `TxFromContext` reads, `Conn(ctx, db)` returns the tx if present else the db (the read primitive everywhere a method takes ctx and does SQL), `BeginTxIfNeeded` returns `ownTx` so only the opener commits or rolls back, and `WithoutTx` strips a closed tx so it is never reused. A caller that opens a tx via `Index.BeginTx` makes git storer writes, index upserts and pipeline updates all participate in ONE commit; this replaced the storer's stateful SetTx/ClearTx and the anti-pattern is passing `*sql.Tx` as an explicit parameter.
- THE LOCK. The main store DB is opened with `_txlock=immediate`, so every `BeginTx` is `BEGIN IMMEDIATE` and holds SQLite's single writer lock until commit; write serialization is that plus `_busy_timeout` alone.
- THE CONSEQUENCE. Because the tx is invisible at the call site, ONNX inference (seconds) ended up inside a write tx twice: rebuild's embeddings phase (lock storms, connect frozen for minutes) and `upsert`. Both now embed OUTSIDE the tx. For upsert the embed had been placed after the in-tx COW check on purpose, so re-indexing already-indexed content paid no inference; hoisting it naively would trade lock contention for inference-on-every-reindex. `searchIndex.cowProbe` resolves that: a read-only pre-tx probe mirroring the in-tx COW condition answers only 'will an embedding be needed?'.

WHAT THIS DOES NOT MEAN: cowProbe is NOT the COW decision — it runs outside the lock and a concurrent writer can invalidate it; the authoritative check stays in-tx, and both wrong answers are safe (a false 'already indexed' costs one in-tx embed on the rare miss path, a false 'not indexed' costs a discarded vector). Do not delete the in-tx fallback: a raced probe would commit a VECTORLESS fact, violating the invariant that no fact is indexed without a vector when an embedder is configured. Caller-donated vectors (`WithPrecomputedEmbeddings`) stay on the in-tx path because applying one costs nothing. 'Rebuild holds no long SQLite lock' does not make Rebuild non-blocking: the per-branch lock is a different lock and is still held for the whole duration. Enforcing test: `TestUpsert_EmbedsOutsideWriteTransaction`, whose embedder attempts `BEGIN IMMEDIATE` on an independent connection and can only succeed if upsert is not holding the lock; it was verified to fail against the pre-fix ordering.
