# The local reconcile only ever FAST-FORWARDS the consensus branch and only ever SKIPS on doubt: diverged history is warn-and-skip, upstream == agent branch is a no-op, an unreadable origin row skips one tick and decides nothing — it never resets a branch and never exits the loop on an error

Rules for AdvanceLocalUpstream (internal/store/local_reconcile.go) and runLocalReconcileLoop (internal/repos/sync.go), PR #205:

1. Advance only when refs/heads/<upstream> is an ancestor of the agent tip (fast-forward). If it is not, log at warn and return ModeNoop. NEVER SetReference to a non-descendant. The recorded force-reset incident (kb/gotchas/repos/remote-sync/ed75e605) is the reason: reconcile acting destructively on a branch assignment cost data once.
2. upstream == agentBranch, or either empty, is a no-op — the degenerate config from that same incident.
3. (Rewritten for issue #411.) The loop is CHOSEN at Sync.Enter by the origin the store holds: an origin (or an unreadable origin status row) → runReconcileLoop, none → runLocalReconcileLoop. A loop ends ONLY on its ctx. An origin appearing or disappearing while a loop runs is a skipped tick, never an exit: the local loop skips its advance when it sees a definite origin or cannot read the row; the origin loop skips when the remote is missing or unreadable. Mutual exclusion is by the stage — one loop per Sync life — and an origin change is an AttachOrigin/DetachOrigin event that restarts Sync, which picks the other loop. (History: a first version exited the loop permanently on any error, so one SQLITE_BUSY silently stopped main from advancing; later versions exited on a definite origin and relied on a separate start path to launch the other loop, which a detach never did — both gone.)
4. Every advance goes through notifyCommit under the branch lock (single chokepoint). Nothing chains into Service.SetOnCommit — that single observer slot belongs to the SSE broadcast; polling is the whole trigger.
5. Errors in a tick are logged with the repo name and retried next tick; the loop ends only on ctx cancellation.

Misreadings: "never reset" is NOT "never move" — fast-forward is the normal case. "Skip on unreadable" is NOT "treat unreadable as no origin" — that would run this loop against a repo the origin loop also owns.

UPDATE (PR #533, squash commit 6f241959 on dev, verified there): on the FLEET repository AdvanceLocalUpstream can now ERROR with a judge refusal (*OwnCommitRefusedError): it runs judgeOwnRange over the commits it would fast-forward main onto and moves nothing when one is refused (kb/invariants/store/verify/own-range). This does not break rules 1 to 5: the loop still never exits on it and never resets a branch; the refusal is logged at WARN every tick and recorded as the fleet's last error (Manager.noteOwnJudge, through the loop's new `after` hook fleetMainAdvanced, cleared when main next moves), and the refused commit stays on the agent branch until an operator drops it (kb/architecture/fleet/drop-commit). MISREADING: 'a skipped advance is always doubt about the origin or history': on the fleet it can be a judged refusal that repeats until the commit is dropped. Any other repository's advance is still unjudged.
