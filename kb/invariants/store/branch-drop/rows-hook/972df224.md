# vcs.Repo.DropBranchLocked deletes a dropped branch's rows in the non-cascading review tables ONLY through the SetOnDropBranchRows hook, run after branch_facts and before the branches row, with the drop's own ctx and under the branch lock; a Repo with no hook refuses every drop before removing the ref

Since PR 10c of the internal/ hierarchy stack (PR #559, merged into dev as d73aad37; branch refactor/hier-10c-drop-hook), the git layer no longer names the review-time tables. DropBranchLocked (internal/store/internal/vcs/branch.go) runs, in order: (0) if no hook is registered, return vcs.ErrNoDropBranchRowsHook BEFORE anything is removed; (1) remove the git ref; (2) DELETE branch_facts for the branch; (2b) call the hook registered with Repo.SetOnDropBranchRows(func(ctx, branchID) error), passing DropBranchLocked's own ctx and the branch id, and return its error unchanged; (3) DELETE the branches row (cascading into branch_commits); then the branch cache entry goes and the post-drop onDrop hook (the index GC) runs. The store registers the hook in newRepoHandler (internal/store/vcs_seam.go), where the one vcs.Repo is built, as vocab.DropBranchReviewState(ctx, db, id) (internal/store/vocab/abstraction.go), which DELETEs restatement_pairs, restatement_cache_state, restatement_verdicts and restatement_throttle_state for that branch_id, in that order, through sqlite.Conn(ctx, db) (the ctx-carried transaction when there is one), and returns fmt.Errorf("drop %s: %w", table, err) at the first failure.

WHY IT IS LOAD-BEARING: those four tables reference branches(id) WITHOUT an ON DELETE CASCADE and foreign keys are enforced (_foreign_keys=1). If a dropped branch's rows survive step 2b, step 3 fails AFTER the ref is already gone, which is exactly the half-removed state the ref-first ordering exists to avoid. That is why an unset hook fails closed at step 0 instead of being skipped: the old code always deleted the rows, and skipping would turn a missing registration into a half-removed branch whenever the review pipeline had state for it.

EQUIVALENCE with the pre-10c code (where the same four DELETEs were a loop inside DropBranchLocked): same statements, same order, same *sql.DB (newRepoHandler passes the db it gives vcs.New), same ctx so the same transaction scope (sqlite.Conn: the ctx tx if present, else autocommit per statement), same position between branch_facts and branches, same branch write lock (DropBranch takes it, demotePeer holds it for DropBranchLocked), same error text. No commit is made, so NotifyCommit / onCommit ordering is not involved. Every PRODUCTION repoHandler, and so every production vcs.Repo, is built by newRepoHandler (internal/store/vcs_seam.go is the only non-test caller of vcs.New, and it calls SetOnDropBranchRows on the Repo it makes), so ErrNoDropBranchRowsHook (the fail-closed refusal when the drop hook is unset) is unreachable in production. It is reachable in tests only by building a Repo on purpose: TestAbstraction_DropBranchRefusesWithoutRowsHook clears the hook with SetOnDropBranchRows(nil). The one other hand-built literal in the tree, `&repoHandler{Repo: &vcs.Repo{}}` in internal/store/branch_test.go (TestLockBranch_DeferReleasesOnPanic), has no hook and no database, but it is lock-only and never drops a branch, so it never reaches step 0. MISREADING to avoid: 'every in-tree repoHandler is built by newRepoHandler' is false (that test literal exists); the claim is about production construction, and a new test that drops a branch must build its Service through store.Open / newRepoHandler (or call SetOnDropBranchRows), never a bare vcs.Repo{}.

ENFORCED BY: TestAbstraction_DropBranchClearsShortlistState (positive precondition: each of the four tables has rows for the doomed branch; after DropBranch, zero rows in each) and TestAbstraction_DropBranchRefusesWithoutRowsHook (hook set to nil: errors.Is ErrNoDropBranchRowsHook, ref and branches row intact), plus TestConformance_ReviewPipelineOnly, which no longer allowlists internal/vcs/branch.go. Sabotage on throwaway commits: not registering the hook fails the first test and the plain DropBranch tests; a hook that returns nil without deleting fails the first test (the branches delete trips the FK); treating a nil hook as a no-op fails the second; a restatement_pairs literal in vcs/branch.go fails the conformance scan.

CONSEQUENCE: a new table that references branches(id) without a cascade must have its per-branch delete added to the registered hook (or be given a cascade), never to vcs; a new constructor of vcs.Repo must call SetOnDropBranchRows or its drops will be refused. MISREADING: SetOnDrop is a different hook (it runs AFTER the branches row is gone, outside the drop's statements, for index GC); do not register row deletes there, they would run after the FK failure.
