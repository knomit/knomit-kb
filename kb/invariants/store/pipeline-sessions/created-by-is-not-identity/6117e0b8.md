# pipeline_sessions.created_by is a CORRELATION HANDLE, not an identity — never gate, authorize, or attribute blame on it

`pipeline_sessions.created_by` (knomit#123) records who opened a session, so an unexpected session is attributable inside the idle-reap window (`pipeline_idle_ttl`, default 60m). It is a CORRELATION HANDLE. It is not an identity, not an authentication result, and not evidence about who the caller was.

MEASURED, not assumed, against the real streamable-HTTP transport (`server.NewStreamableHTTPServer`, the construction `internal/web/server.go` uses):

- A `tools/call` carrying NO `Mcp-Session-Id` is rejected with "Invalid session ID" BEFORE dispatch — the handler never runs. So on the HTTP path the id is never absent (this is the server-side half of the client-side requirement recorded in `kb/gotchas/mcp/http-session-id-threading`).
- A FABRICATED session id that never ran `initialize` is ACCEPTED and reaches the handler, carrying only empty client info. Nothing verifies it.
- `clientInfo` (name/version) survives across calls only for a session that actually initialized against THIS process. It is an enrichment; the id is the key.

The MCP specification is explicit and MUST-strength on the rule this implies: a session id "is not evidence of who the caller is", and possession of a session/state handle MUST NOT be treated as authentication.

SHAPE OF THE VALUE. Honesty is carried in the value itself, not only in documentation, so a reader who never sees the schema comment still cannot mistake it:

    mcp-session:<id>
    mcp-session:<id> client:<name>/<version>

The scheme prefix makes the KIND of claim legible. Every component is caller-supplied, so each is stripped of control characters AND spaces and capped independently (`actorMaxLen`, a defensive resource bound on untrusted input — NOT a corpus property). Spaces are stripped specifically because a space separates the clauses: without that, a client naming itself `x client:someone-else` would forge a second clause.

WHERE IT IS BOUND. Read ONCE in `Pipeline.StartSession`, beside the branch binding and for the same reason (see `invariants/synthesize/session-branch-binding`): it describes the call that OPENED the session, and the MCP handler builds a fresh engine per continue call, so a later read would see a different request or none. It travels there on the context (`synthesize.WithActor`), composed at the request boundary by `internal/mcp/actor.go` — but stops at the engine boundary: the store takes `createdBy` as an explicit parameter, so nothing below `Pipeline` reaches into a context for it. It rides the INSERT, not a follow-up UPDATE like `Scoped`, because a crash between two writes would leave exactly the unattributable row the column exists to prevent.

WHAT THIS FACT DOES NOT MEAN:

- NOT that empty means "unknown". Empty means the opening call carried no handle — every in-process caller (tests, local tools driving `Reviewer` directly) is legitimately empty. There is deliberately no `unknown` sentinel, which would be indistinguishable from a real handle that happened to say so.
- NOT a licence to branch on it. As of #123 NO consumer reads `created_by` to make a decision; it is written and read back for forensics only. Adding a code path that gates, authorizes, rate-limits, or assigns blame on this value converts an unverified client claim into a control decision — the exact failure the MCP rule forbids. If a real identity is ever needed, derive it from a verified token, do not promote this column.
- NOT that `abandoned_session_created_by` (the displaced session's handle, on the review start envelope) is any stronger. It is the same handle read off the displaced row; the caveat travels with it.
- NOT that a value's presence proves the named client made the call. A fabricated id is accepted, so the handle is only as trustworthy as the network path it arrived on.
