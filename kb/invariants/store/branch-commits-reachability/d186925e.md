# Any first-parent ancestor of an on-branch commit is itself on-branch

branch_commits is populated by a full-reachability walk from the branch tip. Repo.PopulateCommitLog in internal/engine/store/internal/vcs/branch_commit_log.go walks with gogit.LogOrderDefault, which is go-git's preorder iterator and follows ALL parents, NOT only the first. Therefore a branch's set of indexed commits is closed under first-parent ancestry.

WHO RELIES ON IT (dev 56e8389c, since PR #698): vcs.LineEvents is the one implementation behind ResolveActiveCommitForPath, HistoryQuery.RevisionsBefore and FactQuery.FactLiveAtCommit.
- It finds a path's commit_log rows on the start commit's first-parent line through the commit_fp jump pointers.
- Its fallback is a bounded walk over commit_parents (LineWalkCTE, parent_order 0).
- For ResolveActiveCommitForPath and FactLiveAtCommit, NO branch filter is applied (`_ = branch`). The line test alone keeps the answer to the start commit's own first-parent line, and the commit_log JOIN keeps it to indexed commits. That is right for a start commit on the branch in question, because its whole first-parent line is on-branch by this invariant.

CONSEQUENCE: if branch_commits is ever populated by something OTHER than a full-reachability walk from the tip, such as a first-parent-only or partial walk, this invariant breaks. ResolveActiveCommitForPath and FactLiveAtCommit could then return commits that are not on the branch, silently.

WHAT THIS DOES NOT MEAN:
- NOT 'no consumer needs an explicit branch filter.' RevisionsBefore passes LineQuery.BranchID, and LineEvents then keeps only rows at commits in branch_commits for that branch: an EXISTS bound as a parameter, in both the jump candidates and the walk. Its anchorCommit may have been committed on a DIFFERENT branch, and there the line test plus the commit_log JOIN would let off-branch lineage through. The no-filter shortcut is specific to readers whose START commit is guaranteed on-branch.
- NOT 'the line test is branch-aware.' It is branch-agnostic. Scoping comes from WHICH commits were indexed, or from the explicit BranchID.

History: this was written for the first_parent_chain virtual table (retired in PR #67), then applied to the shared recursive CTE vcs.FirstParentChainCTE (… ORDER BY fpc.depth LIMIT n). PR #698 removed that CTE from production because it was O(history) per call (kb/gotchas/store/history/active-commit-resolver/d13c9055.md). It survives only as the oracle in internal/engine/store/first_parent_line_test.go.
