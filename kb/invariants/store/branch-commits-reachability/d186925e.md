# Any first-parent ancestor of an on-branch commit is itself on-branch

branch_commits is populated by a full-reachability walk from the branch tip (populateCommitLog uses gogit.LogOrderDefault, which resolves to go-git's preorder iterator and follows ALL parents — NOT first-parent). Therefore the set of indexed commits in commit_log for a branch is closed under first-parent ancestry.

resolveActiveCommitForPath and FactLiveAtCommit walk the parent DAG via a recursive CTE over commit_parents (parent_order = 0) and rely on the commit_log JOIN ALONE to restrict results to indexed (on-branch) commits — no per-step branch_commits membership check. This is safe ONLY because the anchor commit they start from is itself on the branch in question, so its whole first-parent line is on-branch too.

CONSEQUENCE: if branch_commits is ever populated by something OTHER than a full-reachability walk from the tip (e.g. a first-parent-only or partial walk), this invariant breaks and those two resolvers silently return wrong commits.

WHAT THIS DOES NOT MEAN:
- NOT 'the commit_log JOIN always suffices, so every consumer can drop the explicit branch filter.' FALSE — RevisionsBefore DOES add `JOIN branch_commits bc ... WHERE bc.branch_id = ?` (internal/store/revisions_before.go:58), because its anchorCommit may have been committed on a DIFFERENT branch; there the commit_log JOIN is not enough to keep off-branch lineage out. The 'no membership check' shortcut is specific to resolvers whose START commit is guaranteed on-branch.
- NOT 'the walk itself is branch-aware.' The CTE is branch-agnostic (`_ = branch` in resolveActiveCommitForPath); scoping is a property of WHICH commits got indexed, not of the walk.

Historical note: originally written for the first_parent_chain virtual table (retired in PR #67). The CTE replacement (firstParentChainCTE, revisions_before.go) has the same dependency on this invariant.
