# Three-way merge with tree identical to dst MUST be reported as noop, never as merge

Inside mergeIntoBranch, after the three-way merge produces mergedTreeHash, if mergedTreeHash == dstCommit.TreeHash the result is reported as Mode=ModeNoop (NOT 'merge') and NO merge commit is synthesized: it returns AgentReconcileResult{Mode: ModeNoop, NewTip: dstHash} WITHOUT calling SetEncodedObject / SetReference / notifyCommit (internal/store/branch_merge.go). This preserves the commit-log parity invariant: zero-diff merge commits never enter history. It is what makes the squash-merge case fast-forward correctly — when the remote squashes agent's commits, the re-merge yields a tree identical to dst and is suppressed.

CONSEQUENCE FOR CALLERS: NewTip on a noop is dstHash UNCHANGED, so a caller must not treat a noop as advancing the branch, and must not expect a commit hash it can log or push.

WHAT THIS DOES NOT MEAN (corrected 2026-07-22 — the previous wording of this section was itself wrong): ModeNoop does NOT fire only on the merged-tree-equality check. mergeIntoBranch has THREE ModeNoop return sites, and code that switches on Mode must handle all of them identically:
  1. `srcHash == dstHash` — the refs already point at the same commit.
  2. `isSrcAncestor` — src is already an ancestor of dst, so dst is ahead; nothing to merge.
  3. `mergedTreeHash == dstCommit.TreeHash` — the three-way merge produced a tree identical to dst (the squash case above).
Reading ModeNoop as "the three-way merge ran and produced no diff" is wrong for sites 1 and 2, where NO merge was attempted at all. If you need to distinguish 'nothing to do' from 'merged to nothing', you cannot get it from Mode — the distinction is not exposed. What IS true is that all three are dst-unchanged and none of them mints a commit or calls notifyCommit; the real-merge path below site 3 writes the commit, moves the dst ref, and runs populateCommitLog + notifyCommit.
