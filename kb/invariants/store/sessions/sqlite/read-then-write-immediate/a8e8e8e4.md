# On the session DB, any transaction that READS and then WRITES must be BEGIN IMMEDIATE on a dedicated connection — the DSN has _busy_timeout but no _txlock=immediate, so db.BeginTx there is DEFERRED and its first write after a concurrent commit fails 'database is locked' instantly

Rule: the ephemeral session DB (internal/engine/store/sessions, opened by sessions.Open with the stock sqlite3 driver and DSN _journal_mode=WAL&_busy_timeout=5000, NO _txlock=immediate) gives db.BeginTx a DEFERRED transaction. A deferred transaction that reads first and writes later, while another connection commits in between, fails its first write with SQLITE_BUSY / SQLITE_BUSY_SNAPSHOT immediately; the busy timeout only helps a transaction that has not yet read. Every session-DB transaction of the shape read-then-write must therefore take a dedicated *sql.Conn, run BEGIN IMMEDIATE, and COMMIT (ROLLBACK under context.WithoutCancel on failure). Today that is createPipelineSession and ToolIndex.DequeuePaths.

CONSEQUENCE: a new session-DB method that SELECTs and then INSERTs/UPDATEs/DELETEs in one transaction must copy that pattern, and should be covered by a concurrent test (several goroutines, distinct sessions — the DB file is shared, so distinct sessions contend). Write-only transactions (AddSeenPaths, EnqueuePaths) are safe as deferred: their first statement takes the write lock and the busy timeout waits for it.

WHAT THIS DOES NOT MEAN: the sessions.Open comment "no need for _txlock=immediate" is about the main store's vec-extension constraints, not a statement that deferred transactions are safe under concurrency; and the main store's serialization rule (kb/invariants/store/sqlite/write-serialization/9caa7895.md, _txlock=immediate in the DSN) does NOT cover the session DB, which is a separate file with its own DSN. Do not 'fix' this by adding a retry loop around BUSY: an immediate lock makes the loser wait and then read fresh state, which a retry of the same deferred shape does not guarantee.
