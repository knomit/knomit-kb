# Under merges, 'which version of a path was active at commit C' is a first-parent-ancestry question: every resolver walks first-parent over an index closed under that ancestry, and committed_at is read only to DISPLAY the date of a commit already chosen — never to choose it

Under merges, the question 'which version of a path was active at commit C' is answered only by first-parent ancestry from C, because a sibling-branch commit that touched the path with a LATER wall-clock time and was then merged in would win any timestamp ordering while the merge itself kept the local side; so every resolver walks first-parent over an index whose commit set is closed under first-parent ancestry, and the timestamp is read only to display the date of the commit already chosen.

The chain that makes this hold, from population to display:
- POPULATION follows every parent, never short-circuits. `CommitLogSync` walks the DAG the iterator yields and on a dedup hit SKIPS AND CONTINUES; short-circuiting on a known commit is safe only for linear history and would leave the other parent line of a merge unindexed. Making a visited-but-skipped commit cheaper (dedup before the lazy payload) is allowed; shortening the walk is not.
- CLOSURE is what the resolvers rely on. Because `branch_commits` is populated by full reachability from the tip, any first-parent ancestor of an on-branch commit is on-branch, so `resolveActiveCommitForPath` and `FactLiveAtCommit` can walk the `commit_parents` CTE (parent_order = 0) with the `commit_log` JOIN alone and no per-step membership check — safe ONLY because their anchor is guaranteed on-branch. `RevisionsBefore` DOES add the `branch_commits` join because its anchor may have been committed on another branch. If branch_commits were ever populated by a partial or first-parent-only walk, both resolvers would silently return wrong commits.
- RESOLUTION walks first-parent, stepping OVER deletions as write events rather than stopping at them: `resolveActiveCommitForPath` (shared by searchIndex and factIndex, on repoHandler), `resolveTargetCommit` for DERIVED_FROM target commits, and the fact read's fallback-before path, which previously used go-git's committer-time file log and 404'd after any retraction. History navigation reads the index, not a live go-git walk.
- DISPLAY reads committed_at of the chosen commit. The fact panel's date is the fact VERSION's commit date via `RevisionsBefore(limit=1)`, not the anchor's (in live mode the anchor is the branch tip and its date means 'when the repo last changed'). The index `commit_log_path_time (path, committed_at DESC)` makes the naive ORDER BY query the easiest to write and exactly wrong.

WHAT THIS DOES NOT MEAN: the walk itself is NOT branch-aware — scoping is a property of which commits got indexed. 'The commit_log JOIN suffices' does NOT let every consumer drop the explicit branch filter. rebuildGraph's outer ordering by MIN(committed_at) is a write-order convenience and does not affect correctness, because each ref is resolved independently by first-parent walk. Look for an existing primitive before adding a walker here — three overlapping first-parent walkers already exist — and verify any guard by replacing the whole query with the naive commit_log⋈branch_commits form, not by tweaking the sort: an ORDER BY mutation alone leaves the CTE intact and only discriminates via a same-second tie-break.
