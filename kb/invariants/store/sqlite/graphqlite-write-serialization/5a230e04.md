# Cross-branch GraphQLite writes are serialized by _txlock=immediate, which REQUIRES a pre-warmed pinned pool

GraphQLite (the Cypher-over-SQLite extension) provides NO internal write serialization and never retries on SQLITE_BUSY: its cypher() UDF issues writes (DELETE FROM edges / MERGE node) mid-SELECT on the CALLING connection (sqlite3_context_db_handle, not a separate connection), and on BUSY/LOCKED it strips the error code and returns the opaque "Failed to execute MATCH for DELETE" / "Failed to create node in MERGE". Confirmed unchanged from v0.3.10 through v0.6.0 by reading the C source AND a 2400-txn stress repro that failed ~70% WITHOUT serialization on BOTH versions (so upgrading GraphQLite does NOT fix concurrency; v0.4.1+ only adds structured JSON error codes + per-query transform context, not BUSY handling). NOTE: direct-SQL writes to GraphQLite's EAV tables (graphInsertEdgeReturningID, graphSetEdgeProps in graphAddDerivedFromAtCommitTx) DO honor _busy_timeout via mattn's busy handler — only cypher() is unsafe.

The graph is ONE store shared across ALL branches, so the per-branch lock (branchMu) does NOT stop two commits on different branches from racing it (surfaced as a flaky TestConcurrency_SeparateBranchesAreIsolated on linux CI). Writers are serialized at the STORAGE layer via `_txlock=immediate` in the DSN (file DBs only): every database/sql transaction does BEGIN IMMEDIATE, taking the write lock up front so the cypher() writes later in the same tx never contend; the loser blocks on _busy_timeout (5000ms, bounded). This is a DB-level lock with built-in expiry — there is deliberately NO application-level mutex (an earlier indexWriteMu attempt was rejected: an app lock has no expiry and risks the cross-lock deadlocks knomit hit before).

LOAD-BEARING: _txlock=immediate REQUIRES a pre-warmed, pinned pool (service.go Open: SetMaxIdleConns == SetMaxOpenConns == 4, SetConnMaxLifetime(0) + SetConnMaxIdleTime(0), then warmPool() force-opens all 4 connections up front). Reason: a LAZILY-opened connection runs the ConnectHook, which loads the GraphQLite extension — itself a WRITE to its EAV schema. Under immediate, if that lazy open happens while the SAME goroutine already holds the write lock, the new connection's extension init blocks on that held lock -> SELF-DEADLOCK (was a 600s CI hang). Pre-warming guarantees no connection is ever initialized while a write lock is held. COROLLARY: under immediate, never hold a write tx AND issue a bare-pool (conn(ctx,db) without the tx) query in the same goroutine — that needs a second connection and can starve the 4-conn pool against BEGIN IMMEDIATE waiters. rebuildGraph's phase-A.5 commit_log read was moved onto its own tx connection (tx.QueryContext) for exactly this reason.

READ SIDE (separate failure, fixed by RETRY not serialization): concurrent cypher() READS race too. GraphQLite builds its Cypher->SQL translation through a process-shared alias namespace (_gql_default_alias_N); two cypher() reads translating at once on different pooled connections collide and emit malformed SQL — surfaced as `SQL prepare failed: no such column: _gql_default_alias_1.id` (raw <=0.3.10, or wrapped in structured JSON {"code":"EXECUTION_ERROR"} >=0.4.1). Non-deterministic (~0.1% under heavy concurrency; reproduced 94/66000 reads at 60-way); PERSISTS through v0.6.0. Writes avoid it only because _txlock=immediate already serializes them. Reads must NOT be "fixed" by wrapping them in a tx: that takes the write lock, starves the 4-conn pool against BEGIN IMMEDIATE waiters, and makes reads block on the background clustering writer (empirically: timeouts + `database is locked` under load). Instead reads are made resilient by withCypherRetry/isTransientCypherError (internal/store/cypher_retry.go): re-run the whole query+scan up to 5x with jittered sub-ms backoff while it returns a transient error. No Go lock, no write lock, full read concurrency preserved. Applied at HEAD to the live cypher-read sites: IncomingAtCommit, OutgoingAtCommit (internal/store/search_graph_query.go), SubgraphEdges (internal/store/subgraph_edges.go), and SimilarityAdjacency (internal/store/similarity_graph.go) — each closure must be idempotent (re-scans from scratch / uses max-score map updates). WHAT THIS DOES NOT MEAN: the older retry-site names graphExpandSearch and the cypher-based ClusterFacts/louvain() reads cited in this fact's history have been REMOVED from internal/store — do NOT search for them as live retry sites; scoped clustering now reads a bounded subgraph via SubgraphEdges and runs Louvain IN-MEMORY (internal/synthesize/louvain.go), so cluster-compute contention no longer originates from a cypher ClusterFacts call. isTransientCypherError matches TWO signatures (same root cause — no internal serialization/retry for concurrent cypher()): (1) the `_gql_default_alias` translation race above; (2) `abort due to ROLLBACK` — GraphQLite aborts the in-flight statement rather than blocking when a concurrent cypher writer/reader contends the connection. Signature (2) was added in PR #79 (commit 8f06e02) after it slipped through unretried and flaked a contended CI run.

VERSION PIN: GraphQLite is pinned at 0.6.0 in tools/fetchlibs/spec.go (graphqliteVersion) — the Makefile delegates library fetching there; there is no longer a GRAPHQLITE_VERSION variable in the Makefile. Bumped from 0.3.10 for structured error codes; the bump alone does NOT fix either the write or read concurrency issue.

ANTI-PATTERNS: (a) reverting to deferred BEGIN (default db.BeginTx with empty TxOptions) re-exposes the cross-branch write race; (b) MaxIdleConns < MaxOpenConns, or a non-zero ConnMaxLifetime/IdleTime, lets the pool churn/re-init connections and re-introduces the self-deadlock; (c) skipping warmPool; (d) upgrading GraphQLite expecting a concurrency fix; (e) wrapping cypher READS in a transaction to fix the _gql_default_alias or ROLLBACK race — it serializes reads behind the write lock and starves the pool; use withCypherRetry instead. (:memory: is pinned to a single connection and skips all of this.) Regression tests: storytests TestConcurrency_BarrierSeparateBranches (F3b) and TestConcurrency_SeparateBranchesAreIsolated (F3); store TestWithCypherRetry / TestIsTransientCypherError cover the read-retry logic (incl. the ROLLBACK signature).
