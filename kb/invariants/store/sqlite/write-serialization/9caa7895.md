# Store write serialization is _txlock=immediate + _busy_timeout alone; the pinned pool is now a performance choice, NOT a deadlock guard

For FILE databases store.Open builds the DSN `?_journal_mode=WAL&_busy_timeout=5000&_foreign_keys=1&_txlock=immediate` (internal/store/service.go). Every database/sql transaction therefore issues BEGIN IMMEDIATE and takes SQLite's single write lock up front, so concurrent writers serialize cleanly at the storage layer instead of failing mid-statement partway through a read-then-write transaction; the loser blocks on _busy_timeout (5000ms, bounded). SQLite is single-writer regardless — _txlock=immediate only decides WHERE a loser blocks. There is deliberately NO application-level write mutex.

The pool is pinned: SetMaxOpenConns(4) == SetMaxIdleConns(4), SetConnMaxLifetime(0), SetConnMaxIdleTime(0). The `:memory:` fallback is pinned to a single connection (a bare :memory: DB is per-connection, so pooled connections would each be a separate empty database) and skips the file-DB serialization machinery entirely.

WHAT THIS DOES NOT MEAN:
- **The pinned pool is NOT a correctness requirement and there is no pre-warming.** `warmPool()` no longer exists. Historically the pool had to be eagerly force-opened because the ConnectHook loaded the GraphQLite extension, which WROTE to its EAV schema on init — under _txlock=immediate a lazy connection open while the same goroutine held the write lock self-deadlocked (a 600s CI hang). With GraphQLite removed (PR #28) the ConnectHook only calls registerSQLFuncs (knomit_parse_fact, knomit_cosine_sim, knomit_canon_domain) and sets per-connection pragmas — neither writes to the database — so a lazy open can no longer block on a held write lock. Pinning survives only to keep connections warm.
- **MaxIdleConns < MaxOpenConns is no longer a deadlock hazard.** The anti-pattern that made pool churn dangerous was the writing ConnectHook, which is gone. Churn is now merely wasteful.
- **It does not make it safe to hold a write tx while doing slow work.** Because BEGIN IMMEDIATE holds a process-wide write lock for the transaction's whole lifetime, ONNX inference must still never run inside a write transaction — see kb/invariants/store/embed-outside-write-tx/8fe00fe9.md.
