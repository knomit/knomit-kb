# Every in-process fact writer validates at the SOURCE: validateWrite runs in both store write cores (writeFileExact, batchWriteLocked) under the branch lock before any object is written, on each fact whose content differs from the blob at head, against the ontology at the branch tip; REST answers 422, and byte-identical copies (Replay under WithCarriedOver), deletes, unchanged content and branches with no or an unparseable ontology are exempt

RULE (PR #533, squash commit 6f241959 on dev, verified there; ruling: kb/decisions/fact/validation/enforced-everywhere/338656ce.md). store.repoHandler.validateWrite(head, files, deletes) (internal/store/fact_write_validate.go) is called from writeFileExact (WriteFact, WriteFactIfUnchanged, writeFile) and batchWriteLocked (BatchWriteFacts, BatchWriteFactsMustExist). Every in-process writer commits through those two cores: REST create and update, the review pipeline (prune update and merge, distill, reflect, dedup, discovery), fleet code (writeRecord, artifacts), trigger scripts and MCP (which already validated; now twice). A path is judged when it is a fact (isFactPathUnder the fact root) AND is not deleted in the same batch AND its content differs from the blob at head; it is parsed and fact.ValidateFact runs on its topic path (derived as knomit_update derives it: the directory under the fact root). Refusal: *FactInvalidError (errors.Is ErrFactInvalid), wrapping the ontology's own ValidationError or context-gate error, so the message is the rule's. Nothing is written.

REST. writeStoreError maps FactInvalidError to 422 'Fact fails the ontology's validations' carrying the rule's message (documented in openapi for createFact and updateFact; kb/conventions/web/store-error-to-http/5547f4b8.md).

EXEMPT, each deliberately: (1) content byte-identical to the blob at head (a rewrite is not a change); (2) deletes; (3) a branch with NO ontology at its tip (a repository being created) and a branch whose ontology does NOT PARSE (kb/gotchas/store/verify/unparseable-ontology: such a repository is made unwritable where it is opened, so the writers need no second gate, while the entry paths refuse everything); (4) InitRepo's seed commits, merges and rebases (pushed-branch merges keep the result guard; replays only replay commits already validated); (5) a COPY: store.WithCarriedOver(ctx) makes the two cores skip validateWrite, and only Replay (connecting a repository to a remote with disjoint history) sets it, and only when resolveDeadRefs left the content byte-identical. Content a copy ALTERS is judged like any write (TestValidateWrite_AReplayThatAltersALegacyInvalidFactJudgesIt). The context key is unexported; no REST, MCP or review path can set it.

CONSEQUENCES. (1) Editing a legacy fact that fails a rule must bring it into compliance in the same write; a legacy invalid fact is otherwise untouched (kb/gotchas/fact/validation/legacy-invalid-facts). (2) A copy must not be judged: without WithCarriedOver a connect aborted halfway on the first legacy invalid fact, leaving the target holding only part of the facts (TestValidateWrite_ACopyOfALegacyInvalidFactIsCarriedOver); any new bulk copy writer needs the same treatment and a byte-identical check. (3) For test authors: every store write now runs the context gate, so a test ontology that writes context keys must declare them (cmOntology and triggerOntology had to); and an invalid commit for a judge test is made with TestingCommitFiles, which bypasses the store (and skips notifyCommit).

MISREADINGS. 'Every fact in the repo is valid': false, untouched legacy facts stay as they are. 'carried over means skip validation for any bulk write': no, byte-identical copies only. 'The review pipeline can still write a rule-violating fact': no longer; its prune merge of a non-designer principle and its confidence update of a legacy invalid principle are refused as warns, the legacy file unchanged and the merge members kept (internal/synthesize/validation_test.go).
