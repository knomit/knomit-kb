# Custom SQLite vtable cursors MUST NOT re-enter *sql.DB from their Next/Filter/Column callbacks

Anti-pattern with hard evidence: a custom SQLite virtual-table cursor whose Next/Filter/Column callback issues a query against the same *sql.DB the vtable is being scanned on WILL deadlock under concurrency.

MECHANICS: the vtable callback runs from inside a query that's already holding one connection from the pool. The callback's inner db.QueryRow/Query asks the pool for a NEW connection — it does not (and cannot easily) piggy-back on the connection that's executing the parent scan. With SetMaxOpenConns(N) and N concurrent vtable scans, every connection is held by an outer scan and every scan is waiting for an (N+1)th connection. Permanent pool exhaustion; ctx cancellation does not help because Storer.EncodedObject and similar use the non-context Query variants.

DIAGNOSIS SIGNATURE: a goroutine dump where many goroutines are blocked at `database/sql.(*DB).conn` on the same *sql.DB pointer, with cgo callback frames from mattn/go-sqlite3 (goVNext / _cgoexp_*) on the stack above the inner QueryRow.

WHAT TO DO INSTEAD: pre-materialize the data the cursor needs into a regular SQL table (e.g. `commit_parents` holds parent edges) and walk it from pure SQL — typically a recursive CTE. If you genuinely cannot pre-materialize, you must use the cursor's bound *sqlite3.SQLiteConn directly (raw conn, not via database/sql) and accept the maintenance cost.

STATUS AT HEAD: **knomit registers NO custom virtual tables.** The `first_parent_chain` vtab that motivated this rule was retired and replaced by a `WITH RECURSIVE fpc(...)` CTE over `commit_parents` (internal/engine/store/internal/vcs/revisions_before.go; `blast_radius.go` uses the same shape). The `sqlite3_knomit` driver's ConnectHook registers scalar UDFs only, no vtab module.

WHAT THIS DOES NOT MEAN:
- Do NOT go looking for `first_parent_chain` as live code, and do NOT cite it as an example of a vtab in this codebase — it no longer exists.
- The rule is NOT obsolete just because its original instance is gone. It is preventative and fires for ANY future vtable someone adds. Treat it as load-bearing.
