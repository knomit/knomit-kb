# Store write concurrency is three ORTHOGONAL mechanisms for three hazards — branch RWMutex through notifyCommit (torn git-vs-SQL state), CAS on the last_commit watermark (duplicate sync work), _txlock=immediate (cross-branch write serialization) — routed through two chokepoints that every mutation must use

Each concurrency hazard in the store has exactly one mechanism sized to it, the mechanisms are orthogonal rather than layered, and every guarantee they give is routed through a chokepoint that a mutation bypasses at the cost of the guarantee; a reader who attributes one hazard to another mechanism, or who takes a shortcut around a chokepoint, reintroduces the exact failure the mechanism exists to prevent.

The three hazards and their mechanisms:
- TORN STATE between git and SQL, visible to readers. The per-branch `sync.RWMutex` in `repoHandler.branchMu` (`lockBranch` / `lockBranchRead`) is held for the FULL mutation, from ref resolution through `SetReference` AND `notifyCommit`'s index sync; writers take Lock, `Verify` takes RLock. Releasing it between the git write and the SQL update lets a concurrent Verify observe HEAD advanced while `branch_facts` / `facts_vec` / graph lag. This mutex still exists — an earlier reading that it was removed was wrong.
- DUPLICATE WORK from concurrent Sync ticks. Compare-and-swap on the `last_commit` watermark in `meta` (`UPDATE meta SET value=? WHERE key=? AND value=?`); losers see zero rows and discard their work, which is safe because facts are upserted via COW dedup and are idempotent. Sync deliberately does NOT wrap many files in one giant transaction — that would hold the write lock too long.
- CROSS-BRANCH WRITE SERIALIZATION at the storage layer. `_txlock=immediate` in the file-DB DSN makes every transaction `BEGIN IMMEDIATE`; other writers block via `_busy_timeout`. This was ASPIRATIONAL until a specific fix — the implementation had used DEFERRED BEGIN, so cross-branch writers were not serialized and concurrent graph writes failed on CI. Write serialization is that DSN setting plus busy timeout alone; the pinned pool is a performance choice, not a deadlock guard.

The two chokepoints:
- `repoHandler.notifyCommit(ctx, branch, hash)` MUST be called by every mutation that advances a branch ref, while still holding the branch write lock: it appends the commit_log and branch_commits rows, runs `im.Sync` for the branch, then fires the external `onCommit` observer. Callers: writeFile / deleteFile / batchWrite, `mergeIntoBranch` (FF and 3-way), `reconcileAgentMerge`, `replayOntoUpstream`. Advancing a ref via `storer.SetReference` without it leaves SQL stale relative to git and trips Verify's coherence check.
- `Storer.CheckAndSetReference(new, old)` is the CAS primitive at the ref layer: the refs table is one name-keyed table shared across branches, tags and HEAD, and `SetReference` is `INSERT OR REPLACE`, so any path that must detect concurrent ref movement (push, sync merge-result writes) must use CheckAndSetReference and handle `storage.ErrReferenceHasChanged`.

WHAT THIS DOES NOT MEAN: the three mechanisms are NOT substitutes — branchMu does not serialize cross-branch writes, the CAS watermark does not protect torn state, and `_txlock=immediate` does not dedup sync ticks. 'Per-branch Sync mutex removed' refers only to watermark dedup no longer using a mutex; the branch lock for torn-state protection was never removed. `_txlock=immediate` also makes every open transaction a process-wide write lock, which is why slow work must not run inside one (kb/invariants/store/embed-outside-write-tx/8fe00fe9.md).
