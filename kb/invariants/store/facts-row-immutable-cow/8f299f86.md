# facts rows are IMMUTABLE; content-addressed by (path, blob_hash); branches hold junction pointers

facts rows are IMMUTABLE once created — content-addressed by UNIQUE(path, blob_hash) (internal/store/migrate/repo/000001_schema.up.sql); PATH IS PART OF THE IDENTITY. Same content at same path — regardless of which branch or commit — ALWAYS resolves to the same row. Branches hold lightweight junction pointers in branch_facts(branch_id, path, fact_id, commit_hash) with UNIQUE(branch_id, path). Two branches sharing the same content at the same path point to the SAME facts row. COW semantics: when one branch modifies a fact, a new row is created with a different blob_hash; the old row stays for branches still referencing it. Merge between branches copies junction POINTERS, not fact data. Drop branch deletes junction rows then GCs orphaned facts (those with no branch_facts referrers).

LOAD-BEARING CONSEQUENCES: (a) Graph nodes for a fact version are immutable — once built, never updated. Upsert SKIPS current-state graph sync (graphSyncFactTx: TAGGED / IN_DOMAIN / UNDER / SIMILAR_TO edges) on COW hits. EXCEPTION — this does NOT extend to lineage edges: time-aware [:DERIVED_FROM] ref-event edges ARE still written POST-COMMIT on COW hits. searchIndex.writePostCommitDerivedFrom is called from BOTH arms of upsert — once inside the COW-hit block just after the branch_facts pointer update, once at the tail of the COW-miss path (both in internal/store/search_crud.go), and a THIRD time from the Sync path in internal/store/search_index.go for intra-batch refs (see internal/store/derived_from.go). GREP the call sites, do not trust line numbers: they have now drifted 123/258 → 244/364 → 243/365 across three audits of this fact — treat any line number in this fact as expired on arrival. Each new commit asserting the same content is its own ref-event, so 'COW hit skips graph sync' does NOT mean 're-asserting a fact at a new commit adds no lineage edge.' See kb/invariants/store/refs-to-derived-from-edges/eb438c74.md. (b) Embeddings are immutable PER ROW and skipped only on COW HITS — a COW hit requires the SAME (path, blob_hash) pair. facts_vec is keyed by facts.rowid, NOT by blob_hash; there is no by-content vector lookup. The skip is implemented as a pre-transaction read-only cowProbe (inference is hoisted OUT of the write tx — see kb/invariants/store/embed-outside-write-tx/8fe00fe9.md); when that probe races a concurrent writer the COW-miss path embeds in-tx rather than proceeding vectorless. (c) SIMILAR_TO edges are stable; only NEW fact versions trigger edge computation. (d) Syncing a branch that shares most content with an already-indexed branch is nearly free.

WHAT THIS DOES NOT MEAN (documented misreadings):

1. "content-addressed" does NOT make vectors reusable by content alone. A pure MOVE/RENAME (same blob, NEW path) is a COW MISS: it mints a NEW facts row with a NEW rowid, and the moved fact IS RE-EMBEDDED — rebuildEmbeddings (internal/store/search_index.go) embeds every rowid missing from facts_vec, and the upsert COW-miss path (internal/store/search_crud.go) runs fresh ONNX inference; the only vector reuse is a context-donated embedding within the same write. In the 2026-07-03 taskB2 A/B benchmark, 8/8 knomit-assisted runs compressed this fact to "embeddings keyed by content, so moves re-embed nothing" — FALSE at HEAD, flagged as a major conformance violation in 7/8 answers.

2. "COW hit means the write did nothing" is FALSE. A COW hit still writes the branch_facts junction pointer for this branch/commit AND still writes DERIVED_FROM ref-event edges (see consequence (a)). Do not treat a COW hit as a skippable no-op write.

3. "rows are immutable, so rebuild re-embeds everything" is FALSE in the other direction: rebuild deliberately PRESERVES facts.rowid so that facts_vec rows survive, and re-embeds only genuinely new or changed (path, blob_hash) pairs. The mechanism is specific: the rebuild upsert updates IN PLACE rather than INSERT OR REPLACE, because REPLACE is DELETE+INSERT — which would mint a new rowid and fire facts_after_delete, wiping the vector on every rebuild (see the comment above the rebuild INSERT in internal/store/search_index.go).

Anti-pattern: do not UPDATE a facts row in place; insert a new row and update the branch_facts pointer.
