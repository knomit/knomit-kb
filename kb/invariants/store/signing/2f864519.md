# Store.SetSigner is a pre-serve configuration call: vcs.Repo.signer is an atomic.Pointer so a concurrent read is memory-safe, but swapping the key on a live store still changes which key later commits use

Every production caller of SetSigner (internal/corpus/repos lifecycle.go template, clone and init paths; stages.go openStage; edge/web handlers_origin_session.go fresh clone db) calls it right after store.Open, on a store nobody else can see yet: the dispatcher and the consensus merger start only in serveStage.Enter, later. So SetSigner is documented as a PRE-SERVE call.

vcs.Repo.signer is an atomic.Pointer[ssh.Signer] (same shape as testFallback in sign.go), so CommitSigner reading it from the trigger dispatcher goroutine (SignerFingerprint in triggers phaseA) is memory-safe. The precondition still stands: swapping the key on a LIVE store changes which key later commits are signed with, so it is not a supported production operation.

Test consequence: a test that swaps the key on a live repo must settle the dispatcher before AND after the peer write (writeAsPeer in internal/corpus/repos testhelpers). The dispatcher is kicked ONLY by agent-branch advances (ri.onCommit); a commit on main or another branch kicks the CONSENSUS MERGER instead, which can sign merge commits when consensus is enabled, and settle does NOT cover the merger. Those tests do not enable consensus, so the second settle is mostly a guard.

WHAT THIS DOES NOT MEAN: it is not a claim that main commits wake the trigger dispatcher (an earlier draft and the PR body said so; the review corrected it), and the atomic does not make a live swap a supported operation.
