# MergeConsensus no-ops a peer tip whose new commits are ALL merge commits and whose merge changes nothing in the host's tree — without it a peer whose sync always writes a merge commit (git merge --no-ff) ping-pongs with the host forever

MergePushed (F11 UI merge) ALWAYS records a host-signed merge commit and no-ops only when the peer tip is already in dst. Under consensus: auto that converges for a knomit peer, because knomit's own reconcile fast-forwards to the host's merge commit (or writes a merge only when it has new content, and a tree-identical merge is a Noop there), and a tip already in the host's branch is a no-op. It does NOT converge for a peer whose sync always writes a merge commit: each host merge commit is merged back by the peer with a new merge commit, which the host records again — one commit per round, forever (T-B4c, measured red without the rule).

Rule (store.MergeConsensus, mergeOpts.skipMergeOnly, under the dst lock): after the three-way merge, if the merged tree equals dst's tree AND src brings at least one commit dst lacks AND every such commit has two or more parents → ModeNoop, nothing written. A peer's AUTHORED (single-parent) commit is always recorded even when its content is already in the host (M3 behaviour kept). A merge-only tip that DOES change the tree (an edited merge) is recorded.

The 'at least one new commit' clause is load-bearing for testing: without it the rule is vacuously true for a tip already in dst and masks the store's reachable-tip no-op (branch_merge.go isSrcAncestor), so the reviewer's X7b sabotage ('isSrcAncestor && !o.record') went green in T-B4b. With it, X7b turns T-B4a and T-B4b red and dropping skipMergeOnly turns T-B4c red: each rule is pinned by its own test.

Consequence: a --no-ff peer's merge commits are never recorded on the host, so its pushed branch keeps a non-zero to_merge in the Pushed branches list until it authors something. MergePushed (the UI path) is unchanged: a human's merge still always records.
