# The agent loop ends a turn when the model makes the same failing tool call (same tool, byte-identical arguments, same error text) RepeatFailureLimit (3) times in a row; the rest of that reply's calls are answered as skipped so every tool_use stays paired and the turn is flushed

Loop.runCalls feeds each EXECUTED call's outcome to repeatGuard.observe; a success, a different tool, different argument bytes or a different error text resets the streak. At the limit the remaining calls of that assistant reply get SkippedResult and the turn ends with a turnError wrapping ErrRepeatedFailure, the same shape as ErrTooManyCalls, so Loop.settle flushes the turn (an assistant entry remains) and results stay paired (turn-drop invariant). The limit 3 is a policy, not a measurement: one failure is information, a second is a fair retry after reading the error, a third identical failure shows the model is not acting on the error. Motivation: a 4B Ollama model retried one failing knomit_learn about 20 times in PR 763 live acceptance; grants made the retries silent. The sentence shown is RepeatedFailureMessage_DRAFT (copy awaiting user approval).

Does NOT mean: declined calls count (they neither count nor reset), nor calls refused for invalid JSON arguments (not observed by the guard), nor that a failure with varying error text is stopped; the per-turn MaxCalls (500) still bounds those.
