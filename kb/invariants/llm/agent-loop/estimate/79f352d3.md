# For an adaptive loop the estimate of the next request is the last reported tokens plus a SIGNED byte difference of the whole sent view since that response, because an eviction makes the view smaller; a static loop keeps the old added-entries expression

Static rule (unchanged): estimate = max(snapshot bytes/4, lastTokens + bytes/4 of the entries added since lastCount). It assumes the request only grows. Adaptive rule (Loop.Window != nil): estimate = max(projected snapshot bytes/4, lastTokens + (viewBytes(now) - lastBytes)/4), where lastBytes is the byte size of the whole sent view recorded where lastCount is set (after the assistant entry is added). The difference is negative after an eviction, positive after a load or new entries, so one rule covers every cause and a reported prompt count that is too high after a shrink no longer causes a wrong ErrContextFull. lastBytes is part of the baseline settle restores when a turn is dropped (pinned by TestLoop_DroppedTurnRestoresLastBytes: a response that set lastBytes, then a dropped turn, then an exact next estimate; restoring only lastTokens/lastCount fails it, because the delta would then lose the dropped assistant entry's bytes and under-estimate).

Consequence: when the view can change by anything other than appended entries (an eviction now, stubbing of ended turns later), do not reuse the added-entries expression. With only entries added the two rules are equal (asserted).

The rule is an estimate: bytes/4 against real tokens, and the loader's room check (roomLeft) uses it before the results of the current batch are recorded.
