# The llm.Builder hook order IS the cache order: 1 tools, 2 system, 3 repo instructions, 4 frame, 5 working set, 6 conversation, 7 turn — and hooks 1-3 must hold no machine-, session- or time-specific bytes

internal/engine/llm/builder.go defines seven fixed hooks; their numeric order is the render order and therefore the provider cache order (everything before a hook boundary is a cacheable prefix): 1 tools (MCP tools/list as the chat principal sees it), 2 system (mcp.ChatSystemPrompt), 3 repo (the MCP initialize instructions; for the unscoped endpoint ProfileInstructions("code", root, nil) + unboundAddendum), 4 frame (AddFrame returns ErrFrameNotImplemented this milestone; generic Add still accepts HookFrame items), 5 working set, 6 conversation (neutral history), 7 turn.

SCOPE OF SHARING: hook 1 is shared per PERMISSION SET (a principal without Write is not shown the six write tools), hooks 2 and 3 are identical for every principal and every fleet member. mcp.AddPrefix writes the items tool:<name>, "system" and "instructions".

CONSEQUENCE: anything specific to a machine, a session or "now" (hostname, agent branch, binding handle, session id, absolute path, username, today's date) must go into hook 6 (a tool result or a session-context note), never into hooks 1-3. A byte found in tools/list or the instructions that varies per machine must be fixed in the MCP server, where external agents see the same text, never filtered only on the chat path.

Ordering rules inside hooks: tools are sorted by name at Snapshot time (never registration order); other hooks keep insertion order; Replace keeps position and refuses a hook change (moving an item between hooks changes which cached prefix it belongs to, so it is Remove + Add). Hook 6 items can be neither Replaced nor Removed (ErrHistoryAppendOnly; see the append-only invariant).

WHAT THIS DOES NOT MEAN: hook 1 is NOT fleet-wide across permission sets (user decision 2026-11-04, option (a)); a writer's and a reader's hook 1 legitimately differ. And hook 3 is fleet-wide only for the UNSCOPED endpoint kind: a scoped connection's instructions carry that repo's ontology and differ per repo.
