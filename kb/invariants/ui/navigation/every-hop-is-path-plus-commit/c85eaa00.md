# EVERY fact navigation is addressed by (path, commit) — no UI path may read a target at HEAD to decide where to send you, and "the target still exists" is never a reason to drop the pin

Following a reference in the UI opens the target AT THE COMMIT THE REFERENCE RECORDS — the DERIVED_FROM edge's `target_commit`, the version the referrer reasoned over. Unconditionally. Not "unless we are live", not "unless the target still exists", not "unless the target has moved on".

This is the UI's half of kb/principles/philosophy/historical-not-current. That principle is not advisory here: it is the reason the graph is worth storing. A synthesis that cited four observations must keep citing the versions it cited, or "why is this true?" stops being reproducible.

CONCRETELY, IN CODE:
- `hopEdge(path, pinnedCommit)` dispatches `asOf: {mode:'history', commit: pinnedCommit}` and is SYNCHRONOUS. It performs no read. There is nothing to look up: the edge already carries the answer.
- The ONLY non-pinned case is `pinnedCommit === ''` — an edge with no recorded target_commit. Nothing can be addressed, so live is the only reachable answer. This is a degenerate data case, NOT a liveness policy, and must never be widened.
- Retraction needs no branch. Pinning to the edge's commit is what makes a retracted target readable, through the commit-anchored read's `?fallback=before`.
- `groupRefs` must not re-order OUTGOING entries by recency; `versions[0]` is the pinned commit and a newest-first sort silently substitutes the target's later version.

WHAT THIS BANS, BY NAME:
- Reading the target at the HEAD endpoint to classify a hop. If code needs a network round-trip to decide WHERE to navigate, it is already wrong.
- Returning `{mode:'live'}` from any ref-following path on the grounds that the target resolved at HEAD.
- "The target is unchanged, so live and pinned are the same" — they are the same until they are not, and the case where they differ is the only one that matters.

HISTORY, because this recurred: `resolveHopAnchor` (added 2026-06-19, 3e5e5e7b "computes edge-hop liveness from target HEAD state") read the target at HEAD while live and, on 200, returned live — discarding the pin. A fact citing A@5902160 opened A@8f23800 once A was revised. It survived two years of edits and a full connections-panel rewrite because a DECISION fact (kb/decisions/ui/temporal/history-exit-and-live-hops, now RETRACTED) recorded "a live ref-hop stays live unless the target is retracted" as intentional. The wrong rule sat in the corpus beside the principle it violated, so recall handed every session a written justification for the wrong side. That is the failure mode this invariant exists to close.

WHAT THIS DOES NOT MEAN:
- Not "the UI can never be live". Browsing the library, opening a fact from the list, and returnToNow are all live. This governs FOLLOWING A REFERENCE — edge rows, in-body refs, provenance — where a commit is recorded and must be used.
- Not "pinned means stale". If the recorded commit is the target's current tip, the reader sees the current version. That is incidental, not a decision any code makes.
- Not confined to the connections panel. It binds in-body ref hops (refCommits), edge rows, `openFileAt`, breadcrumb crumbs, and anything added later that follows a recorded reference.
- Not satisfied by "we pass the commit somewhere". The commit must reach `asOf`; passing it and then overriding the anchor is the exact bug.
