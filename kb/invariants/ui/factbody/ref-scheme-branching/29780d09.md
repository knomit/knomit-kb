# FactBody renders refs from the SERVER-supplied kind, never a client-side scheme regex

FactBody's References section renders each ref by switching on `kind`, which the server computes and sends as part of the fact's refs array (`[{raw, kind, _links}]`, built by internal/web/ref_view.go BuildRefViews). The client never inspects the ref string to decide what it is.

The five kinds and their rendering:

1. `url` — an `<a href target="_blank" rel="noopener noreferrer">` for http(s) ONLY. `file:///` and any other scheme are classified `url` but render inert, because the browser cannot open them.
2. `fact` — a fact in this repo, present at the anchor being viewed. Clickable span calling `onRefClick`, which feeds the commit-anchored hop. Passed the REPO-RELATIVE path (`refTarget` strips a `kb://<id12>/` prefix), because that is what resolveHopAnchor and the fact URL builder both address.
3. `broken` — a fact in this repo, absent at the anchor. Inert, marked `(unresolved)`.
4. `foreign` — a fact in ANOTHER knomit repo. Inert, marked `(another repo)`. NOT an error: it is simply not ours to open.
5. `source_code` — a `src://` citation. Inert, marked `(source)`.

WHY THE CLIENT CANNOT DECIDE THIS. The rule this replaced was a pure syntax test in FactBody (`schemeless ⇒ clickable`), and syntax cannot answer the two questions that matter. It cannot know whether the target EXISTS — so a typo'd path rendered as a live link to nothing — and it cannot tell a cross-repo ref from a typo. `fact` vs `broken` additionally encodes existence AT THE VIEWED COMMIT, which only the server can determine (its resolver holds the anchor); computing it client-side, or at HEAD, would mark a valid historical ref broken as soon as its target was retracted.

The information was already on the wire and being thrown away: web/src/api.ts flattened `[{raw, kind, _links}]` down to bare strings before FactBody ever saw it.

ANTI-PATTERN (unchanged, and the new rule satisfies it more strictly): never fall back to "if not http(s), treat it as an onRefClick target". That original bug fed `src://knomit/internal/...` into api.fact() as though it were a fact path. Do not reintroduce a client-side scheme regex as a "fallback" — the only permitted fallback is for a server too old to send `kind`, and it must not guess at resolution.

REGRESSION COVERAGE lives in web/src/FactBody.test.tsx: `src://` and `file:///` render as `<span>` (not `<a>`, no href, onRefClick never called on click); a `foreign` ref reads "another repo" and NOT "unresolved"; a `broken` ref is not clickable; and a canonical `kb://<own-id>/x.md` ref hops with the relative path `kb/x.md`.

WHAT THIS DOES NOT MEAN:
- Kinds are NOT a pure function of the ref string. `fact` and `broken` differ only by an anchor-dependent existence check, so the same ref can legitimately be `fact` at one commit and `broken` at another. Never cache a kind across anchors.
- `foreign` is not a degraded `broken`. Do not style it as an error or add a repair prompt.
- `url` does not mean openable. Check for http(s) before rendering an anchor.
- This does not license the client to classify refs for any OTHER purpose either — fact.ClassifyRef in internal/fact is the single authority, and a guard test (TestRefClassification_HasNoSecondImplementation) fails the build on a second implementation.
