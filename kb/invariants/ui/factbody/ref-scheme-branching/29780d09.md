# FactBody renders refs from the SERVER-supplied kind, never a client-side scheme regex

FactBody's References section renders each ref by switching on `kind`, which the server computes and sends as part of the fact's refs array (`[{raw, kind, path, _links}]`, built by internal/edge/web/api/kb/ref_view.go buildRefViews, unexported since 12f). The client never inspects the ref string to decide what it is.

The six kinds (the list in internal/edge/web/api/kb/ref_view.go; re-read at dev ee850fd6) and their rendering:

1. `url` — an `<a href target="_blank" rel="noopener noreferrer">` for http(s) ONLY. `file:///` and any other scheme are classified `url` but render inert, because the browser cannot open them.
2. `fact` — a fact in this repo, present at the anchor being viewed. Clickable span calling `onRefClick`, which feeds the commit-anchored hop. Passed the REPO-RELATIVE path (`refTarget` prefers the server's `path`), because that is what resolveHopAnchor and the fact URL builder both address.
3. `broken` — a fact in this repo, absent at the anchor. Inert, marked `(unresolved)`.
4. `foreign` — a fact in ANOTHER knomit repo. Inert, marked `(another repo)`.
5. `source_code` — a `src://` citation. Not a link, and NO LONGER marked `(source)`: the scheme is visible in the label already. It renders as a SourceRefRow, which adds a button that copies the git command to retrieve the cited blob; that button is the only action on it.
6. `system_file` — a `.knomit/<path>` file (this repo's or another repo's, from fact.RefLocalSystemFile / RefForeignSystemFile); not a fact, so the server sends no target link, only the exact repo-relative `path`. FactBody has no case for it: it falls through the `default` branch and renders as an inert `→ raw` span. A new kind must be added to FactBody's switch (and to REF_KIND_LABEL if it wants a marker); the server's `url` bucket also absorbs `malformed`, so there is no seventh kind for it.

WHY THE CLIENT CANNOT DECIDE KIND. The rule this replaced was a pure syntax test in FactBody (`schemeless ⇒ clickable`), and syntax cannot answer the two questions that matter. It cannot know whether the target EXISTS — so a typo'd path rendered as a live link to nothing — and it cannot tell a cross-repo ref from a typo. `fact` vs `broken` additionally encodes existence AT THE VIEWED COMMIT, which only the server can determine (its resolver holds the anchor); computing it client-side, or at HEAD, would mark a valid historical ref broken as soon as its target was retracted.

WHAT THIS RULE COVERS, AND WHAT IT DOES NOT: CLASSIFICATION vs FORMATTING. This invariant governs decisions about what a ref IS and what may be DONE with it — kind, existence, clickability, hop target. It does NOT reach the cosmetic label. FactBody's `refLabel` does apply a regex to `raw` to abbreviate hashes and swap a known repo id for a name, and that is permitted because of a specific asymmetry: it runs only INSIDE an already-decided `source_code` / `foreign` case, never to choose one, and falls back to `raw` verbatim on no-match. Its worst failure is an ugly string. A client-side regex that fed onRefClick, a kind, or a resolution would still be forbidden — that is the ANTI-PATTERN below, and it is unchanged.

This distinction was drawn the hard way. The shortening was first built server-side (fact.Ref.Display → RefView.Display, a RepoNamer threaded through BuildRefViews / BuildFactView and five handler constructors) on the reading that ANY decomposition of a ref belongs to ClassifyRef. It was reverted: a cosmetic change should not need a server rebuild to appear, and its repo-name lookup could never fire in production (see the src-id-vs-kb-id gotcha). Over-applying this invariant has a cost too.

ANTI-PATTERN (unchanged): never fall back to "if not http(s), treat it as an onRefClick target". That original bug fed `src://knomit/internal/...` into api.fact() as though it were a fact path. Do not reintroduce a client-side scheme regex as a "fallback" for KIND — the only permitted fallback is for a server too old to send `kind`, and it must not guess at resolution.

REGRESSION COVERAGE lives in web/src/FactBody.test.tsx: `src://` and `file:///` render as `<span>` (not `<a>`, no href, onRefClick never called on click); a `foreign` ref reads "another repo" and NOT "unresolved"; a `broken` ref is not clickable; a canonical `kb://<own-id>/x.md` ref hops with the relative path `kb/x.md`; and a `reference labels` block pins the label behaviour separately — hashes abbreviated with raw in the title, a src:// repo id left alone, a kb:// id named only when mounted, a line range preserved, a legacy form untouched, and an unparseable ref falling back to raw.

WHAT THIS DOES NOT MEAN:
- Kinds are NOT a pure function of the ref string. `fact` and `broken` differ only by an anchor-dependent existence check, so the same ref can legitimately be `fact` at one commit and `broken` at another. Never cache a kind across anchors.
- `foreign` is not a degraded `broken`. Do not style it as an error or add a repair prompt.
- `url` does not mean openable. Check for http(s) before rendering an anchor.
- Dropping `(source)` does not mean source refs became clickable. They stay inert; only the redundant marker went.
- This does not license the client to classify refs for any OTHER purpose — fact.ClassifyRef in internal/domain/fact is the single authority, and a guard test (TestRefClassification_HasNoSecondImplementation) fails the build on a second implementation in Go. It cannot see into TypeScript, which is exactly why the rule is written down here.
- It also does not forbid the client TOUCHING a ref string at all. Formatting a label is not classifying. See the covers/does-not-cover section above before citing this fact to block a UI change.
