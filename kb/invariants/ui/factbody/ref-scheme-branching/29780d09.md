# FactBody renders refs from the SERVER-supplied kind, never a client-side scheme regex

FactBody's References section renders each ref by switching on `kind`, which the server computes and sends as part of the fact's refs array (`[{raw, kind, path, display, _links}]`, built by internal/web/ref_view.go BuildRefViews). The client never inspects the ref string to decide what it is, and never takes one apart.

The five kinds and their rendering:

1. `url` — an `<a href target="_blank" rel="noopener noreferrer">` for http(s) ONLY. `file:///` and any other scheme are classified `url` but render inert, because the browser cannot open them.
2. `fact` — a fact in this repo, present at the anchor being viewed. Clickable span calling `onRefClick`, which feeds the commit-anchored hop. Passed the REPO-RELATIVE path (`refTarget` prefers the server's `path`), because that is what resolveHopAnchor and the fact URL builder both address.
3. `broken` — a fact in this repo, absent at the anchor. Inert, marked `(unresolved)`.
4. `foreign` — a fact in ANOTHER knomit repo. Inert, marked `(another repo)`.
5. `source_code` — a `src://` citation. Inert, and NO LONGER marked `(source)`: the scheme is visible in the label already.

DISPLAY IS THE SECOND SERVER-COMPUTED FIELD, AND FOR THE SAME REASON AS KIND. A raw citation like `src://7b4887ce51d9/internal/refs/refs.go@<40-hex>:<40-hex>` is ~110 monospace columns of mostly-hex. `RefView.Display` carries a compact label — `src://core/internal/refs/refs.go@8cba88ff…:c451fd99…` — produced by fact.Ref.Display from the SAME ClassifyRef parse that produced Kind. The client renders `r.display || r.raw` (FactBody's `refLabel`) and does no splitting of its own, because splitting a ref into repo / path / commit / blob IS parsing.

Display is set for `source_code` and `foreign` — the two kinds whose raw form is dominated by a 12-hex repo id. Two transformations: the repo id becomes the repo's NAME when the server's mount table can resolve it (BuildRefViews takes a RepoNamer, production repos.Manager.NameByID), and src:// commit and blob abbreviate to fact.DisplayHashLen (8) plus an ellipsis. An id no repo claims STAYS AN ID; a nil RepoNamer means no id resolves. Empty Display means "render raw", the correct answer for `url`, `fact` and `broken`.

WHATEVER RENDERS DISPLAY MUST KEEP RAW REACHABLE. FactBody puts the full raw citation in the element's `title`. The stored ref keeps full 40-hex commit and blob (see gitHashLen in internal/fact/ref.go: an abbreviated stored hash is unverifiable by anyone who does not already have the repo, which is precisely the reader a citation serves). Abbreviation is only safe because it is a label over an intact address.

WHY THE CLIENT CANNOT DECIDE KIND. The rule this replaced was a pure syntax test in FactBody (`schemeless ⇒ clickable`), and syntax cannot answer the two questions that matter. It cannot know whether the target EXISTS — so a typo'd path rendered as a live link to nothing — and it cannot tell a cross-repo ref from a typo. `fact` vs `broken` additionally encodes existence AT THE VIEWED COMMIT, which only the server can determine (its resolver holds the anchor); computing it client-side, or at HEAD, would mark a valid historical ref broken as soon as its target was retracted.

ANTI-PATTERN (unchanged, and now covering Display too): never fall back to "if not http(s), treat it as an onRefClick target", and never re-derive the short form from `raw` in the browser. The only permitted fallback is for a server too old to send `kind`/`display`, and it must not guess at resolution — an absent `display` falls back to `raw` verbatim, never to a client-side shortening.

REGRESSION COVERAGE lives in web/src/FactBody.test.tsx: `src://` and `file:///` render as `<span>` (not `<a>`, no href, onRefClick never called on click); a `foreign` ref reads "another repo" and NOT "unresolved"; a `broken` ref is not clickable; a canonical `kb://<own-id>/x.md` ref hops with the relative path `kb/x.md`; a `display` label renders verbatim with `raw` in the title and the full hashes absent from the visible text; and a ref with no `display` falls back to `raw`. Server-side: internal/fact/ref_test.go TestRefDisplay + TestRefDisplay_EmptyForKindsWithNothingToShorten, internal/web/ref_view_test.go TestBuildRefViews_Display*.

WHAT THIS DOES NOT MEAN:
- Kinds are NOT a pure function of the ref string. `fact` and `broken` differ only by an anchor-dependent existence check, so the same ref can legitimately be `fact` at one commit and `broken` at another. Never cache a kind across anchors.
- Display is NOT anchor-dependent, but it IS mount-dependent: the same ref renders `src://core/…` on an instance that mounts that repo and `src://722927862513/…` on one that does not. Do not treat Display as stable across instances, and never store it.
- `foreign` is not a degraded `broken`. Do not style it as an error or add a repair prompt.
- `url` does not mean openable. Check for http(s) before rendering an anchor.
- Dropping `(source)` does not mean source refs became clickable. They stay inert; only the redundant marker went.
- This does not license the client to classify OR parse refs for any other purpose — fact.ClassifyRef in internal/fact is the single authority, and a guard test (TestRefClassification_HasNoSecondImplementation) fails the build on a second implementation in Go. It cannot see into TypeScript, which is exactly why the rule is written down here.
