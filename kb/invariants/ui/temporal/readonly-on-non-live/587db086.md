# !isLive(state) disables fact authoring CLIENT-side via isReadOnly = serverReadOnly || repoReadOnly || !branchWritable || !isLive — a BROWSE-context gate that never reaches the Manage panel (which gates on serverReadOnly alone)

When `state.asOf.mode != 'live'`, fact authoring in the browse surface is disabled with tooltip 'Read-only — anchor is not live' (READ_ONLY_TITLE in web/src/state.ts, NO trailing period; readOnlyTitle names a subscription or unauthorable branch first when those apply). Enforcing selector: `isReadOnly(s) = s.serverReadOnly || s.repoReadOnly || !s.branchWritable || !isLive(s)` (state.ts). Its only non-test consumer is RightPanel (`factReadOnly`: retract button, FactEditor, the edit path).

TWO-FLAG MODEL (#324): isReadOnly describes the BROWSED repo/branch/anchor, so it must never gate anything that is not about the browsed content. The Manage panel (RepoManager, ManageOverview) takes a REQUIRED `serverReadOnly` prop instead and gates every control on it — create repo/lens, CreateBlocked, the Logs and Authorizations tabs, archived restore/purge, lens edits, and every repo settings control. A repo's own read-only-ness in Manage is the DISPLAYED repo's mode === 'subscribe', read by RepoDetail from that repo's details: it locks content (description, licence) and the origin reconnect/disconnect the server refuses, and leaves rename, archive, rebuild and upstream open. See kb/decisions/web/manage/readonly-two-flags/38d99ea3.md.

RULE (forward-looking): any keyboard shortcut added later that triggers a FACT mutation MUST check `isReadOnly` in the same handler path that disables the equivalent button. A Manage mutation checks serverReadOnly instead.

WHAT THIS DOES NOT MEAN:
1. `isLive` and `isReadOnly` are NOT equivalent. serverReadOnly (demo mode), repoReadOnly (browsed repo is a subscription) and !branchWritable (browsed branch is not authorable) each make a LIVE anchor read-only. Do NOT treat 'live' as a synonym for 'writable'.
2. "isReadOnly is the app's one read-only flag, so pass it to any mutating surface." FALSE — that is exactly #324: passing it to RepoManager made a subscription landing repo disable instance-wide creation and hide the server log, and locked OTHER repos' settings pages. Instance-scoped or other-entity surfaces take serverReadOnly.
3. The non-live (!isLive) gate is CLIENT-ONLY. Write handlers always resolve at HEAD (handlers_fact_create.go / handlers_fact_write.go); a crafted POST while anchored off-live is still accepted. Do not rely on it as a security boundary. The subscription/branch terms DO have a server twin: refuseUnwritableBranch (readonly.go) 403s fact writes, with the store's read-only flag as backstop.
4. Server-side instance rejection exists only for serverReadOnly: readOnlyGate (readonly.go) 403s every POST/PUT/PATCH/DELETE except the anchored MCP dispatch routes (gated by MCP tool filtering instead).
5. "Keyboard shortcuts live in RightPanel, so auditing RightPanel discharges the forward-looking rule." FALSE — audit every `keydown`/`onKeyDown` site: App.tsx (global '/', Escape, Backspace/Delete → NAV_BACK, 'h' → returnToNow), Library.tsx (list navigation; gates itself on !isLive for navigation-correctness), RightPanel.tsx (ConfirmModal Escape/Enter — Enter confirms a retract, safe only because the modal is reachable solely through the gated retract button), plus component-local handlers in FilterBar/FacetPanel/RepoManager/OverflowCrumb. All navigation-only at last check.

`mode:'diff'` also folds into `!isLive` and is read-only.
