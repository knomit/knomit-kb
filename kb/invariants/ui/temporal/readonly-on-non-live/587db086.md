# !isLive(state) disables mutating actions CLIENT-side; isReadOnly = serverReadOnly || !isLive

When `state.asOf.mode != 'live'`, every mutating action in the UI is disabled with tooltip 'Read-only — anchor is not live' (READ_ONLY_TITLE in web/src/state.ts, NO trailing period): fact CRUD (POST/PUT/DELETE /facts), synthesis-runs, index-rebuilds, origin PUT/DELETE, and origin-session apply/commit. Origin and jobs flows are gated for the same reason fact CRUD is — they all write to repo state. Enforcing selector: `isReadOnly(s) = s.serverReadOnly || !isLive(s)` (state.ts); components read `isReadOnly(state)` (RightPanel retract + FactEditor, RepoManager rebuild/archive, RemoteStatus origin).

RULE (forward-looking): any keyboard shortcut added later that triggers a mutation MUST check `isReadOnly` in the same handler path that disables the equivalent button. Re-verified at HEAD (2026-08-07): still no mutating keyboard shortcut exists.

WHAT THIS DOES NOT MEAN:
1. `isLive` and `isReadOnly` are NOT equivalent anymore. isReadOnly = serverReadOnly || !isLive (state.ts). serverReadOnly is a distinct instance-level 'read-only demo mode' dimension: a LIVE anchor on a demo instance is still read-only. Do NOT treat 'live' as a synonym for 'writable'.
2. The non-live (!isLive) gate is CLIENT-ONLY. The server does NOT reject a mutation because the client is anchored off-live — write handlers always resolve at HEAD (handlers_fact_create.go / handlers_fact_write.go: 'Resolver anchored at HEAD (commit:"")'). Button gating is the ONLY enforcement for the non-live case; a crafted POST while 'read-only via non-live' would still be accepted. Do not rely on the non-live gate as a security boundary.
3. Server-side rejection exists ONLY for serverReadOnly (demo mode), not for non-live anchors: internal/web/readonly.go `readOnlyGate` 403s every POST/PUT/PATCH/DELETE except the MCP dispatch route (gated by MCP tool filtering instead — and the route pattern is anchored so a …/facts/* path merely CONTAINING a /branches/X/mcp segment cannot slip past). So there are TWO independent read-only mechanisms — client-side button gating (non-live) and a server 403 gate (demo mode) — covering different triggers.
4. "Keyboard shortcuts live in RightPanel, so auditing RightPanel discharges the forward-looking rule." FALSE at HEAD — the audit surface is now four sites, three of them window-level `keydown` listeners: App.tsx (global: '/' focus filter, Escape, Backspace/Delete → NAV_BACK, 'h' → returnToNow), Library.tsx (arrows/j/k/Enter list navigation), and RightPanel.tsx (ConfirmModal Escape/Enter, plus ArrowLeft to blur the panel), alongside component-local onKeyDown handlers in FilterBar/FacetPanel/RepoManager/OverflowCrumb. All are navigation-only today, so the rule still holds — but note the two shapes that make this easy to get wrong: App.tsx's Backspace/Delete binding READS as destructive and is not (it dispatches NAV_BACK), while RightPanel's ConfirmModal Enter DOES confirm a retract and is safe only because the modal is reachable exclusively through the already-gated retract button. Library.tsx is the one handler that gates itself, returning early on `!isLive(state)` — for navigation-correctness, not mutation safety. Grep every `keydown`/`onKeyDown` site, not just RightPanel.

`mode:'diff'` also folds into `!isLive` and is read-only today.
