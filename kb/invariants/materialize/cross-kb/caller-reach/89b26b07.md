# materialize follows a cross-KB ref into a repo OUTSIDE the binding only when the CALLER's credential reaches that repo; an unreachable repo is listed exactly like a nonexistent one (kb_unavailable)

The user ruling 'cross-KB refs follow ANY repo registered on the server' is about AVAILABILITY. It does not authorize reading a repo the caller could not read itself.

The rule, as built on feat/materialize:
- The binding's own mounts (the write repo and a lens's read mounts) are always readable: the caller already reaches them.
- Any other repo, found by root-commit id through repos.Manager.ByRootID, is read only when `materialize.Request.MayRead(repoName)` says yes. Both edges (knomit_materialize, REST facts/*/materialize) pass `auth.ReachesRepo(ctx, name)`.
- auth.ReachesRepo is true when nothing confined the credential. Grants (auth.Allowed) carry NO repo dimension, so a caller on the local transports (socket, loopback, TLS certificate) already reaches every repo. The one per-caller repo scope that exists is the OAuth bearer token's AUDIENCE (RFC 8707 resource): BearerMiddleware records it with auth.WithRepoReach, answering for a repo NAME by asking whether the token's audience covers `/api/v1/repos/<name>`.
- Refused and nonexistent answer the SAME reason, `kb_unavailable`, so a caller cannot probe which repos exist. Keep it that way: a distinct reason for 'exists but forbidden' is an existence oracle.
- A nil Manager or nil MayRead reaches nothing outside the binding (fail closed).

CONSEQUENCE: any new server-side read that leaves the request's own repo (not only materialize) must ask auth.ReachesRepo, or a confined token reads past its audience.

WHAT THIS DOES NOT MEAN: ReachesRepo is not a permission check; read permission is still Allowed's question (the tool's read gate). And it is conservative for one credential: a token issued for the unscoped MCP endpoint (/api/v1/mcp) does not cover repo routes, so it gets no cross-KB repos beyond its binding even though it could bind them one by one with knomit_bind.
