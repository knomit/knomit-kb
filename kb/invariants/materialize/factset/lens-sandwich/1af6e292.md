# A lens FactSet's roots are anchored by an N-mount sandwich: EVERY lens member's settled watermark (and rebuild generation) is read before and after ONE fused fan-out under ONE deadline (factset_anchor_wait); any member unsettled or moved re-runs the WHOLE fan-out, and past the deadline the call is ErrIndexMoved with nothing written

fsCall.lensSearchAnchored (internal/corpus/materialize/factset_lens.go) generalizes the repo path's searchAnchored to every member of a lens: it reads SettledWatermark (watermark, generation, settled) of EVERY Binding.Reads() mount, and only when all are settled takes planning memory and runs ONE fused fan-out (runLensSearch); then reads all again. Only if every mount is settled on both sides with an equal watermark AND generation are the hits accepted, and each member's watermark becomes that member's frozen anchor (lensSub.Anchor, env.anchors). Otherwise memory is given back, the call waits (5 ms doubling to 100 ms) and re-runs the WHOLE fan-out (fusion needs every list), bounded by ONE deadline (session.factset_anchor_wait, default 5 s) and the request context; then ErrIndexMoved (MCP tool error, REST 503 once routed). The plan (motif widening, embedding) is computed ONCE before the loop. factsetSearchHook (the repo path's test seam) runs between the fan-out and the second reads.

Why every mount: each hit's (commit, blob) is its version at its own member's anchor only when that member's branch_facts was not being rewritten (68218e91). Pinned by TestLensFactSet_SyncOnR2DuringTheFanOutIsBusy (a write to R2 during every fan-out: waits the deadline, then ErrIndexMoved, nothing written; sabotage 'sandwich W only' is served). After creation every page reads each member at its frozen anchor (TestLensFactSet_R1MovingAfterCreationChangesNothing; sabotage 're-read the watermark per call' shows the new version).

CONSEQUENCES: the busy risk grows with N and with write rates on ANY member (measured: see the measurement fact); a mount whose index has NEVER synced has an empty watermark, which never reads settled, so such a member makes every lens FactSet busy (see the gotcha). Do not narrow the sandwich to the mounts the search targets without a ruling: subs of narrowed-out members still freeze an anchor.

WHAT THIS DOES NOT MEAN: it is not a per-mount retry (design Q-L6 option b); and a member moving AFTER creation changes nothing (anchors are frozen), only RULE 1 'now' marks.
