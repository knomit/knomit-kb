# A FactSet unit's plan depends on earlier units ONLY through 'which facts did units before it write, at which blob'; a fact is written at most once, so the first-written unit per fact (one growing prefix) reproduces every unit's plan byte for byte, in any order, while the caller's reach is unchanged

In internal/corpus/materialize (since PR #702, merged at 233a5404), planning unit u reads cross-unit state in exactly one place: fsState.lookup(h, check, repo, rel, u), called by planner.adopt for every INCLUDED node. Everything else a plan reads is frozen (roots, anchor, tips, the results and reserved tables) or index rows pinned by the anchor; the read-ahead window changes no byte. lookup asks only: was this fact written by a unit < u, and at which blob64 (a back link carries the anchor and that blob, never a number).

A fact is written at most once in a FactSet (after its first write every appearance is a link; within a unit a path is one node). Hence written-before(u) = { h : firstUnit(h) < u }, and the cache keeps per written fact the unit that first wrote it (fsState.wRoot / wRes []uint16 over the frozen tables, xentry.unit in the extra set). One prefix (units 1..planned) then answers every u <= planned: a unit is re-planned alone (no replay of 1..u-1), and pages are a pure function of (FactSet id, position) WHILE THE CALLER'S REACH IS UNCHANGED (see REACH below).

CONSEQUENCES:
- Any new input a unit's plan reads from OTHER units must also be a function of first appearances bounded by u; otherwise random access and concurrent reads stop being byte-identical. TestFactSet_RandomAccessIsByteIdentical (reverse, random, 8 concurrent readers, seeks, export after) fails on a lookup that ignores the bound.
- A page field must not report cache state: UnitsWalked/Sections are the highest unit the page walked (what sequential paging reports), not the prefix's extent.
- A half-applied unit (failed extension) is invisible: its marks carry its unit number, which no lookup bounded by a planned unit counts; re-applying is idempotent.

REACH: the 'everything else is frozen' premise has one exception, accepted by the user's no-reach-re-check ruling (PR #700): which foreign repos the caller may read is checked per content read, not frozen. When reach changes after a unit was planned, re-planning (or first planning) a unit can give different bytes in both directions: a repo LOST reads as kb_unavailable; a WIDENED reach can make a fact appear in full TWICE (the prefix recorded its first write in a later unit w because unit u could not reach it; unit u re-planned with the wider reach writes it too, since firstUnit = w >= u is not a back link). Nothing crashes and the prefix is not corrupted: re-planning never applies to the prefix, lookups stay bounded by the unit, and extension still plans strictly in order. So 'same bytes in any order, concurrently' (TestFactSet_RandomAccessIsByteIdentical) is a claim about a caller whose reach is stable, not about every call ever made on the FactSet.

WHAT THIS DOES NOT MEAN: it does not make the prefix shrinkable or order-free to BUILD: extending still plans units strictly in order (unit planned+1 next, under the entry's extension token). Only READING is order-free. Nor does it change numbering: N.k reservations and forward links still come from the frozen reserved table.
