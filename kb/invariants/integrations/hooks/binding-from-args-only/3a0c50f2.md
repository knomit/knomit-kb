# A hook's knomit binding is read from the MCP entry's ARGS alone: an entry with neither --repo nor --lens (knomitapi.IsUnbound) is UNBOUND whatever its key or directory says, and must never be turned into a repo scope

Since the bridge gained its unbound mode (PR #209), `kb` with neither `--repo` nor `--lens` is a working server that the agent binds per call with knomit_bind. The hooks (Claude session-start, Antigravity pre-invocation) must classify an MCP entry the same way the bridge will run it: from its ARGS, and only its args.

**The rule.** `knomitapi.IsUnbound(args)` is true exactly when no `-repo`/`--repo`/`-lens`/`--lens` token (bare or `=value`) appears. Such an entry is UNBOUND. Both hosts then skip corpus context with reason `unbound` and inject `knomitapi.UnboundNote` (call knomit_repos, then knomit_bind, pass the binding on every call) — one shared constant so the hosts cannot drift. An unbound entry beside a bound one is AMBIGUOUS (two different targets), and a degenerate `--lens` with no value is NOT unbound: it stays a distinct, unusable target, because the bridge exits 2 on an empty flag.

**Why the key cannot help.** A flagless `init` writes key `knomit-repo-<sanitized dir>` (knomitapi.UnboundServerKey) with `"args": []`, so the key of an unbound entry LOOKS exactly like a repo binding. Before #341, Claude's classifyArgs returned the directory basename for an args-less entry: in a directory named `knomit-kb` with an unbound server, session-start injected the real knomit-kb repo's principles while the MCP server itself was bound to nothing — a silent read of a knowledge base the session never chose. Antigravity instead returned no_binding and told the user every conversation to "Re-run init", which would have reproduced the same file forever.

**Consequences to act on.**
- Never derive a scope from a config KEY or a DIRECTORY name when an entry exists. Regression tests that pin this: TestMcpBinding_KeyLooksBound_ArgsUnbound and TestPluginBinding_KeyLooksBound_ArgsUnbound (key `knomit-repo-ingestion`, directory `ingestion`, args `[]` / absent / a bare base URL).
- Pipe init's own output into the consumer when testing (TestRunInit_NoFlags_ScaffoldedConfigIsUnboundToHooks, TestRunInit_NoFlags_WritesUnboundEntry) — hand-built fixtures are how producer/consumer splits have slipped through before.

**WHAT THIS DOES NOT MEAN.**
- It is not "the Claude hooks never use the basename". The fallback for a project with NO knomit entry at all (no .mcp.json, or no kb server in it) is unchanged and deliberately deferred: narrowing it would regress users whose server is configured at user scope. The rule governs what an EXISTING entry means.
- It is not "args-less means broken". Since #209 it means unbound, which is a supported mode.
- An existing test that treated a legacy args-less `knomit` entry as equal to `--repo <basename>` was rewritten: that pair is now ambiguous.
