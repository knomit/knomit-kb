# settings.json hook idempotence must key on the `claude hook <event>` suffix with a QUOTE-AWARE leading token — never the raw command string, never the matcher

When `kb claude init` merges hook registrations into an existing `.claude/settings.json`, "is this hook already registered?" must be answered by reducing each command to its `claude hook <event>` suffix (hookIdentity in tools/bridge/claude/init_merge.go), after confirming the command's FIRST FIELD is the bridge binary via knomitapi.IsKnomitCommand. The canonical identity is `kb claude hook <event>`. Two wrong keys are both tempting and both ship duplicates:

1. The COMMAND STRING. The bridge executable (`kb`) is deliberately never placed on $PATH outside the macOS .app, so real configs invoke it by path — `${CLAUDE_PROJECT_DIR:-.}/dist/kb claude hook post-edit`, `/usr/local/bin/kb …`, `kb.exe …`, or with global flags in between (`kb --log /tmp/b.log claude hook post-edit`). A string compare calls every one of those a different hook and registers a second copy, which then runs the SAME hook twice on every matching tool call.
2. The TEMPLATE'S MATCHER. A user who registered post-edit under their own matcher (say `Bash`) already HAS post-edit; keying on the matcher adds ours under `Edit|Write|MultiEdit` beside theirs.

Both duplicates are invisible in the diff of a long settings.json and nothing downstream detects them, so the only defence is the key. Presence is checked per EVENT, across every entry under that event, not per entry.

Why the first-field check is not optional: an unrelated tool whose command happens to end in `claude hook post-edit` is not our hook, and treating it as one would hide the user's own command behind ours.

WHAT THIS DOES NOT MEAN: it does not mean init reconciles hooks by identity in general — init only ever APPENDS. A knomit hook the user deliberately deleted is indistinguishable from one scaffolded before that hook existed, so it comes back on the next init (the bridge README says so). It also does not mean the user's spelling is normalised: the existing entry keeps its own path and matcher untouched; the identity is used only to decide whether to append.

AMENDED 2026-09-17 after a review round: reducing the command is a two-step operation, and the FIRST step was the wrong one. Taking `strings.Fields(command)[0]` before `filepath.Base` lets an opening quote ride into the token and shreds a quoted path at its spaces, so every one of these registered as a FOREIGN hook and was duplicated:

- `"$CLAUDE_PROJECT_DIR/dist/kb" claude hook post-edit`
- `'$CLAUDE_PROJECT_DIR/dist/kb' claude hook post-edit`
- `"/Users/me/Application Support/kb" claude hook memory-guard`

A hook command is a SHELL line, so a path containing a space MUST be quoted — and on macOS the install lives under "Application Support", which makes the quoted-path-with-spaces form the ordinary spelling rather than an exotic one. splitLeadingToken now takes a single- or double-quoted span as one token before Base; an unterminated quote takes the rest of the line, the reading a shell would give it.

It is deliberately NOT a shell parser: escapes, concatenated quoting and variable expansion are out of scope. It only has to recognise the binary well enough to answer "is this hook already registered", and the fallback for anything it cannot read is the whole normalised command string. That is the safe direction to fail: a missed match costs a duplicate, while the other direction would swallow a user's own hook.

AMENDED 2026-09-18 with the knomit-bridge → kb rename (PR #218): the fallback "never equals a knomit identity" ONLY IF the canonical prefix spells the SAME binary name IsKnomitCommand accepts. The proof: a fallback equal to `kb claude hook <event>` must start with the bare token `kb`, which IsKnomitCommand accepts, so that input takes the canonical branch and never reaches the fallback. The rename's first pass kept the canonical literal at the OLD name while IsKnomitCommand moved to `kb`; a pre-rename `knomit-bridge claude hook post-edit` was then foreign, fell to the fallback, and the fallback was byte-equal to the canonical string, so init reported success while skipping the post-edit hook. See the incident. Consequence: the canonical literal in hookIdentity and the name IsKnomitCommand accepts change in the SAME commit, and the check is behavioural — run init over a settings.json spelling every previously accepted binary name and assert each event is scaffolded. A pre-rename spelling is a FOREIGN command by decision (no compatibility alias), so init scaffolds the working `kb` hook beside the stale one rather than reading the stale one as registered.

SCOPE LIMIT, established 2026-09-17. This normalisation applies only WITHIN the project's `.claude/settings.json`, the one file init reads. Claude Code merges hook entries additively across user, project and local settings and deduplicates only handlers that are identical AS WRITTEN, so a differently-spelled registration at another scope still produces two runs, and init cannot see it to prevent that. See the settings-scopes gotcha.
