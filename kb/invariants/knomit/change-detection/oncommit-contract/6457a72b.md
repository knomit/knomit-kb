# SetOnCommit must be called before any writes; observer drops notifications during re-entrant callbacks

Two load-bearing rules around the onCommit observer:

**1. Init-time-only contract on `SetOnCommit`.** The `onCommit` field on `store.Service`'s repo handler has no synchronization. The design explicitly chose this: the callback is set once at server startup before any write can occur. Calling `SetOnCommit` after writes have begun is a data race. The `repos` package re-applies the callback after `SwapStore` (swapstore.go) — this is safe only because SwapStore holds the appropriate lock.

**2. Observer re-entrancy guard drops mid-run notifications.** `observe.Observer` has an `atomic.Bool` `running` flag (`internal/observe/observe.go:21`). If `fn` is still executing when the debounce timer fires, the notification is silently dropped — `CompareAndSwap(false, true)` fails and the timer goroutine exits without calling `fn`. This means: **if `idx.Sync` (or whatever fn does) takes longer than the debounce window AND new commits land during that run, the new HEAD will not trigger a fresh sync until the NEXT commit arrives.** SSE clients may briefly see a stale HEAD. The design doc did not mention this guard; it was added during implementation. If you change the observer's callback to something slow, this becomes a real problem.

**3. `Stop()` flushes pending synchronously** before returning, so shutdown doesn't lose the final notification — but only if `running` is false. If a slow `fn` is mid-run during Stop, the pending notification is also dropped.
