# Generated okf/* refs must never reach any remote; enforced by a push-site guard plus a refspec test

Constraint accepted during OKF export design: generated OKF refs are derived data local to a knomit store and must never be pushed to a remote.

Options considered: (a) name them refs/heads/okf/* and enforce non-leakage by a guard plus test; (b) name them refs/knomit/okf/* so nothing walking refs/heads can see them, making leakage structurally impossible; (c) store under refs/knomit/okf/* but rename to refs/heads/okf/* in the smart-HTTP advertisement, getting both properties.

Rationale: (b) is structurally safest but `git clone -b` cannot check out a non-branch ref, so external consumers — the entire audience for this feature — would need an explicit fetch refspec. (c) recovers the UX but adds post-processing of go-git's AdvRefs inside the protocol path, where bugs are expensive. (a) was chosen because today's code already cannot leak: knomit has exactly two push sites, internal/repos/sync.go:157 and internal/store/remote_sync.go:241, and both push a single named branch with an explicit refspec (+refs/heads/<branch>:refs/heads/<branch>); nothing enumerates local branches to push, and fetch refspecs are pinned to main + agent/<host> in internal/store/branch.go, so a fetch cannot clobber them either.

The choice: refs/heads/okf/<branch>, plus an assertion at both push sites and a test that fails if any push refspec can match okf/*, and that fails if a new push site is added without the guard.

What this does NOT mean: it does not forbid a USER cloning from knomit and pushing the OKF branch to GitHub — that is the intended distribution path. The prohibition is specifically on knomit's own sync pushing okf/* to a repo's configured origin. It also does not forbid ADVERTISING okf refs over knomit's read-only smart-HTTP endpoint; that advertisement is how the feature is consumed.
