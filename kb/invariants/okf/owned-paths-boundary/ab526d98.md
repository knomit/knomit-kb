# knomit-okf owns exactly index.md, log.md, kb/, views/, .knomit-okf.yaml — it prunes inside them and must never touch anything else

knomit-okf manages a FIXED set of paths in the output repo — index.md, log.md, kb/, views/, .knomit-okf.yaml — and reconciles them exactly: it writes what the bundle contains and deletes anything beneath them it did not write.

Both halves are load-bearing, for opposite reasons.

Deleting is mandatory because overlaying files can never REMOVE them. Without the prune, a retired fact's document stays published forever, contradicting the views/retired.md sitting in the same bundle. A planted stale file was confirmed to survive a re-extract.

Not deleting anything else is equally mandatory: everything outside the owned set belongs to the publisher. A README.md, LICENSE, or .github/ must survive a sync. The naive implementation — clean the working tree, then write the bundle — destroys a publisher's work, which is why the boundary is enforced in code (reconcile REJECTS an unowned path rather than writing it) and not left to convention.

The same boundary governs staging: only owned paths are added to the index, so a publisher's uncommitted edits are never swept into an okf commit.

What this does NOT mean: the tool is not free to add paths to the owned set casually — each one it claims is a directory it will happily delete files from.
