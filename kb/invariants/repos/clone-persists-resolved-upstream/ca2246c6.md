# initClone MUST persist the upstream InitFromRemote RESOLVED, never the one the caller requested

`Service.InitFromRemote` RETURNS the upstream branch it adopted — `(string, error)`, and `initFromEmptyRemote` returns it too. `Manager.initClone` must pass that returned value to `SetRemote`, not `spec.Origin.Branch`.

Why the signature exists: when the caller passes an empty branch, InitFromRemote resolves one itself by store.ChooseConsensusBranch (the remote's symbolic HEAD unless it is an agent/exp/okf branch, else the one other branch, else it refuses with ErrNoConsensusBranch; it no longer prefers or defaults to any name) and creates the local branch and fetch refspecs from THAT. A caller that then persists its own `if branch == "" { branch = <some name> }` fallback (Origins.Set now refuses an empty branch instead of filling one in) writes a remotes row disagreeing with the refspecs the clone just built. For a master-convention origin the row says "main", the refs say "master", and every later sync reads a nonexistent origin/main. This is the same class of bug that `rehydrateUpstreamMain` exists to prevent on the reboot path.

Two related rules on this path:

- `initClone` passes the default ontology in `initFiles`. InitFromRemote IGNORES seed files when the remote has branches (content comes from the clone) and writes them when it does not — so without them, cloning an EMPTY origin produces a repo with no ontology file, unlike every repo from `initLocal`.
- `repoBuilder.upstreamMain` is loaded from the stored remote row by `rehydrateUpstreamMain` and is EMPTY when the repo has no origin. `setupIndex` uses that emptiness as the has-origin test. Never default it to "main": doing so would add a nonexistent branch to the startup index sync for every origin-less repo.

WHAT THIS DOES NOT MEAN: the caller-supplied branch is not ignored. A non-empty `OriginSpec.Branch` is honoured and returned unchanged; the rule is about which value gets PERSISTED, which is always the returned one.

UPDATE (PR #524, verified at merge commit 9db8c106): store.InitFromRemote gained a trailing variadic `opts ...InitOption`. The only option is OwnBranchesOnly(), passed by a fleet-door create (repos.fleetCloneOptions); it narrows the bootstrap fetch to exact refspecs for every non-agent branch plus the instance's own agent branch, never the agent/* wildcard. The upstream resolution and its persistence are unchanged, because the narrowed bootstrap still sees every non-agent branch and the remote HEAD (kb/invariants/store/branch-roles/962ca98d.md).

WHERE IT LIVES NOW (refactor-store-slim-c-bootstrap): Service.InitFromRemote in internal/store/repo.go is a one-line forward (it keeps the contract doc) to remotesync.InitFromRemote in internal/store/remotesync/bootstrap.go, with the same (upstream, remoteWasEmpty, err) results and the variadic InitOption. initFromEmptyRemote is now an unexported function of that file, not a Service method, and still returns the upstream it bootstrapped. The rule is unchanged; callers keep calling store.Service.InitFromRemote.
