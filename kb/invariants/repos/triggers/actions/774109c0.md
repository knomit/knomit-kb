# Every new trigger `do` action needs THREE edits or it silently misbehaves: its own phase-B case ahead of `default:` (the default arm EMITS), its outcome added to phase B's fires sum, and a case in triggerStats.record (the switch has no fallthrough to fires)

phaseB's action switch handles `if` errors, if-false, `do: script`, (since F07 PR 4) `do: push` and (since PR 5) `do: run`; EVERYTHING else falls into `default:`, which records `emitted` and publishes an SSE `trigger` event. Adding a value to activeTriggerDo alone therefore makes the new action emit — and a test that only checks 'it fired' passes. Required, all three:
1. an explicit `case p.trig.Do == fact.TriggerDo<X>` before `default:`;
2. its outcome in the `fires++` condition right after the switch (phase B's run-level fires count);
3. a `case "<outcome>": st.fires++` in triggerStats.record — its switch has no default that counts a fire, so an unknown outcome is an evaluation with 0 fires on GET …/triggers.
Also: the outcome column is free text (no migration), but the openapi TriggerFire.outcome enum is pinned by internal/web/openapi_triggers_contract_test.go.

Tested for push by TestPush_StatisticsAndLog (sabotages: route push through default: → `emitted` + an SSE event; drop the stats case → fires 0).

`do: run` (F07 PR 5) follows the same three edits: its own case calls startRecipe; `started` joins the fires sum and triggerStats.record (`busy`, `recipe-error`, `unbound` are counted but are not fires); and a FOURTH detail: `unbound` is an evaluation that writes NO row, so the row append excludes it next to if-false. The recipe's later RESULT outcomes are counted by triggerStats.recordRecipe, never as evaluations.
