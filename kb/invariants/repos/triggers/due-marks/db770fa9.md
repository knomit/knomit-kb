# A due mark (trigger_due_fires, migration 000030, PRIMARY KEY(branch, trigger, path) + expires_at) means 'this trigger PROCESSED this path at this due instant, whatever `if` said': written for every evaluated outcome EXCEPT a fire dropped for capacity (rate-limited, busy — retried next sweep, F08), replaced on a different instant (re-arm), deleted with the bookmark when the trigger NAME leaves, never capped by the fire-log retention, and untouched by an index rebuild

F07 PR 2. The dispatcher's THIRD table, local cache like trigger_watermarks and trigger_fires (never synced, never copied onto exp/<name>). One row per (branch, trigger, path) with expires_at (the due instant, Unix seconds UTC) and fired_at (the run's clock, Unix seconds UTC).

Rules a consumer must act on:
1. PROCESSED, not emitted (M2): a mark is written for every evaluated (trigger, path) — emitted, if-false, if-error, if-timeout, unparseable, ran, script-error, script-timeout — exactly as a watermark advances whatever `if` said. EXCEPTION (F08 PR A, M3): a due fire DROPPED for capacity — outcome `rate-limited` (the per-minute script cap) or `busy` (a `do: run` recipe at its `concurrent` limit) — was not processed: phase B records it in runState.dueRetry and buffer() skips its mark, so the next sweep (next tick or write) fires it again. Its fire row is still logged, so the log shows every drop and every retry. Script errors and timeouts KEEP their mark (a deterministic throw would otherwise re-fire every tick for the life of the fact). Misreading to avoid: this is NOT a retry of dropped learn/update/retract fires — those stay dropped for good (the bookmark moved past them); only due fires are re-derived state. Pinned by TestDue_RateLimitedRetriedNextSweep, TestDue_BusyRecipeRetried, TestDue_ScriptErrorNotRetried. Consequence: an `if`-false due fact is evaluated ONCE, not on every run for as long as it is live (1,000 such facts would otherwise cost ~250 ms of goja per run, forever). The column keeps the design's name fired_at; the endpoint text says processed. A run whose phase B is aborted (ctx cancelled) buffers nothing: at-least-once.
2. Keyed per TRIGGER and per due INSTANT (maintainer ruling 2026-09-28, D1-B), not per fact version: two `due` triggers on one fact keep separate marks; a body-only edit keeps expires_at and does NOT re-fire; changing the fact's `expires` gives a different instant → the fact fires again when that instant passes and INSERT OR REPLACE replaces the row (re-arm). Same path + same instant = processed: a fact retracted and re-learned at the same path with the same `expires`, or cleared and set back to the same date, does not fire again; a different date does.
3. The marks ride phase C's write-behind buffer (pendingFlush.due) and tx2 with the watermarks (AdvanceTriggerWatermarks(ctx, branch, set, del, due)); phase A overlays the buffered marks (overlayPending), so a run kicked inside the 20 ms flush grace sees them. A crash after the emit and before the flush re-fires on restart (the log then shows both fires), the same at-least-once contract advances have.
4. Written in fireRowBatch-sized multi-row statements (500 rows × 5 columns) and NEVER capped: TriggerFireRetention trims fire ROWS only — a run that evaluated 12,000 due facts logs 10,000 rows and marks 12,000 facts (M7).
5. One rule for both bookkeeping tables (M8): a NAME in `del` (it left the ontology at the head) deletes its bookmark AND its marks on that branch; a renamed or removed-then-re-added trigger is a NEW trigger and processes the currently overdue set once more (D2 (a)). Marks for PATHS no longer live stay (tiny, bounded by the distinct due paths per trigger).
6. rebuildFacts writes facts, fact_expires, the junctions and branch_facts only; it never touches the dispatcher's three tables, so a rebuild neither re-arms a processed fact nor forgets a mark (M6, pinned by TestDue_RebuildDoesNotRefire). A SwapStore replaces the whole DB: the clone's marks are whatever it holds (usually none), and the still-overdue facts fire once more, visibly, in the log.

Misreading to avoid: 'fired_at on fact_expires' (the F07 design's literal wording) — the mark is NOT on F03's table and could not be an ADD COLUMN there (the migration recovery path tolerates one duplicate-column collision and 000019 spent it); per-VERSION keying was rejected because a body edit would re-fire and a later `due` trigger would never fire for marked facts. Tests: TestDueMarks_RoundTripAndForgottenWithTheName, TestAdvanceTriggerWatermarks_DueMarksUnbounded (store); TestDue_FiresOnceAcrossTicks, TestDue_IfFalseEvaluatedOnce, TestDue_ChangingExpiresRearms, TestDue_BodyEditDoesNotRefire, TestDue_RemovedTriggerForgetsMarks, TestDue_RebuildDoesNotRefire, TestDue_CrashBeforeMarkRefiresAndLogsBoth (repos).

Two clocks, both UTC, both Unix seconds: the MARK's fired_at is the run's clock (the instant the sweep compared against); the FIRE-LOG row's fired_at is the flush time (stamped in tx1 when the write-behind buffer lands, up to the 20 ms grace plus the flush later).
