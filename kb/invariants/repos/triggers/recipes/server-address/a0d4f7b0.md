# A recipe's exec child gets KNOMIT_SERVER = the server's OWN address — its local listener only if that listener BOUND (cfg.Socket, which may be KNOMIT_SOCKET, toml socket or the /tmp long-home fallback), else its TCP address — recorded by BOTH cmd/serve.go and the desktop boot via Manager.SetServerAddress; exec NEVER starts a child without it: in the boot window it WAITS (bounded) and otherwise throws 'server address not ready' (run = recipe-error); the recipe's own exec env wins

internal/repos/trigger_recipe.go recipeEnv adds KNOMIT_SERVER = d.serverAddr() (Manager.ServerAddress, an atomic set by SetServerAddress) beside KNOMIT_HOME/TRACE/CAUSE/RUN; exec merges the recipe's `env` over that base, so a recipe can name another server.

WHICH ADDRESS: cmd/listen.go serverAddress(cfg, ul, ln.Addr()) and tools/desktop/boot.go bootServer (server.address) both return serveraddr.ForLocal(<the path ListenLocal was given>) ONLY when the local listener was returned non-nil, else serveraddr.ForTCP(<the TCP listener's bound address>). The path is cfg.Socket / localListenerFrom(cfg).Path — never a re-derived <home>/knomit.sock, because KNOMIT_SOCKET, toml `socket` and the /tmp/knomit-<euid>/<hash>.sock long-home fallback all move it. A held socket (ErrSocketInUse), an overlong path or an unsafe fallback dir leave the server TCP-only, and then it must NOT name the socket: a held one belongs to ANOTHER instance, and naming it would send this server's recipe sessions there — the wrong-instance bug again.

BOTH ENTRY POINTS: cmd/serve.go calls a.Manager().SetServerAddress right after openLocalListener; tools/desktop/app.go calls it after bootServer. test/archtest TestBothServerEntryPointsRecordTheirAddress pins both calls (see kb/gotchas/desktop/separate-server-boot-path for why one alone is a known failure).

BEFORE IT IS SET — the boot window (review F1 on #393): Manager.Start runs inside app.New and starts each repo's dispatcher, which kicks a first run at once (and due sweeps fire on it), all BEFORE serve.go/the desktop bind their listeners and call SetServerAddress. A child started then would have no KNOMIT_SERVER and its kb would reach the desktop lockfile's server — the incident again. So recipeEnv calls waitServerAddr: it polls Manager.ServerAddress every 50 ms, bounded by recipeServerAddrWait (2 min, a var for tests) and by the run's ctx (budget, knomit's stop). Still unknown -> exec THROWS 'exec: server address not ready ...', the program is NOT started, and an uncaught throw ends the run recipe-error. An inherited KNOMIT_SERVER (from knomit's own launcher) is never a substitute; once the address is known it overrides any inherited value. The dispatcher's start-up is deliberately unchanged (the coordinator's ruling: wait in the exec host, not delay the dispatcher). Tests: TestRun_ExecBeforeTheAddressIsSetStartsNothing (no child report, recipe-error naming the cause) and TestRun_ExecWaitsForTheAddress (address set mid-wait -> child starts with it); sabotage 'start the child anyway' turns both red.

TEST HARNESSES must record an address like a booted server: newScriptRepo and the mission e2e newMissionManager call SetServerAddress("http://127.0.0.1:1"); a new harness that execs recipes without it now waits 2 min and fails.

Consequence: adding a third way to start a server (another binary, a test harness that serves) means calling SetServerAddress from it, or its recipes' sessions reach whatever the lockfile names.

Both entry points also LOG the recorded address ("this server's address (KNOMIT_SERVER for kb)", field knomit_server) — the line an operator copies into KNOMIT_SERVER to reach one instance among several, instead of building <home>/knomit.sock (wrong for KNOMIT_SOCKET, toml socket or the long-home /tmp fallback).
