# On the control.db boot path the order is guard → upgradeLensSchema → migrator, and BOTH orderings are load-bearing for different reasons

Introducing `migrate.Control` to control.db does NOT let the boot sequence be reordered or collapsed. Three steps, fixed order, all on one handle:

1. `refuseUnmigratedHome(db, reposDir)` — reads only.
2. `upgradeLensSchema(db)` — Go, pre-baseline.
3. `migrate.Control(db)` — 000001 onward.

**Guard before migrator.** The guard's `SchemaExisted()` arm asks "has the `repos` table ever existed here", and creating that table destroys the evidence. The migrator creates it. If the migrator ran first, the guard would fire on the first boot only and report a clean home on every retry — under a restart policy that turns "refuse loudly" into "refuse once, at 3am, into a log nobody reads". This is why `Manager.Start` opens via `OpenRegistryNoSchema`.

**upgradeLensSchema before the migrator.** The re-key mints ksuids in Go, so it cannot be a .sql file without changing the uid format (repo uids and lens uids must be indistinguishable in shape). But the sharper reason is an index collision: `ALTER TABLE lenses RENAME TO lenses_old` does NOT rename indexes attached to the table. If the baseline's `CREATE UNIQUE INDEX IF NOT EXISTS lenses_name` ran first against a pre-uid `lenses`, the index would survive the rename still named `lenses_name`, and the re-key's own `CREATE UNIQUE INDEX lenses_name` would fail with "index lenses_name already exists". Running the re-key first reproduces exactly the order that works today.

**What this does NOT mean.** It does not mean `upgradeLensSchema` is migration 000002 — it sits deliberately OUTSIDE the numbered sequence, because it repairs a shape that predates versioning and must run before version 1 rather than after it. And it does not mean the guard is redundant now that there is a version table: an unmigrated home has no `schema_migrations` row to distinguish it, which is the whole reason `HasLegacyLensSchema` remains the durable arm.
