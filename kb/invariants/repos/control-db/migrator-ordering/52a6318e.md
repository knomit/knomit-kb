# control.db bring-up is guard then controlUp (conditional re-key then migrate.Control) — the ordering lives inside controlUp, and every opener must CALL it rather than reproduce it

Introducing `migrate.Control` to control.db does NOT let the boot sequence be reordered, collapsed, or re-implemented per entry point. Stated with every component named:

1. `refuseUnmigratedHome(repoReg, reposDir)` — reads only. **`Manager.Start` ONLY.**
2. `controlUp(db)` — the shared bring-up, called by `Manager.Start`, `OpenRegistry` AND `OpenLensRegistry`. Inside it, in this order:
   - a. `HasLegacyLensSchema(db)` — probes for the pre-registry `lenses.write_repo` column;
   - b. `upgradeLensSchema(db)` — the Go re-key, run **only when that probe returns false**;
   - c. `storemigrate.Control(db)` — baseline 000001 onward, run unconditionally.

All on one handle (`internal/repos/registry.go` controlUp; `internal/repos/manager.go` Manager.Start).

**Guard before migrator.** The guard's `SchemaExisted()` arm asks "has the `repos` table ever existed here", and creating that table destroys the evidence. The migrator creates it. If the migrator ran first, the guard would fire on the first boot only and report a clean home on every retry — under a restart policy that turns "refuse loudly" into "refuse once, at 3am, into a log nobody reads". This is why `Manager.Start` opens via `OpenRegistryNoSchema` and defers `controlUp` until the guard has passed.

**Re-key before the migrator.** The re-key mints ksuids in Go, so it cannot be a .sql file without changing the uid format (repo uids and lens uids must be indistinguishable in shape). The sharper reason is an index collision: `ALTER TABLE lenses RENAME TO lenses_old` does NOT rename indexes attached to the table. If the baseline's `CREATE UNIQUE INDEX IF NOT EXISTS lenses_name` ran first against a pre-uid `lenses`, the index would survive the rename still named `lenses_name`, and the re-key's own `CREATE UNIQUE INDEX lenses_name` would fail with "index lenses_name already exists". Worse, the baseline also STAMPS the home at version 1 on the way past, so the collision is permanent: every later open, correctly ordered or not, fails. `controlUp`'s comment states it plainly — one stray caller that migrates control.db without the re-key bricks the home for good.

**Operational consequence:** if you add ANY new code path that opens control.db, call `controlUp` (or `OpenRegistry`, which wraps it). Do not reproduce steps 2a–2c inline, and do not call `storemigrate.Control` directly.

**WHAT THIS DOES NOT MEAN.**

- *Not* "the ordering lives in `Manager.Start`, so a new opener should copy those steps." Since `b0605787` the ordering lives in `controlUp` and `Manager.Start` merely calls it. Copying the sequence into a new opener is how it drifts; `applyControlDB` in `cmd/migrate_registry.go` is the ONE deliberate exemption in production code, and only because it drops and rebuilds the lens tables from the baseline DDL text inside its own transaction, leaving the re-key nothing to convert.
- *Not* "every booted control.db has been through the lens re-key." Step 2b is SKIPPED when `HasLegacyLensSchema` is true — a genuinely pre-registry home (`lenses.write_repo`, membership by NAME) is left exactly as `knomit migrate-registry` expects to find it, because `upgradeLensSchema` copies `write_uid`, a column that shape does not have. See [[lens-registry-no-auto-migrate]] (kb/invariants/repos/lens-registry-no-auto-migrate/9ca80457.md) for which shape heals on open and which does not.
- *Not* "the guard protects every path." Only `Manager.Start` runs `refuseUnmigratedHome`. `OpenRegistry` and `OpenLensRegistry` call `controlUp` with no guard in front, so a tool using them against an unconverted home migrates it without the refusal a server boot would have raised.
- *Not* "`upgradeLensSchema` is migration 000002." It sits deliberately OUTSIDE the numbered sequence, because it repairs a shape that predates versioning and must run before version 1 rather than after it.
- *Not* "the guard is redundant now that there is a version table." An unmigrated home has no `schema_migrations` row to distinguish it, which is the whole reason `HasLegacyLensSchema` remains the durable arm.
