# control.db bring-up is controlUp (conditional lens re-key, then migrate.Control) — the ordering lives inside controlUp, and every opener must CALL it rather than reproduce it

Introducing `migrate.Control` to control.db does NOT let the bring-up be reordered, collapsed, or re-implemented per entry point. Stated with every component named:

`controlUp(db)` — the shared bring-up, called by `Manager.Start` (after `OpenRegistryNoSchema`), `OpenRegistry` AND `OpenLensRegistry`. Inside it, in this order:
   - a. `HasLegacyLensSchema(db)` — probes for the pre-registry `lenses.write_repo` column;
   - b. `upgradeLensSchema(db)` — the Go re-key, run **only when that probe returns false**;
   - c. `storemigrate.Control(db)` — baseline 000001 onward, run unconditionally.

All on one handle (`internal/corpus/repos/registry.go` controlUp; `internal/corpus/repos/manager.go` Manager.Start; `internal/corpus/repos/lens.go` OpenLensRegistry). Outside tests, nothing calls `storemigrate.Control` except through controlUp.

**Re-key before the migrator.** The re-key mints ksuids in Go, so it cannot be a .sql file without changing the uid format (repo uids and lens uids must be indistinguishable in shape). The sharper reason is an index collision: `ALTER TABLE lenses RENAME TO lenses_old` does NOT rename indexes attached to the table. If the baseline's `CREATE UNIQUE INDEX IF NOT EXISTS lenses_name` ran first against a pre-uid `lenses`, the index would survive the rename still named `lenses_name`, and the re-key's own `CREATE UNIQUE INDEX lenses_name` would fail with "index lenses_name already exists". Worse, the baseline also STAMPS the home at version 1 on the way past, so the collision is permanent: every later open, correctly ordered or not, fails. One stray caller that migrates control.db without the re-key bricks the home for good.

**Operational consequence:** if you add ANY new code path that opens control.db, call `controlUp` (or `OpenRegistry`, which wraps it). Do not reproduce steps a–c inline, and do not call `storemigrate.Control` directly.

**WHAT THIS DOES NOT MEAN.**

- *Not* "the ordering lives in `Manager.Start`, so a new opener should copy those steps." The ordering lives in `controlUp` and `Manager.Start` merely calls it. There is no longer any production exemption (the whole-chain replay tool that had one was removed in merge 1cc5413c).
- *Not* "`Manager.Start`'s split open (OpenRegistryNoSchema, then controlUp) guards anything." It used to let a boot check run before the schema existed; that check was removed in merge 1cc5413c. The split now only means Start holds the handle before controlUp can fail.
- *Not* "every booted control.db has been through the lens re-key." Step b is SKIPPED when `HasLegacyLensSchema` is true — a genuinely pre-registry home (`lenses.write_repo`) is left untouched, neither converted nor refused. See [[lens-registry-no-auto-migrate]] (kb/invariants/repos/lens-registry-no-auto-migrate/9ca80457.md).
- *Not* "`upgradeLensSchema` is migration 000002." It sits deliberately OUTSIDE the numbered sequence, because it repairs a shape that predates versioning and must run before version 1 rather than after it.

**The one sanctioned exception (PR #515): a short-lived READ-ONLY open.** "Every opener must call controlUp" applies to every opener that can WRITE. A handle opened with SQLite `mode=ro` (repos.StoredAgentID, via openControlReadOnly, used by `knomit identity show`) deliberately does NOT call controlUp: it can neither create a missing control.db nor migrate or re-key an existing one, so it cannot reorder or skip steps a-c. Calling controlUp from a display command would be the harm: a newer CLI would migrate the control.db of an instance that last booted, or is still running, on an older binary. Conditions for the exception, all required: the open is `mode=ro` on an absolute path via internal/platform/fileuri (see kb/gotchas/store/sqlite/file-uri-dsn), the handle is short-lived and closed by its caller, and it only reads. NOT covered by the exception: OpenRegistryNoSchema (read-write-create, so it can create the file and flips a rollback-journal file to WAL), any read-write handle that merely skips controlUp, and any caller that writes. A reader of the exception must also handle a not-yet-migrated file: a missing file, missing table or missing row is answered as `none`, not as an error.
