# Index state is DERIVED from the lifecycle machine (cursor + the Index job's verdict); IndexEvents are published only by Machine.publish() after a transition, nothing else constructs one, and teardown publishes nothing

Rewritten for issue #411; the mark* mutators, the index state cell, MarkIndexRebuildStart/Done and the per-site marking it described are gone.

THE RULE. There is no index state to write. Machine.computeStatus derives Index{State, Done, Total, Reason} from (a) whether an Index life exists and (b) the job's verdict (r.indexVerdict: nil while running, else the job's error or ErrIndexCancelled), plus the job's progress atomics. Machine.publish() is the ONE place that builds and broadcasts an IndexEvent (via publishIndex/indexPublisher) and the manual rebuild's TaskEvent (publishRebuildTask). It runs on the driver after every transition: enter, exit, indexDone, indexProgressed, crash bookkeeping. Do not construct an IndexEvent anywhere else and do not add a second publish point.

WHY IT CANNOT GO STALE. The 2026-08 stuck-indexing incident and #400's writerless 'indexing' were both an exit path that forgot to mark. With a derived state there is no mark to forget: every way the Index life ends (job done, job panicked — recovered into an indexDone error, CancelIndex, Rebuild replacing it, a rewind) changes either the life or the verdict, and publish runs after it. The verdict is reset to nil in Machine.enter for Open and Index BEFORE that enter publishes, so a stale 'ready' from the previous store or job is never announced as the new state.

ORDER, under the broadcaster lock: store the snapshot (an event never outruns the state a poller reads), emit the IndexEvent and TaskEvent, then wake Watch subscribers. A new Watch takes its first value under the same lock, so a watcher that reacts to 'left indexing' (the create job's done) acts after the event is out.

TEARDOWN publishes nothing: Machine.unmount never calls publish (it drains the stages, then stores the closed status directly and closes the watchers with that last value readable), and publish itself emits no events once the machine is closed — a closed repo's chip is about to disappear and an event would only announce a terminal for a discarded store.

PROGRESS is the one throttled case: indexPublisher emits at most one progress event per repo per second; entry and terminal events (state or reason change) are never throttled and a terminal resets the window. Progress reaches the driver as a coalesced indexProgressed internal event (one pending at a time).

WHAT THIS DOES NOT MEAN: not every piece of index WORK is announced — only changes of the derived state (and throttled progress).

ENFORCEMENT SINCE 14b (PR #631, merge 37dc65d5, re-read there): the event types and hubs moved to internal/corpus/repos/events, which would have turned the old unexported publish methods into exported ones callable from any package. They were instead split onto publishers: IndexEvents are announced only through events.TaskPublisher.BroadcastIndex, called from the single site in index_events.go (m.r.pub.BroadcastIndex, reached only from Machine.publish via publishIndex), and the publisher is held only by the repos parent in unexported fields. So the invariant is enforced by the PACKAGE BOUNDARY PLUS THE PUBLISHER CAPABILITY: outside repos, calling BroadcastIndex on ri.TaskHub() does not compile. The same holds for the machine's rebuild TaskEvent (pub.PublishTask in Machine.publish) and for RepoEventPublisher.Publish. Inside repos the one-publish-point rule is still by convention plus the repos guards. The guards that keep the capability from leaking, and what they miss, are in kb/invariants/testing/event-publishers-guard/10324df7.md; the decision is kb/decisions/repos/events/hub-publisher-split/f6d5c104.md. IndexEvent is now events.IndexEvent.
