# Index-state events are published INSIDE markIndexing/markIndexReady/markIndexFailed and nowhere else — never at a call site — so "every exit path marks" and "every exit path announces" are ONE rule that cannot drift apart

Every index-state change publishes its own event, from inside the three mutators. `RepoInstance.publishIndex` is the only thing that constructs or broadcasts an `IndexEvent`, and the three mark* methods are the only things that change `indexState`. Do not publish from a call site, and do not add a fourth mutator.

WHY A CHOKEPOINT. Index state changed in five places when this was written, ALL inside `Manager.openOne` — the synchronous `DisableBackgroundSync` branch's two exits, and the background heal's `markIndexing` plus its two exits — and more would be added by someone who does not know this event exists (two have been: see the site count below). Publishing on the STATE CHANGE rather than at the sites that cause it makes announcing a property of the change. This is the same shape as `notify-commit-single-chokepoint` in the store, and the same motif: a bypass would defeat the guarantee, so there is no bypass to take.

IT INHERITS THE STUCK-INDEXING GUARANTEE, and this is the load-bearing part. The 2026-08 incident was a heal exit path that reached neither mark, pinning the UI at `indexing` forever; the repair made every exit path mark. Because the event rides ON the mark, that existing rule now carries the new one for free — there is no second "and remember to publish" rule to keep in sync with it, and any future work that preserves the first automatically preserves the second.

THE CANCELLATION EXIT DELIBERATELY MARKS NOTHING, and therefore publishes nothing. The heal goroutine's `if b.indexCtx.Err() != nil { return }` is reached by two kinds of cancel. On TEARDOWN (shutdown, Manager.Close) the instance is going away and its status is no longer observed, so not marking is correct. On SWAPSTORE the repo stays live and observed, and the exit leaves the state at 'indexing' with no writer — before issue #400 (PR #404) that pinned it for the life of the process. The exit is still correct there ONLY because SwapStore's caller now marks: the origin-session commit handler brackets its post-swap Rebuild with MarkIndexRebuildStart/MarkIndexRebuildDone (and marks 'error' when no store can be acquired, except ErrRepoClosed where the repo is being torn down, or when the swap fails with the state still 'indexing'; on a failed swap the handler first restores the previous sync via restorePreviousSync, a synchronous ActivateSync reconcile, and only THEN marks, so a writerless 'indexing' outlasts that restart. Known gap: no test asserts 'indexing' DURING the post-swap rebuild; the web test seeds 'indexing' by hand and asserts 'ready' after, so it passes even without MarkIndexRebuildStart). A reader auditing "every exit announces" must not add a mark at the heal's exit — on a swap it would publish a terminal for the discarded store — but ANY NEW CALLER OF SwapStore must take over the marks the same way, or reintroduce the stuck state.

SEVEN SITES NOW MUTATE THE CELL (counting each bracket as one), not five: the five in openOne (the sync branch's two exits, the heal's markIndexing and its two exits), handleStartRebuild's bracket (handlers_jobs.go), and the origin-session commit's post-swap bracket (handlers_origin_session.go, itself four call sites: MarkIndexRebuildStart, the rebuild's Done, the no-store Done, the failed-swap Done). Both exported brackets rely on single-writer by construction: handleStartRebuild 409s while 'indexing'; the commit marks right after SwapStore returns, when SwapStore has already drained the heal (indexWg) and any manual rebuild (its Acquire on the old store). A short check-then-mark window remains between SwapStore returning and the commit's mark, in which a manual rebuild could slip in.

PROGRESS IS THE ONE THROTTLED CASE. `setIndexProgress` publishes at most once per repo per second; the three mark* calls are never throttled, and a terminal also RESETS the throttle window so a following progress event is not suppressed by a now-irrelevant tick. The structure is what makes a terminal unswallowable — `throttled` is true only on the progress path, and terminals take the other branch — rather than a timing exemption someone can get wrong later.

WHAT THIS DOES NOT MEAN: it is not a claim that every index WORK change is announced. It covers every change to the index STATE CELL. An operation that does index work without touching that cell publishes nothing, which is a property of that operation and not a hole in this rule.
