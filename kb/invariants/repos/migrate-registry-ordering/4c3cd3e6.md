# knomit migrate-registry must never store.Open a legacy repo database before its origin is captured — store.Open runs migration 000017, which irrecoverably drops the columns being read

Migration `000017_remotes_drop_connection` rewrites the `remotes` table (via the `legacy_alter_table` table-rebuild idiom, not `ALTER TABLE ... DROP COLUMN`, because DROP COLUMN re-prepares every trigger including one that fails mid-migration) and its `.down.sql` says explicitly the four connection columns — `url`, `branch`, `auth_method`, `auth_token` — are NOT recoverable afterwards. `store.Open` unconditionally runs `migrate.All` on whatever database it opens.

**The invariant:** `cmd/migrate_registry.go` (`knomit migrate-registry`, the one-shot tool that converts a pre-registry home) must read every legacy repo database's remote connection config using a RAW `sql.Open` handle (`openRaw`, mode=ro, stock `mattn/go-sqlite3` driver, no migrations) and commit it into control.db's `repo_origins` table BEFORE that same database is ever opened through `store.Open`. Reading the root commit for the duplicate-identity survey goes through `storegit.NewStorer` (go-git's storage interface over the raw `*sql.DB`) for the same reason — it applies no migrations either.

**Why this is unrecoverable, not just untidy:** if the tool (or a future 'simplification') called `store.Open` on a legacy repo database to read its origin, migration 000017 would run as a side effect of the open and destroy the very row being read — the user's remote URL and encrypted credential are gone with no undo, and the tool has no way to detect this happened until the origin is already missing from the plan.

**How the tool structurally prevents this:** `migrateRepoDatabases` (which calls `store.Open`, and is the ONLY place in the whole tool that may) is documented and enforced by ordering as the LAST step of `runMigrateRegistry` — it runs only after `applyControlDB` has already committed every captured origin into `repo_origins` inside one transaction, and after `moveRepoFiles` has renamed the databases to their new `repos/<uid>.db` paths. The package doc comment on cmd/migrate_registry.go spells this out as "THE ORDERING INVARIANT" and warns explicitly against 'simplifying' the read paths to `store.Open`.

**Consequence for future maintenance:** any new read this tool needs from a not-yet-migrated legacy repo database must go through `openRaw` or `storegit.NewStorer`, never `store.Open`, until after `applyControlDB` has committed. Getting this backwards is a silent, irreversible data-loss bug that would only surface as users reporting their sync credentials and remote URLs vanished after running the migration tool.
