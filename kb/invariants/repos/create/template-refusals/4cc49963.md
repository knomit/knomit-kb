# A template is refused, by named error and before anything is written, unless: kebab name; source an ACTIVE mounted repo; folder present at the source's consensus tip; only README.md and .knomit/** inside; plain 100644 files only; at most 256 files and 4 MiB; .knomit/ontology.yaml parses as a NEW ontology; no preset id unless it IS that preset; at most one describing fact; and never the reserved fleet ontology id (ErrFleetOntologyReserved, 422, in every template mode)

Each rule and its sentinel (internal/corpus/repos/template.go, internal/engine/store/facts/templates.go): name not kebab-case → ErrTemplateName (400); `template.repo` unknown, archived or a lens name → ErrTemplateSourceNotFound (404); source mounted but its store not open (populating, closing) → ErrTemplateSourceUnavailable (503); no folder at the source's consensus tip, no consensus branch yet, or a describing fact with no folder → ErrTemplateNotFound (404); any path other than README.md and .knomit/**, or two paths equal under lowercasing → ErrTemplateLayout; a symlink, submodule or EXECUTABLE (100755) file → ErrTemplateNotRegular; more than 256 files or 4 MiB → ErrTemplateTooLarge; no .knomit/ontology.yaml → ErrTemplateNoOntology; ontology not valid under ParseNewOntology → ErrTemplateOntology; ontology id of an embedded preset while `refreshDivergence(o, preset) != ""` (the boot refresh's own test) → ErrTemplatePresetID; two `part: template` facts for one name → ErrTemplateDescribedTwice; these seven (ErrTemplateLayout, ErrTemplateNotRegular, ErrTemplateTooLarge, ErrTemplateNoOntology, ErrTemplateOntology, ErrTemplatePresetID, ErrTemplateDescribedTwice) are 422 "Template invalid". A template whose ontology id is `fleet`, in EVERY template mode (template and initialize), → ErrFleetOntologyReserved (422 "Fleet ontology reserved"), raised by ResolveTemplate right after ParseNewOntology: the same sentinel and status every other generic door uses (see the baked-ontology reserved-id invariant). Missing `template.repo`/`template.name` or a template on a mode that refuses it → ErrInvalidName (400).

SINCE PR #520 (verified at merge commit 1a6c03f7) the fleet is not a template, so the earlier fleet-only arms are GONE: ErrTemplateFleetLocal (409 "Fleet template needs initialize"), ErrTemplateFleetPresent (409 "Fleet already present"), ErrTemplateFleetStateUnavailable (503 "Fleet state unavailable"), checkTemplateMode, and its fail-closed fleet-state read. No template path accepts a fleet-id ontology, so nothing in this fact depends on the instance's fleet state. WHY: a template is a user-editable copy and the fleet must not be one (kb/decisions/fleet/baked-into-product/e8e9a852.md). If a playbooks pin older than the fleet-template removal is mounted, its fleet template is still LISTED by ListTemplates and refused at create with the reserved-id error.

Every refusal happens before any repo file exists; CreatePreflight returns it before the 202 and Create re-checks it, and a create that fails later is rolled back by Create's cleanup (no .db/-wal/-shm, no registry row): TestCreateFromTemplate_Refusals asserts both for every row, including the fleet row (ErrFleetOntologyReserved). Since the #433 follow-up every rule is pinned by a sabotage: the `not-new` row's fixture is accepted by ParseOntology and refused by ParseNewOntology; the limits are inclusive (exactly 256 files / 4 MiB accepted, TestTemplateFilesAt_LimitBoundaries).

PRESET IDENTITY IS refreshDivergence, NOT SubsetDivergence (user ruling). The two differ only when the PRESET declares a root attribute the template lacks (refreshDivergence is SubsetDivergence plus RootAttributesEqual), and no embedded preset declares one today, so no real template can tell them apart. ResolveTemplate therefore reads the preset through the package variable templatePresetByID (= fact.EmbeddedPresetByID, which now knows only default and code), and TestCreateFromTemplate_PresetIdentityIsTheRefreshRule stands in a preset WITH a root attribute. CONSEQUENCE: do not inline fact.EmbeddedPresetByID back into ResolveTemplate; the test would lose its only handle on the rule.

MISREADING: 'regular files only' here excludes the executable mode too, so a copy never silently changes a file's mode; and a fact WITHOUT a folder is refused, while a folder WITHOUT a fact is creatable by name (it is only not listed).
