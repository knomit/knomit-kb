# Archiving a repo drops its stored-secret link (origin kept with auth_method none); restoring a repo with an origin over the API needs exactly one credential choice (Manager.RestoreWith)

Manager.archive (internal/corpus/repos/lifecycle.go), after unmounting, unlinks an origin linked to a stored secret with Origins.SetCredential(uid, url, "none", "", ""): URL, branch and Mode are kept, and the archived repo no longer counts in the secret's linked_repos, so it never blocks Secrets.Delete. A failed unlink is only logged (the archive stands). An archived repo with a PASTED token keeps it.

Restore: POST /archived/{id}/restore calls Manager.RestoreWith with a RestoreCredential that must hold exactly one of SecretID (admin; must fit the origin URL, 422), a pasted credential (AuthMethod plus token, operator; MethodMismatch-checked) or None; no choice or several is ErrCredentialChoiceRequired (400), and a secret or pasted credential for a repo with NO origin is ErrNoOriginForCredential (400). A cert (fleet peer) origin takes only None, which keeps cert. The credential is written (SetCredential, with the in-transaction host check) after the state flip and BEFORE the mount, so the first sync round uses it; a refused mount puts the previous credential back and re-archives.

Consequence for callers: RestoreWith(uid, name, nil) keeps whatever credential is stored, which after an archive of a linked repo means anonymous; only tests pass nil, the API always passes a choice. There is no Manager.Restore. Misreading to avoid: 'archive unlinks' does NOT mean archive clears pasted tokens, and 'restore needs a choice' does NOT apply to a repo without an origin (an empty body restores it).
