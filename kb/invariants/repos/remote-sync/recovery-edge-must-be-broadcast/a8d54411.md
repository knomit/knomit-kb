# A remote status that goes error→ok MUST broadcast sync_ok/push_ok even when nothing moved — the UI banner has no other way down

The reconcile loop (runReconcileLoop.doTick, internal/repos/sync.go) used to broadcast `sync_ok` only when `mainChanged || agentChanged`, and `push_ok` only when `pushResult.Pushed`. Both are one-shot SSE events that are never replayed. The web client raises its remote-error banner on `sync_error`/`push_error` and lowers it on a clean remote event.

Consequence: a transient outage (DNS blip, expired-then-refreshed token) that healed on a tick with nothing to pull or push emitted NO event, so the banner stayed up for the life of the window — while `remotes.last_status` in SQLite already read `ok`. Observed 2026-08-04: desktop window showing "Remote sync failed — dial tcp: lookup github.com: no such host" hours after `select last_status from remotes` returned `ok`. A freshly loaded web tab looked fine, because a fresh client starts with no banner — which is exactly why this reads as "the desktop is broken" rather than "the event is missing".

RULE: any tick that ends in success while the PERSISTED prior status was `error` must broadcast, regardless of whether anything moved. The edge is computed from `fresh.LastStatus` / `fresh.LastPushStatus` snapshotted BEFORE Sync/Push run (their deferred `updateRemoteStatus` overwrites the column on the way out), NOT from the loop's in-memory `syncFails`/`pushFails` counters — those start at zero after a server restart, where the recorded status is still `error`. See `shouldBroadcastSyncOK` / `shouldBroadcastPushOK` / `remoteStatusIsError`.

WHAT THIS DOES NOT MEAN: it is not "broadcast sync_ok on every successful tick". A steady-state tick with nothing to do and no prior failure stays silent — that quiet is deliberate, and the recovery edge fires at most once per outage because Sync/Push write `ok` unconditionally on success.

SECOND RULE, on the client side: a remote has TWO halves that fail independently, and every event speaks for exactly ONE of them. `sync_*` reports the fetch/reconcile half (`remotes.last_status`), `push_*` the push half (`last_push_status`). The client keeps them apart — `state.remoteSyncError` / `state.remotePushError`, read through the `remoteErrorText` selector, never directly — and each event updates only its own side. Clearing both on any clean event was a real bug: `sync_ok` is broadcast on every tick that pulls anything, so with an expired push token it lowered the banner and the next failing push tick raised it again, blinking once per reconcile interval for as long as the token stayed dead. The user-facing dismiss is the one action that clears both, because there is one banner and no way to acknowledge half of it.

Why the split matters beyond that flap: each event maps 1:1 onto the column Sync/Push just wrote, so a side-scoped event handler is the INCREMENTAL form of exactly what the persisted-status poll reads WHOLESALE. The two paths then agree by construction. With one shared string they could not: the poll ORs both columns while a single `sync_ok` cleared everything, so poll and events reported opposite things about the same remote.

The same shape is a general trap: any UI latch raised by a one-shot event needs BOTH a broadcast recovery edge and a poll-able source of truth — and if the latch stands for more than one underlying condition, it must be decomposed to match, or the two paths will disagree. Both were done here — the client also re-reads `GET /origin` on repo switch, on SSE reconnect, when the repo manager closes, and once a minute while a failure is on screen, clearing a side when that read says ok (or reports no remote at all) and leaving the banner untouched when the read itself fails.
