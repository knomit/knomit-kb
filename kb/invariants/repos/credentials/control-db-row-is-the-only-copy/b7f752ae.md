# A served repo's control.db row holds the ONLY copy of its origin credential — no path may delete a source row after a failed copy

Since the boot gate guarantees a SERVED repo's store has empty auth columns, that repo's credential exists in exactly one place: its control.db row. There is no second copy anywhere on disk. Two consequences a consumer must act on.

**1. No path may delete a source row after a failed credential copy.** `RepoRegistry.CopyCredential` returns `nil` SILENTLY when its source row is missing, so it must run BEFORE `DeleteActive` (Archive) and BEFORE `DeleteArchive` (Restore) — and if it FAILS, the delete must not happen at all. Archive aborts via its rollback; Restore keeps the archive row and logs at ERROR, because it has nothing to roll back into by that point (the db has moved, `m.Add` has run, the active row is written). Deleting the source anyway destroys the credential permanently with a WARN as the only record — which is what the code did before PR #65's final review caught it.

**2. Ordering inside any credential move is decrypt → write the destination → clear the source.** Interrupted anywhere, the original still exists and the next attempt retries from a clean state. `migrateCredential` follows this: it reads via `LegacyAuth`, writes control.db, and only then calls `ClearAuth`.

**The foreseeable misreading:** that this is about archive bookkeeping tidiness. It is not — it is about a secret with no other copy. A failure here is not recoverable by re-running the operation, because a fresh archive/restore round trip copies active→new-archive then new-archive→active, reading the now-EMPTY active row and never reaching the surviving one. The only remedies are re-authenticating the origin or copying the row by hand in sqlite3.

**Not implied:** this does not mean credential writes must be transactional with the row moves. Best-effort plus "never delete the source on failure" is the chosen shape, because availability of the repo matters more than its credential bookkeeping and the operator can re-authenticate.
