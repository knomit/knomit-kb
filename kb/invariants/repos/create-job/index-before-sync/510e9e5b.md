# Manager.Create narrates the index BEFORE it emits the `sync` step and calls ActivateSync — ActivateSync's synchronous reconcile takes lockBranch(upstream), the lock the background heal holds for the whole index, so sync-first parks the job at "activating sync" for the entire index; CREATE_STEPS in the UI mirrors that order and must list index before sync for every remote mode

In Manager.Create (internal/repos/lifecycle.go), after m.Add the order is: mirrorIndexing(ctx, ri, emit) FIRST, then emit(Step:"sync", Pct: indexPctCeil, IndexState carried forward) and ri.ActivateSync, then the terminal "done" event. The order is load-bearing, not cosmetic. ActivateSync (repoBuilder.startSync, builder.go) runs ONE synchronous Remote().Sync, whose reconcileNow takes lockBranch(upstreamMain) (internal/store/remote_sync.go). openOne starts the background index heal at m.Add, and the heal holds that same branch lock for as long as it indexes the branch (Rebuild self-locks; see the branch-locking invariant). With sync emitted first, the create job reported "95% activating sync" for the whole index while the repo was visibly already indexing — the incident behind PR #230 (a subscribe of knomit-kb sat on "Activating sync" until a page refresh showed the repo indexing). This is a DIFFERENT failure from the clone-create-index-stuck-indexing incident: there ActivateSync cancelled the heal; here the heal is intact and ActivateSync merely waits on its lock, so the job's narration is wrong, not the index. Consequences for consumers: (1) CREATE_STEPS in web/src/CreateProgress.tsx is a mirror of the emit order and must list 'index' before 'sync' for clone, initialize and subscribe — a mirror that disagrees is how the wizard lies about the phase; (2) the sync event carries Pct = indexPctCeil (99), not 95, so the bar never steps backwards after the index band; (3) a job whose context is already cancelled when mirrorIndexing returns SKIPS ActivateSync entirely (see the cancel-during-index gotcha) — otherwise the delete cannot start until the index finishes. What this does NOT mean: it does not remove the heal's own activate() → startSyncLoops path; that still starts the loops after the index, and ActivateSync after it restarts them (syncCancel + syncWg.Wait under syncLoopMu). Enforcing tests: TestCreate_SubscribeNarratesTransferAndIndexPhases asserts the last index-phase event precedes the sync step and the sync step precedes done, with Pct non-decreasing; CreateProgress.test.tsx asserts the UI list order per mode.
