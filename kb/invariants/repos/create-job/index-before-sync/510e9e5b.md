# A sync round takes lockBranch(upstream), which the index heal holds while indexing that branch, so the round waits behind it — background on background, harmless; foreground events that would exit Sync (Attach/Detach/Swap) are refused while the index job runs, so the driver never waits on that lock

Rewritten for issue #411. The create-job ordering this fact used to pin (narrate the index, THEN emit `sync` and call ActivateSync) is gone with ActivateSync: Sync is a stage of the mount walk and starts right after Index launches its job, so CREATE_STEPS in web/src/CreateProgress.tsx has NO sync step for any mode, and the create job only observes the index.

THE CONTENTION THAT REMAINS. Sync's first round (and every round) reconciles the upstream under lockBranch(upstreamMain) (internal/store/remote_sync.go). The Index job holds that same lock for as long as it rebuilds the branch (Rebuild self-locks; kb/invariants/store/index/branch-locking). So on a fresh clone the first sync round parks behind the index. That is background waiting on background: nothing the user is looking at waits, and the round proceeds when the branch is done.

WHY IT NEVER REACHES THE FOREGROUND. Every event that would exit Sync while the index runs — AttachOrigin, DetachOrigin (restart Sync) and SwapStore (rewinds to Populate, a no-op there under mount mode none, so Open and everything above re-enter) — is refused with ErrIndexing before its guard runs (kb/decisions/repos/lifecycle/indexing-exclusive-with-attach-detach-swap). Exits that cannot be refused cannot park the driver behind it either: Unmount cancels all affected lives before draining any (kb/invariants/repos/lifecycle/exit-cancels-all-then-drains), so the index job returns at its next batch boundary and releases the lock the parked round needs; a crash restart drains in a waiter goroutine, never in the driver; Rebuild and CancelIndex exit only Index.

Incident history: PR #586 (see STAGE ENTER IS THE DRIVER TOO below) and PR #230 — the create job sat on '95% activating sync' for a whole index because ActivateSync's synchronous reconcile parked on this lock.

Misreading: this does not mean sync is delayed until the index is ready in general — only rounds that touch a branch the index job currently holds wait.

STAGE ENTER IS THE DRIVER TOO (PR #586, re-read at 8a96c89b). "The driver never waits on that lock" covers stage ENTER as well as exits. A stage Enter runs on the driver goroutine; it MUST NOT take lockBranch on any branch the Index job may hold, because Rebuild self-locks for its whole duration and lockBranch is not ctx-aware. syncStage.Enter broke this from #411 until #586 by calling ensureLocalUpstream inline: remotesync.Index.EnsureLocalUpstream takes lockBranch(upstream) BEFORE it checks whether the ref exists, so even its common no-op case waited for a whole Rebuild of that branch (kb/incidents/repos/create-job/sync-enter-parks-on-index-lock). The repair now runs on the Sync life's goroutine just before the loop's first round (inline on the driver only under Options.Synchronous). Regression: TestCreate_StageEnterDoesNotParkBehindTheIndexRebuild (internal/repos/stage_enter_index_lock_test.go) holds the driver at Serve's Enter while Rebuild holds the lock, so it covers Serve.Enter and Sync.Enter; it does not cover the stages entered before Index. Ordering against the first sync round is pinned by TestOpen_BootstrapsAMissingLocalUpstreamFromOrigin and its _Background variant (sync_local_test.go).

The one stage Enter that does take the lock: Identify.Enter reaches svc.Facts().WriteFact on the read branch (the ontology refresh in loadOntology, and the fleet-master refresh), which takes lockBranch on the driver. That is safe ONLY because Identify is entered after exitStages has cancelled and drained Index and Sync, the long-running lock holders; at that point only short foreground writers can hold the lock.

Misreadings. (a) "A stage Enter may take lockBranch as long as the call is quick" is FALSE: how long the call holds the lock is irrelevant, the question is who else may be holding it. (b) "It is a no-op when the ref exists, so it is harmless" is FALSE: EnsureLocalUpstream locks first, so the no-op still waits.
