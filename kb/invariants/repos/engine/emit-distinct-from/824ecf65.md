# Every fact the reasoning engine writes (EMIT's answer, GAP's hypothesis) passes distinct_from naming every fact the run JUDGED and does not cite (above all the contradictions its body names as weighed against), never a fact whose judgment failed, a retracted one, one in another mount, or a hypothesis

engine_reason.js distinctFrom(refs), used by answerFact (EMIT) and GAP since local commit 20434db7 on feat/expert-eval-runner. The list is every fact in the run's read order that (1) the run judged, meaning its relevance label is yes or no from a judgment that did not fail, (2) the written fact does not cite, (3) still exists on the branch (not retracted), (4) is a local path, and (5) is not a hypothesis or a signal.

Why: a contradicting fact is never in an answer's refs (refs are why we believe it); the answer NAMES it in its body ("Weighed against (and outweighed)"). It shares the answer's subject by construction, so knomit_learn's same-subject gate (similarity in the model's band plus a shared non-generic entity) refused the answer as a duplicate of the very fact it outweighs. That was review cause Z2: on the F7 pilot the refusal came at similarity 0.71, and the run ended in a gap. A gap's hypothesis has the same shape: f04-code-service-1d6a q2's hypothesis was refused against an observation the run had judged not relevant ("same subject, different claim"). A judgment of `no` is exactly the assertion distinct_from makes, so the rule covers every judged fact, not only the contradictions.

Consequence: when you add a new write to the engine, pass distinctFrom(refs) too. When you change what the engine names in a body (weighed against, abandoned lines, unjudged facts), check those facts are judged facts, so they land in the list.

What this does NOT mean: it does not bypass the gate for facts the run never judged, or for a fact whose judgment failed (a failed judgment blocks the write anyway, B4). It does not name hypotheses, because a write that matches a live hypothesis settles it in the same commit and distinct_from would stop that merge. It is not stored on the fact (distinct_from is request-only). Pinned by TestEngineEval_Z1Z2Z3_ContradictionIsNamedNeverCited, which runs with the gate ON (a bag-of-words embedder under the calibrated model id); sabotage: drop the distinct_from from answerFact, and the write is refused and the run ends on a gap.
