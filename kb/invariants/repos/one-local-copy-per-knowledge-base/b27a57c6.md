# repos.repo_id is unique among ACTIVE repos and MUTABLE; for a store swap the uniqueness check is the SwapStore event's guard — the one site — which reads the INCOMING store's root commit before anything is written

**The rule:** at most one ACTIVE repo may hold a given knowledge base (root-commit hash, stored as `repos.repo_id`). Enforced by a real DB constraint: `CREATE UNIQUE INDEX repos_active_repo_id ON repos(repo_id) WHERE state = 'active' AND repo_id IS NOT NULL` (internal/corpus/repos/registry.go). A violating write fails at the SQLite layer and `classifyRegistryErr` maps it onto `ErrRepoAlreadyRegistered`.

**Why:** two local copies of the same knowledge base would both write to `agent/<host>` and clobber each other on push to a shared origin. One local copy per knowledge base is enforced structurally, so nothing downstream (sync, lens membership, addressing) special-cases a duplicate.

**repo_id is MUTABLE.** The lifecycle machine's Identify stage records it (internal/corpus/repos/stages.go; since PR #682 through RepoInstance.recordIdentity, see the update below): it runs on every mount and after every SwapStore, because a disjoint-history origin connect replaces the repo's whole store and its root commit then IS the remote's. A RecordRepoID refusal there is identityConflict, a fatal Identify error: the repo becomes Unavailable rather than serving a duplicate.

**The Swap guard is the one site for a swap.** SwapStore's guard (guardSwap, internal/corpus/repos/events.go) runs before anything is exited or written: it reads the INCOMING store's root commit (inspectIncomingStore on the temp DB, on the identity branch — the read branch when none is given; it was rootCommitOfDB until #444 (merge ec3406df), which also made it refuse an incoming store whose ontology is a symlink, see kb/invariants/repos/ontology/symlinks/1ac1e8f3.md) and refuses with ErrKnowledgeBaseAlreadyLocal when HeldByAnotherActiveRepo names another active repo. The origin-session commit handler sends SwapStore and does NOT do its own root-commit check; do not add a second one there or in any new swap path — any caller that swaps a store goes through the event and so through the guard. An attach is not a swap, and since PR #676 (merge dd73ed85) it has its own one site: guardAttachIdentity, at the end of guardAttach in events.go, runs the one-local-copy check (the remote's knomit-repo-id claim, a tip another active repo holds, the remote branch's first-parent root) for EVERY AttachOrigin, and PATCH /origin/upstream runs it through Manager.CheckOriginBranch; see kb/invariants/repos/remote/attach-identity/545ae852.md. The origin-session wizard's commit handler (internal/edge/web/api/origins/handlers.go) no longer re-checks for a shared-history commit (the remote's root is then the repo's own, which this unique index already makes unreachable); the check at its /test step remains and refuses first. Do not add a second attach-time check at a handler.

**Why the guard and not the constraint:** the constraint fires at Identify, AFTER the apply has installed the new database. The swap is undoable only until the copy (applySwap: origin saved, then the copy last), so a duplicate caught by the constraint leaves the repo Unavailable on a store it should never have installed. Refusing in the guard changes nothing.

Enforcing code: internal/corpus/repos/registry.go (schema, RecordRepoID, classifyRegistryErr); internal/corpus/repos/events.go (guardSwap); internal/corpus/repos/stages.go (Identify's RecordRepoID); internal/corpus/repos/lifecycle.go (create's pre-registration duplicate checks, with RecordRepoID behind them).

UPDATE (PR #520, merge commit 1a6c03f7): guardSwap ALSO refuses, before the same point of no return, (a) a swap of the fleet repository itself (it is never connected) and (b) an incoming store whose ontology id is `fleet` (inspectIncomingStore now returns a fleet flag), both with ErrFleetOntologyReserved (REST 422). Like the symlink refusal, this keeps the guard the one site for swap preconditions: do not add a second fleet check in the origin-session handler. See kb/invariants/fleet/baked-ontology/reserved-id/4cdcf99e.md.

UPDATE (PR #682, branch fix/origin-attach-followups): the one RecordRepoID call for a mounted repo is now RepoInstance.recordIdentity (internal/corpus/repos/stages.go), with two callers that apply the same rule (root commit of the read branch): identifyStage.Enter on every mount, and reidentifyAfterRewind after a successful sync round whose consensus branch was force-updated (remotesync ModeRewound). So a replace_main attach changes repo_id on its first successful round, not at the next mount. A conflict found by that round is logged and turns the repo Unavailable only at its next Identify. Not covered: a round that replays the agent branch and then fails, and an empty repo attached to an unrelated origin (the agent branch keeps its seed root, #541). See kb/decisions/repos/identity/reidentify-after-rewind/20b0d973.md.
