# repos.repo_id is unique among ACTIVE repos and MUTABLE; for a store swap the uniqueness check is the SwapStore event's guard — the one site — which reads the INCOMING store's root commit before anything is written

**The rule:** at most one ACTIVE repo may hold a given knowledge base (root-commit hash, stored as `repos.repo_id`). Enforced by a real DB constraint: `CREATE UNIQUE INDEX repos_active_repo_id ON repos(repo_id) WHERE state = 'active' AND repo_id IS NOT NULL` (internal/repos/registry.go). A violating write fails at the SQLite layer and `classifyRegistryErr` maps it onto `ErrRepoAlreadyRegistered`.

**Why:** two local copies of the same knowledge base would both write to `agent/<host>` and clobber each other on push to a shared origin. One local copy per knowledge base is enforced structurally, so nothing downstream (sync, lens membership, addressing) special-cases a duplicate.

**repo_id is MUTABLE.** The lifecycle machine's Identify stage is the ONE RecordRepoID site (internal/repos/stages.go): it runs on every mount and after every SwapStore, because a disjoint-history origin connect replaces the repo's whole store and its root commit then IS the remote's. A RecordRepoID refusal there is identityConflict, a fatal Identify error: the repo becomes Unavailable rather than serving a duplicate.

**The Swap guard is the one site for a swap.** SwapStore's guard (guardSwap, internal/repos/events.go) runs before anything is exited or written: it reads the INCOMING store's root commit (inspectIncomingStore on the temp DB, on the identity branch — the read branch when none is given; it was rootCommitOfDB until fix/ontology-symlink-refuses-repo, commit e85a04f3, which also made it refuse an incoming store whose ontology is a symlink, see kb/invariants/repos/ontology/symlinks/1ac1e8f3.md) and refuses with ErrKnowledgeBaseAlreadyLocal when HeldByAnotherActiveRepo names another active repo. The origin-session commit handler sends SwapStore and does NOT do its own root-commit check; do not add a second one there or in any new swap path — any caller that swaps a store goes through the event and so through the guard. The shared-history commit (an AttachOrigin, not a swap) keeps a handler-side HeldByAnotherActiveRepo check on the repo's own root, because no swap guard runs for it.

**Why the guard and not the constraint:** the constraint fires at Identify, AFTER the apply has installed the new database. The swap is undoable only until the copy (applySwap: origin saved, then the copy last), so a duplicate caught by the constraint leaves the repo Unavailable on a store it should never have installed. Refusing in the guard changes nothing.

Enforcing code: internal/repos/registry.go (schema, RecordRepoID, classifyRegistryErr); internal/repos/events.go (guardSwap); internal/repos/stages.go (Identify's RecordRepoID); internal/repos/lifecycle.go (create's pre-registration duplicate checks, with RecordRepoID behind them).
