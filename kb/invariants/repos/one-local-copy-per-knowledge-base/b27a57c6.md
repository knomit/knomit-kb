# repos.repo_id is unique among ACTIVE repos and MUTABLE; every uniqueness check must fire BEFORE Manager.SwapStore, which is a point of no return

**The rule:** at most one ACTIVE repo may hold a given knowledge base (root-commit hash, stored as `repos.repo_id`). Enforced by a real DB constraint: `CREATE UNIQUE INDEX repos_active_repo_id ON repos(repo_id) WHERE state = 'active' AND repo_id IS NOT NULL` (internal/repos/registry.go). A violating write fails at the SQLite layer and `classifyRegistryErr` maps the constraint-name/message match onto `ErrRepoAlreadyRegistered`.

**Why:** two local copies of the same knowledge base would both write to `agent/<host>` and clobber each other on push to a shared origin. One local copy per knowledge base is enforced structurally, not by convention, so nothing downstream (sync, lens membership, addressing) has to special-case a duplicate.

**repo_id is MUTABLE, not assigned once at create.** `Registry.RecordRepoID(uid, repoID)` is called on every successful open (Manager.openRegistered) AND after every store swap (Manager.recordSwappedIdentity in internal/repos/swapstore.go) — never once at creation time only. The reason: a disjoint-history origin connect replaces a repo's ENTIRE git store (`Manager.SwapStore`), and after that swap the repo's root commit IS the remote's root commit. The repo's identity for uniqueness purposes literally changes underneath it.

**The trap this fact exists to prevent:** SwapStore itself does not check uniqueness before swapping — by the time `recordSwappedIdentity` runs post-swap and hits `ErrRepoAlreadyRegistered`, the old store is ALREADY GONE (closed, overwritten on disk) and the swap cannot be undone. It is logged loudly ("the pre-swap uniqueness check was skipped or raced") but not repaired. So every caller that can trigger a disjoint-history swap MUST perform its own uniqueness check strictly BEFORE calling SwapStore, using the identity the swap is ABOUT to install (the root commit of the temp/incoming store), not the repo's current one. The one shipped caller is internal/web/handlers_origin_session.go's commit-remote flow: right before `rm.SwapStore(ri, tempDBPath)` it resolves `rootCommitOfDB` on the temp DB and calls `heldByAnotherActiveRepo(rm, ri.UID(), rootCommit)`, refusing with "this remote holds the same knowledge base as the repo %q; connect aborted before any change was made" if another active repo already claims it — explicitly commented as "the LAST point at which refusing is still recoverable".

**Consequence for anyone adding a new swap path:** copying SwapStore's call site without copying its pre-check reproduces a real data-loss bug — a second active repo silently able to overwrite/orphan its own root identity with no rollback. The registry constraint alone is not a safety net here because it fires AFTER the swap, when the only options left are 'log a warning' and 'leave two repos in a state the constraint objects to at the next successful open of either'.

Enforcing code: internal/repos/registry.go (schema, RecordRepoID, classifyRegistryErr); internal/repos/swapstore.go (SwapStore, recordSwappedIdentity); internal/repos/lifecycle.go (Create's post-Add RecordRepoID call, which rolls the whole create back via m.Remove+cleanup on ErrRepoAlreadyRegistered); internal/web/handlers_origin_session.go (the pre-SwapStore heldByAnotherActiveRepo check).
