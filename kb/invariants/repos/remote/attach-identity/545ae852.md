# Every route that chooses or reads a caller-named origin requires `operator` (or is local-only), and every change of WHICH remote branch a repo follows runs the attach guard: AttachOrigin through the machine, PATCH /origin/upstream through Manager.CheckOriginBranch; create and swap have their own one-local-copy sites

RULE (PR #676, revised after review). Two halves, both load-bearing:

(1) WHO. A route that sets, re-points or removes a repo's origin, or clones, probes or previews a remote the caller names, is the host operator's:
- behind requireOperator: PUT and DELETE /repos/{repo}/origin, PATCH /origin/upstream, every /repos/{repo}/origin-sessions route (api/manage/mount.go, web/router.go), /repos:probe-origin and /repos:probe-initialized (mount.go);
- POST /repos when the body carries `origin` (modes clone, initialize, subscribe): handleHALReposCreate applies the same operator gate after decoding, because only the body tells a create with an origin from one without; a create with no origin stays `write`;
- the fleet routes that attach origins: httpx.RequireLocalVia.
Archive restore (POST /archived/{id}/restore) takes only new_name: it re-mounts the origin row stored for that uid, which an earlier (now gated) attach or create chose, so it chooses nothing and stays `write`. route_table.golden shows the route-level gate as `require`; the create gate is in the handler and pinned by TestOriginEscalation_CreateWithAnOriginNeedsTheOperator.

(2) WHAT. guardAttachIdentity (internal/corpus/repos/events.go, at the end of guardAttach) runs for EVERY AttachOrigin event (PUT /origin, the wizard's shared-history commit, the fleet move/follow/restore attaches) AND for PATCH /origin/upstream, which calls Manager.CheckOriginBranch (guardAttach outside the machine: the stored URL and credentials with the NEW branch, no event, so no indexing exclusivity and no Sync restart) before setOriginUpstream rewrites the refspec. The new branch is a new consensus branch, and the origin identity is URL-only (3b684cad), so without this a branch of the same remote holding another repo's knowledge base was adopted unchecked (review B2: reproduced, two local copies of Y). It refuses another ACTIVE repo's knowledge base (knomit-repo-id claim, an advertised tip another repo holds, or the remote branch's first-parent root), and a remote branch with no merge base with the consensus branch while that branch holds a fact, unless the event is AttachOriginReplacing (PUT body replace_main). It is the ONE one-local-copy site for an attach: the wizard's commit handler no longer re-checks (for a shared-history commit the remote's root is the repo's own, which the unique index already makes unreachable).
For PATCH, (b) compares the NEW branch with the CURRENT consensus branch, and replace_main in the PATCH body admits an unrelated one; (a) is never admitted. Note the held-tip layer judges the whole remote: once ANY advertised branch tip is held by another active repo, every attach or re-point to that remote is refused, whichever branch is named.
Paths that do NOT run it, each with its own reason:
- Create (clone, initialize, subscribe) runs the create-path layers instead (CreatePreflight's advertisement layers, then the fresh clone's root before registration; kb/decisions/repos/identity/three-layer-duplicate-refusal/2d0be18a.md). It has no unrelated-history question: there is no main to replace.
- A disjoint-history connect that replaces the whole store is SwapStore, whose guard (guardSwap) is the swap's one-local-copy site.

CONSEQUENCE: do NOT point a repo at a new origin by calling ConfigureGitRemote / Origins.Set / Remote().SetOrigin from a handler; send AttachOrigin (or SwapStore). Do not add a route that chooses or reads a caller-named origin outside requireOperator or RequireLocalVia. Re-derive the route list from route_table.golden and the create handler rather than trusting this one.

MISREADINGS: 'every origin change passes guardAttachIdentity': every change of the followed remote branch does (attach and PATCH upstream); create and swap use their own sites (above); DELETE removes an origin and needs none. '3a19b2d3 covers any branch of the chosen remote': no, it trusts the chosen origin's MAIN as fetched; a new branch is vetted. 'The operator gate makes the identity check redundant': no, it also stops the operator silently importing another local repo's knowledge base and clobbering its agent branch on the shared origin. 'guardAttachIdentity judges the origin on every sync': no, only at attach (#524 trust). 'An unreadable remote passes': no, an identity read that fails or exceeds [git].max_probe_bytes refuses the attach. 'A collection-audience token may pick origins at create because it reads every repo': no, it reads every REGISTERED repo, not an unregistered knowledge base under local_origin_root (review B1).

FOLLOW-UPS CLOSED BY PR #682 (merge b038ab37 on dev, re-read there; src refs re-pinned to it):
- PATCH /origin/upstream FAILS CLOSED and is a compare-and-set. With no origin it answers 409 "No origin"; when the stored origin cannot be read it answers 503 "Repo not ready" or 500 "Failed to get origin"; it no longer skips CheckOriginBranch and falls through. The new branch lands only on the URL the guard vetted (Origins.SetBranch(uid, url, branch), `WHERE url = ?` in the same UPDATE); otherwise 409 "Origin changed" and the git remote follows what control.db records. See kb/invariants/repos/remote/upstream-change/6a1447e1.md.

- Re-identify after replace_main: the sync round that force-updated the consensus branch records the read branch's new root at once (reidentifyAfterRewind), so HeldByAnotherActiveRepo names the repo for the origin's knowledge base from that round, not at its next mount.
