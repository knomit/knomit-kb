# An origin stored with method cert is ALWAYS served by the fleet transport or fails with a named error before any dial: not enrolled is ErrNotEnrolled, unusable pki files are an error, and nothing ever falls back to plain https, an unverified client or a forge credential

KEYED ON THE STORED METHOD (PR #526, merge 0488c05d): 'a fleet origin' below means an origin STORED with auth method cert, which ResolveOrigin set once when the origin was entered (an https URL that pki.ClassifyOrigin judged a peer). Users never type knomit+https any more; it is the internal go-git scheme that only pki.GitURL and the derived .git/config spell, and a typed or stored knomit+https URL is refused (kb/decisions/repos/remote/plain-https-origins/07cc1cef.md, kb/invariants/repos/remote/classification/9b2868e5.md).

The HTTPS twin of kb/invariants/repos/remote/ssh-host-key-verification (which forbids falling back to InsecureIgnoreHostKey).

THE RULE, in full:
1. The scheme is ALWAYS registered. `app.New` calls `pki.InstallGitTransport(cfg.TLS.Dir, keyPath)` whether or not the instance is enrolled, before repos.New and Manager.Start. That covers both boot paths, since the desktop also calls app.New. Without the registration go-git would answer 'unsupported scheme', a different failure, and a later edit could 'fix' that by mapping the scheme onto plain https.
2. The client is resolved at EACH session from the files under [tls].dir. No instance.crt means `ErrNotEnrolled`, with no connection attempted (TestGitTransport_NotEnrolledFailsNamedWithoutConnecting uses a listener that records any accept). A certificate without its root or CRL, or for another key, is an error, also before any dial. There is never a transport that connects without pki.ClientConfig's verifier.
3. Enrolment after boot needs no restart. The source rebuilds when the instance.crt, root.crt or crl.pem bytes change, and a rebuild closes the old client's idle connections.
4. No forge credential reaches a peer, through four layers, any one of which suffices: (1) remoteAuthFromRecord gives an origin stored with method cert nothing from the global [remote] config (keyed on the stored method, never the URL); (2) ResolveOrigin refuses a credential typed for a peer (ErrPeerCredential) and cert as an input (ErrCertNotAnInput), so a forge token is never stored beside a peer URL; (3) the transport refuses a non-nil go-git AuthMethod and URL userinfo; and (4) the transport hands go-git nil auth. (Before #526 layer 2 was 'resolveAuthWithOrigin forces cert from the URL and errors on an explicit token/basic'; resolveAuthWithOrigin now only maps the stored method through pki.GitURL and refuses the internal scheme.) The cmd e2e asserts no Authorization header on the TLS listener.
5. go-git's TLS options (ClientCert, ClientKey, CABundle, InsecureSkipTLS) and proxies are REFUSED on this scheme, because go-git would otherwise clone the http.Transport and edit its tls.Config.

CONSEQUENCE for anyone touching it: do not add a 'not enrolled yet, try plain https' path, do not map knomit+https onto https in the URL layer, do not re-classify a stored cert origin (only pki.GitURL maps a cert origin to the internal scheme; nothing re-decides it, and a classification error is never 'not a peer'), and do not return a transport from a failed source. Each of these turns a named failure into an anonymous or unverified fetch.

MISREADING TO AVOID: 'always registered' does not mean 'always works'. It means the failure is always OURS and always named. Also, 'the fleet port needs no network boundary' is about authentication only; revocation is checked at the handshake, so a kept-alive connection outlives it until the server's idle timeout (a known phase 2 server-side gap, tracked separately).
