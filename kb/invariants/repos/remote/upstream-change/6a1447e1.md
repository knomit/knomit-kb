# PATCH /origin/upstream fails closed and applies the new branch only to the origin URL its guard vetted: Origins.SetBranch is a compare-and-set on the url in the one UPDATE that makes the change, and a refused change restores the git remote to what control.db now records

RULE (PR #682, merge b038ab37 on dev, re-read there; follow-up to the PR #676 review round 3, section 2). Three parts, all load-bearing:

(1) FAIL CLOSED. handleHALSetOriginUpstream (internal/edge/web/api/manage/handlers_origin_hal.go) reads the stored origin BEFORE the branch guard (Manager.CheckOriginBranch) and refuses when it cannot vet: store unavailable -> 503 "Repo not ready" (httpx.WriteStoreUnavailable); any other read error -> 500 "Failed to get origin" (PUT /origin's mapping); no origin -> 409 "No origin". It used to skip the guard on any of these and fall through to setOriginUpstream, which re-read the origin and could find one a concurrent PUT had just attached, and re-point it unvetted. A stopped manager is still checked first and answers 500 "Failed to set upstream branch" with ErrManagerStopped's text, as before.

(2) COMPARE-AND-SET. setOriginUpstream takes vettedURL, the URL CheckOriginBranch judged. control.Origins.SetBranch(uid, url, branch) runs `UPDATE repo_origins SET branch = ? WHERE repo_uid = ? AND url = ?`; zero rows is control.ErrOriginChanged, mapped to 409 "Origin changed" (nothing changed; read the origin and retry). It is the ONE check: an earlier draft also compared the URL the WithRead closure read, but sabotage showed it never decided anything the UPDATE did not (the closure reads the injected origin, which an attach updates last), so it was removed.

(3) RESTORE TO THE WINNER. setOriginUpstream rewrites the git refspec BEFORE the control.db write (its inherited ordering), so a refused write must put the git remote back. On ErrOriginChanged another write won, and control.db records it, so the git remote is restored to control.db's current origin (recordedOrigin), or removed when there is none (a detach won). Restoring the closure's stale read instead would leave the git remote on the old URL after the attach stored a new one. Any other SetBranch failure still restores the read origin.

CONSEQUENCE: a new caller of Origins.SetBranch must pass the URL it vetted (or read) and treat ErrOriginChanged as 'someone else changed the origin', not as a missing row to create. Do not reintroduce a fall-through when the origin cannot be read.

MISREADING: 'PATCH and PUT are now serialised': no; there is no lock between setOriginUpstream and applyAttach. The compare-and-set makes the branch land only on the vetted URL and the restore makes the git remote follow control.db afterwards; a git-config write by an attach that has not yet reached its control.db write can still be overwritten by PATCH's refspec rewrite in that narrow window (the attach's own later steps do not rewrite git config), which is an open residual, operator-only (both routes need operator). It lasts until the next mount: control.db and the injected origin then say R2 while the git config says R1, and FetchOrigin uses the git config URL, but Open re-derives the git remote from control.db at every mount, so it self-heals at restart. A per-repo origin-change mutex shared by applyAttach, applyDetach and setOriginUpstream would close it (PR #682 review N4, follow-up).

PINNED BY (sabotage at branch commit aa99192d, each red alone; the merged tree equals the PR head for every Go file): drop `AND url = ?` -> TestOrigins_SetBranchRefusesAChangedURL (control) + TestSetOriginUpstream_AppliesOnlyToTheVettedURL (manage); restore the stale read -> TestSetOriginUpstream_AppliesOnlyToTheVettedURL step 2; drop the handler's no-origin case -> TestPatchOriginUpstream_NoOriginIsRejected; drop the handler's store-unavailable case -> TestHandleHALSetOriginUpstream_StorelessRepoIs503.
