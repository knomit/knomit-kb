# Every clone/fetch path MUST gate filesystem origins via validateLocalOrigin — no trusted exemption

Any code path that clones or fetches from an origin URL MUST gate filesystem origins through repos.validateLocalOrigin(url, cfg.LocalOriginRoot) BEFORE touching the path. A filesystem origin (bare absolute path or file:// URL — classified by go-git's transport.NewEndpoint, where Protocol=="file") is permitted ONLY when it resolves (symlink-resolved, longest-existing-prefix) inside config.LocalOriginRoot. An empty LocalOriginRoot DISABLES filesystem origins entirely. The policy is ABSOLUTE: there is NO trusted exemption — not the operator's cfg.Git.Origin, not the background sync loop. Network origins (https/ssh/git/scp-style) pass through untouched.

WHY load-bearing: without the gate, a web/API caller could steer the server to clone an arbitrary repo off its own disk. The gate uses the SAME transport.NewEndpoint that go-git's cloner uses, so its classification can never diverge from what is actually cloned (verified against go-git v5.18.0).

Current enforcement points — when you add a NEW origin entry point, you MUST add the gate to it too: (1) Manager.ResolveAuth — immediate clones (repo create via initClone, origin-session /test); (2) Manager.ValidateLocalOrigin — write-time for the deferred PUT /origin path; (3) repoBuilder.initDefaultGit — first-boot clone of the config origin (HARD-FAILS startup, fail-closed); (4) repoBuilder.recoverFromOrigin — startup reconcile (LOG-AND-SKIP, fail-open); (5) runReconcileLoop.doTick — re-checked EVERY tick (policy/symlink can change after write). Boot fails closed (a forbidden first-run clone should never happen); runtime fails open (a config tightening must not tear down an already-serving repo).
