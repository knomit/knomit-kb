# Every clone/fetch path MUST gate filesystem origins via validateLocalOrigin — no trusted exemption

Any code path that clones or fetches from an origin URL MUST gate filesystem origins through `repos.validateLocalOrigin(url, cfg.LocalOriginRoot)` BEFORE touching the path. Classification is NOT a syntactic check for "absolute path or file:// URL" — it is delegated wholesale to go-git's `transport.NewEndpoint`, and ANY endpoint whose `Protocol == "file"` is a filesystem origin (`internal/repos/origin.go`, `localOriginPath`). A filesystem origin is permitted ONLY when it resolves (symlink-resolved, longest-existing-prefix) inside `config.LocalOriginRoot`. An empty `LocalOriginRoot` DISABLES filesystem origins entirely, and empty is the DEFAULT (`internal/config/config.go` assigns no default; `TestLoad_LocalOriginRootEnvOverride` asserts the zero value). The policy is ABSOLUTE: there is NO trusted exemption — not an operator-configured origin, not the background sync loop. Network origins (https/ssh/git/scp-style) pass through untouched.

**WHY load-bearing:** without the gate, a web/API caller could steer the server to clone an arbitrary repo off its own disk. The gate uses the SAME `transport.NewEndpoint` that go-git's cloner uses, so its classification can never diverge from what is actually cloned (verified against go-git v5.18.0).

**Current enforcement points — FIVE, verified by grepping every production call site at commit 4baae4ed.** When you add a NEW origin entry point you MUST add the gate to it too; re-derive this list by grep rather than trusting the count here.

1. `Manager.ResolveAuth` (`manager.go:104`) — gates FIRST, before any auth resolution, covering immediate clones (repo create via `initClone` in lifecycle.go, origin-session /test).
2. `Manager.ValidateLocalOrigin` (`origin.go:96`), called by `handlers_origin_hal.go:448` — write-time for the deferred PUT /origin path.
3. `repoBuilder.build`'s sync-activation path (`builder.go:593`) — re-asserts the policy before the synchronous reconcile and BEFORE tearing anything down, so a now-forbidden stored origin is rejected without orphaning a running loop.
4. `repoBuilder.recoverFromOrigin` (`builder.go:718`) — startup reconcile (LOG-AND-SKIP, fail-open).
5. `runReconcileLoop` (`sync.go:144`) — re-checked EVERY tick.

Runtime fails open: a config tightening must not tear down an already-serving repo.

**WHAT THIS DOES NOT MEAN (misreadings verified false at HEAD, 2026-08-12):**

1. "There are six gates, one of them `initDefaultGit`, and boot fails closed." FALSE at HEAD — this fact said so until this audit. `repoBuilder.initDefaultGit` NO LONGER EXISTS, and neither does the thing it gated: there is no `cfg.Git.Origin` field in `internal/config` at all, so there is no first-boot clone of a configured origin to fail closed on. Origins are attached PER-REPO (`CreateSpec.Origin`) or afterwards. Do not go looking for `initDefaultGit`, and do not read its absence as a gate that went missing — the entry point was removed with the feature. See [[no-default-repo]] (kb/invariants/repos/no-default-repo/1fd5dad8.md).
2. "A local origin means a bare absolute path or a file:// URL, so a RELATIVE path is not one and slips through as a network origin." FALSE — and this is the most dangerous compression, because it invites treating '../../etc/repo' as unvetted-but-harmless. `localOriginPath` delegates to `transport.NewEndpoint`, which treats EVERY string that is neither a `scheme://` URL nor an scp-style `host:path` as a local file path and runs `filepath.Abs` on it. Relative paths are therefore classified as file origins and ARE gated (origin.go's comment names this the closed "relative-path hole"). Never enumerate the local-origin syntaxes yourself; ask `transport.NewEndpoint`. The one string that does pass ungated is an UNPARSEABLE endpoint — `localOriginPath` returns `("", false)` deliberately, leaving the error to the downstream clone rather than silently blessing it as a network origin.
3. "The gate protects the clone, so the clone primitives are safe to call." FALSE. `store.Service.CloneFrom` (`internal/store/repo.go`) and `remoteIndex.Sync` (`internal/store/remote_sync.go`, which runs the FetchContext) perform ZERO origin validation — the entire gate lives UPSTREAM of them, in `internal/repos` and the web origin handler. `handlers_origin_session`'s CloneFrom call is safe only because `ResolveAuth` ran earlier in the same handler. The convenient bypass: a local path needs no credentials, so a new caller that reasonably skips auth resolution also skips the ONLY gate on that path and reaches go-git's file transport ungated. If you call `CloneFrom` or `Remote().Sync` from a new site, gate the URL explicitly — do not infer coverage from the store layer.
4. "Passing validateLocalOrigin means the path is safe to clone." FALSE — a residual TOCTOU window remains: the path can be re-pointed between the check and the clone (origin.go documents this). Symlink resolution closes only the STATIC symlink hole (`TestValidateLocalOrigin_SymlinkEscape`). This is why the reconcile loop re-checks on EVERY tick and build's activation path re-asserts — those re-checks are the mitigation, not redundant belt-and-braces, so do not "optimize" them into a single validation at write time.
5. "Origins are gated, so this is a general defense against being steered at an arbitrary repo." FALSE — it is exclusively a local-FILESYSTEM control. `validateLocalOrigin` returns nil immediately for every non-file protocol, so an https:// origin aimed at an internal host is not filtered here at all. Do not cite this invariant as SSRF coverage.
