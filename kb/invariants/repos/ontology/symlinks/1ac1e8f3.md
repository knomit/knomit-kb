# A symlinked ontology (any rung: .knomit/ontology.yaml, .domains/, domains/) is an ERROR naming its path at every reader and REFUSES the repo (not mounted, listed "unopenable") — never "no ontology", never its link text parsed, and a regular legacy rung does not cover for it

User ruling 2026-10-08, "d": a symlinked ontology.yaml makes the repo fail to open with a clear message. Built in #439 (merge a8ef3d02 on dev), where the repo still mounted readable-but-unwritable. A second user ruling the same day ("refuse the repo") is built on branch fix/ontology-symlink-refuses-repo (commit e85a04f3): a symlinked ontology now REFUSES the repo. It is NOT mounted. A missing, empty or unparseable ontology is NOT refused: those repos still mount readable but unwritable (see kb/decisions/repos/kb-repo-layout/ontology-dot-domains-fallback/318f619a.md).

WHAT "REFUSED" MEANS, per door:
- Boot (Manager.Start → openRegistered): identifyStage.Enter returns the error when errors.Is(ontErr, fact.ErrSymlinkNotFollowed); the machine is Unavailable and the repo is listed by GET /api/v1/repos with state "unopenable" and the message as detail (the identity-conflict path, but reason "unopenable", not "conflict"). Its own endpoints answer 409. It is NOT in Manager.Get, so it does not sync, index or serve MCP.
- Add / clone / subscribe / initialize: branchHasOntology refuses with the same message (unchanged from #439).
- Restore of an archived repo: the mount fails, the restore is undone, and POST /archived/{id}/restore answers 422 "Ontology is a symlink" (archiveErrStatus). The repo stays archived, so it can still be purged.
- Disjoint-history connect (SwapStore): guardSwap refuses BEFORE anything is exited when the incoming store's ontology on the identity branch or on the repo's read branch is a symlink (inspectIncomingStore, internal/repos/events.go); the repo stays on its old store. Without this the swap would install the store and Identify would then turn a working repo Unavailable.

NOT A WAY OUT, and the gap to know about: a repo refused at BOOT has no in-product recovery today. Archive resolves through the live repo map (ErrRepoNotFound for it), Purge only takes an archived repo, and the refused repo does not sync, so a fix pushed to its origin never reaches it. Its registry row stays ACTIVE with its last repo_id, so re-adding the same knowledge base is refused as a duplicate (HeldByAnotherActiveRepo; read from the code, not tested). What clears it: replace the database file with one whose read branch holds a regular ontology and restart. The UI's unopenable page says the repo does not sync and that removing the registration is not supported.

SEEN ONLY AT IDENTIFY: the ontology is read once per mount (kb/decisions/fact/per-repo-ontology/0be51fec.md). A running repo whose read-branch ontology BECOMES a symlink (by sync, or a raw push) keeps serving until its next mount, and is refused then — at the next boot it disappears into "unopenable".

THE ERROR: fact.ErrSymlinkNotFollowed, built by fact.SymlinkNotFollowed(path): "<path> is a symlink, and knomit does not follow symlinks: commit the file itself in its place". Test with errors.Is.

THE RULE: the readers walk fact.OntologyPathsNewestFirst and stop at the FIRST rung PRESENT. If that entry is a symlink, the read fails with the named error. A regular file on a later rung is NOT used instead (that would be a silent substitute taxonomy).

EVERY READER, and what the error does there:
- store.OntologyAtCommit (internal/store/triggers.go): the trigger dispatcher logs it and keeps its last compiled set; the guidance reader (repos/guidance.go) warns once per commit with the message and gives no guidance (it treats it like a store read error, so it re-reads on the next call; only the warning is once per commit).
- store.treeOntology / Service.OntologyAt / Service.OntologyFileAt (internal/store/fleet_read.go, pushed_merge.go): fleet membership (LoadFleet, FleetMembersAt; FleetKeysOf does not read the ontology), the receive-pack verify mode (verifyModeAt) and the verify range gate return it; the consensus setting reader warns with it and reads as off, the sync setting reader warns with it and reads as interval.
- repos.loadOntology (stages.go, the identify stage) reads through Service.OntologyFileAt and returns the named error; identifyStage.Enter then REFUSES the repo (above). OntologyError never carries the symlink error on a mounted repo, and GET /repos's ontology_error never shows it.
- repos.branchHasOntology: clone, initialize and subscribe refuse with it.
- repos.ProbeInitialized (the create wizard's remote probe): Initialized is UNKNOWN (the empty field) and Detail is the message.
- okf export (okf/source okfOntologyDoc): degrades to the embedded default, as it does for any unusable ontology, with a warning carrying the message.
- Template create: the template walk refuses it as ErrTemplateNotRegular wrapping the same error.

- store.Audit (verify_audit.go, the fleet audit) returns it as "audit: fleet: ontology: ...", like LoadFleet; ErrNotFleet is only for a fleet with NO ontology, one that does not parse, or one that is not the fleet preset (#439 review B1; test TestAudit_SymlinkedFleetOntologyIsNamedNotNotAFleet).
- The conflicts setting reader (store/conflict_merge.go) reads it as off, which is fail-safe (conflicts are refused, not auto-settled), and logs it once per consensus-tip commit.

NOT AN ONTOLOGY READER: POST /api/v1/ontologies/validate validates the YAML it is sent, not a git file.

BEHAVIOUR CHANGE WORTH KNOWING: loadOntology used to walk the rungs with ReadFact and skip an EMPTY file to the next rung. It now takes the first rung present; an EMPTY first rung fails the open with "ontology at <path> on <branch> is empty" even if a legacy rung holds one (test TestLoadOntology_EmptyCanonicalDoesNotFallBackToLegacy). This removes a split: before, loadOntology alone skipped an empty rung while every other ontology reader took the first rung present.

CONTRAST: optional .knomit/ files (trigger scripts, recipes, guidance, skills, system files by path) read a symlink as ABSENT with their existing not-found errors; only the ontology fails loudly.
