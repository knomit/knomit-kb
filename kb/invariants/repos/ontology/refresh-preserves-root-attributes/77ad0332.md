# The boot preset refresh may only PRESERVE root attributes: SubsetDivergence counts them and refreshDivergence also refuses a preset that would ADD, CHANGE or DROP one — otherwise a release bump erases verify_signatures fleet-wide in an own-signed commit

The boot refresh in `RepoInstance.loadOntology` (internal/repos/stages.go; it lived in repos/builder.go before the stages split) writes the embedded preset over a stored preset-derived ontology when it is a subset and the bytes differ. That write is a commit SIGNED BY THIS INSTANCE. Under F09 a signed change to `verify_signatures`/`verify_signers` is a POLICY change, so an upgrade must never make one.

TWO GUARDS, both required:
1. `Ontology.SubsetDivergence` compares ROOT attributes exactly like node attributes (`attrsNotSubset`, absent-aware). A stored root attribute the preset lacks is DivergenceAttributes, so the refresh is skipped with reason "attributes". Before this, Serialize dropped the root block and SubsetDivergence never looked, so the next preset bump would have erased the setting on every instance (proposal test 23 = TestLoadOntology_RootAttributesSurvivePresetRefresh).
2. `refreshDivergence` (internal/repos/stages.go) adds `fact.RootAttributesEqual(stored, preset)` AND `fact.ArtifactRulesEqual(stored, preset)`: a preset that CARRIES a root attribute or an artifacts: rule the stored file lacks, or a different value, also blocks the refresh (reason `attributes`). SubsetDivergence alone would allow a preset to ADD a setting.

The guards overlap on the "stored has, preset lacks" case, so removing only one of them does not turn test 23 red; TestRootAttributes_AreDivergence (fact) and TestRefreshDivergence_NeverAddsOrChangesRootAttributes (repos) pin each guard separately.

An explicit `verify_signatures: off` compares as absent, so spelling out the default does not block upgrades.

DOES NOT MEAN: embedded presets may ship root attributes to turn verification on. They cannot: any preset root attribute is divergence for every repo that lacks it.

UPDATE (PR #514, verified at the merge commit): ARTIFACT RULES BLOCK A REFRESH TOO. The root `artifacts:` section (the fleet trust-file rules) is repository policy exactly like a root attribute: SubsetDivergence counts it (artifactsNotSubset), refreshDivergence requires ArtifactRulesEqual in both directions, and the divergence reason is `attributes` (there is no separate reason name). A preset that ADDS, CHANGES or DROPS an artifact rule never reaches an existing repository (kb/invariants/repos/ontology/refresh-preserves-artifact-rules/341d955a.md). Since refreshDivergence is also the preset-identity rule for templates, a template with the fleet id must carry the preset's root attributes and artifacts section byte-compatibly (ErrTemplatePresetID). The embedded fleet preset now DOES ship a root attribute (verify_signatures: enforce) and an artifacts: section; that reaches NEW repositories only (their ontology is written from the preset at create), never an existing one, which is the point of this guard.
