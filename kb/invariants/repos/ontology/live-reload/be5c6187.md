# A repo's ontology is reloaded LIVE when the read branch's ontology blob changes (after every fetch round and on every commit-observer fire): a usable file replaces the one in force IN FULL, an unusable one (missing, empty, unparseable, symlink, or the fleet id without the fleet door) keeps it and is reported in status — this is NOT the boot preset refresh, whose no-attribute-change rule does not apply

RULE (knomit/knomit#429; RepoInstance.reloadOntology, internal/corpus/repos/stages.go).

TRIGGER. Two, both calling reloadOntology(ctx, svc):
1. afterFetch, the `fetched` callback of runReconcileLoop, after EVERY successful fetch round of the origin loop (it also runs reidentifyAfterRewind when the round was ModeRewound). This makes the round's ontology in force when the round returns, which a sync-then-write caller and Synchronous tests rely on.
2. The commit observer (openStage), which fires debounced (1 s) after every ref advance the store makes on any branch via NotifyCommit: a sync merge or fast-forward, a consensus merge into the agent branch, a receive-pack, a local write. This is the catch-all for every way the read branch moves other than a round (an origin attach or upstream re-point moves it through its first round; a store swap re-runs Identify; an index rebuild moves no ref).

THE BLOB COMPARISON. Service.OntologyBlobAt(read branch) names the tip's first rung present and its blob id without reading it. identity.src holds the {commit, path, blob} in force. Same path+blob: nothing is read or parsed (the commit is deliberately not compared). Same as the file a previous reload already refused (identity.reloadSrc): nothing either. Only a different blob is read (OntologyFileAtCommit at that very commit) and parsed.

CONSENSUS IS HONOURED IN FULL (kb/decisions/repos/ontology/consensus-reload-honors-all/3aa84640.md). A usable new ontology REPLACES the one in force as-is: added topics and categories, every attribute changed or added (verify_signatures, learn_dedup, and the rest), removed or renamed topics and validations. There is no subset check, no additive-only filter, no attribute guard. A repo that had NO usable ontology becomes writable when a usable one arrives.

UNUSABLE-FILE FALLBACK. Missing, empty, unparseable, a symlink, or the reserved `fleet` id on a repo without the fleet door (admitFleetOntology) is NOT applied: the ontology in force stays, the repo stays writable, the error goes into identity.reloadErr and is reported by RepoInstance.OntologyStatus -> GET /repos/{name} `ontology.reload_error` (plus reload_commit/path/blob) and the list row's `ontology_reload_error`. The live repo is NOT turned Unavailable for a symlink or the fleet id (the sync loop cannot send to its own machine); the NEXT MOUNT still refuses it as Identify always has. If no usable ontology was in force, the new error replaces OntologyError instead. A fleet repository (fleet door) whose consensus ontology changes, including away from the fleet id, has it applied: that is what its next mount would load.

CONSUMERS THAT FOLLOW THE SWAP, and how: every one reads ri.Ontology() (an atomic pointer) per operation, never a stored copy — MCP knomit_learn/knomit_update (placement, context, learn_dedup, loaded once per call), the REST fact POST/PUT (PUT now loads it once per write), WritableBranch, IsFleet and through it fleet admission, Manager.fleetRepo and every fleet_* duty, guardAttach/guardSwap's ontology id check, federate's topic filter, resolutions, the review pipeline's prune step, artifact patterns (fleet_renew), and the MCP server instructions' 'Available topics' (computed at each session's initialize, so a session initialised BEFORE the swap keeps the text it was sent). Readers that never used the snapshot and read the ontology from git at their own tip: the store's validateWrite (JS validations), the trigger dispatcher (blob-keyed), verify_signatures (receive-pack, fetch judge, verify range), consensus/conflicts/sync settings, guidance, the UI's topic tree (git listing). Each write validates against exactly ONE ontology because the swap is one atomic pointer store and each operation Loads it once.

CONCURRENCY. Writers of RepoInstance.ident (identifyStage.Enter across its whole read+store, identifyStage.Exit, reloadOntology) hold RepoInstance.ontMu; readers never lock. A reload on a not-identified repo (before Identify, or between Exit and Enter in a swap) does nothing.

MISREADING TO AVOID: this is NOT the boot-time preset refresh (refreshPreset/refreshFleetOntology in loadOntology), which is knomit's own release overwriting the stored file in an instance-signed commit. That refresh's rules — refreshDivergence = SubsetDivergence + RootAttributesEqual, i.e. strictly additive and never adding/changing/dropping a root attribute (kb/invariants/repos/ontology/refresh-preserves-root-attributes/77ad0332.md, kb/decisions/fact/ontology/attributes-block-preset-refresh/17bba4fd.md) — do NOT apply to the live reload, and the live reload never runs either refresh and writes nothing. Do not 'harden' the reload by importing those checks: per the user's ruling that is fixing security in the wrong place; security belongs at the consensus gate.
