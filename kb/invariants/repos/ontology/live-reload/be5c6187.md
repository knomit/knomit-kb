# A repo's ontology is reloaded LIVE when the read branch's ontology blob changes (after every fetch round and on every commit-observer fire): a usable file replaces the one in force IN FULL; an unusable one (missing, empty, unparseable, symlink) makes the repo UNWRITABLE until consensus fixes it; the fleet id on a non-fleet repo makes it UNAVAILABLE (fleet_conflict); a read error changes nothing and is retried — this is NOT the boot preset refresh, whose no-attribute-change rule does not apply

RULE (knomit/knomit#429, PR #761; RepoInstance.reloadOntology, internal/corpus/repos/stages.go).

TRIGGER. Two, both calling reloadOntology(ctx, svc):
1. afterFetch, the `fetched` callback of runReconcileLoop, after EVERY successful fetch round of the origin loop (it also runs reidentifyAfterRewind when the round was ModeRewound). The round's ontology is in force when the round returns, which a sync-then-write caller and Synchronous tests rely on.
2. The commit observer (openStage), which fires debounced (1 s) after every ref advance the store makes on any branch via NotifyCommit: a sync merge or fast-forward, a consensus merge into the agent branch, a receive-pack, a local write. The catch-all for every way the read branch moves other than a round (an origin attach or upstream re-point moves it through its first round; a store swap re-runs Identify; an index rebuild moves no ref).

THE BLOB COMPARISON. Service.OntologyBlobAt(read branch) names the tip's first rung present and its blob id without reading it. identity.src holds the {commit, path, blob} the repo's state was read from — usable OR unusable. Same path+blob: nothing is read or parsed (the commit is deliberately not compared), so an unusable file already judged is not judged again. Only a different blob is read (OntologyFileAtCommit at that very commit) and parsed.

CONSENSUS IS HONOURED IN FULL (kb/decisions/repos/ontology/consensus-reload-honors-all/3aa84640.md). A usable new ontology REPLACES the one in force as-is: added topics and categories, every attribute changed or added (verify_signatures, learn_dedup, and the rest), removed or renamed topics and validations. No subset check, no additive-only filter, no attribute guard. A repo with NO usable ontology becomes writable when a usable one arrives.

UNUSABLE -> UNWRITABLE (user decision 1). Unusable means exactly what readOntology refuses: missing at every rung, a symlink (fact.ErrSymlinkNotFollowed), an empty first rung present, a fatal ParseOntology error. The previous ontology is NOT kept: the repo gets identity{ontologyErr, src} (Ontology() nil, OntologyError set), WritableBranch refuses every authored write, and setIdentity calls Service.SetOntologyUnusable so the store's validateWrite refuses EVERY fact write by any in-process writer (review pipeline, triggers, fleet code) with facts.ErrOntologyUnusable. validateWrite also refuses on an unparseable or empty ontology at the written branch's tip on its own (it used to let such writes through with validations skipped). A write that touches no fact (the ontology's own repair) is never refused. Status: OntologyStatus.Error; GET /repos ontology_error; GET /repos/{name} ontology {usable:false, error, commit, path, blob}. When consensus fixes the file (a new blob), the next reload applies it and the repo is writable again under the NEW ontology, with no restart. A symlink arriving live makes the repo unwritable, not Unavailable; the next MOUNT still refuses it.

READ ERROR -> NOTHING (retry). If the tip, its tree or the blob cannot be READ (ontologyReadError, or OntologyBlobAt failing with anything but a symlink), it is 'unknown', never 'no ontology': nothing is stored, src is not moved, the repo stays as it was, and the next round or commit reads again. At Identify the same read error still gives the 'no ontology at …' reason but with an EMPTY src, so the first reload that can read the file applies it.

FLEET ID ON A NON-FLEET REPO -> UNAVAILABLE fleet_conflict (user decision 2). A usable ontology with id `fleet` on a repo without the fleet door (admitFleetOntology fails) is never applied and never left writable: the reload stores identity{ontologyErr, src} (unwritable at once), then hands the instance (once, fleetConflictRetired) to Manager.retireFleetConflict on its own goroutine — the unmount drains the Sync stage the reload may run in. That removes it from the live maps and lists it unavailable (reason unopenable, cause fleet_conflict) under one lock, then unmounts it: the state a mount of it gives. Its way back is the mount's: archive and purge (a fix on the origin cannot reach a repo that no longer syncs).

FLEET TRANSITIONS ON THE FLEET REPOSITORY (fleet door) are applied like any consensus change and logged at Warn naming the edge: 'FLEET -> NOT FLEET' (IsFleet turns false, authored writes open on it, Manager.fleetRepo returns nil, every fleet duty stops) and 'NOT FLEET -> FLEET'.

CONSUMERS THAT FOLLOW THE SWAP: every one reads ri.Ontology() / ri.OntologyError() (an atomic pointer) per operation, never a stored copy — MCP knomit_learn/knomit_update (placement, context, learn_dedup, loaded once per call), the REST fact POST/PUT (PUT loads it once per write), WritableBranch, IsFleet and through it fleet admission, Manager.fleetRepo and every fleet_* duty, guardAttach/guardSwap's ontology id check, federate's topic filter, resolutions, the review pipeline's prune step, artifact patterns (fleet_renew), and the MCP 'Available topics' (computed at each session's initialize, so a session initialised BEFORE the swap keeps its text). The store's write seam follows through SetOntologyUnusable. Readers that read the ontology from git at their own tip: validateWrite's JS validations, the trigger dispatcher (blob-keyed), verify_signatures, consensus/conflicts/sync settings, guidance, the UI's topic tree.

CONCURRENCY. Writers of RepoInstance.ident (identifyStage.Enter across its whole read+store, identifyStage.Exit, reloadOntology) hold RepoInstance.ontMu; readers never lock. A reload on a not-identified repo (before Identify, or between Exit and Enter) does nothing.

MISREADINGS TO AVOID.
- This is NOT the boot-time preset refresh (refreshPreset/refreshFleetOntology in loadOntology), knomit's own release overwriting the stored file in an instance-signed commit. Its rules (refreshDivergence = SubsetDivergence + RootAttributesEqual; kb/invariants/repos/ontology/refresh-preserves-root-attributes/77ad0332.md, kb/decisions/fact/ontology/attributes-block-preset-refresh/17bba4fd.md) do NOT apply here, and the reload never runs either refresh. Do not 'harden' the reload with them: security belongs at the consensus gate.
- Decisions 1 and 2 do NOT filter or refuse USABLE consensus content: they cover only a file that cannot be used at all, and the reserved id's door. 'Unwritable' is not 'keep the old ontology'.
- A read error is not 'missing'.

KNOWN SEPARATE BUG (found by these tests, not fixed here): when the agent branch has diverged, the store's merge of main into it writes a symlinked ontology back as a REGULAR file holding the link text, so a symlink arriving by a real merge reaches the reload as an unparseable file (still unwritable, wrong reason). A fast-forward keeps the mode.
