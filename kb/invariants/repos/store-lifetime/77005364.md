# All store access goes through RepoInstance.Acquire; close/swap detach the handle then drain the refcount — never hold an Acquire across SwapStore/Archive

Every store generation on a RepoInstance is a refcounted storeHandle. The ONLY correct ways to reach the *store.Service are: (1) ri.Acquire() — returns the service plus an idempotent release func the caller MUST invoke when done; (2) ri.WithRead(fn) — scoped convenience over Acquire, fn is NOT called when no store is available and the error says why (ErrRepoClosed after teardown began, ErrStoreUnavailable mid-SwapStore or before a store is attached); (3) ri.Pin() — holds the generation without exposing the service, for callers that hand the whole ri to a component (e.g. synthesize.Reviewer) but must keep the store alive across a long operation.

Why this is safe: closeFn and SwapStore detach the handle under the write lock (teardown also sets a closed tombstone), then wait for the handle's refcount to drain BEFORE closing the service. The WaitGroup discipline is sound because every Add happens under ri.mu.RLock while the handle is still attached, and detaching requires ri.mu.Lock — so no Add can race a Wait. Consequence for consumers: a caller holding an Acquire keeps its generation open even across a concurrent SwapStore (the swap installs the new generation and closes the old one only after the caller releases); a caller that copies the *store.Service pointer WITHOUT holding an Acquire gets use-after-close.

HARD RULE — deadlock: never hold an Acquire (or Pin) across a call that replaces or closes the same repo's store (Manager.SwapStore, Manager.Archive) — the drain would wait on the caller's own reference forever. The origin-session commit handler acquires only AFTER SwapStore for exactly this reason (internal/web/handlers_origin_session.go).

Long-lived holders must pair acquire/release with the actual work lifetime, not the request lifetime: background hub tasks (index rebuild, synthesis run in internal/web/handlers_jobs.go) release when the TASK finishes, and every early-exit path (e.g. hub.Start returning 409) must release explicitly or teardown hangs forever on the leaked count.

WHAT THIS DOES NOT MEAN: it does NOT mean lock scope protects anything by itself anymore — 'I read svc under RLock so I'm safe' is FALSE; the refcount, not the lock, is the lifetime guarantee. It also does NOT mean per-mount safety is free in federation: each mount's RepoInstance must be acquired separately (mcp storeIndices returns a release per mount; fan-out goroutines and cursor-resume stores maps hold one per mount).

Anti-pattern (the bug class this replaced): snapshot svc or store indices under WithRead/RLock, release, then use — that was mcp storeIndices, web gitremote/jobs/origin-session, ri.Verify, and the commit observer before PR #20, and it raced SwapStore/Archive into 'sql: database is closed' errors or nil-interface panics.
