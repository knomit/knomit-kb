# OpenLensRegistry self-upgrades a write_uid-keyed-but-name-PK'd lens schema in place; a write_repo-keyed (pre-registry) lens schema is still only reachable via migrate-registry

There are now TWO distinct legacy lens shapes, and OpenLensRegistry's relationship to CREATE TABLE IF NOT EXISTS differs for each.

**Shape A — fully pre-registry (`lenses.write_repo`, member references by NAME).** The original claim in this fact still holds unchanged: `CREATE TABLE IF NOT EXISTS` is a no-op against it, and OpenLensRegistry has no path to upgrade it. In practice OpenLensRegistry never even gets the chance to try: `Manager.Start`'s boot guard (`refuseUnmigratedHome` / `Registry.HasLegacyLensSchema`, `registry.go:164`, checking for the `write_repo` column) refuses to boot such a home at all, before the lens registry is ever opened, and points the operator at `knomit migrate-registry`. That tool remains the only thing that converts Shape A — same mechanism this fact originally described (`DROP TABLE`+recreate from `LensSchemaSQL`+row translation inside `applyControlDB`).

**Shape B — membership already uid-keyed, but the lens ROW itself still keyed by name (`lenses.write_uid`/`lens_reads.repo_uid` present, no `lenses.uid` column).** This is the shape every home that has ever run `migrate-registry` was left in, once lenses themselves also needed a uid (for lens rename — the same three-identifier model repos already have). As of `internal/repos/lens_migrate.go`, `OpenLensRegistry` now DOES self-upgrade this shape in place, via `upgradeLensSchema(db)` called BEFORE `lensSchema`'s `CREATE TABLE IF NOT EXISTS` runs. It uses an explicit column probe (`lensColumnExists(db, "lenses", "uid")`) — a different mechanism from CREATE-TABLE-IF-NOT-EXISTS, which is what makes it actually work where the old mechanism could not: disables `PRAGMA foreign_keys` (a no-op inside a transaction, so it's issued outside one and restored via defer), renames `lenses`/`lens_reads` to `*_old`, recreates both in the new shape (`lenses.uid TEXT PRIMARY KEY`, `lenses_name` now a plain UNIQUE INDEX, `lens_reads.lens_uid` replacing `lens_reads.lens_name`), mints a fresh `ksuid.New().String()` per existing lens name, copies every lens row and every `lens_reads` row across keyed by the new uid, drops the `*_old` tables, and commits. Idempotent — returns immediately if `lenses.uid` is already present, so a second boot never re-mints uids.

**migrate-registry was also updated to emit/preserve the Shape-B-to-final-shape column.** `applyControlDB`'s `INSERT INTO lenses`/`INSERT INTO lens_reads` now include `uid`/`lens_uid`; without this, either the row silently gets a NULL uid (SQLite allows NULL in a non-INTEGER PRIMARY KEY column, so this would NOT error — the exact silent-no-op class this whole area is trying to avoid) or, since `lens_reads.lens_name` no longer exists as a column at all, the insert errors loudly. `planLenses` now also probes for a pre-existing `lenses.uid` on a `--force` re-run and carries it across rather than re-minting, mirroring the existing precedent for repo uids.

**Consequence, updated:** a home migrated by some path OTHER than `migrate-registry` while still in Shape A is still silently broken on first real query (original claim, unchanged). A home already in Shape B is NOT silently broken anymore — the next `OpenLensRegistry` call (i.e. the next server boot) heals it automatically, with no CLI step required.
