# OpenLensRegistry self-upgrades a write_uid-keyed-but-name-PK'd lens schema in place; a write_repo-keyed (pre-registry) lens schema is SKIPPED — neither converted nor refused

There are TWO distinct legacy lens shapes, and control.db bring-up heals exactly one of them.

**Shape A — fully pre-registry (`lenses.write_repo`, member references by NAME).** Nothing converts it any more and nothing refuses it. `upgradeLensSchema` cannot convert it: it copies `write_uid`, a column this shape does not have. `controlUp` therefore SKIPS the re-key for it (guarded by `HasLegacyLensSchema`), and `migrate.Control`'s `CREATE TABLE IF NOT EXISTS lenses` is a no-op against the legacy table, so the home opens with the legacy table in place. Every LensRegistry query names `uid`/`write_uid` (lens.go), so lens operations on such a home fail at runtime. The one-shot converter (`knomit migrate-registry`) and the Manager.Start boot check that refused this shape were both removed in merge 1cc5413c (#326), on the designer's judgement that no home in use still has it. The skip survives only so that the re-key does not fail on a column it cannot find.

**Shape B — membership already uid-keyed, but the lens ROW itself still keyed by name (`lenses.write_uid`/`lens_reads.repo_uid` present, no `lenses.uid` column).** This is the shape registry-era homes were left in once lenses themselves also needed a uid (for lens rename — the same three-identifier model repos already have). `upgradeLensSchema` (`internal/repos/lens_migrate.go`) heals this shape in place on every open. It is guarded by an explicit column probe (`lensColumnExists(db, "lenses", "uid")`), NOT by `CREATE TABLE IF NOT EXISTS` — which is what makes it work where the DDL alone could not. It disables `PRAGMA foreign_keys` (a no-op inside a transaction, so it is issued outside one and restored via defer, with the restore VERIFIED because this is the single connection the handle hands out for the process's life), renames `lenses`/`lens_reads` to `*_old`, recreates both in the new shape (`lenses.uid TEXT PRIMARY KEY`, `lenses_name` now a plain UNIQUE INDEX, `lens_reads.lens_uid` replacing `lens_reads.lens_name`), mints a fresh `ksuid.New().String()` per existing lens name, copies every lens and `lens_reads` row across keyed by the new uid, drops the `*_old` tables, and commits. Idempotent — returns immediately if `lenses.uid` is already present, so a second boot never re-mints uids.

**Operational consequence:** a Shape-B home needs no CLI step — the next open heals it. A Shape-A home has no supported path in this build.

**WHAT THIS DOES NOT MEAN.**

- *Not* "`OpenLensRegistry` calls `upgradeLensSchema` itself." It calls `controlUp`, which owns the ordering (probe → conditional re-key → `migrate.Control`) and is shared with `OpenRegistry` and `Manager.Start`. Code that opens control.db must call `controlUp`, never reproduce its steps — see [[migrator-ordering]] (kb/invariants/repos/control-db/migrator-ordering/52a6318e.md).
- *Not* "`lensSchema` / `LensSchemaSQL` create the lens tables." Those hand-rolled schema accessors are GONE; the lens tables come from `migrate.Control`'s baseline.
- *Not* "the re-key runs on every open of every home." It is skipped for Shape A (by `HasLegacyLensSchema` in `controlUp`) and returns immediately for an already-uid-keyed home (by its own `lenses.uid` probe). Only Shape B actually does work.
- *Not* "the skip protects Shape A." It only avoids a failed re-key; the home still cannot use lenses.
