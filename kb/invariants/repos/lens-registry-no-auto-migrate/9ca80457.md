# OpenLensRegistry cannot upgrade a legacy name-keyed lens schema — CREATE TABLE IF NOT EXISTS is a no-op against an existing old-shape table, so migrate-registry owns rebuilding it

internal/repos/lens.go's `lensSchema` constant is `CREATE TABLE IF NOT EXISTS lenses (... write_uid TEXT NOT NULL REFERENCES repos(uid) ...)` and similarly for `lens_reads (... repo_uid ...)`. `OpenLensRegistry` runs this DDL unconditionally on every open.

**The trap:** `CREATE TABLE IF NOT EXISTS` is a no-op when a table of that name already exists — SQLite does not diff the column list against what is requested. Against a legacy control.db, `lenses`/`lens_reads` already exist in the OLD name-keyed shape (`write_repo` / `repo` columns instead of `write_uid` / `repo_uid`). `OpenLensRegistry` opening such a database leaves those legacy columns in place, completely unchanged, and every subsequent query this codebase issues against `write_uid` or `repo_uid` fails at runtime with 'no such column' — there is no migration path through OpenLensRegistry itself, by construction of `CREATE TABLE IF NOT EXISTS`.

**Who owns the upgrade instead:** `knomit migrate-registry` (cmd/migrate_registry.go, `applyControlDB`). Inside its single control.db transaction it explicitly `DROP TABLE IF EXISTS lens_reads` then `DROP TABLE IF EXISTS lenses` BEFORE creating the new-shape tables from the exported `repos.LensSchemaSQL` constant (the same DDL `OpenLensRegistry` uses, re-exported specifically so the tool can never drift from the shape it's supposed to produce) — then re-inserts every lens row with its `write_repo`/`repo` NAME references translated to registry `uid`s via the plan built in `planLenses`. The drop-then-recreate has to happen inside the transaction and before the row rewrite because `lens_reads`' foreign key into `repos(uid)` would otherwise block writing translated rows while the OLD `lenses` table (referencing repo NAMES, not uids) is still present.

**Consequence:** a home migrated by any path OTHER than `knomit migrate-registry` — e.g. copying files by hand, or a future tool that tries to call `OpenLensRegistry` directly against a legacy control.db expecting it to 'just upgrade' — silently ships a broken lens registry that fails on first real query, not at open time. `planLenses` detects a control.db already in the new shape (`rawColumnExists(db, "lenses", "write_uid")`) and treats it as a re-run, carrying rows across unchanged rather than re-translating them — so migrate-registry is also safe to run twice.
