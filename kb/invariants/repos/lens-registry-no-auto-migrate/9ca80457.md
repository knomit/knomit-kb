# OpenLensRegistry self-upgrades a write_uid-keyed-but-name-PK'd lens schema in place; a write_repo-keyed (pre-registry) lens schema is still only reachable via migrate-registry

There are TWO distinct legacy lens shapes, and control.db bring-up heals exactly one of them.

**Shape A — fully pre-registry (`lenses.write_repo`, member references by NAME).** Nothing on the open path upgrades it. `upgradeLensSchema` cannot: it copies `write_uid`, a column this shape does not have. `controlUp` therefore SKIPS the re-key for it (guarded by `HasLegacyLensSchema`), and `Manager.Start`'s boot guard (`refuseUnmigratedHome`, whose durable arm is that same `write_repo` probe) refuses to boot such a home at all and points the operator at `knomit migrate-registry`. That tool remains the only thing that converts Shape A: `applyControlDB` DROPs `lenses`/`lens_reads`, recreates them by exec'ing the baseline DDL text, and translates member references from names to uids inside one transaction.

**Shape B — membership already uid-keyed, but the lens ROW itself still keyed by name (`lenses.write_uid`/`lens_reads.repo_uid` present, no `lenses.uid` column).** This is the shape every home that has ever run `migrate-registry` was left in, once lenses themselves also needed a uid (for lens rename — the same three-identifier model repos already have). `upgradeLensSchema` (`internal/repos/lens_migrate.go`) heals this shape in place on every open. It is guarded by an explicit column probe (`lensColumnExists(db, "lenses", "uid")`), NOT by `CREATE TABLE IF NOT EXISTS` — which is what makes it work where the DDL alone could not. It disables `PRAGMA foreign_keys` (a no-op inside a transaction, so it is issued outside one and restored via defer, with the restore VERIFIED because this is the single connection the handle hands out for the process's life), renames `lenses`/`lens_reads` to `*_old`, recreates both in the new shape (`lenses.uid TEXT PRIMARY KEY`, `lenses_name` now a plain UNIQUE INDEX, `lens_reads.lens_uid` replacing `lens_reads.lens_name`), mints a fresh `ksuid.New().String()` per existing lens name, copies every lens and `lens_reads` row across keyed by the new uid, drops the `*_old` tables, and commits. Idempotent — returns immediately if `lenses.uid` is already present, so a second boot never re-mints uids.

**migrate-registry emits the final-shape columns.** `applyControlDB`'s `INSERT INTO lenses`/`INSERT INTO lens_reads` include `uid`/`lens_uid`; without them the row would silently get a NULL uid (SQLite allows NULL in a non-INTEGER PRIMARY KEY column, so this would NOT error — the exact silent-no-op class this area exists to avoid). `planLenses` probes for a pre-existing `lenses.uid` on a `--force` re-run and carries it across rather than re-minting, mirroring the precedent for repo uids.

**Operational consequence:** a Shape-B home needs no CLI step — the next boot heals it. A Shape-A home needs `knomit migrate-registry` and will refuse to boot until it gets it.

**WHAT THIS DOES NOT MEAN.**

- *Not* "`OpenLensRegistry` calls `upgradeLensSchema` itself." It calls `controlUp`, which owns the ordering (probe → conditional re-key → `migrate.Control`) and is shared with `OpenRegistry` and `Manager.Start`. Code that opens control.db must call `controlUp`, never reproduce its steps — see [[migrator-ordering]] (kb/invariants/repos/control-db/migrator-ordering/52a6318e.md).
- *Not* "`lensSchema` / `LensSchemaSQL` create the lens tables." Those hand-rolled schema accessors are GONE; the lens tables now come from `migrate.Control`'s baseline. Do not go looking for them.
- *Not* "the re-key runs on every open of every home." It is skipped for Shape A (by `HasLegacyLensSchema` in `controlUp`) and returns immediately for an already-uid-keyed home (by its own `lenses.uid` probe). Only Shape B actually does work.
- *Not* "the boot guard protects Shape A everywhere." The guard runs in `Manager.Start` only; `OpenRegistry`/`OpenLensRegistry` have no guard in front of `controlUp`.
