# ri.Verify holds an Acquire for the whole store call — long store operations pin the generation, never snapshot-then-release

RepoInstance.Verify(ctx, opts) acquires the store via ri.Acquire() and holds the acquisition (releasing via defer) for the ENTIRE svc.Verify call, then stamps report.Repo with the repo's name. This is the load-bearing pattern for any operation that calls store methods outside a WithRead closure: Acquire, do the work, release. A concurrent SwapStore/Archive drains outstanding acquisitions before closing the service, so the long-running Verify finishes on an open store while the swap/close waits; new acquirers meanwhile fail fast with ErrRepoClosed/ErrStoreUnavailable. Holding the acquisition does NOT block concurrent readers or block SwapStore's lock acquisition — Acquire holds ri.mu.RLock only momentarily; the refcount, not the lock, is what keeps the store open.

HISTORY — this fact previously blessed the OPPOSITE pattern ('snapshot svc under RLock, release, then operate') as SwapStore-safe. That was wrong: it contradicted SwapStore's own barrier assumption, and the same pattern in mcp storeIndices and the web handlers was a real use-after-close race (fixed in PR #20; see the incident fact). If you see snapshot-then-release in old code or old advice, it is the anti-pattern now.

Anti-patterns: (1) copying the *store.Service pointer out of WithRead/RLock and using it after release — use Acquire; (2) running a long store call INSIDE WithRead is acceptable now (WithRead holds a refcount, not a lock, for fn's duration) but Acquire is clearer for multi-step work; (3) holding this Acquire across a call to Manager.SwapStore/Archive on the same repo — self-deadlock (the drain waits on your own reference).
