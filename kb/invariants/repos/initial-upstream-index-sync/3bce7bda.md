# setupIndex MUST heal BOTH agentBranch AND upstreamMain for a repo with a stored origin — cfg.Git.Origin is gone, and a ref that does not resolve is skipped

For a repo with an origin, the initial index heal MUST cover BOTH the agent branch AND upstreamMain. Reason: InitFromRemote populates commit_log for both agent/* AND the upstream during clone, but without an explicit index sync the upstream's branch_facts / facts_vec / graph tables would be EMPTY even though the cloned tree has content — and Verify's facts-coherence check correctly fires on the upstream branch. Anti-pattern: assuming clone-time commit_log population implies index population; clone only does git-side work, the SQL index needs an explicit sync per branch.

WHAT "HAS AN ORIGIN" MEANS (PR #73): NOT cfg.Git.Origin — that config key was REMOVED along with the special "core" repo. The test is `b.upstreamMain != ""`, and upstreamMain is read back from the STORED remotes row by rehydrateUpstreamMain (SetRemote never stores an empty branch; DeleteRemote removes the row). Never default upstreamMain to "main": that guess rewrote the persisted upstream and aimed the heal at a nonexistent branch for every master-convention repo.

THE ONE EXCEPTION (PR #73): a branch whose git ref does not RESOLVE is dropped from the heal by dropUnresolvableBranches before any work is scheduled. This does not weaken the invariant — a ref with no tree has nothing for the index to hold — and it is the honest reading of a stored upstream naming a branch this repo does not have (remotes row disagrees with the repository, e.g. a locally-created repo later pointed at a master-convention origin). Leaving it in made Rebuild fail at HeadCommit on every boot, forever. If the reconcile loop later creates the ref, notifyCommit indexes it normally. The AGENT branch is never dropped: a failing Rebuild there must surface as index-failed.

MECHANISM (PR #82, amended by #73): the heal does not run synchronously inside repoBuilder.setupIndex. setupIndex only RECORDS the work as b.indexBranches []healBranch{name, stale} — asking IndexManager.NeedsRebuild ONCE PER BRANCH, because the schema version is keyed per branch (see kb/architecture/store/graph-schema-version). Manager.openOne then runs healIndexBranches in a BACKGROUND goroutine watching b.indexCtx (its OWN context, not syncCtx) so the HTTP server / web UI come up IMMEDIATELY instead of blocking on a heavy rebuild. repoBuilder.build() constructs the RepoInstance but DEFERS recoverFromOrigin + startSyncLoops to b.activate(), which the goroutine calls only AFTER the heal completes — so the reconcile/commit loops never race the initial index build. Stale branches are Rebuilt, current ones SyncLocked (never bare Sync — the heal is out-of-band and must hold lockBranch). Only index 0 (the agent branch) is fatal. RepoInstance.IndexStatus() reports ready|indexing|error+done/total. DisableBackgroundSync (test harnesses) takes the SYNCHRONOUS path so the open→index-ready contract still holds. Any future path that calls InitFromRemote must route through healIndexBranches (or notifyCommit) so neither branch is left unindexed.
