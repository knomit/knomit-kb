# effort=normal MUST spend ZERO discovery — but it is not a freeze on pipeline behaviour

At effort=normal the review and hypothesize pipelines MUST spend NOTHING on emergent-fact discovery: `bridgeSeeds` returns nil, ZERO `discover` work items are enqueued, and no `origin=discovered` facts are written. Discovery is opt-in via medium/high ONLY, and the DiscoveryConfig default is `normal`. Enqueuing a discover item, engaging bridgeSeeds, or writing a discovered fact at normal effort is a defect.

The scope of the guarantee is the DISCOVERY DIMENSION, and only that: there must be no normal-vs-medium divergence in what discovery costs or produces. A change applied UNIFORMLY at every effort level is NOT a violation of this invariant, even when it changes the work-item queue — chunking the distill item, adding a step, reordering items, altering a prompt.

NAMED MISREADING — this is NOT a general freeze on normal-effort pipeline behaviour. Earlier wording of this fact said normal effort must behave "exactly as before emergent-fact discovery existed", byte-for-byte, and that "even reordering the standard work items" was a defect. That overreached its own stated purpose: every concrete clause names discovery, and the enforcing test (TestReviewer_NormalEffort_DefaultPath, review_effort_normal_test.go) walks the queue generically and asserts only that no `discover` items appear — N distill items are fine by it. Read as a freeze, this fact would block legitimate uniform bug fixes; that is exactly what happened when P0.4/T3 wired chunkFacts into the distill enqueue.

The reason the narrow reading is correct is the dial's semantics, stated by the designer 2026-07-21: EFFORT MEANS HOW MUCH RESOURCE (tokens, time, complexity) THE PIPELINE SPENDS. It was never meant as a freeze of functionality. `normal` is the cheapest rung, not a compatibility mode — so the only thing it promises is that the expensive optional machinery stays switched off.
