# MN5 pins the ENFORCING TEST FILE, not effort=normal's behaviour — and the difference is the whole point

MN5 says `internal/synthesize/review_effort_normal_test.go` stays byte-identical. It is enforced by `TestConformance_EffortNormalTestByteIdentical`, which SHA-256s the file and compares it to `effortNormalTestSHA256`.

WHAT IT PROTECTS: that nobody quietly weakens the test that enforces `invariants/synthesize/effort-normal-byte-identical` — at effort=normal the pipeline spends NOTHING on emergent-fact discovery.

WHAT IT DOES NOT PROTECT, and this is the misreading to guard against because the invariant itself already names it: MN5 is NOT a freeze on normal-effort pipeline behaviour. A change applied UNIFORMLY at every effort level does not violate the invariant, even one that changes the work-item queue. An earlier, broader wording of that fact — "exactly as before emergent-fact discovery existed", byte-for-byte — blocked a legitimate uniform fix when P0.4/T3 wired chunkFacts into the distill enqueue. The narrow reading is the live one.

So the two claims sit one word apart and are not the same claim. Editing the pipeline is often fine; editing its enforcing test is what needs an argument.

A PIN NOBODY HAS TO ARGUE PAST PROTECTS NOTHING, which is why the mismatch message does not say "do not touch". It gives the legitimate update path: update the constant, say in the PR what the contract now is and why it is still the contract, and check the change really is uniform across effort levels — because if it is not, what is being changed is what normal effort SPENDS, and that is the invariant itself rather than MN5.

CROSS-PLATFORM STABILITY IS NOT INCIDENTAL: `.gitattributes` pins `* text=auto eol=lf`, so the bytes are the same on Windows. A CRLF checkout WOULD change the hash, and that is the correct outcome — the protected file would genuinely not be the bytes the pin names.
