# A response_schema's `required` list is inert unless the parser probes the raw object — a wrong envelope key decodes to a zero value and applies as a silent no-op

A review work item's `response_schema` advertises a `required` list, but Go's `encoding/json` silently discards top-level keys it does not recognise, so nothing enforced that list. A response carrying its content under the wrong key — `{"facts": [...]}` against a `distill` item, whose schema requires `"synthesize"` — unmarshalled into a zero-valued `DistillResult`, passed `validateDistillPaths` (which only inspects `Retract`, a field the wrong envelope never populated), and reached `ApplyDistillDecisions` with zero facts. It wrote nothing, returned nil, advanced the work item, and reported `Synthesized: 0`.

Observed 2026-07-27: a live review session lost four distilled facts this way on items 40-43 of session 284faa87. The server had advertised `"synthesize"` on every one of them; the agent had pattern-matched `knomit_learn`'s `facts` array. The loss was invisible from the client — no error, no warning, and a summary that reads as "nothing to do".

`parseDistillResponse` and `parsePruneResponse` now probe the raw JSON object for their required key (`"synthesize"` / `"decisions"`) and error naming both the key expected and the keys received.

**Consequence when adding a step type or a response field:** declaring a key in a schema's `required` list buys nothing on its own. Add the matching `requireResponseKey` call inside the parse function, or the step silently no-ops whenever an agent names the envelope wrong. The same class of hole exists anywhere a JSON Schema `default` or `required` is advertised to a client but never applied server-side.

**WHAT THIS DOES NOT MEAN — it is not a non-empty check.** Presence is verified, not content: `{"synthesize": []}` is a legitimate "nothing worth distilling" and must keep applying cleanly. Rejecting empty arrays would wedge any session whose agent honestly had nothing to contribute, on an item it could never get past.

**WHAT THIS DOES NOT MEAN — `DisallowUnknownFields` is not the equivalent fix.** It would additionally hard-fail responses that carry an extra decorative key alongside the correct one, which parse and apply fine today.

Decode runs before the claim CAS, so a rejected response leaves the work item unanswered and fully retryable — which is what makes failing loudly safe here rather than destructive.
