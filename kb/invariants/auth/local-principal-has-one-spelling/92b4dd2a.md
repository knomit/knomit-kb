# The principal the boot SEEDS and the principal the middleware DERIVES come from one per-platform pair (auth.LocalPrincipal / auth.Peer.Principal) — os.Getuid() returns -1 on Windows, so seeding once wrote a grant for uid:-1 that no request could match

The principal written at boot and the principal derived from a live connection MUST render the same string. They come from one per-platform pair: auth.LocalPrincipal() answers "who is this process" for seeding, auth.Peer.Principal() answers "who is this caller" for internal/edge/web's AuthMiddleware, and both spell the ID with the same per-platform `localID` and carry the same `auth.LocalVia`.

CONSEQUENCE IF BROKEN: boot seeds a grants row no request can match, and the server refuses every local write while looking perfectly healthy. That was the real state on Windows before PR #251: seedOwnUID built the id from os.Getuid(), which returns **-1** there, so boot seeded `bridge:uid:-1@socket`. The function is now seedOwnPrincipal and os.Getuid() no longer appears in internal/app.

NAMED MISREADING — "they share localID, so they cannot disagree" is FALSE as stated. A SYMMETRIC change to localID moves both sides together and the invariant test stays green; verified by forced failure (changing localID from "sid:" to "uid:" does not fail it). What the invariant forbids is one side BYPASSING the function, which is exactly what app.go did. The spelling itself is pinned separately by TestPeerCred_PipeReportsOwnSID in internal/foundation/auth/peercred_windows_test.go.

ENFORCING CODE: TestLocalPrincipal_AgreesWithWhatPeerCredSeesOfUs (internal/foundation/auth/local_test.go) connects the test process to itself over the platform's REAL listener rather than comparing two calls to one function — which would pass however wrong both were.
