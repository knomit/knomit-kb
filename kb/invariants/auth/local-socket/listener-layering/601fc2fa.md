# The local listener path is decided ONLY by config.socketFor(home, fromTOML, fromEnv) — KNOMIT_SOCKET > knomit.toml `socket` > localListenerName(home), the chosen value tilde-expanded and refused unless absolute — and BOTH config.Load (server) and config.SocketPath (bridge) start from config.homeAndConfig (tilde-expanded, absolute home; <home>/knomit.toml only); the bridge never resolves any layer itself

Two unexported functions in internal/config/paths.go together decide the local authenticated listener (unix socket, or Windows named pipe). They came in with knomit#271 / PR #272 and were tightened by knomit#274 / PR #293.

1. `homeAndConfig() (home, configPath string, err error)` (paths.go:124) runs ResolveHome, THEN expandTilde, THEN `filepath.Abs`, THEN findConfigFile on that home. It is the one place that order lives. Home is expanded and made absolute exactly once, here. findConfigFile looks ONLY at `<home>/knomit.toml`, never beside the executable (toml-beside-executable gotcha).
2. `socketFor(home, fromTOML, fromEnv string) (string, error)` (paths.go:202) is pure. It picks fromEnv (the caller passes os.Getenv("KNOMIT_SOCKET")) if non-empty, else fromTOML, else `localListenerName(home)`. An EXPLICIT value (env or TOML) is then tilde-expanded (`~/`, and `~\` on Windows) and must satisfy `isAbsListener`: an absolute path, or on Windows a `\\.\pipe\` name. Otherwise socketFor returns `socket "<v>" must be an absolute path; set KNOMIT_SOCKET or the knomit.toml socket key to one`. The default is not re-checked, because home is already absolute.

BOTH resolvers use both:
- `config.Load` (what `knomit serve` and the desktop pass to auth.ListenLocal): homeAndConfig (config.go:509) → decode knomit.toml into cfg → … → `cfg.Socket, err = socketFor(cfg.Home, cfg.Socket, os.Getenv("KNOMIT_SOCKET"))` (config.go:640), with the error returned as `config: …`. Its env-overlay block has a comment saying KNOMIT_SOCKET is applied in socketFor (config.go:530). Do not add an envOr for it there.
- `config.SocketPath` (paths.go:173; what `tools/bridge/knomitapi.SocketPath` delegates to): homeAndConfig → decode the file into a zero `Config` and read `.Socket` → socketFor, with the error wrapped identically (`config: …`). So both sides refuse a relative socket with the SAME message, and the bridge logs it once and uses TCP. A decode error is returned wrapped with the file's path (`config: <path>: …`, paths.go:181).

Where the listener is OPENED is a separate invariant (auth.ListenLocal, local-listener-single-site). This one is about which PATH both sides compute.

CONSEQUENCES:
- A new layer (another env var, a flag) goes into socketFor's inputs at BOTH call sites, never into one resolver. Changing one side only reproduces the original drift: the bridge dials a path the server never opened, finds nothing, falls back to TCP, and silently loses the verified identity. No error is raised anywhere.
- Any normalisation of the socket value (expansion, validation) goes INSIDE socketFor, never in Load's path loop or in SocketPath. Doing it on one side is a fresh disagreement.
- Any change to how the data root or its knomit.toml is found goes in homeAndConfig, not in Load or SocketPath.
- `knomitapi.SocketPath` stays a thin delegate. Any bridge-side reading of KNOMIT_SOCKET, TOML or HOME is a violation even if it happens to compute the same answer today. Its WARN on failure fires once per process (sync.Once), but the path itself is resolved on every call and never cached (ambient-state-at-package-init).
- A socket change takes effect only after the SERVER restarts. The server resolves once at startup, the MCP bridge once at its own startup (tools/bridge/main.go), and the lazy hooks client on every dial. So after a TOML edit the hooks dial the new path, find no listener, and use TCP without the verified identity, NOT no connectivity. This is accepted and documented on the Config.Socket field. A client-side cache cannot fix it: each hook is a fresh process, and it is the server that is stale.
- The bridge's startup does not resolve the listener at all when an explicit URL is given (CLI argument or KNOMIT_BASE_URL). The lazy hooks client skips it for the same reason.
- A knomit.toml that SocketPath cannot decode is an error (the bridge logs WARN and uses TCP), not a fall-through to the default, because Load refuses the same file.

ENFORCED BY: internal/config/socket_agreement_test.go. It is platform-neutral, and every KNOMIT_* variable is cleared per test. Each case asserts Load().Socket == SocketPath() == expected, for:
- KNOMIT_SOCKET;
- the TOML socket;
- env beats TOML;
- `~/` in KNOMIT_HOME, and `~/` in KNOMIT_HOME with a TOML socket in the expanded root;
- a relative KNOMIT_HOME under t.Chdir (also asserting Load().Home is absolute);
- `~/x.sock` in KNOMIT_SOCKET and in the TOML (both must equal UserHomeDir/x.sock).

_RelativeSocketRefused requires BOTH sides to error with the same message, for env and TOML. tilde_windows_test.go (windows tag) covers `~\` in the socket and in a path field. TestFindConfigFile_OnlyHome pins the config location. A malformed TOML must make SocketPath return an error naming the file. tools/bridge/knomitapi/socketpath_test.go pins the delegation.

WHAT THIS DOES NOT MEAN:
- Not that a relative socket is made absolute. It is REFUSED, because `filepath.Abs` would resolve against each process's own cwd, which is exactly the disagreement. The data root, by contrast, IS made absolute: it is resolved once per process, and a relative root was already per-cwd for everything the server stores.
- Not that TOML edits propagate live (see the restart consequence above).
