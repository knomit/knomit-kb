# authz.Seed (Go) is the ONE authority for role -> permission; Store.SeedRoles syncs control.db to it in BOTH directions at every boot (adds missing rows AND deletes rows Seed does not hold) and bumps the bindings version only when a row changed

internal/foundation/authz/role.go holds Seed, the fixed role -> permission table (design §4 as amended by §15.3 and §16). Migration 000022 only CREATEs the tables (auth_roles, auth_role_permissions, auth_role_bindings, auth_state) because control.db up-migrations may only be CREATE ... IF NOT EXISTS; the rows are written by Store.SeedRoles, which boot calls every time (internal/app authzBoot).

SeedRoles makes the tables EQUAL Seed: it inserts every missing role/permission row and deletes every row Seed does not hold (a permission a role no longer has, or a role Seed does not name). Consequence: to take a permission away from a role, edit Seed; existing databases lose it at the next boot. Hand-editing auth_role_permissions is undone at the next boot.

The bindings version (auth_state key bindings_version) is bumped iff SeedRoles changed a row, so a no-op reseed at every boot does not invalidate the materializer cache. A hand edit that does NOT go through Store does not move the version, so cached policies keep answering until something bumps it.

What this does NOT mean: it does not make roles user-definable or migration-seeded. Roles are a fixed code set; a new role or permission is a code change to Seed (and to the closed Permission list in permission.go).

Current table (P1): admin = all but repo:push; operator = kb:read, kb:write, chat:use, repo:manage, repo:origin, ops:run; contributor = kb:read, kb:write, chat:use; reader = kb:read, chat:use; guest = kb:read; node = kb:read, repo:push. repo:push is node-only (§16) — admin, operator and contributor do NOT hold it. TestSeed_MatchesDesignTable pins the matrix as a literal.
