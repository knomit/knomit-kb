# authz principals have no transport in their identity: os:uid:<n> / os:sid:<SID> / token:<id> / node:<fp> / anonymous; authz.Owner and authz.FromPeer both take the id from auth's per-platform formatter, so a request over our own socket IS the owner

internal/foundation/authz/principal.go. Identity is Kind+ID; Label is display-only and excluded from String() and from every comparison (code compares p.identity()). Unlike the old auth.Principal (<kind>:<id>@<via>), the new spelling carries no Via: how a caller connected is Policy.Via, audit only.

FromPeer(auth.Peer) => os:<peer.ID>; Owner() => os:<auth.LocalPrincipal().ID>. Both IDs come from auth's localID (uid:<n> on unix, sid:<SID> on Windows), the one-spelling pair. Never build an os principal from os.Getuid() (it is -1 on Windows). TestOwner_AgreesWithFromPeerOfOurOwnConnection dials auth.ListenLocal in-process (the named pipe on Windows) and requires FromPeer(peer) == Owner().

ParsePrincipal is strict and rejects any string containing '@', so an old-model principal string can never parse as a new one. It accepts an os principal only in auth's ONE spelling: uid:<decimal> with no sign or leading zero (os:uid:0 is root and fine; os:uid:01 is refused), and sid:S-1-<authority>-<subauthority>... in decimal with no empty or zero-padded component (as ConvertSidToStringSid formats it). A second spelling of one account would be a second principal, so a binding for one would not match a request naming the other.

Consequence: Store.Bind and Materializer.For both require the principal to round-trip through ParsePrincipal to itself (canonical()); For answers anything else with an error and an empty policy (P1 review).
