# A lens create or PATCH may add a member (read mount OR write repo) only when the caller's credential reaches that repo BY NAME (auth.ReachesRepo); members the lens already has are exempt, and an unreachable repo is answered exactly like an unknown uid

Rule (user ruling G4, PR fix/mcp-token-audience). In `checkLensMembers` (internal/edge/web/api/manage/handlers_lenses_hal.go), shared by POST /api/v1/lenses and PATCH /api/v1/lenses/{lens}: a uid NOT in the lens's current member set (write uid + every read uid; empty on create) that the registry knows is treated as unknown unless `auth.ReachesRepo(ctx, rec.Name)` — the same 400 "Unknown repo uid" body, so the refusal is no existence oracle.

Why: a lens MCP endpoint reads every member through the binding, so before this a token for /api/v1/lenses/L with write could PATCH any registered repo into L and then read it — escalation out of its audience. A lens token reaches NO repo by name (tokenRepoReach), so it can add nothing; it can still re-send the members L has, drop members, change the write repo to an existing member, and edit the description. Local callers (AuthMiddleware: AllRepos) and whole-API tokens (/, /api/v1, /api/v1/repos, /api/v1/mcp) reach every repo, so nothing changes for them. A token for /api/v1/lenses reaches every LENS but no repo, so it cannot create a lens over any repo.

CONSEQUENCE: any new path that changes lens membership (an MCP lens tool, a bulk import) must run the same check with the lens's current members, or it reopens the escalation. Pinned by TestOAuthLensPatch_LensTokenCannotAddARepoItDoesNotReach and TestOAuthLensCreate_NeedsTheMembersInReach (internal/edge/web/token_audience_test.go), sabotaged at 16fb71bc.

WHAT THIS DOES NOT MEAN: it is not a permission check — `write` is still required (writeGate); reach only decides WHICH repos may be added. It does not re-check existing members on an unrelated edit.
