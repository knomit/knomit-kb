# A lens create or PATCH needs the caller to reach a repo BY NAME (auth.ReachesRepo) for every member it gives a role or pin the lens does not already give it — a new member, a changed write repo, or a read (uid, branch) pair the lens lacks; an unreachable one is answered exactly like an unknown uid

Rule (user ruling G4 — a lens token may not gain, through its lens, anything it cannot already do; PR #680 after review B1). In `checkLensMembers` (internal/edge/web/api/manage/handlers_lenses_hal.go), shared by POST /api/v1/lenses and PATCH /api/v1/lenses/{lens}, the exemption from the reach check is keyed on what the lens ALREADY HAS (`lensHasOf`: the write uid plus each read mount's (uid, branch); the zero value on create), not on the uid alone:
- the request's `write` uid is exempt only if it IS the lens's current write uid;
- a `reads` entry is exempt only if the lens already has exactly that (uid, branch) pair ("" = the member's read branch at resolve time, as stored).
Anything else whose repo the caller does not reach by name gets the same 400 "Unknown repo uid" body as a uid no repo has, so the refusal is no existence oracle.

Why each part: a lens MCP endpoint reads every member through the binding and writes to its write repo. Adding a repo would let a lens token read it; PROMOTING a read member to write would let it learn/update/retract into a repo it could only read (and give that repo agent + exp/* reads in knomit_changes); RE-PINNING a read member to another branch would let it read that branch through every lens tool and defeat the lens pinned-branch rule for knomit_changes. A lens token reaches NO repo by name (tokenRepoReach), so it can do none of these. It can still: re-send exactly the members and pins the lens has, drop members, and edit the description. Local callers and whole-API tokens reach every repo, so nothing changes for them. A token for /api/v1/lenses reaches every LENS but no repo, so it cannot create a lens over any repo.

(An earlier version of this fact listed "change the write repo to an existing member" as allowed. That was the implementer's choice, not a user ruling, and review B1 showed it widens the token; it is now refused.)

CONSEQUENCE: any new path that changes lens membership, roles or pins (an MCP lens tool, a bulk import) must run the same check against the lens's current (write, (uid, branch)) state, or it reopens the escalation. Pinned by TestOAuthLensPatch_LensTokenCannotAddARepoItDoesNotReach (add, re-role, re-pin) and TestOAuthLensCreate_NeedsTheMembersInReach (internal/edge/web/token_audience_test.go), each check sabotaged at a committed SHA.

WHAT THIS DOES NOT MEAN: it is not a permission check — `write` is still required (writeGate). A mount's `source` (verify metadata) is not compared. It does not re-check members the request leaves out.
