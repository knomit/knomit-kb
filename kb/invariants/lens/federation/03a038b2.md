# Every lens defect so far lived at the union boundary, where a value correct INSIDE one mount is mount-relative and silently wrong when pooled — incomparable ranks turned a retrieval depth into a browse window, per-mount default axes cut highlights by a different ruler than the union ranks by, and a mount-relative path in an aggregate payload resolved against the write repo

A value that is correct within a single source becomes wrong the moment it crosses into a union of sources whenever its meaning is relative to that source, and because a per-source step looks identical whether or not its output is pooled, the defect appears at exactly the field or path where the union's semantics diverge from a single source's, and nowhere else.

Three verified instances, three different mount-relative quantities:
- RANK. Per-mount relevance ranks are NOT comparable across mounts (the union fuses by reciprocal rank rather than merging on a shared key), so bounding each mount's candidates is a legitimate retrieval DEPTH. Commit timestamps ARE comparable, so on the recency path the same per-mount cap became a WINDOW: a mount's 501st-newest fact was unreachable at every offset and the chrono list disagreed with the dashboard by exactly the hidden count. The constant was split — a search depth kept as is, and the recency path requesting offset+limit per mount, which is provably sufficient because a row in the global page is always within its own mount's first offset+limit rows. 'It is documented as deliberate' was not a reason to stop reading: the mechanism was written down, the consequence to a browsing user was not.
- AXIS. Each mount's stats cut its top-N highlights by that mount's OWN default axis, so when the caller names no axis and mounts disagree — the NORMAL case, since the UI sends none and mounts routinely default differently — every mount's highlights were cut by a different ruler than the pooled union ranks by. The correction pins all mounts to the resolved pooled axis and re-fetches; because only highlights are axis-dependent, the corrective pass must re-fetch highlights alone through a narrow method that calls the SAME implementation the full stats call uses, not re-run the whole stats, and that narrow call uses the axis it is given without falling back to the branch default. An explicit `?axis=` skips the correction and is the measurement control.
- PATH. A store highlight's path is mount-RELATIVE; every list-shaped lens read qualified its rows, but the stats endpoint is an AGGREGATE payload whose highlights were the only path-bearing field, so the rule 'every lens read qualifies its paths', applied per handler shape rather than per field, missed it and every read-mount highlight 404'd against the write repo. Qualify AFTER write-first dedup, never before: dedup keys on the relative path so that one fact living on two mounts collapses to the write mount; qualifying first gives the copies different keys and both survive. A test had encoded the unqualified path as expected output while believing it tested ordering.

The same boundary explains two sibling facts: a motif term resolves per branch, so a lens must widen every term to its merged cluster's members before the fan-out or a mount spelling it differently contributes zero; and a query vector computed per mount is N identical inferences, so it is computed once above the fan-out.

WHAT THIS DOES NOT MEAN: it does not say per-mount bounds are wrong — the search depth stays; it does not make the axis correction free (it is still a second highlights fan-out); it does not authorize qualifying paths anywhere before the dedup merge; and where to look next is any lens response that is not a list of facts but carries a path, a rank or a per-mount default somewhere inside it.
