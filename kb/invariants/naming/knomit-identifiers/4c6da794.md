# Three different things are called "knomit" — and as of caaeac09 the MCP server KEY is no longer one of the immovable ones: it is derived per scope, and nothing may look it up by literal

"knomit" names several distinct things that look identical in code. Renaming the wrong one breaks the Claude integration wholesale.

**1. The MCP server KEY in `.mcp.json` — CHANGED 2026-08-14 (commits 45902a74, caaeac09).** This used to be the constant `"knomit"`, and the old rule was NEVER rename it, because the `mcp__knomit__*` tool namespace that every `/knomit-*` skill named by hand depended on it. That coupling is gone:

- Skills now name tools BARE (`knomit_learn`, not `mcp__knomit__knomit_learn`), so they resolve under any key.
- `claude init` DERIVES the key from the scope: `serverKey(repoName, lens)` returns `knomit-<lens>` or `knomit-<repo>`, prefixed unconditionally so the mapping is injective. The old constant made a second `claude init` collide, which is why two knomit servers could never coexist in one project.
- Nothing may look the server up by literal key. `mcpBinding` in `tools/bridge/claude/helpers.go` now selects by `filepath.Base(srv.Command) == "knomit-bridge"`.

**The trap this replaced, which is still the shape to watch for.** The old rule warned that a rename "does not fail loudly — the tools simply stop resolving." That is exactly what happened during the change: the templates were re-keyed and `mcpBinding` still read `cfg.MCPServers["knomit"]`, so every hook fell through to the basename fallback — repo mode against a directory-named repo, and worse, a LENS-scoped project silently demoted to repo mode, the precise wrong-repo hazard `mcpBinding`'s contract forbids. It was caught in code review, not by tests, because every `mcpBinding` test hand-built `.mcp.json` with the literal key rather than going through `runInit`. **When changing anything about this key, grep for the literal AND add a test that pipes `runInit` output into the consumer** — hand-built fixtures cannot catch a producer/consumer split.

**New consequence: ambiguity must fail safe.** Two knomit servers in one project is now possible, and there is no principled answer to "which repo do the hooks bind to?". `mcpBinding` reports ambiguity and `resolveWriteRepo` skips with `"multiple_knomit_servers"` rather than binding to an arbitrary one and running post-edit against the wrong repo.

**2. The MCP protocol server NAME** — `NewMCPServer("knomit", …)` in `internal/mcp/server.go`. This is the `serverInfo.name` advertised in the initialize response. It is NOT the same string as (1) and was not touched by the change; Claude Code builds the tool prefix from the config key, not from this. Do not conflate them.

**3. The git COMMITTER identity** — `knomit` / `knomit@local` on every commit the store writes. Product identity; stays.

**4. The binary and app-state names** — `cmd/root.go` `Use: "knomit"`, `~/.knomit`, `Library/Application Support/knomit`. Stay.

Historically there was a fifth: the default repository name, itself "knomit" — a genuine collision (product=knomit AND default KB=knomit). Renamed to "trunk" (2026-06), then "core" (2026-06-28), then the concept was removed entirely (2026-08-07) — see the no-default-repo invariant. Repo names are now purely the user's choice.

**WHAT THIS DOES NOT MEAN.** It does not mean the key is now free-form and unexamined: it is derived by exactly one function, it must stay injective across scopes, and it is length-bounded so `mcp__<key>__knomit_hypothesize` stays under the API's 64-character tool-name limit. It also does not mean items (2)–(4) became renameable — they did not. And it is still true that breakage here is silent and lands at a distance, in skills and `.mcp.json` files rather than next to the definition.
