# Three different things are called "knomit" — the MCP server name is the one that must NEVER be renamed, because the mcp__knomit__* namespace depends on it

"knomit" names several distinct things that look identical in code. Renaming the wrong one breaks the Claude integration wholesale.

1. **The MCP SERVER name** — the `.mcp.json` block key and the `cfg.MCPServers["knomit"]` lookup in `tools/bridge/claude/helpers.go`, plus `NewMCPServer("knomit", …)`. This string determines the `mcp__knomit__*` tool namespace that EVERY `/knomit-*` skill, hook, and template depends on by name. NEVER rename it. A rename does not fail loudly — the tools simply stop resolving under the names the skills call.

2. **The git COMMITTER identity** — `knomit` / `knomit@local` on every commit the store writes. Product identity; stays.

3. **The binary and app-state names** — `cmd/root.go` `Use: "knomit"`, `~/.knomit`, `Library/Application Support/knomit`. Stay.

Historically there was a FOURTH: the default repository name, which was itself "knomit" — a genuine collision (product=knomit AND default KB=knomit). It was renamed to "trunk" (2026-06), then "core" (2026-06-28, because "trunk" read as git trunk-based development), and finally the concept was removed entirely (2026-08-07) — see the no-default-repo invariant. Repo names are now purely the user's choice and collide with nothing.

WHAT THIS DOES NOT MEAN: this is not a style note about avoiding the word. It is specifically that (1) is load-bearing at a distance — the code that would break lives in skills and .mcp.json files, not next to the definition — so a "consistent rename" refactor across the codebase is exactly the change that breaks it.
