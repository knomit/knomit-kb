# Three different things are called "knomit" — and as of caaeac09 the MCP server KEY is no longer one of the immovable ones: it is derived per scope, and nothing may look it up by literal

"knomit" names several distinct things that look identical in code. Renaming the wrong one breaks the Claude integration wholesale.

**1. The MCP server KEY in `.mcp.json` — CHANGED 2026-08-14/15 (commits 45902a74, caaeac09, d7141821).** This used to be the constant `"knomit"`, and the old rule was NEVER rename it, because the `mcp__knomit__*` tool namespace that every `/knomit-*` skill named by hand depended on it. That coupling is gone:

- Skills now name tools BARE (`knomit_learn`, not `mcp__knomit__knomit_learn`), so they resolve under any key.
- `claude init` DERIVES the key from the scope, and the key names the AXIS as well as the product: `serverKey(repoName, lens)` returns `knomit-lens-<lens>` or `knomit-repo-<repo>`. The old constant made a second `claude init` collide, which is why two knomit servers could never coexist in one project.
- Nothing may look the server up by literal key. `mcpBinding` in `tools/bridge/claude/helpers.go` selects primarily by `filepath.Base(srv.Command) == "knomit-bridge"`.

**Naming the axis is what makes the key injective — the `knomit-` prefix alone did NOT.** The first cut of `serverKey` returned `knomit-<lens>` or `knomit-<repo>` and its doc comment claimed "the prefix is applied unconditionally, so the mapping from scope to key is injective." That claim was false, and the counterexample is the configuration the change exists to enable: repos and lenses are SEPARATE namespaces validated by the same `repos.IsValidName`, so a lens may share a name with a repo — naming a lens after the repo it writes to is the natural naming — and `--repo eng` and `--lens eng` both derived `knomit-eng`. Two `.mcp.json` entries with one key silently drop an entry: the exact clobbering the derivation removed, re-created one level down. `knomit-repo-` and `knomit-lens-` are fixed-length and differ, so no repo key can equal a lens key for any names (a repo literally named `lens-eng` yields `knomit-repo-lens-eng`). `TestServerKey_IsInjective` enforces it. **Generalise the lesson, not the fix: a prefix shared by two namespaces is not a namespace.**

Applying the prefix unconditionally is still load-bearing for the other half — skipping it when the name already carries it is many-to-one by construction (`web` and `knomit-web` both map to `knomit-web`).

**The trap this replaced, which is still the shape to watch for.** The old rule warned that a rename "does not fail loudly — the tools simply stop resolving." That is exactly what happened during the change: the templates were re-keyed and `mcpBinding` still read `cfg.MCPServers["knomit"]`, so every hook fell through to the basename fallback — repo mode against a directory-named repo, and worse, a LENS-scoped project silently demoted to repo mode, the precise wrong-repo hazard `mcpBinding`'s contract forbids. It was caught in code review, not by tests, because every `mcpBinding` test hand-built `.mcp.json` with the literal key rather than going through `runInit`. **When changing anything about this key, grep for the literal AND add a test that pipes `runInit` output into the consumer** — hand-built fixtures cannot catch a producer/consumer split.

**Consequence: ambiguity fails safe, but only on a REAL conflict.** Two knomit servers in one project is now possible, and when they name different scopes there is no principled answer to "which repo do the hooks bind to?" — `mcpBinding` reports ambiguity and `resolveWriteRepo` skips with `"multiple_knomit_servers"` rather than binding to an arbitrary one and running post-edit against the wrong repo. Two refinements keep that fail-safe from firing on configs that have an unambiguous answer:

- **Match tiers.** A COMMAND match is proof; a `knomit-`shaped KEY is a guess (it exists so wrapper scripts, renamed symlinks, versioned binaries and `go run` keep binding). A guess must not dilute proof: key matches count only when nothing matched on command. Otherwise one real bridge beside an unrelated server that merely borrowed the namespace (`knomit-notes`) counted two matches and disabled every hook, telling the user to remove a knomit entry they do not have.
- **Same-target dedupe.** Entries resolving to the same `(repo, lens)` are not ambiguous. `.mcp.json` is merge-required, so re-running init drops a companion and the obvious merge leaves the pre-existing entry beside the freshly derived one, both naming the same repo. A fail-safe that fires there fires on nothing.

**2. The MCP protocol server NAME** — `NewMCPServer("knomit", …)` in `internal/mcp/server.go`. This is the `serverInfo.name` advertised in the initialize response. It is NOT the same string as (1) and was not touched by the change; Claude Code builds the tool prefix from the config key, not from this. Do not conflate them.

**3. The git COMMITTER identity** — `knomit` / `knomit@local` on every commit the store writes. Product identity; stays.

**4. The binary and app-state names** — `cmd/root.go` `Use: "knomit"`, `~/.knomit`, `Library/Application Support/knomit`. Stay.

Historically there was a fifth: the default repository name, itself "knomit" — a genuine collision (product=knomit AND default KB=knomit). Renamed to "trunk" (2026-06), then "core" (2026-06-28), then the concept was removed entirely (2026-08-07) — see the no-default-repo invariant. Repo names are now purely the user's choice.

**WHAT THIS DOES NOT MEAN.** It does not mean the key is now free-form and unexamined: it is derived by exactly one function, it must stay injective across scopes AND across axes, and it is length-bounded (`maxServerKeyLen` = 39, leaving `maxScopeNameLen` = 27 for the name itself) so `mcp__<key>__knomit_hypothesize` stays under the API's 64-character tool-name limit. It does NOT mean "prefixed with `knomit-`" is sufficient for injectivity — that was the exact false claim above. It also does not mean items (2)–(4) became renameable — they did not. And it is still true that breakage here is silent and lands at a distance, in skills and `.mcp.json` files rather than next to the definition.
