# In-process chat calls are served under a context copied from mcpHTTPContext plus the unscoped mount's markers; the cursor owner is the per-chat endpoint, so one chat cannot resume another's cursor even for the same principal

inProcessTransport.requestContext (internal/edge/mcp/inprocess.go) mirrors web.mcpHTTPContext: empty clientsessions.WithHTTPInfo, the principal, and the ceiling, repo reach and lens reach ONLY when the caller supplied them (nil means the edge attached none), plus WithEndpoint(<chat endpoint>), repos.WithSessionScoped and a fresh repos.PinRecorder (what SessionBindingMiddleware adds on /api/v1/mcp). The kernel-verified pid is deliberately not copied: a chat has no socket peer.

The principal is attached to every call, so OpenInProcessSession REFUSES a zero Principal (error 'no principal'); the HTTP side attaches one only when the auth edge produced one, the chat has no such case.

The endpoint must be unique per chat (/api/v1/chats/<id>): with the principal it owns tool-session cursors and tasks (kb/invariants/mcp/ownership/endpoint-and-principal/d870cc94.md). Sabotage evidence: replacing the endpoint with a constant makes chat B resume chat A's query cursor (TestInProcessSession_CursorOwnedPerChat fails).

Close: InProcessSession.Close stops recording BEFORE store.End (stopRecording takes the write side of recMu; record holds the read side across RecordRequest). A call still in flight when Close runs completes but records nothing, because Store.Touch sets ended_at back to NULL and a late record would revive the ended row (TestInProcessSession_CallFinishingAfterCloseLeavesTheRowEnded; removing the stopRecording call fails it).

Consequence: if mcpHTTPContext gains a field, requestContext must gain it too. Does NOT mean the permission gate is bypassed: gatePermission and gateBinding wrap each handler at registration and see this principal. Server-to-client notifications are deliberately discarded (SetNotificationHandler is a no-op), as in mcp-go's own transport.
