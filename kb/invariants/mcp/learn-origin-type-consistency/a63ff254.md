# knomit_learn REJECTS origin×type mismatches: distilled requires type=synthesis; discovered requires type=synthesis or hypothesis

knomit_learn validates the (origin, type) pair via fact.Origin.ValidateForType before writing: origin=distilled is accepted only when type=synthesis (the only type the distill pipeline emits); origin=discovered is accepted only when type=synthesis (forward bridge) or type=hypothesis (backward bridge). origin=authored (or omitted) pairs with any type. The check runs only on explicit origin input in LearnHandler — pipeline writers (ApplyDistillDecisions, applyDiscoveredProposals) set origin directly through the store and enforce their own type sanity.

**Consequence:** an agent that sets origin=discovered on a source-transcribed observation (the 2026-07-15 newsletter-ingestion incident: 15 facts) now gets a hard error steering it to authored, instead of silently polluting the corpus. Since knomit_update cannot change origin, this rejection is the only thing standing between a wrong guess and a retract+re-learn cleanup.

**What this does NOT mean:** it does not make authored+synthesis invalid — that pair is still accepted at learn time (and an origin-LESS synthesis fact still parses back as distilled via the legacy frontmatter heuristic in ParseFact; the schema's 'omit → authored' prose holds for every type except synthesis).
