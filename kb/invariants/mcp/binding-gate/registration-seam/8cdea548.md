# The binding handle gate must wrap each tool handler AT REGISTRATION — mcp-go's tool middleware chain is skipped on the task-augmented dispatch path, so a middleware gate would leave knomit_review and knomit_hypothesize callable ungated

knomit's `binding` handle gate wraps every gated tool handler AT REGISTRATION — `gateBinding(...)` is applied to `t.handler` inside the `AddTool` loop in `internal/mcp/server.go` — and NOT in a `server.Hooks` callback, and NOT via `server.WithToolHandlerMiddleware`. Keep it there.

Three structural properties of mcp-go force this. All three are true of `github.com/mark3labs/mcp-go v0.45.0`, the version pinned in go.mod. The CLAIMS are the structural relationships and they are what to re-check on any version bump; the line numbers are dated support, not the anchor.

1. `OnBeforeCallToolFunc` RETURNS NOTHING. A BeforeCallTool hook can observe a call but cannot hand the handler a different context, so it cannot put the resolved Binding where the handlers already read it. (server/hooks.go:91 as of v0.45.0)
2. `handleToolCall` computes `shouldExecuteAsTask` and RETURNS `handleTaskAugmentedToolCall(...)` BEFORE it builds the `toolHandlerMiddlewares` chain. (server/server.go: the return at ~1504, the chain at ~1512 as of v0.45.0)
3. `executeRegularToolAsTask`, the goroutine that path starts, calls `regularTool.Handler(taskCtx, request)` DIRECTLY. (server/server.go:1713 as of v0.45.0)

CONSEQUENCE a consumer must act on: a tool whose registration declares TaskSupport can be invoked with `params.task` set, and that call reaches exactly the handler that was registered — no middleware chain is applied to it. `knomit_review` and `knomit_hypothesize` both declare `mcpgo.WithTaskSupport(mcpgo.TaskSupportOptional)`, and both are WRITE tools. A middleware-based gate would therefore have left two write tools reachable with no binding handle at all: the precise defect the gate exists to prevent. Registration is the one seam BOTH dispatch paths share, because both of them call the handler that was registered.

THE MISREADING TO AVOID: this is not "mcp-go's middleware is unreliable". On the synchronous path the chain is applied correctly and in reverse order, as documented. The rule is narrower and sharper: the chain is NOT applied on the task-augmented path, so any cross-cutting concern that must hold for EVERY call — authorization, routing, quota, audit — belongs at registration rather than in middleware, for as long as any tool declares TaskSupport. Reading this fact as a general verdict on middleware would forbid a seam that is perfectly safe for tools that cannot take the task path.

WHEN THIS STOPS BINDING: if `knomit_review` and `knomit_hypothesize` ever drop `WithTaskSupport`, no registered tool can take the task-augmented path and a middleware gate becomes safe again. `grep -rn TaskSupport internal/mcp/` settles it in one command — do that before concluding the fact still applies.

WHAT ENFORCES PART OF IT: `TestToolRegistrations_GateAndSchemaAgree` (internal/mcp/binding_gate_test.go) asserts that every `gateRequired` tool declares the `binding` argument in its schema and that only `knomit_bind` is ungated, so a NEW tool wired past the gate is caught. Nothing automatically catches a future MOVE of the gate into middleware — that move is what this fact forbids, and it is why the rule is written down rather than left to the test.

The three call sites were read in the vendored module itself rather than inferred from documentation, and the check is reproducible: `go list -m -f '{{.Dir}}' github.com/mark3labs/mcp-go` locates the source, and the three functions are greppable by name.
