# A stub of an ended turn's tool result offers 'call it again' only when the tool-effects table marks the (tool, action) Replay (read-only AND idempotent); anything unlisted, a write, knomit_bind, review/hypothesize current and page, and any query, explain or materialize call carrying a cursor are NOT replayable and their stub says not to repeat the call

internal/edge/mcp/tool_effects.go: every row of toolEffects states Replay (ReplayYes / ReplayNo; the zero value ReplayUnstated fails TestToolEffects_EveryRowStatesReplay, so a new (tool, action) cannot default silently). Replay means read-only AND idempotent: calling it again returns the same data and has no effect on the session. mcp.Replayable(tool, args) is the one function the chat hands the llm package (ToolWindowSpec.Replayable; nil means never); it classifies through ClassifyCall (one table), and returns false for an unlisted tool or action, undecodable args, and any argument named in the row's ReplayNotWith that is set and non-empty.

Replay=true: knomit_query, knomit_explain, knomit_materialize, knomit_changes, knomit_skill, knomit_repos, knomit_experiment list. Replay=false: knomit_bind (read-only for the KB but changes session binding state), every write, knomit_review page (advances) and current, knomit_hypothesize current, all start/answer/takeover rows, experiment open/sync/commit/rollback.

Two findings that differ from the intuitive table: (1) knomit_review current and knomit_hypothesize current are read-only rows but NOT replayable: Pipeline.Current takes the session's next step when nothing is outstanding (nextItem -> handlePhase -> AdvancePipelineSessionPhase). (2) A `cursor` on knomit_query, knomit_explain or knomit_materialize dequeues the page it names (DequeuePaths), so the same call returns the NEXT page; their rows carry ReplayNotWith [cursor]. knomit_changes' cursor is a stateless keyset and explain's history_cursor is stateless: they replay. A first query/explain/materialize call creates a new tool session (cursor) each time; that is accepted as no change to existing state.

Consequence: the stub (ToolWindow.StubEnded, adaptive providers only) uses the replayable text only for such a call, so the model is never invited to repeat a write or a state-advancing read. Misreading to avoid: Replay is not ReadOnly; do not mark a row Replay because it is read-only. A new read-only row that touches session state must be ReplayNo.

Loader results are never stubbed: ToolWindow.StubEnded skips any tool_result whose tool_use is load_tools (LoadToolsName), whatever its length and whatever Replayable says. They are small, and EvictedResult tells the model 'Load them again if you need them'; a stub saying 'Do not repeat this call unless the person asks' would contradict that and make the model hesitate to reload. The rule keys on the real loader name, not on Replay. Likewise nothing is stubbed when the model reports no context window (usable room 0): there is nothing to derive the excerpt size from. Pinned by TestStub_LoaderResultsAreNeverStubbed and TestLoop_UnknownWindowStubsNothing.
