# A handle may carry a branch pin OR an experiment, never both — the pair is refused at the write and fails loudly at the read, because ranking two sources of "where does this handle point" is a rule nobody remembers

`binding_handles.branch` and `handle_experiments.experiment` both answer "where does this handle point" for a repo pin. Rather than rank them, the pair is made UNREPRESENTABLE: SetHandleExperiment reads the handle's branch first and refuses when it is non-empty, which is every handle knomit_bind mints today (it always writes "").

Because the write refuses it, the combination is unreachable — and that is exactly why the READ fails loudly rather than quietly preferring one: ResolveSessionBindingOnExperiment returns a BindingMalformed SessionBindingError naming both values. Same treatment ResolveSessionBinding already gives its own unreachable case (a lens pin with a non-empty branch). An unreachable branch that silently picks a winner is how a precedence rule survives unnoticed until the day it decides something.

TWO NARROWER THINGS THAN ITS NEIGHBOURS. The mcp-surface decision settles WHERE the active experiment rides and what the tool surface looks like; handle-model describes what a handle maps to. This fact is only about the COLLISION between the handle's two possible pins, which neither of them discusses.

WHY IT MATTERS LATER: binding_handles.branch is inert today but exists so per-handle branch switching is a behaviour change rather than a migration. When that lands, this guard is what turns the collision into a visible failure instead of a silent redirect — so the person implementing it must DECIDE the interaction rather than discover that one already quietly won.
