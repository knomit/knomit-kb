# EVERY load-bearing field of client_sessions is inferred from ordinary request traffic, never asserted by an authority — the id is unverified, the identity self-declared, the presence derived, and `initialized` scoped to one process — so the row is an observational trail and must never gate anything

Four decisions and two gotchas, taken separately, each look like an ordinary design choice. Read together they share one shape, and the shape is the thing to know before touching this subsystem.

EVERY COLUMN IS EVIDENCE, NOT AN ASSERTION — WITH ONE EXCEPTION SINCE 2026-09-22, MARKED BELOW. For each field there is a claim it LOOKS like it makes and a weaker claim it actually supports:

- `id` (the Mcp-Session-Id) looks like proof this server minted the session. It is not: mcp-go's default `StatelessGeneratingSessionIdManager` validates the prefix and UUID SHAPE only, never whether this process issued the id, so a fabricated id is accepted — `internal/mcp/actor.go` measured exactly that.
- `instance_id`, `hostname`, `cwd`, `pid`, `parent_app`, `branch` look like facts about the client. They are SELF-DECLARED request headers, or for direct HTTP callers derived from unverified request data (ip + User-Agent + declared clientInfo — NOT port, which was rejected because a client opens new TCP connections during one session and ip+port would split one session into many instances).
- `last_seen_at` looks like liveness. It is the timestamp of the last request that happened to arrive; live/idle/dead are DERIVED at read time and nothing writes a status flip.
- `initialized` looks like "this client completed a handshake". It means only that THIS server process observed the initialize — a row rebuilt from request headers after a restart carries `initialized = 0` for a client that initialized perfectly well against the previous process.
- `request_count` looks like a message count. It counts requests that CARRIED a session id; the initialize request carries none (the id is minted in the RESPONSE), so a handshake-only client shows 0 and a bridge that initialized and made one call shows 1.
- `principal` — **THE EXCEPTION, AND IT IS NARROW.** This column was empty when this fact was written, reserved for future verified identity. F19 phase 1 (PR #243, merged `cec7c5c1`) FILLS IT for a caller arriving over the LOCAL AUTHENTICATED LISTENER, and the value's shape is per platform:
  - **unix** — `bridge:uid:<n>@socket`, the uid from the kernel (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` on darwin).
  - **windows** — `bridge:sid:<SID>@pipe`, the SID read by impersonating the named pipe's client (F19 phase 1b, PR #251, knomit#245). MEASURED end to end: a real `kb.exe` over the pipe produced `bridge:sid:S-1-5-21-…-1002@pipe`.

  Either way it comes from the OS and not from anything the client said, and which of the two a platform produces is `auth.LocalVia`. The OS's pid for that peer is recorded beside it in the `client_session_peers` side table, deliberately NOT replacing the self-declared `pid`, so a mismatch between what a client claims and what the OS saw stays visible — and it is genuinely per connection, not a constant: two `kb.exe` runs recorded `verified_pid` 10344 and 11824 against their own real pids. A row with no `principal` is a TCP caller and carries no verified identity at all.

THE WEAK DEFAULT IS UPSTREAM OF THE DESIGN, not beside it. Because the id manager accepts ids it never issued, `AfterInitialize`/`OnRegisterSession` fire only on a genuine initialize — so a hook-only registry would silently miss every client that outlived a restart. THAT is why recording lives in the HTTP dispatch layer, which sees every request regardless of how the id was minted, with the hook demoted to enrichment. The two-writer row shape and the existence of an `initialized` column are both downstream consequences of one dependency's default. A schema column exists because of a library's validation choice.

CONSEQUENCE, and it is still the point: NOTHING IN THIS TABLE MAY GATE, AUTHORIZE, OR ATTRIBUTE BLAME. That half is UNCHANGED by F19 phase 1, 1b or 2, and is enforced in the code that landed — permission lives in the `grants` table, keyed by `auth.Principal.String()`, and is read only through `auth.Allowed`; no gate reads `client_sessions` or `client_session_peers`. It remains a correlation trail for operators, consistent with the standing invariant that session handles are correlation and not identity.

SO READ THE TWO HALVES SEPARATELY, because the update changes one and not the other: the table now contains ONE field an authority asserted rather than a client, and it is still not an authorization input. "A verified column exists here" does NOT license gating on it — gate on `grants` via `auth.Allowed`, which is keyed by the same principal string and is the only check. Note that the principal string in this column and the key in `grants` are the same spelling BY CONSTRUCTION (`auth.Principal.String()`), which is why the boot seeding and the request-time middleware must derive it from one function — see the local-principal-has-one-spelling invariant.

CARRIED FROM THE SOURCES, because the synthesis must not smooth them away:

- Do NOT propose a held GET stream, a heartbeat endpoint, or bridge-side reconnect to "make presence exact". That option was considered, verified feasible in mcp-go v0.45.0, and rejected twice and firmly: direct HTTP callers must be first-class, and a long-lived connection breaks over the internet and through proxies that cut idle streams. The approximation is the accepted cost.
- The stateless manager is NOT an mcp-go limitation. `InsecureStatefulSessionIdManager` tracks issued ids, 404s unknown ones and honours DELETE. Switching is a deliberate decision with a consequence — stale bridges would fail loudly after a restart instead of silently continuing, arguably better but a change in observed behaviour — and the 2026-09-14 design deliberately left it alone.
- These rows are OPERATIONAL state, not knowledge. They do not conflict with "git is the only source of truth" any more than the registry does, and they must NEVER be written as facts.
- All three presence thresholds (dead 1h, hidden 3h, purge one week) are SETTINGS, not constants — operational policy, not corpus properties. Hiding at 3h and deleting at retention are separate policies, not one.
- Rows live in control.db rather than the per-repo `<name>.sessions.db` sidecar for two verified reasons: the sidecar is per repo, and a bridge bound to a lens spans several repos with no single repo to live in; and the sidecar is recreated empty on every Service.Open, so a restart would wipe the trail.
