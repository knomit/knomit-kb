# The handle is the only router ON THE UNSCOPED MCP MOUNT — nothing there resolves a binding from Mcp-Session-Id, an unknown handle hard-fails, and a `binding` on a URL-scoped mount hard-fails rather than being ignored; a URL-scoped mount may key state on the session because its URL already fixed the knowledge base

Three rules, and all three are load-bearing together. Dropping any one of them reopens the 2026-09-17 cross-binding incident.

1. NO SESSION LOOKUP. On the unscoped mount `/api/v1/mcp`, `web.SessionBindingMiddleware` does exactly two things: mark the context session-scoped, and install a `repos.PinRecorder`. It does NOT read `Mcp-Session-Id` and does NOT resolve a binding. A client may share one connection — and so one session id — across several independent logical jobs, so any state keyed on that id serves whichever job bound LAST.

2. REQUIRED HANDLE, HARD FAIL. Every tool except `knomit_repos` and `knomit_bind` requires the opaque handle as its `binding` argument on this mount. Missing ⇒ an error naming `knomit_bind` and the argument. Unknown ⇒ exactly `unknown binding handle — call knomit_bind`, which deliberately does NOT echo which handles exist: the handle is the only thing separating two callers on one connection, so enumerating live ones would hand one caller another's routing. There is no fallback of any kind — not to a session, not to a default repo, not to "the only repo".

3. URL-SCOPED REFUSES ON PRESENCE. When `repos.SessionScoped(ctx)` is false the repo comes from the path, and a `binding` argument is refused with `this endpoint is bound by its URL; do not pass binding`. Refused on PRESENCE, so an empty string is refused too. Ignoring it would be worse than failing: the caller believes it selected a base while the URL serves a different one — the exact silent-misroute shape the handle exists to remove.

THE HANDLE NOW ROUTES A THIRD THING (PR #236). Alongside the pin and the read branch it carries the caller's ACTIVE EXPERIMENT, in the sibling table `handle_experiments`, read next to the handle in `resolveHandle`. The three rules above are unchanged and apply to it unaltered — in particular rule 1: the experiment is keyed on the handle and NEVER on the session id, for the same reason and with a worse failure, since an experiment and its parent share an ontology by construction and a misrouted write would commit silently. Do not read "pin plus branch" as the complete list of what a handle decides.

AMENDED BY PR #240: THE HANDLE IS THE ONLY ROUTER **ON THE UNSCOPED MOUNT**. A URL-scoped mount may now carry session-keyed state (`mount_experiments`, keyed on `(session_id, mount_uid)`), because its URL has ALREADY fixed the repo or the lens. That state selects a BRANCH within one knowledge base and can never select the knowledge base itself — which is the whole of what the incident was about. Rule 1 is unchanged where it bites; what changed is that the unscoped mount is now named as its scope rather than left implied.

The permitted region, in reviewer2's words, because the value is in the exhaustiveness: **session state may choose a branch ONLY on a mount whose URL names the repo's own agent branch, or a lens's default — never `main`, never a foreign agent branch, never a mount naming an experiment.** Each exclusion is a hole that was open during review, not a hypothetical:

- `main`, and any non-writable branch, because `WriteBranch()` returns `""` there. A predicate that reads the BINDING cannot tell a URL naming `main` from a URL naming nothing, so deciding eligibility from the binding silently re-pinned a read-only mount onto a writable experiment.
- a foreign agent branch, for the same reason the rule exists at all.
- a mount whose URL NAMES an experiment (`/repos/{repo}/branches/exp:<name>/mcp`), because such a URL is an ADDRESS of the one it names. It serves that experiment and keeps its 404; opening a different one there creates it and refuses to switch.

Eligibility is therefore decided from the ROUTE, never from the binding — see `kb/invariants/mcp/experiments/mount-eligibility-from-the-route`. A connection with no MCP session id has nothing to key on and fails closed at both the middleware and `open`.

Keep the hard-fail rules above exactly as they are: PR #240 does not touch them, and rule 3 — a `binding` argument is refused on a URL-scoped mount — is what the new tests had to work around.

ENFORCING CODE: `resolveHandle` and the gate in `internal/mcp/binding_gate.go`; `internal/web/session_binding_middleware.go` for rule 1; `internal/web/mount_experiment_middleware.go` for the amendment. Guarded by `TestSessionBindingMiddleware_ResolvesNothingFromTheSessionID`, which mints a live handle and then uses that handle's own value AS the session id — the most favourable case any session-keyed lookup could have — and asserts no Binding appears; and by its sibling `TestSessionBindingMiddleware_ResolvesNoExperimentFromTheSessionID`, which does the same with a handle that is genuinely inside an experiment.

SCOPE, since several neighbouring facts cover adjacent ground and none of them states this rule: WHERE the gate must be installed is the registration-seam invariant; WHICH tools exist and which are gated is the tool catalogue; WHY the unscoped mount exists at all is the binding decision; WHY `knomit_repos` alone needs no handle is the discovery-tool decision. This fact is only about what may and may not decide the TARGET of a call.

WHAT THIS DOES NOT MEAN. It is not an authorization boundary: knomit has no authentication, anyone who can reach the endpoint can already reach every repo by URL, and a handle grants nothing new. The handle is unguessable only so a model cannot conjure a valid one from a repo name it has seen.
