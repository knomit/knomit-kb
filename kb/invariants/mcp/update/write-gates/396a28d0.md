# knomit_update's gates on every call: the final serialised bytes must parse and re-serialise identically (CR LF and a newline in the title fail); a CHANGED body must have an even count of ``` fence lines; title and body edge whitespace is trimmed, not rejected; ontology rules still skip .knomit/ paths

`knomit_update` (internal/mcp/update.go) applies these to the assembled fact, on BOTH the `updates.body` path and the `ops` path:

1. **Edge whitespace is trimmed, not refused.** `ParseFact` trims the title and body, so the file format cannot store leading or trailing whitespace on either. The handler trims both before the other gates, so a caller's trailing newline is not an error.
2. **Fences — only when the body changed** (`updates.body` or `ops` present): `fact.CheckFences` refuses an ODD number of lines whose first non-blank characters are ```` ``` ````. It is a parity count, not a CommonMark parse. A frontmatter-only update to a fact that already has an odd count is NOT refused, so legacy facts stay updatable.
3. **Ontology rules** (`fact.ValidateFact`) run for public facts and are skipped for `.knomit/<area>/` paths, unchanged.
4. **Roundtrip on the FINAL bytes** (`checkRoundtrip`, after the refs gate and `SerializeFact`): `ParseFact` then `SerializeFact` must reproduce the serialised string byte for byte. A CR LF pair (ParseFact normalises it) and a newline in the title (the heading splits) fail it. It runs on every update, frontmatter-only ones included.

Consequence: a REST or pipeline write path that wants the same bar should call `fact.CheckFences` and do the same parse/re-serialise compare — they live in `internal/fact` for that reason. The order in code is fences → ontology → refs gate → roundtrip, so when several fail, the fence error is the one reported.

WHAT THIS DOES NOT MEAN: there is no shrink guard, no anchor-mid-word check, no dry run — those were rejected in the ops decision. And `knomit_learn` does not run the fence or roundtrip gates; only update does.
