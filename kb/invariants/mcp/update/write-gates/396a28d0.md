# knomit_update's gates on every call: the write is a compare-and-swap on the blob it read; the final serialised bytes must parse and re-serialise identically (CR LF and a newline in the title fail); an edit must not turn an even count of ``` fence lines odd; title and body edge whitespace is trimmed, not rejected; ontology rules still skip .knomit/ paths

`knomit_update` (internal/mcp/update.go) applies these to the assembled fact, on BOTH the `updates.body` path and the `ops` path:

1. **Edge whitespace is trimmed, not refused.** `ParseFact` trims the title and body, so the file format cannot store leading or trailing whitespace on either. The handler trims both before the other gates, so a caller's trailing newline is not an error. `ops[].delta` is measured on the trimmed form, so it reports bytes actually stored.
2. **Fences — judged on the EDIT, only when the body changed** (`updates.body` or `ops` present): `fact.CheckFenceEdit(before, after)` refuses only when the body had an EVEN number of lines whose first non-blank characters are ```` ``` ```` and now has an ODD number. `before` is the existing body on both paths. A body that was already odd (valid CommonMark can be: a ```` fence quoting a ``` line, ``` inside a ~~~ fence, indented code) is never refused, and odd→even is a repair. It is a parity count, not a CommonMark parse.
3. **Ontology rules** (`fact.ValidateFact`) run for public facts and are skipped for `.knomit/<area>/` paths, unchanged.
4. **Roundtrip on the FINAL bytes** (`checkRoundtrip`, after the refs gate and `SerializeFact`): `ParseFact` then `SerializeFact` must reproduce the serialised string byte for byte. A CR LF pair (ParseFact normalises it) and a newline in the title (the heading splits) fail it; the error names the field (title, body, else frontmatter) and quotes where sent and read-back first differ. It runs on every update, frontmatter-only ones included.
5. **The write is a compare-and-swap.** The handler reads the fact with `ReadFactOpts{WithHash: true}` and commits through `FactIndex.WriteFactIfUnchanged`, which re-checks that the path's blob on the branch tip is still the one read INSIDE the branch write lock. If another write landed in between, nothing is written and the call is refused with `current_commit` = the write-branch tip. This holds with or without `if_commit`: without it, ops computed from stale bytes would otherwise silently overwrite the newer write. `if_commit` itself (bytes at that commit must equal bytes now) is checked before the write; the CAS is what makes it atomic.

Consequence: a REST or pipeline write path that wants the same bar should call `fact.CheckFenceEdit`, do the same parse/re-serialise compare, and write through `WriteFactIfUnchanged` with the blob it read. The order in code is fences → ontology → refs gate → roundtrip → CAS write, so when several fail, the earliest is reported.

WHAT THIS DOES NOT MEAN: only knomit_update runs the fence and roundtrip gates — knomit_learn, the pipelines and REST do not, and SerializeFact does not. Moving them into SerializeFact (so every write path shares them) is a known follow-up, deliberately not done in the PR that introduced them. There is no shrink guard, no anchor-mid-word check, no dry run — those were rejected in the ops decision.
