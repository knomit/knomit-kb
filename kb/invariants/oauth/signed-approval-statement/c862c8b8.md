# A fleet-root-key OAuth approval signs ONE canonical, domain-tagged, instance-bound statement — first line knomit-oauth-approve/v1 or knomit-oauth-deny/v1, then fingerprint, pending id, request digest, [subject, sorted scopes,] expiry, newline-joined with no trailing newline — and the verifier REBUILDS those bytes from validated fields, never verifying client-supplied bytes

THE BYTES (ApprovalStatement.Bytes, the only encoding):
- approve: `knomit-oauth-approve/v1`, <instance fingerprint>, <pending id>, <request digest>, <subject>, <scopes comma-joined, sorted>, <expires unix>
- deny: `knomit-oauth-deny/v1`, <instance fingerprint>, <pending id>, <request digest>, <expires unix>
Lines are joined with \n, and there is NO trailing newline.

Every field is validated before joining, so none can contain a separator:
- the fingerprint is 64 lowercase hex (pki.Fingerprint of the instance key);
- the id has a pending id's shape;
- the digest is RequestDigest's 64 hex;
- the subject matches subjectRE;
- scopes are grantable permission names (never admin), non-empty, without repeats;
- expires is a positive int formatted by strconv, so there is no sign and no leading zero;
- a deny carries no subject and no scopes.

WHY EACH CHOICE:
- **The first line is the domain separation (reviewer S2).** The same fleet root key signs X.509 TBS structures and CRLs, which are DER and start with 0x30. A tagged text statement can never verify as either, nor they as it. This is the rule for EVERY non-X.509 use of the fleet root key: sign a message whose first line is a `knomit-<purpose>/v<n>` tag, and require that exact tag when verifying. Phase 4's fleet-root-signed fleet policy will be the second user.
- **The verb lives in the tag.** An approve signature never verifies as a deny, nor the reverse.
- **Binding the fingerprint** stops a statement for one headless instance from working on another.
- **Binding the request digest (ruling R4).** The digest covers the requester-supplied fields: client_id, client_name, redirect_uri, resource and requested scopes. The operator signs over what they were SHOWN. The instance recomputes the digest from its own pending row and answers ErrStatementMismatch (409) when a relay showed the operator a different request.
- **Rebuild, then verify (S1).** SignedStatement carries the FIELDS plus a base64 signature. ApplySigned rebuilds the bytes and verifies over what it rebuilt, so there is no parse-after-verify gap. The JSON's `issuer` field is only a delivery address and is not signed.

VERIFICATION ORDER in Issuer.ApplySigned, each step with its named error:
1. malformed (400);
2. fleet root: <[tls].dir>/root.crt, read PER STATEMENT, so enrolment after boot works. Absent means ErrNoFleetRoot (503, never a 500): an unenrolled instance cannot do signed approval.
3. ed25519 signature (ErrBadSignature, 403);
4. own fingerprint (ErrWrongInstance, 403);
5. window, now − 5m < expires ≤ now + 10m + 5m, with the skew between two machines' clocks (ErrStatementExpired, 403);
6. replay table (ErrReplayed, 409);
7. pending row: unknown is 404; ErrStatementMismatch is 409;
8. then Approve or Deny, recorded as decided_by and granted_by `fleet-root:<first 8 hex of the root fingerprint>` (oauth.FleetRootLabel; it was `master:<fp8>` before PR #513). That string is deliberately not a principal spelling, so it can never match a grants row.

OPERATOR SIDE (`knomit oauth approve|deny <id> --sign <issuer> [--dir <fleet root dir>] --instance <fp>`; since PR #512 `--dir` defaults to `<home>/fleet` since PR #513, was `<home>/master`):
- The instance fingerprint is the OPERATOR's input (ruling W2). It must appear in the fleet root's issued.jsonl with a serial not in revoked.jsonl, and is never taken from the public description.
- The command fetches GET <issuer>/oauth/pending/<id>, recomputes the digest from the fetched fields (and refuses one that does not match), and prints everything %q-escaped with the redirect HOST first before signing.
- The confirmation comes AFTER the request printout and depends on where the root key is (pki.OpenRoot, PR #512):
  - key in the passphrase-encrypted root.key (file custody): `--passphrase-file -` reads the passphrase after the printout, and typing it is the confirmation;
  - key in the OS keychain (the default after init-root): NO passphrase is asked (none guards a keychain-held key, so a prompt would guard nothing); instead a y/N prompt (`Sign this statement? [y/N]`, anything but y/yes aborts with nothing signed), or `--yes` in place of it. `--passphrase-file -` is accepted but no passphrase is read.
  - A passphrase FILE (not `-`) without --yes is refused up front in both custodies: a file answers no question.
- Without --scopes it signs oauth.DefaultCeiling (D13) explicitly, so the statement always names what it grants.

MISREADING TO AVOID: the signature proves the FLEET ROOT KEY approved; it does not identify the client program. The operator still judges the request from the printed, requester-supplied fields, which is why the redirect host is printed first.

WHAT THE KEYCHAIN PATH DOES NOT MEAN: the y/N answer is consent, not authentication. Under keychain custody any process running as the operator's user can sign with `--yes`; that is the D9 ruling (kb/decisions/pki/root-custody/keychain/614c3df0.md), not a bug in this command.
