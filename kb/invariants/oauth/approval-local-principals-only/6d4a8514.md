# OAuth approvals are accepted ONLY from a local-listener principal (Via == auth.LocalVia: the unix socket, or the named pipe on Windows), OR — since phase 3b — from the anonymous loopback principal holding admin whose request carries the full browser proof; never from a certificate or bearer principal whatever it holds, and only on the plain router

GET /api/v1/oauth/pending, POST …/{id}/approve and …/{id}/deny exist only when [oauth] is configured, only on the PLAIN router (NewAPIRouter adds them after apiRouter; the OAuth listener's router never has them — a bearer there gets 404), behind Server.requireLocalOrSameOriginAdmin. writeGate still runs first on the POSTs, so the caller also needs write.

THE GATE ADMITS EXACTLY TWO CALLERS:
1. p.Via == auth.LocalVia (ViaSocket on unix, ViaPipe on Windows): no further proof. This is 3a's rule (master ruling R5), unchanged; `knomit oauth pending|approve|deny` use it through localAPIClient, which dials auth.DialLocal and nothing else.
2. (3b) p is anonymous@none (Kind anonymous, Via none), NOT on the TLS listener (auth.IsTLSListener), from a loopback RemoteAddr, auth.Allowed(…, admin) through Server.grants() — AND browserProof(r) passes. See kb/decisions/oauth/browser-approval-proof for what the proof is and why.

EVERYONE ELSE IS REFUSED with 403 naming the principal and the reason: an operator or instance CERTIFICATE holding admin by row (the TLS listener serves the same Handler, and every browser header is forgeable by a non-browser client), a bearer principal (tested at the gate function with admin in its effective set), and anonymous without admin.

WHY NOT Require(admin): the anonymous loopback principal holds admin by default ([auth].loopback_default), and a browser page can reach loopback TCP but not the socket; admin alone would let any page the operator visits approve a request (CSRF), and a same-host proxy is loopback too.

TESTING CONSEQUENCES: an 'anonymous is refused' test cannot tell a Via check from an 'ID must be non-empty' check — anonymous has no id; TestPendingAPI_OnlyLocalPrincipals and TestBrowserGate_OnlyAnonymousLoopback drive an OPERATOR CERTIFICATE holding admin by row. The TLS-listener and loopback checks on the browser branch are belts BELOW AuthMiddleware (which never produces anonymous@none there today), so only TestBrowserGate_BeltsBelowAuthMiddleware, calling the gate directly, can see them removed.

CONSEQUENCE ADDED (PR #488, merge 2104fd6d, 2026-10-12; by code reading, not a live approval): branch 1 of the gate (Via == auth.LocalVia, no further proof) now also admits the DESKTOP UI. Its webview used to be anonymous@none over TCP and so needed branch 2's browser proof; since #488 every UI call is made by the desktop process's /api/ proxy over the local socket/pipe, so the server sees bridge:uid:<n>@socket (Windows: bridge:sid:<SID>@pipe), Via == LocalVia, and approve/deny from the UI needs no browser proof. Any script running in a desktop webview window can therefore approve a pending OAuth request on a desktop whose config enables [oauth]. Recorded as a gotcha (kb/gotchas/desktop/auth) with the security review tracked in issue #492; this fact's rule is unchanged and correct, but the sentence 'a browser page can reach loopback TCP but not the socket' no longer describes the desktop's own page. WHAT THIS DOES NOT MEAN: the TLS/OAuth listeners, the browser build and `knomit serve`'s served SPA are unchanged.
