# [oauth.idp].allowed_subjects holds ONLY github-<numeric id> entries (optionally capped: "github-583231 read"), never a login and never empty — a login is refused at load because a renamed GitHub login can be claimed by someone else, and an empty list is refused because it would admit nobody

The allow list for consent path 3 (external IdP, F19 phase 3c) is parsed and validated at config load (config.OAuthIDPConfig.validate, parseAllowedSubject):
- Each entry is `github-<id>` matching ^github-[1-9][0-9]{0,19}$: the provider name, a hyphen, GitHub's numeric user id without leading zeros. The same string is the knomit token subject (principal host:github-<id>@token). The spelling has NO colon (ruling R3) so it passes the issuer's subjectRE unchanged and Principal.String()'s <kind>:<id>@<via> stays unambiguous.
- An entry may be followed by permission names that CAP that person's token ceiling (ceiling = DefaultCeiling(requested) ∩ entry scopes); names are checked with auth.ParseSet and admin is refused.
- A LOGIN is refused, in any form containing '@' (github-@octocat) or not matching the id shape. Why (ruling R4, reviewer B4): the plan first accepted `github:@login` resolved 'once at boot', which is EVERY boot; GitHub documents that a renamed account's old username becomes available for anyone to claim, so the next restart would silently admit the newcomer. The operator resolves a login ONCE, deliberately, with `knomit oauth idp resolve github <login>` (GitHub's unauthenticated GET /users/{login}) and pastes the id. knomit never resolves logins at run time or at boot.
- An EMPTY list is a load error ('would admit nobody'), not a silently useless provider. A duplicate id is a load error.
- [oauth.idp] needs [oauth] issuer and addr; provider must be "github"; a second [oauth.idp] table is a TOML redefinition error, so 'exactly one provider' holds by construction.

CONSEQUENCE: matching is on the stable id only. A login change never changes identity; a deleted-and-recreated account has a new id and is a new, unlisted subject. The login is display-only (consent page and log) and is never stored.

WHAT THIS DOES NOT MEAN: taking an id OFF the list does not by itself end that person's access at once — see the refresh-time check fact for path-3 families; access tokens already issued run to their TTL.
