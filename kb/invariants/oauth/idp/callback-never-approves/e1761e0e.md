# In consent path 3 the provider callback NEVER approves: only an explicit POST /oauth/idp/decide from knomit's consent page does (Origin = issuer origin, Sec-Fetch-Site same-origin when sent, the request's binding cookie, a single-use 5-min form token) — because GitHub completes its own step silently for a user who authorized the app before, so a callback that approved would turn one click on a forwarded link into a token for whoever parked the request

THE ATTACK THIS CLOSES (3c reviewer B1, ruling R1): an attacker parks their own request (their CIMD client, their redirect, their PKCE), reads the pending id from the waiting page, and sends an allow-listed human a link to <victim's instance>/oauth/idp/start/<id>. GitHub documents that a user who already authorized the app 'won't be shown the OAuth authorization page … this step will automatically complete'. A callback that called Approve would hand the attacker a token acting as the victim via /wait — the victim would see only 'approved' afterwards. A GitHub identity proves WHO is at the browser, never that they agree to THIS request.

THE FLOW (internal/oauth/idpflow.go):
- /oauth/authorize, with [oauth.idp] configured, sets the request's browser-binding cookie (see the binding-cookie fact) and stores its SHA-256 in oauth_pending_idp.
- GET /oauth/idp/start/{id}: shape check, row lookup, cookie must match the row (else 403 BEFORE the provider is contacted), undecided and unexpired; then ONE live state per request (a new start replaces the old): state → {pending id, binding hash, PKCE verifier}, expiry min(10 min, the request's). Unknown ids retain nothing.
- GET /oauth/idp/callback: a request carrying `iss` is refused (a knomit authorization response misrouted here — GitHub sends none); the state is consumed on first use whatever follows; the cookie is re-checked against the row; error=access_denied (Cancel at GitHub) decides nothing and leads back to /wait; Identify; then the allow list and the per-subject cap. An unlisted identity, or a cap that leaves nothing of DefaultCeiling(requested), DENIES the request as idp:github:<id> and is logged at INFO with id and quoted login so the operator can add them — this is self-denial, since only the parking browser can reach the callback (S12). Otherwise it renders the CONSENT PAGE and keeps a single-use form token (hashed) for 5 min.
- POST /oauth/idp/decide: the checks in the title, then Approve(id, github-<id>, ceiling, idp:github:<id>) or Deny, clear the cookie, 303 to /oauth/authorize/{id}/wait. /wait is what delivers the code or access_denied to the client's redirect_uri (ruling R2): once the tab left for GitHub nothing else polls it.

THE CONSENT PAGE IS THE ONLY DEFENCE against a victim who opens an attacker's AUTHORIZE URL themselves (their own browser then holds a valid cookie). So it leads, before any button, with 'Approving will send a login code to <redirect host> for client <client id>', then the full redirect URI, client name, resource, the ceiling it will get, and 'you are signed in at GitHub as <login> (github-<id>)'. No script, no autofocus, no auto-submit; html/template escaping; CSP default-src 'none' plus form-action 'self'.

MISREADINGS TO AVOID: (1) 'the cookie stops the attack' — it stops a forwarded START link and login CSRF on the callback, not a forwarded authorize URL; that case is the consent page's. (2) 'GET /oauth/idp/decide is refused only by the method' — the mux pattern is POST-only AND the handler reads PostForm, so a GET carries no decision either way. (3) The pending row stays the real single-decision guard (Store.Decide WHERE decision = ''); the form token being single-use is checked first so a replay is refused as a spent token (400), not by the row (409).

Each rule has a test in internal/oauth/idpflow_test.go against idptest's fake GitHub; 25 sabotage mutants at the branch, 24 caught, the survivor is misreading (2).
