# In consent path 3 the provider callback NEVER approves: only an explicit POST /oauth/idp/decide from knomit's consent page does (Origin = issuer origin, Sec-Fetch-Site same-origin when sent, the request's binding cookie, a single-use 5-min form token) — because GitHub completes its own step silently for a user who authorized the app before, so a callback that approved would turn one click on a forwarded link into a token for whoever parked the request

THE ATTACK THIS CLOSES (3c reviewer B1, ruling R1): an attacker parks their own request (their CIMD client, their redirect, their PKCE), reads the pending id from the waiting page, and sends an allow-listed human a link to <victim's instance>/oauth/idp/start/<id>. GitHub documents that a user who already authorized the app 'won't be shown the OAuth authorization page … this step will automatically complete'. A callback that called Approve would hand the attacker a token acting as the victim via /wait — the victim would see only 'approved' afterwards. A GitHub identity proves WHO is at the browser, never that they agree to THIS request.

THE FLOW (internal/oauth/idpflow.go):
- /oauth/authorize, with [oauth.idp] configured, sets the request's browser-binding cookie (see the binding-cookie fact) and stores its SHA-256 in oauth_pending_idp.
- GET /oauth/idp/start/{id}: shape check, row lookup, cookie must match the row (else 403 BEFORE the provider is contacted), undecided and unexpired; then ONE live sign-in per request (a new start replaces the old): state → {pending id, binding hash, PKCE verifier}, expiry min(10 min, the request's). Unknown ids retain nothing.
- GET /oauth/idp/callback: a request carrying `iss` is refused (a knomit authorization response misrouted here — GitHub sends none); the state is consumed on first use whatever follows; the cookie is re-checked against the row; error=access_denied (Cancel at GitHub) decides nothing and leads back to /wait; Identify. A callback whose sign-in was REPLACED by a newer start while Identify ran decides nothing and touches none of the newer sign-in's state (final review I1: drop() clears byID only if it still points at the sign-in being dropped). Then the allow list and the per-subject cap: an unlisted identity, or a cap that leaves nothing of DefaultCeiling(requested), DENIES the request as idp:github:<id> and is logged at INFO with id and quoted login so the operator can add them — self-denial, since only the parking browser reaches the callback (S12). Otherwise it renders the CONSENT PAGE and keeps a single-use form token (hashed) for 5 min.
- POST /oauth/idp/decide: Origin must equal the issuer's origin AS A BROWSER SERIALIZES IT (no default port: an issuer written https://h:443 compares as https://h, final review M4), Sec-Fetch-Site same-origin when sent, the cookie, the token; then Approve(id, github-<id>, ceiling, idp:github:<id>) or Deny, clear the cookie, 303 to /oauth/authorize/{id}/wait. /wait delivers the code or access_denied to the client's redirect_uri (ruling R2): once the tab left for GitHub nothing else polls it.

THE CONSENT PAGE IS THE ONLY DEFENCE against a victim who opens an attacker's AUTHORIZE URL themselves (their own browser then holds a valid cookie). So it leads, before any button, with 'Approving will send a login code to <redirect host> for client <client id>', then the full redirect URI, client name, resource, 'Access it will get, AT MOST: <ceiling>' (and, for a subject granted before, that its existing grants stand and may be less — R5), and 'you are signed in at GitHub as <login> (github-<id>)'. No script, no autofocus, no auto-submit; html/template escaping.

TWO BROWSER FACTS THE HTTP-LEVEL TESTS COULD NOT SEE (both found in Chromium, both now pinned by tests):
- The consent page's Referrer-Policy is strict-origin, NOT no-referrer: under Fetch's 'append a request Origin header', a form POST from a no-referrer page sends Origin: null even to its own origin, so the Origin check refused every real approval (final review C1). strict-origin still never sends the page URL (the callback query) as a Referer. The test fixture derives Origin from the page's policy instead of setting it by hand.
- The OAuth pages' CSP has NO form-action: Chromium applies form-action to the whole redirect chain of a form submission, and the decide POST's chain ends at the client's redirect_uri on another origin — form-action 'self' blocked the last hop and the client never got its code.
The whole flow was then run in Chromium against the real issuer and the fake GitHub: waiting page → sign-in → consent → Approve → the client's loopback callback received code, iss and state.

MISREADINGS TO AVOID: (1) 'the cookie stops the attack' — it stops a forwarded START link and login CSRF on the callback, not a forwarded authorize URL; that case is the consent page's. (2) 'GET /oauth/idp/decide is refused only by the method' — the mux pattern is POST-only AND the handler reads PostForm, so a GET carries no decision either way. (3) The pending row stays the real single-decision guard (Store.Decide WHERE decision = ''); the form token being single-use is checked first so a replay is refused as a spent token (400), not by the row (409). (4) 'Origin: null is a browser quirk we can accept' — no: the page is made to send a real Origin, and null stays refused.
