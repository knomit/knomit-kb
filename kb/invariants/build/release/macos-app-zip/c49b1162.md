# The macOS release .app.zip must expand to EXACTLY ONE top-level entry, or self-update fails after download and after signature verification

The macOS desktop release artifact (`Knomit-<semver>-<platform>.app.zip`, built by the `release-desktop` target) MUST expand to exactly one top-level entry: `Knomit.app`. Wails `pkg/updater/extract.go` extracts the downloaded archive into a scratch dir, calls `os.ReadDir` on it, and rejects anything where `len(entries) != 1` with `updater: archive must contain exactly one top-level entry, got N`.

`ditto -c -k --sequesterRsrc` VIOLATES this. `--sequesterRsrc` hoists HFS metadata into a second top-level `__MACOSX/` directory. The bundle's only such metadata is `com.apple.provenance`, which macOS stamps on downloaded files and which is worth nothing to preserve — so the flag produced a fatal second entry and no benefit. Verified: repackaging with plain `ditto -c -k --keepParent` yields one entry, and `diff -r` reports the extracted tree identical to the source bundle.

**Consequence — what to never do:** do not add `--sequesterRsrc`, `--rsrc`, or any ditto/zip flag that emits `__MACOSX/`, and do not put a README, checksum file, or second bundle alongside `Knomit.app` in the same archive. Any of these breaks self-update for every client.

**Enforcement:** the `release-desktop` recipe asserts the top-level entry count immediately after `ditto` and fails the build on anything but 1, printing the offending entries.

**WHAT THIS DOES NOT MEAN:** this is NOT caught by signing, by ed25519 verification, or by the `tools/appcast` feed tests. The failure lands in the updater's extract step — AFTER the download completes and AFTER the signature verifies. A violating archive therefore publishes green, passes verification on every client, and fails at install forever, on a release that can no longer be changed. The Makefile guard is the only automated layer that can see it; it was found by running the manual verification gate against a real installed build.
