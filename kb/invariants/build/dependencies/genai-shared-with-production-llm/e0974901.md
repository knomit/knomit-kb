# google.golang.org/genai is imported by BOTH release tooling and the production LLM subsystem — never `go get` it from release-tooling work

`google.golang.org/genai` appears in go.mod's FIRST require block — the direct-dependency block, not the `// indirect` one — pinned at v1.49.0. It has exactly TWO importers in the tree, and that pairing is the whole trap:

1. `internal/llm/gemini.go` — `GeminiAdapter`, the PRODUCTION LLM subsystem (streaming generation, context caching).
2. `tools/relnotes/distill.go` — release-note summarisation, added in PR #69.

**The operational rule: never run a bare `go get google.golang.org/genai`.** Because it is already a direct dependency, `go get` with no version resolves to latest and upgrades silently — no new require line appears, so the diff looks like nothing happened. During PR #69 this bumped v1.49.0 → v1.66.0, dragging 17 minor versions of unreviewed SDK drift into `internal/llm` inside a change that had nothing to do with the LLM subsystem. Caught and reverted in commit f897fcc4; the merged branch changes no dependency at all.

To upgrade genai deliberately: do it on its own branch, pin an explicit version, and exercise `internal/llm` (generation, streaming, and the context-cache path) before merging.

**WHAT THIS DOES NOT MEAN:** it is NOT "a release-tooling dependency" merely because you encountered it while working in `tools/relnotes`. Working inside release tooling is precisely the context in which the production consumer is invisible, and it is the production consumer that carries the blast radius. Symmetrically, this is not an argument to vendor two copies or split the dependency — one pin shared by both importers is the intended shape.
