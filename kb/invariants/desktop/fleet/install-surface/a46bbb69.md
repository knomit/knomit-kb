# Fleet trust material (root, instance certificate, CRL) and the listener config that opens a network port change ONLY through the desktop Settings window's Wails bindings or the fleet routes that are served on the LOCAL listener only (create, join, leave, decommission, revoke's CRL copy; RequireLocalVia) — never through a route a network peer or a browser page can reach — and those bindings (InstallBundle, PublicKeyLine, SaveSettings, RestartServer) refuse any caller window but Settings

Two rules, and each needs the other. (knomit#256)

**1. No route reachable from the network installs trust material.** Every route on the app handler is also served on the mTLS listener and by `knomit serve`, so an install route would be callable by enrolled remote peers. `pki.InstallBundle` may be called from exactly three production files (the third since PR #518, merge 537f2019):
- (`cmd/identity.go`, the operator at a terminal, was a caller until PR #525 deleted the `knomit identity install` verb.)
- `tools/desktop/identity.go`: the Settings binding.
- `internal/repos/fleet_create.go`: the fleet create installs this instance's OWN leaf, which it has just issued from the fresh root it minted, so the material never comes from a request. Its one route, POST /api/v1/fleet/create, is behind `RequireLocalVia` (router.go): served on the unix socket or Windows named pipe only, 403 for an mTLS peer and for a browser page on loopback TCP.

`test/archtest` `TestInstallBundleHasOnlyTheListedCallers` (renamed from ...TheTwoFrontEnds in PR #518; the list is `installCallers`) enforces this. It parses every non-test file for the tag sets "" and "desktop" across darwin, linux and windows, follows any import alias of `internal/pki`, and fails on any other caller, route or not. The pin is on the function name, so it still holds after knomit#299 changed the signature to `InstallBundle(dir, keyPath, raw, InstallOptions{ExpectInstalledRoot})`; the CLI and the desktop must pass the root they read as installed (the create passes the empty InstallOptions{}, meaning it expects NO root installed, which its trust_installed pre-flight has just checked and which makes a concurrent install fail with RootDiffers and roll the create back) (see kb/invariants/pki/install/expected-root-under-lock/eac8d325.md).

**2. Being a Wails binding is NOT enough.** Bindings are app-global, and the main window (the `web/` UI on the same origin) can call every one: see `kb/gotchas/desktop/wails/bindings/caller-window`. So these methods take `context.Context` first and refuse with `errNotSettingsWindow` unless `callerIsSettings(ctx)` holds, meaning the call context's `application.WindowKey` window is named `settingsWindowName` (`knomit-settings`, set in `settingsWindowOptions`):
- `InstallBundle`: writes trust material.
- `SaveSettings`: can set `[tls].addr`, which opens a network port on the next launch.
- `PublicKeyLine`: feeds enrolment. It is not secret, but gated by ruling.
- `RestartServer` (since #504; was `RestartApp`): restarts the supervised server process, which re-reads every config key.

(The `SaveSettings` bullet above predates the ports: since #504 it also writes `http`/`host` and triggers the reload, see the last paragraph.)

`GetIdentity` is read-only and ungated. The JS call signatures are unchanged, because Wails injects the context.

**What the Settings gate does NOT cover (knomit#299).** The window gate decides WHO may call InstallBundle; it says nothing about WHICH fleet root the user agreed to. A bundle pasted from the clipboard can be written by any local process, so since #299 the binding also refuses a root the user has not seen — a first install as `root_unconfirmed`, a move as `root_differs`, each carrying the bundle root's fingerprint and the principal its certificate names — and installs only on a second call that sends the shown pair back (`confirmation_stale` otherwise). A renewal under the installed root needs no confirmation. The window gate still runs first on every call.

**What is proven where.**
- Tests prove only OUR check: a context whose window is not Settings, or that has no window, is refused and writes nothing (`TestFleetIdentity_BindingsRefuseAnyCallerButTheSettingsWindow`). The confirmation shapes are proven by `TestFleetIdentity_FirstInstallNeedsTheRootThatWasShown` and `TestFleetIdentity_ReplaceRootNeedsTheFingerprintsThatWereShown`.
- That page script cannot choose that window rests on reading wails v3.0.0-beta.3, and is NOT reproduced by any test:
  - `webViewAssetRequest.Header` (`pkg/application/application.go`) overwrites `x-wails-window-id` always, and `x-wails-window-name` ONLY WHEN THE WINDOW HAS A NAME;
  - `getTargetWindow` (`messageprocessor.go`) resolves by that name first;
  - Wails gives every unnamed window the name `window-<id>` (`webview_window.go`), which is why the name is always overwritten.
- A Wails upgrade that stops default-naming windows, or stops overwriting the header, would let a page name itself `knomit-settings`. Re-read those three places on every Wails bump.
- A real-webview check that the Settings window's name reaches the binding is a release-time item.

`NativeService`'s exported method set is pinned (`TestFleetIdentity_NativeServiceMethodSetIsPinned`), because every exported method is a new IPC entry point that every window can reach. #299 added no method: the confirmation rides on InstallBundle's existing (raw, confirmFrom, confirmTo) arguments.

**Misreadings to avoid:**
- "Local processes can call bindings." They cannot. The asset server is an in-process scheme handler, and the desktop build links neither Wails' `server` nor its `mcp` mode (`-tags desktop` only).
- "The Settings gate replaces rule 1." It does not: an HTTP route would bypass the window check entirely.
- "The Settings gate means the user chose this fleet." It does not; the root confirmation above is what binds the install to what the user saw.

VERSION NOTE (Wails v3.0.0-beta.28 since PR #487, merge 0486a84f; 2026-10-12): the 'Re-read those three places on every Wails bump' item was done for beta.28, by reading the module source, not by a real-webview run. application.go (webViewAssetRequest.Header, L388-393) still overwrites x-wails-window-id always and x-wails-window-name when the window has one; messageprocessor.go getTargetWindow still resolves by that name first; webview_window.go (L344-346) still names every unnamed window window-<id>. The 'wails v3.0.0-beta.3' pins in the body are the version the gate was first reasoned at. The Settings-only gate, the method-set pin and rule 1 (no HTTP route installs trust material) are untouched by PR #488.

Two additions from that PR that a reader of this gate should not misread: (a) the new /api/ proxy in the asset handler is an HTTP route into the SERVER, not into bindings; it strips x-wails-* so the server never sees the window, which is irrelevant here because no install route exists (rule 1), and bindings still read the headers in-process. (b) The 'knomit-sse' Wails Stream is reachable from any window and is not gated by c.Window(); it carries only GET reads under /api/v1/, so it is not an install or listener-config surface, and a future stream that carried writes would need its own window gate.

THE SIGNAL/EVENT LOOP IS A THIRD LEGITIMATE PATH, AND STILL NO ROUTE (knomit#497, merge 4a9018c4): a running `knomit serve` re-reads knomit.toml and applies listener changes ([tls].addr, http/host/port) when it receives SIGHUP, the Windows reload event or `knomit reload`. That changes no config and installs no trust material: it only re-reads files the operator or Settings already wrote, and the OS delivers the signal/event only to same-user processes, so the 'two front ends' list above is about WRITING config and trust, and the loop does not add a writer. Rule 2's concern (a route reachable by enrolled mTLS peers) is why the trigger is not an HTTP route and not a pipe message. Enforced by test/archtest TestListenersApplyHasOnlyTheSignalLoopAsCaller (by method name and file, so cmd/serve.go as a whole is allowed). What is reloadable and what is not: kb/decisions/serve/reload/f44e4370.md. MISREADING: 'a reload can open a port, so Settings no longer needs its window gate': SaveSettings still gates who may WRITE [tls].addr; reload only applies it sooner than the next launch.

SETTINGS NOW DRIVES THE RELOAD (knomit#504, merge 1c6a0934; 2026-10-13). (1) The gated set is InstallBundle, PublicKeyLine, SaveSettings and RestartServer; the method-set pin lists RestartServer, and a non-Settings caller of SaveSettings is refused before any write or reload (TestSaveSettings_NonSettingsCallerIsRefusedBeforeAnyWriteOrReload, with a positive control from Settings; the gate on RestartServer is pinned by TestRestartServer_RestartsTheServerOnlyFromSettings). Both gates were sabotaged red. (2) SaveSettings, after writing the moved keys (HTTP port scope: kb/decisions/desktop/settings/http-port-scope/ad18a6d0.md), asks the server to reload by a Go call to serveraddr.RequestReload and returns an ack read from server.json. That is still no HTTP route and no pipe message: the reload client has exactly three production callers (cmd/reload.go, internal/serveraddr/reload.go, tools/desktop/native.go), pinned by TestReloadRequestHasOnlyTheCLIAndTheSettingsBindingAsCallers, see kb/invariants/serve/reload/reload-client/6ba726a8.md. The third-path paragraph above stands: the OS trigger adds no writer. MISREADING: 'SaveSettings reloads, so a page script could open a port' - it still cannot call the binding unless it is the Settings window, and the reload re-reads only the file Settings wrote. MISREADING: 'RestartServer is harmless because it only restarts' - restarting drops every live SSE stream and MCP session of the server, so it is gated like the writers; in attach mode it is refused naming the pid (kb/decisions/desktop/settings/attach-mode/279d5688.md).

UPDATE (PR #518, merge 537f2019). Rule 1 is 'no route reachable from the network', not 'no route at all': one route reaches an install, and it is local-listener-only. The archtest pins the CALLERS, not the routes, so it fails on any production code, route or not, that starts calling install outside the three files; a new caller is a reviewed decision recorded in `installCallers`. MISREADINGS: 'the create route is a hole in rule 1': it installs only the leaf it just issued from its own fresh root, behind RequireLocalVia, and refuses outright if any trust material is already installed (trust_installed); 'RequireLocalVia is the Settings gate': it is not, it restricts the transport, not the window, and the desktop's Wails bindings are unaffected. The archtest header (install_callers_test.go) says 'never installable over a network route: only the local listener, behind RequireLocalVia'; CRL-only install (installCRLCallers) still has no production caller.

UPDATE (PR #525, merge fd991d4f). The caller list `installCallers` is now `internal/repos/fleet_create.go`, `internal/repos/fleet_membership.go` (the join) and `tools/desktop/identity.go` (the Settings binding, kept until the Fleet UI of PR 7). The join installs a REQUEST-SUPPLIED bundle, the first time the local listener accepts trust material from a request body: POST /api/v1/fleet/join, behind RequireLocalVia like create, after checking that the bundle's leaf is for THIS instance's key (ErrKeyMismatch) and agent id, refusing while any trust material is installed (trust_installed), passing InstallOptions{} (expects no root installed), and uninstalling it again when anything later in the join is refused. Consent to the root is the operator supplying the bundle; the answer returns `root_fingerprint`. `installCRLCallers` (pki.InstallCRL) now lists `internal/repos/fleet_membership.go`: the master's revoke route installs the CRL it just signed under its own installed root, which is its first production caller. `pki.Uninstall` (leave, decommission, the undo of a refused join, the create rollback) is the inverse; it is not pinned by an archtest list. MISREADINGS: 'the local listener never accepts trust material from a request' is now false for join (the bundle) and PUT /fleet/root (the root key files, written to <home>/fleet, not to [tls].dir); 'RequireLocalVia is the Settings gate' stays false; 'a browser page on loopback TCP can call join' is false (403, tested for every local-only route over loopback TCP and over mTLS).

## UPDATE (PR #528, verified at merge e417fd76): the desktop has NO install binding any more

READ THE TITLE AS HISTORY FOR THE BINDINGS. NativeService.InstallBundle is gone (tools/desktop/identity.go keeps GetIdentity and PublicKeyLine only), together with the Settings window's Install-bundle flow and its root_unconfirmed / root_differs confirmations in the desktop (the pki install classes themselves stay in internal/pki). Trust material now changes ONLY through the fleet routes served on the LOCAL listener (create, join, leave, decommission, revoke's CRL copy, and GET/PUT/DELETE /fleet/root, host and follow, all behind RequireLocalVia); the desktop's main window reaches them over the local socket, joining through POST /fleet/join. test/archtest/install_callers_test.go still pins the production callers of pki.InstallBundle to internal/repos/fleet_create.go and internal/repos/fleet_membership.go, and of pki.InstallCRL to fleet_membership.go. The rule that matters survives: never a route a network peer or a browser page can reach. SaveSettings and RestartServer still refuse any caller window but Settings.
