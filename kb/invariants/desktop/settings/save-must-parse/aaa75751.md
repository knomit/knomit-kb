# The desktop Settings save decodes its edited knomit.toml with config's own parser into config.Config BEFORE writing or toggling anything, and refuses an edit that would not load; and an optional key whose empty value means 'off' ([tls].addr) is never CREATED empty

`tomledit` edits knomit.toml as text, and only within a subset of TOML. Two shapes are outside it: an inline table (`tls = { dir = "…" }`) and a dotted key. On those shapes, setting a key can produce a file BurntSushi refuses ("Key 'tls' has already been defined"), and then knomit no longer starts.

So `applySettings` runs `toml.Decode(edited, &config.Config{})` after all edits and before the autostart toggle and the atomic write. On an error it returns without changing anything. Do not remove this because "tomledit is tested": its tests pin that it FAILS on these shapes (`tomledit.go` package doc).

Second rule: `configKeys` entries marked `optional` (currently only `[tls].addr`, where "" and absent both mean the listener is off) are skipped when the value is empty AND `tomledit.Has` finds no existing assignment. Without this, EVERY save, even a log-level toggle, appended `[tls]\naddr = ""` to files that never had a `[tls]` table. `Has` uses the same line matching as `SetString`, so the two cannot disagree about whether the key exists. Consequence: clearing an existing addr DOES write `addr = ""`, because the key exists.

An env-owned key (`KNOMIT_TLS_ADDR` and the other `configKeys` variables) is still never written, as before.
