# A desktop home is a FRESH install only when it holds NEITHER knomit.toml NOR control.db (and neither stat fails otherwise); a home with either file is an upgrade and is never written to

RULE (knomit#504, merge 1c6a0934; tools/desktop/freshinstall.go). `ensureFreshInstallDefaults` runs in app.go right after the single-instance lock and BEFORE config.Load and the first spawn. It writes `http = false` into `<home>/knomit.toml` only when `isFreshInstall(home)`: neither `knomit.toml` nor `control.db` exists (os.Stat reports not-exist for BOTH). Any other outcome of either stat, including a permission error or an unreadable home, counts as not fresh, so the default is never written over somebody's data root. The write is O_EXCL (a server or a person that wrote a file first wins), mode 0600, after the home is made private (privdir.Ensure). A home that does not exist yet is fresh.

CONSEQUENCE: a fresh desktop install starts with no TCP listener (server.json `http` empty, listener reason `off`, Settings scope Off); the user turns the port on in Settings. The reasoning is in the HTTP-port-scope decision under kb/decisions/desktop/settings.

MISREADING: 'a home with a knomit.toml but no control.db is fresh' (or the reverse) is WRONG. Either file alone makes it an upgrade: a hand-written toml means the user configured it; a control.db alone means a server already ran there, with the default `http = true`. Tests pin a fresh-but-not-yet-created home, an existing toml, and control.db alone (TestEnsureFreshInstallDefaults; the control.db branch was sabotaged red).

KNOWN RESIDUAL: a CLI `knomit serve` that starts on a home with neither file creates control.db within seconds; a desktop launched in that window would see a fresh home. It is the first seconds of a first run, and attach mode is detected separately. The comment in freshinstall.go ('off until you turn it on') goes stale once Settings turns the port on; the file is written once and never rewritten.
