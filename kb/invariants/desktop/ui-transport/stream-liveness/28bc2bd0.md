# Every knomit-sse stream carries a desktop ping every 15 s (ssePingInterval, TrySend), and WailsEventSource reopens a socket that has carried no frame for 45 s (STALE_STREAM_MS): onclose alone does not detect a stream Wails dropped

RULE: the desktop's serveSSEStream starts pingStream once the subscribe frame is valid; it sends {t:'ping'} every ssePingInterval (15 s) with TrySend (never Send: a ping must not block or queue behind a backlog) until the StreamConn context ends. WailsEventSource stamps lastFrameAt when a socket is created and on EVERY frame (ping, open, event, error, even an unreadable one) and runs one interval (STALE_STREAM_MS / 9, 5 s) that, when a socket exists and nothing arrived for STALE_STREAM_MS (45 s = three pings), drops the socket, goes CONNECTING, dispatches error and reopens with the normal backoff and the last event id. close() clears the interval, and so does a refusal (error closed:true), through the same release(): a CLOSED source holds no timer (kb/gotchas/web/sse/closed-paths).

WHY: Wails v3.0.0 reaps a stream session after 10 min without a poll and recreates it empty on the next poll with no close for the old connections (kb/gotchas/desktop/wails/streams/session-reap), so before this the page's chat stream stayed OPEN with nothing behind it and the page saw no chat event until reload (and, under the server's old 60 s chat grace, every new chat ended on stream_grace 60 s after it started; since fix-chat-outlives-page chats end only on DELETE or server stop, kb/decisions/chat/lifetime/outlives-page/bd2a87a7.md, so a dead stream now costs events, never chats).

CONSEQUENCES: a desktop change that removes or slows the ping below STALE_STREAM_MS / 3 makes every quiet stream reconnect every ~45 s (each reconnect is a ready, so every chat on screen and the rail reload); change ssePingInterval and STALE_STREAM_MS together. The browser build is untouched (native EventSource, no watchdog). After a suspension shorter than the reap but longer than 45 s the page may reconnect once spuriously before the queued pings arrive; that is harmless (ready, reload).

WHAT THIS DOES NOT MEAN: WailsEventSource itself does not reconnect a stream the server REFUSED (error closed:true stays final, as for EventSource). Recovery from CLOSED is one layer up, in chatEvents.ts's hub (the page's one chat stream only): on an `error` event whose stream has readyState CLOSED, while the hub still has a subscriber or watcher, it opens a fresh openEventStream(chatEventsUrl()) on the same Hub (subscribers, watchers and rows survive; the new stream's `ready` makes every subscriber reload) after REOPEN_INITIAL_MS 1 s, doubling to REOPEN_MAX_MS 30 s, reset to 1 s by a `ready`, with no give-up while anyone listens. An error while CONNECTING is left to the transport's own retry. The last subscriber or watcher leaving clears the pending reopen timer and closes the stream; the timer re-checks `hub === h` so it never reopens a replaced or closed hub. Other streams opened with openEventStream get no such reopen. (The stale bound used to be compared with the server's 60 s chat grace; that grace no longer exists, so the bound now only decides how long a page goes without events.)
