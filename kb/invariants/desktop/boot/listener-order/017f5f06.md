# The desktop's bootServer opens its listeners in a fixed order — plaintext TCP, local socket/pipe, RequireLocalListener, TLS, lockfile — and every fallible step undoes ALL before it, the TLS listener included

bootServer (tools/desktop/boot.go) runs: (1) netutil.Listen, loopback only; (2) auth.ListenLocal; (3) auth.RequireLocalListener; (4) app.OpenTLSServer — the LAST listener; (5) lockfile.Write — LAST of all.

WHY THIS ORDER: (5) last means no lockfile ever advertises a port nothing serves (the rule since #248). (4) after (3) means a [auth].require refusal never has a network-facing port to release. When (5) fails, the TLS server and its listener are closed AND the base context is cancelled, which stops the pki.Server re-judging loop OpenTLSServer started.

HOW IT IS CLOSED: every error path closes the LISTENER as well as the http.Server (closeTCP, closeTLS), and shutdown calls closeTLS after tls.Shutdown. http.Server.Close and Shutdown close only listeners that Serve has already registered; Serve runs on a goroutine, so a failure or shutdown right after boot can beat it and leave the port bound (measured: the addr-free tests failed until the listeners were closed directly). A Settings restart relaunches straight after shutdown, so a still-bound [tls].addr would bring the successor up without its TLS listener.

CONSEQUENCE for changes here: add a new fallible listener BEFORE the lockfile and give it a close on every later error path; a test that re-binds the address after the failure is what catches a missed one (sabotage at 31f4072d: dropping closeTLS on the lockfile path, or opening TLS before RequireLocalListener without a close, each turned a named test red).

NOT MEANT: this does not make the TLS listener count towards [auth].require. It serves fleet peers, never the local user; require still needs the local socket or pipe (kb/invariants/auth/require-needs-a-bound-listener).
