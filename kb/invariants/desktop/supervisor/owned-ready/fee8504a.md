# The desktop supervisor marks its own child ready only when the home's server.json names the child's pid (answeredByChild) - which holds only because `knomit serve` writes server.json (Advertise) before it serves anything and a supervised serve that cannot write it exits 2

INVARIANT (knomit#517, merge fe86cc9c). tools/desktop/supervisor.go runChild calls setReady() (owned, attached=false) only when a socket probe succeeded AND answeredByChild(c) is true: serveraddr.ReadLock of this home's server.json succeeds and its PID equals c.pid, the pid of the child the supervisor itself spawned (the child is exec'd directly, no re-exec). A probe that succeeds while server.json is missing, unreadable or names another pid is 'not ours yet': runChild logs once ('a server answers on the socket that is not our child') and keeps probing until our child answers or exits. This closes the window described in kb/gotchas/desktop/supervisor/readiness-probe-meets-holder/d9b774ee.md: another server answering while our doomed child is still alive (about to exit 3) used to be taken as ours.

WHAT IT RELIES ON (verify these before changing either side). (1) cmd/serve.go calls ls.Advertise() (writes server.json naming os.Getpid(), atomic temp+rename) after every listener is opened and BEFORE the first serveInto, so nothing answers on any listener before the file exists (kb/invariants/app/listeners/open-order/87bcfaa4.md). (2) A supervised serve that cannot write server.json exits 2 (config, no retry) instead of serving without it, and a serve that does not hold the socket writes no file (kb/decisions/serve/lockfile-write-failure/92ec05ed.md; kb/decisions/serve/supervised-mode/30ad3125.md). So our child's first answer always finds its own pid, and a foreign holder's answer never does.

CONSEQUENCE. Moving Advertise after Serve, or letting a supervised serve skip or defer server.json, leaves the desktop stuck in 'starting' forever: the child answers but server.json never names it, nothing times out and nothing calls fail(). Changing where the supervisor's lockPath resolves (it must equal the child's KNOMIT_HOME server.json) or making the bundled server re-exec (pid would differ) does the same.

NO ESCAPE HATCH (review finding F1, low, unreachable at HEAD). If server.json never names the child while the child is alive and serving, the loop has no bound. Do NOT add a timeout that falls back to ready: that reopens exactly the race this invariant closes (any foreign holder would be marked owned after the timeout). If hardening is wanted, log the pid server.json does name (or the read error) in the 'not our child' line and escalate to Warn after N polls.

MISREADINGS. (a) 'server.json is a liveness signal': it is read only AFTER a successful socket probe, to decide WHO answered; a stale file from a crashed server is harmless because our child overwrites it before its first answer. (b) 'pid match proves ownership in all cases': pid reuse by our child onto a stale file's pid plus a foreign holder that wrote no file degrades only to the pre-#517 brief owned-ready (review F2), never to a hang. (c) Attach detection (which sets attached) is still the supervisor's waitForHolder -> probe -> attach path, not this check.

Restart side: restartServer now returns errAttachedServer{pid} when the server that answers after the restart turns out to be attached (kb/decisions/desktop/settings/attach-mode/279d5688.md).
