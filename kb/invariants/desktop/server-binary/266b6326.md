# The desktop locates its bundled server ONLY bundle-relative: next to the running executable after resolving symlinks, never via PATH, and a missing binary is a typed ServerBinaryMissingError naming the expected path

tools/desktop/serverbin.go (added in #500) finds the shipped `knomit`: `serverBinaryFor(exe)` resolves the desktop executable through symlinks (`filepath.EvalSymlinks`), then looks for `knomit` (`knomit.exe` on Windows) in that real directory. It NEVER falls back to `exec.LookPath`, so a `knomit` on the user's PATH (an older install, a different build) is never run in place of the bundled one. If the file is absent, or a directory sits in its place, it returns `*ServerBinaryMissingError{Path}`: the message contains the expected path and it unwraps to `os.ErrNotExist`.

**Enforced by tests, each sabotage-verified red:** `TestServerBinaryForRefusesPATH` and `TestServerBinaryForMissingNamesExpectedPath` fail if a LookPath fallback is added; `TestServerBinaryForResolvesThroughSymlinkedExecutable` fails if EvalSymlinks is skipped (the locator then picks a decoy beside the symlink). `TestServerBinaryForDirectoryIsMissing` pins the directory case.

**Consequence:** a consumer (desktop PR 5 will be the first) must treat `ServerBinaryMissingError` as a broken install and show the path, not retry via PATH. Wanting a dev override means adding an explicit, named setting, not a PATH fallback.

**What this does NOT mean:** the locator is not yet called at runtime. `serverBinaryPath`, `serverVersion` and `checkServerVersion` are unused until PR 5, so `go vet` is silent but a deadcode lint would flag them. `TestServerBinaryForRefusesPATH` uses a helper that skips on Windows, so PATH refusal is not exercised there.
