# One shared Embedder plus per-branch locking means concurrent batch peaks ADD — now capped at ONE batch wherever a memory ceiling was detected, and UNBOUNDED where none was

`app.New` builds ONE shared `*embeddings.Embedder` for the whole process and `lockBranch` is PER-BRANCH, so a rebuild on branch A and a learn upsert on branch B can be inside `sess.Run` at the same time and their peak memory ADDS. That is the standing structural fact; what changed in PR #176 is what bounds it.

MEASURED, not argued: on the 2026-08-29 post-fix boot, indexing three repos concurrently peaked at 4025 MiB against a single-repo prediction of ~2.5-3.5 GiB.

THE RULE NOW (`batchConcurrency` in `internal/embeddings/resolve.go`):

- A DETECTED ceiling — cgroup v1/v2, or physical RAM — caps batch inference at ONE concurrent run, floor-class or not.
- An UNREADABLE ceiling (we know a limit may apply and could not read it) also caps at one.
- An explicit `max_batch_tokens` above the shipped default caps at one.
- An UNKNOWN ceiling is UNBOUNDED. This is the one class with no memory bound at all; the operator is warned at boot rather than left to discover it.

WHY THE BOUND IS 1 AND NOT 2. Retention decides it. The ONNX arena keeps its high-water mark for the process lifetime, so an overlap overshoot is not a spike that recovers but a permanent floor on resident memory. Capacity 2 was measured at the shape a roomy host actually runs (8x2048 batches) at ratio 1.00 — it bought nothing — while spending ~126-145% of the share `sharedFraction` claims across the detected range.

WHAT THIS DOES NOT MEAN — three separate traps:

1. NOT a per-PROCESS memory bound. `EmbedQuery` and `EmbedDocument` bypass the gate by design, so interactive search never queues behind a rebuild. Each is up to one MaxTokens row (~225 MiB measured), unbounded in COUNT, retained by the same arena. The guarantee covers batch inference only.
2. NOT free. Capping costs ~0% at the wide shapes a roomy host runs and ~36% at the narrower shapes a ~10 GiB host derives. Never write 'costs nothing'; that is true only at the top of the range.
3. NOT a bound on unknown-ceiling hosts. They remain unbounded by deliberate choice — an unmeasured host is not a constrained one — so a machine we failed to measure gets the shipped default budget AND unlimited overlap.

CONSEQUENCE for anyone deriving a memory budget: the cap is what makes a derived ceiling a guarantee rather than an expectation, but ONLY for batch inference and ONLY where detection succeeded.
