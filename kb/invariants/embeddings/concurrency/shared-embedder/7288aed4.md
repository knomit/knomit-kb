# The token budget bounds memory PER RUN, not per PROCESS — concurrent branch work overlaps on one shared Embedder and peaks ADD (holds until PR 2's semaphore)

`app.New` builds ONE shared `*embeddings.Embedder` for the whole process, and `lockBranch` in the search index is PER-BRANCH. So a rebuild on branch A and a learn upsert on branch B can be inside `sess.Run` at the same time, and their peak memory ADDS.

`embeddings.max_batch_tokens` therefore bounds a single run, NOT the process. Do not treat the configured budget as a process ceiling.

MEASURED, not merely argued: on the 2026-08-29 post-fix boot, indexing three repos concurrently peaked at 4025 MiB mid-run against a single-repo prediction of ~2.5-3.5 GiB (675 MiB resident model + ≤1820 MiB worst batch + non-embedding RSS). Two fully overlapping worst-case batches would be ~4.8 GiB.

CONSEQUENCE for anyone deriving a memory-based budget: the derived cap is an EXPECTATION, not a guarantee, while this holds. Sizing a container for one worst batch under-provisions it whenever branches overlap.

THIS FACT IS SCHEDULED TO EXPIRE. A planned follow-up (PR 2) adds a capacity-1 semaphore around BATCH inference only — single-row `EmbedQuery`/`EmbedDocument` deliberately bypass it so interactive search never queues behind a rebuild batch. When that lands, the per-run bound becomes a per-process bound and this fact must be /knomit-update'd rather than left standing.
