# The worst SINGLE batch — not the workload — sets four normally-independent properties at once, so embeddings.max_batch_tokens is never only a memory knob

Across the 2026-08-29 OOM work, the same quantity kept determining things that look like separate concerns. In in-process ONNX embedding, the largest single `session.Run` a process ever performs governs ALL of the following, and `embeddings.max_batch_tokens` is the parameter that sets it:

1. PEAK memory. Cost is `rows × padded_seq`, because every row in a batch is padded to the batch's LONGEST member — so a batch is priced at its longest document, not its average. A fixed count of 32 documents measured anywhere from 283 MiB to 9030 MiB on document length alone.

2. STEADY-STATE memory. The ONNX arena does not return memory to the OS, so the worst batch's cost stays resident for the process lifetime. The budget does not set a spike height; it sets the server's resting footprint. (This is arena behaviour working as designed — NOT a leak to hunt.)

3. CANCELLATION latency. `sess.Run` is uninterruptible, so ctx bounds latency to one batch rather than aborting one; 'one batch' is now budget-dependent. Note the direction is not uniformly better: against the old fixed 32-document chunk, short-string cancellation latency GREW (up to 256 rows per run at the default). The contract is UNIFORM, not improved.

4. The VALIDITY WINDOW for measuring baseline memory. Because of (2), after any large batch idle RSS equals peak RSS, so non-embedding RSS is measurable ONLY between boot completing and the first inference.

CONSEQUENCE: changing `max_batch_tokens` changes all four. Raising it to buy throughput also raises resting RSS and lengthens the worst cancellation; lowering it to fit a small host also shortens cancellation and shrinks resting RSS. Never reason about this parameter as memory-only.

WHAT THIS DOES NOT MEAN: the budget is NOT a per-PROCESS bound. One shared `Embedder` plus per-branch locking means concurrent branch work overlaps and peaks ADD (measured: 4025 MiB across three repos against a ~2.5-3.5 GiB single-repo prediction). A derived cap is an expectation, not a guarantee, until batch inference is serialized.
