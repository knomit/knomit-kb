# Embedding inference memory scales with rows × PADDED sequence length, so batches must be bounded by padded tokens — never by document count

`runRows` pads every row in a batch to the LONGEST row in that batch before one `session.Run` (`internal/embeddings/batching.go`, `embedder.go`). Peak RSS therefore tracks the product `rows × padded_seq`, not either factor alone and not the number of documents.

Measured on embeddinggemma, one process per config (baseline resident model ~675 MiB; figures are delta above it): 8×2048 = 1820 MiB, 16×2048 = 4228 MiB, 32×2048 = 9030 MiB, 32×1024 = 2947 MiB, 32×512 = 1247 MiB, 32×128 = 283 MiB. The SAME document count of 32 spans 283 MiB to 9030 MiB on document length alone.

The product is what matters, demonstrated by holding it constant at 16384 padded tokens and varying the shape 32-fold: 128×128 = 1154 MiB, 64×256 = 1161 MiB, 256×64 = 1143 MiB — within 1.3% of each other.

CONSEQUENCE: any code that decides how much text to hand the embedder at once must reason in padded tokens. `packByTokenBudget` enforces this by sorting rows by charged width DESCENDING, which makes the first row's width the batch maximum so `rows × width ≤ budget` holds by construction.

WHAT THIS DOES NOT MEAN: it is not 'long documents use more memory', which is true but useless. The trap is that a batch is priced at its LONGEST member — one 2048-token fact among 128-token facts costs the batch 2048 per row, so a single long document silently multiplies the cost of everything batched with it.
