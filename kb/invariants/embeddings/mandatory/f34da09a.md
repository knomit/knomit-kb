# Embeddings are mandatory: service refuses to start without an embedder, and a fact is never indexed without a vector

Embeddings are LOAD-BEARING, not an optional degraded mode. Two enforcement points, both added in PR #72 (pluggable embedder):

1. SERVICE BOUNDARY — `app.New` returns a fatal error (propagated to cmd/serve's RunE → non-zero exit) if no embedder can be built: an invalid `embeddings.model` id, or `embeddings.NewEmbedder` failing (missing/undownloadable ONNX model). There is NO 'embedder DISABLED' run mode anymore; the old warn-and-continue branch was deleted. Reason: vector search is the primary retrieval path AND each model's cosine thresholds (`retrieval.Thresholds`: dedup/novelty/SimilarTo/searchFloor/rerank) are calibrated per model — a service with no embedder would both write vectorless facts and silently mis-tune dedup/graph/search.

2. PER-FACT — `store.upsert` (COW-miss path only; COW hits correctly skip embedding per the immutable-fact invariant) FAILS the write — returns an error, rolls back the whole tx, leaves no `branch_facts`/`facts_vec` row — when a configured embedder errors, returns an empty vector, or returns a wrong-dim vector. It no longer logs-and-continues 'fact indexed without vector'. So the index never holds a vectorless fact.

DELIBERATE EXCEPTION: the `store` package can still be opened WITHOUT an embedder (`getEmbedder()==nil`) by read-only tooling and tests; there `upsert` indexes facts without vectors and methodology/search fall back to tag-only ranking. That path is defensive — the running service always has an embedder. Anti-pattern: re-introducing a 'run without embeddings' server mode, or downgrading the upsert embed-failure back to a warning.
