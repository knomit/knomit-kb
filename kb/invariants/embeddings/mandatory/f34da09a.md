# Embeddings are mandatory: service refuses to start without an embedder, and a fact is never indexed without a vector

Embeddings are LOAD-BEARING, not an optional degraded mode. Two enforcement points, both added in PR #72 (pluggable embedder):

1. SERVICE BOUNDARY — `app.New` returns a fatal error (propagated to cmd/serve's RunE → non-zero exit) if no embedder can be built: an invalid `embeddings.model` id, or `embeddings.NewEmbedder` failing (missing/undownloadable ONNX model). There is NO 'embedder DISABLED' run mode anymore; the old warn-and-continue branch was deleted. Reason: vector search is the primary retrieval path AND each model's cosine thresholds (`retrieval.Thresholds`: dedup/novelty/SimilarTo/searchFloor/rerank) are calibrated per model — a service with no embedder would both write vectorless facts and silently mis-tune dedup/graph/search.

2. PER-FACT — `store.upsert` (COW-miss path only; COW hits correctly skip embedding per kb/invariants/store/facts-row-immutable-cow/8f299f86.md) FAILS the write — returns an error, rolls back the whole tx, leaves no `branch_facts`/`facts_vec` row — when a CONFIGURED embedder errors, returns an empty vector, or returns a wrong-dim vector. It no longer logs-and-continues 'fact indexed without vector'. So a service that started successfully never gains a vectorless fact.

DELIBERATE EXCEPTION: the `store` package can still be opened WITHOUT an embedder (`getEmbedder()==nil`) by read-only tooling and tests; there `upsert` indexes facts without vectors and methodology/search fall back to tag-only ranking. That path is defensive — the running service always has an embedder.

WHAT THIS DOES NOT MEAN (misreadings verified false at HEAD, 2026-07-22). The enforcement is scoped to "a service built by app.New", NOT to "any store.Service". Do not compress this to "every facts row has a facts_vec row":

1. "So I can INNER JOIN facts_vec and get every fact." FALSE on the no-embedder path, and it fails SILENTLY rather than loudly. facts_vec is created EMPTY at defaultVecDim=768 by ensureFactsVecDefault during Open, independent of whether an embedder is ever configured (internal/store/vec_table.go) — the table EXISTS but has no rows, so `JOIN facts_vec` just drops every fact. getEmbeddingByFact (internal/store/search_crud.go) maps that to (nil, nil) — no error — and search_query logs "no embedder configured, skipping vec search" at DEBUG level only. A vectorless corpus therefore looks like an empty result set, not like a failure. Any new code joining facts_vec must handle zero rows as a legitimate no-embedder state, not as corruption.

2. "Verify would catch it if vectors were missing." FALSE in exactly the case you would want it: `checkEmbeddingsCoverage` (internal/store/verify.go) RETURNS EARLY with no issues when `getEmbedder() == nil`. Coverage is only audited when an embedder is present — the no-embedder store is unverifiable by design, not verified-clean.

3. "A vector exists, so it is a vector for the CURRENT model." Not implied by this fact. facts_vec starts at the 768 default and is recreated at the real model dim by ensureFactsVec only once an embedder is configured AND a rebuild runs; dim/model identity is tracked separately via the embed-identity meta and NeedsRebuild.

Anti-pattern: re-introducing a 'run without embeddings' server mode, or downgrading the upsert embed-failure back to a warning.
