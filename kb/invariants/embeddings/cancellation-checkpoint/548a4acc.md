# store.Embedder's ctx is a CHECKPOINT, not an abort — and since PR #175 the latency it bounds scales with embeddings.max_batch_tokens

`sess.Run` exposes no run-termination hook, so ONNX inference already in flight runs to completion regardless of cancellation. `ctx` is observed at entry to each call and between batches only: cancelling BOUNDS latency to one batch, it does not abort one (`internal/store/interfaces.go`).

Since PR #175 'one batch' is no longer a fixed quantity. Batches are packed to `embeddings.max_batch_tokens`, so this latency bound scales with that setting and with the length of the documents in flight.

`minRowCharge = 64` in the packer exists partly to keep the bound meaningful: rows are charged `max(len, 64)`, capping a batch at `budget/minRowCharge` rows (256 at the default). Without that floor, callers bounded by NO constant — `learn.go`'s `dedupEmbed` embeds an entire incoming write request, `motif_alias.go` embeds a whole motif vocabulary — would each become one unbounded uninterruptible run.

WHAT THIS DOES NOT MEAN: the rail is NOT strictly better than the old fixed 32-document chunk. Against it, short-string cancellation latency GREW — up to 256 rows per run rather than 32. The honest contract is UNIFORM rather than improved: cancelling now costs at most one budget's worth of inference on every path, which for short strings is more than before and for long documents far less.

CONSEQUENCE: never assume a cancelled embed returns promptly, and never size a client timeout against document count. Size it against the configured token budget.
