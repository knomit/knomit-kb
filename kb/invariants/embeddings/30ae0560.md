# The batch-concurrency bound costs MOST on exactly the machines that need it MOST — because the same memory shortage that makes the bound necessary also makes the batches narrow enough for concurrency to matter

Two facts compose into a consequence neither states on its own.

THE CHAIN. A host with less memory derives a SMALLER token budget. A smaller budget packs FEWER rows per batch. Fewer rows leave ORT's intra-op parallelism unable to saturate the cores, so a second concurrent run has real headroom to exploit. Therefore bounding concurrency costs more there. Measured on an 8-core host, one build, identical total work, varying only the shape: 2 batches of 4x2048 cost 36% to serialize (57.71s -> 78.54s) while 1 batch of 8x2048 cost nothing (65.42s -> 65.25s).

Meanwhile the bound is needed most on precisely those hosts, because concurrent peaks ADD and the ONNX arena retains the resulting high-water mark for the process lifetime — an overshoot is a permanent floor on resident memory, not a spike that recovers.

SO THE COST PROFILE IS INVERTED against the ability to pay it: ~0% on a roomy host that could have afforded the overlap anyway, ~36% on a ~10 GiB host that cannot. The bound is cheap where it is unnecessary and expensive where it is essential.

GENERALISABLE FORM, for any safety bound sized from the resource it protects: expect its cost to concentrate on the constrained cases, and NEVER justify the bound with a cost measured on an unconstrained machine. A measurement taken where the bound is free says nothing about where it binds. Concretely here, the roomy-host ratio of 1.00 was the number that settled the design, and it is the number that understates the cost by the widest margin.

CARRIED FROM THE SOURCES, because the synthesis must not smooth them away:

- The bound is NOT a per-PROCESS memory bound. EmbedQuery and EmbedDocument bypass it by design so interactive search never queues behind a rebuild; each is up to one MaxTokens row (~225 MiB) and unbounded in COUNT, retained by the same arena.
- UNKNOWN-ceiling hosts are UNBOUNDED by deliberate choice — an unmeasured host is not a constrained one — so they get the shipped default budget AND unlimited overlap, with an operator warning at boot.
- The ratios are NOT stable constants. The same configuration measured 1.02 on one build and 1.36 on another; treat magnitudes as indicative and re-measure on a single build before relying on them.
- Never write 'costs nothing'. That is true only at the top of the range.
