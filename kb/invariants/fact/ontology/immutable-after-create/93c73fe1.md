# A repo's ontology is chosen ONCE at create time and is never editable through knomit's own UI afterwards (there is no editor) — it still changes after create in two sanctioned ways: a consensus commit to the file, applied live in full (#429), and the strictly-additive boot preset upgrade

# The rule

The create wizard is the ONLY place in knomit's own product (UI, REST, MCP) where a repo's ontology is authored. There is no post-creation ontology editor, and `.knomit/` stays closed to the fact tools.

That is NOT the same as "the ontology never changes after create". Since #429 there are two sanctioned changes, by two different authors:
1. CONSENSUS: a commit to the ontology file that reaches the repo's read branch through git (sync from the origin, a merge into the agent branch) is applied LIVE and IN FULL — topics added or removed, any attribute changed, verify_signatures included — with no subset check (kb/invariants/repos/ontology/live-reload/be5c6187.md, kb/decisions/repos/ontology/consensus-reload-honors-all/3aa84640.md). Whoever can land a commit on the consensus branch can change the ontology; that is the consensus gate's decision, not knomit's to filter. Such a change can orphan facts under a removed topic; knomit honours it anyway.
2. RELEASE: the boot-time preset refresh below, which is strictly additive.

# Rationale

Removing or renaming a topic orphans every fact filed under it. That is a schema migration — it needs a fact-rewriting plan, not a text box. Shipping an editor without that machinery would let a user break their own corpus with a one-character edit.

The codebase keeps knomit's OWN mutation of a stored ontology safe: the boot-time preset refresh in `RepoInstance.loadOntology` (internal/corpus/repos/stages.go) upgrades to a newer embedded preset ONLY when `refreshDivergence(stored, preset)` is empty. That is `SubsetDivergence` (the stored ontology is a subset of the preset: no topic, child or validation the preset lacks, and no attribute, trigger, context declaration or guidance block it does not carry identically) plus a rule of its own: the root attributes must be identical. So the change is strictly ADDITIVE and cannot orphan anything, and the refresh never adds, changes or drops a repository-level setting such as `verify_signatures`.

# What this does NOT mean

It does NOT mean the stored ontology never changes. Preset-derived ontologies keep receiving additive upgrades at boot, and that behaviour is unaffected. The rule bars USER-AUTHORED edits after creation through the product (there is no editor), not machine upgrades already proven safe by the refresh gate. It also does not mean the file is unchangeable: it lives in git, and a commit to it (for example a root attribute set by hand on the repo's main) is how it changes. Since #429 that change is applied as soon as it reaches the read branch (after the sync round or merge that brings it), not at the next mount; an unusable file (missing, empty, unparseable, symlink) makes the repo UNWRITABLE until consensus fixes it (the old ontology is not kept; user decision 1 on PR #761's review), and the reason is in the repo's status. The preset refresh's subset rules apply ONLY to the refresh, never to a consensus change.

It also does not bar a future migration feature — it bars shipping the editor WITHOUT one.

# Consequence for the UI

The create wizard's review step must say plainly that the ontology cannot be changed afterwards, since this is a one-way door taken at create time. It is stated as plain text, not a warning.

It also raises the stakes on anything that could write the WRONG ontology. A stale async response overwriting the user's choice is not a cosmetic race here: there is no repair path short of recreating the repo. The wizard's ontology step guards every mode transition with a single generation counter for exactly this reason.
