# A repo's ontology is chosen ONCE at create time and is never user-editable afterwards — the only sanctioned change is the strictly-additive preset upgrade, which cannot orphan facts

# The rule

The create wizard is the ONLY place a repo's ontology is authored. There is no post-creation ontology editor.

# Rationale

Removing or renaming a topic orphans every fact filed under it. That is a schema migration — it needs a fact-rewriting plan, not a text box. Shipping an editor without that machinery would let a user break their own corpus with a one-character edit.

The codebase already enforces this in the one place it does mutate a stored ontology: the boot-time preset refresh in `RepoInstance.loadOntology` (internal/repos/stages.go) upgrades to a newer embedded preset ONLY when `refreshDivergence(stored, preset)` is empty. That is `SubsetDivergence` (the stored ontology is a subset of the preset: no topic, child or validation the preset lacks, and no attribute, trigger, context declaration or guidance block it does not carry identically) plus a rule of its own: the root attributes must be identical. So the change is strictly ADDITIVE and cannot orphan anything, and the refresh never adds, changes or drops a repository-level setting such as `verify_signatures`.

# What this does NOT mean

It does NOT mean the stored ontology never changes. Preset-derived ontologies keep receiving additive upgrades at boot, and that behaviour is unaffected. The rule bars USER-AUTHORED edits after creation through the product (there is no editor), not machine upgrades already proven safe by the refresh gate. It also does not mean the file is unchangeable: it lives in git, and a commit to it (for example a root attribute set by hand on the repo's main) is how it changes; loadOntology reads whatever the read branch holds when the repo is next identified.

It also does not bar a future migration feature — it bars shipping the editor WITHOUT one.

# Consequence for the UI

The create wizard's review step must say plainly that the ontology cannot be changed afterwards, since this is a one-way door taken at create time. It is stated as plain text, not a warning.

It also raises the stakes on anything that could write the WRONG ontology. A stale async response overwriting the user's choice is not a cosmetic race here: there is no repair path short of recreating the repo. The wizard's ontology step guards every mode transition with a single generation counter for exactly this reason.
