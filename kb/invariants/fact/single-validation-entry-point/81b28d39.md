# ParseFact and SerializeFact validate the SAME three axes — kind×type, bounds, and origin×type

internal/fact validates on BOTH the read and write side, through the same helpers, so the set of facts SerializeFact will emit is exactly the set ParseFact will accept. Three axes, all symmetric as of 2026-07-21 (P1.6):

1. validateKindAndType(k, t) in kind.go — missing kind normalizes to DefaultKind; kind must be well-known (Epistemic or Pragmatic); k.AllowsType(t) delegates to EpistemicTypes[t] / PragmaticTypes[t]. Returns the normalized Kind.
2. validateBounds(confidence, sources) — range checks.
3. Origin.Validate() + Origin.ValidateForType(t) in origin.go — well-formedness AND the origin×type pairing (distilled requires type synthesis; discovered requires synthesis or hypothesis).

SYMMETRY GUARANTEE: any Fact that round-trips ParseFact → SerializeFact → ParseFact carries a valid (kind, type), in-range bounds, and a legal (origin, type) pair.

HISTORY — the guarantee was ADVERTISED BROADER THAN ENFORCED for months. Until P1.6, SerializeFact validated only kind×type and bounds, and neither function checked origin×type at all. A fact with `origin: distilled` on `type: observation` serialized cleanly and then FAILED ParseFact on read-back: a file the writer could create but nothing could load. Origin.ValidateForType existed but was called from exactly ONE place in the whole repo — an MCP handler — so the synthesize and web write paths bypassed it entirely. Read that as the standing lesson: a doc comment claiming symmetry does not police itself, and the drift was found by code review, not by a test.

DO NOT fix an asymmetry by adding the check to only one side. That does not restore symmetry, it INVERTS it — SerializeFact would then reject pairings ParseFact accepts, so a hand-edited file could be read but never written back.

EMPTY ORIGIN IS "UNSET", NOT "INVALID", and the distinction is load-bearing. Write paths deliberately leave Origin zero so SerializeFact elides the field and ParseFact applies the type-aware default (distilled for synthesis, authored otherwise). Origin("").Validate() returns an error, so calling it unguarded breaks every ordinary authored write. SerializeFact skips origin validation when the field is empty.

Anti-pattern: validating in only one direction to 'preserve compatibility'. Silent serialization of malformed facts was a real prior bug, masked by Upsert's `default 'observation'` on read.

Adding a new Type: add it to EpistemicTypes or PragmaticTypes AND to the AllXxxTypes() helper. Adding a new Origin: add it to AllOrigins() and consider whether ValidateForType should constrain it.
