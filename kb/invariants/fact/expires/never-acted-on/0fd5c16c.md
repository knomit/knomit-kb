# `expires` is a frontmatter date knomit NEVER acts on: no hiding, no deletion, no retraction, no seeding — every read returns expired facts, marked `expired: true`, and only the three opt-in filters (expired, expires_before, expires_after) select by it

Any fact, of any kind or type (signal included), may carry an optional RFC 3339 `expires`. Past it the fact is EXPIRED and that is ALL the word means (user ruling 2026-09-26, F03). Knomit never deletes, hides, retracts, collects, or feeds an expired fact to the review pipeline because it expired. Keeping expired facts in the KB is the design: a human or agent searches (e.g. `knomit_query {expired: true, type: [hypothesis]}`) and decides to keep, update, or retract.

What enforces it: the store filter builder `newFactFilter` adds an expiry clause ONLY when `SearchOptions.Expired` is non-nil or `ExpiresBefore`/`ExpiresAfter` is non-zero; the zero value filters nothing, so every internal caller (pipeline seeding, learn dedup, same-subject, prune neighbours) and every default read behaves exactly as before F03. Results carry `expires` (as written) and `expired` (expires <= the read's clock, whole seconds) on knomit_query rows, knomit_explain nodes (summaries included), the REST facts/search/lens rows, the single-fact view, Highlights/Stats, domain and motif-carrier rows, and the bridge session-start pre-warm text (`(expired <date>)` / `(expires <date>)`).

Consequence: to act on expiry, a consumer queries for it and acts itself; there is no knomit-side lifecycle to wait for or rely on. A signal past its expiry is still on disk until someone retracts it.

Filter semantics, stated because they are the ones callers get wrong: `expired=false` INCLUDES facts with no `expires` (absent means never); `expires_before` and `expires_after` EXCLUDE facts with no `expires` (never is not before or after anything). Expiring within a window w = `expires_after=now` + `expires_before=now+w`.

WHAT THIS DOES NOT MEAN: it does not mean there is a default expiry (absent means never; no constant anywhere, per corpus-property-constants), and it does not mean the fleet design's collection-on-reconcile-tick, due-seed watermark, type-keyed hiding or `expire` op exist — those were proposed in the F03 design and REJECTED by the user in favour of this read-only field.
