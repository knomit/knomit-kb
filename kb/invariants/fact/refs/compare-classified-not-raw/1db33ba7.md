# Every ref comparison must classify then compare PATHS — a raw-string compare against a fact path matches nothing, because refs are stored kb://<own-id>/<path>, so the check ships green and does no work

Any code asking "does this ref name that fact?" must run both sides through fact.ClassifyRef and compare the resulting .Path (checking Kind == RefLocalFact), never compare the raw ref string to a fact path. The reason is that the two are NOT the same string: refs are written to storage in the canonical form kb://<own-id12>/<path>, while a fact's own path is the bare repo-relative form. A literal comparison between them matches NOTHING.

WHY THIS IS AN INVARIANT AND NOT A STYLE NOTE: the failure is SILENT AND INVERTED. A raw-string comparison does not error, does not warn, and does not fail a test — it simply never matches, so a gate built on it excludes nothing, a filter keeps everything, and a counter counts zero. The whole fix ships green while doing no work. In #125 a lineage-exclusion gate written this way would have excluded zero pairs with a fully green suite; it was caught only by deliberately dropping the normalisation and observing that nothing went red.

MEASURED, on this repo's own corpus (live facts, 2026-08-26): of 3405 refs, 523 are canonical kb:// and 236 are bare repo-relative paths; 239 live facts carry at least one canonical local-fact ref and 112 carry at least one bare one. BOTH FORMS ARE LOAD-BEARING AND NEITHER IS RARE, so a comparison written against either spelling alone silently misses a large slice of the population. Do not infer the spelling from the facts in front of you — sample size one is exactly how a developer concludes the corpus uses a single form.

THREE SITES SO FAR, all the same shape: #125's bridge lineage exclusion (member refs vs member paths), #151's discover seed-match (cited refs vs offered seed paths — which additionally split its refs into seeds and extras by raw string while the dedup test twelve lines below it canonicalised, so one half of one function knew how refs are spelled and the other did not), and the #132 self-reference gate. The first two are merged and reffed above; #132 was reported by another lane and is NOT cited here because it had not landed when this was written — check it before relying on it as a third data point. Whenever a new site compares refs, assume it is the same bug until the classification is visible in the code.

THE NAMED MISREADING — a passing test of the comparator proves nothing. A test that constructs the input by hand and passes a bare path exercises neither the spelling nor the repo id. The check that has teeth is an EMPTY-REPO-ID SABOTAGE: with localRepoID = "", every kb:// ref classifies as FOREIGN and the comparison silently reverts to matching nothing, so a test asserting that the empty id excludes/recognises nothing pins the hazard directly (TestBridgeLineage_EmptyRepoIDExcludesNothing, TestSeedSubset_EmptyRepoIDCannotSeeACanonicalSeed). Both assert a FAILURE MODE rather than a feature; if either ever flips, normalisation has stopped depending on the repo id and the right response is to DELETE the test, never to weaken its assertion.

COROLLARY: localRepoID must be THREADED, never defaulted to "". Classifying a stored ref with an empty id reads every local citation as foreign — the same silent no-op by another route. Many existing test fixtures pass "" and work only because they spell every ref as a bare path; that is a property of those fixtures, not of the system.

WHAT THIS DOES NOT MEAN: it is not a licence to canonicalise refs on write paths that are only supposed to append. Membership is tested on the canonical form; the strings a fact already carried are written back verbatim, because rewriting them is a mutation of authored data outside the operation's contract.
