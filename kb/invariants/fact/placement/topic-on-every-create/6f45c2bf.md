# Every write that CREATES a fact runs ONE placement check, fact.ValidatePlacement (declared top-level topic + non-blank category) — knomit_learn, REST POST /facts and REST PUT to a fresh path alike; a fresh PUT outside kb/<topic>/<category>/ is refused; lens reads rely on it

User ruling 2026-11-03: "the first level MUST always match the ontology, LLMs cannot just willy nilly invent topics." Built by PR #748 (branch fix/rest-create-validates-topic).

THE RULE, with every component:
1. fact.ValidatePlacement(ontology, topic, category) is the ONE check: Ontology.ValidatePath on "topic/category" (refuses a first segment that is not a top-level topic; skipped ONLY when the repo has no ontology), then a non-blank category. Every create calls it: knomit_learn (validateAndBuildFacts), REST POST /repos/{repo}/branches/{branch}/facts (topic = domain[0], category = domain[1], default domain[0]), and REST PUT /facts/{path} to a path where NO fact exists (putPlacement, on the topic and category the path names).
2. REST POST with no domain is 400 "Missing domain" ("domain is required: …"); there is NO fallback topic (the old "uncategorized" was removed).
3. A fresh, non-artifact PUT must be <root>/<topic>/<category...>/<name>.md, compared on the LOWERCASED path and root: a path OUTSIDE the ontology root (e.g. decisions/x.md — whose first segment must NOT be read as the topic) or DIRECTLY under it (kb/x.md) is refused with a shape message ("a new fact's path must be kb/<topic>/<category>/<name>.md, …"); kb/architecture/x.md is refused "category is required". The PUT check is skipped when the repo has no usable ontology — in production such a repo is read-only (RepoInstance.WritableBranch), so only bare test instances skip it.
4. Refusals are 422 problem "Invalid fact placement" (title is placeholder copy); the detail is knomit_learn's own text where it applies (`validate path: unknown topic "<topic>"`, `category is required`). Nothing is written.

WHY: a lens read skips a member whose ontology lacks the topic a path filter names (federate.ReadTargetsFor, internal/corpus/federate/federate.go ~:259), so a fact under an undeclared topic is invisible through every lens. Before #748 REST POST wrote domain[0] unchecked and a default-ontology repo accepted domain:["architecture","chain"] with 201.

WHAT IT DOES NOT MEAN:
- It does NOT re-judge EDITS. A PUT to an existing path and knomit_update never re-check placement, so a legacy fact under a since-removed topic stays editable. Do not read this as "every fact in the corpus is under a declared topic": legacy facts, pushes, merges, and the review/discovery pipelines (synthesize decision.go, discovery.go — an open follow-up as of #748) are not covered.
- ValidatePath constrains only the FIRST segment; the category tail is freeform (kb/architecture/fact/ontology-validate-path-freeform-tail/7cc889c7.md).
- It is a different gate from the ontology `validations` rules (store validateWrite, kb/decisions/fact/validation/enforced-everywhere/338656ce.md), which judge content, not placement.

CONSEQUENCE: a new write path that allocates a fact path must call fact.ValidatePlacement, never Ontology.ValidatePath alone (that skips the category rule) and never a second validator. Fixtures writing through REST need kb/<declared-topic>/<category>/<name>.md; the e2e repo is the default preset plus the suite's extra topics (e2e/fixtures/seed.ts e2eOntologyYAML). Web REST tests on a test instance with no Ontology skip the check and pass vacuously; set Ontology in TestInstanceConfig.
