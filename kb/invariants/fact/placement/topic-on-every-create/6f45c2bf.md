# Every write that CREATES a fact names a top-level topic of the repo's ontology — knomit_learn, REST POST /facts and REST PUT to a fresh path run ONE check (fact.ValidatePlacement / Ontology.ValidatePath) and refuse otherwise; lens reads rely on it

User ruling 2026-11-03: "the first level MUST always match the ontology, LLMs cannot just willy nilly invent topics." Built by PR #748 (branch fix/rest-create-validates-topic).

THE RULE, with every component:
1. knomit_learn (validateAndBuildFacts) and REST POST /repos/{repo}/branches/{branch}/facts both call fact.ValidatePlacement(ontology, topic, category): Ontology.ValidatePath on "topic/category" (refuses a first segment that is not a top-level topic; skipped ONLY when the repo has no ontology), then a non-blank category. POST takes topic = domain[0], category = domain[1] (default domain[0]); an absent domain falls back to topic "uncategorized", which is refused on any ontology without that topic.
2. REST PUT /facts/{path} to a path where NO fact exists (it creates one), and not under artifacts/, runs Ontology.ValidatePath on the topic path derived from the LOWERCASED path with the lowercased ontology root stripped. A root-level file (kb/x.md) derives topic "." and is refused.
3. REST answers 422 problem "Invalid fact placement" (title is placeholder copy) with knomit_learn's own text as detail: `validate path: unknown topic "<topic>"` or `category is required`. Nothing is written.

WHY: a lens read skips a member whose ontology lacks the topic a path filter names (federate.ReadTargetsFor, internal/corpus/federate/federate.go ~:259), so a fact under an undeclared topic is invisible through every lens. Before #748 REST POST wrote domain[0] unchecked and a default-ontology repo accepted domain:["architecture","chain"] with 201.

WHAT IT DOES NOT MEAN:
- It does NOT re-judge EDITS. A PUT to an existing path and knomit_update never re-check the topic, so a legacy fact under a since-removed topic stays editable. Do not read this as "every fact in the corpus is under a declared topic" — legacy facts, pushes, merges and pipeline writes are not covered by this check.
- ValidatePath constrains only the FIRST segment; the category tail is freeform (see kb/architecture/fact/ontology-validate-path-freeform-tail/7cc889c7.md).
- It is a different gate from the ontology `validations` rules (store validateWrite, kb/decisions/fact/validation/enforced-everywhere/338656ce.md), which judge content, not placement.

CONSEQUENCE: a new write path that allocates a fact path from a topic must call fact.ValidatePlacement, never a second validator. Test fixtures writing through REST must use a topic the repo's ontology declares; the e2e repo is the default preset plus the suite's extra topics (e2e/fixtures/seed.ts e2eOntologyYAML). Web REST tests on a test instance with no Ontology skip the check (o == nil) and pass vacuously; set Ontology in TestInstanceConfig.
