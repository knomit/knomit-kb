# Private (dot-prefixed) path segments are excluded from fact DISCOVERY at seven walkers and CLOSED to every fact-tool WRITE, MCP and REST, .knomit/ included; exact-path READS are closed too EXCEPT a .knomit/ file by its exact path (explain, REST GET, refs) since 2026-10-06; knomit's own readers still open .knomit/ by name; never enforced via store.validatePath

`fact.IsPrivatePath(path)` is true when ANY `/`-separated segment of the path begins with `.` — file OR directory, at any depth, including under the ontology root. A private path is excluded from fact DISCOVERY and CLOSED to every fact tool — every write and every exact-path read, MCP and REST — with no exception since F25 (three roots, 2026-10-06). Before F25 there was one carve-out, `.knomit/<area>/`; it is gone, and the agents' working files moved to repo-root `artifacts/<area>/` (see below). `spec/mbekg.md` §3.8 states the discovery rule as a MUST for readers.

**Why the site list below is the load-bearing part of this fact.** The implementation plan for PR #68 claimed three creation sites and four discovery walkers. Both counts were wrong, and the gaps were caught only in the final whole-branch review — after seven of eight tasks had already shipped. A missed walker leaks a private stash into a live listing; a missed writer commits a fact that no reader will ever see and returns success for it. Enumerate against this list before assuming a new reader or writer is covered.

**SEVEN DISCOVERY GUARDS (skip on walk).** Verified at `54290347` (the PR #68 merge on `dev`):

1. `internal/store/factpath.go`, inside `repoHandler.isFactPath` — ONE place to write, but it covers SIX readers: `search_index.go`'s three admission points (`Sync`'s full-rebuild branch, `Sync`'s incremental added/modified branch, `rebuildFacts`) and BOTH `verify.go` call sites (`checkFactsCoherence`, `checkFactFormat`). Do not mistake "one call site" for "one reader".
2. `internal/okf/source/facts.go` — the OKF fact walk. The check MUST sit BEFORE the `ParseFact`/`looksLikeFact` step, not after: a hand-placed private draft that fails to parse would otherwise be reported as lost knowledge on EVERY export — a permanent false alarm that trains readers to ignore a real one.
3. `internal/okf/source/history.go`, `okfDeletionFromFile` — removing a private file is not the retirement of a published fact.
4. `internal/okf/source/history.go`, `okfChangeFromFile` — feeds authored time and revision history, and must agree with the fact walk about which paths those apply to.
5. `internal/web/handlers_topics.go` — the fact listing under a topic.
6. `internal/web/handlers_topics.go` — the topic tree listing.
7. `internal/web/handlers_lenses_topics.go` — the lens union tree.

**THE WRITE SITES (history first; the F25 state is in the next section).** Verified at `e4175f7b`, 2026-09-26, BEFORE F25 — the carve-out described in this paragraph no longer exists: Since `2af19060` (2026-08-11, "add IsWritablePrivatePath allow-list for .knomit/<area>/"), `fact.IsWritablePrivatePath(path)` (`internal/fact/private.go`) returns true for exactly `.knomit/<area>/<name…>`: under `fact.PrivateRoot`, at least one subdirectory deep, no `..` anywhere (rejected as a SUBSTRING, because that is what `store.validatePath` enforces and the predicate must never authorise what the writer refuses). Every other private path is still refused. This is knomit's own private-STATE area — invisibility from discovery is the feature there, not the bug — and it is what F05/F08-style agent bookmarks and inbox state would live under.

The write sites and what each does at HEAD:

1. `internal/web/handlers_fact_create.go` (`POST`, path built from topic/category) — refuses EVERY private path (`IsPrivatePath` only, line ~85); topic/category cannot name `.knomit`, so no carve-out is needed here.
2. `internal/web/handlers_fact_write.go` (`PUT .../facts/{path...}`, path FULLY caller-supplied, also the creation route for a brand-new fact) — `refuseNonFactPath`: refuses `IsPrivatePath && !IsWritablePrivatePath`, so `.knomit/<area>/…` is ADMITTED and every other private path refused with a 400 naming the carve-out. This is the site the PR #68 plan missed; without the guard the branch had silently turned it into "committed, permanently invisible, returns 200".
3. `internal/mcp/learn.go` — `knomit_learn` accepts an explicit `path` (mutually exclusive with topic/category) ONLY when `IsWritablePrivatePath(NormalizePath(root, path))`; an empty topicCategory is the downstream signal to skip ontology validation and dedup-merge for that fact. Any other explicit path is refused.
4. `internal/mcp/update.go` — `knomit_update` refuses a REVISION to a private path unless it is writable-private (line ~133); a writable-private fact also skips ontology validation (line ~238).
5. `internal/mcp/retract.go` — `knomit_retract` applies the same `IsPrivatePath && !IsWritablePrivatePath` gate (line ~72).
6. `internal/synthesize/decision.go`, inside `validateOutputPath` — refuses EVERY private path (`IsPrivatePath` only, line ~58), one guard covering FOUR callers: `decision.go` merge, distill, propose, and `discovery.go`'s emergent-fact write. The pipeline never writes into `.knomit/`.

Refusal is chosen over silent skip on purpose: returning 201/success for a fact that never appears in search is silent knowledge loss, and the hardest class of bug to trace back to its cause. The carve-out does not change that: a `.knomit/<area>/` fact is invisible to discovery BY DESIGN and its writer knows it.

**TRAP 1 — the check must NOT go in `store.validatePath`.** It looks like the ideal chokepoint, because every write reaches it. It also guards the writes for `README.md` (via `store.WriteRootFile`) and `.domains/ontology.yaml`. Putting the private rule there breaks the boot-time ontology refresh. The rule belongs at the FACT-creation boundaries listed above, not at the generic path validator underneath them.

**TRAP 2 — private means excluded from DISCOVERY, never from ACCESS.** knomit reads `.domains/ontology.yaml` BY NAME and that is permitted; so is reading, updating-by-hand, or deleting an existing private file. The rule governs WALKING, not OPENING. An implementer who compresses this to "never touch dot-paths" builds a reader that cannot load its own ontology. A human may place files under `kb/.drafts/` by hand and knomit respects them as a private stash; the refusal binds only knomit's own write path.

**TRAP 3 — the ListDir-backed browsers are discovery surfaces too.** Guards 5, 6 and 7 walk the RAW GIT TREE via `ListDir`, not the fact index, so they do NOT inherit `isFactPath`'s guard and must filter independently. Each must test the CONSTRUCTED FULL PATH, not the bare entry name: testing `e.Name` alone lets a private ANCESTOR through, so browsing `.../topics/.drafts/facts` directly would list the stash with live self links.

**TRAP 4 — "refused at the write sites" is no longer "refuses any private path".** A reader who remembers the pre-2af19060 wording will build a caller that never tries `.knomit/<area>/` and will re-derive private state in some other place; a reader who over-generalises the carve-out will expect `kb/.drafts/…` to be writable through the API, which it is not. The predicate is `IsWritablePrivatePath`, and its allow-list is exactly one root.

**Relation to the ontology-root invariant.** This is the SAME location test one level finer, and EXTENDS `kb/invariants/store/indexing/ontology-root-scope/1b35d56b.md` rather than competing with it: membership is decided by where a file sits, never by whether its bytes happen to parse.

**TRAP 5 (verified at origin/dev ba748e2b, 2026-10-06) — "knomit's own private-STATE area" is a description of intent, not of the allow-list.** `reservedPrivate` is empty and `IsWritablePrivatePath` accepts EVERY dotless `<area>`, so `.knomit/skills/<name>/…` is as writable through learn, update, retract and the REST PUT as `.knomit/jobs/…` is — and `.knomit/skills/` is CONFIGURATION that knomit_skill serves to sessions from the tip of main, not state nobody reads. Dot segments below the area (`.knomit/jobs/.git/x.md`) are accepted too. Details, the two doors and what is NOT reachable (recipes, trigger scripts): kb/gotchas/fact/private-paths/skills-writable/209ec2c1.md.

**F25 — THE STATE NOW (PR #422, merge commit 74fa6cd3 on dev).** `fact.IsWritablePrivatePath` and `reservedPrivate` are DELETED: no caller can ask "may I write this dot path", the answer is always no. Every site below refuses every path with a dot segment, `.knomit/` included:

WRITES — knomit_learn `path` and `retract` (learn.go), knomit_update (update.go), knomit_retract (retract.go): `closedToFactTools` (internal/mcp/closed_paths.go) after NormalizePath, error "<path> is private: … closed to the fact tools". REST PUT and DELETE (`refuseNonFactPath`): 400 "Private path". REST POST and the synthesize pipeline: unchanged (they already refused every private path). Experiment resolutions (`resolutions.Normalize`, shared by MCP and REST): EVERY kind keyed on a dot path is refused — `{body}` and the side picks alike.

READS (new with F25) — knomit_explain (plain, `commit`, `history_cursor`, via `resolveExplainTarget` → `fact.IsFactFilePath`, which now admits no private path), knomit_query `path` (refused, instead of silently returning nothing), REST GET `/facts/*` (branch, before sub-resource dispatch), `/commits/{sha}/facts/*`, `/lenses/{lens}/facts/*` (`refusePrivateRead`, judging the path both raw and percent-decoded).

ARTIFACTS — `fact.IsArtifactPath`: `artifacts/<area>/<name…>`, at least one folder deep, no empty segment, NO segment beginning with `.` at ANY depth (the pre-F25 rule checked only `<area>`), no `..`. `NormalizePath` keeps a path whose first segment is `artifacts` (case-insensitive) at the repo root. Discovery excludes artifacts by LOCATION, with no new filter: isFactPath, the OKF walk, knomit_changes and the trigger diff all key on the ontology root, which is why config refuses `ontology_root = "artifacts"` (or nested under it).

NOT AFFECTED: knomit's OWN readers open `.knomit/` by exact name at the consensus tip — the ontology loader, RecipeAt/ScriptAt, SkillsAt/knomit_skill, preset refresh, repo create, create-from-template. Those are not fact tools (TestThreeRoots_F23Case_NothingReachesConsensus shows knomit_skill serving a git-placed skill while every fact door is refused). TRAP 2 above still holds in that sense: private is closed to the FACT TOOLS, not to knomit.

TRAP 4 and TRAP 5 above describe the pre-F25 carve-out and are history. The misreading to avoid now: "the API cannot write any agent state" — it can, under `artifacts/<area>/`; and "artifacts are facts in another folder" — they are never indexed, queried, listed by changes, exported or trigger-visible, and refuse a `context`.

READS OF .knomit/ REOPENED (2026-10-06, branch feat/system-file-reads; user ruling "reopen reads by path, writes MUST WORK for artifacts in the root still"). The F25 READS paragraph above now holds for every dot path EXCEPT a file under `.knomit/` named by its exact path (`fact.IsSystemFilePath`: `.knomit/` + at least one segment, no empty, `.` or `..` segment, case significant):
- knomit_explain: `resolveExplainTarget` tests IsSystemFilePath BEFORE NormalizePath and returns the file raw (kind `system_file`); `history_cursor` on it is refused. A malformed `.knomit/` path still falls through to closedToFactTools.
- REST GET `/facts/.knomit/<path>` and `/commits/{sha}/facts/.knomit/<path>`: raw bytes (`serveSystemFileRead`, before `refusePrivateRead`). The LENS route `/lenses/{lens}/facts/*` still refuses `.knomit/`.
- A fact may ref `.knomit/<path>` (kind local_system_file); the refs gate requires the file at the branch tip.
UNCHANGED: every WRITE door above (learn `path`/`retract`, update, retract, REST PUT/DELETE, experiment resolutions, trigger scripts' host check) still refuses `.knomit/`; knomit_query `path` still refuses it; the seven discovery guards still skip it (nothing indexes or lists it); every other dot path (`kb/.drafts/…`, `.github/…`) stays closed to reads and writes. artifacts/ is unchanged.
The misreading to avoid now: "readable means writable" (it does not), and "readable means queryable" (it is reachable by exact path only). Details: kb/architecture/mcp/explain/system-file-node/742f2418.md, kb/architecture/refs/system-file-refs/0bbf4f93.md.
