# The fleet repository's origin is changed ONLY by POST /fleet/host (drop it: the master hosts, needs [tls].addr and external_addresses, a member is refused `member_keeps_origin`, a hub is `hub`) and POST /fleet/follow (attach it: F1 `origin_invalid` before any dial; a peer of THIS fleet, or a forge whose main carries this fleet's root, or on the master an empty forge it moves the fleet to; anything else `not_this_fleet`); both are local-only and run under fleetOpMu

THE GUARDS, as of PR #528 (verified at merge e417fd76). They replaced the R3.3 guards of PR #525, which sat in the generic origin handlers (DELETE /repos/{fleet}/origin through Manager.DetachRepoOrigin, PATCH origin/upstream = fleet_upstream_fixed, the manual merge = not_master / judge_refused). Those handlers are now refused outright for the fleet repository by one gate (the fleet repository is changed only through /fleet), and Manager.DetachRepoOrigin, ErrFleetUpstreamFixed, RepoInstance.FleetMergeRefusal and their codes (fleet_upstream_fixed, not_master and judge_refused on the merge route) no longer exist. The guards live on two local-only routes (the RequireLocalVia group), each taking fleetOpMu:

1. POST /fleet/host (Manager.HostFleetHere): 409 `not_registered` with no fleet; 409 `hub` when the copy has no origin; guardFleetDetach then the detach as ONE step under fleetOpMu (a stand-down, which passes while the copy has an origin, could otherwise remove the root key between the master check and the detach and leave a hub with no master). A MEMBER: 409 `member_keeps_origin` ('a member's fleet copy keeps its origin; only the master hosts the fleet'; without an origin a member has no main and nothing to push to). The master: allowed only if refuseNoHubListener passes, i.e. [tls].addr is set (422 `listener_required`) and external_addresses is set (422 `addresses_required`); the texts end with 'run `knomit reload`'. The same function is the create's pre-flight. On success the master's copy is the hub (GET /fleet hosting `none`).
2. POST /fleet/follow {url} (Manager.FollowFleetHost): refuseFleetOrigin first (F1, 422 `origin_invalid`, before anything dials). UPDATE (PR #529, verified at merge 60ddfb1c): the route then splits on the URL against the stored origin (kb/invariants/fleet/follow/credential-vs-move/7b230fe8.md): the stored forge URL or no url on a forge copy is a CREDENTIAL change (probe and store, nothing else); a URL that classifies as a peer of THIS fleet (certificate chains to this root, auth method cert) is followed, and a credential for a peer is refused (ErrPeerCredential / auth_invalid); any other forge URL must hold THIS fleet's root on its main (else 422 `not_this_fleet`) and is followed by a member with its own credential, or is a MOVE of the fleet when the caller is the master (an empty forge is accepted for the master only; kb/invariants/fleet/move/onto-forge/d83bd272.md). The answer carries `change` (followed | moved | credential | unchanged). An unreachable URL or a refused credential is refused (`unreachable`: 'the forge could not be reached' / 'the forge refused the credential') instead of stored; AttachOrigin's own checks run (probe, and a different ontology is 409 `not_this_fleet`). Every error text is credential-free.
3. The upstream branch of the fleet repository is fixed at create, and nothing changes it (PATCH origin/upstream is 409 `fleet_repository` like every generic mutation). The merge of a pushed branch on the fleet repository is the master's automatic merger only; the operator's manual merge is refused (409 `fleet_repository`) and the master's merger re-judges each branch against the CURRENT main and demotes one it now refuses (kb/invariants/fleet/fetch-judge).

HOST RECORD (PR #527, writer updated by PR #528): a successful POST /fleet/host also writes the host record (artifacts/fleet/host, the hub's https URLs) and publishes main, since the master has become the host. It is answered as DONE even when that write fails (WARN logged), and the hub's local reconcile re-asserts the record every round (fleetHostRound), so a failed write is repaired within a round. The record never carries userinfo. See kb/architecture/fleet/host-record/9c4e1732.md.

MISREADINGS. (1) "Only create and host-here write the host record": the hub's reconcile rewrites it every round it differs. (2) "A host-here that returned success has written the record": it may not have yet. (3) "POST /fleet/follow updates the host record": CORRECTED by PR #529. A MASTER's move onto a forge (follow of a different forge URL) DOES rewrite the host record (the forge URL, credential-free, in step 3 of moveFleetToForge). A credential change (the stored forge URL or no url) and a MEMBER's follow do not (live-verified: forge refs and the record byte-identical after a rotation). The host-record writers are therefore create, Host here, the hub's reconcile round AND the master's move. (4) "The master may host freely": without [tls].addr and external_addresses it is refused. (5) "Follow repoints at any host": it takes any PEER of this fleet, not only the new master; two copies pointed at each other leave nobody hosting, and a stand-down in that state succeeds (review note, not fixed).

UPDATE (PR #529, verified at merge 60ddfb1c): the 'THE GUARDS' list above is extended, not replaced: follow now also takes forges, and the master's move is an interrupted-able multi-step operation (kb/architecture/fleet/move/interrupted-move/e9c7d31c.md); POST /fleet/index-rebuild joins the same local-only, fleetOpMu group (kb/architecture/fleet/index-rebuild/fd9e69d0.md).
