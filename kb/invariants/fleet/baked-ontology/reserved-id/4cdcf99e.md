# The id `fleet` is RESERVED: every generic door (create in all modes, clone, subscribe, restore, connect) refuses a fleet-id ontology, and a fleet-id repo mounts only through the fleet door or, at boot, as the ONE uid recorded in control.db instance_fleet_repo; any future create/join path MUST record its uid

The fleet ontology is built into knomit (fact.FleetOntology, the embedded ontology_fleet.yaml). It is NOT a preset and NOT a template: OntologyByPreset and EmbeddedPresetByID have only the default and code arms, the preset picker lists default and code, GET /api/v1/ontologies/presets/fleet answers 404 (unknown preset), and the old fleet template machinery (ErrTemplateFleetLocal, ErrTemplateFleetPresent, ErrTemplateFleetStateUnavailable, checkTemplateMode) is gone. The ontology id `fleet` is RESERVED. One sentinel, ErrFleetOntologyReserved (REST 422 'Fleet ontology reserved'; text: only `knomit fleet` creates or joins a fleet repository).

REFUSED, with nothing written, at every generic door:
- CREATE, wherever the request names the ontology: `ontology_preset: fleet`; YAML whose id is fleet in mode custom or initialize (refuseReservedOntology, called from CreatePreflight and again from Create; YAML that does not parse is reported by the create itself, not by this rule); a template whose ontology id is fleet in mode template or initialize (ResolveTemplate).
- IDENTIFY, for every mount that reads an ontology (clone, subscribe, restore, boot): admitFleetOntology admits a fleet-id ontology only when RepoInstance.fleetDoor is set. A clone or subscribe of a fleet remote is therefore refused AFTER the transfer and rolled back, not at preflight.
- RESTORE: Restore mounts with fleetDoor=false, so an archived fleet-id row is refused (REST 422) and stays archived.
- CONNECT / store swap: guardSwap refuses an incoming fleet-id store and any swap of the fleet repository before its point of no return (REST 422).

WHO HAS THE DOOR: fleetDoor is true only (a) for the mount RegisterFleet creates (CreateSpec.fleetDoor is unexported), and (b) at boot, for the single repo whose uid is stored in control.db table instance_fleet_repo (migration 000016: one row, id = 1, repo_uid REFERENCES repos(uid) ON DELETE CASCADE). RegisterFleet calls recordFleetRepo right after its is-it-a-fleet check; if recording fails it deletes the mount and answers 500 record_failed. Nothing clears the row except the foreign-key cascade when the repos row is deleted, which unregister, delete and purge all do. Manager.Start reads the recorded uid once and passes the door to openRegistered only for that uid; if the record cannot be read, NO repo is admitted. It is a table, not a column, because the control migration chain admits only CREATE ... IF NOT EXISTS.

BOOT CONFLICT: any other registered repo whose ontology is or becomes id fleet (an upstream that switched its ontology and the change arrived by sync, a second fleet row, a hand-edited control.db, a home from an older build) is refused at Identify and listed unavailable with reason unopenable and cause fleet_conflict (CauseFleetConflict). It is not the fleet repository: it is not mounted, fleetRepo() and guardFleetRemoval never see it, boot does not archive it, and the user can archive and purge it like any ordinary repo.

CONSEQUENCE (act on this): any future path that makes an instance a fleet host or member (fleet create, fleet join) MUST open its mount with the fleet door AND call recordFleetRepo with the new uid. Without the record the fleet mounts for that session and is fleet_conflict-unavailable after the next restart. Today only RegisterFleet does both.

DOES NOT MEAN: the record is how a MOUNTED repo is recognised as the fleet. It is not; fleetRepo() and RepoInstance.IsFleet() still read the ontology id. The record only decides which fleet-id row may be admitted at boot. Nor were `consensus: auto` or the fleet_conflict cause removed; both are still there.
