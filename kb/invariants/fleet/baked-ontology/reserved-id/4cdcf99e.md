# The id `fleet` is RESERVED: every generic door (create in all modes, clone, subscribe, restore, connect) refuses a fleet-id ontology, and a fleet-id repo mounts only through the fleet door or, at boot, as the ONE uid recorded in control.db instance_fleet_repo (plus, while an unfinished create's marker exists, the repository named by that marker); every create/join path MUST record its uid, and JoinFleet and CreateFleet do

The fleet ontology is built into knomit (fact.FleetOntology, the embedded ontology_fleet.yaml). It is NOT a preset and NOT a template: OntologyByPreset and EmbeddedPresetByID have only the default and code arms, the preset picker lists default and code, GET /api/v1/ontologies/presets/fleet answers 404 (unknown preset), and the old fleet template machinery (ErrTemplateFleetLocal, ErrTemplateFleetPresent, ErrTemplateFleetStateUnavailable, checkTemplateMode) is gone. The ontology id `fleet` is RESERVED. One sentinel, ErrFleetOntologyReserved (REST 422 'Fleet ontology reserved'; text: only the fleet API (/api/v1/fleet/...) creates or joins a fleet repository; it said `knomit fleet` until PR #518, a CLI that never creates).

REFUSED, with nothing written, at every generic door:
- CREATE, wherever the request names the ontology: `ontology_preset: fleet`; YAML whose id is fleet in mode custom or initialize (refuseReservedOntology, called from CreatePreflight and again from Create; YAML that does not parse is reported by the create itself, not by this rule); a template whose ontology id is fleet in mode template or initialize (ResolveTemplate).
- IDENTIFY, for every mount that reads an ontology (clone, subscribe, restore, boot): admitFleetOntology admits a fleet-id ontology only when RepoInstance.fleetDoor is set. A clone or subscribe of a fleet remote is therefore refused AFTER the transfer and rolled back, not at preflight.
- RESTORE: Restore mounts with fleetDoor=false, so an archived fleet-id row is refused (REST 422) and stays archived.
- CONNECT / store swap: guardSwap refuses an incoming fleet-id store and any swap of the fleet repository before its point of no return (REST 422).

WHO HAS THE DOOR: fleetDoor is true only (a) for the mount JoinFleet or CreateFleet creates (CreateSpec.fleetDoor is unexported; PR #525 replaced RegisterFleet with JoinFleet), and (b) at boot, for the single repo whose uid is stored in control.db table instance_fleet_repo (migration 000016: one row, id = 1, repo_uid REFERENCES repos(uid) ON DELETE CASCADE). JoinFleet checks the ontology is the fleet ontology and that its root on main is the bundle's, THEN calls recordFleetRepo; if recording fails it undoes the join (the mount and the installed material) and answers 500 record_failed. CreateFleet (PR #518) calls it right after m.Create, and a failure there rolls the whole create back. Nothing clears the row except the foreign-key cascade when the repos row is deleted, which leave, decommission, a refused join's undo and purge all do (the generic delete is refused for the fleet repository). Manager.Start reads the recorded uid once and passes the door to openRegistered only for that uid and, since PR #518, for the repository whose NAME is the one in an unfinished create's marker (control.db instance_fleet_create), so that the boot rollback can open a fleet repository that died before recordFleetRepo and take back what it pushed; if the record cannot be read, NO repo is admitted. It is a table, not a column, because the control migration chain admits only CREATE ... IF NOT EXISTS.

BOOT CONFLICT: any other registered repo whose ontology is or becomes id fleet (an upstream that switched its ontology and the change arrived by sync, a second fleet row, a hand-edited control.db, a home from an older build) is refused at Identify and listed unavailable with reason unopenable and cause fleet_conflict (CauseFleetConflict). It is not the fleet repository: it is not mounted, fleetRepo() and guardFleetRemoval never see it, boot does not archive it, and the user can archive and purge it like any ordinary repo.

CONSEQUENCE (act on this): any future path that makes an instance a fleet host or member (fleet create, fleet join) MUST open its mount with the fleet door AND call recordFleetRepo with the new uid. Without the record the fleet mounts for that session and is fleet_conflict-unavailable after the next restart. Today JoinFleet (PR #525, merge fd991d4f) and CreateFleet (PR #518, merge 537f2019) do both. The marker-name admission is a rollback aid, not a second recorded fleet: it is read only while a create has not finished, and it never makes a non-fleet repository a fleet (the door only ADMITS a fleet-id ontology; the create's undo also requires the repository to hold the fleet ontology).

DOES NOT MEAN: the record is how a MOUNTED repo is recognised as the fleet. It is not; fleetRepo() and RepoInstance.IsFleet() still read the ontology id. The record only decides which fleet-id row may be admitted at boot. Nor were `consensus: auto` or the fleet_conflict cause removed; both are still there.

ENFORCEMENT OF THE WRITERS (G1, PR #582, merged into dev as 333bc2b0; re-read at 333bc2b0). The six control.db fleet-state writers, setFleetState, recordFleetAttempt, recordFleetRepo, writeFleetCreateMarker, setFleetCreateRoot and finishFleetCreate, are package-level functions (not methods) declared in internal/corpus/repos/fleet_identity.go. CONSEQUENCE: they may be called only from fleet.go, fleet_create.go, fleet_identity.go, fleet_master.go, fleet_membership.go and fleet_refusal.go (all in internal/corpus/repos). TestFleetStateWriters_OnlyFleetCallers (internal/corpus/repos/fleet_state_callers_test.go) enforces it: it WALKS internal/corpus/repos recursively (a child directory's file is keyed dir/file.go and is never allowed), matches a bare callee and a selector callee, fails on ANY mention of a writer's name (including a function value taken without a call) in a file outside the six, requires each writer to be declared in fleet_identity.go and called somewhere, requires more than 20 walked files, and compares the exact per-call site list (one entry per call, for example fleet_membership.go:recordFleetRepo once) against a literal `want` string. A recordFleetRepo call from anywhere else could make an arbitrary repository mount as the fleet at boot, so a new caller is a deliberate edit of both the allowlist and `want`.

DOES NOT MEAN: (a) the guard covers test files; it skips _test.go, so a test may call a writer. (b) it covers writeFleetArtifacts or any other fleet function; only the six named writers are guarded. (c) inside the six allowed files the function-value check is off: there only CALLS are counted, so a writer passed or stored as a function value inside an allowed file passes unnoticed. (d) the allowed list says which FILES may call, not which functions: any function in those six files may call any writer.
