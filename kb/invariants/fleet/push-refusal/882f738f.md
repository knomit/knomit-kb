# A fleet copy with an origin accepts NO push over /git (repos.Manager.FleetPushRefusal, at the web edge in pushPolicy): a master with an origin holds fetched, unjudged member tips, and receive-pack judges only the commits a host does not hold

RULE (PR #524, verified at merge commit 9db8c106). For the fleet repository, repos.Manager.FleetPushRefusal(ri) returns a refusal, applied at the web edge in pushPolicy, whenever the copy HAS an origin (master or member); an unreadable origin row also refuses (fail closed). Only the hub (the master's copy with NO origin, a knomit-hosted fleet) accepts pushes. The message tells the pusher to push its agent branch to the fleet's origin and does not echo the origin URL, which may carry credentials.

WHY (the laundering attack, #523 S3 / #524 B1): a master with an origin FETCHES every member branch, refused tips included, so it holds objects nobody admitted; receive-pack judges only the commits the host does NOT hold. A hand-built pack carrying only the merge M(X, main) of a refused, held tip X and main would bring just M to the judge; a clean merge has no content of its own, so M is admitted and X reaches main. Pinned end to end over mTLS by TestFleetMaster_ForgeCopyRefusesPushesSoARefusedTipCannotBeLaundered (a plain go-git push would not show it: it sends X, which gets judged; the hand-built pack with M alone does). Sabotage evidence: with the refusal removed the push was accepted and X reached the fleet's main.

DEFENCE IN DEPTH, NOT THE ONLY GUARD: the receive-pack walk on the fleet repository no longer trusts 'held' (it stops only at held commits reachable from main or an admitted agent/* branch: kb/decisions/store/git-serve/receive-pack/new-commit-walk/75ab4d9f.md), so a hub that was once a forge copy, or holds objects from a pre-#524 member clone, still judges X. With the refusal removed the push is refused for X by that walk (TestFleetMaster_HubJudgesAHeldRefusedCommitAsNew, ...HubJudgesACommitItsMemberCloneHeld). Keep both: the invariant is 'a commit the receive-pack walk skips must be reachable from main or an admitted ref'.

NEW REFUSAL TO KNOW: it also refuses a push to a MEMBER's copy (a member has an origin). That is consistent with 'nobody pushes to a non-master'; on the K hub (no origin) nothing changes.

MISREADING: 'members can no longer push' is false; on a forge they push to the forge, on a hub they push to the hub (no origin).

UPDATE (branch fix/fleet-switch-replay, verified at a78d1b22; re-pin at the merge commit): FleetPushRefusal also refuses on a copy with NO origin (a hub) while this instance is not the fleet's master (isFleetMaster false, or unreadable: fail closed): a hub whose master stood down takes no push, because nothing there merges it and the new master hosts with what main held at the stand-down. The text carries FleetPushRefusalStoodDown, which GET /fleet's last_error_stood_down reads on the refused member. MISREADING: 'a hub always takes pushes': only while its instance is the master.

VERIFIED AT THE MERGE (PR #531, squash commit 8ca72760 on dev, 2026-10-16): FleetPushRefusal (fleet_master.go) refuses a copy with an origin (FleetPushRefusalHasOrigin), fails closed on an unreadable origin row, and refuses a copy with NO origin when ri.isFleetMaster is false, with the text carrying FleetPushRefusalStoodDown ("its master stood down, and it takes no push"). Note the hub check is isFleetMaster (the marker on main names this instance), not actsAsFleetMaster.
