# POST /fleet/follow decides by the URL against the stored origin, never by which page asked: the stored forge URL (or no url) on a forge copy is a CREDENTIAL change that probes and stores and nothing else; a different forge URL is a MOVE on the master and a plain follow on a member; the answer's `change` says which ran

Verified at the merge of PR #529 (60ddfb1c). Manager.FollowFleetHost (POST /fleet/follow, local-only, under fleetOpMu) runs F1 (refuseFleetOrigin, 422 origin_invalid before anything dials) and then splits on the URL compared with the STORED origin (followFleetHost):

1. FORGE COPY (stored origin exists and its method is not cert) AND the url is empty OR sameFleetURL to the stored one: a CREDENTIAL change (changeFleetCredential). An empty url means the stored URL. A credential not given keeps the stored one (no method, or the stored method with no token, keeps the stored token); auth_method `none` is the explicit reset to anonymous. The method is checked against the stored URL's scheme (MethodMismatch, 422 auth_invalid). If method and token equal the stored ones the answer is `change: unchanged` and NOTHING runs. Otherwise the new credential is probed against the forge (it must reach it), stored through AttachOrigin with the stored URL, and that is all: no seed, no host record, no publish, nothing a member sees. A URL that now classifies as a peer (cert) is 409 not_this_fleet (point the copy at it instead). Answer `change: credential`.
2. The url classifies as an instance of THIS fleet (cert): the copy follows it (a master switch); a credential is refused (auth_invalid, the certificate is the credential). Answer `change: followed`.
3. ANY OTHER forge URL (followForge): on a member it follows the forge the fleet moved to with the member's OWN credential (`followed`); on the MASTER it is a MOVE of the whole fleet (moveFleetToForge, see the move-onto-a-forge invariant in kb/invariants/fleet/move) and the answer is `change: moved`. No url on a copy that is not a forge copy is 400 url_required.

CONSEQUENCES. Rotating a forge token on the master is safe: it cannot move the fleet or rewrite the host record. The host record is rewritten by a master's MOVE (and by create, Host here and the hub's reconcile round); NOT by a credential change and NOT by a member's follow. A fleet's forge URL can change only through the move.

MISREADINGS. (1) 'Update access may carry a new URL': on a forge copy a different URL is a move/follow, not a credential change; the page's Update access sends no url at all. (2) 'Sending the same URL again re-runs the move': it is `unchanged` (or `credential`), so an interrupted move cannot be finished by re-sending the forge it stopped on (see kb/architecture/fleet/move). (3) 'Never pushes' means no seed, no host record and no publish of the follow itself: AttachOrigin restarts the Sync stage, so the ordinary origin round runs at once and may push the agent branch or publish main if it is ahead.

TESTS. TestFleetFollow_TheMasterChangesOnlyItsCredential (forge refs and record byte-identical before and after), TestFleetREST_FollowNamesAnUnchangedCredential, TestRefuseMethodForURL.
