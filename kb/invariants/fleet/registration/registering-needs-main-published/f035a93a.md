# A registering fleet on the instance that publishes main (the root holder) becomes registered only after the round's push, INCLUDING the publish of main, succeeded: every push path publishes main first (RepoInstance.publishesFleetMain) and fleetPushed only READS the outcome, staying registering with last_error while it failed; a member's registering still completes on any successful push of its agent branch

PR #518 (merge 537f2019) introduced the rule; PR #524 (verified at merge commit 9db8c106) moved WHERE the publish happens. Why the rule exists: before #518, fleetPushed completed registering -> registered on ANY successful push of the fleet repository's agent branch. For a forge create that was wrong: a create whose publish of main failed stayed registering, and the sync loop's next agent-branch push flipped it to registered while the forge's main was still unpublished.

THE RULE, all parts (as of #524): there is ONE publish path, `publishFleetMainOn(ctx, svc, from, auth)` = store PublishUpstream (never forced) and then local main follows. It is called by `publishFleetMainNow` (fleet create, and FleetRetry via Manager.pushFleet) and by `fleetPeers.publish` (the sync loop's round). An instance's push round publishes main when `RepoInstance.publishesFleetMain` holds: it is the fleet's master (isFleetMaster: root key file here and its certificate the root on MAIN), OR it holds the root before main does (fleet door, fleet repo, root key file here, and the root certificate on the AGENT branch: holdsFleetRootAt; the forge create whose publish of main failed). The loop publishes on every round whose own push did not fail, whether or not that push sent anything. A publish error is the round's push error: it reaches onPush -> fleetPushed. `fleetPushed` NO LONGER publishes: it records the attempt (last_error on error) and, on a nil error, moves registering -> registered; so a failed publish keeps the state registering with last_error, and only a round whose publish succeeded lets it enter registered. (#518's first version had the registering arm call publishFleetMainNow itself; that was removed in #524, along with Manager.holdsFleetRootOf.) publishFleetMain (the create's own step) sets registering explicitly on failure, whatever a concurrent loop push did meanwhile.

THE OTHER ARM IS UNCHANGED: an instance without the root (a member registering through PUT /api/v1/fleet) has nothing to publish (publishesFleetMain is false: no root key file); its registered still means 'my agent branch was pushed'. fleetPushed still ignores non-fleet repos and ignores state standalone, which is why a create in progress (state set only at the end) is never published.

CONSEQUENCES. For the root holder 'registered' means main is on the origin; for a member it does not mean the record is on main (the master merges later; the status shows record_state pending). A hosted-here create is registered at the point of no return and then advances local main, so 201 vs 202 is decided by record_state (kb/architecture/fleet/create/sequence). The loop runs on the reconcile loop's goroutine, after Push has released the push lock, so PublishUpstream can take it.

PINNED BY: TestFleetMaster_TheLoopRoundPublishesMainForTheCreatorOnce (after a create whose publish failed, one loop round publishes main and enters registered, and the create's publish seam is not called a second time) and #518's TestCreateFleet_ForgePublishFailureStaysRegistering (through FleetRetry, which takes the same path). MISREADINGS: 'registered means the fleet is live on the forge' holds for the root holder only; and 'the root holder is the master' is false until main holds the root (publishesFleetMain is the broader predicate).
