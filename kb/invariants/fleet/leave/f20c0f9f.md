# POST /api/v1/fleet/leave makes ONE push of the `left` record (which names the leaf the instance leaves with, leaf_serial) and then, whatever that push did, drops the fleet repository from every lens, deletes it, runs pki.Uninstall and returns the state to standalone, so it works offline; the master is refused (`is_master`); the call itself revokes nothing, the acting master's next round does once the record is on main

RULE (PR #525, verified at merge commit fd991d4f, LeaveFleet in internal/repos/fleet_membership.go). Under fleetOpMu. A standalone instance with no fleet repository answers 409 `not_registered`. The fleet's MASTER is refused with 409 `is_master` (nothing changes): it decommissions, or hands the root on (GET then PUT /fleet/root) and stands down (DELETE /fleet/root) first. For a member: (1) write the own record with state `left` on the agent branch; (2) ONE push attempt of the agent branch; (3) WHATEVER (1) and (2) did: drop the repository from every lens that reads it (a lens may hold it as a read mount only), delete the repository, run pki.Uninstall on [tls].dir, set control.db state standalone. The answer is 200 FleetStatus plus `pushed` (true only if the record was written AND the push succeeded) and `push_error` (the reason otherwise, 'the left record was not written: ...' included).

CONSEQUENCES. (a) Leave works OFFLINE and cannot get stuck: the durable retry-until-pushed unregistration of #334/#336 is gone, so a failed push means the fleet never sees `left`; the master must then revoke the leaf by hand (POST /fleet/revoke), because the automatic revocation (PR #532, verified at a1b0ca5d: kb/invariants/fleet/leave/master-revokes-left/d2132d6b.md) starts from a left record on main. (b) Leave removes the instance from the fleet's NETWORK too: the uninstall makes a running mTLS listener here refuse every peer and cut open connections without a restart (kb/invariants/pki/established-connections/9928b5a7.md) and the knomit+https client finds no certificate. (c) The instance key and the per-root CRL watermark stay, so a later join with a fresh leaf for the same key is possible once the master has revoked the old leaf (enroll refuses `enrolled` otherwise).

MISREADINGS. 'Leave revokes the member': the CALL does not and cannot (only the root key signs a CRL); since PR #532 the acting master's duty revokes the leaf named by the left record's leaf_serial in its first round after that record is on main (LeaveFleet writes it through writeOwnRecord, from the certificate installed in [tls].dir; none installed, no serial, revoke by hand). Until then, and for ever when the push failed, the old leaf still chains to the root, and even after the revocation other members' listeners admit it until they install the CRL (only the master installs it today). 'Leave is refused while offline': the push error is reported, not fatal. 'Leave undoes the join': it removes the local state; the record `left` (if pushed) stays on the fleet.
