# Invariant: the fleet's acting master revokes a leaver's leaf by itself only when main holds a `left` record that names a leaf (leaf_serial), main's current leaf for that id has exactly that serial, and main's CRL does not list it; a left record naming no serial is never revoked automatically

RULE (PR #532, squash-merged into dev as a1b0ca5d, verified there; internal/repos/fleet_leave.go). A member cannot revoke its own leaf (only the root key signs a CRL), so Leave revokes through the MASTER. The leave duty revokes a member's leaf, exactly as POST /fleet/revoke does (revokeLeaf: new CRL built from main's CRL, crl.pem and revocations/<serial>.txt committed on the master's agent branch, the local revoked.jsonl line and crl.pem copy, the CRL installed here, reason "left the fleet"), when ALL of these hold for a member record on the fleet's MAIN (leftLeafDue, the single rule; GET /fleet/members `revoke_due` reads the same function): (1) main holds the fleet's PKI and a CRL; (2) the record's state is `left` as written; (3) the record carries a non-empty `leaf_serial`; (4) main's CURRENT leaf for that agent id (certs/<id>.pem) has exactly that serial (lowercase hex); (5) main's CRL does not list that serial. The member is not the master's own id. Dropping any one condition is a different, wrong rule.

leaf_serial: a line of the `left` record naming the certificate the member held when it left. writeOwnRecord sets it ONLY for state `left`, from the instance certificate installed in [tls].dir (installedLeafSerial); an `active` record never carries it; it is not an advertised field (not in AdvertisedDiff) and older readers ignore it as an unknown field. No installed certificate: the record names none.

WHO RUNS IT. Only an instance that ACTS as the master: fleetLeaveRound returns unless actsAsFleetMaster (holds the root key AND main's master marker names this instance AND no fleetMasterPause), so a root holder main does not name, or a paused master, revokes nobody; the gate lives INSIDE fleetLeaveRound, so it holds on both hostings wherever the call sits. Hub (knomit-hosted): fleetHostRound calls it after the host-record re-assert, before main follows the agent branch. Forge: fleetPeers.duty = RepoInstance.fleetMasterDuty, run by peers.runDuty inside the origin round's `if master` arm right after peers.admit and before the push and the publish of main. Both take fleetOpMu with TryLock: a fleet operation in flight makes the round skip the duty and the next round runs it. The duty publishes nothing itself; the round that ran it publishes the revocation.

THREE GUARDS INSIDE THE PASS. (a) Once: a leaf main's CRL already lists is skipped, so a left record on main is revoked once; without the skip an ErrAlreadyRevoked would abort the pass and block later leavers. (b) Unpublished CRL: if the CRL on the master's agent branch differs byte for byte from main's CRL (a revocation not yet published), the pass writes nothing and a later round retries, because building from main's CRL would drop that revocation. (c) Several leavers: one pass chains the CRLs, each built on the previous. A failure is logged and the next round retries.

TIMING AND REACH. The revocation happens at the master's first round after the member's `left` record is on main, not at the moment of Leave. Hub: the merger merges on receive, so about one local round. Forge: the master must first fetch the member's branch (fetch interval, 300 s by default). Only the master installs the new CRL (pki.InstallCRL has one production caller, revokeLeaf in fleet_membership.go, which runs only on the master): members do not fetch the CRL from main yet, so other members' listeners keep admitting the revoked leaf until they install it. The rejoin then needs no manual revoke: the old leaf is on the CRL, so enroll admits the same key (kb/invariants/fleet/enroll/5c5a3bef.md) and the fresh leaf has a new serial, which differs from any older left record's serial, so the duty never revokes it.

MISREADINGS. (1) 'The leaving member revokes itself' or 'Leave revokes': no; LeaveFleet writes the left record, pushes once and uninstalls; the master revokes later. (2) 'It happens even if the left push failed': no record on main means nothing is revoked; the operator revokes by hand (POST /fleet/revoke). (3) 'Any left record revokes': a left record written before leaf_serial existed, or by an instance with no certificate installed, names no serial and is never auto-revoked (the duty logs it at Debug). (4) 'A stale left record can revoke a rejoin's fresh leaf': no, condition (4); this replaced an earlier landing-order rule (a left record landing after the leaf) that a reviewer showed revoking the fresh leaf of a manual-revoke-then-re-enroll sequence; store.FleetLandedDepth went with it. (5) 'A member can get another revoked': no; the judge's record-owner rule refuses a left record outside the author's own folder and the loader skips a record whose agent differs from its folder. A forge admin writing members/<id>/ on main directly can cause it, which the trust-the-forge decision accepts. (6) 'revokes_left true means a revocation is pending': it only says THIS instance's rounds run the duty (GET /fleet: master AND not master_paused AND main holds the PKI and a CRL).
