# The master switch is GET, PUT, DELETE /api/v1/fleet/root: GET returns <home>/fleet's files (root key included), PUT installs them only where <home>/fleet holds NOTHING, DELETE stands down (deletes <home>/fleet, keeps the membership) and is refused with `hub` while the copy has no origin; nothing checks the other side, so one master at a time is the operator's job

RULES (PR #525, verified at merge commit fd991d4f; all three local listener only and under fleetOpMu).
- GET /fleet/root: the files of <home>/fleet that exist, among root.key, root.crt, crl.pem, issued.jsonl, revoked.jsonl, as {dir, root_fingerprint, files}; `Cache-Control: no-store`. 404 `no_root` when root.key is absent. A non-regular file is an error.
- PUT /fleet/root {files}: REFUSED 409 `root_present` when <home>/fleet holds ANY entry (not only root.key: the files land by a rename that never replaces a directory with content). Also `unknown_file` (a name outside the five), `root_incomplete` (root.key and root.crt are required) and `root_invalid` (pki.LoadRoot on the staging directory <home>/fleet.receiving says the key and certificate are not one root, or the directory is not private). The files go to the private staging directory first, then a rename. The answer is 201 {dir, root_fingerprint}.
- DELETE /fleet/root (stand-down): 404 `no_root` without a root key; 409 `hub` when the fleet repository's copy HERE has no origin (this instance hosts the fleet: standing down would leave the hub without a master and the members without a host), otherwise deletes <home>/fleet and answers 204. The membership (repository, installed certificate, state) is untouched.

THE SWITCH, in the order the e2e uses: GET on the old master; PUT on the new one (it is a master only once the root.crt it installed equals artifacts/fleet/root.crt on the fleet's MAIN, so a PUT of a root that is not the fleet's leaves it a non-master: GET /fleet shows master false); the new master becomes the hub by DELETE /repos/{fleet}/origin (allowed for a master with [tls].addr and external_addresses) or points at the forge; the old hub's copy is repointed at the new master (PUT origin, not gated); only then does the old master's stand-down pass (before, `hub`); members repoint with PUT origin.

WHAT THIS DOES NOT DO. Nothing contacts the other instance: two instances holding the root at once is possible and unsupported (kb/decisions/fleet/two-masters-unsupported/daea77c9.md). The root KEY travels in a response body, which is why the routes are local-only and why the key's earlier 'never leaves custody by any route' is false (kb/decisions/pki/root-custody/plain-key-file/781b626f.md). Decommission (POST /fleet/decommission) also deletes <home>/fleet, root key included. Members' leaves stay valid after a stand-down: it revokes nothing.

PINNED BY TestFleetMasterSwitch_KnomitHosted (cmd), TestFleetMembership_ForgeRootMovesAndTheOldMasterStandsDown and TestFleetMembership_TheHubCannotStandDown (repos).

MISREADINGS. 'PUT overwrites the old root': never, it needs an empty <home>/fleet. 'Standing down makes this instance a plain member again': it keeps the membership but is no longer the master; its listener, leaf and record are untouched.

## UPDATE (PR #528, verified at merge e417fd76): the switch is finished from the UI, with TWO known gaps

SEQUENCE NOW. Old master A: Export root key (GET /fleet/root). New master C: Import (PUT /fleet/root), then Host the fleet here (POST /fleet/host, which needs C's [tls].addr and external_addresses and, for members to be able to join, a RUNNING listener: `knomit reload` after the import). A: Point at the new host (POST /fleet/follow with C's fleet URL), then Stand down (DELETE /fleet/root), which succeeds only now that A has an origin (it is refused `hub` before; the UI offers Point at inline on that refusal). The Fleet -> Settings page walks all of it (FleetFollowFlow is Point at). TestFleetMasterSwitch_KnomitHosted (cmd) runs it on real mTLS hubs.

KNOWN GAP N1 (true at merge e417fd76 of PR #528; reads FALSE once PR8 fixes it, then update this fact): after a SELF-HOSTED master switch in which the new master's copy of the fleet repository is BEHIND the old hub's (the old hub merged something after the new master last synced, e.g. a member's pushed branch), the new host refuses the old master's pushes, and keeps refusing them. The old master's agent branch is replayed onto the new host's main, including its own create-time commit that wrote the host record, and the new host's judge refuses it ("host-record: agent ... changes artifacts/fleet/host: only the fleet's master writes where the fleet is hosted"). The old master's Settings shows "Last sync failed ... Retrying on the next sync", which never helps; its records and any facts it authors never reach the fleet; the only way out is Leave plus a revoke and re-enroll. Reproduced live; the cmd test misses it because there the new master is fully current with the old hub before it hosts, so nothing is replayed. Same class: after a revoke and same-key re-enroll, the replaced leaf's artifact-replace rule (replace_when leaf-renewal: NotBefore must be later than the replaced leaf's) refuses the old master's older leaf for the re-enrolled member. Candidate fixes (PR8): do not replay the old hub's master-only commits onto the new host's main; or make Host here refuse (fetch first) while this copy's main is behind its origin's; or have the judge accept a replayed master-only commit whose content is already on main. MISREADING: "the switch is safe if the UI finished": not while the new master was behind.

KNOWN GAP N3 (same condition: reads false once openapi is fixed): the openapi text of DELETE /fleet/root still says to point the copy at the new master first with `PUT /repos/{fleet}/origin`, which is 409 `fleet_repository`; the route to name is POST /fleet/follow (the server's own `hub` refusal text is already right).

UPDATE (PR #529, verified at merge 60ddfb1c): (1) Stand down (DELETE /fleet/root) is also refused 409 `not_following_host` when the copy has an origin that is not one of the URLs the host record on main names (GET /fleet follows_host false): a hub pointed at a plain member, or a copy that followed the wrong peer, would leave the fleet without a master where it is hosted (refuseNotFollowingHost; a main with no host record decides nothing). The refusal text says to Point at the fleet's host and, right after pointing, to WAIT for the first sync, because the first sync is asynchronous and a stand-down immediately after Point at can be refused until main arrives. Test: TestFleetStandDown_RefusedWhileNotFollowingTheHost.
