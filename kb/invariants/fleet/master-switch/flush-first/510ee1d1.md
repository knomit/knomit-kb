# A master switch FLUSHES first: root export (GET /fleet/root), stand-down (DELETE /fleet/root) and a forge decommission on the acting master publish its fleet branch and refuse with 409 unpublished_changes while main still lacks any commit of it; the dead-master fallback (Host here with confirm_loss) may lose those commits

RULE (fleet PR8b, PR #537, merged into dev at b4677384 and re-read there; user ruling as relayed 2026-10-17: "flush" all changes, "block any new incoming changes, THEN give up the master role"). `flushBeforeSwitch`, called under fleetOpMu by `FleetRootFiles` (GET /fleet/root), `StandDown` (DELETE /fleet/root, which also holds the consensus merger's run lock) and a FORGE `DecommissionFleet` (POST /fleet/decommission, before deleteFleetMaster; fleetOpMu ONLY: holding the merger's run lock across the repository's removal hung), on the ACTING master only (actsAsFleetMaster). EVERY way of giving up the role flushes first:
1. `publishMasterWrite` (forge: push the agent branch, publish main; hub: main follows locally);
2. `fleetBranchPublished`: the agent branch tip must be main's tip or an ancestor of it (Triggers().IsAncestor);
3. otherwise 409 `unpublished_changes` with a plain message whose last sentence (unpublishedWayOut) fits the case: main held by the judge of this instance's own commits (store.ErrOwnCommitRefused) -> drop that commit first (the "Drop commit <hash>" card, POST /fleet/drop-commit), waiting never helps; a forge -> fix the origin or wait for the next sync round; the hub (no origin) -> wait for the next sync round. StandDown and DecommissionFleet keep the root, the repository and main's master marker.
The master duties TryLock fleetOpMu, so nothing new is written meanwhile.

WHY (PR #537 re-review R1). A forge stand-down publishes ONLY the marker deletion straight onto the forge's main (deleteFleetMaster -> PublishUpstreamChange); the agent branch's other commits stayed behind. A revoke whose publish had failed then never reached the main the new master worked from: its renewal re-certified the revoked member, or its CRL re-sign took the same Number and the old revocation could never land (crl-newer). The reviewer's probe is kept as internal/repos TestFleetSwitch_AnUnpublishedRevokeSurvivesAMasterSwitch (fails with the pre-fix code: renewal-due and CRL-due cases leave bravo unrevoked); TestFleetSwitch_ExportAndStandDownWaitForTheFlush pins the refusal. Re-review 2: a forge decommission (publishes only the marker deletion, then DELETES the repository, so the unpublished revoke was gone for good) had no flush; TestFleetSwitch_GivingUpTheRoleAfterAnEarlyExport (export first, then an unpublished revoke, then stand-down or decommission, nothing due or renewal due: all four keep bravo revoked) and TestFleetSwitch_ADecommissionWaitsForTheFlush pin it; TestFleetSwitch_TheRefusalOnAHeldHubMainPointsAtTheDrop pins the hub message.

CONSEQUENCES.
- A root holder cannot claim while main still names the old master (fleetCandidate needs a main naming no master); taking over WITHOUT the old master's stand-down is Host here with `confirm_loss` (the dead-master fallback, hub path), which knowingly risks whatever the old master never published. KNOWN GAP, not recovered: a revocation made by a master that then died unpublished MAY be lost; revoke again on the new master. It can still land only while the new master has issued no CRL of its own (the old CRL N+1 is then strictly newer than main's N; whether the rest of that late branch is admitted was not tested). Once the new master has issued CRL N+1 or later, the judge's crl-newer rule refuses the old master's CRL, so it can never un-revoke or replace a newer list.
- This SUPERSEDES the 2026-10-16 "no flush" wording of kb/decisions/fleet/master-switch/stand-down-first/9efa08ef: stand-down still comes first, but it flushes before giving up the role.

THE FULL LIST of ways the acting master can change, and which flush or need confirm_loss, is kb/invariants/fleet/master-switch/handoff-paths/ (reviewed against this code, 13 paths).

MISREADING. "Stand-down needs nothing first": it needs the fleet branch published; on a forge that is unreachable it is refused. "Only stand-down and export flush": a forge decommission flushes too (the hub decommission has no successor and does not). "A dead master's unpublished revoke is always lost": it MAY land late (see above); do not rely on either outcome, revoke again.
