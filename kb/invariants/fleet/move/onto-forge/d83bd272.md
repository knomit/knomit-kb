# The master moves the fleet onto a forge in a fixed order, seed (PublishTo) BEFORE attach, then host record, then pushFleet; a refused seed changes nothing (publish_refused) and a failed host-record write restores the previous origin; the target must hold THIS fleet's root on main or be EMPTY (no ref at all)

Verified at the merge of PR #529 (60ddfb1c); user ruling 2026-10-16: the hub moves onto a forge as a mode of POST /fleet/follow on the hosting master. Applies when the master (from the hub, which has no origin, or from another forge) follows a forge URL other than the stored one (followForge -> moveFleetToForge, under fleetOpMu after F1).

SAME-FLEET CHECK (remoteFleetRoot, a shallow single-branch probe clone of the target's main): the remote's main must carry artifacts/fleet/root.crt EQUAL to this copy's, or the remote must be EMPTY and the caller the master. Anything else is 422 not_this_fleet: main carries another root or none (remoteRootDiffers); no main but other branches or tags (remoteNoMain, see the no-main-is-not-empty incident in kb/incidents/fleet/move); an empty forge for a member (only the master seeds a new repository). Unreadable is ErrOriginUnreachable. The forge is probed with the credential given first (probeFleetForge).

ORDER (moveFleetToForge): 1. SEED: svc.Remote().PublishTo pushes the agent branch tip as the forge's main (without force) and as the agent branch (force). 2. ATTACH: AttachOrigin; the Sync stage restarts on the origin loop, which on the master is the fetching master (SyncWithPeers, the judge, the merger, publish). 3. HOST RECORD: writeFleetHost with the forge URL, credential-free. 4. pushFleet publishes main (a failure here is only logged; the origin round retries).

WHY THE SEED IS FIRST (the user asked for 'set the origin, then push'; the code deliberately deviates): the origin round that the attach starts trusts the forge's main AS FETCHED, rewinds included (kb/architecture/fleet/master-merges/91e3f6da.md, trust-the-forge-main). Attaching first would let that round force-update local main to the forge's main, and on a diverged forge replay the hub's branch onto it. Seeding first makes the forge refuse a diverged main (409 publish_refused, 'it must be empty or behind this copy's', 'Nothing changed here') before anything changes. Nothing reads what a failed seed left on the forge until an origin points there.

ATOMICITY: a failure in 1 or 2 changes nothing here. A failure in 3 restores the previous origin (a DetachOrigin for the hub, a re-attach of the stored URL, method and token for a forge; a cert origin is re-classified) and returns the error, so the copy is exactly as it was. A failure in 4 does not undo the move.

AFTER THE MOVE: GET /fleet hosting is the forge, host_record is the forge, follows_host true on the master; every member's follows_host is FALSE until it points at the forge with its own credential, and its pushes to the old hub are refused (a copy with an origin accepts no push). A member's unmerged work is not lost: it re-pushes on its first sync after pointing at the forge and the fetching master merges it (TestFleetHubMovesToAForge).

MISREADINGS. (1) 'Attach first, push second is equivalent': it is equivalent only when the forge is empty or behind; only on a diverged forge does the order matter, which is why the pinning test uses a diverged forge. (2) 'A master with an origin does not merge': it is the fetching master. (3) 'The move works for a member': a member's follow of a forge only attaches.

TESTS. cmd TestFleetHubMovesToAForge (e2e, a member's unmerged change merged by the fetching master); internal/repos TestFleetMove_TheHubMovesOntoAnEmptyForge, TestFleetMove_BackOntoAForgeWhoseMainIsBehind, TestFleetMove_ADivergedForgeMainIsRefusedBeforeAnyChange (sabotage: dropping the seed turns it red; dropping it does NOT turn the empty-forge test red, because the first origin round publishes main onto an empty forge anyway), TestFleetMove_AFailedHostRecordRestoresTheOrigin (both subtests), TestFleetFollow_AForgeMustHoldThisFleet.
