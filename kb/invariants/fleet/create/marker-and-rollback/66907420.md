# A fleet create is bracketed by the instance_fleet_create marker (control.db, migration 000017); the point of no return is the ONE transaction that sets the fleet state and deletes the marker, and a failed step, a crash (boot), the next create and the next registration all run the same state-driven rollback, which on failure keeps the marker and answers create_unfinished (409)

PR #518 (merge 537f2019). THE MARKER. control.db table instance_fleet_create (migration 000017, CREATE TABLE IF NOT EXISTS; id = 1 CHECK so there is at most one): repo_name (the fleet repository's local name, free when the create began), started_at, root_id (pki.RootID of the root the create minted, '' until it exists), tls_dir_existed (whether [tls].dir existed before). It is a separate table because the control migration chain admits only CREATE ... IF NOT EXISTS (TestControl_UpMigrationsAreIdempotentDDL) and instance_identity's fleet_state CHECK cannot gain a state without rebuilding that table. The migration's prose must contain no semicolon: the idempotency guard splits the file on semicolons before it strips comments. writeFleetCreateMarker fails if a marker is already there.

POINT OF NO RETURN. finishFleetCreate(db, state, now) is ONE SQLite transaction: it sets fleet_state (registered with no origin, registering with an origin) AND deletes the marker. Both or neither. Before it commits, the fleet state is still standalone and every failure is rolled back; after it, nothing is rolled back (a failed publish of main leaves registering + last_error and is retried, kb/invariants/fleet/registration/registering-needs-main-published). Because the state is set only here, fleetPushed (which ignores state standalone) can never publish main for a fleet that is about to be rolled back. The rollback ends with the same call, finishFleetCreate(standalone), so the marker is deleted LAST and every earlier undo step may run again.

THE ROLLBACK (undoFleetCreate) reads what to undo from the marker and from what exists on disk, not from what a failed call remembers, newest first: (1) the repository: the mounted repository holding the fleet ontology that is the recorded uid or has the marker's name (fleetCreateRepo; a user repository can never hold the fleet ontology, so one that later took the name is never touched). First its forge branch is retracted (RetractPushedBranch, kb/architecture/store/remote-sync/retract-pushed-branch), then deleteRepo. A repository of the marker's name registered since started_at that did not mount (unavailableFleetCreateRepo) is deleted locally only. (2) uninstallFreshTrust, only if the root installed in [tls].dir is the marker's root id: when tls_dir_existed is false the whole [tls].dir goes (crl.number included), otherwise only instance.crt, crl.pem and root.crt (the per-root watermark entry and the <dir>.lock file stay). (3) the staging directory <home>/fleet.creating is removed whole. (4) removeCreatedRoot: <home>/fleet is removed only if its root.crt has the marker's root id. (5) finishFleetCreate(standalone).

WHO RUNS IT, ALWAYS UNDER fleetOpMu: a failing step of CreateFleet (under context.WithoutCancel); BOOT (startFleetBootReconcile runs recoverFleetCreate before fleetBootReconcile); the top of CreateFleet; the top of JoinFleet (PR #525: RegisterFleet no longer exists, the join took its place; leave, enroll, revoke and decommission do not run it). Manager.Start also admits, through the fleet door, the repository NAMED by an unfinished create's marker, so a forge repository that died before recordFleetRepo mounts (instead of fleet_conflict) and its pushed branch can be taken back. Without that the boot rollback could not open it.

WHEN THE ROLLBACK FAILS: the marker is kept, the error is written to the fleet's last_error, and the answer is create_unfinished (409) from recoverFleetCreate (a create or registration that finds the marker), or the original error with 'the rollback is incomplete' appended (a create whose own undo failed). It is retried at the next start, create and join. A create or join is refused until the rollback succeeds. PR #525 added the way out to the 409 text: 'If the forge's agent/<id> moved to a tip this instance did not push, delete that branch on the forge by hand, then retry' (the retract uses a lease on the last tip this instance saw, pushed or fetched, so a foreign tip is never deleted).

TESTS: TestCreateFleet_FailureAtEachStepRollsBack and _DiedAtEachStepIsRolledBackAtBoot (steps marked, root, repo, recorded, committed, installed, rooted), _DiedIsRolledBackByTheNextCreate, _DiedRepoThatDoesNotMountIsRolledBackAtBoot, _ForgeDiedBeforeTheRecordIsRolledBackAtBoot, _ForeignInstallIsLeftAlone, _RootWrittenMeanwhileIsLeftAlone.

MISREADINGS. 'Deleting the marker is the point of no return': it is the transaction that also sets the state; the rollback deletes the marker too, as its last step. 'The rollback deletes whatever is in <home>/fleet or [tls].dir': only the root or install the marker's root id names. 'A marker found at boot means a crash': it means a create that is not running; the guarantee that no create is running rests on fleetOpMu AND on one Manager per home (a second process booting on the same control.db during a live create would roll it back; nothing here changes that single-server assumption). 'A rollback that fails stops everything': it blocks create and registration (create_unfinished) until it succeeds; reads and the rest of the instance work. NOT EXERCISED (read from code): if Commit reports an error after the transaction landed, undoFleetCreate then finds no marker and does nothing, so the fleet is not destroyed and the create just answers an error. TESTED SINCE PR #525: a rollback that FAILS. TestCreateFleet_FailedRollbackIsRetriedUntilTheForgeBranchIsGone leaves a foreign tip on the forge's agent branch: the marker stays, create and join both answer create_unfinished, last_error says 'rollback incomplete', and once the branch is deleted by hand the retry succeeds.
