# fleetOpMu serialises every fleet operation (CreateFleet, JoinFleet, LeaveFleet, enroll, revoke, decommission, the root GET/PUT/DELETE, the fleet repository's origin detach) and the boot rollback because each checks the state and then changes it, and because a create marker found under the lock is taken to be a dead create's: a losing concurrent create's rollback would delete the winner's root

PR #518 (merge 537f2019), widened by PR #525 (merge fd991d4f; RegisterFleet and UnregisterFleet no longer exist). Manager.fleetOpMu is held by CreateFleet, JoinFleet, LeaveFleet, EnrollFleetMember, RevokeFleetMember, DecommissionFleet, FleetRootFiles (GET /fleet/root), InstallFleetRoot (PUT), StandDown (DELETE), `DetachRepoOrigin` on the fleet repository (check and detach as ONE step: a stand-down passes while the copy has an origin, and without the lock it could remove the root key between the master check and the detach and leave a hub with no master) and the boot rollback goroutine (startFleetBootReconcile). Every membership route is local-listener only AND takes this lock (TestFleetOps_TakeTheFleetLock pins each waiting while the lock is held; TestFleetMembership_DetachTakesTheFleetLock pins the detach, but NOT that the check and the detach share one hold: a lock taken after the guard stays green). Take it only with lockFleetOp, which is TryLock, else the test hook `contended`, else Lock.

WHY (two reasons). (1) Each of these reads the fleet state and then changes it; two at once would both pass the 'standalone' check. (2) The rollback treats a marker it finds under the lock as a DEAD create's: recoverFleetCreate runs at the top of every create and registration and undoes whatever the marker names. If two creates ran at once, the second one's recovery (or its own failure rollback) would roll back the FIRST one's live create and delete the winner's repository, install and root directory. The first version of #518 had exactly this exposure (the loser's rollback deleted the winner's root directory); the lock is what makes 'a marker under the lock is a dead create' true.

THE LOSER IS REFUSED, NOT RUN: the second create waits for the first, then fails its pre-flight with fleet_present; the winner's root survives (TestCreateFleet_ConcurrentCreatesOneWins parks create A at the 'marked' step and requires B to report a wait through the contended hook; no sleeps). TestFleetOps_TakeTheFleetLock pins each operation waiting while the lock is held.

CONSEQUENCES. The boot rollback holds the lock and may make one network call (the forge branch retract), bounded by network_timeout, so a create or registration that arrives right after boot waits for it. A test that holds fleetOpMu, or that 'kills' a create (errFleetCreateDied) and then restarts, must first wait for fleetBootWg: the same Manager's boot goroutine takes fleetOpMu and rolls back any marker it finds, which masks the sabotage or undoes the 'dead' create before the test restarts (startFleetHost does this wait).

MISREADINGS. 'The lock protects against another process': it is an in-process mutex; one Manager per home is assumed. 'The pre-flights already make a second create fail': they run after the lock is taken; without the lock two creates both pass them. 'a read-only-looking route needs no lock': GET /fleet/root takes it too, so a read of <home>/fleet never sees a stand-down or a PUT half done; 'the machine takes the lock': it does not, which is why DetachRepoOrigin can call Send while holding it without deadlock.

UPDATE (PR #527, verified at merge commit c6e282db). A second kind of holder exists: the hub's fleetHostRound (kb/architecture/fleet/host-record/9c4e1732.md) takes fleetOpMu with a BARE TryLock and SKIPS the round when an operation holds it, instead of going through lockFleetOp (TryLock, the contended hook, then a blocking Lock). That is deliberate: a create or detach holds fleetOpMu while its Sync stage runs the local-reconcile loop inline under Synchronous, so a blocking Lock in the round would deadlock. A skipped round is not lost: the next round (every local_reconcile_interval, default 30 s, and each commit wake) writes. The line above, "take it only with lockFleetOp", therefore holds for every operation that must run, and NOT for a periodic duty that may skip. MISREADING: "every fleetOpMu holder waits its turn": fleetHostRound never waits. It also never starves: operations hold the lock briefly (the longest hold is the boot rollback's one bounded network call).

UPDATE (PR #528, verified at merge e417fd76): `DetachRepoOrigin` no longer exists. The fleet repository's origin detach is Manager.HostFleetHere (POST /fleet/host) and its attach is Manager.FollowFleetHost (POST /fleet/follow); BOTH take fleetOpMu (lockFleetOp) and HostFleetHere still checks (guardFleetDetach) and detaches as ONE step under one hold (TestFleetMembership_DetachChecksAndDetachesAsOneStep). Read every `DetachRepoOrigin` above as HostFleetHere. The lock list therefore grows by FollowFleetHost; the generic origin routes never reach the Manager for the fleet repository (409 fleet_repository).

UPDATE (PR #529, verified at merge 60ddfb1c): two more holders, both through lockFleetOp: Manager.RebuildFleetIndex (POST /fleet/index-rebuild) and the whole of FollowFleetHost including the master's move onto a forge (followFleetHost: defer m.lockFleetOp()()), which means the seed push, the attach, the host-record write and pushFleet of a move all run under ONE hold, and a slow forge delays every other fleet operation (and the boot rollback) for that long. MISREADING: 'a failed move leaves the lock held': the deferred unlock runs on every return.
