# fleetOpMu serialises CreateFleet, RegisterFleet, UnregisterFleet and the boot rollback because each checks the state and then changes it, and because a create marker found under the lock is taken to be a dead create's: a losing concurrent create's rollback would delete the winner's root

PR #518 (merge 537f2019). Manager.fleetOpMu is held by CreateFleet, RegisterFleet, UnregisterFleet (the last since review finding N7) and the boot rollback goroutine (startFleetBootReconcile). Take it only with lockFleetOp, which is TryLock, else the test hook `contended`, else Lock.

WHY (two reasons). (1) Each of these reads the fleet state and then changes it; two at once would both pass the 'standalone' check. (2) The rollback treats a marker it finds under the lock as a DEAD create's: recoverFleetCreate runs at the top of every create and registration and undoes whatever the marker names. If two creates ran at once, the second one's recovery (or its own failure rollback) would roll back the FIRST one's live create and delete the winner's repository, install and root directory. The first version of #518 had exactly this exposure (the loser's rollback deleted the winner's root directory); the lock is what makes 'a marker under the lock is a dead create' true.

THE LOSER IS REFUSED, NOT RUN: the second create waits for the first, then fails its pre-flight with fleet_present; the winner's root survives (TestCreateFleet_ConcurrentCreatesOneWins parks create A at the 'marked' step and requires B to report a wait through the contended hook; no sleeps). TestFleetOps_TakeTheFleetLock pins create, register and unregister each waiting while the lock is held.

CONSEQUENCES. The boot rollback holds the lock and may make one network call (the forge branch retract), bounded by network_timeout, so a create or registration that arrives right after boot waits for it. A test that holds fleetOpMu, or that 'kills' a create (errFleetCreateDied) and then restarts, must first wait for fleetBootWg: the same Manager's boot goroutine takes fleetOpMu and rolls back any marker it finds, which masks the sabotage or undoes the 'dead' create before the test restarts (startFleetHost does this wait).

MISREADINGS. 'The lock protects against another process': it is an in-process mutex; one Manager per home is assumed. 'The pre-flights already make a second create fail': they run after the lock is taken; without the lock two creates both pass them. 'UnregisterFleet is read-only so it needs no lock': it changes the state.
