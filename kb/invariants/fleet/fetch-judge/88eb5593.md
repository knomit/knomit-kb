# The master's fetch-time judge covers EVERY commit of tip∖main with receive-pack's judge core (non-empty selfRoot, no signer = pusher), memoised per (branch, tip, main); the merger re-judges each local agent/* against the CURRENT main before merging and DEMOTES a branch it now refuses

RULE (PR #524, verified at merge commit 9db8c106). When a forge-hosted fleet's master fetches a member branch, the branch ENTERS the repository only through store.AdmitPeerBranch, which is JudgePeerBranch plus promotion:
- It judges EVERY commit of `tip ∖ main` (a walk from main, as CheckRange does), not the tip alone. A refused commit under an admissible tip refuses the branch: the reason names that commit and the refusal's tip is the branch tip (TestFleetMaster_ARefusedCommitUnderAnAdmissibleTipIsRefused).
- It uses receive-pack's core: verify.PrivatePathClosure, then verify.JudgeIncoming (internal/store/verify/incoming.go; the former body of receivePack.verify; receive-pack, in the gitserve child, passes a signer = pusher check, the fetch judge passes nil). SHAPE AT THE PR #564 MERGE d7bd363f: the walk of tip minus main and both calls are made DIRECTLY by remotesync.Repo.JudgePeerBranch (internal/store/remotesync/peer_admit.go) with the shared *vcs.Repo (rh.Repo.Repo), reading the fleet through fleetrec.At at the consensus branch; the parent's repoHandler forwards judgeIncoming and privatePathClosure were DELETED (no forwarding wrapper remains in package store; checkOwnLineage and the public names stay in verify_seam.go). Service.JudgePeerBranch and Service.AdmitPeerBranch (internal/store/service_sync.go) are thin forwards that resolve the consensus branch once and refuse "" (ErrNoConsensusBranch) before the core runs; AdmitPeerBranch promotes through remotesync.Repo.PromotePeer. Do not look for judgeIncoming or privatePathClosure on repoHandler; a rule change in verify.JudgeIncoming still reaches the fetch judge automatically. selfRoot is the fleet's fact root and is NON-EMPTY, so rule A and the record-owner rule run; with an empty selfRoot an own-record edit would be refused (TestFleetMaster_FetchedEditOfAnotherMembersFolderIsRefused has the control). There is NO pusher on a fetch, so there is no signer = pusher rule. Every other rule (signature state, records, rules A/B, `not-owner`, `malformed-tree`, artifact rules) is the push's, and rule changes in judgeCommit reach the fetch judge automatically (TestFleetMaster_FetchedEditByAnExistingMemberIsRefusedNotOwner pins an existing member's edit of another member's folder as `not-owner` at fetch).
- The verdict depends on main, so the memo key is (branch, tip, main) (peerKey), not the tip: a leaf issued on main admits a join refused before it (no-cert), and a revocation refuses a branch admitted before it. Entries at an older main are dropped. A refused tip is not re-judged until its tip OR main moves.
- Two writers use the memo: the fetch judge (the branch's tip on the origin) and the merger (the local branch's tip, which can be an OLDER admitted tip while the fetch refuses a newer one). An admission clears a branch's refusal only when it is of the same tip or comes from the fetch judge, so a merger's admission of an older tip cannot erase a newer tip's refusal (TestFleetPeers_AMergerAdmissionOfAnOlderTipKeepsTheRefusal).
- main's history is read once per round (and once per merger run) as store.MainHistory and shared by every branch judged.

RE-JUDGE AND DEMOTE (both hostings): before merging, consensusMerger asks fleetPeers.mayMerge, which re-judges the local agent/* branch against the CURRENT main with the same memo. A branch admitted earlier and now refused (a revocation landed on main) is recorded as `last_refusal` and DEMOTED: store.DemotePeerBranch (a thin Service forward to remotesync.Repo.DemotePeerBranch since PR #564; it does not refuse an empty consensus branch name, unlike JudgePeerBranch and MainHistory) drops refs/heads/<branch> under its write lock, only while it is still at the judged tip (a push or promotion that moved it meanwhile is left alone). The objects stay on the host; receive-pack's walk re-judges them if they come back (kb/decisions/store/git-serve/receive-pack/new-commit-walk/75ab4d9f.md). The fetch judge demotes too. One refused earlier and now admissible is admitted (on a forge the next round promotes it). Pinned by TestFleetMaster_ARejudgedRefusalDemotesTheAdmittedBranch (forge and knomit-hosted hub rows).

WHAT IT DOES NOT MEAN: the fetch judge does NOT cover the forge's main (see the trust-the-forge decision); it does not re-verify history already on main; and, as of PR #524, the operator's manual web merge (MergePushed) did not re-judge. SINCE PR #525 (verified at merge commit fd991d4f) it does on the fleet repository: the merge route calls `RepoInstance.FleetMergeRefusal`, which refuses a non-master (`not_master`) and on the master runs `svc.JudgePeerBranch(branch, own agent branch, expected_tip, nil)` (this same judge core, tip minus main, against the current main) and answers 409 `judge_refused` before MergePushed runs (kb/architecture/store/git-serve/pushed-branch-merge/f9ec4794.md). TEST GOTCHA: because the merger demotes a refused branch, a route-level test of a refused branch on the master can get 404 instead of 409; retry on 404 and assert only that no merge happened. A restart clears the memo and refusals, so each fetched branch is judged once more.

UPDATE (PR #527, verified at merge commit c6e282db). (1) The refusal bookkeeping (fleetPeers.verdictLocked) dedups: the same branch refused again at the SAME tip for the SAME reason is not a new refusal, and last_refusal and the 200-entry ring keep the FIRST one's time, so a stuck branch (main moved, or a retried push) cannot fill the ring. An ADMITTED push (receive-pack's pushed(), latest = true) clears the branch's current refusal and does not touch the memo (the merger re-judges an admitted tip against the main it merges into). (2) judgeIncoming now sets judge.entry, which switches on the host-record rule for this fetch judge and receive-pack alike (kb/invariants/store/verify/host-record/899af4cd.md); CheckRange does not. MISREADING: "the dedup is per branch": it is per (branch, tip, reason); a new tip or a new reason is a new entry.
