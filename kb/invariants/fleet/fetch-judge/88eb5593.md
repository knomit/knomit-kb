# The master's fetch-time judge covers EVERY commit of tip∖main with receive-pack's judge core (non-empty selfRoot, no signer = pusher), memoised per (branch, tip, main); the merger re-judges each local agent/* against the CURRENT main before merging and DEMOTES a branch it now refuses

RULE (PR #524, verified at merge commit 9db8c106). When a forge-hosted fleet's master fetches a member branch, the branch ENTERS the repository only through store.AdmitPeerBranch, which is JudgePeerBranch plus promotion:
- It judges EVERY commit of `tip ∖ main` (a walk from main, as CheckRange does), not the tip alone. A refused commit under an admissible tip refuses the branch: the reason names that commit and the refusal's tip is the branch tip (TestFleetMaster_ARefusedCommitUnderAnAdmissibleTipIsRefused).
- It uses receive-pack's core: repoHandler.privatePathClosure, then repoHandler.judgeIncoming (the former body of receivePack.verify, which is now a thin wrapper passing signer = pusher). selfRoot is the fleet's fact root and is NON-EMPTY, so rule A and the record-owner rule run; with an empty selfRoot an own-record edit would be refused (TestFleetMaster_FetchedEditOfAnotherMembersFolderIsRefused has the control). There is NO pusher on a fetch, so there is no signer = pusher rule. Every other rule (signature state, records, rules A/B, `not-owner`, `malformed-tree`, artifact rules) is the push's, and rule changes in judgeCommit reach the fetch judge automatically (TestFleetMaster_FetchedEditByAnExistingMemberIsRefusedNotOwner pins an existing member's edit of another member's folder as `not-owner` at fetch).
- The verdict depends on main, so the memo key is (branch, tip, main) (peerKey), not the tip: a leaf issued on main admits a join refused before it (no-cert), and a revocation refuses a branch admitted before it. Entries at an older main are dropped. A refused tip is not re-judged until its tip OR main moves.
- Two writers use the memo: the fetch judge (the branch's tip on the origin) and the merger (the local branch's tip, which can be an OLDER admitted tip while the fetch refuses a newer one). An admission clears a branch's refusal only when it is of the same tip or comes from the fetch judge, so a merger's admission of an older tip cannot erase a newer tip's refusal (TestFleetPeers_AMergerAdmissionOfAnOlderTipKeepsTheRefusal).
- main's history is read once per round (and once per merger run) as store.MainHistory and shared by every branch judged.

RE-JUDGE AND DEMOTE (both hostings): before merging, consensusMerger asks fleetPeers.mayMerge, which re-judges the local agent/* branch against the CURRENT main with the same memo. A branch admitted earlier and now refused (a revocation landed on main) is recorded as `last_refusal` and DEMOTED: store.DemotePeerBranch drops refs/heads/<branch> under its write lock, only while it is still at the judged tip (a push or promotion that moved it meanwhile is left alone). The objects stay on the host; receive-pack's walk re-judges them if they come back (kb/decisions/store/git-serve/receive-pack/new-commit-walk/75ab4d9f.md). The fetch judge demotes too. One refused earlier and now admissible is admitted (on a forge the next round promotes it). Pinned by TestFleetMaster_ARejudgedRefusalDemotesTheAdmittedBranch (forge and knomit-hosted hub rows).

WHAT IT DOES NOT MEAN: the fetch judge does NOT cover the forge's main (see the trust-the-forge decision); it does not re-verify history already on main; and the operator's manual web merge (MergePushed) does not re-judge, so a head refused at the current main but not yet demoted can still be merged by an operator in that window. A restart clears the memo and refusals, so each fetched branch is judged once more.
