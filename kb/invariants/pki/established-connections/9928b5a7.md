# A connection on the TLS listener stays open only while a fresh handshake from the same peer would be accepted, checked at most one tick late — and the check is snapshot.check, the SAME VerifyInstanceChain VerifyConnection runs, never a narrower test

THE RULE (knomit#258). A connection accepted by the mTLS listener is kept open only while `snapshot.check(cs, UsageClient)` against the CURRENT snapshot passes. `snapshot.check` is `VerifyInstanceChain(cs.PeerCertificates[0], cs.PeerCertificates[1:], s.root, s.crl, time.Now(), usage)`, and it is ALSO what the handshake runs: `reloader.verify` calls it and only adds the `tls_refused` log line. One function, two callers, so the handshake and the re-check cannot disagree about a peer.

WHEN IT RUNS on an established connection, and all three are needed:
1. when the connection is first tracked, at its first `StateActive` (`ConnRegistry.ConnState` → `judge`). This catches a handshake verified under an OLDER snapshot: one in flight while a new CRL was adopted, or one that handshook, sent nothing (StateNew, untracked) until after the adoption, then started talking.
2. right after a handshake's `refresh` adopts a new file set (`Server.refresh`, outside the reloader's lock).
3. once per interval in `Server.Run` → `tick`: refresh (adopting without any ClientHello), then EXACTLY ONE sweep whether or not the tick adopted. Without the timer, adoption only ever happens on a ClientHello and a kept-alive connection is never reached.

CONSEQUENCES TO ACT ON:
- Because the check is the full verification, it cuts a REVOKED peer, a peer whose certificate EXPIRES mid-connection, and every peer of the old fleet after `install --replace-root`. That is the rule, not a side effect: all three are what a fresh handshake would refuse.
- The bound is one `tlsRecheckInterval` (`pki.DefaultRecheckInterval`, 10s) after the CRL lands on disk, plus zero for a connection first tracked after adoption.
- A refused connection's UNDERLYING socket is closed (`c.NetConn().Close()`), not `tls.Conn.Close()`, which sends close_notify under the lock a handler's Write holds and so can be stalled by a peer that stops reading. The `tls_conn_closed` line (reason = the named error, `serial`, `peer` fingerprint, `remote`) is logged BEFORE the close.
- Any new listener that serves enrolled peers must use `pki.NewServer`, set `http.Server.ConnState: s.ConnState`, and run `s.Run(ctx)`. `pki.ServerConfig` alone re-checks nothing after the handshake; it survives only for test callers.

WHAT THIS DOES NOT MEAN:
- NOT "revocation checks the CRL on every request". Requests are not checked; connections are, at the three moments above. A revoked peer can complete requests for up to one interval.
- NOT a licence to add a cheaper `IsRevoked`-only path for the sweep. That is the two-verifiers motif; the sabotage that narrowed the check to `IsRevoked` turned the expiry test red, which is how you would notice.
- NOT coverage for HIJACKED connections: `StateHijacked` forgets the connection (net/http never reports it closed). No knomit handler hijacks today; one that does must re-verify its own connections.
