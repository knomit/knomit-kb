# InsecureSkipVerify appears in knomit ONLY on a tls.Config whose VerifyConnection runs pki.VerifyInstanceChain, and every path through that verifier that cannot verify returns an error — the HTTPS twin of the SSH rule that forbids falling back to InsecureIgnoreHostKey

WHY InsecureSkipVerify IS NEEDED AT ALL: knomit certificates carry only a `knomit://<role>/<host>-<fp8>` URI SAN. crypto/tls's own client verification demands a DNS or IP SAN matching the dialed host, so it refuses every knomit peer; go-git's ClientCert/CABundle options have no hook to replace it. `InsecureSkipVerify: true` turns Go's check off so knomit's can run.

THE RULE: that field may be set ONLY on a tls.Config whose `VerifyConnection` calls `pki.VerifyInstanceChain` (chain to the fleet root ALONE, the right EKU, CRL, SAN shape, fingerprint cross-check, role), and every path through the verifier that cannot verify — no peer certificate, no CRL, a CRL from another root, anything VerifyInstanceChain refuses — must return an error. The config must also be impossible to BUILD without its inputs: `pki.ClientConfig` returns an error when instance.crt, root.crt or crl.pem is missing or bad, so a verifier with nothing to verify against never exists. Today the sites are `pki.ClientConfig` (production) and the test clients in server_test.go and `pkitest.Fleet.Client`, which follow the same shape.

THE TRUST ANCHOR IS THE FLEET ROOT ALONE. VerifyInstanceChain puts ONLY the fleet root in `Roots`; certificates the PEER sends go in `Intermediates` and never become anchors. `TestVerifyInstanceChain_PeerSuppliedCAIsNeverATrustAnchor` (a correctly shaped leaf presented with its own attacker CA as an 'intermediate' → ErrUntrustedRoot, with a positive control that the same leaf verifies when that CA IS the root) and `TestServerConfig_PeerSuppliedCAInTheChainIsRefused` (the same over a real handshake) go red under the review's sabotage S-D — adding the intermediates to the roots pool — which before them left the whole suite green. That one line would be a complete trust bypass.

RootCAs IS INERT under InsecureSkipVerify — crypto/tls never consults it. `ClientConfig` sets it to the fleet root for the reader only. `TestClientConfig_RootCAsIsInertTheFleetRootAloneDecides` enrols a server under a 'public' root, puts that root in a client's RootCAs, and asserts refusal; a faithful sabotage (verifier trusting cfg.RootCAs at handshake time) turns it red. Adding the system pool to RootCAs therefore changes nothing — and editing VerifyInstanceChain's pool to include it would make any publicly trusted certificate a fleet peer (not catchable in-process; do not do it).

SABOTAGE EVIDENCE: making the client VerifyConnection `return nil` turns the other-root, revoked-server and CRL-reload tests red; the server side's equivalent is pinned in kb/gotchas/pki/require-any-client-cert-is-stronger.

MISREADING TO AVOID: 'knomit uses InsecureSkipVerify' is not 'knomit skips verification'. And the rule is not satisfied by a VerifyConnection that merely exists: one that logs and returns nil on an unexpected state is exactly the InsecureIgnoreHostKey fallback the SSH invariant forbids.
