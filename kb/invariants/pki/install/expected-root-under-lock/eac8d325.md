# An identity install is decided against the root the CALLER SAW, under a cross-process lock: pki.InstallBundle installs only if the installed root ("" = none) still equals InstallOptions.ExpectInstalledRoot when read under <pki>.lock, and refuses otherwise with a RootDiffersError naming the root it found — never re-reading and proceeding

RULE. Every production caller of `pki.InstallBundle` (the desktop Settings binding and `cmd/identity.go`, pinned by test/archtest) passes `InstallOptions{ExpectInstalledRoot}`. That is the RootID fingerprint of the root it READ as installed and — when that root is new to this instance — SHOWED the user and had confirmed; "" means it saw no root installed. Under a cross-process exclusive lock on `<pki>.lock` (flock / LockFileEx, `pki.LockFile`), InstallBundle reads the installed root (`pki.InstalledRoot`) and:
- root.crt present but unreadable or not Ed25519 → refuse, ALWAYS (no expected value can vouch for bytes nobody could have seen); the error names the file, and removing it is the way out;
- installed fingerprint != ExpectInstalledRoot → refuse with `*RootDiffersError{Installed: <what it found, empty when none>, Bundle}`; nothing written;
- otherwise the CRL watermark check, then the writes, still under the lock.

The lock is held from that read through the writes and the watermark record, so the root compared is the root replaced. There is no replaceRoot flag: expecting the installed root while installing a bundle from another root IS the move to another fleet.

CONSEQUENCES for a caller:
- Read the installed root with `pki.InstalledRoot(dir)` and pass exactly that. It returns the zero RootInfo for a MISSING root.crt and an error for an unreadable one. REFUSE on that error BEFORE showing or asking anything: read as "none" (as `pki.Status`, which drops an unreadable root, would have it), an unreadable root turns into a first-install question that pki then refuses after the user confirmed. Both front ends do this (TestFleetIdentity_UnreadableRootIsRefusedBeforeAsking, TestIdentity_UnreadableRootIsRefusedBeforeAsking).
- Never pass the bundle's own root, and never re-read and retry on RootDiffersError — surface it. Desktop: after a confirmation it is confirmation_stale naming the root now installed; on an unconfirmed call (a renewal) nobody was asked, so it becomes a fresh root_unconfirmed / root_differs question. CLI: "the installed fleet root changed while this command ran".
- Collecting consent is YOURS, not pki's: pki will install a first bundle for ExpectInstalledRoot "" and a foreign root for ExpectInstalledRoot = current without asking anyone. The desktop refuses an unseen root as root_unconfirmed / root_differs and installs only on a second call carrying the shown pair. The CLI prints the root and principal and needs --root <fp>, --yes, or a y/N answer on a terminal. A renewal (bundle root == installed root) needs no consent.
- Run `pki.PreviewBundle(keyPath, raw)` before asking: it runs the bundle-and-key checks, so the user is never asked to trust the root of a bundle that could never install.
- The lock file is a SIBLING of <pki>, never inside it, so a refused install still leaves <pki> exactly as it was (absent on a fresh home); only <pki>'s parent is created, 0700. The lock file is never deleted: unlinking a lock file lets a waiter hold a lock on an orphaned inode while a newcomer locks a fresh one.
- REQUIREMENT that follows: <pki>'s PARENT must be writable by the installing user. A [tls].dir made ahead of time inside a directory that user cannot write (e.g. /etc/knomit/pki under a root-owned /etc/knomit) used to accept installs and now fails with "install lock <dir>.lock: …" (TestInstallBundle_UnwritableParentNamesTheLock). Every lock error is prefixed "install lock <path>".
- The wait for the lock is bounded (installLockWait); a timeout says it waited for another identity install.

MISREADINGS:
- "The desktop's installMu serialises installs." Only within one process; the CLI is another process. The pki lock is what serialises them.
- "A first install has nothing to compare against." It compares against "none installed" (so a root installed underneath by another process is refused), and the caller compares the bundle root with the operator's out-of-band fingerprint.
- "Atomic renames make concurrent installs safe." They keep the FILES consistent; they do not keep the DECISION (which root was confirmed) true. That is the lock's job.
- "pki.Status is how to read the expected root." No: Status is for display, and it reports an unreadable root.crt as absent. Use InstalledRoot.

Proven by internal/pki/install_test.go:
- TestInstallBundle_RootChangedSinceReadIsRefused (A installed and read; C installed by "another process"; B expecting A → RootDiffersError naming C, C intact — deterministic, no goroutines);
- TestInstallBundle_FirstInstallIsCheckedAgainstNoRoot (parent created, <pki> absent after refusal, lock beside it);
- TestInstallBundle_WaitsForTheInstallLock;
- TestInstallBundle_UnreadableInstalledRootFailsClosed;
- TestInstalledRoot_MissingIsNoneUnreadableIsAnError;
- TestInstallBundle_UnwritableParentNamesTheLock.
