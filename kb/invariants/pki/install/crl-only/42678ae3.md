# pki.InstallCRL installs a CRL alone only when its root is the INSTALLED root and its Number is STRICTLY above that root's watermark; an equal or lower Number is refused with ErrCRLRollback and crl.pem stays untouched

RULE (fleet design D13, PR #512). `InstallCRL(dir, rootCert, raw)`:
1. raw must be exactly one `X509 CRL` PEM block that parses (no trailing PEM blocks), else `ErrCRLInvalid` (checked before the lock);
2. under the install lock (`lockInstall(dir)`, the one InstallBundle uses), the installed root (`InstalledRoot(dir)`) must have rootCert's RootID, otherwise `*RootDiffersError`, including when NO root is installed: a CRL never installs or changes a root;
3. the CRL must be signed by rootCert (`CheckCRL` against `AcceptedNumber(dir, rootCert)`);
4. its Number must be STRICTLY greater than that watermark: lower or EQUAL is `ErrCRLRollback`. With no watermark yet, any valid CRL passes.
Only then crl.pem is written (writeFileAtomic, 0600) and the watermark raised (RecordAcceptedNumber).

WHY EQUAL IS REFUSED. `CheckCRL` alone accepts Number == watermark (it refuses only lower), and InstallBundle still uses that 'not lower' test. For a CRL-only install an equal Number is either the CRL already held or a different list reusing a Number; neither may replace crl.pem.

CONSEQUENCES. The member tick should call InstallCRL only when the fleet repo's crl.pem Number exceeds the watermark, and treat ErrCRLRollback on an EQUAL Number as 'nothing to do', not an incident. A refused call leaves crl.pem and crl.number untouched (TestInstallCRL_OnlyAboveTheWatermark). test/archtest/install_callers_test.go pins pki.InstallCRL's production callers (installCRLCallers, empty at merge): the fleet reconcile's member tick must be added there deliberately.

MISREADING. This is not InstallBundle's rule: a bundle's CRL with an equal Number is still accepted by InstallBundle.

UPDATE (PR #525, verified at merge commit fd991d4f): `installCRLCallers` is no longer empty: it lists `internal/repos/fleet_membership.go`, whose revoke route (POST /api/v1/fleet/revoke, local listener only) installs the CRL it has just signed under its own installed root, (the CRL is built from main's current CRL with Number + 1, so it normally passes the rule above; a refusal, for example ErrCRLRollback when this instance's watermark is already higher than main's CRL, comes back as the failure below). A failure there is reported in the answer's `install_error` and does not undo the revoke (the CRL is already committed and published). The member tick is still not a caller and must be added to `installCRLCallers` deliberately when it lands (PR 8). MISREADING: 'InstallCRL has no production caller' (the earlier text) is false at fd991d4f; 'members install newer CRLs from the fleet repository' is still false.

UPDATE (fleet PR8, PR #536, merge 67e19eb3): the member tick landed. `installCRLCallers` lists internal/repos/fleet_tick.go beside fleet_membership.go; `Manager.installMainCRL` calls InstallCRL only when main's Number exceeds AcceptedNumber for the installed root and treats ErrCRLRollback as nothing to do, as the CONSEQUENCES above asked.
