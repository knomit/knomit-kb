# A fleet revocation file is ONE canonical, domain-tagged, root-bound statement (knomit-revoke/v1, root fingerprint (64 lowercase hex), serial (lowercase hex, no leading zero), revocation time (RFC 3339 UTC, whole seconds), reason (printable ASCII, at most 200), newline-joined, then 'signature: <base64 ed25519>') and pki.VerifyRevocation REBUILDS the bytes from validated fields, requires the file to be exactly their canonical encoding, checks the fingerprint is this root's, then verifies; it never verifies bytes taken from the file

The second user of the domain-separated signed-statement rule of the oauth approval (kb/invariants/oauth/signed-approval-statement/c862c8b8.md): the fleet root key also signs X.509 certificates and CRLs (DER, starting 0x30), so a non-X.509 use signs a text message whose first line is a knomit-<purpose>/v<n> tag. Code: internal/pki/revocation.go (RevocationStatement.Bytes, SignRevocation, VerifyRevocation). pki.RevokeSerial returns the signed file as Revocation.Statement. The commit judge verifies an ADDED fleet/revocations/*.txt with VerifyRevocation against the tree's root (artifact-pki on failure).

WHAT IT DOES NOT MEAN: the statement is a record, not the enforcement. A serial is revoked for TLS and rule B only by being on crl.pem; the judge does not cross-check a statement against the CRL. A file name means nothing (ordering and meaning come from the signed content). A revocation file in the fleet repository does not revoke anything by itself.
