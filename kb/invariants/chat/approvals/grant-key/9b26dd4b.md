# A chat's 'Allow for session' grant is keyed (binding pin, tool, action): the pin is the repo:<uid> or lens:<uid> the call's handle resolves to, so a grant for repo A never covers repo B, two handles on one repo share it, a review answer never covers a takeover or start, and an unknown tool or action is never grantable

The gate (chat.Decide) asks mcp.ClassifyCall, the one (tool, action) table: a read-only call runs with decision kind auto. A side-effecting call whose handle resolves (clientsessions BindingHandle -> pin) looks up grantKey{pin, tool, action}; with no grant it emits an approval event and blocks until the person answers, the turn is cancelled or the chat ends. The action for a single-action tool is the tool name without its knomit_ prefix (learn, update, retract). A write whose handle does not resolve (no `binding`, a handle that names nothing, or no session store) is NOT auto-approved: it asks, with no target named, and is not grantable, exactly like a failed lookup (TestChat_UnresolvedTargetWriteAsksAndIsNotGrantable, covering learn, update, retract, experiment open/sync/commit/rollback, review start/answer and hypothesize start, each with the binding absent and bogus; shown red against the old branch that returned auto). The server's binding gate refusing such a call later is a second line of defence, never the approval. Before 2026-11-05 this case ran as decision auto with no card (live acceptance of PR 763, unbound knomit_learn). A call whose handle LOOKUP FAILS (InProcessSession.TargetPin returns an error: the control store is busy or closed) fails closed the same way: it asks, with no target named, and is not grantable (TestChat_TargetLookupErrorAsksInsteadOfRunning, shown red when the error is treated as unresolved). A call the table does not know always asks and POST approvals with allow_session on it is 400; a repeat of the call asks again (TestChat_UnknownActionAsksAndIsNeverGrantable, shown red against the one guard, the Grantable refusal in answerApproval). The grant lookup in Decide is unconditional with no known check of its own: a grant is stored only by answerApproval and only for a Grantable call, so no stored key can belong to an unknown or unresolved call. A turn whose context is already cancelled returns the cancellation from Decide before any approval is emitted (TestChat_CancelledContextEmitsNoApproval). Non-destructive writes (hypothesize start, experiment open, sync, commit) ask too and are grantable (TestChat_NonDestructiveWritesAsk).

Consequences a reader must keep: (1) allow_session on knomit_learn into alpha must not cover beta (the pin differs); (2) it DOES cover a second handle on alpha (same pin); (3) review answer, start, takeover and page are separate actions: a grant for answer covers neither takeover nor an experiment rollback, and a page needs no approval. Removing the pin from the key, or folding takeover into answer, reopens a write that no one approved; each is pinned by a test that was shown red against that change.

Does NOT mean grants outlive the chat: they live in the chat and end with it. GET /chats/{id}/grants lists them for the Settings tab. A grant is REVOCABLE: DELETE /chats/{id}/grants with the body {target, kind, tool, action} exactly as the listing shows it removes that one grant (chat.revokeGrant deletes every key whose grantInfo equals it, 404 when none does), so the next call of that tool and action on that target asks again while every other grant stays in force (TestChat_RevokedGrantAsksAgainAndLeavesTheOtherInForce). Revoking does not decide a call that is already waiting for approval, and a revoked grant is not recorded anywhere: the listing simply no longer has it.

Does NOT mean a grant on knomit_learn is a grant to add facts only: knomit_learn takes a retract argument, so (pin, knomit_learn, learn) also covers deletions made through learn's atomic-move retract. The key is (pin, tool, action) and learn with a retract is the action learn; the user decided on 2026-11-04 not to split it (kb/decisions/chat/approvals/ba7069ac.md). A separate knomit_retract call still asks.
