# One id everywhere: the chat id (chat-<32 hex>), the clientsessions session id, the endpoint /api/v1/chats/<id>, the Knomit-Trace value chat:<id> and the persistent session log's filename stem and every line's session_id are the same string; the log is <home>/chat-logs/<id>.jsonl (dir 0700, file 0600), append-only, and survives the chat

sessionLog implements llm.SessionLog: one JSON object per line with session_id, seq, ts and type in chat_start, request (model, per-hook item ids and token estimates, usage including cache read and write), turn (neutral Entry), tool_call (call id, name, args, is_error, result), approval (call id, tool, action, decision, pin) and chat_end (reason). A tool result is kept inline up to 8192 bytes (cut at a rune boundary) with truncated and bytes set; the full result lives only in the chat's temp file. The log's approval action and pin come from the gate (callMeta), because llm.ApprovalLog carries only call id, tool and decision.

Why the id must be one string: the Sessions page joins on the clientsessions id, the commit trailer is searched by chat:<id>, and the log is the only durable record of what a chat did once its temp files are gone. Writing the log under any other id breaks all three joins silently; TestSessionLog_CorrelatesWithMCPSession fails when the log's session_id differs from the chat id.

The secret is never in the log: a test greps the process log, the session log, every temp file and every response for a plaintext api_key. Rotation and retention are out of scope.
