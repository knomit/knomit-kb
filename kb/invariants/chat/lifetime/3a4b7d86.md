# A chat ends 60 seconds (chatStreamGrace) after its OWNER's last page events stream closes (or at creation when none is attached), on DELETE, or when the server's lifetime ends; ending unwinds a blocked approval, records ended_at on the MCP session, removes the temp dir, and appends a chat_end record to the persistent session log and closes it (the log FILE is never removed); each process keeps its temp files in one lock-guarded run directory that the next start sweeps

Heartbeat (P11), per page not per chat: there is ONE events stream per browser tab (GET /chats/events, carrying every chat of the caller, each event tagged with its chat id; the per-chat /chats/{id}/events route is gone). A chat's grace timer runs only while its owner has NO page stream attached: it starts at creation when none is attached, and for every chat of the owner when the owner's LAST page stream closes; any attaching page stream stops the timers of all the owner's chats. Several tabs or browsers each hold one stream and a chat lives while any one is attached. A chat created while a page stream is attached starts no timer; the timer callback (graceFired) FIRST clears the fired timer and only then re-checks the owner's stream count, so neither the create-then-attach race can end a covered chat nor can a stream closing while the timer fires leave a chat with no stream and no clock (startGrace returns early while a timer is set, so clearing after the check would lose the clock). Two guards, each with its own test: detachPage starts clocks only when the owner's set is empty, and graceFired re-checks the count. Does NOT mean a chat survives its owner closing every tab: after the last page stream closes it still ends 60s later. A reconnect within the grace keeps the chat and the stream's first frame is a page-level event: ready (the client reloads what it shows). The page does NOT send DELETE on pagehide any more (it used to): another tab may show the same chats, so closing a tab must not end them; the grace after the last page stream closes is now the only way a closed browser ends its chats (reloading a tab keeps them).

chat.end runs once, whichever caller wins: it forgets the chat (later requests are 404), cancels the chat context so a blocked Decide and a running turn return, waits for the turn goroutine (bounded at 10s), sends chat_end (tagged with the chat id) to the owner's page streams, which stay open, closes the InProcessSession (clientsessions End: ended_at), appends a chat_end record to the session log and closes that file (sessionLog.End; the file itself stays) and removes <run>/<chatID>. Skipping the session close leaves a row that never ends; a test fails on it.

Server shutdown (the third way a chat ends): App.Close ends the Server's Lifetime, which starts the chat manager's shutdown on its own goroutine (every chat's end runs in parallel, then the run directory is released). App.Close then calls web.Server.WaitReleased(shutdownReleaseWait = 15s) BEFORE manager.Close, because manager.Close closes control.db and the teardown writes to it (the client_sessions row's ended_at, then the chat_end log line). The bound is 10s (maxTurnEndWait: the longest one chat waits for a turn that ignores cancellation, chats end in parallel) plus 5s of headroom for the teardown after that wait (sess.Close: one control.db UPDATE, the chat_end log line, RemoveAll), each far shorter than 5s on a healthy disk; serveUntil's HTTP grace is unrelated to this bound; a teardown stuck past it is logged and abandoned so a stop cannot hang. WaitReleased covers the origin-session manager too. After App.Close returns, every chat's row has ended_at, its log's last line is chat_end and no turn is still running. TestApp_CloseEndsALiveChatBeforeControlDBCloses runs a chat mid-turn through the real App and reads control.db and the log after Close; it was shown red with the WaitReleased call removed. The in-package TestChat_ShutdownEndsEveryChatAndRemovesTheRun cannot see this ordering because its harness keeps the store open.

Does NOT mean the wait is unbounded or that a hung model call delays the stop past 15s: past the bound the chat is left half torn down (row open, log without chat_end) and the next start's sweep removes only the temp dir.

Temp layout (P12): <sessionsDir>/run-<id>.lock + run-<id>/<chatID>/{transcript.jsonl,calls/<callID>.json}, dirs 0700 and files 0600. The run-lock and sweep scheme is httpx.AcquireRunDir / SweepDeadRuns, extracted from api/origins (which uses it too): liveness is an OS lock, never a pid, and the sweep removes only runs whose lock it can take. Mount sweeps once, synchronously, before serving. The session log directory is separate (<home>/chat-logs) and nothing here removes it.
