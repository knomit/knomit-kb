# New knomit UI reuses the app's existing paradigms (the repos page's top tiles that switch the view, the create-repo wizard for multi-step create/join) and never shows a user internal plumbing such as the knomit+https:// URL scheme

Ruled by the designer on 2026-10-15, reviewing the first Fleet UI mockups (PR 7): "I want to bring these in line with how the repos creation workflow works - like tiles and the top, which when selected will show different data. Also, I want the fleet creation or join to be a wizard - like the create repo workflow is. Same paradigm, no reason to invent anything." And on the `knomit+https://` URLs shown in the join form: "why invent this, what's the benefit ? why do we even need to know that, I mean, from the joiner point of view, is there any difference when you join ?!"

TWO RULES:
1. A new page or flow copies an existing knomit paradigm: a page with several views uses the repos page's tiles at the top, where selecting a tile changes the data shown below; any multi-step create or join flow is a wizard in the create-repo wizard's paradigm (its steps, back/next, review step, error display). Same components, same wording patterns.
2. A user types and sees only what they need to tell apart. If a distinction exists only for knomit's plumbing (which git transport, which URL scheme selects it), knomit decides it internally and the UI does not ask for it or show it.

OPERATIONAL CONSEQUENCE: a UI or mockup brief names the existing component to copy and tells the agent to list anything with no existing pattern as an open question, not to invent one. Before a field or value goes into a UI, ask whether the user needs that distinction.

WHAT THIS DOES NOT MEAN: it does not freeze the existing UI or forbid new views; it forbids new interaction paradigms where an existing one fits. It does not mean the internal distinction is removed from the code: the knomit+https scheme exists for a real transport reason (kb/decisions/repos/remote/knomit-https-scheme/180d8654.md); the rule is only that the user is not made to know it.

CORRECTION (designer, 2026-10-15, on the second Fleet mockups, which copied the create-repo wizard literally — including a Name field a fleet does not need — and used the wizard's choice tiles as the navigation of the master's view): "I know I said repos, but I meant the f-ing look and way of operating, not an EXACT copy. I mean, 'Create a fleet' need a 'name' ? ... why the f-ing tiles, when this is NOT A WORKFLOW ? Why not follow the same visual paradigm we have for the repos like 'Browse' / 'Activity' / etc ?" "Use the appropriate visual paradigm for the appropriate operation, so we can keep everything consistent."

SO THE RULE IS: match the PARADIGM TO THE KIND OF OPERATION, then reuse that paradigm's look and behaviour. A one-off multi-step workflow (create, join) is a wizard in the create-repo wizard's look and way of operating — with only the steps and fields THIS operation needs. A persistent thing you inspect and manage (a repo, the fleet) uses the repo page's tabbed views (Browse / Activity / Settings and the like). The wizard's choice tiles are a control INSIDE a workflow step, never navigation.

WHAT THIS DOES NOT MEAN: 'reuse the repos workflow' does not mean copying its fields, steps or wording one for one. Every field must be justified by the operation at hand; a field that exists only because the template had it is a defect.
