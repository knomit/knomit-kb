# On the motif surfaces every rendered element is treated as a CLAIM about the data, and an element is drawn only when the data supports exactly that claim — no hue (hue claims a subject), names whole or counted (a truncated name claims the opposite), the count beside a list is the list's own, a cell says value / pending / failed and never a false zero, a derived mode stores nothing, and a control whose measurement carried no signal is removed

A rendered element — a colour, a number, a truncated name, an enabled control, a stored mode value — is read by a person as a claim about the underlying data, so on these surfaces an element is drawn only when the data supports exactly that claim, and where the data cannot support it the element is withheld, folded into a count, replaced by an explicit pending or failed state, or removed outright rather than allowed to assert something false.

The instances, each a different kind of element:
- COLOUR CLAIMS A SUBJECT. Every neighbouring hue names a subject facet, and a motif's whole claim is subject-independence, so motifs are the colourless element everywhere, marked by the ≈ relation glyph and read text-first. A real `chipColors.motif` entry exists to say 'no colour' because the fallback would render path-grey — silently wrong rather than deliberately colourless. Colourlessness is permanent, not a slot awaiting a freed hue.
- A TRUNCATED NAME CLAIMS THE OPPOSITE. A motif name is a compressed sentence whose claim sits in the tail, so right-ellipsis inverts it; names render whole or fold into a counted `+N` cell, definitions wrap rather than clip, and only carrier TITLES may ellipsize because they identify rather than claim.
- A COUNT BESIDE A LIST IS A CLAIM ABOUT THAT LIST. The pivot heading once printed the cluster's carrier count, the same number only until another chip narrowed the rows; a reader saw 14 beside 8 rows and concluded the filter was broken. Any count drawn next to a collection is computed from that collection or says in the UI what else it counts; the motifs block states its own contrast outright (health strip authored-only and never narrowed, header count narrowed), and a fixture pinning such a pairing must give the two quantities different values or it tests nothing.
- A CELL SAYS ONE OF THREE THINGS. Edge and motif cells distinguish resolved-zero (rendered inert, never removed, so the row does not collapse), pending (`···`) and failed (`!`); a failed fetch must never render as a zero because the hook clears the arrays on error. With the row's border, fill and dividers gone, colour and cursor are the WHOLE of what separates inert from live from failed.
- A DERIVED MODE STORES NO VALUE. The pivot is a peer mode derived from the motif chip exactly as relevance is derived from the search box; writing it into `librarySort` recorded a derived value over the remembered one and erased where the reader came from, so `PIVOT_MOTIF` must never write the sort, the ≈ segment is an EXIT twin of the search exit, and a derived mode disables the rest of the strip because it forces the ordering. A rule stated for one derived mode did not generalise itself to the second; state it for a third explicitly.
- A CONTROL THAT WOULD SHOW A NUMBER WITH NO SIGNAL IS REMOVED. The widen rungs honoured every design rule (measured delta before the click, inert when empty, nothing hard-coded) and were still removed because across every live corpus the stem rung was dead and the token-2 rung admitted unrelated motifs joined by a stopword; a control whose value is a corpus property must be measured against the corpus before it ships. The inert-when-empty rule itself stands.
- ABSENCE IS ITS OWN STATE. In a build whose client lacks the motif reads, the block absents itself without layout holes rather than erroring, because reporting a fault in a build working as intended would itself be a false claim; and the singleton fold never shows a count with nothing under it.

WHAT THIS DOES NOT MEAN: the edges row's reinstatement was a deliberate reopening for NAME-CONTROLS and does not reopen permanent count-readout rails or the empty-collapse protocol; `EXIT_MOTIF` is not a general clear-filters; a content chip alone disables only the path segment, a distinct case from the derived-mode rule; and widening is not impossible in principle — the server side is intact and it is dead because this corpus has no judge merges and this tokeniser's near-miss class is noise.
