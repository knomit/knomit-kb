# Review is a gate, not a loop

Run ONE `/code-review high` per PR, in a fresh session, after tests pass. Triage every finding into blocks-merge / fix-later / won't-fix BEFORE editing anything — a high-effort review is designed to surface uncertain findings and will always find some, so an untriaged review reads as a wall of blockers. Fix only the blockers, in one batch, then merge without re-reviewing. Re-review only if a fix touched a file outside the original diff.

A fix that needs a new file or a new flag is a design change, not a fix. Stop and settle the design as its own decision instead of patching. Cross-component state (can-the-user-leave, is-it-busy) gets one owner and one gate, decided before the first line — not assembled reactively across review rounds.

Why: PR #80 was 30 minutes to implement and 4 hours to fix. Two "close the review findings" rounds added 438 lines across 6 files — more than the 369-line feature itself — and reached into `App.tsx` and `TopBar.tsx`, which the original PR never touched. Five flags (`leavable`, `commitFailed`, `connectBusy`, `onBusyChange`, `leftRef`) accumulated to answer one question nobody had decided: may the reader leave? Every new flag became the next round's bug — `leftRef` was itself a stale-flag bug that existed only because `leftRef` existed. The loop does not terminate when patches are themselves reviewed.

What this does NOT mean: it is not a ban on fixing review findings, and not permission to merge over a real defect. Blockers still get fixed before merge. It targets the second and third review PASSES over the same PR, not the first. Nor does it mean high-effort review is the wrong level — `high` is correct for the single pass; the discipline is in the triage that follows it, not in reviewing less.
