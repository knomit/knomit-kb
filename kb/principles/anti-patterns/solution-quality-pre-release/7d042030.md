# While pre-release, reject quick wins and minimum-change solutions

Knomit has not shipped yet. While pre-release, do NOT prioritize "quick wins", "drop-in" swaps, or "minimum changes" — and do NOT rank or tier options by integration effort or how little existing code they touch. Rank options solely by which produces the BEST end result, and treat the current architecture as mutable when a better design demands it: hardcoded constants (e.g. factsVecDim=768), hand-rolled single-purpose components (e.g. the BERT-WordPiece-only tokenizer), and embedded inference/model choices are all changeable, not constraints to design around. There is no migration-cost penalty pre-release — the SQLite index is rebuildable from git — so greenfield the right design instead of retrofitting.

What NOT to do: presenting a recommendation as effort-ordered tiers ("Tier 0: free win, Tier 1: low-risk, Tier 2: real work"); calling something a constraint when it is really just code we wrote and can change; choosing a worse model/design because it's a closer drop-in to what exists; rationalizing a shortcut as "good enough for now."

Revisit this principle once knomit ships and real migration cost makes incrementalism rational again. Stated and reinforced by the designer 2026-06-04 ("I'm looking for the BEST SOLUTIONS... we're still building this software, it was not released yet. Do NOT take 'quick wins' or 'minimum changes' as something that has priority").
