# Two Claude Cowork jobs shared one Desktop MCP connection and therefore one Mcp-Session-Id, so their knomit_bind calls overwrote each other and five writes were served from the wrong knowledge base — caught only because the two ontologies shared no topic

On 2026-09-17 two Claude Cowork sessions ran concurrently: a scheduled task bound to lens `knomit-positioning` and an interactive crawl bound to repo `agentic-engineering`. Claude Desktop opens ONE connection per configured MCP server and shares it across all Cowork sessions, so both jobs flowed through one knomit-bridge process (pid 62841), one stdio pipe, one JSON-RPC id counter and one `Mcp-Session-Id`. `session_bindings` was keyed on that id with an upsert, so each job's `knomit_bind` overwrote the other's: the bridge log shows the binds alternating SEVEN times between 15:02 and 15:32. Four `knomit_learn` calls and one `knomit_update` ran against the wrong target, and the crawl's dedupe queries ran against `core` silently.

THE NEAR MISS, which is the part that matters. Those five writes FAILED — but only because the two ontologies happened to have no topic in common, so they died as "unknown topic technology" / "unknown topic incidents". Nothing in the routing caught anything. Between two bases that share a topic the same writes would have committed silently into the wrong repo, with a correct-looking success result naming the wrong destination.

WHY NO CLIENT-SIDE FIX WAS POSSIBLE. Nothing in the wire messages identifies the Cowork session: no `_meta`, no header, nothing. Desktop consumes the session id for its own permission gating and never forwards it. This is not a Desktop bug to wait on — MCP revision 2026-07-28 removed protocol sessions and `Mcp-Session-Id` entirely and directs servers that need cross-call state to use server-minted handles passed as ordinary tool arguments (SEP-2567). A client sharing one connection across logical sessions is the model the protocol moved to, so session-keyed binding was built on a construct the spec deleted.

STILL IN FORCE AFTER PR #240, which reintroduced session-keyed state on URL-SCOPED mounts (`mount_experiments`). The lesson is NOT reversed: session-keyed state remains forbidden wherever it would choose a KNOWLEDGE BASE, and PR #240 admits it only where the URL has already made that choice — there it can select a branch within one base and nothing more. The same sharing this incident describes is still live and is knowingly accepted there: two jobs on one connection share one row, so one opening an experiment moves the other with it — within the one repo the URL named. A reader meeting the new table without this paragraph concludes the incident's finding was overturned.

ESCAPE ADDED BY PR #664: on a scoped (--repo/--lens) connection a job can avoid the shared session row by calling knomit_bind (which there changes only the branch) and passing its own handle: one handle per job. A handle-routed call masks the connection's session state (kb/invariants/mcp/session-binding/scoped-handle-masks-mount-state), and committing or rolling back ANOTHER job's experiment by name no longer ejects the caller from its own (kb/invariants/mcp/experiments/commit-by-name-keeps-caller; the same ejection existed on the unscoped endpoint). The accepted hazard REMAINS for jobs that pass no handle: they still share the one session-keyed row.

EVIDENCE: `/tmp/knomit-bridge.log` (pid 62841); `~/Library/Logs/Claude/main.log` around 15:01–15:35 — "Connected to knomit (9 tools)" appears ONCE, and the permission lines name session `local_b2ec1e4b…`; `~/.knomit/control.db` `session_bindings` held exactly one row.

REGRESSION ANCHOR: `TestIncident20260917_TwoCoworkJobsOneMCPSession` in `internal/edge/web/incident_20260917_bind_handle_test.go`. It runs two jobs over one session id through the real router and asserts every write and read by content. Its fixture deliberately gives both repos the SAME ontology, because that is the condition under which a misrouted write lands silently — a test built the other way cannot fail for the real reason.

WHAT THIS DOES NOT MEAN: the incident was not a bug in Claude Desktop, and not a bug in mcp-go. Both behaved as specified. The defect was knomit keying routing state on an identifier that does not identify what knomit needed identified. It is also NOT the same failure as a session whose MCP connection never came up at startup — here the connection was healthy and shared, which is the opposite problem.
