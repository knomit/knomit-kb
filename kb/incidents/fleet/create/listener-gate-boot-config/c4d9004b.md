# A fresh instance could not host a fleet even after the Fleet port was set and `knomit reload` run: the hub check and GET /fleet judged the port by the BOOT config, which a reload never updated (fixed in #545, merged 7ce30154)

WHAT HAPPENED (reproduced on the real binary at dev b4677384, fixed by PR #545, re-read at merge commit 7ce30154). A fresh `knomit serve` home with no `[tls].addr`: the user set the Fleet port in knomit.toml and ran `knomit reload` (the desktop Settings save runs the same reload). Two things then said no. `knomit reload` printed `tls: off (no_certificate)` and exited 1 (the red Settings line). And `POST /fleet/create` was refused 422 `listener_required` ("a fleet hosted here needs the mTLS listener: set [tls].addr in knomit.toml ..."), the very step just done. GET /fleet `host` was unchanged: listener_on false, no listener_reason.

ROOT CAUSE. The server judged the Fleet port by its BOOT config. `Manager.FleetStatus` (host.listener_on) and `refuseNoHubListener` (the create's hub check) read `m.deps.Cfg.TLS.Addr`, the config the process booted with. A reload updates the Listeners (their `tlsCfg` and TLSState, reason no_certificate) but never the Manager's config copy, so a Fleet port set after boot never counted. #537's create-starts-the-listener door (`StartTLSWhenInstalled`, which DOES read the reloaded `tlsCfg`) was unreachable because the create was refused before it.

THE FIX. `Listeners.TLSListening()` returns `(configured, listening, reason)`: the [tls].addr the listeners reflect NOW (empty when off), the address actually bound, and why a configured one is not listening. `Manager.SetTLSListener(f)` takes that three-value func (cmd/serve.go sets it once the listeners are bound). `Manager.tlsAddr()` returns f's configured address, and falls back to the boot config's `[tls].addr` only when no reporter was set (tests, a process without listeners). `FleetStatus.Host.Listener`/`ListenerOn` and `refuseNoHubListener` both read `tlsAddr()`. The listener counts as CONFIGURED, not listening: the create installs the certificate and `startTLSAfterInstall` starts it (the unchanged #537 path). The reverse case holds: a reload that switches the port off makes the next create `listener_required` again.

CONSEQUENCE. Any new check of "is a Fleet port set" must read `Manager.tlsAddr()` (the running listeners), never `deps.Cfg.TLS.Addr`; the boot config is only the fallback for a process with no listeners. The same shape (a copy of config taken at boot, a reload that moves only the live object) is what this incident was.

PINS. internal/repos/fleet_listener_live_test.go: TestFleetHub_ListenerConfiguredByAReloadCountsBeforeTheCertificate and TestFleetHub_ListenerSwitchedOffByAReloadIsOff (sabotage: `tlsAddr()` returning the boot config turns both red). A real reload's TLSListening reporting the configured address is pinned in internal/app/listeners_reload_test.go.

VERIFIED END TO END (real binary): fresh instance, Fleet port set by reload (exit 0), the wizard offered Host here, the create succeeded in the SAME process, the listener came up with no restart (log: "mTLS listener started: the certificate it needs is installed"), and a second fresh instance enrolled and joined over it.

NOT MEANT: the external address is a separate requirement (the server refuses `addresses_required` without one); this fact is only about the Fleet port.
