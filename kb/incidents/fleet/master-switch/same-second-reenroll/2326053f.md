# The PR #528 walk finding (old master's branch refused artifact-replace after a same-key re-enroll and a master switch) was a re-enroll in the SAME second as the revoked leaf: equal NotBefore, which no leaf-renewal judge admits, reaching main unjudged; #533 (renewalIssueTime, the own-commit judge) closed it, and cmd TestFleetWalk pins it

WHAT WAS SEEN (PR #528 browser walk, 2026-10-16): after a revoke and a same-key re-enroll of C on master A, and the master switch to C, A's (now a member) push was refused by C's judge: "artifact-replace: artifacts/fleet/certs/<C>.pem is replaced but replace_when leaf-renewal does not hold: its NotBefore ... is not later than the replaced leaf's".

CAUSE (verified in fleet PR8b, PR #537, re-read at the merge b4677384): before #533, `EnrollFleetMember` issued the re-enrolled leaf as of now; IssueLeaf's NotBefore is now - clockSkew at one-second precision, so a revoke + re-enroll within the same second as the first issuance produced a leaf with the SAME NotBefore. The hub's own commits then reached main unjudged, so that replace sat in history, and a later judge (the new hub judging the old master's branch) refused it. A regression test (cmd TestFleetWalk_OldMastersBranchIsAdmittedAfterARejoinAndASwitch: create, join, revoke, leave, re-enroll same key, rejoin, root moved, old master stands down, new master hosts, old master follows and pushes) asserts the replacement leaf on main has a strictly later NotBefore and the old master's branch is admitted and merged. It FAILS at the #528 merge (e417fd76) and at the #532 merge (a1b0ca5d) on equal NotBefore, and passes at #533's merge (6f241959) and after: `renewalIssueTime` (pki.IssueTimeAfter) makes the NotBefore strictly later, and judgeOwnRange refuses such a commit before main moves anyway. Nothing more needed fixing in PR8.

CONSEQUENCE. Any code that REPLACES a leaf (enroll's rejoin, the renewal duty) must issue with renewalIssueTime, never plain now.
