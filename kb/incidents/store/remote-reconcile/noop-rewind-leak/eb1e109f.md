# Incident: a rewind whose replay walk was empty kept the branch as it stood, and a rewind back to an ancestor skipped the walk altogether, so the caller's force-push sent the commits the origin had removed back to it (#539)

WHAT HAPPENED (found while building the experiment fix of #538; fixed in #539, merge 266f96f5, nits in #540, merge ba40165b). When the origin rewinds main (a force-push that removes a fact or a secret, G6 scrub), reconcileMainTo reports ModeRewound for ANY non-fast-forward, a move back to an ancestor included, and the agent branch goes through reconcileAgentRebase -> replayOntoUpstream. Two shapes kept the removed content and pushed it back:
1. EMPTY WALK. The agent branch has nothing of its own beyond the watermark (the agent wrote the secret, main and the watermark moved to it, then main was force-moved to a child of an earlier commit). unpushedCommits stops at the watermark at once, the walk is empty, local is not an ancestor of the upstream, and the old rule returned ModeNoop 'strictly ahead'. The branch kept kb/secret.md; the caller's force-push sent the scrubbed commit back to the origin that removed it. Same for a hub whose divergence is only merges.
2. REWIND TO AN ANCESTOR (reset HEAD~1 plus force-push). unpushedCommitsDropping returned empty as soon as the upstream was an ancestor of local, ignoring the watermark, so it never ran the walk and kept the removed commit even with an own write on top.

THE FIX (internal/store/remote_reconcile_rebase.go): `strictlyAhead` means the upstream is an ancestor of local AND the watermark is at or below the upstream; a watermark BEYOND the upstream means the origin moved back past what this branch consumed, so the branch is not ahead but behind a removal and the walk runs. An empty walk on shared history then REBUILDS the branch on the upstream (ModeRebase, nothing replayed). Unchanged outcomes: equal is a no-op, behind fast-forwards, strictly ahead is a no-op, and a DISJOINT upstream keeps the no-op (see the residuals gotcha). An own experiment merge is not lost by the rebuild because the side collection (#535) makes the walk non-empty. In a fleet it is strictly safer: a fallback member no longer pushes the old master's merges, which the new host refuses for good as not-pusher.

CONSEQUENCES for a reader: (a) a 'nothing to replay' answer from the rewind path is only safe when local is at most a strict linear extension of the upstream with the watermark not past it; (b) the watermark is part of the 'ahead' test; a repo with NO watermark was not covered by #539, and #542 (merge 637960bc) closes that case by seeding the missing watermark (kb/invariants/store/remote-reconcile/watermark-seed/0f9cc562.md), EXCEPT on a truly first sync, where there is no watermark and no remote-tracking ref to seed it from, so a reset to an ancestor there still pushes the removed commit (kb/gotchas/store/remote-reconcile/rewind-residual-leaks/cd3a2bbf.md); (c) any change to how merges or empty walks are handled must be tested with own work behind a second parent (sabotage of the side collection turns OwnExperimentMergeOnlySurvivesTheRebuild red).

MISREADING. 'A rewind can no longer push back removed content': false, see the residuals gotcha; shared-history walks with a watermark are covered.

#540 pinned the last unpinned branch of the predicate: TestReconcileAgentRebase_RewindToAnAncestorDoesNotKeepAScrubbedCommit/watermark_below_the_upstream_stays_as_it_is (a watermark strictly below an ancestor upstream stays a no-op; only this subtest goes red when 'below' never counts as ahead), and the Sync doc comment now says a rewind with no local-only commits is rebuilt, not fast-forwarded.
