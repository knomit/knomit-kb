# Reference edges were re-resolved at every commit a blob arrived at (COW hits), so outgoing reads returned the union: 2,053 duplicate groups and 507 refs pinned to several versions on knomit-kb; fixed by writing a blob's edges once (PR fix/graph-blob-edges)

BUG (dev up to 7db596b0): the upsert COW-hit path (index/search_crud.go, 'each new commit asserting the same content is its own ref-event') called writePostCommitDerivedFrom at every commit an already-indexed blob arrived at: a merge carrying it, another branch, an experiment commit, restore. It re-resolved the refs at that commit. The dedup guard keys on (src, tgt, source_commit, target_commit), so each arrival added edges. Reads match by version node (714f8566), so OutgoingAtCommit returned the UNION.

MEASURED on a backup of the live knomit-kb store, before the fix:
- 21,235 DERIVED_FROM edges;
- 2,053 exact-duplicate groups (same source blob, target path and target_commit);
- 1,732 refs pinned at more than one target_commit;
- 507 refs pinned to more than one target VERSION.
This confirms the earlier hypothesis (kb/gotchas/store/outgoing-at-commit-shared-blob, retracted in this same PR because the incident settles it) that a version would list several versions of one target, including another branch's.

AFTER the fix (GraphSchemaVersion 8 rebuild of both maintained branches, 30.7 s): 15,544 edges, and 0 / 0 / 0.

The user's model (2026-10-30): node identity = blob. A blob's refs become edges ONCE, at the commit that introduced it. If the blob never changes, its refs never change. A merge carrying a blob unchanged adds nothing; a merge resolving a conflict makes a new blob with new edges.

Visible consequence: Connections and explain no longer list duplicate rows, or a target at a later version the source never saw when it was written.
