# Concurrent cursor calls answered 500 'dequeue error: DequeuePaths delete: database is locked': ToolIndex.DequeuePaths read the queue then deleted inside a DEFERRED transaction on the shared session DB — FIXED by BEGIN IMMEDIATE on its own connection (branch fix/materialize-cursor-concurrency)

SEEN: a UI prototype paged five REST materializations in parallel (GET .../facts/{path}/materialize/pages, first call ?depth=4&max_nodes=200&limit=5, then ?cursor=<id> until has_more is false), each walk a DIFFERENT fact with its OWN cursor. Two cursor-only calls answered HTTP 500. With two in parallel plus client retries all 50 walks finished, which hid the bug.

REPRODUCED (Go tests against a real session DB and the real REST handler, no live server): at every concurrency tried (2, 5, 10, 20 parallel walks, and 2-20 callers on ONE cursor) cursor calls fail within milliseconds with problem detail "dequeue error: DequeuePaths delete: database is locked" (title "Materialize failed", status 500). The first call never fails: it only writes (CreateToolSession, EnqueuePaths).

CAUSE: ToolIndex.DequeuePaths (internal/engine/store/sessions/tool_index.go) ran SELECT ... ORDER BY sort_key LIMIT ? and then DELETE + UPDATE tool_sessions inside db.BeginTx(ctx, nil), a DEFERRED transaction. The session DB is opened by sessions.Open with _busy_timeout=5000 but WITHOUT _txlock=immediate (its comment says the stock driver needs neither). A deferred transaction that has read under a WAL snapshot and then tries to write after another connection committed cannot upgrade its lock: SQLite returns SQLITE_BUSY at once and the busy timeout never waits it out. The session DB is ONE file per store for every tool session, so two walks on DIFFERENT cursors collide — this is not a same-cursor race. NextPage wrapped the error as "dequeue error: %w"; the REST handler maps every non-expiry error to 500 (handlers_materialize.go, the default case after ErrCursorExpired).

BLAST RADIUS: every DequeuePaths caller, i.e. every cursor resume on that store: REST materialize pages, knomit_materialize, knomit_query (queryResume) and knomit_explain (explainResume). On MCP the same text came back as a tool error (isError result), not an HTTP 500.

FIX: DequeuePaths takes a dedicated *sql.Conn and runs BEGIN IMMEDIATE ... COMMIT (ROLLBACK under context.WithoutCancel on any failure), exactly the pattern createPipelineSession already used for the same reason. A concurrent dequeue now waits (bounded by the 5 s busy timeout) and then reads the queue as the winner left it, so no item is handed to two callers.

REGRESSION TESTS: TestDequeuePaths_ConcurrentWalksOnSeparateSessions and TestDequeuePaths_ConcurrentCallsOnOneSession (store level; every walk sees all items in sort_key order, every item dequeued exactly once) and TestMaterializePages_ConcurrentWalksAllComplete (REST handler, 2/5/10/20 walks, limit=1). Sabotage: BEGIN IMMEDIATE -> BEGIN DEFERRED turns all three red with the original error text.

WHAT THIS DOES NOT MEAN: it does not make a whole NextPage atomic. Two callers paging the SAME cursor at once each get distinct items, but NextPage re-enqueues nodes that did not fit under PageCap in a later statement, so concurrent same-cursor pages can come back out of order. A cursor is meant to be paged by one caller at a time.
