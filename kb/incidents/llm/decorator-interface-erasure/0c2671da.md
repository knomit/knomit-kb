# Wrapping an LLMAdapter in a decorator silently ERASES BatchAdapter — consumers detect batching by type assertion, which just starts returning false

internal/llm uses optional-interface extension: LLMAdapter is the base, BatchAdapter adds CompleteBatch/BatchEnabled, and consumers discover batch support with a type assertion. A decorator returning a concrete type therefore DROPS that capability — and the loss produces no error, no log, no compile failure. The assertion simply returns false and the caller quietly takes the non-batch path.

TracingAdapter committed exactly this bug and shipped with it: when KNOMIT_LLM_TRACE was set, a batch-capable Gemini adapter lost BatchAdapter for the whole process. It went unnoticed only because CompleteBatch had ZERO consumers repo-wide — the capability was erased but nothing was asking for it. Found by code review during P1.2 (2026-07-21), not by any test.

**Fix, and the pattern for any future decorator:** wrap conditionally — `if ba, ok := inner.(BatchAdapter); ok { return &xBatchAdapter{...} }` — and note this forces the constructor to return an INTERFACE, not a concrete type, since a concrete type cannot conditionally implement BatchAdapter. NewTracingAdapter now returns TracingCloser for this reason. Pinned by TestNewAdapter_PreservesBatchAdapter, which fails against the pre-fix TracingAdapter.

**Consequence:** before adding any decorator to internal/llm (metrics, caching, fallback, routing), check what optional interfaces the inner adapter may satisfy and preserve each one. The decorator stack is Tracing(Resilient(Provider)), so an erasure at ANY layer erases it for everything above.

**What this does NOT mean:** it is not an argument against optional interfaces. It is a warning that they are invisible to the compiler at the wrap point — the type checker cannot tell you a capability was dropped, so only an explicit assertion test can.
