# Renaming the bridge executable made hookIdentity's raw-command fallback byte-equal to the OLD canonical identity, so init silently skipped scaffolding the post-edit hook beside a stale pre-rename one — the canonical string must always start with the CURRENT binary name

## What happened (2026-09-18, PR #218, the knomit-bridge → kb rename)

`hookIdentity` in tools/bridge/claude/init_merge.go computes the identity settings.json hook entries are deduplicated on. For a command whose leading token passes `IsKnomitCommand` it returns a canonical string `<canonical-binary> claude hook <event>`; for any other command it falls back to the whitespace-normalised full command. The invariant (kb/invariants/integrations/claude-code/init-merge/833aaef8.md) rests on the fallback never equalling a canonical identity.

The rename changed `IsKnomitCommand` to accept only `kb` but the first pass left the canonical literal as `"knomit-bridge claude hook " + event`, reasoning that both sides of the comparison go through the same function so the literal was inert. It was not: a pre-rename `knomit-bridge claude hook post-edit` in an existing settings.json is now a FOREIGN command (no alias), falls through to the fallback, and the fallback IS the string `knomit-bridge claude hook post-edit` — character-for-character the canonical identity the template's `kb claude hook post-edit` produced. Init over a pre-rename config reported +session-start, +post-ask, +memory-guard, +pre-compact and silently skipped post-edit, leaving a hook pointing at a binary that no longer exists, no working one, and a success message.

Reading the code did not catch it; running init over a deliberately pre-rename config did. Reproduction: a scratch git repo with only a .claude/settings.json carrying `knomit-bridge claude hook post-edit`, then `kb claude init -repo <anything>` — pre-fix reports four hooks added and no post-edit, post-fix reports five.

## Fix

Canonical identity is `"kb claude hook " + event` — the canonical prefix must spell the SAME binary name `IsKnomitCommand` accepts, so a fallback string can equal it only if its leading token is that binary, in which case it is not a fallback. Regression cases in TestHookIdentity: bare `knomit-bridge claude hook post-edit` and the quoted-path spelling must not collide with the post-edit identity; TestIsKnomitCommand: `knomit-bridge` and `/usr/local/bin/knomit-bridge` are both false.

## Consequence for the next rename or alias

If the binary is ever renamed again, or an alias is accepted by `IsKnomitCommand`, the canonical literal in `hookIdentity` changes in the SAME commit, and the check is behavioural: run `kb claude init` over a settings.json that spells every previously accepted name and assert every event is scaffolded (a `+<event>` line each) rather than skipped. A unit table on `hookIdentity` alone would have passed with the bug present because both sides went through the same function.

Misreading to avoid: "the literal is internal, so it is inert" — it is compared against user-authored strings, so it is part of the contract.

This is distinct from the settings-scopes gotcha (Claude Code's own cross-scope dedup of identical handlers), from the .mcp.json args-only refresh, and from the naming invariant about the three things called "knomit": this one is about init's OWN hook identity function colliding with itself across a rename of the executable.

Related, not a defect: a pre-rename .mcp.json entry is left untouched with no companion and no warning, because it sits under the exact key init would use and the key tier says "already there". Accepted by the decision; a warning is a possible follow-up.
