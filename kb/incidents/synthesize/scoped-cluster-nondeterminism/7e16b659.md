# ScopedCluster fed Louvain a randomized node order, making community assignment nondeterministic CORPUS-WIDE — dedup, prune, distill and both bridge axes all drew a different partition each run

**The defect.** `ScopedCluster` built its path list by iterating a Go map. Go randomises map iteration, so the paths reached Louvain's node numbering in a different order every run, defeating the seeded PCG that was supposed to make clustering reproducible. The same corpus clustered differently run to run.

**Blast radius — wider than the feature that found it.** `cluster.go` (now internal/corpus/synthesize/graph/cluster.go, with the guarantee in graph/cluster_determinism_test.go) is on the SHARED clustering path feeding dedup, prune, distill and both bridge axes. This was found during motif work but was never a motif bug.

**How it surfaced.** A motif bridge candidate enumerated in four runs of five and vanished in the fifth. Cause was confirmed by INTERVENTION before any fix was written.

**The fix.** One line — `sort.Strings(paths)` before `SubgraphEdges` — plus a property test. A sorted-map container was considered and declined: same asymptotics with worse constants for a build-once-iterate-once map, a new dependency, and signature churn wherever the subgraph flows. **The guarantee lives in `cluster_determinism_test.go`, not in the data structure** — so anyone replacing the sort must keep that test passing, and anyone adding a new map-ordered input to a seeded algorithm should expect the same failure.

**Why it was not a behaviour change in the sense that matters.** Every session already drew a random partition, so nothing could depend on a particular one. The line pins the draw rather than changing which draw is correct.

**The named misreading.** "Seeded PRNG" does not mean "deterministic". A seeded algorithm is deterministic only if its INPUT ORDER is too, and map iteration is the standard way that fails silently — there is no error, only a different answer.
