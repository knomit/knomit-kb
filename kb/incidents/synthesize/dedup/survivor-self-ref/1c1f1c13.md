# A review dedup merge left the survivor citing ITSELF (#280): dedupMergeRefs unioned the loser's citation of the winner onto the winner, and the ref gate let it through because the loser CARRIED that ref

WHAT HAPPENED. On 2026-09-24 an automatic review dedup (dedupCluster, internal/synthesize/dedup.go) merged kb/incidents/web/library/paging-duplicate-page/5866b86c.md (loser) into kb/gotchas/web/testing/library-loadmore-ref-passive-mirror/a965b6f6.md (winner), revision 106d32b3. The loser cited the winner in canonical form (`kb://3ec012f5b4d2/kb/gotchas/.../a965b6f6.md`). dedupMergeRefs built the winner's write list as union(winner.Refs, loser.Refs) + loser path and never removed the winner's own path, so the survivor cited itself. It was hand-repaired in a965b6f6 revision c75239ca.

WHY NOTHING STOPPED IT. refs.Gate.CheckBatch rejects a self-ref only when it is NEWLY added. A self-ref the fact already CARRIED is grandfathered (kb/decisions/refs/self-reference-gate-grandfathers-carried). dedupCluster passes the operands' refs as `prior`, and this ref WAS carried, by the loser. So the gate's carried exemption, correct for legacy self-refs, is exactly what let a new one in. The gate's self-ref check is defence in depth; the guarantee has to come from each producer filtering its own output. The comment in internal/refs/refs.go claimed mergeFacts was the only producer and that it was gone. It now names both.

THE FIX (PR for #280). dedupMergeRefs takes the winner's path and localRepoID. It drops from the WRITE list every ref where `fact.ClassifyRef(r, localRepoID)` is RefLocalFact with a Path equal to the winner's classified path. That is the same comparison mcp.mergeFacts uses for its own self-refs (#132). Properties, each pinned by a test:
- both stored forms are caught: canonical kb://<own-id>/ and bare kb/;
- case is folded: ClassifyRef lowercases local fact paths, and the winner's on-disk path carries the ontology root's real case;
- a FOREIGN kb://<other-id>/ ref at the same relative path is KEPT;
- a legacy self-ref the WINNER itself already carried (pre-#132) is dropped by the same filter. That is intended: this path rewrites the winner anyway, so it repairs the row;
- the loser's own path is still appended, as the record of the merge;
- the `carried` set is NOT filtered and is still derived only from the operands (kb/gotchas/refs/gate/prior-aliasing). The gate judges only what is written.

REGRESSION ANCHOR: TestDedupCluster_SurvivorDoesNotCiteItself (internal/synthesize/dedup_self_ref_test.go) drives dedupCluster, the path that produced 106d32b3, with the loser citing the winner in both forms, and asserts that the persisted winner has no self-ref and still cites the loser. TestDedupMergeRefs_DropsWinnerSelfRef covers the unit cases. localRepoID MUST be non-empty in these tests: with an empty id ClassifyRef reads kb://<own-id>/ as FOREIGN, and a filter keyed on RefLocalFact then misses the exact form #280 was produced by. Passing "" at the call site reddens the canonical-form case, which was checked.

OUT OF SCOPE, by designer ruling on #280: cross-topic mechanical merges (an incident merged into a gotcha) and the winner-body-only rule are intended. The loser stays reachable through history via knomit_explain. No topic guard or body-containment check was added.

WHAT THIS DOES NOT MEAN: it does not make the gate reject carried self-refs. The legacy population is still unrepairable from read-only mounts, so that exemption stays. Any NEW write path that unions refs from another fact must filter its own path itself, the way mergeFacts and dedupMergeRefs now both do.
