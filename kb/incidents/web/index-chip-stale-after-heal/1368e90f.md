# A repo showed "indexing" for hours after its index was ready: the startup heal's completion published NO event, the app's repo list is a one-time snapshot, and the only index poll covered the active branch's banner — three gaps that each looked like someone else's job

Observed 2026-09-18 on 0.5.3 at f5f47854. The desktop UI showed `knomit-kb` as "indexing" for hours while `GET /api/v1/repos` and both branch roots reported `index_state: ready`. The server had restarted at 06:55.

THREE GAPS, none of which is a bug on its own, which is why it survived:

1. Every repo opens with `ri.markIndexing()` and heals in a background goroutine (`Manager.openOne`), and that flip published NOTHING. The SSE stream carried `task`, `status`, `sync` and `push` — and a heal makes no commit, so no `status` fired. The index state is the one piece of repo status that changes with no commit behind it.
2. The web app fetches its repo list ONCE at bootstrap into `useState` and re-fetches only on an explicit repo-manager change. That list feeds `RepoIndexChip` in three places. A chip captured as "indexing" during the startup heal stayed captured until a mutation or a reload.
3. The only index-state poll was the 2 s branch-status poll, which dispatched `SET_STATUS` for the active branch's BANNER and never touched the list. So the one mechanism that did notice the transition could not reach the component that was wrong.

FIXED in PR #219 (merged 594b551a) by publishing an `IndexEvent` from a chokepoint inside the mark* methods and adding a server-wide stream the UI patches its list from. The 2 s poll is gone; the banner follows the event.

REGRESSION ANCHOR: `TestRepoIndexEvents_StartupHealEmitsIndexingThenReady` (internal/web/handlers_repo_events_test.go). It drives a real create through the HTTP API — `Manager.Create → Add → openOne` — with the stream attached and asserts the sequence `index indexing` … `index ready`.

THE TEST'S OWN TRAP, recorded in its comment: it must run the BACKGROUND branch of openOne. Setting `DisableBackgroundSync: true` makes the sequence `[ready]` and fails the test, because that branch heals inline and never calls `markIndexing` — so a test written on the harness path could only ever observe `ready` and would pass against the unpublished bug. Verified by that mutation rather than by reading.

WHAT THIS DOES NOT MEAN. The index state itself was never wrong: `IndexStatus()`, the REST payload and both branch roots were correct throughout, and only the client's copy was stale — so a reader debugting a similar report should check whether the SERVER disagrees before looking at the heal at all. It is NOT the 2026-08 stuck-indexing incident, where the state itself was pinned because a heal exit path reached no mark; here every mark fired correctly and nobody was told. And it says nothing about the create job, which never depended on the stream: it mirrors IndexStatus() directly and was correct before and after.
