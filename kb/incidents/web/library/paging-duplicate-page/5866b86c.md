# Library could append the same page twice (rows 50-89 duplicated) or stop paging after a scope change: a stale loadMore closure ran between a commit and React's passive flush; fixed by mirroring loadMoreRef in useLayoutEffect (PR #273)

SYMPTOM. It first surfaced as a merge-gate test flake (knomit#270): `expected [0, 50, 50] to deeply equal [0, 50]` in Library.lens.test.tsx on the CI Node 22 leg. It is a PRODUCTION defect in web/src/Library.tsx, not only a test race. In a browser, an IntersectionObserver notification delivered between React's commit and its passive-effect task ran the previous loadMore. In the lens union and repo Recent lists that fetched the offset just loaded, and rows 50-89 were appended twice (duplicate React keys). After a lens scope change it held the old scope's exhausted flag, and the new list never paged. The old observer is still connected during that gap, because its disconnect is itself a passive cleanup. Reach is narrow, since the sentinel must cross its threshold inside the window, but real.

CAUSE. loadMoreRef was mirrored in a passive useEffect while the loading refs its guards read were mirrored during render. Details in the gotcha kb/gotchas/web/testing/library-loadmore-ref-passive-mirror.

FIX (PR #273). (1) `useLayoutEffect(() => { loadMoreRef.current = loadMore; })`: the ref is current by the end of the commit. This relies on paging updates rendering in a blocking lane; a startTransition around them would reopen the gap, and the code comment says so. (2) Found in review: the repo Recent branch never set `loadingRef.current = true` synchronously, unlike the lens branch, so two observer ticks before the setLoading re-render both passed the guard and appended the next page twice. It now does.

REGRESSION ANCHOR. Library.lens.test.tsx, describe 'Library — the sentinel sees the current list at the commit that shows it'. Three tests fire the sentinel from a MutationObserver at the commit, and they failed before fix (1): [0,50,50]; [0,0] (50 never requested); [0,50,50] for repo Recent. A fourth, 'repo Recent: two ticks before a re-render request the next page once', failed before fix (2) with 150 rows instead of 100. If any of them fails again, the window is back. Do not 'stabilise' them with waits.

NOT DONE, deliberately: a requested-offset guard (kb/decisions/web/library/requested-offset-guard-skipped-in-273). The repo Recent path also has no generation guard against a response landing after a filter change; that is tracked as its own issue.
