# A cross-site page could write facts through the plain listener (#287): a text/plain form or fetch to http://127.0.0.1:<port> is a CORS simple request, carries a legitimate loopback Host, and ran as anonymous@none because handlers decode JSON regardless of Content-Type

WHAT HAPPENED. Measured during the #281 RCA (reviewer input 5) and again at dev 131376e3: any web page could `fetch('http://127.0.0.1:19278/api/v1/repos/<r>/branches/<b>/facts', {method:'POST', mode:'no-cors', body: JSON-as-text/plain})`, or submit an HTML form to that URL, and get a 201 with a fact written as anonymous@none under the default `loopback_default`. No DNS rebinding was needed.

WHY NOTHING STOPPED IT.
- A form POST, or a fetch with text/plain or no Content-Type, is a CORS SIMPLE request. The browser sends it without a preflight, so corsMiddleware never gets to say no, and the page only loses the ability to READ the response. The side effect happens anyway.
- The Host is the real loopback address, so the #281 Host check (421 on a foreign DNS name) correctly admits it.
- AuthMiddleware minted anonymous@none, and the fact handlers json.Decode r.Body without looking at Content-Type.
- The 3b OAuth approval gate already refused this shape for its two routes (Origin, X-Knomit-Client, JSON type), but nothing guarded the rest of the plain listener.

THE FIX (PR for #287, commit f26476ae). AuthMiddleware's anonymous branch now also checks Origin (loopbackOriginOK) right after the Host check and before minting anonymous. GET, HEAD and OPTIONS are exempt; every other method is judged. Outcomes:
- no Origin passes (non-browser clients);
- http(s)://<r.Host> passes (case-insensitive, default port ignored);
- an Origin in Server.CORSOrigins passes (the desktop's Wails origins, byte-exact);
- anything else is 403 "Cross-origin request refused", `null` included.
Server.authEdge threads CORSOrigins into BOTH AuthMiddleware invocations (outer router and API router). There are no client changes and no Content-Type rule; the shared JSON decoder is a separate follow-up.

REGRESSION ANCHOR: TestIssue287_CrossSitePlainPostIsRefused (internal/web/auth_origin_guard_test.go) replays the measured request over a real 127.0.0.1 listener through Server.Handler. It asserts 403 and zero writes, with a same-origin control that still writes. Siblings pin the rest:
- TestOriginGuard_RefusedOrigins covers null, the vite origin against the real port, another port, a path, userinfo, malformed, a prefix, and a repeated header;
- TestOriginGuard_AdmittedOrigins covers no Origin, own origin, the vite proxy, an https proxy for a loopback_hosts name, and default ports both ways;
- TestOriginGuard_EveryMutatingMethodAndRoute covers PUT/PATCH/DELETE and /repos:probe-origin;
- TestOriginGuard_ReboundStill421 checks the Host check still runs first;
- TestOriginGuard_DesktopWailsOriginWrites and TestApp_OriginGuardWiring check the allowlist reaches both edges and both boot paths;
- TestOriginGuard_DesktopPreflight checks OPTIONS is untouched.
Seven sabotage rows, listed in the test file header, were each applied and each failed its named test.

RESIDUALS.
- Any local process can still send any Origin, or none, exactly as before.
- Browsers old enough to omit Origin on a cross-site form POST (Firefox before 70, 2019) are not stopped.
- Same-origin text/plain still decodes as JSON.

WHAT THIS DOES NOT MEAN: it is not a CSRF token and not authentication. It establishes only that a page on another origin is not the one asking. It also does not replace the 3b gate's stricter arrival-port Origin rule, which still applies on top for the OAuth decide routes.
