# A '--source' documented as one-off silently repointed the repo, and pruning turned that into data loss — two safe changes composing into an unsafe one

knomit-okf's `--source` flag was documented as "override the KB URL for this run", but `fetchSource` fetched THROUGH the stored `knomit-source` remote and kept its URL "in step" with whatever it was handed — deleting and recreating the remote whenever they differed. So a one-off override became permanent, and every later bare `sync` followed the wrong knowledge base.

Separately, fetch had gained `Prune: true`, which is correct on its own: `refs/knomit-okf/source/*` mirrors upstream branches, and stale refs would make `branches` report a deleted branch as live.

The two composed into DATA LOSS. One `sync --source <other-kb>` would repoint the remote AND prune away the original knowledge base's source refs, because the fetch prunes whatever the new remote does not advertise. Neither change is wrong alone; together they destroy state.

Fix: `fetchSource` builds an ANONYMOUS remote per call and never reads or writes stored config. `createSourceRemote` records the remote, and only `clone` calls it — clone is the one command whose job includes deciding where a repository's knowledge comes from. A genuinely relocated KB is repointed deliberately with `git remote set-url`. Regression: TestFetchSource_DoesNotRewriteTheStoredRemote.

The transferable lesson, which is bigger than this bug: when a change makes an operation MORE destructive (pruning, force-writing, cascading deletes), re-examine every existing code path that chooses that operation's inputs. The prune was reviewed against "is pruning correct?" and passed. Nobody asked "what now happens when the URL is wrong?" — and a flag documented as harmless was silently supplying wrong URLs.

What this does NOT mean: it is not an argument against pruning, which stays. It is an argument for auditing input-selection paths whenever blast radius grows.
