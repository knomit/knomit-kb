# A fixed per-mount candidate cap made 903 core facts unreachable at every offset — a retrieval DEPTH for relevance was reused as a browse WINDOW for recency

**Symptom.** In the `all` lens the dashboard reported 2053 facts and the chronological list reported 1150, on the same screen. Scrolling the list stopped dead: offset 1145 returned 5 rows, offset 1150 returned 0. 2053 − 1150 = 903 = core's 1403 facts minus 500.

**Cause.** `maxLensFactCandidates = 500` was applied as the per-mount `SearchOptions.Limit` with `Offset: 0`, for BOTH the relevance and the recency paths of `/lenses/{l}/facts`. For a text-less query `RecentFacts` returns committed_at-DESC, so each mount contributed only its 500 most recent rows and paging walked inside that materialised set. A mount's 501st-newest fact was therefore unreachable at every offset — on the surface whose entire purpose is browsing the corpus. Everything before 2026-07-19 in core was invisible to the chrono list, while remaining reachable via the ontology tree (`/topics`, uncapped) and via search.

**Why the cap was wrong here and right elsewhere.** Per-mount relevance ranks are NOT comparable across mounts (RFC §7.1) — which is why the union fuses by reciprocal rank rather than merging on a shared key. With no next-globally-ranked row to walk toward, bounding retrieval costs only the tail of each ranking: a legitimate DEPTH. Commit timestamps ARE comparable, so recency has a global order and the same bound becomes a WINDOW that hides rows. One constant serving both readings let a sound search decision masquerade as a browse policy.

**Fix.** Split the constant: `maxLensSearchCandidates` (500, retrieval depth, unchanged behaviour) and `maxLensRecencyDepth` (backstop only, so one absurd offset cannot ask every mount to materialise its corpus). The recency path now requests `offset+limit` per mount, which is provably sufficient — a row in the global page [offset, offset+limit) is always within its own mount's first offset+limit rows — so every row is reachable while per-request work stays bounded. Counts were fixed in the same change; see the count-vs-transfer invariant.

**Not caught because it was documented.** `kb/gotchas/lens/browsing-ui-accepted-gaps` gap 4 recorded it as "per-mount 500-row snapshot bounds `total`" — nine words at the tail of a bullet titled "Flat-envelope asymmetry", concluding "All deliberate; document in API docs rather than 'fixing'". The mechanism was written down; the consequence (facts unviewable on a browse surface) was not, and nobody asking "can I see all my facts?" would open that bullet. The sharp version existed in a comment in `handlers_lenses_stats.go` explaining why stats avoids that code path — "a systematic under-count on any repo with >500 facts" — in a different file, about a different subsystem.

**Method lesson.** "It is documented as deliberate" is not a reason to stop reading. Ask what the documented mechanism DOES to a user, and whether the surface it was designed for is the surface it is now serving.
