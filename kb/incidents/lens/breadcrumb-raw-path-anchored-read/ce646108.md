# History-mode breadcrumb titles must fetch via the lens endpoint — any surface holding a canonical crumb path may NOT hand it to repo-scoped api.fact

**Incident (2026-07-19, fixed c38402b):** entering history mode in a lens context logged server ERRs (`readFileAtCommit: commit: object not found`). `FilterBar` swaps to `TrailBreadcrumb` when `!isLive`, and its title prefetch called commit-anchored `api.fact(state.repo, state.branch, crumb.factPath, commit)` — write repo + RAW `kb://<id12>/` path + a mount commit sha. Impact was cosmetic (crumb fell back to basename; the fact body itself anchored correctly), plus log noise.

**Root pattern (second occurrence):** the lens temporal sweep (Task 17) worked from an enumerated file list (TimelineNav, useTimeTravel, EdgesRail, VersionWalker) — TrailBreadcrumb was on neither the design handoff's file list nor the plan's, so it was never converted. Enumerated-surface sweeps miss the surface nobody listed; greping for `api.fact(` / `state.repo` consumers is the reliable inventory.

**Rule now:** any component that receives a fact path originating from lens browsing (trail crumbs, nav stack entries) holds a CANONICAL path and must fetch through the lens endpoint (`getLensFact`) when in a lens context — never repo-scoped `api.fact`. TrailBreadcrumb takes a `lensName?` prop for this; titles are fetched live (per-mount commit anchoring would need an id12→mount mapping the client doesn't keep; basename fallback covers failure).

**Regression anchor:** the lens-context tests in web/src/TrailBreadcrumb.test.tsx (getLensFact called with RAW path, api.fact never).
