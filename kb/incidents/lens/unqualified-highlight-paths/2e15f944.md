# Lens dashboard highlights 404'd because /lenses/{lens}/stats was the ONE lens read emitting mount-relative paths — an aggregate payload hid the only path-bearing rows in it

**Symptom.** Clicking any highlight on a lens summary dashboard returned `404 no fact at path "kb/technology/…/7cc50183.md"` from `/lenses/{lens}/facts/*`. Repo context was fine; only lenses broke.

**Measured, before any change**, for the same fact:
- `/lenses/all/facts` → `kb://d88770a51516/kb/technology/…/7cc50183.md`
- `/lenses/all/search` → `kb://d88770a51516/kb/technology/…/7cc50183.md`
- `/lenses/all/stats` → `kb/technology/…/7cc50183.md`  ← bare

Not one highlight in the payload was qualified.

**Cause.** `store.Highlight.Path` is mount-RELATIVE (it comes from `live.path` inside one mount's query). A bare path on the lens wire resolves against the WRITE repo — so every highlight owned by a READ mount asked the wrong repo. `/facts`, `/search` and `/topics` all pass their rows through `lensWirePath`; the stats handler never did. The fix is that call at the dedup merge, where the winning mount index is known: `h.Path = lensWirePath(b, targets[i].RT, h.Path)`.

**Why this one was missed — the transferable part.** Every other lens union read is a LIST OF FACTS, so "qualify each row" is the obvious shape of the handler. `/stats` is an AGGREGATE payload — totals, histograms, an axis — and `highlights` is the only path-bearing field buried in it. The rule "every lens read qualifies its paths" was applied per-handler-shape rather than per-field, so the one path-bearing field inside a non-list payload slipped through.

**Where else to look for the same shape**: any lens response that is not a list of facts but carries a path somewhere — today that is `/stats` (highlights) and, if it ever grows one, anything embedding a fact path in a summary, an activity roll-up or a link.

**Ordering constraint that the fix must respect**: qualify AFTER `federate.WriteFirstWinners`, never before. Dedup exists because one fact path can live on two mounts (a re-rooted fork shares server-generated fact UUIDs), and it keys on the RELATIVE path; qualifying first gives the two copies different keys, so both survive and the write mount stops winning. There is a regression test pinning that order.

**A test was asserting the bug.** `TestLensStats_HighlightsAreGlobalTopNotFirstMount` checked `Highlights[0].Path == "kb/b.md"` where `beta` is a READ mount — so it encoded the unqualified path as expected output while believing it tested ordering. It now asserts by title. A test that names one thing and pins another is how a whole-payload defect survives a suite that looks thorough.
