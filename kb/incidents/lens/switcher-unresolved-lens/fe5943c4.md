# Entering a lens context MUST go through the single-owner resolution effect — per-entry-point resolveLens calls caused a 404 on first fact click

**Incident (2026-07-19, fixed a9ffbe4):** switching to a lens via the TopBar switcher left `state.lens` null forever: only the manager Browse button and bootstrap restore called `resolveLens`; the switcher just dispatched `SET_CONTEXT`. The Library still rendered (its lens reads need only `state.context.name`), which masked the failure until a fact was opened — RightPanel's `lensCtx && lensName` gate (lensName = `state.lens?.name`) fell through to the repo-scoped `api.fact` with the raw `kb://<id12>/` path → 404. TopBar mounts chip and the sources dropdown were silently empty too.

**Invariant now:** lens-doc resolution has ONE owner — the App effect keyed on `lensResolutionPending(state)` (`context.kind==='lens' && lens?.name !== context.name`). Entry surfaces (switcher, manager Browse, bootstrap restore, and any future one) only dispatch `SET_CONTEXT`; none may call `resolveLens` directly. The one exception is `refreshContextAfterChange`, which re-resolves the SAME lens name after a mount edit — a case the predicate deliberately does not cover.

**Why it was missed:** each task-scoped review verified its own surface (Task 13: "selection dispatches SET_CONTEXT"; Task 12: the resolvers that existed then). No task owned the cross-cutting property "every context entry resolves", and there is no App mount-test harness to catch it end-to-end.

**How to apply:** when adding any new way to enter a lens context, dispatch `SET_CONTEXT` and nothing else — resolution follows automatically; do NOT add a resolveLens call (a duplicate is mostly harmless but re-fragments ownership). Regression anchor: the `lensResolutionPending` test in web/src/state.test.ts.
