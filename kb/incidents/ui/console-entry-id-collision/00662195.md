# Date.now() + Math.random() does NOT produce unique ids — float precision caps it at ~4096 values per millisecond, and React keyed on it dropped rows

web/src console entries were keyed on `id: Date.now() + Math.random()`. That looks unique and is not. Date.now() is ~1.7e12, where a float64's ulp is 2^-12, so the fractional part can only take ~4096 distinct values in a given millisecond. Measured: 197 unique ids across 200 entries logged in one tick.

The entries are React list keys, so colliding ids made rows DISAPPEAR from the rendered console — during exactly the event the console exists to capture, an SSE burst. Silent: no warning, no error, just missing log lines when you most need them. Fixed in P1.7 (2026-07-21) with a monotonic counter.

**Consequence — the general rule:** never build an id by ADDING a random fraction to a large timestamp. The magnitude of the timestamp destroys the precision of the random part. If you want time-ordered unique ids, use a monotonic counter (optionally paired with a timestamp in a SEPARATE field, which is what this code does now — `time` is still recorded, it is just no longer load-bearing for identity).

**Testing note that makes the regression test real:** asserting 'N ids are unique' is not enough on its own — it passes trivially if the burst happens to straddle milliseconds. The test also asserts the burst genuinely SHARES timestamps, so it reproduces the condition the old scheme could not survive.

**What this does NOT mean:** Math.random() is not the problem and neither is Date.now(). The bug is the ADDITION — combining them into one float. Concatenating them as a string, or keeping them as separate fields, has no such collision.
