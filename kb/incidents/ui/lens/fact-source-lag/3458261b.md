# In a lens, factSource still names the PREVIOUS fact's mount for one getLensFact round trip after the open fact changes. useFactEdges paired it with the new path and 404'd /incoming and /outgoing on a cross-mount switch. Readers of state.factPath must gate on openFactSourceResolved, and the reducer must NOT clear the source on a switch

SYMPTOM (PR #740): in lens `all` (alpha write, beta read), opening a beta fact AFTER an alpha fact made two console 404s: GET /repos/alpha/branches/<b>/facts/<beta relative path>/incoming and /outgoing. Then the edges reloaded on beta's route. beta -> alpha did the reverse (beta's route for an alpha path). Opening a beta fact first, with no other fact open, was fine. So was a hop within one mount.

CAUSE: RightPanel re-dispatches SET_FACT_SOURCE only when getLensFact answers for the NEW factPath. The reducer clears factSource only when the fact CLOSES (factPath -> null), not when it changes. useFactEdges runs synchronously on the new state.factPath, and its lens guard was `!state.factSource`. So for one round trip, factHistoryAnchor(state) paired the previous fact's mount with the new fact's relative path.

FIX: openFactSourceResolved(state) in web/src/state.ts is true when factSource owns state.factPath. For kb://<id12>/... that means source.id === id12. For a bare path it means source.id === state.lensWriteId, the write member's root-commit id. SET_LENS records that id, which resolveLens matches by UID from the repo listing. The match is by identity, so a read mount that shares the write repo's NAME is not mistaken for it. The name stands in only when the listing gave no id (an older server). Outside a lens it is always true (decision 10a3bcc0). useFactEdges gates on it.

CONSEQUENCE: any NEW reader that pairs state.factPath (the new path) with state.factSource / openFactSource / factHistoryAnchor(state) must gate on openFactSourceResolved too. A bare null check is not enough.

WHAT THIS DOES NOT MEAN: it does NOT mean the reducer should drop factSource when factPath changes. That was tried and broke things. RightPanel keeps rendering the PREVIOUS `fact` until the new one loads, and VersionWalker pairs factHistoryAnchor(state, fact.path) (the previous path) with the previous source, which is coherent. Clearing the source sent that render to openFactSource's write fallback {lens.write, ''}, and /commits returned 400 on an empty branch. The test 'factSource survives a switch to another mount until SET_FACT_SOURCE replaces it' pins this. Readers keyed on the loaded fact (VersionWalker /commits, MaterializeView) were already correct and need no gate.

HISTORY AND DIFF (review lows, same PR): the cross-mount switch CAN happen while asOf is history or diff. While a timeline is open, the mounts picker still works. Unticking a mount refetches the lens union list, and its openFirstRow re-selects the first row with AMEND_NAV, which keeps asOf. Reproduced in a browser: alpha fact in history, untick alpha. RightPanel's anchored branch read repos/alpha/.../commits/<c>/facts/<beta path> (404 shown as the error), and TimelineNav anchored on alpha. Now RightPanel's anchored branch runs only once openFactSourceResolved is true. Before that, it calls getLensFact only to dispatch SET_FACT_SOURCE, without showing the live body, and the effect re-runs on the resolution. In diff mode RightPanel resolves the source the same way. TimelineNav (LeftPanel) and FactDiffView wait on the gate.

RESIDUAL (fixed by PR #747, see the next paragraph): the asOf commit kept by AMEND_NAV is the PREVIOUS mount's commit. After the fix, every read goes to the right mount, but a commit from mount A does not exist in mount B. So the anchored read of the beta fact at alpha's commit fails: GET repos/beta/.../commits/<alpha sha>/facts/... returns 500 "readFileAtCommit: commit: object not found" (the server maps an unknown commit to 500, not 404), and the edges return 404. Whether a cross-mount re-select should drop to live was an open UX ruling, not something this fix decided.

RULED AND FIXED (user 2026-11-03, PR #747): it does NOT drop to live. The server answers that read, the edges and the commit detail with 404 `code: commit_not_in_repo`, never 500. RightPanel (and FactDiffView) shows the NoVersionAtCommit state and keeps asOf, so history stays on and the reader scrubs from the new fact's timeline. See kb/decisions/web/rest/unknown-commit-404/41472083.md. Re-read at the #747 merge 452d41af: the gates above are unchanged there (RightPanel `anchorCommit && !sourceResolved`, useFactEdges `lensCtx && !sourceResolved`, state.ts openFactSourceResolved at the same blob).
