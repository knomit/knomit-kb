# In-body ref hops MUST pin to the DERIVED_FROM edge's target_commit, never the referrer's fact.commit_hash + fallback=before (404s across PR merges)

Clicking a fact's in-body reference (FactBody onRefClick -> RightPanel -> hopEdge) MUST anchor the hop on that ref's OUTGOING DERIVED_FROM edge `target_commit` — the version of the target the referrer reasoned over. That value is served in the `commit` field of GET .../facts/{path}/outgoing (api.explain -> RefGroup.versions[0].commit) and is the SAME value EdgesRail's "OUT" rows already hop to (onHop(group.path, versions[0].commit)). It must NOT be the referrer's own `fact.commit_hash` + `?fallback=before`.

WHY THE OLD APPROACH 404s: `fallback=before` from the referrer's CURRENT commit resolves the target along THAT commit's FIRST-PARENT trunk (resolveActiveCommitForPath — first-parent, never wall-clock). When the referrer's displayed version sits above a PR-merge commit and the target's referenced version lives on the merge's SECOND-parent (agent-branch) line AND was retracted before the referrer's version, first-parent walk-back from the tip never reaches it, so the read returns 404 "no fact at path ... at commit". Observed under the foobar lens: core @ agent/mindev.local-8ef0cd32, referrer kb/technology/security/ai-agents/synthesis/agent-access-is-blast-radius.md -> target kb/technology/security/ai-agents/6cf51b30.md. Edge target_commit f28d736b sits on the merge's 2nd parent; the branch tip 3c50ca08 is on the merged main line, so /commits/3c50ca08/facts/6cf51b30.md?fallback=before -> 404, while /commits/f28d736b/facts/6cf51b30.md?fallback=before -> 200.

THE FIX: RightPanel fetches the open fact's outgoing edges into a path->target_commit map and pins each in-body ref hop to it, falling back to fact.commit_hash only when a ref has no matching edge. That edges fetch MUST wait for the lens mount (state.factSource) to resolve — until then openFactSource returns the lens WRITE repo (empty branch) and the read hits the wrong mount, leaving the map empty (the reason the first cut still 404'd). Enforced by RightPanel.refhop.test.tsx.

CONSEQUENCE FOR ANY REF-FOLLOWING SURFACE: anchor on the edge's target_commit, NEVER referrer-HEAD + fallback=before. Audited siblings: the breadcrumb reads each crumb at its own asOf (the hop's pinned commit) — correct; EdgesRail IN/OUT rows use the edge commit — correct; MCP explain reads children AtCommit = edge target_commit (OutgoingAtCommit) — correct; timeline "files affected" uses the viewed commit by construction — correct.

WHAT THIS DOES NOT MEAN: the REST `?fallback=before` is NOT broken. It correctly resolves "path as of commit C along first-parent" and correctly 404s when the path was never on C's trunk (verified: anchored at the retract commit d175e8e0 it returns the pre-retraction version; at the tip it returns 404). Do NOT "fix" fallback to cross merge boundaries — that would violate the first-parent resolver invariants and become non-deterministic. The defect was the client asking the wrong question, not the server's answer.

DURABILITY: the edge target_commit is reproduced by a from-scratch clone+reindex, NOT an incremental-indexing artifact. rebuildGraph Phase B (internal/store/search_index.go) resolves each ref-event at its ORIGINAL source commit via resolveTargetCommit — a historical commit's first-parent ancestry is immutable — so f28d736b is recomputed deterministically. Verified end-to-end via store.CloneFrom + IndexManager().Rebuild against the public remote github.com/knomit/cyberai-kb. This holds because PR #3 was a true 2-parent merge (agent-line commits stay reachable from main HEAD); a SQUASH-merge workflow would break it (and would also GC the target blob, making navigation moot).
