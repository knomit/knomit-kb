# "no fact at path X at commit <merge>" in a LIVE view = the tab's cached headCommit went stale at the merge commit — NOT history rewrite, NOT index corruption, and NOT (in this incident) a user time-travel pin

Incident 2026-08-29, repo knomit-kb, branch agent/h1v302-8215ac8f: browsing to kb/meta/methodology/review/agreement-blind-spot/185e1fa6.md in a LIVE (non-history-mode) view showed `no fact at path ... on branch ... at commit fe30076a...`. The user was NOT time-travelling — an initial diagnosis of "sticky asOf pin" was WRONG and was corrected by the user's direct testimony.

ACTUAL MECHANISM: in live repo context the UI anchors every edges fetch at the CLIENT-CACHED head — edgeAnchorCommit(s) returns state.headCommit when live outside a lens — issuing commit-anchored subresource requests /commits/{headCommit}/facts/{path}/incoming|outgoing. state.headCommit is refreshed only by (a) the status bootstrap at page load, (b) SSE `status` events, and (c) api.status refresh on task completion. The SSE feed is lossy: commitObserver.Notify (internal/repos/observer.go) debounces 1s and, when the timer fires while the previous callback (Acquire → IndexManager().SyncLocked → hub.broadcastStatus) is STILL RUNNING, the CompareAndSwap fails and the notification is silently DISCARDED — pending was already cleared, nothing re-arms. After the local_wins merge fe30076a (17:52), the observer's SyncLocked run was long (indexing + embedding the merged facts on a batch-1-capped machine), so head broadcasts for the follow-on learn commits were droppable, and the tab's headCommit stuck at fe30076a. Every fact created after the merge (da17d16 18:53 onward) then failed its edges fetch with the exact quoted 404 from handlers_fact_sub.go — while the fact body itself (un-anchored live read) loaded fine.

What was RULED OUT by verification, so the next debugger does not re-suspect it: (1) mergeIntoBranchLocked writes ParentHashes{dstHash, srcHash} — agent branch stays first parent; raw commit objects confirm; no rewrite across the GitHub PR round-trip. (2) commit_parents, commit_log, branch_commits, branch_facts all cross-check against raw git objects. (3) Repo-scoped REST batch-tested: 30–40 facts, reads + both edge directions, HEAD- and merge-anchored — zero failures; the server answers correctly for whatever anchor it is given. (4) as_of.commit in a fact response is the READ ANCHOR (branch head at read time), not the fact's version commit — do not read it as an off-by-one.

CONSEQUENCE: when a user reports "no fact at path ... at commit C" on facts that exist at HEAD, and C is a merge/older commit, first establish WHERE the anchor came from — UI history pin (user-visible READ_ONLY badge) vs stale client headCommit (user sees LIVE). A page reload fixing it confirms client staleness. Repairs live in two places: the observer must not drop notifications (re-arm or re-Notify after the running callback finishes), and a live-mode 404-at-cached-head should trigger a head refresh + retry instead of rendering a raw error.
