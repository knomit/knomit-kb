# "no fact at path X at commit <merge>" while browsing = a persisted time-travel pin at the local_wins merge commit, NOT history rewrite, index corruption, or merge-code failure

Incident 2026-08-29, repo knomit-kb, branch agent/h1v302-8215ac8f: browsing to kb/meta/methodology/review/agreement-blind-spot/185e1fa6.md showed `no fact at path ... at commit fe30076a...`. Root cause: the UI held a time-travel pin (state.asOf, history mode) at fe30076a — the `merge: main into agent/... (local_wins)` commit of 17:52 — and the fact was created at da17d16 (18:53), AFTER the pin. The commit-anchored read 404 is temporally CORRECT. The pin is sticky by design: APPLY_NAV preserves asOf across every subject hop (asOfPersistence tests), so one hop onto an edge whose target_commit is the merge commit pins ALL subsequent browsing there. Merge commits are pin magnets: every fact whose current version arrived via the merge resolves its active commit to the merge commit, so edges into that cohort all carry it.

What was RULED OUT by verification, so the next debugger does not re-suspect it: (1) mergeIntoBranchLocked writes ParentHashes{dstHash, srcHash} — agent branch stays first parent; the raw commit objects in the objects table confirm it; no history rewrite happened across the GitHub PR round-trip (agent→main PR #11, other agent's PR #10 merged back via local_wins). (2) commit_parents, commit_log, branch_commits, and branch_facts were all cross-checked against the raw git objects and agree. (3) The repo-scoped REST API was batch-tested: 30–40 facts, reads and both edge directions, HEAD-anchored and merge-anchored — zero failures. (4) as_of.commit in a fact response is the READ ANCHOR (branch head at read time), not the fact's own version commit — comparing it against commit_log's row for the fact and concluding "off by one" is a misreading; the fact's version date is as_of.date.

CONSEQUENCE: when a user reports commit-anchored 404s on facts that exist at HEAD, first ask whether the anchor commit is a merge commit and whether the UI shows the read-only/anchored state (READ_ONLY_TITLE "Read-only — anchor is not live"); the recovery is returning to live, not touching the store.
