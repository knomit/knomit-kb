# syncStage.Enter ran ensureLocalUpstream on the driver, and EnsureLocalUpstream takes lockBranch(upstream) before checking the ref, so whenever the Index job's Rebuild won that lock the whole mount walk waited for the index: the create sat on step "register" without narrating "indexing", and every event the driver handles (CancelIndex, Rebuild, ...) waited with it

MECHANISM. The mount walk enters Index (indexStage.Enter launches the job goroutine; index.Index.Rebuild takes LockBranch(branch) as its FIRST statement and holds it for the whole rebuild), then Serve, then Sync. Until the fix, syncStage.Enter called r.ensureLocalUpstream(ctx, svc) inline, on the lifecycle machine's single driver goroutine, before starting the loop goroutine. remotesync.Index.EnsureLocalUpstream takes LockBranch(upstream) BEFORE it checks whether refs/heads/<upstream> already exists, so even its usual no-op case contends for the lock. For a subscription the read branch IS the upstream, so the heal's Rebuild holds exactly that lock. Which goroutine got the lock first was scheduling: driver first -> a microsecond no-op; index first -> the driver waited for the entire Rebuild. This violated the lifecycle decision that the driver never waits for background work (kb/decisions/repos/lifecycle/state-machine).

CONSEQUENCES when the index won: (1) Mount did not reply Ready until the index finished, so watchIndex started after the index had already left "indexing" and the create job went register (85%) -> done with no "index" step — the PR #230 symptom shape. (2) The driver handled no external event meanwhile: a CancelIndex sent in that window returned only after the index finished (577 ms of a 580 ms index in a forced repro; 0.36 ms with the fix). With real embeddings on a large repo that is minutes. What was NOT affected: cancelling the create. Machine.Send(Unmount) calls rootCancel first, the index job returns at its next batch and releases the lock (kb/invariants/repos/lifecycle/exit-cancels-all-then-drains).

HOW IT SHOWED. TestCancelCreate_DuringIndexLandsWithoutWaitingForTheIndex failed with "the create never reported an in-flight index while still running" — only under -race and only with GOMAXPROCS > 1 (stress at dev 0c24a7ab: 14 failures in 90 -race runs; 0 in 75 non-race runs; 0 at -cpu 1, where the new index goroutine cannot run until the driver yields). It was first noticed on the E7a merge (PR #584) and suspected to be merge-induced; dev failed as often.

ORIGIN. Introduced by #411 (cd980a94), which moved the d1367592 bootstrap from repoBuilder.activate — which ran before any index job existed — into syncStage.Enter, which runs after Index has launched its job.

FIX (branch fix/sync-enter-parks-on-index-lock). The repair runs on the Sync life's goroutine, immediately before the loop's first round (inline only under Options.Synchronous, where the driver runs that round anyway). Its ordering against the first network round — what TestOpen_BootstrapsAMissingLocalUpstreamFromOrigin pins — is unchanged. It is not delayed in the case it exists for: when the local upstream is actually MISSING, planIndex drops an unresolvable upstream and a Rebuild of a missing read branch fails at HeadCommit, so the index never holds that lock for long. EnsureLocalUpstream was deliberately NOT given a lock-free pre-check: off the driver, the only waiter left is the reconcile goroutine, whose first round takes the same lock right after anyway, so a pre-check would change nothing observable.

REGRESSION. TestCreate_SyncEnterDoesNotParkBehindTheIndexRebuild forces the losing interleaving deterministically: an embedder that only a cancel releases holds Rebuild inside its embeddings phase (so lockBranch is held), and the Options.Hook on (StageSync, "enter") lets Sync.Enter go only then. It requires step "index"/IndexState "indexing" while Running and that Send(CancelIndex) returns while the index still holds the lock.

MISREADING: this was not a timing-flaky test. The assertion (a running create reports its in-flight index) is the done-means-indexed contract; every failing run was the product actually parking.
