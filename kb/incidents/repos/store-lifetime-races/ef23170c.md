# Four store-lifetime races (snapshot-then-release, Archive under readers, Rescan vs Create double-open, undrained observer) fixed by the Acquire refcount — regression-anchored in instance_lifetime_test.go

The 2026-07-20 code review found four independent races that shared one root cause — store lifetime was guarded by lock scope instead of a usage refcount:

1. mcp storeIndices copied the five index interfaces out of WithRead and used them after the RLock was released; SwapStore/Archive could close the SQLite handle mid-call. The lens federation fan-out multiplied this per mount, and upstream had added recoverFanout to absorb the nil-svc panic symptom — which caught the nil window but NOT the closed-store case (a closed service is non-nil and passes svc==nil guards).
2. Manager.Archive deleted the instance from the map then closed the store; a handler that had resolved ri from middleware before the delete ran WithRead on a closed service (no closed tombstone existed).
3. Manager.Rescan decided 'new repo' from m.Get(name) alone and never consulted the creating reservation set, so during a Create/Restore clone window (the .db exists on disk long before m.Add) it double-opened the same database and the create's Add orphaned the first instance's SQLite handle and goroutines.
4. The commit observer's debounced SyncLocked callback ran on no WaitGroup and Observer.Stop does not wait for a running callback, so a commit within the ~1s debounce window raced svc.Close().

All four were fixed by one mechanism (the Acquire/release refcounted storeHandle — see the store-lifetime invariant) rather than four point patches. Regression tests: internal/repos/instance_lifetime_test.go (close waits for in-flight Acquire; concurrent WithRead vs close never observes a closed store, run with -race; SwapStore drains old-generation users before closing; Rescan skips names reserved by an in-flight Create; Acquire after close returns ErrRepoClosed). The federated symptom is pinned by TestQueryFederation_UnavailableMountFailsLoud / _RecentUnavailableMountFailsLoud in internal/mcp/query_federation_test.go — an unavailable mount now fails the whole query with a clean mount-labelled error instead of a recovered panic.

Lesson: when several concurrency bugs share the shape 'pointer outlives the lock that produced it', fix the lifetime model once (refcount/tombstone) instead of guarding each call site — point patches (recoverFanout, svc==nil checks) treat symptoms and miss the closed-store case.
