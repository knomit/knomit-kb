# TestDispatch_NoStoreHeldDuringIf and TestScript_NoStoreHeldDuringScript cannot see a store lease held across phase B (a swap cancels the dispatcher before the leases drain); TestDispatch_PhaseBHoldsNoLease, a counting acquire wrapper, is the real guard

Found by the PR #632 reviewer (L1) and fixed in the PR; merged as ee850fd6, re-read there. Two tests claimed in their comments that holding Acquire across phase B turns them red ('Sabotage: hold Acquire across phase B'). The reviewer ran it: release() changed to defer release() after phase A, and both tests stayed GREEN. WHY: a SwapStore goes through Machine.exitStages, which cancels every life (the dispatcher's run is the Serve life) and waits for them in reverse order BEFORE openStage.Exit drains the leases; phase B aborts on ctx within one evaluation and releases either way, so the swap's latency cannot tell a held lease from a released one. The comment was wrong from the day it was written.

THE REAL GUARD. TestDispatch_PhaseBHoldsNoLease (internal/corpus/repos/triggers_test.go) parks the real dispatcher, builds a second one with trigger.New over a counting wrapper of ri.Acquire (counter incremented on acquire, decremented in release), records the outstanding count in the EvalDelay hook at each evaluation, runs one RunOnceForTest pass (phase C only buffered, so no table writes) and requires at least one evaluation and every recorded count 0. Re-run by the re-reviewer at 03c56e27: release deferred to the end of the run gives 'Should be zero, but was 1'. NoStoreHeldDuringIf's own real sabotage is dropping phase B's per-evaluation ctx check (the swap then waits behind the slow ifs: 2.36 s). TestScript_NoStoreHeldDuringScript's comment was corrected the same way.

LESSON. A sabotage note in a test comment is a claim and must be re-run against a commit before it is trusted or copied. A latency-based test observes ctx-cancel behaviour, not resource ownership; to observe ownership, count the acquires.

UPDATE (PR #653, merged as 0156f299, re-read there): TestScript_NoStoreHeldDuringScript no longer has any wall-clock bound; the 1 s swap and 500 ms Serve-restart bounds described above are gone, and re-adding them re-creates a flake (on Windows slow-tests the swap took 1.8 s against the 1 s bound). The script now makes one host call, knomit.query({spinning: true}), answered by a stub hook without Acquire that signals a channel, then runs `while (true) {}` under ScriptBudget 24 h, so only cancellation can end it. The test waits for that signal, swaps, waits for the script to fire again on the new Serve, then restartServe; both can complete only by interrupting the spinning script. It still observes ctx-cancel interruption, not lease ownership; the lesson 'count the acquires to observe ownership' stands and TestDispatch_PhaseBHoldsNoLease remains the real guard.

Sabotage of the new form (reviewer, against a commit): making runSandboxed interrupt only on DeadlineExceeded turns the test red in about 60 s (the 30 s hang detector, then Manager.Close gives up after its 30 s drain bound). It does not hang until go test's timeout. A short script budget must NOT be restored to make a failure quicker: that brings the wall-clock flake back.

PR #656 (merge commit 819d56a0) removed TestDispatch_NoStoreHeldDuringIf's wall-clock bound: it had asserted the swap finished in under 1s while phase B ran 30 evaluations of 90 ms, and failed at 1.75s under CPU load. It now follows the TestScript_NoStoreHeldDuringScript pattern: the EvalDelay hook signals the first evaluation on a channel, each evaluation sleeps 2 s (30 of them, a minute), and the swap and restartServe must finish before a 20 s hang detector, which a swap draining behind the if phase cannot meet. Sabotage (removing phase B's per-evaluation ctx.Err check in trigger/triggers.go) is red at about 20 s. LIMIT: EvalDelay is an uninterruptible time.Sleep, so a swap may legitimately wait one evaluation (2 s); it cannot be made unbounded the way ScriptBudget can. WEAKNESS: the check after the swap (that the run started again) waits on the same evaluating channel, which may still hold a stale token from the pre-swap run (the channel is buffered and 1-2 evaluations may have queued before cancel), so that wait alone does not prove a restart; restartServe's own hang detector is what guards the property. A follow-up PR addresses this. This test still does not see a lease held across phase B (above).
