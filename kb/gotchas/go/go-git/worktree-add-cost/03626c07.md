# go-git's worktree.Add recomputes the ENTIRE worktree Status() per call — staging N files costs N×O(N)

`wt.Add(path)` in go-git v5 calls `w.Status()` internally on every invocation, and Status walks the whole worktree. Staging a generated tree one file at a time is therefore quadratic: N calls × O(N) work.

Measured on a 1969-file bundle: **115.9s** with `wt.Add`, **3.6s** with `wt.AddWithOptions(&git.AddOptions{Path: p, SkipStatus: true})` — a 32× difference producing a BYTE-IDENTICAL index (verified by comparing every entry name and hash across both paths). On a 2817-file corpus the naive version pushed a whole clone past three minutes, with the failure presenting as a hang rather than as slowness.

Why it hides: the cost is invisible at test scale. A fixture of 10–20 files stages instantly, so the bug ships and only appears against a real corpus. Per-call cost is roughly CONSTANT (proportional to total worktree size), so profiling a single Add looks fine — the quadratic total only shows when you count the calls.

TWO fixes, and they compose — apply both, in this order:

1. Do not stage what has not changed. Compare the desired content's blob hash (`plumbing.ComputeHash(plumbing.BlobObject, content)`) against the existing index entry; equal means the index already records exactly this content, so skip the Add entirely. On a real sync this cut staging from 3038 files to 44 — **189ms**. Cheapening each call is second best; not making the call is best.

2. For the calls that remain, pass `SkipStatus: true`.

What this does NOT mean — SkipStatus is not a free speed-up to sprinkle on every Add. Status is what resolves two cases, so skipping it is only safe when neither can occur: (1) the path is a DIRECTORY (`doAddDirectory` needs Status to enumerate what changed beneath it), and (2) the path is MISSING from disk, i.e. staging a deletion (`doAddFile` uses Status to decide to drop the index entry). Handle deletions separately — for a generated tree, prune index entries directly instead.

Nor is the hash-skip safe on its own reasoning: it holds only because the writer has just guaranteed the working file matches the desired content, and because anything actually written is staged unconditionally. Pin it with a test that requires an incremental run to produce a tree byte-identical to a full re-stage, and confirm that test FAILS when the skip is made unsound.

Generalize the smell, not just the fix: before calling any library helper in a loop over a large collection, check whether that helper does per-call work proportional to the whole collection. Convenience wrappers that are correct for one item are frequently accidental O(n²) when iterated.
