# go-git's CheckoutOptions.Keep means SoftReset (HEAD moves, files do NOT), and untracked files never block a checkout

In go-git v5.18.0, `Worktree.Checkout` does not implement branch switching itself — it translates its options into a `Reset` mode and delegates. The mapping is a three-way if/else in `worktree.go`, and BOTH non-default branches are traps:

- default (neither flag): `ResetOptions{Mode: MergeReset}`
- `opts.Force` -> `HardReset`
- else if `opts.Keep` -> `SoftReset`

`SoftReset` returns from `Reset` immediately after `setHEADCommit`, before the index reset and before `resetWorktree`. So `Checkout{Branch: ref, Keep: true}` moves HEAD to the branch and LEAVES EVERY FILE ON DISK UNCHANGED — a switch that silently did not happen. It is not a gentler checkout; it is not a checkout at all.

Separately, `MergeReset` calls `containsUnstagedChanges()` and returns `ErrUnstagedChanges` (message: "worktree contains unstaged changes") if it is true. That helper walks `diffStagingWithWorktree(false, true)` and **skips every change whose Action is `merkletrie.Insert`**. An Insert in that direction is a file present in the worktree and absent from the index — i.e. UNTRACKED. So the condition that blocks a checkout is precisely: a MODIFICATION or DELETION of a file that is already in the index. An untracked file, however many of them, never blocks it.

The error names no path. Neither the file nor the reason reaches the caller — only the bare sentinel.

CONSEQUENCE. Reaching for `Keep: true` to make a checkout tolerate a dirty worktree is wrong in a way that will not fail loudly: the command reports success, HEAD moved, and the working tree still holds the previous branch's content. If you need a branch switch that tolerates dirt, go-git offers no such mode — you must clear the blocking paths yourself and then use the default checkout. To do that you need to know which paths block, which means computing it yourself from `Worktree.Status()` (worktree status not `Unmodified` and not `Untracked`), because `ErrUnstagedChanges` will not tell you.

Why knomit-okf does exactly that: `checkoutOutputBranch` switches between OKF output branches in a directory that also holds the publisher's own files. `Keep` is unusable per the above. `Force` (HardReset) is unusable for a different reason — it resets the WHOLE worktree, so it is entitled to files outside the paths this tool owns, which `kb/invariants/okf/owned-paths-boundary/ab526d98.md` forbids. So `unstagedOwnership` partitions the blocking paths through `owns()`: an unowned (publisher) path is reported by name and the sync refuses, while an owned (bundle) path is rewritten from the index by `restoreOwnedFromIndex` and the default checkout then proceeds. The owned half is safe only because `export` rewrites every owned path from the source commit immediately afterwards.

WHAT THIS DOES NOT MEAN:

- NOT "`Keep: true` is the safe/polite version of `Force`". They are not two strengths of the same operation. `Force` overwrites the worktree; `Keep` never touches it. Only the unflagged default both updates files and guards against losing changes.
- NOT "a dirty worktree blocks a go-git checkout". Untracked files are dirt by every colloquial definition and are explicitly exempt. Testing this path with a newly-created file will show no error and prove nothing — the fixture must MODIFY a file that is already committed.
- NOT a claim about `git` the CLI, which happily carries uncommitted changes across a branch switch when they do not conflict. This divergence from git's own behaviour is the reason the workaround is needed at all.
