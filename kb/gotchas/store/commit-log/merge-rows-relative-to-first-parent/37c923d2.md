# A commit_log row at a MERGE commit means only 'differs from parent 0' — a PR merge gets a row for every path its PR changed, so any consumer that treats rows as write events lists merges instead of the writes behind them

commit_log's rows come from a tree diff of EVERY commit, merges included, against its FIRST parent only. Since #347 that is derivation's own diff (deriver.commitChanges / diffTrees), which TestCommitChanges_EqualsGitDiff pins equal to the older changedFilesInCommit. For a merge commit M, a commit_log row (M, path, action) therefore says only "path at M differs from path at M^1". It does NOT say M introduced that content. A PR merge into main gets a `modified` row for every path the PR changed, because main's previous tip lacks the PR's content, even though M's blob is byte-identical to M^2's.

Consequences a consumer acts on:
- Walking first-parent and taking rows as revisions (RevisionsBefore) yields ONE merge per PR, and every write behind the merge is invisible. This was the knomit_explain history bug: 15 of 36 revisions on a merge-delivered private slot, ending with more_available:false.
- To enumerate real changes, compare blobs at merges: M is a change only if its blob differs from EVERY parent's. The path_changes derivation (deriver in internal/store/path_changes.go) does this. It lists the changed .md paths from its OWN first-parent tree diff, NEVER from commit_log rows: a tampered or drifted row once lost a revision for good (review A1). It then looks blobs up (case-insensitively, through a tree cache) only for those paths. A merge row whose blob equals a non-first parent's becomes a CARRY (entry = 0, resolves_to = the entry that introduced the content); a merge with no row is TREESAME to parent 0 and needs no lookup.
- A merge with NO row for the path is TREESAME to its first parent: that is the LocalWins case, where the other side's write was discarded.

WHAT THIS DOES NOT MEAN: commit_log is not wrong or incomplete. The rows are exact for the question "what changed on this line relative to its first parent", which is what resolution (first-parent RevisionsBefore, resolveTargetCommit) asks. The trap is only reusing those rows to ENUMERATE history.
