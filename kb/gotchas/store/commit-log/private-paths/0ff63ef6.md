# commit_log records EVERY changed path, private-state .knomit/ paths included, although the fact index's isFactPath filter excludes them — so knomit_explain on a .knomit/jobs slot returns the slot's own last commit and a real history, not the branch HEAD

The store keeps two per-path records with DIFFERENT admission rules:

- The fact index (branch_facts, search, graph) admits only `repoHandler.isFactPath` paths: under the ontology root, `.md`, and no dot-prefixed segment (`fact.IsPrivatePath`). A `.knomit/<area>/` slot is never indexed, never queryable.
- `commit_log` is filled by `AppendCommitLog` / `populateCommitLog` from `changedFilesInCommit`, which diffs each commit against its first parent and records EVERY changed path. There is no `isFactPath` or `IsPrivatePath` filter on this path.

Consequence a consumer acts on: history-backed reads that go through `commit_log` WORK for private-state paths. `knomit_explain` on `.knomit/jobs/x/y.md` returns `commit` = the last commit that touched the slot, a populated `history`, and no `deleted` flag (its liveness check, `FactQuery.LastCommitForPath`, is also commit_log-backed). A caller may pass that commit back as `knomit_update`'s `if_commit` exactly as for a public fact; `TestUpdateOps_IfCommitFromExplainPasses` pins that flow end to end.

WHAT THIS DOES NOT MEAN: it does not make private paths discoverable. knomit_query, the UI and export still never see them, because those read the fact index, not commit_log. And it does not mean the two filters are deliberately different — nothing states that. Do not infer commit_log's contents from isFactPath (this exact misreading was made while designing if_commit: reading the index filter and assuming commit_log shared it predicted explain would return branch HEAD for a slot; a test showed the slot's own commit).
