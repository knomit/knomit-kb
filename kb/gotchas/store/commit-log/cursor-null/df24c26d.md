# A commit-log cursor whose hash has no commit_log row reads NULL from MIN(committed_at), not ErrNoRows: scanning it into int64 was a 500, defaulting it to 0 gives a silent empty 200 page, and 'no row' does NOT mean the repo lacks the commit

Storer.CommitLogQuery resolves an after/from/before cursor with `SELECT MIN(committed_at) FROM commit_log WHERE commit_hash = ?` (lookupTS), then `SELECT MAX(rowid)` for the same hash (lookupMaxRowid). An aggregate over no rows returns ONE row holding NULL, not sql.ErrNoRows. Scanning that into an int64 failed with "converting NULL to int64 is unsupported", and the REST list answered 500 "Failed to list commits".

AS BUILT (PR #747): lookupTS scans into sql.NullInt64 and returns storegit.ErrCursorNotInLog when the value is NULL. lookupMaxRowid has NO NULL check, on purpose: it runs only after lookupTS found a row with the same WHERE, so its MAX can never be NULL. A guard there was unreachable (a review sabotage left every test green) and was deleted. The storer cannot return a model sentinel, because test/archtest TestLayers refuses an engine/store/git -> engine/store/model import. vcs.Repo.CommitLogQuery translates it.

"NO ROW" IS NOT "NOT HELD": commit_log has one row per CHANGED path, so a commit the repo holds that changed no file has zero rows. The fsck parity check skips that direction for this reason. The write path never makes such a commit (an identical rewrite returns the current head), but a merge whose side is already in the first parent's tree, or an empty commit arriving from a remote, does. So vcs checks the object store. If the store lacks the commit, or the value is not a 40-hex hash, the error is model.ErrCommitNotFound (404 commit_not_in_repo). If the store holds it, the error is model.ErrCommitNotInLog (400 commit_not_in_log, "Commit has no log position"). The test builds that commit with storetest.CommitFiles, writing an unchanged tree.

THE TRAPS: (1) the one-line fix of treating NULL as 0 makes the cursor condition match nothing, and the list answers 200 with an EMPTY page that reads as "no commits". A sabotage showed exactly that (count 0). Never fix a NULL scan by defaulting the value. (2) Mapping every missing row to commit_not_in_repo tells a client that a commit it really has does not exist, and the web UI would show "no version" for it.

MERGED as 452d41af (PR #747). The refs are re-pinned there and the claims re-read: lookupTS checks NULL, lookupMaxRowid has no NULL check, vcs.CommitLogQuery maps ErrCursorNotInLog using the object store, and the test uses storetest.CommitFiles. The user approved the 400 commit_not_in_log answer (decision 41472083).
