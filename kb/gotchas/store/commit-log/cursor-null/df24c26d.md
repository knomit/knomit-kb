# The commit-log cursor lookups (MIN/MAX over commit_log) return NULL for a hash the repo lacks; scanning that into int64 was a 500, and treating NULL as 0 would silently answer an empty 200 page

Storer.CommitLogQuery resolves an after/from/before cursor with `SELECT MIN(committed_at)` and `SELECT MAX(rowid) FROM commit_log WHERE commit_hash = ?`. An aggregate over no rows returns ONE row holding NULL, not sql.ErrNoRows. So an unknown hash never looks like "not found" to a Scan into int64: it fails with "converting NULL to int64 is unsupported", which the REST list answered as 500 "Failed to list commits".

PR #747 scans into sql.NullInt64 and returns model.ErrCommitNotFound when it is not Valid (404 commit_not_in_repo at the web layer). Both lookups check, and either one alone is enough to catch an unknown hash.

THE TRAP: the attractive one-line fix, `ts.Int64` with NULL treated as 0, makes the cursor condition match nothing. The list then answers 200 with an EMPTY page, which reads as "no commits" rather than as an error. A sabotage run showed exactly that (count 0). Keep both checks, and never "fix" a NULL-scan error by defaulting the value.
