# A resolution for a path that did not conflict must be caught against the computed conflict set BEFORE any merge path — inside the walk the check can never be complete

Two holes make the in-loop version unfixable.

The FAST-FORWARD and NOOP returns never enter `mergeTreesWithStrategy` at all, so a resolution sent with a clean merge would have been silently dropped — and on the fast-forward path the ref had already moved by the time anything could notice.

A path only DST changed never appears in `DiffTree(base, src)`, so the walk cannot see it even when it runs. A resolution naming one is a caller who believes the merge is something other than it is, and ignoring the entry lets them conclude they settled a path they never touched.

So the keys are validated up front against a conflict set computed by a detection pass, before any merge path — including the two early returns, each of which now guards before it moves anything.

RELATED, AND SURPRISING: resolving EVERY conflict to the parent's side yields a tree identical to dst, so `mergeIntoBranchLocked` returns ModeNoop — no merge commit is written and the parent ref does not move — while `CommitExperiment` still deletes the experiment. The action did happen; a summary claiming "merged into <parent>" would send someone looking for a commit that was never created, so the mode is reported instead.

DISTINCT FROM invariants/store/local-reconcile/never-reset-never-exit, which shares only the word ModeNoop. That fact is about the reconcile loop's refusal to act on doubt; this one is about validating caller-supplied resolution keys before a merge path runs.
