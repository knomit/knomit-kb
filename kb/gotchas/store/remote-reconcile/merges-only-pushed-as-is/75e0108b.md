# KNOWN GAP: on a rewind, an agent branch that diverged from the new upstream with ONLY merge commits beyond it (empty replay walk) is left as it stands and force-pushed, merges and everything they brought in included

WHAT (store behaviour at 60ddfb1c, kept unchanged by branch fix/fleet-switch-replay at b25765bd). replayOntoUpstream with an empty unpushedCommits walk: local == upstream is a no-op, local an ancestor of upstream fast-forwards, and EVERY other shape is a no-op that keeps the branch as it stands, so the caller's force-push sends it. When the branch diverged on shared history and everything beyond the upstream is merges (a hub's consensus merges of members' branches, an experiment's merge commit, a reconcile merge), those merges and the content they brought in are pushed as this copy's branch.

CONSEQUENCE IN A FLEET (reasoned, not reproduced end to end): an old master that follows a new host whose main lacks its last merges pushes members' commits inside its own branch; the new host's receive-pack judges each new commit under signer-is-pusher, so a member's commit signed by the member is refused `not-pusher` and the old master's sync fails. After a stand-down-first switch the new main holds those merges, so this shape does not arise; it can in the dead-master fallback.

WHY IT WAS NOT FIXED: PR #531's first version moved such a branch onto upstream ('shape 3'); the review (B1) showed that silently drops a committed experiment, whose merge commit is the only reference to its work (CommitExperiment deletes the experiment). The review's option (b), collecting this agent's own non-merge commits through merges, would fix both; not built.

MISREADING: 'the stop rule causes this': no, the empty walk on a diverged merges-only branch predates it.

VERIFIED AT THE MERGE (PR #531, squash commit 8ca72760 on dev, 2026-10-16). Unchanged: replayOntoUpstream with an empty walk and no dropped commit still keeps the branch as it stands (no-op, caller force-pushes). NARROWING to know: when the walk DROPPED a marker-only commit (SetReplaySkipPaths, the fleet repository's artifacts/fleet/master), the branch is rebuilt on upstream with what is left, so a merges-only divergence that also carried a dropped marker commit is NOT pushed as it stands; it is rebuilt on upstream and the merges are not kept (reproduced by the #535 gap probe). In a FLEET that is not data loss: what lies behind a hub master's consensus merges is members' commits (they push their own branches to the new host; the old master could not deliver them anyway, the new host refuses them under signer-is-pusher as not-pusher) or old main, and the fleet repository refuses experiments. The gap above is the no-drop case.

UPDATE (PR #535, verified at merge 48e7d8d5). (1) The review's option (b), collecting the instance's own commits through merges, is BUILT (kb/invariants/store/remote-reconcile/side-replay/7c9af34f.md; incident kb/incidents/store/remote-reconcile/experiment-merge-lost/23318e68.md). In an ORDINARY repository a branch whose only divergence is a clean own experiment merge therefore no longer has an empty walk: it is rebuilt on the upstream with the merge replayed as one commit (ModeRebase), not kept and force-pushed as it stands (ModeNoop). What remains of this gap is the empty walk proper (nothing of the instance's own behind the merges, no dropped commit), whose no-op is unchanged. (2) The gap also applies to MEMBERS after a dead-master fallback: a member that fast-forwarded onto the old master's merge (watermark = that tip) has an empty walk and no dropped commit, so its branch is kept as it stands and force-pushed with the old master's merges inside (reasoned from the probe, not run end to end). MISREADING: 'the experiment case is why this gap exists, so it is closed' is wrong in the other direction too: only the experiment case is closed; the fleet case is not changed.
