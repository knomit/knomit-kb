# KNOWN GAP: on a rewind, an agent branch that diverged from the new upstream with ONLY merge commits beyond it (empty replay walk) is left as it stands and force-pushed, merges and everything they brought in included

WHAT (store behaviour at 60ddfb1c, kept unchanged by branch fix/fleet-switch-replay at b25765bd). replayOntoUpstream with an empty unpushedCommits walk: local == upstream is a no-op, local an ancestor of upstream fast-forwards, and EVERY other shape is a no-op that keeps the branch as it stands, so the caller's force-push sends it. When the branch diverged on shared history and everything beyond the upstream is merges (a hub's consensus merges of members' branches, an experiment's merge commit, a reconcile merge), those merges and the content they brought in are pushed as this copy's branch.

CONSEQUENCE IN A FLEET (reasoned, not reproduced end to end): an old master that follows a new host whose main lacks its last merges pushes members' commits inside its own branch; the new host's receive-pack judges each new commit under signer-is-pusher, so a member's commit signed by the member is refused `not-pusher` and the old master's sync fails. After a stand-down-first switch the new main holds those merges, so this shape does not arise; it can in the dead-master fallback.

WHY IT WAS NOT FIXED: PR #531's first version moved such a branch onto upstream ('shape 3'); the review (B1) showed that silently drops a committed experiment, whose merge commit is the only reference to its work (CommitExperiment deletes the experiment). The review's option (b), collecting this agent's own non-merge commits through merges, would fix both; not built.

MISREADING: 'the stop rule causes this': no, the empty walk on a diverged merges-only branch predates it.
