# KNOWN GAPS in the rewind's scrub protection after #539 and #542: a disjoint upstream keeps the branch (tracked as issue #541), a repo with no watermark AND no remote-tracking ref (a truly first sync) that is reset to an ancestor still pushes the removed commit, and an own write above the watermark that edits a removed file brings the file back (accepted)

READ THIS BEFORE SAYING 'nothing removed upstream returns after a rewind'. At merge ba40165b (#539 + #540) the rewind path rebuilds a branch on shared history whose replay walk is empty (incident: kb/incidents/store/remote-reconcile/noop-rewind-leak/), but three shapes still keep or return removed content:

(a) DISJOINT UPSTREAM. A history rewritten down to its ROOT to scrub something shares no commit with the local branch. With nothing of the agent's own past the watermark, replayOntoUpstream keeps the no-op ('nothing to replay onto a disjoint upstream; the branch stays as it is') and the force-push sends the scrubbed history back. It cannot simply be rebuilt: attaching a fresh local repo to a remote of the same knowledge base is the same shape (its watermark is the InitRepo seed, never on any origin), and taking the remote's main there changes the repository's identity (its root commit); tests TestSwap_CopyFailureRestoresStoreAndOrigin and TestHandleCommit_Disjoint_FailedSwapRestartsThePreviousSyncMode pin that identity. Closing it needs a signal that the watermark was ever on the origin. STATUS: the user ruled (2026-10-17) that this is tracked as enhancement issue #541 (stop, show the delta, let the user choose what to keep; delta export), not a silent rebuild. Also pre-existing: a local repo WITH writes that is attached to a disjoint remote already loses its seed root, so its ID changes; the identity stability those two tests pin holds only for a repo with no writes.

(b) NO WATERMARK. A repo with NO watermark ref (refs/knomit/agent-base/<branch>; made before it existed and not synced since) uses the merge base as its stop point, and strictlyAhead without a watermark is the upstream-ancestor test alone. If the origin resets main to an ancestor of the branch, the branch reads as strictly ahead, keeps the removed commit and pushes it. STATUS: CLOSED by PR #542 (merge 637960bc, 2026-10-17) EXCEPT on a truly first sync: sync() reads refs/remotes/origin/<main> before the fetch moves it and seeds the missing watermark there (where the origin was at the last fetch); a repo with no watermark AND no remote-tracking ref seeds nothing, the merge-base fallback stays, and this shape still leaks there by design (no signal of where the origin was). Two limits of the fix even where it applies: a seed beyond what the branch consumed (a fetch whose reconcile failed) loses no own work but keeps the removed commit and rebuilds the branch; and neither the watermark nor the tracking refs are reset when the origin URL changes, so own commits only the old origin held are dropped on the first rewind against a new origin. See kb/invariants/store/remote-reconcile/watermark-seed/0f9cc562.md and the UPDATE in replay-stop/5482c3ab.md.

(c) AN OWN WRITE ABOVE THE WATERMARK THAT EDITS A REMOVED FILE. The scrubbed commit stays unreachable, but the file comes back with the edited body (the local side wins), and its path and content are pushed. Pre-existing (the same on dev before #539). STATUS: accepted by the user (2026-10-17): 'this is up to however manages consensus (main)'.

NOT A GAP BUT A COST: the rewind drops CONSUMED own commits the new upstream lacks (kb/decisions/store/remote-reconcile/consumed-own-work-dropped/); the user accepted that too.

MISREADINGS. 'The disjoint no-op is intended behaviour': it is a known residual, kept only because closing it breaks attach identity. 'Issue #541 is the fix for the no-watermark case': no, #541 is the root-deep rewritten-origin case; the no-watermark fix is PR #542. 'A repo with no watermark still leaks after #542': only a truly first sync (no tracking ref either) does.

UPDATE (PR #544, merge 8a01d3ca on dev, read there): the limit in (b) that 'neither the watermark nor the tracking refs are reset when the origin URL changes, so own commits only the old origin held are dropped on the first rewind against a new origin' (C2) is CLOSED for a switch: on the first round with a different origin the rewind does not run, so nothing is dropped; the branch is merged with the new main and pushed as it stands. It still holds for a SAME-origin rewind. Shape (a), the disjoint upstream, is unchanged (issue #541): a switch to an origin with no common history keeps the existing rules. New residuals of the switch rule (old-origin commits ride along; A to B to A counts as a switch): kb/gotchas/store/remote-reconcile/origin-switch-residuals/50e78ce6.md; the rule: kb/decisions/store/remote-reconcile/origin-switch/5269d61e.md.
