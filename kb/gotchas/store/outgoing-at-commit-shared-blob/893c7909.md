# HYPOTHESIS: OutgoingAtCommit's ignored branch may surface another branch's target commits when the same (path, blob) is written on two branches with refs that resolve to different target versions; unreproduced

STRUCTURAL FACT, read at the merge commit of PR #614: GraphStore.OutgoingAtCommit (internal/engine/store/index/search_graph_query.go) resolves the effective write-commit with ResolveActiveCommitForPath, reads the blob hash at that commit, and then collects edges with graphDerivedFromNeighbours keyed only by the source Fact node (path, blob_hash). Its doc comment says the branch parameter is accepted for symmetry and reserved, and that branch reachability is intentionally not enforced; the only filter is dropping candidates whose target_commit is missing from commit_log. The Fact node is keyed by (path, blob_hash), not by branch. Per kb/invariants/store/refs-to-derived-from-edges/eb438c74.md, DERIVED_FROM edges are immutable and accumulate per ref-event (dedup only makes an identical repeated write idempotent), so two ref-events with different target_commit are two edges.

PREDICTION (not reproduced, not exercised by any test): if byte-identical content for one path is written on two branches, and its refs resolve (resolveTargetCommit) to different target versions on each, the node carries both sets of DERIVED_FROM edges, so /outgoing for that fact on either branch would list both branches' target commits. Raised in the PR #614 review as a reviewer observation. Not checked: how the ingest dedup guard keys a ref-event (if it ignores target_commit the case collapses), and whether a second branch's write of identical bytes re-runs the post-commit edge write at all.

CONSEQUENCE: do not cite this as a bug. Reproduce it with two branches and a diverging target before relying on it or filing it. The intended asymmetry stays: IncomingAtCommit filters by branch_commits, OutgoingAtCommit does not (see kb/gotchas/store/anchored-read-ignores-branch/2b146823.md).
