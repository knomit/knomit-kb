# fact_domains.domain and fact_domain_tokens.domain can hold DIFFERENT strings for the same fact — joining the two tables on `domain` is a false-positive generator

# The two domain tables agree at write time and can still disagree on disk

Both writers insert the SAME `canonicalizeDomain(domain)` value into `fact_domains.domain` and `fact_domain_tokens.domain` (`search_crud.go` upsert, `domain_match.go` repopulateDomainTokens). So a naive reading says the two columns must always match.

On disk they do not. Measured on a live `knomit-kb` repo, 2026-08-12: 6 fact ids where `fact_domains` holds the pre-de-hyphenize form and `fact_domain_tokens` holds the current one — `'claude-code'` vs `'claude code'`, `'mutation-gates'` vs `'mutation gates'`, `'design-philosophy'` vs `'design philosophy'`.

**Cause:** `canonicalizeDomain` gained a de-hyphenize step after those rows were written. `repopulateDomainTokens` rewrote the TOKEN side under the new canonicalization; nothing rewrote `fact_domains`. Both inserts are `INSERT OR IGNORE`, so the stale row was never replaced.

**Consequences.**
1. For an integrity check: never join `fact_domains` to `fact_domain_tokens` on `domain`. On this home that join reports 6 phantom failures in each direction. Compare at `fact_id` granularity (clean on all four live repos) and treat a `(fact_id, domain)` set difference as a WARNING about canonicalizer drift, not a structural ERROR.
2. For search: domain FILTERING reads `fact_domains` (old string) while token CONTAINMENT reads `fact_domain_tokens` (new string), so for these facts the two surfaces disagree about what the fact's domain is.

**What this does NOT mean:** the tables are not free to diverge in general. A fact_id present in one table and absent from the other IS structural drift and is an error — that case measured 0 across every live repo.
