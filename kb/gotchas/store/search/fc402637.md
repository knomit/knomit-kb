# The text-less Search path (no Text, QueryByPath or QueryVec) ranks only by its ORDER BY: newest commit first, then path ascending, because every row scores 100; before #660 it had no ORDER BY

FactQuery.search takes the text-less path when Text, QueryByPath and QueryVec are all empty. Every row there gets Score 100, so the ORDER BY is the whole ranking and also decides which rows the LIMIT keeps. The order is `ORDER BY COALESCE(cl.committed_at, 0) DESC, f.path ASC`: the tie-break recentFactsSearch applies after score, and the RecentFacts order. Before #660 there was no ORDER BY, so both the order and which rows survived the LIMIT were whatever SQLite's plan produced.

Consequence: callers and tests may rely on text-less results being newest-first, then path-ordered (path is unique per branch, so the order is total); with Limit N the N newest matching facts are kept; a score comparison on this path means nothing. MCP knomit_query calls with filters but no text take this path, so they are deterministic too (newest first, then path); only queries with text are relevance-ranked, fused across mounts with RRF.

Symptom it fixed: the storytest flake TestSearch_RankingStableUnderDeterministicEmbedder, where two identical Search("") calls returned tied rows in different orders.

WHAT THIS DOES NOT MEAN: the vector path's tie order is not covered (it sorts by score only; equal-score candidates keep their metadata-query order). Search ignores Offset, so paging continuity still comes from the MCP snapshot session, not from this ORDER BY.
