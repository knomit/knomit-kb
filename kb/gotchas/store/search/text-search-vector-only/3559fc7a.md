# Text search is vector-only: a text query needs a query vector, a working KNN and the cosine cutoff — and before #372 every failure of the three returned an empty list

factQuery.Search (internal/store/search_query.go) has no keyword path for text. A text query is answered only by (1) obtaining a query vector (the caller's QueryVec, else EmbedQuery), (2) a KNN over facts_vec, and (3) keeping candidates whose cosine is strictly above the cutoff (the caller's min_similarity, else the model's SearchFloor). The `else keywords` wording in older comments was wrong.

Before #372, each step could fail without a trace in the response: a missing or failed query vector, a failed or unscannable KNN query, and an over-high cutoff all ended in `return nil, nil`, which the MCP handler serialised as {"facts":[]} with isError=false, indistinguishable from 'nothing matched'. The most likely real-world trigger was a caller passing an unreachable min_similarity: EmbeddingGemma cosines run cool (a near-verbatim title query tops out near 0.54), and the displayed `score` is cosine x 100, so a value such as 45 (or even 0.7) silently returned nothing.

CONSEQUENCE for a reader. An empty text result is only 'no matches' when no cutoff was supplied and no error came back. After #372: step 1 and 2 failures are errors (the failure now reaches MCP isError / REST 500); step 3 with a caller cutoff yields a `notice` giving the cutoff and the best cosine; and SearchOptions.Diag (a per-call OUTPUT parameter, never shared across concurrent calls) exposes VecHits, BestCosine, Cutoff and Candidates. The no-embedder case (a store opened without an embedder, tests and tooling only; app.New refuses to start that way) deliberately still answers a text query with an empty list, now with a Warn log, so an empty text result from a store with no embedder is NOT evidence of anything; the QueryByPath (similar-to) lookup keeps its older log-and-return-empty behaviour.
