# BatchWriteFacts never refuses a delete of an absent path — a missing leaf AND (since #389) a missing folder are both silent no-ops; only a storage failure fails the batch

MEASURED, because the obvious reading ("a delete of something absent fails the batch") is wrong, and a review finding was once built on it.

At fa1b6d03 (PR #389, #375 option b), `BatchWriteFacts` returns NO error for a delete path that is absent. That covers every shape:

- a missing leaf whose folder still holds other facts;
- a leaf that never existed, in a folder that does exist;
- a leaf whose folder does NOT exist, whether it never existed or a delete emptied it. Knomit now DROPS a folder its delete empties, as git does, so a repeat delete of the same path lands in this case.

Before #389 the third shape failed the whole batch with `deleteFromTree: subtree %q not found`. That error no longer exists. A delete now fails the batch only on a STORAGE error, such as a subtree object the tree names but the store does not hold (TestBatchWriteFacts_DeleteFailureCommitsNothing). Such a failure still leaves the batch's writes uncommitted.

An absent-path delete leaves the tree unchanged, but a delete-only batch of that shape still MINTS a commit whose tree equals its parent's. One exception: if the walk passes through a legacy (pre-#389) EMPTY folder, that folder is dropped (see the delete-drops-empty-folders invariant).

CONSEQUENCE: you cannot rely on a failed batch to tell you a delete target was missing. Use BatchWriteFactsMustExist, which checks inside the branch lock and returns *RetractMissingError. Equally, you do not need to pre-filter merge or retract sources to avoid aborting a batch.

There IS still a reason to filter such a delete list, and it is a different one: whatever the caller records as "retired" must name only what the call actually removed. In the review pipeline that list drives the in-flight refresh, which strips those paths out of still-queued work items. So a path reported retired when nothing removed it deletes a LIVE fact from the judge's view. The synthesize prune merge filters with FactExists for exactly this reason.

WHAT THIS DOES NOT MEAN:
- Not "deletes are unchecked". A storage failure still aborts the batch atomically.
- Not "DeleteFact is a no-op on an absent path". DeleteFact has its own existence check under the lock and refuses with "does not exist".
