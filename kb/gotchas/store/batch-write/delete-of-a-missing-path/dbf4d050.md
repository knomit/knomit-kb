# BatchWriteFacts refuses a delete ONLY when the path's parent subtree is absent entirely — a missing leaf in an existing directory is a silent no-op

MEASURED, because the obvious reading is wrong and a review finding was built on it.

`BatchWriteFacts` returns an error for a delete path only when that path's parent SUBTREE does not exist in the tree at all (`deleteFromTree: subtree "nested" not found`). Three cases that do NOT error:

- a missing leaf whose directory still holds other facts;
- a leaf that never existed, in a directory that does exist;
- a leaf whose directory was emptied by deleting its last file — go-git keeps the (now empty) subtree, so a later delete of that same path is still a no-op.

CONSEQUENCE: you cannot rely on a failed batch to tell you a delete target was missing, and equally you do not need to pre-filter merge or retract sources to avoid aborting a batch. A source path that was ever a real fact lived in a real directory, so it can never reach the erroring case.

There IS still a reason to filter such a delete list, and it is a different one: whatever the caller records as "retired" must name only what the call actually removed. In the review pipeline that list drives the in-flight refresh, which strips those paths out of still-queued work items — so a path reported retired when nothing removed it deletes a LIVE fact from the judge's view.

WHAT THIS DOES NOT MEAN: not "deletes are unchecked". The never-existed-subtree case does error and does abort the whole batch, leaving the batch's writes uncommitted — see TestBatchWriteFacts_DeleteMissingPathFails.
