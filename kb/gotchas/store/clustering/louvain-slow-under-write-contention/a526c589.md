# Slow Louvain / 'database is locked' was the embeddings rebuild holding the SQLite write lock through ONNX — CONFIRMED + FIXED (PR #82)

CONFIRMED + FIXED (PR #82). The ~90s Louvain stalls and the 'database is locked' storms seen during connect/rebuild were the EMBEDDINGS phase of index Rebuild holding the SQLite single-writer lock for the full duration of ONNX inference. rebuildEmbeddings opened a transaction (BEGIN IMMEDIATE acquires the write lock under _txlock=immediate) and THEN ran the embedder batch-by-batch INSIDE it; inference over hundreds of facts kept the write lock held for tens of seconds, so any concurrent writer — louvain() intermediate state, reconcileAgentMerge, incremental im.Sync — blocked on _busy_timeout (5s), retried, and re-blocked. That serialization, not algorithm cost, produced the suspiciously constant ~90s settle and the lock storms (which on a slow machine froze connect at 0/568 for minutes).

FIX: rebuildEmbeddings now computes ALL embeddings OUTSIDE any transaction (batcher.EmbedDocuments / EmbedDocument into an in-memory slice), then opens a SHORT tx solely to INSERT the finished vectors. The write lock is now held for milliseconds, not for the inference duration, so concurrent louvain/reconcile/sync no longer starve. A new searchIndex.rebuilding atomic.Bool also lets CachedClusterFacts serve the cached cluster result (or empty) instead of contending while a rebuild is in flight. Companion fact: the three-phase rebuild architecture (kb/architecture/store/fast-rebuild-three-phase).
