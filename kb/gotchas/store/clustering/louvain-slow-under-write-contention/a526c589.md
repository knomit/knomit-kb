# Louvain compute balloons ~0.1s → ~90s when it runs near background writes

`ClusterFacts` (`cypher('RETURN louvain(γ)')` in internal/store/search_graph.go) runs ~0.0–0.2s in steady state but takes a consistent ~86–92s on the occasions it runs shortly after background WRITE activity. Observed 4×; every slow run followed either a repo open + `reconcileAgentMerge` burst, or an `index sync: incremental update` (new commits indexed ~12s earlier). Quiet-DB runs are always fast, independent of graph size (slow runs had FEWER clusters: 17–19 vs 30–37 for fast runs).

Ruled out: NOT `withCypherRetry` backoff (sub-ms × 5 attempts), NOT a single `_busy_timeout` wait (5s). The ~90s is suspiciously constant across different graph sizes → a fixed settle/wait window, not algorithm cost.

Leading hypothesis (UNCONFIRMED): `louvain()` read contends with concurrent writes — `reconcileAgentMerge`, embedding (gemini batch), incremental `im.Sync` — all serialized by `_txlock=immediate`; if louvain writes intermediate state it blocks on busy_timeout behind a `BEGIN IMMEDIATE`, retries, re-blocks. Alternatives: cold GraphQLite graph projection on first louvain after store open; or contention with the review pipeline's ≤8 concurrent neighbor `cypher()` reads. Decisive next step is split-timing + contention instrumentation inside ClusterFacts to capture one slow occurrence. Full plan: .claude/plans/2026-06-10-louvain-slow-compute-investigation.md
