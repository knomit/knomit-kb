# 'database is locked' storms during rebuild = embeddings phase held the SQLite write lock through ONNX inference — CONFIRMED + FIXED (PR #82)

CONFIRMED + FIXED (PR #82). The 'database is locked' storms (and, historically, ~90s graph-wide louvain() stalls) seen during connect/rebuild were the EMBEDDINGS phase of index Rebuild holding the SQLite single-writer lock for the full duration of ONNX inference. rebuildEmbeddings opened a transaction (BEGIN IMMEDIATE acquires the write lock under _txlock=immediate) and THEN ran the embedder batch-by-batch INSIDE it; inference over hundreds of facts kept the write lock held for tens of seconds, so any concurrent writer — reconcileAgentMerge, incremental im.Sync (and, at the time, louvain() intermediate state) — blocked on _busy_timeout (5s), retried, and re-blocked. That serialization, not algorithm cost, produced the lock storms (which on a slow machine froze connect at 0/568 for minutes).

FIX (still current): rebuildEmbeddings now computes ALL embeddings OUTSIDE any transaction (batcher.EmbedDocuments / EmbedDocument into an in-memory slice), then opens a SHORT tx solely to INSERT the finished vectors. The write lock is held for milliseconds, not for the inference duration, so concurrent writers no longer starve. The durable lesson: NEVER hold the SQLite write lock across ONNX inference (or any slow compute) — compute outside the tx, write inside a short one.

HISTORICAL NOTE: the louvain()/CachedClusterFacts/searchIndex.rebuilding machinery this fact originally cited was removed by PR #98 (graph-wide louvain + cluster cache deleted; clustering is now in-process and scoped). The embeddings-rebuild write-lock fix is independent of clustering and remains in force. Companion: kb/architecture/store/fast-rebuild-three-phase.
