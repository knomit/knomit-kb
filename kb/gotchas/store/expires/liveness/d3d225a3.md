# fact_expires is one row per dated fact VERSION (keyed by the content-addressed facts row) shared by every branch and never garbage-collected in practice (GC has no production caller): a version superseded by an edit leaves an orphan row forever, a version retracted on the agent branch keeps its row while main holds it, and a main-only fact has a row too — liveness on a branch is branch_facts, so anything that must act only on LIVE dated facts must join branch_facts(branch) and never read fact_expires alone

Measured at origin/dev 0ef7edee for F07 PR 2 (the worker's and the reviewer's probes agreed on every path). facts rows are content-addressed, UNIQUE(path, blob_hash), immutable and shared by every branch; fact_expires(fact_id PRIMARY KEY REFERENCES facts(id) ON DELETE CASCADE, expires, expires_at) therefore holds one row per dated fact VERSION ever indexed on any branch. Liveness is branch_facts(branch_id, path) → fact_id, UNIQUE(branch_id, path), maintained synchronously by every write path (each ends in notifyCommit → im.Sync under the branch lock: writeFileExact, deleteFile, batchWrite, merges, replay, AdvanceLocalUpstream) or by Rebuild.

Per path, what happens to the fact_expires row of the removed/replaced version: retract or delete or batch delete — searchIndex.delete removes the branch_facts pointer and deletes the facts row (cascade) ONLY when no other branch points at the version, so after a reconcile main usually still holds it and the row STAYS; an update that clears or changes `expires`, a body-only edit, a merge that rewrites the file — the new version gets its own facts/fact_expires rows and the OLD row stays as an orphan forever (only GC(), which nothing calls in production, would remove it); a merge that deletes, a rewind that scrubs — the pointer goes and the row goes only if no branch holds the version; a rebuild REPLACEs the live rows and does not remove orphans; SwapStore replaces the whole table with the clone's; a fact live on main and not yet merged into the agent branch has a row with no agent pointer.

Consequence: a sweep written over fact_expires alone (as the F07 design's first wording invited, 'fact_expires holds rows only for facts live at HEAD') would fire for a fact whose author CLEARED its date, for a superseded version, for a fact retracted here but still on main, and for a main-only fact. The letter of that wording cannot be made true without breaking F03's reads on main and exp/* (they LEFT JOIN the shared table); its INTENT ('a removed fact can never fire', maintainer clarification 2026-09-28: 'matches only facts that are still alive') is met by the liveness join branch_facts(agent) ⋈ fact_expires plus a confirmation against the HEAD tree — which is what DueCandidates does. No F03 maintenance path 'lags' and none was changed. Do not 'fix' the orphans by deleting fact_expires rows on update: the same row can be live on another branch.
