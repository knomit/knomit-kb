# TestVerifyIsNeverInTheWritePath's NAME list let fleetrec.* calls through after the move into a child package; since #552 and #553 it also rejects ANY package-qualified call into fleetrec or verify from fact_write.go and vcs/sign.go

internal/engine/store/verify_not_in_write_path_test.go greps the SOURCE TEXT of fact_write.go and internal/vcs/sign.go (it is a text scan, so a comment counts) with three rules. Rule 1 is a fixed alternation of call names (CheckRange, Audit, LoadFleet, LoadFleetAt, FleetMembersAt, FleetPKIAt, FleetAt, loadMembers, loadFleetPKI, newJudge, ...). Rule 2, added after hier-08 (PR 552), is the package-qualified pattern `\bfleetrec\.\w+\(`: ANY call into the fleetrec package fails the guard, whatever its name. Rule 3, added by the verify extraction (PR 553), is `\bverify\.\w+\(`: ANY call into the verify package fails the guard the same way. Both rules are on dev at 1370c1d4.

WHY RULE 2 EXISTS: rule 1 is bound to spellings, not to the property 'no verification in the write path'. When hier-08 moved the fleet read into internal/engine/store/fleetrec, the same read became reachable as fleetrec.At, FileAt, KeysOf, Since, MainLog and ResolveCommit; none is in the name list, so a call to fleetrec.At( from fact_write.go PASSED while the old spelling FleetAt( failed. The first fix (listing LoadMembers, LoadMembersOfTree, LoadFleetAtCommit) only chased names. Sabotage on throwaway commits confirmed: fleetrec.At( and fleetrec.KeysOf( now fail with 'calls into the fleetrec package from the write path'; FleetAt( still fails rule 1. At the #552 merge (2ca72643) ONLY the fleetrec rule existed on dev; #553 (merged as 1370c1d4) added rule 3 for `\bverify\.\w+\(`, so a new verify export such as verify.Audit or any future name fails too. The verify package is internal/engine/store/verify, so a verify.<name>( call from the write path is now caught by rule 3 as well as by the name list.

CONSEQUENCE for future extractions: when a verify- or fleet-reading function moves into a child package, add the child's package qualifier (`\b<pkg>\.\w+\(`) to the guard in the same change, and prove it bites by putting a call to a name NOT in the list (e.g. <pkg>.KeysOf()) into fact_write.go on a throwaway commit. Do not rely on extending the name list.

WHAT THIS DOES NOT MEAN: the guard does not forbid fact_write.go from importing a child package; it forbids calls qualified by the fleetrec or verify package names. A call through an import alias (`import f "knomit/internal/engine/store/fleetrec"` then `f.At(`), a dot-import, or a method on a value returned from another package is still invisible to a text scan: the pattern matches the literal package name, so renaming the import on the way in defeats it. The guard is not a call-graph check.

PATH NOTE at hier-09 (PR #555, merged into dev as 6733104c; verified there): the first file the guard reads is now facts/fact_write.go (relative to internal/store; it was fact_write.go before the facts child moved it), next to internal/vcs/sign.go. A function that moves between the parent and the facts child changes which spelling reaches the guard: facts calls into vcs and verify are spelled vcs.<Name>( and verify.<Name>(, and the verify rule fires on any verify.<Name>( inside facts/fact_write.go.

UPDATE at hier-11 (PR #560, branch refactor/hier-11-sync; merged as 3e4c6cff; the guard file is byte-identical there to 31de34e4, where the proofs below were run): the origin-synchronisation child (internal/store/remotesync; first extracted as internal/store/sync, renamed before merge, see kb/decisions/store/remotesync-package-name/feac7433.md) holds the publish-time judge JudgeOwnRange, which was in NO list before (it was an unexported method of the parent). The guard now has a fourth rule and one more name: rule 4 is `\bremotesync\.\w+\(` over the same two files (facts/fact_write.go and internal/vcs/sign.go). The package is named remotesync precisely so the rule does not have to match the bare word sync: the first cut matched `\b(storesync|sync)\.\w+\(` and so falsely flagged the standard library's sync.OnceFunc( (and any other stdlib sync call) in the guarded files; that regex is gone. And `judgeOwnRange|JudgeOwnRange` joined rule 1's name list, because JudgeOwnRange is reached as a METHOD on the promoted handle (`rh.JudgeOwnRange(`), which no package-qualifier rule can see. Proven on throwaway commits at 31de34e4: a real `remotesync.NewIndex(nil)` call (with its import) in facts/fact_write.go fails with 'calls into the remotesync package from the write path', a stdlib `sync.OnceFunc(func(){})` call there PASSES (the false positive is gone), and `// rh.JudgeOwnRange(a)` fails rule 1 ('JudgeOwnRange(' in the quoted match). WHAT THIS DOES NOT MEAN: the rules do not make a call to a sync method on a value of some other name visible (a method on a variable `r` whose type is a remotesync handle, an import alias such as `s "knomit/internal/store/remotesync"`); like the other package rules it is a text scan of two files, not a call-graph check.
