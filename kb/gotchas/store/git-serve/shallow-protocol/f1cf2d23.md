# knomit's upload-pack implements shallow itself (go-git's server has none), and four protocol judgements were each found by a failing real-git test: shallow section gated on depth ALONE; the deepen probe round answered with the shallow list and nothing else; client shallows graft the want walk only without a depth; unshallow requires the commit's PARENTS transferred

Background: go-git's built-in transport/server advertises only agent and ofs-delta, rejects any unadvertised capability, and returns "shallow not supported" for shallows. go-git's CLIENT adds the `shallow` capability whenever CloneOptions.Depth != 0 (remote.go:1163 in v5.19.2), so the wizard's depth-1 branch probe against a knomit origin got HTTP 500 — the defect that started PR #205. The fix builds the object set in knomit (packObjects, internal/store/httphandler_pack.go): a request without depth is an unlimited walk, `deepen N` is the same walk cut N commits from each want, every transferred commit carries its complete tree, haves are subtracted with the have-walk STOPPING at the client's reported shallows (a shallow client does not hold the parents of its shallow commits).

The four judgements, each pinned by a real-git (2.55.0) test that failed without it:
1. Emit the shallow/unshallow section only when the request carries a DEPTH. git's consume_shallow_list reads one only under stateless_rpc && deepen; go-git's NewUploadPackResponse sets isShallow = !req.Depth.IsZero(). A plain `git pull` from a shallow clone sends `shallow` lines with NO deepen; a section there desynchronises the stream.
2. git sends want+deepen as its own probe round, reads the shallow list up to the flush, then sends haves in a NEW request over the same stream. That probe round must be answered with the shallow section and NOTHING else — an ACK/NAK appended there is still buffered when the next round's shallow list is read (`fatal: git fetch-pack: expected shallow list`).
3. Client shallows graft the want walk only when there is NO depth; with a depth the depth governs. Otherwise a routine fetch by a depth-1 clone transfers the whole history.
4. `unshallow <sha>` is emitted only when the commit's PARENTS are transferred, not merely the commit; otherwise the client drops a graft point it still needs. Shallow/unshallow lines are emitted relative to what the client reported (changes only), which is what makes stateless rounds idempotent.

Performance rule (review finding): the cheap commit-level negotiation runs on every round, the expensive object build (negotiation.objects) runs ONCE, after the negotiation is settled (`done` received or a common have acknowledged), and still before any bytes are written so a failure is a clean 500. Building on every round made an 801-commit incremental pull take 1.1 s; after: 348 ms. Residual: the tree walk visits each commit's full tree without a shared seen set, about 3x slower than revlist.Objects on large histories — fine at current sizes.

Not advertised, on purpose: deepen-since, deepen-not, deepen-relative. Consequence: `git fetch --deepen=N` (relative) is refused CLIENT-side ("Server does not support --deepen") before any bytes reach knomit; use absolute `git fetch --depth=N`. `--unshallow` sends an absolute depth of 2147483647 and works.

Misreading: a want-side subtraction of everything reachable from haves WITHOUT the shallow stop set produces a pack missing trees on re-deepen; the stop set is load-bearing.
