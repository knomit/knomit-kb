# knomit's upload-pack packfile BYTES are nondeterministic run to run — the object set is built by ranging over Go maps, so only the framing and the object SET are safe to assert

MEASURED, not inferred: the same fixture store, the same hand-built upload-pack request, three runs in one session returned full-clone packs of 3620, 3622 and 3611 bytes. The DELIVERED OBJECTS were identical every time; only the encoding differed.

Cause: `negotiation.objects` builds the object list with `for h := range n.wantCommits` and `for t := range treeObjs` — both Go maps, whose iteration order is randomised per process. Order decides delta base selection, so it decides pack size and pack bytes.

**The consequence to act on:** never assert on raw upload-pack response bytes, and never compare a pack captured on one commit against a pack captured on another. A test that does is flaky by construction, and a REVIEWER who does will report a phantom regression against a branch that changed nothing. This bit a real review plan (PR #208), whose acceptance criterion "a body byte-identical to the body produced by the same request on dev" could not be satisfied by dev against itself.

What IS stable and worth asserting, verified over three runs: the ref advertisement; the pkt-line framing before the pack (`0008NAK\n` then raw `PACK` for a client that did not request side-band, with NO trailing flush-pkt; a flush-terminated muxed stream when side-band-64k was requested); the shallow-probe and bare-NAK rounds in full; the demuxed band-2 progress lines; and the SET of object hashes and types obtained by decoding the pack into a memory storer. PR #208's own sideband test uses exactly this shape — it compares the sideband and non-sideband responses' unpacked object sets to each other rather than pinning a packfile fixture.

NOT a defect to go fix casually. Sorting the object list would make packs reproducible, but it also changes delta selection for every client, and the object build is the expensive half of the request (see the build-once negotiation rule in the shallow-protocol fact). PR #208 was explicitly told to leave it alone.
