# repoHandler.LastCommitForPath can name a commit that does not hold the file (REPRODUCED after a merge, PR #693 round 3); the suspected cause is go-git's FileName-filtered Log diffing each commit against the NEXT commit in committer-time order, not its real parent

CLAIM (unreproduced). LastCommitForPath (vcs.Repo.LastCommitForPath, internal/engine/store/internal/vcs/branch.go:798 at d73aad37; it was repoHandler's, branch.go:747, before #550) calls go-git Log{From: head, FileName: &path, Order: LogOrderCommitterTime}. It returns the first non-merge commit the filtered iterator yields. In go-git v5.19.2 (plumbing/object/commit_walker_path.go, getNextFileCommit), the 'parent' each commit is diffed against is simply sourceIter.Next(), the next commit in the committer-time walk. It is not that commit's actual parent. The real-parent check (isParentHash) applies only when checkParent is set, which comes from All. So on a history where two lines interleave in time before a merge, a commit can be reported as touching the path because it differs from an UNRELATED neighbour in time order, or skipped because the unrelated neighbour happens to hold the same blob. indexFile (internal/engine/store/index/search_index.go:602 at d73aad37, search_index.go:594 before #557) stamps the result as the fact's SourceCommit.

PREDICTION and FALSIFYING TEST. Build two lines from a common base:
- line A edits kb/x.md at t1 and t3;
- line B edits only kb/y.md at t2 and t4;
- merge them, and sync the merge.
The hypothesis predicts x.md's indexed SourceCommit != `git log -1 --no-merges -- kb/x.md` (the t3 commit). If they match across interleavings, including B committing between A's edits, the hypothesis is false, and this fact should be retracted or downgraded.

CONSEQUENCES if true:
- Replacing LastCommitForPath with the commit_log SQL lookup (factQuery.LastCommitForPath, internal/engine/store/index/search_query.go:224 at d73aad37, search_query.go:205 before #557) is NOT an equivalence-preserving optimization. It answers a different question (the per-commit action log), so it would change SourceCommit rather than fix it.
- The one fast path that is safe either way: when HEAD is a non-merge commit whose parent is the last-indexed commit, every path changed in this sync was last touched by HEAD. That skips the Log entirely and touches no merge semantics. This is the fast path proposed in knomit#357.

Not meant: this does not claim that SourceCommit is wrong today on linear histories, which is the common case, or that any user has hit it. Nor is it the reachability or UI-timestamp question: those read commit_log's first-parent walk, while this one is about how go-git's path-filtered Log chooses the commit it diffs against.

REPRODUCED (PR #693 round 3, 2026-10-30; also at dev 7db596b0): the merge shape. X is written on branch A; B moves on (R changed, Z written); A is merged into B. LastCommitForPath(B, kb/x.md) returned B's last non-merge commit cZ, which does NOT contain kb/x.md. indexFile recorded it as branch_facts(B, x).commit_hash, so HEAD explain (Connections) for X on B was empty. The interleaving mechanism above is the likely cause, but it was not traced inside go-git; what is confirmed is that the result can name a commit that lacks the file.

CONSEQUENCE NOW: indexFile no longer records LastCommitForPath's commit. It records recordedCommit (kb/invariants/store/index/recorded-commit-holds-blob): the path_changes entry live at the tip, and LastCommitForPath only as a fallback, and only if it holds the blob. A replacement of LastCommitForPath for the recorded commit therefore already exists and is NOT the commit_log 'latest row' lookup. Any other caller of LastCommitForPath must still check that the commit holds the blob.
