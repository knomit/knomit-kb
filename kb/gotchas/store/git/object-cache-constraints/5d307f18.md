# An object cache for storegit.Storer (knomit#357) must be PER-Storer (a process-global cache broke TestInitSubscription_ForwardsSidebandProgress, where server and client stores share object hashes), must be invalidated by DeleteObjectForTest (or TestPopulateCommitLog_NoTreeReadsForKnownCommits loses its teeth), and must be bounded like go-git's cache.ObjectLRU

Established 2026-09-30 by a reviewer session's prototype of the cache proposed in knomit#357. The prototype measured internal/synthesize at 276 → 117 s non-race and 1136 → 474 s under -race, with every test passing and 0 DATA RACE. It surfaced three constraints any implementation must keep.

(a) PER-Storer, never process-global. A global cache keyed by object hash broke TestInitSubscription_ForwardsSidebandProgress (internal/store/repo_progress_test.go:17). That test's server and client stores live in one process and hold the same object hashes, so a global cache served the client objects it had never received, and the fetch it is meant to observe did not have to transfer them. Content addressing makes an object's BYTES shareable; it does not make its PRESENCE in a given store shareable.

(b) DeleteObjectForTest (storer.go:233) must evict from the cache too. TestPopulateCommitLog_NoTreeReadsForKnownCommits (commitlog_lazy_payload_test.go:116) deletes tree objects to prove that a re-walk never reads them. With a cache in front, a deleted tree would still be served, and the test would pass whether or not the code reads trees.

(c) Bounded, following go-git's cache.ObjectLRU as the filesystem storer does. Objects are immutable, so no invalidation is needed beyond (b), but an unbounded cache over a whole repository is a memory leak for a long-running server.

Not meant: this does not say the cache is risky or optional. It is the measured fix for the tree-width cost, and these are the three places a naive version silently breaks.
