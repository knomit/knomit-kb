# A store commit's index sync costs O(width of the trees along the changed path) in UNCACHED SQLite object reads, several times per commit: go-git's merkletrie DiffTree calls NumChildren on every same-named sibling (decoding its tree), storegit.Storer.EncodedObject has no object cache, and indexFile runs a FileName-filtered go-git Log (another DiffTree) for EVERY indexed file

Profiled 2026-09-30 at dev 68cc310b on TestStructural_PluralFold (internal/synthesize). 71% of its CPU was go-git DiffTree → Storer.EncodedObject.

The path:
- Every WriteFact reaches notifyCommit → searchIndex.Sync.
- Sync diffs trees about 3 times: DiffFiles; repoHandler.LastCommitForPath called once PER indexed file from indexFile (search_index.go:594); and CommitLogSync.
- go-git's merkletrie diff calls NumChildren on every same-named sibling node, which decodes that sibling's tree object even when its hash is unchanged.
- storegit.Storer.EncodedObject (storer.go:159) is a plain SQLite SELECT. There is no object cache anywhere in internal/store (repoHandler holds only a branch cache).

Consequence: a commit's cost grows with the width of the trees along the changed path, i.e. how many sibling category directories sit beside it. Measured at N≈400–600 writes: 25 ms per write when each fact has its own directory (404 sibling subtrees), vs 6.5 ms per write for flat kb/fN.md. A fixture written one commit per fact is therefore O(N²).

Batching does NOT remove the term. BatchWriteFacts of 404 facts into one commit still spends most of its time in LastCommitForPath: one DiffTree per file, so files × width inside a single sync.

Likely production relevance (inferred, NOT measured in production): writes on a wide ontology, and merge or rebuild syncs touching many files, pay the same cost. triggers_perf_test.go already records write latency rising from about 4.7 ms at 50 facts to 16 ms at 1,000.

Candidate fixes, none implemented:
- (1) indexFile could take the last-touching commit from commit_log. factQuery.LastCommitForPath (search_query.go:205) already reads it from SQL. Or, in an incremental sync of a non-merge HEAD, use HEAD for files in the diff. Either must preserve 'last NON-merge commit' for merge syncs.
- (2) An immutable-object LRU in storegit.Storer. Objects are content-addressed, so nothing needs invalidating.

Not meant: this is not 'go-git is slow'. The cost is the combination of per-file Log calls and an uncached SQL object store.
