# A store commit's index sync costs O(width of the trees along the changed path) in UNCACHED SQLite object reads, paid three times per commit: notifyCommit runs three near-identical DiffTrees of the same HEAD-vs-parent pair (Sync's DiffFiles, indexFile's per-file LastCommitForPath, AppendCommitLog), go-git's merkletrie decodes every same-named sibling tree, and storegit.Storer.EncodedObject has no object cache — tracked as knomit#357

Profiled 2026-09-30 at dev 68cc310b on TestStructural_PluralFold (internal/synthesize), independently by two sessions. Re-read at dev b9cdf382: the cited files are unchanged.

THE PATH, per commit. notifyCommit = searchIndex.Sync + AppendCommitLog, and together they run three near-identical DiffTrees of the SAME HEAD-vs-parent pair:
- Sync's DiffFiles (search_index.go:365);
- indexFile's repoHandler.LastCommitForPath, once PER indexed file (search_index.go:594 → branch.go:747, a FileName-filtered go-git Log, which is one DiffTree per step);
- AppendCommitLog (branch_commit_log.go:108).

In each diff, go-git's merkletrie compare calls NumChildren on every same-named sibling, which decodes that sibling's tree even when its hash is unchanged. storegit.Storer.EncodedObject (storer.go:159) is a plain SQLite SELECT, with no object cache anywhere in internal/store. In the profile, 71% of CPU is DiffTree → EncodedObject, and 81% of samples are flat in runtime.cgocall, i.e. SQLite. The cost is SQLite object reads, NOT filesystem work.

CONSEQUENCE: a commit's cost grows with the width of the trees along the changed path, i.e. how many sibling category directories sit beside it. Measured at N≈400–600: 25 ms per write when each fact has its own directory (404 sibling subtrees) vs 6.5 ms per write flat. A fixture written one commit per fact is O(N²). Batching into one commit does NOT remove the term: LastCommitForPath still runs one DiffTree per file, so files × width inside a single sync. Likely production relevance (inferred, not measured in production): writes on a wide ontology, and merge or rebuild syncs touching many files. triggers_perf_test.go already records write latency rising from 4.7 ms at 50 facts to 16 ms at 1,000.

FIXES, as of knomit#357 (not implemented):
- (1) A per-Storer, bounded object cache. A prototype measured internal/synthesize at 276 → 117 s non-race and 1136 → 474 s under -race; TestStructural_PluralFold under -race went 47 → 12.9 s. All tests passed with 0 DATA RACE. It has hard constraints: see kb/gotchas/store/git/object-cache-constraints/5d307f18.md.
- (2) A fast path in indexFile. When HEAD is a non-merge commit whose parent is the last-indexed commit, every path changed in that sync was last touched by HEAD itself, so no per-file Log is needed.
- NOT a fix: replacing LastCommitForPath with the commit_log SQL lookup (factQuery.LastCommitForPath, search_query.go:205). The two are NOT equivalent: commit_log records per-commit actions, while indexFile wants the last non-merge commit touching the path at this head. See also the merge-misattribution hypothesis, kb/gotchas/store/git/last-commit-for-path/970c2a9d.md.

Not meant: this is not 'go-git is slow'. The cost is three redundant diffs per commit on top of an uncached SQL object store.
