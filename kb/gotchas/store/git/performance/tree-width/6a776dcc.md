# A store commit's index sync costs O(width of the trees along the changed path) in UNCACHED SQLite object reads through Sync's go-git DiffFiles, because merkletrie decodes every same-named sibling tree and storegit.Storer.EncodedObject has no object cache (knomit#357); since c4a41798 indexFile no longer runs LastCommitForPath per file (measured 0 calls on ordinary writes at dev f04bc8d6), it runs only on recordedCommit's fallback

STATE AT dev f04bc8d6 (re-read and measured 2026-10-31). History of this fact: profiled 2026-09-30 at dev 68cc310b on TestStructural_PluralFold (internal/corpus/synthesize), independently by two sessions; re-measured in round 4 of PR #692 (below).

THE PATH, per commit. vcs.Repo.NotifyCommit (internal/engine/store/internal/vcs/branch_commit.go) runs AppendCommitLog FIRST, which records the commit and derives its path_changes rows, and THEN the index sync (index.Index.Sync, internal/engine/store/index/search_index.go). The go-git tree walks on that path at f04bc8d6:
- Sync's incremental step calls vcs.Repo.DiffFiles (internal/engine/store/internal/vcs/branch.go), which is go-git object.DiffTree of last-indexed vs HEAD. Still one per sync. A first sync with no watermark lists every file instead (ListAll) and indexes each.
- indexFile no longer calls LastCommitForPath for every file. Since c4a41798 it calls Index.recordedCommit, which first asks vcs.LiveChange for the path_changes entry live at the tip and takes it when that entry's blob is the file's blob. Only otherwise does it fall back to vcs.Repo.LastCommitForPath (still a FileName-filtered go-git Log, one DiffTree per step, internal/engine/store/internal/vcs/branch.go), and uses that answer only if the commit holds the blob; else the tip.
- AppendCommitLog's payload is no longer a go-git DiffTree: derivation's own diffTrees (internal/engine/store/internal/vcs/path_changes.go) skip entries whose hash and mode match, so they do not decode unchanged siblings.

WHERE THE LastCommitForPath FALLBACK STILL RUNS (verified in the code at f04bc8d6, not inferred). recordedCommit has exactly three callers, all in search_index.go: indexFile (every fact file a Sync indexes, incremental or first full sync), rebuildFacts (every fact path of a Rebuild, computed before its transaction), and repairRecordedCommits (the v8 upgrade drain, every branch_facts row of a drained branch). In each, LastCommitForPath runs only when the path_changes step does not answer: head is ""; LiveChange returns no entry (head has no commit_fp row, i.e. is not derived, or no path_changes row for the path lies on head's first-parent line); LiveChange or the blob lookup errors; or the live entry's blob differs from the blob being recorded. Nothing else in internal/ calls LastCommitForPath at f04bc8d6.

MEASURED at f04bc8d6 (2026-10-31, throwaway test in internal/engine/store with a temporary counter at the top of LastCommitForPath, not committed): 50 single WriteFact calls, one 200-file BatchWriteFacts, 20 modifies, 5 reverts to an earlier blob, 10 writes on a feature branch, a real three-way merge feature->main carrying 10 files, and IndexManager().Rebuild of the branch: ZERO LastCommitForPath calls in every step. Falsified the probe by disabling the path_changes step in recordedCommit: 50, 200, 20, 5, 10, 10 and 521 calls respectively. So the per-file LastCommitForPath cost no longer applies to ordinary writes, batches, merges or rebuilds; the fallback conditions above were not hit by any of them.

WHY sibling width costs: in each go-git diff, merkletrie's compare calls NumChildren on every same-named sibling; go-git's treeNoder.NumChildren calls Children, which decodes that sibling's tree to build a noder per child, even when its hash is unchanged (go-git v5.19.2, plumbing/object/treenoder.go). storegit.Storer.EncodedObject (internal/engine/store/git/storer.go) is a plain SQLite SELECT, with no object cache anywhere in internal/engine/store at f04bc8d6. In the 2026-09-30 profile, 71% of CPU was DiffTree -> EncodedObject and 81% of samples were flat in runtime.cgocall, i.e. SQLite. The cost is SQLite object reads, NOT filesystem work.

CONSEQUENCE at f04bc8d6: a commit's sync cost grows with the width of the trees along the changed path through DiffFiles (one diff per sync), plus one LastCommitForPath walk per file only on the fallback. The 2026-09-30 measurements (N~400-600: 25 ms per write with one directory per fact, 404 sibling subtrees, vs 6.5 ms flat; one-commit-per-fact fixtures O(N^2); a batch still files x width because LastCommitForPath ran per file) were taken when indexFile called LastCommitForPath for every file; the files x width term in a single batch is gone with c4a41798, the width term of the one DiffFiles per sync is not. Not re-measured since. internal/corpus/repos/triggers_perf_test.go recorded write latency rising from 4.7 ms at 50 facts to 16 ms at 1,000 at the time; that number predates c4a41798 too.

FIXES, as of knomit#357 (open at f04bc8d6):
- (1) A per-Storer, bounded object cache. A prototype measured internal/synthesize at 276 -> 117 s non-race and 1136 -> 474 s under -race; TestStructural_PluralFold under -race went 47 -> 12.9 s; all tests passed with 0 DATA RACE (measured before c4a41798). Hard constraints: kb/gotchas/store/git/object-cache-constraints/5d307f18.md.
- (2) The indexFile fast path this fact used to propose (skip the per-file Log when HEAD's parent is the last-indexed commit) is effectively what recordedCommit's path_changes step now does, for every commit that is derived.
- NOT a fix: answering recordedCommit from commit_log actions instead of the blob-checked path_changes entry; commit_log records per-commit actions, not which commit holds this blob after a merge. See kb/gotchas/store/git/last-commit-for-path/970c2a9d.md for LastCommitForPath naming a commit without the file after a merge.

Not meant: this is not 'go-git is slow'. The remaining cost is go-git tree diffs on top of an uncached SQL object store.

MEASURED AGAIN (round 4 of PR #692, closed unmerged; measured on its branch at 5712956d, which does NOT contain c4a41798, seeding ~500,000 facts for the FactSet worst-case matrix): with every result's 499 facts in one directory and 25 such directories per group, LastCommitForPath was 56% of the seed's CPU and a 499-file batch took ~10 s at ~100 results and kept growing. The cost per file was the merkletrie diff's NumChildren decoding EVERY sibling subtree along the path, so it scaled with the total entries of the siblings at each level, not with the number of changed files. Spreading the same facts over directories of 50 (and results over groups of 25) brought a batch to ~3 s with mild growth. At f04bc8d6 that per-file LastCommitForPath term does not run on such a seed (see MEASURED at f04bc8d6), so do NOT cite the 56% figure as dev's profile; keeping directories narrow still helps the one DiffFiles per sync, by an amount not measured on dev.
