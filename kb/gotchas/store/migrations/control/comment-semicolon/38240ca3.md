# A semicolon anywhere in a control up-migration's SQL COMMENT fails TestControl_UpMigrationsAreIdempotentDDL — it splits the file on ";" BEFORE stripping comments, so the tail of a commented sentence becomes a bare "statement"

Discovered 2026-09-16 writing `000004_session_bindings.up.sql` (the session-bound MCP mount).

TestControl_UpMigrationsAreIdempotentDDL in `internal/store/migrate/control_test.go` enforces that every control up-migration is replayable DDL. Its check is:

    for _, stmt := range strings.Split(string(body), ";") {
        s := strings.TrimSpace(stripSQLComments(stmt))
        if s == "" { continue }
        require.Regexp(t, `(?i)^CREATE (TABLE|UNIQUE INDEX|INDEX) IF NOT EXISTS `, s, ...)
    }

Both components matter and the ORDER of the two is the trap: the split on ";" happens FIRST, and `stripSQLComments` — which removes everything from "--" to end of LINE — runs on each resulting chunk SECOND. So a semicolon inside a `--` comment line splits that line in half. The first half keeps its "--" and strips to empty (skipped); the second half begins mid-sentence with NO leading "--", survives stripping as ordinary text, and fails the CREATE regex.

Concretely, this comment line:

    -- and must never gate anything; this one is client-asserted ROUTING state

produced the failure `Expect "this one is client-asserted ROUTING state" to match ^CREATE (TABLE|UNIQUE INDEX|INDEX) IF NOT EXISTS`. The migration SQL itself was already valid idempotent DDL — only the prose was at fault.

OPERATIONAL CONSEQUENCE: when writing a control migration header comment, punctuate with commas, em dashes, or full stops and colons — never a semicolon. These files carry long rationale comments by convention (000003_client_sessions.up.sql has a seven-line header), so the constraint bites prose far more often than SQL.

WHAT THIS DOES NOT MEAN: it is NOT a rule that migrations may hold only one statement, and it is NOT about SQL string literals (no control migration has one today, but a ";" inside a quoted literal would break the same naive split for the same reason — the splitter is not a SQL parser). It also does not mean the migration would fail to APPLY: the semicolon version migrates a database perfectly well, and sqlite never sees the comment. The failure is entirely in the test's lexer, which is why it surfaces as a confusing assertion about a fragment of your own prose rather than as a SQL error.
