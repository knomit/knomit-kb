# New commit_log columns must go in 000001 (Core/v1), not a later ALTER migration

Any new column on the commit_log table must be added directly to 000001_schema.up.sql (the base/v1 schema), NOT as a separate ALTER migration — even though ALTER is the pattern used for other tables (e.g. facts.kind in 000006).

WHY: migrate.Core only migrates to version 1, and it is the bootstrap used by storegit.NewMemoryStorer (the git package's own in-memory Storer). The git package OWNS commit_log writes (CommitLogSync's INSERT lists the full column set). If a commit_log column lived only at version >1, a Core-bootstrapped Storer's commit_log would lack it and CommitLogSync would fail with 'no such column'. So commit_log's complete write schema must exist at v1. This is exactly why author_email (and now author_name) sit in 000001 rather than in an ALTER migration. Confirmed: author_email is in 000001 with no ALTER; facts.kind (a non-commit_log column) was added via ALTER 000006.

CONSEQUENCE for existing on-disk DBs: editing 000001 in place is silently ignored by golang-migrate for DBs already past v1 (it tracks only the version integer, no checksum re-validation). So adding a commit_log column does NOT reach existing persistent caches (e.g. ~/.knomit/repos/*.db); their next CommitLogSync INSERT breaks until the DB file is deleted and rebuilt from git. This is acceptable under the 'git is the only source of truth; the DB is a rebuildable cache' principle, but it means a column addition requires recreating existing cache DBs, not just restarting. Note `:rebuild` alone does NOT fix it (it re-walks git into the existing table); the .db must be removed so migrate.All recreates the schema fresh.
