# With plain JOINs SQLite drove vec0 KNN reads from facts/branch_facts and re-ran the whole KNN per row: each indexed write cost (facts rows) x ~4 ms on Windows, a 501-fact commit took 9 min 12 s (5.9 s pinned), and the plan flipped with planner statistics, so text search took 10 ms or 1.2 s on the same data

Measured on the Windows 10 dev host, 2026-11-02, while root-causing #725 (TestLensQuery_EpSelectsBeforeTheWindow timing the Windows web step out after 10 min).

Plan: `SELECT ... FROM facts_vec fv JOIN facts f ON f.id = fv.rowid WHERE fv.embedding MATCH ? AND fv.k = ?` planned as `SCAN f USING COVERING INDEX sqlite_autoindex_facts_1 | SCAN fv VIRTUAL TABLE INDEX 0:3{___}___`: the vec0 KNN inner, re-run once per facts row. One vec0 KNN cost about 4 ms here whatever the row count (4.1 ms at 21 vectors, about 4.3 ms averaged to 501), so graphBuildSimilarityEdges, which runs for every indexed fact version, made each write cost (facts rows, all versions and branches) x 4 ms, and a batch of n facts quadratic: cumulative KNN time 5.6 s / 22.4 s / 50 s / 88 s after 50/100/150/200 facts, 9 min 2.6 s of the 9 min 12 s 501-fact commit; the CPU profile was 99% sqlite3_step under graphBuildSimilarityEdges. With `facts_vec fv CROSS JOIN facts f` the same commit took 5.7-5.9 s and the test 7-10 s (566 s before). Linux and macOS CI ran the same test in 47 s and 74 s: inferred the same plan with a cheaper per-KNN cost.

Why it was intermittent: the plain-JOIN plan depends on sqlite_stat1. On a fresh store with no statistics or a fresh ANALYZE the similarity read was vec0-outer; with statistics still describing a one-fact store (what PRAGMA optimize leaves before a large batch lands, dumped from the #725 store: facts indexes '1 1' / '1 1 1', branch_facts '1 1' / '1 1 1') it flipped to facts-outer. The search reads (facts_vec JOIN facts JOIN branch_facts) went `SCAN bf` outer with no statistics. Observed consequence: the lens text query of that test took 8-13 ms in some runs and 1.1-1.2 s in others, same binary, same data; with CROSS JOINs it took 9-10 ms. That attribution of the flip to statistics is inferred from the planted-statistics plans, not traced per run.

Consequence: an EXPLAIN on a fresh test store can show a good plan for a query that production runs badly; check plans under stale and fresh statistics (TestVecKNN_JoinOrderKeepsVec0Outer plants them). The cost of a bad vec0 plan also scales with the platform's per-KNN cost, so Windows exposes it first: a slow Windows test that writes many facts with a real embedder is a reason to look at plans, not at the timeout.

Not measured: the cost on a large production store or of rebuildGraph (same SQL, so the same plan exposure is inferred). The rule that came out of it is the invariant under kb/invariants/store/index/vec0-knn-join-order/.

After the fix (review of PR #730): CROSS JOIN pins only the outer loop. Under the same stale one-fact statistics the pinned plans keep vec0 outer but their inner lookups become full SCANs (`SCAN f USING COVERING INDEX sqlite_autoindex_facts_1`, `SCAN bf`, `SCAN bf2`), about k x (|facts| + |branch_facts|) row visits per read; tracked as #731.

Resolution of the residual (#731, measured on darwin/arm64 with the stub embedder; Windows and Linux not measured): the stale one-fact statistics come from the first Sync's PRAGMA optimize, and because creating sqlite_stat1 is DDL they are broadcast to EVERY pooled connection. Later ANALYZE/optimize runs reload statistics only on the connection that ran them (no schema cookie change), so reader connections stayed stale until restart. Stale statistics cost the graph write statements more than the five vec0 reads: in the natural one-fact stale state graphMergeEdge fell back to SCAN edges (graphNodeIDByProps walked node_labels, by label=? or a full scan, only when node_labels' statistics ALONE were stale, per the RCA), taking 1 fact + 2000 in one BatchWriteFacts from ~5 s to ~9 s, of which the five reads' share was ~0.6 s; on a stale 8k-fact store a vec0 read cost +25% to +52%. Fix: Sync refreshes statistics at 1, 2, 4, 8, ... facts indexed and bumps the schema cookie when sqlite_stat1 changed (the same batch: ~4.7 s); see kb/invariants/store/index/planner-statistics/71d4caa1.md. Also: a test that plants statistics and EXPLAINs through the *sql.DB sees them only because database/sql reuses the most recently used connection; hold every pooled *sql.Conn.
