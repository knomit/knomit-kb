# checkOwnLineage judges origin's agent TIP even when that tip is already reachable from origin's main: walkHistory checks the stop set only for parents, never for its start commit, so a fully merged but unsigned agent tip still fails E4 at clone time

A defect in the E4 design described by kb/decisions/store/verify/first-contact/dbecb0e6 ('every commit beyond origin's main'). internal/store/verify_walk.go walkHistory(start, stop, visit) pushes the start commit unconditionally and consults `stop` only when descending to parents. checkOwnLineage (verify_e4.go) calls it with start = origin's agent-branch tip and stop = everything reachable from origin's main. When the agent tip is itself in main's history (a forge fast-forward merge of agent/<host> into main, the agent branch left in place), the tip is still visited and judged; if it is not own-signed or accepted — e.g. a clone's own init commit, unsigned by design — InitFromRemote fails with 'origin's agent/... holds 1 commit(s) not signed by this instance, beyond origin's main', which is false ('beyond' does not hold).

Observed 2026-10-03 while fixing TestRemote_PushWithConcurrentRemoteUpdate on the lifecycle-machine branch: after MergeIntoMain left main == agent/test == the unsigned init commit, B's clone still refused. The test now deletes the merged branch instead. Not fixed (store was out of that PR's scope); the likely fix is to return early when stop[start] is true. Consequence until fixed: re-cloning an instance whose unsigned init commit was fast-forward-merged into main, with the agent branch kept on the forge, is refused; 'knomit verify accept <sha>' or deleting the merged agent branch on the forge works around it.
