# The history upgrade (path_changes derivation on an upgraded DB or a pathChangesVersion change) assumes ONE process on the database while it opens — a second process writing the same DB during the open is unsupported; migrate a copy and move it back

WHAT: openHistory runs while a repo opens or is bootstrapped (OpenRepo, InitRepo, InitFromRemote, InitSubscription, and Replay's clone target), BEFORE the repo serves a request or accepts a write. It reads git and prepares every commit's rows first, then writes them and the version key in ONE SQL-only transaction. On a failure it rolls back and the open fails (the next open retries). User decision, #347 round 6: kb/decisions/mcp/explain/history-enumeration.

THE LIMIT: nothing inside one process can write while it opens, so the pass takes no care over concurrent writers. A SECOND PROCESS writing the same repo database meanwhile is OUT OF SCOPE (user ruling). Such a process could advance a branch after the pass read its tip. The branch's new commits would then be underived until something derives them, and a reset pass could delete rows that process wrote between the prepare and the transaction.

WHAT TO DO: if a database must be migrated while something else may hold it, migrate a COPY (open it once with a single process), then move it back. The user expects to migrate once.

CONSEQUENCES:
- A long open is expected on the first start after an upgrade: 1 s to 3 s on the live knomit-kb and agentic-engineering copies. It is one transaction, so a crash leaves the old state and the next open redoes it.
- Do NOT add batching or a background pass to shorten it. Batching existed only for writer fairness, and the single transaction is what makes a failure leave nothing half-derived.
- The pass also clears commit_log_stage, since rows there belong to a rebuild that died before its swap. That is safe only because no rebuild can be running in this process during open.

NAMED MISREADING: 'open-time means single-threaded, so any open-time work may skip transactions'. The pass's atomicity is still what keeps a failed upgrade from serving a half-derived history (TestOpenHistory_FailedPassKeepsRepoClosed).
