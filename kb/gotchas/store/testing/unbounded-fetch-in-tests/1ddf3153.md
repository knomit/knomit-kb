# store.Open leaves netTimeout at 0 = NO deadline — a test that waits on a failing fetch is timing out on the host's resolver, not on knomit

`netCtxWith` treats `timeout <= 0` as "return the parent context unchanged" — the legacy hang-forever behaviour — and `store.Open` does NOT set `netTimeout`. Only `SetNetworkTimeout`, called by the repos builder from config, bounds anything.

So a test that opens a bare Service and lets a fetch fail against an unreachable URL has an UNBOUNDED fetch. Its duration is whatever the host's DNS/TCP stack takes to give up, which is not a property of the code under test. `TestSync_FetchHoldsConfigReadLock` waited 5s for Sync to resume: ~0.3s on a dev machine, over budget on a GitHub ubuntu runner whose resolver does not fail `.invalid` fast, and the job went red for a reason unrelated to its assertion.

**Consequence for a consumer:** any store test whose timing depends on a network call failing must call `SetNetworkTimeout` explicitly. Verified by pointing the remote at a blackholed IP: without the timeout the test reproduces the CI failure exactly (same message, 5.22s); with a 250ms timeout it passes in 0.79s.

**What this does NOT mean:** production is not unbounded — the builder always wires the configured timeout. The gap is specific to a Service built directly by `store.Open`, which in practice means tests.
