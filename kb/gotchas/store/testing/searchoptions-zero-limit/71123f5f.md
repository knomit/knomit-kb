# `store.SearchOptions{}` has Limit 0, which becomes a literal `LIMIT 0` — so any test asserting "X is absent from RecentFacts" with a bare options struct passes vacuously

`RecentFacts` (and the other `SearchOptions`-taking queries) pass `opts.Limit` STRAIGHT into the SQL — `queryArgs := append(..., opts.Limit, opts.Offset)` feeding `LIMIT ? OFFSET ?` in `internal/store/search_query.go`. There is no floor, no default, no "0 means unlimited" convention. So a zero-valued `store.SearchOptions{}` produces a literal `LIMIT 0` and returns **zero rows unconditionally**, whatever the index actually holds.

**Why this is a trap and not just an API wart.** The failure is silent and it is asymmetric. A test asserting something IS present fails loudly and you fix it in seconds. A test asserting something is ABSENT — the shape you reach for when checking that a non-fact file stayed out of the fact index — passes for the wrong reason and keeps passing forever. It reads as evidence and is not.

This was found live: a test written to prove `LICENSE` never enters the fact index used `RecentFacts(ctx, branch, store.SearchOptions{})` and would have passed identically if `LICENSE` had been indexed on every write.

**What to do.** Two things, together — the first alone is not enough:
1. Set an explicit `Limit` (e.g. `SearchOptions{Limit: 50}`).
2. Add a POSITIVE CONTROL in the same test: write a genuine `kb/`-rooted fact and assert it IS returned, alongside asserting the thing under test is not. Without it the test still cannot distinguish "correctly excluded" from "this query returns nothing here regardless" — a filter typo, a wrong branch, or an unsynced index all reproduce the vacuum.

**Scope check performed:** at the time of writing, no other call site in the repo passes a bare `SearchOptions{}` to `RecentFacts`, so the known blast radius was that single test. That is a snapshot, not a guarantee — the constructor still makes the bug easy to reintroduce.

**What this does NOT mean.** It is not a claim that `Limit` should default to unlimited; a hard cap on a recency query is a reasonable API. The defect is entirely in tests that omit it and then assert on emptiness.
