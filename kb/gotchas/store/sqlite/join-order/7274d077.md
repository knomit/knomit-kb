# SQLite drove the due sweep's `fact_expires JOIN branch_facts` from branch_facts by branch_id — linear in the LIVE facts on every run, ~0.5 ms per 10,000 with nothing due, ANALYZE or not — so DueCandidates uses `fact_expires fe CROSS JOIN branch_facts bf` (SQLite honours the written order for CROSS JOIN) to pin the covering-index range on expires_at: an idle sweep is then 7–15 µs and the cost is linear in the past-dated rows only

Measured while adding BenchmarkDueCandidates (F07 PR 2, branch feat/f07-due). The proposal's probe measured `SEARCH fe USING COVERING INDEX fact_expires_at (expires_at<?) | SEARCH bf USING INDEX branch_facts_fact (fact_id=?)` and quoted 5–11 µs with nothing due. The shipped query, written as a plain `JOIN` with `bf.branch_id = ?` (bound literal or a `(SELECT id FROM branches WHERE name = ?)` subquery, no difference), planned as `SEARCH bf USING INDEX sqlite_autoindex_branch_facts_1 (branch_id=?) | SEARCH fe USING INTEGER PRIMARY KEY (rowid=?)` — with and without ANALYZE — i.e. it walked every live fact of the branch and probed fact_expires per row: 0.46–0.77 ms at 10,000 live facts with ZERO due rows, and that cost would be paid on every dispatcher run (every write, every tick) once a `due` trigger exists.

The fix is the join order: `FROM fact_expires fe CROSS JOIN branch_facts bf ON bf.fact_id = fe.fact_id WHERE fe.expires_at <= ? AND bf.branch_id = ?`. SQLite's planner treats CROSS JOIN as an explicit order constraint (left table outer), so the query is driven by the covering index fact_expires_at and probes branch_facts_fact per PAST-DATED row. Measured after (20 iterations, Apple M-series, rows inserted directly, ANALYZE): live 1,000/due 0: 15 µs; 1,000/500: 0.53 ms; 10,000/0: 6.6 µs; 10,000/100: 56 µs; 10,000/5,000: 7.1 ms; 50,000/500: 0.24 ms — linear in the due rows, independent of the live count, as designed. The ORDER BY bf.path costs a temp b-tree over the candidate rows only.

Consequence for anyone writing a query that must be cheap when its selective predicate is on the SMALLER side of a join: check EXPLAIN QUERY PLAN with realistic row counts, and do not trust ANALYZE to pick the selective index when the other side has an equality on a low-cardinality column (one branch id covers every live fact). In SQLite the join order IS the cost model, and CROSS JOIN is the sanctioned way to state it.
