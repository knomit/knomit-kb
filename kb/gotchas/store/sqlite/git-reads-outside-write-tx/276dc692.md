# go-git object reads go through the raw *sql.DB pool, never the ctx transaction: a git read inside an open write tx needs a SECOND connection, and an in-memory store has only one

The git object storer (internal/engine/store/git/storer.go) reads objects with s.conn(), which returns the raw pool s.db, not the transaction in ctx. So ReadBlobHashAtCommit, CommitObject and ancestry walks each take a pool connection of their own, even when the caller holds a write transaction.

- Store.Open (service.go) uses SetMaxOpenConns(1) for an in-memory DB: a git read inside an open tx there waits for a connection that never frees.
- On a file DB (pool of 4, _txlock=immediate) it works, but it holds the process-wide write lock across the git I/O.

OPERATIONAL CONSEQUENCE: do every git read BEFORE opening a write transaction, and keep the transaction to SQL. applyBlobRefs (index/derived_from.go) follows this: the introducing commit, the claim's order and the targets are resolved first, then the claim is re-checked and written with the edges in one tx.

WHAT THIS DOES NOT MEAN: SQL reads through conn(ctx, db) inside the tx are fine; they use the transaction. The rebuildGraph comment that git reads 'touch no DB connection' is inaccurate on this point.
