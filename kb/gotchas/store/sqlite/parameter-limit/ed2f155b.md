# SQLite caps bound parameters per statement (32,766 here, 999 on older builds) — a query with one placeholder per fact id breaks on whole-corpus operations, and in a review pipeline it breaks SOFT

SQLite enforces `SQLITE_MAX_VARIABLE_NUMBER` per statement — **32,766 on this build, 999 on older ones**. Any query that builds one `?` per fact id works on every test fixture and breaks on a real corpus.

**Why it is worse than a normal limit.** In the review pipeline the failure is SOFT. The step does not crash; it degrades to "nothing found" plus a health line. Unchunked, the shortlist would simply stop working somewhere past ~16k facts and would say so only in a line nobody reads. A hard error would have been kinder.

**The remedy.** `chunkIDs` splits id lists at `sqlIDChunk = 400`, deliberately well under even the 999 historical cap, and every id-list query in the abstraction index goes through it.

**The rule.** MEASURE the limit on the build you ship, do not assume it. The two values differ by 33x and the small one is the one that will be in production somewhere.

**The named misreading.** This is not "keep queries small for performance". Chunking here is a CORRECTNESS requirement — the unchunked query does not run slowly, it fails, and in this pipeline it fails quietly.
