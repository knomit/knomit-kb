# A read-only sweep that opens a knomit index database with `mode=ro&immutable=1` ignores the -wal file, so it can read a stale snapshot missing the newest commits — copy the .db AND its -wal to scratch and read the copy

Each mounted knomit repo has a per-repo SQLite index database (under the repos directory of the knomit home) in WAL mode. Recent commits live first in the -wal sidecar and reach the main .db file only at a checkpoint. A URI of the form `file:<db>?mode=ro&immutable=1` tells SQLite the file cannot change, so it skips locking and does not consult the -wal file: the reader sees only what was last checkpointed into the .db. The corpus-hygiene curator for step 14c hit this on 2026-10-25 (a read-only sweep read a stale index snapshot).

CONSEQUENCE: for a read-only sweep of the corpus (listing fact paths, blob hashes, entities, refs, branch_facts), do not use immutable=1 on the live files. Copy the .db and its -wal (and -shm if present) into scratch together, open the COPY normally, and confirm it contains your newest commit (for example compare a recently written fact's branch_facts.commit_hash) before trusting any count. Fact bodies can be read from the copy too: facts.blob_hash joins to objects.hash, whose data column holds the raw fact file.

WHAT THIS DOES NOT MEAN: it does not say a plain `mode=ro` open is unsafe or wrong; a read-only open without immutable=1 does read the WAL (and may create -wal/-shm sidecars when no server is running, see the readonly-wal-sidecars gotcha). It does not say the index is the source of truth either: the fact files in git are, and the index is derived state. And a stale-looking immutable read is not always reproducible: when the WAL has just been checkpointed, an immutable read and a normal read agree, so a clean result from immutable=1 proves nothing about a later run.
