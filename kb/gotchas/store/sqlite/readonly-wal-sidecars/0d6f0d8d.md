# With no server running, a read-only read of a WAL-mode control.db (`knomit identity show`) leaves control.db-wal and control.db-shm behind; run as another user against someone else's home they make the server's writes fail with 'attempt to write a readonly database' — accepted, because the knomit home is per-user

Conditions (all required): control.db is in WAL mode (the server's normal state), NO server currently holds it open, and something opens it read-only (mode=ro), e.g. repos.StoredAgentID via `knomit identity show`. A read-only WAL reader must create the shared-memory index, and it cannot checkpoint, so on close it does NOT remove them: measured before `[control.db]`, after `[control.db control.db-shm control.db-wal]` (-shm 32 KiB, -wal 0 B). The earlier read-write opener created the same files but removed them on last close.

While a server IS running the sidecars already exist and belong to it: the read-only read creates nothing, does not block on a server's open write transaction (returns the committed value), and does not stop the server's last-close cleanup.

CONSEQUENCE: if the command is run as a DIFFERENT OS USER against another user's home (for example root or a shared account pointed at someone's knomit home), the leftover -wal/-shm are owned by that user, and the real owner's server then fails its writes with `attempt to write a readonly database`. Remedy: delete the stray control.db-wal and control.db-shm while no server is running.

DECISION: accepted, no code change in PR #515. The knomit home is per-user, so cross-user access to a home is not a supported path; `immutable=1` was rejected as unsafe while a server runs, and deleting sidecars after the read risks racing a starting server.

WHAT THIS DOES NOT MEAN: it is not corruption and not data loss; the db content is intact. It does not happen for the same user, where the server reopens the files normally.
