# FIXED (PR #637, issue #587): EnsureLocalUpstream checks ctx right after LockBranch and completes a half-written upstream (ref present, branches row missing or tip not in branch_commits) at the ref's own hash, never moving it

STATUS: FIXED by PR #637 (issue #587, https://github.com/knomit/knomit/issues/587); merge commit 91c5d29e. Originally found in PR #586, which left it out of scope.

THE ORIGINAL DEFECT. remotesync.Index.EnsureLocalUpstream (internal/engine/store/remotesync/local_reconcile.go) takes LockBranch(upstream) (no ctx parameter; the wait cannot be abandoned) and then ran with no ctx.Err() check. A caller cancelled while parked behind an index Rebuild (the Sync life at Unmount) got the lock with a dead ctx, SetReference of refs/heads/<upstream> succeeded, and EnsureBranch / PopulateCommitLog failed on the cancelled ctx: the ref existed without its branches row, commit_log or notify. A later call saw the ref and returned (false, nil), so the half-state was permanent.

WHAT CHANGED.
1. ctx.Err() is checked once the lock is held, before any read or write; a cancelled caller returns a wrapped context.Canceled with nothing written.
2. The existence check is no longer "ref present -> (false, nil)": it asks vcs.Repo.CommitRecorded(upstream, refHash) and, when that is false, runs the SQL half (recordLocalUpstream: EnsureBranch, then PopulateCommitLog or RepopulateBranch, then NotifyCommit) at the ref's own hash and returns (true, nil). The ref is never moved on that path; advancing stays reconcileMain's decision.
3. FOLLOW-UP in the same PR (commit 9b3ff233, branch commit; the merge is 91c5d29e). With a branches row present the repair runs RepopulateBranch (drops branch_commits rows not reachable from the ref, adds missing ones, one swap, same step AdvanceBranchTo runs after a force-update); with no row it runs the batched PopulateCommitLog. So it also completes a torn reconcileMain create / fast-forward / force-update and a torn AdvanceLocalUpstream fast-forward, beyond #587. Test: TestEnsureLocalUpstream_CompletesATornForceUpdate (Verify flags commit-log issues on main before the repair, none after; the stale tip row is gone). The create path's SQL after SetReference runs under context.WithoutCancel (AdvanceBranchTo's rule once a ref has moved), so a cancel cannot tear it; the repair path moves no ref and keeps the caller's ctx, since a cancelled repair is simply repaired by the next call (CommitLogApply is one transaction).

WHY BOTH. The ctx check alone closes only the cancel-while-parked path. The ref is written before its SQL bookkeeping and SetReference cannot be undone, so any later failure (EnsureBranch, PopulateCommitLog, a killed process) left the permanent half-state. The self-heal makes the sequence safe to retry; the ctx check makes the common Unmount case write nothing at all.

WHY NOT REORDER (EnsureBranch before SetReference, as AdvanceLocalUpstream does). PopulateCommitLog walks from the ref, so it must run after SetReference whatever the order; reordering only moves the window.

WHAT THIS DOES NOT MEAN. The repair checks the branches row and the tip's branch_commits row only. It does NOT detect an index (branch_facts / facts_vec) left stale by a failed im.Sync inside NotifyCommit after AppendCommitLog succeeded; that is the index heal's job (healIndexBranches / the Index stage, initial-upstream-index-sync). Nor does it ever move the ref to origin/<upstream>. And a true return no longer means "bootstrapped from origin": the caller (internal/corpus/repos/stages.go) logs "local upstream created or completed".

OPEN NOTE (optional, from review of 9b3ff233; not done). On the repair path with a row present but branch_commits empty on a long history, RepopulateBranch inserts the whole history in one write transaction, where PopulateCommitLog would use PathChangeBatch batches. Reviewer's optional refinement: run PopulateCommitLog first (batched inserts), then RepopulateBranch, which would then only drop rows, to avoid one large swap. Needs a crash or SQL error to reach that case now that the create path cannot be torn by a cancel. Not blocking; AdvanceBranchTo's rewind and RebuildCommitLog already make swaps of this size.

Tests: internal/engine/store/local_reconcile_halfwrite_test.go: TestEnsureLocalUpstream_CancelledWhileParkedOnTheLockWritesNothing (holds the lock, waits until the call is visibly parked via runtime.Stack, cancels, releases; asserts no ref and no row, then a live call bootstraps fully), TestEnsureLocalUpstream_CompletesAHalfWrittenUpstream (ref without row; ref+row without commit_log; origin/main moved elsewhere to prove the ref is not moved), TestEnsureLocalUpstream_CompletesATornForceUpdate. Each fix was sabotaged once and its test went red.
