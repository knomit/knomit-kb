# FIXED in #698 (dev 56e8389c): the first-parent history readers (ResolveActiveCommitForPath, RevisionsBefore, FactLiveAtCommit) were O(whole first-parent history) per call because their recursive CTE ended in ORDER BY fpc.depth LIMIT n; they now share vcs.LineEvents over commit_fp jump pointers, with a bounded commit_parents walk as the fallback

STATUS: FIXED at dev 56e8389c (PR #698). This note records what the problem was, so the same mistake is not made again.

THE PROBLEM (dev up to f04bc8d6, and 8a2d79d0): ResolveActiveCommitForPath, HistoryQuery.RevisionsBefore and FactQuery.FactLiveAtCommit each ran FirstParentChainCTE (a recursive walk over commit_parents, parent_order 0) JOINed to commit_log, ending in ORDER BY fpc.depth LIMIT n. SQLite's recursion stops early under a bare LIMIT, but with an ORDER BY it must produce and sort the whole join first. So every call walked the entire first-parent chain, and the cost grew with history length, not with how far back the path was last written. Measured on knomit-kb (depth 893), the resolver took about 650 µs per call from the tip.

WHAT #692 TRIED: #692 (closed unmerged) stopped the recursion at the first commit that wrote the path. That gives the same answer, but costs O(depth to that writer), which for a long-stable fact is still most of the history. Measured, it was 0.5x-1.3x the old cost, slower on a 252k-path synthetic store. Its RevisionsBefore sibling, 927f7366, measured the same.

THE FIX (internal/engine/store/internal/vcs/revisions_before.go, LineEvents):
- All three readers call vcs.LineEvents(from, LineQuery{Path, Writes, BranchID, Limit}).
- It reads the path's own commit_log rows, nearest first by commit_fp depth, in keyset pages of 16. Each row is checked for 'on from's first-parent line' by jumping with the commit_fp jump pointers, O(log depth) statements per candidate, using a CHECKED jump.
- The cost grows with the path's own events, not with history length. Measured: 4.5x-12.5x faster than the old query from the tip and 3.3x-6.7x from random commits, on knomit-kb, knomit core and the synthetic store, with 0 mismatches.
- All statements of one call run in ONE read transaction: the caller's, otherwise a deferred BEGIN on one pooled connection.

FALLBACKS to a bounded commit_parents walk (LineWalkCTE, which stops at the limit-th hit):
- from has no commit_fp row;
- from has commit_fp.degraded = 2 AND fewer rows than the limit were found above the boundary;
- a jump contradicts the rows: a node's depth is not its distance from from, or it has no pointer for the next jump.

WHAT IT DEPENDS ON: every commit_fp row's depth and pointers must agree with its first-parent ancestors' rows. deriver.wouldCutDerivedLine keeps that true under re-derivation (see kb/invariants/store/path-changes/content-addressed/11606a61.md).

CONSEQUENCE, still general: a recursive CTE whose outer query has ORDER BY ... LIMIT does NOT short-circuit. To stop early, stop expanding inside the recursive member, as LineWalkCTE's `WHERE walk.hits < ?3` does, or avoid the walk altogether.

DOES NOT MEAN:
- commit_parents is obsolete. The fallback walk and fsck's full-DAG check still read it.
- LiveRevision uses LineEvents. It reads path_changes through vcs.LiveChange, which has no guard and no walk fallback and relies on the re-derivation rule alone.
