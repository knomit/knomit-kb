# OPEN: vcs.Repo.ResolveActiveCommitForPath is O(whole first-parent history) on EVERY call at dev f04bc8d6: its recursive CTE ends in ORDER BY fpc.depth LIMIT 1, and the ORDER BY makes SQLite produce the entire chain join before the LIMIT; a fix is being ported in a separate PR and has NOT landed

STATUS: OPEN at dev f04bc8d6. A fix was written on PR #692 (round 4), which closed unmerged, so it never reached dev. It is being ported in a separate PR; until that PR merges, treat the cost below as current. Do not describe it as fixed.

THE CODE at f04bc8d6 (internal/engine/store/internal/vcs/revisions_before.go): ResolveActiveCommitForPath runs FirstParentChainCTE (WITH RECURSIVE fpc over commit_parents, parent_order 0, from fromCommit) JOINed to commit_log on commit_hash, WHERE cl.path = ? AND cl.action IN ('added','modified'), ORDER BY fpc.depth ASC LIMIT 1. Its doc comment claims SQLite's pull-based recursion stops once LIMIT 1 is satisfied. That holds only WITHOUT an ORDER BY: with it, SQLite must produce every row of the join to sort them, so every call walks the whole first-parent chain from fromCommit back to the root. Cost grows with the repository's history length, not with how far back the path was last written.

HOW IT WAS FOUND (CPU profile on the PR #692 branch, on a backup of knomit-kb): the first page of a 500-result FactSet spent 170-200 ms of ~620 ms in this function, about 0.4 ms per call, called once per fact through GraphStore.OutgoingAtCommit. That specific FactSet caller is gone at dev: since PR #696 the materialize planner reads ref_edges through index.LevelReader and never calls OutgoingAtCommit. The function itself is unchanged and is still called at f04bc8d6 by GraphStore OutgoingAtCommit/IncomingAtCommit (search_graph_query.go), by Index.resolveTargetCommit once per ref edge a write resolves (derived_from.go), by facts' fallback-before read (fact_read.go) and by FactQuery (search_query.go). The 0.4 ms figure was measured on one repo's history; it is not a constant.

CONSEQUENCE: a recursive CTE whose outer query has ORDER BY ... LIMIT does NOT short-circuit. To stop a recursion early, stop expanding inside the recursive member (a condition on the recursive SELECT), e.g. carry an EXISTS on commit_log by its (commit_hash, path) key and expand no further from a row that wrote the path; the first such row has the smallest depth, so the answer is the same. Any such change needs an equivalence test against the ORDER BY form over a history with a modify, a delete, a re-add and a real merge.

DOES NOT MEAN: the other FirstParentChainCTE users (RevisionsBefore, FactLiveAtCommit) were profiled; they were not. Nor that writes are otherwise cheap: see kb/gotchas/store/git/performance/tree-width/6a776dcc.md for the tree-width cost of a store commit's index sync.
