# go-git v5.19.2: TreeWalker.Next turns a failed GetTree on a mode-040000 entry into io.EOF, so tree.Files(), NewTreeWalker and object.DiffTree END SILENTLY at a Dir entry that names a blob or a missing object, dropping that entry and the rest of its level; FindEntry, TreeEntryFile and GetTree do return errors

Structural claim about the dependency, pinned to go-git v5.19.2 (the module version in go.mod at 3ac59b57); the line numbers (plumbing/object/tree.go, the Dir branch of TreeWalker.Next, about lines 543-552) are dated support only. Re-verify when go-git is bumped.

THE BEHAVIOUR. When TreeWalker.Next meets an entry of mode 040000 and GetTree on its hash fails, it sets err = io.EOF and returns. The cause can be a blob, a missing object or an undecodable tree. The caller sees a normal end of the walk: the entry and everything after it in the walk are never seen, and no error is reported. Everything built on that walker ends there too: tree.Files() (FileIter), NewTreeWalker, and object.DiffTree, whose treenoder.transformChildren lists children with a non-recursive TreeWalker, so the rest of THAT LEVEL is dropped (a bogus entry that sorts first, such as kb/-, hides dot paths and siblings after it at its level; it did not hide a root .knomit/ change because the bogus entry was in another directory). Observed: DiffTree returned 1 change with err nil where two entries were missing.

CONSEQUENCE. Never judge, load or diff an untrusted tree with these walkers before store.checkTreeShape has passed it. A gate built on them judges a prefix of the tree: it admitted an unsigned merge that added content after the bogus entry, and hid other members' records from the loader. Also: a go-git push client walks the same way, so it omits the objects of such a tree and cannot send it (the host answers 'incomplete'); decoding canonicalises every mode (canonicalTreeMode: unknown becomes Submodule).

MISREADING. 'go-git returns an error for a bad tree' is false for the walkers; it is true for Tree.Tree, FindEntry, TreeEntryFile and GetTree (typed lookups; the SQL storer filters by type). Also tree.Files() skips submodule entries while a TreeWalker yields them (it descends only filemode.Dir), which is why checkM3 uses the walker.

RELATED: the tree-shape invariant (judgeCommit first) is the fix; the member loader fails its load for the same reason.
