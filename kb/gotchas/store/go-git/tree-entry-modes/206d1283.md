# go-git's filemode.FileMode.IsFile() is true for a SYMLINK (and for an executable): a reader that gates on IsFile alone serves a symlink's blob, which is the link-target NAME, as if it were file content

In go-git v5 (checked at v5.19.2, the version knomit's go.mod pins; plumbing/filemode/filemode.go), `FileMode.IsFile()` returns true for Regular, Deprecated, Executable AND Symlink. Submodule and Dir are the only false cases. `Tree.File(path)` and `Commit.File(path)` do not check the mode at all: they return a symlink's entry as a File whose `Mode` is Symlink. A symlink's blob holds only its target's path text. So a reader gated on `entry.Mode.IsFile()` alone, or on `tree.File` succeeding, does not follow the link. It serves the target NAME as if that were the file's content, and it treats the entry as present.

THE ONE TEST: store.isSystemFileMode(m) = m.IsFile() && m != filemode.Symlink (internal/store/system_files.go). Every reader of a .knomit/ entry by mode uses it; do not spell IsFile again for a new one.

WHERE KNOMIT HANDLES THIS (since fix/loader-symlinks; user rulings 2026-10-08: "we do NOT want to follow symlinks, so 404" and "d": a symlinked ontology fails the repo by name):
- Optional files read a symlink as ABSENT, through their existing not-found errors (no new error class): SystemFileAt (found=false: REST 404, refs gate "does not exist", explain deleted), the skill loader SkillsAt/SkillFilesAt (#438; a regular skill.md beside a symlinked SKILL.md is the skill), privateFileAt = ScriptAt/RecipeAt (ErrNoScriptAtCommit/ErrNoRecipeAtCommit), GuidanceAt (ErrNoGuidanceAtCommit; it used to be ErrGuidanceUnusable). A directory or submodule at those paths is still an error, not absent.
- The ONTOLOGY fails instead, with fact.ErrSymlinkNotFollowed naming the path ("<path> is a symlink, and knomit does not follow symlinks: commit the file itself in its place"). See kb/invariants/repos/ontology/symlinks/1ac1e8f3.md for every reader.
- Templates (#433) accept only Regular/Deprecated; a symlink there is ErrTemplateNotRegular wrapping the same named error.

STILL MODE-BLIND, deliberately, at fix/loader-symlinks: skills.go's loose-entry check `e.Mode.IsFile()` (a symlink directly under skills/ is skipped as not-a-folder, which is right); store.TemplateFactsAt (kb/ template facts, not .knomit/); loadMembers (fleet member records under kb/); branch_merge treeBlobHash and okf history's parent `p.File` presence checks (merge and history plumbing that copies or compares blobs, not loaders). These are not .knomit/ loaders.

CONSEQUENCE: any new reader of git tree entries must decide on symlinks EXPLICITLY. `IsFile()` is not "regular file". Do not refuse Executable by accident: trigger scripts and any .knomit/ file may legitimately be +x, and tests now pin that (store TestOntologyReaders_ExecutableIsAFile, TestPrivateFileAt_SymlinkIsAbsentExecutableIsAFile, TestSystemFileAndSkill_ExecutableIsAFile, the exec.md case of TestGuidanceAt).

WHAT THIS DOES NOT MEAN: go-git never follows a symlink inside a tree. The risk is serving or accepting the link text, not path traversal.
