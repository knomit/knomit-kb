# go-git v5.19.2 ignores PushOptions.ForceWithLease for a delete refspec (:refs/heads/x): the delete goes through unconditionally, and RequireRemoteRefs is the lease that works

Module: github.com/go-git/go-git/v5 v5.19.2 (the version in go.mod at knomit 537f2019). Read in remote.go of that version: Remote.addReferencesToUpdate hands a delete refspec (rs.IsDelete()) to deleteReferences, which takes NO forceWithLease argument; only the non-delete path (addOrUpdateReferences -> checkForceWithLease) honours PushOptions.ForceWithLease. So a push of :refs/heads/<branch> with ForceWithLease set deletes the branch whatever its tip is. The option is accepted and does nothing.

WHAT WORKS: PushOptions.RequireRemoteRefs ([]RefSpec of '<hash>:<ref>'). Remote.PushContext resolves it with checkRequireRemoteRefs against the push session's OWN advertisement (the same advertised refs the delete command's Old value is built from), and refuses the whole push if the ref is not at that hash; the origin then applies the command's Old value as its compare-and-swap. Limits: wildcards are not supported in RequireRemoteRefs, and a ref that does not resolve is an error. knomit uses it in remotesync.Index.RetractPushedBranch (kb/architecture/store/remote-sync/retract-pushed-branch); TestRetractPushedBranch_LeavesAForeignTipAlone fails when the lease is removed.

CONSEQUENCE: any code that deletes a remote branch through go-git and wants a lease must use RequireRemoteRefs, and must not trust a ForceWithLease on that call. A test that deletes with ForceWithLease and a wrong lease would pass the delete and prove nothing about the lease.

VERSION PIN. Verified by reading v5.19.2 only (module cache copy), not run against another version; behaviour in later or earlier versions is unknown. Re-read remote.go after any go-git bump; line numbers move (addReferencesToUpdate was near line 620, the check near line 1509 in v5.19.2).
