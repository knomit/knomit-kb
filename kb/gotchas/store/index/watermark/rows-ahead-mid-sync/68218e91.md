# During Index.Sync, branch_facts is AHEAD of meta.last_commit: rows are rewritten file by file and the watermark moves last, so 'watermark == X' does NOT mean branch_facts is at X unless no sync_pending:<branch> marker names another head

Index.Sync (internal/engine/store/index/search_index.go) indexes a commit by upserting/deleting branch_facts rows one file at a time, each in its own implicit transaction (by design, decision ecf83a7f), and only after every row runs casLastCommit to move meta.last_commit:<branch>. Between the first row and the CAS a reader sees the OLD watermark beside rows of the NEW head. A reader that compares the watermark to an anchor and then reads branch_facts can therefore serve a version from after the anchor (or miss a path the sync just deleted), even if it reads the watermark before AND after its row read, and even if the watermark and rows are read in ONE statement (one snapshot): the snapshot itself is torn, because the writer is not atomic across the two tables. The per-branch lock (branchMu) does not help a reader that does not take lockBranchRead, and the materialize reads do not. Reproduced in TestFactSetReads_LiveAtDuringSync via Index.SetBeforeSyncCASHookForTest (red when the marker is dropped).

FIX AS BUILT (PR C, review N1): Sync commits a sync_pending:<branch> meta row naming the head it is writing BEFORE its first row, and deletes it (only while it still names that head) after a successful CAS. A failed sync (error or panic) or a lost CAS leaves it set, which only disables the fast paths until something clears it. CLEARING RULES (review round 2, R2-1), all under the branch lock, so no sync of the branch is in flight to own the marker: (1) the next Sync with work replaces it with its own head and clears it after its CAS; (2) Sync's already-at-HEAD early return deletes a marker naming ANOTHER head (a marker naming the head is harmless and kept); (3) Index.Rebuild deletes the branch's marker together with setting last_commit (every row was just rewritten); (4) vcs DropBranch(Locked) deletes the branch's last_commit:, sync_pending: and rebuild_gen: keys (so the experiment teardown deletes only graph_schema_version:) (CreateBranch inherits the parent's watermark with INSERT OR IGNORE, so a leftover last_commit: would shadow it; fsck would also count a dropped branch as maintained); (5) the experiment drop deletes it. Without (2) and (3) a failed sync followed by a commit that bypassed Sync (SetSyncSuspended bulk replay, an external ref update) and a Rebuild left the idle branch unsettled for good: every FactSet creation 503 and LiveAt always historical (reviewer probe M2, now TestFactSetReads_StaleMarkerIsCleared). Readers: HistoryQuery.LiveAt's fast path reads the watermark, the marker and the rows in ONE statement and uses branch_facts only when the watermark equals the anchor AND the marker is absent or equals the watermark; otherwise it answers from the derived history (vcs.LiveVersionAt), which is keyed by commit and unaffected by rows written past the anchor. HistoryQuery.SettledWatermark returns (watermark, rebuild generation, settled) from one statement; the generation is meta rebuild_gen:<branch>, which every Index.Rebuild bumps BEFORE it clears the watermark, because a whole Rebuild at the SAME head between two reads leaves the watermark equal and settled on both sides (an ABA, review R3-2); the search is anchored only when watermark AND generation are unchanged; an EMPTY watermark (a Rebuild in progress sets "" before rewriting every row, or a branch never synced) is NOT settled. The FactSet's first call searches only once the watermark is settled and requires it settled and unchanged after the search; until then it waits (5 ms doubling to 100 ms between looks), bounded by the request context and session.factset_anchor_wait (default 5s, "0" tries once, at most config.FactSetStallLimit = 1m, the per-write deadline a FactSet export enforces), then returns ErrIndexMoved (503 with Retry-After). The wait holds NO planning slot: the slot is taken only once the watermark reads settled, for the search itself, and released before every wait; holding it across the wait let four waiting first calls refuse every page, seek and export of existing FactSets (review R3-1). The experiment drop deletes the marker with last_commit and graph_schema_version.

CONSEQUENCE: any new reader that treats 'watermark == anchor' as 'branch_facts is at the anchor' must also check the marker in the same statement (SettledWatermark or the LiveAt pattern); a before/after watermark sandwich alone is not enough. Index.Rebuild is already safe: it sets the watermark to "" first, which no anchor equals.

WHAT THIS DOES NOT MEAN: it does not make branch_facts reads consistent in general: readers that want the branch's state NOW (RULE 1's CurrentBlobs, the search itself) still see a partially synced branch; only readers that pin an anchor need the check.
