# During Index.Sync, branch_facts is AHEAD of meta.last_commit: rows are rewritten file by file and the watermark moves last, so 'watermark == X' does NOT mean branch_facts is at X unless no sync_pending:<branch> marker names another head

Index.Sync (internal/engine/store/index/search_index.go) indexes a commit by upserting/deleting branch_facts rows one file at a time, each in its own implicit transaction (by design, decision ecf83a7f), and only after every row runs casLastCommit to move meta.last_commit:<branch>. Between the first row and the CAS a reader sees the OLD watermark beside rows of the NEW head. A reader that compares the watermark to an anchor and then reads branch_facts can therefore serve a version from after the anchor (or miss a path the sync just deleted), even if it reads the watermark before AND after its row read, and even if the watermark and rows are read in ONE statement (one snapshot): the snapshot itself is torn, because the writer is not atomic across the two tables. The per-branch lock (branchMu) does not help a reader that does not take lockBranchRead, and the materialize reads do not. Reproduced in TestFactSetReads_LiveAtDuringSync via Index.SetBeforeSyncCASHookForTest (red when the marker is dropped).

FIX AS BUILT (PR C, review N1): Sync commits a sync_pending:<branch> meta row naming the head it is writing BEFORE its first row, and deletes it (only while it still names that head) after a successful CAS. A failed sync or a lost CAS leaves it set, which only disables the fast paths until the next sync of the branch overwrites it. Readers: HistoryQuery.LiveAt's fast path reads the watermark, the marker and the rows in ONE statement and uses branch_facts only when the watermark equals the anchor AND the marker is absent or equals the watermark; otherwise it answers from the derived history (vcs.LiveVersionAt), which is keyed by commit and unaffected by rows written past the anchor. HistoryQuery.SettledWatermark returns (watermark, settled) from one statement; the FactSet's anchored search requires settled on both sides of the search, else retries once and returns ErrIndexMoved (503). The experiment drop deletes the marker with last_commit and graph_schema_version.

CONSEQUENCE: any new reader that treats 'watermark == anchor' as 'branch_facts is at the anchor' must also check the marker in the same statement (SettledWatermark or the LiveAt pattern); a before/after watermark sandwich alone is not enough. Index.Rebuild is already safe: it sets the watermark to "" first, which no anchor equals.

WHAT THIS DOES NOT MEAN: it does not make branch_facts reads consistent in general: readers that want the branch's state NOW (RULE 1's CurrentBlobs, the search itself) still see a partially synced branch; only readers that pin an anchor need the check.
