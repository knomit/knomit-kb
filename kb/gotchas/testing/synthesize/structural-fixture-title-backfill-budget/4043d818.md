# TestStructural_* in internal/synthesize can fail with `expected "rare-token", actual ""` on a slow Windows runner because seedShortlist backfills title vectors under the PRODUCTION 15 s latency budget (titleBackfillBudget) and ensureTitleVectors returns partial coverage SILENTLY; the fixture's pair has the two highest fact ids, so it sits in the last of 13 batches and is the first thing a stall drops (knomit#298)

**Observed.** CI job 108283236877 (run 36199632457, PR #295, `tests / slow-tests (windows-2025 synthesize)`, 2026-09-25): `--- FAIL: TestStructural_RareTokenStaysClosed (49.63s)` at restatement_structural_allowance_test.go:193, `expected: "rare-token" actual: ""`, message `fixture must produce a rare-token match, or the gate is not being tested`. The PR changed nothing in synthesize or store; the leg passed on the ten dev runs before it and on the two PR runs after it. First observed occurrence. Tracked in knomit#298.

**Mechanism (read at HEAD 416652b7).** `seedShortlist` (restatement_helpers_test.go:232) calls `ensureTitleVectors(ctx, deps, branch, titleBackfillBudget)`; that constant is the production latency budget, `15 * time.Second` (restatement.go:39). `ensureTitleVectors` (restatement.go:57-94) embeds titles 32 at a time `for time.Now().Before(deadline)` and then returns whatever coverage it reached WITH NO ERROR. `LiveFactsMissingTitleVector` orders `BY f.id ASC` (store/abstraction.go:79). `structuralEnv` writes ~404 filler facts and THEN the pair under test, so the pair holds the two highest ids: 406 facts = 12 full batches + 22, both halves in batch 13, the last. A stall of ~15 s anywhere in the backfill leaves the pair with no title vector; it is then never minted by KNN nor by the structural pass (structuralCandidates only returns pairs touching the on-axis requeue), and `pairKindIn` returns "" (its 'never stood' value), which is exactly the CI symptom (not "title-knn"). Nothing logs the shortfall and the fixture never asserts coverage.

**Evidence.** Forced locally (worker session, `go test -overlay` scratch test, repo untouched): fill the axis for 12 batches only -> coverage 384/406 -> refresh -> `pairKindIn` = ""; finish the backfill -> "rare-token". The real backfill on an i5-3470 takes ~0.6 s for 406/406, refresh ~1.9 s, so CI had to be ~25x slower or stall once. In the failing job the gap from the failing instance's last `index sync: incremental update` line to the next test's `git store initialized` is 16 s (23:24:56 -> 23:25:12) against 1-3 s for every passing instance: the 15 s budget plus the refresh. One other instance in the same job also shows a 16 s gap and its test passed, so a budget hit is not always fatal (it depends on whether the dropped batch held the pair). The stall's own cause (sqlite lock wait, AV scan, runner disk) is not visible in the log. 17/17 local runs of the test passed (59-101 s each), as expected with a 0.6 s backfill. Deterministic inputs ruled out: rarity cuts (factWeightedMedianDF), the hash embedder, id order and candidate ordering are all fixed for a fixed fixture; the wall clock is the only nondeterministic input between write and assertion.

**Consequence.** All 16 tests that use `structuralEnv` (identity_test.go: 11, restatement_structural_allowance_test.go: 5) are exposed; which one fails depends on which needs the last batch. A red `slow-tests (windows-2025 synthesize)` with `actual: ""` on a `pairKindIn` fixture assertion is this, not the diff: check the 16 s gap in the log, re-run once, and do not bisect the PR.

**Fix direction (not applied).** In `seedShortlist`, pass a budget that cannot expire in a test (time.Hour, or loop until `TitleVectorCoverage` is complete), AND assert full coverage in the fixture so a slow runner fails loudly as 'axis incomplete' rather than as a false claim about the gate. Do not raise the production constant for the test's sake: it is a latency budget by design (restatement.go:31-39).

**Misreadings.** This is NOT the golang/go#81238 heap corruption (no fatal, no panic; a clean assertion failure) and NOT an index-lag problem (every instance logs the same 405 incremental-update lines). It is also not the dev-box scheduling advice in kb/conventions/testing/dev-box-limits: that fact is about how to run suites on the shared machine; this one is about a fixture that lies when the machine is slow.
