# internal/synthesize's runtime is fixture construction: 20 TestStructural_* each rebuild a 406-fact corpus one commit per fact in per-fact directories (75% of the package under -race, ~47 s each locally, 60–247 s each on Windows); the 'SLOW, and deliberately so' comment defends the corpus SIZE, not the one-commit-per-fact shape — building once and copying k.db per test keeps every assertion and cut the structural group 856 s → 162 s under -race

Measured 2026-09-30 at dev 68cc310b.

Package totals:
- local macOS arm64: 276 s non-race, 1136 s -race
- CI ubuntu: 502 s non-race (tests.yml run 36583365756), 1224 s -race (race.yml run 36732003756)
- CI macOS: 423 s
- CI Windows: over 2400 s

The 20 TestStructural_* take 856 s under local -race (75%). After them nothing exceeds 25 s (Paging). The package has 0 t.Parallel. There are no hangs, no LLM or judge calls (restatementEmbedder is a fake), and no waited-out timeouts.

Run 36583365756 (the windows-2025 synthesize leg of tests.yml) hit `-timeout 40m` with only TestPaging_EveryPageFitsTheDeliveredCap/body=100 running, 24 s in. All goroutines were idle. It was the serial sum, 2383 s of passed tests, not a hang.

Why it is slow: structuralEnv (identity_test.go:40-52) writes 404 filler facts plus the pair with one WriteFact commit each. Each filler goes in its own directory, so every commit pays the tree-width cost (see the store/git/performance/tree-width gotcha). newRestatementEnv(t, 600/400), manyTwinsEnv and sweepOrderEnv follow the same pattern.

The comment at identity_test.go:29-39 was added by the Windows port (54f45452) to document observed slowness. Its 'deliberately' defends structuralFiller = 404: shortlistBudget scales at 5 per 1000, and the reservation needs a budget of at least 2. The per-fact-commit shape has no stated reason. The code under test does not read commit granularity: the 'oldest first' sweep orders by pair mint order (p.rowid), and pairs are minted after all writes.

Experiments (scratch worktree, not merged):
- (A) Build the filler once, still one commit per fact, and give each test a byte copy of k.db opened with OpenRepo. All 20 structural tests pass. Per test: 10 s → 0.45 s non-race. Group: 856 s → 162 s under -race. What remains is three one-time builds of about 47 s: the template, manyTwinsEnv and sweepOrderEnv.
- (B) Write the filler as one BatchWriteFacts commit. All 20 pass. 10 s → 4.5 s per test. Batching changes fact-id order within the batch and puts every filler fact in one commit_log entry. The 'pair has the highest ids' property survives because the pair is written in a later commit.

A plus B, applied to the flat 400/600-fact envs as well, should bring the package to a few minutes under -race. That is an estimate. The flat envs have not been checked for commit-history dependence by running them batched.

Not meant: do not lower structuralFiller. The count is load-bearing; the commit shape is not.
