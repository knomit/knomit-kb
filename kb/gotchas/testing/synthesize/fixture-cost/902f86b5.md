# internal/synthesize's runtime is fixture construction: 20 TestStructural_* each rebuild a 406-fact corpus one commit per fact in per-fact directories (75% of the package under -race, ~47 s each locally, 60–247 s each on Windows); the 'SLOW, and deliberately so' comment defends the corpus SIZE, not the one-commit-per-fact shape — building once and copying k.db per test keeps every assertion and cut the structural group 856 s → 162 s under -race

Measured 2026-09-30 at dev 68cc310b. Re-read at b9cdf382, where identity_test.go and restatement_helpers_test.go are unchanged.

Package totals:
- local macOS arm64: 276 s non-race, 1136 s -race
- CI ubuntu: 502 s non-race (tests.yml run 36583365756), 1224 s -race (race.yml run 36732003756)
- CI macOS: 423 s
- CI Windows: over 2400 s

The 20 TestStructural_* take 856 s under local -race (75%). After them nothing exceeds 25 s (Paging). The package has 0 t.Parallel. There are no hangs, no LLM or judge calls (restatementEmbedder is a fake), and no waited-out timeouts.

Run 36583365756 (the windows-2025 synthesize leg of tests.yml) hit `-timeout 40m` with only TestPaging_EveryPageFitsTheDeliveredCap/body=100 running, 24 s in. All 6 goroutines were idle. It was the serial sum, 2383 s of passed tests, not a hang.

WHY: structuralEnv (identity_test.go:40-52) writes 404 filler facts plus the pair with one WriteFact commit each, and each filler goes in its own directory. So every commit pays the tree-width cost of kb/gotchas/store/git/performance/tree-width. newRestatementEnv(t, 600/400), manyTwinsEnv and sweepOrderEnv follow the same pattern.

The comment at identity_test.go:29-39 is MISLEADING on two counts:
- It says 'The cost is filesystem work'. The cost is SQLite object reads: 81% of samples are in cgocall.
- Its 'deliberately' defends the COUNT, not the shape. structuralFiller = 404 because shortlistBudget scales at 5 per 1000 and the reservation needs a budget of at least 2. The one-commit-per-fact shape has no stated reason. The comment was added by the Windows port (54f45452) to document observed slowness.

The code under test does not read commit granularity: the 'oldest first' sweep orders by pair mint order (p.rowid), and pairs are minted after all writes.

LEVERS, all measured:
- (A) Build the filler once (still one commit per fact) and give each test a byte copy of k.db opened with OpenRepo. The copy must be taken after svc.Checkpoint() (service.go:416). All 20 structural tests pass. Per test: 10 s → 0.45 s non-race. Group: 856 s → 162 s under -race. What remains is three one-time builds of about 47 s: the template, manyTwinsEnv and sweepOrderEnv.
- (B) Write the filler as one BatchWriteFacts commit. All 20 pass. 10 s → 4.5 s per test. It changes fact-id order; see kb/gotchas/testing/fixtures/batch-changes-fact-id-order/6547b85d.md.
- (C) The per-Storer object cache (knomit#357). This fixes the cause rather than the fixtures. Prototype: package 1136 → 474 s under -race; PluralFold 47 → 12.9 s. A and B stack on top of it.

Not meant: do not lower structuralFiller. The count is load-bearing; the commit shape is not. And not 'the tests are slow on Windows': Windows only multiplies the same per-commit cost.
