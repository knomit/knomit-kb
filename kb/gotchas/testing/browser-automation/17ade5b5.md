# Playwright's keyboard.type() bypasses macOS's system text-substitution service, so it cannot verify a WKWebView autocapitalize/autocorrect fix even under a real WebKit engine

Playwright's page.keyboard.type()/press() dispatch synthetic key events directly to the page's input handling; they do not route through the OS-level text-input service (NSSpellChecker / text substitution) that a physically-typed keystroke goes through in a real, native WKWebView window on macOS. That OS-level service — not the DOM autocapitalize/autocorrect/spellcheck attributes alone — is what silently turned "test" into "Test" in web/src/CreateRepoForm.tsx's repo-name <input>, the bug the Task 6 create-repo-wizard spike exists to guard against for the CodeMirror-based OntologyEditor.

Verified experimentally during that spike: with the guard attributes deliberately removed from web/src/OntologyEditor.tsx, a Playwright-driven check against a genuine WebKit browser (installed via `npx playwright install webkit`, confirmed via navigator.userAgent containing AppleWebKit/605.1.15 ... Safari/605.1.15 — the actual WebKit engine, not the Chromium the plugin_playwright MCP tools default to) produced byte-identical typed output to the same check with the guards present. If the check were sensitive to the guard, removing it should have changed something; it didn't, because synthetic events never reach the layer the guard targets.

Consequence: a WebKit-engine Playwright check is real evidence that (a) the guard DOM attributes are present and correctly applied, and (b) CodeMirror's own contenteditable mechanics (typing, Tab, caret, selection) behave sanely under WebKit — but it is NOT evidence that the macOS system autocapitalize/autocorrect substitution service leaves the editor's content alone. That specific question can only be answered by a human physically typing into the real desktop app (Wails/WKWebView), not by any Playwright-driven automation regardless of which browser engine it uses. WHAT THIS DOES NOT MEAN: it does not mean Playwright-WebKit checks are worthless — they're still the best automatable proxy available and did catch a real, useful finding (basicSetup's Tab-moves-focus default) — just that they cannot close this specific corruption question.
