# MN2 now scans the whole synthesize/motif/ directory (non-vacuous), but MN4/MN6 key lists never named motif_alias.go or motif_define.go, and the loose-tier scan reads function bodies only

State at PR 606 (merge 4f817867): TestMN2_NoLLMInMotifCode in internal/domain/fact/motif_conformance_test.go scans every non-test Go file under internal/corpus/synthesize/motif/ via goSources and fails if it finds none, so an LLM-path string in motif_alias.go or in a NEW motif/ file turns it RED (sabotaged both ways). Before this fix the MN2/MN4/MN6/MN13 guard keys never named motif_alias.go or motif_define.go, so moving them narrowed nothing, and an llm string in motif_alias.go left MN2/MN4/MN6 GREEN. MN4 and goSources walk all of internal/ and still see motif/. MN6 was still a per-file key list at this commit (later widened to directories for bridge/ and graph/, see PR 607).

Guards that do cover the child: the recursive TestMotifMatch_LooseTiersAreNeverReachedByAutomation (walks synthesize) and the moved TestMN13_NoCorpusPropertyConstantsInAliasSelection, which parses motif_alias.go relative to the child's own directory. A package-level `var _ = "token-1"` does NOT trip the loose-tier scan, which inspects function bodies only; a sabotage must be inside a func.

Consequence: when moving a file, check each guard's key list AND whether it walks by directory; a key that names a file is a guard that a new neighbour file escapes.

UPDATE (PR 607): the later state, with MN6 walking bridge/ and graph/ by directory, is in kb/conventions/testing/motif-guards/2bb0d7e4.md.
