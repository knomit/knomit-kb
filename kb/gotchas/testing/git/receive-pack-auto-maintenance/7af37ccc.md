# A push into a file:// bare test remote leaves git's detached auto-maintenance (`git maintenance run --auto`, holding objects/maintenance.lock) running after the push returns; test bare repos are created through internal/testsupport/gitfixture, which sets maintenance.auto=false (#651, #654)

Every push into a file:// test remote runs the real git-receive-pack, from the git CLI and from go-git's file transport, which execs the git binary. After the push, receive-pack starts `git maintenance run --auto --quiet --detach` (seen in GIT_TRACE2_EVENT on git 2.56). That child takes objects/maintenance.lock BEFORE it detaches and removes it afterwards, so the push returns while the lock can still be in the remote, until the detached process next gets the CPU. In one measurement on one unloaded machine, 9 of 100 pushes left the lock behind (a measurement, not a constant).

Symptoms, both only under load: TestMultiRepo_WritesAndRemotesIndependent hashed remote B's bytes twice and got different results because the lock from B's own Connect-time push came or went; and TestFleetREST_FollowNamesAnUnchangedCredential (CI ubuntu) failed with "TempDir RemoveAll cleanup: unlinkat .../fleet.git: directory not empty" after every assertion had passed.

Fix: `maintenance.auto=false` in the bare repository. receive-pack reads it in that repository and starts no child. A work clone needs `-c maintenance.auto=false` too, because commit runs auto-maintenance. With it, 0 of 100 pushes left the lock. Judge this with git's trace2 event log (did receive-pack start a maintenance child), never with timing.

The seam: internal/testsupport/gitfixture (InitBare, CloneBare, NoAutoMaintenance, IsAutoMaintenance). About 40 test files create their bare repos through it. TestBareReposComeFromGitfixture (test/archtest) fails a _test.go file, test/ or internal/testsupport file that creates a bare repository directly (`--bare` argument, PlainInit/PlainClone with isBare true). A new bare fixture must use gitfixture. KNOWN LIMIT of that guard (review R3-S1): it misses a raw-string `--bare`, a flag inside a longer `sh -c` string, PlainCloneContext (isBare is Args[2]), and gogit.Init/Clone with a nil worktree; none exists in the tree. Its exemption is per enclosing function, not per repository. It is a guard, not a proof.

TRACE-ORACLE GOTCHA (review R2 of #654): an oracle that matches the WORD "maintenance" in argv also counts `git config maintenance.auto false`, the fixture's own setup, once that git inherits the test's GIT_TRACE2_EVENT; the testenv test went red 3 of 3 for exactly that. Count the SUBCOMMAND (gitfixture.IsAutoMaintenance: `maintenance run`, `gc --auto`), not the word. And run fixture git with an ISOLATED environment (gitfixture.isolatedEnv: PATH and HOME, the OS variables SYSTEMROOT, TEMP, TMP, USERPROFILE and TMPDIR that Windows git needs, GIT_CONFIG_GLOBAL and GIT_CONFIG_SYSTEM at /dev/null, GIT_CONFIG_NOSYSTEM=1), so neither GIT_TRACE2_EVENT nor GIT_DIR nor a developer's init.templateDir reaches it. TestInitBare_InheritsNothingFromTheEnvironment has a positive control (an inheriting git does copy the template). Whether this environment is enough on the Windows CI legs is unconfirmed: PR CI runs Go tests on ubuntu only, and the Windows legs run on pushes to dev.

CI: PR CI did not catch the red testenv test because test/testenv was in no tests.yml step (see the explicit-package-lists gotcha). #654 added ./test/testenv/... and ./internal/testsupport/... to the story/web step, so both now run in PR CI.

WHAT THIS DOES NOT MEAN: production is not affected (a user's own remote running auto-maintenance is normal). It is also NOT established that the Windows `tmp_objdir-incoming` ... `directory is not empty` failure in kb/gotchas/ci/windows/tempdir-receive-pack-staging/240205a1.md is this cause: that fact attributes it to a cancelled reconcile push still holding receive-pack's quarantine directory, and nothing in #654's code or tests touches that mechanism. Hypothesis only; that fact was left unchanged.
