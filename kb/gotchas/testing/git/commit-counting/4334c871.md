# `git log -- <path>` hides a commit that rewrites a file with identical bytes, so a 'no commit was written' test must compare the branch tip (or rev-list --count), not the path's log

Found while sabotaging F10's fleet boot reconcile: the sabotages 'write on every boot' and 're-register without comparing' stayed GREEN because the tests counted record VERSIONS with `git log --format=%H <branch> -- <record path>`. knomit's WriteFact then committed a byte-identical rewrite (a new commit, unchanged tree for that path; no longer so for WriteFact since #432, still so for batch writes), and git's path-limited log only lists commits that CHANGE the path, so the noise commit was invisible. Fixed by asserting on the branch tip (`git rev-parse <branch>` unchanged) and on `git rev-list --count from..to` for 'exactly one commit'.

CONSEQUENCE: any test claiming 'nothing was written' or 'exactly N commits' in knomit must count commits on the branch, not path history; path history is right only for 'earlier values are earlier versions'. Since #432 the single-file doors (WriteFact, WriteFactIfUnchanged, WriteRootFile) make NO commit for byte-identical content (kb/invariants/store/writes/no-op/767f16fe.md), but batch writes (BatchWriteFacts, BatchWriteFactsMustExist, so knomit_learn) still commit an all-identical batch; the tip/rev-list rule stands for both.
