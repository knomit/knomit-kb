# A Go test sandbox that redirects the user's state dir by setting HOME (darwin) and XDG_STATE_HOME (linux) does NOTHING on Windows, where userdirs reads LOCALAPPDATA: tools/desktop's TestWriteFile_ tests wrote note.txt and pwned.txt into the real %LOCALAPPDATA%\knomit\exports of every Windows box that ran them until sandboxHome set LOCALAPPDATA too (PR #302)

**Mechanism.** internal/config StateDir resolves per OS through internal/platform/userdirs: HOME on darwin, XDG_STATE_HOME (or HOME) on linux, LOCALAPPDATA on windows (userdirs_windows.go). A sandbox helper written on a Mac sets the first two and reads as complete; on Windows the tests then run against the real per-user state dir, pass (the writes succeed), and leave files behind. Nothing caches the lookup, so `t.Setenv("LOCALAPPDATA", tmp)` is sufficient and takes effect per test.

**How it was found.** Widening the Windows desktop CI step to the whole suite (knomit#264) made the reviewer ask what each newly admitted test touches on a real machine; the evidence was two files in this box's real exports dir stamped at the minute of the worker's local run. The tests were green the whole time: a sandbox that silently misses is exactly the failure a green run cannot show.

**Rule.** Any test that redirects a user directory must set EVERY variable the resolver reads on EVERY OS the test compiles on, in one helper, with a comment per line naming the OS it serves (tools/desktop/native_test.go sandboxHome is the shape). When a suite is first run on a new OS, grep its fixtures for Setenv("HOME"…) and check the resolver for that OS before the first CI run. Misreading to avoid: 'the tests pass on Windows' does not mean the sandbox held; check the real directory for leftovers after the run. This is the TEST-side twin of kb/gotchas/config/home/windows-drive-root (which is about production resolving the data root from a scrubbed environment); same resolver, opposite direction.
