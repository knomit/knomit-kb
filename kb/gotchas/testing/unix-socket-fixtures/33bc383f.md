# A unix-socket test fixture can silently build the WRONG condition — t.TempDir() overruns the 104-byte sun_path cap so a "missing socket" test gets EINVAL, and Go unlinks on Close so a "stale socket" test has nothing stale — so every such test needs a positive control naming WHICH failure it produced

TWO fixtures in ONE change each built a condition other than the one their name claimed, which is what makes this a pattern rather than an anecdote. Both were caught by the test FAILING, not by anyone reading it — and a small change of luck in either would have left a permanently green test asserting nothing.

SHAPE 1 — the path is too long to be a socket at all. macOS caps `sun_path` at 104 bytes. `t.TempDir()` yields paths like `/var/folders/7t/pt2yj6…/TestNewHTTPClient_MissingSocketFallsBackToTCPWithoutWarning3386878468/002/absent.sock`, which is over it, so `net.Dial("unix", …)` fails with `EINVAL` (`connect: invalid argument`) rather than `ENOENT`. A test meaning "there is no socket here" was in fact exercising "this path could never be a socket" — a different branch, and in this case the one that SHOULD still warn. Use a short `os.MkdirTemp("/tmp", …)` path for any unix socket in a test.

SHAPE 2 — the stale socket is not stale. `net.Listen("unix", …)` sets unlink-on-close, so `l.Close()` REMOVES the socket file. A fixture meaning "a server died and left its socket behind" therefore produced a missing file, which is exactly the OTHER case. A crashing process is precisely what does not unlink, so the fixture must say `l.(*net.UnixListener).SetUnlinkOnClose(false)` before closing.

Both shapes share one structure: the fixture produced a DIFFERENT error from the one intended, the code under test handled that other error acceptably, and the assertion — "the call still succeeded" — could not tell the two apart.

CONSEQUENCE, and it generalises past sockets: when a test's SUBJECT is which failure occurred, asserting only that the happy path survived is not evidence. Give every such test a POSITIVE CONTROL that names the branch taken. Here that means asserting the quiet path emitted its Debug line (not merely that it emitted no warning — a fixture that never reached the code at all would also emit no warning), and pinning the neighbouring case in its own test so the two branches are distinguished by something other than hope: `…MissingSocketFallsBackToTCPWithoutWarning` asserts Debug and no WARN, `…OverlongSocketPathStillWarns` asserts the WARN, and together they pin that the quiet path is keyed on `ENOENT` specifically rather than on "any failure to reach the socket".

THE MISREADING TO AVOID: this is not "unix sockets are fiddly in tests". It is that a fixture is CODE THAT IS NOT TESTED, so a fixture which quietly constructs the wrong precondition produces a test that is green, fast, and worthless — and reviewers read assertions, not fixtures.
