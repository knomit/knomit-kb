# A fixture built around a PLATFORM-SPECIFIC limit cannot fail on a platform that lacks the limit, so a green run there was never evidence — the unix-socket cases moved a defect between macOS and Windows twice before anyone saw it

THE GENERAL RULE, sharpened after it bit twice in one PR: when a fixture's behaviour depends on a limit that only SOME platforms have, a passing run on a platform without that limit carries no information about the fixture. It cannot fail there. Treating that green as evidence is the error, and it survives review because a green CI job and a correct test are indistinguishable from the outside.

THE CONCRETE PAIR, and note that the SAME test moved its defect between platforms rather than acquiring a new one:

1. `t.TempDir()` yields a long path. macOS caps `sun_path` at 104 bytes, so `net.Dial("unix", …)` on it fails with EINVAL, not ENOENT. A test meaning "there is no socket here" was therefore exercising "this path could never BE a socket" — a different branch. On Windows and Linux the path is short or the limit absent, so it passed there and said nothing.
2. Fixing that with a short `os.MkdirTemp("/tmp", …)` path is correct on macOS and Linux and IMPOSSIBLE on Windows, where `/tmp` does not exist — `GetFileAttributesEx /tmp: The system cannot find the file specified`. The fix inverted which platform was lying: the quiet-but-wrong platform became loud, and the previously-loud one went quiet.

The test needed BOTH a short path AND a platform guard. Getting only the first is what made a green CI run at the intermediate commit look like evidence it never was.

A THIRD SHAPE, same family: `net.Listen("unix", …)` sets unlink-on-close, so `l.Close()` REMOVES the socket file. A fixture meaning "a server died and left its socket behind" produced a MISSING file — again the other case. A crashing process is precisely what does not unlink, so the fixture must call `l.(*net.UnixListener).SetUnlinkOnClose(false)` before closing.

WHAT THE THREE SHARE: the fixture produced a DIFFERENT error from the one intended, the code under test handled that other error acceptably, and the assertion — "the call still succeeded" — could not tell the two apart.

CONSEQUENCES TO ACT ON, and they generalise past sockets:

- Give any test whose SUBJECT is WHICH failure occurred a POSITIVE CONTROL naming the branch taken. Asserting "no warning was logged" is not enough: a fixture that never reached the code would also log nothing. Assert the quiet path emitted its Debug line AND pin the neighbouring case in its own test, so the two branches are distinguished by something other than hope.
- Guard a test that exercises a mechanism a platform LACKS, rather than letting it pass vacuously there. Name the tracking issue in the skip message.
- Verify the guard did not overreach: on a platform that CAN run these, the suite should report zero SKIP lines. A guard that quietly drops the tests where they are meaningful is the same failure wearing the opposite coat.
- Verify the tests are SKIPPED and not EXCLUDED. "The job passes" and "the tests are absent" look identical from outside; cross-compile the test binary for the platform and confirm the test names and the skip string are present in it.

THE MISREADING TO AVOID: this is not "unix sockets are fiddly in tests". It is that a fixture is CODE THAT IS NOT TESTED, so a fixture which quietly constructs the wrong precondition yields a test that is green, fast and worthless — and reviewers read assertions, not fixtures.
