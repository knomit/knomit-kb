# A test that swaps the global zerolog logger onto a bytes.Buffer races with any started Manager's background goroutines; the sink must be mutex-guarded

TestSecretsAPI_NeverReturnsValue assigned the global log.Logger to a zerolog writer over a plain bytes.Buffer, then started a repos.Manager via newSecretsFixture. Manager.Start launches the session reaper goroutine, which logs through the global logger (for example its 'session reaper: started' line) at an arbitrary time while the test goroutine reads logs.String(). Under -race this is a DATA RACE between bytes.Buffer.Write (reaper goroutine) and bytes.Buffer.String (test goroutine). The race is in the test sink, not in the secrets handlers or store: the HTTP requests are served synchronously and the product code logs from its own goroutines legitimately. The fix is a mutex-guarded lockedBuffer in the test file. Consequence: any test that captures log output while a started Manager (or any component with background goroutines) is alive must use a concurrency-safe sink; wait-free reads of a bare bytes.Buffer are only safe when no goroutine can log. This does NOT mean the secrets API leaks or mis-synchronizes anything; the never-returns-a-value assertion is unchanged. Not a reason to add sleeps or to stop the Manager early in the test.
