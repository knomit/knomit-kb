# A sort.SliceStable→sort.Slice regression is INVISIBLE to an already-ordered fixture at any size — pdqsort short-circuits on zero inversions

To prove a test actually guards sort STABILITY, the fixture must arrive OUT OF ORDER with ties inside it. An already-sorted fixture passes identically under sort.Slice and sort.SliceStable no matter how large it is.

The half-truth that misleads: 'Go's sort.Slice is insertion sort below n≈13 and therefore accidentally stable, so use a bigger fixture.' The threshold is real but it is not the only fast path. Above it sort.Slice is pdqsort, whose partialInsertionSort pass detects a sequence with zero inversions and returns immediately — leaving the input untouched. A fixture of 20 elements that all compare EQUAL and are supplied in caller order is, by definition, already ordered, so pdqsort never permutes it and the mutation survives.

Measured directly: 20 equal-keyed elements in caller order preserved their order under both comparators; 10 groups of 2 tied elements supplied newest-group-first had their ties reordered by sort.Slice and preserved by sort.SliceStable.

How to apply: build the fixture in the shape the production caller actually produces. For a git commit walk that is groups newest-first with same-second ties inside each group — which is both realistic AND genuinely unsorted, so the sort has to do work. Then assert an ordering-derived property, not the raw slice.

This matters beyond sorting: a guard nobody has watched FAIL is not a guard. Mutate the production code and confirm the red before trusting any test written to pin behaviour.
