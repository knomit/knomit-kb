# factsetGoneFixture (REST factset tests) assumed r1 and r2 commit in one wall-clock second; fixed by write order (r2 before r1), the same class and the same fix as #707's F4 flake

The recent-sorted / text-less list orders by WHOLE-SECOND commit time, newest first, then by path (gotchas/store/search/fc402637). A fixture that writes facts in SEPARATE commits and expects path order is right only when every write lands in one second.

The instance: factsetGoneFixture (internal/edge/web/api/kb/handlers_materialize_factset_test.go) wrote kb/u/r1.md and then kb/u/r2.md, and its users expect r1 to be unit 1 and r2 unit 2.
- When the two writes straddled a second boundary, r2 was newer and listed first.
- TestFactSet_ResumeInsideAShrunkUnitContinuesAtTheNextUnit then failed ("continues at unit 2's first section": got r1). This was seen in a full `go test ./...` run on fix/lens-query-parity-2.
- Forcing the old order a second apart also fails TestFactSet_ResumeAfterACitedRepoIsGone.
- The other two users (ResumeIgnoresAnUnrelatedUnreachableRepo, ResumeUnknownAndForeignCursorsStay404) do not depend on the order.

Fix (#715, merged as 31a99271): write r2 BEFORE r1. Then r1 is newer or tied, so it lists first whether or not the seconds differ. This is the same technique as #707 (876c8ca3, F4 frame-ancestors seed; kb/gotchas/materialize/factset/tests/one-second-assumption/4417245c.md). Verified both ways: with r2 and r1 forced a second apart, all four users pass; with the old order forced a second apart, two fail.

RULE for fixtures over a recency or text-less listing: choose the WRITE ORDER (or one BatchWriteFacts commit) so the wanted listing holds whether the writes tie or straddle a second. A later write must never be expected to sort after an earlier one by path.

WHAT THIS DOES NOT MEAN: do not fix these with sleeps or awaitNextSecond. That makes the test slower and still couples it to the clock; ordering by construction removes the dependency.
