# Speeding up a store fixture changes what it builds: BatchWriteFacts assigns fact ids in index-sync (path) order, not the order the fixture wrote them, which matters to id-ordered readers like abstraction.go:79's ORDER BY f.id and to pair rowids; and copying a built k.db to share a fixture is only safe after svc.Checkpoint()

Two sharp edges met while speeding up internal/corpus/synthesize fixtures on 2026-09-30. See kb/gotchas/testing/synthesize/fixture-cost/902f86b5.md.

1. BATCHING CHANGES FACT-ID ORDER. A loop of WriteFact calls gives facts ids in loop order, one commit and one incremental sync each. One BatchWriteFacts commit indexes all its files in a single sync, and ids follow that sync's order, which is PATH order (so topic10 sorts before topic2). Readers ordered by fact id then see a different order:
- LiveFactsMissingTitleVector's `ORDER BY f.id ASC` (abstraction.go:79) decides which facts land in the LAST title-backfill batch.
- Restatement pair rowids (mint order) follow from that.
This is harmless for TestStructural_* today, after PR #304 (knomit#298). Their pair is written in a separate, later commit, so it still has the highest ids, and seedShortlist backfills to full coverage. All 20 pass batched. But a fixture whose assertion depends on WHICH fact is newest, or which falls in the last batch, gets a different corpus with no error. The order must be restored explicitly, e.g. by a second commit.

2. COPY ONLY AFTER CHECKPOINT. A shared fixture built once and copied per test (the k.db file holds git objects and index together, so a byte copy clones the repo) must call svc.Checkpoint() (service.go:416) before copying. Recent writes otherwise sit in the WAL, and a copy of k.db alone is a stale store. Closing the service also checkpoints; an open service does not.

Not meant: neither is a reason to avoid batching or copying. They are the two things to state in the fixture's own comment when you do.

CONFIRMED IN SHIPPED CODE (#441, merged as 19a6a6da). restatementEnv.writeFiller now batches the 404-fact TestStructural filler. A before/after probe showed the filler's ids running topic0, topic1, topic10, topic100, topic101 … (path order), where they used to run topic0 … topic4 (loop order). Everything a test reads stayed byte-identical: every non-filler fact's id rank, all ~2,400 standing restatement pairs with kind and cosine in rank order, the selected candidates and the health struct. The pair and twins are written AFTER the batch, one WriteFact each, and that is what keeps them newest and in their own write order. A fixture that needs a specific order WITHIN a batch cannot get it from BatchWriteFacts. It must either use paths that sort in the order it needs or write those facts separately.
