# A refusal test that asserts status + a reason SUBSTRING keeps passing when an EARLIER layer starts refusing with the same status — if that layer's message happens to contain the substring, the row silently stops testing the layer it names

Found in #287. TestBrowserGate_EachMissingProofRefuses (internal/web/oauth_browser_gate_test.go) pins the 3b OAuth approval gate. Each row asserts 403, `strings.Contains(body, reason)` and "request still undecided". When AuthMiddleware gained an Origin check that runs BEFORE the gate, five mutation rows started being refused by the new guard instead, with the same 403. Only ONE of them failed, the row whose reason was "Sec-Fetch-Site". The other four had reason "Origin", and the new guard's detail text happens to contain the word Origin ("…a page at Origin \"null\"…"). They stayed green while no longer exercising the gate at all.

Why it hides: status alone cannot tell two 403 layers apart, and a one-word reason is exactly the kind of token a neighbouring layer's human-readable detail also contains. The test then pins "something refused this", not "this gate refused this". A later edit weakening the gate's own Origin rule would pass every one of those rows.

What was done:
- The test lists the rows refused earlier explicitly (refusedByOriginGuard, like the #281 refusedEarlier set of 421 rows) and asserts the guard's TITLE for them.
- It ALSO asserts the converse: every other row must NOT carry the guard's title, so a future earlier layer that captures a row is caught instead of absorbed.
- Review found a second casualty of the same shadowing: the gate rule 'the desktop allowlist is never own origin' was no longer exercised by ANY test. Its row runs without an allowlist, so the guard now refuses it first. With the allowlist set, the only case where the rule matters, a wails://localhost POST passes the guard by design, and nothing asserted that the gate still refuses it. TestBrowserGate_AllowlistedOriginIsNeverOwnOrigin now sets CORSOrigins and asserts all three: 403 with the GATE's reason ("is not this listener's own origin"), NOT the guard's title, and the request undecided. The old row is renamed "Origin wails, no allowlist (refused earlier by the #287 guard)". Making browserProof accept the Wails origin now fails that test and nothing else, which is exactly the coverage that had silently gone.

CONSEQUENCE: when adding a check in front of an existing refusal path, grep the downstream tests for substring assertions and run them against the new layer's message, not just for red/green. Assert the distinguishing TITLE (problem+json title is what clients key on here) or a phrase unique to the layer, and pin the negative ("not refused by X") for rows that must reach the inner layer. Then ask, for every inner rule a shadowed row used to cover, whether any input still reaches it; if the outer layer now admits only the configuration the old row did not use, add a row with that configuration.

WHAT THIS DOES NOT MEAN: substring reasons are not wrong in themselves; the gate's per-proof reasons are useful. The trap is only that a shared status plus a generic word cannot identify the layer.
