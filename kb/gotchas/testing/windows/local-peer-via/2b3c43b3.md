# A test that fakes the local-socket caller must build its Peer with auth.LocalVia, not a hard-coded auth.ViaSocket: on Windows the local listener is a named pipe (ViaPipe), the grants key is <kind>:<id>@<via>, so boot-seed grants made for LocalPrincipal never match and the request is 403

TestOriginEscalation_LocalSocketCallerSetsAnOrigin granted the boot-seed loopback_default permissions to auth.LocalPrincipal() and then presented the request as auth.Peer{ID: me.ID, Via: auth.ViaSocket}. On unix LocalVia is ViaSocket so they agree. On Windows LocalPrincipal carries Via ViaPipe (local_windows.go: `const LocalVia = ViaPipe`), the grants key is <kind>:<id>@<via>, and the faked peer came out as bridge:sid:S-1-5-...@socket, which holds no grant: 403 'requires the write permission; principal ... @socket does not hold it'. It stayed hidden behind the JSON-escape 400 of the same test until PR #712 fixed that.

What to do: when a test fakes the caller of the local authenticated listener, take the Via from auth.LocalVia (and the ID from auth.LocalPrincipal), so the fake follows the platform.

What this does NOT mean: tests that use a synthetic principal on BOTH the grant side and the request side with the same literal (e.g. 'uid:501' + ViaSocket in internal/foundation/auth and internal/edge/web tests) are self-consistent and run fine on Windows; they are not the bug. Only a test that mixes the real LocalPrincipal with a hard-coded Via is.
