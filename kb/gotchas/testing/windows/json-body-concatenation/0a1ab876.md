# A Go test that builds a JSON request body by string concatenation and embeds a filesystem path breaks only on Windows: C:\Users\RUNNER~1\... puts \U in a JSON string, the server answers 400 'invalid character U in string escape code', and PR CI never runs the Windows tests — encode the body with json.Marshal

Eight TestOriginEscalation_* tests in internal/edge/web were red on every dev push from dd73ed85 (2026-10-29) in the Windows job 'tests / build-test (windows-2025)', step 'Story, web + desktop-helper tests'. They built bodies like `{"url":"`+bare+`","branch":"main"}` where `bare` is a raw t.TempDir-derived path. On Windows that is C:\Users\RUNNER~1\..., and `\U` is not a valid JSON escape, so httpx.DecodeJSON answered 400 'Invalid request body ... invalid character 'U' in string escape code' at byte 12. Tests whose url came from seedKnomitRemoteForTest (a file:///C:/... URL, forward slashes) passed, which hid the pattern. Pull-request CI does not run the Windows tests, so PRs were green.

What to do: build any test request body that embeds a path or URL variable with encoding/json (the file's escBody(map[string]any{...}) helper), never by concatenation. Do NOT 'fix' it by filepath.ToSlash on the input: the defect is that the body was not encoded, and a path with a quote or a backslash would still corrupt it.

What this does NOT mean: pure literal bodies like {"branch":"main"} need no change, and the server is not at fault — rejecting the malformed JSON is the correct behaviour. Other files concatenate a url variable the same way (e.g. consensus_branch_web_test.go, handlers_fleet_membership_test.go, handlers_origin_hal_test.go) and are green today only because their urls happen to be file:/// or http URLs.
