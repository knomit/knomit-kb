# internal/app TestOpen_Supervised/tls_address_held flakes rarely because newFixture's two freeAddr calls can return the SAME port, so the plaintext and TLS addresses collide; one re-run is the right response and the failure says nothing about the PR under test

Symptom: CI job tests / build-test (ubuntu-latest) fails with `--- FAIL: TestOpen_Supervised/tls_address_held:_warn_and_serve_without_it` in package internal/app, at the assertion `tcp=<nil> local=<non-nil> tls=<nil>` (wanted ls.TCP non-nil). Seen on PR #690 (web/ and tools/desktop only), passed on a single re-run of that job.

Cause: newFixture (internal/app/listeners_test.go, origin/dev lines 56 and 60) calls freeAddr twice, once for the plaintext cfg.Host/cfg.Port and once for tlsAddr. freeAddr listens on 127.0.0.1:0, reads the port, and CLOSES the listener before returning, so nothing reserves the port; the kernel can hand the same ephemeral port to the second call. Plaintext and TLS then share one address. The test holds tlsAddr, which therefore also holds the plaintext port, so the plaintext bind fails with addr-in-use and ls.TCP is nil. Evidence: the failing log named 127.0.0.1:36429 in BOTH the 'plaintext listener address is held by another process' and the 'tls listener address is held' warnings.

What to do meanwhile: a single re-run of the failed job is the correct response. The failure is not evidence against the PR under test; check that the PR touches nothing under internal/app before dismissing it. Do not loosen the assertion.

Fix direction (not yet done): make newFixture retry until the two addresses differ, or keep the first listener open while picking the second.

Does NOT mean: the listener open order or the addr-in-use handling is broken. Production binds plaintext then socket then mTLS as in the open-order invariant; only the test fixture can pick colliding ports. Other subtests that call requireFree on both addresses could flake the same way.
