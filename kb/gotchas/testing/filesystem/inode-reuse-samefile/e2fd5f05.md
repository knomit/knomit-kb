# ext4 gives a just-freed inode to the next file created at the same path, so os.SameFile says "same file" across a remove-and-recreate there — it can NEVER prove "replaced"; it stays a valid "NOT replaced" check only while a live process still holds the original

THE MECHANISM: an inode number is only an identity while the inode is in use. ext4 allocates a new inode by scanning the group bitmap for the lowest free one, so after `os.Remove(path)` frees inode A, the very next file created in that directory (here a unix socket re-bound at the same path) gets inode A again. Same device, same inode number → `os.SameFile(before, after)` returns TRUE for a file that is genuinely new.

MEASURED 2026-09-22 (remove a socket, re-create one at the same path, compare): ext4 on a real loop mount 500/500 and 50/50 same inode (two independent runs); APFS (darwin), tmpfs and Docker's overlay 0/500 and 0/50. That split is why every developer Mac and every default Docker container passed a test that failed on the ubuntu-latest CI runner, whose /tmp is on ext4.

THE INSTANCE: `TestListenLocal_StaleSocketIsReplaced` asserted `!os.SameFile(stale, after)` as its positive control that ListenLocal had replaced a crashed server's leftover socket. It failed the first time internal/auth ran on Linux in CI (PR #250), with the code correct. Reproduced 5/5 on an ext4 loop mount, green on darwin. Fixed by checking BEHAVIOUR instead: before, a dial to the path gets ECONNREFUSED (proving stale); after, a dial is received by the NEW listener's Accept and `PeerCred` is ok on the accepted conn (proving replaced).

WHERE SameFile IS STILL RIGHT: the live-owner tests (`TestListenLocal_LiveSocketIsNotStolen`, `TestListenLocal_RefusingLiveOwnerIsNotStolen`) assert the owner's socket is the SAME inode after a second ListenLocal. Measured 0/50 false positives on every filesystem, ext4 included: the owner's bound socket keeps the original inode in use, so a thief that removed and re-created the path could not be handed it. "Not replaced while the original is still held open" is sound; "replaced after the original was freed" is not.

CONSEQUENCES TO ACT ON:
- Never use os.SameFile, or a raw inode compare, to prove a file was REPLACED after the old one was removed. Assert what the new file DOES (it answers, carries new content, the new owner receives the connection).
- Using SameFile to prove NOT replaced is sound only while something keeps the original inode alive; if nothing does, it has the same hole.
- A filesystem-identity assertion needs a run on ext4 before it counts. Green on APFS, tmpfs or overlay is not evidence about it (see the platform-specific-fixture gotcha).
