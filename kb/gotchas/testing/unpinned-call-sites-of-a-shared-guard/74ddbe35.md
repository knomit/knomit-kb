# A guard with good tests and UNPINNED CALL SITES is worth less than it looks — auth.RequireLocalListener had a 5-case table, an integration test and a forced red, and mutating cfg.Auth.Require to a constant at either call site left every test in the tree green

auth.RequireLocalListener had a thorough unit test, an integration test against a real held pipe, and a forced red on each. NEITHER of its two PRODUCTION call sites was pinned: mutating cfg.Auth.Require to `false` at tools/desktop/app.go left the desktop suite green, and the same in cmd/serve.go left the cmd suite green.

WHY THE TESTS COULD NOT SEE IT: every desktop test called bootServer directly with a `requireAuth` of its own, so nothing asserted the REAL config value arrived. The guard was tested; the WIRING was not — and the wiring is where a positional bool beside a related string goes wrong silently.

THE FIX IS THE PARAMETER SHAPE, NOT ANOTHER TEST. bootServer now takes a `localListener{Path, Require}` built by localListenerFrom(cfg), and cmd/serve calls openLocalListener(cfg) with the whole config. There is no longer a pair of arguments at either call site to transpose, and the one place config becomes that value is pinned BOTH WAYS — asserting only the `true` case would pass for a mapping hard-coded to `true`, which fails in the other direction: every boot refused when the listener is merely held.

WHERE A CHEAP END-TO-END IS NOT AVAILABLE, SAY SO. cmd/serve reaches this point only after app.New, which needs the embedding model, so a RunE test is not the cheap option; the derivation is pinned instead and the reason is written next to the test.

THE QUESTION TO ASK of any shared check: if I replaced the argument at each call site with a constant, what goes red? If the answer is nothing, the suite is testing the helper, not the behaviour.
