# readFact consults its fallback flag only after the pinned read fails with ErrPathNotFound, so a test cannot observe fallback forwarding on a request whose primary read succeeds

In readFact (internal/edge/web/handlers_fact_read.go) the fallback parameter is read in one place: after the pinned (AtCommit) ReadFact returns an error, `fallback && !a.IsHEAD() && errors.Is(rerr, model.ErrPathNotFound)` starts the BeforeCommit walk-back. handleCommitAnchoredFact sets fallback from ?fallback=before. When the pinned read succeeds the flag is never consulted.

CONSEQUENCE: a test that the handler forwarded fallback must use a request whose primary read fails with not-found (a path retracted at the pinned commit), and assert the read log ("at <sha> <path>" then "before <sha> <path>") or the walked-back version. Under the old FactReader stub a recorded `lastFallback` field could assert forwarding on a succeeding read; a real store cannot show it, so such an assertion is vacuous (draft-reported: the replacement test was pinned by review sabotage A15).

DOES NOT MEAN: that fallback is ignored on HEAD anchors for a reason a test can see: HEAD-anchored callers pass false and the flag is also skipped by the !a.IsHEAD() guard.
