# index.Facade.SetOverridesForTest replaces the WHOLE Overrides struct, so two web helpers on one mount would silently drop the earlier observer and a == 0 counter would pass vacuously; since W0d2 installMountOverrides fails the test instead, and search path= and since_fork are pinned

SetOverridesForTest (internal/engine/store/index/testseams.go) stores the given Overrides on all four query services of the Facade and returns a restore to the PREVIOUS set; it does not merge. In internal/edge/web, countMountReads, slowMountRead and observeMountSearch each install one. If two of them landed on the same mount, the earlier observer would be dropped with no error, and a counter asserting == 0 would pass vacuously.

FIXED in W0d2 (PR #610, merged as c3571f43; re-read there): the three helpers install through ONE function, installMountOverrides (handlers_lenses_stats_test.go), which t.Fatalf's when another helper already installed an Overrides on that store.Service. TestMountOverrideHelpersRefuseASecondObserver tries all nine ordered pairs of the three helpers (the self-pairs included), each on a fresh store; disabling the guard turns it RED. A test that needs a delay AND a count (or a Reads observer AND a Search observer) on one mount must say so in ONE Overrides. DOES NOT MEAN: that stacking is impossible; the guard knows only the three helpers, so a direct SetOverridesForTest call in a web test would bypass it (there is none at c3571f43).

Second gap found by the PR 605 review, also closed in W0d2: dropping q.Path in searchRepo, or in the lens search fan-out, used to leave the whole web package green. TestHandleSearch_PathNarrowsTheResults and TestLensSearch_PathNarrowsEveryMount (handlers_search_path_test.go) pin it: the best match sits OUTSIDE the prefix, an unqualified path applies to every mount in its own terms, a kb://<id12>/ path to one mount repo-relative. An unqualified path under a topic a mount's ontology lacks skips that mount (ReadTargetsFor), so the lens test uses preset topics.

since_fork is pinned too: TestHandleHALFactsCollection_SinceForkNarrowsToTheExperiment and TestHandleSearch_SinceForkNarrowsToTheExperiment open an experiment (svc.Merge().OpenExperiment), write one fact on it and one on the agent branch; without ?since_fork both list, with it only the experiment's, and off an experiment branch it is a 400. Dropping PathsIn in recentFacts or searchRepo turns them RED.
