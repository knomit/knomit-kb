# index.Facade.SetOverridesForTest replaces the WHOLE Overrides struct, so two web helpers installed on one mount silently drop the earlier observer and a == 0 counter then passes vacuously; web search path= is also unasserted anywhere

SetOverridesForTest (internal/engine/store/index/testseams.go) stores the given Overrides on all four query services of the Facade and returns a restore to the PREVIOUS set; it does not merge. In internal/edge/web, countMountReads, slowMountRead and observeMountSearch each install one. If two of them land on the same mount, the earlier observer is dropped with no error, and a counter asserting == 0 passes vacuously. A test that wants both a Reads observer and a Search observer on one mount must put both in one Overrides. The positive controls in PR 605's tests prevent this today; nothing enforces it for later tests (reviewer suggestion: have the helpers t.Fatal when an override is already installed, or add one composing helper).

Second pre-existing gap found by the same review: dropping q.Path in searchRepo leaves the whole web test package green. context_test.go and expires_test.go pass path= to /search but their corpora do not discriminate on it, and no search stub asserted Path at base either, so no assertion was lost in PR 605. A repo /search?path=kb/x/ test narrowing against a fact outside kb/x/, plus a lens search with an unqualified path=, was being added in W0d2. Until it lands, do not treat path= on search as covered.
