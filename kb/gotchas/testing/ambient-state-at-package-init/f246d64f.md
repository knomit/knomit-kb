# ANY package-level var built from AMBIENT state — an env var or the filesystem — makes that package's suite measure the machine rather than the commit, and t.Setenv cannot fix it afterwards because init already ran

THE GENERAL RULE, first, because the instance below is only how it was found: a package-level variable whose initialiser reads `os.Getenv`, the filesystem, the network or the clock is evaluated at PACKAGE-INIT time — before any test body runs, before any `TestMain`, before any `t.Setenv`. Whatever the machine happened to look like at that instant is then frozen for the life of the process. A test that sets the same environment variable afterwards is setting a value that has already been read, so it is a no-op that LOOKS like configuration.

THE VERIFICATION CONSEQUENCE, which is why this is not merely a design smell: the repo's convention is to verify in a clean worktree at the SHA that was pushed. A clean worktree controls the CODE. It does not control `$HOME`, `$PATH`, the environment, or what daemons happen to be running — so a package whose behaviour is fixed at init from ambient state is exactly the case that convention does not cover. Both the author's and the reviewer's runs can be green, at the right SHA, in clean worktrees, and still say nothing about the commit.

THE INSTANCE. `var HTTPClient = NewHTTPClient(SocketPath(), os.Getenv("KNOMIT_BASE_URL") != "", httpTimeout)` in `tools/bridge/knomitapi` chose a transport at init from an env var and the presence of a unix socket file. Measured, same commit, same machine, the only difference being whether a socket existed at the resolved home:

    $ go test ./tools/bridge/knomitapi/                  # no socket
    ok      knomit/tools/bridge/knomitapi   0.193s

    $ # stale socket planted at ~/.knomit/knomit.sock
    $ go test ./tools/bridge/knomitapi/
    --- FAIL: TestSessionContext_PrinciplesComeFromTargetedQueryNotRecentWindow
    --- FAIL: TestSessionContext_PrincipleNotRepeatedUnderRecentWork
    --- FAIL: TestSessionContext_InvariantsFallbackOnlyWithoutPrinciples
    FAIL

THE PASSING CASE IS WORSE THAN THE FAILING ONE. A DEAD socket produces a loud failure. A LIVE one lets those tests reach the developer's real local server instead of their `httptest` one, where they can pass for entirely the wrong reason — a false green that survives review, because reviewers read assertions and not the machine the suite ran on.

THE FIX IS TWO CHANGES AND THE FIRST ALONE IS NOT ENOUGH. (1) Build on FIRST USE rather than at init — but laziness only MOVES the freeze to whichever test runs first, so it does not fix a suite. (2) Re-read the ambient input at the point of USE — here, inside `DialContext`, so the answer still tracks the environment after the client exists. Then pin the suite: `isolateHome(t)` sets `KNOMIT_HOME`, `KNOMIT_REPO` and `KNOMIT_BASE_URL` in every test that could touch the socket path, so no test can reach the developer's machine even by accident.

THE TEST TO APPLY TO ANY PACKAGE-LEVEL VAR: does its initialiser read the environment, the filesystem, the network or the clock? If so, ask what this package's suite would do on a machine where that answer differs. If the honest answer is "something else", the suite is evidence about the machine and not about the commit — and no amount of care about WHICH SHA you run it at will change that.

THE MISREADING TO AVOID: this is not "avoid package-level vars" or "avoid globals". A package-level var built from a CONSTANT, or from nothing, is fine and freezing is exactly what you want. The defect is the combination — package-level lifetime plus an ambient input — and either one alone is harmless.
