# Writing Go source through a quoted shell heredoc or perl -0pi from the agent Bash tool on this Windows box DROPS one backslash from every doubled pair, so `\\.\pipe\` lands on disk as `\.\pipe\` — it compiles, and the failure surfaces far away

On the Windows dev box, writing Go source through a QUOTED shell heredoc (`<<'EOF'`) from the agent's Bash tool dropped one backslash from every doubled pair: the Go raw string `` `\\.\pipe\` `` was written to disk as `` `\.\pipe\` ``. The same happened through `perl -0pi -e`, and again later in a Markdown file.

IT COMPILES. The failure surfaces far from the cause — here as `ListenPipe: Incorrect function` on a path that LOOKS right in the log, because `%q` of `\.\pipe\x` prints `"\\.\\pipe\\x"`, which reads exactly like the correct value to anyone scanning output.

WHAT TO DO: write any literal containing backslashes with the Write/Edit tools rather than a shell heredoc, and verify afterwards with `grep -nF` on the raw line rather than reading it back through another shell layer (which can eat them a second time and show you what you expected).

This is a property of the AGENT HOST's shell layering on this machine, not of Go, winio or knomit. It is recorded here because it cost real debugging time twice in one change and would cost it again for anyone editing Windows path constants from the same environment.
