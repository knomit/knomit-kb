# A cursor test over a repos.NewTestInstanceWithDeps fixture without a UID mints a cursor that NEVER resumes: Binding.PinID is "" and every resume reads as expired

Binding.PinID fails closed on an empty uid (pinOf returns ""), and the resume checks in query, explain and materialize.NextPage refuse a session whose stored binding is "". So a test fixture built with repos.NewTestInstanceWithDeps and no UID can serve page 1 with a cursor, and every page-2 call answers the expiry error (on REST: 404 "Cursor not found"), which looks exactly like an ownership or read-set bug.

CONSEQUENCE: any fixture that pages through a cursor must set TestInstanceConfig.UID (the kb package's newMatStoreManager now sets UID "uid-<name>", as internal/edge/web's newMaterializeRepos already did). Before suspecting the owner check, check the fixture has a UID.

WHAT THIS DOES NOT MEAN: it is not a production bug; every registered repo has a uid (Registry.Insert rejects an empty one).
