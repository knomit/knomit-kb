# FactSet replay on a 500x499 store: the cost was the facts+commit_log JOIN of every ref row (2.6x the rows alone), not the Go driver; the memory was Go map overhead (about 2x payload). Fixed by reading versions only for unseen targets, a speculative read-ahead, and frozen sorted tables

Measured on PR C (#696) with the synthetic 500 results x 499 distinct refs store, Apple M4, warm:

- TIME. A full replay of the second levels (499,000 ref rows) cost 1.66 s when every row was joined to its target's facts row and commit_log date (the old GraphStore.RefLevel), and 0.63 s for the rows alone. The CPU profile was ~90% inside sqlite3_step, not in per-column cgo scans: the join was the cost. On that shape the second-level targets are siblings the unit already holds, so their metadata was read for nothing. EXPLAIN showed only primary-key and index probes; the store is far larger than a connection's page cache, so each probe is page access.
- FIX (index.LevelReader, internal/engine/store/index/level_reader.go): per call, two prepared statements reused across units (rows by a json_each-bound blob set; versions by json_each-bound (path, blob, commit) triples); a level reads versions ONLY for targets the unit has not seen. Plus a read-ahead (materialize fsCall.readAhead): windows of 6 units read their roots' metadata and rows, then level by level, speculatively, the next level's versions and rows in 4 parallel chunks, pipelined behind the planner and overlapped with the reservation (on pages; since review N2 the export reads its windows synchronously inside its planning slot, which made it about 10% slower). The numbers below were measured at a846ce43. Far seek to unit 500 went 3.0 s -> 1.3 s, replay 3.2 s -> 1.6 s; deep chains (shape D) 1.34 s -> 1.09 s.
- MEMORY. The written set and reserved map as Go maps held 36 MiB for 22 MiB of payload per FactSet; as frozen sorted tables of 24-byte entries (FactHash, blob64, 32-bit check, unit, k) plus per-call bitsets and a small extra set (sorted slice + 4096-entry tail) they hold 7.6 MiB. Four concurrent walks peak at 109 MiB (was 289 MiB) once a page also drops the plans of units it has passed.

CONSEQUENCE: before blaming the driver for a slow batched read, compare the statement with and without its joins on the real store; and size cache state as slices, not maps, when entries number in the hundreds of thousands.

WHAT THIS DOES NOT MEAN: the read-ahead is an optimization only. A unit whose rows or versions it did not read falls back to its own level read with the same answer (TestFactSet_ReadAheadWindowChangesNothing pins byte identity across windows). The per-unit read bound (Depth+2) now applies to the reads beyond the read-ahead and to the single-fact plan.

UPDATE (PR #702, merged at 233a5404; same store, Apple M4, warm, 64 MiB budget; TestFactSet_MeasureAccess in factset_measure_access_test.go). The written bitsets became first-written units (2 bytes per frozen entry, 32-byte extra entries), so a unit is re-planned alone and the 'replay' above no longer exists for backward reads. Before -> after: far seek to 500 1.47 s -> 1.44 s; backward seek to unit 3 after it 41 ms (3 units replayed) -> 32 ms (1 unit); two readers alternating at units 3 and 400 666 ms -> 1.9 ms per call (3997 -> 1 units planned in 20 calls). The 4 planning slots are gone and planning memory is reserved under the budget instead: 4 FactSets at once 115 MiB -> 77 MiB heap peak (5.5 s -> 6.5 s); 16 at once: 12 of 16 refused with 503 before, none refused after, 81 MiB peak, 25.6 s wall (about two B-sized plans fit in 64 MiB; the rest wait). Reservation sizes were measured, not guessed: a far seek at max_nodes 500 peaked 30 MiB above what it kept and a 500 x 499 reservation build 33 MiB (Go heap in use, GC slack included); a first estimate from bytesPerSection was 8x low and let 16 FactSets reach a 250 MiB heap. CONSEQUENCE: size a reservation from a measured heap peak (HeapInuse with GC slack), never from the accounted size of what is kept.
