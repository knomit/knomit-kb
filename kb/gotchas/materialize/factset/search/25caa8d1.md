# A relevance list is ONE ranked list at depth MaxFactSetFacts that /search pages by offset, and the FactSet is that whole list: a text search at a smaller limit is NOT a prefix of it (the KNN window grows with the limit and filters apply after the window), so neither the list nor the FactSet ever runs a smaller window; vector ties rank by path

Since PR #735 (branch fix/relevance-list-paging; user report 2026-11-02: the "all" lens showed "Matches 50", would not scroll, and its FactSet held 500 units), the relevance results list and its FactSet are built from ONE search:

- REPO: GET /repos/{repo}/branches/{branch}/search ranks at depth materialize.MaxFactSetFacts (500) whatever `limit` is. The KNN window is k = 500 x 5 = 2500 (x 2 or x 3 under a high min_similarity), the same on every page, so pages join up. It returns the slice [offset, offset+limit) through index.SearchOptions.Page: FactQuery.search ranks and trims the list exactly as without a page, then cuts the page out BEFORE phase 2. A page therefore reads only its own bodies and runs ExtractContext only on them (SearchDiag.BodiesLoaded counts them). The text-less path pages in SQL with LIMIT min(page, 500-offset) OFFSET offset, which is exact because its ORDER BY (committed_at DESC, path ASC) is total. The response's `total` is the ranked list's length (SearchPage.Total, at most 500); `count` is the page's length. `limit` defaults to materialize.UIListLimit (50), which is now the PAGE size, not the list's length.
- FACTSET: materialize.runFactSetSearch runs that same call (factsetSearchOnce at MaxFactSetFacts) and keeps the first req.Facts rows. Unit n is row n of the list, and the list's last page ends at the FactSet's last unit. sort=recent uses RecentFacts from offset 0 at the same depth, which is an exact prefix of the /facts collection's pages.
- LENS: /lenses/{lens}/search asks every mount for federate.MaxSearchCandidates and cuts the fused, deduped union to MaxFactSetFacts rows before paging. The lens FactSet does the same fused read and keeps at most MaxFactSetFacts units, so it too equals the list.

WHY ONE DEPTH: a text search at limit 500 is NOT a prefix-extension of the same search at limit 50. In FactQuery.search (internal/engine/store/index/search_query.go) the KNN window is limit x 5 (x 2 or x 3 under a high min_similarity), and the FILTERS (type, kind, origin, path, entities, ...) apply AFTER that window, in the metadata SQL. Take 300 observations at cosine 0.9 plus type=hypothesis: a limit-50 call lists only the 5 hypotheses at 0.95 and ends SHORT, while the depth-500 list holds 30 (the 25 at 0.6 too). Pages ranked at `limit` or at `offset+limit` would end the list at 5 while the FactSet held 30.

TIES: the vector candidates come from an IN query with no ORDER BY. index.rankCandidates orders hits by cosine, highest first, and equal cosines by path ascending (stable insertion sort), so every page and the FactSet read one order. Text-less search orders by committed_at DESC, path ASC in SQL.

CONSEQUENCES:
- Do NOT rank a page at `limit` or `offset+limit`, and do NOT bring back the old "run the UI's 50 first, then extend" FactSet (PR #696). TestFactSet_IsThePagedListForFilteredText and TestSearch_OffsetPagesEndWhereTheFactSetEnds (handlers_materialize_factset_test.go) and TestLensSearch_OffsetPagesEndWhereTheFactSetEnds (internal/edge/web/lens_factset_list_test.go) go red.
- Do NOT drop the path tie-break in rankCandidates. The REST-level tests do not catch a dropped tie-break, because the metadata rows already come back in path order on the current SQLite plan; TestRankCandidates_TiesByPath (search_rank_test.go) does.
- Every /search call pays for a k = 2500 KNN and the depth-500 metadata ranking, even `?limit=10`. It does NOT pay for 500 bodies: only the page's own are read. TestSearch_PageLoadsOnlyItsOwnBodies pins this on both the vector and the text-less path. The lens legs still read every mount's whole list, bodies included, because RRF needs every list.

WHAT THIS DOES NOT MEAN:
- It does not mean the list is unbounded. Rows past MaxFactSetFacts are unreachable by offset on both routes. The lens `total` is the paged list's length, min(fused union, 500), not the number of facts that match.
- It does not mean pages are a snapshot. Each page re-runs the search over the current index. Pages over an unmoved index are contiguous and disjoint. Since #739 a new head does NOT reset the web list to page 1. The list re-reads the rows it has loaded, [0, n), with the same offset/limit paging, and keeps the reader's place (kb/architecture/web/library/keep-place/f5fe0d39.md).
- It does not cover the Recent list: repo /facts without text still pages past 500 rows (COUNT(*) total), while a FactSet caps at 500.

Origin: the first-50 design came from review of PR #692 and landed with PR #696; PR #735 replaced it with paging.
