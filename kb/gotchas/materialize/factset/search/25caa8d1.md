# A FactSet's first 50 results are the UI's own 50-row list, not a prefix of the same search at limit 500: a text search's KNN window grows with the limit and its filters apply after the window, so runFactSetSearch runs the UI's call at limit 50 first and only extends a full list; vector ties rank by path

At dev f04bc8d6, a FactSet (materialize a search) builds its result list in materialize.runFactSetSearch (internal/corpus/materialize/factset.go) like this: it first runs the very call the UI's results list makes, at limit UIListLimit = 50, and freezes that answer as the prefix. Only when that list is FULL (exactly 50 hits) AND the request's Facts is above 50 does it search again at limit Facts and append, in that second call's order, every result the prefix does not already hold. A list the UI shows short (fewer than 50) is the whole FactSet; a Facts below 50 truncates the list.

WHY a single search at limit Facts is wrong: a text search at limit 500 is NOT a prefix-extension of the same search at limit 50. In FactQuery.search (internal/engine/store/index/search_query.go) the KNN window is limit x 5 (x 2 or x 3 under a high min_similarity), and the FILTERS (type, kind, origin, path, entities, ...) apply AFTER that window, in the metadata SQL. So a filtered text search at limit 500 can return results the 50-row list never showed, and more of them.

TIES: the vector candidates come from an IN query with no ORDER BY. index.rankCandidates orders hits by cosine, highest first, and equal cosines by path ascending (stable insertion sort), so the UI's list and both FactSet calls read one order. Text-less search orders by committed_at DESC, path ASC in SQL, so its prefix is exact anyway.

CONSEQUENCE: do NOT 'optimize' runFactSetSearch into one search at limit Facts. TestFactSet_FirstFiftyAreTheUIListForFilteredText (internal/edge/web/api/kb/handlers_materialize_factset_test.go) goes red: 300 observations at cosine 0.9 fill the UI's 250-row window, so the type=hypothesis list shows only the 5 hypotheses at 0.95, while a limit-500 window also holds 25 hypotheses at 0.6, giving 30 units. Do NOT drop the path tie-break in rankCandidates either. On the current SQLite plan the metadata rows already come back in path order, so the REST-level test does not catch a dropped tie-break; TestRankCandidates_TiesByPath (internal/engine/store/index/search_rank_test.go) does.

WHAT THIS DOES NOT MEAN: it does not mean results 51..Facts are what the UI would show on a later page. They are the limit-Facts search's order with the first 50 removed, and the UI has no such page.

Origin: found in review of PR #692 (closed unmerged); the behaviour landed on dev with PR #696.
