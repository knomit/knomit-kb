# A lens member whose index has NEVER synced (SettledWatermark: empty watermark AND empty rebuild generation) is EMPTY on a lens FactSet: no roots, no search leg, not waited on, no anchor; a member settled once and now syncing or rebuilding still makes the call wait; and a path filter whose first segment is not a member's ontology topic drops that member from the fan-out

Found while building F3 (feat/lens-factset-facade).

1. SettledWatermark is settled only when the watermark is non-empty, and a store that was InitRepo'd but never synced (no write since) has an empty watermark. The N-mount sandwich requires every SEARCHED member settled (since review M1; before it, every member), so one such member that the search reads makes the call wait out factset_anchor_wait and answer ErrIndexMoved. A never-synced member narrowed out by repo=, skipped by the path filter's topic, or a read member under since_fork is not waited on (TestLensFactSet_UnsearchedUnsyncedMemberIsNotWaitedOn). The repo path has the same rule for its one mount. Production syncs every store when it opens, so it bites test fixtures first: a lens fixture member with no facts at all made the first engine tests time out at 5 s. Fix in tests: give every member at least one fact (newLensMember writes a seed fact). Before 'fixing' production, ask: an empty watermark is also what a Rebuild in progress looks like, so treating it as settled would anchor on rows being rewritten.

2. The fused lens read's target selection (federate.ReadTargetsFor) skips a member whose ontology lacks the path filter's first segment as a topic. On fixtures built with the real default ontology (the MCP lens e2e repos), search.path "kb/u/" therefore selects NO member and the lens FactSet has zero units, while the same search on the repo path finds the facts. Same as the lens list (by construction); use a real topic path (kb/architecture/...) in lens fixtures.

WHAT THIS DOES NOT MEAN: neither is a facade bug to route around per call; both are the lens list's and the anchor rule's existing semantics, inherited on purpose.

RULING (user, 2026-11-01, option b; built on fix/lens-factset-strings): item 1 above is superseded for LENS members. lensFactSetFirstPage drops a member from the searched targets BEFORE the fan-out when fsCall.neverSynced says so, so no leg reads its unsettled index, the sandwich does not wait on it, env.anchors leaves it out, and it stays an empty sub (its name still labels refs into it, ruling Lens 1). No page note, no new visible text.

THE PREDICATE: neverSynced(m) = (wm == "" && generation == "") from HistoryQuery.SettledWatermark(ctx, m.branch). Why it does not catch a member that was settled once: the watermark is set by the first sync to finish and only Index.Rebuild clears it, and Rebuild bumps rebuild_gen:<branch> BEFORE clearing last_commit:<branch>, so a rebuilding member reads ("", gen>=1) and an incrementally syncing one keeps its watermark (pending marker set): both still wait exactly as before. A first sync still in flight (no watermark yet, no generation; Index.Sync's 'full rebuild (no previous commit)' path does not bump the generation) counts as never-synced: it has no settled state to read. A deleted branch (vcs deletes all three meta keys) also reads as never-synced.

REPO FACTSETS ARE UNCHANGED: a plain repo FactSet on a never-synced repo still waits out factset_anchor_wait and answers ErrIndexMoved (searchAnchored); the ruling covers lens members only.
