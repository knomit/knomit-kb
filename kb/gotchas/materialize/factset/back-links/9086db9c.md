# A FactSet back link's target UNIT is recorded in the written prefix (wRoot/wRes/extra.unit) but its section NUMBER is not: only a target written at its designated place (result 'N', reserved 'N.k') has a number derivable without the target unit's plan

At dev 3f4a8b84 (after #702/#706/#709), fsState.lookup (internal/corpus/materialize/factset_state.go) returns a BACK link as plink{back: true, blob} with unit 0 and no number in three cases: the fact is in the extra written set (xentry.unit = the unit that first wrote it), or it is a result / reserved fact already written (wRoot[i] / wRes[i] = the first-writing unit). So the first-writing UNIT of every back-link target is known for free. Its NUMBER is not stored anywhere: a fact first written as a descendant gets a tree number 'w.x.y' assigned in planner.sections, which lives only in that unit's plannedUnit (kept plans: LRU of keptPlans = 8 per entry, factset_cache.go). Only when the target was written at its designated place is the number derivable from the frozen tables alone: a result in its own unit is strconv(unit), a reserved fact in its owner unit is 'unit.k' (planner.sections enforces this).

CONSEQUENCE: adding `number` to back links (plan Q-UI7) is NOT free. It needs either (a) storing the first-writer's ordinal beside the unit (free in xentry's padding, +2 bytes per wRoot/wRes entry) and resolving the number at page time through planUnitOf(w) (a kept plan or a re-plan of unit w alone: Depth+2 batched index reads per distinct earlier unit not kept), or (b) storing the number string per written fact (memory per written fact against session.factset_memory_mib), or (c) sending the unit only. Adding `unit` alone costs nothing.

The lens facade needs no new code for either: lensEntry.remap (factset_lens.go) already remaps FactSetLink.Unit and the first component of FactSetLink.Number for ANY link with Unit > 0; a back link's target is always in the same sub. Only its comment ('a back link carries the anchor only') would go stale.

WHAT THIS DOES NOT MEAN: it does not mean the export lacks back-link numbers. renderFactSetNode resolves them through factsetNumbers, filled in document order, so the export always knows them. The gap is only for a page whose earlier units were not sent in the same response.
