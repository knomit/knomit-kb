# Measured once (one dev laptop, this build): the 3-mount lens sandwich answers busy for 100% of first calls with writers committing back to back or every 5 ms per member, 20% at one write per 20 ms per member, 0% at 100 ms and slower; unloaded first calls take about 6 ms

TestLensFactSet_MeasureSandwichBusyRate (KNOMIT_LENS_FACTSET_MEASURE=1; CI skips it), run once on feat/lens-factset-facade: a 3-mount lens (three in-process sqlite stores, 300 text-searchable facts per member), anchor wait 5 s (the default), 20 first calls per pace, depth 1; one writer goroutine per member committing one small fact per pace (each write syncs that member's index synchronously).

- no writers: busy 0/20; latency p50 6 ms, p90 7 ms, max 13 ms
- writers back to back: busy 20/20; every call waited the full 5 s (18,257 writes)
- one write per 5 ms per member: busy 20/20; 5.0 s each
- one write per 20 ms per member: busy 4/20 (20%); p50 30 ms, p90 5.0 s
- one write per 100 ms per member: busy 0/20; p50 19 ms, p90 49 ms
- one write per 500 ms per member: busy 0/20; p50 18 ms

These numbers describe one machine, one build and in-process stores; they are not a property of the code. Do NOT derive a constant (a retry count, a deadline, a pace limit) from them. What they do show qualitatively: a lens FactSet cannot be created while any member syncs continuously, the deadline (not the retry loop) decides the latency of a busy answer, and a repo-path baseline at the same paces was not measured (follow-up if the rate matters).
