# daulet/tokenizers ships NO Windows libtokenizers.a (darwin/linux only through v1.27.0) — fetchlibs builds it from source with cargo for windows/amd64

The per-platform `internal/engine/embeddings/cgo_link_<goos>_<goarch>.go` files statically link `libtokenizers.a` (`-L dist/<platform>/lib`), so EVERY build of the main binary needs that static lib. But daulet/tokenizers publishes only darwin/linux assets — verified against the v1.27.0 release (latest) and the recent release list: there is NO `libtokenizers.windows-*` artifact at any version. A prior CI comment claiming 'daulet/tokenizers does ship a windows-amd64 static lib (v1.27.0)' was FALSE and has been corrected.

Consequence: for windows/amd64 `tools/fetchlibs` `tokenizersSpec` does not fetch (that would 404); it BUILDS libtokenizers.a from source with cargo for the x86_64-pc-windows-gnu target (needs Rust/cargo, `rustup target add x86_64-pc-windows-gnu`, and the MSYS2/mingw CGo toolchain), and `internal/engine/embeddings/cgo_link_windows_amd64.go` links it with an extra `-lntdll`. Other Windows architectures (windows/arm64) are rejected as unsupported. The upstream gap is therefore bridged by the from-source build, not a blocker; re-check upstream releases only if you want to drop the cargo step.
