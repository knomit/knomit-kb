# go build ./... fails in a fresh git worktree with "ld: library 'tokenizers' not found" — dist/<goos>-<goarch>/lib is gitignored, so run `make tokenizers-lib` or symlink dist/ in before calling a build failure a code failure

`internal/embeddings` links `libtokenizers.a` statically through a per-platform `cgo_link_<goos>_<goarch>.go` file whose LDFLAGS point at `${SRCDIR}/../../dist/<goos>-<goarch>/lib`. That directory is fetched by `tools/fetchlibs` (`make setup`, or `make tokenizers-lib` for just this library) and is gitignored, so it exists ONLY in checkouts where someone has run the fetch. A fresh `git worktree add` gets the source tree and none of dist/.

Consequence: in that worktree `go build ./...` and `go test ./...` fail for every package that transitively imports `internal/embeddings` (cmd, internal/app, tools/desktop -tags desktop, tools/calibrate, tools/motifannex, and every test binary that links them) with `ld: library 'tokenizers' not found`. Every commit on the branch reports BUILD FAIL, including ones that are known-good on the main checkout, which reads exactly like a broken refactor.

On Windows the same cause presents differently. The linker is mingw gcc, and the message is `ld.exe: cannot find -ltokenizers: No such file or directory` (cgo_link_windows_amd64.go: `-L${SRCDIR}/../../dist/windows-amd64/lib -ltokenizers`). Plain `go test` output shows ONLY `FAIL <pkg> [build failed]`, and the ld line is buried in a long gcc command. On the shared 8 GB Windows box that bare `[build failed]` was once misread as memory pressure; it was this.

How to tell it apart: `go vet ./...` and `go list -deps` do not link, so they stay green while `go build` fails. Vet clean plus a build failing at link time is the environment, not the code.

Fix before concluding anything: run `make tokenizers-lib` (and `make download-ort` if the binary will be RUN, not just built) in the worktree, or symlink the main checkout's `dist/` into it. Then re-run the build. On Windows, where building libtokenizers.a from source is slow, the cheapest fix for a throwaway review worktree is to point at the main checkout's libraries instead of fetching: `CGO_LDFLAGS=-L<main-checkout>/dist/windows-amd64/lib` for the link, plus `ORT_LIB_PATH=<main-checkout>/dist/windows-amd64/lib/onnxruntime.dll` for tests that load ONNX Runtime (internal/app). Verified: tools/desktop -tags desktop and internal/app build and pass that way.

This does NOT mean dist/ should be committed. The libraries are large per-platform binaries, and fetchlibs is the single source of truth for their versions. It also does not affect CI, which runs fetchlibs before building. It bites only local worktrees, bisects and sabotage-verification runs that start from a bare checkout.
