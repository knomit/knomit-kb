# appimagetool REQUIRES $ARCH and cannot infer it — a hardcoded value silently mislabels the runtime instead of failing the build

Found 2026-07-29 by building knomit's Linux desktop AppImage on an aarch64 VM with `ARCH=x86_64` still hardcoded in the Makefile.

`appimagetool` will not run without `$ARCH` set, but it does **not validate it against the AppDir's actual binaries**. Given the wrong value it succeeds, embedding a runtime for that architecture around a payload built for another. The result is an artifact that builds green in CI and fails only on an end user's machine.

The symptom is visible only if you look: `file Knomit-0.5.0-linux-arm64.AppImage` reported `ELF 64-bit LSB pie executable, x86-64` for an arm64 build, with a BuildID **byte-identical** to a genuinely-x86_64 build made earlier (the embedded runtime is the same file). With `ARCH=aarch64` the same AppDir produced `ELF 64-bit LSB pie executable, ARM aarch64` and a different BuildID.

**Act on this by deriving ARCH from the build's own architecture, never literalising it.** appimagetool uses `uname` names, Go uses its own, so the mapping is explicit: `amd64 -> x86_64`, `arm64 -> aarch64`. knomit does this in the Makefile via `APPIMAGE_ARCH`.

Second, separate gotcha found in the same session: the appimagetool release asset is itself per-architecture (`appimagetool-x86_64.AppImage` vs `appimagetool-aarch64.AppImage`), so a CI snippet that downloads the x86_64 one is fine on `ubuntu-latest` but wrong for a local arm64 build.

**What this fact does NOT mean:** it is not that CI was broken — GitHub's `ubuntu-latest` is x86_64, so the hardcoded value happened to be correct there. The hazard is that the failure mode is silent mislabelling rather than a build error, so it stays latent until someone builds on a different host or CI adds an arm64 runner.
