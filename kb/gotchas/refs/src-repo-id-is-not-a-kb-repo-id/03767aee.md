# A src:// ref's repo id is the SOURCE repo's root commit and matches NO mounted knomit repo — there is no source-repo registry anywhere, by design

`kb://<id>/<path>` and `src://<id>/<path>@<commit>:<blob>` both carry a 12-hex repo id, and they are DIFFERENT NAMESPACES. Confusing them is easy because the width and the syntax match exactly.

- A `kb://` id is a KNOWLEDGE-BASE STORE's root commit — `RepoInstance.ShortID()`, the value `/api/v1/repos` returns as `id` and the knomit_repos mount table shows. Live examples: knomit-kb = 3ec012f5b4d2, core = d88770a51516.
- A `src://` id is the SOURCE CODE repository's root commit, computed by the authoring agent with `git rev-list --max-parents=0 HEAD | cut -c1-12` in the checkout it is citing. For the knomit source repo that is 7b4887ce51d9.

THESE NEVER COINCIDE in practice, because a KB store is a different git repository from the code it documents.

THE CONSEQUENCE THAT BITES: `repos.Manager.NameByID(id12)` walks MOUNTED REPOS comparing ShortID, so handing it a src:// repo id returns "" — always, on every instance. Any feature of the form "resolve a src:// ref's repo to something" is dead on arrival unless it introduces a new registry. This was learned the hard way: a ref-label feature shipped a server-side id→name overlay wired to NameByID, verified green against a hand-written demo fact that happened to cite a MOUNTED KB repo's id, and could never have fired in production. The test data was shaped to fit the code instead of production.

THERE IS NO SOURCE-REPO REGISTRY, and that is deliberate, not an oversight:
- The server holds no source objects and cannot verify a src ref — stated in internal/mcp/learn.go and internal/mcp/instructions.go. Nothing in the codebase ever runs `git cat-file` for a ref.
- `Ref.Blob` is read ONLY inside internal/fact (length/hex validation). It is never handed to git.
- internal/okf's `RenderOpts.ResolveSource` is the designed hook for src→URL, and it is never populated in production. concept.go refuses to guess one from the bundle's own remote, saying a KB repo is usually a different repo from the code it documents.
- `LensRead.Source` looks like a candidate and is NOT one: internal/mcp/repos.go says outright that the slug "is NOT what a `src://` ref carries — `src://` refs are keyed by the SOURCE repo's own root commit". It is stored and echoed, never parsed or resolved.

WHAT TO DO INSTEAD: leave a src:// repo id as written. It is only 12 characters, and an unresolvable id is more honest than a guessed name.

WHAT THIS DOES NOT MEAN:
- Not "repo ids are unresolvable". A `kb://` id resolves fine against the mounted repo list — on the server via NameByID, in the browser via /api/v1/repos' `id` field. Cross-repo FACT refs can be named; source refs cannot.
- Not "src:// refs are useless without a registry". `git cat-file blob <blob>` in the right checkout returns the exact bytes forever, which is what the full 40-hex blob is for. The gap is only in NAMING the repo, not in retrieving from it.
- Not a call to add a registry. Adding one is a real feature with a config surface; it is not a bug fix.
