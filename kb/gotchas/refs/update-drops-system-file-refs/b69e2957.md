# knomit_explain lists a fact's `.knomit/<path>` refs under a separate `files` field, not under `refs.external`, so copying local + external into a knomit_update refs list silently DROPS them

Seen 2026-10-28 while updating two knomit-playbooks template facts. A ref of form (5) `.knomit/<path>` (a system file in the repo) is stored as `kb://<repo-id>/.knomit/<path>`. knomit_explain returns it in `refs.files`, NOT in `refs.local` or `refs.external`. knomit_update `refs` REPLACES the whole list (update.go builds the new list from updates.refs and runs it through the ref gate; nothing re-adds prior refs). So a caller that rebuilds the list from `local` + `external` loses every `files` entry, with no error: the update succeeds and the fact just no longer shows the file at its commit.

This is documented behaviour, not a bug: the replace rule is in the knomit-update skill and the system-file ref form in kb/architecture/refs/system-file-refs/0bbf4f93.md. What is undocumented is that `files` is a third bucket of the same list.

DO: when resending refs, send local + external + files, with each `files` entry as the bare `.knomit/<path>`. The gate then requires the file to exist at the branch tip. Restoring a dropped entry is a plain knomit_update with the full list; no other field is needed.

DOES NOT MEAN: a src:// ref to the same file is a substitute. The src ref pins a git blob at a source commit; the `.knomit/` ref makes explain read the file as it stood at the fact's commit. They are different refs.
