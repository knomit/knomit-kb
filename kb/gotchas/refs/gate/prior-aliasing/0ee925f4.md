# Passing the SAME slice as both `refs` and `prior` to refs.Gate.Apply silently disables the gate — prior must be a snapshot that can diverge from the write list

`Gate.CheckBatch` skips any ref whose classified path is in `carried := g.pathSet(prior[from])`. So a caller that writes `gate.Apply(ctx, path, refs, refs)` — the same variable in both argument positions — exempts EVERY local ref in the write, unconditionally. The call still compiles, still returns canonicalized refs, and still reads like a gate; it just can never reject anything, now or after any future change.

This is not hypothetical. `dedupCluster` in internal/synthesize/dedup.go shipped exactly that (PR #104): its merged ref list is `union(winner.Refs, loser.Refs) + loser.File`, every element of which was genuinely carried, so passing it twice was correct FOR TODAY'S code — and would have laundered any ref a later change appended to the write list before the call (a lineage pointer to a synthesized parent, an annex/motif ref).

CONSEQUENCE: when a write path's refs are all carried, build the carried set into its OWN list at the point where "every element came from an existing fact" is provably true, and pass that:

    carriedRefs := append([]string(nil), mergedRefs...)
    canonRefs, _, err := gate.Apply(ctx, path, mergedRefs, carriedRefs)

The copy is the point: `prior` must be able to diverge from `refs`, or the check is decorative. Reviewing a call site, read the two arguments as "what is being written" and "what was already carried" and ask whether anything could ever be in the first and not the second.

WHAT THIS DOES NOT MEAN: the exemption itself is not a bug. internal/refs deliberately never re-judges a carried ref — a ref is checked once, against the commit its write lands on — and removing `prior` would make one retraction anywhere in history render every fact that ever cited it uneditable. The bug is only ever the aliasing.
