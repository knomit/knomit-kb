# KNOWN FOLLOW-UP: a GitHub-hosted knowledge base's auto-merge workflow can merge AFTER main has moved since `verify ci` ran, so what lands is not the merge the gate judged; the fix (a concurrency group, or --match-head-commit plus re-checking that main has not moved) belongs to that workflow, not to this repository's code

FOUND in the PR #533 review (review 4, NIT-C); NOT fixed and not fixable in the knomit repo: the knowledge base's merge workflow (merge-agent-branches.yml, `gh pr merge --merge`) lives in each knowledge-base repository; this repository ships only the template tools/ci/verify-signatures.yml. `knomit verify ci` judges the merge of the candidate into main AS MAIN WAS when the job ran (kb/invariants/store/verify/ci-merge-result). If another PR merges between the verify step and `gh pr merge`, git merges the candidate into the NEW main, a result the gate never judged: two valid sides can still combine into an invalid fact.

FIX DIRECTION (reviewer's, not built): serialize the verify-and-merge jobs for a knowledge base with a workflow `concurrency` group, or re-check that main has not moved before merging. `--match-head-commit` pins the PR's HEAD, i.e. the candidate, and does NOT by itself pin main, so it must be paired with the main re-check.

CONSEQUENCE: do not claim 'verify ci passing guarantees the merged fact is valid'; it guarantees it for the main the job saw. Receive-pack and knomit's own merges are not exposed (they validate the merge result under the branch lock). Status: open follow-up as of 2026-10-17.
