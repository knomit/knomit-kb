# ADVICE for any forge-hosted knowledge base that adopts `knomit verify ci`: a workflow that verifies and then merges separately can merge onto a main that moved after the verify; serialize the two or pin the verified main SHA. NOT a live defect: none of the user's KB repos run it today

STATUS: advice, not a known defect. The user stated (2026-10-17) that none of their knowledge-base repositories run `knomit verify ci`, so this race is not live anywhere today. Read it when a forge-hosted KB is about to adopt CI verification; do not treat it as a bug in an existing repository or as an open follow-up of PR #533.

ORIGIN: found in the PR #533 review (review 4, NIT-C). The merge workflow (merge-agent-branches.yml, `gh pr merge --merge`) lives in each knowledge-base repository; this repository ships only the template tools/ci/verify-signatures.yml. `knomit verify ci` judges the merge of the candidate into main AS MAIN WAS when the job ran (kb/invariants/store/verify/ci-merge-result). A workflow that runs verification and THEN a separate `gh pr merge` can merge onto a main that moved in between: git merges the candidate into the NEW main, a result the gate never judged. Two shapes: a stale verdict (a member revoked after the verify still lands), and two individually valid changes combining into an invalid fact. Receive-pack and knomit's own merges are not exposed (they validate the merge result under the branch lock).

ADVICE 1, for a workflow that keeps verify and merge as separate steps: put verify and merge in ONE concurrency group so no other PR's merge can run between them; OR record the verified main SHA and merge only if main still points at it. `gh pr merge --match-head-commit` pins only the PR HEAD (the candidate), NOT main, so it does not close the race alone; pair it with the main re-check.

ADVICE 2, a single atomic command (the user's idea, POSTPONED, not built): `knomit verify merge` would fetch main and the candidate, verify against that exact main (including the merge result), create the merge with that main as first parent, push without force (git refuses if main moved) and retry a few times. Open questions before building it: branch protection (direct push versus PR-only), the workflow token's push rights; GitHub marks the PR merged when the pushed commit contains its head.

CONSEQUENCE: do not claim 'verify ci passing guarantees the merged fact is valid'; it guarantees it for the main the job saw. MISREADING: 'there is an open race in our knowledge bases' is false today; the race exists only in a workflow that adopts the gate with separate verify and merge steps.
