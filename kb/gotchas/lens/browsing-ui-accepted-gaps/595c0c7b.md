# Lens browsing UI v1 ships with named accepted gaps — cross-mount ref-hop classification, repo-scoped lens _links, at:HEAD write-repo resolution

The lenses-ui branch (34b1127..e06a5e3, final review approved 2026-07-19; post-incident sweep 2026-07-20) deliberately ships these known gaps; do not report them as new bugs, and close them knowingly:

1. **Cross-mount ref hops**: a ref inside a fact that names a fact on a DIFFERENT mount (already `kb://<other-id>/…`-qualified) passes through hop qualification untouched, but its temporal classification (live/retracted probe in useTimeTravel.resolveHopAnchor) runs against the OPEN fact's mount, not the target's. Same-mount hops are correct (qualifyHopTarget re-qualifies bare targets with the source mount's id). Pre-existing gap, not worsened.
2. **Lens fact `_links` are repo-direct URLs** (`/repos/<mount>/…`), not lens-scoped — deliberate (the handler comment documents it); the web client never follows them. A HAL-native client following links round-trips correctly but leaves the lens surface.
3. **`at:HEAD` in a lens context resolves against `state.headCommit`** — the write repo's head — even when the open fact is on a read mount. Explicit-sha `at:` anchors are fine (they resolve against the open fact's mount like scrubbing).
4. **Flat-envelope asymmetry**: lens read endpoints return flat `{facts,total}` / `{results,total}` / `{values}` (served with hal+json content-type) while their repo twins are HAL `_embedded`; lens facts `sort=` is accepted-and-ignored (recency only); per-mount 500-row snapshot bounds `total`. All deliberate; document in API docs rather than "fixing". The `/lenses/{lens}/stats` endpoint (gap 6) follows the same flat-envelope convention.
5. **Live updates watch only the write repo**: the SSE events stream (App.tsx EventSource) is repo-scoped to `state.repo` = the lens's write repo, so the union list does NOT auto-refresh when a READ mount commits; the user sees new read-mount facts only on the next manual refetch (filter change, context re-entry, reload). STILL OPEN.
6. **RESOLVED (771a608d, 2026-07-20)** — was: the browse stats panel showed write-repo-only stats in a lens context because there was no lens-wide stats endpoint. Now `GET /lenses/{lens}/stats` (internal/web/handlers_lenses_stats.go, behind LensMiddleware) fans out over federate.ReadTargetsFor reusing the repo statsProvider/activityProvider per mount — RFC §9.1 fail-whole-request on any mount error — and returns an exact-sum union roll-up (total-weighted avg_confidence, max last_commit, merged domains/entities) plus a per-repo breakdown (is_write / id12 / branch, repo= narrowing, non-null maps). RightPanel's summary view (LensStatsView) renders the union header + merged histograms over per-repo rows via api.getLensStats when lensCtx, and surfaces an explicit error (never a false "no facts" empty) when the request fails. Note the per-repo list mirrors the sibling ontology-aware skip: under a topic-delimited `path=`, a mount lacking that topic is absent from `repos[]` (decision-17 tension, accepted as consistent with facts/search).

**Why:** each was adjudicated during the wave's reviews or the 2026-07-20 sweep (see .superpowers/sdd/progress.md LENSES-UI WAVE section) as either pre-existing, deliberate design, or low-impact; fixing them was traded against shipping v1. Gap 6 was subsequently built out (union stats endpoint) once the read-endpoint pattern was established.

**How to apply:** when extending lens browsing (cross-mount walking is deferred feature #2 in the backlog), start from gap 1; when writing API docs, fold in gap 4. Gap 5 remains the natural scope of a "lens live-refresh" follow-up (union stats — gap 6 — is now done); the same SSE work that makes the union list auto-refresh would also live-refresh the stats panel.
