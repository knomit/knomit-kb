# Lens browsing UI v1 ships with named accepted gaps — cross-mount ref-hop classification, repo-scoped lens _links, at:HEAD write-repo resolution

The lenses-ui branch (34b1127..bd6b09f, final review approved 2026-07-19) deliberately ships these known gaps; do not report them as new bugs, and close them knowingly:

1. **Cross-mount ref hops**: a ref inside a fact that names a fact on a DIFFERENT mount (already `kb://<other-id>/…`-qualified) passes through hop qualification untouched, but its temporal classification (live/retracted probe in useTimeTravel.resolveHopAnchor) runs against the OPEN fact's mount, not the target's. Same-mount hops are correct (qualifyHopTarget re-qualifies bare targets with the source mount's id). Pre-existing gap, not worsened.
2. **Lens fact `_links` are repo-direct URLs** (`/repos/<mount>/…`), not lens-scoped — deliberate (the handler comment documents it); the web client never follows them. A HAL-native client following links round-trips correctly but leaves the lens surface.
3. **`at:HEAD` in a lens context resolves against `state.headCommit`** — the write repo's head — even when the open fact is on a read mount. Explicit-sha `at:` anchors are fine (they resolve against the open fact's mount like scrubbing).
4. **Flat-envelope asymmetry**: lens read endpoints return flat `{facts,total}` / `{results,total}` / `{values}` (served with hal+json content-type) while their repo twins are HAL `_embedded`; lens facts `sort=` is accepted-and-ignored (recency only); per-mount 500-row snapshot bounds `total`. All deliberate; document in API docs rather than "fixing".

**Why:** each was adjudicated during the wave's reviews (see .superpowers/sdd/progress.md LENSES-UI WAVE section) as either pre-existing, deliberate design, or theoretical-window; fixing them was traded against shipping v1.

**How to apply:** when extending lens browsing (cross-mount walking is deferred feature #2 in the backlog), start from gap 1; when writing API docs, fold in gap 4.
