# A lens's latency is the SUM of its legs with nothing superlinear in the federation layer — every verified lens slowness so far was per-leg (a fixed inference repeated once per mount, a per-row SQL callback on branches the alias table does not cover, per-repo pool plus CPU contention), and each time the federation layer was blamed first and measured last

When a read fans out over several sources, the shared fan-out layer is the plausible suspect for slowness because it is the only new structure, but the verified causes have all been per-leg costs that the fan-out merely multiplied or exposed, so a slow federated read means a slow leg or a per-leg cost repeated, and the misattribution to the shared layer survives ordinary measurement because a wall-time number is consistent with both explanations.

The three investigations and where the cost actually was:
- A FIXED COST REPEATED ONCE PER LEG. The store embeds the query whenever the options carry no vector, and the federated twins grew a loop the single-mount handler never had, so one query string was embedded once per mount — the overwhelming majority of a lens text read, linear in mount count and unrelated to corpus size. The diagnostic tell: a per-mount cost that does not shrink against an EMPTY mount is a fixed inference, not data. Fix: compute the vector once above the fan-out (web and MCP sides both), leaving the store's inner path to embed only when the vector is absent; a nil vector remains the degraded path, never an error, and vectors are never shared across different query strings or embedders.
- A PER-ROW COST INSIDE ONE LEG. A pure stemming helper registered as a SQL function is evaluated per (fact, motif) row inside the vocabulary query, but only on branches the alias table does not cover — so a freshly created agent branch pays for every row and a fully aliased branch pays nothing. The lens cost was exactly the sum of its mounts with no superlinearity and no server-side N+1; the federation and the per-request union rebuild were hypothesised and rejected by measurement. Before blaming the fan-out for a slow motif surface, check alias coverage for the branch being read, and treat any pure helper reached from a registered SQL function as being in a hot loop.
- CONTENTION THAT IS NOT WHERE IT LOOKED. The instance handle is a read lock plus a wait group — a lifetime guarantee for teardown and store swap, never mutual exclusion — so concurrent lens reads cannot serialise on it; the earlier writeup that said the fan-outs 'partly serialise on per-mount read locks' was wrong and made parallelising the fan-out look unsafe when it was safe. What remains measured but unattributed is that concurrent reads of the SAME repo do worse than the same number across different repos, pointing at the per-repo SQLite pool plus CPU; the curl harness cannot separate those, so the residual sublinear slope is OPEN and lock restructuring is not the lever.

WHAT THIS DOES NOT MEAN: it does not say federated reads are contention-free, only that the instance-level lock is not where contention lives; it does not say the pool is the cause; it does not license sharing a query vector across different strings or embedders; and it does not say the union rebuild is slow — on a fully alias-resolved branch that path is never entered.
