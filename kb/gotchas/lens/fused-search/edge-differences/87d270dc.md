# REST and MCP lens list reads: since PR #711 recency depth and repo= narrowing are ALIGNED (same function, same errors); ten intentional edge differences remain (serial REST /facts, relevance depth, filter-required, error rendering, store acquisition, logging, precedence, entity alias, total); the MCP nil-instance panic was fixed in #704

PR #704 moved the lens list read into `federate` (PlanFused + FusedSearch/FusedRecent) as a byte-identical refactor. These differences between the two former copies were found and KEPT, each via a parameter or by staying in the edge. They await a user decision. Do not unify them silently.

CLOSED by PR #711 (user ruling 2026-11-02, "align them": a lens is a virtual repo, UX as close to a repo's as possible): items 3 and 5 below. The others are still open.

1. CONCURRENCY:
   - REST /lenses/{lens}/facts reads its mounts SERIALLY: `FusedOptions{Serial: true}`, which stops at the first failure and does not recover panics.
   - REST /search and MCP (both modes) use the concurrent `FanOut`.
   - Observable only on a PANIC: serial lets it reach net/http on the request goroutine; concurrent turns it into a "panicked" MountError (REST title "Mount failed").
2. PANIC LABEL, the one behaviour change: before the PR, MCP did `defer recoverFanout(mountLabel(t.RT), ...)`.
   - That evaluated `rt.RI.Name()` BEFORE the recover was armed, so a nil RepoInstance would have panicked in a bare goroutine and killed the process (b9c7ab96 rule 3).
   - The shared FanOut uses the nil-safe label, so MCP now answers `search error: mount <branch> panicked: ...`.
   - For a non-nil instance the text is byte-identical: `mount <name>@<branch> panicked: <v>`.
   - Pinned by TestQueryFused_NilInstanceMountPanicIsAToolError (relevance and recent). Moving the label build back inside the goroutine, unguarded, crashes the test binary.
3. RECENCY DEPTH:
   - REST /facts re-derives depth: offset+limit, doubled against a merge horizon up to maxLensRecencyDepth 10000. It uses per-mount totals (`Fused.Totals`) for `total`.
   - CLOSED (#711): MCP queryRecent now calls the same federate.FusedRecentDeep with depth = need = max_results and maxDepth = federate.MaxRecencyDepth (concurrent, not Serial). Its snapshot is therefore REST /facts?offset=0&limit=<max_results>, row for row (TestLensQuery_RecentDepthIsRESTs). A text query still runs once on both. MCP returns no `total`; REST's summed per-mount total stays REST-only.
4. RELEVANCE DEPTH: REST asks 500 per mount (maxLensSearchCandidates); MCP asks max_results. The caller sets Opts.Limit.
5. CLOSED (#711): knomit_query has a `repo` argument (array, or a single string) passed as FusedQuery.Repos, the same NarrowByRepo as REST repo=. Its description is knomit_materialize search.repo's ruled S6 text, from one shared constant (repoParamDescription).
   - An unknown name is the tool error `no mount named "X" in lens "Y"`, the same text as REST's 422 "Unknown repo" detail.
   - A binding that is not a lens (!FromLens()) refuses any repo with exactly "repo is only accepted on a lens" (the FactSet's S4).
   - A one-member lens accepts its one member's name, as REST does.
   - `repo` does NOT count toward MCP's "at least one filter is required" (item 6).
   - Like every filter, it is ignored on a cursor page.
6. "at least one filter is required" applies to MCP relevance only.
7. ERROR RENDERING:
   - REST: problem documents by `PlanError.Stage`. Motif stage → WriteStoreError "Failed to resolve motif filter" with the failing mount's branch. Targets → 400. Repos → 422. Embed → 500 with the handler title. Leg failure → "Search failed" / "Failed to list facts" / "Mount failed".
   - MCP: raw text for plan errors, and `search error: ...` / `recent error: ...` for leg failures.
8. STORE ACQUISITION:
   - REST `ri.WithRead` passes the raw acquire error, which renders as 503.
   - MCP `storeIndices` maps any acquire error to errStoreUnavailable, wrapped as `mount <name>@<branch>: ...`.
9. Embedding log lines differ (lensQueryVec vs fanoutQueryVec); the vectors are the same.
10. Diagnostic logs differ: REST logLensSearchDiag after fusion; MCP logQueryDiag with raw per-mount counts.
11. Error precedence: REST validates expiry/context AFTER planning (embedding first); MCP validates everything first.
12. REST only, outside the shared function: /search forwards `entities=` only, while /facts merges `entity=`+`entities=`.

CONSEQUENCE: before "fixing" any of the OPEN items to match, ask. Item 1 is the likeliest candidate (making /facts concurrent changes only panic behaviour and latency). Item 2 is already resolved in the crash-safe direction.

NOT MEANT: these are NOT differences in ordering, failure choice, dedupe or widening. Those are now one implementation, and the goldens on both edges pin them.
