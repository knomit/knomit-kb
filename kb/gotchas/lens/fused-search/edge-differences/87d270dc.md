# REST and MCP lens list reads: recency depth and repo= narrowing ALIGNED by #711; relevance depth (one federate.MaxSearchCandidates), filter-required (gone) and entity= on /search ALIGNED by the follow-up; still intentional: serial REST /facts, error rendering, store acquisition, logging, error precedence, total; the MCP nil-instance panic was fixed in #704

PR #704 moved the lens list read into `federate` (PlanFused + FusedSearch/FusedRecent) as a byte-identical refactor. These differences between the two former copies were found and KEPT, each via a parameter or by staying in the edge. They await a user decision. Do not unify them silently.

CLOSED by PR #711 (user ruling 2026-11-02, "align them": a lens is a virtual repo, UX as close to a repo's as possible): items 3 and 5 below. CLOSED by the follow-up (PR #715, merged as 31a99271; user rulings 2026-11-02): items 4, 6 and 12. The others are still open; item 8 (store acquisition) was ruled to stay as is.

1. CONCURRENCY:
   - REST /lenses/{lens}/facts reads its mounts SERIALLY: `FusedOptions{Serial: true}`, which stops at the first failure and does not recover panics.
   - REST /search and MCP (both modes) use the concurrent `FanOut`.
   - Observable only on a PANIC: serial lets it reach net/http on the request goroutine; concurrent turns it into a "panicked" MountError (REST title "Mount failed").
2. PANIC LABEL, the one behaviour change: before the PR, MCP did `defer recoverFanout(mountLabel(t.RT), ...)`.
   - That evaluated `rt.RI.Name()` BEFORE the recover was armed, so a nil RepoInstance would have panicked in a bare goroutine and killed the process (b9c7ab96 rule 3).
   - The shared FanOut uses the nil-safe label, so MCP now answers `search error: mount <branch> panicked: ...`.
   - For a non-nil instance the text is byte-identical: `mount <name>@<branch> panicked: <v>`.
   - Pinned by TestQueryFused_NilInstanceMountPanicIsAToolError (relevance and recent). Moving the label build back inside the goroutine, unguarded, crashes the test binary.
3. RECENCY DEPTH:
   - REST /facts re-derives depth: offset+limit, doubled against a merge horizon up to maxLensRecencyDepth 10000. It uses per-mount totals (`Fused.Totals`) for `total`.
   - CLOSED (#711): MCP queryRecent now calls the same federate.FusedRecentDeep with depth = need = max_results and maxDepth = federate.MaxRecencyDepth (concurrent, not Serial). Since the follow-up, both start at the same federate.FanoutDepth(text, need) (REST need = offset+limit, MCP need = max_results): with text that is federate.MaxSearchCandidates (500) on both, so MCP's snapshot is REST /facts?offset=0&limit=<max_results>, row for row, WITH OR WITHOUT text (TestLensQuery_RecentDepthIsRESTs, TestLensQuery_RelevanceDepthIsRESTs). MCP returns no `total`; REST's summed per-mount total stays REST-only.
4. CLOSED (follow-up): RELEVANCE DEPTH is ONE constant, federate.MaxSearchCandidates (500), on REST /search, REST /facts with text, and MCP knomit_query (relevance, and sort=recent with text). REST's maxLensSearchCandidates and lensFanoutDepth are thin aliases of it and of federate.FanoutDepth. MCP max_results caps only the fused, frozen snapshot, never the per-mount depth. A per-mount depth of max_results used to drop a write-mount copy ranked below it, so its foreign kb:// twin survived write-first dedupe on MCP only.
5. CLOSED (#711): knomit_query has a `repo` argument (array, or a single string) passed as FusedQuery.Repos, the same NarrowByRepo as REST repo=. Its description is knomit_materialize search.repo's ruled S6 text, from one shared constant (repoParamDescription).
   - An unknown name is the tool error `no mount named "X" in lens "Y"`, the same text as REST's 422 "Unknown repo" detail. An explicit empty name (`"repo": ""` or `[""]`) is an unknown name too, as REST `?repo=` is; an empty LIST narrows nothing.
   - A binding that is not a lens (!FromLens()) refuses any repo with exactly "repo is only accepted on a lens" (the FactSet's S4). This check is in parseQueryRepo, so a repo-only call on a repository endpoint gets this refusal (TestLensQuery_RepoOnlyOnARepoNamesTheRepo).
   - A one-member lens accepts its one member's name, as REST does.
   - Like every filter, it is ignored on a cursor page.
6. CLOSED (follow-up): no filter is required on either surface. MCP's hasAnyFilter refusal is gone; a filterless first call is bounded by the snippet page (20 rows of ~400-rune snippets, body_truncated; include_body pages are 3), pinned by TestLensQuery_FilterlessFirstPageIsBounded.
7. ERROR RENDERING:
   - REST: problem documents by `PlanError.Stage`. Motif stage → WriteStoreError "Failed to resolve motif filter" with the failing mount's branch. Targets → 400. Repos → 422. Embed → 500 with the handler title. Leg failure → "Search failed" / "Failed to list facts" / "Mount failed".
   - MCP: raw text for plan errors, and `search error: ...` / `recent error: ...` for leg failures.
8. STORE ACQUISITION:
   - REST `ri.WithRead` passes the raw acquire error, which renders as 503.
   - MCP `storeIndices` maps any acquire error to errStoreUnavailable, wrapped as `mount <name>@<branch>: ...`.
9. Embedding log lines differ (lensQueryVec vs fanoutQueryVec); the vectors are the same.
10. Diagnostic logs differ: REST logLensSearchDiag after fusion; MCP logQueryDiag with raw per-mount counts.
11. Error precedence: REST validates expiry/context AFTER planning (embedding first); MCP validates everything first.
12. CLOSED (follow-up): REST /search now merges `entity=`+`entities=` as /facts does (a declared parameter is honoured, never silently dropped; TestLensSearch_EntityIsHonoured). The follow-up also synced the filter set: knomit_query gained exclude_type, kind, exclude_kind and ep; the REST lens reads gained applies_to (see ebd05389). Undeclared parameters: since PR #718 (merged as 18fa59a6; user ruling 2026-11-02), REST /search and /facts, both repo and lens, answer 400 `unknown parameter "<name>"` to any query parameter they do not declare (kb/invariants/web/rest/list-route-params/58392eb6.md).

CONSEQUENCE: before "fixing" any of the OPEN items to match, ask. Item 1 is the likeliest candidate (making /facts concurrent changes only panic behaviour and latency). Item 2 is already resolved in the crash-safe direction.

NOT MEANT: these are NOT differences in ordering, failure choice, dedupe or widening. Those are now one implementation, and the goldens on both edges pin them.
