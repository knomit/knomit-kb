# A federated fan-out embeds the query ONCE — SearchOptions.QueryVec is the seam; four twins of the repo /search each grew a per-mount embed

The repo-scoped /search handler always pre-embedded the query and set SearchOptions.QueryVec before searching. All FOUR federated twins diverged by embedding inside the per-mount loop instead: web lens /search, web lens /facts?q= (the Library search box), and MCP queryFirstCall AND queryRecent. Same string, one ONNX inference (~81 ms) per mount — 88% of a 5-mount lens search (464 ms), +~89 ms per mount, exactly linear (~3.6 s extrapolated at 40 mounts).

THE TELL that finds this class of defect: a fixed per-mount cost with NO relation to corpus size. An EMPTY mount cost 82.7 ms for ?q=cache and 0.42 ms for a filter-only query on the same endpoint.

The fix is the seam the repo handler already used: compute the vector once (lensQueryVec on the web side, fanoutQueryVec on the MCP side) and set base SearchOptions.QueryVec before the fan-out; the store's inner path embeds only when len(QueryVec)==0, so no mount re-embeds. Hoisting is byte-identical by construction — every mount already received a vector from the same server-wide embedder and the same string.

What this does NOT mean: it does not license sharing vectors across DIFFERENT query strings or embedders, and a nil QueryVec still degrades exactly as before (keyword-only when no embedder). The regression tests pin the inference COUNT against the mount count, with the pre-fix arm asserting the old N-per-fanout number so the defect is proven, not assumed.
