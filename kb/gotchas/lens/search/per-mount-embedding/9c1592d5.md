# A federated fan-out must embed the query ONCE — store.Search embeds whenever SearchOptions.QueryVec is empty, so N mounts meant N identical inferences

store.Search runs the embedding inference whenever `SearchOptions.QueryVec` is empty. A federated read loops over mounts, so before PR #185 every lens text read embedded the SAME query string once PER MOUNT.

Measured on a 5-mount lens: `GET /lenses/all/search?q=cache` spent 406.8 ms of 464 ms — 88% — in five EmbedQuery calls of 81.1/81.3/81.4/81.4/81.6 ms. `/lenses/all/facts?q=` had it too, at 494 ms. The cost is exactly linear, +~89 ms per mount (~3.6 s extrapolated at 40 mounts).

THE DIAGNOSTIC TELL, which is what makes this recognisable again: the cost is FIXED PER MOUNT and has no relation to corpus size. The same query against an EMPTY mount (0 facts) cost 82.7 ms; that same mount answered a text-less filter in 0.42 ms. If a per-mount cost does not shrink with a small mount, suspect a fixed inference, not the data.

Four call sites had it — web lens search, web lens `facts?q=`, and MCP `queryFirstCall` AND `queryRecent`. queryRecent counts because RecentFacts delegates to recentFactsSearch whenever there IS a text query, so the recency browse embeds exactly like the relevance one; a filter-only browse does not embed at all. Both sides of that boundary are pinned by test.

Why only the federated twins: `SearchOptions.QueryVec` has always existed for this and the repo-scoped /search handler has always set it. The twins grew a LOOP the single-mount original did not have, so the pre-existing hoist ran once per iteration instead of once per request. The fix is the seam the repo handler already used: compute the vector once (lensQueryVec on the web side, fanoutQueryVec on the MCP side) and set base SearchOptions.QueryVec before the fan-out; the store's inner path embeds only when len(QueryVec)==0.

The hoist cannot change a result: repos.Manager installs ONE embedder on every repo instance, so the N vectors were identical by construction. Verified, not argued — 14 varied lens reads captured from the pre- and post-change binaries were byte-for-byte identical. The regression tests pin the inference COUNT against the mount count, with the pre-fix arm asserting the old N-per-fanout number so the defect is proven, not assumed.

WHAT THIS DOES NOT MEAN (corrected under #372; the earlier text said a failed inference falls back per mount and 'never fail a read because a query could not be embedded', and that there is a keyword-only fallback; all three were wrong): text search is vector-only, there is NO keyword fallback. A nil vector from the hoist now means only 'no text' or 'no embedder handed in', in which case each mount embeds for itself (and a store with no embedder at all returns no hits, with a Warn). When an embedder IS present and EmbedQuery fails or returns an empty vector, fanoutQueryVec / lensQueryVec return the error and the handler fails the request ONCE, up front (MCP isError, REST 500) — one inference, not N failing ones. A read that cannot embed its text query therefore fails; it must not come back empty. It also does not license sharing vectors across DIFFERENT query strings or embedders.
