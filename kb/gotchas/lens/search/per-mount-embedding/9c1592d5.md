# A federated fan-out must embed the query ONCE — store.Search embeds whenever SearchOptions.QueryVec is empty, so N mounts meant N identical inferences

store.Search runs the embedding inference whenever `SearchOptions.QueryVec` is empty. A federated read loops over mounts, so before PR #185 every lens text read embedded the SAME query string once PER MOUNT.

Measured on a 5-mount lens: `GET /lenses/all/search?q=cache` spent 406.8 ms of 464 ms — 88% — in five EmbedQuery calls of 81.1/81.3/81.4/81.4/81.6 ms. `/lenses/all/facts?q=` had it too, at 494 ms.

THE DIAGNOSTIC TELL, which is what makes this recognisable again: the cost is FIXED PER MOUNT and has no relation to corpus size. The same query against an EMPTY mount (0 facts) cost 82.7 ms; that same mount answered a text-less filter in 0.42 ms. If a per-mount cost does not shrink with a small mount, suspect a fixed inference, not the data.

Four call sites had it — web lens search, web lens `facts?q=`, and MCP `queryFirstCall` AND `queryRecent`. queryRecent counts because RecentFacts delegates to recentFactsSearch whenever there IS a text query, so the recency browse embeds exactly like the relevance one; a filter-only browse does not embed at all.

Why only the federated twins: `SearchOptions.QueryVec` has always existed for this and the repo-scoped /search handler has always set it. The twins grew a LOOP the single-mount original did not have, so the pre-existing hoist ran once per iteration instead of once per request.

The hoist cannot change a result: repos.Manager installs ONE embedder on every repo instance, so the N vectors were identical by construction. Verified, not argued — 14 varied lens reads captured from the pre- and post-change binaries were byte-for-byte identical.

WHAT THIS DOES NOT MEAN: a nil vector is the degraded path, not an error. With no embedder, no text, or a failed inference, each mount still falls back to its own embedder, else keyword-only search. Never fail a read because a query could not be embedded.
