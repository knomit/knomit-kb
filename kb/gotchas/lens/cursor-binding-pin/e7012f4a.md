# The §7.3 cursor pin is name-based: the lens/repo collision half is CLOSED, but the pin is still not rename-stable and lens delete+recreate still resumes

Tool-session cursors are pinned to their binding by NAME plus write-mount branch (`tool_sessions.binding`; checks in `queryResume`/`explainResume`). `Binding.Name()` is the lens name for a lens and the repo name for a lens-of-one.

**CLOSED (was the original finding).** This fact previously said neither `LensRegistry.Create` nor `Manager.ValidateLens` rejects a lens named identically to a repo, so a lens `core` writing to repo `core` produced the same `Binding.Name()` on both endpoints and a cursor could resume across them. That is FIXED: `ErrLensNameConflictsRepo` exists and is enforced in `validateLensLocked` (`internal/corpus/repos/manager.go`), and its own comment cites this gotcha. Repo creation had the mirror guard (`lensNameConflict`) already. The two namespaces are now disjoint by construction, so the cross-binding resume described below is no longer reachable. Do not re-report it.

**STILL OPEN, and newly reachable.** The collision was closed by making NAMES unique — the pin is still a name. Two consequences survive:

1. *Not rename-stable.* Repo rename now exists (`Manager.RenameRepo`), so renaming a repo changes `Binding.Name()` and silently orphans every in-flight `knomit_query`/`knomit_explain` cursor against it: the next page returns "session expired". Recoverable (the client restarts the query) and cursors idle out in 15 minutes, but it is silent.
2. *Delete+recreate of a same-name lens mid-cursor* still passes both resume checks and hydrates read-mount items on the NEW pinned branch. Frozen commits still protect content and unreadable rows are skipped, so damage stays bounded.

**WHAT THIS DOES NOT MEAN.** It does not mean the binding pin is broken for distinct names — foreign-binding rejection is tested and byte-indistinguishable from expiry.

**The accepted fix, in flight.** Move the pin off names entirely onto prefixed ids — `repo:<uid>` / `lens:<uid>` — which closes both survivors at once (a renamed repo keeps its uid; a recreated lens gets a fresh one). That requires lenses to have a uid, which they currently do not. See `kb/decisions/mcp/sessions/cursor-pin-on-ids/642dc805.md` and `kb/decisions/lens/identity/lens-uid/853359e7.md`. Once that lands, `ErrLensNameConflictsRepo` stops being load-bearing for cursor soundness and survives only as a UX nicety — stop citing it as the reason the pin is sound, but do not remove it on those grounds without a separate decision.
