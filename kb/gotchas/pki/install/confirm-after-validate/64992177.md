# Asking the user to confirm a bundle's fleet root BEFORE checking the bundle against this instance's key and its own chain makes them vouch for a bundle that can never install — the key-mismatch or chain refusal then arrives only after the confirmation; run pki.PreviewBundle(keyPath, raw) first

While building knomit#299 the first cut of the CLI (and the desktop binding) previewed the bundle with SplitBundle alone — enough to get the root fingerprint — and asked for confirmation before calling InstallBundle. TestIdentity_InstallRefusals caught it: a bundle issued for ANOTHER instance's key, installed on a fresh home, came back "the bundle's fleet root … is not confirmed" instead of "not this instance's" key. The user would have been asked to compare a fingerprint for a bundle that fails anyway, and a script would have been told to add --root to a bundle that is simply wrong.

Fix: `pki.PreviewBundle(keyPath, raw)` runs checkBundle — the same checks InstallBundle runs before it takes its lock (shape, key match, chain + CRL signature of the bundle's own root) — and only then returns the root and principal to show. Both front-ends call it first; malformed / key_mismatch / chain refusals therefore arrive before any confirmation.

Consequence: when adding a confirmation step in front of an install-like operation, validate everything that does not depend on installed state BEFORE asking. What PreviewBundle cannot check (the installed-root comparison, the CRL watermark) stays in InstallBundle under its lock, so a passing preview is not a promise the install succeeds.
