# Asking the user to confirm a bundle's fleet root BEFORE every check that can refuse without their answer makes them vouch for an install that is refused anyway — run pki.PreviewBundle(keyPath, raw) (bundle, key, chain) and pki.InstalledRoot(dir) (an unreadable installed root) first, and refuse on either before asking

Two instances of the same trap, both hit while building knomit#299 (PR #310).

1. BUNDLE-ONLY CHECKS. The first cut of the CLI (and the desktop binding) previewed the bundle with SplitBundle alone — enough to get the root fingerprint — and asked for confirmation before calling InstallBundle. TestIdentity_InstallRefusals caught it: a bundle issued for ANOTHER instance's key, installed on a fresh home, came back "the bundle's fleet root … is not confirmed" instead of "not this instance's" key. Fix: `pki.PreviewBundle(keyPath, raw)` runs checkBundle — the same checks InstallBundle runs before it takes its lock (shape, key match, chain + CRL signature of the bundle's own root) — and only then returns the root and principal to show.

2. AN UNREADABLE INSTALLED ROOT (found in review). Both front ends read the installed root in a way that turned an unreadable root.crt into "no root": the binding ignored LoadRootCert's error, and the CLI used pki.Status, which leaves Root nil. So the user saw a FIRST-INSTALL question, confirmed, and only then did pki refuse (it always refuses an unreadable root). Fix: `pki.InstalledRoot(dir)` returns none only for a MISSING root.crt and an error naming the file otherwise; both front ends refuse on that error before showing anything (TestIdentity_UnreadableRootIsRefusedBeforeAsking, TestFleetIdentity_UnreadableRootIsRefusedBeforeAsking).

Consequence: when adding a confirmation step in front of an install-like operation, run every check that can refuse regardless of the user's answer BEFORE asking — the bundle's own validity and the readability of the installed state alike — and read installed state with a reader that distinguishes "absent" from "unreadable". What cannot be checked before asking (the installed root changing underneath, the CRL watermark) stays in InstallBundle under its lock, so a question that was asked is still not a promise that the install succeeds.
