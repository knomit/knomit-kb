# Under RequireAndVerifyClientCert, crypto/tls rejects an untrusted or expired client certificate BEFORE VerifyConnection runs, so the refusal carries no reason; knomit uses RequireAnyClientCert with ClientCAs nil so ONE verifier refuses everything with a named error

In crypto/tls (go1.26.6, handshake_server_tls13.go:1056-1061) the server calls `processCertsFromClient` — which, under `RequireAndVerifyClientCert`, verifies the chain against `ClientCAs` — BEFORE it calls `VerifyConnection`. So with the 'obviously strict' setting an untrusted or expired client certificate fails the handshake inside crypto/tls, `VerifyConnection` never runs, and nothing can log WHY the peer was refused. It also means two verifiers (Go's against ClientCAs, ours for CRL/SAN/fingerprint) that can drift apart.

WHAT knomit DOES: `pki.ServerConfig` sets `ClientAuth: tls.RequireAnyClientCert` and leaves `ClientCAs` nil. A certificate is still REQUIRED; ALL verification — chain to the fleet root, expiry, CRL, SAN shape, fingerprint, role — happens in `VerifyConnection` via `pki.VerifyInstanceChain`, and every refusal is logged with one of its named errors. The field carries a comment telling the next reader not to 'fix' it.

CONSEQUENCES a consumer must act on:
- `r.TLS.VerifiedChains` is EMPTY on this listener. Code that maps a request to a principal must read `r.TLS.PeerCertificates[0]`, and that is safe ONLY because no connection reaches a handler without VerifyConnection having accepted it.
- Under RequireAny, `reloader.verify` is the ONLY gate. The test file documents the sabotage: making it `return nil` turned every refusal test red (self-signed, expired, other root, revoked incl. resumed, lower CRL Number, stale CRL). Rerun that after touching verify or configFor.

MISREADING TO AVOID: this is not 'client certificates are optional' — RequireAny still refuses a client that presents none (and verify refuses an empty chain as a second line). The generalisation worth keeping: when a library's built-in verification runs before your hook, choosing the setting that switches it off can be the stricter design, provided your hook is the complete verifier and a sabotage test proves it is the only gate.
