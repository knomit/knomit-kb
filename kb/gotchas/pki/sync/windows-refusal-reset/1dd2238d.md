# On Windows a peer's TLS refusal can reach us as a connection reset or abort instead of a TLS alert, so pki's peerError does not see ErrRefusedByPeer and a refusal on a live sync can classify as `other` instead of `revoked`

WHAT WAS SEEN. In PR #537's CI (run 39037170323), build-test on windows-2025 failed once in internal/foundation/pki TestClassifyOrigin_APeerRefusingUsIsAnError: Windows reported `wsarecv: connection aborted` before the TLS alert arrived, so the error was not a *net.OpError with Op "remote error" and ErrRefusedByPeer was not produced. The branch touched neither the test nor the classifier; the rerun passed. Not reproduced since; the cause is the reading of that one failure.

WHY IT MATTERS. `peerError` (internal/foundation/pki/client.go) maps ONLY a remote alert (Op == "remote error") to ErrRefusedByPeer; anything else becomes "peer did not answer after the handshake". The fleet's refusal classes (`revoked`, `moved`, `other`, the `last_error_refusal` field on GET /fleet, from #536's classifyFleetRefusal) are built on that error, so on Windows a refusal that arrives as a reset would show as `other` (or as an unreachable peer), not `revoked`.

CONSEQUENCE. Do not read `other` on a Windows member as proof that the host sent a different alert; and treat a one-off red of that test on windows as this race before treating it as a regression. If the class must be reliable on Windows, the mapping needs to accept a reset right after the handshake as a refusal; that is not built and no test covers it.

MISREADING. "Windows never reports revoked": it usually receives the alert; the reset is a race, seen once.

TRACKED AND RELATED. The classes this race can mis-sort are defined in kb/invariants/fleet/sync/refusal-classes/7c861da6.md (revoked = the host refused a certificate valid here; moved = this instance refused the host; other = anything else, which is where a reset lands). The Windows reset itself is tracked as GitHub issue #543 (https://github.com/knomit/knomit/issues/543).
