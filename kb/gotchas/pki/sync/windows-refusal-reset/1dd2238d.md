# On a Windows CLIENT a TLS refusal by a peer that closes immediately after the failed handshake arrives as WSAECONNRESET/WSAECONNABORTED instead of the bad_certificate alert (RST discards the unread alert); knomit's listener now half-closes and drains refused connections, and the client redials once on such a reset — a reset is still never read as a refusal

WHAT HAPPENS (measured on Win10 19045, go1.26.8, #543). In TLS 1.3 the client finishes its handshake before the server judges its certificate, and writes its HTTP request. The server's VerifyConnection refuses, crypto/tls sends bad_certificate, and net/http's failed-handshake path (conn.serve) closes the socket AT ONCE (no closeWriteAndWait). Closing with the client's request unread, or receiving it after the close, makes the server's TCP stack send RST; Windows DISCARDS received-but-unread data when an RST arrives, so if the client has not yet read the alert it is lost and the first read fails: `wsarecv` Errno 10054 WSAECONNRESET (client slow after its write) or 10053 WSAECONNABORTED (client slow before its write; the message in the PR #537 CI failure). The error is *net.OpError{Op:"read", Net:"tcp", Err:*os.SyscallError(wsarecv, Errno)}, not Op "remote error", so it is not ErrRefusedByPeer. Counts against the pre-fix close: ClassifyOrigin serial 1/2000 abort, 16-way parallel under CPU load 3/2000 (2 reset, 1 abort); a client sleeping 20 ms after its handshake: 50/50 reset or abort. A half-close + drain server: 100% alert in every pattern. It is the CLIENT's OS that loses the alert (inferred: Linux keeps queued data readable after RST), whatever OS the server runs.

THE FIX (PR #741, merged to dev at 043501bb). (a) pki.NewListener (used by auth.ListenTLS) wraps each raw conn UNDER tls.NewListener; NewServer's GetConfigForClient marks a conn whose VerifyConnection refused; its Close does CloseWrite, a bounded drain (1 s / 64 KiB, at most 64 lingering per listener, else hard close), then Close. Every other close (the #258 sweep's included) stays hard. CONDITION: the mark is set only by the GetConfigForClient of a config built by pki.NewServer; pki.NewListener over any other tls.Config closes every connection hard, and refusals that never reach VerifyConnection (no client certificate, a bad CertificateVerify, the uninstalled snapshot) are not marked either. A revoked or invalid certificate, #543's path, always goes through VerifyConnection. (c) For hosts that predate (a): a reset/abort after our handshake and before any byte of the answer is redialled ONCE in ClassifyOrigin (peerAccepted) and in the fleet transport's info/refs GET (advertisedOnce); never mid-transfer, never twice; Windows only (isConnReset, matched by Errno value). Decision: kb/decisions/pki/tls/refusal-alert-delivery/526c5914.md.

REJECTED, DO NOT DO: treating a reset/abort right after the handshake as a refusal (ErrRefusedByPeer). It would need the refusal-classes invariant changed (revoked requires the bad_certificate alert text, so a mapped reset reads `other` and stops nothing), would name crashes and middlebox resets as refusals (a false `revoked` halts a healthy member's sync), and contradicts joinReachErr (reset after the handshake = unreachable) and ClassifyPeerError's no-bare-EOF rule.

CONSEQUENCES. A one-off `other` or unreachable on a Windows member against an OLD host can still be this race if the redial also lost it (about one in a million per round); the next round self-corrects. Tests that need the reset DETERMINISTICALLY (pki refusal_close_test.go) do not sleep: the client seam afterHandshakeHook blocks until the test server's ConnState reports the refused connection New->Closed (after its Close returned), an HTTPClient connection's first read also waits for its request to be written, and the old-close fixture closes with SO_LINGER 0 so it always sends RST. A 20 ms sleep was NOT enough under load (5/120 wrong outcomes under 12 parallel -race processes); the signal-driven version had 0 failures in 1440 runs; any new TLS listener for enrolled peers must use pki.NewListener or it reintroduces the reset.

MISREADING. "Windows never reports revoked": it does; the alert normally wins, and after the fix it always does against a fixed host. "Any reset after the handshake is a refusal": no — it is redialled, never classified as one.
