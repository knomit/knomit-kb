# A same-host proxy or tunnel that forwards the browser's Host unchanged (code-server's /proxy/<port>/, tailscale serve, Codespaces/dev tunnels, an nginx keeping Host) gets 421 from knomit ≥ #281 until its name is in [auth].loopback_hosts OF THE INSTANCE BEHIND THAT PROXY — add the key BEFORE upgrading, older binaries only warn about it

SHAPE. Such a proxy connects to knomit from loopback and forwards the Host the browser used. The maintainer's path is Tailscale → code-server → /proxy/<port>/. Verified in code-server 4.112.0's source: http-proxy 1.18.1 `createProxyServer({})` with no changeOrigin, targeting http://0.0.0.0:<port>. At the plain listener that request is indistinguishable from a DNS-rebound page except by the NAME. So after #281 it is refused with 421, and the detail names `[auth].loopback_hosts`.

WHICH INSTANCE. `[auth].loopback_hosts` is PER INSTANCE: each knomit reads only its own knomit.toml, and the check runs on the instance the proxy connected to. `tailscale serve` connects from 127.0.0.1 on the machine it runs on and forwards Host unchanged, so the tailnet name in a 421 (e.g. `<machine>.<tailnet>.ts.net`) identifies the MACHINE whose knomit must be reconfigured — not the machine in front of you. Observed 2026-09-27: an operator on a two-machine tailnet got the 421 from machine B's knomit, added the name to machine A's knomit.toml, restarted A, and still got the 421; A already answered that Host with 200. The 421 says "in this instance's knomit.toml and restart it" (main listener and diag port alike) and deliberately does NOT print the file's path: a DNS-rebound page is same-origin with the response and would read the data root and username. The operator has to map the instance to its machine; the Host's machine name is the pointer. Config is not hot-reloaded, so the restart is required.

FIX, zero-break order: on the machine the proxy runs on, add `loopback_hosts = ["<name>"]` under `[auth]` in THAT knomit's knomit.toml BEFORE installing the new binary, then restart it. Older binaries decode it into nothing and only log "unknown config key, ignored" (config.warnUndecoded), so nothing breaks at either step.

NOT AFFECTED:
- a proxy addressed by an IP literal (a Tailscale 100.x address);
- vite's `npm run dev` (Host localhost:5173);
- the desktop webview (127.0.0.1:<port>);
- kb over TCP or the socket;
- the OAuth listener's reverse proxy (it never runs AuthMiddleware);
- any non-loopback deployment (Docker, LAN).

WHAT LISTING MEANS: everyone who reaches knomit through that name holds [auth].loopback_default. That is what already happened silently before #281. Never list a name whose DNS you do not control; a .local mDNS name can be claimed by any LAN host. The full reasoning lives in the Go doc comment on config.AuthConfig.LoopbackHosts, not in the 421 body.

MISREADING TO AVOID: "I added the name and restarted, so the 421 must be a bug" — first check that you edited the knomit.toml of the instance on the machine the Host names.
