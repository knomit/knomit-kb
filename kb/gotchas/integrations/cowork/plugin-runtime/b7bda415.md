# A Cowork plugin's .mcp.json takes only type http/sse with a url — a stdio command entry installs cleanly and never starts, which an earlier probe mismeasured as "plugin MCP never runs"

Measured 2026-08-24 in two independent Cowork chats running an installed, enabled plugin built by `knomit-bridge cowork init --probe`, then RE-INTERPRETED the same day against the official Claude Desktop docs. The measurement stands; the conclusion first drawn from it was too general and is corrected here.

**The schema.** A plugin `.mcp.json` entry, as read by Claude Desktop (which hosts Cowork), is `{"mcpServers": {"<name>": {"type": "http", "url": "...", "oauth": true}}}`. Documented verbatim: "Each entry uses `type` (`http` or `sse`), not `transport`, and supports `url`, `headers`, and `oauth` only". There is NO stdio (`command`/`args`/`env`) shape in a plugin's `.mcp.json` on this host. Claude Code's own plugin docs DO show a stdio `command` example — the two hosts consume the same plugin FORMAT with different MCP schemas, and that mismatch is the trap.

**What was actually measured.** The probe declared `{"command": "sh", "args": [...]}`. No tool from it appeared, in either chat. That is the expected behaviour for an entry whose required `type`/`url` keys are absent — the entry is inert, not blocked. Plugin `skills/` loaded and were invocable in both chats: that is the positive control proving the plugin really was installed and enabled, so the negative is about the entry's shape, not the install. The probe's `hooks/hooks.json` SessionStart hook also never fired; that negative is unexplained and unrelated to the MCP schema.

**What does NOT follow.** "A Cowork plugin cannot provide MCP tools" does NOT follow, and neither does the original prescription to ship skills only and have the user paste an `mcpServers` entry into `claude_desktop_config.json` by hand. Only the stdio shape was ever tested. Whether a correctly-shaped `type: http` connector works — and specifically whether Claude Desktop dials it from the HOST (where a server on 127.0.0.1 is reachable) or from inside the sandboxed Cowork VM (where it is not) — is UNTESTED and is the question that decides whether a zero-config Cowork plugin is possible.

**The sandbox is real, but it may not be the dialer.** Inside a Cowork session `curl http://127.0.0.1:19278` returns exit 7, connection REFUSED — a separate network namespace, not a filtered one; `host.docker.internal` does not resolve. Independently, the docs state that Claude Desktop fetches plugin marketplaces "on the host operating system, outside the Cowork VM", so at least some plugin machinery is host-side. Do not assume the agent's shell and the MCP client share a network namespace; that assumption is exactly what makes the stdio result look like a verdict on all plugin MCP.

**A separate trap this measurement produced.** `CLAUDE_PLUGIN_ROOT` being empty in an agent's own shell is NOT evidence about Cowork. It is exported only to hook and MCP child processes, and is empty in a Bash-tool shell on a working macOS Claude Code host too — verified directly. A probe that concludes from its absence measures nothing.
