# In Claude Cowork a plugin's skills load but its MCP servers and hooks never run — the transport lives in the desktop app's claude_desktop_config.json

Measured 2026-08-24 in two independent Cowork chats running an installed, enabled plugin built by `knomit-bridge cowork init --probe`. Cowork consumes the Claude Code plugin FORMAT but not its whole runtime, and the shipped docs describe only the format.

**What loads and what does not.** Plugin `skills/` load and are invocable. A plugin's `.mcp.json` servers NEVER spawn — no tool from them appears in the session's tool list. A plugin's `hooks/hooks.json` NEVER fires — a SessionStart hook injected nothing. All three were consistent across both chats.

**The session shell is a sandboxed Linux VM with no route to the host.** `curl http://127.0.0.1:19278` returns exit 7, connection REFUSED — not a timeout. The distinction matters: a loopback interface exists in the sandbox and nothing is listening on it, so this is a separate network namespace rather than a filtered one. `host.docker.internal` does not resolve, so it is not Docker-for-Mac-style networking either. The desktop app's `vm-support-probe.json` records `virtSupport: supported`, corroborating a VM.

**The transport that DOES work is the desktop app's own config.** On macOS, `~/Library/Application Support/Claude/claude_desktop_config.json` holds an ordinary stdio `mcpServers` entry (`{"command": "knomit-bridge", "args": ["--lens", ...]}`). That process runs on the host, reaches `localhost:19278` normally, and its tools are bridged into the sandboxed session. So stdio MCP works in Cowork — what fails is a PLUGIN declaring it.

**Consequence for anything shipping a Cowork plugin:** ship skills, and install the MCP entry separately by hand in the desktop config. A bundle carrying `.mcp.json` or `hooks.json` installs cleanly and silently does nothing, which is harder to diagnose than an absent integration. `knomit-bridge cowork init` therefore renders skills only and PRINTS the desktop-config entry it cannot install; the probe machinery lives behind `--probe` as a separate plugin so re-measuring never costs the user their working skills.

**What this fact does NOT claim.** `${user_config.*}` substitution and `CLAUDE_PLUGIN_DATA` persistence remain UNTESTED, not disproven: both are delivered only to hook and MCP child processes, and neither ran, so there was nothing to observe. Whether plugin FILES are present in the sandbox filesystem is also unresolved — the one attempt used `find / -maxdepth 4`, and the bundle would sit around depth 8.

**A trap this measurement produced.** `CLAUDE_PLUGIN_ROOT` being empty in an agent's own shell is NOT evidence about Cowork. It is exported only to the hook and MCP processes the plugin runtime spawns, and is empty in a Bash-tool shell on a working macOS Claude Code host too — verified directly. A probe that tests the variable and concludes from its absence measures nothing; hunt for the bundle under `~/.claude/plugins/cache/<marketplace>/<plugin>/` instead.
