# A Cowork plugin connector is registered as a REMOTE server and dialled by Anthropic's servers — it can never reach localhost, and a stdio command entry is not a supported shape at all

Measured 2026-08-24 across two independent Cowork chats plus a direct connector-install attempt, and corrected twice the same day. Cowork consumes the Claude Code plugin FORMAT but not its runtime, and the shipped docs describe only the format.

**Connectors are dialled from Anthropic's cloud, not from your machine.** Enabling a plugin connector issues `POST /api/organizations/{org}/mcp/remote_servers`. With a loopback URL it returns 400 with this message verbatim: "url: Localhost URLs cannot be used because our servers cannot reach your local machine. Provide a publicly accessible MCP server URL." So a plugin's `.mcp.json` connector is a REMOTE MCP server registered server-side. The dialer is neither the desktop app nor the sandboxed Cowork VM — it is Anthropic's infrastructure, which must be able to reach the URL over the public internet.

**Consequence.** A Cowork plugin cannot, by any local trick, expose a server running on the user's own machine. A TLS reverse proxy in front of the local server does not help: the URL is rejected server-side at registration, before anything is ever dialled (verified — a proxy on :19443 logged zero connections across repeated enable attempts). Trusting a self-signed certificate in the macOS keychain does not help either, for the same reason.

**Named misreading.** The connector form first rejects a plain-HTTP URL with "URL must start with 'https'". That scheme check is a SEPARATE, EARLIER validation, and satisfying it does NOT bring you closer to working — an `https://localhost:...` URL then fails the localhost check above. Do not read the https demand as "add TLS locally and this will work".

**The stdio shape does not exist here.** A plugin `.mcp.json` entry on this host is `{"mcpServers": {"<name>": {"type": "http", "url": "...", "oauth": true}}}` — documented as "Each entry uses `type` (`http` or `sse`), not `transport`, and supports `url`, `headers`, and `oauth` only". An earlier probe declared `{"command": "sh", "args": [...]}` and saw nothing start; that entry was INERT for want of its required keys, and its silence was wrongly generalized to "plugin MCP never runs". Claude Code's own plugin docs DO show a stdio `command` example — same format, different MCP schema, and that mismatch is the trap.

**What still works, and is the only local route.** An ordinary stdio `mcpServers` entry in the desktop app's own `~/Library/Application Support/Claude/claude_desktop_config.json` (`{"command": "knomit-bridge", "args": ["--lens", ...]}`). That process runs on the host, reaches `localhost:19278` normally, and its tools ARE bridged into sandboxed Cowork sessions. Stdio MCP therefore works in Cowork; what cannot work is a PLUGIN declaring it, or any connector pointing at a local address.

**Other measured behaviour.** Plugin `skills/` load and are invocable — the positive control proving install and enable really happened. Plugin `hooks/hooks.json` never fired; that negative is real and still unexplained. Inside a session, `curl http://127.0.0.1:19278` returns exit 7, connection REFUSED (a separate network namespace, not a filtered one); `host.docker.internal` does not resolve.

**Still untested.** `${user_config.*}` substitution and `CLAUDE_PLUGIN_DATA` persistence remain UNTESTED, not disproven — both are delivered only to hook and MCP child processes, and on this host no such local process is ever spawned for a plugin.

**A trap this measurement produced.** `CLAUDE_PLUGIN_ROOT` being empty in an agent's own shell is NOT evidence about Cowork. It is exported only to hook and MCP child processes, and is empty in a Bash-tool shell on a working macOS Claude Code host too — verified directly.
