# FIXED (45902a74): the `.mcp.json` server key is now DERIVED from the scope, and skills use bare tool names — previously both were hardcoded to "knomit", making `claude init` structurally single-server

**Status: fixed on 2026-08-14 in commit 45902a74, with the key derivation corrected twice since (caaeac09, d7141821).** Kept because the ordering constraint and the naming convention it established are load-bearing for anyone touching this area again.

**What was broken.** `tools/bridge/claude/templates/mcp.json.tmpl` and `mcp.json.lens.tmpl` both emitted the literal `mcpServers` key `"knomit"`, parameterising only the `--repo` / `--lens` argument. A second `claude init` in the same project therefore collided on that key, so two knomit servers could never coexist — exactly the configuration a repo + lens setup wants. Compounding it, ten of the eleven skills hardcoded the fully-qualified tool name `mcp__knomit__knomit_<tool>`, which only worked BECAUSE the key was constant.

**The convention that now holds — apply it to any new skill or template:**

1. **Skills name tools bare**: write `knomit_learn`, never `mcp__knomit__knomit_learn`. A bare name resolves under any server key and cannot rot; a fully-qualified one breaks the moment the key changes, and a model facing an unresolvable tool name invents a plausible one rather than asking (`kb://bc6eac5f37df/kb/gotchas/ai/agents/tools/parameters/missing-arguments/2b9d15c8.md`).
2. **The server key is derived and names its AXIS**, by `serverKey(repoName, lens)` in `tools/bridge/claude/init.go`: `knomit-lens-<lens>` when a lens is given, else `knomit-repo-<repo>`. The prefix is applied unconditionally — see the knomit-identifiers invariant for why both properties are load-bearing and for the two collisions that motivated them.

**Two tempting simplifications of the key, BOTH of which shipped and BOTH of which were wrong.** Neither is a hypothetical; each was written, reviewed, and reverted, so the pull toward them is real:

- *Skip the prefix when the name already starts with `knomit`*, so a repo named `knomit` keeps the key `knomit` rather than the ugly `knomit-knomit` — sold as backward compatibility for projects already scoped to a knomit-prefixed name. It is many-to-one by construction (`web` and `knomit-web` both map to `knomit-web`), and it bought no compatibility at all: `.mcp.json` is merge-required, so an existing config is never rewritten in place. Removed in caaeac09.
- *One shared `knomit-` prefix for both axes.* Repos and lenses are separate namespaces validated by the same `repos.IsValidName`, so `--repo eng` and `--lens eng` both derived `knomit-eng`. Removed in d7141821. **A prefix shared by two namespaces is not a namespace.**

In both cases the collision reinstates exactly the key clobbering this whole change removed, and in both cases the doc comment asserted injectivity the code did not have. `TestServerKey_IsInjective` now enforces it.

**The ordering constraint, which is the part worth remembering.** De-qualifying the skills had to land BEFORE (or with) the key change. The reverse order leaves a window in which the key has changed but every skill still names `mcp__knomit__*`, i.e. every skill is broken. Any future change to the key derivation carries the same hazard: check what still names tools by their qualified form first.

**Why existing installs were not broken.** `.mcp.json` is a merge-required file in `claude init` — when it already exists, init writes a `.mcp.json.knomit` companion and reports a conflict instead of overwriting. Existing users therefore keep their `knomit` key, and their now-de-qualified skills keep working under it. `mcpBinding` also still recognises a `knomit`-shaped KEY as a fallback when the command is unrecognisable, though only as a lower tier than a command match.

**Also fixed in the same commit:** `tools/bridge/claude/templates/CLAUDE-md-block.txt` shipped the literal placeholder `<KNOWN_INVARIANT_PATHS>` that no Go source substituted, landing verbatim in every user's CLAUDE.md and leaving the most important recall trigger unactionable in every session. Replaced with a self-contained condition. The block marker is now versioned (`<!-- knomit:integration v2 -->`) so a stale installed block can be told apart from a current one — and as of d7141821 `blockMarkerCurrent` is READ OFF the template's first line rather than restated as a Go constant, because the hand-copy drifts silently in both directions (bump the template alone and a current block reports stale forever; bump the constant alone and every install reports current).

**This does NOT mean** multi-server support needed the tool-description headline feature. Measurement showed routing between servers is already correct without it (see the linked non-use fact); these scaffolding fixes were the whole blocker.
