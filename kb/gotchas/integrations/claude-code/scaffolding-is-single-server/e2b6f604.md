# `knomit-bridge claude init` cannot scaffold two knomit servers: both mcp.json templates hardcode the key "knomit", and ten of eleven skills hardcode the `mcp__knomit__` tool prefix

`tools/bridge/claude/templates/mcp.json.tmpl` and `mcp.json.lens.tmpl` both emit the literal server key `"knomit"`, parameterising only the `--repo` / `--lens` argument. Running `claude init` a second time therefore collides on that key — **there is no way to scaffold two knomit servers**, which is exactly the configuration the binding-aware-descriptions design exists to serve.

Compounding it, ten of the eleven skills hardcode the fully-qualified tool name `mcp__knomit__knomit_<tool>` — in `.claude/skills/knomit-*/SKILL.md` AND in `tools/bridge/claude/templates/skills/`, so it ships to every user. Any server key other than `knomit` makes every one of those names point at a tool that does not exist, and a model facing a name it cannot resolve invents a plausible one rather than asking (see `kb://bc6eac5f37df/kb/gotchas/ai/agents/tools/parameters/missing-arguments/2b9d15c8.md`).

**Consequence to act on:** the two fixes must land in this order — de-qualify the tool names in the skills FIRST (write `knomit_learn`, not `mcp__knomit__knomit_learn`; bare names resolve fine and never rot), THEN derive the `.mcp.json` key from `--repo`/`--lens`. The reverse order leaves a window in which every skill is broken.

Separately, `tools/bridge/claude/templates/CLAUDE-md-block.txt:8` ships the literal placeholder `<KNOWN_INVARIANT_PATHS>`, which no Go source substitutes — it lands verbatim in every user's CLAUDE.md, making the most important recall trigger (which paths are load-bearing) unactionable in every session.

**This does NOT mean** multi-server support needs the headline feature. Measurement showed routing is already correct without it; these scaffolding fixes are the whole blocker.
