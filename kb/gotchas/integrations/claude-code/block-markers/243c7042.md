# A block delimiter matched by substring instead of by line breaks on the file most likely to contain it — the one documenting the delimiter

Discovered 2026-09-17 on PR #213. The knomit block in a scaffolded CLAUDE.md is delimited by `<!-- knomit:integration vN -->` and `<!-- /knomit:integration -->`, and classifyClaudeMd found them with strings.Index / strings.Contains — anywhere in the text.

WHY THAT IS NOT A NEAR-MISS. The population of files this runs against is CLAUDE.md files belonging to projects that use knomit. A project explaining its own integration to contributors writes the marker in a sentence — "our knomit block is delimited by `<!-- knomit:integration v4 -->`, do not hand-edit between them". Documenting the delimiter is the single most likely way for the delimiter to appear outside the block, and the tool that reads it is the one the documentation is about. The self-referential case is the COMMON case here, not the adversarial one.

TWO FAILURES, both silent, and the safer-looking one is worse:

- A quoted OLDER marker (`v2`) became the start of the region. The replacement ran from the prose sentence through the real block's closing marker, so the sentence was destroyed and replaced by the new block.
- A quoted CURRENT marker (`v4`) hit the `strings.Contains(content, blockMarkerCurrent)` arm first, which reports the file as already up to date. A genuinely stale v3 block sitting below the sentence was therefore never repaired — and never would be, on that run or any later one, because the mention is permanent. The file advertises the current version while carrying the old block: exactly the half-merged state (marker v4, hook absent) that motivated the whole init-merge change.

THE RULE. A delimiter is a STRUCTURAL POSITION, not a string. Both markers count only when they are alone on their own line, whitespace-trimmed; classifyClaudeMd walks lines and records byte offsets rather than searching the blob. The `## Working with knomit memory` heading fallback is line-anchored too, for the same reason.

THE GENERALISATION, worth applying before writing the next marker-matcher: when a tool's delimiter is something users can legitimately WRITE ABOUT, substring matching is not a corner case, it is a design error — and it fails silently in both directions, eating content it should not have bounded and declining to fix content it should have.

WHAT THIS DOES NOT MEAN: it does not make the markers unspoofable. A prose line containing nothing but the bare marker, unquoted and unindented, is still indistinguishable from a real one — that is inherent to an in-band delimiter and is not worth defending against. It only means the ordinary way of mentioning a marker (inline, inside backticks, in a sentence) no longer collides with it.
