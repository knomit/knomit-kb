# knomit-bridge is never placed on $PATH outside the macOS .app, so Claude Code's bare-command hooks fail silently in Linux dev containers / code-server

`.claude/settings.json` wires SessionStart, PostToolUse (Edit|Write|MultiEdit, AskUserQuestion) and PreCompact hooks as the bare command `knomit-bridge claude hook <name>` — this resolves only via `$PATH`.

`.mcp.json`, by contrast, wires the knomit MCP server with an explicit path: `${CLAUDE_PROJECT_DIR:-.}/dist/knomit-bridge`. So in a Linux dev container / code-server checkout, the `mcp__knomit__*` tools work fine (explicit path) while the hooks fail (bare command, not on PATH) — the two failure surfaces look inconsistent unless you know they resolve the binary differently.

On macOS the gap is invisible because Knomit.app symlinks `Contents/MacOS/knomit-bridge` into `<home>/bin` on every launch specifically "for a stable MCP command path" (see the desktop bundle-bridge decision below) — nothing in a code-server/container environment plays that role, since there is no desktop app running.

`make dist` builds `dist/<goos-goarch>/knomit-bridge` and refreshes a stable `dist/knomit-bridge` symlink to it (Makefile `symlink_tool`), but never touches `$PATH`.

Consequence: after `make dist` in a fresh Linux/code-server checkout, symlink the built binary into a directory already on `$PATH` (e.g. `ln -sfn "$(pwd)/dist/knomit-bridge" ~/.local/bin/knomit-bridge`) or the four Claude Code hooks above will fail to run even though the MCP server itself works.

WHAT THIS DOES NOT MEAN: it does not mean the knomit MCP integration itself is broken — `mcp__knomit__*` tool calls (query/learn/etc.) work independently of this, since they go through the explicit `.mcp.json` path, not `$PATH`.
