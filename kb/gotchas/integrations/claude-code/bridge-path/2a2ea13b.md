# The bridge executable `kb` is never placed on $PATH outside the macOS .app, so Claude Code's bare-command hooks fail silently in Linux dev containers / code-server

(Executable name: `kb` since PR #218, 2026-09-18; it was `knomit-bridge` before, and any config still spelling the old name launches nothing — there is no compatibility alias.)

`.claude/settings.json` wires SessionStart, PostToolUse (Edit|Write|MultiEdit, AskUserQuestion), PreToolUse (memory-guard) and PreCompact hooks as the bare command `kb claude hook <name>` — this resolves only via `$PATH`.

`.mcp.json`, by contrast, wires the knomit MCP server with an explicit path: `${CLAUDE_PROJECT_DIR:-.}/dist/kb`. So in a Linux dev container / code-server checkout, the `mcp__knomit__*` tools work fine (explicit path) while the hooks fail (bare command, not on PATH) — the two failure surfaces look inconsistent unless you know they resolve the binary differently.

On macOS the gap is invisible because Knomit.app symlinks `Contents/MacOS/kb` into `<home>/bin` on every launch specifically "for a stable MCP command path" (see the desktop bundle-bridge decision below) — nothing in a code-server/container environment plays that role, since there is no desktop app running.

`make dist` builds `dist/<goos-goarch>/kb` and refreshes a stable `dist/kb` symlink to it (Makefile `symlink_tool`), but never touches `$PATH`.

Consequence: after `make dist` in a fresh Linux/code-server checkout, symlink the built binary into a directory already on `$PATH` (e.g. `ln -sfn "$(pwd)/dist/kb" ~/.local/bin/kb`) or the Claude Code hooks above will fail to run even though the MCP server itself works. Two-letter caveat: `kb` is also the command name of an unrelated Python package, so check `command -v kb` resolves to knomit's before blaming the hooks.

WHAT THIS DOES NOT MEAN: it does not mean the knomit MCP integration itself is broken — `mcp__knomit__*` tool calls (query/learn/etc.) work independently of this, since they go through the explicit `.mcp.json` path, not `$PATH`.
