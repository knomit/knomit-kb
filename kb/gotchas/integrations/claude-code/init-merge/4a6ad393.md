# init's .mcp.json same-key path REWRITES the entry, so a project using the derived key with a custom `command` loses that path on re-init

`knomit-bridge claude init` merges `.mcp.json` by rewriting the entry under the DERIVED server key (knomitapi.ServerKey) in place, per the init-merge decision. The consequence nobody asked for: the rewrite replaces the whole entry VALUE, including `command`. A project that uses the derived key and has deliberately set an explicit binary path — `"command": "${CLAUDE_PROJECT_DIR:-.}/dist/knomit-bridge"` — gets it reset to the bare `knomit-bridge` on the next init. Bare `knomit-bridge` does not resolve outside the macOS .app, so on a Linux dev box or code-server checkout that silently stops the MCP server from loading.

Measured on 2026-09-17 against the knomit checkout's own working copy (which had been hand-migrated to the derived key `knomit-lens-knomit-dev`): init rewrote `${CLAUDE_PROJECT_DIR:-.}/dist/knomit-bridge` to `knomit-bridge`.

The knomit repo itself is NOT exposed to this at HEAD: its committed `.mcp.json` still uses the legacy literal key `knomit`, which is the different-key case and takes the companion-file path, leaving the file byte-identical. The exposure begins the moment that key is migrated to the derived one.

WHAT THIS DOES NOT MEAN: it is not a bug in the merge — rewriting the same-key entry in place is exactly what the decision specifies, and it is what refreshes an entry pointing at a stale scope. It means the decision has an open question: whether a customised `command` should be preserved across the refresh. Raised on PR #213; not resolved there.
