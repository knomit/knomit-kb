# init's .mcp.json merge refreshes only `args` on an existing entry — `command` and every other key are the user's, because a rewritten command silently stops the MCP server loading

RESOLVED 2026-09-17 in PR #213 before merge; kept because the ownership split it established is the thing to re-read before touching this merge again.

THE HAZARD AS BUILT FIRST. `knomit-bridge claude init` merges `.mcp.json` by rewriting the entry under the DERIVED server key (knomitapi.ServerKey). The first cut replaced the whole entry VALUE, including `command`. Measured against the knomit checkout's own working copy, already hand-migrated to the derived key `knomit-lens-knomit-dev`: init rewrote `"command": "${CLAUDE_PROJECT_DIR:-.}/dist/knomit-bridge"` to the bare `"knomit-bridge"`. Bare `knomit-bridge` does not resolve outside the macOS .app (see the bridge-path gotcha), so on a Linux dev box or code-server checkout that silently stops the MCP server loading — a refresh whose only symptom is the tools going quiet.

THE RULE THAT NOW HOLDS. An existing entry under the derived key splits along OWNERSHIP, and the split is the load-bearing part:

- `args` carry the SCOPE, which init derived from --repo/--lens. init owns them and refreshes them.
- `command` is DEPLOYMENT-specific — which binary, at which path, for this machine. The user owns it and init must never write it on an entry that already exists.
- Every other key on that entry (`env`, and anything Claude Code adds later) is the user's for the same reason: init did not put it there and cannot know what it is for.

Consequences a consumer should act on: an entry already naming the right scope is left byte-identical and prints NO `Updated` line, so a summary that mentions .mcp.json means args genuinely moved; and replacing the args value does not reflow it, so a one-line `"args": ["--lens", "eng"]` comes back on one line.

WHAT THIS DOES NOT MEAN. It does not mean init never writes `command`: the no-entry-at-all case adds the whole template entry, command included, because there is nothing of the user's to preserve. It also does not mean the entry is merged key by key in general — only `args` is ever touched on an existing entry. And it does not apply to the knomit repo's own committed `.mcp.json`, which still carries the legacy literal key `knomit`: that is the DIFFERENT-key case, which takes the companion-file path and must never be migrated or renamed.
