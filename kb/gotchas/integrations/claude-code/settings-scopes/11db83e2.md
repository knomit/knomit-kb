# Claude Code merges hook entries additively across settings scopes but deduplicates IDENTICAL handlers — so init's cross-file duplicate risk is real only for a differently-spelled command

Checked against the Claude Code docs on 2026-09-17 (code.claude.com/docs/en/hooks and /docs/en/settings), because a review finding claimed knomit hooks registered at another settings scope would get a second project-level copy from `knomit-bridge claude init`.

WHAT THE DOCS SAY. Two sentences carry it, and the second is the one that changes the conclusion:

- Hook locations: "Hook entries merge across settings levels rather than replacing each other: user, project, and local settings add their own hooks without removing managed ones, and the disableAllHooks setting can't disable managed hooks from outside managed settings."
- Hook handler fields: "All matching hooks run in parallel. If you define the same handler in more than one settings file, it runs once. A plugin's or skill's copy of the same handler stays separate."

So the merge IS additive across ~/.claude/settings.json, .claude/settings.json and .claude/settings.local.json — but Claude Code DEDUPLICATES identical handlers, and a plugin's or skill's copy is deliberately exempt from that dedup.

THE CONSEQUENCE FOR `claude init`, which reads only the project file and cannot see the other scopes:

- User-level registration with a command string BYTE-IDENTICAL to the one init writes: init adds a project-level copy, Claude Code dedups, the hook runs once. Redundant in the file, harmless at runtime.
- User-level registration with a DIFFERENT spelling of the same hook — `/usr/local/bin/knomit-bridge claude hook post-edit` at user level against init's bare `knomit-bridge claude hook post-edit` at project level — is NOT the same handler, so both run and the hook fires twice per tool call. This is the case that bites, and it is the likely one: knomit-bridge is not on $PATH outside the macOS .app, so a user-level registration is exactly the one most likely to be path-prefixed (see the bridge-path gotcha).

Note the asymmetry with knomit's own rule: init normalises `claude hook <event>` spellings to ONE identity when deduplicating WITHIN the project file, but Claude Code's cross-scope dedup is on the handler as written. knomit's normalisation does not extend across scopes and cannot, because init never reads the other files.

WHAT THE DOCS DO NOT SAY: they never define "the same handler". Identical command string is the reasonable reading and matches observed behaviour, but it is not stated, so do not build anything that depends on a looser notion of sameness.

SUPPORTING: the docs put "hooks" in the Shared project scope's "use it for" column ("Team permissions, hooks, plugins, and the environment variables the project needs"), which confirms `.claude/settings.json` is the right file for init to write — the question is only what to do about registrations init cannot see.
