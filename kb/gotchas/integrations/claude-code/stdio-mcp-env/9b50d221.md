# Measured on Claude Code 2.1.287 (2026-10-02): a stdio MCP server started from `claude -p --strict-mcp-config --mcp-config '<json>'` INHERITS claude's own environment (an arbitrary marker var and KNOMIT_SERVER both arrived, with PATH and HOME) — so a recipe-set KNOMIT_SERVER reaches the session's `kb` without the MCP config carrying it

PROBE (2026-10-02): a /bin/sh stdio MCP server that writes `env` to a file, then answers initialize and tools/list. Run: `KNOMIT_SERVER=unix:///probe/inherited.sock PROBE_MARKER=parent-env-42 claude -p 'Reply with the single word ok.' --model haiku --strict-mcp-config --mcp-config '{"mcpServers":{"probe":{"command":"<abs path>/dump.sh","args":[]}}}' --max-budget-usd 0.05`. Exit 0. The server's environment (71 variables) contained KNOMIT_SERVER=unix:///probe/inherited.sock and PROBE_MARKER=parent-env-42, plus claude's PATH and HOME.

CONSEQUENCE: knomit's recipe child (the `claude` process) gets KNOMIT_SERVER in its environment from recipeEnv, and the `kb` Claude Code starts inherits it, so examples/mission work-task.js and examples/recipes/claude-session.js put no address in mcp.config. If a future Claude Code version stopped passing the environment through, the session's kb would fall back to the lockfile/default — the wrong-instance bug — and the fix is an `env` block in the MCP server entry (`{"command":"kb","args":[],"env":{"KNOMIT_SERVER":"..."}}`).

WHAT THIS DOES NOT ESTABLISH: it is one version, one transport (stdio), one launch mode (headless -p with --mcp-config). It says nothing about other MCP hosts (Claude Desktop, Cowork, Antigravity) or about servers configured in .mcp.json / user settings. A limit measured on one build is not a property of the code: re-measure before relying on it for another host.
