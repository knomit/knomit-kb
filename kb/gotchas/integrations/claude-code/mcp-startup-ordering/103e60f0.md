# A Claude Code session connects MCP servers ONCE at startup: knomit must be listening before the session launches, or that session has no knomit_* tools for its whole life

The knomit server process must ALREADY be listening on its port when a Claude Code session starts. Claude Code connects each configured MCP server once, during session startup; a server that is down at that instant is marked failed for the ENTIRE life of that session and is never retried. There is no reconnect-on-demand.

Observed 2026-09-17: the reviewer session started before `./dist/knomit serve` came up (server started 11:26, session earlier) and reported `knomit-lens-knomit-dev (-32603): "http request: Post http://localhost:19278/api/v1/lenses/<lens>/mcp: dial tcp [::1]:19278: connect: connection refused"`. Every `knomit_*` tool was absent for the whole session even after the server was healthy.

THE ERROR TEXT MISDIRECTS. It names `[::1]`, which reads as an IPv6-binding bug — the server binds 127.0.0.1 only, so `curl http://[::1]:19278/...` does fail while `curl http://127.0.0.1:19278/...` succeeds. That is a red herring: Go's dialer tries ::1 first and reports only the first address on failure, and it falls back to 127.0.0.1 fine when something is listening. Verified by running `./dist/knomit-bridge --lens <lens>` by hand against the live server: it logs `url: http://localhost:19278/...` and gets `status: 200`. Do not go looking for a dual-stack/bind fix; check whether the server was up at session start.

OPERATIONAL CONSEQUENCE. Start (or confirm) the knomit server BEFORE launching a session, especially when spawning master/worker/reviewer sessions in parallel — a session launched during the server's startup window silently loses knomit for its whole run, and its recalls become no-ops that report nothing wrong. A session already in that state cannot be repaired by starting the server; it needs a restart, or the workaround below.

WORKAROUND WITHOUT RESTARTING. The lens HTTP endpoint is reachable directly, so an affected session can still read and write the corpus by speaking JSON-RPC over curl: POST `initialize` to `http://127.0.0.1:19278/api/v1/lenses/<lens>/mcp` with `Accept: application/json, text/event-stream`, capture the `Mcp-Session-Id` response header, POST `notifications/initialized`, then POST `tools/call` requests threading that header. This is how the 2026-09-17 reviewer session ran its recall.

WHAT THIS DOES NOT MEAN: it does not mean the hooks are dead too. Hooks are separate — they shell out to `knomit-bridge claude hook <event>` per invocation and resolve the binary via $PATH, so they keep working in a session whose MCP connection failed (and fail independently when the binary is off $PATH, which is a different problem). A session with no `knomit_*` tools may still be writing session-start and post-edit hook traffic normally.
