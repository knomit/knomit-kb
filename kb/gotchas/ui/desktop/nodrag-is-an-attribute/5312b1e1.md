# In the top bar `--wails-draggable: no-drag` and the `data-nodrag` ATTRIBUTE are not interchangeable — startWindowDrag bails on closest('[data-nodrag]'), so a control with the CSS var alone starts a window drag and eats its own click

The CSS custom property speaks to wails. The JS handler does not read it: `startWindowDrag` returns early only when `e.target.closest('[data-nodrag]')` matches. A control carrying the var alone therefore begins a native window drag on mousedown, and the drag swallows the click — on desktop the control barely responds.

Both forms are needed on any interactive element in the bar, for two different consumers.

THE INVERSE MATTERS TOO. A NON-interactive label must keep dragging: making the branch chip an unconditional `<button>` with no-drag punched a dead hole in the title bar wherever no handler was wired. The chip is now a `<button>` with both no-drag forms when it opens the picker, and a plain draggable `<span>` otherwise — element and drag treatment follow the behaviour.

A TEST MUST ASSERT BOTH DIRECTIONS. Pinning only "it does not drag" passes on a build where nothing drags; pinning only "it drags" passes on one where the picker is unclickable.

SIBLING of gotchas/ui/desktop/topbar-drag-region-ancestor, which is about WHERE the tag must sit (an ancestor of both trigger and menu). This one is about WHICH tag — the attribute the handler actually reads, versus the property only wails sees.
