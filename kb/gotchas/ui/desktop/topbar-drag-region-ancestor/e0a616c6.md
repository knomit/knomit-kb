# A floating menu in the top bar needs `data-nodrag` on an ancestor of BOTH trigger and menu — a tag on the trigger alone leaves the menu's options unclickable on desktop

**The mechanism.** `TopBar` makes the whole bar a window-drag handle: `startWindowDrag` fires on the bar's `onMouseDown` and posts `wails:drag` over the WKWebView / WebView2 message transport, bailing only when `(e.target as Element).closest('[data-nodrag]')` matches. `closest()` walks the target and its ANCESTORS. Nothing else cancels it.

**The trap.** A menu rendered as a SIBLING of its trigger has no tagged ancestor, even when the trigger itself carries `data-nodrag`. Mousedown on a menu option therefore posts `wails:drag`, the native drag loop swallows the click, and the option cannot be activated at all on the desktop build — while working perfectly in the browser and in jsdom, where no native drag loop exists. `MountsPicker` shipped exactly this: a tagged trigger, an untagged sibling menu, and a picker whose every option was dead in the app.

**Consequence to act on.** When adding ANY control to the top bar that opens a floating surface, put `data-nodrag` on the node that CONTAINS both the trigger and the surface — the positioning wrapper, not the trigger. Two legal shapes:

1. Tag the common wrapper (what `MountsPicker` does — the wrapper is already needed as the menu's containing block, so an absolute menu resolves against it rather than against the whole top bar).
2. Render the menu through `createPortal` so it is not inside the drag region at all (what `TopBar`'s own switcher menu does).

**Second half: `-webkit-app-region` is inert here.** WKWebView ignores it. Wails gates dragging on the inherited `--wails-draggable` custom property, which is why `TopBar` sets `{'--wails-draggable': 'no-drag'}` alongside every `data-nodrag`. `MountsPicker` carried a `WebkitAppRegion: 'no-drag'` that had never done anything; a control that sets only that has no protection whatsoever. Belt and braces is the house style: set both, because `data-nodrag` guards the explicit postMessage path and `--wails-draggable` guards the runtime's own.

**What this does NOT mean.** It is not about z-index or pointer-events — the menu receives the mousedown fine; the drag simply starts first. And it is not testable by asserting the trigger alone: the enforcing test (`describe('the desktop drag region')` in `MountsPicker.test.tsx`) asserts `closest('[data-nodrag]')` from EVERY rendered option, not just the container, because the drag check runs from the actual mousedown target.
