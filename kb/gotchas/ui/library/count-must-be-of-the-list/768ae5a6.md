# A count rendered beside a list must be OF that list — the pivot heading printed the cluster's carrier_count, so the one number a reader checks to see whether a filter worked was the one number that could not move

The Library header's count printed the motif cluster's `carrier_count` while pivoting, on the grounds that it was the same number said more directly. It is the same number ONLY for as long as nothing else narrows the list. Add `domain:reliability` to a pivot and the rows went **14 → 8 while the number beside them went on saying 14**.

It reached a reader as *"adding a domain or entity chip after a pivot has no effect."* The filtering was never broken. Two things hid that:

1. The picker lists `agentic engineering` first, and all 302 facts in that repo carry it — so that particular chip genuinely changes nothing, and the first thing a reader tries confirms the wrong diagnosis.
2. The real bug: the heading's number ignored every chip but the motif. **The one reading a reader checks to see whether their filter did anything was the one reading that could not move.**

**Fix (PR #180, 2026-08-31):** `MotifPivot.carrierCount` is deleted; the header renders the same `count` every other mode renders. One number, one source. `carrier_count` still exists on the cluster and is still the right number in the motif panel and the vocabulary rows — the bug was not the field, it was drawing it beside a differently-scoped list.

**THE SHAPE WORTH KEEPING.** Two quantities that agree in the common case are not thereby the same quantity — **and a test whose fixture makes them equal cannot tell you which one you are reading.** `Library.pivot.test.tsx`'s mock returned 26 for the cluster AND 26 for the list total, so it passed against both implementations and reviewed clean. The regression test now returns a narrowed total that is deliberately NOT the carrier count, and was checked by SABOTAGE: pinning the header to a constant fails it.

**Operational consequence.** Any count drawn next to a collection — facet rows, edge cells, health strips, a pivot heading — must be computed from the collection it sits beside, or must say in the UI what else it is counting. (The motifs block already states one such contrast outright: its health strip is authored-facts-only and never narrowed by the search, while its header count IS.) And any fixture pinning such a pairing must give the two quantities DIFFERENT values, or it is testing nothing.
