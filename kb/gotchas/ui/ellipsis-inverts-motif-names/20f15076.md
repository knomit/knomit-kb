# Right-truncating a motif name INVERTS its claim — a motif is a compressed sentence whose claim lives in the tail, so ellipsis is banned; names render whole or fold into a counted +N

A motif name is subject-predicate-object compressed into kebab-case, and the claim sits at the end: `failure-presents-as-…` is the OPPOSITE claim of failure-presents-as-success; `stated-limit-not-…` reads as 'not stated'; `configured-limit-n…` loses the entire point. This is the inverse of a file path, where the tail merely locates and head-truncation is the convention — so the app's existing truncation habit is exactly the wrong reflex here.

The repair (shipped in PR #177): names render WHOLE or not at all; overflow is a counted `+N` cell opening the panel where every name is whole; at widths where nothing fits, the segment degrades continuously to the `≈ +N` counter. The same argument applies one level up to blind DEFINITIONS — the sentence's point is usually in its second half — so definitions wrap rather than clip (a review finding caught nowrap+ellipsis on the vocabulary block's definition and it was removed).

How to apply: any new surface showing motif names or definitions must not use textOverflow ellipsis on them; carrier TITLES may still ellipsize (they identify, not claim).

(Naming note, PR #180: the vocabulary block is `MotifsBlock`, formerly `ShapesBlock`. The rule is unchanged; only the component's name moved — see kb/decisions/ui/motif/vocabulary-fourth-block/b5534397.md.)
