# App and Library both register window keydown listeners, so preventDefault in one does not stop the other — a modified arrow fired both handlers

Two independent `window.addEventListener('keydown', …)` handlers are live at once: App's (global commands — /, Escape, Backspace/Delete, ⌘[ / Alt+←) and Library's (list navigation — arrows, j/k, Enter). They are SIBLINGS on the same target, so `e.preventDefault()` in one does not stop the other, and `stopPropagation` would not either at the same target/phase.

THE BUG THIS CAUSED: adding Alt+← as Back in App made a single keypress dispatch NAV_BACK from App and GO_UP from Library — the location moved TWO levels for one press. Nothing in either handler was wrong on its own.

THE RULE NOW: the Library owns BARE arrows only and returns early on `e.metaKey || e.ctrlKey || e.altKey`; modified keys belong to window-level commands in App. Bare ArrowLeft is still GO_UP — Up and Back are different controls and both exist.

RELATED ORDERING RULE, same handler: App checks ⌘[ / Alt+← BEFORE its `tag === 'INPUT'` and `rightPanelFocused` guards. Those guards stop LIST keys firing in the wrong place, and neither reason applies to a chord nothing types. Backspace/Delete stay behind them, because those do type.

WHAT THIS DOES NOT MEAN:
- Not "add stopPropagation". Both listeners are on `window`; propagation is not what orders them. The fix is that exactly one handler claims each key combination.
- Not "consolidate the handlers". They have different guard conditions (Library additionally gates on rightPanelFocused and on being live) and different lifetimes.
- Not confined to arrows: any new global chord must be checked against Library's bare-key set, and any new Library key against App's.
