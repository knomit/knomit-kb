# CORRECTED: OS directory logic DOES belong in internal/platform — it never needed the app name. Only the name constants stay outside, and they belong to an existing owner (internal/config), not to a package of their own

This fact previously argued the opposite, and the argument was wrong in a way worth keeping visible because it is an easy one to repeat.

THE ORIGINAL CLAIM: the platform tier's "take the knomit type as a parameter" escape hatch (logging.Options) does not extend to the app NAME, because parameterising a directory literal would put that literal back at every call site and give three binaries three chances to disagree — so the whole path helper had to live outside internal/platform.

WHY IT WAS WRONG: it rejected the wrong design. Parameterising the name was never the only way in. The OS logic — which directory Windows/macOS/Linux designate, the %LOCALAPPDATA% reconstruction, the XDG lookup, the refusal to guess when nothing resolves — NEVER NEEDED THE NAME AT ALL. Split by what each half knows and the tension disappears:

- internal/platform/userdirs returns BASE directories (StateDir, HomeDir) with nothing joined on. No app name, no parameter, no knowledge of any application. It satisfies the tier's property outright.
- The caller joins its own name on. There is still exactly ONE spelling of it, so the single-owner goal that motivated the helper is fully preserved.

THE GENERAL SHAPE, which is the reusable part: when a helper looks like it cannot enter a tier because it mixes two kinds of knowledge, check whether the tier-appropriate half is SEPARABLE before concluding the tier is wrong. "It needs app knowledge" was true of the package as written and false of the OS logic inside it.

A SECOND CORRECTION, from the same review: the app half did not deserve a package either. Two string constants ("knomit", "home") plus the functions applying them are not a package; they belong to an existing owner. They now live in internal/config, which already owns Config.Home — "where does the data root go by default" is the same question one step earlier. internal/apppaths is DELETED.

CONSEQUENCE for anyone placing a new helper: the archtest (TestPlatformKnowsNothingAboutKnomit) checks IMPORTS only, so it would have passed either way — it never contradicted the old placement and does not endorse the new one. The tier's documented property is what decides, and it is decided per HALF, not per package.

WHAT THIS DOES NOT MEAN: the parameterisation caution itself still holds. Threading an app name through a platform API as an argument would still scatter the literal and is still the wrong fix. The point is that it was a false choice — not that it was acceptable after all.
