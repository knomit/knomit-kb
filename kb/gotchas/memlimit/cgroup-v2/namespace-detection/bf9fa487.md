# A cgroup2 mount's ROOT FIELD in /proc/self/mountinfo is rendered relative to the reader's cgroup namespace — that is what distinguishes a namespaced process from a genuine root-cgroup host process

The Linux kernel renders a cgroup2 mount's root field (field 4 of a /proc/self/mountinfo line) RELATIVE TO THE READING PROCESS'S cgroup namespace root, via cgroup_show_path. When the mounted cgroupfs root is an ANCESTOR of the reader's namespace root — the state produced by entering a cgroup namespace without remounting cgroupfs — the field cannot be expressed downward and renders with `..` components.

Measured on Linux 6.1.0-44-amd64 on 2026-08-29, same binary, three states:

  host process, no cgroup ns (falling through to physical RAM is CORRECT):
    32 22 0:27 /         /sys/fs/cgroup ... - cgroup2 cgroup2 rw,nsdelegate,...
  `unshare -Cr`, cgroup ns with NO cgroupfs remount (falling through is WRONG):
    32 22 0:27 /../../.. /sys/fs/cgroup ... - cgroup2 cgroup2 rw,nsdelegate,...
  cgroup ns + mount ns + fresh cgroup2 mount (the real container shape):
    254 193 0:27 /       /tmp/.../cg2   ... - cgroup2 none rw,nsdelegate,...

In the same namespaced process /proc/self/cgroup reads `0::/` in BOTH the second and third cases, which is why the cgroup path alone cannot tell them apart.

CONSEQUENCE for anything sizing itself from a cgroup memory limit (internal/memlimit): when /sys/fs/cgroup's cgroup2 mountinfo root field is not `/`, the mount does not correspond to /proc/self/cgroup's view, so failing to find memory.max is NOT evidence of "no limit" and must not be reported as os-total. Reporting physical RAM there over-reports — the unsafe direction, since the whole point is preventing an OOM. The same check also catches a runtime that bind-mounts a cgroup subtree without a cgroup namespace, where the root field is a real subpath rather than `..`.

A SECOND, independent recovery signal: in the namespaced-without-remount state the entire host cgroup tree is still readable — only the identity of your own node is lost. Scanning every cgroup.procs under /sys/fs/cgroup for your own PID recovers it exactly (measured: pid 649093 -> /sys/fs/cgroup/system.slice/system-code\x2dserver.slice/code-server@pba.service; 68 cgroup.procs files, ~7 ms for the whole find). cgroup.procs renders PIDs in the READER's pid namespace, so this still works when the pid namespace is unshared as well. Run it only when the mountinfo check reports misalignment, then do the normal ancestor walk from the node found.

RULED OUT as a signal: comparing /proc/self/ns/cgroup against /proc/1/ns/cgroup. Reading or stat-ing /proc/1/ns/* requires ptrace access and returns EPERM for an ordinary non-root process — measured on the same host.

WHAT THIS DOES NOT MEAN: it does not mean the mountinfo root field tells you the limit, or that a `/` root field proves you are unconstrained. It only tells you whether /sys/fs/cgroup and /proc/self/cgroup describe the same namespace view, i.e. whether a "no memory.max found" reading may be trusted.

This FALSIFIES the KNOWN LIMITATION note on cgroupV2Limit and the accompanying TestDetect_NamespaceWithoutRemount_OverReports (both added in cb40bb4b), which assert the over-reporting state is "not fixable from inside the process" because it is "byte-identical to an ordinary unlimited host process sitting at the root cgroup". It is not byte-identical: /proc/self/mountinfo differs.
