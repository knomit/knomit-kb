# The token "knomit" is AMBIENT across every integration surface — a directory, a config key, a tool prefix, a transcript substring — so matching on the name is never evidence, and four separate defects came from treating it as such

"knomit" simultaneously names the product, the binary (`cmd/root.go` `Use: "knomit"`), the app-state directories (`~/.knomit`, `Library/Application Support/knomit`), the git committer (`knomit`/`knomit@local`), the MCP protocol server NAME advertised by `NewMCPServer`, the derived per-scope `.mcp.json` server KEY, the Antigravity plugin DIRECTORY, and — because the checkout is `.../knomit/knomit` — an ordinary path segment in every developer's cwd. Four separate defects came from code or analysis that treated an occurrence of that token as identifying one of them.

**1. A directory named knomit is not the plugin dir.** `locatePluginDir` checked `filepath.Base(cwd) == pluginDirName` with an UNCONDITIONAL EARLY RETURN and no check that an `mcp_config.json` was present. A workspace itself named knomit satisfied it, returned the workspace root, and skipped both remaining probes — greeting the user on every conversation with advice that could not fix it while a good plugin dir sat one level down. Fix: `... && isPluginDir(cwd)`.

**2. Nothing may look the MCP server up by literal key.** The key used to be the constant `"knomit"`, which made a second `claude init` collide and two knomit servers impossible. It is now DERIVED per scope and names its AXIS — `knomit-lens-<lens>` or `knomit-repo-<repo>` — and `mcpBinding` selects primarily by `filepath.Base(srv.Command) == "knomit-bridge"`. A `knomit-`shaped KEY is only a lower-tier GUESS, counted solely when nothing matched on command, so an unrelated server that merely borrowed the namespace (`knomit-notes`) cannot dilute a real match.

**3. A prefix shared by two namespaces is not a namespace.** Repos and lenses are separate namespaces validated by the same `repos.IsValidName`, so the first cut's `knomit-<name>` mapped `--repo eng` and `--lens eng` to one key — re-creating the clobbering one level down, while the doc comment asserted an injectivity the code lacked. `TestServerKey_IsInjective` enforces it now. The mirror error also shipped: skipping the prefix when the name already carries it is many-to-one by construction (`web` and `knomit-web` both → `knomit-web`).

**4. The same trap in a MEASUREMENT, not in code.** Of 998 subagent briefs, **832 (83%) mention "knomit" ONLY because the project directory is named knomit** — so a naive grep reports ~95% coverage and suggests the guidance is reaching subagents and being ignored. It is not reaching them: 2 (0%) carry the CLAUDE.md block, 0 (0%) carry "knomit as long-term memory", 12 (1%) name any `/knomit-*` command.

**THE RULE THEY JOINTLY SUPPORT.** A name match is a HINT; corroborate it with a property only the real referent has — a file that only the real directory holds, the command basename rather than the config key, a derived key that names its axis, the block's actual text rather than the product substring. And when the corroboration FAILS, fall through to the remaining probes rather than returning: in case 1 the extra probes were already written and correct, and the defect was purely the early return.

**WHAT THIS DOES NOT MEAN.**

- *Not* "stop trusting cwd" — cwd remains the primary and correct source for the plugin dir, and the `workspacePaths` fallback exists for a platform change to hook cwd, not for that bug. Nor is it "validate more": a name check that falls through on failure would have been harmless.
- *Not* that the derived server key is now free-form. It is produced by exactly one function, must stay injective across scopes AND across axes, and is length-bounded (`maxServerKeyLen` 39, `maxScopeNameLen` 27) so `mcp__<key>__knomit_hypothesize` stays under the API's 64-character tool-name limit.
- *Not* that the other referents became renameable. The MCP protocol server NAME, the git committer identity, and the binary/app-state names all stay; only the config KEY moved. Do not conflate the protocol name with the config key — Claude Code builds the tool prefix from the key.
- *Not* that ambiguity should always fail safe. Two entries resolving to the SAME `(repo, lens)` are not ambiguous, and a fail-safe firing there fires on nothing — `.mcp.json` is merge-required, so re-running init routinely leaves a duplicate naming one repo.
- *Not*, for case 4, that injecting context is sufficient to make subagents CAPTURE — that remains a hypothesis; what it definitely fixes is subagents working blind against invariants. And do not conclude the main thread is fine: 62% of the 139 sessions with >= 5 edits captured nothing.

**Where breakage lands.** Silently, and at a distance — in skills and `.mcp.json` files rather than next to the definition, and in analyses that report a percentage of the wrong population. When changing anything here, grep for the literal AND add a test that pipes the PRODUCER's output into the consumer; every `mcpBinding` test hand-built `.mcp.json` with the literal key, which is why a producer/consumer split was caught in review rather than by tests.
