# The Windows pipe name is a hash of the data root, lower-cased and cleaned first — Windows paths are case-insensitive, so hashing the raw string would give C:\Users\x and c:\users\x two different pipes and silently lose the bridge's identity

config.SocketPath() and config.Load both resolve the local listener through one per-platform localListenerName(home): `<home>/knomit.sock` on unix, and on Windows `\\.\pipe\knomit-<first 8 bytes of SHA-256>` of the data root.

The name CARRIES the data root because the pipe namespace is flat and machine-wide — a pipe cannot sit inside the root the way a socket file does. It is derived from the root and nothing else, so two instances with different roots get different pipes and one with the same root gets the same pipe, which is what lets `kb` find `knomit serve` with nothing configured.

THE ROOT IS filepath.Clean'd AND LOWER-CASED BEFORE HASHING, because Windows paths are case-insensitive: C:\Users\x\knomit and c:\users\x\knomit are ONE directory, and a bridge that hashed one while the server hashed the other would find no pipe and fall silently back to TCP. Same failure shape as the data-root drift recorded in the header of internal/config/paths.go; nothing raises an error anywhere.

The 8 bytes are a collision boundary between data roots on one machine, NOT a security boundary — the pipe's ACL is that.

The `\\.\pipe\` prefix is spelled in BOTH internal/config (which builds the path) and internal/auth.PipePrefix (which recognises it when opening or dialling), because internal/auth has no knomit dependencies by design. TestSocketPath_IsOpenableAndDialableByAuth (internal/config/localpipe_windows_test.go) pins them together by round-tripping a real listener through both and reading a peer off it, rather than by comparing the constants.
