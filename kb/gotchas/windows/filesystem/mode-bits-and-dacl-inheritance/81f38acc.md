# On Windows, Go's file modes are NOT permissions: os.WriteFile/OpenFile perm sets only FILE_ATTRIBUTE_READONLY, Chmod toggles only that bit, Mkdir ignores the mode, and Stat().Mode().Perm() reads 0666 (0444 if read-only); a file's DACL is inherited from its directory, and a temp-file-plus-rename write REPLACES the target's DACL with the temp file's inherited one

**Measured (worker session, 2026-09-26, go1.26.8 windows/amd64, x/sys v0.46.0).** syscall.Open passes a SECURITY_ATTRIBUTES with no descriptor (syscall_windows.go:396-403), so the new file gets its parent's inheritable ACEs; the only effect of perm is `perm&S_IWRITE == 0 -> FILE_ATTRIBUTE_READONLY`. syscall.Chmod (:759-774) and os.(*File).Chmod toggle that bit only. syscall.Mkdir is CreateDirectory(path, nil). Perm() is synthesised (os/types_windows.go:179-181). Consequences seen in this tree: every `0o600`/`0o700` on the write side (identity.go, pki, credentials.go, settings.go, knownhosts.go, lockfile.go) is a no-op for privacy on Windows; `if fi, err := os.Stat(path); err == nil { mode = fi.Mode().Perm() }` 'keep the user's mode' reads 0666 and carries nothing; the oauth_idp.go client_secret_file mode check is gated off on Windows for this reason.

**The rename trap.** A file protected with its own DACL (SetNamedSecurityInfo with PROTECTED) is UNPROTECTED again after `os.CreateTemp(sameDir)` + write + `os.Rename(tmp, path)`: the rename keeps the temp file's inherited DACL (measured: D:(A;ID;FA;;;SY)(A;ID;FA;;;BA)(A;ID;FA;;;user), protected=false). A fix-up applied to the final path is undone by the next save. Either protect the temp file before the rename (SetSecurityInfo on its handle, or CreateFile with the SA) or, the choice knomit made (kb/decisions/security/data-root/private-on-every-platform), protect the DIRECTORY with inheritable ACEs so every temp file is born private.

**Setting a DACL from x/sys.** SecurityDescriptorFromString(sddl) -> sd.DACL() -> SetNamedSecurityInfo(path, SE_FILE_OBJECT, DACL_SECURITY_INFORMATION|PROTECTED_DACL_SECURITY_INFORMATION, nil, nil, dacl, nil). Without PROTECTED in securityInformation the SDDL's own 'P' is ignored and the inherited ACEs are merged back (measured: 5 ACEs, protected=false). 'GA' is stored as FA (0x1f01ff); tests should expect FA. Reading back: GetNamedSecurityInfo + sd.Control()&SE_DACL_PROTECTED + sd.DACL() + GetAce, with one unsafe cast from ACCESS_ALLOWED_ACE.SidStart to *SID; reading OWNER needs READ_CONTROL only.

**Propagation to existing children (measured on a directory with OICI ACEs).** SetNamedSecurityInfo on the directory re-propagates to EVERY existing descendant synchronously: ~0.13-0.16 ms per file with Defender on (25 files 6 ms; 10,000 files 1.3 s; 100,000 files 16 s); a second call on an already-protected root costs ~2 ms because it is skipped. Share modes do not matter: a file another process holds open with FileShare.None still receives the new ACEs. BUT a child the caller cannot change (owned by someone else with an explicit Deny WRITE_DAC), run UNELEVATED, is skipped SILENTLY: the call returns success, the siblings before and after it update, that child keeps its old ACEs, and nothing reports it. Elevated, the same child IS updated, so measurements from an elevated shell overstate what a normal user gets. Only a post-walk (Inspect over the tree) can surface a partial propagation.

**What the default profile gives.** Under %LOCALAPPDATA% every file inherits SYSTEM, Administrators and the user only (all (I)), so the default install is private without any of this; under C:\ a directory inherits BUILTIN\Users:(RX) and Authenticated Users:(M). The exposure is exactly a KNOMIT_HOME outside the profile. And because C:\ lets Authenticated Users create folders, another local user can PRE-CREATE that root, owned by them, with a protected DACL naming themselves: 'protected' must not be read as 'deliberately set by the user'.

**Misreadings.** 'The tests pass on Windows' says nothing here: a permission test under t.TempDir() inherits owner-only from the profile and is green on code that sets nothing; use a parent with a deliberately broad DACL. And 'we chmod 0600' in a code comment is a unix statement; on Windows read it as 'inherits from the directory'.
