# The pipe's ACL gates who may OPEN the name, NOT who may create it: \\.\pipe\ is world-creatable, so the "ACL is the credential, like the 0700 data root" parallel is true for opening and false for creating. Since knomit#265 the CLIENT closes the gap by verifying the pipe's OWNER at dial time (own SID, SYSTEM or Administrators), which the SDDL's O: part makes the user even for a UAC-elevated server; a same-user squatter and a local admin remain out of reach

knomit's pipe is created with SDDL `O:<our SID>D:P(A;;GA;;;<our SID>)(A;;GA;;;SY)` (the `O:` part since knomit#265): protected, this user and SYSTEM only, no deny ACE (a DACL with no matching ACE already denies, and an explicit deny would also lock US out if our SID ever appeared in the denied group).

The DACL controls who may OPEN knomit's pipe, which is the real parallel to 0600 under a 0700 data root. It does NOT control who may CREATE a pipe by that name: the `\\.\pipe\` namespace is flat and world-creatable (NPFS has no parent directory), so another local process can take `knomit-<hash>` before knomit boots and receive the bridge's traffic. The 0700 data root on unix gates creation too; the pipe namespace does not.

IT IS NOT A SILENT HIJACK ON THE SERVER SIDE: knomit then fails to create the name (FILE_CREATE on an existing name -> ERROR_ACCESS_DENIED -> ErrSocketInUse) and says so. With [auth].require FALSE both server binaries warn and serve TCP only; with it TRUE the boot fails outright.

WHAT A SQUATTER GOT BEFORE #265 (measured 2026-09-26): every connection, and the full HTTP request the bridge writes the moment the dial returns: every MCP JSON-RPC line (tool calls, knomit_learn/knomit_update bodies), the client identity header (host, OS user, cwd, pid, parent app, branch) and `Authorization: Bearer <access token>` when `kb login` had been run against that local base. Its answers went straight to the agent's stdout, and the hooks client injected whatever facts it returned: a prompt-injection channel. `knomit oauth approve|deny` could be faked.

WHAT THE CLIENT CAN SEE (measured): on the conn DialLocal returns, `GetSecurityInfo(handle, SE_KERNEL_OBJECT, OWNER_SECURITY_INFORMATION)` gives the pipe's owner; READ_CONTROL is inside the GENERIC_READ DialLocal asks for, so a squatter that withholds it makes the dial fail outright. Use SE_KERNEL_OBJECT: SE_FILE_OBJECT fails with ERROR_INVALID_PARAMETER on an unprotected DACL. GetNamedPipeServerProcessId + OpenProcess(PQLI) + OpenProcessToken + GetTokenUser also works, unelevated client to elevated server included, but has a PID-reuse race. Windows has no 'impersonate the server' primitive and go-winio's dial has no server-verification option (SQOS flags govern what the SERVER may do with the CLIENT's token).

THE OWNER TRAP: without `O:` the pipe's owner is the creating token's TokenOwner, which for a UAC-elevated server is BUILTIN\Administrators (same as the #301 directory finding), so 'owner == my SID' would reject the real desktop. `O:<own SID>` is accepted from an elevated token because a token may always assign its own user as owner.

WHAT REMAINS: a squatter running as the SAME user is indistinguishable by any SID check (the unix same-uid boundary); a local Administrator can own anything; the cross-user outcome (owner = the squatter's SID) is inferred from how the kernel assigns owners, not measured on this box. The thorough answer is still a certificate (phase 2).

NAMED MISREADING: "the ACL makes the pipe as safe as a 0600 socket under a 0700 root". It does not, in the creation direction; the owner check at dial time is what closes it for other non-admin users, and only that.
