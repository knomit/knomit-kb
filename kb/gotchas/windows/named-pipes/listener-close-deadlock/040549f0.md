# go-winio v0.6.2's pipe listener Close can block FOREVER when it races a client connecting and hanging up — its one close signal is consumed and then lost — so knomit pins go-winio at microsoft/go-winio#388 (7e8af9b09c) or later, which no tagged release yet contains

In go-winio v0.6.2, `win32PipeListener.Close` sends ONE value on `closeCh` and then waits on `doneCh`. When the listener routine has a ConnectNamedPipe pending, `makeConnectedServerPipe` consumes that value, closes the pending pipe and REUSES the connect goroutine's result, mapping only `nil` and `ErrFileClosed` to `ErrPipeListenerClosed`. If a client connected and hung up in that window, the result can be another errno — measured on Windows 10 here: `ERROR_OPERATION_ABORTED` (0x3e3) came back from Accept unmapped. `listenerRoutine` then sees closed=false, returns to its top-level select, and Close waits on `doneCh` forever with no signal left to send. The stack signature is Close parked in `chan receive` at pipe.go:578 and `listenerRoutine` parked in `select` at pipe.go:462.

Measured with a scratch stress test (http.Server over winio.ListenPipe; a client dials and closes at once, which is exactly what auth.DialLocal does when it refuses a pipe's owner; then srv.Close with a 5 s bound): v0.6.2 hung 2 times in 3000 iterations; 7e8af9b09c hung 0 times in 10000.

Consequences:
- This is not a test-only flake. `knomit serve` (cmd/listen.go) and the desktop (tools/desktop/boot.go) close the same listener via ListenLocal's cleanup, so on v0.6.2 their SHUTDOWN could hang.
- Do NOT downgrade go-winio to v0.6.2 or to any tag that predates microsoft/go-winio#388, even though a tagged release looks 'more stable' than a pseudo-version. When a tagged release that contains #388 ships, move to it.
- The cleanup ORDER in TestOAuthCLI_ForeignListenerIsSurfaced (RefuseEveryPipeOwnerForTest restored before srv.Close) was suspected in #344 and is NOT the cause. The hang reproduces with no knomit auth code involved at all.
- Anti-pattern: bounding the Close with a timeout in knomit's wrapper. That hides the hang but leaks the listener goroutine and the first pipe handle, so the pipe NAME stays held and the next ListenLocal in the same process gets ErrSocketInUse.
- The bump carried go.mod's go directive to 1.26.0 (and x/sys, x/mod, x/sync forward); CI and release already build with Go 1.26.
