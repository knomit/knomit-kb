# go-winio v0.6.2's pipe listener Close can block FOREVER when it races a client connecting and hanging up — its one close signal is consumed and then lost — so knomit requires go-winio v0.6.3 (the first tag containing microsoft/go-winio#388, 7e8af9b09c) or newer

Current state: knomit is on tagged go-winio v0.6.3, the first tagged release that contains microsoft/go-winio#388 (7e8af9b09c). The defect below exists in v0.6.2 and in any version that predates #388; it is fixed in v0.6.3 and later.

In go-winio v0.6.2, `win32PipeListener.Close` sends ONE value on `closeCh` and then waits on `doneCh`. When the listener routine has a ConnectNamedPipe pending, `makeConnectedServerPipe` consumes that value, closes the pending pipe and REUSES the connect goroutine's result, mapping only `nil` and `ErrFileClosed` to `ErrPipeListenerClosed`. If a client connected and hung up in that window, the result can be another errno — measured on Windows 10 here: `ERROR_OPERATION_ABORTED` (0x3e3) came back from Accept unmapped. `listenerRoutine` then sees closed=false, returns to its top-level select, and Close waits on `doneCh` forever with no signal left to send. The stack signature is Close parked in `chan receive` at pipe.go:578 and `listenerRoutine` parked in `select` at pipe.go:462.

Measured with a scratch stress test (http.Server over winio.ListenPipe; a client dials and closes at once, which is exactly what auth.DialLocal does when it refuses a pipe's owner; then srv.Close with a 5 s bound): v0.6.2 hung 2 times in 3000 iterations; the #388 commit 7e8af9b09c (the code v0.6.3 ships) hung 0 times in 10000. Through knomit's REAL path the rate is far higher: ListenLocal, RefuseEveryPipeOwnerForTest, then oauthPending over localAPIClient/DialLocal, then srv.Close. v0.6.2 hung 3 times in 106 iterations (about 1 in 35), with the exact CI stack signature and ERROR_OPERATION_ABORTED; 7e8af9b09c hung 0 times in 6000.

Tag choice: `gh api repos/microsoft/go-winio/compare/7e8af9b09c...<tag> --jq .status` is `ahead` for v0.6.3 and v0.6.4 and `behind` for v0.6.2. v0.6.3 is the first tag containing #388, so it is the one knomit uses. v0.6.4 was checked (v0.6.3..v0.6.4) and has no pipe changes: it is an x/sys bump and an mkwinsyscall generator fix only.

The regression guard is `TestLocalListener_CloseAfterRefusedDialDoesNotHang` (cmd/oauth_listener_close_windows_test.go, package ./cmd). It runs that real path 300 times with Close bounded at 10 s. Measured: on v0.6.2 it failed 5 of 5 runs (at rounds 3 to 81), and on a later forced run (knomit#350) it failed at round 15 with the message 'closing the listener hung after a refused dial (knomit#344); is go-winio older than microsoft/go-winio#388?'. On the #388 code it passed 20 of 20 (~2.6 s each), and on v0.6.3 it passes (~2.9 s). If it fails, suspect a go-winio downgrade before suspecting knomit's auth code.

Consequences:
- This is not a test-only flake. `knomit serve` opens the listener through app.OpenListeners (internal/app/listeners.go, called from cmd/serve.go) and closes it via ListenLocal's cleanup, so on v0.6.2 its SHUTDOWN could hang. When this was measured the desktop also closed it in-process (tools/desktop/boot.go, since removed); no desktop code calls ListenLocal outside tests now.
- Do NOT lower that test's round count to save time: at about 1 in 35 per round, 300 rounds miss a regression with probability ~0.02%, and 30 rounds would miss it about 40% of the time.
- Do NOT downgrade go-winio to v0.6.2 or to any tag that predates microsoft/go-winio#388, even though an older tagged release looks 'more stable'. Any tag at or after v0.6.3 is acceptable; the comment at the ListenPipe call in internal/foundation/auth/listen_windows.go says the same.
- The cleanup ORDER in TestOAuthCLI_ForeignListenerIsSurfaced (RefuseEveryPipeOwnerForTest restored before srv.Close) was suspected in #344 and is NOT the cause. The hang reproduces with no knomit auth code involved at all.
- Anti-pattern: bounding the Close with a timeout in knomit's wrapper. That hides the hang but leaks the listener goroutine and the first pipe handle, so the pipe NAME stays held and the next ListenLocal in the same process gets ErrSocketInUse.
- The earlier bump to the #388 pseudo-version carried go.mod's go directive to 1.26.0 (and x/sys, x/mod, x/sync forward); CI and release already build with Go 1.26.
