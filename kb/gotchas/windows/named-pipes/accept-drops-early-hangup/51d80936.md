# go-winio's pipe listener silently DROPS a client that connects and hangs up before the server issues ConnectNamedPipe — Accept never returns for it — so a test that dials, closes, then waits on Accept with no deadline can hang forever

In go-winio (verified at the pinned v0.6.3-0.20260925173824-7e8af9b09c4b, pipe.go), the listener's firstHandle is opened SYNCHRONIZE-only and is not connectable, so a client's CreateFile gets ERROR_PIPE_BUSY and retries every 10 ms until Accept makes a new instance in makeServerPipe (pipe.go ~433). That instance is connectable the moment it exists, but ConnectNamedPipe is issued later from a separately spawned goroutine (pipe.go ~439-440 -> connectPipe ~551). If the client opens AND closes in that gap, ConnectNamedPipe returns ERROR_NO_DATA, and listenerRoutine (pipe.go ~466-472) deliberately retries ('connection was immediately closed by the client, try again'): it discards the instance and waits for another client. Accept does not return for the dropped client.

Consequence for tests: any test that dials, lets the client close, and THEN waits for Accept to hand it the server end will hang if the close beats ConnectNamedPipe. The window is microseconds on an idle box (0 hangs in ~4000 local runs) but hit CI twice (#367: PR #363 run 36863649277 attempt 2, PR #398 run 37038625151 attempt 1; TestDialLocal_RejectsAForeignOwner, test goroutine at local_windows_test.go:179, Accept at pipe.go:562, connectPipe pending). A 200 ms sleep injected before connectNamedPipe reproduces it on the first try.

Tests that keep the client open until Accept returns are NOT exposed: a late ConnectNamedPipe then returns ERROR_PIPE_CONNECTED, which go-winio treats as success. http.Server-based fixtures absorb the retry in their accept loop.

To observe the server side of a client that closes immediately, issue an overlapped ConnectNamedPipe on a raw CreateNamedPipe handle BEFORE dialling: a pending connect completes when the client connects even if it has already hung up, and a ReadFile then gives 0 bytes + ERROR_BROKEN_PIPE for a clean close (n>0 if the client wrote first).

Not meant: this is not the Close deadlock of microsoft/go-winio#388 (kb/gotchas/windows/named-pipes/listener-close-deadlock/040549f0.md); the pin does not cover it. Not a production bug: a server that misses such a client just keeps listening. And ERROR_NO_DATA does NOT prove the client wrote nothing, since a write-then-close also produces it.
