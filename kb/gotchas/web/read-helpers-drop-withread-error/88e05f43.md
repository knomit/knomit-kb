# Most web read helpers still discard RepoInstance.WithRead's error, so a GET on a repo whose store cannot be reached runs no store code and falls through with zero values (an empty 200, or an empty fact) instead of the 503 that REST writes now answer

RepoInstance.WithRead runs its closure only when Acquire succeeds; otherwise it returns ErrStoreUnavailable (or the populating wrapper, or ErrRepoClosed) WITHOUT calling the closure. PR #618 made the REST WRITE helpers return that error (kb/decisions/web/rest-write-store-unavailable-503/5ce4cfbc.md). The read side was left as it was, by decision of that PR (report only).

VERIFIED at 585974c5 by grep and reading: WithRead's return value is dropped (a bare `ri.WithRead(func...)` statement) in about 25 call sites across handlers_activity.go (loadActivity), handlers_commits.go (logPaginated), handlers_completions.go, handlers_domains.go (two), handlers_events.go (the head-commit snapshot), handlers_fact_read.go (readFact), handlers_fact_sub.go (five helpers: explainFact, incomingAtCommit, outgoingAtCommit, factLiveAtCommit, factExistsAt), handlers_facts_collection.go (recentFacts), handlers_motifs.go (five), handlers_search_hal.go, handlers_stats.go (loadStats, loadHighlights), handlers_topics.go (listTopicDir, topicFactByPath) and server.go (listRepoBranches, readBranchRoot). Two sites discard it deliberately with `_ =` (fact_version_date.go: a missing date, not a failed request; one in handlers_experiments.go). Sites that DO check it: the experiments, changes, jobs, pushed-branches and experiment-diff handlers (503 "Store unavailable" with the raw error as detail), and handlers_branches.go. commitDetail uses Acquire directly and checks it.

EFFECT per helper is INFERRED from the code, not measured here: the closure is skipped, so the result variables keep their zero values and err stays nil. List-style helpers therefore return an empty list or zero stats and the handler answers an empty 200; readFact returns a zero Fact and a nil error, so a GET of a fact answers a 200 with an EMPTY fact. PR-REPORTED (measured by the PR author on a store-less instance at its branch head, not re-run): readFact answers 200 with path "" and title ""; commitDetail answers 404 "Commit not found" with detail "repo store is unavailable". listRepoBranches documents nil, nil for a store that is unavailable (opening) as its intended contract, so it is not a defect of the same kind.

STATUS: a USER RULING IS PENDING on whether to fix the read helpers (return WithRead's error; writeStoreError already answers 503 for it) and on the 503 wording ("Repo not ready" on the write path versus "Store unavailable" on the WithRead routes above). Until ruled, do not describe the web layer as answering 503 for an unreachable store: only the write routes, the repo PATCH and the system-file read do.

DOES NOT MEAN: that every discard has the same user-visible effect (an empty list, an empty fact and a missing date differ), or that the `svc == nil` branches inside these closures guard the case: they never run, because a nil store means Acquire fails and the closure is skipped.
