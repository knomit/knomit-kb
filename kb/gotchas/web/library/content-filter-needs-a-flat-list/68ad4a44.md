# A content filter the ontology TREE cannot honour must join hasContentFilters, not just its own effect — otherwise it is dead in the DEFAULT mode and silently issues no request at all

`state.librarySort` starts at `'path'`, so the list a reader actually sees is the ontology TREE, served by `api.browse` — a directory walk that carries no content filters and has no `sinceFork` in its deps. A filter wired only into the Recent and Relevance effects therefore repaints its chip and fires NO request: the chip turns green above a list that still shows every fact.

The cure already existed three lines above the bug. `Library.tsx` documents the same failure for facet chips — "a chip applied in Path mode is silently ignored... a filter needs a flat list to be a filter OF, so it borrows Recent" — implemented as `hasContentFilters`. Since-fork was simply never added to that test. The fix is that one term, not a second mechanism.

SECOND SYMPTOM, unreported until the fix: `hasContentFilters` also feeds `contentFiltered` into `LibraryHeader`, which BLOCKS the Path sort button while a filter is on. Path cannot honour the filter either, so that button was still being offered and would have silently dropped it.

HOW IT SHIPPED. The first test set `librarySort: 'recent'` in its fixture. The real default is `'path'` and the bug lived only in the default, so the test passed against broken code — a UI test that forces a non-default mode can be green on exactly the build that is wrong.
