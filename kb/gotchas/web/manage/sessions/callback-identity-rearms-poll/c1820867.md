# ManageSessions puts onLiveCount in load's useCallback deps and re-arms its poll effect on [load], so a parent that passes an unstable callback (an inline arrow) re-runs the effect and issues one extra GET /api/v1/sessions per parent render; and the Manage header's own count effect depends on sessionsOpen, so it must skip its read while the page is open or the tab switch costs a second read

**What bit (PR #197 review, two rounds):** opening the Sessions tab issued two list reads instead of one. It had TWO causes with different signatures, and the first review attributed the measurement to the wrong one:

1. The header effect in RepoManager.tsx depends on `sessionsOpen`; flipping it re-ran the effect, which issued a read at the very moment ManageSessions was mounting to report its own count through `onLiveCount`. Pre-existing; the header comment claimed it piggybacked on the page, but the code honoured that only for the focus listener. Fix: `if (!sessionsOpen) readLiveCount()` in the effect body (RepoManager.tsx ~:185).
2. Passing `onLiveCount={n => {...}}` as an inline arrow changed the prop's identity every render. ManageSessions has `onLiveCount` in `load`'s useCallback deps and runs `useEffect(..., [load])`, so a new arrow ⇒ new load ⇒ the poll effect tears down and re-runs ⇒ one extra read per subsequent RepoManager render, including the renders the page itself causes by reporting a changed count. Fix: `handleLiveCount` as a `useCallback(..., [])` that still bumps the stale-read generation counter.

**Why the split matters:** a test that renders ManageSessions standalone with a stable prop passes on both broken and fixed code. The test that catches both is in RepoManager.test.tsx, 'opening Sessions costs exactly one list read': it clicks through the tab transition and asserts a delta of exactly 1 (catches the header read), then re-renders RepoManager with the page open and asserts zero further reads (catches the arrow). Restoring each fault alone fails exactly one of the two assertions.

**Consequence for editors:** any new prop handed to ManageSessions (or to any component that lists a callback in a data-loading useCallback's deps) must be referentially stable across the parent's renders, and any header-level reader of the same endpoint must defer to the page while it is open. There is also a stale-read guard: every header read takes a generation from `liveCountGen`, `onLiveCount` bumps it, and only the latest generation's result (or failure) is applied, so a page-reported count can never be overwritten by a header read that was already in flight.

**Misreading to avoid:** this is not 'never pass arrows as props'. It is specific to props that sit in the deps of a callback that an effect keys on; those re-arm the effect.
