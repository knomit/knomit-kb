# REST read surface as found (dev b4d232ee): repo is addressed by NAME in the URL, changes `since` takes a commit not a time, search and the facts collection return no bodies, search has no cursor, and no endpoint reads many facts at once

Found by building a client of the REST API (the materialize research spike, 2026-10-25) and re-read against dev b4d232ee on 2026-10-26. Five properties a REST client written from the MCP tools' habits gets wrong:

1. The repo segment of /api/v1/repos/{repo}/... is the repo NAME. RepoMiddleware looks the segment up by name (Manager.Get) and answers 404 'no repo named "..."' otherwise; the spike measured that the 12-hex repo id returned 404. (A registered repo with no live store is 409, not 404.)
2. `GET .../changes?since=` takes a COMMIT (or the MCP tool's <repo12>:<commit40> bookmark naming this same repo). The handler comment states it is a read of two trees, 'no timestamp'. There is no time-window filter: to get 'the last 14 days' a client pages `commits` and picks the newest commit older than the window itself. A `since` not behind head is 409; unknown is 400. Page size is 1 to 100.
3. Search items (searchResultItem) and facts-collection items carry path, title, score/kind/type/domain/entities/motifs and links but NO body; reading bodies takes one `GET .../facts/{path}` per fact (or `.../commits/{sha}/facts/{path}` for a commit-pinned read).
4. The REST search handler takes `limit` only (limitParam, bounded by maxLimit); it has no cursor parameter, unlike the MCP knomit_query. Deeper recall means a bigger limit up to the bound, not paging.
5. The router registers no endpoint that reads a set of facts (bodies, refs) in one call. A document built from N facts costs at least N fact reads; the spike's closure of 25 matches to 114 facts took 331 HTTP calls in 47 s on localhost.

Consequence: a client that needs bodies for a set, a time window, or deep recall must do the extra reads itself and budget the call count. WHAT THIS DOES NOT MEAN: these are properties of dev at b4d232ee; a later bulk read or time filter would change items 2, 3 and 5, so re-read handlers_changes.go and router.go before relying on them. Unpinned branch selection is a separate trap the spike hit: without a branch in the URL it landed on a different agent branch whose changes returned 787 rows.
