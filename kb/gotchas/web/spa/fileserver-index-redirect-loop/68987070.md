# http.FileServer answers ANY path ending in /index.html with a 301 to "./", and "./" resolves against the REQUEST path — so an SPA fallback that rewrites the path and re-dispatches to the FileServer is a redirect loop, not a fallback; open index.html and serve it with http.ServeContent instead

net/http's `serveFile` (the engine under `http.FileServer`) carries this
rewrite, with `redirect=true`, which is the mode `http.FileServer` always uses:

    // redirect .../index.html to .../
    if strings.HasSuffix(r.URL.Path, indexPage) {
        localRedirect(w, r, "./")
        return
    }

It exists so a directory has ONE canonical URL. It keys on the REQUEST PATH,
fires before any file is opened, and there is no way to opt out of it while
still going through the FileServer.

The SPA fallback knomit shipped until PR #223 did exactly the thing that trips
it: on a path with no matching file it cloned the request, set
`r2.URL.Path = "/index.html"`, and handed it back to the SAME FileServer.

MEASURED, not inferred (probe against the pre-fix handler):

    GET /repos/alpha/browse  -> 301  Location: "./"
    GET /index.html          -> 301  Location: "./"
    GET /                    -> 200  (index.html body)

`Location: "./"` is RELATIVE, and a relative redirect resolves against the
request path, not the site root. So `/repos/alpha/browse` redirects to
`/repos/alpha/` — which has no file either, so it falls back to `/index.html`,
which 301s to `"./"`, which is `/repos/alpha/` again. That is a redirect loop
the browser terminates by giving up. Only `/` escapes, because there the
suffix test never matches.

WHY IT WAS DORMANT, which is the part worth carrying forward. knomit's UI has
no client-side router — no react-router dependency, no pushState/replaceState
anywhere under web/src — so the app never generates a deep path and nothing
ever entered the loop. The only way to reach it was to type a URL. It was
found by WRITING A TEST for the fallback's cache headers, not by observing a
failure, and it would have turned into a live bug the day anyone added
routing. A fallback path that nothing exercises is not a working fallback; it
is an untested one.

THE FIX SHAPE. Open index.html from the fs.FS yourself and pass it to
`http.ServeContent`, and NEVER re-dispatch a rewritten path to the FileServer.
ServeContent does no path rewriting of any kind — it writes the bytes you hand
it under the name you hand it — and it still performs the If-None-Match
comparison against an ETag already set on the header map, so the conditional
request keeps working.

WHAT THIS DOES NOT MEAN — 1. Not "http.FileServer is unsuitable for SPAs". It
is correct for files that EXIST: /assets/*, /config.js and /favicon.svg all go
through it here. The rewrite bites only the FALLBACK, where the path served
differs from the path requested. The rule is narrower and more useful than
"avoid FileServer": never make a FileServer serve a path other than the one
the client asked for.

WHAT THIS DOES NOT MEAN — 2. The loop is not caused by the SPA catch-all route
`/*`. Deleting the catch-all removes the fallback, not the rewrite: a plain
`http.FileServer` with no SPA handler anywhere still answers GET /index.html
with a 301 to "./". Blaming the router sends the next reader to the wrong file.

RELATED, SAME FAMILY: the same `serveFile` will also render a DIRECTORY as an
HTML listing. Under a long-cached prefix that means the listing is both an
enumeration of every bundle name and a year-long cache entry, which is why
/assets/ 404s on a directory before any Cache-Control is stamped.
