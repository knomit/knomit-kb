# Fleet Settings reads the stored auth method keyed on fleet_repo + hosting, which a credential change does not alter: a finished flow bumps a revision that re-fetches WITHOUT invalidating the previous answer, or the Hosting actions blink out and the Access row goes stale

Verified at the merge of PR #529 (60ddfb1c), web/src/FleetSettings.tsx. The page reads the copy's stored origin (method) once per `originKey = fleet_repo + ' ' + hosting` (not on a hub) and shows the Access row and decides which Hosting actions exist from it. Update access changes the CREDENTIAL only, so neither fleet_repo nor hosting changes and a key made of them never fires: the Access row kept showing the old method until a reload (found in the browser walk). First fix (keying the read on a revision) made the Hosting actions vanish until the re-read landed, because a new key invalidates the previous answer (CI web-ui node 22 failed). FINAL: `originRev` is bumped in a flow's onDone and is a dependency of the read's effect but NOT part of originKey, so the previous read stays valid until the new one lands.

RULE for any page state derived from a server read: key the read on what identifies the thing, re-trigger it on a counter, and never put the counter in the key that gates rendering.

TEST. FleetSettings.config.test.tsx 'the Access row re-reads the stored method after Update access finishes' (sabotaged red both ways: dropping setOriginRev, and re-keying on the revision; the test holds the re-read and asserts the actions stay).
