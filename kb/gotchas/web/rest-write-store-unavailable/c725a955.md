# The web package's ri.WithRead callers ignore its error, so a REST fact write to a repo whose store is unavailable answers 201/200/204 and writes nothing (pre-existing defect, fix planned)

State at 660cc910 (W0h, PR #617). RepoInstance.WithRead (internal/corpus/repos/instance.go) calls fn only when Acquire succeeds; when the instance has no store handle Acquire fails with ErrStoreUnavailable (or errPopulating while the populate stage runs, or ErrRepoClosed) and WithRead returns that error WITHOUT calling fn. factResolves, priorRefs, writeFact and deleteFact (internal/edge/web/handlers_fact_write.go) discard WithRead's return value, so on such a repo they return zero values and a nil error. Consequence by endpoint: POST answers 201 with a view of a fact that was never written, PUT answers 200, DELETE answers 204; nothing reaches git. The false success applies to a write that carries no new refs: when the gate does check a ref, factResolves yields (false, nil), so the ref reads as unresolvable and the request is refused with 422 instead (and priorRefs yields nil refs, so a PUT has no carried-forward exemption). systemFileResolver in the same file ignores WithRead's error the same way.

The `if svc == nil { err = errFactNotFound }` branches inside the four closures never run: newStoreHandle(nil) returns nil, so a nil store means Acquire fails and the closure is skipped. They do not guard this case. The doc comments of the four functions name it as a known pre-existing defect.

PR-REPORTED (not checkable in code): the 201/200/204 outcome was measured at the W0h branch head on a storeless writable test instance (repos.NewTestInstanceWithDeps with an agent branch and no Svc).

STATUS: a fix (answer 503 instead of a false success) is planned as a separate follow-up PR, deliberately not part of W0h (a behaviour change inside a refactor PR). It does NOT exist at 660cc910; re-read the four functions before relying on this gotcha after that PR lands, and retract or update this fact then.

CONSEQUENCE: any fix has to check WithRead's error in all four functions (and systemFileResolver); a test mutating the `svc == nil` branches cannot be killed because they are unreachable.

DOES NOT MEAN: that every ri.WithRead caller in web has the same user-visible effect. Check each caller; the read helpers (loadStats, readFact, listTopicDir, ...) have the same discard-the-error shape, but for a read the zero value is an empty or not-found answer rather than a false success.
