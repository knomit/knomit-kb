# A reload restores the browse context (repo | lens) from localStorage, not the URL, and never restores the branch: it always lands on the repo's read branch, so an open experiment is lost

Nothing in web/src reads the browse context from the URL; the only query-string state is materialize=1/mat_* (RightPanel) and factset/fs_* (factsetOptions). On boot App reads loadLastContext() (repoSelection.ts: the JSON under localStorage 'knomit.context', legacy 'knomit.repo') and dispatches SET_CONTEXT; saveLastContext writes it on every context change. localStorage is shared by every tab of the origin, so it is LAST-WRITER-WINS: after tab B switches repo, a reload of tab A lands on tab B's repo or lens.

The branch is not persisted anywhere. The status bootstrap passes initialBranch: state.branch, which is '' after a reload, so bootstrap.ts falls back to bootBranchOf (read_branch || agent_branch). A reload inside an experiment (entered via enterBranch / BranchPicker) returns to the agent/read branch, and state.sinceFork does not survive.

Consequence: any feature that writes list or view state into the URL and re-applies it on reload (e.g. the Library list search, a FactSet re-create) re-applies it against whatever context localStorage and the boot pick produce, which can be a different repo, lens or branch from the one the state was captured on. Making the context itself URL-restorable is a change to App boot (loadLastContext precedence, pickRepo, the bootstrap's initialBranch), not to the list.

This does NOT mean a single-tab reload loses the repo or lens: it keeps it via localStorage. It is the branch, and multi-tab divergence, that are lost.
