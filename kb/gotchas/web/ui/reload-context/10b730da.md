# A reload restores the browse context from the URL first (ctx_repo/ctx_lens by registry uid, ctx_branch incl. exp/), localStorage only when the URL names none; before #713 it was localStorage-only (last writer wins across tabs) and the branch was never restored

As of PR #713 (feat/list-search-url), useListUrl (web/src/listUrl.ts) reads the URL once when App mounts. App's boot effect then asks it BEFORE loadLastContext:
- ctx_repo=<RepoInfo.uid> picks that repo from the live list, but only if browsableRepo.
- ctx_lens=<Lens.uid> fetches api.listLenses() to map the uid to a name. That is one extra request, made only when the URL names a lens.
- ctx_branch is entered once the default boot has landed on the read branch, the way enterBranch does: api.status(repo, branch) then SET_STATUS. That is one extra request, made only when the URL branch differs.

Only after that is the list (l_* keys) restored, in one RESTORE_LIST, so since_fork survives an exp/ reload.

If the URL names a uid that no longer resolves, or a branch whose status call fails or answers a different branch, the boot falls back to exactly the pre-#713 behaviour: loadLastContext, the read_branch. The list and factset keys that depended on that context are dropped (abandon), never applied to another context.

What stays true: localStorage ('knomit.context') is still written on every context change and is still LAST-WRITER-WINS across tabs, so a URL with NO ctx_* keys still lands on whatever repo or lens another tab last chose. The branch is still not persisted outside the URL.

Consequence:
- Anything that wants a tab's view to survive reload must ride the URL's ctx_* and l_* keys (written by useListUrl's write-back effect with replaceState).
- New list state must be added to listUrl.ts (parse, write, RESTORE_LIST) as well as to listSearch.ts.

This does NOT mean the URL is authoritative mid-session. It is read once per page load; afterwards the state is written INTO it.

ORDERING (fixed in #713 review H1, at 827bd1f3): the URL wins only if 'resolving' never judges a context that has not been set yet. The first version adopted the URL repo BEFORE awaiting the speculative getRepo. On the commonest reload, the same tab, the URL repo equals the localStorage repo, so that await is taken. If getRepo was slower than the repo list, the restore saw state.context.repo === '' and abandoned. The write-back then wiped every ctx_*/l_* key and factset=1. Now:
- adopt(next) runs in the same tick as SET_CONTEXT, after the await.
- 'resolving' WAITS while the context is the initial unset { repo: '' }.
Each of these alone prevents the bug; both are kept.

Late answers (#713 review L2): the restore's api.status(repo, ctx_branch) and App's enterBranch both drop an answer that lands after the user has left that repo, because SET_STATUS has no repo guard. The restore checks that its phase is still 'resolving' with the same context; enterBranch checks stateRef.current.repo.
