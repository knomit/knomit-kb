# The Sessions table's experiment chip fills a handle's EMPTY branch from a mount matched on kind+uid — a display join over two differently-scoped facts, not a claim that the handle routes to the experiment

WHAT THE CODE DOES. `writeChip(kind, uid, branch, mounts)` in ManageSessions.tsx picks the branch chip for a target line, and the handle's OWN branch wins: a non-empty `branch` renders the ordinary blue chip and the mount is never consulted. Only when `branch` is empty does it look for an entry of `r.mounts` matching on BOTH `m.kind` and `m.uid` with a non-empty `m.experiment`, and render the green flask chip for it. Neither → no chip, because "" means the target's own branch. The same helper feeds the summary line and the per-handle `Writes to` cell; the singular `r.binding` fallback passes `''`, so there the mount is the only possible answer and wins.

WHY THE HANDLE WINS. kb/invariants/mcp/experiments/one-answer-per-handle makes "a branch pin AND an experiment" unrepresentable for a handle — the write refuses the pair and the read fails loudly rather than ranking them. So a non-empty `branch` IS that handle's answer about where it points, and a mount's experiment overriding it would be the UI inventing exactly the precedence rule the server refuses to have. An earlier revision of this code did override it, which is what this fact was first written about.

WHY THE MOUNT HALF IS STILL ONLY A DISPLAY JOIN. The two sides are scoped differently. `mounts` is per URL-SCOPED MOUNT — what a session writes to on a mount whose URL named a repo or lens, with kb/invariants/mcp/experiments/mount-eligibility-from-the-route the rule for which mounts may take that state at all. `bindings` is per HANDLE, and a handle routes by the handle argument on the call. Nothing makes a handle on repo X inherit an experiment the same session opened on a URL-scoped mount of repo X. So the chip means "this session has an experiment open on this target, and this handle named no branch of its own", NOT "this handle's writes land on exp/<name>".

MATCH ON KIND AND UID, NOT UID ALONE. A repo and a lens that happen to share a uid are different targets; matching on uid alone put one's experiment on the other's line.

IN PRACTICE THE TWO RARELY COEXIST — a bridge is started `--repo`/`--lens` (URL-scoped, mounts, no handles) or unscoped (handles, no mounts) — which is why the join reads as obviously right and why a contrived session holding both is what exposes it. Confirmed in a browser against the live server: the real rows were URL-scoped lens callers with `bindings: []`, so they render through the SINGULAR fallback path, and a fabricated multi-handle row was needed to exercise the grouped path at all.

WHAT THIS DOES NOT MEAN. It is not a bug to fix by dropping the chip: showing the session's experiment beside the target it belongs to is the point of the redesign, and it replaced a Branch column that asserted the same thing once PER SESSION, which was strictly less true. A mount whose target no handle named still gets its own line, because that column rendered `r.mounts` unconditionally and the experiment would otherwise be visible nowhere. The trap is only in reading a flask chip as per-handle routing — if a future change gates anything on it, that answer must come from routing state (`binding_handles`), never from this join.

DISTINCT FROM the decision that authorised the redesign (kb/decisions/web/sessions/binding-groups-drop-branch-column), which records the options, the rationale and the choice, and names the uid join in one clause as part of what to build. This fact is about what that join DOES and DOES NOT assert once built.
