# The Sessions table's experiment chip joins `mounts` to a binding group BY UID, which is a display join over two differently-scoped facts — it is not a claim that the handle routes to the experiment

WHAT THE CODE DOES. `writeChip(uid, branch, mounts)` in ManageSessions.tsx picks the branch chip for a target line: if any entry of `r.mounts` has `m.uid === uid` and a non-empty `m.experiment`, it renders the green flask EXPERIMENT chip for that mount; otherwise it renders the blue chip for the binding's own `b.branch`, and nothing when that is empty. The same helper feeds the summary line, the per-handle `Writes to` cell in the detail row, and the singular `r.binding` fallback.

WHY THE JOIN IS ONLY A DISPLAY JOIN. The two sides are scoped differently. `mounts` is per URL-SCOPED MOUNT: it records what a session writes to on a mount whose URL named a repo or lens, and kb/invariants/mcp/experiments/mount-eligibility-from-the-route is the rule for which mounts may take that state at all. `bindings` is per HANDLE, and a handle routes by the handle argument on the call. Nothing makes a handle on repo X inherit the experiment that the same session opened on a URL-scoped mount of repo X. So the chip says "this session has an experiment open on this target", NOT "this handle's writes land on exp/<name>".

IN PRACTICE THE TWO RARELY COEXIST — a bridge is started `--repo`/`--lens` (URL-scoped, mounts, no handles) or unscoped (handles, no mounts) — which is why the join reads as obviously right and why a contrived session holding both is what would expose it. Confirmed in a browser against the live server: the three real rows were URL-scoped lens callers with `bindings: []`, so they rendered through the SINGULAR fallback path, and a fabricated multi-handle row was needed to exercise the grouped path at all.

WHAT THIS DOES NOT MEAN. It is not a bug to fix by dropping the chip: showing the session's experiment beside the target it belongs to is the point of the redesign, and it replaced a Branch column that asserted the same thing once PER SESSION, which was strictly less true. The trap is only in reading the chip as per-handle routing — if a future change gates anything on it, or surfaces it as "this handle writes to", that reading has to be re-derived from routing state (`binding_handles`), never from this join.

CONSEQUENCE FOR THE DETAIL ROW SPECIFICALLY. `Writes to` is the per-handle column, so it is the cell where the misreading is most available. It currently shows the mount's experiment for every handle on a target the mount names, including handles that never touched that mount.

DISTINCT FROM the decision that authorised the redesign (kb/decisions/web/sessions/binding-groups-drop-branch-column), which records the options, the rationale and the choice, and names the uid join in one clause as part of what to build. This fact is about what that join DOES and DOES NOT assert once built.
