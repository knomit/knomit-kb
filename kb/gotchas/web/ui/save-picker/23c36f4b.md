# A browser save dialog needs a fresh user click, so Export fetches first and opens showSaveFilePicker right away, and falls back to a 'Save as…' button when the click has gone stale; and a picker-first design would leave an empty file when the export then fails

showSaveFilePicker exists only in Chromium browsers (Chrome, Edge) and requires transient user activation (a few seconds after a click). Export is a fetch of up to a few MB first. Opening the picker BEFORE the fetch would be gesture-safe but Chrome creates the chosen file the moment it is picked, so a failed or cancelled export would leave an empty file, breaking 'on failure write no file'. So the order is: fetch the whole document, then call the picker; if the browser refuses (SecurityError / NotAllowedError because the click is stale) saveTextFileAs answers {kind:'needs-gesture'} and the view shows 'The export is ready. [Save as…]', whose click opens the dialog with a fresh gesture; the fetched text is kept, nothing is exported twice. AbortError (the user cancelled) is {kind:'cancelled'}: nothing written, nothing shown. Desktop (Wails) dialogs need no gesture, so the native dialog opens straight after the fetch. NOT verified in a real Wails webview or in Safari/Firefox; in Chrome the picker was exercised in Playwright with a stubbed showSaveFilePicker (suggestedName and the written bytes checked), not with the real OS dialog.
