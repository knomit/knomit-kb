# Export does NOT use showSaveFilePicker (user ruling): a browser export is a plain download, because the picker needs a fresh click, leaves an empty file when the export then fails, and does not exist in Safari or Firefox

The browser save picker was built first and then removed by ruling (2026-10-29): browsers download into their configured download location, identically everywhere; only the desktop app asks (native dialog, NativeService.SaveFileAs, opened in Downloads). Why the picker was a poor fit, so nobody reintroduces it: (1) showSaveFilePicker exists only in Chromium and needs transient user activation (a few seconds after a click), but Export fetches the whole document (up to a few MB) first, so the click is often stale and the dialog is refused (SecurityError/NotAllowedError); (2) opening it BEFORE the fetch is gesture-safe but Chrome creates the chosen file the moment it is picked, so a failed or cancelled export leaves an empty file, breaking 'on failure write no file'; (3) Safari and Firefox have no picker, so a second code path with a confirmation was needed. The code for all that (needs-gesture outcome, Save as... step, the cannot-ask confirmation) is gone. saveTextFile (fleet bundle and root key) still prefers the picker where it exists; that is a different caller and was not changed. Does NOT mean: the desktop may write without asking; it must always show the native dialog.
