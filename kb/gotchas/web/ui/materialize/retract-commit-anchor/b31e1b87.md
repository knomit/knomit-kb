# Materialize at a retract commit must use the read's own commit (fact.commit_hash), not the view's anchor: at the anchor the fact does not exist

The timeline lists the commit that RETRACTED a fact as one of its versions. Viewing the fact there, FactView reads it with ?fallback=before (history mode with an anchor), and the server answers with the LAST LIVE version, setting as_of.commit (the client's fact.commit_hash) to that version's commit, not the anchor. Materializing at the anchor asks /commits/<retract>/facts/<path>/materialize/pages for a fact that is not in that tree: 404 'could not read <path> at <commit>'.

Fix (PR #793, squash-merged as b7a34667): FactView's materializeCommit(anchorCommit, fact) gives `fact.commit_hash || anchorCommit` when anchored, undefined when live. It equals the anchor whenever the read did NOT fall back, because readFact (handlers_fact_read.go) returns head = a.Commit for a non-fallback anchored read; only the fallback branch returns a different commit (fbRes.FromCommit). So the change touches exactly the retracted-at-anchor case.

The page URL is not rewritten: Browse's materialize writes only its options (materialize=1, mat_*), and the URL's anchor stays the retract commit. A reload re-derives the same commit. The chat side panel mounts the same FactView with materializeInUrl=false, so it gets the fix too.

Consequence for any other anchored action on the shown fact (export, edges, copy-at-commit): if it addresses the fact at the anchor, it has the same bug at a retract commit. Use the read's as_of.commit.
