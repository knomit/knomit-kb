# RightPanel's breadcrumb title cache must only record a fact under the path it was LOADED for: the panel keeps the previous fact while a new path loads, so pairing state `fact` with the new factPath labels the new crumb with the old title

SYMPTOM (PR #747, browser): lens with history open, alpha fact 1 open, alpha unticked. The trail read "alpha fact 1 › alpha fact 1". The FIRST crumb (dim) was correct: the previous fact, alpha@live, as selectTrail's prefix (AMEND_NAV does not push). The SECOND crumb, the current one (bright, beta fact @ 690a0ca), was WRONG: it showed the previous fact's title.

CAUSE: the CACHE_FACT_TITLE effect ran on [fact, factPath, anchorCommit] and dispatched factTitleKey(factPath, anchorCommit) -> fact.title. On a switch, RightPanel keeps the PREVIOUS `fact` until the new one loads (see 3458261b), so for that render it paired the NEW path and commit with the OLD title. Normally the new fact's load overwrites the entry. When the new read never yields a fact (404 commit_not_in_repo, the no-version state), the wrong title stays. The cache key is path@commit, so the bad entry lands exactly on the new crumb's key, and TrailBreadcrumb trusts the shared cache before its own fetch.

FIX: the success paths in the fact-read effect call showFact(f), which records factLoadedFor.current = factPath before setFact. The cache effect requires factLoadedFor.current === factPath. Test: RightPanel.lens.test "never caches the previous fact's title under the new path...". A sabotage that removed the gate turned it red. After the fix the browser shows "alpha fact 1 › beta fact 1".

CONSEQUENCE: any effect that derives something keyed on factPath from `fact` must check that the fact belongs to that path. The rule from 3458261b (gate readers of state.factPath) applies to the loaded fact too. This is a different failure from ce646108, which is about WHICH endpoint a crumb fetches its title from.
