# Making the top bar tab strip shrink-proof at a phone width collapses the target label to 13px (2px for a fleet): the label needs a min-width and the strip must scroll itself

The first cut of PR #534 stopped the 375px tab clipping by making the facet tab strip flexShrink 0 so the target label would 'give way first (with an ellipsis)'. The review measured the result in a real browser: the label gave way ENTIRELY, to 13px (alpha shown as 'a') and to 2px for a fleet with its master chip, with no ellipsis visible, so with the rail closed the user could not tell which repository, lens or fleet they were on. Every vitest passed, and the PR's own sweep logged the rect without stating the result.

The trap is the compound: a flex row of [brand, sep, label, divider, tabs, gear] at 375px has too little width, and whichever item is allowed to shrink absorbs ALL of the shortage. Making the strip rigid just moves the starvation to the label.

Fix as merged (59813b66): the label has min-width 96px, its name span 3ch, and the tab strip shrinks and scrolls inside itself (flexShrink 1, overflowX auto), with rigid tab buttons. Measured after: label 96px (119 for a long name, ellipsis, full name in the `title`), strip 76-99px.

CONSEQUENCE: when tightening a flex row for a narrow viewport, assert the width of EVERY item that can shrink (label >= ~60px at 375px), not only that nothing clips or scrolls the page; and pin the min-width through the cascade (see the cascade test util convention).

WHAT THIS DOES NOT MEAN: it does not say the strip must scroll at every width; at 641px and wider all tabs are visible and unscrollable.
