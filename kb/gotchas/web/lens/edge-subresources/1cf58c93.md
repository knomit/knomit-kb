# FIXED — lens fact routes now dispatch /commits|/incoming|/outgoing against the resolved mount; they used to fall through into the fact reader and 500 "object not found" for EVERY fact

HISTORY (broken until the issue #178 fix): the repo-branch route registered facts/* as handleHALFact(b, p.factReader, p.factSub) — factSub dispatches the fact sub-resources. The lens route registered facts/* as handleHALLensFact(b, p.factReader) ONLY — no factSub. A request to /api/v1/lenses/{lens}/facts/{path}/incoming therefore matched the wildcard fact read with the literal path "kb/.../<uuid>.md/incoming", which fails inside readFileWithHash with HTTP 500 `entry ... /incoming: object not found` — for every fact, deterministically. Verified live 2026-08-29 against lens knomit-dev.

NOW: handleHALLensFact takes the factSub provider and dispatches /commits, /incoming and /outgoing itself. splitFactSubResource strips the suffix BEFORE addressing, because the lens route must resolve the mount from the FACT path, not from the URL naming one of its sub-resources — a kb://<id12>/… address parses only once the suffix is off. The three sub-resource handlers now take the resolved *repos.RepoInstance as a parameter instead of reading repos.RepoFromContext: under LensMiddleware that context value is the lens's WRITE repo, which is the wrong mount for a qualified path. The store is queried with the mount-relative path, and the emitted _links stay repo-scoped exactly as the lens fact body's do.

CONSEQUENCE: a consumer may now derive an edge URL from a lens fact URL by appending /incoming or /outgoing. The web UI's own path is unchanged — useFactEdges still waits for SET_FACT_SOURCE and calls api.explain against the SOURCE MOUNT's repo-scoped route — so this fix is for direct API consumers, not a UI behaviour change.

WHAT THIS DOES NOT MEAN: it did not mean lens facts had no edges, and it did not mean the store's edge index was broken — the same fact's edges always fetched fine through the repo route. The gap was purely the lens router surface. It also does NOT mean every trailing segment is now handled: a fact path with some OTHER trailing segment still 500s from the go-git tree walk, on the repo route as well as this one. Mapping that error to a 404 would also mask genuine object-store corruption, so it was left alone deliberately (see the issue #178 fix-shape decision).
