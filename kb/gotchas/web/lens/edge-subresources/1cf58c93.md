# Lens REST routes register NO fact sub-resources — /lenses/{lens}/facts/{path}/incoming|outgoing falls through into the fact reader and 500s "object not found" for EVERY fact

The repo-branch route registers facts/* as handleHALFact(b, p.factReader, p.factSub) — factSub dispatches the /incoming, /outgoing, /history, /snapshot sub-resources. The lens route registers facts/* as handleHALLensFact(b, p.factReader) ONLY — no factSub. A request to /api/v1/lenses/{lens}/facts/{path}/incoming therefore matches the wildcard fact read with the literal path "kb/.../<uuid>.md/incoming", which fails inside readFileWithHash with HTTP 500 `entry ... /incoming: object not found` — for every fact, deterministically. Verified live 2026-08-29 against lens knomit-dev.

CONSEQUENCE: any consumer that derives an edge URL from a lens fact URL by appending /incoming or /outgoing gets a 500 that looks like data corruption but is a missing route. The web UI dodges this only because useFactEdges waits for SET_FACT_SOURCE and then calls api.explain against the SOURCE MOUNT's repo-scoped route (/repos/{repo}/branches/{branch}/facts/{path}/incoming|outgoing), which works.

WHAT THIS DOES NOT MEAN: it does not mean lens facts have no edges, and it does not mean the store's edge index is broken — the same fact's edges fetch fine through the repo route. The gap is purely the lens router surface. If lens-level edge endpoints are added later, they must resolve the mount first (same LensMiddleware resolution the fact read uses).
