# The lens single-fact 404 detail must echo the requested wire path, qualifier included, at every not-found exit; echoing the mount-relative path at any exit turns the detail into a mount-topology oracle

handleHALLensFact (internal/edge/web/handlers_lenses_read.go) answers every not-found case (the exits are listed here; PR #620 adds the read-mount store-down exit at the end) through lensFactNotFound(w, r, requested): a malformed kb:// path, an unmounted id12, and a missing or retracted fact at a mounted id (the bare read, and the sub-resource gate that reads first). `requested` is the wire path exactly as the client sent it, qualifier included, and the detail is `no fact at path "<requested>"`.

CONSEQUENCE: keep echoing `requested` at all of these exits. TestLensFact_UnknownID404MatchesNotFound pins the detail exactly for a known mount with a missing fact and for an unmounted id.

DOES NOT MEAN: that echoing the mount-relative path (rel) is a harmless cleanup. Doing so at either exit makes the detail itself reveal topology: a mounted id would answer "kb/y/2.md" while an unmounted one answers "kb://<id12>/kb/y/2.md", so a caller iterating candidate ids reads "mounted" off the detail. The title being identical is not enough. (Review sabotage S11a and S11b, echo rel at either exit, were GREEN against the base tests and RED once the details were pinned; draft-reported.)

FIXTURE LESSON (an instance of kb/conventions/testing/web/99f75ede.md): the base test pinned the detail only where rel == requested (bare paths), so the choice between the two had one candidate and could not fail. A fixture for a choice needs a path where the two candidates differ (a qualified kb://<id12>/ path). The malformed-kb:// exit is not pinned by that test.

UPDATE (PR #620, user rulings 2026-10-24; verified at 1a860912): a READ mount whose store cannot be reached is a fourth not-found exit; the WRITE mount's is NOT. The write mount (a bare path, or kb://<id12>/ naming the write repo) answers the 503 "Repo not ready" every other route answers, because every lens has a write mount and saying it is down reveals no topology. A 503 on a read mount would be an oracle (an unmounted id answers 404), so a read mount keeps the byte-identical lensFactNotFound echoing the REQUESTED path. resolveLensFactMount decides the role ONCE from the resolved instance (readMount = rt.RI != bind.Write(), not whether the path was qualified); lensFactMount.answersNotFound(err) = errFactNotFound || (readMount && storeUnavailable) is asked at both readFact exits (the bare read and the sub-resource gate) and, as writeSystemFile's hideUnavailable argument, by the `.knomit/` read (serveLensSystemFileRead).

DOES NOT MEAN: that a bare lens fact path always 404s on a store failure (on the write mount it is the 503), or that a lens fan-out route hides it (facts, search, completions, motifs, motif cluster, stats and topics fail the whole request with the 503, RFC 9.1).

FIXTURE NOTE: a closed READ mount loses its id (Identify's exit), so a kb://<id12>/ path to it already resolves as unmounted (Binding.ByID) and answers the unmounted 404; the read-mount store-down branch is reachable only in a race and is pinned at the decision by TestLensFactMount_RoleDecidesTheUnavailableAnswer (PR-reported), with TestLensFact_ReadMountStoreUnavailableIsTheMissingFact404 covering the byte-identical 404 through the reachable unmounted equivalent.
