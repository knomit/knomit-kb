# net/http sets r.TLS ONLY when the accepted conn is literally a *tls.Conn, so wrapping a TLS listener's connections (to mark them, count them, anything) silently leaves r.TLS nil on every request — knomit marks the TLS listener with its own http.Server's ConnContext instead

`net/http`'s conn.serve does `if tlsConn, ok := c.rwc.(*tls.Conn); ok { … }` (server.go:1914, go1.26.6): it runs the handshake and fills `r.TLS` ONLY for that concrete type. A listener that returns ANY wrapper around the *tls.Conn — the natural way to tag 'this came from the TLS listener' — still carries TLS bytes, but every request arrives with `r.TLS == nil`. Nothing errors.

In knomit that would have made AuthMiddleware's step 1b refuse EVERY enrolled peer with 403 'Authentication required … no client certificate'. Measured by sabotage: wrapping the conns in auth.ListenTLS turns `TestTLSServer_RealHandshakeReachesTheHandlerAsTheInstancePrincipal` red with exactly that 403.

WHAT knomit DOES: `auth.ListenTLS` returns `tls.NewListener`'s listener UNWRAPPED. 'Which listener' is told by the SERVER: the TLS listener gets its own `http.Server`, sharing the Handler, whose `ConnContext` is `auth.TLSConnContext` and marks every connection; `auth.IsTLSListener(ctx)` reads the mark. `r.TLS != nil` is deliberately NOT the signal — it stops being unique once a second TLS listener exists (phase 3 tokens), and the TLS listener's rule (never anonymous, reads included) must not leak onto it.

CONSEQUENCE for tests: a unit test that builds `req.TLS = &tls.ConnectionState{…}` by hand proves only the mapping and CANNOT catch this; only a real handshake through the real listener can. Keep one such test for any code path that reads r.TLS.

MISREADING TO AVOID: this is not 'ConnContext cannot see TLS' — ConnContext receives the *tls.Conn fine, but it runs at accept, BEFORE the handshake, so peer certificates are not available there either. Map certificates to principals at request time from r.TLS.
