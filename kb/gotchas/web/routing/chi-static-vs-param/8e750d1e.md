# chi DOES backtrack from a static segment to the {repo} param — by method and by deeper path — so a static route shadows a same-named repo on exactly one method+path; what breaks a repo named `creates` is the greedy `{id}` CHILD, not an absence of backtracking

Repo names are `[a-z0-9_-]`, so `events`, `creates` and every other static segment under `/repos/` are LEGAL repo names, and a static sibling of `/repos/{repo}` can shadow one. How far the shadow reaches is the part that is easy to get wrong in both directions.

MEASURED, with a throwaway chi router registering `/repos/events` (static leaf, GET only), `/repos/creates/{id}`, and a `/repos/{repo}` subtree:

```
GET     /repos/events           -> STREAM          <- shadowed
DELETE  /repos/events           -> DELREPO:events  <- falls through
PATCH   /repos/events           -> PATCHREPO:events
GET     /repos/events/branches  -> BRANCHES:events <- falls through
GET     /repos/creates          -> GETREPO:creates <- works
GET     /repos/creates/branches -> CREATE:branches <- BROKEN
GET     /repos/normal           -> GETREPO:normal
```

SO: a static LEAF costs exactly one method+path, because chi retries the `{repo}` edge when the static edge has no handler for the method or no child for the next segment. A repo shadowed that way is otherwise completely usable — archive, patch, branches, facts all resolve.

A static segment with a PARAM CHILD is the dangerous shape. `/repos/creates/{id}` leaves `GET /repos/creates` working, then swallows every two-segment sub-route: `{id}` matches `branches` and wins. That is why `repo-creates` is a sibling collection rather than nested, and the decision is right.

THE REASON ONCE GIVEN FOR IT WAS WRONG, which is the trap this fact exists to close. `router.go` used to say chi "prefers a static segment over the {repo} param without backtracking, so nesting it here would make a repo actually named 'creates' unreachable at every route below." Backtracking demonstrably happens; what kills the `creates` case is the greedy param child. Acting on the rule as stated, a reader concludes that ANY static route under `/repos/` makes a same-named repo wholly unreachable — which overstates a static leaf's cost, and leaves them unable to predict which of two static routes is actually safe. The comment was corrected to the measured rule in PR #222; the rule to carry is: **static LEAF = one method+path shadowed; static + param child = the subtree below it is gone.**

THE PRACTICAL CONSEQUENCE IS NOW STRUCTURAL, not a judgement. Nothing static is allowed under `/repos/` at all — see the no-static-children invariant — precisely because this difference is invisible from "static beats param" and asking each route's author to work out which case they are in is how `/repos/events` shipped.

Verify before relying on this: it is a property of the chi version vendored here, established by running the table above, not by reading chi's docs.
