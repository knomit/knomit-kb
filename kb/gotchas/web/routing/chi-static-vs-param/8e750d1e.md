# chi DOES backtrack from a static segment to the {repo} param — by method and by deeper path — so a static route shadows a same-named repo on exactly one method+path; what actually breaks a repo named `creates` is the greedy `{id}` CHILD, not the absence of backtracking router.go's comment blames

Repo names are `[a-z0-9_-]`, so `events`, `creates` and every other static segment under `/repos/` are LEGAL repo names, and a static sibling of `/repos/{repo}` can shadow one. How far the shadow reaches is the part that is easy to get wrong in both directions.

MEASURED, with a throwaway chi router registering `/repos/events` (static leaf, GET only), `/repos/creates/{id}`, and a `/repos/{repo}` subtree:

```
GET     /repos/events           -> STREAM          <- shadowed
DELETE  /repos/events           -> DELREPO:events  <- falls through
PATCH   /repos/events           -> PATCHREPO:events
GET     /repos/events/branches  -> BRANCHES:events <- falls through
GET     /repos/creates          -> GETREPO:creates <- works
GET     /repos/creates/branches -> CREATE:branches <- BROKEN
GET     /repos/normal           -> GETREPO:normal
```

SO: a static LEAF costs exactly one method+path. `GET /api/v1/repos/events` reaches the index stream instead of a repo named `events`; that repo is otherwise completely usable — archive, patch, branches, facts all resolve, because chi retries the `{repo}` edge when the static edge has no handler for the method or no child for the next segment.

A static segment with a PARAM CHILD is the dangerous shape. `/repos/creates/{id}` leaves `GET /repos/creates` working, then swallows every two-segment sub-route: `{id}` matches `branches` and wins. That is why `repo-creates` is a sibling collection rather than nested, and the decision is right.

BUT THE STATED REASON IS WRONG, and it mispredicts. router.go's comment says chi "prefers a static segment over the {repo} param without backtracking, so nesting it here would make a repo actually named 'creates' unreachable at every route below." Backtracking demonstrably happens; what kills the `creates` case is the greedy param child. Acting on the comment as written, a reader concludes that ANY static route under `/repos/` makes a same-named repo wholly unreachable — which would have made `/repos/events` look far more expensive than it is, or, in the other direction, would leave them unable to predict which of two static routes is actually safe. The rule to carry is: static LEAF = one method+path shadowed; static + param child = the subtree below it is gone.
