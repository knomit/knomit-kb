# chi v5.4.0 registers the HTTP QUERY method on every Mount, so the API route table gains QUERY rows for /mcp mounts; regenerate the golden, do not treat it as a regression

Bumping github.com/go-chi/chi/v5 from v5.2.5 to v5.4.0 makes chi's method table include QUERY (RFC 10008), and Mount registers every method in that table. Consequence: internal/edge/web/testdata/route_table.golden gains 8 QUERY rows (the /mcp, /mcp/*, /lenses/{lens}/mcp, /lenses/{lens}/experiments/{name}/mcp and /repos/{repo}/branches/{branch}/mcp mounts, each with and without /*), and TestRouter_RouteTableMatchesGolden fails with 'route not in golden' until regenerated with `go test ./internal/edge/web -run TestRouter_RouteTableMatchesGolden -update-route-table`. The middleware chains on the new rows are identical to the POST rows; nothing else in the table changed. Before this bump a QUERY request to a mount got 405 from chi; now it passes the same auth/writeGate/scoped-mount middleware as POST (isMutatingRequest ignores QUERY, so writeGate does not demand write) and reaches mcpDispatch. mcp-go v0.45.0 StreamableHTTPServer.ServeHTTP switches only on POST/GET/DELETE and answers every other method with http.NotFound, so the observable result is 404 with body '404 page not found' (not 405); the JSON-RPC body is not executed and no SSE stream opens. Pinned by TestMCPMounts_QueryMethodIsRefused404 (internal/edge/web/mcp_query_method_test.go) on /mcp and the URL-scoped repo mount; verified falsifiable by making the dispatch rewrite QUERY to POST (status 200, test red). The lens mounts share the same mcpDispatch but are not exercised by that test. The 404 is mcp-go's behaviour, not ours: an mcp-go upgrade that handles extra methods turns the test red, which is the intent. Does NOT mean any new endpoint was added by us. If the golden diff on a future chi bump contains anything other than QUERY rows, that is a real routing change.
