# A read-only CodeMirror view is still contenteditable, so chatPanelState.typingIn read it as a text field and the side panel's Esc stopped closing the panel; the view marks its content data-k-readonly-text and typingIn exempts it. jsdom hides this: it has no isContentEditable

ChatSidePanel's window Esc handler skips the key when typingIn(document.activeElement) is true. typingIn returns true for INPUT/TEXTAREA/SELECT and for any element whose isContentEditable is true. A CodeMirror view with EditorState.readOnly (editable left on, which keyboard selection, Mod-F and the find bar need) has a contenteditable .cm-content, so with focus in the tool result Esc would no longer close the panel. Fix: JsonView sets EditorView.contentAttributes data-k-readonly-text='true', and typingIn returns false for anything inside [data-k-readonly-text] AFTER the INPUT/TEXTAREA/SELECT check (so the find bar's input, which lives inside the editor, still counts as typing; its own Esc handler calls preventDefault, which the panel handler honours via defaultPrevented).

Test trap: jsdom does not implement HTMLElement.isContentEditable (undefined), so a test that focuses .cm-content and presses Esc passes even without the exemption. ChatSidePanel.test defines isContentEditable=true on the element first and asserts typingIn directly; the sabotage pass showed the plain version stayed green.

Consequence: any new read-only editor surface inside the chat must carry data-k-readonly-text or Esc breaks there. Misreading to avoid: do not 'fix' this by setting EditorView.editable to false.
