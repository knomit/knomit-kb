# With no reachable store the origin endpoints disagree: GET origin 500, PUT origin 503 "No store available", PATCH upstream 500, DELETE origin 503 "Repo not open", and a GET /repos row simply has no remote key

Status of each origin route when the repo's store cannot be reached (getOrigin / setOriginUpstream get an Acquire failure and return it as errOriginNoStore). UNCHANGED by W0i (PR #619, merged 585974c5): the status matrix is the one the code had before the provider deletion. Read from handlers_origin_hal.go and handlers_repos_hal.go at 585974c5:
- GET /origin: 500 "Failed to get origin", detail the error text.
- PUT /origin (handleHALSetOrigin, prior-origin read via getOrigin): 503 "No store available".
- PATCH /origin upstream (handleHALSetOriginUpstream): 500 "No store available" when the error is errOriginNoStore, else 500 "Failed to set upstream branch".
- DELETE /origin: no getOrigin call; m.Send(DetachOrigin) and the lifecycle refusal map (writeLifecycleProblem): ErrNotOpen is 503 "Repo not open". That a store-less instance reaches ErrNotOpen is PR-REPORTED, not re-run.
- GET /repos row: remoteHealthOf returns nil on any getOrigin error or an absent origin, so the row has NO remote key (omitempty pointer). A consumer must read absence as "nothing to show", never as healthy (kb/decisions/web/repos/remote-health-on-listing/fd41124e.md).

STATUS: pre-existing inconsistency, NOT ruled on. A user ruling is pending on whether the origin routes should answer one status (and which wording, "Repo not ready" as the REST write path now uses, or "No store available"). Until ruled, do not assume a client can tell "store unavailable" from the status code alone on these routes; GET and PATCH answer 500 for it.

DOES NOT MEAN: that W0i introduced these answers or changed any of them; the tests pin them as they were.
