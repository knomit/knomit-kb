# A materialized fact's `depth` is its BFS distance from the root, NOT how deeply it nests in the article: a real walk with depth <= 6 nests 35 levels, so heading level, gutter, numbers and the section path must use the derived tree depth

Node.depth (internal/corpus/materialize/walk.go, set from the BFS node's dist) is the shortest distance from the root and is what the depth OPTION limits (0..10). The reading order is a pre-order DFS over that BFS-chosen set, so a fact cited down a chain nests as deep as the chain is long while its depth stays small. Measured on the local KB: kb/invariants/fleet/push-refusal/882f738f.md has BFS depth <= 6 but TREE depth 35 (in the browser run on the agent branch: 91 sections, tree depth 28, the gutter capped at 6); kb/decisions/mcp/learn/same-subject-refusal/f77be375.md has depth 10 and tree depth 14. Real articles are mostly long single-cite chains. CONSEQUENCE: anything about NESTING must use the tree depth derived by treeInfo() (parent = latest earlier non-ancestor node citing the fact): the heading ladder and tag, the depth gutter, the numbers and their 3-level cut, and the sticky section path. The first indented version (a guide line per level beyond 3) walked off the right edge on exactly these chains. The only legitimate uses of the payload's depth in the view are the option limit and the 'depth N reached' end line. A test fixture whose depth field is deliberately shallow on a long chain catches the mix-up. Does NOT hold on hand-built data where a fact cites only EARLIER facts (every fact then falls back to the top).
