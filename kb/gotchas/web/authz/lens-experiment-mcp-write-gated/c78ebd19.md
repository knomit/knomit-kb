# Today (old model) the lens-experiment MCP mount /lenses/{lens}/experiments/{name}/mcp is NOT matched by mcpRoutePattern (readonly.go), so writeGate demands the write permission for its POST/PUT/PATCH/DELETE, MCP reads included; the new registry treats it as kb:read like every other MCP mount

mcpRoutePattern matches only /repos/X/branches/Y/mcp, /lenses/X/mcp and /mcp (each followed by / or end). The lens-experiment mount added later (LensExperimentMiddleware, router.go) is not in it, so isMutatingRequest treats a POST there as a write and writeGate requires auth.Write even for knomit_query. A principal holding read but not write therefore cannot use MCP on a lens experiment, while it can on every other mount; the read-only demo gate would refuse it too.

Found by TestRouteRules_EquivalentToOldGates (P1), which reads the old gate off the live middleware chain. P1 is dark and changes no behaviour, so the old gate was left as is; the route registry declares the mount kb:read (design §3: the per-tool gate decides) and the equivalence test lists the 8 rows (POST/PUT/PATCH/DELETE x mcp and mcp/*) as intended deviations. The flip (P4) deletes mcpRoutePattern with writeGate, which removes the defect.

What this does NOT mean: writes through that mount are not unprotected after the flip: each MCP tool call is gated on its own permission (mcp.PermissionFor, kb:write for writes).
