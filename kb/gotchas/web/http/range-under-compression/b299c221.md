# A compressor in front of http.ServeContent turns every Range request into a malformed 206 — Content-Range describes identity bytes while the body is gzipped; knomit hides Accept-Encoding from the compressor whenever Range is present (identityForRangeRequests), and does NOT strip Range

chi's `middleware.Compress` wraps the ResponseWriter and gzips whatever the handler writes if the content type is on the allowlist. `http.ServeContent` (which `http.FileServer` uses) honours `Range` by writing status 206, a `Content-Range: bytes a-b/total` header describing the IDENTITY byte range, and then the identity bytes of that range — which the compressor then gzips. Result, measured by the reviewer on PR #223 before the fix: `GET /assets/x.js` with `Range: bytes=0-99` and `Accept-Encoding: gzip` → 206, `Content-Range: bytes 0-99/2017`, `Content-Encoding: gzip`, a ~90-byte body that gunzips to 100 bytes, and no Content-Length. That is a protocol violation: the header and the body disagree about what the bytes are, which corrupts resumable downloads and segmented CDN origin fetches. It was newly reachable because assets had never been behind a compressor before.

**The fix and why that shape.** `identityForRangeRequests` (internal/web/static.go) sits OUTERMOST in the static group and, when the request carries `Range`, deletes `Accept-Encoding` on a CLONE of the request before passing it down, so chi selects no encoder and the 206 is the identity bytes it claims. The alternative — stripping `Range` so the whole file is served — is also well-formed but answers a range request with the entire file, which is exactly the bandwidth the compression work exists to save. Ordering matters: the guard must run BEFORE the compressor, because it works by hiding the header from it. The API router needs no equivalent: its handlers (openapi, ontologies yaml) use plain `w.Write` and never honour Range.

**Misreadings to avoid.** (1) This does not mean the compressor is unsafe on static files in general; only Range responses are affected. (2) An unsatisfiable range returns 416, and the immutable cache stamp is status-gated (200/304/206 only), so a 416 carries no cache directive — do not 'fix' that by broadening the gate. (3) The tests assert the exact identity bytes and the Content-Range value, not just the absence of Content-Encoding; keep them that way. (4) This is a DIFFERENT trap from the allowlist one (chi-compress-allowlist): that one is about which types get compressed at all; this one bites even when the type is correctly listed.
