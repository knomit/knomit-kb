# internal/web/server.go Server.grants() still calls log.Fatal when [auth].loopback_default is invalid — unreachable from `knomit serve` only because app.New's seedOwnPrincipal parses the same value first and returns an error, and PR #286's AST guard against log.Fatal reads cmd/ only, so this latent os.Exit is not covered

After PR #286 (fixes #261) cmd/serve.go has no log.Fatal and a test (cmd/serve_run_test.go) parses cmd/ with go/ast and fails if one reappears. One remains on the serve path outside cmd/: internal/web/server.go:133, in Server.grants(), `log.Fatal().Err(err).Msg("[auth].loopback_default invalid")`. Today serve cannot reach it: app.New calls seedOwnPrincipal (internal/app/app.go, around L248), which parses cfg.Auth.LoopbackDefault first and returns an error, so the boot fails before any request is served. But the guard is by ORDERING, not by construction: a web.Server built by a path that skips seedOwnPrincipal (a test literal with a bad loopback_default, or a future boot path) would os.Exit inside a request handler, skipping every defer including the crash marker's release — exactly the #261 failure shape.

Consequence: if you touch Server.grants() or add a boot path, make that site return/propagate an error (or validate loopback_default in config.Validate) rather than relying on seedOwnPrincipal having run. Left out of scope in #286 and noted in its description. This is a different fact from the loopback-default-and-boot-seeding decision: that one is about WHAT grants() and the seed do; this one is about the exit path grants() takes on a parse failure.
