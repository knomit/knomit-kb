# Filtering a provider-returned slice with `kept := s[:0]` rewrites the provider's backing array — caught only by a two-requests-against-one-stub test

The motif vocabulary handler's ?q= narrowing was first written as `kept := clusters[:0]; ... append(kept, c)` over the slice the motifsProvider returned. That filters IN PLACE: it rewrites the caller-visible backing array, so any provider that returns a retained slice (a cache, or a test stub returning the same fixture twice) hands out corrupted data on the next call. With defaultMotifsProvider it was invisible (fresh slice per store read) — the failure surfaced only in a test that made TWO requests against ONE stub, where request 1 corrupted the cluster list request 2 read. Fixed by allocating a fresh slice for the narrow (and copying before the in-place name sort), with a comment saying why.

Consequences: (1) never `s[:0]`-filter or sort.Slice a slice received across an interface boundary unless the contract says the callee owns it; allocate. (2) A handler test that exercises each endpoint once cannot catch this class — reuse the same stub across two requests when the handler transforms provider data. (3) The implementation plan document itself carried the buggy code and its single-request tests passed over it; plan code blocks are input to review, not authority.
