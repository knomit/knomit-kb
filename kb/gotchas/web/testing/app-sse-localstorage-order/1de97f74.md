# The pre-existing App.sse.test.tsx failure ("after a resubscribe the new stream drives the app and the old one is dead", line 616) is a test-ORDER leak, not an SSE bug: vitest's jsdom HAS localStorage (on Node < 25 natively, on Node >= 25 only via the web/src/test-setup.ts shim) and it persists across tests in one file, the previous test saves {kind:repo,repo:beta} via saveLastContext, so the failing test boots straight into beta and its click on beta is a no-op — one branch stream, not two

SYMPTOM. `npx vitest run src/App.sse.test.tsx` fails exactly one of 44: `expect(streamsMatching('/branches/')).toHaveLength(2)` at App.sse.test.tsx:616 receives 1. Run alone with `-t`, the same test passes. Reproduced 2026-09-22 on clean dev at 5e1f539c.

NODE VERSION SCOPE (added 2026-09-23, issue #259). Everything below about jsdom's localStorage holds on Node < 25, which is where it was measured (the 2026-09-22 sessions ran Node 22). On Node >= 25 under vitest 4, `localStorage` in a test was Node's own global (undefined), NOT jsdom's, so this file failed ALL 44 tests with a TypeError at `localStorage.clear()`, which hid this order leak entirely. Since the fix for #259, web/src/test-setup.ts installs jsdom's Storage on every Node, so the statements below hold on both. See kb/gotchas/web/testing/node-webstorage-shadows-jsdom.

CAUSE, verified in three steps. (1) A throwaway two-test file showed `typeof localStorage === 'object'` and a value set in test A still readable in test B: the jsdom environment (jsdom ^29.1.1, vitest ^4.1.0, `environment: 'jsdom'`) provides a real, per-file-persistent localStorage on Node < 25. (2) App.sse.test.tsx's beforeEach carries a comment saying "this jsdom environment provides no localStorage at all … so there is no persisted context to clear" and therefore never clears it; that comment was written at 5437ab6c under the SAME jsdom and vitest majors, so it was wrong when written, not made wrong by an upgrade. (3) The test immediately before the failing one ("closes the old stream and opens a new one when the repo changes") switches to repo `beta`; App's `saveLastContext(state.context)` effect writes it; the failing test's mountApp then hits `loadLastContext()` → `pickRepo('', list, 'beta')` and boots on `/repos/beta/branches/…/events`. Its click on `toknomitr-repo-option-beta` changes nothing, so no teardown/resubscribe happens and only one branch stream ever exists. Adding `localStorage.clear()` to the file's beforeEach (temporarily, then reverted) made all 44 pass.

WHY IT LOOKED LIKE FLAKINESS. It is deterministic within the file, but it only bites when the earlier test runs first in the same worker, so it comes and goes with how the suite is invoked and with which files land in which worker; kb/conventions/testing/dev-box-limits recorded it present (2026-09-15/16), absent (2026-09-21) and present again (2026-09-22). The 2026-09-21 absence is now explained differently: that session ran Node 26, where App.boot's 11 failures were the webstorage TypeError and this file, which did not yet clear storage, could not observe persisted context from Node's undefined localStorage. The earlier attribution to d3a005be (PR #196) was a coincidence of when someone first ran the file after the resubscribe tests were added ahead of a boot that honours localStorage; nothing in that commit touches storage.

CONSEQUENCE. The house pattern already exists: App.boot.test.tsx, ManageSessions.test.tsx and repoSelection.test.ts all `localStorage.clear()` in beforeEach/afterEach. Any App-level test file whose tests can change `state.context` (a repo or lens switch) MUST do the same, and the "no localStorage" comment in App.sse.test.tsx should be deleted rather than left to mislead the next reader. Fix is a one-line test change, not app code; the resubscribe logic under test is correct.

FIXED, PR #246, merged as caa0d860. `localStorage.clear()` now sits in this file's beforeEach directly after `installFakeEventSource()`, and the misleading comment is replaced by one naming the leak. The failure was reproduced on clean dev at 5e1f539c immediately before the change and the file ran 44/44 after, so the evidence runs in both directions rather than only ending green. Only beforeEach clears, deliberately: App.boot.test.tsx also clears in afterEach, but each test FILE gets its own environment, so an afterEach could only guard against a leak that cannot cross files anyway.

MISREADING TO AVOID. This is NOT evidence that the SSE teardown/resubscribe is broken, and NOT a reason to add retries or longer waitFor timeouts — the stream count is exactly right for the repo the app actually booted into. It is also not a vitest parallelism issue (see kb/gotchas/web/testing/vitest-parallel-flakiness): `--no-file-parallelism` cannot change the order of tests inside one file. And #246 adding `localStorage.clear()` is what made this file fail 44/44 on Node >= 25 before the shim: that does NOT make #246 a regression, and reverting it re-opens this leak.
