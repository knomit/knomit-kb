# The pre-existing App.sse.test.tsx failure ("after a resubscribe the new stream drives the app and the old one is dead", line 616) is a test-ORDER leak, not an SSE bug: vitest's jsdom HAS localStorage and it persists across tests in one file, the previous test saves {kind:repo,repo:beta} via saveLastContext, so the failing test boots straight into beta and its click on beta is a no-op — one branch stream, not two

SYMPTOM. `npx vitest run src/App.sse.test.tsx` fails exactly one of 44: `expect(streamsMatching('/branches/')).toHaveLength(2)` at App.sse.test.tsx:616 receives 1. Run alone with `-t`, the same test passes. Reproduced 2026-09-22 on clean dev at 5e1f539c.

CAUSE, verified in three steps. (1) A throwaway two-test file showed `typeof localStorage === 'object'` and a value set in test A still readable in test B: the jsdom environment (jsdom ^29.1.1, vitest ^4.1.0, `environment: 'jsdom'`) provides a real, per-file-persistent localStorage. (2) App.sse.test.tsx's beforeEach carries a comment saying "this jsdom environment provides no localStorage at all … so there is no persisted context to clear" and therefore never clears it; that comment was written at 5437ab6c under the SAME jsdom and vitest majors, so it was wrong when written, not made wrong by an upgrade. (3) The test immediately before the failing one ("closes the old stream and opens a new one when the repo changes") switches to repo `beta`; App's `saveLastContext(state.context)` effect writes it; the failing test's mountApp then hits `loadLastContext()` → `pickRepo('', list, 'beta')` and boots on `/repos/beta/branches/…/events`. Its click on `toknomitr-repo-option-beta` changes nothing, so no teardown/resubscribe happens and only one branch stream ever exists. Adding `localStorage.clear()` to the file's beforeEach (temporarily, then reverted) made all 44 pass.

WHY IT LOOKED LIKE FLAKINESS. It is deterministic within the file, but it only bites when the earlier test runs first in the same worker, so it comes and goes with how the suite is invoked and with which files land in which worker; kb/conventions/testing/dev-box-limits recorded it present (2026-09-15/16), absent (2026-09-21) and present again (2026-09-22). The earlier attribution to d3a005be (PR #196) was a coincidence of when someone first ran the file after the resubscribe tests were added ahead of a boot that honours localStorage; nothing in that commit touches storage.

CONSEQUENCE. The house pattern already exists: App.boot.test.tsx, ManageSessions.test.tsx and repoSelection.test.ts all `localStorage.clear()` in beforeEach/afterEach. Any App-level test file whose tests can change `state.context` (a repo or lens switch) MUST do the same, and the "no localStorage" comment in App.sse.test.tsx should be deleted rather than left to mislead the next reader. Fix is a one-line test change, not app code; the resubscribe logic under test is correct.

MISREADING TO AVOID. This is NOT evidence that the SSE teardown/resubscribe is broken, and NOT a reason to add retries or longer waitFor timeouts — the stream count is exactly right for the repo the app actually booted into. It is also not a vitest parallelism issue (see kb/gotchas/web/testing/vitest-parallel-flakiness): `--no-file-parallelism` cannot change the order of tests inside one file.
