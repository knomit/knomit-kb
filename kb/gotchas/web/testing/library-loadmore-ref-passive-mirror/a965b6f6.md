# Library.lens duplicate offset fetch ([0,50,50]) is a stale loadMore closure: loadMoreRef is mirrored in a PASSIVE effect while lensLoadingRef is mirrored during RENDER, so a sentinel tick between a commit and its passive flush runs the previous loadMore with the loading guard already cleared

knomit#270, fixed in PR #273 (merged as ec38e06d; the fix is commit a20c9f91, hardened in 5038f422). The web-ui CI failure `stops paging once a page comes back short of the limit: expected [0, 50, 50] to deeply equal [0, 50]` and its sibling `pages again after a scope change` came from ONE mechanism in web/src/Library.tsx. Their symptoms are opposite. (This fact also carries the former incident record kb/incidents/web/library/paging-duplicate-page/5866b86c, merged into it by review dedup on 2026-09-24.)

MECHANISM (as of dev 9d83dd7a, before the fix). `lensLoadingRef.current = lensLoading` and `loadingRef.current = loading` were assigned DURING RENDER (still so at the merge, Library.tsx:660-662). `loadMoreRef.current = loadMore` was assigned in a PASSIVE `useEffect`, and the IntersectionObserver callback always calls `loadMoreRef.current()` (Library.tsx:762 at the merge). When page 2 resolves, one render sets rows=90, exhausted=true and loading=false, and commits. In the gap between that DOM commit and React's passive-effect flush, which can be a whole Scheduler task later and wider under load, the loading ref already read false while `loadMoreRef.current` was still the PREVIOUS closure (`lensExhausted=false`, `lensRows.length=50`, `total=140`). A sentinel tick in that gap passed every guard and requested `offset: lensRows.length` = 50 again. After a scope change the same gap held scope 1's closure, whose `lensExhausted=true` made it silently no-op, so offset 50 was never requested. The repo-Recent path shares the ref, and a stale `facts.length` gave the same duplicate there.

PRODUCTION REACH — this is a production defect, not only a test race. In a browser, an IntersectionObserver notification delivered in a task between React's commit and its passive-effect task ran the previous loadMore: in the lens union and repo Recent lists that fetched the offset just loaded, and rows 50-89 were appended twice (duplicate React keys); after a lens scope change the new list never paged. The OLD observer is still connected during that gap, because its disconnect is itself a passive cleanup. Reach is narrow (the sentinel must cross its threshold inside the window) but real.

THE FIX at the merge: `useLayoutEffect(() => { loadMoreRef.current = loadMore; })` (Library.tsx:754). Its comment says the guarantee assumes blocking-lane rendering: a startTransition around paging updates would reopen the gap. The repo Recent branch also sets `loadingRef.current = true` synchronously (Library.tsx:713), as the lens branch already did; without it two observer ticks before the setLoading re-render appended the next page twice. A requested-offset guard was deliberately NOT added (kb/decisions/web/library/requested-offset-guard-skipped-in-273).

THE SCOPE DIMENSION (knomit#275, PR #306; two more windows of the same shape).
(a) A stale page. #273 left the repo Recent branch of loadMore appending whatever page came back: a page requested for one scope and landing after a filter/path/query change put old-scope rows onto the new list and cleared the new scope's loading flag, even while the new scope's own first page was still in flight. The fix adds `recentGenRef`, the counterpart of `lensGenRef`. The Recent scope-reset `useAsync` bumps it as its FIRST statement, above its isLens/sort early returns, so leaving Recent also drops an in-flight page. (The lens effect bumps after `if (!isLens) return`.) loadMore snapshots it into `gen` beside the synchronous `loadingRef` write, and BOTH the `.then` (`if (gen !== recentGenRef.current) return;`) and the `.catch` (`setLoading(false)` only when `gen` is current) drop a stale response. The repo branch has no `total`/`exhausted` writes in loadMore, so rows and the loading flag are all the guard has to cover.
(b) A tick INSIDE the reset. The reset is a passive effect: it bumped the generation and called setLoading(true), but the loading ref was mirrored only on the NEXT render, and until then `loadMoreRef` held the closure rendered with the NEW scope's filters and the OLD row count. A sentinel tick in that window passed the loading guard and requested offset = old length from the new scope under the NEW generation, which the generation check cannot tell from a real page: page 1 then lands, and the list skips or duplicates rows. Both resets now write their loading ref synchronously beside setLoading(true): `loadingRef.current = true` in the Recent reset, and `lensLoadingRef.current = true` in the lens reset. The two refs are declared beside their state (not in the Infinite scroll block) so the resets, which come earlier in the component, can write them; the React Compiler lint rejects a ref written in an effect declared above the ref.
Regression anchors in Library.lens.test.tsx: describe 'Library — repo Recent drops a page requested for a previous scope' has a stale page landing after the new page 1 (and the next tick requests the new scope's offset 50), one landing before it (the spinner stays and no old row renders), and a stale page REJECTING before it (the spinner stays). Describe 'Library — a tick inside the scope reset requests nothing' covers repo Recent and the lens union, and expects exactly [0, 0] offsets. All five fail without their fix.

WHY TESTS HIT IT. RTL's waitFor succeeds on the DOM commit (a MutationObserver/microtask), not after passive effects. The test's `fire()` right after `waitFor(...90 rows)` landed in the gap whenever the runner was loaded.

THE RULE NOW.
1. A ref an event-source callback (IntersectionObserver, ResizeObserver, a DOM listener) reads to reach "the current function" must be mirrored in `useLayoutEffect` or during render, never in a passive `useEffect`, whenever other state that callback's guards read is mirrored during render. AFTER A COMMIT is not AFTER PASSIVE EFFECTS.
2. A paged fetch whose list a scope change can reset needs a generation token checked in both its success and its failure path. Both Library branches now have one.
3. Any code that sets a loading flag the callback's guard reads through a render-phase ref — the scope reset as much as loadMore itself — must write the ref synchronously too. setState alone leaves the guard open until the next render, and a generation token does not cover that window, because the tick runs under the new generation.

HOW TO TEST THIS CLASS — and the regression anchor. Fire the callback from a MutationObserver when the DOM shows the state you care about: that runs after the commit and before the passive flush, so the window is hit on every run. Wait on conditions (sentinel present plus observer registered; 'the tick at the commit has fired'), not sleeps: a tick's request is issued synchronously. See the describe 'Library — the sentinel sees the current list at the commit that shows it' in Library.lens.test.tsx (L691 at the merge). It has four tests with exact offset sequences: short page [0,50]; scope change [0,0,50]; repo Recent [0,50]; and repo Recent with two ticks before a re-render, which requests the next page once. The first three fail with the passive mirror; the fourth fails without the synchronous loadingRef write. If any of them fails again, the window is back: do not 'stabilise' them with waits. For a window INSIDE a passive effect (rule 3), a MutationObserver is too late: by the commit that shows the effect's result, render has mirrored the flag. Fire the tick synchronously from a mock the effect itself calls (the new scope's first-page request), which runs while the effect is still in the window.

MISREADING TO AVOID. This is not the older generation-0 observer race that kb/gotchas/web/testing/vitest-parallel-flakiness describes. That one was fixed by the single observer plus loadMoreRef; this was the residue of that fix, with the ref mirrored one phase too late. It is also not solved by more waitFor or by retries in the test. Nor is the layout-effect mirror a scope guard: it makes loadMore current, but a request already in flight when the scope resets is only dropped by the generation token, and a request issued INSIDE the reset is only prevented by the reset's synchronous loading-ref write.
