# Library.lens duplicate offset fetch ([0,50,50]) is a stale loadMore closure: loadMoreRef is mirrored in a PASSIVE effect while lensLoadingRef is mirrored during RENDER, so a sentinel tick between a commit and its passive flush runs the previous loadMore with the loading guard already cleared

knomit#270, fixed in PR #273 (merged as ec38e06d; the fix is commit a20c9f91, hardened in 5038f422). The web-ui CI failure `stops paging once a page comes back short of the limit: expected [0, 50, 50] to deeply equal [0, 50]` and its sibling `pages again after a scope change` came from ONE mechanism in web/src/Library.tsx. Their symptoms are opposite.

MECHANISM (as of dev 9d83dd7a, before the fix). `lensLoadingRef.current = lensLoading` and `loadingRef.current = loading` were assigned DURING RENDER (still so at the merge, Library.tsx:660-662). `loadMoreRef.current = loadMore` was assigned in a PASSIVE `useEffect`, and the IntersectionObserver callback always calls `loadMoreRef.current()` (Library.tsx:762 at the merge). When page 2 resolves, one render sets rows=90, exhausted=true and loading=false, and commits. In the gap between that DOM commit and React's passive-effect flush, which can be a whole Scheduler task later and wider under load, the loading ref already read false while `loadMoreRef.current` was still the PREVIOUS closure (`lensExhausted=false`, `lensRows.length=50`, `total=140`). A sentinel tick in that gap passed every guard and requested `offset: lensRows.length` = 50 again. After a scope change the same gap held scope 1's closure, whose `lensExhausted=true` made it silently no-op, so offset 50 was never requested. The repo-Recent path shares the ref, and a stale `facts.length` gave the same duplicate there.

THE FIX at the merge: `useLayoutEffect(() => { loadMoreRef.current = loadMore; })` (Library.tsx:754). Its comment says the guarantee assumes blocking-lane rendering: a startTransition around paging updates would reopen the gap. The repo Recent branch also sets `loadingRef.current = true` synchronously (Library.tsx:713), as the lens branch already did.

WHY TESTS HIT IT. RTL's waitFor succeeds on the DOM commit (a MutationObserver/microtask), not after passive effects. The test's `fire()` right after `waitFor(...90 rows)` landed in the gap whenever the runner was loaded.

THE RULE NOW. A ref an event-source callback (IntersectionObserver, ResizeObserver, a DOM listener) reads to reach "the current function" must be mirrored in `useLayoutEffect` or during render, never in a passive `useEffect`, whenever other state that callback's guards read is mirrored during render. AFTER A COMMIT is not AFTER PASSIVE EFFECTS.

HOW TO TEST THIS CLASS. Fire the callback from a MutationObserver when the DOM shows the state you care about: that runs after the commit and before the passive flush, so the window is hit on every run. Wait on conditions (sentinel present plus observer registered; 'the tick at the commit has fired'), not sleeps: a tick's request is issued synchronously. See the describe 'Library — the sentinel sees the current list at the commit that shows it' in Library.lens.test.tsx (L691 at the merge). It has four tests with exact offset sequences: short page [0,50]; scope change [0,0,50]; repo Recent [0,50]; and repo Recent with two ticks before a re-render, which requests the next page once. The first three fail with the passive mirror; the fourth fails without the synchronous loadingRef write.

MISREADING TO AVOID. This is not the older generation-0 observer race that kb/gotchas/web/testing/vitest-parallel-flakiness describes. That one was fixed by the single observer plus loadMoreRef; this was the residue of that fix, with the ref mirrored one phase too late. It is also not solved by more waitFor or by retries in the test.
