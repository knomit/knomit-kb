# Library.lens duplicate offset fetch ([0,50,50]) is a stale loadMore closure: loadMoreRef is mirrored in a PASSIVE effect while lensLoadingRef is mirrored during RENDER, so a sentinel tick between a commit and its passive flush runs the previous loadMore with the loading guard already cleared

knomit#270. The web-ui CI failure `stops paging once a page comes back short of the limit: expected [0, 50, 50] to deeply equal [0, 50]` and its sibling `pages again after a scope change` come from ONE mechanism in web/src/Library.tsx. Their symptoms are opposite.

MECHANISM (at 9d83dd7a). `lensLoadingRef.current = lensLoading` is assigned DURING RENDER (L661-662), but `loadMoreRef.current = loadMore` is assigned in a PASSIVE `useEffect` (L743). The IntersectionObserver callback always calls `loadMoreRef.current()` (L751). When page 2 resolves, one render sets rows=90, exhausted=true and loading=false, and it commits. In the gap between that DOM commit and React's passive-effect flush, `lensLoadingRef.current` is already false while `loadMoreRef.current` is still the PREVIOUS closure (`lensExhausted=false`, `lensRows.length=50`, `total=140`). A sentinel tick in that gap passes every guard and requests `offset: lensRows.length` = 50 AGAIN. In the scope-change test the same gap yields the other symptom: the stale closure is scope 1's, `lensExhausted=true`, so it silently no-ops and offset 50 is never requested.

WHY TESTS HIT IT. RTL's waitFor succeeds on the DOM commit (a MutationObserver/microtask), not after passive effects. React 19 runs a default-lane commit's passive effects in a later Scheduler task, which yields every ~5ms. Under CPU load the gap widens, and the test's `fire()` right after `waitFor(...90 rows)` lands in it.

PROOF, DETERMINISTIC (2026-09-23, Node 22.23.2). A probe fired the observer callback from a MutationObserver when row 90 appeared, i.e. after the commit and before the passive flush: 3/3 `[0, 50, 50]`, the exact CI signature. Changing ONLY L743 to `useLayoutEffect` made the probe pass 3/3 (reverted afterwards; diagnosis only). The file alone passes 10/10 unloaded.

PRODUCTION REACH: real but narrow. A browser can deliver an IntersectionObserver notification in a task between React's commit and its passive-effect task. The old observer is ALSO still connected in that gap, because its disconnect is itself a passive cleanup. The sentinel must cross the threshold inside that window, so it is rare. The effect would be rows 50-89 appended twice (duplicate React keys). The repo-Recent branch of loadMore has the same shape (loadingRef assigned in render, stale `facts.length`).

The comment at L739-741 ("an IntersectionObserver callback only ever fires after a commit, so post-commit freshness is enough") is the wrong premise: AFTER A COMMIT is not AFTER PASSIVE EFFECTS.

MISREADING TO AVOID: this is not the older generation-0 observer race that kb/gotchas/web/testing/vitest-parallel-flakiness describes. That one was fixed by the single observer plus loadMoreRef, and this is the residue of that fix's ref being mirrored one phase too late. It is also not solved by more waitFor or retries in the test.
