# RepoManager 'releases the selection when you scroll under your own steam' is a jsdom artefact: with zero layout, SettingsPage's scroll-spy always decides 'scrolled to the end' and spies the LAST section, which is the very section (danger) the test expects to lose aria-current

knomit#270, fixed in PR #273 (commit bffd1cf5). web/src/SettingsPage.tsx computes the spied section on a requestAnimationFrame after mount and on scroll/resize. In jsdom scrollHeight, scrollTop and clientHeight are all 0, so `scrollHeight - scrollTop - clientHeight <= 2` is always true and `spied` becomes the LAST section. `active = pinned ?? spied`. In RepoManager's repo detail the last section is `danger`.

The old test pinned toc-danger, fired a wheel (which clears the pin, leaving active = spied), and waited for toc-danger to LOSE aria-current. That only happened if the wheel landed before the spy's first rAF, while spied was still the initial first section. Once the ~16ms jsdom rAF had run, spied = danger and the assertion could never pass. Load decided which won; with a 50ms pause before the wheel it failed 3/3.

TEST-ONLY. In a browser, releasing the pin while scrolled to the end correctly leaves the last section current. The oracle was wrong, not the code.

THE FIX, and the rule for any scroll-spy test in jsdom: pin a NON-LAST section (the test now pins `index`), and await one requestAnimationFrame inside act BEFORE the release, so the release is judged against the spy's settled answer on every run. The test carries a comment naming this, so it is not 'fixed' back to danger. Sanity: the test fails without the wheel, so it still tests the release.

NOT the Library.lens mechanism, and not a fixture shared with App.boot (App.boot never mounts RepoManager's settings page).
