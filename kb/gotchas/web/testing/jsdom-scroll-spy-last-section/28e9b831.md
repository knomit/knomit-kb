# RepoManager 'releases the selection when you scroll under your own steam' is a jsdom artefact: with zero layout, SettingsPage's scroll-spy always decides 'scrolled to the end' and spies the LAST section, which is the very section (danger) the test expects to lose aria-current

knomit#270. web/src/SettingsPage.tsx computes the spied section on a requestAnimationFrame after mount and on scroll/resize (L94-135). In jsdom scrollHeight, scrollTop and clientHeight are all 0, so `scrollHeight - scrollTop - clientHeight <= 2` is always true and `spied` becomes the LAST section. `active = pinned ?? spied`. In RepoManager's repo detail the last section is `danger` (RepoManager.tsx L1229).

The test (RepoManager.test.tsx L237-247) clicks toc-danger (pin = danger), fires a wheel (pin released, active = spied), and waits for toc-danger to LOSE aria-current. That only happens if the wheel lands before the spy's first rAF, when spied is still the initial first section. Once the ~16ms jsdom rAF has run, spied = danger and the assertion can never pass, so waitFor times out. Load decides which one wins.

PROOF, DETERMINISTIC (2026-09-23): the same test with a 50ms pause before the wheel fails 3/3.

TEST-ONLY. In a browser, releasing the pin while scrolled to the end correctly leaves the last section current. The oracle is what is wrong: the test pins the one section the spy will report anyway. Pinning a NON-last section (e.g. index) and asserting it loses aria-current is deterministic whichever way the rAF lands.

NOT the Library.lens mechanism, and not a shared fixture with App.boot (which never mounts RepoManager's settings page).
