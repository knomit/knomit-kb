# RepoManager 'releases the selection when you scroll under your own steam' is a jsdom artefact: with zero layout, SettingsPage's scroll-spy always decides 'scrolled to the end' and spies the LAST section, which is the very section (danger) the test expects to lose aria-current

knomit#270, fixed in PR #273 (merged as ec38e06d; commits bffd1cf5 and cbee464e). web/src/SettingsPage.tsx computes the spied section on a requestAnimationFrame after mount and on scroll/resize. In jsdom scrollHeight, scrollTop and clientHeight are all 0, so `scrollHeight - scrollTop - clientHeight <= 2` is always true and `spied` becomes the LAST section. `active = pinned ?? spied` (spied is initialised at SettingsPage.tsx:51). In RepoManager's repo detail the last section is `danger` (RepoManager.tsx:1229).

The old test pinned toc-danger, fired a wheel (which clears the pin, leaving active = spied), and waited for toc-danger to LOSE aria-current. That only happened if the wheel landed before the spy's first rAF, while spied was still the initial first section. Once the ~16ms jsdom rAF had run, spied = danger and the assertion could never pass. Load decided which won; with a 50ms pause before the wheel it failed 3/3.

TEST-ONLY. In a browser, releasing the pin while scrolled to the end correctly leaves the last section current. The oracle was wrong, not the code.

THE FIX, and the rule for any scroll-spy test in jsdom (RepoManager.test.tsx:237-259 at the merge): pin a NON-LAST section (the test now pins `index`), await one requestAnimationFrame inside act, then RE-ASSERT the pin still holds, and only then fire the wheel. That way the release is judged against the spy's settled answer on every run, and the final assertion proves the wheel cleared the pin rather than something earlier. The test carries a comment naming the jsdom reason, so it is not 'fixed' back to danger. Sanity: the test fails without the wheel.

NOT the Library.lens mechanism, and not a fixture shared with App.boot (App.boot never mounts RepoManager's settings page).
