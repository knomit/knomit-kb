# web vitest flakes are effect/waitFor races, NOT a parallelism bug — --no-file-parallelism only narrows the window

The web/ vitest suite has nondeterministic flakiness under CPU load. The failures are React effect/`waitFor` races that lose when a passive effect has not flushed before an assertion runs — they are NOT logic bugs, and they are NOT caused by file parallelism.

DO NOT REACH FOR `--no-file-parallelism`. An earlier revision of this fact prescribed it as the "verification workaround". That is a MASK: parallel workers only add CPU contention, which widens an already-existing race window. Proof (2026-07-21): the sentinel flake reproduces running its file ALONE, with zero file parallelism, purely by adding background CPU load. Fix the race in the test; do not serialize the suite. As of 2026-07-21 the flag appears nowhere in package.json, vite.config.ts, the Makefile or CI, and git log -S finds no commit that ever added it — so the earlier advice was never actually applied, and the suite has been running parallel all along.

RATE, measured 2026-07-21: roughly 1 full-suite run in 8-15 fails, not the "3 of 4" an earlier revision claimed. The rate fell because racy tests were hardened over time, so treat any rate figure here as a snapshot, not a constant.

ROOT CAUSE OF THE SENTINEL FLAKE (fixed by P1.7): Library.tsx re-creates its IntersectionObserver whenever `loadMore`'s identity changes, so several observer callback generations exist over a test's life. The test fired `observerCallbacks[observerCallbacks.length - 1]`, but the preceding `waitFor` guarantees only the DOM COMMIT of the first page — not the passive effect that registers the post-fetch observer. Under contention the DOM assertion wins that race, so the test fires the STALE generation-0 closure, whose guard `lensRows.length >= total` evaluates `0 >= 0` and returns. That is a SILENT no-op: no second fetch, no error, and the next waitFor simply times out with a confusing row-count mismatch. Two paging tests carried this race; both are fixed by retrying against the CURRENT last callback until the expected offset is actually requested.

HARDENING PATTERN (this part of the original fact was right): wrap the state you actually assert on inside `waitFor(...)` rather than asserting eagerly after a separate `waitFor` on something else. Corollary for observer-driven tests: never assume the last registered callback is the current one — await the registration you need.

WHAT THIS DOES NOT MEAN: it does not mean every flake here is this exact race. Library.sort.test.tsx's `selectedIdx` highlight assertion is a different instance of the same CLASS (an effect committing one render after the rows appear). Diagnose each on its own; the shared lesson is the class, not the instance.
