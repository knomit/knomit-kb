# web vitest flakes are effect/waitFor races, NOT a parallelism bug — --no-file-parallelism only narrows the window

The web/ vitest suite has nondeterministic flakiness under CPU load. The failures are React effect/`waitFor` races that lose when a passive effect has not flushed before an assertion runs — they are NOT logic bugs, and they are NOT caused by file parallelism.

DO NOT REACH FOR `--no-file-parallelism`. An earlier revision of this fact prescribed it as the "verification workaround". That is a MASK: parallel workers only add CPU contention, which widens an already-existing race window. Proof (2026-07-21): the sentinel flake reproduces running its file ALONE, with zero file parallelism, purely by adding background CPU load. Fix the race in the test; do not serialize the suite. As of 2026-07-21 the flag appears nowhere in package.json, vite.config.ts, the Makefile or CI, and git log -S finds no commit that ever added it — so the earlier advice was never actually applied, and the suite has been running parallel all along.

RATE, measured 2026-07-21: roughly 1 full-suite run in 8-15 fails, not the "3 of 4" an earlier revision claimed. The rate fell because racy tests were hardened over time, so treat any rate figure here as a snapshot, not a constant.

ROOT CAUSE OF THE SENTINEL FLAKE (fixed by P1.7): Library.tsx re-creates its IntersectionObserver whenever `loadMore`'s identity changes, so several observer callback generations exist over a test's life. The test fired `observerCallbacks[observerCallbacks.length - 1]`, but the preceding `waitFor` guarantees only the DOM COMMIT of the first page — not the passive effect that registers the post-fetch observer. Under contention the DOM assertion wins that race, so the test fires the STALE generation-0 closure, whose guard `lensRows.length >= total` evaluates `0 >= 0` and returns. That is a SILENT no-op: no second fetch, no error, and the next waitFor simply times out with a confusing row-count mismatch. Two paging tests carried this race; both are fixed by retrying against the CURRENT last callback until the expected offset is actually requested.

HARDENING PATTERN (this part of the original fact was right): wrap the state you actually assert on inside `waitFor(...)` rather than asserting eagerly after a separate `waitFor` on something else. Corollary for observer-driven tests: never assume the last registered callback is the current one — await the registration you need.

KNOWN MEMBERS (2026-09-16 review of PR #208 added two, and they widen the class beyond paging): `Library.lens.test.tsx` (scope-change paging), `Library.sort.test.tsx` (sentinel offset, and separately the `selectedIdx` highlight), `Library.memo.test.tsx > selecting a row re-renders only the rows whose selection actually changed` — a RENDER-COUNT assertion, so one stray extra render is enough — and `RepoManager.test.tsx > releases the selection when you scroll under your own steam`. Same class, different surfaces: a render-count oracle is as load-sensitive as a waitFor one.

**UPDATE 2026-09-24 (PR #273, knomit#270) — two members are no longer this class.** `Library.lens.test.tsx` paging turned out to be a PRODUCTION stale-closure race (the loadMore ref mirrored one phase too late — kb/gotchas/web/testing/library-loadmore-ref-passive-mirror), and `RepoManager.test.tsx > releases the selection…` a jsdom zero-layout oracle (kb/gotchas/web/testing/jsdom-scroll-spy-last-section); both are fixed with deterministic commit-time or settled-state tests, so a failure in either is now a REAL failure. `Library.sort` and `Library.memo` remain members. The lesson generalises: a member of this class can hide a real defect — diagnose each one rather than filing it here by symptom.

ATTRIBUTION RULE, and the trap that makes it necessary. Re-run the suite on the BASE COMMIT UNDER LOAD before blaming a diff for a flake. Measured 2026-09-16: on `dev` at 6f0fcc53 the suite passed 5/5 unloaded, then under 6-way CPU load failed the RepoManager scroll test on that same commit — with none of the branch's code present. The branch had looked guilty for a good reason: it introduced `useRepoCreates`, a MODULE-LEVEL shared store with a poller, mounted by `RepoManager`, and `RepoManager.test.tsx` never calls `__resetRepoCreatesForTest` the way the new test files do. Cross-test state bleed is a compelling story for exactly that failure, and it is the wrong one — vitest isolates module state PER TEST FILE by default (`isolate: true`, forks pool), so it cannot reach `Library.*` at all, and the file passes 12/12 standalone.

What a branch that merely ADDS test files contributes is suite concurrency (104 files to 107), which is more CPU contention, which widens the existing window. That is the same mechanism as the 2026-07-21 proof, arriving by a different route: the diff is the load, not the bug.

WHAT THIS DOES NOT MEAN: it does not mean every flake here is one race. Diagnose each on its own; the shared lesson is the class, not the instance. It also does not mean a module-level store in a component under test is FINE — it is a real hazard worth resetting between tests — only that per-file isolation rules it out as the explanation for failures in OTHER files.
