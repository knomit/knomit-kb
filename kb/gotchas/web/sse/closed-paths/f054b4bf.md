# An event stream ends CLOSED only on a refusal or the client's own close(): EventSource on a non-200 answer or wrong content type, WailsEventSource only on the desktop's error frame with closed:true; readyState is already CLOSED when that error dispatches

WHICH PATHS END CLOSED (readyState 2), per transport behind openEventStream (web/src/eventStream.ts):
- Browser EventSource: the connection fails for good on a non-200 HTTP answer or a Content-Type other than text/event-stream (e.g. the server refusing GET /chats/events). A plain network loss is NOT one: EventSource goes CONNECTING and retries. Per the HTML spec, 'fail the connection' sets CLOSED and then fires error, so a listener reading readyState inside the error event sees 2.
- WailsEventSource (desktop): only (a) an `error` frame with `closed: true` (the desktop's upstream leg was refused; `status` carries the HTTP code), where onFrame sets CLOSED and drops the socket BEFORE dispatching error, and (b) the caller's own close(), which also clears every listener so nothing hears it. Everything else stays CONNECTING and retries with the 0.5-5 s backoff: an error frame without closed, the Wails socket's onclose, the stale-stream watchdog (STALE_STREAM_MS), and a failed import of /wails/runtime.js.

CONSEQUENCE: code that wants to recover a dead stream detects it as `error` with readyState === 2 at dispatch time; an error with readyState 0 means the transport is already retrying and a second stream would duplicate it. chatEvents.ts's hub relies on exactly this ordering (pinned for Wails by the refusal test in eventStream.test.ts, which records readyState inside the error listener). Changing WailsEventSource to dispatch error before setting CLOSED would silently disable the hub's reopen on the desktop.

WHAT THIS DOES NOT MEAN: a CLOSED stream is not proof the server is down for good; a refusal can be transient (a server restarting behind the desktop proxy), which is why the chat hub reopens with back-off rather than giving up.
