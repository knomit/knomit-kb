# A proxy that compresses or buffers text/event-stream silently kills every SSE stream — the server writes and flushes normally, the connection stays open, and the browser receives nothing; `Cache-Control: no-cache, no-transform` plus `X-Accel-Buffering: no` is the fix, and a stream with a poll fallback hides the symptom

**The symptom.** Manage → Logs shows "Waiting for log output…" forever while the terminal scrolls. Nothing else looks wrong: the endpoint returns 200, the server writes every frame and flushes it, the connection stays open, no error appears in the app, the server log, or the browser console.

**The cause.** An intermediary that compresses by content type will happily gzip an SSE response, because it is `text/*` — and a compressor BUFFERS. The maintainer reaches knomit through Tailscale → code-server → its `/proxy/<port>/` path proxy; code-server wraps proxied responses in Express `compression`. Measured through that path with a browser's Accept-Encoding: **10 bytes in 20 s** (the gzip header, nothing else), versus **39 frames in 6 s** for the same URL with no Accept-Encoding.

**The fix, in startSSE so it covers every endpoint at once:**

    Cache-Control: no-cache, no-transform
    X-Accel-Buffering: no

`no-transform` is the standard prohibition (RFC 9111 §5.2.2.6) and is exactly what compression's `shouldTransform` checks. Its regex is `/(?:^|,)\s*?no-transform\s*?(?:,|$)/` — anchored to a comma boundary — so the directive MUST stand alone and must not be glued to another token. A test asserting the header merely *contains* "no-transform" would pass on a value the module still compresses; pin it with that regex. `X-Accel-Buffering: no` is the nginx-family lever for proxies that buffer without compressing: non-standard, ignored by anything that does not know it, and the only thing that reaches that class.

**Verified end to end**, branch build vs dev through the real proxy, both sending Accept-Encoding: gzip — fixed: no Content-Encoding, 1790 bytes, 9 frames in 8 s; unfixed: `Content-Encoding: gzip`, 10 bytes, 0 frames.

**WHY IT HID, and the part worth remembering.** A stream with a POLL FALLBACK degrades to the poll: Sessions kept updating every 30 s and looked merely stale, so nobody suspected its stream was dead. Logs has no poll, so it showed an empty pane and became the visible symptom of a fault affecting all eight streams equally. A fallback that makes a broken transport look like a slow one is a debugging cost, not only a resilience benefit.

**The other half of the lesson:** none of this is visible from the server side or from a direct request to the port. Chrome and Firefox, eight viewports, DOM measurements and screenshots against 127.0.0.1 ALL looked perfect while the maintainer's page was empty, because the proxy was never in the path. For any "the UI is not updating" report, establish what sits between the browser and the server BEFORE measuring anything else.

**WHAT THIS DOES NOT MEAN:** not a reason to disable compression globally or to stop the UI being proxied. The headers are the targeted signal, and they are per-response.
