# Rail state for a chat created in this page comes from the page stream's per-chat chat_state record: events for chats not yet listed are kept, not dropped, and add() takes the record as the row

POST /chats with a first message starts the turn inside the create call, so that chat's running chat_state (and the title taken from the first message) go out on the page stream before the page knows the chat id; chat_state is sent only on change, so nothing repeats them. createChat answers with identity only. If the hub drops events for chats nobody subscribes to, the new row has no state (drawn idle) and no title (drawn as the model name) until a reload reads GET /chats.

Invariant: the hub (chatEvents.ts) records the latest chat_state per chat id for EVERY chat the stream carries, subscribed or listed or not (latestChatState). useChats watches the stream at page level (watchChatStates), which also keeps the stream open when no chat is listed yet. add(c) takes the record as the row's state, title, turns and times; later chat_state events apply to the row directly. No refetch. The record is bounded by the owner's own chats (the stream carries no one else's), is dropped on chat_end, cleared on every connect (ready), and goes with the stream when the last subscriber and watcher leave.

Precedence is the rule from the rail work: a chat_state received while a list read is in flight beats that read's older row (the during map); a chat added after a read began beats that read's row for it (the add carries what the stream said). The record is read only when a row is created by add(); it never overrides a listed row.

Does NOT mean: the list is never read again (it still is: on load, focus, and reconnect). The earlier shape that read GET /chats once after add() was replaced because it left a gap for an add during the first read and raced the response against an event. For the one-stream-per-tab work: the hub routes by topic and chat events carry the chat tag; keep the per-chat record keyed by that tag.
