# A chat created in this page has no chat_state in its rail row: POST /chats with a first message starts the turn before the page can subscribe, and chat_state is sent only on change, so useChats reads the new row once after subscribing

The page stream carries every chat of the caller, but the client drops an event for a chat nobody has subscribed to (chatEvents route). createChat answers with identity only (id, provider, model, name), and with a first message the server starts the turn inside that call, so its running chat_state and the title taken from the first message are sent before useChats has the chat in its list and subscribes. chat_state is sent only when the row changed, so nothing repeats them: the row kept no state (drawn idle) and no title (drawn as the model name) until a reload read GET /chats. Later events (a failure, the turn ending) did arrive, so only the state at creation was stale.

The fix: add() records the id as unread; once the subscription effect has subscribed it, and the first list read has landed, useChats reads GET /chats once and patches ONLY those rows (events applied meanwhile win). It never replaces the list, so the pin-backing-list invariant is untouched.

Not this: the rail is not wrong about chats listed at page load (the list read supplies their rows), and the fix is not a re-read of the list on every add. Re-pin the ref below to the merge commit after the PR merges.
