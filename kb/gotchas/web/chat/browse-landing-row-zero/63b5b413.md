# Landing in Browse on a fact from outside it must take the reveal path in a render the Library's in-flight list read cannot beat: in Recent or search the list selects row 0 when the open fact is not on page 1 and keeps the anchor, silently showing another fact at that commit

Library's Recent and search reads AMEND_NAV to row 0 when the open fact is not on the page they got, and AMEND_NAV keeps asOf. So a landing at a commit that keeps Browse's sort, filters or free text shows ANOTHER fact at that commit under a band that looks right. A fact retracted at HEAD is on no list, so Recent always got this wrong.

Two parts, both needed. (1) The reveal path (useNavigationManager, reveal with optional asOf): path chip, sort 'path', empty free text and, from a chat, since-fork off, one APPLY_NAV. A reveal inside Browse (a highlight) leaves since-fork on, and is demoted as before: it has no return that would restore it. Asking for the tree is only safe if nothing demotes it: the tree selects nothing by itself, but Library's effectiveSort runs Relevance for any search and Recent for any content filter, and since-fork counts as one (hasContentFilters), so with it on in an experiment row 0 replaced the fact. Since-fork comes back on the return to the chat: it is on the nav entry (kb/invariants/ui/navigation/nav-entry-captures-ways-of-looking/06e6b0af.md). Only while the experiment is still there: NAV_BACK keeps it only with an experiment, and a re-read that finds the branch gone (BRANCH_GONE) clears it with the filters.

KNOWN BROWSE BEHAVIOUR, NOT FIXED HERE: a tag or origin chip demotes Path to Recent, so row 0 replaces the fact when it is not on the list's first page. A tag click in the chat's panel asks for the same thing and so can land on a DIFFERENT fact, confirmed live; Browse's own tag click does the same. It does not mean a tag lands on the fact it was clicked on. It is on the list of Browse's own behaviours for a separate later PR.

A cmd-click on a chat's fact chip takes this path with the chip's branch, like every other landing. (2) The race. On the commit where a new repo's branch lands, the Library's read starts under the OLD sort before the landing renders. If the landing renders later, that read can answer first and its AMEND_NAV lands on top of the fact (same microtask in a test, a small real window in production). So the landing runs in a useLayoutEffect, whose update renders in the same task and marks that read stale before it can answer, and the branch-switch landing dispatches inside flushSync, for the same reason. Do NOT move either to a passive effect or an unflushed .then: both fail the App-level test with a list answering in the same microtask. Inside that flush the landing goes BEFORE the status: its entry has to catch the old branch with the old fact, or Back pairs the old fact with the new branch.

Also: a landing moves Browse to the branch the fact was read from. A commit-anchored read succeeds from any branch of the repo (the commit is the repo's), but the timeline then lists that other branch's history, without the commit, and the date comes out wrong (seen: Jul vs Nov).

Testing trap: the module-level resolve cache and the URL's list state survive between App tests in a file, and the URL beats localStorage, so a landing test must reset both; order-dependent passes hid this once. A row-0 read of a LIVE version on landing is not the trap: it was the back-crumb's title before fromChat stopped the trail there.

LIMITS: the ordering in part (2) is pinned by an App-level jsdom test whose list answers in the same microtask; the production window it closes is argued from React's scheduling, not measured. Which landings take this path, as merged: a fact chip's cmd-click and the navigating controls of a fact in the chat's panel. A commit chip is not one: it opens in the panel and never lands in Browse (kb/decisions/ui/chat/commit-link-target/2c5e5366.md).
