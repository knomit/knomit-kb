# Landing in Browse on a fact from outside it must take the reveal path in a render the Library's in-flight list read cannot beat: in Recent or search the list selects row 0 when the open fact is not on page 1 and keeps the anchor, silently showing another fact at that commit

Library's Recent and search reads AMEND_NAV to row 0 when the open fact is not on the page they got, and AMEND_NAV keeps asOf. So a landing at a commit that keeps Browse's sort, filters or free text shows ANOTHER fact at that commit under a band that looks right. A fact retracted at HEAD is on no list, so Recent always got this wrong.

Two parts, both needed. (1) The reveal path (useNavigationManager, reveal with optional asOf): path chip, sort 'path', empty free text and since-fork off, one APPLY_NAV. Asking for the tree is only safe if nothing demotes it: the tree selects nothing by itself, but Library's effectiveSort runs Relevance for any search and Recent for any content filter, and since-fork counts as one (hasContentFilters), so with it on in an experiment row 0 replaced the fact. Since-fork stays off when the reader comes back; it is not on the nav stack. A tag clicked in the chat's panel lands with its chip on purpose: that is the same demotion a tag click has in Browse, and row 0 can replace a fact not on page 1 there too.

A cmd-click on a chat's fact chip takes this path with the chip's branch, like every other landing. (2) The race. On the commit where a new repo's branch lands, the Library's read starts under the OLD sort before the landing renders. If the landing renders later, that read can answer first and its AMEND_NAV lands on top of the fact (same microtask in a test, a small real window in production). So the landing runs in a useLayoutEffect, whose update renders in the same task and marks that read stale before it can answer, and the branch-switch landing dispatches inside flushSync, for the same reason. Do NOT move either to a passive effect or an unflushed .then: both fail the App-level test with a list answering in the same microtask.

Also: a landing moves Browse to the branch the fact was read from. A commit-anchored read succeeds from any branch of the repo (the commit is the repo's), but the timeline then lists that other branch's history, without the commit, and the date comes out wrong (seen: Jul vs Nov).

Testing trap: the module-level resolve cache and the URL's list state survive between App tests in a file, and the URL beats localStorage, so a landing test must reset both; order-dependent passes hid this once. A row-0 read of a LIVE version on landing is not the trap: it was the back-crumb's title before fromChat stopped the trail there.
