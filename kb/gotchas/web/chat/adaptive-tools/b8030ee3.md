# The chat warms the embedding ranker's tool vectors in a goroutine at open, which takes the N embeddings off the first turn only if it finishes first: Rank embeds whatever is missing, the cache is process-wide per embedder id, and an embedder failure leaves the lexical ranking to guess alone

Without a warm-up the first turn of the first adaptive chat of a process embeds every tool (EmbedDocument per tool) before its first request. manager.warmRanker starts one goroutine at chat open, bound to the chat's context, that calls mcp.WarmToolVectors: it fills the process-wide tool-vector cache (keyed by embedder id, tool name and description) so the first Rank embeds only the message. It is a head start, not a guarantee: a turn sent before it finishes makes Rank embed the missing tools itself (concurrent embedding of the same tool is harmless, both write the same vector), and a warm-up error is logged and costs nothing else. Later chats of the same process find the cache full.

Ranker choice: chat.newRanker builds the blend of the embedding ranker and the lexical ranker (llm.NewBlendedRanker, reciprocal rank fusion; see kb/decisions/chat/adaptive-tools/blended-ranker) when the process has an embedder, and uses the lexical ranker alone when the embedder is nil. When the embedder fails at call time the blend skips it and the guess is the lexical ranking alone; the preload record then says lexical with embedding_error (a class). The embedding ranker applies no similarity cutoff. An Anthropic chat never touches the embedder (TestChat_StaticChatNeverEmbeds). The preload record names which ranking produced the guess.

The embedder must be safe for concurrent use: the warm-up goroutine and a turn's Rank can run together (the production embedder is shared by the whole server, so it already is). Measured latencies are not asserted anywhere; the live acceptance run records them.
