# markdown.css's `.k-prose :first-child { margin-top: 0 }` (specificity 0,2,0) silently zeroes a single-class margin-top on any element that opens its paragraph, list item or cell — e.g. a chat chip at the start of a line; restate such margins on the doubled .k-prose.k-chat-answer selector

markdown.css has `.k-prose :first-child { margin-top: 0 }`. Its specificity is (0,2,0) — the pseudo-class counts — so it beats any single-class rule such as `.k-chat-chip { margin-block: -2px }` on an element that is the FIRST ELEMENT CHILD of its parent. In a chat answer that is every chip opening a paragraph or a table cell (`| `3fc77970` | ...`): the chip lost its top margin only there, so the same chip aligned in one cell and not in the next. Found 2026-11-09 by measuring in Chromium: computed margin-top 0px on the chips while the rule read -2px.

Consequence: put any margin a chat element needs on `.k-prose.k-chat-answer <selector>` (0,3,0), the same doubled-class pattern App.css uses for chat code/tables. What this does NOT mean: jsdom tests cannot catch it — cascade.testutil's computed() reads App.css only and counts '.' for specificity, so it neither loads markdown.css nor weighs pseudo-classes; a browser measurement or a source-text assertion is the check.
