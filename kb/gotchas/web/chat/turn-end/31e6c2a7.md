# The chat snapshot (GET /chats/{id}) is authoritative: it carries every turn whole, the page replaces what it lists verbatim and re-reads on ready and on every turn end; the only client-held state beyond it is the turn just sent, confirmed by its POST

Every SSE connect starts with `ready`, and the page answers with an async GET /chats/{id}. That snapshot is the WHOLE truth about every turn: the server records, on each turn's user item, the turn's summed usage and cost_usd (absent without a price card), its price warning, and how it ended (error, plus cancelled for the person's own Stop), and returns usage_seq (the seq of the last usage event the items include). The page replaces every turn the snapshot lists, verbatim. There is NO carry-over of usage, errors or warnings from the previous state: the earlier index-plus-user-text matching and the empty-message rule were deleted because each patch of a snapshot that lacked those fields produced a new race (a ghost turn that kept the chat running forever; usage attached to the oldest turn of a second tab).

Rules: (1) turn_done and turn_error update the page at once AND start a fresh snapshot read; (2) reads are numbered and only the latest started is applied, so a stale read cannot undo a turn end; (3) Stop dispatches `stopped` locally whether or not the cancel succeeds; (4) a cancelled turn_error sets no error and keeps the partial text, and a snapshot turn flagged cancelled shows no error; (5) tool_call only moves a call forward and a usage event is ignored when its seq is at or below lastUsageSeq (counted once; a snapshot sets lastUsageSeq to its usage_seq); (6) `running` comes from the snapshot or from live events, never forced by the page.

The turn just sent is the one thing the page holds beyond a snapshot (`local`, with a sendId). The server appends the user item to its view BEFORE it answers 202, so a snapshot STARTED after the POST answered 2xx lists the turn. The page therefore: keeps a local turn after a snapshot's turns unless the read started after its POST was accepted (`confirmed`); removes it OUTRIGHT, whatever it holds, when the POST fails (409 while a stopped turn unwinds, any non-2xx, a network error), the error shown in the action-error line (404 means the chat is gone); and does not apply live events to an unconfirmed local turn (a late event from the turn before belongs to that turn; if there is no earlier turn the event is dropped, and the snapshot a turn end starts has it). A POST unanswered after SEND_TIMEOUT_MS (15 s: the 202 does not wait for the model, so a healthy answer takes a round trip; 15 s outlasts a slow link or the desktop proxy's first request and still bounds a hung connection) counts as failed; if it did reach the server the turn appears in the next snapshot.

Do not 'replay buffered events' instead: text_delta frames cannot be told from ones the snapshot already holds. Misreading to avoid: the snapshot is not re-read on every event, only on ready and on a turn's end; between them live events are the page's, and a read can lose events that arrive between the server cutting it and the page applying it until the turn-end read replaces it.
