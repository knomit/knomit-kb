# The chat snapshot (GET /chats/{id}) is authoritative and every live event names its turn: the page routes by that index, replaces what a snapshot lists verbatim, and re-reads on ready, turn end, an unknown turn and a send timeout

Every connect of the page's ONE events stream starts with a page-level `ready` (no chat id); chatEvents.ts delivers it to EVERY subscribed chat, and a chat that subscribes after the stream already said ready is told once on a microtask, so each ChatFacet answers with an async GET /chats/{id}. Events are first routed by their `chat` tag to that chat's subscribers (an event for a chat nobody shows is dropped), then by turn index as below. That snapshot is the WHOLE truth about every turn: the server records, on each turn's user item, the turn's summed usage and cost_usd (absent without a price card), its price warning, and how it ended (error, plus cancelled for the person's own Stop), and returns usage_seq (the seq of the last usage event the items include). The page replaces every turn the snapshot lists, verbatim (snapshotState); nothing is patched onto a listed turn from the previous state. The one thing kept beyond a snapshot is the turn just sent (see below).

ROUTING BY INDEX. The server puts `turn`, the view index of the turn's user item, on text_delta, tool_call, approval, usage, warning, turn_done and turn_error, and on the 202 that answers POST /turns. Each snapshot turn knows its own index (`at`, its position in `items`). The page applies an event to the turn with that `at`, so a late event from a stopped turn lands on that turn even after a new local turn exists, and a late turn end from an older turn does not end the newer turn's run (only the latest turn's end clears `running`). An event for an index the page has no turn for belongs to the local unconfirmed turn when there is one (it is the server's next turn: this is how the page learns the index when an early event beats the 202, and the turn is then confirmed); with no local turn it is a turn the page does not know (started in another tab) and the page reads a snapshot (`staleSeq`), applying nothing.

Other rules: (1) turn_done and turn_error update the page at once AND start a fresh snapshot read; (2) snapshot reads are COALESCED: one is in flight at a time; a trigger meanwhile (turn end, unknown turn, send with no answer) only marks that another is wanted, the in-flight answer is NOT applied (it was cut before the trigger and may miss a turn end) and exactly one more read follows however many triggers arrived; (3) Stop dispatches `stopped` locally whether or not the cancel succeeds; (4) a cancelled turn_error sets no error and keeps the partial text, and a snapshot turn flagged cancelled shows no error; (5) tool_call only moves a call forward and a usage event is ignored when its seq is at or below lastUsageSeq (a snapshot sets lastUsageSeq to its usage_seq); (6) `running` is the snapshot's own flag, a send sets it, and the latest turn's end or Stop clears it; the page never infers it from the shape of a snapshot. An approval event is routed by its turn too, so its card lands in its call's row.

The turn just sent (`local`, with a sendId) is the one thing the page holds beyond a snapshot. The server appends the user item to its view BEFORE it answers 202, so a snapshot STARTED after the POST answered 2xx lists it; the page keeps a local turn after a snapshot's turns unless the read started after its POST was accepted (`confirmed`); it removes it OUTRIGHT when the POST fails (409 while a stopped turn unwinds, any non-2xx, a network error, a timeout), showing the error in the action-error line (404 means the chat is gone). A POST unanswered after SEND_TIMEOUT_MS (15 s: the 202 does not wait for the model, so a healthy answer takes a round trip; 15 s outlasts a slow link or the desktop proxy's first request and still bounds a hung connection) counts as failed AND, like any failure without a status, makes the page read a snapshot, because the server may have appended the turn (and be waiting on its approval).

Do not 'replay buffered events': text_delta frames cannot be told from ones the snapshot already holds. Misreading to avoid: the snapshot is not re-read on every event, only on ready, on a turn's end, on an unknown turn and after a send with no answer.
