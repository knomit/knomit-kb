# Follow-to-bottom traps: our own scroll event can land after the page grew; a queued frame can outlive the reader's scroll up; StrictMode leaves a stale rAF handle; scroll anchoring lowers scrollTop during a reflow on a fresh page; a gentle scroll up inside the slack gets re-pinned

Five ways a follow-to-bottom transcript goes wrong. ChatPanel guards each one, and each guard has a test in ChatFollow.test.tsx that fails when the guard is removed. Every case in that file runs plain and under StrictMode.

1. OWN EVENT AFTER GROWTH. Scroll events are dispatched once per frame, after the write that caused them. While a fast answer streams, this order is normal: write to the bottom, a delta grows scrollHeight, then the scroll event fires. That event sees the bottom hundreds of px away, and so do the intermediate steps of a smooth scroll. Guard: the scroll rule stops following only when scrollTop DECREASED by more than 1px relative to the last value (`lastTop`, which is also set after each programmatic write). Our writes and content growth only ever move scrollTop down or leave it; a shrink clamp lands at the bottom.

2. QUEUED FRAME VS SCROLL UP. The pin is queued in requestAnimationFrame, and the reader can scroll up between the delta that queued it and the frame. Guard: the rAF callback re-reads the follow flag.

3. STRICTMODE STALE HANDLE (found in review of PR #812). The unmount cleanup cancelled the queued frame but left `frame.current` non-zero. StrictMode (main.tsx, dev only) mounts, cleans up and mounts again with the SAME refs. So pin() saw a handle, returned early forever, and the transcript never followed in dev. Guard: the cleanup sets `frame.current = 0`. Without the reset, 6 of the StrictMode test runs fail. General lesson: a cleanup that releases a resource held in a ref must also reset the ref, because StrictMode reuses refs across its remount.

4. ANCHORING DURING REFLOW (found in review). A resize that makes the window wider and shorter together (800x800 to 1300x600) makes Chrome's scroll anchoring lower scrollTop, and the scroll event arrives before the ResizeObserver re-pins. Rule 1 then reads it as the reader leaving. It shows up on a FRESH page: the reviewer reloaded before every run, and the build without the guard (1b66e6db) flipped 20 of 20 runs while the build with it (7cc85e0f) flipped 0 of 20. Repeating the resize in one page without a reload hides it (0 flips in 34 runs before the fix and 0 in 22 after, on my machine). So measure resize regressions with a reload per run. Guard: `overflow-anchor: none` while following, `auto` only while reading.

5. GENTLE SCROLL INSIDE THE SLACK. With only the scroll rule, a slow wheel or trackpad scroll up that moved less than 24px before the next frame stayed inside the slack and was re-pinned, so the reader could not escape. In Chrome, before the fix, 0 of 3 attempts stopped following. Guard: a wheel step up (deltaY < 0, with scrollTop > 0) stops following at once. Resuming by hand needs a move DOWN into the slack; otherwise the wheel step's own scroll event, which lands inside the slack, would re-arm following and undo the fix.

Consequence: if you change the follow logic, keep all five guards and run ChatFollow.test.tsx. LogsFacet solves rule 1 differently, with a selfScroll flag cleared on the next frame. That does not cover growth between the write and the event, which is why the chat uses direction.

Known and deliberately not handled (scope cut, 2026-11-09): a wheel step up over a box inside the transcript that scrolls by itself (the thinking summary) also stops following, although the transcript does not move. Keyboard and touch scrolls only leave through the scroll rule, so a keyboard or touch scroll up of less than 24px during a fast stream can be re-pinned.
