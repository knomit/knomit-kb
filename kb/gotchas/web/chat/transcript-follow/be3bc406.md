# A follow-scroll's own scroll event can arrive after the next delta grew the page, so 'not at the bottom' is not evidence the reader scrolled up; ChatPanel stops following only when scrollTop DECREASED, and the queued per-frame write re-checks the flag

Scroll events are dispatched asynchronously (once per frame), after the write that caused them. While a fast answer streams, the sequence write-to-bottom -> delta grows scrollHeight -> scroll event fires is normal, so that event sees the bottom hundreds of px away. A handler that stops following whenever the gap exceeds the slack would flip to 'not following' on its own write. The same holds for the intermediate steps of a smooth scroll (pill click / End), which move down but are not yet at the bottom.

What ChatPanel does: it remembers the last scrollTop (`lastTop`, also updated after each programmatic write) and stops following only when a scroll event shows scrollTop LOWER than that (minus 1px) with the bottom more than 24px away. Programmatic writes and content growth only ever move scrollTop down or leave it, so they can never trip it. Content shrinking can clamp scrollTop down, but a clamp lands at the bottom (gap 0), which reads as 'at the bottom', so it cannot trip it either.

Second half: the write is queued in requestAnimationFrame, and the reader may scroll up between the delta that queued it and the frame. The rAF callback re-reads the following flag and does nothing if it is off; without that check the queued write yanks the reader back. Test: ChatFollow.test.tsx 'a scroll up between a delta and its frame wins'.

Consequence: if you change the follow logic, keep both guards and their tests (the sabotage of each fails exactly one test). LogsFacet solves the same race differently (a selfScroll flag cleared on the next frame); that pattern does not cover growth between the write and the event, which is why the chat uses direction.
