# Follow-to-bottom traps: our own scroll event can land after the page grew; a queued frame can outlive the reader's scroll up; StrictMode leaves a stale rAF handle; scroll anchoring can lower scrollTop during a reflow; a gentle scroll up inside the slack gets re-pinned

Five ways a follow-to-bottom transcript goes wrong. ChatPanel guards each, and each guard has a test in ChatFollow.test.tsx that fails when the guard is removed.

1. OWN EVENT AFTER GROWTH. Scroll events are dispatched once per frame, after the write that caused them. While a fast answer streams, this order is normal: write to the bottom, a delta grows scrollHeight, then the scroll event fires. That event sees the bottom hundreds of px away, as do the intermediate steps of a smooth scroll. Guard: the scrollbar fallback stops following only when scrollTop DECREASED (by more than 1px) relative to the last value (`lastTop`, also set after each programmatic write). Our writes and content growth only ever move scrollTop down or leave it. A shrink clamp lands at the bottom.

2. QUEUED FRAME VS SCROLL UP. The pin is queued in requestAnimationFrame, and the reader can scroll up between the delta that queued it and the frame. Guard: the rAF callback re-reads the follow flag.

3. STRICTMODE STALE HANDLE (found in review of PR #812). The unmount cleanup cancelled the queued frame but left `frame.current` non-zero. StrictMode (main.tsx, dev only) mounts, cleans up and mounts again with the SAME refs. So after the first mount's frame was cancelled, pin() saw a handle, returned early forever, and the transcript never followed in dev. Guard: the cleanup sets `frame.current = 0`. Every ChatFollow test also runs under StrictMode; without the reset, 5 tests fail. General lesson: a cleanup that releases a resource held in a ref must also reset the ref, because StrictMode reuses refs across its remount.

4. ANCHORING DURING REFLOW (reported in review). A resize that makes the window wider and shorter together (800x800 to 1300x600) was seen by the reviewer to make Chrome's scroll anchoring lower scrollTop, with the scroll event arriving before the ResizeObserver re-pinned. Rule 1 then read it as the reader leaving (1 in 3 for the reviewer). I could not reproduce it before the fix: 34 of 34 resizes kept following, at rest and mid-stream. After the fix: 22 of 22. Guard regardless: `overflow-anchor: none` while following, `auto` only while reading.

5. GENTLE SCROLL INSIDE THE SLACK. With only the scrollbar fallback, a slow wheel, trackpad or key scroll up that moved less than 24px before the next frame stayed inside the slack and was re-pinned, so the reader could not escape. Measured in Chrome before the fix: 0 of 3 attempts stopped following. Guard: explicit upward input (wheel, touch, up keys) leaves at once via leave(). Re-arming by hand needs a move DOWN into the slack.

Consequence: if you change the follow logic, keep all five guards and run ChatFollow.test.tsx, which runs every case plain and under StrictMode. LogsFacet solves rule 1 differently, with a selfScroll flag cleared on the next frame. That does not cover growth between the write and the event, which is why the chat uses direction.
