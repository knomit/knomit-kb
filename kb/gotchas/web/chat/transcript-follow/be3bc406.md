# Follow-to-bottom traps: our own scroll event can land after the page grew; a queued frame can outlive the reader's scroll up; StrictMode leaves a stale rAF handle; scroll anchoring lowers scrollTop during a reflow on a fresh page; a gentle scroll up inside the slack gets re-pinned; an up key may scroll another box; trackpad wheel noise

Seven ways a follow-to-bottom transcript goes wrong. ChatPanel guards each, and each guard has a test in ChatFollow.test.tsx that fails when the guard is removed.

1. OWN EVENT AFTER GROWTH. Scroll events are dispatched once per frame, after the write that caused them. While a fast answer streams, this order is normal: write to the bottom, a delta grows scrollHeight, then the scroll event fires. That event sees the bottom hundreds of px away, as do the intermediate steps of a smooth scroll. Guard: the scrollbar fallback stops following only when scrollTop DECREASED (by more than 1px) relative to the last value (`lastTop`, also set after each programmatic write). Our writes and content growth only ever move scrollTop down or leave it. A shrink clamp lands at the bottom.

2. QUEUED FRAME VS SCROLL UP. The pin is queued in requestAnimationFrame, and the reader can scroll up between the delta that queued it and the frame. Guard: the rAF callback re-reads the follow flag.

3. STRICTMODE STALE HANDLE (found in review of PR #812). The unmount cleanup cancelled the queued frame but left `frame.current` non-zero. StrictMode (main.tsx, dev only) mounts, cleans up and mounts again with the SAME refs. So after the first mount's frame was cancelled, pin() saw a handle, returned early forever, and the transcript never followed in dev. Guard: the cleanup sets `frame.current = 0`. Every ChatFollow test also runs under StrictMode; without the reset, 5 tests fail. General lesson: a cleanup that releases a resource held in a ref must also reset the ref, because StrictMode reuses refs across its remount.

4. ANCHORING DURING REFLOW (reported in review). A resize that makes the window wider and shorter together (800x800 to 1300x600) was seen by the reviewer to make Chrome's scroll anchoring lower scrollTop, with the scroll event arriving before the ResizeObserver re-pinned. Rule 1 then read it as the reader leaving. It shows up only on a FRESH page. The reviewer reloaded the page before every run: the build without the guard (1b66e6db) flipped 20 of 20 runs, and the build with it (7cc85e0f) flipped 0 of 20. Repeating the resize in one page without a reload hides it: I saw 0 flips in 34 runs before the fix and 0 in 22 after. Measure resize regressions with a reload per run. Guard: `overflow-anchor: none` while following, `auto` only while reading.

5. GENTLE SCROLL INSIDE THE SLACK. With only the scrollbar fallback, a slow wheel, trackpad or key scroll up that moved less than 24px before the next frame stayed inside the slack and was re-pinned, so the reader could not escape. Measured in Chrome before the fix: 0 of 3 attempts stopped following. Guard: explicit upward pointer input (wheel, touch) leaves at once via leave(). Re-arming by hand needs a move DOWN into the slack.

6. A KEY THAT SCROLLS SOMETHING ELSE (found in the delta review). Clicking plain text in the side panel leaves focus on <body>, and PageUp/ArrowUp/Home then scroll the side panel or nothing. When the key alone called leave(), following stopped while the transcript stayed put (top 984, dist 0, pill shown), and new text streamed out of view under the pill. Guard: an up key only ARMS a leave (armUp). The transcript's next scroll event confirms it if scrollTop went down by any amount, even 1px inside the slack. A scroll that did not go up neither confirms nor consumes it. It lapses after 300ms. While armed, pins are held, because a programmatic scrollTop write cancels the browser's smooth keyboard scroll and the confirmation would never come. The lapse runs the held pin. Measured in Chrome after the fix, during a stream with the side panel open: after a click in the middle of chat-side-panel, PageUp, ArrowUp and Home each kept following (3/3, pill hidden, text still followed). After a click over the transcript, each left (3/3: PageUp 1827 -> 1237, ArrowUp -40px, Home -> 0), and the view held while 70-122px streamed in.

7. WHEEL NOISE. A trackpad sideways swipe over a wide table (.k-chat-table-scroll), or a ctrl+wheel pinch-zoom, can carry a small negative deltaY. Guard: the wheel handler ignores events with ctrlKey or |deltaX| > |deltaY|.

Consequence: if you change the follow logic, keep all seven guards and run ChatFollow.test.tsx, which runs every case plain and under StrictMode. LogsFacet solves rule 1 differently, with a selfScroll flag cleared on the next frame. That does not cover growth between the write and the event, which is why the chat uses direction.
