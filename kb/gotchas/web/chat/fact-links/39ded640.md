# The fact links' prefer list (turnPrefer) takes each call's repo from callTarget, which reads the server's in_base and target, not the call's arguments; a fixture or event that sends only `arguments` drops that call's repo, and a commit chip needs the list to hold exactly one repo

turnPrefer (chatFactLinks.ts) builds the prefer list sent to POST /facts/resolve: for each call of the turn, latest first, callTarget(call, binding in force), plus the store of a kb:// file or path argument; then the binding in force when the turn began; duplicates and blanks dropped. callTarget (chatState.ts) is the one function shared with the activity line: a bind's target is what it names; any other call's is the server's `target` (the repo or lens its arguments name, as a string) when the server's `in_base` is set, else the binding in force; a call without in_base (the loader, an unbound catalogue read, knomit_explain with only a file) contributes nothing. Consequence: a test fixture, snapshot item or event for a call that names a repo must carry in_base: true and target, exactly as the server sends them; arguments alone no longer put the repo in the list.

Checked against a real server (lfm3, own home): a bind sends in_base and target; a knomit_query with repo "demo-d" as a string under a binding on demo-c sent in_base: true, target "demo-d", and the page POSTed prefer ["demo-c","demo-d"]; a query that carried only the opaque binding handle sent in_base: true and no target (it falls back to the binding in force). A model that sends repo as a LIST gets in_base but no target, so that repo is not in the list.

The server answers a commit hash only when the list holds exactly ONE repo (handlers_facts_resolve.go): bound to one repo and citing its hash, the page shows the commit chip; with two repos in the list, a hash that names no fact stays inline code. A bind that failed still counts for the list (callTarget does not look at is_error; boundAfter does), so a failed bind to a second repo can keep a commit from being linked.

Does NOT mean: the page may read the repo from arguments to compensate. The running event drops arguments over 16 KiB, so an argument-based rule words the same call differently live and after a reload (see kb/conventions/web/chat/activity-line/dee02e91.md).
