# The fact links' prefer list (turnPrefer) takes each call's repo from callTarget, which reads the server's in_base and target, not the call's arguments; a fixture or event that sends only `arguments` drops that call's repo, and a commit chip needs the list to resolve to exactly one reachable repo

turnPrefer (chatFactLinks.ts) builds the prefer list sent to POST /facts/resolve: for each call of the turn, latest call first, callTarget(call, binding in force), plus the store of a kb:// file or path argument; then the binding in force when the turn began; duplicates and blanks dropped. callTarget (chatState.ts) is the one function shared with the activity line: a bind's target is what it names; any other call's is the server's `target` (the repo or lens its arguments name, as a string) when the server's `in_base` is set, else the binding in force; a call without in_base (the loader, an unbound catalogue read, knomit_explain with only a file) contributes no repo of its own. Consequence: a test fixture, snapshot item or event for a call that names a repo must carry in_base: true and target, exactly as the server sends them; arguments alone no longer put the repo in the list. Order: a bind to demo-c followed by one query naming repo demo-d gives ["demo-d","demo-c"] (latest call first); a later call that only carries the binding handle adds the binding in force (demo-c) at its own, later position, so it moves demo-c to the front.

Checked against a real server (lfm3, own home). A bind sends in_base and target. A knomit_query that carried only the opaque binding handle sent in_base: true and no target (it falls back to the binding in force). knomit_query declares `repo` as an ARRAY of names (query.go, WithArray); a plain string is only tolerated, and the array form is the schema's own shape, not an oddity. The server's `target` is set only from a string `repo` or `lens`, so a call that sent the array form gets in_base but no target, and its repo is not in the list. The query with repo "demo-d" in my run came back as an error: a `repo` filter on a query needs a binding that came from a lens, and that run's binding was a repo (demo-c), so the server refused it (errRepoNotLens, query.go). The call still sent in_base: true and target "demo-d", and the page still put demo-d in the list: the list is built from what a call NAMED, whether or not it succeeded. knomit_explain with only a file fails on the chat endpoint with errMissingHandle (binding_gate.go, gateBinding); its kb:// store still enters the list.

The server answers a commit hash only when the list RESOLVES to exactly one reachable repo (handlers_facts_resolve.go, len(preferred) == 1 after preferredRepos). Entries are names, repo ids (as kb:// carries them) or lens names; a lens stands for its write repo then its reads, so a single lens entry with two members gets no chip, and a repo name plus its id are the same repo and still get one. Names that do not resolve to a repo the caller can reach are dropped before the count. Bound to one repo and citing its hash, the page shows the commit chip; with two reachable repos, a hash that names no fact stays inline code.

Any call that names a repo counts toward the list whether it failed or not, not only a bind: callTarget does not look at is_error (boundAfter, which tracks the binding in force, does). So a failed bind or a refused query naming a second reachable repo can keep a commit from being linked; a failed call naming a repo the caller cannot reach is dropped by preferredRepos.

Does NOT mean: the page may read the repo from arguments to compensate. The running event drops arguments over 16 KiB, so an argument-based rule words the same call differently live and after a reload (see kb/conventions/web/chat/activity-line/dee02e91.md).
