# UI must default to server-authoritative agent_branch, not the first agent/* branch

Symptom: after connecting repo 'core' to a shared remote, the Library showed ZERO facts even though 836 were correctly indexed. Cause chain: the remote's HEAD pointed at a FOREIGN agent branch (agent/Alexs-MacBook-Air...), so CloneFrom adopted it as a local head and DefaultBranch() returned it (stored as the consensus -> push-only warning). The repo then had two agent/* git heads; only THIS machine's branch (agent/mindev.local-..., via MatchedAgent/agentBranch) was rebuilt/indexed at commit. The frontend getAgentBranch picked branches.find(b => b.name.startsWith('agent/')) — the first alphabetically — landing on the foreign branch with 0 indexed facts.

Key facts: (1) ListBranches/the /branches endpoint lists git heads, including foreign + unindexed branches. (2) branch names are colon-encoded in HAL URLs (agent:mindev... not agent/mindev...). (3) GET /api/v1/repos/{repo} returns the authoritative agent_branch (ri.AgentBranch()). Fix: getAgentBranch now uses RepoDetails.agent_branch. PR #513 (D18) removed the agent/* heuristic fallback altogether: when the server gives no agent_branch it returns the subscription's read_branch, else the only branch if the branch list has exactly one, else it THROWS (cannot tell which branch). No branch is ever picked by its name or prefix. Follow-up, not in #513: drop the single-branch fallback and show the error instead. No data loss — purely UI branch selection. Deeper trigger left unaddressed (user accepted the push-only consensus): a remote whose HEAD is an agent branch rather than main.
