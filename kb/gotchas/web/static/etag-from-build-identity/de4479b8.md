# A build-identity ETag (version.String()) on index.html collapses to a constant for bare builds ("dev") and dirty-tree rebuilds (same SHA), so no-cache+304 serves a STALE index pointing at hashed bundles that no longer exist — a blank app; knomit's static ETag is therefore the sha256 of each file's own bytes (etagger), never the version

The first cut of PR #223 used the build identity that `/api/v1/version` reports as the strong ETag for every non-content-hashed file (index.html, config.js, favicon.svg, the SPA fallback). The reviewer showed it collapses: `version.String()` returns "dev" whenever `Commit` is empty (plain `go build`, `go run`, tests), and the Makefile's GIT_COMMIT is the HEAD SHA, which does not move for a dirty-tree rebuild. With `Cache-Control: no-cache` the browser revalidates on every load, receives 304 because the tag matches, and keeps its cached index.html — whose `<script src="assets/index-<hash>.js">` now points at a bundle the new binary does not embed. Blank app, no console clue beyond a 404 on the asset, until a manual cache clear. Simulated end to end, not reasoned: build A → ETag "dev"; build B with different assets plus the old ETag → 304 empty; the referenced asset → 404.

**As built.** `etagger` (internal/web/static.go) memoizes, per served path, the quoted sha256 of the file's own bytes, computed on first serve under an RWMutex; the map is bounded by real files because `tag()` runs only after `fs.Stat` succeeds. The ETag is set before delegating to `http.ServeContent`, which answers `If-None-Match` with 304 itself (a hand-rolled 304 that leaves Content-Type set can pick up `Content-Encoding: gzip` on an empty body — let ServeContent do it). Reviewer verified under race detector with 300 concurrent first-serve requests, and that each tag equals the sha256 of the body actually served. Tests assert the tag is quoted, stable across requests, DIFFERS when content differs (two MapFS fixtures), and differs between config.js and favicon.svg — that last assertion is the one that would have caught the shared-build-string design.

**Consequences.** Any validator for a revalidate-every-time resource must change with the CONTENT, not with a proxy for it. Released `make` builds at a new commit were never affected, which is why an acceptance run against a release would have passed and hidden this. Misreading to avoid: this does not argue against `no-cache` on index.html — that policy is correct; the trap was the validator.
