# KNOWN DEFECT (unreproduced, reasoned from code; issue #629): re-testing an origin session in stateError after a failed /test that had already opened clone.db fails with "repository already exists", because clone.db stays in the session folder and the 409 check does not cover stateError

TRACKED as GitHub issue #629 (https://github.com/knomit/knomit/issues/629). FOUND in review of PR #626 and NOT FIXED. UNREPRODUCED: this is reasoned from reading handlers.go at c3c293b0, no test or run exercised it. Chain: /test opens store.Open(<session folder>/clone.db) and then, if CloneFrom fails (or the same-knowledge-base check refuses), closes the store, sets stateError and returns; RemoteStore stays nil and clone.db stays on disk. The /test re-run guard refuses (409) only sessions with a RemoteStore or in tested/previewed/applied/committed, so a stateError session passes it; a second /test then opens the leftover clone.db and its CloneFrom is expected to fail with "repository already exists", leaving the session in stateError again. Consequence: after a failed first /test the user cannot retry on the same session; the way out is a new session (POST replaces the old one). Not a data-loss path. DOES NOT MEAN: that the 409 guard is wrong; it protects good sessions. A fix would remove or reuse clone.db on a stateError retry, or refuse stateError too with the same 'create a new session' message; verify by a test that fails a first clone and re-runs /test before recording either as the behaviour.
