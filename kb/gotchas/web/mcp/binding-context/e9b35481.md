# The repo-scoped MCP route puts NO Binding in the context — only a RepoInstance — so anything reading a PinID there must go through BindingFromContext, which panics when the context has neither

Only the LENS mount calls `repos.WithBinding` (LensMiddleware). On the repo-scoped mount — `/repos/{repo}/branches/{branch}/mcp` — RepoMiddleware puts a `*RepoInstance` in the context and BranchMiddleware puts the branch name, and NOTHING puts a `*Binding` there.

So `repos.BindingFromContextOpt(ctx)` returns `(nil, false)` on every repo-scoped MCP request. Code that reads a binding only through the Opt form silently records an empty PinID for the single-repo path — the common case — while working perfectly on the lens path, which is the rarer one. That is what makes the bug easy to ship: the test that exercises a lens passes.

`repos.BindingFromContext(ctx)` is the one that answers correctly for both: with no explicit binding it synthesizes the lens-of-one from the context RepoInstance plus bound branch. But it PANICS when the context holds neither a Binding nor a RepoInstance, so it is unsafe to call from anything that runs on unscoped routes.

**What to do:** try `BindingFromContextOpt` first, then guard `BindingFromContext` behind a `RepoFromContextOpt` check, and return "" when neither is present. `bindingPin` in `internal/edge/web/client_sessions.go` is the worked example.

**Not what this means:** the repo route is not missing a middleware. Synthesizing the binding from the RepoInstance is deliberate — it is what lets the single-repo path stay behaviour-identical without a middleware change.
