# The kind exclusion is enforced by DIFFERENT code on the two seed-scan paths — SQL on the full scan, AcceptSeed only on the incremental one; a test that exercises just one proves less than it looks

reviewStrategy states the epistemic-only seeding rule twice, and its own comment calls the SQL half "purely an efficiency measure" with AcceptSeed as "the authoritative statement of the rule". That is true of what the SQL clause is FOR and false of what it DOES on the full-scan path.

SeedQuery() returns SearchOptions{IncludeKinds: [epistemic]}. On the first run (no watermark) dirtyFacts goes through the index Search, so a pragmatic fact never comes back at all and AcceptSeed is never asked about it. Only the incremental path — DiffFiles, then fact.ParseFact per changed file — actually puts each fact to AcceptSeed.

Verified by mutation on branch feat/signal-type: forcing `AcceptSeed` to `return true` fails the incremental subtest of the seed-filter tests and leaves the full-scan subtest PASSING.

The consequence for anyone writing or reading these tests: a full-scan-path assertion that a pragmatic fact is not a seed pins the SQL clause, not AcceptSeed. If you change AcceptSeed and only the full-scan case is green, you have tested nothing about your change. Cover both paths, and know which one each is holding.

What this does NOT mean: it does not mean the SQL clause is the authoritative rule and AcceptSeed is dead code. AcceptSeed is the only guard on the incremental path, which is the path that runs on every subsequent session, and it is the one place the rule is stated in Go where a reader will find it. Two enforcement points are the right design here; the trap is only that they are not equally reachable, so they are not interchangeable as test targets.
