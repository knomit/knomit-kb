# In the synthesize test store ScopedCluster yields ZERO clusters at the default resolution/min size — no SIMILAR_TO edges means Louvain singletons that filterSmallClusters drops — so any 'X is in no cluster' assertion passes vacuously; wrap SubgraphEdges AND pass explicit (1.0, 2)

Test environments built with newRestatementEnvWith / store.Open write facts and vectors but no SIMILAR_TO edges, so store.SubgraphEdges returns nothing. Two separate things then empty the result, and each needs its own remedy:

1. NO EDGES. louvainCommunities over an edgeless graph returns one SINGLETON community per node. That result is non-empty, so ScopedCluster's category-grouping fallback (which fires only when the edge read errors or no community maps back to a fact) NEVER fires; filterSmallClusters then drops every singleton at min size 2. Remedy: wrap the index with a SearchQuery whose SubgraphEdges returns every pair of the collected paths (completeEdges in neighbor_kind_filter_test.go), so membership is decided only by which paths the neighbour search admitted.

2. RESOLUTION. The production resolution 4.0 splits even a connected 2-node, 1-edge graph into singletons, so the edge wrapper alone is not enough for small fixtures. Remedy: pass explicit resolution 1.0 with min size 2.

Without both, a 3-fact fixture gave ZERO clusters, and any negative membership assertion ("the policy is in no cluster", "the cousin never co-clusters") is true of an empty result and measures nothing. TestCousins_FenceKeepsANonSeedCousinOutOfTheSubgraph hit the same trap first and was rewritten for it. Also assert the POSITIVE half (the two observations DO cluster) before the negative one, and a PREMISE that the unfiltered QueryByPath search returns the fact being excluded (requireUnfilteredSearchFinds), or a fact that was never similar enough passes for the wrong reason.

A second, subtler vacuity from the same work: "the policy is still live and still kind=pragmatic" does NOT prove no cross-kind merge happened. When the POLICY wins a dedup pair it stays pragmatic (dedupCluster writes the winner back from its own parsed file) and the observation is deleted into it. Assert that the policy's refs name neither observation (a merge appends the loser's path to the winner's refs). Mutation-checked: without that ref assertion, removing dedupCluster's kind-equality check left the real-path subtest green.

END TO END, where neither remedy can be injected (#349, internal/web/agent_trace_review_e2e_test.go drives knomit_review over the real router, so ScopedCluster gets the instance's resolution 4.0 and the real SubgraphEdges): edges DO exist when the store has an embedder before the facts are written — store.Service.SetEmbedder plus TestInstanceConfig.Embedder with a deterministic hash embedder (identical title+body -> cosine 1) — because the search index builds SIMILAR_TO edges on upsert (graphBuildSimilarityEdges) whenever an embedder is set. Point 1 above is therefore about stores WITHOUT an embedder. Point 2 still bites: ONE identical pair gave 'clusters: 0'. What works without touching the resolution is THREE disjoint identical pairs (m=3 edges, so each pair's modularity gain 1 - 4*1*1/(2*3) is positive): the start then writes six dedup commits, a merge and a removal per pair. Require those commits to exist before asserting anything about them.
