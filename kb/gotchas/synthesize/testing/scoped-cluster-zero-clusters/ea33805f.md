# In the synthesize test store ScopedCluster yields ZERO clusters at the default resolution/min size — the store builds no SIMILAR_TO edges — so any 'X is in no cluster' assertion passes vacuously; wrap SubgraphEdges and pass explicit (1.0, 2)

Test environments built with newRestatementEnvWith / store.Open write facts and vectors but no SIMILAR_TO edges, so store.SubgraphEdges returns nothing and ScopedCluster falls back to category grouping. At the production defaults (resolution 4.0, min community size 2) that gave ZERO clusters for a 3-fact fixture. Any negative membership assertion ("the policy is in no cluster", "the cousin never co-clusters") is then true of an empty result and measures nothing. TestCousins_FenceKeepsANonSeedCousinOutOfTheSubgraph hit the same trap first and was rewritten for it.

WHAT TO DO. Wrap the index with a SearchQuery whose SubgraphEdges returns every pair of the collected paths (completeEdges in neighbor_kind_filter_test.go) and pass explicit resolution 1.0 / min size 2, so membership is decided only by which paths the neighbour search admitted. Then assert the POSITIVE half too (the two observations DO cluster) before the negative one. Pair it with a PREMISE that the unfiltered QueryByPath search returns the fact being excluded (requireUnfilteredSearchFinds), or a fact that was never similar enough passes for the wrong reason.

A second, subtler vacuity from the same work: "the policy is still live and still kind=pragmatic" does NOT prove no cross-kind merge happened. When the POLICY wins a dedup pair it stays pragmatic and the observation is deleted into it. Assert that the policy's refs name neither observation (a merge appends the loser's path to the winner's refs). Mutation-checked: without that ref assertion, removing dedupCluster's kind-equality check left the real-path subtest green.
