# KNN neighbourhood is ASYMMETRIC, so a cached pair may exist only because B's top-K included A — delta maintenance that rescans only the changed fact destroys discoveries nothing will rediscover

Top-K nearest-neighbour is not a symmetric relation. A may be in B's top-K while B is nowhere in A's. The standing pair cache is the union over every fact's top-K, so a given pair can owe its existence entirely to ONE side's neighbourhood.

**The trap.** The obvious delta maintenance — "a fact changed, so drop every pair touching it and rescan that fact" — deletes pairs that only the OTHER side's scan could have produced. Rescanning the changed fact cannot re-mint them, because they were never in its top-K to begin with. The discovery is gone and nothing will find it again; the cache looks healthy and simply holds fewer pairs each time a fact is edited.

**The repair, and why it recurses.** The fix is to requeue the PARTNERS of the dropped pairs (`PartnersOfFacts`) so their neighbourhoods are recomputed too. Done naively, that reproduces the identical bug one level out: if requeuing a partner also deletes the partner's existing pairs, the partner's own asymmetric discoveries are destroyed in exactly the same way.

**The named misreading.** "The pair cache is derived, so losing entries is safe" is FALSE here. Derived state is safe to lose when it can be regenerated from its source; these entries cannot, because the scan that produced them is not the scan that will be re-run.
