# go-git v5.19.2: concurrent clones/fetches/pushes in ONE process corrupt packs under -race (~1 clone in 80: 'object not found', 'malformed PACK file: checksum mismatch', receiver 'final sha1 did not match' / 'missing blob'), reproduced with go-git's own memory storage and no knomit code; 0 in 1,200 without -race; so internal/repos tests that use a git transport stay sequential (#446)

Found when #445 made the internal/repos clone, subscribe, fetch, push and probe tests t.Parallel. `go test -race` then failed intermittently: for example 4 failures in 37 s with `-race -count=6 -run 'TestCreateFromTemplate|TestMount_Subscription|TestCreate_|TestProbeInitialized'`, and 1 of 2 full-package runs. The errors were 'clone: InitFromRemote: fetch: object not found', a push's 'unpack-objects abnormal exit / fatal: final sha1 did not match', and 'missing blob object'.

It is NOT shared test state:
(1) The same set with -parallel 1 under 10 CPU burners is green, so load alone does not trigger it.
(2) A standalone test reproduces it with go-git only. 8 goroutines, each with its own bare repo made by the git CLI, each run gogit.Clone over file:// into memory.NewStorage() 10 times. Under -race about 1 clone in 80 fails in every run; without -race, 0 in 1,200.
(3) Every fixture (home, bare repo, playbooks copy) is per-test.
The repro is in issue #446.

The race detector prints NO 'DATA RACE'. A hypothesis, NOT verified: the culprit is state shared through sync.Pool (buffer or zlib pools); race mode treats the pool as a happens-before edge, so the detector cannot see its misuse.

Consequence in this repo: since #445, internal/repos tests that move objects over a git transport (file://, smart HTTP, probe) do not call t.Parallel. The rule is written above TestMain in main_signer_test.go. #446 lists 6 tests that are still parallel and still use a transport, as a follow-up to make sequential: 3 consensus/conflict smart-HTTP tests, 2 ProbeInitialized HTTP tests and Walkthrough_AttachOK.

NOT MEANT:
- Release builds are not shown to be affected. No failure outside -race has been seen. But a server syncing many repos at once is the same pattern, so treat it as open (#446 tracks the upstream report and the HTTP/SSH check).
- It is not a reason to serialize production sync.
- It is not evidence against parallel tests in general: the 137 self-contained repos tests stay parallel and are green under -race.
