# sha1cd v0.6.0 (pulled in by go-git v5.19.2) returns WRONG SHA-1 digests on arm64. Its blockARM64 assembly takes its loop bound from register R16, which it never sets. This was the real cause of the #446 'concurrent go-git clones corrupt packs under -race' failures. It is fixed in sha1cd v0.7.0 / go-git v5.19.3. amd64 was never affected.

Supersedes the go-git 'concurrent clones corrupt packs under -race' gotcha written for #445/#446. That symptom was real, but the cause was not go-git, not sync.Pool and not shared test state.

MECHANISM. go-git hashes objects and pack trailers with github.com/pjbgf/sha1cd. In sha1cd v0.6.0, the arm64 assembly `blockARM64` (sha1cdblock_arm64.s) starts with `ADD R16, R2, R21` and loops on `CMP R16, R21 / BLS end`. R16 is a scratch register that the function never loads. It holds whatever the caller left there. If that value is within 64 of 2^64, the addition wraps and the block is skipped. The hash state then comes back unchanged and the digest is wrong. The amd64 assembly takes its bound from SI, which is loaded from p_base, so amd64 does not have this bug. Upstream: pjbgf/sha1cd#214, fixed by pjbgf/sha1cd#215 (it replaces the check with `CBZ R2, end`) and released in sha1cd v0.7.0. go-git v5.19.3 requires sha1cd v0.7.0 (and go-billy v5.9.2). knomit moved to both in PR #759 (the #446 fix).

WHAT IT LOOKS LIKE. A wrong object id or pack checksum. go-git reports 'object not found' or 'malformed PACK file: checksum mismatch'. A git CLI receiver reports 'final sha1 did not match' or 'missing blob object'. The race detector prints no DATA RACE, because there is no data race. Concurrency matters only because it changes what is left in R16.

MEASURED (issue #446 standalone repro, darwin/arm64, Go 1.27.1, -race, 8 goroutines x 10 file:// clones into memory storage = 80 clones per run, 30 runs each):
- go-git v5.19.2 + sha1cd v0.6.0: 71 of 2400 clones failed (27 of 30 runs red);
- go-git v5.19.3 + sha1cd v0.7.0: 0 of 2400;
- go-git v5.19.2 + sha1cd v0.7.0 only: 0 of 2400. Only sha1cd changed in this control, so sha1cd is the cause.

CONSEQUENCES.
- RELEASE builds on arm64 were exposed too (darwin/arm64 and linux/arm64, any go-git user before v5.19.3). The faulty code is the same with or without -race. -race only makes the bad register value much more common. 0 failures in 1,200 clones without -race shows the bug is rarer there, not that it cannot happen. A wrong digest in production can show up as a failed clone, fetch or push, or as an object id that does not match its content.
- amd64 builds (CI's ubuntu and windows legs, amd64 servers) were NOT affected by THIS bug. A corrupt-pack failure on amd64 has some other cause. Do not explain it with this fact.
- v0.7.0 is not an arm64-only change. It also changes the amd64 hashing paths: pjbgf/sha1cd#216 compresses a single chunk per blockAMD64 call; #218 cuts per-block collision-detection work and cgo allocations; #221 adds a new AVX2/BMI2 fallback for amd64 CPUs without SHA-NI. So 'amd64 was not affected' covers v0.6.0's R16 bug only. It does not rule out a future amd64 digest problem coming from the new v0.7.0 code. If wrong digests ever show up on amd64 after this bump, the new code is a suspect, the AVX2 path in particular on CPUs without SHA-NI.
- If 'object not found' / 'checksum mismatch' comes back from concurrent go-git use, check `go list -m github.com/pjbgf/sha1cd` FIRST. Anything below v0.7.0 on arm64 is this bug. Then look elsewhere.
- internal/corpus/repos tests that move objects over a git transport may again call t.Parallel (the convention fact kb/conventions/testing/repos/t-parallel/5f6e05c8.md was updated for this).

NOT MEANT:
- It does not mean concurrent go-git transfers are proven safe in every way. It means the one corruption seen in #446 is explained and fixed.
- It does not mean -race causes it. -race only makes it more frequent.
- Production sync was never serialised because of this, and it should not be.
