# Under Machine.Options.Synchronous (the test harness), a Mount reply from mountExisting or Create can arrive while IndexRunning is still true: the reply means the walk reached Ready, not that indexing finished, so a test must waitIndexSettled before sending Attach, Detach or Swap

Even with Machine.Options.Synchronous (the test harness mode, which only skips the experiment sweep and runs one inline sync round; the index job STILL runs in the background), the reply to an external Mount event can reach the caller while Status.IndexRunning is still true. The Mount is sent by mountExisting (manager.go) and by the create path (lifecycle.go, MountCreate).

Why, all in internal/corpus/repos/machine.go:
- The driver goroutine answers the external Mount inside handleExternal (the answer(rep, applyErr) call, ~:417), after the walk reached Ready.
- The index job's completion arrives as an internal indexDone event; drive (~:327-337) processes internal events only AFTER handleExternal returns, and handleInternal sets m.r.indexVerdict (~:429) only then.
- indexRunning() is `lives[StageIndex] != nil && indexVerdict == nil` (~:477), so between the Mount reply and that handleInternal call it is true even if the job has already finished.
- Send's fast path (~:253-272, the `e.exclusiveWithIndex() && st.IndexRunning` case) and the recheck in handleExternal (~:367) both answer ErrIndexing in that window, for Attach, Detach and Swap.

CONSEQUENCE: a test that mounts a repo and then sends AttachOrigin, DetachOrigin or SwapStore must first call waitIndexSettled(t, ri) (machine_helpers_test.go) on that instance. ONE EXCEPTION since 2026-10-28: a DetachOrigin on a SUBSCRIPTION is answered ErrSubscriptionOrigin by MachineEvent.standingRefusal ahead of the index gate, so it needs no wait (TestWalkthrough_Detach dropped its wait; TestWalkthrough_SubscriptionDetachDuringIndexing asserts it with the index held). Without it, under -race and parallel load the send gets ErrIndexing instead of the error or success being asserted (7/1008 in the reviewer's measurement; see the walkthrough-flakes gotcha).

WHAT THIS DOES NOT MEAN: 'the mount reply means the repo is idle'. It means the walk reached Ready, not that indexing finished. Nor does the window mean the machine is wrong or that ErrIndexing should be relaxed: ErrIndexing before any guard is the decided behaviour (decision cc2212e3), and the test must wait rather than the check change. The only refusals ahead of ErrIndexing are standingRefusal's (today: subscription Detach); a guard's own verdict (probe failure, swap identity checks) still comes after it.
