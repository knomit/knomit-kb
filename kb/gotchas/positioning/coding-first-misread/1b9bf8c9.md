# knomit is DOMAIN-AGNOSTIC — the fact model stores any knowledge — but every public proof point is coding-shaped, so outsiders (and analysts) misread it as a coding-agent tool; the maintainer has corrected this explicitly

On 2026-09-13 the maintainer corrected a product assessment that called knomit's depth 'coding facts with source refs' and framed non-coding use as unproven: 'knomit can store any facts about anything ... far from it'.

What the evidence actually shows. The fact model is domain-agnostic: typed facts with confidence, domains, entities and refs of ANY scheme (https://, kb://, src://). The non-code corpora exist and are large — the agentic-engineering KB (repo bc6eac5f37df) holds hundreds of web-sourced facts on security, evaluation, reliability and MCP with no source refs at all; cyberai-kb likewise. The use-cases page lists researchers/analysts, teams, and decentralized deployments alongside developers. The MCP server ships chat and generic profiles next to code.

Why the misread happens (this is a MESSAGING gap, not a capability gap): the only deep host adapter is Claude Code with post-edit/source-ref hooks; the published A/B experiment is a coding task; the README quick-start and the docs 'Publish & Integrate' pages address coding agents; the dogfood KB is about the knomit codebase. An outside reader — and a research agent summarising the public surface — infers 'coding agents are the primary segment'.

CONSEQUENCES: (1) never describe knomit as coding-first in comparisons, positioning or risk analyses; say 'proof and tooling depth are concentrated in one coding host today'. (2) A general-purpose host adapter (Hermes, OpenClaw) is the vehicle for the first PUBLISHED non-coding proof, and should be planned as such. (3) Website/README work should surface the non-code corpora and personas.

WHAT THIS DOES NOT MEAN: it does not mean the code profile's source-ref features are unimportant — they are the deepest tooling knomit has; it means they are one profile, not the product's scope.
