# A timeout of 0 means NO LIMIT, and context.WithTimeout(ctx, 0) means ALREADY EXPIRED — the real kb bridge builds its client with Timeout 0, so a per-dial helper that converted it straight to a deadline failed every pipe dial instantly

tools/bridge/main.go builds its HTTP client with Timeout 0 ON PURPOSE: it holds SSE long-polls open and a deadline would cut them. A per-dial helper that does context.WithTimeout(ctx, timeout) with that value sets a deadline of NOW, so every local dial fails instantly.

The consequence is invisible in the worst way: the real kb.exe would never once have used the named pipe, would have fallen back to TCP on every request, and would have looked perfectly healthy while running as the anonymous principal — the exact failure knomit#245 exists to remove.

NOTHING IN THE TEST SUITE CAUGHT IT, because every test passed a real timeout. It was found by a reviewer asking a question about ERROR_PIPE_BUSY budgets, not by a test.

localDialBudget now gives the local dial a QUARTER of the request's budget capped at 2s (localDialCap), and a flat 2s when there is no limit. That also stops a BUSY pipe — winio retries those every 10ms until the context expires rather than failing fast — from consuming the whole request and leaving the TCP fallback nothing. TestNewHTTPClient_UnlimitedTimeoutStillPrefersTheLocalListener is the regression.

NOTE: this caps the UNIX dial too, where it was previously bounded only by the caller's timeout. A connect() to a live unix listener returns immediately or with ECONNREFUSED, so the cap is not reachable in practice there.

GENERALISATION WORTH KEEPING: whenever a package converts a "0 means no limit" duration into a deadline, 0 has to be special-cased BEFORE the conversion, not after.
