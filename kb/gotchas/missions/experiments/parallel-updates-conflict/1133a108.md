# Parallel mission tasks that knomit_update the SAME facts in per-task experiments cannot all land AS WRITTEN: before #412 every later experiment commit was refused for conflicts; since #412 the commit follows the repo's `conflicts` setting (refused only where it resolves to refuse, field-merged under merge, where one side's edit to a field both changed is still dropped)

Observed in the first IPO mission real run (2026-10-02, f05522da, three agents on two machines). Three cross-check tasks, one per agent, each opened an experiment on the knowledge base and ran knomit_update on the same 9 hypothesis files. The first agent's experiment was fast-forwarded into its agent branch; with realtime push/pull the consensus merge carried those edits into the other two agent branches within seconds. When the other two committed, `knomit_experiment commit` found the parent branch had changed the same paths after the fork and refused for conflicts: at f05522da every experiment commit ran StrategyRefuse, even in a repo set to `conflicts: merge`. The work-task skill forbids picking sides, so both rolled back and acked "Failed:", which tripped the mission's stop condition.

SINCE #412 (merge 55a47911): experiment commit honours the repo's `conflicts` setting, read at the tip of the consensus branch (kb/decisions/fleet/first-mission/experiment-commit-honors-conflicts/211e894d.md). So the refusal now happens only where the setting resolves to refuse: a repo with no `conflicts` key and no `consensus: auto` (TestCommitExperiment_NoConflictsSetting_StillRefuses), or a key set to off. Under `conflicts: {facts: merge}`, or `consensus: auto` with `conflicts` absent (which reads facts: merge / state: consensus, TestCommitExperiment_ConsensusAutoDefault), the later commits LAND: the conflicting facts are field-merged with the parent as the consensus side (TestCommitExperiment_ConflictsMerge_FieldMerges), and every dropped side is reported.

Consequence, still: parallel updates of ONE shared fact are a design smell even when they land. Under merge, a field both sides changed (confidence, typically) keeps one side's value, so one agent's corroboration or contradiction is silently superseded (reported in the merge, not in the fact); under refuse, the task fails. Serialise such passes, or have each agent write NEW facts and fold them with one writer, which is what the mission template does since #410, in the shape F26 settled (kb/architecture/examples/mission/cross-check/d70b0d8c.md): cross-checks write annotations in the MISSION repo under annotations/<task id>/ (learn_dedup: off, context.kind: verdict) and make no commit on the target KB, and ONE fold task, posted after the round's acks, is the only writer of the hypotheses in the target KB. Since F26 hypotheses live in the target KB with ITS dedup (normally on); a counter-hypothesis names what it counters in distinct_from.

What this does NOT mean: experiments were not broken; the refusal was the designed behaviour at f05522da and nothing from the refused experiments landed. And 'since #412 parallel updates are fine' is the misreading to avoid: they land, but they lose information.

Related, F-R2 (a counter-hypothesis written with knomit_learn merged into the hypothesis it counters even with distinct_from): FIXED by #412 as well; learn's dedup merge now declines a match the call names in distinct_from (kb/decisions/mcp/learn/distinct-from-honoured-by-merge/91cf6418.md). review's dedup can still merge the two later.
