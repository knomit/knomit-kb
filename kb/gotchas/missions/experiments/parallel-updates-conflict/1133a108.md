# Parallel mission tasks that knomit_update the SAME facts in per-task experiments cannot all land: once the first commits and the 3 s sync brings its edits into the other agents' branches, every later experiment commit is refused for conflicts and the work-task skill rolls it back

Observed in the first IPO mission real run (2026-10-02, f05522da, three agents on two machines). Three cross-check tasks, one per agent, each opened an experiment on the knowledge base and ran knomit_update on the same 9 hypothesis files. The first agent's experiment was fast-forwarded into its agent branch; with realtime push/pull the consensus merge carried those edits into the other two agent branches within seconds. When the other two committed, `knomit_experiment commit` found the parent branch had changed the same paths after the fork and refused for conflicts. The work-task skill forbids picking sides, so both rolled back and acked "Failed:", which tripped the mission's stop condition (more than one Failed ack in a wave).

Consequence: corroborate/contradict passes over shared facts must be SERIALISED (one agent at a time, the next posted after the previous ack lands), or each agent must write NEW facts (counter-hypotheses, evidence observations) rather than updating shared ones. Running them in parallel wastes every session but the first.

What this does NOT mean: experiments are not broken; the refusal is the designed behaviour for a conflicting commit, and the facts are not corrupted (nothing from the refused experiments landed). Related: a counter-hypothesis written with knomit_learn can be merged into the hypothesis it counters by same-subject dedup, even with distinct_from (reported by a session in the same run), so 'write a counter instead' needs checking that a new path was created.
