# hookSpecificOutput.additionalContext is a discriminated union — only twelve CC events carry the variant, and a hook wired to any other event has its ENTIRE result discarded, not just the field

Claude Code's `hookSpecificOutput` is a discriminated union keyed on `hookEventName`. Only these twelve events carry an `additionalContext` variant: **PreToolUse, PostToolUse, PostToolBatch, PostToolUseFailure, UserPromptSubmit, UserPromptExpansion, SessionStart, Setup, SubagentStart, Stop, SubagentStop, Notification**. Every other event — PreCompact, SessionEnd, PermissionRequest, … — fails schema validation no matter what is emitted, and CC's failure mode is to **discard the hook's whole result**. The cost is the entire nudge, not one dropped field, and the hook still exits 0 with output, so it looks like it worked.

There are TWO independent ways to trip this, and fixing one does not fix the other:

1. **Wrong or missing `hookEventName` inside the object.** CC compares it against the event it dispatched and throws `Hook returned incorrect event name: expected 'X' but got 'Y'` (string confirmed present in the CC 2.1.226 binary). The name must be the **settings.json event** the hook is wired to, NOT the bridge's own subcommand name (`post-edit`, `pre-compact`, …).
2. **The event is not in the union at all.** Correct `hookEventName` does not help; the variant does not exist.

The twelve-event list was read off CC 2.1.226's actual output schema. **CC's own "Expected schema:" error hint is a lossy subset — do not trust it** for deciding whether an event carries the variant.

Operational consequences:

- A hook wired to a non-carrying event must emit **plain text on stdout** instead of any JSON envelope.
- Callers must pass `wiredEvent(in.HookEventName, fallback)` rather than a hardcoded literal, so re-wiring a hook to a different event in settings.json cannot silently reintroduce failure mode 1. `hookPostAsk` and `hookPostEdit` both do this.

**WHAT THIS DOES NOT MEAN — plain stdout is not a universal escape hatch.** Stdout is NOT uniformly injected into the model's context; each event routes it somewhere event-specific. `hookPreCompact`'s stdout is read as `newCustomInstructions` into the summarizer's prompt; `hookSessionStart`'s is auto-wrapped as a system reminder. Before falling back to stdout for a new event, check where that event actually routes it — "it printed, so the model saw it" is the same silent-success trap in a different costume.

This bit the bridge twice: once as the original bug (no `hookEventName` at all, so all three JSON-emitting hooks were dead), and once as an incomplete fix (PreCompact still wrapped in a JSON envelope it can never accept). Both passed tests that round-tripped our own encoder — an assertion has to name the CONSUMER's contract, not that we wrote what we intended to write.
