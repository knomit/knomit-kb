# After http.Client.Do or localCall, errors.Is(err, io.EOF) also matches a dropped connection (a *url.Error wraps io.EOF), so treating it as an empty 2xx body made destructive fleet verbs exit 0 on an unknown outcome; only the decoder's bare io.EOF, compared with ==, means the body was empty

WHAT HAPPENED (PR #666, found in review). cmd/fleet.go fleetAPI calls localCall (cmd/oauth.go) into a json.RawMessage. localCall returns the json decoder's bare io.EOF when a 2xx answer has no body (a 204 or an empty 200), which is success with nothing to print. The first version tolerated it with errors.Is(err, io.EOF). But when the server closes the connection without answering, http.Client.Do returns a *url.Error that WRAPS io.EOF, and localCall returns that error as it is; errors.Is matched it too, so the verb printed nothing and exited 0 although the request's outcome was unknown (decommission, leave, master resign are destructive).

RULE. Tolerate only the identity comparison `err != io.EOF` (the decoder's bare value). Any wrapped EOF, a dropped connection, is an error. In cmd/fleet.go fleetAPI the comparison carries a comment saying so.

CONSEQUENCE. Anywhere a call can fail in the transport OR in a body decode, errors.Is(err, io.EOF) cannot tell 'nothing to read' from 'the connection died': take the EOF branch only for the error returned by the decoder itself, not for what http.Client.Do returned. MISREADING: this is not 'never use errors.Is for io.EOF'; it is that an EOF wrapped by the transport is a different outcome from the decoder's.

PINNED BY TestFleetCLI_DroppedConnectionIsAnError (cmd/fleet_test.go): a handler hijacks the connection and closes it; fleetAPI must return an error and print nothing, and the test asserts the handler ran (hijacked).
