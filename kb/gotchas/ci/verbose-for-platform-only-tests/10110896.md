# `go test` without -v prints one line per PACKAGE, so a green CI step proves the package ran and says nothing about WHICH tests did — for a package whose platform-specific half compiles on one OS only, that is the whole question

A job log carrying `ok knomit/internal/auth 0.628s` proves the package compiled and ran on that runner — and says nothing about WHICH tests did.

For most packages that is fine. It is not fine for a package whose platform-specific half is compiled on exactly one OS: internal/auth's named-pipe tests exist only under `//go:build windows`, so the windows-2025 leg is the only place they ever execute, and a package that silently stopped building them would still print `ok`.

Asked to prove from CI that the pipe tests ran there, a grep for their names returned NOTHING — not because they had not run, but because nothing prints names without -v. The available evidence was a CHAIN: the step names ./internal/auth/, the log shows `ok` for it, and none of the ten Windows-only tests in that package calls t.Skip, therefore they ran. Sound, and it has to be re-derived by every future reader.

NOT FIXED, AND DELIBERATELY NOT. A separate verbose step for internal/auth was written and then REVERTED: the PR was already approved and out of draft, and a new CI step after approval is scope growth the change did not need. Measured while it existed, so the cost is known if anyone wants it later: its own step running `go test -v ./internal/auth/` adds ~35 log lines and 0.6s and names all 31 tests. `-v` on the shared step would make internal/config and internal/embeddings verbose too, for no gain.

NAMED MISREADING: "the package is in the step list and the step is green, so the platform tests ran." That is an INFERENCE, not an observation, and it is only as good as the assumption that nothing skips.
