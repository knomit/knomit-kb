# A Go runtime fatal "found pointer to free object" in the Windows internal/web CI job is heap corruption DETECTED at a later sweep, not caused there. It has recurred (2 occurrences, 2 different detection sites) and is tracked in #279. The package links sqlite3 and sqlite-vec through cgo, and the 'handler exploded' and nil-Manager panics in the log are RECOVERED test noise, not the crash. Re-run first, then separate trigger from cause before blaming anything

**Occurrences** (tracked in knomit#279; append each new one there and here):
1. 2026-09-18, CI run 35376722655 on PR #225 (head 9f145959, a routes-only diff). Detected in `mallocgc ← slicebytetostring ← chi/v5/middleware.prettyStack.parse ← PrintPrettyStack ← knomit/internal/web.reportPanic`, i.e. while pretty-printing the deliberate panic. It passed on an immediate re-run.
2. 2026-09-23, CI run 35933264713 attempt 1, job 107424484598, on PR #273 (web/ test files and Library.tsx only, no Go). Detected on a SCHEDULER M with no user goroutine: `stopm → acquirep → mcache.prepareForSweep → mcentral.uncacheSpan → sweep → reportZombies` (`mgcsweep.go:893`). The runtime said `marked free object in span … elemsize=16 … (bad use of unsafe.Pointer or having race conditions? try -d=checkptr or -race)`. No goroutine was `[running]` and none was in cgo. The test in flight was `TestServerHandler_MountsAPIRouter`. FAIL internal/web after 262s; attempt 2 passed.

TWO DIFFERENT DETECTION SITES for one symptom is itself evidence: the corruption is made somewhere else and found at whatever next sweeps that span.

**How to read it.** (1) A GC fatal names where corruption was DETECTED; the allocation or sweep site is a victim, not a suspect, and so is any diff that sits near it. (2) The internal/web test binary is cgo-linked (`go list -deps -test ./internal/web` pulls github.com/mattn/go-sqlite3 v1.14.34 and github.com/asg017/sqlite-vec-go-bindings/cgo v0.1.6; the Windows job builds them against MSYS2 mingw sqlite3 headers), so a cgo pointer-rule violation or a C-side overrun presents exactly this way, nondeterministically. knomit's own non-test Go imports `unsafe` only in internal/platform/memlimit/ostotal_windows.go and internal/embeddings/ortinit_windows.go. (3) The deliberate panic tests run reportPanic → crashdump (`debug.Stack()`, `runtime.ReadMemStats`, stop-the-world), the point in the suite most likely to surface pre-existing corruption: detectors, not causes. (4) A PR that shifts allocation timing can be a TRIGGER while being incapable of being the CAUSE.

**The log is full of panics that are NOT the crash, which is the trap in reading it.** In the same stretch it prints two `panic: handler exploded` blocks and two `panic: runtime error: invalid memory address or nil pointer dereference` blocks. All four are RECOVERED and pretty-printed by chi's `middleware.Recoverer` (recoverer.go:45); the `->` frames are PrintPrettyStack's format. The first two are deliberate: TestMetricsMiddleware_CountsPanicAs500 (observability_test.go:61) and TestReportPanicMiddleware_WritesBundleAndStill500s (panic_report_test.go:25). Neither escapes, since each ends in its own tRunner and the handler spawns no goroutine. The other two are nil `*repos.Manager` dereferences (Manager.Get manager.go:527, Manager.LensRegistry manager.go:478) inside TestReadOnlyRouter_FactRouteBypassRegression, which drives the router with no manager. The real crash is the later `fatal error: found pointer to free object` with a `runtime stack:` block. Search for `fatal error:`, not `panic:`.

**Runbook, cheapest first.** (a) Re-run the job; if it goes green, append the run id in #279. Do not close it as 'flake' in your head. (b) Build the Windows job once with `GOEXPERIMENT=cgocheck2` (build-time on Go 1.25/1.26; the old `GODEBUG=cgocheck=2` was removed in 1.21) to catch a cgo pointer-rule violation where it happens instead of at the next sweep. `-race` is worth one run but cannot see C-side scribbling. (c) Check whether the Windows runner builds go-sqlite3 and sqlite-vec with the same C flags as Linux; a Windows-only C build difference is a strong prior for a Windows-only heap fatal. (d) If it recurs on one SHA, run `./internal/web/...` alone, without ./test/storytests/, and with the PR's new tests excluded, to separate trigger from cause.

**Misreadings to avoid.** Do not gate an unrelated PR on this: attributing a GC fatal to the nearest diff is adjacency, not evidence. Do not dismiss a recurrence as 'Windows is flaky': this package runs in production, and a reproducible corruption deserves its own investigation, with the panic tests as reproducers, not the accused. And do not read the recovered `nil pointer dereference` panics above the fatal as the crash.
