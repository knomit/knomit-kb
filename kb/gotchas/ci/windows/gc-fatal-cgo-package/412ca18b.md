# A Go runtime fatal "found pointer to free object" in the Windows internal/web CI job is heap corruption DETECTED at the next allocation, not caused there — the package links sqlite3 and sqlite-vec through cgo, the deliberate 'handler exploded' panic test is the loudest GC moment (debug.Stack + runtime.ReadMemStats) so it is the detector, and a route-only diff cannot be the cause; re-run first, then separate trigger from cause before blaming anything

**Observed 2026-09-18, once.** CI run 35376722655 on PR #225 (head 9f145959, a diff that only registers routes: r.Method GET/HEAD on /assets/*, r.Head on the SPA fallback, hoisted /docs handler) failed ONLY `tests / build-test (windows-2025)` with:

```
panic: handler exploded
fatal error: found pointer to free object
runtime.(*mspan).reportZombies → sweep → mheap.reclaim → mallocgc → slicebytetostring
  ← chi/v5/middleware.prettyStack.parse ← PrintPrettyStack ← knomit/internal/web.reportPanic
FAIL knomit/internal/web 195s
```

The same job passed on the PR's previous commit 2b895c0a and on the nine runs before it, and passed again on an immediate `gh run rerun --failed` of the same SHA. Nondeterministic.

**How to read it.** (1) A GC fatal names where corruption was DETECTED; the allocation in chi's pretty-stack printer is a victim, not a suspect, and so is the routing change that sits near it in the diff. (2) The internal/web test binary is cgo-linked (`go list -deps ./internal/web/` pulls runtime/cgo, github.com/mattn/go-sqlite3 and github.com/asg017/sqlite-vec-go-bindings/cgo), so a cgo pointer-rule violation or a C-side overrun presents exactly this way, at an unrelated allocation site, nondeterministically. That mechanism is live in this package and predates any given PR. (3) The deliberate panic test (`observability_test.go`, `panic("handler exploded")`) runs reportPanic → crashdump, which calls `debug.Stack()` and `runtime.ReadMemStats` (stop-the-world) — the point in the suite most likely to surface pre-existing corruption. It is a detector. (4) A PR that adds an httptest.Server and a few dozen requests shifts allocation timing, so it can be a TRIGGER while being incapable of being the CAUSE; nine green runs of a nondeterministic corruption are weak evidence of absence either way.

**Runbook, cheapest first.** (a) Re-run the job; green → record here (append the run id), do not close as 'flake' in your head. (b) If it recurs on the same SHA: run the Windows job with the PR's NEW tests excluded (`-run` skipping them) and the server code unchanged — green separates test-load trigger from code cause in one run. (c) Build the Windows job with `GOEXPERIMENT=cgocheck2` (build-time on Go 1.25/1.26; the old `GODEBUG=cgocheck=2` was removed in 1.21) to catch a cgo pointer-rule violation at the violation instead of at the next sweep; `-race` is worth adding but cannot see C-side scribbling. (d) Check whether the Windows runner builds go-sqlite3 and sqlite-vec with the same C flags as Linux — a Windows-only C build difference is a strong prior for a Windows-only heap fatal.

**Misreadings to avoid.** Do not gate an unrelated PR on this: attributing a GC fatal to the nearest diff is adjacency, not evidence. Do not dismiss a recurrence as 'Windows is flaky': a reproducible corruption in a package that runs in production deserves its own investigation with the panic test as the reproducer, not the accused.
