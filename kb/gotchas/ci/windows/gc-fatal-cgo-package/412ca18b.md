# A Go runtime fatal "found pointer to free object" in the Windows internal/web CI job was heap corruption caused by golang/go#81238 (Windows exception dispatch overruns the goroutine stack on AMX hosts), TRIGGERED by a test that dereferenced a nil *repos.Manager; cgo was never involved. Five occurrences 2026-09-18..23, closed by knomit#279: the test got a real Manager and tests.yml fails the Windows leg on any recovered nil dereference

**Cause (established 2026-09-25, knomit#279).** golang/go#81238, OPEN, milestone Backlog: on windows/amd64 a hardware fault in Go code (a nil dereference is an access violation) is dispatched by the kernel ON THE FAULTING GOROUTINE'S STACK: CONTEXT + XSTATE + EXCEPTION_RECORD plus the dispatcher/sigtramp frames. Go reserves `stackSystem = 4096` bytes for that (runtime/stack.go:75 in 1.26.8). On AMX-capable Intel hosts the kernel lays out the 8 KiB XTILEDATA area even for a process that never uses AMX, and the frame measures ~11.6 KiB in total, so it overruns `stack.lo` into the heap span beneath the stack (how far depends on the goroutine's free headroom; a fresh goroutine has the least). Under the Green Tea GC (default since Go 1.26) small-object spans keep their mark bits INLINE in the span, so that metadata is what gets clobbered, and a LATER sweep, on whatever goroutine sweeps that span, throws `found pointer to free object` from reportZombies (mgcsweep.go:893). Upstream data: Xeon 6973P-C 44/64 jobs crash, Xeon Platinum 8573C 73/162, AMD EPYC 0/1305; the GitHub windows-2025 pool is mixed. It reproduces upstream with CGO_ENABLED=0. On unix the same nil dereference is also a hardware fault, but SIGSEGV is delivered on the signal stack, so the goroutine stack is untouched and a recovered one is only a log line: do not 'fix' unix by analogy.

**Trigger in knomit.** `TestReadOnlyRouter_FactRouteBypassRegression` (internal/web/readonly_test.go) built `&Server{ReadOnly: true}` with a nil Manager and served two deliberately NON-gated MCP routes; both reached RepoMiddleware -> Manager.Get -> RWMutex.RLock on address 0+offset, a real access violation, recovered by chi's Recoverer. Those were the ONLY real hardware faults PRINTED in the Windows job's output. The deliberate `panic("handler exploded")` tests are SOFTWARE panics, never touch the kernel, and were only ever noise. A SECOND real fault printed nothing: `TestSingleShotPathsBypassTheSemaphore` (internal/embeddings/serialize_test.go) reached `sess.Run` on a nil ONNX session in a fresh goroutine and swallowed the panic with a bare `recover()`; job 106148265186 (2026-09-20, unit-test step) died in that package with `unexpected signal during runtime execution` in closechan right after that fault.

**Occurrences (5, all in `tests / build-test (windows-2025)`, all go1.26.8 on image windows-2025-vs2026 20260828.587, each with a goroutine in `[flushing proc caches]` and each within the same log second as the readonly test's recovered faults):**
1. 2026-09-18 run 35376722655 / job 105703009398, PR #225 (9f145959), elemsize=48. Detected on the SAME goroutine that took the fault, while chi pretty-printed it: mallocgc -> mheap.alloc -> reclaim -> sweep -> reportZombies. (An earlier revision of this fact said it was printing the 'handler exploded' panic; it was the nil-Manager one from readonly_test.go:97.) Attempt 2 passed.
2. 2026-09-19 run 35409074256 / job 105804829897 (fe68d426, feat/cancel-repo-create), elemsize=16, bgsweep. Not re-run.
3. 2026-09-22 run 35774055269 / job 106902636444 (caa0d860, dev push), elemsize=16 freeindex=170, scheduler M stopm -> acquirep -> prepareForSweep. Not re-run.
4. 2026-09-22 run 35780178520 / job 106923384475 (66e242e1, feat/auth-windows-pipe), elemsize=16, bgsweep. Not re-run.
5. 2026-09-23 run 35933264713 / job 107424484598, PR #273 (60ad47a1), elemsize=16 freeindex=335, scheduler M. Attempt 2 passed.
Rate: 5 of 205 Windows build-test attempts that reached the web step (2026-09-17..25), about 2.4% per attempt. Three distinct detection sites for one cause is exactly what 'corruption made at the fault, found at the next sweep of that span' predicts.

**Why the span dumps were useless.** All five print every slot `unmarked` and no `zombie`: golang/go#80799 (open, Go1.28), reportZombies reads the mark bits from the wrong place under Green Tea. Do not try to identify the dangling object from that dump.

**Why cgo was cleared.** The internal/web test binary links only go-sqlite3 v1.14.34, sqlite-vec v0.1.6 and runtime/cgo; knomit's two `unsafe` users (memlimit, ortinit_windows) are not linked into it. go-sqlite3 passes Go callbacks through a C.malloc'd handle map, sqlite-vec registers a plain C function pointer, x/sys GetTokenUser returns interior pointers into a Go []byte. Nothing was in cgo at any detection, and upstream needs no cgo. GOEXPERIMENT=cgocheck2 and -race were never run and would have found nothing; GOEXPERIMENT=nogreenteagc would only move the symptom.

**Local negative result, weak.** Not reproduced on a non-AMX Intel i5-3470 (449 iterations of the four tests, GOGC=5, default build) with no positive control; consistent with the cause, not confirmation of it.

**Fix (PR #295, branch fix/279-windows-fault-heap-corruption).** (1) Both read-only router tests take `newTestManagerWithRepos(t)`; the non-gated routes answer 404 (RepoMiddleware) and 503 (lens registry not started), asserted exactly. (2) `runRows` returns an error on a nil ONNX session; the serialize test asserts that error and recovers nothing. (3) Every go test step in build-test AND slow-tests runs through `.github/scripts/go-test-capture.sh`, which keeps the `go test -json` stream in $RUNNER_TEMP and prints plain-go-test-shaped console output; `.github/scripts/go-test-fault-guard.sh` (Windows-only, `!cancelled()`) fails on any `invalid memory address or nil pointer dereference` in those streams. **THE -json IS LOAD-BEARING: plain `go test` DISCARDS a passing package's output and prints only `ok pkg`, so a tee of plain output contains a recovered panic only after the package has already failed** (forced: the old nil-Manager test prints 0 matches plain, 2 under -json). The first version of this PR had that hole; review caught it. (4) The Windows toolchain probe prints the CPU model. A hit on the guard means a TEST dereferenced nil: give it the real dependency; do not weaken the guard.

**What the guard cannot see.** A bare `recover()` that swallows the panic silently (the embeddings shape above) prints nothing under -json either. That is a review rule: on Windows a test must never reach a nil dependency, whatever it does with the panic. It also cannot help the desktop or bridge binaries in production.

**What this does not fix.** Production. The server's Recoverer/reportPanic path recovers handler panics, so a real fault in a handler on a Windows AMX host corrupts the heap the same way; nothing in knomit's tree can change the kernel's frame size. The fix has to come from Go: CL 828724 (proposed, unmerged as of 2026-09-07; upstream has not shown a larger reserve is the complete fix) sizes the reserve from the host; CL 824724, merged to master, only turns the corruption into a deterministic throw. Bump Go when a release carries a fix and drop the guard's rationale, not the guard.

**Misreadings to avoid.** A red Windows job ending in this fatal on an unrelated PR is not the PR's fault, and after this fix it should not happen at all: if it does, look for a NEW real fault in the captured streams first. Do not read the recovered `nil pointer dereference` lines above a fatal as noise on Windows; on this platform they are the cause. Do not conclude 'no fault' from a green plain `go test` log; only the -json stream shows a passing test's output.
