# In the full CI the build-test (windows-2025) job runs its test steps in sequence (Desktop app builds, vets and tests on Windows, then Unit tests, then story/web, then bridge/cmd), so the first red step hides every later one: after fixing one Windows failure expect the NEXT masked one, and a PR's fast CI does not run Windows tests at all

In .github/workflows/tests.yml the build-test matrix leg windows-2025 executes: 'Desktop app builds, vets and tests on Windows (-tags desktop)' (go test -tags desktop ./tools/desktop/), then 'Unit tests (no model download)', then the harness-isolation guard, story/web/desktop-helper tests, bridge/platform/app/cmd tests, the contract cells. A step that fails stops the job (no continue-on-error), so every later step is not run. On PR #516 (2026-10-14) three independent Windows-only failures were stacked behind each other: the desktop log file left open (TestSaveSettings_*), then TestSupervisor_Exit3SwitchesToAttach, then internal/pki TestExportImport_RoundTripMovesTheKey (a 0600 check Windows cannot satisfy), which had been hidden behind the desktop failure since at least #510 and never ran on Windows during that time. Each fix needed a full CI round to reveal the next (about ten minutes per Windows build-test on that day: dated, not a constant).

AN OPEN PR DOES NOT SEE THIS: the PR (fast-shape) CI runs build-test on ubuntu only; Windows and macOS get only build-vet (compile and vet). All three failures could surface only in the full CI (workflow_dispatch or the post-merge run).

OPERATIONAL CONSEQUENCE. When a full-CI Windows run is red, read the log of the FIRST failing step and then assume later steps are unverified; do not infer the later packages are green because they are not mentioned. After pushing a Windows fix, dispatch the full CI and expect another round. Do not diagnose the later package from the earlier failure.

NOT MEANT: the order is not a bug to fix by itself, and it does not mean the later tests are broken; they were simply not run.
