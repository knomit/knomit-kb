# On Windows CI a test that attached a file:// bare remote can fail AFTER every assertion passed with "TempDir RemoveAll cleanup: unlinkat …\remote.git\objects\tmp_objdir-incoming-*: The directory is not empty" — the reconcile loop's push was cancelled at teardown while a receive-pack still owned its staging dir

**Symptom (one sighting).** PR #282's first CI run (run 36036126278, job 107756547737, `build-test (windows-2025)`) failed `knomit/internal/web` with exactly one failing test, `TestHandleHALSetOrigin_PlainRemoteIsAllowedAndKeepsTheOntology` (1.47s). The test had NO assertion failure. Its only failure line was:

    testing.go:1464: TempDir RemoveAll cleanup: unlinkat C:\…\TestHandleHALSetOrigin_…\001\remote.git\objects\tmp_objdir-incoming-U34PZR: The directory is not empty.

**Mechanism (the reading most consistent with the log; not reproduced).** `tmp_objdir-incoming-*` is the quarantine directory C git's receive-pack creates on the RECEIVING repo while a push is in flight. The test attaches a file:// bare remote (`remote.git`, inside the test's `t.TempDir()` root), so the repo's reconcile loop pushes to it. At teardown the cleanups run LIFO: `newRealManagerWithLocalOriginRoot`'s `t.Cleanup(m.Close)` runs first and cancels the loop — the log shows `Push: context canceled` / `reconcile: push abandoned; loop is stopping` / `reconcile loop stopped` — and THEN the TempDir RemoveAll runs. Cancelling the push's context does not wait for the receiving side to finish writing or delete its quarantine directory. On Linux the removal just wins or loses silently; on Windows a directory that is still being written cannot be unlinked, so RemoveAll reports it and the test FAILS after passing.

**Red herrings in the same log.** `reconcileMain: origin/main has DISJOINT history … force-updated` and `mergeIntoBranch: no common ancestor between "main" and "machine/test" (disjoint histories)` are EXPECTED for this test: it seeds a plain remote with unrelated history on purpose (`seedPlainRemoteForTest`) and accepts 200 or 502. The `handler exploded` / nil-pointer panics are recovered test noise (see the gc-fatal-cgo-package gotcha).

**Consequence.** Classify this signature as a Windows teardown flake, not a regression in whatever PR it appears on — #282 touched only refs/fact/resolutions/synthesize/mcp/skills and could not reach the origin handler or the reconcile push. Re-running is the right first call. If it recurs, the fix is TEST-SIDE, one of: (a) make teardown wait until the reconcile loop's in-flight push has fully exited (including the receiving git process) before the TempDir cleanup runs, or (b) retry RemoveAll briefly on Windows for the remote dir. Same failure CLASS as the set-orphans-live-instance gotcha: a still-live handle that Linux hides and Windows turns into a TempDir failure after every assertion passed.

**WHAT THIS DOES NOT MEAN.** It does not mean the disjoint-history reconcile is broken, and it does not mean Manager.Close fails to stop the loop — the loop did stop. It also is not yet a known recurring flake: failed CI and Race runs checked back to 2026-09-22 showed no other `tmp_objdir` or RemoveAll-cleanup hits. Raise confidence and `sources` if it recurs; if a second sighting shows a different mechanism, update this fact rather than adding a sibling.
