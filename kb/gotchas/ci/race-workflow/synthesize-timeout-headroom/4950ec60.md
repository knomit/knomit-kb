# internal/synthesize under `go test -race` on ubuntu-latest takes 1006–1643 s across the Race runs of 2026-09-19..24, against race.yml's `-timeout 30m` (1800 s): the worst observed run had 157 s of headroom, so a `test timed out after 30m0s` panic in that package is the NEXT non-race red this job will produce

Measured from the `ok knomit/internal/synthesize <seconds>` line of eleven consecutive race.yml runs (35458319863 through 36025605402): 1006, 1611, 1586, 1578, 1643, 1080, 1580, 1327, 1556, 1342, 1573 seconds. race.yml's comment says 30m was chosen as ~2.4x a 744 s figure measured on an Apple-Silicon dev machine; the GitHub runner is running at about 2.2x that figure, so the real margin is ~1.1x. The other slow packages are far from the limit (pki ≤ 208 s, repos ≤ 288 s, store ≤ 152 s).

Consequence: when this package times out, the log will show a goroutine dump and `panic: test timed out after 30m0s` under internal/synthesize with no DATA RACE block. That is a budget failure, not a race and not a hang. The workflow's own rule applies: RE-MEASURE and raise -timeout (or split the package's slow tests) rather than round up on a hunch.

WHAT THIS DOES NOT MEAN: the job-level timeout-minutes: 90 is not the binding limit and is deliberately looser; the per-package -timeout is what fires first.
