# Two load flakes in internal/corpus/repos walkthrough tests were TEST-FIXTURE defects, both fixed in #653: TestWalkthrough_ArchiveMidIndexWithAParkedSyncRound failed in pushToBareMain's local-path git clone, and TestWalkthrough_Detach asserted ErrSubscriptionOrigin while the repo was still indexing (the machine answers ErrIndexing first)

Observed on dev and on PR CI runs between 2026-10-16 and 2026-10-25, each passing on rerun and in the failing PR's untouched area. Both causes were then PROVEN by reproduction and both fixtures fixed in PR #653 (merged as 0156f299; the diff is test-only, no production code changed).

1. TestWalkthrough_ArchiveMidIndexWithAParkedSyncRound (machine_test.go). Cause: the setup helper pushToBareMain (sync_mode_test.go) cloned the bare origin BY LOCAL PATH. A local-path clone copies (or hardlinks) objects/ file by file, while the manager's sync round pushes into the same bare repo through git-receive-pack, which stages objects in objects/tmp_objdir-incoming-* and then moves or deletes them, and `git maintenance --auto` creates and removes objects/maintenance.lock after a push. A file the copy listed but could not read fails the clone with "failed to copy file to ...: No such file or directory". The two historical signatures ("tmp_objdir-incoming" and "maintenance.lock: No such file") are ONE mechanism. Reproduced outside the suite: 1 of 900 local clones failed with that message while a second process pushed; 0 of 300 failed with `--no-local`. Fix: `git clone --no-local`, which goes through upload-pack and reads the object database the way a fetch does. `--no-local` covers the maintenance.lock signature too, so a future sighting of either signature on a head that has the flag is NOT this known flake. It is a pure test artefact: production never shells out to git clone (every production clone goes through go-git, which speaks the upload-pack protocol and does not copy objects/).

2. TestWalkthrough_Detach (machine_test.go). Cause: the test called DetachOrigin while the subscription was still indexing, and ErrIndexing is checked before any origin rule (kb/decisions/repos/lifecycle/indexing-exclusive-with-attach-detach-swap/cc2212e3.md). The machine was right; the test was wrong. Measured by a reviewer with a -race test binary as 16 parallel processes, 1008 runs per side: without the wait 7/1008 failed at the DetachOrigin assertion with `expected "a subscription requires its origin"`, `in chain: "repo is indexing"`; with the fix 0/1008. Fix: the test waits with waitIndexSettled on the subscription before the Detach.

CONSEQUENCE: a red run of either test on a head that contains #653 is a REAL signal, not a known flake; do not rerun-and-forget it. The earlier advice to rerun first applies only to heads that predate 0156f299.

WHAT THIS DOES NOT MEAN: (a) tests must stop pushing to a bare origin that a sync round also pushes to. Concurrent pushes to different refs are safe for git; the hazard was only the file-by-file local-path clone. (b) --no-local is a general cure for go-git concurrency problems; the go-git concurrent-clone corruption (kb/gotchas/deps/go-git/concurrent-clone-corruption/52c06cdc.md) is a different, in-process mechanism and that package stays sequential. (c) The assertion in TestWalkthrough_Detach should be weakened or the production check order changed; it should not.

The Windows teardown race in the sibling gotcha is a different failure (cleanup after all assertions passed).
