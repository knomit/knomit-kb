# tests.yml names its Go packages EXPLICITLY per job step, so a new package is tested by CI on NO OS until someone adds it — "CI green" says nothing about it; internal/auth ran only on developers' Macs from PR #243 until PR #250

THE MECHANISM: `.github/workflows/tests.yml` does NOT run `go test ./...`. Each job step lists its packages by path — the build-test unit step (`./internal/embeddings/ ./internal/config/ ./internal/fact/ …`), archtest, storytests/web/desktop-internal, bridge/platform/cmd; slow-tests (synthesize/store/repos); desktop (`./tools/desktop/...`). A package that appears in no step is compiled only if something that IS tested imports it, and its own `_test.go` files never execute, on any OS.

THE INSTANCE: `internal/auth` shipped in PR #243 (F19 phase 1) with its PeerCred, ConnContext and grants tests, and was in no step. Every CI run was green and none of those tests ran; the Linux-specific `SO_PEERCRED` path had had `go vet` and nothing else. The #250 reviewer found it by grepping the job logs for `knomit/internal/auth` — zero lines in every job. It only surfaced because a test in that package (a backlog-saturation fixture) was PROVEN to fail on Linux in a container while CI stayed green. PR #250 added `./internal/auth/` to the build-test unit step, which runs on ubuntu, macos and windows.

CONSEQUENCES TO ACT ON:
- A PR that CREATES a Go package must also add it to a step in tests.yml, on the OS matrix it needs. Adding tests to a new package without that is adding tests nobody runs.
- A reviewer must not read "CI green" as evidence about a package. Grep the job logs for `knomit/<pkg>` (an `ok` or `FAIL` line naming it) before accepting a claim that its tests pass in CI.
- A package tested only by the developer on one OS carries the platform-specific-fixture risk in full: its green run is evidence only for that platform.

DISTINCT FROM the storytests build-tag gotcha: there the tests are hidden from `go test ./...` by a build tag and CI DOES run them; here CI's own lists omit a package, so CI never runs it.

MISREADING TO AVOID: this is not "some jobs skip slow tests". It is that the package LISTS are opt-in, so the default for any package nobody remembered is zero coverage, and the summary gives no sign of it.
