# A sabotage check that restores files with `git checkout -- <file>` also reverts any UNCOMMITTED edit in that file: commit before sabotaging, and check `git show --stat` before claiming what a commit contains

WHAT HAPPENED (#347 round 8, 2026-09-30): a scripted sabotage loop patched a source file, ran the test, then restored the file with `git checkout -- <file>`. The same files held uncommitted fix edits (a refactor in path_changes.go and branch_commit_log.go). The restore silently threw those edits away. The next commit contained only the new test file, but its message claimed the refactor too. The reviewer caught it by reading the diff; the local tests had passed, because the reverted code was still valid.

RULE:
- Commit, or stash explicitly, BEFORE any sabotage run that restores files through git. `git checkout --` restores to the INDEX/HEAD, not to 'before my sabotage'.
- Alternatively, restore from a copy the script saved itself, never from git.
- Before reporting what a commit contains, run `git show --stat <commit>`; never infer it from the commit message you wrote.
- A `git status` right after the sabotage loop that shows fewer modified files than expected is the tell.

NOT MEANING: sabotage checks are risky and should be skipped. They are required by the review process; just order them after the commit.
