# The desktop app boots its OWN http.Server in tools/desktop/boot.go, so anything done to the listener in cmd/serve.go never reaches it — which is why F19 phase 1's unix socket does not exist on a desktop-served machine

THERE ARE TWO SERVER BOOT PATHS IN THIS REPO AND THEY SHARE ONLY THE HANDLER.

`cmd/serve.go` is the CLI path: it builds an `http.Server`, opens the TCP listener, and — since F19 phase 1 — also opens `cfg.Socket`, chmods it 0600, removes a stale one, and sets `ConnContext: auth.ConnContext` so unix peer credentials reach the request context.

`tools/desktop/boot.go` `bootServer` is the DESKTOP path, and it is a separate construction: its own `http.Server` literal over `netutil.Listen(preferredPort)`, a TCP listener only. It sets `BaseContext` but NOT `ConnContext`, and it does not reference `config.Socket` at all — measured, zero occurrences in the file.

THE RULE THAT FOLLOWS: a change to the LISTENER, to the `http.Server` fields, or to anything else in `cmd/serve.go`'s serving setup does NOT reach the desktop. Only changes that go through `app.Handler()` — middleware, routes, the MCP mount — or through a helper both paths call, are shared. `cmd/serve.go` is not "the server"; it is one of two.

CONSEQUENCE, observed rather than reasoned: on a machine served by the desktop app, F19 phase 1's unix socket IS NEVER OPENED. After restarting a fresh desktop build at the merge commit there is no `~/.knomit/knomit.sock`. Everything downstream of it follows — the bridge finds no socket and falls back to TCP, so it becomes the ANONYMOUS loopback principal rather than `bridge:uid:<n>@socket`, `client_sessions.principal` stays NULL, and `client_session_peers` gets no row. Nothing fails loudly, because the TCP fallback is by design; the verified identity is simply absent. Phase 1 therefore delivers its identity model to `knomit serve` users and not to desktop users. Tracked as "F19 phase 1c: desktop app never opens the unix socket".

WHY IT IS EASY TO MISS, and the reason this is written down: the two paths converge on the same `app.Handler()`, so every HTTP-level test passes identically under both and no test distinguishes them. The divergence is entirely in how the server is CONSTRUCTED and LISTENED ON, which is the part no handler test can see. Before concluding that a serving-layer change is live everywhere, grep `tools/desktop/boot.go` for it.
