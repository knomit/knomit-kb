# The desktop app boots its OWN http.Server in tools/desktop/boot.go, so anything done to the listener in cmd/serve.go never reaches it — F19 phase 1's unix socket was missing on desktop-served machines for exactly this reason until phase 1c moved it into a helper both paths call

THERE ARE TWO SERVER BOOT PATHS IN THIS REPO AND THEY SHARE ONLY THE HANDLER.

`cmd/serve.go` is the CLI path: it builds an `http.Server`, opens the TCP listener, and serves `app.Handler()`.

`tools/desktop/boot.go` `bootServer` is the DESKTOP path, and it is a separate construction: its own `http.Server` literal over `netutil.Listen(preferredPort)`, with its own `BaseContext`, its own shutdown, and its own discovery lockfile.

THE RULE THAT FOLLOWS: a change to the LISTENER, to the `http.Server` fields, or to anything else in `cmd/serve.go`'s serving setup does NOT reach the desktop. Only changes that go through `app.Handler()` — middleware, routes, the MCP mount — or through a helper both paths call, are shared. `cmd/serve.go` is not "the server"; it is one of two.

THE INCIDENT THIS CAME FROM (history, fixed): F19 phase 1 (PR #243, merge cec7c5c1) opened the unix socket and set `ConnContext: auth.ConnContext` in `cmd/serve.go` ONLY. At that commit `bootServer` had no `ConnContext` and did not reference `config.Socket` at all. On a desktop-served machine — the normal install — the socket was never opened: no `~/.knomit/knomit.sock` after restarting a fresh desktop build, so the bridge fell back to TCP and became the ANONYMOUS loopback principal instead of `bridge:uid:<n>@socket`, `client_sessions.principal` stayed NULL and `client_session_peers` got no row. Nothing failed loudly, because the TCP fallback is by design. Phase 1c (issue #248, branch feat/auth-desktop-socket) fixed it the way this rule prescribes: the socket steps moved into `auth.ListenLocal`, and both `cmd/serve.go` and `bootServer` call it and set `ConnContext` (see the local-listener invariant).

WHY IT IS EASY TO MISS, and the reason this stays written down: the two paths converge on the same `app.Handler()`, so every HTTP-level test passes identically under both and no test distinguishes them. The divergence is entirely in how the server is CONSTRUCTED and LISTENED ON, which is the part no handler test can see. Before concluding that a serving-layer change is live everywhere, grep `tools/desktop/boot.go` for it — and prefer a helper both paths call over editing either one inline.
