# Taking a self-update orphans every live knomit-bridge MCP session — by design, but self-update makes a rare trigger routine

MEASURED 2026-07-29. Self-update's "Install & Restart" relaunches the desktop app, and the embedded server comes back on a DIFFERENT port. `knomit-bridge` resolves its `baseURL` from `<StateDir>/server.json` exactly ONCE, at bridge process startup, and never re-reads it. Every already-running MCP client therefore keeps posting to the old port and gets `dial tcp 127.0.0.1:<old>: connect: connection refused` on every call, indefinitely, until the CONSUMER restarts the bridge process. Restarting the knomit server does not help — the stale address lives in the bridge, not in the server.

**This is BY DESIGN.** See the linked decision: bridge-side lazy recovery was implemented (PR #83, `feat/bridge-lockfile-recovery`) and deliberately dropped, because an MCP session is server-process-local state keyed by `Mcp-Session-Id` with no protocol primitive to restore it — so "recovery" is necessarily a silent reset, and the spec assigns that decision to the client.

**What is NEW here** is the trigger's frequency. Before self-update, an orphaned session required a crash or a manual restart. Self-update makes it a routine consequence of a normal user action, at the exact moment the design intends users to act (an update lands mid-session). Any long-lived agent session open when a user clicks Install & Restart loses knomit until it reconnects.

**Consequence — what to do:** after taking a desktop update, reconnect the knomit MCP server (in Claude Code: `/mcp` → knomit → reconnect) before relying on knomit tools. Treat `connection refused` immediately following an update as expected, not as a server fault — check for a live server on the port in the CURRENT `server.json` before investigating further.

**WHAT THIS DOES NOT MEAN:** it is NOT an argument for re-adding bridge-side recovery/retry — that is the exact design the linked decision rejects, with reasons that this observation does not weaken.
