# On an UNSIGNED .app the notification centre refuses every update banner (UNErrorDomain error 1) — the tray badge and menu item are the only surfaces that actually work

MEASURED 2026-07-29 on macOS against a real installed unsigned bundle (bundle id `com.knomit.desktop`, no code signature), updating 0.5.0 → 0.5.1. This retires an assumption the verification checklist explicitly flagged as the one most likely to be wrong — and it was wrong.

Every `SendNotificationWithActions` call fails with `Error: The operation couldn't be completed. (UNErrorDomain error 1.)` — `UNErrorCodeNotificationsNotAllowed`. No banner is ever delivered, so the "Install & Restart" action button is never reachable. `pkg/services/notifications` documents "packaged and signed" as its requirement and only guards on the bundle identifier, which an unsigned bundle satisfies — so the service constructs fine and fails at send time, not at setup.

**Consequence — what a consumer must act on:** for any unsigned build, the OS banner is NOT a deliverable surface. The tray icon badge and the tray's `Install <version> & Restart` menu item are the ONLY paths by which a user can learn about and take an update. They work because `checkAndNotify` calls `AnnounceUpdate` FIRST and unconditionally, before attempting the banner — inverting that order, or gating the tray on the banner succeeding, would leave an unsigned build with a running updater, a published release, and no way to learn either exists.

The failed send is not recorded by `notifyLog` (only an ACCEPTED banner is marked), so the attempt repeats on every poll. That is deliberate — a user who grants permission later still gets told — and means the warning line recurs once per check interval. Expected log noise, not a leak.

**Related defect:** `pollForUpdates` logs this as `background update check failed`, but the `Check` succeeded and only the banner failed. The message misattributes the failing component, and on unsigned builds this is the COMMON case, so it will routinely point debugging at the wrong layer.

**WHAT THIS DOES NOT MEAN:** it does NOT mean the notification code is broken or that the windowless design failed — the fallback behaving this way IS the design working. It also does NOT establish that code-signing would fix it; signing was not tested, so "sign the bundle and banners will work" remains an untested hypothesis.
