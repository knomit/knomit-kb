# A macOS self-update replaces the WHOLE .app, so the bundled `knomit` and `knomit-desktop` always move together, but the running server child holds the old binary during the swap: the desktop stops it first (stopServerFirst, since #503), and if the updater's Restart then fails the boot is FAILED (dialog), not respawned

In Wails v3.0.0-beta.28 `pkg/updater/helper.go`, `runHelperSwap(target, ...)` backs up the whole target (`target + ".bak"`), replaces it with the new one and relaunches; line 94 maps a darwin executable inside a `.app` to the `.app` directory. So `Contents/MacOS/knomit` and `knomit-desktop` are replaced in one swap and can never be a mixed old/new pair. The updater is darwin-only (tools/desktop/update.go); Linux and Windows have no updater.

**Consequence for PR 5:** once the desktop launches the bundled server as a child, that child still runs the OLD binary when the swap happens. Unix unlink-and-rename tolerates the open inode, but the desktop should stop its server child before it triggers the relaunch, or the old server keeps its listeners and lock while the new app starts. This is owed to desktop PR 5; #500 does not do it because nothing launches the child yet.

**What this does NOT mean:** it does not say the swap is unsafe today; with no child process there is nothing to stop. Third-party internals: pinned to Wails v3.0.0-beta.28, so re-read helper.go after any Wails upgrade.

DONE in PR #503 (merge 8be999a0, 2026-10-12): 'owed to desktop PR 5' is paid. `stopServerFirst` (tools/desktop/update.go) wraps the updater so its Restart first stops the supervised child (stdin close, kill after the 10 s grace) and only then triggers the swap and relaunch; TestStopServerFirstStopsBeforeTheUpdaterRestarts pins the order (it was red with the stop placed after the restart). If the updater's Restart FAILS after the server was stopped, supervision cannot be resumed (the stop ended the run loop), so `stopServerFirst.failed` (wired to the supervisor's `fail`) sets the boot status to failed with 'the update could not restart Knomit (...); the knomit server was already stopped for it. Reopen Knomit', which drives the existing fatal dialog. Before that was added the status stayed Ready while nothing served (no amber tray, no dialog, UI 502s) - found in review of #503; TestStopServerFirst_AFailedRestartIsAFailedBoot pins it with a real supervisor and a positive control that the server pid is gone. The dialog title still reads 'Knomit could not start' for an update failure (cosmetic).
WHAT THIS DOES NOT MEAN: in ATTACH mode there is no child to stop, and an attached server is not touched by the update (it keeps the old binary until its owner restarts it); and the failure path does not respawn the server - 'failed boot' is deliberate.
