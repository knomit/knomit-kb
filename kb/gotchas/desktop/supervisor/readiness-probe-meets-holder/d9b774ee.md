# supervisor.runChild probes the socket while its child is still ALIVE, so any server answering there marks the child ready as OWNED: a test's stand-in holder for the exit-3 path must answer only after the child has exited (s.child == nil), or TestSupervisor_Exit3SwitchesToAttach flakes ('ready but not attached after exit 3'), mostly on Windows where teardown is slow

MECHANISM (tools/desktop/supervisor.go). runChild publishes the child as s.child, then loops: probe the socket (GET /api/v1/version) until the child answers OR exits; a successful probe calls setReady() immediately, with attached=false, while the child process may still be alive. The probe cannot tell WHO answered. Exit 3 means the local listener is held by another live process; the run loop then waitForHolder -> probe -> attach, which sets attached.

THE TEST FLAKE (found on PR #516's first full-CI branch run, intermittent, passed in dev's earlier runs). TestSupervisor_Exit3SwitchesToAttach's stand-in holder (externalServer) answered as soon as spawns.jsonl held a line, but the fake child writes that line BEFORE it exits with 3. A probe landing between 'spawn recorded' and 'child reaped' succeeded against the holder, setReady() fired as if our own child were ready, waitReady returned, and isAttached() was still false: 'supervisor_test.go: ready but not attached after exit 3'. Windows process teardown is slow enough to hit the window; on macOS it reproduced 3/3 once the fake's exit3 slept 300 ms.

FIX AND RULE. The holder now answers only when a spawn has been recorded AND s.child == nil (read under s.mu): the scenario the test's comment describes, a holder that was still booting at the first probe. The fake's exit3 keeps a fixed 300 ms linger so the window exists on every platform; the linger is not what makes the test pass (removing it stays green) and only makes the old condition reproducible off Windows. The assertions are unchanged: attached, exactly one spawn, no backoff. Any new test with a fake that stands in for 'another server' must not answer while the supervisor still holds a live child.

PRODUCT NUANCE, NOT FIXED (review finding F1, low impact, a product call): the same window exists in production. If another server starts answering on the socket while our child is alive and about to exit 3, the supervisor briefly reports ready as OWNER; during that window 'Restart server' acts on the dying child instead of being refused as attached (attach-mode decision kb/decisions/desktop/settings/attach-mode/279d5688.md), restartServer returns nil although nothing was restarted, and the state converges to attached within one exit-3 cycle. The UI talks to the same socket throughout. Options noted by the reviewer: defer setReady until the child has survived one probe interval, or recheck c.exited after a successful probe. MISREADING: the test fix does not mean the supervisor race is closed.
