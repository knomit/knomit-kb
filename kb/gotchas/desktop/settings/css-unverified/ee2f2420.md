# The sidebar Settings window (PR #510) has been seen in the real Wails window on macOS only; on Windows (WebView2) its layout is still unverified

STATE AT knomit#504 (merge 1c6a0934, 2026-10-13): the HTTP-port scope row (three-way radio group with per-scope copy, the verbatim All-networks warning) and the attach banner (pid, both versions, skew warning) were styled in tools/desktop/ui/src/App.css (.row.scope, .banner). No worker or reviewer had a display: the PR was checked by vitest (jsdom, which cannot falsify layout), by process-level evidence and by the shipped go tests. Nobody has seen these rows rendered in the real Wails window on macOS or Windows (the Windows reports cover the transport, supervisor and reload, not these rows).

CONSEQUENCE: treat any claim about how the warning wraps, whether the radios align, or whether the banner is readable as unverified. A reviewer's spec-reading of the CSS is a hypothesis, not a finding. A real-window pass (macOS and Windows) is owed at release time; when done, update this fact with the evidence or retract it.

NOT MEANT: it does not say the CSS is wrong, only that nothing observed it.

UPDATE 2026-10-13 (PR #510, branch feat/desktop-settings-sidebar, merged to dev as 545994a2): `.row.scope` and the radio-row layout no longer exist; the window became a sidebar of four pages and the scope is a segmented control (`.seg`, selection marked by an `.is-on` class set from state, not `:has()`). The new layout, the attach banner, the restart bar and the All-networks warning WERE rendered in a real browser: Chromium at 680x472 via the Vite dev server with a stubbed @wailsio/runtime, every page and the env, scope-lock, attach+restart, busy-port, enrolled, root-confirm, error and long-message states. That is browser evidence, not real-window evidence: nobody has yet seen it in the Wails WebKit (macOS) or WebView2 (Windows) window, where native title-bar height and font rendering differ. The release-time real-window pass is still owed.

UPDATE 2026-10-13 (after merge 545994a2): the user opened the new sidebar Settings window in the real desktop app on macOS (Wails WebKit) and checked it before merging PR #510. The macOS real-window pass for the PR #510 layout is therefore DONE. Still owed: a real-window pass on Windows (WebView2), where native title-bar height and font rendering differ. Until that happens, claims about Windows layout are hypotheses.

WHAT THIS DOES NOT MEAN: the user's check covered the layout as merged, not every state the Chromium screenshots covered (env lock, attach+restart, enrolled, root-confirm, error). Those states are browser-verified, and only the default views are known to have been seen in the macOS window.
