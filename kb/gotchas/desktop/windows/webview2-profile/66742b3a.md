# On Windows the desktop's WebView2 profile is %APPDATA%\<exe file name>\EBWebView (Wails passes it explicitly), so WEBVIEW2_* environment variables are ignored and a second copy of knomit-desktop.exe shares the user's real profile unless its file name differs

Measured 2026-10-12 on Windows 10 22H2 with WebView2 runtime 154.0.4258.62 and Wails v3.0.0-beta.28 (versions are dated support; re-check on a Wails bump). The desktop's WebView2 user-data folder is `%APPDATA%\<exe file name>\EBWebView`: Wails passes an explicit path, so setting WEBVIEW2_USER_DATA_FOLDER had no effect, and WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS (used to ask for a remote-debugging port) had no effect either (no port opened).

CONSEQUENCE: a verification copy of knomit-desktop.exe started under the SAME file name uses the user's real profile, i.e. the same `http://wails.localhost` origin storage (localStorage, preferences) as the user's own app. To get a separate profile, run the copy under a DIFFERENT exe file name (a copy named knomit-verify.exe got its own profile) and delete `%APPDATA%\<that name>` afterwards.

WHAT THIS DOES NOT MEAN: setting KNOMIT_HOME (or KNOMIT_HOME plus LOCALAPPDATA) isolates the server's data and single-instance lock, NOT the browser profile; and WEBVIEW2_* variables are not a way to isolate or instrument the desktop's webview. Not tested: whether a Wails option exists to override the path.
