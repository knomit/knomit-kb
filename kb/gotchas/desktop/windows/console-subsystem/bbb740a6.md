# AttachConsole(ATTACH_PARENT_PROCESS) SUCCEEDS even when the shell already gave the process a working redirected stdout — so a GUI-subsystem binary must decide from the HANDLE, not the attach result, or `prog.exe --version > out.txt` silently writes an empty file

Measured on knomit-desktop.exe (linked `-H windowsgui`) on Windows 10, launched three ways:

| launch | STD_OUTPUT_HANDLE | GetFileType | AttachConsole(PARENT) |
|---|---|---|---|
| no redirection | `0x0` | 0 = FILE_TYPE_UNKNOWN | **succeeds** |
| `prog.exe > out.txt` | valid | 1 = FILE_TYPE_DISK | **succeeds** |
| `prog.exe \| something` | valid | 3 = FILE_TYPE_PIPE | **succeeds** |

Two separate surprises, and both are needed to get this right:

1. **A GUI-subsystem process DOES inherit a working stdout when the shell redirects one.** The common belief that `-H windowsgui` means "output is always lost" is false. Only the unredirected row is broken; there, Go's `os.Stdout` wraps handle `0x0` and every write fails with "The handle is invalid".

2. **AttachConsole's return value does not discriminate the rows.** It returns success in all three, because the parent (cmd.exe, pwsh) has a console in all three. It fails only when there is genuinely no parent console (Explorer, tray, login item) or when the process already has one (a CONSOLE-subsystem binary gets ERROR_ACCESS_DENIED).

CONSEQUENCE: the repair must be gated per stream on whether that stream's handle is usable — `os.Stdout.Stat() != nil` is the cheap test, since it calls GetFileType underneath. Code that instead does `if AttachConsole(...) { os.Stdout = CONOUT$ }` unconditionally will, for the two redirected rows, send output to a console nobody is watching and leave the file or pipe EMPTY. That is a silent wrong answer, not a visible failure, and it defeats every script and CI step that captures the version.

Also measured: AttachConsole by itself repoints the process's OS-level STD_OUTPUT_HANDLE to the console (observed `0x160` -> `0x174`), but Go captured its handle at runtime init, so `os.Stdout` keeps the original and Go-level writes are unaffected either way. Repairing the Go side therefore requires explicitly opening `CONOUT$` and assigning `os.Stdout`/`os.Stderr`.

WHAT THIS DOES NOT MEAN: it is not "never attach a console". The unredirected row is real and is the case a human hits typing `knomit-desktop.exe --version` at a prompt; without the attach that prints nowhere. Verified with a forced-failure control — a GUI binary that only calls `fmt.Println` produced nothing in the console screen buffer, while the guarded implementation printed the version there.
