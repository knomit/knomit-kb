# A GUI-subsystem (-H windowsgui) binary has TWO separate output traps: AttachConsole succeeds even when stdout is already a valid redirect (so guard on the HANDLE, not the attach), and PowerShell's native `>` drops the output entirely no matter what the program does

Measured on knomit-desktop.exe (linked `-H windowsgui`) on Windows 10, bytes landing in the destination, 3 runs each:

| launch | STD_OUTPUT_HANDLE | GetFileType | AttachConsole | bytes |
|---|---|---|---|---|
| bare, no redirection | `0x0` | 0 = UNKNOWN | succeeds | n/a (goes to console) |
| cmd.exe `> out.txt` | valid | 1 = DISK | succeeds | 15, 15, 15 |
| PowerShell `\| Set-Content out.txt` | valid | 3 = PIPE | succeeds | 16, 16, 16 |
| PowerShell `> out.txt` (5.1 AND 7.x) | valid | 3 = PIPE | succeeds | **0, 0, 0** |

**TRAP 1 — the attach is not the signal.** AttachConsole(ATTACH_PARENT_PROCESS) returns SUCCESS in every row above, because the parent shell has a console in every row. Only the bare row has an unusable stdout; a GUI-subsystem process DOES inherit a working stdout when the shell redirects one. It fails only when there is genuinely no parent console (Explorer, tray, login item) or when the process already has one (a CONSOLE-subsystem binary gets ERROR_ACCESS_DENIED).

CONSEQUENCE: gate the repair PER STREAM on whether that stream's handle is usable — `os.Stdout.Stat() != nil` is the cheap test, since it calls GetFileType underneath. Code that instead does `if AttachConsole(...) { os.Stdout = CONOUT$ }` unconditionally sends cmd's `> out.txt` to a console nobody is watching and leaves the file EMPTY. Silent wrong answer, not a visible failure.

Also: AttachConsole by itself repoints the process's OS-level STD_OUTPUT_HANDLE to the console (observed `0x160` -> `0x174`), but Go captured its handle at runtime init, so `os.Stdout` keeps the original. Repairing the Go side therefore requires explicitly opening `CONOUT$` and assigning `os.Stdout`/`os.Stderr`.

**TRAP 2 — PowerShell's `>` is unfixable from inside the program.** PowerShell does not wait on a GUI-subsystem child: it gives it a PIPE rather than the file handle and closes the read end without draining it, so the bytes are discarded whether or not the write reports success. This is NOT the same bug as trap 1 and no code change fixes it — CONOUT$ would not put the bytes in the file either. Control that isolates it: the same shells redirect a CONSOLE-subsystem binary (knomit-okf.exe) to a file correctly (ps5.1 56 bytes, pwsh7 26, cmd 26). It is PowerShell's handling of GUI children and applies to ANY `-H windowsgui` program.

CONSEQUENCE: document `| Set-Content file` or `cmd /c "... > file"` as the way to capture output from a GUI-subsystem binary in PowerShell. Any script or CI step that captures such a binary's `--version` with a native `>` gets an empty file and no error.

WHAT THIS DOES NOT MEAN: it is not "never attach a console". The bare row is real and is the case a human hits typing `knomit-desktop.exe --version` at a prompt; without the attach that prints nowhere. Verified with a forced-failure control — a GUI binary that only calls `fmt.Println` produced NOTHING in the console screen buffer (read back via ReadConsoleOutputCharacterW), while the guarded implementation printed the version there.

The guard's premise is pinned by TestWritableRejectsTheNullHandle / TestWritableAcceptsRedirectedStreams in console_windows_test.go, which were verified to fail on an inverted `writable()`. Those tests run only on a developer's Windows box: CI's compile gate for this file is build+vet only.
