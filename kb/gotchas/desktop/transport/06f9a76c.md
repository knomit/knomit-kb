# OPEN Windows verification for the desktop UI transport (run on macOS only): Streams latency and batching, the 304-to-500 rewrite, and the fetch-streamed POSTs streamApply/streamCommit, whose progress events buffer on Windows but whose requests complete and which the GET-only Streams adapter deliberately does not cover

Status at merge 2104fd6d; retract or rewrite this fact when a Windows run happens. The decision it qualifies is the one under kb/decisions/desktop/ui-transport. The reviewer's ruling (verdict on #487/#488): this is an item for the Windows verification list, NOT a defect of #488.

WHAT IS DERIVED FROM SOURCE ONLY (Wails v3.0.0-beta.28), NOT RUN: (1) Streams on Windows: per-event latency of about one poll round trip, batches up to 1 MiB split into `more` polls without loss, a 204 every 20 s on an idle stream keeping it alive, and an upstream close within 2 s of the page closing a stream. (2) The Windows writer rewrites a 304 to a 500; no conditional request from the app was found, so it is unhandled. (3) Linux was not run either (source says it streams and cancels).

streamApply / streamCommit (web/src/api.ts): POSTs with a body that read the response incrementally (readSSEStream, res.body.getReader()) through the /api/ proxy in the asset handler; they are the only getReader users and are not EventSource. On macOS/Linux their progress events arrive as produced (by reasoning and the proxy's SSE unit test; not run in the live UI). On Windows the beta.28 writer holds the body until the handler returns, so progress would arrive in one batch at the end; the operation still completes and the final events and errors still arrive. That is degraded progress, not a failure. They are NOT on the Streams adapter because it is GET-only and path-validated (first-frame path under /api/v1/), while these POSTs carry bodies and pre-stream problem answers (409 'Repo is indexing', cancel_indexing body). Do not widen knomit-sse to carry them.

TO VERIFY ON WINDOWS: (a) progress timing in the connect-remote wizard's apply and commit; (b) a commit longer than a minute completes with no timeout or truncated final event; (c) the 409 problem-JSON path still surfaces. If the batching is unacceptable, the follow-ups are a second Stream name for POST-initiated runs, or having apply/commit return a job id that is followed over the existing event streams.

FALLBACK recorded in the design: if the Windows run of Streams disappoints, put a loopback proxy listener with a token on Windows only.

HOW TO RUN THE STREAMS PART (what the spikes prepared): the spike page driving the Wails Stream wire directly, then the real UI, on a scratch home with a port other than the live instance's; record per-event latency, close-to-upstream-drop time, a burst larger than 1 MiB (the logs backlog) and a 3-minute idle.

WHAT THIS DOES NOT MEAN: 'Windows is broken' or 'Windows works' are both unsupported; and a green Go test run on Windows proves nothing here, because the Windows tests of the proxy and streams skip at runtime (the local listener is a pipe there) and only a GOOS=windows vet of the file list was run.
