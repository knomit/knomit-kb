# MEASURED on Windows 10 (WebView2 154, Wails beta.28): a finite fetch-streamed response through the asset handler is delivered only when it ends, and Flush() returns nil so a handler cannot detect it — streamApply/streamCommit (the only getReader users in web/src/api.ts) would show wizard progress only at the end; the real wizard was not run and the Streams-or-accept decision is pending

Windows run of 2026-10-12 against the build at the #488 merge (2104fd6d): Windows 10 Pro 22H2, WebView2 runtime 154.0.4258.62, Wails v3.0.0-beta.28. The environment figures are dated support, not properties of the code; the structural claims are the buffering and the unobservable Flush.

WHAT WAS MEASURED. A synthetic route served through the SAME Wails asset handler, read with the same loop as readSSEStream (res.body.getReader(), decode, split on newline), as a finite SSE response that flushes after every event: GET with 6 events at 1 s, POST with 6 events at 1 s, POST with 36 events over 70 s. In every run NO event reached the page until the response ENDED: for the 6 s run the first event arrived at +6013 ms (per-event delays 6008, 5009, 4009, 3010, 2009, 1010, 10 ms; 7 events within 6 ms); for the 70 s run the response headers and all 36 events arrived together at +70.03 s. Nothing timed out, truncated or errored up to 70 s. The handler's http.NewResponseController(w).Flush() returned nil, NOT http.ErrNotSupported, so the handler has no signal that its flushes are being held (Windows writer buffers until the handler returns; see kb/gotchas/desktop/wails/asset-server/cf988294).

WHAT FOLLOWS FOR THE CODE. streamApply and streamCommit (web/src/api.ts) are POSTs with a body that read the response incrementally through the /api/ proxy in the asset handler; they are the only getReader users (streamTest and streamPreview already use openEventStream). They have no AbortController and no timeout. On Windows they therefore COMPLETE with the final events and errors intact, but the wizard's progress display (phases, counts) would appear only at the end, all at once. That is degraded progress, not a failure. They are NOT on the Streams adapter because it is GET-only and path-validated (first-frame path under /api/v1/), while these POSTs carry bodies and pre-stream problem answers (409 'Repo is indexing', cancel_indexing body); do not widen knomit-sse to carry them.

DECISION PENDING (not made): either (a) move apply/commit onto the Streams carrier (a second Stream name for POST-initiated runs, or have them return a job id followed over the existing event streams), or (b) accept end-only progress on Windows and document it. A person has not yet judged whether end-only progress is acceptable.

NOT VERIFIED: the real connect-to-remote wizard was NOT run (it needs a remote KB for the clone and same-root-commit check, which the Windows host lacked); the evidence is the synthetic route only. Also unverified: whether a real apply/commit longer than a minute completes without truncation in the live wizard, and that the 409 problem-JSON path still surfaces there. The proxy and streams Go tests skip at runtime on Windows (the local listener is a pipe), so a green Windows test run proves nothing about this.

WHAT THIS DOES NOT MEAN: 'streamApply/streamCommit are broken on Windows' is false (they complete); 'the wizard shows live progress on Windows' is false; and 'Windows works' is not established for the wizard even though Streams-carried event streams were measured fine (see the Windows Streams measurements fact).
