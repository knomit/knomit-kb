# OPEN: the desktop UI transport has been run on macOS only — on Windows its Streams latency and batching, the 304-to-500 rewrite and the fetch-streamed apply/commit progress (streamApply, streamCommit) are source-derived and unverified, and the latter two are known to buffer there

Status at merge 2104fd6d; retract or rewrite this fact when a Windows run happens. The decision it qualifies is the one under kb/decisions/desktop/ui-transport.

WHAT IS DERIVED FROM SOURCE ONLY (Wails v3.0.0-beta.28), NOT RUN: (1) Streams on Windows: per-event latency of about one poll round trip, batches up to 1 MiB split into `more` polls without loss, a 204 every 20 s on an idle stream keeping it alive, and an upstream close within 2 s of the page closing a stream. (2) The Windows writer rewrites a 304 to a 500; no conditional request from the app was found, so it is unhandled. (3) Linux was not run either (source says it streams and cancels).

KNOWN GAP (not in the six EventSource sites, so not on the Streams adapter): web/src/api.ts streamApply and streamCommit POST with fetch and read the response body incrementally (readSSEStream, res.body.getReader()) through the /api/ proxy in the asset handler. On macOS/Linux those progress events arrive as produced; the Windows writer holds the body until the handler returns, so there the progress arrives only at the end (the request still completes). A follow-up must move them onto a Stream or give the Windows path another carrier.

FALLBACK recorded in the design: if the Windows run of Streams disappoints, put a loopback proxy listener with a token on Windows only.

HOW TO RUN IT (what the spikes prepared): the spike page driving the Wails Stream wire directly, then the real UI, on a scratch home with a port other than the live instance's; record per-event latency, close-to-upstream-drop time, a burst larger than 1 MiB (the logs backlog) and a 3-minute idle.

WHAT THIS DOES NOT MEAN: "Windows is broken" or "Windows works" are both unsupported; and a green Go test run on Windows proves nothing here, because the Windows tests of the proxy and streams skip at runtime (the local listener is a pipe there) and only a GOOS=windows vet of the file list was run.
