# RESOLVED by #509 (PR #754): the Wails Windows asset handler buffers a streamed response until the handler returns (beta.28 measured; still true on v3.0.0 GA, where Flush now returns http.ErrNotSupported), so apply/commit progress streamed on their POST arrived only at the end; they now answer 202 with an events link followed as a GET event stream

STATUS (2026-11-03, issue #509, PR #754): RESOLVED for the connect wizard. apply and commit no longer stream on their POST. The POST starts the run and answers 202 with `_links.events` (and the same Location), `.../origin-sessions/{id}/apply/events` or `/commit/events`, which the page follows with openEventStream (a GET event stream, carried by the knomit-sse Wails Stream on the desktop). See kb/decisions/web/origin-sessions/apply-commit-events-link/d8e11bf4.md and kb/architecture/web/origin-sessions/runs (the run/log mechanism). Live progress on the real Windows desktop still needs a person to confirm (agent sessions on the dev box have no desktop).

WAILS v3.0.0 GA (re-checked 2026-11 in the module cache, internal/assetserver/webview/responsewriter_windows.go): Write still accumulates into an in-memory buffer handed to WebView2 only in Finish, after the handler returns; the source itself says a streaming response cannot work on Windows. What changed since beta.28: the writer no longer implements http.Flusher, so http.NewResponseController(w).Flush() returns http.ErrNotSupported (on beta.28 it returned nil). A handler can now DETECT that it cannot stream, but still cannot stream.

ORIGINAL MEASUREMENT (Windows 10 Pro 22H2, WebView2 154.0.4258.62, Wails v3.0.0-beta.28, build at #488 merge 2104fd6d, 2026-10-12): a synthetic route through the same asset handler, read with res.body.getReader(), finite SSE flushing after every event: GET 6 events at 1 s, POST 6 events at 1 s, POST 36 events over 70 s. NO event reached the page until the response ENDED (6 s run: first event at +6013 ms; 70 s run: headers and all 36 events at +70.03 s). Nothing timed out or truncated up to 70 s.

CONSEQUENCE FOR NEW CODE: any UI feature whose progress or live data comes on a streamed response through the desktop asset handler (POST or GET) is end-only on Windows. Give it a GET event stream opened with openEventStream; for an action with a body, start it with a POST that returns a link (the #509 pattern), never a GET that starts the write (EventSource and knomit-sse reconnect, which would re-run it). Do not widen knomit-sse to carry POST bodies.

WHAT THIS DOES NOT MEAN: it does not mean every streamed POST in web/src is fixed (materializeApi.ts still reads a download with getReader; a download completes, it only loses incremental progress on Windows); it does not mean Wails fixed the buffering (it did not, as of v3.0.0 GA); and 'Flush returns nil' is no longer true on GA. The desktop proxy and streams Go tests skip at runtime on Windows (the local listener is a pipe), so a green Windows test run proves nothing about this.
