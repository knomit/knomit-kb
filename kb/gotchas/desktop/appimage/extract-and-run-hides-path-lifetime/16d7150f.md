# APPIMAGE_EXTRACT_AND_RUN=1 leaves a PERSISTENT /tmp/appimage_extracted_<hash>/ dir, so it cannot reproduce any bug about AppImage paths vanishing — only a real FUSE mount can

Verified 2026-07-29 on the `knomit-dev` OrbStack VM (Ubuntu 26.04 aarch64) while checking the `tools/desktop/bundled.go` copy-instead-of-symlink fix.

An AppImage has two execution modes with **materially different path lifetimes**:

- **Real FUSE mount** (default): payload appears at `/tmp/.mount_<Name><random>/`, and that mount is **torn down when the process exits**. Any absolute path into it becomes dangling.
- **`APPIMAGE_EXTRACT_AND_RUN=1`** (the fallback for FUSE-less hosts, and the one CI/containers usually take): payload is unpacked to `/tmp/appimage_extracted_<content-hash>/`, which is a **plain directory that SURVIVES process exit** and is reused across runs of the same build.

**The consequence a tester must act on:** any test about AppImage path lifetime — dangling symlinks, cached absolute paths, PID files, registered launcher paths — passes vacuously under `APPIMAGE_EXTRACT_AND_RUN=1` and proves nothing. Running the PRE-FIX knomit build that way showed `~/.knomit/bin/knomit-bridge -> /tmp/appimage_extracted_11bb.../usr/bin/knomit-bridge` with the target **still present** and `knomit-okf version` succeeding. The identical binary run with real FUSE left `-> /tmp/.mount_KnomitgFAdkC/usr/bin/knomit-okf` and failed with `No such file or directory`.

So: to test path lifetime you must install `fuse3` and run the AppImage WITHOUT the env var. Docker containers typically lack `/dev/fuse`; the OrbStack VM has it.

**What this fact does NOT mean:** `APPIMAGE_EXTRACT_AND_RUN=1` is not broken or wrong — it is the correct documented fallback for hosts without FUSE, and knomit's release notes recommend it. The point is narrower: it is not a substitute for FUSE *when the thing under test is how long a path lives*. It is perfectly fine for testing that an AppImage merely launches.
