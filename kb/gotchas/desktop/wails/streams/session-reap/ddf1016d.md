# Wails v3.0.0 reaps a stream session after 10 min without a poll and silently recreates it on the page's next poll with no close for the old connections, so a WailsEventSource (and the one chat page stream) stays OPEN with nothing behind it and never reconnects

MECHANISM (Wails v3.0.0 pkg/application, confirmed by a scratch test against the module source): a stream session is ONE page load in one window; every Stream the page opens is multiplexed over its single held poll (stream_session.go). reapStale closes a session whose lastSeen (set by each poll/open) is older than streamSessionTTL (60 s) with no connections, or streamSessionGrace (10 min) WITH connections. Closing it cancels every StreamConn's context (so knomit's serveSSEStream returns, the upstream GET is cancelled and the server's chat page stream detaches: detachPage starts the 60 s grace of every chat of the owner) and DISCARDS the queued frames, so no close frame reaches the page. Reaping does not retire the page generation, so the page's next poll with the same session id and generation gets a NEW empty session (sessionWithAdmission create path, 204 or frames, never 410). The page's WailsSocket objects for the old connection ids never get onclose; WailsEventSource only reconnects on onclose or an error frame, so it stays readyState OPEN forever, and chatEvents.ts's hub keeps routing to that dead stream. Every chat the page creates afterwards has no page stream at the server: it starts its grace at creation and ends with chat_end reason stream_grace exactly 60 s after chat_start, its turn having run with no client seeing an event. Only a page reload recovers.

USER INCIDENT this explains (desktop 0.5.3, 2026-11-08): three chats ended together at 22:43:06 UTC (detach at 22:42:06, consistent with a reap on the 20 s sweep after >10 min without a poll), then every new chat from 23:22 on showed No response yet with the counter running and vanished after 60 s with stream_grace. The TRIGGER (why the page stopped polling for >10 min: hidden/occluded window or sleep suspending the webview's JS) is inferred, not observed.

CONSEQUENCE: any knomit stream over knomit-sse can be orphaned this way, not only the chat stream; the page cannot rely on onclose for liveness on the desktop. The fix gives the desktop leg its own heartbeat (see the fix-chat-stream-attach PR).

WHAT THIS DOES NOT MEAN: it is not the browser's 6 HTTP/1.1 connections per origin (the desktop uses no browser HTTP for SSE, and chat already uses one page stream); and the 16 sessions per window cap is about page loads, not streams, so opening many chats does not approach it.
