# Wails v3.0.0 reaps a stream session after 10 min without a poll and silently recreates it on the page's next poll with no close for the old connections, so a WailsEventSource (and the one chat page stream) stays OPEN with nothing behind it and never reconnects on its own (the page loses events; since fix-chat-outlives-page it no longer loses chats)

MECHANISM (Wails v3.0.0 pkg/application, confirmed by a scratch test against the module source): a stream session is ONE page load in one window; every Stream the page opens is multiplexed over its single held poll (stream_session.go). reapStale (stream.go; streamSessionTTL = 3 * streamHoldTimeout, swept every streamHoldTimeout = 20 s) closes a session whose lastSeen (set by each poll/open) is older than streamSessionTTL (60 s) with no connections, or streamSessionGrace (10 min) WITH connections. Closing it cancels every StreamConn's context (so knomit's serveSSEStream returns, the upstream GET is cancelled and the server's chat page stream detaches; until fix-chat-outlives-page detachPage then started the 60 s grace of every chat of the owner, and since then it ends nothing) and DISCARDS the queued frames, so no close frame reaches the page. Reaping does not retire the page generation, so the page's next poll with the same session id and generation gets a NEW empty session (sessionWithAdmission create path, 204 or frames, never 410). The page's WailsSocket objects for the old connection ids never get onclose; WailsEventSource only reconnects on onclose or an error frame, so it stays readyState OPEN forever, and chatEvents.ts's hub keeps routing to that dead stream. Every chat the page creates afterwards has no page stream at the server, so its turn runs with no client seeing an event; until fix-chat-outlives-page it also started its grace at creation and ended with chat_end reason stream_grace exactly 60 s after chat_start. Since that change (kb/decisions/chat/lifetime/outlives-page/bd2a87a7.md) a chat ends only on DELETE or server stop, so a reaped stream costs the page its EVENTS, never its chats: the reopen (below) or a reload picks every chat up again.

USER INCIDENT this explains (desktop 0.5.3, 2026-11-08): three chats ended together at 22:43:06 UTC (detach at 22:42:06, consistent with a reap on the 20 s sweep after >10 min without a poll), then every new chat from 23:22 on showed No response yet with the counter running and vanished after 60 s with stream_grace. The TRIGGER (why the page stopped polling for >10 min: hidden/occluded window or sleep suspending the webview's JS) is inferred, not observed.

The incident above was under the old grace; with the current server the same reap leaves the chats listed.

CONSEQUENCE: any knomit stream over knomit-sse can be orphaned this way, not only the chat stream; the page cannot rely on onclose for liveness on the desktop. The fix (PR #809) gives the desktop leg its own heartbeat: kb/invariants/desktop/ui-transport/stream-liveness/28bc2bd0.md.

WHAT THIS DOES NOT MEAN: it is not the browser's 6 HTTP/1.1 connections per origin (the desktop uses no browser HTTP for SSE, and chat already uses one page stream); and the 16 sessions per window cap is about page loads, not streams, so opening many chats does not approach it.
