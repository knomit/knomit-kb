# A Wails macOS status item is created blank unless SetIcon ran before Run

Wails v3 alpha.98's macosSystemTray.run() installs the tray image only under `if s.icon != nil` — it reads whatever the SystemTray already holds at the moment NSApplication builds the status item. A SystemTray whose first SetIcon lands later (e.g. from an events.Common.ApplicationStarted hook) therefore sits on the menu bar as an EMPTY SLOT until that hook fires.

Consequence: newTrayIconState (tools/desktop/trayicon.go) calls t.apply() synchronously before returning, so the status item is born wearing art. This is safe pre-Run because SystemTray.SetIcon with a nil impl is just a field write — it does NOT dispatch to the main thread, so there is no NSApplication to race.

The tradeoff this accepts: on macOS the initial light/dark pick comes from the AppleInterfaceStyle user default, which reports light even in dark mode until launching finishes, so the first glyph may be mistoned. watchTrayAppearance re-applies on ApplicationStarted and corrects it. A briefly wrong tone beats a blank menu bar — do not "fix" the mistoning by removing the synchronous apply.
