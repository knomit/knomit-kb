# Wails v3.0.0's (and beta.28's) Windows asset response writer still buffers every response until the handler returns, so SSE through the asset handler delivers nothing there — Wails Streams work on Windows only because each held poll answer COMPLETES (parked until a frame exists, up to 1 MiB per answer, 204 after 20 s)

Read from the module source at github.com/wailsapp/wails/v3 v3.0.0 (pinned by go.mod at 9e8bdef9; first written against v3.0.0-beta.28 and re-read at v3.0.0, where the writer, the held-poll mechanism and the constants below are unchanged); line numbers are dated support, the structural claims are what to re-check on a Wails bump. ONE CORRECTION at v3.0.0: the Windows writer now deliberately does not implement http.Flusher, so http.NewResponseController(w).Flush() returns http.ErrNotSupported there; the measurement (b) below that it returned nil was true of beta.28 only, and a handler MAY now detect that its flushes are held (kb/gotchas/desktop/transport/06f9a76c already records this). REPRODUCED on Windows 10 22H2 with WebView2 154.0.4258.62 on 2026-10-12 (the claims below that say 'unverified on Windows' are superseded by the appended paragraph).

THE WRITER. internal/assetserver/webview/responsewriter_windows.go says outright that it does not implement http.Flusher: Write appends to an in-memory bytes.Buffer and Finish hands the whole body to WebView2 once (PutByteContent). So an SSE handler behind the asset handler, even with ReverseProxy FlushInterval -1, flushes into that buffer and the page receives nothing until the handler returns, which for SSE is never. macOS (responsewriter_darwin.go) hands each Write to the scheme task immediately, and Linux (responsewriter_linux.go) writes into a pipe WebKit reads: both stream. No release note beta.4..beta.28 says the Windows writer streams. The same writer rewrites a 304 to a 500 (the app sends no conditional headers that were found; unverified on Windows).

WHY STREAMS WORK THERE. A Wails Stream never asks the writer to stream. Go-to-JS is ONE parked GET per window (serveStreamPoll in pkg/application/stream_transport.go): it blocks in awaitFrames (stream_session.go) until at least one frame exists, drains a batch capped at streamMaxResponseBytes = 1 MiB (stream.go; its comment says it exists because the Windows writer accumulates the whole body), writes it with a Content-Length and RETURNS, which is exactly what makes the Windows writer deliver. With nothing to send it returns 204 after streamHoldTimeout = 20 s. The JS client immediately issues the next poll, so the round trip is the batching window. JS-to-Go is an ordinary POST.

CONSEQUENCES. Anything that must stream to the webview on Windows has to be a Wails Stream, not a streamed asset-handler response. Delivery on Windows costs one completed HTTP response per batch.

WHAT THIS DOES NOT MEAN: "Wails now supports streaming" is false for the Windows asset handler; "Streams are zero-latency on Windows" is false (measured about 5 ms median per event, see the Windows Streams measurements fact) and by construction latency is one poll round trip with bursts batched up to 1 MiB; and macOS/Linux do not NEED Streams for SSE (the asset handler streams per event there, measured on macOS at 0-1 ms and byte-exact for a 250 KB GET), the desktop uses Streams everywhere only to keep one transport. Request cancellation is wired on all three platforms at beta.28 (not re-verified at v3.0.0) (macOS cancelURLRequest, Linux request_lifetime_linux.go, Windows a CDP-based tracker; confirmed by measurement on macOS only), which reverses the beta.3 finding that an aborted request never cancels the handler context.

WINDOWS MEASUREMENT (2026-10-12, build at the #488 merge 2104fd6d, Wails v3.0.0-beta.28; WebView2 version is dated support). (a) A finite SSE response that flushes per event through the asset handler is delivered only when the handler returns: 6 s and 70 s runs both delivered every event at the end, with no timeout or truncation. (b) at beta.28, http.NewResponseController(w).Flush() on that writer returned nil, NOT http.ErrNotSupported, so a handler could not detect that its flushes were being held (superseded at v3.0.0: it returns ErrNotSupported, see the correction above); still do not gate behaviour on Flush's error. (c) A handler-written 304 (with and without If-None-Match from the page) reached the page as 500: CONFIRMED, no longer only read from source. Nothing the app serves today produces a 304 (no ETag or Last-Modified on /api/v1/openapi.yaml or /), so the rewrite matters only if a conditional-capable response is ever added on the asset path. (d) Streams worked as designed on the same machine; see the Windows Streams measurements fact. Consequence for streamApply/streamCommit: see kb/gotchas/desktop/transport/06f9a76c.
