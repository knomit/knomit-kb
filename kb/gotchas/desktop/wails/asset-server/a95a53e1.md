# Wails stamps x-wails-window-id (and x-wails-window-name when the window has one) on every asset-handler request, so the /api/ proxy must strip every x-wails-* header and Origin before dialing the server — the server then sees the desktop process, never the calling window

At v3.0.0-beta.28 pkg/application/application.go (webViewAssetRequest.Header, around L388-393) clones the request headers and sets x-wails-window-id always and x-wails-window-name only when the window's name is non-empty (unnamed windows are named window-<id> in webview_window.go, so it is always set in practice). Behind apiProxy those headers would be forwarded to the server unless removed.

WHAT apiProxy DOES (Rewrite in tools/desktop/uiproxy.go): deletes Origin and every header whose lower-cased name starts with "x-wails-", and sets the outgoing Host to localhost. Origin goes because the server's origin checks apply to TCP peers (kb b1f866c1) and a socket peer skips them; the wails:// origin means nothing there. Pinned by TestAPIProxy_StripsWailsAndOriginHeadersAndRewritesHost.

CONSEQUENCE: the server cannot tell which window made a call; every proxied request arrives as the desktop process's verified local peer on the socket/pipe. Per-window authority for UI-path traffic, if ever needed, has to be decided on the desktop side (a Wails Stream handler has c.Window(); apiProxy has the injected header before stripping it). Today no such gate exists: any window, Settings included, can reach /api/ and open knomit-sse, which only carries GET reads under /api/v1/ that the page could already fetch.

WHAT THIS DOES NOT MEAN: the Settings-only gate on NativeService bindings (kb a46bbb69) is untouched, since bindings go through /wails/runtime, not /api/, and still read the headers in-process; stripping upstream does not weaken it.
