# Every exported NativeService method is callable from the desktop's MAIN window too, not only from Settings: Wails v3 bindings are app-global and both windows share the wails://localhost asset origin. A binding CAN tell its caller apart, because Wails injects the caller window's id and name natively

# Every NativeService method is callable from the main window, and a binding can identify its caller window

This was established by reading. No real webview was run. It holds at `wails/v3 v3.0.0-beta.3` (`go.mod`) and knomit `e8a8f1e1`.

**Both windows are on one origin.** The desktop's main window (the shared `web/` SPA, loaded by `window.SetURL("/")`) and the Settings window (`/desktop/settings.html`) are served by the SAME Wails asset handler: `application.Options.Assets.Handler: configInjectingHandler(…)` in `tools/desktop/app.go`. So they share the origin `wails://localhost` on darwin/linux and `http://wails.localhost` on Windows.

**The main window already talks to the runtime.** It posts to `/wails/runtime` by hand, in `web/src/externalLinks.ts` for `Browser.OpenURL`.

**Nothing scopes a binding to a window.** Wails' HTTP transport dispatches any `{object, method, args}` it receives (`pkg/application/transport_http.go` `processBody`). It has no per-window or per-service allowlist. So script running in the main window can do `Call.ByName('main.NativeService.<Any>', …)`. That includes script injected through content the knowledge UI renders.

`tools/desktop/native.go` already names "a single UI XSS" as the threat model for this service. It is the reason `WriteFile` is sandboxed.

**A binding CAN authenticate its caller window.**
- `webViewAssetRequest.Header` (`pkg/application/application.go`) OVERWRITES `x-wails-window-id` and `x-wails-window-name` with the values of the webview that actually made the request. Page script cannot spoof them.
- `messageprocessor_call.go` puts the resolved window into the call context as `ctx.Value(application.WindowKey)`.
- A bound method whose first parameter is `context.Context` receives that context. The JS call signature does not change.

**Who cannot reach bindings.** Local processes and remote peers cannot. The asset server is an in-process scheme handler, not a TCP port. The desktop build uses only `-tags desktop` (`Makefile` `DESKTOP_BUILD`), so Wails' `server` mode (`//go:build server`) and `mcp` mode (`//go:build mcp`) are not linked. Adding either tag would change this.

**What to do with this.** A binding that mutates trust or network exposure must check that the caller is the Settings window, by `Name()` or by identity against the `auxWindows.settings` pointer. Such bindings include installing a fleet bundle, and saving a `[tls].addr` that opens a network port. Read-only bindings, such as the public key line, need no check.

**WHAT THIS DOES NOT MEAN**
- "Wails bindings are exposed over HTTP." They are not. Keeping trust-material writes off `a.Handler()` routes is still right, because those routes are also served on the mTLS listener and by `knomit serve`.
- "Only the Settings UI can call NativeService because only it imports `@wailsio/runtime` Call." Importing the runtime is not required. A bare `fetch` suffices, as `externalLinks.ts` shows.
