# `make desktop` replaces the artefact the user's RUNNING desktop was launched from — on macOS it deletes the whole .app bundle (killing the desktop AND its supervised server child), on Windows it overwrites knomit-desktop.exe without killing the process — and the single-instance lock is PER HOME: flock on `desktop.lock` beside the home's server.json (`<StateDir>/desktop.lock` for the DEFAULT home, `<home>/desktop.lock` otherwise), a `Local\knomit-desktop-<hash of that path>` named mutex on Windows (no file), so a second desktop can run alongside on any other KNOMIT_HOME

THREE FACTS THAT COMPOSE INTO A TRAP, and the third removes the obvious escape.

ONE: on darwin, `make desktop` runs `desktop-app-macos`, whose FIRST line is `rm -rf $(APP)`, where `APP := dist/$(PLATFORM)/Knomit.app`. It then rebuilds the desktop binary, `kb` and `knomit-okf` into that bundle.

TWO: on a development box the user's desktop app is typically launched FROM that bundle inside the checkout, not from a copy. Measured: the running process's command was `<checkout>/dist/darwin-arm64/Knomit.app/Contents/MacOS/knomit-desktop` — the same path the make target deletes. That desktop process IS the lens server. And `.mcp.json` points the agent's MCP client at `${CLAUDE_PROJECT_DIR}/dist/kb`, in the same tree. So an agent session that runs `make desktop` is destroying and replacing the server behind its OWN knomit tools, mid-session — the tools it needs to write facts and to commit its experiment.

THREE (TRUE ONLY FOR THE DEFAULT HOME since knomit#493, merge 9860c726 - see 'CHANGED BY #493' at the end): you cannot dodge it by starting a second desktop alongside the user's on the default home. `run` calls `singleinstance.Acquire(paths.LockfilePath())` and prints "knomit-desktop is already running" if it cannot take the lock. `LockfilePath` is `<StateDir>/server.json`, and `StateDir` resolves from the per-USER OS state directory — `KNOMIT_HOME` does not influence it. Pointing a second instance at a scratch `KNOMIT_HOME` therefore isolates its DATA and not its lock: it still refuses to start. One desktop per user while the state dir is the default (darwin as measured; Windows see the WINDOWS section below).

CONSEQUENCES for any task that must verify desktop behaviour with a real build:

- The user's running app has to be STOPPED first; there is no side-by-side option. Plan for that interruption and get agreement, rather than discovering it when the build exits "already running".
- Write any knomit facts into the experiment BEFORE the rebuild, not after. A rebuild that fails, or a restarted app that does not come back, leaves the session unable to record what it just learned — the knowledge is lost at exactly the moment it was earned.
- A scratch `KNOMIT_HOME` is still worth using to keep the real `control.db` out of the test, but know what it buys: data isolation, not instance isolation.

THE GENERAL SHAPE, worth carrying past this repo: when the artefact under test is ALSO the tooling the tester runs on, "rebuild and verify" is not a read-only act. Check what the build target deletes, and what is currently running out of that path, before invoking it.

WINDOWS (measured 2026-10-12 on Windows 10 22H2, build at the #488 merge 2104fd6d; the machine is dated support, the mechanism is the claim). Two of the statements above are different there:

(1) NOTHING IS DELETED OR KILLED. The non-darwin branch of `make desktop` (Makefile) runs `go build ... -o $(DIST)/knomit-desktop$(EXE)`, which on Windows overwrote the exe the user's running desktop was started from. Windows allowed it; the running process kept running from memory, unaffected, while the on-disk binary became the new build. The next launch uses the new binary. So the 'rebuilding destroys the server behind your own tools' trap does not bite on Windows, but the running app and the file on disk now DIFFER, and `kb.exe` and `knomit-okf.exe` are rebuilt too.

(2) A SECOND DESKTOP CAN RUN BESIDE THE USER'S, if the state dir is redirected as well. The single-instance lock is `<StateDir>/server.json`, and on Windows StateDir is `%LOCALAPPDATA%\knomit` (userdirs_windows.go), which `KNOMIT_HOME` does not influence. Setting BOTH `KNOMIT_HOME` and `LOCALAPPDATA` to scratch directories let a scratch desktop start next to the user's and serve its own pipe; setting only `KNOMIT_HOME` leaves the lock shared (the point made above). Also redirected: server.json, so `kb` finds the scratch server via the lockfile only under the same two variables.

WHAT THIS DOES NOT MEAN: 'on Windows rebuilding is safe' is false for the user's data and tooling (the next restart picks up whatever was built, mid-session); 'KNOMIT_HOME isolates a scratch desktop' is false on every platform; and 'a second desktop is impossible' holds only with the default state dir. For a verification copy that must not share the user's WebView2 profile, see the WebView2 profile fact (profile path follows the exe file name).

CHANGED BY #493 (merge 9860c726): the desktop now passes config.LockfilePath() to singleinstance.Acquire (tools/desktop/app.go). That resolves through ResolveHome: the DEFAULT home keeps <StateDir>/server.json (byte-for-byte the old path, so everything above still holds there), while any other KNOMIT_HOME/KNOMIT_REPO gets <home>/server.json. So a second desktop CAN start beside the user's when it runs on a non-default KNOMIT_HOME - KNOMIT_HOME alone now isolates its lock as well as its data, on every platform, and the Windows 'both KNOMIT_HOME and LOCALAPPDATA' requirement in (2) above applies only to a scratch desktop on the default home. What this does NOT mean: the user's own running app still has to be stopped before `make desktop` replaces its artefact (the rebuild trap is unchanged); a second desktop on the same home is still refused, and the socket flock plus the #488 boot failure back-stop it; the WebView2 profile still follows the exe file name on Windows. Why the single-instance check ignores schema-2 files written by `knomit serve`: kb/gotchas/desktop/single-instance.

CHANGED BY #503 (merge 8be999a0, 2026-10-12) - read this before the paragraphs above: THE LOCK IS NO LONGER server.json. tools/desktop/internal/singleinstance now takes an OS lock that dies with the process: flock(2) on a file named `desktop.lock` in the directory of config.LockfilePathFor(home) (so `<StateDir>/desktop.lock` for the DEFAULT home, `<home>/desktop.lock` for any other KNOMIT_HOME/KNOMIT_REPO), and on Windows a named mutex `Local\knomit-desktop-<first 8 bytes, hex, of sha256(lower(clean(that path)))>` (`Local\` is already per logon session). It does NOT read server.json or any pid, so the schema-2 exemption for a `knomit serve` file is gone; there is no stale-lock cleanup either, the OS releases the lock when the holder dies, and the handle is not inherited by the supervised child. Acquire is still synchronous before any UI. A second desktop on the SAME home prints 'knomit-desktop is already running.' and exits 0; a desktop on another home runs beside it (verified on macOS and on Windows: two desktops and two servers at once). On Windows there is NO desktop.lock FILE at all - the mutex is the whole lock, so 'delete the lock file' has nothing to delete there.
What this changes in the trap above: (1) the 'state dir is not influenced by KNOMIT_HOME' statements apply only to the DEFAULT home; a scratch KNOMIT_HOME alone isolates the lock on every platform (the Windows 'both KNOMIT_HOME and LOCALAPPDATA' requirement is gone for scratch homes). (2) On macOS `make desktop` deleting the running bundle now kills the running desktop AND the `knomit` child it supervises (they run from the same .app; the server follows the desktop's death through its stdin lifeline), so the 'destroys the server behind your own tools' trap is unchanged in effect. (3) On Windows the rebuild still overwrites the exe without killing it. A running supervised child keeps running the old `knomit` binary until the desktop is restarted.
WHAT THIS DOES NOT MEAN: the desktop does not own the home exclusively - a `knomit serve` started by hand on the same home is ATTACHED to, not refused (kb/decisions/desktop/supervisor); and the WebView2 profile still follows the exe file name on Windows.
