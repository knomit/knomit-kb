# Installing a bundle never STARTS an mTLS listener by itself: a listener already up adopts the new files, one that was off at boot for lack of a certificate stays off until a restart in the desktop's own boot (desktop Settings offers the restart) but, for `knomit serve`, a RELOAD (SIGHUP, `knomit reload`) starts it since #497

`app.OpenTLSServer` decides at BOOT whether there is a TLS listener at all. With `[tls].addr` set and no `instance.crt` in `[tls].dir`, it returns (nil, nil, nil), logs a WARN, and no `pki.Server` or reloader exists. An install that happens later, from the desktop's Settings window or from `knomit identity install` against a running `knomit serve`, writes the files and starts nothing.

When a listener IS running, its reloader adopts a new set of `instance.crt`, `root.crt` and `crl.pem` that verifies together within the recheck interval. This holds for a replaced root too, so no restart is needed.

The desktop makes the boot's decision visible. `bootServer` records a `tlsState`:
- listening: the bound address;
- configured but not listening: `no_certificate`, or `addr_in_use` for `app.ErrTLSAddrInUse`;
- off.

It records this at the branches it already takes, so the state cannot disagree with the WARN in the log. `run()` publishes the state to `NativeService`, and `GetIdentity` returns it with the CURRENT `[tls].addr` (`configuredNow`). The Settings UI offers its one restart when an install succeeds while a listener is wanted (`configuredNow` is set) but not listening (`installNeedsRestart` in `ui/src/fleet.ts`).

Misreading to avoid: the CLI's post-install line "a running `knomit serve` picks this up within its recheck interval" is true ONLY when serve's listener was already up. A serve that booted with an addr but no certificate needs a restart too. That wording predates #256 and is unchanged.

OBSOLETE FOR `knomit serve` SINCE knomit#497 (merge 4a9018c4): a reload (SIGHUP, `knomit reload`, the Windows reload event) calls Listeners.Apply, which starts the mTLS listener that was off for lack of a certificate once the files are there, and adopts a changed [tls].addr or [tls].dir (tested: TestApply_TLSAddAndDrop, TLSAddrWithoutACertificateIsReported, TLSRebindMovesTheListenerAndKeepsTheOldOnFailure). The install itself still starts nothing; the sequence for a serve that booted without a certificate is install, then reload, and no restart. The reason, when it does not come up, is in server.json listeners.tls.reason (no_certificate, addr_in_use, tls_failed). STILL TRUE until the desktop's boot moves to knomit serve (PR 5): the desktop's in-process boot decides once, tlsState and installNeedsRestart are unchanged, and Settings still offers the restart. The CLI line 'a running knomit serve picks this up within its recheck interval' remains true only for an already-up listener; for a serve that booted without a certificate say 'run knomit reload'. Details: kb/decisions/serve/reload/f44e4370.md.

NOTE (PR #503, merge 8be999a0): the desktop no longer has its own boot (bootServer, tlsState, tlsNoCertificate, tlsAddrInUse are deleted). The server is a separate `knomit serve --supervised` process, so 'the desktop's own boot' above is `knomit serve`'s boot, and the 'a reload starts it' route (SIGHUP, `knomit reload`) applies to the desktop's child too. The desktop reads TLS state from server.json (`listeners.tls`, reason 'off' shown as empty) for Settings; kb/decisions/desktop/supervisor has the restart behaviour (RestartApp now restarts only the server, and refuses an attached one).
