# Installing a bundle never STARTS an mTLS listener by itself: a listener already up adopts the new files, one that was off at boot for lack of a certificate stays off until a restart in the desktop's own boot (desktop Settings offers the restart) but, for `knomit serve`, a RELOAD (SIGHUP, `knomit reload`) starts it since #497

`app.OpenTLSServer` decides at BOOT whether there is a TLS listener at all. With `[tls].addr` set and no `instance.crt` in `[tls].dir`, it returns (nil, nil, nil), logs a WARN, and no `pki.Server` or reloader exists. An install that happens later, from the desktop's Settings window or from `knomit identity install` against a running `knomit serve`, writes the files and starts nothing.

When a listener IS running, its reloader adopts a new set of `instance.crt`, `root.crt` and `crl.pem` that verifies together within the recheck interval. This holds for a replaced root too, so no restart is needed.

The desktop makes the boot's decision visible. `bootServer` records a `tlsState`:
- listening: the bound address;
- configured but not listening: `no_certificate`, or `addr_in_use` for `app.ErrTLSAddrInUse`;
- off.

It records this at the branches it already takes, so the state cannot disagree with the WARN in the log. `run()` publishes the state to `NativeService`, and `GetIdentity` returns it with the CURRENT `[tls].addr` (`configuredNow`). The Settings UI offers its one restart when an install succeeds while a listener is wanted (`configuredNow` is set) but not listening (`installNeedsRestart` in `ui/src/fleet.ts`).

Misreading to avoid: the CLI's post-install line "a running `knomit serve` picks this up within its recheck interval" is true ONLY when serve's listener was already up. A serve that booted with an addr but no certificate needs a restart too. That wording predates #256 and is unchanged.

OBSOLETE FOR `knomit serve` SINCE knomit#497 (merge 4a9018c4): a reload (SIGHUP, `knomit reload`, the Windows reload event) calls Listeners.Apply, which starts the mTLS listener that was off for lack of a certificate once the files are there, and adopts a changed [tls].addr or [tls].dir (tested: TestApply_TLSAddAndDrop, TLSAddrWithoutACertificateIsReported, TLSRebindMovesTheListenerAndKeepsTheOldOnFailure). The install itself still starts nothing; the sequence for a serve that booted without a certificate is install, then reload, and no restart. The reason, when it does not come up, is in server.json listeners.tls.reason (no_certificate, addr_in_use, tls_failed). STILL TRUE until the desktop's boot moves to knomit serve (PR 5): the desktop's in-process boot decides once, tlsState and installNeedsRestart are unchanged, and Settings still offers the restart. The CLI line 'a running knomit serve picks this up within its recheck interval' remains true only for an already-up listener; for a serve that booted without a certificate say 'run knomit reload'. Details: kb/decisions/serve/reload/f44e4370.md.

NOTE (PR #503, merge 8be999a0): the desktop no longer has its own boot (bootServer, tlsState, tlsNoCertificate, tlsAddrInUse are deleted). The server is a separate `knomit serve --supervised` process, so 'the desktop's own boot' above is `knomit serve`'s boot, and the 'a reload starts it' route (SIGHUP, `knomit reload`) applies to the desktop's child too. The desktop reads TLS state from server.json (`listeners.tls`, reason 'off' shown as empty) for Settings; kb/decisions/desktop/supervisor has the restart behaviour (RestartApp now restarts only the server, and refuses an attached one).

NOTE (PR #504, merge 1c6a0934): Settings still offers 'Restart server' after a first enrolment (installRestart), and the binding is now RestartServer, not RestartApp. Since #497 a reload starts an mTLS listener that was off for lack of a certificate, and Save reloads after every save, so the heavier restart is probably unnecessary after install; this was NOT exercised (needs a fleet bundle) and is a fix-later item from the PR 504 review, not a changed behaviour. Do not tell users a restart is required; do not remove the button on this fact alone.

NOTE (PR #518, merge 537f2019): FLEET CREATE IS A THIRD INSTALLER, AND IT SAYS NOTHING. POST /api/v1/fleet/create installs this instance's own certificate into [tls].dir (pki.InstallBundle) and starts no listener. Its pre-flight requires [tls].addr and external_addresses to be SET for a fleet hosted here, but not that the listener is open: an instance whose server booted with [tls].addr and no certificate has no mTLS listener, and after a create it still has none until a reload (`knomit reload`, SIGHUP) or restart. The response carries no reload hint (there is no CLI to print one, and the REST answer is the fleet status only; the earlier idea of a create-time hint was not built). So, in that case (server booted without a certificate), a fresh hosted-here fleet is not reachable by members until the operator reloads; with a listener already up, it adopts the new files by itself. This fact's claims above are unchanged; only the list of installers grew.

NOTE (PR #525, verified at merge commit fd991d4f): TWO MORE INSTALLERS AND ONE REMOVER. `POST /api/v1/fleet/join` installs the bundle it is given (`pki.InstallBundle`, local listener only) and, like the create, starts no listener; a running listener adopts it, one that never started still needs a reload. The `knomit identity install` CLI verb no longer exists, so the CLI line quoted above is gone. A running listener ALSO adopts an UNINSTALL: when `pki.Uninstall` (leave, decommission, a refused join's undo, the create rollback) leaves instance.crt, root.crt and crl.pem all absent, the reloader adopts an uninstalled snapshot within a tick, refuses every handshake and cuts the open connections, without a restart (kb/invariants/pki/established-connections/9928b5a7.md). A PARTIAL set keeps the last good set. Consequences: leave and decommission need no restart to take the instance out of the fleet; install, uninstall, install again (leave then rejoin) needs no restart while the listener stays up. MISREADING: 'installs adopt without restart, so uninstalls do not' is false; the adoption is symmetric for the all-present and all-absent sets only. This fact still says nothing about STARTING a listener: a join on an instance whose server booted without a certificate has no listener until a reload.

NOTE (PR #526, merge 0488c05d): the join now installs the bundle DOCUMENT it is given (POST /fleet/join takes {bundle, auth?} and reads the URL from the bundle; pki.InstallBundle still accepts the bare PEM the create and the desktop use). POST /fleet/join:check is NOT an installer: it writes the bundle into a private temporary directory, classifies against it and removes it, so it never changes [tls].dir and never affects a running listener (kb/architecture/fleet/join-check/6fba2b2c.md). A handshake refused after an uninstall is now logged as `tls_refused` (kb/invariants/pki/established-connections/9928b5a7.md). Nothing here changes the listener-start facts above.

## UPDATE (PR #528, verified at merge e417fd76): the Fleet UI says so, from GET /fleet host.listening

A fleet create, a join or Host here installs the certificate but starts no listener, so a hub master whose [tls].addr is configured can sit with host.listening false (listener_reason `no_certificate`) while members cannot join. The Fleet pages gate every "can join" / "push to it" claim on host.listening and say to restart knomit or run `knomit reload` otherwise (enroll card, Members ask card, Hosting, create Review, Host-here confirm, Settings Hosted by; text in fleetText.ts listenerNotRunning). Starting the listener automatically after the install is NOT built (PR8): pki.Server's reloader exists only for a listener that booted, and Listeners.Apply from a route is forbidden by test/archtest/reload_callers_test.go; it needs a narrow "start TLS once the files appear" path in app.Listeners. Verified live: after create and after Host here server.json said no_certificate; `knomit reload` flipped host.listening with no restart.
