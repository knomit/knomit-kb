# Installing a bundle never STARTS an mTLS listener in a running process: a listener that is already up adopts the new files by itself, but one that was off at boot for lack of a certificate stays off until a restart — which is why desktop Settings offers the restart after such an install

`app.OpenTLSServer` decides at BOOT whether there is a TLS listener at all. With `[tls].addr` set and no `instance.crt` in `[tls].dir`, it returns (nil, nil, nil), logs a WARN, and no `pki.Server` or reloader exists. An install that happens later, from the desktop's Settings window or from `knomit identity install` against a running `knomit serve`, writes the files and starts nothing.

When a listener IS running, its reloader adopts a new set of `instance.crt`, `root.crt` and `crl.pem` that verifies together within the recheck interval. This holds for a replaced root too, so no restart is needed.

The desktop makes the boot's decision visible. `bootServer` records a `tlsState`:
- listening: the bound address;
- configured but not listening: `no_certificate`, or `addr_in_use` for `app.ErrTLSAddrInUse`;
- off.

It records this at the branches it already takes, so the state cannot disagree with the WARN in the log. `run()` publishes the state to `NativeService`, and `GetIdentity` returns it with the CURRENT `[tls].addr` (`configuredNow`). The Settings UI offers its one restart when an install succeeds while a listener is wanted (`configuredNow` is set) but not listening (`installNeedsRestart` in `ui/src/fleet.ts`).

Misreading to avoid: the CLI's post-install line "a running `knomit serve` picks this up within its recheck interval" is true ONLY when serve's listener was already up. A serve that booted with an addr but no certificate needs a restart too. That wording predates #256 and is unchanged.
