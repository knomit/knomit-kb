# tools/bridge CANNOT import tools/desktop/internal/* — Go's internal rule — so any path logic the bridge, the desktop and config must agree on has to live under internal/; that shared owner is internal/config (the bridge already imports it), NOT a package of its own

Go's internal rule: a package under tools/desktop/internal/ is importable only from within tools/desktop/. tools/bridge is a sibling, so it cannot reach tools/desktop/internal/paths however much the two need to agree.

WHAT THAT COST BEFORE THE SHARED OWNER EXISTED: the bridge carried its own copy of the per-OS switch, with cases for darwin and linux only. On Windows lockfilePath() returned "unsupported platform windows", the caller logged it at Debug and fell back to the default base URL — so `kb` silently talked to the wrong port while the desktop's lockfile sat unread in %LOCALAPPDATA%\knomit. A silent copy that drifts, which is the shape the internal rule pushes you into if you let it.

THE OWNER IS internal/config, not a dedicated package. An interim revision of this fact named internal/apppaths; that package has been DELETED. config.StateDir / config.DefaultHome / config.LockfilePath are the shared entry points now, and the OS half beneath them is internal/platform/userdirs.

WHY config IS THE RIGHT OWNER RATHER THAN A NEW PACKAGE — and the measurement that settles it: the bridge ALREADY imported internal/config before this move. Measured with `go list -deps ./tools/bridge` before and after, its knomit-package set SHRANK by exactly one entry (apppaths) and gained nothing. The "keep the bridge light" concern that would argue for a separate package does not apply, because the dependency was already paid. config is also the natural owner on its own terms: it holds Config.Home, and the default is the same question one step earlier.

CONSEQUENCE when adding anything else three binaries must agree on: put it under internal/, check with `go list -deps ./tools/bridge` whether the owner is already in the bridge's closure, and prefer an existing owner to a new package. A package created for two constants is the failure the apppaths deletion corrected.

WHAT THIS DOES NOT MEAN: it is not "everything shared goes in config". Only what config is already the owner of. The OS-level question — which directory an OS designates — is not config's and lives in internal/platform/userdirs, which knows no application at all.
