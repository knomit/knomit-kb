# findConfigFile checks beside os.Executable() BEFORE <home>/knomit.toml — so a knomit.toml next to only ONE binary (server or bridge/kb) is read by that binary alone, and the two can resolve different sockets

`config.findConfigFile(home)` returns `filepath.Dir(os.Executable())/knomit.toml` if it exists, and only otherwise `<home>/knomit.toml`. Every binary evaluates this against ITSELF: `knomit serve`, the desktop, and the bridge / `kb`. Since knomit#271 the bridge reads the `socket` key from whatever file this returns (config.SocketPath). So:
- a knomit.toml beside the bridge binary only: the bridge uses its `socket`, the server never reads it, and the bridge dials a listener nobody opened. TCP fallback, verified identity lost, no error.
- a knomit.toml beside the server binary only: the server uses its `socket`, and the bridge falls through to <home>/knomit.toml or the default. Same silent failure.

The same shape holds for a RELATIVE socket path (knomit#272 review F6): both sides agree on the string, but each resolves it against its OWN cwd.

ACCEPTED, NOT FIXED (master ruling on PR #272 review F2): both binaries ship side by side (dist/, the .app bundle), so in a normal install they see the same file. `<home>/knomit.toml` is seen by both wherever they live, so it is the place to put a `socket` override. A follow-up issue covering both directions and F6 is to be filed after #272 merges. findConfigFile was deliberately left unchanged. The accepted gap is named in a comment at the call site in config.SocketPath.

CONSEQUENCE: when a bridge reports "local listener unreachable" or never gets a verified identity while the server is up, check for a knomit.toml beside either executable before suspecting the layering code.
