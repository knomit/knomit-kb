# knomit.toml is read ONLY from <home>/knomit.toml — findConfigFile no longer looks beside os.Executable(), because the server and the bridge/kb are different binaries and a file beside one of them was read by that binary alone

`config.findConfigFile(home)` returns `<home>/knomit.toml` if it exists, else "". It does NOT look beside `os.Executable()` any more.

Until knomit#274 (PR #293) it checked `filepath.Dir(os.Executable())/knomit.toml` FIRST. Every binary evaluated that against itself (`knomit serve`, the desktop, the bridge / `kb`), so a knomit.toml beside only ONE binary was read by that binary alone. The two sides then resolved different local listeners, the bridge fell back to TCP, and the verified identity was lost with no error.

WHY IT WAS DROPPED, not merely documented (user decision on #274):
- the lookup came in with the first layered-config commit (672fbf5b) with no recorded reason;
- nothing shipped relies on it: the release tarball carries only the three executables plus lib/, and the macOS bundle ships no knomit.toml;
- it broke the desktop: Settings writes `<home>/knomit.toml` (tools/desktop/app.go newNativeService), so a stray file beside the executable would have made every Settings save silently ineffective.

The rejected alternative was to keep the lookup and log which file each binary read.

MIGRATION AID: `config.IgnoredExecutableConfig(home)` returns the knomit.toml beside the executable when one exists and is not the same FILE (os.SameFile) as `<home>/knomit.toml`, so a symlinked or case-variant data root does not warn falsely. `knomit serve` (cmd/serve.go) and the desktop (tools/desktop/app.go) call it and warn AFTER configuring their logger, naming `ignored` and `read`. It is deliberately NOT in config.Load: Load runs before logging is set up, so a warning there went to bare stderr and was lost with --log-file and in the GUI. `kb` and the bridge never warn.

CONSEQUENCES:
- Do not reintroduce a per-binary search location. Any location evaluated against the running executable, its cwd or its own environment is a divergence channel between server and bridge (see the rendezvous-inputs synthesis).
- An operator who had a knomit.toml beside the binary must move it to `<home>/knomit.toml`. The server's or the desktop's log says so at startup.
- Do not move the warning into Load "for completeness": nothing Load logs reaches the configured log.
- Enforced by `TestFindConfigFile_OnlyHome` and `TestIgnoredExecutableConfig` (internal/foundation/config/config_test.go). Both plant a knomit.toml beside the test binary; the second also checks a symlinked root.

WHAT THIS DOES NOT MEAN:
- Not that the desktop's bundled tools stopped being found beside the executable. installBundledTool (tools/desktop/bundled.go) still copies binaries from beside os.Executable(); only the CONFIG search changed.
- Not that the warning makes the file effective. It is informational only.
