# config.Load (and so config.Validate) is shared by `knomit serve`, every CLI subcommand AND the desktop app — a Validate rule about a SERVER-only setting refuses every entry point, including binaries that never use the setting: PR #292's non-loopback [runtime].addr refusal makes an existing `:6060` config fail `knomit grants list` and the desktop boot, which opens no diag port at all

internal/config.Load is the one loader: cmd/serve.go, the CLI subcommands (grants, identity, oauth, verify, …) and tools/desktop (app.go ~L85, native.go ~L205) all call it, and it runs Validate. So any rule added to Validate is enforced for every binary that reads the config, whether or not that binary acts on the field. PR #292 (fixes #288) added: `[runtime].addr` with a non-loopback host is refused unless `[runtime].allow_remote = true`. A config that already has the common pprof idiom `addr = ":6060"` therefore fails to load EVERYWHERE after upgrade — not only in serve, where the port is opened, but in `kb`-side CLI calls and in the desktop app, which never opens the diag listener. The error text names the fix (use 127.0.0.1:<port>, or set allow_remote), which is the mitigation; the PR description calls the break out.

Consequence for the next server-only rule: either accept that it breaks every entry point loudly (as #292 did, deliberately, because the message is self-explanatory) or enforce it at the boot site (app.New / checkLocalListener style, see the [auth].require check that lives in app rather than config.Validate for exactly this reason: `kb` and other clients load the same config and have no business failing on a server-only combination). WHAT THIS DOES NOT MEAN: it does not mean Validate is the wrong place for rules about the config's own consistency; it is the wrong place for rules about what ONE binary will do with a value.
