# os.UserHomeDir on Windows reads only %USERPROFILE%; config.go discards its error, so a scrubbed environment puts the knomit data root at C:\.knomit

internal/config/config.go Defaults() does `home, _ := os.UserHomeDir(); Home: home + "/.knomit"`, and expandTilde() repeats the pattern. On Windows, Go's os.UserHomeDir consults ONLY %USERPROFILE% (HOME, HOMEDRIVE/HOMEPATH and LOCALAPPDATA are ignored). With USERPROFILE unset it returns "" plus an error; the error is dropped, so Home becomes "/.knomit", which Windows resolves to the current drive's root: C:\.knomit. Setting KNOMIT_HOME bypasses Defaults() entirely, so any acceptance run that sets it cannot reveal this; only a run WITHOUT KNOMIT_HOME exercises the default.

Observed on the Windows dev box 2026-09-19 14:46: C:\.knomit held a freshly generated id_ed25519 (different fingerprint from the real one) and 1 of 3 model files from a server boot (app.New: keypair, then EnsureModel) that died ~48 s in during the 617 MB external-data download; no control.db, no repos/, no known_hosts, so the stray key never signed or pushed anything and the folder is safe to delete.

Which launch path had USERPROFILE stripped was NOT identified, and the hunt is closed. Measured and CLEARED (all resolve C:\Users\<user>): PowerShell, Git Bash, C:\msys64 bash (-lc and -c), C:\msys64\usr\bin\make.exe from PowerShell, Windows session-0 helper Claude sessions, and a Task Scheduler task registered Interactive/Limited (the acceptance route in .claude/plans/windows-support.md; probe run by the user 2026-09-20, USERPROFILE present). Only `env -i`, `env -u USERPROFILE`, or `USERPROFILE= prog` reproduce it. The e2e harness (e2e/global-setup.ts, e2e/fixtures/knomit.ts) and every repo test that builds an env inherit process.env and set KNOMIT_HOME; nothing in the tree calls os.Clearenv or blanks USERPROFILE. Do not spend time hunting the culprit again: the mechanism is the bug.

Consequences: (1) never drop the UserHomeDir error; on Windows fall back the way tools/desktop/internal/paths/paths_windows.go already does (LOCALAPPDATA, then reconstruct from UserHomeDir, then a named error) and otherwise refuse to start rather than write to a drive root. (2) The same dropped-error pattern exists at tools/desktop/internal/autostart/autostart_darwin.go and tools/motifannex/main.go. (3) Adjacent Windows gaps found in the same pass: tools/bridge/main.go lockfilePath() has no windows case, so `kb` on Windows never finds the desktop's server.json and silently uses the default base URL; and HOME is typically EMPTY in a plain Windows PowerShell session, so the e2e harness, which locates ~/.knomit/models via process.env.HOME, misses the cache and re-downloads ~617 MB per e2e run on Windows (use os.homedir()).

Misreading to avoid: "session 0 or Task Scheduler strips USERPROFILE": it does not; both were measured with it present.
