# FIXED: os.UserHomeDir on Windows reads only %USERPROFILE%, and config.go used to discard its error, so a scrubbed environment put the knomit data root at C:\.knomit — now guarded by internal/platform/userdirs and config.DefaultHome, which refuse to start rather than guess

WAS (the bug, as of 2026-09-19). `internal/config/config.go` Defaults() did `home, _ := os.UserHomeDir(); Home: home + "/.knomit"`, and expandTilde() repeated the pattern. On Windows, Go's os.UserHomeDir consults ONLY %USERPROFILE% (HOME, HOMEDRIVE/HOMEPATH and LOCALAPPDATA are ignored). With USERPROFILE unset it returns "" plus an error. The error was dropped, so Home became "/.knomit", which Windows resolves against the current drive's root: C:\.knomit.

Setting KNOMIT_HOME bypassed Defaults() entirely, so any acceptance run that set it could not reveal this; only a run WITHOUT KNOMIT_HOME exercised the default.

Observed on the Windows dev box 2026-09-19 14:46:
- C:\.knomit held a freshly generated id_ed25519 (a different fingerprint from the real one) and 1 of 3 model files, from a server boot (app.New: keypair, then EnsureModel) that died about 48 s into the 617 MB external-data download.
- There was no control.db, no repos/ and no known_hosts, so the stray key never signed or pushed anything.

Which launch path had USERPROFILE stripped was never identified, and the hunt is closed.
- Measured and CLEARED (all resolve C:\Users\<user>): PowerShell; Git Bash; C:\msys64 bash (-lc and -c); C:\msys64\usr\bin\make.exe from PowerShell; Windows session-0 helper Claude sessions; and a Task Scheduler task registered Interactive/Limited (probe run by the user 2026-09-20, USERPROFILE present).
- Only `env -i`, `env -u USERPROFILE` or `USERPROFILE= prog` reproduce it. The mechanism was the bug.

FIXED BY the decision to move the Windows data root under %LOCALAPPDATA% and to make every lookup failure an error (kb/decisions/config/home/windows-home-under-localappdata-no-migration/b58b16ae).

NOW GUARDED BY (verified at 131376e3):
- internal/platform/userdirs (userdirs_windows.go):
  - stateDir uses %LOCALAPPDATA%;
  - if it is unset, stateDir reconstructs <profile>\AppData\Local from os.UserHomeDir;
  - if that fails too, it returns an error naming %LOCALAPPDATA% and %USERPROFILE%. It never returns a guessed path.
- config.DefaultHome builds on that; config.withHomeHint adds "Set KNOMIT_HOME to the directory knomit should use"; ResolveHome and Load stop startup on the error.
- config.Defaults() leaves Home EMPTY on purpose, with a comment recording this bug, so an unresolved root can no longer become a real directory by string concatenation.
- expandTilde returns `cannot expand "~/…": <err>` instead of dropping the error.
- home_windows_test.go and userdirs_windows_test.go pin the no-drive-root behaviour.

ADJACENT GAPS FOUND IN THE SAME PASS, all since closed at 131376e3:
- tools/desktop/internal/autostart/autostart_darwin.go now returns an error when os.UserHomeDir fails.
- tools/motifannex no longer exists.
- The `kb` bridge's lockfilePath delegates to config.LockfilePath, so it finds the desktop's server.json on Windows too.
- The e2e harness locates the model cache through e2e/helpers/appdirs.ts (LOCALAPPDATA, else os.homedir()), not process.env.HOME, which is often empty in Windows PowerShell.

CONSEQUENCE THAT STILL HOLDS: any new code that resolves a user directory must go through internal/platform/userdirs or config.DefaultHome / ResolveHome, and must propagate the error. `x, _ := os.UserHomeDir()` followed by a join is the exact shape of this incident.

Misreading to avoid: "session 0 or Task Scheduler strips USERPROFILE". It does not; both were measured with it present.
