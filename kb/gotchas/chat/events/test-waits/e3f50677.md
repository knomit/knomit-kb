# running=false in the chat snapshot comes BEFORE the turn's chat_state and terminal event are sent: a test that must see the end go out waits on finishTurn's afterEnd seam, never on the snapshot

chat.finishTurn sets running=false under c.mu, releases c.mu, then (in this order, outside the lock) appends the turn_end transcript line, writes the session log's preload record, calls noteState (which broadcasts chat_state because the row left "running"), runs the betweenRunAndEnd seam, and only then calls emitEnd (turn_done or turn_error). The transcript and log writes are disk I/O, so under load the gap is wide. A GET /chats/{id} cut in that gap already shows running=false.

Consequence for tests: a page stream attached after polling running=false but before noteState gets chat_state as its first event after ready, and the end LIVE, not as the parked replay. TestChat_EveryTurnEndReachesTheClientOnce (stream dropped subtests) did exactly that and failed under load with "expected turn_error, actual chat_state" (27 of 540 runs of the top-level test with 6 parallel copies, -count 30, -cpu 1,2,8 and 10 busy-loop CPU burners; every failure was the invalid_tool_call_arguments subtest). A probe that moved the seam ahead of noteState and attached inside it reproduced chat_state as the first event deterministically.

The same gap broke TestChat_AnEndThatLandsAfterTheNextTurnStartedIsNotParked (5 of 540): the seam starts turn two, the test attached as soon as turn two had started, but turn one's emitEnd runs AFTER the seam returns, so the attached stream got turn one's turn_done live (turn 0) and the test read it as a stale parked end.

Fix (branch fix/flaky-chat-turn-end): chat.afterEnd, a test seam finishTurn defers once the turn was not ended, so it fires after emitEnd returned (broadcast done, and the end parked if no stream took it). Tests wait on it through endsOf/waitEnd in turnend_test.go. The dropped-stream subtests also wait for the server to detach the closed stream (harness.waitDetached, polling manager.pages) instead of sleeping 50ms: stream.close returns when the CLIENT read loop ends, and until the handler detaches the stream a broadcast counts it as having taken the frame, so the end would not be parked.

This is NOT a product bug: in both interleavings the client gets every event once and each end names its turn, which the page routes by (the snapshot-authoritative fact). Does NOT mean afterEnd fires for a chat that ended mid-turn: finishTurn returns before the defer when c.ended is set.
