# Ontology `validations` (fact.ValidateFact) run on exactly THREE write paths — knomit_learn, knomit_update and experiment {body} resolutions; review's own writes (distill, prune/subsume, reflect, dedup merge, discovery) and the REST POST/PUT fact endpoints never evaluate a JS rule, so a topic's format rules bind only what agents write by hand — hypothesize is validated because the agent persists through knomit_learn

Verified at origin/dev ba748e2b (2026-10-06): `fact.ValidateFact(o, topicPath, f)` (internal/fact/validation.go) is called from internal/mcp/learn.go (the fresh-fact gate and again on the merged fact after applyDedupMerge), internal/mcp/update.go, and internal/resolutions/resolutions.go (a `{body}` resolution is a fact write, kb/decisions/experiments/resolution-bodies-are-writes/67cd27d8.md). Nothing else calls it.

WHAT SKIPS IT:
- internal/synthesize/decision.go — the confidence `update` writes, `ApplyPruneDecisions` (subsume: BatchWriteFacts), distill's new synthesis facts, and the `review` batch (reflect's methodology facts) all go straight to `gs.WriteFact`/`gs.BatchWriteFacts` after SerializeFact.
- internal/synthesize/dedup.go — `dedupCluster`'s pairwise merge writes the winner with WriteFact.
- internal/synthesize/discovery.go — emergent facts are written with WriteFact.
- internal/web/handlers_fact_create.go (POST) — ValidateTitle only; no ValidatePath, no rules.
- internal/web/handlers_fact_write.go (PUT) — runs `ValidateContext` (the typed `context` gate from #413) but, as its own comment says, not the JS rules, which that endpoint has never run.

WHAT DOES NOT SKIP IT: knomit_hypothesize mutates nothing (its result type deliberately has no summary counters); the agent persists each hypothesis through knomit_learn, so a `validations:` block on the topic DOES bind hypotheses. That is why the #410 mission-kb design could enforce a hypothesis format on `forecast` through the ontology.

CONSEQUENCE: a topic rule is a gate on AGENT-authored writes, not an invariant of the files under that topic. A synthesis or methodology fact distilled into a topic with rules, a prune merge of two conforming facts, or a REST-edited fact can violate the rule and still be committed. Do not design a mission or a template on the assumption that `validations` guarantee every fact under a path has a shape; if a later consumer parses that shape, it must tolerate review output. Also: review's writes skip ValidateContext too, so they inherit context only by copying (see kb/invariants/fact/context/two-gates/ebd742be.md for what review does with a malformed stored map).

WHAT THIS DOES NOT MEAN: structural validation (kind×type, bounds, origin×type, title, context SHAPE) is NOT skipped anywhere — it lives in SerializeFact and every writer serialises (kb/invariants/fact/single-validation-entry-point/81b28d39.md). The gap is the ontology's per-topic rules and the `ValidatePath` topic check, not well-formedness.
