# ANY illegal (type, origin) pairing is normalised to the type-aware default AT PARSE and the result elided at serialize — so every read-modify-write silently reattributes those facts, and prune's merge path still does

**The class, stated at its real width.** `ParseFact` applies the type-aware origin default to ANY ILLEGAL `(type, origin)` pairing — not only the "discovered observation" case first recorded — and `SerializeFact` then elides the resulting `authored`. A read-modify-write therefore rewrites the stored `origin` line without anyone asking it to.

**Measured (Phase-4 entry-12 audit, 2026-08-24):** 61 reattributions on `core`, splitting **31 `discovered`→authored and 30 `distilled`→authored**; 16 on `merged` (9+7). The `distilled` half is what makes the class broader than first recorded. The "other" bucket was EMPTY on all five corpora, so the class is fully characterised. Motif loss was zero (179 annex-written motif instances all round-trip clean — the first corpus state where that column means anything, and NOT evidence about production motifs).

**WHAT THIS DOES NOT MEAN.**
- **It is NOT "every fact loses its origin on rewrite".** Only facts whose STORED `(type, origin)` pairing is already ILLEGAL are affected — 61 of 1,688 live facts on `core`. A legal pairing round-trips unchanged.
- **It is NOT a bug in the origin default.** The default is correct at parse; the loss is that the corrected value is then written BACK over the original, so the corpus forgets what it used to claim. Parse and serialize are each individually right.
- **It does NOT mean every round-trip writer is affected equally.** REINFORCE is REMEDIATED — a lossy target is skipped with a reason, not written (`kb/invariants/synthesize/discovery/reinforce-write-contract/6595b1cb.md`). **Prune's merge path is NOT, and inherits the class**: measured on this stack silently deleting a stored `origin: distilled` line end to end.

**STANDING OPERATIONAL HOLD at the time of recording.** `core` alone carries the 61 facts of this class. **Hold review sessions on `core` until issue #107's guard question is decided** — PR #109 unblocked the dedup path, but unblocking dedup does not make the MERGE path safe for that corpus. Tracked as issue #107; do not treat #109 merging as clearing this.

**The named misreading, and it is IN THE CODE.** The "next write self-heals" rationale comment in `internal/fact` OVERSTATES the general case. Self-healing assumes the next write carries the correct origin to restore; for a fact whose stored origin was already illegal, the next write carries the DEFAULT — which is what destroyed it. Do not rely on that comment.

**How the audit of this class was itself blind in this class's way** — it compared two post-parse values and reported all 61 cases as no-ops. See `kb/meta/methodology/instrument-reads-truncated-values/9c9d386d.md`.
