# ANY illegal (type, origin) pairing is normalised to the type-aware default AT PARSE and the result elided at serialize — so every read-modify-write silently reattributes those facts, and prune's merge path still does

**The class, stated at its real width.** `ParseFact` applies the type-aware origin default to ANY ILLEGAL `(type, origin)` pairing — not only the "discovered observation" case first recorded — and `SerializeFact` then elides the resulting `authored`. A read-modify-write therefore rewrites the stored `origin` line without anyone asking it to.

**Measured, then repaired.** The Phase-4 entry-12 audit (2026-08-23) found 61 reattributions on `core`; a re-measure on 2026-08-24 found **65** (32 `discovered`→authored, 33 `distilled`→authored) — the population had grown with the corpus, which is why a count is re-taken immediately before any repair rather than carried. 16 on `merged` (9+7). The `distilled` half is what makes the class broader than first recorded. The "other" bucket was EMPTY on all five corpora, so the class is fully characterised. Motif loss was zero (179 annex-written motif instances all round-trip clean — the first corpus state where that column means anything, and NOT evidence about production motifs).

**`core` IS NOW REPAIRED TO ZERO (2026-08-24).** All 65 were classified per-fact and repaired; the post-repair audit on a fresh snapshot of the quiesced live store reports **reattributed = 0**, other bucket empty, unparsable 0, and byte-identical up by exactly 65 (1394 → 1459 of 1787 live facts). A direct stored-bytes scan confirms **0 illegal pairings remain across all 1787 live facts**. Repair commits `66e1c2b5aaa7` … `e4724e9af9c6`, 65 commits under actor `mindev.local-8ef0cd32+repair@agents.knomit.io`. Disposition table: `.claude/plans/motif/2026-08-24-core-repair-dispositions.md`.

**What the repair found, and why `authored` was right.** All 65 were `operation=learn` newsletter ingests written 2026-07-15→18, entirely BEFORE origin×type enforcement landed (P1.6, 2026-07-21); each had exactly one blob version, so the tag was original agent input, never drift. Decisively, **the origin tag was a per-session constant, not a per-fact claim**: all 12 ingest runs were 100% pure, each emitting either all-`discovered` or all-`distilled`, and the same real-world event ingested in two runs carried OPPOSITE origins. And 0/65 cited another fact while 19/19 legitimate `distilled`+`synthesis` facts (`operation=subsume`) did — a distillation derives from facts and cites them. They were source-transcribed observations, which is the shape `kb/invariants/mcp/learn-origin-type-consistency/a63ff254.md` names `authored` as correct for.

**The repair form, and why the line was REMOVED rather than set to `authored`.** Absence IS the corpus-canonical encoding of authored on a non-synthesis type: of 1787 live `core` facts, 1429 authored observations all store no origin line and NOT ONE fact anywhere carries an explicit `origin: authored`. Writing the literal line would have parsed correctly but been elided by `SerializeFact` on the next write, leaving those 65 permanently non-byte-identical. **This is NOT the wholesale origin-drop that issue #107 forbids** — #107 forbids dropping origins to satisfy a check; this was a per-fact evidenced finding that the value was never a provenance claim, with every pre-repair blob still reachable in history.

**STANDING OPERATIONAL HOLD — LIFTED 2026-08-24 by designer ruling**, on the verified audit zero: with the population empty there is nothing left for the lossy path to lose on `core`. Review sessions on `core` are permitted again. **This does NOT mean the mechanism is fixed.** Issue #107 remains OPEN for the real future risk — an import repeating the pre-enforcement shape would re-create the class, and `prune`'s merge path is still unremediated and still inherits it. A clean corpus is not a safe path.

**WHAT THIS DOES NOT MEAN.**
- **It is NOT "every fact loses its origin on rewrite".** Only facts whose STORED `(type, origin)` pairing is ILLEGAL are affected. A legal pairing round-trips unchanged.
- **It is NOT a bug in the origin default.** The default is correct at parse; the loss is that the corrected value is then written BACK over the original. Parse and serialize are each individually right.
- **It does NOT mean every round-trip writer is affected equally.** REINFORCE is REMEDIATED — a lossy target is skipped with a reason (`kb/invariants/synthesize/discovery/reinforce-write-contract/6595b1cb.md`). **Prune's merge path is NOT.**
- **The repair does NOT decide #107's guard question.** Whether rewriting paths should REFUSE a lossy round trip is still open.

**The named misreading, and it is IN THE CODE.** The "next write self-heals" rationale comment in `internal/fact` OVERSTATES the general case. Self-healing assumes the next write carries the correct origin to restore; for a fact whose stored origin was already illegal, the next write carries the DEFAULT — which is what destroyed it. Do not rely on that comment.

**Any instrument for this class must read the STORED BYTES.** The audit of this class was itself blind in this class's way — it compared two post-parse values and reported all 61 cases as no-ops. The repair tool was built under the same rule: content by text edit on stored bytes, with `ParseFact` used only to VERIFY the output, never to construct it. See `kb/meta/methodology/instrument-reads-truncated-values/9c9d386d.md`.
