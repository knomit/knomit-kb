# ANY illegal (type, origin) pairing is normalised to the type-aware default AT PARSE and the result elided at serialize — so every read-modify-write silently reattributes those facts, and prune's merge path still does

**The class, stated at its real width.** `ParseFact` applies the type-aware origin default to ANY illegal `(type, origin)` pairing — not only the "discovered observation" case first recorded — and `SerializeFact` then elides the resulting `authored`. A read-modify-write therefore rewrites the stored `origin` line without anyone asking it to.

**Measured (Phase-4 entry-12 audit, 2026-08-24):** 61 reattributions on `core`, splitting **31 `discovered`→authored and 30 `distilled`→authored**; 16 on `merged` (9+7). The `distilled` half is what makes the class broader than recorded. The "other" bucket was EMPTY on all five corpora, so the class is fully characterised. Motif loss was zero (179 annex-written motif instances all round-trip clean).

**Status of the two consumers.** REINFORCE is REMEDIATED — a lossy target is skipped, not written. **Prune's merge path is NOT, and inherits the class**: it has been measured on this stack silently deleting a stored `origin: distilled` line end to end.

**Operational consequence, standing at the time of recording.** `core` alone carries the 61 facts of this class. Hold review sessions on `core` until issue #107's guard question is decided — unblocking the dedup path does not make the merge path safe for that corpus. Tracked as issue #107.

**The named misreading, and it is in the code.** The "next write self-heals" rationale comment in `internal/fact` OVERSTATES the general case. Self-healing assumes the next write carries the correct origin to restore; for a fact whose stored origin was already illegal, the next write carries the DEFAULT, which is what destroyed it. Do not rely on that comment.
