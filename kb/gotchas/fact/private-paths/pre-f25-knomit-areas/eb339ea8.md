# Files a repo already holds under .knomit/<area>/ from before F25 stay in git but are UNREACHABLE through every fact tool — no read, update or retract by path; a job that kept state there (e.g. a crawl-state slot) must move to artifacts/<area>/ or it fails on its next run

F25 (three roots) closed every dot path to the fact tools with no exception. Before it, sessions and jobs could write `.knomit/<area>/…` through knomit_learn `path` and then update/retract/explain it. After it:

- Existing files there are untouched in git and in history (nothing migrates them), still invisible to discovery as before.
- knomit_explain, knomit_update, knomit_retract, learn's `retract`, and REST GET/PUT/DELETE on them all refuse with "is private … closed to the fact tools" (MCP) or 400 "Private path" (REST). So a job whose prompt says "read your state at .knomit/jobs/<x>/state.md and update it" breaks: the read is refused, and learning a fresh slot there is refused too.
- The fix is a prompt/config change in the job, not in knomit: use `artifacts/<area>/…` (same tools, same exact-path semantics, same invisibility). Old state can be moved by hand with git (`git mv .knomit/<area> artifacts/<area>`, commit, push/merge) if the job needs its history.

WHAT THIS DOES NOT MEAN: it does not affect `.knomit/` files knomit reads by name (ontology, skills, recipes, trigger scripts) — those keep working, and are now changeable only through git.
