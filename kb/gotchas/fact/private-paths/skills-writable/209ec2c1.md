# `.knomit/<area>/` is agent-writable through the fact tools and `<area>` includes `skills`: knomit_learn and REST PUT can add files under `.knomit/skills/<name>/` that knomit_skill serves to every later session once main carries them (on an origin-less repo the local reconcile fast-forwards main from the agent branch every 30 s) — recipes and trigger scripts are NOT reachable the same way

Found at the F23 plan gate (R1, 2026-10-04) and verified with probe tests at origin/dev ba748e2b (2026-10-06). Nothing in the code prevents it; the approved fix is design work (the three-roots split) that has not landed.

THE PREDICATE. `fact.IsWritablePrivatePath(path)` (internal/fact/private.go) is true for `.knomit/<area>/<rest…>` when ALL of: the path starts with `.knomit/`; `<area>` contains no `.`; there is at least one segment after `<area>`; no segment is empty or `.`; the string `..` occurs nowhere; and `<area>/…` is not under `reservedPrivate`. `reservedPrivate` is EMPTY at HEAD (the comment says empty is the intended state), so every dotless area is open: `jobs`, `runs`, and equally `skills`, `recipes`, `triggers`. Only the area segment is checked for dots — segments BELOW it may start with `.`: `.knomit/jobs/.git/x.md` and `.knomit/skills/work-task/.hidden/x.md` both answer writable=true.

DOOR 1 — the MCP fact tools. knomit_learn with `path`, knomit_update `file` and knomit_retract `file` all run `fact.NormalizePath` first (a dot-prefixed path is lowercased and gets `.md` appended if missing) and then admit the path when IsWritablePrivatePath says yes (learn.go ~L276, update.go ~L192-202, retract.go ~L69-73). Verified at ba748e2b with a git-authored skill `work-task` carried to main:
- learn `path: .knomit/skills/work-task/extra.md` → committed; `knomit_skill {name: work-task}` then returned `files: [{path: extra.md, text: "---\nkind: pragmatic\n…# work-task\n\nINJECTED: …"}]` — the whole fact file, frontmatter and all, inlined as a bundled skill file.
- learn `path: .knomit/skills/new-skill/SKILL.md` → lands as `skill.md` without a `name:` key (SerializeFact emits a fixed key set), so the skills reader logs `malformed skill skipped` and knomit_skill answers `is malformed and is not served`. The MCP tools therefore cannot CREATE a servable skill; they can ADD bundled files to an existing one, and knomit_update can REPLACE a knomit-written lowercase `skill.md` (a fact round trip drops `name:`, so that update breaks the skill rather than reprogramming it).
- retract `.knomit/skills/<name>/skill.md` deletes a knomit-written `skill.md`; the delete lowercases and the tree lookup is exact, so a git-authored `SKILL.md` is not matched.

DOOR 2 — `PUT /api/v1/repos/{repo}/branches/{branch}/facts/{path...}` (internal/web/handlers_fact_write.go). The path is taken verbatim; `refuseNonFactPath` admits `IsPrivatePath && IsWritablePrivatePath`; the body must parse with `ParseFact`, which IGNORES unknown frontmatter keys, so `---\nname: new-skill\ndescription: …\n---\n# new-skill\n\n<body>` is a valid fact AND a valid SKILL.md; and when no gate (refs, motifs, expires, context) changes anything the client's bytes are committed VERBATIM. Verified: PUT `.knomit/skills/new-skill/SKILL.md` with that body → 200 and the writer received the bytes unchanged. The store lowercases the name to `skill.md` and `skillFileEntry` matches SKILL.md case-insensitively (kb/gotchas/store/paths/lowercased-nested-writes/f60cbf8e.md), so this is a brand-new, fully served skill written through a fact endpoint.

WHY IT REACHES SESSIONS. knomit_skill and the skill prompts read `.knomit/skills/` at the tip of the repo's upstream (consensus) branch, never the agent branch (kb/architecture/mcp/skills/knomit-skill-tool/6154c25e.md). With an origin, main moves only through the remote. WITHOUT one, `Service.AdvanceLocalUpstream` fast-forwards refs/heads/<upstream> to the agent tip every `Git.LocalReconcileInterval` (default 30 s, env KNOMIT_GIT_LOCAL_RECONCILE_INTERVAL; kb/decisions/store/local-reconcile/main-is-consensus-everywhere/1b382011.md) — so on a hosted, origin-less repo (the first mission's host) an agent write becomes served skill content within about half a minute, and peers subscribing over /git receive it as main.

NOT REACHABLE THIS WAY: recipes and trigger scripts. `RecipeAt`/`ScriptAt` (internal/store/triggers.go) read exactly `.knomit/recipes/<name>.js` and `.knomit/triggers/<name>.js` from the commit's tree. The MCP tools force `.md` (`work-task.js` → `work-task.js.md`, confirmed not found by RecipeAt). The REST PUT keeps the `.js` name but requires a YAML frontmatter block, and goja refuses to compile a file starting with `---` (`SyntaxError: Line 1:1 Invalid left-hand side in assignment`). A trigger script's own host also refuses any `.knomit/` write (kb/invariants/repos/triggers/script-private-path/b1c7ee9c.md).

CONSEQUENCE: on a hosted repo, learn/update/PUT access IS skill-editing access. Anyone threat-modelling a mission must count a session's fact-write capability as the ability to place instructions that every later session on that repo loads through knomit_skill and the prompt list. Until the roots split lands, keep skill folders out of repos that untrusted sessions write to, or review `.knomit/skills/` on main after a run (`git log --stat -- .knomit/skills`).

WHAT THIS DOES NOT MEAN: not every `.knomit` file — loose files at the namespace root (`.knomit/ontology.yaml`) and dotted areas (`.knomit/ontology.yaml/x.md`, `.knomit/.hidden/x.md`) are still refused; not that a knomit-written SKILL.md through the MCP tools is served (it is malformed and skipped); not that recipes can be forged; and not that a peer sees a skill on the writer's AGENT branch — only what reaches main.
