# `expires` must stay a STRING validated with time.Parse(time.RFC3339): yaml.v3 decodes a date-only `2026-10-01` into time.Time WITHOUT error, and a pre-F03 binary silently DROPS an unknown `expires:` key on any parse/serialize round trip

Measured 2026-09-26 with a probe test: yaml.v3 decodes `expires: 2026-10-01` (date-only) into a `time.Time` field with no error, and into a `string` field verbatim; offsets and quoted forms also decode into string unchanged. A time.Time frontmatter field would therefore silently accept exactly the ambiguous input the write rule refuses. So Fact.Expires is a string; validateExpires requires time.RFC3339 (explicit offset), wrapping ErrInvalidExpires. Write is strict (SerializeFact refuses; REST PUT with raw bytes returns 422 because it commits client bytes verbatim); read is lenient (ParseFact drops a malformed value into ExpiresWarnings so an old file stays loadable). SerializeFact emits it as a quoted string after `refs` only when set, so undated facts stay byte-identical.

Second half of the gotcha: before F03 the frontmatter struct had no expires key and yaml.Unmarshal is non-strict, so ParseFact→SerializeFact (knomit_update, review's confidence update) DROPPED a hand-written `expires:` line. A mixed-version fleet still has this: any instance on an older binary strips the field when it rewrites a fact. Upgrade every instance that mounts a repo before relying on the field there.

Comparison granularity: IsExpiredAt compares whole unix seconds, exactly as the index's facts.expires_at, so a sub-second expiry can never make the marker and the filter disagree.
