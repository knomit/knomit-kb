# `learn_dedup: off` parses only because go-yaml v3 decodes the bare scalar `off` as the STRING "off"; a yaml bool (`false`/`true`) is rejected at parse on purpose

go-yaml v3 follows YAML 1.2's core schema when decoding into `any`. Only `true`/`false` become bools, and the YAML 1.1 words `off`/`on`/`yes`/`no` stay strings. So `learn_dedup: off` reaches the validator as the string "off", and the validator accepts exactly the strings "off" and "on".

A yaml bool is REJECTED with a fatal diagnostic that names the topic path, the key, and the accepted values. `learn_dedup: false` is ambiguous: it can mean "dedup is off" or "the off-switch is false". The unambiguous spelling is also the one that parses. Quoted `"OFF"` and other case variants are rejected too, because the comparison is exact.

The ENCODER goes the other way. When Serialize writes the value back, go-yaml v3 quotes it as `"off"` because it would be a bool in YAML 1.1. It still re-parses as the string "off", so the round trip keeps the value but not the spelling.

CONSEQUENCE: if a yaml library change ever started decoding bare `off` as a bool, every flagged ontology would stop parsing (fatal) instead of silently losing the flag. TestOntologyAttr_BareOffDecodesAsString is what notices. Do not "fix" such a failure by also accepting bools, because that re-opens the ambiguity.
