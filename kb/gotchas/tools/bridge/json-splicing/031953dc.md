# A "does this value have delimiters?" check is not a type check — one weak predicate in init's JSON splicer produced four defects, and the quietest wrote a duplicate key and reported success

Discovered 2026-09-17 on PR #213, where `knomit-bridge claude init` gained byte-level JSON merging (tools/bridge/claude/init_merge.go splices into the user's text at offsets recorded by a json.Decoder token walk, rather than decoding and re-emitting).

THE TRAP. The index records a `jsonSpan{open, close}` per value and a `container()` predicate meaning "this value has delimiters". Guarding a splice with `container()` reads like a type check and is not one:

- An OBJECT and an ARRAY both satisfy it. Splicing an object member into an array — `insertMember(data, arraySpan, ...)` — emits `[1,2,"Event":[...]]`, which does not parse. The reverse, an array element into an object, is equally broken.
- A SCALAR fails it, but a caller that then treats "not a container" as "absent" is worse off than one that crashes: scalars index to `span{-1,-1}`, and the splice helpers take those offsets literally.

FOUR DEFECTS, ALL FROM THAT ONE PREDICATE, ordered by how loud they were:

1. A settings.json of `null` / `42` / `true` / `"a string"` PANICKED — `slice bounds out of range [:-1]` in lineIndent, because jsonNode.child returns nil for every lookup on a scalar, so insertHookEntry took its "no hooks object" arm and spliced at -1.
2. `{"hooks": [1,2]}` spliced a member into the array and surfaced as `invalid character ':' after array element` — an error that looks like a parser complaint about the INPUT but is actually the merge's own corrupted OUTPUT, re-indexed.
3. `{"hooks": {"SessionStart": {...}}}` spliced an array element into an object.
4. The quiet one, and the worst. `{"hooks": "nope"}` took the same "absent" arm as the panic but did not crash: it appended a SECOND `"hooks"` key to the root and returned a nil error. `{"hooks": "nope", "hooks": {...}}` parses — Go's decoder takes last-wins — so init printed its success summary over a config whose meaning depends on which reader you ask. A panic announces itself; this does not.

THE RULE THAT NOW HOLDS. jsonNode records `isArray` beside `isObject` and exposes `object()` and `array()`; `container()` appears in no guard. A splice site must assert the exact kind it is about to write into. Shape validation for settings.json (root is an object, `hooks` is an object, every event is an array) lives in checkSettingsShape and runs from preflightSettings — BEFORE any file is written, because the merge itself runs during the template walk, by which time CLAUDE.md and .mcp.json have already been rewritten, and a failure there leaves a half-landed scaffold.

THE GENERAL LESSON, worth carrying to any positional editor: when a predicate answers a WEAKER question than the operation needs ("has delimiters" vs "is the kind I am about to write into"), the failures do not cluster at the loud end. One of these four panicked; two emitted invalid JSON; one wrote a silently-wrong file and reported success. Reaching for the weaker predicate is attractive precisely because it makes the scalar case go away, which is the case that would otherwise have crashed early and cheaply.

WHAT THIS DOES NOT MEAN: it does not mean byte-level splicing was the wrong choice — decode-and-re-emit would have renumbered the user's indentation and reordered their keys, which is the whole point of the PR. It means a positional editor needs type assertions at the point of the write, not a shape check at the door alone: init_merge.go keeps both, so the merge functions are safe for a caller that skipped the preflight.
