# knomit_learn's dedup merge folds ANY non-hypothesis top match into the incoming fact even when the incoming fact cites it: citing in refs escapes only the same-subject gate, which runs after the merge; the escape from the merge is distinct_from

applyDedupMerge (internal/edge/mcp/learn.go, loop at ~709-934, called at ~1114) searches Path: categoryDirOf(path) — a raw path prefix, so the same directory, its descendants and prefix siblings — with Limit 1 and MinSimilarity at the model's Dedup floor, and takes only results[0]. It declines to merge for exactly: learn_dedup off on the incoming topic (~747) or on the match's topic (~806); the match already absorbed an earlier fact of this call (`consumed`, ~809); the call retracts the match (~818); or the match is named in this fact's distinct_from (~838). Nothing in the loop reads the incoming fact's refs. A non-hypothesis match is therefore folded into (and written at) the existing path even when the incoming fact's refs cite that very fact; an existing hypothesis matched by a non-hypothesis is instead subsumed (the new fact is written at its own path and the hypothesis retracted in the same commit, ~855).

Citing is the escape only for the later same-subject gate: in internal/edge/mcp/learn_same_subject.go the caller skips a candidate the incoming fact already cites (citedIn, ~468 and ~505-511, 'declared lineage'). checkSameSubjectCollisions is called at ~1131, after the merge at ~1114, and never sees a fact the merge touched.

Consequence: to write a fact beside a near-identical one (a derived restatement, a counter-claim, a settling observation), a cite is not enough; name the existing path in distinct_from, otherwise the new fact silently becomes a revision of the cited one. Misreading to avoid: this is not a bug in the cite escape; it is the stage order, and the merge scope is the intended string prefix (see the prefix-scope fact).

WHAT THE RESPONSE TELLS YOU (re-verified at origin/dev b352cb79): a merge is announced only when it is a hypothesis folded into a hypothesis (hypothesisMergeNote names the kept and DROPPED prediction) or when the merge did not corroborate (note 'merged into existing fact <path>; no new refs, sources unchanged', or the expires/context 'not applied' notes). A non-hypothesis merge whose incoming fact brings a novel ref produces NO note: the summary still reads 'wrote 1 fact' and the only signal is that commits[].file is an EXISTING path, not a fresh one. The identity of the merged fact (title, body, kind, type, origin) is taken from the winner of newFactWins: higher confidence wins; on equal confidence the incoming fact wins unless it has strictly fewer sources. So a new fact at confidence >= the existing one overwrites the existing title and body; a new fact at lower confidence is the one lost (its refs, entities and domains are still pooled in). Metadata is always pooled: confidence takes the max, entities and domain are unioned.

CONSEQUENCE: after every knomit_learn into a category that already holds a near-identical fact, compare commits[].file with the paths you expect; if it is an existing path, the learn merged. To recover, read the original body from history (knomit_explain on that path at the prior commit), restore it with knomit_update, then re-learn the new fact with distinct_from: [<existing path>]. Passing distinct_from up front is cheaper whenever you know a near-duplicate exists.

WHAT THIS DOES NOT MEAN: the absence of a note is not evidence that nothing merged, and a distinct_from on the call does not protect against merging into some OTHER match; it declines only the paths it names (the top match only, Search runs with Limit 1).
