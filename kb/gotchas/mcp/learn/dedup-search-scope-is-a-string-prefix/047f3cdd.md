# Learn's auto-merge "same category" search is a raw string-prefix match — it reaches every subdirectory below the incoming fact's directory AND sibling directories that share the prefix

applyDedupMerge (internal/mcp/learn.go) scopes its limit-1 dedup search with `Path: categoryDirOf(paths[i])` — the incoming fact's directory with no trailing slash, e.g. `kb/ops/tasks`. The store turns a non-empty SearchOptions.Path into `AND f.path LIKE ?` with argument `q.Path+"%"` (internal/store/search_query.go). So the search matches:

1. every fact in any SUBDIRECTORY of the incoming fact's directory (`kb/ops/tasks/protocol/...`), and
2. every fact in a SIBLING directory whose name starts with the same string (`kb/ops/task` matches `kb/ops/tasks/...`).

On a hit, the incoming fact is retargeted onto the matched file and mergeFacts rewrites that file. The merged fact is re-validated with ValidateFact against the INCOMING fact's topicCategories[i], not against the matched file's topic.

Consequence: any design that relies on 'the merge only ever touches facts in the incoming fact's own directory' is wrong. Examples are a per-topic switch that protects a subtree, or an argument that a stricter child category can't be merged into from its parent. Exclusions have to be enforced on the CANDIDATE (match.Path) side as well as the incoming side. Found while reviewing PR #255 (F02 `learn_dedup: off`): the flag is checked only for the incoming fact, so an unflagged fact learned at a parent category could still merge into a flagged child's fact.

WHAT THIS DOES NOT MEAN: the search is not corpus-wide. It never reaches a directory outside the string prefix, so another topic or an unrelated category is never matched. The sibling-prefix case (2) is a plain bug; the subdirectory case (1) may or may not be intended, and nothing in the code says which.
