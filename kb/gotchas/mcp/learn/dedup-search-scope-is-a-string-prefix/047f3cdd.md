# Learn's auto-merge search scope is a raw string prefix BY DESIGN: it reaches descendants, prefix siblings, `_` wildcards and case variants of the incoming fact's directory, while the same-subject gate's cap is deliberately exact-directory

applyDedupMerge (internal/mcp/learn.go) scopes its limit-1 dedup search with `Path: categoryDirOf(paths[i])`. That is the incoming fact's directory with no trailing slash, e.g. `kb/ops/task`. The store turns a non-empty SearchOptions.Path into `AND f.path LIKE ?` with the argument `q.Path+"%"` (newFactFilter, internal/store/search_query.go). So learning into ops/task searches, and can merge into:

1. the directory itself (`kb/ops/task/...`),
2. every DESCENDANT (`kb/ops/task/child/...`),
3. every prefix SIBLING (`kb/ops/tasks/...`),
4. `_` wildcard matches (SQLite LIKE treats `_` as any one character), and
5. ASCII-case variants (LIKE is ASCII case-insensitive).

THIS IS INTENDED. Issue #260 reported it as a bug and was closed as won't-fix (not planned): the similarity threshold (dedupThreshold) is the real gate, not the path. A near-duplicate that clears it collapses into the existing fact whatever path the caller supplied (principles/philosophy/dedup-not-append). Since PR for #260's docs follow-up, the comment at the search in applyDedupMerge states this and cites #260. Do not re-file it and do not narrow the scope to an exact directory without revisiting that decision.

On a hit, the incoming fact is retargeted onto the matched file and mergeFacts rewrites that file. The merged fact is re-validated with ValidateFact against the INCOMING fact's topicCategories[i], not against the matched file's topic. That follows from the prefix scope and is part of the accepted behaviour.

THE TWO STAGES USE DIFFERENT SCOPES, DELIBERATELY. The same-subject gate's `sameCategoryDir` (internal/mcp/learn_same_subject.go) caps only candidates in EXACTLY the incoming fact's directory (`strings.EqualFold(categoryDirOf(candidatePath), categoryDir)`) at the Dedup floor. That is narrower than the merge's prefix, and it is safe: a fact the merge folded is marked touched, and the gate skips touched facts (`touched[i]`) before it looks at any candidate. So prefix siblings and descendants the merge picked are MERGED, not refused. A sibling or descendant at or above Dedup that the merge did NOT fold can be treated as cross-category and refused. That happens when its topic has learn_dedup: off, when it was already consumed by an earlier fact in the call, or when it fell outside the small global KNN pool (k = limit*2..5, filtered after the KNN). Refusal is the fail-safe outcome there.

Consequence: any design that relies on 'the merge only ever touches facts in the incoming fact's own directory' is wrong. Examples are a per-topic switch that protects a subtree, or an argument that a stricter child category can't be merged into from its parent. Exclusions have to be enforced on the CANDIDATE (match.Path) side as well as the incoming side. This is why applyDedupMerge also declines a match whose own topic has `learn_dedup: off`: `ontology.LearnDedupOff(topicPathOf(ontologyRoot, match.Path))`, after the search and before the `consumed` check (PR #255, F02).

The LIKE clause is shared: knomit_query documents `path` as a raw prefix, and synthesize's ScopedCluster (internal/synthesize/cluster.go) passes `Path: path.Dir(seed)` with the same prefix semantics.

WHAT THIS DOES NOT MEAN: the search is not corpus-wide. It never reaches a directory outside the string prefix, so another topic or an unrelated category is never matched. Cross-category near-duplicates are the same-subject gate's job (entity-anchored refusal), not the merge's.
