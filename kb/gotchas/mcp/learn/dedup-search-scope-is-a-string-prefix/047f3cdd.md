# Learn's auto-merge "same category" search is a raw string-prefix match: it reaches every subdirectory below the incoming fact's directory AND sibling directories that share the prefix, while the same-subject gate assumes an exact directory

applyDedupMerge (internal/mcp/learn.go) scopes its limit-1 dedup search with `Path: categoryDirOf(paths[i])`. That is the incoming fact's directory with no trailing slash, e.g. `kb/ops/tasks`. The store turns a non-empty SearchOptions.Path into `AND f.path LIKE ?` with the argument `q.Path+"%"` (newFactFilter, internal/store/search_query.go). So the search matches:

1. every fact in any SUBDIRECTORY of the incoming fact's directory (`kb/ops/tasks/protocol/...`), and
2. every fact in a SIBLING directory whose name starts with the same string (`kb/ops/task` matches `kb/ops/tasks/...`). This is a plain bug, tracked as issue #260.

SQLite LIKE semantics also apply: `_` in the path is a single-character wildcard, and matching is ASCII case-insensitive.

On a hit, the incoming fact is retargeted onto the matched file and mergeFacts rewrites that file. The merged fact is re-validated with ValidateFact against the INCOMING fact's topicCategories[i], not against the matched file's topic.

THE TWO STAGES DISAGREE ABOUT SCOPE. The same-subject gate's `sameCategoryDir` (internal/mcp/learn_same_subject.go) decides "the merge already had its chance at this candidate" by an EXACT directory match (`strings.EqualFold(categoryDirOf(candidatePath), categoryDir)`). A candidate in a subdirectory or prefix sibling was within the merge's reach, but the gate treats it as outside it. Any fix to the search scope must move sameCategoryDir with it.

Consequence: any design that relies on 'the merge only ever touches facts in the incoming fact's own directory' is wrong. Examples are a per-topic switch that protects a subtree, or an argument that a stricter child category can't be merged into from its parent. Exclusions have to be enforced on the CANDIDATE (match.Path) side as well as the incoming side. This was found while reviewing PR #255 (F02 `learn_dedup: off`). The flag was first checked only for the incoming fact, so an unflagged fact learned at a parent category could still merge into a flagged child's fact. As merged (33130549), applyDedupMerge also declines a match whose own topic is flagged: `ontology.LearnDedupOff(topicPathOf(ontologyRoot, match.Path))`, after the search and before the `consumed` check. topicPathOf strips the ontology root (case-insensitively) and the file name.

The LIKE clause was deliberately left alone in #255. knomit_query documents `path` as a raw prefix, and newFactFilter is shared. A fix to the merge's scope belongs at the learn call site (search with `dir + "/"`, or post-filter on `categoryDirOf(match.Path)`), together with a decision on whether subdirectories stay in scope.

WHAT THIS DOES NOT MEAN: the search is not corpus-wide. It never reaches a directory outside the string prefix, so another topic or an unrelated category is never matched. The sibling-prefix case (2) is a plain bug; the subdirectory case (1) may or may not be intended, and nothing in the code says which.
