# Learn's auto-merge search scope is a raw string prefix BY DESIGN: it reaches descendants, prefix siblings, `_` wildcards and case variants of the incoming fact's directory, while the same-subject gate's cap is deliberately exact-directory

applyDedupMerge (internal/mcp/learn.go) scopes its limit-1 dedup search with `Path: categoryDirOf(paths[i])`. That is the incoming fact's directory with no trailing slash, e.g. `kb/ops/task`. The store turns a non-empty SearchOptions.Path into `AND f.path LIKE ?` with the argument `q.Path+"%"` (newFactFilter, internal/store/search_query.go). So learning into ops/task searches, and can merge into:

1. the directory itself (`kb/ops/task/...`),
2. every DESCENDANT (`kb/ops/task/child/...`),
3. every prefix SIBLING (`kb/ops/tasks/...`),
4. `_` wildcard matches (SQLite LIKE treats `_` as any one character), and
5. ASCII-case variants (LIKE is ASCII case-insensitive).

THIS IS INTENDED. Issue #260 reported it as a bug and was closed as won't-fix (not planned). Within the prefix the similarity threshold (dedupThreshold) is the gate, not the exact directory (principles/philosophy/dedup-not-append). The reach is still BOUNDED by the string prefix of the incoming fact's directory: another topic or an unrelated category is never searched. PR #294 put this into the comment at the search site, citing #260. Do not re-file it, and do not narrow the scope to an exact directory without revisiting that decision.

On a hit, the incoming fact is retargeted onto the matched file and mergeFacts rewrites that file. ValidateFact then re-validates the merged fact against the INCOMING fact's topicCategories[i], not the matched file's topic path. This is accepted. ValidateFact runs root rules, then the topic segment's rules, then rules on each ontology child node along the INCOMING path. A prefix sibling or descendant shares the topic segment, so the root- and topic-level rules are identical. They could differ at the topic segment only if a fact sat at a topic root and one topic name were a prefix of another; neither holds (a category is required, and no topic name prefixes another). Rules declared on a deeper ontology node of the MATCH's own path are not run.

THE TWO STAGES DO NOT AGREE ON SCOPE, AND THAT IS ACCEPTED UNDER #260. The same-subject gate's `sameCategoryDir` (internal/mcp/learn_same_subject.go) exempts from refusal only candidates at or above Dedup in EXACTLY the incoming fact's directory (`strings.EqualFold(categoryDirOf(candidatePath), categoryDir)`). When the merge folds a candidate, the incoming fact is touched and the gate never runs for it (`touched[i]` skip). For a candidate at or above Dedup that the merge did NOT take, placement decides the outcome:
- in the exact directory, the gate skips it;
- as a prefix sibling or descendant, it is still eligible for a same-subject refusal.
The merge does not take a candidate when it was not the top-1 hit, was already consumed by an earlier fact in the call, was declined by the candidate-side LearnDedupOff check, or was starved out of the KNN k-window (k = limit*2..5, drawn globally and filtered AFTER the KNN).

Consequence: any design that relies on 'the merge only ever touches facts in the incoming fact's own directory' is wrong. Examples are a per-topic switch that protects a subtree, or an argument that a stricter child category can't be merged into from its parent. Exclusions have to be enforced on the CANDIDATE (match.Path) side as well as the incoming side. This is why applyDedupMerge also declines a match whose own topic path has `learn_dedup: off`: `ontology.LearnDedupOff(topicPathOf(ontologyRoot, match.Path))`, after the search and before the `consumed` check (PR #255, F02). It guards a flagged child or flagged prefix sibling reached through the prefix, whose messages must stay intact.

The LIKE clause is shared: knomit_query documents `path` as a raw prefix, and synthesize's ScopedCluster (internal/synthesize/cluster.go) passes `Path: path.Dir(seed)` with the same prefix semantics.

WHAT THIS DOES NOT MEAN: the merge does not reach any near-duplicate anywhere. It is bounded by the string prefix of the incoming directory, so another topic or an unrelated category is never matched. Cross-category near-duplicates are the same-subject gate's job (entity-anchored refusal), not the merge's.
