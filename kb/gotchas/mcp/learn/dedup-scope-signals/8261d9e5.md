# For coordination signals, learn dedup reaches only the incoming fact's category prefix, so per-claimer claim categories (claims/<task>/<fixed-length agent-id>/) do not fold into each other; the risk is same-category signals: a second task in one lane is REFUSED (the merge would carry two entities and the one-id rule rejects it), a second working copy in one queue is FOLDED (one working copy naming two tasks)

Measured by TestMission_SignalTopicsNeedDedupOff (internal/mcp) with the length embedder (equal-length text at cosine 1.0) against the shipped mission ontology with learn_dedup removed from one topic: tasks/lane-a -> the second post fails with 'dedup-merge: validation "one-id"'; inbox/<agent>/working -> the second learn returns the first path and the fact's entities become [task-1, task-2]. With the shipped learn_dedup: off both land as two files with their own expires.

Why claims do not fold: applyDedupMerge's search path is the incoming category dir as a raw LIKE prefix (kb/gotchas/mcp/learn/dedup-search-scope-is-a-string-prefix), each claimer's claims live in their own category, and agent ids are fp-suffixed to a fixed length, so no claimer's directory is a prefix of another's. This corrects the F08 RCA's P6d, which named claims as the case.

CONSEQUENCE: keep learn_dedup: off on every signal topic that holds several templated facts per category (tasks per lane, working copies per agent, acks). MISREADING: 'claims need dedup off to keep their timers' is not what was measured; the timer-loss shape needs two claims in ONE category.
