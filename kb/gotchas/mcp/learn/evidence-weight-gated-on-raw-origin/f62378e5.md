# computeEvidenceWeights gates on the RAW Origin field, which mergeFacts leaves empty — so a dedup-merge that the incoming fact wins ERASES the existing fact's stored evidence_weight

A `knomit_learn` write that dedup-merges into an existing distilled/discovered
fact can silently erase that fact's stored `evidence_weight`. Two mechanisms
combine, neither wrong alone.

1. `mergeFacts` (internal/edge/mcp/learn.go) assembles the merged fact field by
   field — Title, Body, Kind, Type, Origin, Domain, Entities, Confidence,
   Sources, Refs — and NEVER assigns `merged.EvidenceWeight`. It starts at 0
   whatever the existing fact carried.
2. `computeEvidenceWeights` runs AFTER `applyDedupMerge` in `LearnHandler` and
   would restamp a weight, but it skips any fact whose `Origin` is not
   `fact.Distilled` or `fact.Discovered` — testing the RAW field. `mergeFacts`
   copies Origin from whichever fact wins `newFactWins`, and an agent writing a
   synthesis fact through knomit_learn normally OMITS origin (the tool schema
   says to; the empty value is left for the serialize/parse round trip to
   default). So the merged Origin is "", the gate skips, and the weight stays 0.

SerializeFact then elides both keys: no `origin:` line (correct — a
`type: synthesis` fact reads back as distilled) and no `evidence_weight:` line,
because it writes that key only when the value is > 0. The weight is gone from
the file, the index, the web badge, and every weight-ordered query.

CONSEQUENCE: do not treat a stored evidence_weight as durable across a
dedup-merge. Any code asking "is this fact machine-origin?" before the write
completes must resolve origin through `defaultOriginForType`, not read
`f.Origin` — the raw field is legitimately empty at that point on the learn
path. This is the same defect class fixed in PR #93 for the ontology-rule
sandbox.

WHAT THIS DOES NOT MEAN: it is NOT "any dedup-merge drops the weight". Three
preconditions must all hold — the existing fact is a weighted synthesis fact,
the incoming fact WINS `newFactWins` (higher confidence, or equal confidence
and `sources >= existing.sources`), and the incoming fact omits origin. When
the existing fact wins, or the incoming one passes an explicit
`origin: distilled`, the merged Origin is a machine origin and the weight is
recomputed from the pooled ref set. Also not to be confused with `mergeFacts`
in internal/corpus/synthesize/dedup.go — a DIFFERENT function over `factForLLM` in
the prune pipeline, whose caller does recompute the weight.

NOT YET REPRODUCED: derived by reading the write path, not from an observed
corpus regression. A test that learns a high-confidence synthesis fact over an
existing weighted one and asserts the resulting file still carries
`evidence_weight` would confirm or kill it.

UPDATE (#647, merge 76d2b017): the claim that mergeFacts copies Origin from whichever fact wins is superseded. Same-type merges now set merged.Origin = newFact.ResolvedOrigin() (the incoming origin with the type default applied, so an unset incoming synthesis is distilled, not empty); differing types keep the stored origin. Fact.ResolvedOrigin() is exported for exactly this reason: computeEvidenceWeights still gates on the RAW Origin field, and a raw empty origin there would stop re-weighting a merged synthesis. See kb/decisions/mcp/learn-hypothesis-report/c5923523.md. The max-weight carry-across in mergeFacts (the comment citing #94 in internal/edge/mcp/learn.go) is also present at that commit; this fact's mechanism 1 was not re-reproduced here.
