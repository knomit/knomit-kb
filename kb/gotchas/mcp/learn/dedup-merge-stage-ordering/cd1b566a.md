# Every LearnHandler stage is positional relative to applyDedupMerge — a stage before it cannot see merge-induced state, and a stage after it sees fields the merge silently zeroed

`applyDedupMerge` is the pivot of `LearnHandler`: it rewrites the fact set in
place. It retargets `paths[i]` to the existing fact's path and replaces
`facts[i]` with a `mergeFacts` result. That result pools some fields (sources
sum, confidence max, domain/entities union), inherits others from the winner
(title, body, kind, type, origin), and silently ZEROES any field mergeFacts
does not assign. So every other stage's correctness depends on which side of
it the stage sits. Three separate defects have come from that, which is what
makes it a pattern rather than coincidence:

- BEFORE the merge, a stage cannot see merge-induced state. The duplicate-path
  guard ran before the retarget, so it structurally could not see
  dedup-induced path collisions.
- AFTER the merge, a stage sees fields the merge clobbered.
  `computeEvidenceWeights` runs after it and gates on the raw `Origin` the
  merge copied from the winner. For the common agent call that is empty, so
  the fact is skipped and the prior evidence_weight is erased.
- ValidateFact is deliberately called TWICE for this reason: once on the built
  fact, and again on the merged one inside applyDedupMerge, because the merge
  can produce a fact that violates a rule both inputs satisfied. That second
  call still sits before computeEvidenceWeights, so ontology rules always see
  evidence_weight = 0 on a merged fact.

CLASSIFICATION POINTS inside applyDedupMerge, in order:
1. Private state (`topicCategories[i] == ""`), a pre-search check on the
   INCOMING fact: skip, and DROP the embedding donation
   (`donatePaths[i] = ""`), because nothing ever upserts a private path.
2. `learn_dedup: off` on the incoming topic
   (`ontology.LearnDedupOff(topicCategories[i])`, F02), a pre-search check
   on the INCOMING fact: skip, and KEEP the donation. The fact is written at
   its own minted path and indexed. It reads only the topic path, which the
   merge never changes. It leaves `touched[i]` unset, so the same-subject
   stage has its own matching incoming-side skip. Because it is pre-search,
   the fact also skips hypothesis subsumption.
3. `learn_dedup: off` on the MATCH's topic
   (`ontology.LearnDedupOff(topicPathOf(ontologyRoot, match.Path))`), a
   post-search, pre-merge check on the CANDIDATE: decline the match and
   write the incoming fact at its own path. This is needed because the search
   scope is a raw path prefix that reaches flagged descendants (see
   merge-search-scope-is-a-raw-prefix). It sits before the `consumed` check,
   so a declined match is not marked consumed.
A new classification belongs here. For each one, decide whether it is about
the incoming fact or the match, whether the donation survives (is the fact
indexed at paths[i]?), and whether the same-subject stage needs a matching
skip.

CONSEQUENCE: when adding or moving a stage in LearnHandler, state explicitly
which side of applyDedupMerge it belongs on and why, and check every Fact field
it reads against what mergeFacts does to that field. A stage reading a field
mergeFacts does not assign is reading 0 or "" on the merge path, not the value
the caller supplied. Cover the merge path in its test, not just the
straight-through write.

WHAT THIS DOES NOT MEAN: not "move everything after the merge". Both sides are
legitimate. Validation must run on the merged fact, while the duplicate-path
guard has to reject early, before work is done. The rule is to make the
placement deliberate and test the merge path, not to prefer one side.
