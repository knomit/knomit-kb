# learn's auto-merge does NOT search 'the incoming fact's own category directory': it searches a raw path PREFIX, which reaches descendants and prefix-sharing siblings, and the same-subject gate assumes an exact directory

Everything around `applyDedupMerge` (internal/mcp/learn.go), including its own comments and several facts, says the auto-merge searches "the incoming fact's own category directory". What it actually does is pass `Path: categoryDirOf(paths[i])` to `Search`. `newFactFilter` (internal/store/search_query.go) turns that into `f.path LIKE ?` with `q.Path + "%"`, which has NO trailing slash. The scope is therefore a raw string prefix:
- DESCENDANTS: a search from `kb/ops/tasks` returns facts under `kb/ops/tasks/protocol/...`.
- PREFIX-SHARING SIBLINGS: a search from `kb/ops/task` returns facts under `kb/ops/tasks/...`. This is a pre-existing bug, tracked as issue #260.
- SQLite LIKE semantics: `_` in the path is a single-character wildcard, and matching is ASCII case-insensitive.

A match anywhere in that scope is merged INTO. The incoming fact is retargeted onto the match's path and inherits the winner's title and body. The merged result is then re-validated against the INCOMING topic's rules, not the rules of the topic the file lives in.

The same-subject gate's `sameCategoryDir` (internal/mcp/learn_same_subject.go) decides "the merge already had its chance at this candidate" by an EXACT directory match. So the two stages disagree about what the merge's scope was.

HOW IT BIT: F02 (`learn_dedup: off`, PR #255) first protected flagged topics only on the INCOMING side. Review found that an unflagged parent's learn could still merge into a message under a flagged child, through the prefix. The fix added a CANDIDATE-side check in applyDedupMerge (`ontology.LearnDedupOff(topicPathOf(ontologyRoot, match.Path))`). It deliberately left the LIKE clause alone: knomit_query documents `path` as a raw prefix, and the filter is shared.

CONSEQUENCE: any rule that says "the merge only touches facts in directory X" is false today. A per-topic protection has to check the MATCH's own topic path, not just the incoming fact's. A fix to the scope belongs at the learn call site (search with `dir + "/"`, or post-filter on `categoryDirOf(match.Path)`), not in newFactFilter. That fix also needs a decision on whether descendants stay in scope, and sameCategoryDir must change with it.
