# knomit_learn's schema marks `title` required but the handler never checks it — an omitted title commits a fact with an empty `# ` heading that ParseFact rejects, so query never lists it, explain and update fail with "could not read"/"empty title heading", and only retract + relearn repairs it — and knomit_update silently ignores unknown keys in `updates`, so a partial write reports success

Observed 2026-09-17 on knomit 0.5.3.2eed2b99. A master session called knomit_learn four times (one decision, three migrated conventions) with every field EXCEPT `title`. The tool's JSON schema lists `title` in `required` (internal/mcp/learn.go, learnToolSchemaProperties), but the handler does not validate the request against that schema and does not check for an empty title, so each call SUCCEEDED, returned a commit hash and a path, and committed a file whose first body line is `# ` with nothing after it.

Every read path then rejects the file, because the fact parser (internal/fact/format.go) returns "empty title heading" for a bare `# `:
- knomit_query never lists the fact — the indexer cannot parse it, so it is invisible to search (and to same-subject checks for later writes).
- knomit_explain reports `could not read <path> at <tip>` — readFactVersion treats a parse failure exactly like a missing file, so the message points at the branch TIP and reads as "the fact is not in the tree" even though `git show <tip>:<path>` returns it. The git history is fine; the /git remote serves the file.
- knomit_update fails with `parse fact error: ParseFact "<path>": empty title heading`, because update reads and parses the existing file first. A broken fact therefore cannot be repaired in place.
- knomit_retract WORKS (it does not parse the file), so the repair is retract each broken path, then knomit_learn again with a title. The relearned facts get NEW ids, so anything that cited the old path (a brief, a message, a plan file) must be updated.

THE SIGNAL THAT WAS MISSED: a same-subject refusal labels each submitted fact by its title (`fact 0: "<title>"`). An empty label — `fact 0: ""` — means the title is missing. Treat that as a stop, not as cosmetics.

CONSEQUENCES: always pass `title` to knomit_learn (the skills' prose says so, the server does not enforce it). When a fact you just wrote cannot be explained "at <tip>" although learn returned a commit, check `git show <tip>:<path>` through the /git remote before suspecting reconcile, indexing lag or the lens: a parse failure and a missing file are reported identically. The fix belongs in the server, by the same ruling that rejects unresolvable refs at write time (kb/decisions/mcp/learn-rejects-unresolvable-local-refs): learn should reject an empty or whitespace-only title and update should reject blanking one, so the write path never accepts what the read path cannot parse. As of this fact that fix is not shipped.

WHAT THIS DOES NOT MEAN: it does not mean the reconcile loop dropped commits (the symptom first looked that way because the failures began just after a pull); nor that the lens read view differs from the write branch. Both were ruled out by cloning the /git remote and finding the files at the tip. It is also not the refs gate's subject: that gate covers citations, and no gate covers the title.

SAME CLASS, FOUND THE SAME DAY BY THE WORKER SESSION: knomit_update SILENTLY IGNORES unknown keys in `updates`. A call passing an `append` key (not in the schema) returned success with a new commit hash; the title and refs it also carried were applied and the body was not — a partial write reported as a full one, caught only by reading the body back. The server-side fix belongs with the title check: reject unknown keys in `updates`, and reject an empty title in both learn and update. Until then, read every fact back after every write (knomit_explain on the path) and compare the field you changed.
