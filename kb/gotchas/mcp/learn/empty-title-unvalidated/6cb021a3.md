# knomit_learn once committed a fact with no title (a bare `# ` heading ParseFact rejects), invisible to query and unreadable by explain/update, repairable only by retract + relearn; knomit_update once ignored unknown keys in `updates` and reported success. Both now FAIL the call: fact.ValidateTitle (in SerializeFact, and early in learn/update/REST create) refuses a blank or multi-line title, and update refuses undeclared `updates` keys

Observed 2026-09-17 on knomit 0.5.3.2eed2b99. A master session called knomit_learn four times (one decision, three migrated conventions) with every field EXCEPT `title`. The tool's JSON schema listed `title` in `required` (internal/edge/mcp/learn.go, learnToolSchemaProperties), but the handler did not validate the request against that schema and did not check for an empty title, so each call SUCCEEDED, returned a commit hash and a path, and committed a file whose first body line is `# ` with nothing after it.

Every read path rejects such a file, because the fact parser (internal/domain/fact/format.go) returns "empty title heading" for a bare `# `:
- knomit_query never lists the fact — the indexer cannot parse it, so it is invisible to search (and to same-subject checks for later writes).
- knomit_explain reports `could not read <path> at <tip>` — readFactVersion treats a parse failure exactly like a missing file, so the message points at the branch TIP and reads as "the fact is not in the tree" even though `git show <tip>:<path>` returns it. STILL TRUE: a parse failure and a missing file are reported identically by explain.
- knomit_update fails with `parse fact error: ParseFact "<path>": empty title heading`, because update reads and parses the existing file first. A broken fact therefore cannot be repaired in place.
- knomit_retract WORKS (it does not parse the file), so the repair for a fact ALREADY broken this way is retract, then knomit_learn again with a title. The relearned fact gets a NEW id, so anything that cited the old path must be updated.

THE SIGNAL THAT WAS MISSED: a same-subject refusal labels each submitted fact by its title (`fact 0: "<title>"`). An empty label meant the title was missing.

A SECOND WAY IN, found in review of the fix: a title with a line break. "\nFoo" serialises as the same empty `# ` heading; "Foo\nBar" reads back as title "Foo" with "Bar" silently moved into the body.

STATUS — FIXED (branch fix/learn-title-unknown-updates; re-pin to the merge commit after it lands):
- `fact.ValidateTitle` refuses an absent, empty or whitespace-only title (`ErrTitleRequired`, "title is required") and any \n or \r anywhere in it, edges included, checked on the raw value (`ErrTitleMultiline`, "title must be a single line"). `SerializeFact` calls it, so every write path that serialises a Fact is gated: knomit_learn, knomit_update, REST create, experiment {body} resolutions, the synthesize pipelines and replay. REST PUT is the exception — it stores the client's bytes — and is protected by ParseFact, which it runs first. The synthesize prune-merge and reflect-propose validators use the same function, so a bad model title is refused before the item is claimed.
- It is also checked EARLY for the caller's sake: knomit_learn per fact (`fact N: title is required` / `fact N: title must be a single line`, batch writes nothing), knomit_update on `updates.title` with the other argument checks, REST create for its 400. learn and REST create then trim the title's edge whitespace, as update does, so the stored heading is what ParseFact reads back.
- knomit_update refuses any key in `updates` that the served schema does not declare, naming every unknown key (sorted) and the accepted set: `unknown key "append" in updates for knomit_update; valid keys are: body, confidence, ...`. origin, topic, category, path and file all trip it; the check runs before the file lookup. knomit_learn likewise refuses unknown keys inside each fact object. The accepted sets did not change; body edits belong in the top-level `ops` argument.

CONSEQUENCES NOW: a missing or multi-line title, or a stray key, is a refused call, not a silent partial write — read the error and resend. A lens server built BEFORE this fix still has these holes, so on an older server keep reading every fact back after writing it.

WHAT THIS DOES NOT MEAN: the fix does not repair facts already committed with an empty title — those still need retract + relearn. It does not mean the reconcile loop dropped commits (the symptom first looked that way because the failures began just after a pull), nor that the lens read view differs from the write branch; both were ruled out by cloning the /git remote. And it does not make explain distinguish a parse failure from a missing file.
