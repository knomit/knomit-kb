# knomit_learn once committed a fact with no title (a bare `# ` heading ParseFact rejects), invisible to query and unreadable by explain/update, repairable only by retract + relearn; knomit_update once ignored unknown keys in `updates` and reported success. Both now FAIL the call: SerializeFact refuses a blank title on every write path, and update refuses undeclared `updates` keys

Observed 2026-09-17 on knomit 0.5.3.2eed2b99. A master session called knomit_learn four times (one decision, three migrated conventions) with every field EXCEPT `title`. The tool's JSON schema listed `title` in `required` (internal/mcp/learn.go, learnToolSchemaProperties), but the handler did not validate the request against that schema and did not check for an empty title, so each call SUCCEEDED, returned a commit hash and a path, and committed a file whose first body line is `# ` with nothing after it.

Every read path rejects such a file, because the fact parser (internal/fact/format.go) returns "empty title heading" for a bare `# `:
- knomit_query never lists the fact — the indexer cannot parse it, so it is invisible to search (and to same-subject checks for later writes).
- knomit_explain reports `could not read <path> at <tip>` — readFactVersion treats a parse failure exactly like a missing file, so the message points at the branch TIP and reads as "the fact is not in the tree" even though `git show <tip>:<path>` returns it. STILL TRUE: a parse failure and a missing file are reported identically by explain.
- knomit_update fails with `parse fact error: ParseFact "<path>": empty title heading`, because update reads and parses the existing file first. A broken fact therefore cannot be repaired in place.
- knomit_retract WORKS (it does not parse the file), so the repair for a fact ALREADY broken this way is retract, then knomit_learn again with a title. The relearned fact gets a NEW id, so anything that cited the old path must be updated.

THE SIGNAL THAT WAS MISSED: a same-subject refusal labels each submitted fact by its title (`fact 0: "<title>"`). An empty label meant the title was missing.

STATUS — FIXED (branch fix/learn-title-unknown-updates; re-pin to the merge commit after it lands):
- `fact.ValidateTitle` refuses an absent, empty or whitespace-only title with `ErrTitleRequired` ("title is required"). `SerializeFact` calls it, and every write path goes through SerializeFact — knomit_learn, knomit_update, REST create and PUT, experiment {body} resolutions, the synthesize pipelines and replay — so the broken state can no longer be written by any of them. knomit_learn also checks it FIRST for each fact, so the error reads `fact N: title is required` and the batch writes nothing; the REST create handler uses it for its 400, which now also covers a whitespace-only title (it used to catch only "").
- knomit_update refuses any key in `updates` that the served schema does not declare, naming every unknown key (sorted) and the accepted set: `unknown key "append" in updates for knomit_update; valid keys are: body, confidence, ...`. origin, topic, category, path and file all trip it. The accepted set did not change; body edits belong in the top-level `ops` argument.

CONSEQUENCES NOW: a missing title or a stray `updates` key is a refused call, not a silent partial write — read the error and resend. A lens server built BEFORE this fix still has both holes, so on an older server keep reading every fact back after writing it.

WHAT THIS DOES NOT MEAN: the fix does not repair facts already committed with an empty title — those still need retract + relearn. It does not mean the reconcile loop dropped commits (the symptom first looked that way because the failures began just after a pull), nor that the lens read view differs from the write branch; both were ruled out by cloning the /git remote. And it does not make explain distinguish a parse failure from a missing file.
