# A bridge client_sessions row shows request_count 1 after initialize + one tool call, because `initialize` carries no Mcp-Session-Id in its REQUEST — the first Touch is the call AFTER it

The session id is MINTED in the initialize RESPONSE, so the initialize request itself carries none. The HTTP dispatch recorder keys on the request's `Mcp-Session-Id` and no-ops without one, so it records nothing for initialize; the row's first `Touch` — and its `request_count = 1` — comes from the next call.

That is why the row has two writers, not one. `Store.SetClientInfo`, called from the `AfterInitialize` hook (the only place the host's declared clientInfo exists), UPSERTS: on a fresh session it CREATES the row with `initialized = 1`, `request_count = 0` and transport `http`, and the first real Touch then fills in the declared bridge columns and flips transport to `stdio`.

Two consequences a reader will otherwise get wrong:

- `request_count` is a count of requests that CARRIED a session id, not of JSON-RPC messages. A handshake-only client shows 0.
- `initialized = false` does NOT mean "never initialized". It means THIS server process never saw the initialize — the row was rebuilt from request headers after a restart, because the default mcp-go session manager accepts any well-formed id (see the stateless-id-manager gotcha). That is what the UI's "resumed" badge reports.

Verified end to end on 2026-09-14: bridge sends initialize + tools/list, row comes back `request_count: 1`, `client.name` set, `initialized: true`.
