# SQLite's SQL-variable cap is COMPILE-TIME, so never size a chunk from a measured one — and until 2026-09-17 the unbounded sessions list could trip it, silently serving every session with an empty binding set

THE STANDING TRAP, which outlives the bug below: `SQLITE_MAX_VARIABLE_NUMBER` is a COMPILE-TIME limit, not a property of SQLite. It is 32766 on the bundled 3.51.2 — measured, 32766 placeholders succeed and 32767 fails — but it was 999 before 3.32 and a system or differently-built library can still be 999 today. So any `IN (...)` built one placeholder per item must be chunked at a CONSERVATIVE constant, never at a number derived from measuring the library in front of you. A constant encoding a measured environment property breaks on the one machine that differs, and breaks silently, because nothing re-measures.

FIXED 2026-09-17 in PR #217 (merged f5f47854). `Store.List` is now bounded — `Filter.Limit`, default `DefaultListLimit` 500, clamped to `MaxListLimit` 2000, with no unlimited value, resolved by the exported `ResolveListLimit` so the handler's policy echo cannot drift from the page it served. `Store.SessionBindings` chunks at the exported `BindingChunkSize` = 900, and `TestBindingChunkSize_ConservativeAgainstOldestCap` asserts it stays under the pre-3.32 cap of 999 — so an "optimisation" to the measured 32766 fails a test rather than a deployment.

TRUNCATION IS SIGNALLED, not silent: `List` queries one row PAST the limit and drops it, returning `truncated`. The REST collection carries `truncated` and `policy.limit` / `policy.max_limit`; the UI shows "showing the N most recent of more"; the live badge renders a lower bound. The page kept is ordered `last_seen_at DESC, id`, so truncation keeps the most recently active rather than an arbitrary slice.

THE PRE-FIX STATE, for anyone reading history (evidence anchored at 17d520be in the refs). `Store.List` had no LIMIT and returned every row in the presence window, or the whole retention window with `?include=hidden`. `SessionBindings` then bound one placeholder per session, so the page size became a variable count. Past the cap the bulk read failed, `handleHALClientSessions` caught it, logged, and served the rows with EVERY binding set dropped — nothing 500'd. The resulting page was indistinguishable from a true one without reading the log, because a session that has only used URL-scoped mounts legitimately renders with an empty set too.

TWO LESSONS THAT SURVIVE THE FIX.

1. FIX THE UNBOUNDED READ, not only the chunking. Chunking alone would have moved the cliff: the list would still have been unbounded, the response would still have grown without limit, and some other per-row cost would have become the next failure.

2. A CHUNKING BUG RETURNS NO ERROR. A loop that drops the last partial chunk yields incomplete sets with a nil error, which reads downstream as "those sessions presented no handles". Test chunking against the real production constant and PAST its boundary (not on it), asserting per-item completeness rather than a total.

WHAT THIS DOES NOT MEAN: the degradation path itself was right and is kept. Serving rows without their binding sets rather than failing the whole page is the correct trade — the last-seen pin is on the row and the page stays useful. The defect was that the page was unbounded in the first place.
