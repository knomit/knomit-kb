# The sessions list has no LIMIT and the binding-set read binds ONE SQL variable per session, so a large enough page trips SQLite's compile-time variable cap and silently degrades to rows-without-sets — and the cap is a property of the BUILD, so never chunk at a measured number

STATE AS OF 17d520be (PR #216). `Store.List` has no LIMIT of any kind — it returns every `client_sessions` row inside the presence window, or the whole retention window with `?include=hidden`. `Store.SessionBindings` then builds ONE placeholder per session id for its `IN (...)`, so the page size becomes a SQL variable count.

THE FAILURE IS SILENT-ISH BY DESIGN AND THAT IS THE TRAP. Past the cap the bulk read fails with "too many SQL variables", and `handleHALClientSessions` catches it, logs a warning, and serves the rows with EVERY binding set dropped. Nothing 500s. A reader sees a normal-looking sessions page where every session appears to have presented no handle — which is also exactly how a URL-scoped-only session legitimately renders, so the degraded page is indistinguishable from a true one without reading the log.

THE CAP IS A PROPERTY OF THE BUILD, NOT OF SQLITE. Measured at 32766 on the bundled SQLite 3.51.2 (32766 placeholders succeed, 32767 fails). But `SQLITE_MAX_VARIABLE_NUMBER` is a COMPILE-TIME limit: it was 999 before 3.32, and a system or differently-built library can still be 999 today. So the practical reachability differs per deployment — unreachable in a 3h presence window on the bundled build, plausibly reachable on a 999-variable build with `?include=hidden` over a 168h retention.

WHAT TO DO, and the order matters. Fix it on `Store.List` — bound the page — not only by chunking the binding read. Chunking alone just moves the cliff: the list is still unbounded, so the response still grows without limit and some other per-row cost becomes the next failure. Chunk as well, but at a CONSERVATIVE constant (900 is safe on every build anyone is likely to link), never at 32766 or anything else derived from measuring today's library. A constant that encodes a measured environment property is the thing that breaks on the one machine that differs, and it breaks silently because nothing re-measures.

AND A CHUNKING BUG RETURNS NO ERROR. A loop that drops the last partial chunk yields incomplete sets with a nil error, which reads downstream as "those sessions presented no handles". Test chunking against the real production constant and past its boundary, not against a test-only small one.

WHAT THIS DOES NOT MEAN: it is not a reason to distrust the degradation path itself. Serving rows without sets rather than failing the page is the right trade — the last-seen pin is on the row and the page stays useful. The defect is that the page is unbounded in the first place.
