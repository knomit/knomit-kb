# knomit's MCP server accepts ANY well-formed Mcp-Session-Id, including ones it never issued — mcp-go's default manager validates format only, so a server restart does NOT force clients to re-initialize and OnRegisterSession fires only on a real initialize

VERIFIED 2026-09-14 against mcp-go v0.45.0 and internal/web/server.go. `buildMCPHandler` calls `mcpserver.NewStreamableHTTPServer(mcpSrv)` with NO options. mcp-go's default is `StatelessGeneratingSessionIdManager`: `Generate` mints `mcp-session-<uuid>`, but `Validate` checks ONLY the prefix and UUID shape — never whether this process issued the id — and `Terminate` is a no-op. Consequences:

1. After a knomit server restart on the SAME port, a bridge keeps its old session id, every request is accepted, and mcp-go builds a throwaway session object per request. The client never re-initializes. (A restart that changes the port is a different story — see the self-update orphan gotcha.)
2. `OnRegisterSession` / `AfterInitialize` fire ONLY on a genuine `initialize` POST. A hook-only registry of connected clients therefore misses every client that outlived a restart, and every caller that fabricated an id — which `internal/mcp/actor.go` already measured as accepted.
3. Inside mcp-go, `DELETE` (session termination) does nothing: `Terminate` is a no-op and the id stays valid afterwards. BUT since PR #192 (2026-09-14) knomit's own MCP dispatch wrapper (`recordClientSession`, internal/web) observes the DELETE and sets `client_sessions.ended_at`, so a knomit-bridge sending DELETE on stdin EOF DOES achieve something: the session row is marked ended instead of going dead by silence. Do not read this fact as 'sending DELETE is pointless' — it is pointless to mcp-go, and load-bearing to knomit's presence registry.

What this does NOT mean: it is not an mcp-go limitation. `InsecureStatefulSessionIdManager` (opt in via `WithSessionIdManager`) tracks issued ids in memory, returns 404 'session not found' for unknown ones, and honours DELETE — a host receiving the 404 re-initializes and the hooks fire. Switching is a deliberate decision with a consequence: stale bridges after a restart would fail loudly (404) instead of silently continuing, which is arguably better but changes observed behaviour. The client-session tracking design (2026-09-14) deliberately leaves the manager alone and records sessions at the HTTP dispatch layer, which sees every request regardless of how the id was minted, using AfterInitialize only as enrichment.
