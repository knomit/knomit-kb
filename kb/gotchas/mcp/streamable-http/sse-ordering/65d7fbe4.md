# mcp-go v0.45.0's streamable-HTTP POST writes pending notifications to the SSE stream BEFORE the JSON-RPC response, so a task-augmented tools/call whose task completes first delivers notifications/tasks/status ahead of its CreateTaskResult — a client (or test helper) that takes the first `data:` line as the response is wrong

Mechanism, in mcp-go v0.45.0.
- server/server.go:1598/1601: handleTaskAugmentedToolCall starts the tool in a goroutine and returns CreateTaskResult.
- When the task finishes, completeTask calls sendTaskStatusNotification (server.go:2193). That broadcasts through sendNotificationToAllClients (session.go:172) to EVERY initialized session's notification channel (s.sessions.Range). If a channel is full, the notification is dropped silently (select default).
- server/streamable_http.go handlePost writes the response LAST. Notifications that reach the session during the POST are written to the stream as they arrive, by a goroutine started before HandleMessage (~431-468), which also upgrades the response to SSE. Any still queued when HandleMessage returns are drained next (~483-500).
- So whenever the task completes before that drain, the POST's body is `data: {notifications/tasks/status ... completed}` followed by `data: {result: {task: ...}}`. This is legal SSE.

Observed: TestOAuthMCP_TaskPathRespectsTheCeiling failed in Race workflow runs 36441730126, 36457474102, 36583365116 and 36601821120 with `not a task-augmented dispatch (no taskId): map[... method:notifications/tasks/status ...]`. The cause was the test helper rpcAt, which took the FIRST `data:` line. It did not reproduce locally in 500 runs, even under -race with CPU burners. It reproduces deterministically with a 300 ms sleep injected before `return &mcp.CreateTaskResult`, using a scratch -modfile whose replace points at a patched copy of the module.

Fix (branch fix/race-workflow-flakes): rpcAt scans every `data:` line. It skips any message with a "method" key, which covers notifications AND server-to-client requests (those carry an id too). It returns the message whose id matches the request's. A JSON-RPC error with id null (a parse error) is therefore skipped when the request had an id. Since 6565f84a, rpcAt also checks sc.Err(), so an oversized line fails as 'token too long'.

Consequence for anyone parsing knomit's MCP POST responses: the first SSE event is not necessarily the response. Match on id, and skip messages that have a method. This is NOT limited to task-augmented calls. Because the status notification is broadcast, it can land in a DIFFERENT session's POST, or in the caller's NEXT request (e.g. the tasks/result poll).
