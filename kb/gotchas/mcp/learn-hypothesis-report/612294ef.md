# knomit_learn deletes a stored hypothesis as a side effect when an incoming non-hypothesis fact is similar to it; since #642 it says so in a note and a `settled:` commit line, and the only undo is re-learning with distinct_from

WHAT HAPPENS. When knomit_learn writes a non-hypothesis fact whose top dedup match (cosine at or above the per-model Dedup floor, inside the incoming directory's raw path prefix) is a stored hypothesis, applyDedupMerge does NOT merge. It writes the incoming fact at its OWN fresh path, cites the hypothesis in its refs, and RETRACTS the hypothesis in the same commit (subsumeHypothesis). That retraction used to be silent: the response said 'wrote 1 fact' and only the commit contents showed a path gone.

WHAT THE CALLER IS TOLD NOW (#642, merge 77896f0a). One short note per incoming fact in the response `notes`: 'fact N: retracted hypothesis <path> (settled by this fact, cited in refs); to keep it, re-learn it with distinct_from: [<new fact path>].' (settledNotes). And ONE commit-message line, 'settled: <path>[, <path>...]' (settledCommitLine), in the same paragraph as the `near:` line, before the trailers. The `retracted` and `commit` response fields are UNCHANGED: they still list only the paths the CALLER passed in `retract` (the atomic-move contract, kb/invariants/mcp/learn/atomic-move/e4fff5d1.md). A subsumed hypothesis appears in the note and the commit line, never in `retracted`.

CONSEQUENCES.
- The word is 'settled', never 'confirmed': the trigger is textual similarity, so it fires when the new observation REFUTES the prediction as readily as when it confirms it. Do not read the note as a verdict. The policy fact kb/decisions/synthesize/learn-dedup-with-hypothesis-collision/deafb49c.md was corrected to 'settled' by #648, which closed issue #641.
- UNDO. If the hypothesis should have lived, re-learn it as a hypothesis with distinct_from naming the NEW fact's path (the note prints it). knomit_update cannot bring it back: the path is deleted, and update edits an existing file. Restoring the old text from history with knomit_explain on the prior commit is how you get the body back.
- To avoid the subsumption up front, name the hypothesis path in distinct_from on the observation: a match named there is declined before subsumption and the observation lands beside it (see kb/decisions/mcp/learn/distinct-from-honoured-by-merge/91cf6418.md).

WHAT THIS DOES NOT MEAN. It does not make subsumption opt-in or add a verdict check; behaviour is unchanged, only reported. It does not add a response field: see the Option A decision. It does not apply when the incoming fact is itself a hypothesis (hypothesis into hypothesis is a merge with a kept/DROPPED note) or when the incoming topic has learn_dedup: off (the search is skipped).

UPDATE (#648, merge 2782d21c). Everything above still describes the UNDECLARED similarity path, which still records no verdict. A caller who knows the outcome now declares it: a fact's request-only `settles: [{path, outcome}]` cites the hypothesis, retracts it in the same commit and records `Knomit-Outcome: <path> confirmed|refuted` in the trailer; the response note then reads 'fact N: hypothesis <path> confirmed|refuted; retracted, cited in refs.' and the declared outcome wins over similarity (the hypothesis is never reported twice). Two more notes exist: 'fact N: matched hypothesis <path>, settled by fact M in this call.' for a second fact whose nearest match another fact settles (no citation), and 'fact N: matched <path>, already taken by fact M in this call.' when an earlier fact already took the match. Contract: kb/invariants/mcp/learn/settles/3bf57718.md; ruling: kb/decisions/mcp/learn-hypothesis-report/55bfa96f.md.

So 'It does not add a verdict check' above remains true of the SIMILARITY path only: the way to get a verdict is to declare it, not to expect the similarity path to infer one. The UNDO is unchanged for the similarity path; for a declared settle, the same re-learn with distinct_from applies, but then the Knomit-Outcome line stays in history.
