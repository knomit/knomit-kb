# When two facts of the SAME type merge in knomit_learn, origin follows the identity winner, and an UNSET incoming origin reads as authored: re-learning a discovered hypothesis verbatim at higher confidence relabels it (current behaviour, pending user decision)

CURRENT BEHAVIOUR at #643 merge a20152c9 (unchanged from before #643; verified in review round 2 by probes at the PR head, and mergeFacts shows it: `if newFact.Type == existing.Type { merged.Origin = winner.Origin }`). When the incoming and stored types agree, the merged fact takes the identity winner's origin. The winner is the incoming fact when it states the same thing and newFactWins (higher confidence, or equal confidence and at least as many sources). Probed with same text and incoming confidence 0.9 over stored 0.6:
- stored synthesis/distilled, incoming synthesis with explicit origin authored -> stored becomes authored (pipeline output credited to a human).
- stored synthesis/authored, incoming synthesis distilled -> becomes distilled.
- stored hypothesis/discovered, incoming hypothesis with origin UNSET -> becomes authored, and the hypothesis-merge note says nothing about origin.

The third row is the realistic one: the tool tells agents to leave origin unset for facts they write directly, an unset origin is elided on disk, and a non-synthesis type reads an elided origin back as authored (an elided origin on a synthesis reads back as distilled). So an agent re-learning a discovery-engine prediction verbatim at higher confidence silently relabels it.

CONSEQUENCE. Do not assume a learn merge preserves origin. If a stored fact's origin matters (evidence-weight gating reads it, and decision kb/decisions/mcp/origin-by-grouping-method/e532ec2a.md says origin records how the candidate group was formed), pass distinct_from or check the result. Origin cannot be repaired with knomit_update (it is immutable): the fix is retract plus re-learn.

STATUS. This is NOT a ruling. Reviewers proposed two follow-ups for the user to choose between: (minimum) an unset incoming origin never replaces the stored one; (fuller) origin always stays with the stored fact, as kind and type now do. Neither is built. Re-read the code before relying on this: if mergeFacts no longer has the same-type branch, retract this fact.

WHAT THIS DOES NOT MEAN. When the types DIFFER, origin stays with the stored fact (the type-keep ruling, #643). It is not specific to hypotheses; the three rows span synthesis and hypothesis.
