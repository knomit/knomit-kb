# mcp-go v0.45.0 Client.ListTools already follows nextCursor itself (no repeated-cursor guard); one page per call is Client.ListToolsByPage, which LoadPrefix uses

In github.com/mark3labs/mcp-go v0.45.0, client.Client.ListTools calls ListToolsByPage and then loops while result.NextCursor != "", appending each page (client/client.go, ListTools). So a caller of ListTools gets the whole list even under a server pagination limit, and its NextCursor is always empty. The loop has no guard against a server that returns the same cursor again. The server side (server/server.go listByPagination) applies WithPaginationLimit AFTER the tool filters, so a permission-filtered list pages correctly.

Consequence: a reviewer or test that reads "ListTools called once, no cursor loop" as truncation is wrong at this version; and a test that wants to see a short page must call ListToolsByPage. knomit's mcp.LoadPrefix pages explicitly with ListToolsByPage, follows nextCursor, and fails on a repeated cursor; TestLoadPrefix_PagesToolsList runs it on the real server with WithPaginationLimit(4) for a writer and a reader, checks that one raw ListToolsByPage page is shorter than the set and has a cursor, and that the paged result equals the unpaged one. Pin the version: a later mcp-go could change ListTools.
