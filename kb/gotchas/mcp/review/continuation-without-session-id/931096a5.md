# A knomit_review call carrying `response` but no `session_id` silently STARTS a new session. That abandons the caller's own active session on the same (tool, branch), re-serves the same first cluster with progress reset, and discards the answer

ReviewHandler (internal/mcp/review.go) dispatches on `case sessionID == ""` FIRST and calls reviewer.StartSession, so `response`, `item_id` and `completion_token` on the same call are never read and nothing reports that they were dropped. StartSession calls CreatePipelineSession(tool, branch, ...), and that marks EVERY active pipeline_sessions row with the same `tool` AND `branch` as 'abandoned' before inserting the new one. The only trace is the new result's `abandoned_session` field, and it holds the caller's OWN previous session id.

Consequence: an agent that keeps passing `binding` but drops `session_id` on its continuations loops forever. Each call opens a fresh session from the same unchanged watermark, gets the same first cluster (under a new item id) with progress completed=0 and remaining unchanged, and its keep/merge answer is never applied. A later continue on the original id fails with `session "<id>" is abandoned, not active`. Reproduced 2026-09-24 over the real API router on the unscoped mount: five answers without session_id produced five sessions, each abandoning the one before, with remaining constant.

Related shape: the (tool, branch) key is NOT a per-binding or per-client key. Two unscoped clients that bind the same repo get different handles but the same agent branch, so a second client's start displaces the first client's review. That case is LOUD: the loser's next continue returns `... is abandoned, not active`.

WHAT THIS DOES NOT MEAN: binding handles do not mix sessions. A continuation that carries the right session_id reaches its session under any valid handle to the same repo, including a second handle from the same client or another client's handle. The handle picks the branch; it plays no part in finding the session.
