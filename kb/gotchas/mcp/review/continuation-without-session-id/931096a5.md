# A knomit_review answer without its `session_id` is REFUSED; before the fix it silently started a new session, abandoning the caller's own and re-serving the same first item with progress reset, so an agent that dropped session_id looped forever

CURRENT RULE: a knomit_review call carrying `response`, `item_id`, `completion_token` or `page` without `session_id` is refused with an error naming session_id. Nothing is applied, and no session is started or abandoned (ReviewHandler, internal/mcp/review.go, checked before the start/continue dispatch). knomit_hypothesize refuses a `response` or `item_id` without `session_id` the same way. A knomit_review response must also carry `item_id`. `session_id` with no response re-serves the current item. Every review and hypothesize result carries a `next` line naming the session_id (and item_id) to pass. On the unscoped endpoint that line says to pass the binding and that the binding is not the session.

THE FAILURE THIS CLOSED (seen 2026-09-24 from Cowork scheduled tasks on the unscoped mount): the review handler dispatched on `case sessionID == ""` first. A call without session_id was therefore a START, whatever else it carried. The start abandoned every active pipeline_sessions row with the same `tool` AND `branch`, which was the caller's own session. It then re-planned from the unchanged watermark and served the same first cluster (under a new item id) with progress reset. The answer was never read. The only trace was the result's `abandoned_session`, which held the caller's OWN previous id. Symptom: "every continuation silently abandoned its own session and re-served the identical first item, stuck at N remaining, regardless of keep or merge". knomit_hypothesize had the identical shape.

WHY A MODEL DROPS session_id: on the unscoped endpoint two opaque values flow through these calls. `binding` must go on every call, and a model can take it to carry its state. Single-page items carried no hint naming session_id. The fix answers both: the refusal is loud, and every result names the session_id.

WHAT THIS DOES NOT MEAN: binding handles never mixed sessions. A continuation that carries the right session_id reaches its session under any valid handle to the same repo. The separate parallel-start problem (two callers on one branch displacing each other) is decided in the resume-not-displace decision.
