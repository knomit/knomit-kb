# knomit_update REQUIRES moment_name and validates it, then never records it: the commit subject is always "update: <fact title>", so a corroborate:/contradict: label passed as moment_name is unrecoverable from git

internal/mcp/update.go reads moment_name, refuses it if empty or multi-line (checkMomentName), and then does not use it again: the commit message is built as fmt.Sprintf("update: %s", fact.Title). knomit_learn and knomit_retract do carry their moment_name into the commit, so the asymmetry is easy to miss.

Consequence: any convention that puts meaning in an update's moment_name — e.g. the mission runbook's `corroborate: <evidence path>` / `contradict: <evidence path>`, counted with `git log --grep` — measures zero even when sessions follow it exactly. Observed in the first IPO mission rehearsal (2026-10-02, 9c8129bb): two updates the session reported as "contradict: …" and "corroborate: …" appear in git only as `update: <title>` with the Knomit-Trace/Cause/Run trailers.

What to do until it changes: record the corroborate/contradict label somewhere that is persisted (the fact body or refs, or the task's ack), or measure from confidence changes in knomit_explain history. What this does NOT mean: the trace trailers are still written on updates; only the moment label is lost. It also contradicts the claim in kb/invariants/mcp/write-tools/moment-name-one-line/6c691ae7 that moment_name is copied into the commit message for all three write tools — true for learn and retract only.
