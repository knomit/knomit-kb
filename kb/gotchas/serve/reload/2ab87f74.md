# Reload re-runs the boot loader, so KNOMIT_PORT, KNOMIT_HTTP, KNOMIT_HOST, KNOMIT_TLS_ADDR and KNOMIT_LOG_LEVEL in the SERVER's own environment keep beating knomit.toml: a supervisor that spawns the server with any of them silently defeats Settings edits and reloads

MECHANISM (knomit#497 merge 4a9018c4; cmd/serve.go): one `loadCfg` closure (config loader plus flags) feeds BOTH boot and every reload, and a reload does not re-read the process environment: the server's env is the one it started with. Environment variables beat knomit.toml in that loader. So a toml edit followed by a reload moves nothing for any key the server's environment sets, and the reload still reports success (generation advances, the listener keeps its old address).

CONSEQUENCE FOR THE DESKTOP SUPERVISOR (PR 4/PR 6): never set KNOMIT_PORT, KNOMIT_HTTP, KNOMIT_HOST, KNOMIT_TLS_ADDR or KNOMIT_LOG_LEVEL in the environment of the server it spawns, and pass the user's environment through unchanged. tools/desktop/settings.go `OverriddenByEnv` reads the desktop's own env, which a child inherits, so the Settings UI's 'overridden by environment' indication stays consistent only under that rule. Nothing in tools/desktop sets them today (no Setenv, no cmd.Env), so this is a constraint on future code, not a present defect. The e2e harness sets KNOMIT_PORT in the server env deliberately, which is fine for it.

OBSERVED: a run with KNOMIT_PORT exported in the server's environment kept the old port after a toml port change and reload; the cmd test sets KNOMIT_PORT for that reason.

NOT MEANT: this is not a reload defect, boot and reload agree. It also does not mean the CLI's environment matters: `knomit reload` runs in the caller's environment, but only the server's own env is read at reload.
