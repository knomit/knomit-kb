# Attaching a forge whose main is BEHIND local main makes the first origin round force-update local main to the forge's; it heals only when the agent branch descends from the forge main, and a DIVERGED forge main replays the hub's branch onto it

Observed while building PR #529 (reproduced from the log: 'reconcileMain: ... force-updated'). On the master, the origin round that AttachOrigin starts trusts the forge's main as fetched, rewinds included (kb/architecture/fleet/master-merges/91e3f6da.md). So attaching a forge before pushing to it lets that first round move LOCAL main to the forge's main. If the agent branch descends from the forge's main (the forge is empty or merely behind), the round heals itself within the same round and nothing is lost. If the forge's main has DIVERGED, the hub's branch is replayed onto it, mixing two histories. CONSEQUENCE: anything that points the master at a forge with history of its own must push (seed) first and let the forge refuse a diverged main, as moveFleetToForge does (kb/invariants/fleet/move/onto-forge/d83bd272.md). A test of 'the seed matters' must use a diverged forge: with an empty or behind forge, removing the seed leaves the test green (verified by sabotage), because the first round publishes main anyway.

MISREADING: 'the attach is safe whatever the forge holds because the round heals': only when the forge is an ancestor of the agent branch.
