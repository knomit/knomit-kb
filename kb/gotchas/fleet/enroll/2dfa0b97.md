# EXPECTED BEHAVIOUR (user ruling 2026-10-17): enroll's existing-id check reads MAIN only, so on a forge-hosted master whose first enroll could not publish (the leaf is only on the master's agent branch) a second enroll of the same id issues a second leaf, and the first stays valid but unreachable by the revoke route

USER RULING (2026-10-17), verbatim: "it's OK - it's the expected behavior. I mean, if you register on a master that has no access to the forge what can we do ?" This is NOT a defect awaiting a fix: the earlier wording "to be closed in PR 8" is withdrawn. Do not file it as debt or close it unasked; the operational rule below is the answer.

THE BEHAVIOUR (PR #525, accepted at review, verified at merge commit fd991d4f). Both the existing-id check (the enroll invariant, same PR) and revoke read the fleet through `fleetAtMain`. A FORGE-hosted master's enroll commits certs/<id>.pem and issued/<serialA>.pem on its AGENT branch, then publishes (pushFleet: agent branch, then main without force). If that publish fails the answer is 201 with `published: false` and a `publish_error`, and main does not hold leaf A. An operator who then enrolls the SAME id again (instead of waiting for the sync loop to publish) finds no leaf on main, passes the check, and issues leaf B, even for ANOTHER key because the key comparison reads main too. certs/<id>.pem on the agent branch is now B; main later gets B, and A's issued/<serialA>.pem reaches main with it. If bundle A was already installed on the joiner, A is a valid leaf that POST /fleet/revoke can never reach (it finds serials only through certs/<id>.pem): the same failure the enrolled-id rule prevents, in a narrower case.

WHY IT IS ACCEPTED NOW. It needs a failed publish that the answer already flags AND an operator who re-enrolls before the sync loop publishes. A's issuance record is on main eventually, so a serial-aware revoke can still reach it. Revoke is a manual master duty anyway (kb/decisions/fleet/membership/leave-means-revoke/97126da4.md). A KNOMIT-HOSTED master is not affected: its publish is a local fast-forward of main.

THE TWO POSSIBLE FIXES, neither of which is owed (the ruling above makes this expected behaviour; recorded only in case the user reopens it): (a) run the existing-id check against the master's AGENT-branch tip, a superset of main for the master's own writes (the cheapest change: `fleetAtMain` -> the agent tip); (b) make leave/revoke revoke every issued/<serial> for the id that is not on the CRL, not only certs/<id>.pem.

OPERATIONAL RULE until then. After an enroll answers `published: false`, do not enroll that id again until main holds the leaf (the answer's publish_error says why; the sync loop retries); and never hand a bundle to a joiner before `published` is true.
