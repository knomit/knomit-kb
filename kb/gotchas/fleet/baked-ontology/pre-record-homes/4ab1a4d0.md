# A dev-built fleet created through the old `preset: fleet` path (or a fleet registered before PR #520, which has no recorded uid) boots as fleet_conflict; the way out is archive then join again (POST /api/v1/fleet/join), and there is no migration by design

Only the fleet-door mounts write control.db instance_fleet_repo (CreateFleet and, since PR #525 replaced RegisterFleet, JoinFleet), and the record was added in PR #520. A fleet repository that already existed on a dev build has no recorded uid, so at boot it is refused at Identify and listed unavailable with cause fleet_conflict. Two shapes:
- a fleet HOST created locally through the old `preset: fleet` create path: no door can make it again (preset fleet is now refused); archive then purge it.
- a MEMBER registered by an older build: archive it, then join again: it needs the master to enroll the instance's key first (POST /api/v1/fleet/enroll, which refuses `enrolled` while the old leaf on main is not revoked: the master revokes it first), then POST /api/v1/fleet/join with the new bundle. Join works only while the fleet state is standalone, no fleet repository is mounted or recorded (fleet_present otherwise) and no trust material is installed (trust_installed otherwise: leave, which runs Uninstall, or move the files out). The `unregistering` stuck state no longer exists (PR #525 deleted it; leave removes the fleet here at once).

No backfill or migration exists on purpose: no release contains any fleet code (v0.5.3 has none), so a backfill would be dead weight.

MISREADING: fleet_conflict does not mean data loss or a second real fleet. Nothing is archived or deleted automatically, and the repository's database is intact until the user archives it. Also see the baked-ontology reserved-id invariant for the rule that makes any new create/join path record its uid.
