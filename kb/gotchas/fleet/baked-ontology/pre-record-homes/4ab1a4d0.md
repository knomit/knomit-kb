# A dev-built fleet created through the old `preset: fleet` path (or a fleet registered before PR #520, which has no recorded uid) boots as fleet_conflict; the way out is archive then register again, and there is no migration by design

Only RegisterFleet writes control.db instance_fleet_repo, and it was added in PR #520. A fleet repository that already existed on a dev build has no recorded uid, so at boot it is refused at Identify and listed unavailable with cause fleet_conflict. Two shapes:
- a fleet HOST created locally through the old `preset: fleet` create path: no door can make it again (preset fleet is now refused); archive then purge it.
- a MEMBER registered by an older build: archive it, then `knomit fleet register <url>` again. That works while the fleet state is `registered` and no fleet is mounted. In state `unregistering` the instance stays stuck (there is no archive escape any more and the unregistration retries on every sync): an accepted pre-release window; the immediate-leave change closes it.

No backfill or migration exists on purpose: no release contains any fleet code (v0.5.3 has none), so a backfill would be dead weight.

MISREADING: fleet_conflict does not mean data loss or a second real fleet. Nothing is archived or deleted automatically, and the repository's database is intact until the user archives it. Also see the baked-ontology reserved-id invariant for the rule that makes any new create/join path record its uid.
