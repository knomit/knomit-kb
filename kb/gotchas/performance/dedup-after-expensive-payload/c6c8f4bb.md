# A dedup check cannot save you if the payload is computed BEFORE the check runs — when an iterator returns (key, payload) together, the payload is paid unconditionally

THE SHAPE (reusable, not specific to commit_log): when an iterator contract hands back a key and its payload TOGETHER, the payload is computed unconditionally — including for every key the consumer is about to reject. A cheap dedup/skip check placed AFTER the expensive work does not gate it; it only discards the result. Look for this wherever a producer callback returns `(id, heavyThing, error)` and the consumer's first act is a membership lookup on `id`.

WORKED EXAMPLE (PR 71). `storegit.Storer.CommitLogSync(branchName, iter)` took `iter func() (hash string, parents []string, entries []CommitLogEntry, err error)`, and its dedup step — `SELECT COUNT(*) FROM branch_commits WHERE branch_id = ? AND commit_hash = ?` — ran only after iter() had returned. In the production caller `repoHandler.populateCommitLog`, producing `entries` means `changedFilesInCommit(c)`, an `object.DiffTree` of the commit against its first parent: ~307 SQLite object loads, ~2 ms per commit. Every repo open re-walks an already-populated DAG, so nearly every commit is a dedup hit. Opening core.db (1831 commits) computed 1831 diffs and threw all of them away: 4.187 s, of which the check was ~0.2% of the walk and the discarded work ~99.5%.

THE FIX: make the payload a thunk. `type CommitLogPayload func() (parents []string, entries []CommitLogEntry, err error)`; iter now returns `(hash string, payload CommitLogPayload, err error)` and CommitLogSync calls `payload()` ONLY after the branch_commits lookup misses. `AppendCommitLog` got the same shape and now also skips `repo.CommitObject(hash)` for an already-recorded commit. Measured: OpenRepo on core.db 4.187 s -> 68.6 ms; boot of 24 repos 35.4 s -> 3.0 s and 37.9 s -> 1.9 s. Output verified identical, not merely faster: after booting all 24 repos on each binary, branch_commits / commit_log / commit_parents row counts and an md5 over every (commit_hash, path, action) row were byte-identical across all four repo shapes.

CONSEQUENCE FOR CONSUMERS OF CommitLogSync: `iter` MUST return the hash cheaply. All per-commit work belongs inside the returned CommitLogPayload. Widening what iter returns eagerly — adding one more field 'while we're here' — silently reinstates the whole regression, because the cost moves back in front of the check. Regression anchors: `TestCommitLogSync_SkipsPayloadForKnownCommits` (re-walk of recorded commits must invoke zero payloads) and `TestPopulateCommitLog_NoTreeReadsForKnownCommits` (deletes the tree objects of recorded commits, so any attempted diff errors outright — the re-walk must still succeed).

WHAT THIS DOES NOT MEAN — 1. It does NOT mean the diff got cheap. The ~307 object loads / ~2 ms per commit are untouched, and are still paid in full wherever the commits are genuinely new: first populate of a freshly cloned repo, `Rebuild` phase 0 via `rebuildCommitLog` (measured 4.9 s of a 14.9 s rebuild — the largest component when embeddings are intact), and migrations that clear commit_log and force a re-walk. Two measured-but-unchased leads for that cost: `merkletrie` appears not to prune subtrees whose hashes match (a one-file commit should cost ~10 tree loads, not ~307; `plumbing/object/treenoder.go`'s `transformChildren` builds a noder for EVERY entry of a tree, which may defeat the prune on wide trees), and `Storer` has NO object cache at all, so consecutive commits re-load trees they just read — commit N-1's tree IS commit N's parent tree; go-git's own filesystem storer fronts this with `cache.ObjectLRU`, ours does not.

WHAT THIS DOES NOT MEAN — 2. It does NOT weaken the DAG walk. A dedup hit still skips-and-continues; every commit is still visited and merge-parent lines still followed. This is the distinction the skip-and-continue invariant implies but does not spell out: you may NOT make the walk shorter, but you MAY make each step cheaper.

TWO DIAGNOSIS CORRECTIONS established by the same measurements, both of which had been asserted earlier and are false: (a) objects are stored UNCOMPRESSED, so there is no zlib decode on this path and per-load latency (6.9 us) is not the problem — the cost is the NUMBER of object loads; (b) open cost is linear in DISTINCT COMMITS ON HEAD, not commits x branches — OpenRepo walks only the HEAD branch and `healIndexBranches`' `SyncLocked` does not populate the commit log, so a repo used from five machines does not pay 5x.
