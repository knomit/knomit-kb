# `<home>/running.marker` is a HEURISTIC, not a lock — its primary job is the unclean-exit warning at the next `serve` boot; as migrate-registry's "is a server up" check it misses a desktop-hosted server entirely and a server on the long-home /tmp socket fallback, and migrate-registry is irreversible

**What the marker is.** `cmd/serve.go` (L132-L143 at d7f01ac1) writes `<home>/running.marker` at boot through `crashdump.NewMarker`, removes it on a clean exit, and deliberately leaves it behind on a panic unwind (`EndUnlessPanicking`). Its PRIMARY consumer is the next `serve` boot: `Marker.Begin` finds the stale file and logs ONE warning, "previous run exited uncleanly (possible crash); see crashes/". That is history about the previous process, which no liveness mechanism can supply: the flock on `knomit.sock.lock` is released on every kind of exit and a Windows pipe name dies with its process (see socket-liveness-flock), so a successor learns nothing from them about HOW its predecessor died. The socket lock therefore does NOT make the marker obsolete (verified 2026-09-27).

**Its second consumer is a heuristic.** `knomit migrate-registry` (`refuseIfServerRunning`, L437-L460) refuses to run while the marker exists. That answers "did a serve start against this home and not shut down cleanly", which is NOT "is a server running against these files right now". It misses in both directions:

- **False negative, the dangerous one, case 1: the desktop app.** `tools/desktop/boot.go` boots the server WITHOUT writing running.marker (it takes the socket lock but never calls crashdump.NewMarker), so a desktop-hosted server is completely invisible to migrate-registry's check. Quit the desktop app before migrating.
- **False negative, case 2: another --home spelling that lands on a DIFFERENT marker file.** For the default layout a symlinked or relatively-spelled `--home` reaches the SAME `<home>/running.marker` inode, so the marker does see it (an earlier revision of this fact overstated this gap). The gap is real when the socket path falls back to `/tmp/knomit-<euid>/<hash>.sock`: that hash is of the home STRING (long-home-fallback), so two spellings of one directory are two different servers as far as any path-derived check goes.
- **False negative, case 3: a serve that exited cleanly while a second one was still up.** Two serves on one home share one marker file; the first one's clean exit deletes it under the second.
- **False positive.** A crashed server leaves the marker behind, so the check fires with nothing running. `--ignore-running-marker` exists for exactly this, and the error message says so.

**Why this matters more than an ordinary race:** migrate-registry is irreversible. Migration `000017` drops the repo connection columns, and only `control.db` is backed up (`VACUUM INTO`). A concurrent writer during the run is not a retry-able failure, it is corrupt data. A stronger form (probe the socket lock, or an advisory lock on `control.db`) was considered and NOT built on 2026-09-27: it would add a two-platform auth probe for a command already marked DEPRECATED and slated for removal, and it would still miss TCP-only servers (path too long, unsafe socket dir, second instance, KNOMIT_SOCKET set for the server but not the tool).

**Operational consequence:** the marker's ABSENCE is not evidence that no server is running. Before migrating a real home, quit the desktop app, confirm by process, and copy the whole home first (the tool backs up only control.db).

**WHAT THIS DOES NOT MEAN:** not that the check is useless and `--ignore-running-marker` should be passed routinely. The flag covers the stale-marker-after-crash case only; passing it while a server IS up produces exactly the corruption the check exists to prevent. And not that the marker should be deleted when migrate-registry goes: the crash-warn role stays.
