# `<home>/running.marker` is a HEURISTIC, not a lock — a server started with a different --home pointing at the same directory is invisible to it, and migrate-registry is irreversible

`knomit migrate-registry` refuses to run while `<home>/running.marker` exists. `cmd/serve.go` writes the marker at boot and clears it on clean exit, so it answers "did a server start against this home and not shut down cleanly" — which is NOT the same question as "is a server running against these files right now".

It misses in both directions:

- **False negative (the dangerous one).** A server started with a *different* `--home` that resolves to the same directory — a symlink, a bind mount, a relative path from another cwd — writes its marker somewhere else, or nowhere this check looks. The migration proceeds against a live database.
- **False positive.** A crashed server leaves the marker behind, so the check fires with nothing running. `--ignore-running-marker` exists for exactly this, and the error message says so.

**Why this matters more than an ordinary race:** migrate-registry is irreversible. Migration `000017` drops the repo connection columns, and only `control.db` is backed up (`VACUUM INTO`). A concurrent writer during the run is not a retry-able failure, it is corrupt data. The stronger form would be an advisory lock on `control.db`; that was recorded rather than built.

**Operational consequence:** the marker's ABSENCE is not evidence that no server is running. Before migrating a real home, confirm by process (and copy the whole home first — the tool backs up only control.db).

**WHAT THIS DOES NOT MEAN:** not that the check is useless and `--ignore-running-marker` should be passed routinely. The flag covers the stale-marker-after-crash case only; passing it while a server IS up produces exactly the corruption the check exists to prevent.
