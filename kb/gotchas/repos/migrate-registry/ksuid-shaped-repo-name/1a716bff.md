# A legal repo NAME can parse as a ksuid — `isValidRepoName` allows `[a-z0-9_-]` with no length cap — so migrate-registry's bare-ksuid guard has a false-positive class (p ≈ 5e-7, and it fails LOUD)

`isValidRepoName` (internal/repos/manager.go) accepts any non-empty string of **lowercase letters, digits, hyphens and underscores**, with **no length limit**. A ksuid is 27 base62 characters; an all-lowercase-alphanumeric one is therefore a legal repo name, and `ksuid.Parse(name)` will succeed on it.

`migrate-registry` keys two guards on exactly that test — a `repos/<name>.db` whose name parses as a ksuid but has no row in the repos table is refused, because that is the wreckage of a half-restored archive, and registering it would leave a repo permanently NAMED after a ksuid.

So a user who genuinely named a repo with 27 lowercase alphanumerics hits a guard meant for wreckage. Probability is roughly **5e-7 per repo** (a random 27-char lowercase-alnum name parsing as valid ksuid), and the failure mode is a **loud refusal naming the file**, which is the safe direction — nothing is silently mis-registered.

**Operational consequence:** if this ever fires on a real repo, the fix is to rename the `.db` file, not to relax the guard. The message already says so ("… not a ksuid first").

**WHAT THIS DOES NOT MEAN:** this is not a bug to go fix. A guard with a ~5e-7 false-positive rate that fails loud and refuses to proceed is the correct tradeoff against silently registering a ksuid-named repo, which is unrecoverable downstream. Tightening `isValidRepoName` to forbid ksuid-shaped names would be a breaking change to the name grammar for a rounding-error case.
