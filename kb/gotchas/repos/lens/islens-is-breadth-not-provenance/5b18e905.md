# Binding.IsLens answers "does this federate across more than its own write repo" — NOT "did the caller connect through a lens"; a single-member lens returns false, and Binding.FromLens is the provenance signal

`Binding.IsLens()` walks `b.reads` and returns true only if at least one read mount is a repo OTHER than `b.write`. That is federation BREADTH. A lens can legally be defined with exactly one member — its own write repo — and such a binding returns `IsLens() == false` even though the caller reached it through `/lenses/<name>/…` and not `/repos/<repo>/…`.

`Binding.FromLens()` (added feb92f80) is the PROVENANCE signal: it reads `strings.HasPrefix(b.pinID, "lens:")`, exploiting the fact that PinID is deliberately prefixed `repo:<uid>` for a synthesized lens-of-one and `lens:<uid>` for a resolved lens definition.

CONSEQUENCE: any code answering "how did this caller connect / which mount configuration is this" must call FromLens. Any code asking "do I have more than one mount to fan out over / is single-repo fast-pathing safe" must call IsLens. The write-destination stamp (internal/mcp/writedest.go) is the first consumer of FromLens: with IsLens it dropped the lens name for a single-member lens, making that result byte-indistinguishable from a direct repo connection — the exact confusion the stamp exists to remove.

WHAT THIS DOES NOT MEAN: FromLens is not a replacement for IsLens. The RFC §9.4 rule that session instructions stay single-repo for a lens-of-one is a BREADTH question and correctly keeps using IsLens; swapping it for FromLens would hand federation prose to a caller with one mount. Nor is FromLens infallible — a uid-less binding mints an empty PinID (pinOf fails closed) and therefore reads as not-from-a-lens, the same four-barriers-unreachable case PinID documents.
