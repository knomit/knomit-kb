# FIXED (PR #639, issue #456): TestTriggers_InlineJSCacheBySource failed under -count>1 because the inline-JS compile cache is process-global; the test now puts a per-run nonce in the trigger source

FIXED by PR #639 (issue #456); merge commit 78a70006. Superseded the earlier "still open" state found by the PR #632 reviewer.

Cause: the inline-JS compile cache in internal/domain/fact (triggers.go, inlineJS) is process-global, keyed by trigger name + sha256 of the source. A second iteration (-count>1) found the changed js already compiled, so the assertion "a changed js compiles once" failed (4 of 5 iterations at -count=5).

Fix (test only): TestTriggers_InlineJSCacheBySource (internal/corpus/repos/triggers_inline_test.go) builds its trigger source with a per-run time.Now().UnixNano() nonce, so every run has its own cache entries. The nonce is fixed within a run, so v(1) and v(2) still differ and the test still asserts exactly +1 compile for a changed js. Reviewer sabotage with a constant nonce: run 1 passes, runs 2 and 3 fail under -count=3, so the nonce is what makes repeats pass. Production code is unchanged: the cache stays process-global by design (see kb/architecture/fact/ontology/triggers/inline-js/09638689.md).

CONSEQUENCE: a -count>1 failure of this test is a real signal again. Any new test that asserts on compile counts of an inline js: trigger must give its source a per-run nonce for the same reason.

DOES NOT MEAN: that the cache is per-test or resettable. TestTriggerCache_ChangedIfRunsNewProgram (internal/domain/fact) is a different flake and not this cache; see its own gotcha.
