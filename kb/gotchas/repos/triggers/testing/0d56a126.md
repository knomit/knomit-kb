# TestTriggerCache_ChangedIfRunsNewProgram can still time out under heavy load: EvalIf's 100ms ruleEvalTimeout is a const; the test now reports the timeout, it does not prevent it

CAUSE of the TestTriggerCache_ChangedIfRunsNewProgram flake (internal/domain/fact/triggers_test.go): it is NOT the inline-JS compile cache (the test uses a local TriggerCache). CompiledTrigger.EvalIf interrupts its goja VM after ruleEvalTimeout, a package const of 100ms (internal/domain/fact/validation.go), and the test used to discard EvalIf's error, so on a loaded machine a timed-out evaluation returned false and surfaced as a misleading "signal should match".

WHAT PR #639 CHANGED: only the test. It uses mustEvalIf, which fails with "EvalIf errored: ..." so a timeout reports as a timeout. It does NOT make the test pass under load.

STILL OPEN: the test can still fail under heavy load, now with a clear timeout error. A real fix needs a per-call timeout (EvalIf taking or reading a configurable budget), which is a production change that has NOT been made; because the const is shared with rule evaluation, do not raise it just to quiet one test.

CONSEQUENCE: a failure whose message is "EvalIf errored: ... exceeded 100ms" is load, not a regression in trigger caching; a failure of the old form ("signal should match") would now indicate a real wrong program.
