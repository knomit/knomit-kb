# TestTriggerCache_ChangedIfRunsNewProgram can still time out under heavy load: EvalIf's 100ms ruleEvalTimeout is a const; the test now reports the timeout, it does not prevent it

CAUSE of the TestTriggerCache_ChangedIfRunsNewProgram flake (internal/domain/fact/triggers_test.go): it is NOT the inline-JS compile cache (the test uses a local TriggerCache). CompiledTrigger.EvalIf interrupts its goja VM after ruleEvalTimeout, a package const of 100ms (internal/domain/fact/validation.go), and the test used to discard EvalIf's error, so on a loaded machine a timed-out evaluation returned false and surfaced as a misleading "signal should match".

WHAT PR #639 CHANGED: only the test. It uses mustEvalIf, which fails with "EvalIf errored: ..." so a timeout reports as a timeout. It does NOT make the test pass under load.

CLOSED BY #645 (merge ce64a9bc): the test no longer times out under load. CompiledTrigger has an UNEXPORTED evalTimeout field (internal/domain/fact/triggers.go); ifBudget() returns it when > 0, else ruleEvalTimeout. Only in-package tests set it: mustEvalIf in triggers_test.go sets one minute. Production never sets it (the only constructor, compileTrigger, leaves it zero), so production EvalIf is still exactly 100ms. TestEvalIfDefaultBudgetIs100ms pins both the const and the default budget. The shared ruleEvalTimeout const is unchanged and rule validation (validation.go) still uses it directly; do not raise it to quiet a test.

NOT A TESTSEAMS DOOR: the test is in package fact, so an unexported field needs no mustBeTest export and the testseams archtests (which match *ForTest / Testing* names and the trigger/ and store/ testseams files) do not apply. A production write to evalTimeout would be a bug.

PINNED (the earlier 'STILL UNPINNED' line was stale; checked against HEAD at the #646 merge ff045df3): TestEvalIfUsesIfBudget sets evalTimeout to 37ms on a trigger whose `if` is a busy loop and requires the error to say 'exceeded 37ms'; an EvalIf that read ruleEvalTimeout directly would report 'exceeded 100ms' and fail it. TestEvalIfDefaultBudgetIs100ms separately pins ifBudget() and the const.

CONSEQUENCE: after #645, "EvalIf errored: ... exceeded 100ms" from this test would NOT be load (its budget is a minute); treat it as a real regression (for example mustEvalIf losing its override). A failure of the old form ("signal should match") would indicate a real wrong program. The 100ms behaviour that remains in production (since #646 it bounds the condition alone, after setup) is described in kb/gotchas/repos/triggers/if-budget/a23be27e.md.
