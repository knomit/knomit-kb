# Two quick `on: learn` seeds against a `do: run` recipe with the default concurrent:1 can COALESCE into one dispatcher pass, and then phase B starts both fires ~1 µs apart, so the second is ALWAYS a `busy` row (dropped, never retried) — a test that expects one run per seed must give the recipe `// knomit: {"concurrent": N}` or wait between seeds

This is the testing consequence of the runner's 'full -> busy row, no queue' rule (kb/architecture/repos/triggers/recipes/runner/e3a210c6.md).

Mechanism (origin/dev dfaaa48b):
- A recipe without a header gets RecipeDefaultConcurrent = 1 (internal/fact/recipe.go:27; the header prefix is `// knomit:`, on line 1, as strict JSON).
- startRecipe (internal/repos/trigger_recipe.go:296) uses a non-blocking tryTake. When the slot is taken, the fire is recorded with outcome `busy`, error 'recipe <name> is at its limit of N concurrent run(s); the fire is dropped', and run_id "".
- Only `on: due` busy fires are retried (triggers.go:1389, rs.dueRetry). An `on: learn` busy fire is gone for good. This is intended and documented (openapi.yaml 'DROPPED, not queued'; examples/mission/README.md).
- When the dispatcher picks up two commits in ONE pass, it emits one fire per (trigger, path) in sorted path order and starts them back to back. A second fire against a concurrent:1 recipe therefore finds the slot held every time, not just sometimes.

Seen in #409: TestREST_TriggersByRun seeded kb/tasks/a/fire.md and fire-2.md back to back, then waited for two runs. It failed 14/50 locally and on ubuntu and macOS CI. The fire rows showed one run row, fire-2.md started and done, and fire.md busy. When the two seeds landed in separate passes (the log order shows a recipe finish between the two fires), the test passed. Fixed by giving the test's recipe `// knomit: {"concurrent": 2}`; TestRun_RunIDCorrelates already uses concurrent:3 for the same reason.

Consequence: any test (or mission template) that writes several facts quickly and expects one recipe run per fact must either raise `concurrent` or serialise the writes on observed results. Not meant: this is not a dispatcher bug, and coalescing is not lost fires. Both fires ARE emitted; the cap drops the second.
