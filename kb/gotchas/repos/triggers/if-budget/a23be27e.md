# A trigger `if`'s 100ms budget starts before the globals are frozen, so under heavy load a trivial condition can be recorded as if-timeout because deepFreeze was slow (current behaviour, not a ruling)

CURRENT BEHAVIOUR at #645 merge ce64a9bc (internal/domain/fact/triggers.go, EvalIf). The time.AfterFunc that interrupts the goja VM with 'trigger <name>: if exceeded 100ms' is armed BEFORE sandboxGlobals runs (the frozen JSON copies of the globals, built with deepFreeze), and only then is the user's `if` program run. So the 100ms budget bounds global setup PLUS the condition, not the condition alone. A sandboxGlobals error is returned as-is; the interrupt fires wherever the VM happens to be.

EVIDENCE (PR #645 review, load runs on the parent commit): most failures were interrupted inside deepFreeze ('global fact: ... if exceeded 100ms at f (deepFreeze:...)'), before the condition ran.

CONSEQUENCE. Under heavy CPU load production can record if-timeout (the dispatcher's classification of an interrupted EvalIf, internal/corpus/repos/trigger/trigger_stats.go) for a trivial condition such as `fact.type === 'x'`, because freezing the globals was slow; the trigger is then treated as not matching. An if-timeout is therefore not proof the CONDITION is slow. Production still uses exactly ruleEvalTimeout: the evalTimeout override exists only for in-package tests (kb/gotchas/repos/triggers/testing/0d56a126.md).

WHAT THIS DOES NOT MEAN. It is not a ruling that setup should be inside the budget; it may be intended, and nothing here says to change it. It is also not specific to large globals: it was observed on small ones under load.
