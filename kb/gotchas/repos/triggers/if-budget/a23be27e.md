# A trigger `if`'s 100ms budget starts AFTER the globals are frozen (bindGlobals), so it bounds the condition alone; before #646 it also covered deepFreeze and a loaded machine recorded a trivial condition as if-timeout

CURRENT BEHAVIOUR since #646 (merge ff045df3; supersedes the #645-era text, which said the budget covered setup). CompiledTrigger.EvalIf (internal/domain/fact/triggers.go) builds a fresh VM, then calls bindGlobals, which runs sandboxGlobals (the frozen JSON copies of the globals, built with deepFreeze) and then the test-only afterSetup stand-in, and ONLY THEN arms the time.AfterFunc that interrupts the VM with 'trigger <name>: if exceeded <budget>' and runs the user's `if` program. ifBudget() (ruleEvalTimeout, 100ms, unless an in-package test set evalTimeout) therefore bounds the user's condition ALONE. A sandboxGlobals error is returned before any timer exists. An if-timeout now means the CONDITION ran past the budget.

HISTORY. Before #646 the timer was armed before sandboxGlobals, so under heavy CPU load a trivial condition such as `fact.type === 'x'` was recorded as if-timeout (the dispatcher's classification, internal/corpus/repos/trigger/trigger_stats.go) because deepFreeze was slow. Load check on 2000 evaluations with CPU hogs: about 630 if-timeouts per run on the parent commit, all inside deepFreeze, 0 after the fix.

TEST SEAM. afterSetup is an unexported CompiledTrigger field that only in-package tests set (compileTrigger leaves it nil). bindGlobals runs sandboxGlobals and afterSetup as ONE step so the seam cannot sit outside the budget while the real setup sits inside it; TestEvalIfBudgetExcludesSetup goes red if the bindGlobals call moves after the timer. Moving only the seam, with the real setup copied elsewhere, is not caught.

No user code runs between setup and the timer: the globals are host Go maps, JSON.parse (no reviver) yields plain data, deepFreeze is host-authored, and the VM is fresh.

WHAT THIS DOES NOT MEAN. It does not mean setup is bounded: nothing limits it (see the user ruling in kb/decisions/repos/triggers/if-budget-setup-unbounded/05cb1404.md). evaluateRule (validation.go, rules) already armed its timer after the fact was bound; it never had this shape. script.go's runSandboxed still arms its budget (ScriptEvalTimeout, 5s) before setup; it was deliberately left out of #646 because it has far more headroom and the same AfterFunc also carries dispatcher cancellation.
