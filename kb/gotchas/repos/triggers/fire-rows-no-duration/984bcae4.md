# Fire-log rows store ZERO in every duration column (duration_ms, diff_ms, change_ms belong to the run row only), so a per-fire `host_ms` cannot go on the row without a migration — F07 PR 3 puts `host_ms` on the slow WARN line and subtracts it from the trigger's own duration (statistics, p95, slow detector), and OpenAPI declares no TriggerFire.host_ms

RecordTriggerRuns (internal/store/triggers.go) inserts fire rows with `0, 0, 0, 0, 0, 0, 0` for evaluated/paths/fires/fires_not_logged/duration_ms/diff_ms/change_ms; only the run row carries the run's durations. The proposal's "the fire-log row's duration_ms carries host_ms" was therefore not built (stated deviation). What exists: phase B computes `elapsed = time.Since(t0) - hostMS` where hostMS is the time spent inside host calls (`scriptHost.spent`), records that as the trigger's own work, and logs `host_ms` next to `change_ms` on the "slow trigger" WARN. A script that is slow in its OWN JavaScript trips the detector; one that makes many calls shows it in host_ms on the WARN, not in the table.
