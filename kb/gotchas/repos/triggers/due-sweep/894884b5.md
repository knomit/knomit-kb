# The due sweep must deduplicate candidate rows per PATH and re-check the mark against the HEAD's instant, not the candidate row's: a stale candidate (the index behind the ref, or a test feeding the removed path) whose HEAD version carries a different, already-past `expires` would otherwise fire once per candidate row and again on every run

Found while writing TestDue_RemovedBeforeItsDateNeverFires/update_change (F07 PR 2). The test feeds every run a STALE candidate row for the removed path with the OLD instant through the dueCandidates hook, next to the join's row with the NEW instant. A first draft of sweepDue kept one hit per candidate ROW and compared the mark to the ROW's instant: both rows survived the mark filter (no mark yet), both confirmed at the head (the new date had passed), so the same (trigger, path) fired TWICE in one run; and on later runs the stale row (old instant ≠ the mark's new instant) kept passing the filter, confirmed at the head, and fired AGAIN every run.

The rule now: (1) hits are keyed by path, triggers unioned (appendTrigger), so N candidate rows for one path are one confirmation and at most one fire per trigger; (2) after the head confirmation the mark is compared with the HEAD's instant (`marks[key] == *at` → done), because the head is the truth and the candidate row may describe a version the ref has already replaced. The pre-confirm filter still uses the row's instant (it is the cheap filter; a mismatch there only costs one blob read). In production the join lists a path once (UNIQUE(branch_id, path)) and the index lags the ref by milliseconds, so the shape is rare — but 'rare' is how a double fire hides. Sabotage that reddens the test: compare with the candidate's instant after the confirm, or key hits by row.
