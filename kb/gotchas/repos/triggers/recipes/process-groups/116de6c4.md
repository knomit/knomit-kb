# Killing a recipe's program means killing its GROUP: Unix needs Setpgid + Cancel=kill(-pgid, SIGKILL) + WaitDelay (a grandchild holding stdout otherwise keeps Wait blocked), and Windows needs a job object with KILL_ON_JOB_CLOSE whose limit must be CLEARED before CloseHandle after a clean exit — else closing the handle kills a grandchild the recipe detached on purpose; but under the Windows DESKTOP the server's jobs nest inside the desktop's own kill-on-close job, so a detached grandchild still dies with the desktop (measured)

internal/corpus/repos/trigger_recipe_exec_unix.go / _windows.go (F07 PR 5, H5, M3, R2-1).

Unix: SysProcAttr{Setpgid: true} at fork; cmd.Cancel kills -pid (ESRCH → os.ErrProcessDone); cmd.WaitDelay = 2 s. A finished exec's group is never signalled, so a detached grandchild survives (status `spawned`).
Windows: CreateJobObject + SetInformationJobObject(JobObjectExtendedLimitInformation, LimitFlags=KILL_ON_JOB_CLOSE) BEFORE Start; after Start, OpenProcess(PROCESS_SET_QUOTA|PROCESS_TERMINATE, pid) (os.Process exposes no handle) → AssignProcessToJobObject → CloseHandle; Cancel = TerminateJobObject (falls back to Process.Kill when the child never made it into the job; `assigned` is an atomic.Bool because Cancel runs on another goroutine). On a clean exit the limit is set back to 0 before the job handle is closed; on timeout/stop it is closed with the limit set.
Known gap (not hardened): a child that forks before AssignProcessToJobObject leaves that grandchild outside the job — os/exec has no suspended start. Tests therefore fork only after a go-signal: the test hook recipeExecHooks.afterStart(pid), called right after the assignment (after Start on Unix), writes <dir>/go-<pid> which the helper polls (TestRun_TimeoutKillsProcessGroup, TestRun_CleanExitLeavesDetachedGrandchild). x/sys v0.46.0 has no IsProcessInJob, and "am I in any job" would be the wrong signal anyway on a CI host that runs tests inside a job.
The Windows half was only type-checked locally; windows-2025 CI is its proof — T7 and T7b passed there on #346's runs 36501228915 and 36502965917.

UPDATE (PR #503, merge 8be999a0; MEASURED on Windows 10 22H2, 2026-10-12): the 'detached grandchild survives a clean exit' guarantee above holds only for a `knomit serve` run OUTSIDE the desktop. The desktop's supervisor (tools/desktop/supervisor_windows.go) puts the spawned `knomit serve --supervised` into its own job object with KILL_ON_JOB_CLOSE and, unlike the recipe code, NEVER clears that limit. Windows job objects nest, and the server's per-recipe jobs are created inside it, so every process a recipe starts - including a grandchild it deliberately detached (`Start-Process ping -n 777 -WindowStyle Hidden` from a recipe's exec) - is also a member of the desktop's job. When the desktop exits or is killed the job closes and the grandchild dies with it: observed 0.2 s after `taskkill /F` of the desktop (the detached ping first, the server 0.2 s later). A desktop Quit closes the same job by construction (not separately tested). On macOS and Linux the same grandchild OUTLIVES a desktop quit (its own process group; nothing kills it), so the platforms now differ; this is probably the intended policy ('nothing the server starts outlives the desktop') but it was never stated as a decision.
CONSEQUENCE: a recipe that needs a long-lived detached helper cannot rely on it surviving the desktop on Windows; run `knomit serve` outside the desktop (or as a service) for that. Do not 'fix' it by clearing the limit in supervisor_windows.go without also deciding what happens to the server when the desktop dies (the job is what ends it, kb/gotchas/desktop/windows/supervisor).
