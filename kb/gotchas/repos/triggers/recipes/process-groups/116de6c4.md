# Killing a recipe's program means killing its GROUP: Unix needs Setpgid + Cancel=kill(-pgid, SIGKILL) + WaitDelay (a grandchild holding stdout otherwise keeps Wait blocked), and Windows needs a job object with KILL_ON_JOB_CLOSE whose limit must be CLEARED before CloseHandle after a clean exit — else closing the handle kills a grandchild the recipe detached on purpose

internal/repos/trigger_recipe_exec_unix.go / _windows.go (F07 PR 5, H5, M3, R2-1).

Unix: SysProcAttr{Setpgid: true} at fork; cmd.Cancel kills -pid (ESRCH → os.ErrProcessDone); cmd.WaitDelay = 2 s. A finished exec's group is never signalled, so a detached grandchild survives (status `spawned`).
Windows: CreateJobObject + SetInformationJobObject(JobObjectExtendedLimitInformation, LimitFlags=KILL_ON_JOB_CLOSE) BEFORE Start; after Start, OpenProcess(PROCESS_SET_QUOTA|PROCESS_TERMINATE, pid) (os.Process exposes no handle) → AssignProcessToJobObject → CloseHandle; Cancel = TerminateJobObject (falls back to Process.Kill when the child never made it into the job; `assigned` is an atomic.Bool because Cancel runs on another goroutine). On a clean exit the limit is set back to 0 before the job handle is closed; on timeout/stop it is closed with the limit set.
Known gap (not hardened): a child that forks before AssignProcessToJobObject leaves that grandchild outside the job — os/exec has no suspended start. Tests therefore fork only after a go-signal: the test hook recipeExecHooks.afterStart(pid), called right after the assignment (after Start on Unix), writes <dir>/go-<pid> which the helper polls (TestRun_TimeoutKillsProcessGroup, TestRun_CleanExitLeavesDetachedGrandchild). x/sys v0.46.0 has no IsProcessInJob, and "am I in any job" would be the wrong signal anyway on a CI host that runs tests inside a job.
The Windows half was only type-checked locally; windows-2025 CI is its proof.
