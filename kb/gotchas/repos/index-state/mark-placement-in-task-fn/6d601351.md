# Marking the index state in the HANDLER instead of inside the task fn is the stuck-indexing failure by a new route: the loser of the single-flight marks `indexing`, returns 409, and no task is left to ever clear it — and every test of the feature still passes

`MarkIndexRebuildStart()` runs INSIDE the function passed to `hub.Start`, not beside the 409 check in the handler. The placement is the whole of the correctness, and moving it two lines up is silently catastrophic.

WHY. `hub.Start("rebuild", ...)` is a per-op single-flight: when a rebuild is already running it returns an error and the task fn NEVER RUNS. With the mark inside the task fn, the loser of that race reaches no mark at all — correct. With the mark in the handler, the loser marks `indexing`, then `hub.Start` fails, then the handler returns 409 — and there is no task to reach a terminal. **The index is pinned at `indexing` forever**, which is the 2026-08 stuck-indexing failure arriving through a route that incident never touched.

THE PART WORTH INTERNALISING: this passed EVERY test written for the feature. The rebuild-succeeds test, the 409-while-indexing test, the failure-marks-error test and the bracket's unit test are all green against it, because each drives a path where the mark and its terminal both run. Only a request that is REFUSED BY THE HUB distinguishes the two placements, and that case had no assertion about index state — it checked the status code and the problem title.

HOW IT WAS FOUND, and the method generalises. A mutation matrix that included a REARRANGEMENT and not only deletions. A deletion asks "is this line load-bearing"; a rearrangement asks "is this line load-bearing HERE", and the entire defect lived in the where. Every deletion mutation in that run failed exactly one test; the rearrangement failed none, which is what exposed the hole.

The repair is `TestRebuild_SecondRebuildIsTheHubConflict`: it occupies the hub's rebuild slot with a blocking task, issues a rebuild against a READY index so the request passes the 409 check and is refused by the hub, and then asserts the losing request left `IndexStatus()` at `ready` and emitted ZERO index frames. Re-run the rearrangement against it and it fails alone.

GENERAL FORM, for any cross-cutting mark, claim or counter placed around a guarded operation: put it where the GUARD HAS ALREADY BEEN PASSED, not where the request arrives. A mark before a gate that can still refuse is an unpaired mark on the refusal path, and the refusal path is the one nobody writes an assertion for.
