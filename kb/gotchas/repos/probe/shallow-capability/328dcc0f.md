# The branch-inspection probe requests Depth 1 only when the server ADVERTISES shallow, else a full single-branch clone under the byte budget; ProbeOrigin deliberately keeps remote.ListContext because it never requests a depth and its four-state error classification is load-bearing

PR #205. The wizard's "does this branch already hold a knowledge base" step (ProbeInitialized → probeInitializedBranch, internal/repos/initialized.go) used to hardcode Depth: 1. go-git's client turns any non-zero depth into the `shallow` capability on the wire, and a server that does not advertise it (go-git's built-in server, older knomit builds) rejects the request as HTTP 500. Now `advertise` reads the advertisement once through the transport session (refs AND capabilities; remote.ListContext discards the capabilities) and probeInitializedBranch takes shallowOK: Depth 1 when `shallow` is advertised, otherwise Depth 0, a full single-branch clone bounded by budgetedStorage (Git.MaxProbeBytes). The probe budget still spans every network call of one probe.

ProbeOrigin (probe.go) was NOT converted and should stay on remote.ListContext: it lists refs without ever requesting a depth, so capabilities buy it nothing, and its error classification into the four wizard states is load-bearing (kb/invariants/repos/probe/four-states-not-three); changing its transport call is blast radius for no gain.

Test fixture notes that cost time: a file:// remote is NOT a no-shallow fixture (go-git's file transport execs the real git-upload-pack, which advertises shallow); a server that lacks the capability must be built from go-git's transport/server package on httptest, and the test must assert its advertisement really lacks `shallow` before relying on it. go-git's repo.Log is not shallow-aware, so a depth-N test walks first parents by hand.
