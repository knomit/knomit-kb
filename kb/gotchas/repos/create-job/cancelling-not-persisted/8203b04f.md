# A `cancelling` create job does not survive a server restart: jobs live only in memory, so a restart mid-cancel after the repo was registered leaves the repo as an ordinary repository with no flag and nothing to finish the delete — recovery is manual archive + purge

Create jobs (Manager.createJobs) are an in-memory map minted by StartCreate; nothing persists them. If the server restarts while a job is CreateCancelling and the repo is already registered (post m.Add), the job is gone on boot while the registry row and .db remain, so the repo comes back through openRegistered as a normal, unflagged repository and the delete that cancel promised never runs. The same holds for a create still running mid-transfer: its registry row was inserted before the transfer and cleanup() never ran, so it reports as a missing/unopenable repo rather than vanishing. Recovery today is DELETE /api/v1/repos/{name} then DELETE /api/v1/archived/{uid}. Not fixed in PR #230; a fix would persist the cancel intent (e.g. a state on the registry row) and finish it at boot. Misreading to avoid: this is not the CreateJobTTL reaper — a cancelling job is never reaped while the process lives.
