# A cancel during the index phase lands after the in-flight EMBEDDING BATCH, not instantly: the index job checks its context only between batches, and the same bound applies to CancelIndex's reply and to every Unmount's drain — measured 0.07s to "Cancelling…", ~15–35s to the cancelled card on knomit-kb with the embedder on

UPDATE (issue #411): ActivateSync, indexCtx/indexWg and shutdown are gone. A cancel during the index now: CancelCreate cancels the job context → watchIndex returns (it only observes) → Create removes the repo, whose Unmount cancels the machine's root ctx and drains every stage; the index job notices between embedding batches. The same one-batch bound therefore ALSO bounds CancelIndex's reply (it waits for the Index life to drain) and every Unmount's drain (archive, Manager.Close, a cancelled create). There is no sync step to skip any more.

Original mechanism, verified live on PR #230: CancelCreate cancels the job context → mirrorIndexing returns on ctx.Done() → Create checks ctx.Err() and SKIPS ActivateSync (before that skip existed the synchronous reconcile blocked on the branch lock the heal holds, and the job sat at step=sync "activating sync" pct=99 in state cancelling for the whole index — observed for minutes at 32/697 facts) → Create returns ri → the worker goroutine runs DeleteRepo → Archive → ri.shutdown cancels indexCtx and waits indexWg → the heal notices between batches → Purge. So the latency of a late cancel is bounded by ONE embedding batch (batch_concurrency=1, max_batch_tokens ~3118 on the dev box), not by the remaining index. Measured in Chromium: cancel pressed 72s in (index phase), "Cancelling…" 0.17s later, cancelled card 15.2s later; the worker's run saw 35s. Making it faster means checking the context inside the indexer's batch loop — a separate change to internal/store's index build, not something to fold into the create path. Misreading to avoid: a cancelled job must NEVER report step "sync"; TestCreate_CancelledDuringIndexSkipsSyncActivation asserts exactly that from inside an index-phase emit, and TestCancelCreate_DuringIndexLandsWithoutWaitingForTheIndex asserts on the step, not on wall-clock — a timing bound there passed under sabotage on a 200-fact fixture because the index was nearly done when the cancel landed, i.e. it was a machine-speed assertion.

CORRECTION (#368, 2026-10-02): 'bounded by ONE embedding batch' holds only with an embedder on. Without one (tests, CI), the index's cancellation is checked between phases and SQL steps. A late cancel then waits for:
- the in-flight SQL step: phase 0 (rebuildCommitLog) can finish a step it is already in;
- RepoInstance's svc.Close(), which checkpoints whatever WAL the index left.
Measured locally: about 0.06 s idle and 0.8-1.3 s under write+fsync load. On a degraded Windows CI runner it reached about 17 s (run 36590870983: commit-log phase 7.0 s, then about 10 s silent before 'archived').
There is no retry or sleep in the cancel path. #403 (bulk operations checkpoint their own WAL) would shrink the close cost. The test's `elapsed < fullCreate` check was removed in #368 because it never caught the regression.
