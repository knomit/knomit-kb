# A cancel pressed during the index phase lands after the in-flight EMBEDDING BATCH, not instantly: Create skips ActivateSync when its context is cancelled, but Archive's shutdown still waits on indexWg and healIndexBranches checks its context only between batches — measured 0.07s to "Cancelling…", ~15–35s to the cancelled card on knomit-kb with the embedder on

Mechanism, verified live on PR #230: CancelCreate cancels the job context → mirrorIndexing returns on ctx.Done() → Create checks ctx.Err() and SKIPS ActivateSync (before that skip existed the synchronous reconcile blocked on the branch lock the heal holds, and the job sat at step=sync "activating sync" pct=99 in state cancelling for the whole index — observed for minutes at 32/697 facts) → Create returns ri → the worker goroutine runs DeleteRepo → Archive → ri.shutdown cancels indexCtx and waits indexWg → the heal notices between batches → Purge. So the latency of a late cancel is bounded by ONE embedding batch (batch_concurrency=1, max_batch_tokens ~3118 on the dev box), not by the remaining index. Measured in Chromium: cancel pressed 72s in (index phase), "Cancelling…" 0.17s later, cancelled card 15.2s later; the worker's run saw 35s. Making it faster means checking the context inside the indexer's batch loop — a separate change to internal/store's index build, not something to fold into the create path. Misreading to avoid: a cancelled job must NEVER report step "sync"; TestCreate_CancelledDuringIndexSkipsSyncActivation asserts exactly that from inside an index-phase emit, and TestCancelCreate_DuringIndexLandsWithoutWaitingForTheIndex asserts on the step, not on wall-clock — a timing bound there passed under sabotage on a 200-fact fixture because the index was nearly done when the cancel landed, i.e. it was a machine-speed assertion.
