# Push holds the agent-branch write lock across the network push (plain RWMutex, no ctx, bounded only by [git].network_timeout, 120 s): any write — including a script's knomit.learn in phase B — waits behind it; a push trigger makes that hold happen every ~1–2 s during a burst instead of every 300 s

remoteIndex.Push takes lockBranch(agentBranch) and holds it through repo.PushContext; lockBranch is a sync.RWMutex that ignores ctx, and the push is bounded only by the network timeout (default 120 s). Every fact write takes the same lock. So `knomit.push(); knomit.learn(...)` in a script, or the next fire's script, can wait up to the network timeout if the origin hangs, and the 5 s script budget cannot interrupt a Go lock wait (the deadline note in trigger_script.go covers a write already INSIDE the lock, not one waiting to acquire it).

The hazard predates F07 PR 4 (the periodic tick does the same); PR 4 changes its frequency: with a `do: push` trigger during a continuous burst, a round that has something to push holds the lock about once per (1 s window + tick time) instead of once per interval, which shows up as write tail latency. The lever is the window length (a code constant); no ctx-aware lock was built (trust ruling: capability, no hardening). The PR 4 claim is narrow: the kick SEND never blocks and the tick never runs on the dispatcher goroutine — NOT that phase B never waits on the network.
