# RESOLVED by F21 S1's snapshot push: Push used to hold the agent-branch write lock across the network push (bounded only by network_timeout, 120 s), so any write waited behind it; it now holds the write lock only to read the tip, and only a second PUSH waits (on pushMu)

STATUS: resolved by the F21 S1 snapshot push (kb/architecture/store/remote-sync/snapshot-push): Push now takes a per-branch push mutex for the whole push and the write lock ONLY to read the branch tip, then pushes that hash. A write waits for one ref read, never for the network; what still waits on a push's network time is another PUSH (fleet or create-time), on pushMu. The text below describes the code BEFORE S1.

Before S1: remoteIndex.Push took lockBranch(agentBranch) and held it through repo.PushContext; lockBranch is a sync.RWMutex that ignores ctx, and the push is bounded only by the network timeout (default 120 s). Every fact write takes the same lock. So `knomit.push(); knomit.learn(...)` in a script, or the next fire's script, can wait up to the network timeout if the origin hangs, and the 5 s script budget cannot interrupt a Go lock wait (the deadline note in trigger_script.go covers a write already INSIDE the lock, not one waiting to acquire it).

The hazard predates F07 PR 4 (the periodic tick does the same); PR 4 changes its frequency: with a `do: push` trigger during a continuous burst, a round that has something to push holds the lock about once per (1 s window + tick time) instead of once per interval, which shows up as write tail latency. The lever is the window length (a code constant); no ctx-aware lock was built (trust ruling: capability, no hardening). The PR 4 claim is narrow: the kick SEND never blocks and the tick never runs on the dispatcher goroutine — NOT that phase B never waits on the network.

REGRESSION TEST: TestPush_HungOriginDoesNotStallWrites (internal/store/remote_push_snapshot_test.go) pins the resolved behavior. At the #569 merge 1edec00b it is in its ORDERING form: it waits until the hung origin has accepted the push's connection, then requires ten writes to complete while the push is still in flight (the push's done channel is still empty), with 10 s and 30 s waits as hang detectors only. The earlier form bounded a write at 1 s and failed at 1.138 s under load; see kb/conventions/testing/timing/assert-ordering/1b60e3a6.md.
