# A peer's origin sync interval is fixed at 300 s: remotes.interval/push_interval default to 300 and nothing in the code writes them (no API, no config key), so any protocol whose timing rides a peer's fetch (the mission claim window X) must assume 300 s

Measured at origin/dev b9cdf382, re-read at the #358 merge 771967d2: internal/store/remote.go inserts remotes rows with defaultSyncInterval (300) for both interval and push_interval, and the reconcile loop in internal/repos/sync.go re-reads the remote each iteration and waits loopInterval(fresh) = min(interval, push_interval), falling back to 300 when <= 0. A git grep for push_interval/interval writers finds only those INSERTs and the migrations: the HAL origin view exposes interval read-only, and config.GitConfig has only local_reconcile_interval (the no-origin host's loop, default 30 s). A peer still gets rounds sooner when a `do: push` trigger or knomit.push() kicks its loop (1 s countdown), and that round fetches too, but nothing else shortens the fetch cadence.

CONSEQUENCE: the F08 RCA's advice 'set a 15 s sync interval on mission peers, X = 60 s' cannot be followed; the mission template sets its claim window X = 360 s (300 + push countdown + host fast-forward + a few seconds; 2X = 720 s for the dead-winner rule). MISREADING: this is not the host's local_reconcile_interval, which IS configurable and governs the no-origin host's own due sweeps.

**Since F21 S2 (`feat/sync-mode`):** the remotes.interval column is STILL fixed at 300 s with no writer, but a repo whose ontology sets the root attribute `sync: {pull: realtime}` (read at the consensus branch's tip) does not use it: its origin loop waits `[git].realtime_pull_interval` instead (knomit.toml, 3 s default, >= 1 s), and `sync: {push: realtime}` gives every agent-branch commit the 1 s countdown. So the 300 s assumption holds only for repos WITHOUT `sync` (and always for subscriptions, which ignore it). The F08 template now sets `sync: {push: realtime, pull: realtime}` and X = 15 s (feat/mission-template-realtime, 2026-10-01; healthy origins only, see kb/decisions/fleet/f08/claim-window-realtime/). The 300 s case still governs a mission repo that drops `sync`, and any participant on a knomit older than F21. See kb/architecture/repos/sync/sync-mode/c125223d.md.
