# Multiple local agent/* branches are distributed design, not drift or data loss — don't 'fix' convergence

knomit is a distributed, multi-agent system: several agents work the same repo, each writes its OWN agent branch (agent/<hostname>-<key-fingerprint>, app.agentBranch in internal/app/identity.go), and branches converge through the shared origin. Other agents' branches are present LOCALLY too — both as refs/heads/agent/* (fetched into the local ref store) and refs/remotes/origin/agent/*. A single repo DB legitimately holds many agent/* branches with different tips and different fact counts (e.g. an agent branch with 0 local facts is simply another machine's branch this instance doesn't index).

**The trap (observed, cost real work):** seeing multiple local agent/* branches, or two branches for the same machine (hostnames flip .local/.lan; keys get regenerated), and reading it as 'identity drift', 'silent divergence', or 'data loss'. It is NOT. Per-identity branches diverging and reconciling via origin is the intended model. During review of PR #35/#32 this misread produced a cascade of invalid findings and three issues (#36 stale-branch/HEAD-ancestry, #37 refspec rewrite, #38 test coverage) that were all later closed as not-valid, and nearly led to a 'persist a stable branch name' fix that would have worked AGAINST the design (two agents from a copied DB would then share one lineage).

**What IS load-bearing:** which branch a given DB writes to is recorded explicitly in the agent_branch_owner meta row, not inferred from HEAD or from branch-name shape (see the takeover decision fact). HEAD is not lineage.

**How to apply:** before reporting a review finding or proposing a fix that rests on 'these branches should be the same' or 'this divergence is a bug', confirm the architectural assumption with the user first. In a distributed system, 'multiple branches / multiple copies of state' is a convergence question (handled by origin/sync), not automatically drift. When one small fix seems to spawn many follow-on issues, suspect the framing before assuming the code is deeply broken. Reproduce a claim (throwaway test) before asserting it — that is what separated the one real bug (upstreamMain reset on reboot, PR #39) from the invalid ones.
