# A test whose Manager sets DisableBackgroundSync CANNOT observe `indexing` at all — it heals inline and never calls markIndexing — so any test of index-state transitions written that way passes against the very bug it is meant to catch

THE TRAP, first: reach for `DisableBackgroundSync: true` because it makes a repo test deterministic, and any assertion you write about index STATE silently becomes unfalsifiable. That branch of `openOne` heals SYNCHRONOUSLY and marks only a terminal — it never calls `markIndexing` — so the observable state sequence is `[ready]`, with no `indexing` in it, ever. A test asserting "the heal announces indexing then ready" written on that harness cannot fail, including against a build where the event is not published at all.

THE MUTATION, which is the part to re-run rather than trust. Adding the flag to the Manager in `TestRepoIndexEvents_StartupHealEmitsIndexingThenReady`:

```
# with DisableBackgroundSync: true
--- FAIL: TestRepoIndexEvents_StartupHealEmitsIndexingThenReady
    state sequence = [ready], want indexing … ready
# without it
ok  knomit/internal/web
```

That is the discriminator: the `indexing` assertion is what pins the test to the PRODUCTION goroutine path. The note lives in the test's own comment so a future reader re-runs it instead of believing a report.

WHY IT IS SHAPED THIS WAY: the flag exists so tests need not wait on a background goroutine, and inline healing is a perfectly good answer to that. The sharp edge is that it does not merely change the TIMING of the state transitions, it removes one of them — which is invisible from the flag's name and from the call site.

HOW TO STAY SAFE: build the Manager WITHOUT the flag whenever the assertion is about index state or index events, and make `indexing` (not just the terminal) part of what you assert — a test that only checks the end state is equally green on both branches and tells you nothing about which one ran. Where a test genuinely needs the flag for unrelated determinism, do not also assert on index state in it.

WHAT THIS IS NOT: not the 2026-08 stuck-indexing incident, which was PRODUCTION state pinned at `indexing` by an exit path reaching neither mark. This is the mirror image and test-only — a harness that never ENTERS `indexing`, so it cannot see a state being pinned there or an event going missing.
