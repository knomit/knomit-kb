# cHost.settle orders, it does not quiesce: a beforeMerge hook installed after settle can miss a merger pass already parked on the agent-branch lock, and only holding consensusMerger.runMu across the setup closes the race

cHost.settle (consensus_test.go) returns once a merger pass that STARTED after the call has ENDED. That contract holds, but it does not wait for the merger to go idle: the merger's kick channel (capacity 1) can still hold a kick when settle returns. Kicks also come from outside the test's control: settle's own second kick, the peer reconcile loop's registration push, and ri.onCommit for a commit on any non-agent branch. The pass that such a kick starts runs right after settle returns.

consensusMerger passes are serial (runMu). Each pass reads currentConsensusHooks().beforeMerge, then calls MergeConsensus, which takes lockBranch(agent). A test that settles, starts an index job that holds lockBranch(agent), and only then installs a beforeMerge hook can lose the race: the post-settle pass reads a nil hook, parks on the lock unseen, and holds every later pass, so the hook never fires. This was TestWalkthrough_WorkerCrashDuringIndexing ("the merger reached its merge", 21/1000 under 16-way -race stress on macOS). Debug logs of failing runs show the order: pass start, test settled, beforeMerge hook=false, job holds lock, hook set. Waiting for the peer's registration first is not enough; it was tried and 16/1000 runs still failed.

CONSEQUENCE: to observe the merger's NEXT pass, hold consensusMerger.runMu across the setup (take it before the index job starts, release it only after setConsensusHooks has installed the hook). While runMu is held no pass is in flight, and every pass after the Unlock reads the hook. Register the unlock as a t.Cleanup after the Manager's Close cleanup so an early require failure releases it first (LIFO); Close never waits on a merger parked on runMu. Holding the mutex is a same-package test access to an unexported field, not an export.

WHAT THIS DOES NOT MEAN: (1) do not 'fix settle'. No change to settle can close this race, because the stray kicks come from peer registration pushes and from commits to other branches, which settle does not control; even a settle that waited for quiescence could be followed by a new kick before the hook goes in. (2) settle is not broken for its documented purpose (ordering after a pass that started later). (3) Tests that install the hook BEFORE any push and never settle first (consensus_test.go PushLatencyUnchanged) are not affected.
