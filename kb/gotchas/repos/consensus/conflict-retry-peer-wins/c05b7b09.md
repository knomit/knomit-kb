# With `conflicts` off or absent, after consensus: auto refuses a conflict, the PEER's own sync (a LocalWins merge of the host's consensus branch) moves the merge base, and the next auto-merge applies the peer's version cleanly, replacing the host's version (review F1). The drop is now recorded by a Knomit-Conflict trailer, and `conflicts: merge` replaces the behaviour with a fact-level merge

Measured in T-B5 (internal/repos/consensus_test.go). Host and peer both edit fact X from a common base. The peer pushes; the consensus merger's MergeConsensus refuses (StrategyRefuse, no side) and memoises (branch, tip). So far 'left for a human'.

Then the peer's ordinary sync fetches the host's consensus branch (now carrying the host's X) and merges it into its agent branch with StrategyLocalWins: the peer keeps ITS X and writes cm = [c, h]. It pushes cm, a new tip, so the merger retries. On the host the merge base of (agent, cm) is now h, the host has not changed X since h, the peer has → a clean three-way merge that takes the PEER's X. No conflict, no warning. In the modify/delete shape the same path brings a deleted fact back.

Condition: the host's consensus branch must carry something else the peer lacks; if the only difference is the conflicting path, the peer's LocalWins merge is tree-identical and reconcileAgentMerge reports Noop without a merge commit, so the peer re-pushes nothing new and the conflict stays refused.

Consequence: 'a conflict is left for a human' holds only until the peer's next sync that brings anything else. PR B (merged as #353) shipped this behaviour unchanged and T-B5 pins it. Conflict-merge PR 1 (feat/conflict-merge) keeps it for a repo whose consensus branch tip has no `conflicts` setting, or `conflicts: off`, because absent means off. Two things change. (1) The peer's LocalWins merge commit now carries `Knomit-Conflict: <path> kept=dst dropped=src-modify strategy=local_wins …`, so the replaced host version is named, not silent (TestConflictMerge_Absent_IsToday_Recorded). (2) With `conflicts: merge` the merger no longer refuses a fact conflict: MergeConsensus merges the two versions (StrategyMergeFacts) and the peer converges to the same bytes, so F1 does not arise (TestConflictMerge_HostMergesFirst_Converges). See architecture/store/merge/merge-facts. Misreading to avoid: the merger itself never takes a side — the side is taken by the peer's LocalWins reconcile.
