# After consensus: auto refuses a conflict, the PEER's own sync (LocalWins merge of the host's consensus branch) moves the merge base, and the next auto-merge applies the peer's version cleanly — the host's version is silently replaced (review F1; the user approved a fact-level conflict merge to replace this, not yet shipped)

Measured in T-B5 (internal/repos/consensus_test.go). Host and peer both edit fact X from a common base. The peer pushes; the consensus merger's MergeConsensus refuses (StrategyRefuse, no side) and memoises (branch, tip). So far 'left for a human'.

Then the peer's ordinary sync fetches the host's consensus branch (now carrying the host's X) and merges it into its agent branch with StrategyLocalWins: the peer keeps ITS X and writes cm = [c, h]. It pushes cm, a new tip, so the merger retries. On the host the merge base of (agent, cm) is now h, the host has not changed X since h, the peer has → a clean three-way merge that takes the PEER's X. No conflict, no warning. In the modify/delete shape the same path brings a deleted fact back.

Condition: the host's consensus branch must carry something else the peer lacks; if the only difference is the conflicting path, the peer's LocalWins merge is tree-identical and reconcileAgentMerge reports Noop without a merge commit, so the peer re-pushes nothing new and the conflict stays refused.

Consequence: 'a conflict is left for a human' holds only until the peer's next sync that brings anything else. PR B (merged as #353) shipped this behaviour unchanged and T-B5 pins it. It is no longer awaiting a ruling: the user approved a fact-level conflict MERGE that will replace refuse-then-peer-wins (design .claude/plans/2026-09-30-peer-conflict-rca-proposal.md, implementation brief .claude/plans/2026-09-30-brief-conflict-merge-implement.md). Until that ships, the behaviour described here, as pinned by T-B5, stands. Misreading to avoid: the merger itself never takes a side — the side is taken by the peer's LocalWins reconcile.
