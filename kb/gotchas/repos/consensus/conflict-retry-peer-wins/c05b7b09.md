# With `conflicts` off or absent, a conflict that consensus: auto refused is overridden by the peer within one round. The peer's own LocalWins sync moves the merge base, the next auto-merge applies the peer's version cleanly, and the drop is now RECORDED (Knomit-Conflict). With `conflicts: merge` the field-level merge replaces this override

Measured in T-B5 (internal/repos/consensus_test.go). Host and peer both edit fact X from a common base. The peer pushes; the consensus merger's MergeConsensus refuses (StrategyRefuse, no side) and memoises (branch, tip). So far 'left for a human'.

Then the peer's ordinary sync fetches the host's consensus branch (now carrying the host's X) and merges it into its agent branch with StrategyLocalWins: the peer keeps ITS X and writes cm = [c, h]. It pushes cm, a new tip, so the merger retries. On the host the merge base of (agent, cm) is now h, the host has not changed X since h, the peer has → a clean three-way merge that takes the PEER's X. No conflict, no warning. In the modify/delete shape the same path brings a deleted fact back.

Condition: the host's consensus branch must carry something else the peer lacks; if the only difference is the conflicting path, the peer's LocalWins merge is tree-identical and reconcileAgentMerge reports Noop without a merge commit, so the peer re-pushes nothing new and the conflict stays refused.

Consequence: 'a conflict is left for a human' holds only until the peer's next sync that brings anything else. PR B (merged as #353) shipped this behaviour unchanged and T-B5 pins it. SINCE #355 (merged at 68cc310b), the behaviour depends on the `conflicts` root attribute at the consensus branch's tip. With `conflicts: merge` (or merge:upstream), the one-round peer override is REPLACED by the field-level merge: the host's merger and the peer's sync compute the same merged fact, and neither version is silently dropped. With `conflicts` off or absent, the override still happens exactly as described above, but it is no longer silent. Conflict-merge PR 1 keeps it for a repo whose consensus branch tip has no `conflicts` setting, or `conflicts: off`, because absent means off. Two things change. (1) The peer's LocalWins merge commit now carries `Knomit-Conflict: <path> kept=dst dropped=src-modify strategy=local_wins …`, so the replaced host version is named, not silent (TestConflictMerge_Absent_IsToday_Recorded). (2) With `conflicts: merge` the merger no longer refuses a fact conflict: MergeConsensus merges the two versions (StrategyMergeFacts) and the peer converges to the same bytes, so F1 does not arise (TestConflictMerge_HostMergesFirst_Converges). See architecture/store/merge/merge-facts. Misreading to avoid: the merger itself never takes a side — the side is taken by the peer's LocalWins reconcile.
