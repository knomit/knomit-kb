# Manager.Set REPLACES m.repos[name] without closing the instance it displaces, and Manager.Close only tears down what is in the map — so a fixture that swaps a live repo for a stand-in orphans its open .db handles, which Linux hides and Windows reports as a TempDir RemoveAll failure AFTER every assertion has passed

`Manager.Set(name, ri)` overwrites `m.repos[name]`. It deletes the displaced
instance's stale `byUID` entry — its doc comment says so — and does NOTHING
with the instance itself. It is not closed, not shut down, not returned to the
caller. `Manager.Close` then iterates the map as it stands when it runs, so an
instance displaced earlier is never in it and never torn down.

A test fixture that swaps a REAL repo for a stand-in therefore leaks every
handle the real one held.

MEASURED, not inferred. Counting this process's open descriptors under the
fixture's `t.TempDir` home, after the manager had closed:

    without the restore:  8 open handles
    with it:              0

The eight were `<uid>.db`, its `-wal` and `-shm`, and `<uid>.sessions.db` with
its own wal/shm — the whole SQLite file set of one repo.

WHY IT IS INVISIBLE UNTIL IT IS NOT. Linux unlinks a file with an open handle
without complaint, so the leak has no symptom there and the test passes. On
Windows `RemoveAll` cannot delete an open file, so `t.TempDir`'s cleanup fails
— AFTER every assertion in the test has already passed. It therefore reads as
a test-infrastructure problem on one platform while the test's own output says
it succeeded:

    testing.go: TempDir RemoveAll cleanup: unlinkat ...\repos\<uid>.db:
      The process cannot access the file because it is being used by
      another process

THE FIX: restore the displaced instance in `t.Cleanup`; do not close it by
hand.

    orig := m.Get("alpha")
    t.Cleanup(func() { m.Set("alpha", orig) })
    m.Set("alpha", standIn)

`t.Cleanup` is LIFO and the manager helper registers its `Close` first, so the
restore runs before it and `Manager.Close` performs its ordinary full teardown.
That matters: exported `RepoInstance.Close()` only runs `closeFn`, while
`Manager.Close` drives the whole `shutdown` sequence (cancel index heal and
sync, wait both, shut the hub, then release the store). A fixture closing by
hand would be a SECOND teardown path free to drift from the real one, in the
place least likely to be noticed.

WHAT THIS DOES NOT MEAN — 1. `Set` is not buggy, and it must NOT be "fixed" by
closing what it displaces. Renaming a live repo re-keys `Manager.repos` in
place precisely by removing and re-adding the SAME instance under a new name,
and there the store must stay open
(kb/decisions/repos/rename/rekey-in-place/4667c447.md). A `Set` that closed on
displacement would break rename. Non-closing is load-bearing; what is missing
is any signal that the caller now owns an instance nothing will tear down.

WHAT THIS DOES NOT MEAN — 2. Production is not exposed, but not for the reason
it first appears. There are TWO production callers and neither displaces a
live instance: `openRegistered` (from `Start`) fills an empty map, and `Add`
registers a name that is not currently live. The safety lives in the CALLERS'
circumstances, not in `Set` — and it is invisible from `Set` itself, whose doc
comment anticipates replacement, handles the stale `byUID` entry, and says
nothing about the orphan. A third caller that replaces a live name makes the
hazard real in production, and `Add` is the one a future feature is likelier
to reach for.

WHAT THIS DOES NOT MEAN — 3. It is not "remember to close things in tests".
The fixture did nothing unusual: it used the standard manager helper, which
already registers `m.Close()` in `t.Cleanup`, and that helper is correct. The
leak came from taking an instance OUT of the structure the helper tears down.
Any operation that removes a live instance from the map without closing it has
the same shape — the rule is about the map, not about the test.

A SIBLING, SAME FUNCTION, SAME SHAPE: `Manager.Set(name, nil)` stores nil
rather than deleting the key
(kb/gotchas/repos/manager/set-nil-stores-nil/29bdd4fc.md), also latent because
no production caller does it. Two distinct hazards in one small setter, both
reachable only from tests, is itself the signal: `Set` is a bare map write
wearing a method's clothes, and every guarantee around it belongs to somebody
else.
