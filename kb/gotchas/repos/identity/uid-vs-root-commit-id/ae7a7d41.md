# A repo has THREE identifiers with different lifetimes — uid (membership), root-commit id (fact addressing), name (display); GET /repos returns all three

`GET /api/v1/repos` (and `GET /api/v1/repos/{repo}`) return `name`, `uid` and `id`, and they are three different things that are easy to substitute for one another:

- `uid` — the `repos(uid)` registry primary key, a ksuid. Exists from the moment a repo is CREATED (before it has ever been opened), survives a rename (a single UPDATE of `repos.name`), and survives a disjoint-history origin connect that swaps the store. This is what lens membership is keyed by and the only identifier lens requests accept for a member.
- `id` — `RepoInstance.ShortID()`, the first 12 hex of the repo's ROOT COMMIT. Only exists once the store has been opened, and CHANGES on a store swap. This is what `kb://<id12>/…` qualified fact paths address, and what the replica guard (`ErrReplicaInLens`) compares.
- `name` — per-machine, unique among ACTIVE repos only, mutable, display-and-routing (`/repos/{repo}/…`, lens `repo=` mount narrowing).

CONSEQUENCE: never use one where another is expected. A uid in a `kb://` path addresses nothing; a root-commit id sent as a lens member uid is a 400; a name stored as membership dangles on rename. In `web/src/api.ts`, `RepoInfo` carries `uid?` and `id?` as separate optional fields for this reason, and `LensMember.uid` is a registry uid while `LensSource.id` is a root-commit id — same-looking hex strings, different namespaces.

WHAT THIS DOES NOT MEAN: `uid` is NOT a global identity. It is machine-local registry state in `<home>/control.db`; two machines holding clones of the same knowledge base give it different uids. The identifier that IS the same in every clone is the root-commit `id`.
