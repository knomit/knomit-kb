# Two engine runs at the same time on ONE loaded scenario world get different results than the same runs made one after the other (gold oracle, same questions) — run concurrent engine runs on separate world copies

Measured 2026-10-12 with the eval runner's first design (two arms on two endpoints, both lanes on one LoadedWorld, gold oracle, example + three pilot worlds, modes H and M2, Test J replay): serialized, both arms scored 7 of 8 chains correct in both modes and 1.0 on replayed relevant/support/synthesize; concurrent, one arm dropped to 6 of 8 in M2 and the replayed relevant (0.96-0.98), support (0.93) and assess (0.80) accuracies differed between the arms although the oracle is deterministic. Putting both arms on one endpoint (one lane, serial) restored identical results.

The cause is NOT diagnosed. What it is not (eval-runner review, 2026-10-12): not engine state (each run has its own script state) and not the embedder. The likely area, unverified, is failed or late host calls when two runs hit one store at once (an sqlite busy, or a rollback on one lane during the other's read). Read this as: two Engines running concurrently over one repo instance are not known to be independent.

Consequence: the eval runner gives each endpoint lane its own LoadScenario copy (internal/synthesize/eval_runner.go runWorld), because it builds one Engine per arm and two arms on two endpoints run at the same time. Anyone who runs SEVERAL Engines concurrently over one repo should not assume their reads are isolated until this is diagnosed.

What this does NOT mean: knomit_reason on ONE server is not exposed. A server has one Engine, and Engine.slot has capacity 1 (engine.go NewEngine; RunWith takes the slot before the script runs and holds it for the whole run), so concurrent askers' runs are serialised, never interleaved. (Corrected 2026-10-12: the earlier consequence line named the MCP knomit_reason tool with several askers as exposed; that was false for one server.)
