# A registered repo that fails to mount (state missing / unopenable / conflict in GET /repos) has NO in-product removal or repair: Archive needs a live instance, Purge needs an archived repo, it does not sync, and its ACTIVE registry row keeps blocking a re-add of the same knowledge base

Manager.openRegistered (internal/repos/manager.go) records a repo whose mount fails as Unavailable (reason missing / unopenable / conflict) instead of dropping it; GET /api/v1/repos lists it with `detail`, and its own endpoints answer 409 (RepoMiddleware). That keeps it VISIBLE, but nothing in the product can act on it:

- Archive (DELETE /repos/{repo} → Manager.archive) resolves the name through m.repos, the live map, so it answers ErrRepoNotFound for an unavailable repo.
- Purge (DELETE /archived/{id} → Manager.Purge) only accepts a row in state archived.
- It is not mounted, so its sync loop never runs: a fix pushed to its origin never reaches the local database.
- Its registry row stays state ACTIVE with the repo_id its last successful Identify recorded, so HeldByAnotherActiveRepo / the repos_active_repo_id index make a re-add of the SAME knowledge base fail as a duplicate (read from identity.go and registry.go; not exercised by a test).

The web UI says so in so many words (RepoUnavailable in web/src/RepoManager.tsx: "Removing the registration itself is not supported yet"). What does clear it today: put a working database file at RepoPath(uid) (<home>/repos/<uid>.db) and restart — for a symlinked ontology (refused since #444, merge ec3406df) that means a database whose read branch has a regular ontology file.

CONSEQUENCE for anyone adding a new reason to refuse a mount: the refusal is a dead end for the user unless that change also gives them a way out. Do not describe recovery as "purge and re-add" for an unavailable repo — that path exists only for an ARCHIVED one (e.g. a restore refused with 422 for a symlinked ontology leaves the repo archived, and it can be purged).

NOT what this says: that unavailable repos are hidden (they are listed), or that archived repos are stuck (restore and purge both work on them).
