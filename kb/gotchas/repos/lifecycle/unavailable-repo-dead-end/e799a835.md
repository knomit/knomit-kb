# A registered repo that fails to mount (missing / unopenable / conflict) is ARCHIVED to get out — Archive works without a store, and archiving alone frees its name and knowledge base for a re-add; before feat/archive-unavailable-with-reason (#450) it was a dead end

Manager.openRegistered (internal/repos/manager.go) records a repo whose mount fails as Unavailable (reason missing / unopenable / conflict, plus a typed Cause for the refusals code acts on) instead of dropping it; GET /api/v1/repos lists it with `detail`, and its own endpoints answer 409 (RepoMiddleware).

THE WAY OUT (#450, feat/archive-unavailable-with-reason): DELETE /repos/{repo} → Manager.ArchiveWith → archive. When the name is not in m.repos, archive looks it up in m.unavailable BY NAME (inline scan under m.mu) and archives it without an instance: lens check by uid, Registry.Archive (state flip + reason row in one transaction), delete from m.unavailable, no unmount. The reason's Condition records the state it was in ("<reason>: <detail>", e.g. "missing: database file not found"). Then:
- Archiving ALONE unblocks a re-add of the same knowledge base: repos_active_repo_id, the active-name index and Origins.ActiveRepoWithURL all count ACTIVE rows only. Test TestArchive_UnopenableRepoArchivesAndUnblocksReAdd shows the re-add refused before the archive and accepted after.
- Purge (DELETE /archived/{id}) then removes the row, the reason (FK cascade) and the file (absent file tolerated for a missing repo).
- The web UI's unavailable-repo page (RepoUnavailable in web/src/RepoManager.tsx) offers Archive with an optional note.

A SYMLINKED ONTOLOGY is not left unavailable at all: Start archives it itself (autoArchiveRefused, source system) — see kb/decisions/repos/lifecycle/auto-archive-refused/0c903c08.md and kb/invariants/repos/ontology/symlinks/1ac1e8f3.md. A lens member with that refusal is the exception: archive refuses lens members, so it stays unavailable and the user must drop it from the lens first.

ONE REMAINING DEAD END: an UNAVAILABLE fleet repository while the fleet row is "unregistering". The fleet guard and fleetRemoved recognise the fleet repo only when it is mounted, so archiving it succeeds but leaves the row "unregistering", and RegisterFleet keeps refusing with advice ("or the fleet repository be archived") that no longer clears it. Documented on ArchiveWith and in kb/decisions/repos/lifecycle/auto-archive-refused/0c903c08.md; not changed by #450.

STILL TRUE: an unavailable repo is not mounted, so it does not sync — a fix pushed to its origin never reaches the local database. In-place repair is still "put a working database at RepoPath(uid) and restart".

WHAT IT WAS BEFORE #450 (why the motif): Archive resolved only m.repos (ErrRepoNotFound for an unavailable repo), Purge accepted only an archived row, and the ACTIVE row kept blocking the re-add — the UI said "Removing the registration itself is not supported yet".

CONSEQUENCE for anyone adding a new reason to refuse a mount: give it a typed Cause in unavailableReason and decide whether boot should archive it (content-deterministic, cannot heal in place, independent of mount order) or leave it for the user to archive. Either way the user has a way out now; do not add a refusal that bypasses openRegistered's Unavailable bookkeeping, or Archive cannot find it.

NOT what this says: that an unavailable repo is archived automatically (only the symlinked ontology is), or that archiving deletes anything (the file stays until purge).
