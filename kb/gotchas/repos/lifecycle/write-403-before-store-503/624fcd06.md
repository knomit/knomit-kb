# On a machine-backed repo, a REST write while the store is detached answers 403 "Read-only branch", not 503: the lifecycle exits Identify before it detaches the store, so WritableBranch refuses every branch first

StageOpen is declared before StageIdentify (stages.go), and Machine.exitStages exits stages in reverse, so Identify's Exit runs before Open's detach of the store. identifyStage.Exit stores identity{ontologyErr: errNotIdentified}, and RepoInstance.WritableBranch returns false whenever OntologyError() != nil (checked first, before the fleet and agent-branch tests). So a REST write that arrives during teardown, a swap or a populate is refused with 403 "Read-only branch" before any write helper can see ErrStoreUnavailable or ErrRepoClosed, on the agent branch as well as on experiments. Verified at 585974c5 by reading both functions; the end-to-end 403 is PR-reported (TestFactWrite_ClosedRepo_RefusedAndWritesNothing).

CONSEQUENCE: a test that wants the 503 over HTTP needs a store-less instance WITH an identity (repos.NewTestInstanceWithDeps without Svc); a closed machine-backed repo exercises the 403. The write helpers can be driven directly on the closed instance to see ErrRepoClosed.

DOES NOT MEAN: that 403 is the intended answer for a transient state. It is the fail-closed outcome of the ordering, recorded but not ruled on; the 403 detail says only the agent branch accepts writes, which is misleading for a transient outage.

STATUS UPDATE (PR #620, user ruling 2026-10-24): this 403 eligibility message is explicitly OUT of scope of the unified store-unavailable 503 (kb/decisions/web/read-store-unavailable-503/d5d606a6.md) and stays on triage. Still true at 1a860912: PR #620 changed no write path's ordering, so a closed machine-backed repo still answers 403 first on a REST write; READS on such a repo are different (a store-less or closed repo answers GET /changes with 409 identity-unresolved first, see kb/gotchas/web/store-unavailable-503-reachability/eee2bdac.md).
