# A migrator will not recreate what its version table says it already created — so rebuild dropped tables from DDL, not from the migrator

**Status: the concrete hazard this fact described is FIXED. The lesson is kept because it is general and was learned expensively.**

`migrate-registry` converts a pre-registry control.db by DROPping the legacy `lens_reads`/`lenses` and rebuilding them. Once the rebuild went through a versioned migrator instead of a DDL constant, that sequence acquired a failure mode that did not exist before: **a migrator will not re-create what its version table says it already created.**

The reachable path was: `controlUp` skips `upgradeLensSchema` for a `lenses.write_repo` home but still runs the baseline, so any prior `repos.OpenRegistry` touch left a home simultaneously STAMPED v1 and legacy-shaped. `migrate-registry` then dropped the lens tables, called the migrator, the migrator saw v1 applied and did nothing — and the tables were gone. Symptom: `rewrite lens "<name>": no such table: lenses`.

**The first fix was wrong in an instructive way.** Dropping `schema_migrations` alongside the tables makes the baseline re-run, and that works — but it treats the symptom. It also rewinds EVERY future control migration on any home the tool touches, and it left the destructive DROP outside the transaction, which is how the far worse silent-lens-loss bug got in (see the linked decision).

**The real fix is not to ask the migrator at all.** `applyControlDB` now executes the baseline's own DDL text — `migrate.ControlBaselineSQL`, IF NOT EXISTS throughout — inside its transaction, right after the drops. The stamp becomes irrelevant, so no `schema_migrations` drop is needed and no future migration is rewound. `migrate.Control` runs after the commit purely to record the version.

**The general lesson, which outlives this tool:** anything that reaches around a migrator to drop or alter objects the migrator owns must either rewind the migrator's bookkeeping or stop relying on the migrator to put them back. Dropping the object is only half the operation, and rewinding the bookkeeping is the weaker of the two answers.
