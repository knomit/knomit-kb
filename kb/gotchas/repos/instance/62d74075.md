# RepoInstance.Acquire is a READ lock — concurrent lens reads do not serialise on it; the observed contention is the per-repo SQLite pool plus CPU, split unmeasured

Corrects an attribution in the 2026-09-01 lens motif performance investigation, which claimed concurrent lens fan-outs "partly serialise on per-mount read locks". That is wrong: RepoInstance.Acquire is mu.RLock() + WaitGroup.Add(1) — never exclusive — so readers cannot serialise on it.

The WaitGroup is the part that misleads, so name what it is FOR: teardown (Archive/Close) and replacement (SwapStore) drain outstanding holders before closing the underlying handle. It is a LIFETIME guarantee, not mutual exclusion. Seeing a WaitGroup beside an RLock and reading the pair as "a lock" is how the original misattribution happened.

The wrong attribution had a cost beyond being wrong: it made parallelising the lens fan-outs look unsafe when they were always safe to parallelise — which is exactly what PR #185 then did, for a 4x on lens search.

What was actually measured: 8 concurrent /lenses/all/stats requests took 717 ms wall vs 105 ms for one; 4 concurrent repo /stats on the SAME repo took 89 ms vs 55 ms on four DIFFERENT repos. That points at the per-repo SQLite connection pool (SetMaxOpenConns(4) in store/service.go) plus CPU saturation. The split between pool contention and CPU remains UNMEASURED — the curl harness carries ~15-20 ms of process-spawn noise; separating them needs a benchmark over real stores. BenchmarkFanOutMounts does NOT settle it: it deliberately keeps SQLite out and measures only the fan-out's own shape.

What this does NOT mean: it does not mean concurrent lens reads are contention-free — it means the lens/instance-level lock is not where the contention lives, so do not reach for lock restructuring to fix fan-out latency.
