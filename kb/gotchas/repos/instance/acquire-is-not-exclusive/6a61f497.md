# RepoInstance.Acquire is a READ lock — concurrent lens reads never serialise on it; the contention is the per-repo SQLite pool plus CPU, and that split is still unmeasured

`RepoInstance.Acquire` is `ri.mu.RLock()` plus a `WaitGroup.Add(1)`, and `WithRead` is the scoped form of it. It is NEVER exclusive: concurrent readers of the same mount cannot serialise on it. The WaitGroup exists so teardown (Archive/Close) and replacement (SwapStore) drain outstanding holders before closing the handle — it is a lifetime guarantee, not mutual exclusion.

This CORRECTS an earlier attribution. A 2026-09-01 measurement writeup explained a lens-open fan-out taking more wall time than its slowest request by saying the fan-outs "partly serialise on per-mount read locks". That reading is wrong, and it also had a practical consequence: it made parallelising the lens fan-outs look unsafe when it was in fact safe, which is exactly what PR #185 then did.

What IS there, measured but not fully attributed: 8 concurrent `/lenses/all/stats` take 717 ms against 105 ms for one; 4 concurrent reads of the SAME repo (89 ms) do worse than 4 across DIFFERENT repos (55 ms). That asymmetry points at the per-repo SQLite pool — store.Open sets `SetMaxOpenConns(4)` per repo — plus CPU saturation.

WHAT THIS FACT DOES NOT CLAIM: it does not say the pool is the cause. Those numbers come from a curl harness carrying ~15–20 ms of process-spawn noise per invocation, which cannot separate pool contention from CPU saturation. The remaining sublinear slope on lens stats is OPEN. Settling it wants a benchmark over real stores; BenchmarkFanOutMounts deliberately keeps SQLite out of the picture and measures only the fan-out's own shape.
