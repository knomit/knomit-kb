# A clone's credential comes from the CreateSpec's OriginSpec, NOT cfg.Remote — and persisting it goes through the control.db Origins tenant, which needs Deps.KeyPath

Manager.initClone resolves the clone credential from `authConfigFromSpec(spec.Origin)` — the AuthMethod/AuthToken carried on the CreateSpec's OriginSpec. The server-level `cfg.Remote` (config.RemoteAuthConfig) is NOT consulted for the credential: Manager.ResolveAuth copies exactly ONE field off it, `KnownHosts`, when the spec leaves it empty, and nothing else. A caller that sets cfg.Remote.User/Password/Token and then calls Create in clone mode clones ANONYMOUSLY, and an authenticating remote answers 401 ("authentication required: unauthorized") from InitFromRemote's fetch.

Consequence, and they are a pair — supplying the credential in the spec is only half of it: after `initClone` returns, `Create` (internal/corpus/repos/lifecycle.go) persists the origin by calling `m.origins.Set(uid, Origin{URL, Branch: resolvedUpstream, AuthMethod, AuthToken})` into control.db's `repo_origins` table. `Origins.Set` REFUSES a non-empty AuthToken when it has no `*store.Crypt` ("refusing to store credential ...: encryption unavailable"), returning an error that fails the whole create at persist-origin. **UPDATE (repo-registry-in-control.db, 2026-08): the Crypt is no longer built per-repo by a `configureCrypt` on the store.** There is now exactly ONE Crypt, built once in `Manager.Start` from `Deps.KeyPath` and shared by the whole `Origins` tenant (internal/corpus/repos/origins.go) across every repo — `store.SetCrypt` and per-repo `configureCrypt` are gone; the store itself holds no Crypt and no credential at all (see the auth-methods architecture fact). An unreadable/empty KeyPath only WARNS at Start, so the failure still lands later, at `origins.Set`, looking unrelated to the missing key file.

Basic auth packs the pair into the single token field as "user:password", split on the first colon by authConfigFromSpec.

WHAT THIS DOES NOT MEAN: cfg.Remote is not dead. It still feeds the RECONCILE path (makeRemoteAuthFn / runReconcileLoop) as the fallback under the persisted `repo_origins` row (injected into the store via `Service.SetOrigin`), and its KnownHosts is inherited by spec-driven SSH clones. The split is initial-clone-reads-the-spec, reconcile-reads-the-record-over-cfg.

How this surfaced: removing the special "core" repo (PR #73) made Manager.Create the only way a repo is born, so the Storyboard test harness's Connect() switched from re-booting with cfg.Git.Origin (which DID resolve cfg.Remote, via the deleted initDefaultGit) to Manager.Create in clone mode. WithRemoteAuth kept setting cfg.Remote, the credential stopped reaching the clone, and the token-expiry contract cell failed its precondition against a basic-auth remote. Fixed by mapping cfg.Remote onto the OriginSpec and booting that manager with a sandbox key file.
