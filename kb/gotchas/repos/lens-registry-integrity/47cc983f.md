# Restore(archiveID, newName) can dangle lens refs — the lens registry guards only Archive/Purge, not restore-under-new-name or rename

The lens registry (internal/repos/lens.go, tables in <home>/control.db) stores per-machine repo NAMES, and referential integrity is enforced only at the Archive and Purge choke points (lifecycle.go guards via RefsRepo → ErrRepoInUseByLens).

**The gap:** Manager.Restore(archiveID, newName) revives an archived repo under a NEW name while a lens may still reference the OLD name — leaving a dangling read mount, and freeing the old name for an unrelated future repo to silently capture. Additionally, RFC §5.2 assumes "Manager updates the registry on rename", but NO repo-rename operation exists at HEAD — when one is built, it MUST update lens rows in the same step.

**Consequence:** anyone implementing Restore changes or a rename operation must either block the operation while the old name is lens-referenced, or update the registry's lens rows atomically with it. Lens bind-time resolution (Phase 2 LensMiddleware) must fail loudly on a mount name that doesn't resolve — never silently shrink the read set (RFC §9.1).

**What this does NOT mean:** it does not mean the registry should switch to storing repo IDs — it is machine-local operational config keyed by name by design (RFC decision 8); the fix belongs at the mutation choke points.

Recorded in RFC §17 deferred work (discussion #8) during the Phase 1 whole-phase review.
