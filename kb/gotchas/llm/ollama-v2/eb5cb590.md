# Ollama can fail mid-stream with an {"error":...} line under HTTP 200; the Ollama adapter turns it, a missing done line, an undecodable line and a server-rejected tool call into errors

Per Ollama's errors doc (docs/api/errors.mdx, main read 2026-11-04) an error after the response started arrives as a final object such as {"error":"an error was encountered while running the model"} and the HTTP status stays 200. OllamaChat.Stream returns that text as an error; a stream that ends before a done:true line (dropped connection) and a line that is not JSON are also errors (the deleted earlier adapter skipped undecodable lines). Every decoded line calls StreamOptions.Progress, including thinking-only lines that reach no sink, which is what keeps WrapChat's first-activity timer from cutting off a thinking model. Non-200 statuses are formatted "ollama: HTTP <code>: <body>" so the existing isRetryable overload classifier (429/503/529) still matches. Tool-call arguments: Ollama always sends them as a JSON object (api.ToolCallFunctionArguments marshals as an object, api/types.go v0.40.14). A model whose arguments are not valid JSON makes the SERVER fail the request: 'llama-server returned invalid tool call arguments for <name>' (llm/llama_server.go, v0.40.14), as an HTTP 500 {"error":...} before any output or as an {"error":...} line after it. The adapter surfaces both as a turn error (no Response, not retried: 500 is not overload); it never produces a ToolUse with RawArgs/ArgsErr, and the adapter has no non-object-arguments branch (deleted, user decision 2026-11-04: unreachable). null or absent arguments are an empty call ({}). Consequence for the agent loop (PR4, Review Focus 4): on Ollama, malformed tool arguments fail the whole turn and never come back to the model as a tool error; the bad-args-become-tool-errors path applies to other providers only.
