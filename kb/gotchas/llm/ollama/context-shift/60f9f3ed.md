# On models whose KV cache supports shifting, llama-server's context shift (on by default in Ollama) silently discards KV while generating and still ends done_reason 'stop'; the runner disables shifting on other models (seen on qwen35); knomit sends shift:false so an overrun ends 'length' (ErrTruncated)

Ollama v0.40.14 (vendoring llama.cpp b11963) launches llama-server with --context-shift unless the request sends shift:false or the model is deepseek2 (server/sched.go resolveContextShift, llm/llama_server.go; ChatRequest.Shift, json shift, top-level not under options, api/types.go). The silent cut applies ONLY to models whose KV cache supports shifting. After the context is created, common_init_from_params checks llama_memory_can_shift and, when it is false, logs 'KV cache shifting is not supported for this context, disabling KV cache shifting' and sets ctx_shift=false, whatever the request or the --context-shift flag said (llama.cpp b11963 common/common.cpp:1467-1470; line numbers are dated support, the version is the claim). knomit still sends shift:false because it cannot know which kind of model it has. On a shiftable model, when prompt plus output reaches num_ctx WHILE GENERATING, llama-server discards half of the tokens after n_keep from the KV cache (Ollama sends num_keep = 4 by default), so the head of the prompt after the first num_keep tokens (most of the system prompt, which sits right after those 4 tokens, plus the oldest turns) vanishes mid-response and the response STILL ends done_reason 'stop'. Nothing signals the cut. Only the response being generated is affected; the stored history is intact and the next request resends everything. knomit therefore sends shift:false on every request (user decision, 2026-11-04): llama-server then stops with STOP_TYPE_LIMIT, Ollama reports done_reason 'length', and the adapter returns a *StopError that Is ErrTruncated with the partial response (tools/server/server-context.cpp, llama.cpp b11963; line numbers are dated support, the version is the claim). Trade-off: shift is a runner launch attribute, so another client of the same shared Ollama that sends a different shift value forces a model reload each time the two alternate; accepted. Misreading to avoid: shift:false does NOT stop prompt-too-long 400s. A prompt with n_tokens >= n_ctx is refused at slot start with 'request (N tokens) exceeds the available context size (M tokens), try increasing it' whether shift is on or off, and that is ErrContextFull, a different error from ErrTruncated. Consequence: PR4 must still reserve output room (num_ctx covers input plus output) so a normal reply does not hit 'length'. Tested by TestOllamaChat_ShiftFalseOverrunIsErrTruncated (request body carries shift:false; done_reason length gives a StopError that Is ErrTruncated). Confirmed live on Ollama 0.40.14 (llama.cpp b11963), 2026-11-04, driving OllamaChat.Stream at dev 014ca530. Model lfm2 (knomit-r3-350m-q4, shiftable): shift:true ended 'stop' after 1856 prompt + 678 generated tokens, more than num_ctx 2048, i.e. the silent shift happened; shift:false ended 'length' at 1856+192=2048. Model qwen35 (hf.co/unsloth/Qwen3.5-4B-GGUF:Q4_K_M): llama-server was launched with --context-shift --keep 4 but the runner logged 'common_init_: KV cache shifting is not supported for this context, disabling KV cache shifting', and the overrun ended done_reason 'length' whether shift was true or false (1440+608=2048). Each shift value launched a fresh llama-server, which confirms the reload trade-off.

Misreading to avoid: 'a shift:true control on any model proves the shift' is false. A shift:true run that ends 'length' (as on qwen35) shows the runner disabled shifting, not that shift:false worked; only a model that can shift (lfm2) discriminates the two values.
