# An Ollama chat's first request can be refused because the toolset plus repo instructions alone exceed num_ctx minus the reply reserve; the loop now says so with the sizes, and no default num_ctx is claimed to be enough

In PR 763 live acceptance an Ollama model with num_ctx 32768 refused its first turn: about 22K tokens of tool schemas and repo instructions plus the window/4 reply reserve left no room. The size of the toolset varies with the tools exposed and the repo instructions, so that measurement is not a property of the code and no constant is derived from it; the example config's num_ctx is left unchanged. There are two distinct paths for an OPENING request (nothing in hook 6, at most the first user entry in hook 7). (1) Pre-send: Loop.checkBudget finds estimate + reserve > window and returns OpeningTooBigMessage_DRAFT naming the estimated opening tokens, the window, the reserve and the room left, plus the raise-num_ctx hint for provider ollama. (2) Server refusal: the adapter returns ErrContextFull although the estimate FITS the window the model reports; Loop.openingRefused returns OpeningRefusedByServerMessage_DRAFT, which says the server refused the opening despite the estimate (EST tokens, reported window) and, for ollama, that the server's num_ctx is likely smaller than the opening. It must never claim 'needs X, leaves L' there, because by the estimate there is room (TestLoop_AdapterRefusalOfTheOpeningSaysTheServerRefusedDespiteTheEstimate). Later turns keep the generic context-full message. Copy is DRAFT awaiting user approval.

Does NOT mean 32768 can never work or that 65536 always works.
