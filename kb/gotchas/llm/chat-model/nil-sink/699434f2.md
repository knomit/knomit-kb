# ChatModel.Stream documents 'sink may be nil', but a model from llm.WrapChat (every chat's model) calls sink unguarded in its resilient wrapper: pass a no-op sink, never nil

internal/engine/llm/chat.go's ChatModel interface says sink may be nil, and the raw adapters (AnthropicChat, OllamaChat) do replace a nil sink with a no-op. But the resilient wrapper (resilience.go, resilientChat.Stream) hands the inner model its own closure, which calls the caller's sink(e) with no nil check, so any text, tool-use or done event panics with a nil pointer dereference when the caller passed nil. Every chat's model goes through WrapChat, so code that calls c.loop.Model.Stream directly (a side request such as the chat's auto-title) must pass func(llm.Event) {}.

Found while writing the chat auto-title (title.go defaultTitleStream): the test harness's scripted model also calls sink unguarded, which is how it surfaced. Consequence: pass a no-op sink. Does NOT mean the adapters are unsafe with nil: only the wrapper (and test doubles) are. Fixing resilientChat to guard sink would make the interface comment true; until then the comment is wrong for wrapped models.
