# `claude -p` writes EVERY prompt to the 1-hour cache (billed at the cache-write rate, 2x base input for Haiku 5.5) and reads none of it back, even across calls that share a system prompt and a 1.1k-token leading prefix; it adds ~600 input tokens of fixed overhead per call

Measured 2026-10-26 (materialize research spike, round 3; 84 Haiku 5.5 CLI calls, evidence in the git-ignored round3/COST.md, so no pinned ref). Command shape: `claude -p --model haiku --system-prompt S --tools "" --no-session-persistence --output-format json --setting-sources "" --strict-mcp-config --disable-slash-commands`, prompt on stdin, one process per call.

1. Every call's input is reported as cache WRITE tokens, not plain input: 251,288 tokens written to the 1-hour cache across the 84 calls and about 0 read back, because each call is a separate process with different content. Billed at the 1-hour cache-write rate: for Haiku 5.5 $0.20/MTok against $0.10/MTok base input and $0.01/MTok cache read (Anthropic list prices fetched 2026-10-26, prompts up to 100k tokens; output $0.50/MTok) - dated support, re-check before reusing.
2. Fixed overhead: input tokens fit about 594 + 1.37 x (characters/4) by least squares over the 84 calls, i.e. roughly 594 tokens of CLI framing per call plus a tokenizer ratio of 1.37 vs chars/4. About $0.00012 per call of pure overhead, $0.0100 over the 84.
3. The CLI's `total_cost_usd` matched a recomputation from the reported usage and the list rates to ~1e-17 summed over all 84 calls, so the dollar figure carries no extra surcharge; the inflation is in the token classes.

4. A shared prefix did not change this (round 7, 2026-10-26; evidence in the git-ignored round7-lean/COST.md and judge/). 100 Haiku 5.5 CLI calls (50 per question) used the SAME --system-prompt and a user message whose first ~1.15-1.18k API tokens (above the 512-token minimum cacheable prefix) were identical across calls, with only a title and excerpt differing at the end; one warm-up call ran first and the other 49 ran 6 in parallel after it. 99 of 100 calls reported cache_read_input_tokens = 0 and billed the whole message as cache creation; the single exception was the art1 warm-up call (2,084 cache-read tokens, probably left over from an earlier prefix-measurement run of the same prefix, not from a sibling call). The spike's explanation, NOT directly tested, is that the CLI places its cache breakpoint after the whole message, so a differing tail changes the cached unit. Anthropic's own docs say a cache hit needs an identical prefix up to the breakpoint, which is consistent with that explanation. What was measured is the absence of reads for a shared system prompt plus a shared leading part of the message.

Consequence: a cost estimate for CLI-driven Haiku calls should price input at the cache-write rate and add ~600 tokens per call; many small calls are disproportionately dear (extraction was 47% of the pipeline's spend). Calling the API directly without cache_control would price the same input at $0.10/MTok and drop the overhead (derived from list prices, not measured). WHAT THIS DOES NOT MEAN: do not plan on `claude -p` prefix caching across a fan-out of calls that share a prefix; any saving from prefix caching in such a design is a direct-API computation (explicit cache_control), not something the CLI gave in these runs. Caching is not worthless in general - a large prefix reused within the cache lifetime reads at 10% of base input - and these numbers say nothing about other models, other CLI versions, or interactive sessions.
