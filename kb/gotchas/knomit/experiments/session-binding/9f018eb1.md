# An open knomit experiment binding does NOT survive a knomit server restart: the session silently falls back to the agent branch, and a write to a fact that exists only on exp/<name> fails with "file not found" — re-open the experiment (knomit_experiment open <name>) before writing after any restart

Observed 2026-09-27 during F07 PR 1b. The session had opened experiment `feat-f07-trigger-dispatch` (knomit_experiment open moves the connection onto exp/feat-f07-trigger-dispatch) and written 7 facts there. The user then restarted the knomit server. Later, three knomit_update calls on those facts (kb/architecture/repos/triggers/change-context/..., kb/decisions/repos/triggers/fire-log-write-behind/..., kb/invariants/repos/triggers/watermarks/...) all failed with `file not found: <path>`. `knomit_experiment list` showed the experiment still existing but `"branch": "agent/mindev.local-8ef0cd32"` and "this session is on agent/...": the state that pins a connection to its experiment branch — keyed by (session id, mount uid) on a URL-scoped bridge, see the mcp-surface decision — lives in the server's memory and is lost on restart, while the experiment itself (a branch plus an experiments row) persists.

This is a DIFFERENT loss from kb/gotchas/knomit/experiments/commit-ordering (another session or the UI COMMITS the experiment and the owner heals onto the agent branch): here nobody touched the experiment; the server forgot which branch the session was on.

Why it fails safe here but not always: an UPDATE of an experiment-only fact fails because the path does not exist on the agent branch. A knomit_learn of a NEW fact would NOT fail — it would land on the agent branch, which is exactly the misattribution the experiment exists to prevent (facts describing code that has not merged, or that review then changes). So the failure mode to fear is a silent one.

What to do: after any knomit server restart (the coordinator may tell you, or a tool call may start behaving as if the experiment were gone), call knomit_experiment list and check `active_experiment`/the summary line; if the session is on the agent branch, call knomit_experiment open <name> again — re-opening an existing experiment resumes it and moves the session back onto its branch (no reconnect needed) — and only then write. Re-opening with a description replaces the description; without one keeps it. Verify with knomit_repos: the bound write mount shows `"experiment": "<name>"` and `write_branch: exp/<name>` when inside.

Misreading: "the experiment was rolled back" — no; the branch and its facts were intact, only the session's pointer had reset.
