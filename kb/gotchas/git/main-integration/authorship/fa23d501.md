# Never squash-merge agent branches into main — it destroys per-fact authorship

The trunk/history UI attributes each fact to the git AUTHOR of the commit that last touched its path, read verbatim from commit_log.author_name/author_email — which is populated directly from c.Author.Name/c.Author.Email of each git commit (commitEntries in fact_history.go). The history API exposes the author (not the committer) as-is. So the UI is a faithful mirror of git authorship in main.

Knomit's MCP server never writes main (main = consensus); merging agent branches into main happens EXTERNALLY (GitHub or git CLI). The merge strategy therefore decides whether agent authorship survives:

- GitHub 'Squash and merge' collapses all the agent's per-fact commits into ONE new commit whose author is whoever clicked merge (the GitHub user). Every fact touched in that squash is then attributed to the merger's identity, and the original agent authors are gone from main entirely. This is the observed symptom: 'the UI shows my GitHub user, not the agent that authored the fact.'
- 'Create a merge commit' (git merge --no-ff) preserves every original agent-authored commit; only the merge commit itself is authored by the merger. Per-fact attribution stays correct.
- 'Rebase and merge' preserves the author (committer becomes the merger).

Rule: integrate agent branches into main with a real merge commit or rebase-merge, NEVER squash. Squash flattens provenance — and once per-author tokens exist (author != committer), squash would flatten all distinct authors into the merger too. The author/committer split only survives integration if the merge preserves history.
