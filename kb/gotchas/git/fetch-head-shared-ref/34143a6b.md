# FETCH_HEAD is ONE shared ref per repository, so a background agent's own `git fetch` silently redirects your `git reset --hard FETCH_HEAD` to ITS commit — reset to origin/<branch> and echo the SHA

Hit on 2026-09-16 while gating PR #210. The sequence was: `git fetch origin feat/mcp-catalog`, then launch `/code-review 210` (which runs in the background), then `git reset --hard FETCH_HEAD`. The reset landed on 897e17ed — the PREVIOUS merge commit — instead of adb6133f, the PR head that had just been fetched.

MECHANISM. FETCH_HEAD is a single file in .git, not a per-invocation value: every `git fetch` in that repository overwrites it, whatever process ran it. `/code-review` performs its own fetch of the PR under review. So between your fetch and your reset, the agent's fetch replaces FETCH_HEAD, and the reset resolves to whatever was fetched LAST rather than to what you fetched.

CONSEQUENCE, and why this one is worth a fact: it fails SILENTLY. git reports success and prints a commit line, so there is no error to notice — the only signal is that the printed SHA is not the one you expected. A reviewer who does not read it back runs the whole gate against the wrong tree: tests pass, criteria check out, and the verdict describes code that is not in the PR.

REMEDY. After `git fetch origin <branch>`, resolve and reset against the remote-tracking ref `origin/<branch>`, never FETCH_HEAD; the same applies to `git diff` and `git show` while an agent is in flight. Pin the ref before launching a concurrent agent when the order allows it, and always echo `git log -1 --format='%h %s'` after a reset so a wrong checkout is visible rather than assumed.

WHAT THIS DOES NOT MEAN. It is not a git bug and not specific to worktrees — a linked worktree shares .git with the main checkout, so it shares FETCH_HEAD too, but a single ordinary clone with two processes behaves identically. It is not fixed by fetching immediately before the reset: the competing fetch can land in the gap, and the gap is not under your control. And it is not specific to `/code-review` — ANY background agent that fetches in the same repository does this, so the rule is about concurrency, not about one tool.
