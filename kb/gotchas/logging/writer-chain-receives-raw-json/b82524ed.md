# Every extra writer handed to logging.Build/BuildWriter (the `ring` argument and the `tees` variadic) receives zerolog's RAW JSON event, not console text — only the ConsoleWriter wrappers format, so a consumer wanting human-readable lines must bring its own wrapper

`BuildWriter` assembles a `zerolog.MultiLevelWriter`. The stderr sink is `zerolog.ConsoleWriter{Out: consoleOut}` and the file sink is a second `ConsoleWriter` (with `NoColor` and `TimeFormat: fileTimeFormat`), but `ring` and each entry of `tees` are appended UNWRAPPED. zerolog hands every writer in a MultiLevelWriter the same marshalled JSON event, so those two arguments see `{"level":"info","time":...,"message":...}` — never `<stamp> <LVL> <message>`.

This is easy to get wrong in the direction that LOOKS fine: `crashdump.Global` (the ring) genuinely wants raw records, so the existing call site gives no hint that a new consumer might not.

**Consequence:** a consumer that needs the human-readable shape passes its own formatting wrapper, not itself. `logging.Tap.Writer()` is the worked example — it returns `zerolog.ConsoleWriter{Out: t, NoColor: true, TimeFormat: fileTimeFormat}`. NoColor because ANSI escapes would reach the consumer inside the level token; `fileTimeFormat` (RFC3339) because it contains no space, and a stamp with a space shifts the level out of the second whitespace token and silently disables the Manage Logs tab's level filter.

**Pin the format through the REAL chain.** `TestTapWriter_EmitsTheFileFormatThroughTheRealChain` builds a logger via `Build` and asserts on what lands in the tap, rather than writing a hand-made line into it — a test that feeds the consumer directly proves nothing about what zerolog actually delivers.

**WHAT THIS DOES NOT MEAN:** `tees` is not a second `ring`. They are separate parameters because `ring` has one documented job (crash reports retain the recent tail) and overloading it would make that doc a half-truth.
