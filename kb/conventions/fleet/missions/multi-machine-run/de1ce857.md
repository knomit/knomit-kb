# Running a mission across machines (what worked first time in the first mission, 2026-10-02): one host instance with the mTLS listener bound to a private-network (tailnet) address, each peer enrolled with `knomit identity enroll` on the operator side and `knomit identity install --root <fingerprint>` reading the bundle from stdin (over ssh for a Linux peer), every repo cloned or subscribed FROM the host — including repos the host itself only subscribes to — KNOMIT_SERVER exported for every `kb` on every member, and a remote peer built from an isolated clone with its `dist` first on PATH

Source: the first mission's real run (three instances: a host+worker and a local peer on one macOS machine, a remote Debian x86_64 peer), recorded in the run report of 2026-10-02 and the rehearsal of the same day. Every item below ran without a fix; the items are generic (no addresses, names or paths belong in this fact).

1. ONE HOME PER INSTANCE. Each instance runs `knomit serve` with its own KNOMIT_HOME and its own plaintext port; strip CLAUDE* variables from the environment of a session-running instance. Fleet enrolment lives in that home's pki dir.
2. FLEET ROOT ON THE OPERATOR'S MACHINE, never on an instance: `knomit identity init-master` prints the root fingerprint (SHA-256 over the root key's SSH wire encoding — NOT `openssl x509 -fingerprint`; rehearsal finding F3). Hand that value out of band.
3. ENROL EACH PEER: on the operator side `knomit identity enroll` signs the instance's existing public key into a bundle; on the instance `knomit identity install --root <fingerprint>` with the bundle on stdin (`--bundle -` or no flag). For a Linux peer this is one ssh command with the bundle piped to its stdin; `install` without `--root` prints the fingerprint it sees, which is the value to confirm. Enrolment is per instance home.
4. mTLS LISTENER ON THE HOST: set `[tls].addr` (env KNOMIT_TLS_ADDR) to the host's private-network address and port — a tailnet IP worked — and keep the plaintext listener on loopback. The mTLS listener is a separate http.Server over the same handler, on only when the address is set and a certificate is installed (kb/decisions/auth/tls-separate-listener/34bcb7f1.md). Pushing to /git requires an enrolled instance certificate; `external_addresses` is how a member advertises itself and is copied verbatim from its knomit.toml (kb/invariants/fleet/member-addresses/40335d34.md).
5. REPOS: the host HOSTS the mission repo and the mission's KB (no origin, so their main advances by the local reconcile). Peers CLONE (write) the mission repo and KB from the host's mTLS address and SUBSCRIBE (read-only) to the reference KBs. The host may itself SUBSCRIBE to a KB from another instance or a local archive and still serve it onward: a subscription is served for fetch over /git and only refuses pushes (`pushPolicy` in internal/web/gitremote.go). Peers subscribing to it see its main.
6. LENS ON EVERY MEMBER: the same lens name everywhere (write: the mission KB; read: the mission KB plus the reference KBs), so a session bound to the lens on any member writes to the same KB.
7. KNOMIT_SERVER EVERYWHERE: each instance logs `this server's address (KNOMIT_SERVER for kb)` at start; export exactly that value for every `kb`/bridge invocation on that machine (kb/architecture/bridge/server-address/resolution/7d8ca9d3.md; why: kb/incidents/bridge/server-address/knomit-home-did-not-choose/b2797a72.md). Recipe `exec` children get it automatically (kb/invariants/repos/triggers/recipes/server-address/a0d4f7b0.md); anything the operator runs by hand does not.
8. ISOLATED BUILD ON A REMOTE PEER: clone the knomit source into the peer's home at the exact commit, `make build` (it needed no system packages on Debian 12), and start the peer from a script that puts that build's `dist` FIRST on PATH for the peer's process only — the user's own `knomit`/`kb` on that machine stay untouched. On macOS `make desktop-install` leaves the PATH `knomit`/`kb` stale; `make build` plus linking the binaries is what refreshes them (rehearsal E1/F1). Sessions on the peer then use the isolated `kb` and the machine's own `claude` login.
9. DETACH: `knomit serve` execs in the foreground; a remote start over ssh needs `setsid nohup` or equivalent.

WHAT THIS DOES NOT MEAN: it is not a security review of the topology (loopback plaintext + tailnet mTLS was chosen for a run on trusted machines), and it does not say the operator's permission classifier will allow every step unattended — in both runs a subscribe and an ssh were denied to the agent and done by the user. Keep real addresses, hostnames and home paths in the run's own files, never in facts.
