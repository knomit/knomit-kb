# Set up a fleet repository ROOT FIRST: commit artifacts/fleet/root.crt and crl.pem when the repository is created, and add members only afterwards. root.crt is added only while it is missing (write-once), so whoever adds it first owns the fleet's PKI

Ruling (PR #514 round 3, ruling 4) answering review F5 (trust on first root). OPTIONS: (a) declare the expected root fingerprint in the ontology: not taken; (b) build 'root + members in one commit' tooling: REJECTED, no new mechanism; (c) keep the existing write-once rule (a root is added only if missing) and DOCUMENT the order: CHOSEN. The documented order closes the window in which an already-admitted member could commit a rogue root. It is written in the fleet preset's comment (internal/domain/fact/ontology_fleet.yaml), the knomit-playbooks fleet template README, and the design doc (D7).

A root alone without a CRL leaves every member's next commit refused no-cert (rule B fails closed), so the CRL lands with it.

ENFORCED BY CODE ON ONE PATH (PR #518, merge 537f2019): Manager.CreateFleet (POST /api/v1/fleet/create) commits root.crt + crl.pem as the FIRST commit on the new fleet's agent branch, then the leaf (certs/<id>.pem + issued/<serial>.pem), then the member record, and only then publishes main. MISREADING: this is not enforced by the store or the judge. A fleet repository that did not come from the create (one joined from a host or forge is whatever that host holds) still accepts the first root.crt anyone commits, and write-once makes a wrong first add irreversible inside the gate (only a hand commit with verification off can undo it). The order is a property of the create, not of the repository.
