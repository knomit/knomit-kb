# A panel hanging inside an overflow:hidden pane clamps itself with usePanelClamp against the nearest [data-panel-bounds] ancestor — the pane marks the element that CLIPS, the panel takes maxWidth and min(nominal, maxHeight), and its list (not its header) is the flex:1/minHeight:0 scroller

**The mechanism (web/src/hooks.ts).** `usePanelClamp(ref, active)` runs in a layout effect while `active`:
- It finds `el.closest('[data-panel-bounds]')` (`PANEL_BOUNDS_ATTR`) and the panel's `parentElement`, which is its containing block.
- It returns `maxWidth = bounds.right − PANEL_BOUNDS_GUTTER(8) − parent.left` and `maxHeight = bounds.bottom − 8 − (parent.bottom + PANEL_GAP(6))`, each floored at 0.
- With no bounds ancestor it returns `{}`, meaning no clamp.

**Re-measure triggers, the complete list:**
1. on open (the layout effect itself);
2. the bounds element resizing (ResizeObserver);
3. the anchor resizing (the same ResizeObserver);
4. the bounds element SCROLLING (`scroll` listener). An overflow:hidden pane still scrolls programmatically, e.g. on scroll-into-view, which moves the anchor inside a pane of unchanged size, and no resize fires;
5. window `resize`, ONLY as the fallback where `ResizeObserver` does not exist (jsdom). Alongside an observer it would measure every resize twice.

**The complete trigger list does NOT mean the clamp cannot go stale.** A ResizeObserver reports SIZE changes, not position. The anchor can MOVE at unchanged size with no resize or scroll firing. Example: while a panel is open, the meta row above the edges row gains a line from async content, which pushes the anchor down inside a bounds element whose size did not change. `maxHeight` then stays too tall by that amount, so the panel's bottom can be clipped by the pane, until the next resize or scroll re-measures.

The list rail's drag resizes the pane without resizing the window, so (2) is the main production path. A measure that yields the same maxWidth and maxHeight keeps the previous state object, so it does not re-render the panel. Closing (ConnectionsPanel stays mounted, so `active` goes false) and unmounting both disconnect the observer and remove the listeners.

**Consumers:** ConnectionsPanel and MotifPanel pass `maxWidth` through and use `maxHeight: Math.min(NOMINAL, clamp.maxHeight ?? NOMINAL)` (`CONNECTIONS_PANEL_MAX_HEIGHT` 360, `MOTIF_PANEL_MAX_HEIGHT` 420). Their nominal widths are unchanged. RightPanel puts `data-panel-bounds` on the fact view's `flex:1; minHeight:0; overflow:hidden` wrapper, the box that actually clips the header's panels.

**Why measure the PARENT, not the panel:** ConnectionsPanel slides in with `translateY(-8px → 0)`, so its own rect is up to 8px off during the first frames. The parent is the stable anchor that `top:100%; left:0` hangs from.

**Why measure the PANE, not the viewport:** the pane is what clips. Whenever the list rail is open, the viewport extends past the pane on the left, so a viewport clamp would still let the pane cut the panel.

**A clamp is only a scroll if the list is what gives.** Each panel is `display:flex; flexDirection:column; overflow:hidden`, the header is `flexShrink:0`, and the list is `flex:1; minHeight:0; overflowY:auto`. Drop `minHeight:0` and the list's min-content propagates up and pushes past the clamp (kb gotcha flex-min-content-propagation). `panelClamp.test.tsx` pins all of these for both panels.

**The header survives VERTICAL clamping only.** It is one flex row with esc/× pushed right by `marginLeft:auto`. Nothing in it has `minWidth:0` or truncation, and its min-content width is roughly 150–200px. Clamp `maxWidth` below that and esc/× are pushed past the panel's right edge and clipped by the panel's own overflow:hidden. At `maxWidth: 0` the panel shows as a 2px sliver of border. That is reachable only in extreme layouts (a pane under ~236px, e.g. a ~600px viewport with the list rail at max) and was left as is in PR #328.

**Consequence for a new panel in an overflow:hidden region:** call usePanelClamp with the panel's ref, make sure the region that clips carries `data-panel-bounds`, and make the panel's own parent its containing block (position:relative). The RightPanel wiring tests assert both for ConnectionsPanel AND MotifPanel.

**What this does NOT mean:**
- *Not* a viewport or portal clamp. The panel stays in-tree (see the panel-clamp-in-tree decision).
- *Not* a flip or reposition. The anchor is fixed (left:0, top:100%), and the panel only ever SHRINKS. If the anchor itself is at or past the pane edge, the result is 0, and the panel collapses rather than moving.
- *Not* that the window resize listener is dead code to delete. It is the only trigger where ResizeObserver is absent, and a test covers that path with the global removed.
- *Not* verified by jsdom. The tests stub getBoundingClientRect and a fake ResizeObserver, and pin the arithmetic, triggers and teardown. Whether the panel visibly fits is a browser-pass claim (kb convention browser-pass-gate).
