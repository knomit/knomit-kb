# Layout claims on the Manage panes need a browser pass as a gate — jsdom passed both the broken and the fixed version of two separate defects, so a green vitest run is not evidence about layout

Any change to the Manage panes that makes a claim about SIZE, POSITION or SPACING must be verified by driving the running app and measuring boxes. A green `vitest run` is not evidence for such a claim, and must not be reported as if it were.

**Grounds.** In PR #202 two layout defects shipped or nearly shipped under a fully green suite, because jsdom does not perform layout:

- A card at `min-height: auto` rendered 1570px inside a 1056px pane (see kb/gotchas/web/ui/manage-page/flex-min-content-propagation/0e211270.md). 1470 tests passed against both the broken and the corrected version.
- A checkbox overlapped its own label text (see kb/gotchas/web/ui/inline-label-flex-whitespace/3054dd67.md). Invisible to jsdom AND to a close style-object review; found by a user looking at the app.

**What a jsdom assertion CAN do, and what it cannot.** It can pin the PROPERTY that produces the behaviour — `card.style.minHeight === '0px'`, `label.style.gap === '6px'`, the root's floor, the absence of an `overflow` on the card. It cannot observe the rendered outcome. Assertions of this kind should say so where they live, so a later reader does not mistake a green suite for a verified layout.

**Two method rules, both learned by getting them wrong:**

1. **Measure by resizing the real viewport; never by mutating the container in-page.** A first measurement run that set `detailCol`'s `height` and `flex: 'none'` from inside the page produced different and misleading numbers than a genuine window resize, and had to be discarded.
2. **An assertion of ABSENCE can pass vacuously against the wrong element.** The guard for "the card carries no overflow" selected `firstElementChild`, which on the PRE-change structure was the heading row rather than the card — so it passed against the very code it existed to catch. Fixed by first asserting the element IS the card (`expect(card.querySelector('table')).not.toBeNull()`). Assertions of specific VALUES fail closed; assertions of absence do not. Every new assertion should be run against the parent commit and seen to fail.

**Corollary about reviewing CSS by reasoning.** A well-argued review finding — drop `minHeight: 0` so the card floors at min-content — was accepted, implemented, and was wrong; it caused the 1570px card. Reasoning about the cascade produces confident, plausible, incorrect prescriptions. Measure before prescribing, and before accepting a prescription.

**WHAT THIS DOES NOT MEAN.** Not that every Manage-pane change needs a browser pass — a copy edit, a handler change or a data-shape fix does not. The trigger is a claim about size, position or spacing.

**Related, and a different trap in the same family:** `npx tsc --noEmit` under `web/` type-checks zero files and always exits 0 — see kb/gotchas/build/web/typecheck/9b4704c3.md. Use `cd web && npm run build`. Reporting "tsc clean" from `--noEmit` reports nothing.
