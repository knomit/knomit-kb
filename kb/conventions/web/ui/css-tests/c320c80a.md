# Tests of phone-width CSS resolve the cascade over the real App.css with cascade.testutil.ts; a test that only pins class hooks does not falsify the CSS

jsdom does no layout and evaluates no @media, so a test of narrow-width CSS cannot just render and measure. `computed(element, property, width)` in web/src/cascade.testutil.ts reads the real web/src/App.css (cwd is web/ under npm test) and decides, for one element at one viewport width, which declaration wins (!important, then inline style, then specificity, then source order). It was moved out of connectNarrow.test.tsx unchanged in PR #534; connectNarrow, TopBar.test.tsx (label min-width 96px at 640 and 375, 0px at 641 and 1280) and App.rail.test.tsx (body column, rail 100% width and max-height 40% at 640 and 375; 236px and no column override at 641 and 1280) all use it.

RULE: a test of phone-width CSS asserts the resolved value at widths on BOTH sides of the breakpoint through `computed`, and asserts the class hooks (`k-shell-body`, `k-rail`, `k-bar-label`) exist on the real components.

WHY: the first cut of #534 had a test that pinned only hooks and shrink styles. A reviewer deleted the whole @media block and the test still passed, and deleting the hooks from App.tsx/TargetRail.tsx left the suite green while the stacking silently stopped. After the rewrite, six committed sabotages (delete the block, drop each of three hooks, strip flexShrink 1 to 0, label min-width to 0) each failed a test.

WHAT THIS DOES NOT MEAN: the cascade check does not replace a real-browser pass; it proves the stylesheet says the right thing, not that the layout fits. The label-collapse gotcha was invisible to every vitest and was found only by measuring in Chromium.
