# The log viewer is split by how a line is READ (web/src/logLines.ts: parseLine, rank, visibleLines) versus how it LOOKS (web/src/LogView.tsx: highlight, splitTail, day divider, styles); the parse layer lives in a .ts module because react-refresh/only-export-components forbids non-component exports from a component file, and ManageLogs must count with the same visibleLines the body filters with

**Rule:** anything that parses, ranks or filters a log line goes in `web/src/logLines.ts`; anything that renders one goes in `web/src/LogView.tsx`, which exports only the component. Do not add a non-component export to LogView.tsx; the repo's lint config (react-refresh/only-export-components) rejects it, and the same rule is why ManageSessions.tsx says it exports components only and why useClientSessionChanges.ts is its own file.

**Why the whole parse layer moved, not one function (PR #199 lint fix):** ManageLogs.tsx needs `visibleLines` so the "N shown" count is computed by the very function the body filters with and the two can never disagree. `visibleLines` leans on `atOrAbove`, `searchText`, `levelOf`/`parseLine`, so exporting only it would have traded three lint hits for four. The honest seam is read-vs-look.

**Two contracts that travelled with the parser and must stay true:**
- A line's shape is `<RFC3339 stamp> <LVL> <message>`, the FILE format from internal/platform/logging, pinned by a test through the real writer chain; the server's log tap must keep emitting that shape or the level filter silently stops ranking.
- The store's dropped-lines marker (logStore.ts `droppedMarker`) is deliberately NOT in that shape, so it is unrankable and a level filter can never hide a gap the server has admitted to. `highlight` and `splitTail` are un-exported helpers inside LogView.tsx.

**Also in ManageLogs:** the "behind" pill count is React state set in the scroll handler beside `setFollow(false)`, not a ref read during render; the ref version was correct only because the single writer happened to pair it with a state change. Setting it from an effect instead would trip react-hooks/set-state-in-effect.

**Misreading to avoid:** 'move helpers out of component files' is not a general instruction to scatter helpers; the parsing comments that each encode a fixed bug travelled as a block for that reason.
