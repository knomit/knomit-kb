# Every API handler that reads a JSON request body reads it with decodeJSON (or decodeOptionalJSON when the body may be absent) — never json.NewDecoder(r.Body) — which answers 415 unless Content-Type is application/json, 413 over the caller's own limit, 400 "Invalid request body" with the byte offset, and writes v only on success; it accepts unknown fields and cannot protect a mutation that has no body

RULE. A handler in internal/web that decodes a JSON request body calls `decodeJSON(w, r, &v, maxBytes)` and returns when it reports false (it has already written the problem document). A route whose body is OPTIONAL calls `decodeOptionalJSON` instead. Do not write `json.NewDecoder(r.Body).Decode` in a handler.

WHAT IT ENFORCES (internal/web/decode_json.go):
- Content-Type must parse (mime.ParseMediaType) to exactly `application/json`. Parameters such as charset, and letter case, are tolerated. Anything else, INCLUDING AN ABSENT Content-Type, is 415 "Unsupported Media Type" and the body is not read. `application/merge-patch+json` and other +json types are refused too.
- maxBytes > 0 wraps MaxBytesReader; an over-long body is 413 "Request body too large" naming the limit. maxBytes 0 means NO limit. Each call site passes the limit it already had (maxCreateBodyBytes, maxRepoPatchBodyBytes, maxRenameBodyBytes); the helper invents none, and none may be added for fact bodies as a fixed constant (fact size is a corpus property).
- A syntax or type error is 400 "Invalid request body" with the byte offset (and the field, for a type mismatch). An empty body on decodeJSON is 400 too.
- v is written ONLY on success: the body is decoded into a fresh value and copied, so a half-decoded body never leaves a caller holding partial input.
- decodeOptionalJSON lets an EMPTY body through whatever its Content-Type (v untouched), and holds a non-empty body to the same rules. A chunked body (ContentLength -1) is judged by peeking one byte, which is put back.

WHY. A cross-site page cannot send `application/json` without a CORS preflight, which corsMiddleware refuses for an origin it does not allow. So this rule turns every body-carrying mutation into a non-simple request: a second, independent layer behind the loopback Origin check (kb/invariants/auth/loopback-anonymous-host), for a browser that sends no Origin at all.

WHAT IT DOES NOT DO — the misreadings:
- It does NOT protect a mutation with NO body. DELETE fact/repo/lens, experiment commit/rollback/sync, origin-session commit, synthesis and index runs carry no body, so there is no Content-Type to judge; against a browser that omits Origin they rely on the Origin check alone. This is deliberate: see the decision under kb/decisions/web/json-decode-partial-not-mutation-wide.
- It does NOT reject unknown fields. That is not a CSRF control, and it would break a client for sending more than the server reads.
- It does NOT limit body size by default. 0 is no limit.
- It is not applied to: oauth_pending_api approve (browserProof already requires JSON from a browser), the OAuth listener (bearer tokens are not ambient), /mcp (mcp-go checks its own Content-Type), git, ontologies:validate (YAML), or any route without a body.

CLIENT EVIDENCE at the change. The web UI (and the desktop, which serves the same api.ts) sends `Content-Type: application/json` on every body mutation. It sends experiment commit/rollback/sync as a POST with NO body and NO Content-Type (api.ts experimentAction), which is why those routes use decodeOptionalJSON. The bridge only talks to /api/v1/mcp. The README curl for POST /repos sends JSON. Runtime check against a live server: the UI's repo create (202), repo description PATCH (200), experiment rollback (204) and commit (204) all succeeded; curl text/plain POST /facts got 415, curl JSON got 201.

TESTS. Fixtures that post a JSON body build the request with `newJSONRequest` (httptest.NewRequest plus the header); a test about the Content-Type rule sets or deletes the header afterwards. The helper's table test is TestDecodeJSON; the router-level tests (real 127.0.0.1 listener, Server.Handler) are TestDecodeJSON_PlainTextFactPostIsRefusedThroughTheRouter and TestDecodeOptionalJSON_ExperimentCommitThroughTheRouter. All fail with the Content-Type check sabotaged.
