# Every API handler that reads a JSON request body reads it with httpx.DecodeJSON (or httpx.DecodeOptionalJSON when the body may be absent) — never json.NewDecoder(r.Body) — which answers 415 unless Content-Type is application/json, 413 over the caller's own limit, 400 "Invalid request body" with the byte offset, and writes v only on success; it accepts unknown fields and cannot protect a mutation that has no body

RULE. A handler in internal/edge/web that decodes a JSON request body calls `decodeJSON(w, r, &v, maxBytes)` and returns when it reports false (it has already written the problem document). A route whose body is OPTIONAL calls `decodeOptionalJSON` instead. Do not write `json.NewDecoder(r.Body)` or `io.ReadAll(r.Body)` in a handler: TestNoHandlerDecodesARequestBodyOutsideDecodeJSON parses internal/edge/web and fails on either, naming decodeJSON. Its allowlist (bodyReadAllowed) holds only ontologies:validate (YAML) and OAuth approve (behind browserProof), each with its reason, and an entry whose read has gone fails too. It sees the ordinary shape (a `.Body` field in the call's arguments, directly or through MaxBytesReader); a body passed through a variable first is not seen.

WHAT IT ENFORCES (internal/edge/web/decode_json.go):
- Content-Type must satisfy `isJSONMediaType`: media type exactly `application/json`, parameters such as charset and letter case tolerated. Anything else, INCLUDING AN ABSENT Content-Type, is 415 "Unsupported Media Type" and the body is not read. `application/merge-patch+json` and other +json types are refused. isJSONMediaType is the ONE predicate: browserProof (the OAuth approval gate) calls it too, so the two gates cannot disagree about what counts as JSON.
- maxBytes > 0 wraps MaxBytesReader; an over-long body is 413 "Request body too large" naming the limit, including when the excess is trailing whitespace. maxBytes 0 means NO limit. Each call site passes the limit it already had (maxCreateBodyBytes, maxRepoPatchBodyBytes, maxRenameBodyBytes); the helper invents none, and none may be added for fact bodies as a fixed constant (fact size is a corpus property).
- The body must be EXACTLY ONE JSON value: after it, only whitespace. `{...} garbage`, `{...}{...}` and `{...}}` are 400 "Invalid request body" ("trailing data after the JSON value"). It is checked with Decoder.Token()==EOF, not More(), because More reports false for a stray closing bracket.
- A syntax or type error is 400 "Invalid request body" with the byte offset (and the field, for a type mismatch). An empty body on decodeJSON is 400, and so is a nil r.Body (a hand-built request; net/http's server always sets http.NoBody).
- v is written ONLY on success, and then WHOLE: the body is decoded into a fresh value and copied, so callers pass a zero value — a field the body omits ends up zero, not kept from what v held.
- decodeOptionalJSON treats a body that is empty OR ONLY JSON WHITESPACE as absent, whatever its Content-Type, and leaves v untouched: `curl -X POST -d ' '` (a single space sent as a form) is an ordinary experiment commit. It reads past the leading whitespace to decide, whatever the declared length, and that whitespace counts toward maxBytes. A body with anything else in it is held to decodeJSON's rules.

WHY. A cross-site page cannot send `application/json` without a CORS preflight, which corsMiddleware refuses for an origin it does not allow. So this rule turns every body-carrying mutation into a non-simple request: a second, independent layer behind the loopback Origin check (kb/invariants/auth/loopback-anonymous-host), for a browser that sends no Origin at all.

WHAT IT DOES NOT DO — the misreadings:
- It does NOT protect a mutation with NO body, nor an optional-body route sent an empty or whitespace-only body. Those rely on the Origin check alone against a browser that omits Origin; the complete list is in kb/decisions/web/json-decode-partial-not-mutation-wide. This is deliberate.
- It does NOT reject unknown fields. That is not a CSRF control, and it would break a client for sending more than the server reads.
- It does NOT limit body size by default. 0 is no limit.
- It is not applied to: oauth_pending_api approve (browserProof already requires JSON from a browser, via the same isJSONMediaType), the OAuth listener (bearer tokens are not ambient), /mcp (mcp-go checks its own Content-Type), git, ontologies:validate (YAML), or any route without a body.

CLIENT EVIDENCE at the change. The web UI (and the desktop, which serves the same api.ts) sends `Content-Type: application/json` on every body mutation. It sends experiment commit/rollback/sync as a POST with NO body and NO Content-Type (api.ts experimentAction), which is why those routes use decodeOptionalJSON. The bridge only talks to /api/v1/mcp. The README curl for POST /repos sends JSON. Runtime check against a live server: the UI's repo create (202), repo description PATCH (200), experiment rollback (204) and commit (204) all succeeded; curl text/plain POST /facts got 415, curl JSON got 201.

TESTS. Fixtures that post a JSON body build the request with `newJSONRequest` (httptest.NewRequest plus the header); a test about the Content-Type rule sets or deletes the header afterwards. The helper's table test is TestDecodeJSON (plus TestDecodeJSON_NilBody); the router-level tests (real 127.0.0.1 listener, Server.Handler) are TestDecodeJSON_PlainTextFactPostIsRefusedThroughTheRouter and TestDecodeOptionalJSON_ExperimentCommitThroughTheRouter, the latter including the whitespace-only form commit. All were seen red: the Content-Type rows with the check sabotaged, the rest before their fix.
