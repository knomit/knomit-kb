# A web API call that carries secret_id, any /secrets call, PUT /origin/credential with secret_id (including null), DELETE /origin and a gated origin-session commit send the same-origin proof header (oauthHeaders / secretAwareHeaders in api.ts); a call without secret_id stays a plain JSON request

The server admits linking, unlinking and the secrets API only through the local-or-same-origin admin gate, which for a browser needs the same-origin proof: `X-Knomit-Client: web`, a JSON Content-Type on mutations, and the Origin the browser adds itself. In web/src/api.ts these calls build their headers with `oauthHeaders(true)` or `secretAwareHeaders(secretId)`: every `/api/v1/secrets` call (secretsCall), `setOriginCredential` when the body has a `secret_id` key (a string links, null unlinks), `createRepo` / `probeOrigin` / `probeInitialized` / `createSession` / `restoreRepo` when they carry a secret_id, `deleteOrigin` (a linked repo's detach unlinks), the fleet routes (fleetCall, already), and `streamCommit` with `gated: true` (the session links a secret or replaces a linked origin; it then also sends a JSON body `{}`).

Consequence: when adding a new call that may carry secret_id, route its headers through `secretAwareHeaders(secret_id)`, or the server answers 403 and the UI shows a permission refusal. Do not add the header to calls that never reach the admin gate: on the desktop every call is cross-origin, and the header turns a simple request into one with a CORS preflight.

Not meant: the header is not authentication. It is one part of the browser proof; a remote OAuth bearer or an operator token still fails the admin gate whatever headers it sends. Pinned by web/src/api.secrets.test.ts.
