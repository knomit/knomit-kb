# A bounded list endpoint takes its page size in the query, echoes the resolved size AND the ceiling in the response, and reports `truncated` from a probe row — and EVERY consumer of it must carry the marker with the number

The shape established by `GET /api/v1/sessions` in PR #217, to copy when bounding any other list.

FOUR PARTS, each earning its place.

1. PAGE SIZE IN THE QUERY, with a default and a ceiling and NO unlimited value. `?limit=`; omitted or non-positive takes the default; above the max is clamped. Omitting the unlimited form is the point — leaving one means the unbounded read is still reachable, which is what was being removed.

2. THE RESOLVED SIZE AND THE CEILING ARE ECHOED in the response (`policy.limit`, `policy.max_limit`), beside the other thresholds. The default-and-clamp rule lives in ONE exported function (`ResolveListLimit`) that both the store and the handler call, so the number echoed is the number served. Two copies of that rule drift the first time one changes.

3. `truncated` COMES FROM A PROBE ROW, not from a count comparison. Query `LIMIT n+1`, drop the extra, report whether it was there. `len(rows) == limit` cannot distinguish a full page from an exhausted one, and those are exactly the two states a caller needs to tell apart. Test BOTH directions — an exactly-full page must NOT be truncated, and one row more must be — because an off-by-one is wrong in a different way on each side.

4. THE ORDER IS PART OF THE CONTRACT. `ORDER BY last_seen_at DESC, id` is what makes truncation meaningful rather than arbitrary: the page that survives is the most recently active, which is what the view is for, and the tie-break makes the cut deterministic. A test must assert WHICH rows survived and in what order — a count-only assertion passes against a LIMIT that keeps any page at all.

AND THE RULE THAT IS EASIEST TO MISS: EVERY consumer of a bounded list must carry the truncation marker WITH the number it derived. Bounding the read and marking it in one place, while a second consumer keeps rendering a bare figure from the same page, reintroduces the silent failure one component over. On #217 the table was honest and the badge beside it was not, from the same response, with `truncated` unused on the adjacent line.

WHAT THIS DOES NOT MEAN: not every list needs this. It is for a list whose size is driven by external activity and can therefore grow without a bound the code controls. A list of the server's own repos or lenses does not qualify — see the deliberate no-paging decision for `knomit_repos`, where the growth path is a `match` argument rather than a page.
