# A PR that adds or MOVES a public HTTP endpoint shows its openapi.yaml entry in the same PR — #219 shipped a public SSE stream with no spec entry at all and the review gate cleared it, because the gate covered what was briefed and pre-registered and this was in neither

THE RULE: if a PR adds a public HTTP endpoint, or moves one to a new path, the diff includes its entry in `internal/web/static/openapi.yaml`. A move is included deliberately — a relocated endpoint whose spec entry stays at the old path is worse than none, because it is confidently wrong.

THE ANCHOR, verified rather than recalled: PR #219 added `GET /api/v1/repos/events`, a public SSE stream, and `594b551a` does not touch `openapi.yaml` at all. The endpoint shipped undocumented and the review gate CLEARED it. PR #222, which moved that endpoint to `/api/v1/repo-events`, added the entry — closing a gap rather than updating a path.

WHY IT WAS MISSED, and this generalises past OpenAPI. The gate covered what the brief listed and what the reviewer had pre-registered, and "a new public endpoint appears in the spec" was in NEITHER. A review gate assembled from briefs and pre-registrations has holes exactly where nobody thought to look, and those holes surface one incident at a time — this was the second completeness class that gate acquired from a miss rather than from design. A periodic sweep of what a gate does NOT cover is cheaper than waiting for the next miss to name it.

WHERE THE RULE LIVES MATTERS. It is also written into the repo-event handler's own comment: adding a kind is "a new case in the switch below and a new entry in the OpenAPI description, not a new stream". A rule that lives only in whoever happens to be reviewing is weaker than one written where the work happens — prefer putting a completeness requirement at the code it governs, and keep the reviewer's copy as backstop rather than as the only copy.

ACCEPTED COST: the repo-event scope rule now exists in both the handler comment and the spec description, which can drift. Taken deliberately — an API consumer cannot read a Go comment.

WHAT THIS DOES NOT CLAIM: that every endpoint currently in the router is documented. That is UNVERIFIED, and a reader must not infer spec completeness from this convention. It states what a PR must do from now on, not what the spec already contains.
