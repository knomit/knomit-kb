# A lens provider stub that RECORDS what it saw needs a mutex — the fan-out calls it once per mount concurrently, and without it the race is in the test's bookkeeping, not the code

The lens provider contract is now "called ONCE PER MOUNT, CONCURRENTLY" for the stats and search fan-outs. Production providers are stateless empty structs and need nothing. Test stubs that record what they saw — `lastOpts`, `lastPath`, `lastAxis`, call counters — are shared mutable state across goroutines and MUST hold a mutex.

Without it `-race` fails, and the failure is misleading: the race is in the test's own bookkeeping, not in the code under test. Reading such a report as a production defect sends you looking in the wrong place.

As of PR #185 the concurrently-reachable set is five stubs: lensSearchStub, lensStatsStub, lensActivityStub, motifResolvingLensStub and lensPivotFactsStub. lensFactsStub is NOT locked, because the facts fan-out is still serial — which is the maintenance point: the set is defined by which fan-outs are concurrent, not by which stubs exist. Parallelising `/lenses/{lens}/facts` or `/lenses/{lens}/topics` extends it.

This surfaces late and from an unrelated direction. lensPivotFactsStub arrived with the motif work and was fine while it landed; it only raced after a REBASE put it under the newly-concurrent search fan-out. Merging a branch that adds a recording stub and a branch that makes a fan-out concurrent produces a race neither branch had.

Lock the recording only, not the whole method — the canned lookup that follows is read-only.
