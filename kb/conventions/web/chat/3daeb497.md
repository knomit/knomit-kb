# A tool row's label is toolCallLabel: the loader's loaded tools, else chatCopy.toolVerb for the four tools toolKind names (bind, query, materialize, explain), else toolRowLabel's 'knomit: Knomit <rest>' derived from the name

chatState.toolCallLabel(call) words a timeline row: a load_tools call with loaded tools reads chatCopy.loadedToolsRow ('Loaded tools: a, b'); otherwise chatCopy.toolVerb(toolKind(name), running) when it returns one; otherwise toolRowLabel(name). toolKind is a HARDCODED name table (knomit_bind -> bind, knomit_query -> query, knomit_materialize and knomit_explain -> read) and toolVerb a hardcoded verb per kind ('Bound', 'Searched'/'Searching', 'Read'), approved copy from 2026-11-06. toolRowLabel strips a leading 'knomit_', replaces underscores with spaces and writes 'knomit: Knomit <rest>' (knomit_repos -> 'knomit: Knomit repos'); any other name is shown as it is. So a NEW knomit tool needs no page change and falls back to toolRowLabel, but bind/query/materialize/explain rows are worded by the web UI, not by the tool's metadata or description: the server sends no tool titles or descriptions to the page (GET /chats items carry name, arguments, is_error, duration_ms, summary, loaded only). The verbs do not depend on is_error: a FAILED bind still reads 'Bound <target>' (in red, with a red dot). The row, the side panel's header (ToolCallHead) and its breadcrumb all use toolCallLabel, so they cannot disagree. Misreading to avoid: the label is wording for the person, never an identifier; code keys on the call id and the tool NAME (e.g. 'knomit_materialize' decides fact rendering), not on the label.
