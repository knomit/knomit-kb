# A count raise TRIES to continue in place (new first call, reading past the ordinals on screen) but on real data usually falls back to a restart that keeps the reader's place, because the walk includes breadth-first and orders depth-first

MCP/REST materialize cursors refuse every argument except the cursor (and, on the first call only, limit), so raising Max facts cannot extend the old cursor. MaterializeStream (web/src/useMaterializeStream.ts) therefore issues a new first call with the larger count and compares each re-read ordinal n that is already on screen with what is shown (path + repo). If they match it drops them and appends from the first new ordinal, with nothing replaced or dimmed. THEY USUALLY DO NOT MATCH on real data: BFS to depth decides WHICH facts are included and a pre-order DFS decides their ORDER, so a larger cap admits facts that land between existing ones and shifts everything after. A mismatch falls back to a restart: the text dims, and the view records the section that was at the top (MaterializeView captures it whenever the stream goes stale with no place pending), fetches on until that section reappears at its new position, scrolls to it, and says so if it is gone and it landed on the nearest earlier one. So 'Raise to N and continue' is a restart that keeps your place in practice; the in-place path holds only when the longer walk happens to be a prefix-extension. optionChange() in materializeOptions.ts classifies the intent (same / continue / restart); the fallback is decided by the data. It does NOT mean the cursor is reused, and it does NOT mean on-screen sections are never replaced.
