# In the Move flow, a typed URL that is the forge the fleet is already on shows 'The fleet is already on this forge' and offers Update access instead of Test connection; Review is unreachable for it

As of PR #530 (4bdcf031). FleetFollowFlow in mode 'move' with fromForge set (the master on a forge, no interrupted move) computes alreadyHere = sameFleetURL(trimmed, fromForge) (the browser mirror of the server comparison). While true: an OutcomeCard (tone ask, testid fleet-follow-already-here, headline 'The fleet is already on this forge') shows the URL; the Test connection button is replaced by 'Update access…' (testid fleet-follow-update-access) when the parent passed onUpdateAccess, and otherwise stays but disabled; so the Review step cannot be reached for the same forge. FleetSettings passes onUpdateAccess, which switches the page to the Access flow (setFlow('access')); the flow is keyed by mode so it remounts, and focusFirstField moves the keyboard to the auth-method select (the clicked button has unmounted, so focus would otherwise fall to <body>). Back/cancel clears that hand-off.

The spelling does not matter: HTTPS://tok@GitHub.com/acme/fleet/ counts as the stored https://github.com/acme/fleet (FleetSettings.config.test.tsx).

CONSEQUENCE: this replaces the old behaviour where choosing the forge's own URL previewed a full move and only the submit answer (`unchanged`) said nothing moved. MISREADING: the page check does not replace the server rule; the server still answers `unchanged` for the same forge if a request arrives (kb/decisions/fleet/config-parity/update-access-credentials-only/d71c2a95.md). An interrupted move (fromForge undefined) is not covered: its move-back URL is deliberately not the stored forge.
