# Nil-safe methods on the child handle replace parent forwards: Dispatcher.Kick and Dispatcher.FiresByRun accept a nil receiver, so callers write ri.triggers.Kick() with no nil check and the RepoInstance forwards were deleted

At ee850fd6 (PR #632; guard P, ba1210d3, is the rule that forbids the forwards). RepoInstance.triggerKick (nil check plus kick) and RepoInstance.TriggerFiresByRun (nil check plus read) only forwarded to the dispatcher and were deleted. Dispatcher.Kick and Dispatcher.FiresByRun accept a nil receiver, so ri.onCommit, the index job's success, the reconcile loops (r.triggers.Kick is passed as the loop's kick func; ri.triggers is set once in newInstance and never reassigned, so the method value binds the same pointer the old method read, and calling a method value on a nil pointer returns without dereferencing) and the web handler (ri.Triggers().FiresByRun) call them without a check. FiresByRun on nil returns an empty slice and nil.

RepoInstance.TriggerReport STAYS: it renders the DISABLED report (the subscription or read-only reason, which only the instance knows) and otherwise returns Dispatcher.Report(ctx, logN, ri.Name()). Passing the name keeps the 'fire log unreadable' warning on the repo's CURRENT name after a rename (the dispatcher keeps the name it was built with, as every other dispatcher log line does). Report is not nil-safe by design.

CONSEQUENCE: a child handle that the parent holds as a possibly-nil pointer should make its read-only or coalescing methods nil-safe rather than add a forwarding method on the parent. WHAT THIS DOES NOT MEAN: Run is not nil-safe and no longer exists as an exported method (see the run-func capability decision).
