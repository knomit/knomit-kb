# `gofmt -w <dir>` in a repo that already has unformatted files sweeps up whatever else is dirty, silently widening a diff past the scope you just told a reviewer you were working within — format the files you edited, by name, and list them

This repo has files that are not `gofmt`-clean at `dev` and have been for a long time. That is the precondition that makes the habit dangerous: on a fully-formatted tree `gofmt -w <dir>` is a no-op on everything you did not touch, so the risk is invisible until the day it is not.

WHAT HAPPENED. A change scoped to four files ran `gofmt -w internal/web/` rather than naming them. Two OTHER files in that directory were already unformatted — 22 and 8 dirty lines at `dev` — and were silently reformatted too. The round's own scope line said "nothing else", and the reviewer found two more files in the diff.

WHY IT MATTERS MORE THAN WHITESPACE. Nothing broke: the sweep is semantically null by construction, and that is exactly the problem. A reviewer who has been told the scope is four files and finds six has to establish for each extra one whether it is null, and the tool gives no signal distinguishing "I reformatted this deliberately" from "a wildcard reached it". The cost is reviewer trust in the scope statement, which is expensive to rebuild and cheap to avoid.

THE CONSEQUENCE TO ACT ON: run `gofmt -w` on the FILES you edited, spelled out, not on a directory or a `./...`. If a sweep does happen, DECLARE the extra files and say why they were touched — a declared reformat is fine, an undeclared one is a defect in the scope statement.

WHEN REFORMATTING AN EXTRA FILE IS ACTUALLY FINE: when the change already edits it. Formatting a file you are modifying anyway is ordinary hygiene, and reverting it to restore misformatted code would be the odder move. The test is whether the change touches the file at all — NOT whether it touched the specific lines the formatter moved.

A MEASUREMENT TRAP that showed up while adjudicating this, worth its own sentence because it produced a wrong conclusion in review: `gofmt`-dirtiness measured across a series of commits is not a proxy for whether a file was EDITED. A file can be modified while its dirty-line count stays constant, so "formatting unchanged until now" does not imply "content unchanged until now". One `git diff -w <base>..<head> -- <file>` settles it; the proxy cannot.
