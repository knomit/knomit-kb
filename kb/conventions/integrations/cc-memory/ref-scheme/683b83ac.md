# Knomit ref scheme: kb://<repo-id>/<path> for facts, src://<repo-id>/<path>@<commit>:<blob> for source, https:// and file:/// for external

Refs follow four forms.

(1) A FACT IN THIS REPO. Write the bare repo-relative path, `kb/<topic>/…/<uuid8>.md`, exactly as knomit_query returned it. You never supply this repo's id: the write path rewrites the ref to the canonical `kb://<repo-id>/<path>` form ON WRITE, so the stored corpus is uniform while authoring stays simple. Writing the qualified form yourself is accepted and equivalent.

The target MUST resolve when the call lands or the ENTIRE call is rejected, naming every offending ref. All facts in ONE knomit_learn call are committed together, so facts written in the same call may cite each other in any order — including circularly. Only citations ACROSS calls must point at facts that already exist.

Both halves — the resolve check and the canonicalization — live in package `internal/refs` as `refs.Gate` (`New`, `CheckBatch`, `Apply`), and EVERY write path routes through it: knomit_learn, knomit_update, the REST create/update handlers, and the synthesize pipelines. Ref CLASSIFICATION is separate and lives in `internal/fact` (`fact.ClassifyRef`), which is a pure leaf with no store dependency.

(2) A FACT IN ANOTHER REPO: `kb://<repo-id>/<path>`, where `<repo-id>` is the first 12 hex of that repo's root commit. Do not construct it — COPY it verbatim from the knomit_query or knomit_explain result that gave you the fact, which already returns other mounts' paths in this form. Never checked, since the repo may not be mounted.

(3) SOURCE CODE: `src://<repo-id>/<path>@<commit>:<blob>[#L<start>-L<end>]`. Here `<repo-id>` is the SOURCE repo's root commit — a different id from any knomit repo id, and the only id you ever supply. Produce all three by running git in the checkout you are citing:

    git rev-list --max-parents=0 HEAD | cut -c1-12   # <repo-id>
    git rev-parse HEAD                                # <commit>, full 40 hex
    git rev-parse <commit>:<path>                     # <blob>, full 40 hex

That last command FAILING is the check: it means the file did not exist at that commit. knomit's object database holds fact blobs only and never source, so the server CANNOT verify a src ref — validation is shape-only (parseable; a new-form ref must carry full 40-hex commit and blob). Never cite source that does not exist in the repo's history.

The blob is what makes the citation durable: `git cat-file blob <blob>` returns the exact bytes even after the file is renamed or deleted, which a commit-only ref cannot. It also makes drift a hash compare — `git rev-parse HEAD:<path>` differing from the ref's blob means the file changed, and `git diff <blob> HEAD:<path>` shows how.

The legacy form `src://<name>/<path>[@<commit>]`, keyed by a repo NAME rather than a root commit, is accepted PERMANENTLY and is never rewritten. Most of the existing corpus is in it. Do not "fix" refs in that form.

(4) EXTERNAL: `https://` or `http://` for URLs, `file:///abs/path` for filesystem references outside any repo.

Never write a bare non-fact path like `internal/store/service.go`. A schemeless ref IS a repo-relative FACT path — that is what schemeless means — so it will be treated as a fact that does not exist and rejected at write time. A non-fact resource always carries a scheme.

WHAT THIS DOES NOT MEAN:
- The 40-hex rule applies ONLY to the new src form (a 12-hex repo id AND a blob). Legacy src refs with a 7-char commit stay valid forever; nothing abbreviates or expands them.
- "Rewritten on write" applies only to refs naming a fact in THIS repo. Foreign kb://, src://, and external refs are stored byte-for-byte as written.
- The rejection on an unresolvable ref is NOT a resolution check on the whole corpus. Only refs to facts in this repo are checkable, and only for refs the write NEWLY ADDS — refs a fact already carried are passed as `prior` and never re-evaluated, so they resolve at their own commit forever.
- A ref to a RETRACTED fact is NOT rejected. The gate's predicate is `FactExistsAt`, which walks back through retractions the way every reader does; the retracted fact still has a navigable last-valid blob.
- `<repo-id>` is not one thing. In `kb://` it identifies a knomit repo; in `src://` it identifies a source-code repo. They are different repos with different root commits.
- `canonicalizeLocalRefs` and `checkLocalRefsResolve` no longer exist as symbols — that logic is `refs.Gate`. Do not grep for them.
