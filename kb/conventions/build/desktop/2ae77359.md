# The desktop bundle carries the ONE `knomit` that `make build` produced, copied not recompiled: `desktop` depends on `build`, the targets copy `$(DIST)/knomit`, and a second `go build` of the server for the bundle is forbidden

Since desktop PR 4 (#500, merge 5ee881bc) the `desktop` target is `desktop: build desktop-ui`. The server is compiled exactly once, by `build` (`go build ... -o $(DIST)/knomit .`); the desktop targets compile only `knomit-desktop`, `kb` and `knomit-okf`. Placement: macOS `desktop-app-macos` runs `cp $(DIST)/knomit $(APP)/Contents/MacOS/knomit`, guarded by `test -x $(DIST)/knomit`; the AppImage copies `$(DIST)/knomit` to `usr/bin/knomit`; Windows/Linux standalone `desktop` asserts `test -f $(DIST)/knomit$(EXE)` and the binary stays beside `knomit-desktop` and `lib/` (the layout in kb/gotchas/desktop/windows/build/fcffd02b).

On macOS the copy is re-signed with the desktop's flags, so the bundle's bytes differ from `dist/knomit` ONLY in the signature; `knomit version` of both and `knomit-desktop --version` print the same build string.

**Consequence:** never add a second `go build .` of the server to a desktop target. Two compiles can embed different version strings or tags and let the bundled server drift from the tarball server; the version cross-check in tools/desktop/serverbin.go exists to catch exactly that skew.

**What this does NOT mean:** the desktop binary has NOT stopped linking the server in-process; until desktop PR 5 it still boots its own server. The shipped `knomit` is not yet launched by the desktop. Nor does it mean `make desktop` can skip `build`: running a desktop target with `dist/knomit` absent fails with a message telling you to run `make build`.
