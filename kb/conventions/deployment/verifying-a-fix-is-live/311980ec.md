# Verify branch state SEPARATELY from binary state — a verified-running binary is no evidence the fix is in the shared branch

When reporting that a fix is deployed, run BOTH checks. Runtime evidence never implies branch state:
- Binary: build time postdates the commit; the new symbol is present (`strings <binary> | grep <symbol>`).
- Branch: `gh pr view <n> --json state` and `git merge-base --is-ancestor <commit> origin/<branch>`.

WHY, from the 2026-08-29 OOM fix: the running server was verified to contain the fix by both binary checks, and production behaviour then confirmed the fix worked — all while the PR was still OPEN and `origin/dev` contained NEITHER commit. The binary had been built straight from the feature branch's working tree. For several hours the deployed binary was ahead of its own source of truth, and anyone building from `dev` (CI, another machine, a container image) would have silently gotten the original bug back.

The error was claiming a SCOPE the evidence did not support — 'the fix is merged and deployed' from evidence that only established 'the fix is running'.

WHAT THIS DOES NOT MEAN: it does not mean runtime verification is unreliable or redundant. It was correct, necessary, and the production confirmation stood unchanged once the merge landed. Only the branch claim was unsupported.

Make the branch check ROUTINE, not inspired: in the incident it surfaced by accident during an unrelated `gh pr view`, not from anyone thinking to look.
