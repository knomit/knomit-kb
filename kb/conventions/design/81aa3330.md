# Where two surfaces must agree, this codebase makes them agree BY CONSTRUCTION — one shared call site, one validation entry point, one resolver — never by keeping two implementations in step

Three decisions in three unrelated areas reach for the same move, each stating the rationale in its own words. Taken together they are a house convention worth naming before the fourth case is designed the other way.

**The three instances.**

1. **A preview and the thing it previews share ONE query.** `/motifs/{key}`'s carriers preview calls the SAME `factsCollectionProvider.RecentFacts` the `/facts` endpoint uses, with `SearchOptions{Motifs: cluster.Members, MotifMatch: exact}`, and advertises the full pivot as a `_links.facts` URL carrying exactly those members and tier. Preview and pivot therefore cannot diverge, and the handler test asserts the recorded options field-by-field so a drift fails a test rather than shipping. Stated consequence: to change pivot semantics change the store query path — **do not add a second carrier query.**

2. **Two view modes share ONE resolver.** The fact panel's timestamp resolver is called with the resolved head sha for HEAD anchors and the pinned sha for commit anchors, so live and history modes "agree BY CONSTRUCTION rather than by two branches being kept in step". And the correct implementation turned out to be *calling the primitive that already existed* (`store.RevisionsBefore`) rather than writing a new query — which is also what defuses the trap, since the naive `ORDER BY committed_at DESC` on `commit_log` is both the easiest query to write and exactly wrong under the first-parent invariant. Stated consequence: **look for an existing primitive before adding one here; this area already has three overlapping first-parent walkers.**

3. **Every write path shares ONE validation entry point.** The motif field's rules are applied in `SerializeFact` and nowhere else, which is what makes learn, update, dedup-merge, prune, distill and discover all covered with NO per-path code.

**The claim they jointly support.** When two surfaces must give the same answer, the cheap-looking option is a second implementation plus a test that keeps them aligned; the option taken here is one implementation both surfaces call, so alignment is not a property anyone has to maintain. The reuse is not merely economy — in case 2 it is what makes the CORRECT algorithm the path of least resistance, and in case 3 it is what makes coverage total rather than proportional to how many write paths someone remembered.

**WHAT THIS DOES NOT MEAN — and the counterweight is inside the sources themselves.**

- *Not* "one code path means symmetry everywhere". The motif contract is DELIBERATELY ASYMMETRIC between the single validation entry point and parse: `SerializeFact` rejects, `ParseFact` DROPS what the gate would reject rather than failing, so a version legal when committed stays readable forever and a tightened rule never makes history unparseable. Do not "fix" that into symmetry. One entry point for VALIDATION is the convention; identical behaviour on the inverse is not.
- *Not* that sharing a path removes the need for a discriminating test. Case 1 keeps a field-by-field assertion on the recorded options precisely so a future divergence fails loudly, and case 2's guard had to be strengthened to a tie-break-independent ABSENCE assertion before it discriminated at all.
- *Not* that every similar-looking function is the primitive you want. `store.MotifIndex.CarrierTitles` is NOT the carriers preview's source (bare titles, capped, for the judge pass and `knomit_explain` siblings), and `RevisionsBefore` differs from `resolveActiveCommitForPath` in joining `branch_commits` so off-branch lineage never surfaces. Reuse requires checking that the primitive's conditions are yours, not that its name reads right.
- *Not* a licence to collapse two surfaces whose answers are SUPPOSED to differ. Case 2 rejected showing the anchor commit's date not because it duplicated code but because it answers a different question.
