# A brief that says "verify facts against HEAD; code wins" produces HEAD-first verification that reads a moved blob as a wrong fact — verification of a fact starts by resolving each ref at the referring fact's pinned commit and blob, and HEAD is consulted only to learn whether the code moved since

When a brief for a worker session (or a subagent, or a future fine-tuned model) says "verify the facts against HEAD; code wins", the worker compares each fact's claim to the file as it stands at HEAD, finds a difference wherever the code has moved since the fact was written, and reports the fact as drifted or wrong. That inverts knomit's temporal model. A fact's refs carry a commit and a blob; the fact is a claim about THAT version. The correct order, every time, is:

1. Resolve each ref at the referring fact's own pinned commit and blob (`git cat-file blob <blob>`, or knomit_explain with the fact's `commit` for kb:// refs) and confirm the claim holds there. If it does not hold at its own commit, the fact was wrong when written.
2. Only then compare the pinned blob to HEAD (`git rev-parse HEAD:<path>`). A different blob means the code moved. That is a reason to add a fresh ref and a dated note saying what changed and in which commit, and possibly to lower confidence; it is NOT by itself evidence that the fact is wrong, and the old ref stays.
3. A kb:// ref is read at the version the referrer pointed to (knomit_explain does this per edge); a `superseded` summary means the cited fact moved on, which is the same situation as a moved blob.

Consequence for anyone writing a brief: write "resolve every ref at the fact's pinned commit first; compare to HEAD only to detect movement" and never "verify against HEAD". Consequence for anyone reviewing a worker's report: a report that says "verified at HEAD file:line" without naming the pinned blob has skipped step 1 and its "drift" findings conflate "wrong when written" with "code moved since".

This sits beside two neighbouring rules and is not either of them: corpus-freshness (re-read a fact before claiming drift, because a peer may have rewritten it) is about the fact's own currency; compute-refs-never-recall is about constructing a ref correctly. This fact is about the ORDER of verification and the interpretation of a mismatch.

What this does NOT mean: it does not mean facts are never updated when code moves. The recall skill's handshake (compare blob to HEAD, diff on mismatch) still applies; the point is the order and what a mismatch means. Stated by the designer on 2026-10-12 after a research session reported ten "drifted" facts by the HEAD-first method: "refs are pinned and MUST be followed based on the commit of the fact that referred to it. This is the freaking problem with models independent from knomit, YOU NEVER EVER follow that link."
