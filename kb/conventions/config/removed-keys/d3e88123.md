# A removed config key or env var is a BOOT ERROR naming its replacement: config.Load checks the TOML metadata and the environment against config.removedKeys and returns *config.RemovedKeyError{Key, Replacement} instead of the 'unknown config key, ignored' warning

Added in auth P0 (PR #814, merge b5d17520). internal/foundation/config/removed_keys.go holds `removedKeys []removedKey{Path, Env, Replacement}`; Load runs checkRemovedTOML on the decoded MetaData (a table matches every key under its prefix, so `[oauth.idp]` with any child triggers) BEFORE warnUndecoded, and checkRemovedEnv with os.LookupEnv (set-but-empty still counts). The first hit returns `config: [oauth.idp] was removed: <replacement>`. Today's entries: the `[oauth.idp]` table and KNOMIT_OAUTH_IDP_CLIENT_SECRET (GitHub sign-in was removed; approve agents with `knomit oauth approve`).

WHY: an ignored removed key looks exactly like a working setting, and for a security setting (an allow list that no longer gates anything) that is the wrong failure. CONSEQUENCE: to retire a key, ADD it to removedKeys with its replacement; never delete the struct field and rely on the unknown-key warning, and never keep a compatibility alias (design 14.2). Later auth phases add [auth].require, loopback_default, loopback_hosts, [oauth].addr/issuer and KNOMIT_OAUTH_ADDR the same way.

DOES NOT MEAN: unknown or mistyped keys are errors; they still only warn (TestLoad_WarnsOnUnknownKey).

GOTCHA (verified): BurntSushi/toml reports a dotted key under [oauth] (`[oauth]` then `idp.client_id = "x"`, or `oauth.idp.client_id = "x"` at top level) as only `oauth.idp.client_id`, NOT `oauth.idp`, so the prefix match in checkRemovedTOML is what catches it; an exact-match-only check would miss it. TestLoad_RemovedKeysAreBootErrors has both spellings.
