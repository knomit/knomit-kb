# A per-item failure in a synthesize pass warns and skips THAT item — returning an error from inside the loop costs the whole review session, permanently

Every write loop in internal/synthesize (decision.go's merge loop, discovery.go's proposal loop) reports a per-item failure with `onProgress(ProgressEvent{Phase: "warn", ...})` and `continue`. dedupCluster was the outlier: it returned an error from every step of the merge — ReadFact/ParseFact for winner and loser, the ref gate, SerializeFact, WriteFact, DeleteFact — so one bad cluster member aborted StartSession before it planned anything, and aborted again on every retry. That is the knomit#103 shape: the corpus could not be reviewed at all until a human hand-edited the offending fact. Fixed in PR #104's follow-up; regressed by TestDedupCluster_SkipsUnparsableMember.

CONSEQUENCE: in these loops, an error that is attributable to one item (an unparsable blob written by an older serializer, a hand-edit on the KB branch, a rejected ref) must warn and skip that item. Reserve `return nil, err` for failures that are attributable to the pass itself — the embedding search errgroup, a dead store handle — where continuing would just repeat the same failure per item.

Two details that make skipping safe rather than merely quieter: skipping a merge must leave BOTH facts in the surviving cluster (so nothing downstream is handed a path that is still on the branch), and any in-memory bookkeeping for a write that already succeeded must happen BEFORE the step that can still fail — dedupCluster updates clusterByPath after WriteFact and before DeleteFact for exactly that reason.

WHAT THIS DOES NOT MEAN: not "swallow the error". The warn event is load-bearing — it is what tells the operator the pair was skipped, and a test asserting the warning fired is how you tell skipping apart from silently doing nothing.
