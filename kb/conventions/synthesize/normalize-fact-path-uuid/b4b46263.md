# Every LLM-emitted synthesis output path gets an 8-char UUID filename — distill, prune-merge and discovery via normalizeFactPath, reflect via BuildFactPath

Synthesized facts from DISTILL flow through normalizeFactPath(path) (decision.go, ApplyDistillDecisions) which REPLACES the filename with an 8-char UUID, matching the convention used by knomit_learn. Example: 'kb/security/chrome-extension-threat-surface-2026.md' -> 'kb/security/<uuid>.md'. WHY: prevents LLM-generated filenames from clashing with each other or with learn-generated facts.

AS OF knomit#107a (PR #131), PRUNE-MERGE DOES THE SAME. ApplyPruneDecisions now calls `mf.Path = normalizeFactPath(mf.Path)` after its validateOutputPath/validateOutputType/hypothesis guards and before fact.NewFact. The LLM's DIRECTORY choice is still honoured; only the filename is replaced.

All four validateOutputPath callers now yield a UUID filename, by two different routes — three by REPLACING an LLM-supplied filename (merge, distill, and discovery's emergent-fact write via normalizeFactPath), one by never accepting one at all (reflect's propose arm builds its path with fact.BuildFactPath from a topic/category pair, and BuildFactPath already generates the uuid filename).

WHAT THIS DOES NOT MEAN — the superseded warning, kept as history because it explains why the fix exists. This fact previously read: 'prune-MERGE outputs are NOT UUID-normalized ... Merge path-uniqueness therefore depends on the LLM emitting a distinct path and on downstream dedup — NOT on UUID replacement. Do not assume a prune-merge output path is collision-proof by UUID.' That warning was TRUE and load-bearing for months, and it described a real data-loss path rather than a design: validateOutputPath checks ontology root and private paths and NOTHING ELSE — there is no collision check on that path — so an LLM-supplied merged.path naming a live fact overwrote it whole (body, refs, motifs, origin) with no warning. The warning is now obsolete because the hazard is closed, not because it was wrong.

WHAT THIS STILL DOES NOT MEAN: normalization is not a collision CHECK. Nothing anywhere compares an output path against existing facts; uniqueness comes from the uuid filename being fresh, not from detecting a clash. A future path that accepts an LLM filename without normalizing re-opens the same hole, and validateOutputPath will not catch it.

NORMALIZE, not reject, was a deliberate designer ruling. Rejecting a merge on collision would silently undo a consolidation the judge asked for — the argument decision.go's own DropInvalidMotifs comment makes a few lines below. Both halves are pinned by tests: one that a pre-existing fact survives, and one that the merge STILL WRITES under a normalized path. The second is the load-bearing one — under the rejected alternative the first still passes.

Directory/path case is normalized separately by fact.NewFact (lowercases the full path unconditionally); normalizeFactPath only rewrites the filename and defers case to fact.NewFact. Companion guards in decision.go: validateOutputPath rejects paths outside ontologyRoot (case-insensitive prefix) and rejects private dot-prefixed segments; validateOutputType rejects empty/invalid epistemic type — empty type historically slipped to disk and was masked by Upsert's `default 'observation'` on the SQL column, hiding the bug.
