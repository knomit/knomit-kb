# LLM-emitted DISTILL paths flow through normalizeFactPath (8-char UUID); prune-merge paths are validated but NOT UUID-normalized

Synthesized facts from DISTILL flow through normalizeFactPath(path) (decision.go, ApplyDistillDecisions) which REPLACES the filename with an 8-char UUID, matching the convention used by knomit_learn. Example: 'kb/security/chrome-extension-threat-surface-2026.md' -> 'kb/security/<uuid>.md'. WHY: prevents LLM-generated filenames from clashing with each other or with learn-generated facts.

WHAT THIS DOES NOT MEAN: prune-MERGE outputs are NOT UUID-normalized. ApplyPruneDecisions writes the LLM-emitted mf.Path VERBATIM — it runs validateOutputPath (case-insensitive ontology-root prefix) + validateOutputType, then fact.NewFact(mf.Path) and gs.WriteFact(..., merged.Path(), ...), with NO normalizeFactPath call (only ApplyDistillDecisions calls df.Path = normalizeFactPath(df.Path)). Merge path-uniqueness therefore depends on the LLM emitting a distinct path and on downstream dedup — NOT on UUID replacement. Do not assume a prune-merge output path is collision-proof by UUID.

Directory/path case is normalized separately by fact.NewFact (lowercases the full path unconditionally); normalizeFactPath only rewrites the filename and defers case to fact.NewFact. Companion guards in decision.go: validateOutputPath rejects paths outside ontologyRoot (case-insensitive prefix); validateOutputType rejects empty/invalid epistemic type — empty type historically slipped to disk and was masked by Upsert's `default 'observation'` on the SQL column, hiding the bug.
