# An eval lane that measures a harness defect is stopped and re-run on the fixed build, not finished for the schedule

When an expert-spike eval lane (synthesize.RunEval, TestEvalRun) is measuring a harness defect rather than a model, the lane is stopped, the defect is fixed on a small branch merged locally, and the affected arm is re-run on the fixed build. It is never finished just to keep the schedule, and its numbers never feed a bar.

What happened. Phase 1b (2026-10-13) ran on the first build and the user halted it: "if the process is broken why are we continuing?". Its numbers described six harness defects, not the models: (1) menu coverage: 60 of 257 replay items had an empty first-step menu and 17 gold move types were never offered; (2) the existing-answer grader (citedIDs) mis-scored answers that cite themselves (oracle F1 0.33, 0.83 after the fix); (3) DECIDE/assess briefs cut fact bodies at 240 characters against 1200 for SYNTHESIZE (22 of 50 assess items cut); (4) an output-schema property named `reasoning` tripped the claude CLI safeguard (43 failed calls; 0 of 152 after renaming it `rationale`); (5) no thinking switch: the 2.6B GGUF template opens a think block and Ollama ignores the switch (llama-server honours it: 223 vs 2,123 tokens per call); (6) found in Phase 2 lane 2: per-fact label arrays were unbounded and no max_tokens was sent, so the 2.6B repeated labels under the json_schema grammar until the 16k context filled (5 minutes, a failed judgment, M4 unscorable).

The tell. The ceiling arm's clean chains were no better than its failed ones (Opus correct 0.07 on clean chains, so the ceiling was a floor), or one arm failed in a way that reads as a model limit (the 1.2B collapsing to one label, the 2.6B running to a timeout). When the ceiling cannot beat the floor, suspect the instrument before the models.

The rule.
- Stop the lane; do not let it finish "for the data".
- Fix on a small branch (fix/expert-harness-defects, fix/expert-schema-bounds) and merge it locally into expert-spike.
- Re-run only the affected arm on the fixed build (the 2.6B validation H+J after the schema-bounds merge; Opus and 1.2B records from the earlier build were kept).
- Keep the stale records in a build-named sibling directory outside the bars (eval/phase2/validation-build-e82577d1/).
- STATUS.md names the build per arm, so a reader can see which records came from which build.

The misreading to name. The earlier rule "no code change during the test" does not mean continuing a test whose instrument is broken. It protects a valid test from drive-by edits; it yields to evidence that the test is invalid (the user's ruling of 2026-10-13).

What this does not mean. It does not license changing the harness to improve a score: each fix must be a defect with evidence (a measured miscoverage, a refusal count, a truncation), and arms that did not touch the defect keep their records. Sampled decoding is a separate matter: two runs of the same arm already differ on 12 of 68 outcomes, so a difference of that size between builds is not by itself a defect.
