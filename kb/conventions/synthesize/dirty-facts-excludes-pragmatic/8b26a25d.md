# The seed kind filter is reviewStrategy.AcceptSeed (dirtyFacts is its CALLER); seeds are kind=epistemic ONLY and pragmatic facts never enter synthesis

Seeds are restricted to kind=epistemic ONLY — pragmatic facts (policy, heuristic, signal) are EXCLUDED from the synthesis pipeline.

WHERE THE FILTER LIVES. It is `reviewStrategy.AcceptSeed(f) bool { return f.Kind == fact.Epistemic }` in internal/synthesize/review_strategy.go. `dirtyFacts` (pipeline.go) is the CALLER that applies it on both scan paths, not the filter itself — this fact previously named dirtyFacts and pointed at review.go, and anyone grepping review.go for the rule now finds nothing. dirtyFacts normalises an empty Kind to DefaultKind before the check, so a fact file with no `kind:` line is treated as epistemic and still seeds.

The rule is stated twice, and the two statements are NOT equally reachable:

1. `SeedQuery()` pushes `IncludeKinds: [epistemic]` into SQL. On the FULL-SCAN path (no watermark) this is what actually excludes a pragmatic fact — it never comes back from the index, so AcceptSeed is never asked.
2. `AcceptSeed` is reached only on the INCREMENTAL path, where DiffFiles + ParseFact hands it every changed fact.

AcceptSeed is the authoritative STATEMENT of the rule and the only guard on the incremental path; the SQL clause is there for efficiency but is load-bearing on the full scan. See [[exclusion-differs-by-scan-path]] — it matters when writing tests, because a full-scan assertion pins the SQL clause and proves nothing about AcceptSeed.

NEIGHBOURS ARE FILTERED TOO, BY A DIFFERENT RULE (knomit#308, decision 3624365c). Seeds alone were never enough: the searches that GROW a cluster from an epistemic seed had no kind filter, so a policy filed beside an observation joined its cluster and dedupCluster merged the two mechanically. Now:
- CLUSTERING neighbour searches — ScopedCluster's per-seed expansion (all five callers: review prune, RAPTOR, backward bridges, both calibrate reports) and the prune cousin sweep (joinCousinsForPrune) — pass `IncludeKinds` = config `[cluster_cache] neighbor_kinds` (env KNOMIT_CLUSTER_CACHE_NEIGHBOR_KINDS), default `["epistemic"]`, read via `RepoInstance.ClusterNeighborKinds()`. Config refuses an empty list (an empty IncludeKinds means EVERY kind to the store), and ScopedCluster errors on one too.
- MECHANICAL DEDUP is not on that config and never will be: dedupCluster's search is pinned to epistemic (`dedupSearchKinds`) and it refuses any pair whose kinds differ or are unknown (`sameKnownKind`, fails closed on "").

The seed rule above does NOT depend on that config. Widening neighbor_kinds to include pragmatic makes a policy a cluster NEIGHBOUR, never a seed.

WHY the rule exists: the decision-application code (mergedFact, distillFact in decision.go/types.go) does NOT carry Kind through. Letting a pragmatic fact in would have it silently rewritten as kind=epistemic on commit and the original deleted — corrupting policies, heuristics and signals. This is a correctness filter, not a preference. The same reason is why widening neighbor_kinds is not yet a supported production setting: a JUDGED prune merge or a RAPTOR distill over a widened cluster still writes through mergedFact/distillFact.

What this does NOT mean: do not "fix" mergedFact/distillFact to carry kind as a side-quest. If they are ever extended to do so, this filter may be removed — but not one commit before. And that removal licence covers the SEED filter only, NEVER dedupCluster's `sameKnownKind`: mechanical dedup does not go through mergedFact at all (it writes the winner back from its own file and deletes the loser), so it corrupts across kinds by DELETION whatever mergedFact carries (incident 94172e81). Also, "pragmatic facts are excluded from synthesis" does not mean they are excluded from every cluster: under a widened neighbor_kinds they can sit in one.

Signal (F01) inherits this exclusion whole, by kind. IN THE SEED FILTER no type-level exclusion was added for it and none should be — kind is the right granularity here, because every pragmatic type needs excluding for the same reason.

Do not generalise that sentence past this filter. The same-subject gate in knomit_learn is a DIFFERENT mechanism on the write path, and it does skip signal BY TYPE (learn_same_subject.go:150) — correctly, because there the granularity genuinely differs: policy and heuristic must still be able to collide with an incoming fact, and only signal has the task-id-as-entity shape that makes that gate meaningless. See [[same-subject-skips-signal-by-type]]. "Pragmatic facts are already excluded" is true of the seed pool and false of the write path.
