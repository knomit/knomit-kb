# The fleet design set (.claude/future/fleet/: README table + in-flight list, each proposal's Status block, the rulings section of 01-principles-and-constraints.md) is updated at EVERY ruling, design revision, build start and merge — it is the source the product documentation will be bootstrapped from

User rule, verbatim (2026-10-01): "make sure fleet proposals and roadmap are ALWAYS updated with what we're building. They will become the documentation". Earlier, same direction: "plans are ok, but PLEASE update the fleet proposals as well - we MUST keep them up to date, I will use them to bootstrap the documentation".

Operational consequence: whoever relays a user ruling, receives a proposal revision, starts a build or closes out a merge edits the fleet docs in the SAME step — the README status table and "In flight" list (the roadmap), the affected proposal's Status block (In flight / What shipped / Not built), and the verbatim ruling in 01-principles-and-constraints.md's closing section when it changes a principle. Briefs for workers on a fleet feature must carry this rule. Writing to .claude/plans/ alone does NOT satisfy it.

WHAT THIS DOES NOT MEAN: it does not mean waiting for the merge. Work still in design is recorded as in design (marked "nothing built"), so the docs never claim unbuilt behaviour as shipped; at merge the In-flight entry moves to What shipped with the PR and merge SHA.
