# Three-session protocol (master / worker / reviewer): the MASTER writes NO code; it briefs the WORKER for every code change and the REVIEWER for every PR, verifies claims against code and CI, owns tickets and the knomit experiments; tickets get `status: in-progress` plus an agent-id comment at pickup and an RCA with a proposal shown to the designer BEFORE any code; on the Mac the designer merges, on the Windows box the master does

**The protocol (stated by the owner on 2026-09-25 and again, emphatically, on 2026-09-26).** Three peer Claude sessions run on this machine: `master` (Fable 5.1, the expensive budget), `worker` (Opus 5.5) and `reviewer`. Roles: the master scopes, recalls from knomit, writes the RCA and proposal, dispatches; the worker makes every code change in its own git worktree under its scratchpad and pushes branches; the reviewer reviews read-only and reports findings CONFIRMED/PLAUSIBLE with file:line; the master reads the diff, opens the PR, dispatches review, merges on green, closes the ticket, and owns the knomit experiment named after the branch. The master does not edit source, tests or workflow files itself, because Fable tokens are what the owner is protecting: 'DO NOT SPEND MY FABLE TOKENS in this session to write code'.

**Ticket etiquette.** At pickup: label `status: in-progress` (created 2026-09-25; the repo's other status labels are draft/proposed/accepted/implemented/rejected, plus wontfix/bug/enhancement) and comment with the knomit agent id (`DESKTOP-DESE6AF-b3545310` for the Windows box's master; `Pauls-iMac.local-c6d5bcff` for the Mac's). Before any code: post the RCA and proposal and wait for the go-ahead. At close: swap the label to `status: implemented`, close with a comment naming the merge commit (PR bases are `dev`, so GitHub never auto-closes), and list the knomit facts on the PR.

**Briefs.** A worker brief names the branch, base, files, the exact change, the verification command (foreground, one at a time on the 8 GB Windows box; see kb/conventions/testing/dev-box-limits), the commit message, and asks for the hash back. A reviewer brief names the PR, the commits, what to check, and asks for a verdict. Each session's commit trailer names ITS OWN model (the worker's says Opus 5.5); that is correct attribution, not a deviation.

**Mac refinements (Pauls-iMac.local, 2026-09-25/26, over #260, #280, #287, #305, #299, #308).**
- The DESIGNER merges on the Mac; the master hands over the PR URL with the verdict. A session may not approve a PR on GitHub for the user: the auto-mode classifier refuses it as self-approval, so the reviewer's approval lives in its report.
- RCA is dispatched read-only and SPLIT: the reviewer does the RCA (verify the issue's claims at HEAD with file:line, reproduce on an isolated home if cheap and safe, weigh fix directions, rejected alternatives, test shape, ~600 words); the worker does an inventory in parallel when useful (callers, clients, config plumbing). The master spot-checks load-bearing line refs itself before presenting. The designer often narrows or overrides (#260 closed wontfix; #280 narrowed to one defect; #308 made configurable): record with /knomit-decided on the agent branch (pass distinct_from for the same-subject candidates the gate lists; motifs are 2-4 kebab words) and SEND THE EXACT FACT PATH to the worker, which cannot see it until its experiment syncs.
- Forward the reviewer's edge cases to the worker BEFORE it builds; they become checklist items. Follow-up commits, never amend the reviewed commit. The reviewer re-runs mutation/sabotage checks itself and checks experiment facts by asking the worker for store bodies (it cannot read the experiment branch).
- Worktrees: state the ab185422 rule in EVERY brief; a restarted session has no memory of it (third incident 2026-09-26). Experiment names are kebab-case, no `/`.
- A CI failure that is a Go module-proxy TLS timeout is `gh run rerun <id> --failed`, not a code investigation. A base-branch conflict is resolved by the worker with a MERGE of origin/dev (never rebase, so reviewed hashes survive) and the reviewer verifies the resolution is lossless.
- Close-out after the merge: the worker re-pins every src:// ref in the experiment to the MERGE commit (recompute ranges; a squash orphans branch commits), re-reads each claim there, commits the experiment, posts the fact listing on the PR via --body-file, deletes the branch, resets knomit-worker to origin/dev; the master closes the issue with the listing and fast-forwards the shared checkout. A decision fact that describes PRE-fix code is NOT re-pinned to post-fix code.
- The master keeps a handoff card at .claude/plans/<date>-master-session-card.md when the designer restarts the session to free context.

**Misreading to avoid.** 'It is a two-line change' is not an exception; the point is where the tokens are spent, not the size of the diff. Reading code, logs and diffs in the master to VERIFY is fine and expected. 'The issue already names the fix, skip the RCA' is also not an exception: #305 and #287 both changed shape in RCA.
