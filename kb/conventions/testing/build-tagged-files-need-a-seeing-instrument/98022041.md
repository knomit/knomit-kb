# A cross-GOOS PACKAGE vet does compile that package's build-tagged test files, but tools/desktop cannot be vetted that way at all — vetting an explicit FILE LIST is the instrument that sees it, and "the cross-vet was clean" only covers the packages it was pointed at

Working on Windows, tools/desktop/boot_socket_unix_test.go (`//go:build desktop && !windows`) was edited and left with three unused imports. It stayed green locally at every step and failed CI's macOS `tests / desktop` job at every SHA from a merge commit onward. Unused imports are a COMPILER error, so anything that COMPILES the file catches them — and nothing compiled it.

WHAT DOES WORK, and what does not:

- A cross-GOOS PACKAGE vet DOES compile that package's build-tagged test files. Verified by planting an unused import in internal/auth/local_unix_test.go: `GOOS=linux CGO_ENABLED=0 go vet ./internal/auth/` reports it. So the instrument was sound; it was simply not aimed at the package that changed.
- tools/desktop CANNOT be cross-vetted as a package: `GOOS=linux|darwin CGO_ENABLED=0 go vet -tags desktop ./tools/desktop/` fails before type-checking, because sqlite-vec-go-bindings/cgo has no Go files without cgo and wails/pkg/mac is excluded on linux. Same wall that stops internal/web and internal/app.
- Vetting an explicit FILE LIST resolves only those files' own imports and never walks into the cgo dependency:

      GOOS=linux CGO_ENABLED=0 go vet -tags desktop \
        tools/desktop/boot.go tools/desktop/boot_test.go \
        tools/desktop/boot_localpeer_test.go tools/desktop/boot_socket_unix_test.go

  It reproduces CI's error exactly: `boot_socket_unix_test.go:9:2: "io" imported and not used`.

TWO CAVEATS THAT DECIDE WHETHER IT IS USABLE: (1) the list must supply every symbol the target file references, or vet reports e.g. `undefined: bootServer` instead of the real diagnostic — the list is CURATED PER TARGET FILE, not one command to memorise; (2) that failure is LOUD, a non-zero exit naming the symbol, so a wrong list can only refuse to answer, never produce a false PASS.

NAMED MISREADINGS: "the cross-vet was clean" — true of the packages it named, and read as a statement about the tree. And "`undefined: X` means the technique does not work" — it means EXTEND THE LIST.

THE RULE: after touching a file build-tagged for another platform, either run an instrument that DEMONSTRABLY sees it (proven by a forced red once, not by the absence of output), or say out loud that CI is that file's first compile and watch the run before calling the work done.
