# internal/repos: a test may call t.Parallel only if nothing it reaches changes process-wide state, it moves no objects over a git transport, and it asserts no latency or short positive deadline; top-level parallel tests start only after every sequential test has finished, so hook-setting tests and latency gates keep the machine to themselves

Introduced by #445 (merged a6ef5739); the rule is written above TestMain in internal/repos/main_signer_test.go.

Go semantics this rests on: a top-level test that calls t.Parallel pauses until EVERY top-level test that did not call it has returned, Cleanups included. Only then do the parallel ones run, beside each other. So a sequential test's global mutation (restored in its Cleanup) can never overlap a parallel test. Only the parallel set must be audited.

DISQUALIFIES a test (directly or through any helper):
- setHooks / SetTriggerClockForTest (triggerTestHooks);
- the sync, consensus and recipe-exec hooks;
- the other package seams: swapCopy, hostPlatform, guidanceWarnHook, templatePresetByID, recipeServerAddrWait, experimentSweepIntervalOverride;
- captureLogs (log.Logger), time.Local, version.Version;
- t.Setenv / Chdir;
- store.SetTestFastDurability;
- fact.DeactivateTriggerDoForTest, and fact.InlineJSCompilesForTest (a process-wide counter);
- any clone, fetch, push, subscribe, remote probe or served smart-HTTP clone (go-git corrupts packs under -race when transfers run concurrently: issue #446);
- an assertion on a latency or a short POSITIVE deadline. Examples: the write-latency gates, EmitReachesStreamWithoutDebounce (500 ms), a 2 s Eventually.
Negative windows ('does not happen within 100 ms') may stay parallel, because load only makes them pass more easily.

HOW it was audited in #445: a go/ast call-graph pass over the package (test and production files, methods matched by name, conservatively). It flags assignments to package-level vars, .Store/.Swap on them, assignments to another package's vars, and the setter calls above. 532 tests came out clean and 117 not. Remote use was taken from the logs of a SEQUENTIAL run (in a parallel run test2json attributes global-logger output to the wrong test) plus a body grep.
Result: 237 tests ≥ 0.2 s on Windows went parallel. 100 of them were taken back off for the git-transport reason, leaving 137. #446 lists 6 more that still use a transport and should be made sequential.

Why only ≥ 0.2 s tests: a quick test gains nothing and adds audit surface.

NOT MEANT:
- 'Each test has its own t.TempDir' is not enough; process-wide state and go-git transport are the actual constraints.
- The package repos_test (TestMission_* e2e) is not covered: it uses SetTriggerClockForTest and t.Setenv(PATH) and stays sequential.
- Passing `-count=1` five times is not evidence: the transport corruption showed only under -race, and the reviewer found it with `-race -count=6` on the clone families.
