# internal/corpus/repos: a test may call t.Parallel only if nothing it reaches changes process-wide state and it asserts no latency or short positive deadline (moving objects over a git transport is NOT a disqualifier since #446); top-level parallel tests start only after every sequential test has finished, so hook-setting tests and latency gates keep the machine to themselves

Introduced by #445 (merged a6ef5739); the rule is written above TestMain in internal/corpus/repos/main_signer_test.go.

Go semantics this rests on: a top-level test that calls t.Parallel pauses until EVERY top-level test that did not call it has returned, Cleanups included. Only then do the parallel ones run, beside each other. So a sequential test's global mutation (restored in its Cleanup) can never overlap a parallel test. Only the parallel set must be audited.

DISQUALIFIES a test (directly or through any helper). The general rule: any package-level variable that a test assigns, directly or through a setter, is a process-wide seam, and so is any global of another package that a test assigns. The items below are EXAMPLES, not a complete list:
- setHooks / SetMissionTriggerHooksForTest (triggerTestHooks);
- the sync, consensus and recipe-exec hooks;
- the fleet hooks: fleetTestHooks (via setFleetHooks), fleetRenewTestHooks, SetFleetClockForTest;
- the origin-write seams: beforeCredentialWrite, afterCredentialReread, beforeAttachOriginWrite, beforeDetachOriginWrite, beforeSwapOriginWrite;
- the other package seams: swapCopy, hostPlatform, guidanceWarnHook (SetGuidanceWarnHookForTest), templatePresetByID, recipeServerAddrWait, experimentSweepIntervalOverride;
- captureLog / captureLogs (log.Logger), time.Local, version.Version;
- t.Setenv / Chdir;
- storetest.SetFastDurability;
- fact.DeactivateTriggerDoForTest, and fact.InlineJSCompilesForTest (a process-wide counter);
- an assertion on a latency or a short POSITIVE deadline. Examples: the write-latency gates, EmitReachesStreamWithoutDebounce (500 ms), a 2 s Eventually.
Negative windows ('does not happen within 100 ms') may stay parallel, because load only makes them pass more easily.

HOW it was audited in #445: a go/ast call-graph pass over the package (test and production files, methods matched by name, conservatively). It flags assignments to package-level vars, .Store/.Swap on them, assignments to another package's vars, and the setter calls above. 532 tests came out clean and 117 not. Remote use was taken from the logs of a SEQUENTIAL run (in a parallel run test2json attributes global-logger output to the wrong test) plus a body grep.
Result: 237 tests ≥ 0.2 s on Windows went parallel. 100 of them were taken back off for the git-transport reason, leaving 137.

GIT TRANSPORT IS NO LONGER A DISQUALIFIER (#446). From #445 until #446, a test that cloned, fetched, pushed, subscribed, probed a remote or served a smart-HTTP clone had to stay sequential, because concurrent go-git transfers corrupted packs under -race. The cause was not go-git. It was sha1cd v0.6.0's arm64 SHA-1 assembly, which read the uninitialised register R16 and sometimes returned a wrong digest (kb/gotchas/deps/sha1cd/arm64-wrong-digest/0b50178f.md). It is fixed by go-git v5.19.3 / sha1cd v0.7.0. PR #759 (the #446 fix) put t.Parallel back on the 93 of those 100 tests that still exist (the other 7 had been deleted). It first re-checked the two remaining conditions against current code: no process-wide seam is reachable from any of them, and their timing is only hang detectors (10-120 s Eventually) or a negative window, so none stayed sequential. The 6 transport tests #446 listed as 'still parallel' (3 consensus/conflict smart-HTTP, 2 ProbeInitialized HTTP, Walkthrough_AttachOK) stay parallel. Verified with `CGO_ENABLED=1 go test -race -count=6 ./internal/corpus/repos/` on darwin/arm64: green (1950 s), no DATA RACE.
If pack corruption ('object not found', 'checksum mismatch', 'final sha1 did not match') comes back in parallel transport tests, check the sha1cd version first (`go list -m github.com/pjbgf/sha1cd`; it must be at least v0.7.0). Do not serialise the tests again before that check.

Why only ≥ 0.2 s tests: a quick test gains nothing and adds audit surface.

NOT MEANT:
- The example list being silent about a seam does not make the seam safe. A package var added later that a test assigns disqualifies that test the same way.
- 'Each test has its own t.TempDir' is not enough; process-wide state is the actual constraint (and latency assertions).
- Dropping the transport condition does not drop the others: a transport test that also sets a hook, captures the global logger or gates on a latency still stays sequential.
- The package repos_test (TestMission_* e2e) is not covered: it uses SetMissionTriggerHooksForTest and t.Setenv(PATH) and stays sequential.
- Passing `-count=1` five times is not evidence of parallel safety: the #446 corruption showed (almost) only under -race, and the reviewer found it with `-race -count=6` on the clone families. Verify a widened parallel set the same way.
