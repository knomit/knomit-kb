# A test that guards 'X does not block Y' asserts the ORDER (Y completed while X was demonstrably in flight at its blocking point) and keeps wall-clock only as a hang detector; a per-operation latency bound or a round-shaped convergence deadline fails under load

RULE: when a test guards that operation X does not block operation Y, assert three things in order: (1) X demonstrably REACHED its blocking point (a signal from the stand-in, e.g. the hung origin accepted the connection), (2) Y COMPLETED while X was still in flight (X's done channel is still empty when Y returns), and (3) only then release X. Any wall-clock wait stays as a HANG DETECTOR, set far above what a loaded machine needs (10 s for the writes, a 30 s watchdog standing in for network_timeout), so it fails only on a real stall and never on slowness.

WHY NOT A LATENCY BOUND: TestPush_HungOriginDoesNotStallWrites (internal/store/remote_push_snapshot_test.go) used to bound each write at 1 s and failed at 1.138 s on a loaded runner (fixed in PR #569). A per-operation latency bound measures the machine as much as the code. The same holds for a wall-clock convergence deadline when convergence is round-shaped (it takes N rounds, each as slow as the machine): the deadline is a guess about speed. It is the budget-from-faster-machine motif (kb/gotchas/ci/race-workflow/synthesize-timeout-headroom/4950ec60.md, kb/gotchas/repos/triggers/testing/race/77ef53fc.md): a budget calibrated on a fast machine becomes a flake on a slow one.

CONSEQUENCE: a test that cannot prove X was in flight proves nothing (an X that returned early would also let Y finish); assert (1) and (2) explicitly, and fail with a message saying so. MISREADING: this does not forbid timeouts; it moves them from the assertion to the hang detector.
