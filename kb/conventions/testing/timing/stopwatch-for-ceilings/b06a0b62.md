# A test that asserts a CEILING on a duration the trigger dispatcher measures (run, diff, change build, a trigger's own time, host_ms) uses TestHooks.Stopwatch, not real time; recipe row durations are NOT on the stopwatch (#659)

AS OF merge 1aaaf983 (#659). The dispatcher reads these DURATIONS through `stopwatch()` (triggers.go; trigger_script.go for host calls): the run's duration, the diff, the change build (change_ms), a trigger's own work (statistics, p95, slow detector) and a script's host calls (host_ms). In production stopwatch() is time.Now. A test installs `trigger.TestHooks.Stopwatch`; on a `fakeStopwatch` (triggers_perf_test.go) time moves only when the test calls `advance`, so every measured span is exactly the advances made inside it.

NOT on the stopwatch at this merge: RECIPE row durations. trigger_recipe.go still sets `row.DurationMS = time.Since(t0).Milliseconds()`. A test of a recipe row's duration cannot use the stopwatch. (A follow-up PR is changing this; re-read trigger_recipe.go before relying on either statement.)

Rule: a test that asserts a CEILING on a stopwatch-measured duration uses the stopwatch. Examples: "a fast trigger is not slow", "the change build is not charged to the trigger", "the p95 of fast evaluations is fast", "host time is not the script's own". A trivial `if` takes 0 ms on the stopwatch, while on real time under `go test -race` load it took tens of milliseconds: TestScript_TimeoutIsOutcome recorded 81.7 ms of "own" time against a 50 ms bound. Advance the stopwatch where the cost lives: `slowIfOn` advances it in EvalDelay (inside the trigger's timed section), `TestHooks.InChange` (formerly ChangeDelay, a sleep) runs inside the change build, and a stub host call can advance it too. A test that asserts only a FLOOR (at least 80 ms after a 90 ms sleep) may keep the real sleep (`slowIf`), because load only makes it longer.

What the call guard enforces, exactly (TestTriggers_RepoCallsAreAllowlisted, trigger/triggers_guard_test.go): `time.Since` is off the allowlists of triggers.go and trigger_script.go, and `time.Now` is off trigger_script.go's, so trigger_script.go is forced onto stopwatch. triggers.go still allows `time.Now` (clock() needs it), `?.Sub` and `?.Milliseconds`, so a `time.Now().Sub(t0)` added to triggers.go PASSES the guard and is caught only by review. trigger_recipe.go's list still allows `time.Now` and `time.Since`. A new duration measurement in triggers.go or trigger_script.go should go through stopwatch().

Consequence: assert exact values on the stopwatch (0.0, 90.0), not `< 40`. A sabotage that moves a cost onto the wrong side then shows the full advance (80 ms, 3,600,000 ms), never a noise-sized difference. Sabotages that went red: dropping `- hostMS` from phase B (TestScript_HostTimeIsNotTheScripts: expected 0, actual 3.6e+06) and timing the whole run (three dispatch tests red).

What this does NOT mean: the stopwatch is not the run clock. `TestHooks.Now` stays the run's one clock (the due sweep, the sandbox's Date). The script budget is a real ctx deadline that the stopwatch does not move, so a script budget test still needs real time (see the bracket-the-deadline convention).
