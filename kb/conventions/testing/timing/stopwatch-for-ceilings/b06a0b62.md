# A test that asserts a CEILING on a duration the trigger dispatcher measures (run, diff, change build, a trigger's own time, host_ms, recipe row duration) uses TestHooks.Stopwatch, not real time; every recorded duration goes through stopwatch(), enforced by TestTriggers_DurationsOnlyThroughStopwatch (#659, #661)

AS OF merge 3abc5c6c (#661, on top of #659's 1aaaf983). The dispatcher reads EVERY recorded DURATION through `stopwatch()` (triggers.go; trigger_script.go for host calls; trigger_recipe.go runJob for a recipe run's row): the run's duration, the diff, the change build (change_ms), a trigger's own work (statistics, p95, slow detector), a script's host calls (host_ms) and a recipe row's DurationMS. In production stopwatch() is time.Now. A test installs `trigger.TestHooks.Stopwatch`; on a `fakeStopwatch` (triggers_perf_test.go) time moves only when the test calls `advance`, so every measured span is exactly the advances made inside it. At #659 alone recipe rows still used time.Since; #661 moved them (row.DurationMS = stopwatch().Sub(t0).Milliseconds()), so a test of a recipe row's duration CAN now use the stopwatch.

Rule: a test that asserts a CEILING on a measured duration uses the stopwatch. Examples: "a fast trigger is not slow", "the change build is not charged to the trigger", "the p95 of fast evaluations is fast", "host time is not the script's own". A trivial `if` takes 0 ms on the stopwatch, while on real time under `go test -race` load it took tens of milliseconds: TestScript_TimeoutIsOutcome recorded 81.7 ms of "own" time against a 50 ms bound. Advance the stopwatch where the cost lives: `slowIfOn` advances it in EvalDelay (inside the trigger's timed section), `TestHooks.InChange` (formerly ChangeDelay, a sleep) runs inside the change build, and a stub host call can advance it too. A test that asserts only a FLOOR (at least 80 ms after a 90 ms sleep) may keep the real sleep (`slowIf`), because load only makes it longer.

What enforces "every duration goes through stopwatch" (TestTriggers_DurationsOnlyThroughStopwatch, trigger/triggers_guard_test.go, #661): it walks EVERY non-test .go file of the trigger package (filepath.Glob in the package directory, not subdirectories). It bans `time.Since` and `time.Until` everywhere. It allows `time.Now` only inside the functions named in wallClockReaders: `clock` (the run clock) and `stopwatch` in triggers.go, and `execRecipe` in trigger_recipe.go (the pinned Date handed to the recipe sandbox, a wall time and not a duration); each listed reader must call time.Now exactly once. It requires every `.Sub` call to be `stopwatch().Sub(t0)`. So `time.Now().Sub(t0)`, which the call allowlist alone (TestTriggers_RepoCallsAreAllowlisted) accepts, is red, and so is a duration from the run clock (`d.clock().Sub`, `rs.now.Sub`) or from a saved reading (`end.Sub(t0)`). A function value (`now := time.Now; now().Sub(t0)`) escapes the new guard, but the allowlist catches the call `now`. Sabotage (reviewer, against a commit): timing a recipe run with time.Now/time.Since again turns both guards red.

Consequence: assert exact values on the stopwatch (0.0, 90.0), not `< 40`. A sabotage that moves a cost onto the wrong side then shows the full advance (80 ms, 3,600,000 ms), never a noise-sized difference. Sabotages that went red: dropping `- hostMS` from phase B (TestScript_HostTimeIsNotTheScripts: expected 0, actual 3.6e+06) and timing the whole run (three dispatch tests red). A new duration in the dispatcher is written stopwatch().Sub(t0) and is checked by the guard.

What this does NOT mean: the stopwatch is not the run clock. `TestHooks.Now` stays the run's one clock (the due sweep, the sandbox's Date). The script budget is a real ctx deadline that the stopwatch does not move, so a script budget test still needs real time (see the bracket-the-deadline convention). Nor is the guard a ban on time.Now in the package: the three readers above are legitimate.
