# On the shared dev box run Go suites one package at a time in the foreground with -timeout 2400s -p 1 -parallel 2, vitest with --maxWorkers=2; a web/ vitest baseline is only meaningful with the Node version named (the box has Node 26 default and Node 22), lint baseline 93 in a clean worktree, desktop tag builds only in CI

On the shared dev box, run Go test suites ONE PACKAGE AT A TIME, in the FOREGROUND, with `-timeout 2400s -p 1 -parallel 2`; run vitest with `--maxWorkers=2` whenever a Go suite is also running. Observed by the worker and reviewer sessions on 2026-09-15 and 2026-09-16 (PR #209); numbers drift as dev moves, so re-measure before relying on them.

- internal/web takes 430–620 s serial and exceeds the default 10-minute go test timeout; internal/repos alone (~490–570 s) also exceeds the 600 s DEFAULT. Serial merged-tree times on 2026-09-16: mcp ~181–326 s, repos and web each ~490–510 s.
- internal/synthesize is ~465–480 s serial on a QUIET box (2026-09-20/21: 469.9, 464.5, 463.2, 469.4, 472.6, 477.8 s across the experiments stack, PRs #235–#241, sequential and pgrep-verified idle). That is within ~130 s of the 600 s default, so any contention pushes it over: the same package hit the default timeout while another session's suite ran. The cost is a pre-existing 600-fact corpus seed in review_paging_test.go, not per-PR code. (Under the same serialized flags in 2026-09-20/21 the other packages were far below: repos ~92 s, web ~27–29 s, store ~19 s, mcp ~14 s — the 2026-09-16 numbers above were taken on a slower tree; re-measure, do not average.) synthesize's result CARRIES across a push only when no package it depends on changed — internal/store AND internal/store/migrate (embedded SQL) included — checked by diff, not assumed.
- The timeout only holds when suites run SERIALLY. Two Go suites in parallel stretched internal/web to 1199.4 s against a 1200 s limit and then past it, and pushed internal/repos past 600 s — both looked like failures and were pure timeouts.
- BACKGROUND `go test` batches were OOM-killed four times in a row on FREE memory (~2 GB) while AVAILABLE stayed above 11 GB: the build cache inflates page cache and the watchdog reads free, not available. Foreground runs survive. If a package still dies, split it by test-name prefix (`-run '^Test[A-M]'` …) and verify the chunks partition `go test -list 'Test.*'`. A harness whose foreground command cap is 600 s cannot run synthesize, repos or web whole in the foreground; chunk, or exclude the slow package from `./...` and run it alone, and verify the partition against `go list ./...` BEFORE running.
- web/ vitest baseline: NAME THE NODE VERSION or the number means nothing (rewritten 2026-09-23, issue #259). The box has two Nodes: `/opt/homebrew/bin/node` = 26.7.0 (the default on PATH, installed 2026-08-11) and `/opt/homebrew/opt/node@22/bin/node` = 22.23.2 (CI's `node-version: '22'`). The Linux checkout at /home/pba/data/knomit/knomit is a DIFFERENT machine and has only `/usr/bin/node` 22.23.2 (no Node 26, no nvm/fnm; observed 2026-09-23, #270). A web/ result from there covers Node 22 only, and CI's Node 26 leg is the only Node 26 evidence. Before the #259 fix, vitest 4 on Node >= 25 never installed jsdom's localStorage (kb/gotchas/web/testing/node-webstorage-shadows-jsdom), so the SAME commit gave very different counts per Node. At bba1ea54 it was 98 failures on Node 26 and 0/1694 on Node 22. At a7bed673 it was 11 (all App.boot) on Node 26 and 1 (App.sse:616) on Node 22. The history this bullet used to record as the box "drifting between days" (2026-09-21: ELEVEN in App.boot; 2026-09-22: ONE in App.sse; 2026-09-23: 98) was two Node binaries plus three PRs adding `localStorage.clear()` to hooks, NOT dev or the box moving. The App.sse:616 failure was a real order leak, fixed by #246 (kb/gotchas/web/testing/app-sse-localstorage-order). After the fix (PR #267, merged as e6523e7d), the true baseline is 0 DETERMINISTIC failures on BOTH Nodes: at 752e42d4, Node 26 gave 1696/1696 on 4 of 4 worker runs, and CI run 35899749081 gave 1696/1696 on both the Node 22.23.2 and the Node 26.10.0 leg. The `web-ui` CI job (.github/workflows/tests.yml, Node 22 and 26 legs) is now the enforcing instrument, so a red web suite on dev is a CI failure, not folklore.
- web/ vitest LOAD FLAKES are the same at base and head, so attribute them only by INTERLEAVING (kb/gotchas/web/testing/vitest-parallel-flakiness). In 16 ABBA-interleaved full runs on Node 22 from equal fresh `npm ci`s (load 84–115; reviewer session, 2026-09-23, PR #267 gate), base bba1ea54 and head 752e42d4 each had at least one failure in 3 of 8 runs. The worker's earlier sequential batches showed "head 3 of 7, base 0 of 7", and that was a streak. It is exactly the false asymmetry that comparing sequential batches produces. Members seen that day, on both sides: RepoManager "releases the selection when you scroll" (the most frequent), Library.memo render count, two App.boot tests ("feeds a remembered lens's embedded write_branch", "discards the speculative result"), and Library.lens paging. FIXED in PR #273 (knomit#270), once merged: RepoManager "releases the selection when you scroll" (a jsdom zero-layout oracle, kb/gotchas/web/testing/jsdom-scroll-spy-last-section), the Library.lens paging tests (a production stale-closure race, kb/gotchas/web/testing/library-loadmore-ref-passive-mirror), and App.boot's "desktop, server still booting" pair (teardown order, kb/gotchas/web/testing/aftereach-stack-order-before-cleanup). NOT fixed there, still baseline members: Library.memo render count, and the two App.boot tests named above. #273's file-level cleanup-first change may cover those two, but that is unverified. One further single failure was seen during #273's verification: App.index "ignores a create for a different repo, and a finished create" failed once in 5 full runs, then 0 of 20 isolated under 6-way load on both head and dev. It is unattributed.
- Library.lens paging no longer falls under the re-run-once rule. Before #273 it was a KNOWN BASELINE FLAKE THAT REACHED CI RUNNERS (L610, `expected [0, 50, 50] to deeply equal [0, 50]`, CI run 35910329548 on the Node 22 leg; its sibling "pages again after a scope change" failed on the box on both Nodes), and the PR #267 ruling was to re-run once. FIXED in PR #273: the duplicate fetch was a real stale-closure race in Library.tsx, and commit-time regression tests now hit it on every run. Once #273 is merged, a failure in Library.lens paging, RepoManager scroll-release or App.boot's booting pair is a REAL failure, not this class; the #270 re-run-once rule is retired for them. Pre-existing failures do not count against a PR and are not fixed as ride-alongs.
- BOX LOAD FLOOR (observed 2026-09-23): 20 orphaned `yes` processes (ppid 1, started 2026-09-16 12:49 and 14:00, probably left from a CPU-load flake experiment) held the load average at 50–140 on 10 cores. That day, 'no other suite running' did NOT mean 'quiet'. Check `uptime` and `ps -Ao pcpu,comm -r | head` before calling a measurement quiet, and state the load next to any timing.
- `npm run lint` in web/ reports 93 problems (91 errors, 2 warnings) at dev. It was measured 2026-09-21 and re-confirmed byte-identical 2026-09-22 at a7bed673 by both the worker (clean checkout) and the reviewer (clean worktree). The earlier figure of 94 was an ARTIFACT of measuring with `git checkout <base> -- web/src`, which leaves the branch's new files on disk and counts them. The baseline must be taken in a CLEAN worktree at the base (kb/conventions/testing/lint-baseline-needs-a-clean-worktree/30d47cb9). Check parity by the (file, rule) multiset, not the total, so that a rule swap cannot pass as parity. A brief that quotes a number is quoting a snapshot: the PR #244 brief said "94 warnings" and was wrong on both the count and the word.
- The desktop build tag (`-tags desktop`) does not compile locally (gtk4 / webkitgtk-6.0 missing); CI's dedicated macOS `desktop` job compiles and tests it, so desktop-tagged files are compiler-verified in CI only.
- test/storytests `TestRemote_RoundTripPreservesHistory` flaked ONCE (2026-09-21) inside git clone ("failed to copy file to .git/objects/info/packs_…") and passed on three consecutive re-runs; recorded as environment, not attributed.

SERIAL ACROSS SESSIONS, not just within one (added 2026-09-20, PR #235): "one suite at a time" is a property of the BOX, so a worker session and a reviewer session running suites at the same time collide exactly like two suites in one shell. On 2026-09-20 the reviewer's run of internal/synthesize hit the 600 s per-package timeout while the worker's `go test ./...` ran concurrently; both binaries sat at ~25% CPU, the signature of contention. The number was unattributable (PR, box, or collision) and was discarded; the quiet-box re-measurement above settled it. Protocol: the MASTER session owns the box. The worker runs its final suite once, reports the time it ended, and runs no `go test` until released; the master then tells the reviewer "box is quiet as of <time>"; the reviewer measures baseline and PR sequentially and states in the findings that the box was quiet for each. A gate run taken under contention can produce a spurious failure attributed to the PR, which is the worst failure mode a gate has; a green run under contention is not evidence either.

Consequence: put the flags, the Node version for web/ baselines, and the cross-session serialization rule in every worker and reviewer brief. Misreading to avoid: a timeout or an OOM kill under these conditions is an ENVIRONMENT result, not evidence the PR broke a test — and a timing taken while another session's suite ran is not a property of the environment either; do not record it as a limit. Likewise, a web/ vitest count quoted without its Node version is not a baseline, and a flake-rate difference between two SEQUENTIAL batches is not an attribution.
