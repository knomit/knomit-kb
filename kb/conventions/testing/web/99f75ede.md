# When porting a web stub test to a real store, every axis the code chooses along needs two different values in the fixture (value, path, mount, cluster key vs canonical, BRANCH), and a sort the handler does is pinned only if the real store's already-sorted order is made unsorted first

Rule: when a stub fixture is replaced by a real-store fixture, keep every distinction the stub drew on purpose. In W0e (PR #611) the rewritten drift fixture had cluster key == canonical == config-drift, so the repo cluster detail could read or look up its definition by CanonicalID and every test stayed GREEN; review caught it. The key vs canonical distinction is produced on a real store whenever the elected spelling's tokens are not in sorted order.

It is pinned by TestHandleHALMotifCluster_DefinitionIsKeyedByClusterKey (handlers_motifs_test.go), which uses the cluster key fallback-silent displayed as the canonical silent-fallback, with its stale definition. Sabotage S2a (Definitions read by CanonicalID) and S2b (defs[CanonicalID]) both go RED. At the merge commit the detail looks up definitions by cluster.ClusterKey (motifDefinitions(..., []string{cluster.ClusterKey})).

CONSEQUENCE: any new motif test fixture asserts, as a precondition, that key and canonical differ. DOES NOT MEAN every motif fixture needs a differing pair, only the ones whose handler path chooses between the two.

SECOND INSTANCE, BRANCH AXIS (W0f, PR #612, first head 87bd214c, found in review; merged as 9b06d2ca, re-read there). Every mount of newTestLensManager sat on machine/test and every newRealStoreManager request named agent:test == ri.AgentBranch(), so listing or enriching every mount at targets[0].RT.Branch, or at ri.AgentBranch(), stayed GREEN on the real-store port. The stubs ignored the branch argument, so the gap pre-existed, but the real store is where it becomes testable. Fix pattern. Lens: pin a read mount at a second branch (svc.CreateBranch before createLens, reads [{repo: beta, branch: agent/elsewhere}], betaPinnedBranch in handlers_lenses_topics_test.go) and put a same-path decoy with another title and type on that mount's agent branch. Repo: request a non-agent branch, with a decoy on the agent branch (TestHandleTopics_EnrichesAtTheRequestedBranch).

THIRD INSTANCE, SORT AXIS (same PR). A stub can return names in any order; a real store's ListDir returns git-tree order, which is already sorted, and a directory present on both mounts makes the merged first-seen order sorted too. So dropping sort.Strings(dirNames) in handleHALLensTopics stayed GREEN on the real store while the stub at base went RED. Fix: give each mount a directory the other lacks, chosen so the merged first-seen order is unsorted whichever mount is fanned out first (alpha architecture/ + gotchas/, beta architecture/ + decisions/; TestLensTopics_UnionMergedLevel). Contrast kb/gotchas/testing/web/ae481c81.md: there a mutation is truly unobservable on any real store; here it IS observable once the fixture is shaped for it, so do not file a sort or branch mutation as equivalent before trying.

CONSEQUENCE (generalised): before claiming no coverage lost in a stub-to-real-store port, list each argument the code passes or choose-among that the stub ignored or let the test control (value, path, mount, branch, order) and run one sabotage per argument that picks the other value. DOES NOT MEAN every fixture needs two branches or an unsorted order, only fixtures whose handler path chooses along that axis.
