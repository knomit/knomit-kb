# When porting a web stub test to a real store, every axis the code chooses along needs two different values in the fixture (value, path, mount, cluster key vs canonical, BRANCH, ITEM within a collection), and a sort the handler does is pinned only if the real store's already-sorted order is made unsorted first

Rule: when a stub fixture is replaced by a real-store fixture, keep every distinction the stub drew on purpose. In W0e (PR #611) the rewritten drift fixture had cluster key == canonical == config-drift, so the repo cluster detail could read or look up its definition by CanonicalID and every test stayed GREEN; review caught it. The key vs canonical distinction is produced on a real store whenever the elected spelling's tokens are not in sorted order.

It is pinned by TestHandleHALMotifCluster_DefinitionIsKeyedByClusterKey (handlers_motifs_test.go), which uses the cluster key fallback-silent displayed as the canonical silent-fallback, with its stale definition. Sabotage S2a (Definitions read by CanonicalID) and S2b (defs[CanonicalID]) both go RED. At the merge commit the detail looks up definitions by cluster.ClusterKey (motifDefinitions(..., []string{cluster.ClusterKey})).

CONSEQUENCE: any new motif test fixture asserts, as a precondition, that key and canonical differ. DOES NOT MEAN every motif fixture needs a differing pair, only the ones whose handler path chooses between the two.

SECOND INSTANCE, BRANCH AXIS (W0f, PR #612, first head 87bd214c, found in review; merged as 9b06d2ca, re-read there). Every mount of newTestLensManager sat on machine/test and every newRealStoreManager request named agent:test == ri.AgentBranch(), so listing or enriching every mount at targets[0].RT.Branch, or at ri.AgentBranch(), stayed GREEN on the real-store port. The stubs ignored the branch argument, so the gap pre-existed, but the real store is where it becomes testable. Fix pattern. Lens: pin a read mount at a second branch (svc.CreateBranch before createLens, reads [{repo: beta, branch: agent/elsewhere}], betaPinnedBranch in handlers_lenses_topics_test.go) and put a same-path decoy with another title and type on that mount's agent branch. Repo: request a non-agent branch, with a decoy on the agent branch (TestHandleTopics_EnrichesAtTheRequestedBranch).

THIRD INSTANCE, SORT AXIS (same PR). A stub can return names in any order; a real store's ListDir returns git-tree order, which is already sorted, and a directory present on both mounts makes the merged first-seen order sorted too. So dropping sort.Strings(dirNames) in handleHALLensTopics stayed GREEN on the real store while the stub at base went RED. Fix: give each mount a directory the other lacks, chosen so the merged first-seen order is unsorted whichever mount is fanned out first (alpha architecture/ + gotchas/, beta architecture/ + decisions/; TestLensTopics_UnionMergedLevel). Contrast kb/gotchas/testing/web/ae481c81.md: there a mutation is truly unobservable on any real store; here it IS observable once the fixture is shaped for it, so do not file a sort or branch mutation as equivalent before trying.

CONSEQUENCE (generalised): before claiming no coverage lost in a stub-to-real-store port, list each argument the code passes or choose-among that the stub ignored or let the test control (value, path, mount, branch, order) and run one sabotage per argument that picks the other value. DOES NOT MEAN every fixture needs two branches or an unsorted order, only fixtures whose handler path chooses along that axis.

FOURTH INSTANCE, COLLECTION-ITEM AXIS (W0g1, PR #613, first head 4fea23ea, found in review; merged as f0b81155, re-read there). A handler that loops over a collection (the files of a commit in commitDetail, the items of a page in handleHALCommitsList) chooses per item, so its fixture needs at least TWO items with different values on EVERY code path the loop body can take, not only on one. The first detail fixtures had ONE file under the root in each commit, so reversing `files` (S3) or resolving titles from detail.Files[0].Path (S4) stayed GREEN. Fixing c7 alone (kb/c.md 'C one' plus kb/d.md 'D one', plus notes/out.md outside the root) covered the index title read but S4b, the at-commit read, stayed GREEN until c5 also changed two files (modifies kb/b.md and adds kb/e.md 'E one'), and the before-commit read (S4c) needed c6 to delete both kb/b.md and kb/e.md. The Gone, Deleted and OnlyUnderTheRoot tests pin both files in order (path, action, title, self link). Same rule for dates: the list test uses newSpacedCommitsFixture so c5, c6 and c7 sit in distinct seconds and the item dates are pinned strictly decreasing (S7 and S7d go RED). CONSEQUENCE: for each source a loop body can read (index, at-commit, before-commit), give THAT path its own commit with two distinct items, then sabotage by reversing the loop and by taking item 0 for all. DOES NOT MEAN every loop needs a multi-item fixture on every path, only paths whose body picks or orders per item. Related but distinct: kb/conventions/testing/wiring-fixtures/a1a18a20.md (pairwise-distinct field values in one response; this fact is distinct candidates across items of a collection and across the axes the code chooses along).

FIFTH INSTANCE, ANCHOR-VS-HEAD AXIS (W0g2, PR #614, first head found in review; merged as 99e0d3a5, re-read there). A point-in-time predicate is chosen at an anchor commit, and the fixture must give an anchor whose answer differs from the branch head's. factPresentAtCommitOr404 (handlers_fact_sub.go) evaluates FactLiveAtCommit or FactExistsAt at the ANCHOR commit. In the first W0g2 fixture every gate-deciding request was anchored at the requested branch's head (e14), so evaluating the gate at HEAD (FactExistsAt with commit "", or FactLiveAtCommit at the branch head) stayed GREEN (review sabotage S1 and S2). Fixed by TestCommitAnchoredSub_GateIsEvaluatedAtTheAnchor (handlers_commit_anchored_incoming_test.go): kb/r.md is live at x1 and retracted at head, so the request anchored at x1 answers 200 without fallback; at x0, before r existed, with ?fallback=before it answers 404. Each direction the predicate can flip needs its own anchor: S1 and S2 both go RED only because both directions are pinned. CONSEQUENCE: for each point-in-time gate, write one request whose anchor and head disagree in each direction (live-at-anchor and gone-at-head, absent-at-anchor and present-at-head) before running the head-evaluation sabotage. DOES NOT MEAN every anchored handler needs an anchor different from head, only handlers that gate on a predicate evaluated at the anchor.
