# TestRouter_RouteTableMatchesGolden pins every API route's method, pattern, middleware chain and handler-constructor name against testdata/route_table.golden, built with walkFull (not chi.Walk); a legitimately new route fails it until the golden is regenerated with -update-route-table

Verified at a8bf8d7a (PR #628). internal/edge/web/route_table_golden_test.go walks s.NewAPIRouter() with walkFull (chi.Walk drops the middleware of a group a subrouter is mounted in, see kb/gotchas/web/routing/chi-walk-group-middleware/28673578.md), and writes one line per route: `METHOD pattern | mw1 > mw2 > ... | handler`, sorted, 189 lines. Middleware are listed outermost first; the last column is the handler's own function name (the handler constructor), so a swapped handler is a diff as well as a moved route. The golden was generated from the router BEFORE the 12e move (97ae7c19) and the move left it byte-identical, which is what proved the re-plumbing.

FINGERPRINT. Names go through mwFingerprint: import path, package qualifier, closure suffix and the first letter's case are dropped, so web.fleetRepoRefused and httpx.FleetRepoRefused compare equal. The toolchain-dependent part is in the gotcha about runtime.FuncForPC and the Go 1.26 inlining chain.

CONSEQUENCES. Adding, removing, re-grouping or re-ordering a route fails the test naming the line (`route not in golden` / `golden route missing`). When the change is intended, regenerate with `go test ./internal/edge/web -run TestRouter_RouteTableMatchesGolden -update-route-table` and READ the diff before committing it. It will also fail for a handler constructor renamed in a pure refactor.

DOES NOT MEAN: that handlers behave the same (only their constructor NAME is in the dump, not their body), or that middleware arguments are pinned (a gate built with a different manager prints identically).
