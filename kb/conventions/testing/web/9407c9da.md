# A web handler test that needs a failing store read installs the owner's fault hook on the real store and asserts BOTH the injected error text in the problem body AND an atomic hit count of 1; a 500 alone passes for the wrong read

In internal/edge/web (W0b, PR #600, merged fa631358): to test a handler's failure path, install the owner's hook on the real store, svc.Search().SetReadFaultForTest(fn) with fn matching the index.ReadName of the intended read EXACTLY, then assert (1) the injected error's text appears in the problem body and (2) an atomic.Int64 hit counter equals 1. A bare 500 assertion also passes when a different read failed or the store errored for an unrelated reason. Helpers: newRealStoreManager and failIndexRead in handlers_completions_test.go. Review sabotage confirmed the tests go RED when the failRead line is removed. Hook closures can run on several goroutines (lens fan-out), hence atomic counters.

DOES NOT MEAN: that hooks replace real-store positive tests; they are fail-only and never fake an answer (see kb/decisions/store/web-provider-removal/a8b768db.md).

SECOND EXAMPLE (W0f, PR #612, merged 9b06d2ca, re-read there): failListDir in handlers_topics_test.go fails ListDir of exactly one path through facts.Index.SetListDirFaultForTest (svc.Facts()), passes every other listing, and counts hits in an atomic.Int64; the topic tests assert the problem title, the injected text and a hit count of 1. A hook keyed on the path (not just the read name) is the right shape when one handler issues several listings, so the count proves the intended listing failed. facts.Index.GetByPath has no hook, so its error stays untested.
