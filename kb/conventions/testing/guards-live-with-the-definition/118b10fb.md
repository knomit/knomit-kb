# The test that guards a change often lives with the DEFINITION it protects, not with the caller you edited — so a package list derived from the diff misses it and the suite goes red after review, not before

Two instances in one stack, same shape.

`internal/fact` guards every motif and serialization rule repo-wide. It went RED on a change whose diff touched only `internal/resolutions`.

`internal/store/migrate` guards the control chain. It went RED on a change whose diff contained NO GO FILES AT ALL — only a `.sql` migration.

Derive the run list from what the change MEANS, not from which directories it touched. Touch motif or serialization code, run `internal/fact`. Touch a `.sql` file, run `internal/store/migrate`. `internal/synthesize` carries "any package synthesize depends on", which includes `store/migrate` through the embedded SQL.

DISTINCT FROM gotchas/testing/hardcoded-version-in-a-guard, which shares the `controlObjects` name. That fact is about an assertion pinned to a literal that goes stale; this one is about which PACKAGES you run at all. They compound in the migrate case — the package was not run, and when it was, the obvious repair would have turned it green while leaving the new table unverified — but either can happen without the other.
