# Every reader answering a CONTENT question must call ReadBranch(), never AgentBranch() — a subscription has no agent branch and would read from ""

`ReadBranch()` is the branch a repo's CONTENT is read from: the agent branch when the repo has one, the followed upstream when it is a subscription. `AgentBranch()` answers a different question — "where may this repo author?" — and is empty for a subscription.

Before subscriptions the two were always the same value, so call sites used `AgentBranch()` for both meanings without distinguishing them. Any such site now reads from `""` on a subscription. Converted in this change: root-commit/ID resolution, the repo DTO's advertised branch and its README/MCP link, ontology loading, and unpinned lens mounts.

**Consequence for a consumer:** pick by the QUESTION you are answering, not by which one is non-empty. Reading content → `ReadBranch()`. Deciding whether a write is allowed, or naming the branch a write would land on → `AgentBranch()` / `WritableBranch()`.

**Wire-level corollary:** the repo DTO OMITS `agent_branch` for a subscription rather than sending `""`, because an empty string reads as "unknown" to a client deciding whether to offer a write affordance, where absence reads as "none". `read_branch` is always present.

**Worked example (PR #227, dev 444be652).** The single-repo GET embeds the branch root under `_embedded.branch` and the single-lens GET embeds its write member's root under `_embedded.write_branch`. Both are built by ONE function (`branchRootBody` in internal/web/handlers_branches.go) that takes the branch NAME as an explicit parameter, and the two call sites pass DIFFERENT accessors: the repo embed answers a content question → `ReadBranch()`; the lens embed answers a write question → `AgentBranch()`. A lens whose write member is a subscription therefore OMITS `_embedded.write_branch` entirely (named test), exactly as the repo DTO omits `agent_branch` — never a root built for branch `""`. A shared builder is the place this rule is easiest to break in the tidy direction (one accessor at both sites because the signature invites it); the explicit branch parameter is the guard.
