# reason.js control modes M2/M4/MF live ONLY in its <modes> section plus four `// mode-hook` lines: one `carry` model call judges relevance AND support of every fact the last moves surfaced and queues the next 2, 4 or all moves; the unchanged ASSESS applies the labels via CARRIED; mode H (default) is proved identical to the script with the section stripped

ReasonOptions.Mode (H default, M2, M4, MF; anything else is an error). In a carried mode route() sends ASSESS to CARRY unless carried moves are still queued (then WIDEN runs the next) or the carry just ran (then ASSESS runs). CARRY hydrates every pending fact, builds a PROVISIONAL menu (the frontier as if every pending fact were relevant), and makes ONE `carry` call (schema {reasoning, labels:[{fact, relevant, verdict}], moves:[menu numbers] maxItems k}). Its labels are installed as CARRIED.relevant / CARRIED.support, which judge() returns instead of calling the model, so ASSESS (with every guard the loop has) applies them unchanged; chooseFrom's choose_move returns carriedChoice: the next queued move that is on the LIVE frontier (one that is not — its origins judged irrelevant or abandoned — is recorded `refused:`), an empty queue is the model's stop, a failed carry takes the top-ranked entry as a failed H choice does. The carried moves run back to back and their results are judged by the NEXT carry, so the model picks k moves without seeing what the first k-1 surface. backtrack_choice and the closing judgments (synthesize, assess, hypothesize, seek) stay one call each in every mode. A premise check (checkPremises) runs for the last refs_out of each carried batch only.

The H identity: TestEngineModes_HIsByteForByteTheLoop strips the <modes>...</modes> lines and every line ending `// mode-hook` from repos.EmbeddedReasonScript(), runs both scripts on five oracle questions, and requires identical model request bodies, results and answer-fact text. The stripped script equalled expert-spike's engine_reason.js byte for byte at 11b2c893 and again after the loop-blocker merge d7156461; at the eval-runner merge 51ca7d6d it equals d7156461's loop plus the two 20434db7 loop changes that apply to every mode (distinct_from on EMIT and GAP writes, GAP filing under the majority topic), which sit outside the section.

Consequence for anyone editing reason.js: put mode/replay code inside the section or on a mode-hook line, and nothing else there; a change to the loop outside the section changes H and M alike. What this does NOT mean: M modes are not the E01 wording 'the model chooses a move, sees its result, makes the next judgment' inside one call — one chat completion cannot see a move's result, so Mk is 'k moves chosen blind, judged together next call'.
