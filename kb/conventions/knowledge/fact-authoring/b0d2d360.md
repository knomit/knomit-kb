# Invariant facts must state operational consequences, name foreseeable misreadings, and ref the enforcing code

Three authoring rules for invariant/architecture facts, each blocking a demonstrated failure mode:

1. STATE THE OPERATIONAL CONSEQUENCE, not just the structure. An invariant should end with the concrete thing a consumer would otherwise get wrong ("...so a pure MOVE mints a new row and IS RE-EMBEDDED"), because readers compress structural claims into slogans and act on the slogan.

2. NAME THE FORESEEABLE MISREADING explicitly ("this does NOT mean vectors are reusable by content alone"). A correct fact whose tempting-but-false corollary is left unstated will produce that corollary in consumers at scale.

3. REF THE ENFORCING CODE (or its regression test), never only the design doc. Design docs record intent at write time and cannot drift-check; src:// refs into code at a pinned commit are what /knomit-why and drift detection can verify against HEAD.

Evidence (2026-07-03, taskB2 A/B benchmark): kb/invariants/store/facts-row-immutable-cow said "content-addressed by (path, blob_hash)" and "Upsert SKIPS embedding on COW hits" — both true — but stated no move consequence, named no misreading, and ref'd only a March plan doc. 8 of 8 knomit-assisted runs independently compressed it to "embeddings keyed by content, so category moves re-embed nothing" (false at HEAD: facts_vec is keyed by facts.rowid) and shipped that error in otherwise-strong design proposals; 7/8 were flagged as major conformance violations by the judge. Shared knowledge propagates its compressions at a 100% rate — the fact, not the reader, is the economical place to stop that.
