# Invariant facts must state operational consequences, name foreseeable misreadings, and ref the enforcing code

Three authoring rules for high-retrieval facts — primarily invariant/architecture, but they apply to ANY fact likely to be retrieved and acted on (policies, gotchas, load-bearing decisions), because compression danger tracks RETRIEVAL FREQUENCY, not topic. Each rule blocks a demonstrated failure mode:

1. STATE THE OPERATIONAL CONSEQUENCE, not just the structure. A fact should end with the concrete thing a consumer would otherwise get wrong ("...so a pure MOVE mints a new row and IS RE-EMBEDDED"), because readers compress structural claims into slogans and act on the slogan.

2. NAME THE FORESEEABLE MISREADING explicitly ("this does NOT mean vectors are reusable by content alone"). A correct fact whose tempting-but-false corollary is left unstated will produce that corollary in consumers at scale. State compound conditions in FULL — name every component; never abbreviate a multi-part condition into a catchier summary, because a silently-dropped component is exactly how a true compound fact compresses into a false slogan. COUNTER-RULE (equally load-bearing): name ONLY misreadings you can actually foresee — do NOT drown a fact in speculative caveats; an over-caveated fact is a different failure mode that buries the real consequence.

3. REF THE ENFORCING CODE (or its regression test), never ONLY the design doc. Design docs record intent at write time and cannot drift-check; src:// refs into code at a pinned commit are what /knomit-why and drift detection can verify against HEAD.

These rules are themselves enforced at authoring time by internal/mcp/instructions.go (the corpus-authoring guidance the MCP server injects on connect) and the knomit_learn body-param contract (internal/mcp/learn.go), and are adversarially audited after the fact by the /knomit-harden skill.

Evidence (2026-07-03, taskB2 A/B benchmark): kb/invariants/store/facts-row-immutable-cow said "content-addressed by (path, blob_hash)" and "Upsert SKIPS embedding on COW hits" — both true — but stated no move consequence, named no misreading, and ref'd only a March plan doc. 8 of 8 knomit-assisted runs independently compressed it to "embeddings keyed by content, so category moves re-embed nothing" (false at HEAD: facts_vec is keyed by facts.rowid — see the INSERT INTO facts_vec(rowid, ...) at internal/store/search_crud.go) and shipped that error in otherwise-strong design proposals; 7/8 were flagged as major conformance violations by the judge. Shared knowledge propagates its compressions at a 100% rate — the fact, not the reader, is the economical place to stop that.

WHAT THIS DOES NOT MEAN:
- NOT 'only invariant/architecture facts need this.' The invariant/architecture scope is a PRIORITY, not a boundary — a frequently-retrieved gotcha, policy, or decision compresses into a false slogan just as readily. Apply the rules to any fact whose misreading would be costly.
- NOT 'rule 3 forbids design-doc refs, or requires deleting them.' It forbids the design doc as the ONLY anchor. Keep the plan ref as provenance and ADD a src:// code ref — satisfy 'never only the design doc' by adding code refs, not by stripping doc refs. (knomit_update refs replace wholesale — the list you send is the list the fact keeps — so when re-anchoring, resend the doc ref along with the new code refs rather than dropping it.)
- NOT 'satisfy the three rules and the fact is safe.' Mechanical compliance REDUCES but does not eliminate compressibility — a fact can state a consequence, name one misreading, ref code, and still carry a DIFFERENT attractive false corollary. The three rules are the authoring floor; the /knomit-harden adversarial read (compress -> derive consequences -> verify against code) is the actual verification.
