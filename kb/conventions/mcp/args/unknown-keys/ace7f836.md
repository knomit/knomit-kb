# An MCP tool argument key the handler does not read is REFUSED, never ignored — at the top level (rejectUnknownArguments, #122) and inside an object argument (rejectUnknownObjectKeys, knomit_update's `updates`): the valid set is derived from the served schema, and the error names every unknown key plus the valid set

An MCP tool call is a JSON object with no arity check, and mcp-go does no schema validation on the server path. A key the handler never reads makes the call run a DIFFERENT, VALID operation and report success: knomit#121/#122 (a `scope` key knomit_review did not have ran as an unscoped pass and advanced the review watermark), and the 2026-09-17 knomit_update call whose `updates.append` was dropped while the rest of the update landed.

The rule, as implemented in internal/mcp/args.go:
- Top-level arguments: `rejectUnknownArguments(req, tool)` runs before any per-argument validation. Underscore-prefixed keys (`_meta`, client transport metadata) are exempt.
- Keys inside an object argument: `rejectUnknownObjectKeys(req, arg, declared, toolName)`, used for knomit_update's `updates` against `updateToolSchemaProperties()`. No underscore exemption: nothing but the caller writes inside an argument.
- Both share `undeclaredKeys`: the valid set is DERIVED FROM THE SCHEMA THE TOOL SERVES, never a second hand-kept list, and unknown keys and the valid set are sorted so the message is deterministic. The message names every unknown key and the valid set, because a caller cannot correct itself from "invalid arguments".
- Where an argument is decoded into a struct, decode it with `unmarshalArgStrict` (DisallowUnknownFields) as a backstop, and pin the struct's json tags equal to the schema's properties with a test (`TestUpdateInput_MatchesServedSchema`), so the schema and the decoder cannot drift into refusing a declared key.

Consequence: when adding an object argument to a tool, check its keys with rejectUnknownObjectKeys against the same properties map the schema serves. When adding a field to `updates`, add it to BOTH updateToolSchemaProperties and updateInput; the pinning test fails otherwise.

WHAT THIS DOES NOT MEAN: it is not type validation — a declared key with a wrong-typed value is the decoder's business (e.g. if_commit's own check). And not every object argument in every tool is covered yet: knomit_learn's per-fact objects are decoded leniently today, so an unknown key inside a `facts[i]` object is still ignored. Check before assuming coverage.
