# An MCP tool argument key the handler does not read is REFUSED, never ignored — at the top level (rejectUnknownArguments, #122), inside an object argument (rejectUnknownObjectKeys: knomit_update's `updates`) and inside each element of an array of objects (rejectUnknownItemKeys: knomit_learn's `facts`): the valid set is derived from the served schema, and the error names every unknown key plus the valid set

An MCP tool call is a JSON object with no arity check, and mcp-go does no schema validation on the server path. A key the handler never reads makes the call run a DIFFERENT, VALID operation and report success: knomit#121/#122 (a `scope` key knomit_review did not have ran as an unscoped pass and advanced the review watermark), and the 2026-09-17 knomit_update call whose `updates.append` was dropped while the rest of the update landed.

The rule, as implemented in internal/mcp/args.go:
- Top-level arguments: `rejectUnknownArguments(req, tool)` runs before any per-argument validation. Underscore-prefixed keys (`_meta`, client transport metadata) are exempt.
- Keys inside an object argument: `rejectUnknownObjectKeys(req, arg, declared, toolName)`, used for knomit_update's `updates` against `updateToolSchemaProperties()`. Message: `unknown key "a", "b" in updates for knomit_update; valid keys are: ...`.
- Keys inside each object of an array argument: `rejectUnknownItemKeys(req, arg, declared, item)`, used for knomit_learn's `facts` against `learnToolSchemaProperties()`. Each offending element is reported by index on its own line (`fact 1: unknown key "confidense", "tags"`), then the valid set; it runs before anything is decoded or written, so the batch writes nothing.
- No underscore exemption below the top level: nothing but the caller writes inside an argument.
- All three share `undeclaredKeys`: the valid set is DERIVED FROM THE SCHEMA THE TOOL SERVES, never a second hand-kept list, and unknown keys and the valid set are sorted so the message is deterministic. The message names every unknown key and the valid set, because a caller cannot correct itself from "invalid arguments".
- Where an argument is decoded into a struct, it is decoded with `unmarshalArgStrict` (DisallowUnknownFields) as a backstop, and the struct's json tags are pinned equal to the schema's properties by a test (`TestUpdateInput_MatchesServedSchema`, `TestLearnFactInput_MatchesServedSchema`), so the schema and the decoder cannot drift into refusing a declared key.

Consequence: when adding an object or array-of-objects argument to a tool, check its keys with rejectUnknownObjectKeys / rejectUnknownItemKeys against the same properties map the schema serves. When adding a field to `updates` or to a learn fact, add it to BOTH the schema properties function and the input struct; the pinning test fails otherwise.

WHAT THIS DOES NOT MEAN: it is not type validation — a declared key with a wrong-typed value is the decoder's business (e.g. if_commit's own check). And it covers the three places named above, not every nested object in every tool: before adding a nested object argument elsewhere, check whether it is covered rather than assuming it.
