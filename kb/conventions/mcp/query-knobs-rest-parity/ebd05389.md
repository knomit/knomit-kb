# knomit_query exposes score + limit/min_similarity/type/domain_exact knobs at REST parity (paginated; snippet page max 100 / body max 5)

PR #70 widened the knomit_query MCP surface (internal/mcp/query.go) to match the REST search handler:

- SCORE: each result fact now carries `score` (float, relevance in [0,100]; 100 for filter-only / text-less queries). Previously not returned.
- LIMIT / PAGE SIZE: knomit_query is now CURSOR-PAGINATED with mode-dependent page caps, normalised by `pageSizeFor(limit, includeBody)` (NOT the old `clampQueryLimit`/`maxQueryLimit` — those were removed). Snippet mode: default `defaultPageSize`=20, max `maxPageSize`=100. include_body mode: default `includeBodyDefaultPage`=3, max `includeBodyMaxPage`=5 (full bodies are heavy, so the per-page cap is tiny — page via the returned `cursor`). NOTE: this NO LONGER mirrors the REST handler's single 500 cap (internal/web/handlers_search_hal.go still clamps limit>500 -> 500). The MCP surface deliberately diverged here because it paginates; the per-page cap is small by design and callers walk pages with `cursor`. The lockstep-with-REST convention below is about RELEVANCE-SEARCH KNOBS, not this page cap.
- NEW PARAMS forwarded into store.SearchOptions: min_similarity (cosine floor; 0 -> server default), type ([]string -> IncludeTypes), domain_exact (bool -> DomainExact).
- TYPE-ONLY QUERIES: the 'at least one filter' validation now COUNTS `type` (text-less type-only query returns all facts of that type) because the store supports it and REST already accepted it. The error message lists type among the valid sole filters.

UPDATE (PR #85): knomit_query gained a `sort` knob (relevance default / recent). sort=recent routes to store.RecentFacts and is also a valid SOLE selector — the validation now accepts {any filter} OR sort=recent. Every row now also returns `committed_at`. This knob is intentionally NOT mirrored on the REST search endpoint: REST serves recency through a SEPARATE resource (the facts-collection endpoint backed by the same RecentFacts).

UPDATE (PR #96): knomit_query gained an `origin` filter (accepts a single value or a list of authored|distilled|discovered -> SearchOptions.IncludeOrigins). Unlike `sort`, origin is a RELEVANCE-SEARCH filter, so the parity convention applies — keep it mirrored on the REST search endpoint. See decisions/architecture/fact-model/origin-field for the field itself.

CONVENTION / anti-pattern: when adding a RELEVANCE-search knob to one of knomit_query (MCP) or the REST search endpoint, add it to BOTH — they are kept at deliberate parity. The `sort` knob and the per-page cap are the documented exceptions: recency is a distinct REST resource, and MCP paginates so its page cap is intentionally smaller than REST's 500. Diverging the relevance-search KNOBS accidentally is the thing to avoid.
