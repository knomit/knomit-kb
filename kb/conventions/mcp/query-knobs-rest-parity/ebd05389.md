# knomit_query exposes score + limit/min_similarity/type/domain_exact knobs at REST parity (limit capped 500)

PR #70 widened the knomit_query MCP surface (internal/mcp/query.go) to match the REST search handler:

- SCORE: each result fact now carries `score` (float, relevance in [0,100]; 100 for filter-only / text-less queries). Previously not returned.
- LIMIT: no longer hardcoded to 20. clampQueryLimit(req limit) normalises: limit<=0 -> defaultQueryLimit (20); limit>maxQueryLimit (500) -> 500. The 500 cap MIRRORS the REST handler (internal/web/handlers_search_hal.go) so a caller cannot materialise the whole corpus in one tool response. Keep MCP and REST caps in lockstep — if one changes, change both.
- NEW PARAMS forwarded into store.SearchOptions: min_similarity (cosine floor; 0 -> server default 0.40), type ([]string -> IncludeTypes), domain_exact (bool -> DomainExact).
- TYPE-ONLY QUERIES: the 'at least one filter' validation now COUNTS `type` (text-less type-only query returns all facts of that type) because the store supports it and REST already accepted it. The error message lists type among the valid sole filters.

UPDATE (PR #85): knomit_query gained a `sort` knob (relevance default / recent). sort=recent routes to store.RecentFacts and is also a valid SOLE selector — the validation now accepts {any filter} OR sort=recent. Every row now also returns `committed_at`. This knob is intentionally NOT mirrored on the REST search endpoint: REST serves recency through a SEPARATE resource (the facts-collection endpoint backed by the same RecentFacts).

UPDATE (PR #96): knomit_query gained an `origin` filter (accepts a single value or a list of authored|distilled|discovered -> SearchOptions.IncludeOrigins). Unlike `sort`, origin is a RELEVANCE-SEARCH filter, so the parity convention applies — keep it mirrored on the REST search endpoint. See decisions/architecture/fact-model/origin-field for the field itself.

CONVENTION / anti-pattern: when adding a RELEVANCE-search knob to one of knomit_query (MCP) or the REST search endpoint, add it to BOTH — they are kept at deliberate parity. The `sort` knob is the documented exception: recency is a distinct REST resource, not a search-endpoint param. Diverging the relevance-search surfaces accidentally is the thing to avoid.
