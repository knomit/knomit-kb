# Agent-facing text (skill templates, MCP tool descriptions, server instructions, gate error messages) is an INSTRUCTION to an agent mid-task: it states the rule and the command, and NEVER an issue or PR number, a "used to be", a "legacy" story, or any other memory of how things were

The reader of a skill template under tools/bridge/skills/templates, of a knomit_* tool description, of the MCP server instructions, or of a gate/validation error message is an AGENT in the middle of a task. It needs three things: what the rule is, what command produces a correct result, and what to do when the rule cannot be met. It does not need, and is actively harmed by, anything else.

Designer's intent, stated verbatim by the maintainer on 2026-09-24 after PR #282 added a paragraph to three write-side skills that cited an issue number and narrated legacy ref forms: "we should never ever use the skills as a changelog, and we should not use them as a memory either ('remember the time when we used to do x y z? well, we don't do it anymore') — who the hell cares?"

CONCRETELY FORBIDDEN in agent-facing text:
- issue or PR references ("(knomit#249)", "ships in #236", "post-#236 build");
- history or narrative ("used to be", "no longer", "still accepted", "is never rewritten", "the older form");
- explanations of what the server can or cannot detect ("knomit cannot tell an invented hash from a real one") — the agent needs "compute it with git", not the threat model;
- a name for a deprecated form ("legacy") with a story attached. If an agent may ENCOUNTER an old form while reading, give it one clause on how to resolve it ("a ref with only a commit: git show <commit>:<path>") and nothing about why it exists.

WHERE THAT MATERIAL BELONGS: the reason for a rule goes in a knomit fact (decisions/, gotchas/, incidents/) that cites the PR; the PR body and the issue carry the history; the code comment carries the mechanism. A skill may cite NOTHING of the sort.

OPERATIONAL CONSEQUENCE: when a PR changes a rule an agent must follow, the skill/description edit is the RULE ONLY, in the imperative, and the PR body gets the why. Reviewers reject agent-facing text containing `#\d+`, `knomit#`, or a past-tense account of behaviour. PR #282 adds a template test that fails on any issue reference in a skill template (see the src ref added by that PR's experiment).

WHAT THIS DOES NOT MEAN: it does not forbid the ONE-LINE operational handling of an old data form an agent will actually meet (the resolve-by-hand line in knomit-recall and knomit-why stays). It forbids explaining, dating, or justifying that form.

Related: tool descriptions are prompt engineering for the calling agent (kb/conventions/mcp/tool-description-is-prompt-engineering/13cf1258.md); skills are generated from the bridge templates, so the fix goes in the template and is redeployed with `kb claude init`, never hand-edited in .claude/skills (kb/gotchas/integrations/claude-code/skills-ship-inside-the-binary/ffa94d9d.md).
