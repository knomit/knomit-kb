# In the master + worker + reviewer session setup, the MASTER session orchestrates ONLY — diagnosis, briefs, coordination, merges of reports — and never writes code, runs test suites, commits or opens PRs itself; all of that goes to the worker, and review goes to the reviewer

When the user starts a Claude Code session and says sessions named "worker" and "reviewer" are available (ListAgents shows them as peers), the session that received the task is the master, and its job is coordination: investigate enough to write a precise brief, send the brief to the worker (with the recalls done or the instruction to recall), send review requests to the reviewer, and integrate what comes back. The master does not edit files, does not run the test suites, does not commit and does not create the PR.

Why: the master runs on the most expensive model and its context is the budget the user cares about most. On 2026-09-24 the master diagnosed the Race CI failure correctly and then wrote the whole PR #284 fix itself, using the reviewer but never the worker; the user's reaction was "I told you to use worker for that". Delegation is not optional when the sessions are provided.

How to apply: after the diagnosis, the master writes a brief that names the branch, the invariants recalled from knomit, the exact verification commands and the expected report shape, sends it with SendMessage to "worker" (notify_when_idle: true), and waits. Review goes to "reviewer" the same way. Working-tree ownership follows the shared-checkout convention (worker and reviewer use their own worktrees; the shared checkout stays on dev) — the master does not switch the shared tree's branch either.

WHAT THIS DOES NOT MEAN: it does not forbid the master from reading code, running read-only git/gh commands, or querying CI logs to build the brief; diagnosis is the master's job. It also does not apply when no worker/reviewer sessions exist — a lone session does its own work.
