# Refactor PRs may delete truly dead internals and consolidate code, but removing or narrowing a route, API contract or user-visible capability (including never-wired code like the web JobRegistry) is raised with the user BEFORE it is done

User guidance, 2026-10-24, verbatim: "it is ok to remove dead code and to consolidate and simplify as part of this work. I just don't want to accidentaly remove code I do not want to. Also, if you find something that does not work, let me know". On the job routes, the user said: "we still need to cancel a running or pending job, so the API has to stay there and actually work".

RULE: (1) A refactor PR may delete truly dead internals and consolidate or simplify code; each removal is listed in the PR body. (2) Any removal or narrowing of a route, an API contract or a user-visible capability is raised with the user BEFORE it is done. That includes code that merely looks dead because it was never wired up, such as the web JobRegistry. (3) For never-wired user-facing code, ask whether to wire it up or remove it; removal is not the default. (4) Anything found broken goes to the user directly, not only to a local triage list.

DOES NOT MEAN: that dead code may not be deleted, or that the user must be asked before deleting unexported helpers that nothing calls. 'Nothing calls it' is not the test for a user-facing route or capability: check whether it was meant to be reachable.
