# Progress and summary counts must report the DELTA a user acts on, not the operation the code performed

A `knomit-okf sync` that altered 44 documents printed `3038 written · 0 removed` and `Staging 3038 files`. Both numbers were literally TRUE — the code did rewrite and re-stage 3038 files — and both were the wrong thing to say. The user read "everything was regenerated" and asked whether the tool was broken. The commit was a correct 44-file diff the whole time.

Two distinct failures, and the second is the one that keeps recurring:

1. Real waste. Rewriting and re-staging unchanged files cost 15.2s of a 27.2s run. Fixed by skipping files already identical on disk and staging only those whose index entry hash differs from the rendered blob.

2. A reporting failure that NO TEST CAUGHT. Every test passed while the tool described its own behaviour falsely, because tests assert what the code does, not what the operator will conclude from what it says. Output is an interface with no type checker.

How to apply: when emitting a count, ask what decision the reader makes with it. "How many files did I open for writing" is an implementation detail; "how many documents changed" is the answer to "did my 8 new facts land?". Report the delta, and give the total as context rather than as the headline — `44 changed · 0 removed (of 3038)`.

The smell to watch for: a summary line whose number is a loop counter. A count that always equals the size of the collection is describing the loop, not the work.

What this does NOT mean: do not hide the total, and do not compute a pretty number that diverges from what happened. The fix here made the code actually DO less work, so the honest count and the cheap count became the same number — which is the outcome to aim for.
