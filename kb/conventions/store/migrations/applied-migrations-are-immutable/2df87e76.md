# An applied migration becomes immutable the moment anything outside your control might have run it — in-place edits are legitimate only while that set is PROVABLY empty

Designer ruling, recorded during the motif campaign (2026-08).

**The rule.** A numbered migration stops being editable the moment any database you do not control might already have applied it. Until then — and ONLY until then — editing it in place is legitimate and is better than stacking a corrective migration nobody can read.

**What makes it "provably empty".** Check real databases' `schema_migrations` table. Not: assume the branch was local. Not: reason that the feature is unreleased. The proof is an observation about deployed state, and it is cheap to make.

**Consequence when the set is NOT empty.** Ship a new numbered migration. An edited applied migration produces two databases that both claim the same version number and hold different schemas.

**NOTHING WILL TELL YOU.** `golang-migrate` compares version NUMBERS, not content — there is no checksum, no drift detection, and no test in this repo that enforces this rule. It is a process discipline with no enforcing code, and that is exactly why it is written down: the only detector is a human remembering to ask.

**WHAT THIS DOES NOT MEAN.**
- **"Pre-release, so migrations are still fluid" is NOT the test.** Pre-release software still has developer machines, CI caches, and lab corpora that have run the migration. The question is never the release status of the project; it is whether a database exists that already applied THIS file.
- It does not exempt the `.down.sql` half — a down migration that no longer matches its up is the same divergence, discovered at the worst moment.
- It is not advice about tidiness. The failure mode is two schemas indistinguishable by version, which surfaces later as an unexplainable query error on one machine.
