# Every up-migration body must be safe to re-run on a database where it ALREADY applied — recovery re-executes it

The golang-migrate sqlite3 driver runs THREE separate transactions per migration: `SetVersion(N, dirty=true)`, then the body, then `SetVersion(N, dirty=false)`. A crash between the body's commit and the final SetVersion leaves the migration FULLY APPLIED with `dirty = 1`. `upWithRecovery` then rewinds to N-1 and re-runs N — so an up-migration body is executed a second time against a database that already contains its effects.

**Rule:** write `CREATE TABLE/INDEX/TRIGGER IF NOT EXISTS`, `DROP ... IF EXISTS`, `INSERT OR IGNORE`. A bare `CREATE TABLE` is a latent recovery failure; `000008_fact_domain_tokens` was exactly that bug and was fixed to `IF NOT EXISTS`.

**The exception SQLite forces, and how it is handled.** `ALTER TABLE ... ADD COLUMN` has no `IF NOT EXISTS` form, so migrations 000005, 000006, 000011, 000012 and 000019 CANNOT be made idempotent. `upWithRecovery` covers them with a second, narrower step: if the re-run fails with `already exists` or `duplicate column name`, that error is itself proof the body committed (the body is transactional, so a partial application would have rolled back), and recovery marks N applied via `Force(N)` and continues. Do NOT read this as "non-idempotent migrations are fine" — the fallback only recognises those two SQLite signatures. A non-idempotent statement that fails any other way (a data-modifying `UPDATE`/`INSERT` that double-applies, or one that errors differently) is NOT covered and will leave the repo unopenable.

**The fallback absorbs exactly ONE collision per run — and WHERE that binds.** After forcing past the first collision, `forcePastCommittedBody` runs the rest with `m.Up()`, and a SECOND `duplicate column name` there is a hard error (`continuing past recovered migration N: …`).
- Real dirty recovery does NOT hit this: it rewinds ONE version (N-1) on a database where no migration after N ever ran, so a later ADD COLUMN has nothing to collide with.
- It binds when a database already at the HEAD schema has its version row REWOUND and everything is re-run. That is exactly what `TestMigration000014_…`, `TestMigration000015_…` and `TestMigration017_…` do (open at head, set `schema_migrations` back, re-run), and any ADD COLUMN after 000019 is a second collision there: F03's first 000026, which ALTERed `facts`, turned all three red. 000023's header records the same limit and rebuilt its table with DROP+CREATE.
- Working rule for this repo: do not add an `ALTER TABLE … ADD COLUMN` migration. Put new per-fact data in a `CREATE TABLE IF NOT EXISTS` side table keyed by `facts(id)` (000026 `fact_expires`, F03), or rebuild a derived table with DROP+CREATE. Do NOT make those fixtures rewind the new migration to get green: they are the only guard that a rewound head database stays re-runnable.

**Separate class — migrations that can fail on pre-existing DATA** (e.g. `CREATE UNIQUE INDEX` over rows that violate it). Recovery deliberately does NOT retry these past one attempt; see [[dirty-self-heal-once]]. Such a migration must repair the data itself first, as `000015_edges_merge_identity` does by deleting duplicate edges before creating the index.

Enforcing code: `upWithRecovery` / `forcePastCommittedBody` in `internal/store/migrate/migrate.go`; regression tests `TestMigrate_RecoversWhenBodyAlreadyCommitted` and `TestMigrate_DoesNotLoopOnDeterministicFailure` in `internal/store/migrate/recovery_test.go`, and the three store migration tests above.
