# Every up-migration body must be safe to re-run on a database where it ALREADY applied — recovery re-executes it

The golang-migrate sqlite3 driver runs THREE separate transactions per migration: `SetVersion(N, dirty=true)`, then the body, then `SetVersion(N, dirty=false)`. A crash between the body's commit and the final SetVersion leaves the migration FULLY APPLIED with `dirty = 1`. `upWithRecovery` then rewinds to N-1 and re-runs N — so an up-migration body is executed a second time against a database that already contains its effects.

**Rule:** write `CREATE TABLE/INDEX/TRIGGER IF NOT EXISTS`, `DROP ... IF EXISTS`, `INSERT OR IGNORE`. A bare `CREATE TABLE` is a latent recovery failure; `000008_fact_domain_tokens` was exactly that bug and was fixed to `IF NOT EXISTS`.

**Scope: this policy covers BOTH migration sequences, not just the repo store.** migrate.All / migrate.Core apply internal/store/migrate/repo/*.sql to the per-repo store DB; migrate.Control applies internal/store/migrate/control/*.sql to the single machine-wide <home>/control.db. migrate.All and migrate.Control both call the SAME upWithRecovery — so a control.db migration body must be exactly as safe to re-run as a repo/ one, for the same reason and via the same code path. control/000001_control_baseline.up.sql follows the rule: every CREATE TABLE/INDEX is IF NOT EXISTS, so re-running it against a home that already has these tables (created ad hoc before control.db was versioned) is a no-op — the home is simply stamped v1.

**The exception SQLite forces, and how it is handled.** `ALTER TABLE ... ADD COLUMN` has no `IF NOT EXISTS` form, so migrations 000005, 000006, 000011 and 000012 CANNOT be made idempotent. `upWithRecovery` covers them with a second, narrower step: if the re-run fails with `already exists` or `duplicate column name`, that error is itself proof the body committed (the body is transactional, so a partial application would have rolled back), and recovery marks N applied via `Force(N)` and continues. Do NOT read this as "non-idempotent migrations are fine" — the fallback only recognises those two SQLite signatures. A non-idempotent statement that fails any other way (a data-modifying `UPDATE`/`INSERT` that double-applies, or one that errors differently) is NOT covered and will leave the repo (or control.db) unopenable.

**Separate class — migrations that can fail on pre-existing DATA** (e.g. `CREATE UNIQUE INDEX` over rows that violate it). Recovery deliberately does NOT retry these past one attempt; see [[dirty-self-heal-once]]. Such a migration must repair the data itself first, as `000015_edges_merge_identity` does by deleting duplicate edges before creating the index.

Enforcing code: `upWithRecovery` in `internal/store/migrate/migrate.go`, called from both `migrate.All` and `migrate.Control`; regression tests `TestMigrate_RecoversWhenBodyAlreadyCommitted` and `TestMigrate_DoesNotLoopOnDeterministicFailure` in `internal/store/migrate/recovery_test.go`.
