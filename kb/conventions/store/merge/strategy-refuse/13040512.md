# StrategyRefuse is a NON-EMPTY ConflictStrategy handled inside mergeTreesWithStrategy, and it is STRICTER than the other two on a dual-add — a strategy whose contract is "make no choice" cannot treat a colliding Insert as non-conflicting

StrategyRefuse collects every conflicting path and returns a typed *MergeConflictError BEFORE mergeIntoBranchLocked writes any ref. The tree it built is discarded unwritten — loose objects only, no ref moved.

TWO THINGS ARE EASY TO GET WRONG HERE.

1. The VALUE must be non-empty. mergeIntoBranchLocked rewrites an empty strategy to StrategyLocalWins, so a zero-value "refuse" would be silently downgraded into the very resolution it exists to prevent.

2. It must be handled in ALL THREE change arms — Modify, Delete and INSERT. LocalWins and RemoteWins both treat a pure Insert as non-conflicting, so a refuse implemented by adding a third branch only to Modify and Delete would silently overwrite a path both sides added with different content. Refuse treats that as a conflict; the other two do not, and that asymmetry is deliberate.

The strategy stays a PARAMETER chosen at the call site, as conventions/store/sync/strategy-local-wins already says. Experiments choose it twice, in opposite directions: commit merges exp -> parent with StrategyRefuse, and sync merges parent -> exp with StrategyRemoteWins, because the strategy names which SIDE wins and the parent is `src` on that direction. Reading RemoteWins as "the remote" rather than "src" is how a sync silently keeps the experiment's version of exactly the path it was run to resolve.
