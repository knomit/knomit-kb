# kb's proxy compares its build with the server's once, beside the proxy loop, and writes ONE stderr line on a mismatch; any missing signal prints nothing, stdout stays the MCP stream, and `kb version` and the hooks never check

Added by #412 (merge 55a47911) after the first-mission rehearsal ran a stale `kb` against a newer server with nothing saying so.

- `serveProxy` (tools/bridge/main.go) starts `go warnVersionSkew(errw, NewServerClient(srv, versionCheckTimeout=2s), srv.Base, srv.Raw, version.String())` and then runs the proxy loop at once: the MCP handshake never waits for it.
- `warnVersionSkew` (tools/bridge/version.go) GETs `/api/v1/version` and compares its `full` field with the local `version.String()` (the server builds `full` with the same function, so the formats match). On a difference it writes `kb: version <local> differs from the server's <server> at <addr>; update whichever is older` to stderr and logs a warn in the kb log.
- No answer, a non-200 status, an undecodable body or an empty `full` print NOTHING (debug log only): a warning must not rest on a signal kb does not have. It never exits and never fails the command.
- Only the long-lived proxy checks. `kb version` stays offline (its stdout is its output); the `claude`/`antigravity` hooks do not check (they run once per agent tool event); `login`/`logout`/`init` do not either.

Pinned by tools/bridge/version_skew_test.go, including TestServeProxy_VersionSkewNeverTouchesStdout (stdout byte-identical to the MCP response while the warning lands on the error writer) and a hung-server case bounded by the 2 s timeout.

WHAT THIS DOES NOT MEAN: kb does not refuse to run against another build, and a silent stderr does not prove the versions match (the check may simply have had no answer).
