# ONE artifact — a general-purpose host adapter — is simultaneously the proposed growth vehicle, the only fix for the coding-first misread, AND a thing already built and shelved once, so the binding constraint is the decision to MERGE one, not the capacity to build one

Three facts written on the same day, each about a different subject, all resolve onto the same artifact.

- The Hermes fit analysis recommends building a general-purpose host adapter, and names its own BIGGEST EXECUTION RISK as "the shelved-adapter pattern", citing OpenClaw.
- The positioning gotcha says a general-purpose host adapter (Hermes, OpenClaw) is THE VEHICLE for the first published non-coding proof — the misread is a messaging gap, and this artifact is what closes it.
- The OpenClaw status fact records that exactly such an adapter was fully built and Docker-tested by 2026-07-04, has never been in dev/master, and by 2026-09-13 sat 16 ahead / 834 behind dev with PR #9 still open.

WHAT THAT COMPOSITION SAYS, which no single fact does: the same deliverable is the answer to three separate problems — distribution, positioning proof, and exercising the chat/generic MCP profiles that have never had a host — and it has already been produced once at full quality and not shipped. So the binding constraint is not design, not capability, and not the analysis: it is the decision to merge and release one. "Should we build a Hermes adapter?" is therefore the second question. The first is why the completed one did not ship, and whether that has changed.

WHY THE COST IS UNDER-COUNTED. Each problem's owner sees only their own share of the shelving. The distribution case sees a missing channel; the positioning case sees a missing proof point; the integrations case sees an unmerged branch. None of them prices the other two, so a shelved adapter looks like deferred work from every angle and like a compounding blocker from none of them. The OpenClaw fact already names the operative rule — decide that branch's fate BEFORE building a second general-purpose adapter — and this composition is why that rule is load-bearing rather than tidy-minded.

WHAT IS REUSABLE EITHER WAY, per the OpenClaw fact: generic-profile SKILL.md templates for 8 knomit operations written for non-coding knowledge work; the plugin-spawns-knomit-bridge-as-stdio-subprocess pattern (single Go auth chokepoint); snapshot-tools-at-init-then-register-synchronously; the knomit_review task-mode working/resume contract for hosts with tool timeouts; the `-scope project|user` install layout. Merging requires rebasing across 834 commits, notably the knomitapi/skills shared-core extraction that landed later.

CARRIED FROM THE SOURCES, because the synthesis must not smooth them away:

- The Hermes fit analysis is an ANALYST's conclusion, NOT a user-ratified decision. A /knomit-decided fact should record the maintainer's confirmation or amendment. Nothing here upgrades it.
- The OpenClaw design was NOT rejected. No fact and no PR comment records a reason; it may simply be capacity. Do not read "shelved" as "declined".
- It does NOT mean the code profile's source-ref features are unimportant — they are the deepest tooling knomit has. The point is that they are one profile, not the product's scope.
- It does NOT mean knomit should model the user (USER.md / Honcho's theory-of-mind job stays theirs), and it does NOT mean the Hermes memory-provider slot is required for value — the general-plugin path delivers compiled context even where another provider holds the slot.
- All three are snapshots of 2026-09-13, including the branch's 834-behind position and dev HEAD 9f9f5c93. Re-check the branch state before acting.
