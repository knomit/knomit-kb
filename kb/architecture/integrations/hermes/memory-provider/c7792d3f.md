# Hermes Agent's external memory is a SINGLE-SELECT provider slot that runs ALONGSIDE (never replaces) MEMORY.md/USER.md — and recalled context must enter via prefetch() or a pre_llm_call hook because the system prompt is frozen mid-session

Verified against the Hermes docs on 2026-09-13.

Built-in memory is two bounded files in ~/.hermes/memories/: MEMORY.md (2,200 chars, ~800 tokens) and USER.md (1,375 chars). Both are injected as a FROZEN snapshot at session start; the memory tool has add/replace/remove and NO read; it errors on overflow rather than compacting. Mid-session writes persist to disk but do not reach the prompt until the next session, because Hermes deliberately keeps the system prompt stable to preserve prefix cache.

External memory: `memory.provider:` in config.yaml selects EXACTLY ONE provider (docs: "Only one external memory provider can be active at a time"). It runs alongside the built-in files, never replacing them. Eight providers ship in the repo under plugins/memory/: honcho, openviking, mem0, hindsight, holographic, retaindb, byterover, supermemory. No Letta provider exists.

Provider interface (agent/memory_provider.py, abstract MemoryProvider): required `name`, `is_available()`, `initialize(session_id, hermes_home=..., platform=..., agent_context=primary|subagent|cron|flush)`, `get_tool_schemas()`, `handle_tool_call()`, `get_config_schema()`, `save_config()`; optional `system_prompt_block()` (static), `prefetch(query, session_id)` (runs BEFORE each turn with the user's message; results over 10,000 chars are spilled to a file with a head/tail preview), `queue_prefetch()`, `sync_turn(user, assistant, messages)` (MUST be non-blocking, use spawn_context_thread), `on_memory_write(action, target, content)` (mirrors every built-in add/replace/remove), `on_pre_compress(messages, require_checkpoint)` (before lossy compaction; checkpoint API v2 is fail-closed), `on_session_end(messages)`, `shutdown()`. Registered from a plugin's `register(ctx)` via `ctx.register_memory_provider(instance)`; manifest is plugin.yaml with name/version/description/hooks.

A GENERAL plugin (not a provider) can instead register `pre_llm_call`, which may return `{"context": "..."}` injected into the user turn, plus `pre_tool_call` (block/approve), `post_tool_call`, `on_session_start/end`, tools, slash commands. General plugins COEXIST with whatever provider is active. Plugins are disabled by default (`hermes plugins enable <name>`).

CONSEQUENCES for a knomit adapter: (1) a knomit memory provider competes with mem0/honcho/supermemory for the one slot, so ship the per-turn context injection ALSO as a general plugin (pre_llm_call) that coexists with any provider; (2) recalled facts must be delivered through prefetch()/pre_llm_call, not system_prompt_block(), or they never change mid-conversation; (3) on_memory_write + sync_turn give knomit a WRITE path that does not depend on the model choosing to call knomit_learn — the exact hole measured under Claude Code (kb/gotchas/mcp/tool-selection/write-path-non-use); (4) prefetch is on the turn path of a chat agent used from phones — budget well under 1 s; docs' own example uses a 3 s timeout; (5) leaf subagents have no `memory` tool, so provider-registered tools are their only recall path; skip extraction when agent_context is not primary.

WHAT THIS DOES NOT MEAN: it does not mean a provider replaces MEMORY.md — the files keep being injected, and provider writes are additional. It does not mean Hermes has no memory hooks for non-providers — pre_llm_call is available to any plugin.
