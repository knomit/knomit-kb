# A peer's pushed branch reaches the host's agent branch only through two merges: the operator's web merge (POST /repos/{repo}/branches/{branch}/merge → store.MergePushed) and, under `consensus: auto`, the consensus merger (store.MergeConsensus); each writes one host-signed merge commit [agent tip, tip] under the agent branch's lock or refuses, including when the result would change a dot path (409 "Merge would change system files")

WHAT: F11 lets a peer push its own agent/<peer> branch to a host. That branch reaches the host's agent branch (and from there, through the host's ordinary sync or local reconcile, the upstream/main and the origin) through exactly TWO merges, both into ri.AgentBranch() and never into main:
1. the operator's web merge described here (store.MergePushed);
2. the consensus merger (internal/repos/consensus.go, F08) when the ontology at the consensus branch's tip sets `consensus: auto`: on the instance that owns the consensus branch it merges every pushed branch as soon as the push lands, through store.MergeConsensus (no side taken, conflicts refused and left for a human, a refused tip remembered and retried only when it moves, plus a no-op for a tip that only merged the host back in).
No MCP tool, CLI or trigger merges a pushed branch. An earlier version of this fact said "only the operator" and "no loop"; that is FALSE wherever `consensus: auto` is on.

PRIVATE-PATH GUARD (PR #511): both MergePushed and MergeConsensus set mergeOpts.guardPrivate, so a merge whose RESULT would change any dot path of the agent branch (.knomit/, any segment beginning with ".") is refused with *store.PrivatePathMergeError (errors.Is ErrPrivatePathMerge) and nothing moves, whatever `resolution` or `conflicts` setting picked the sides. The web merge answers 409 "Merge would change system files" with `private_paths` and `peer_commit`; the consensus merger handles it like a conflict (one warning, the tip remembered). See kb/invariants/store/git-serve/pushed-branch-merge/private-path-guard/fbd12444.md.

REST:
- GET /repos/{repo}/pushed-branches lists every local branch repos.RepoInstance.IsPushedBranch accepts (agent/*, not ri.agentBranch (EXACT equality with the persisted branch), not the upstream; since PR #513 a peer branch whose name ends in this instance's fp8 IS listed and IS eligible for `consensus: auto`, because nothing is inferred from a name) with tip, tip_time, tip_author, to_merge (commits reachable from the tip and not from the agent branch), merge_base, other_files_changed (paths outside the ontology root). A subscription lists none.
- POST /repos/{repo}/branches/{branch}/merge {expected_tip, resolution?} merges into ri.AgentBranch() — the target is NEVER a parameter. It is the FIRST route that enforces `operator` (requireOperator = Require(operator), switched off only with authDisabled like writeGate); writeGate adds `write`. The shipped loopback_default holds both, so the web UI and desktop app need no setup; an instance certificate ({read, push:own}) is refused by writeGate, a certificate granted write but not operator by Require.

STORE (MergePushed → mergeIntoBranchLockedOpts with mergeOpts{srcTip, record, side}; every other caller passes the zero value and is unchanged):
- srcTip: the src ref is read under the dst lock; if it is not expected_tip the call returns *BranchMovedError (409 "Branch moved") before any object is written, else it merges exactly that commit.
- record: never fast-forward (the FF shape gets a merge commit whose tree is the peer's), never a tree-identical Noop (a zero-diff merge commit is written, so the peer tip becomes reachable and to_merge clears — otherwise it would read 1 forever after the peer's reconcile merged main). The only Noop is 'expected_tip already in the agent branch'. Commit-log parity holds: checkCommitLogParity compares against branch_commits visibility and accepts no-op commits.
- side: StrategyRefuse unless a `conflicts` setting at the consensus branch's tip settles a path (the host's own branch is the consensus side; an explicit resolution overrides the setting); an unsettled conflict is *MergeConflictError → 409 with conflicting_paths, paths_without_base, base_commit, host_commit (dst) and peer_commit (src). With resolution host|peer, EVERY conflicting path detected under the dst lock takes that side (host → ResolveDst, peer → ResolveSrc). ours/theirs are refused with 400: the asker is the host's operator, for whom git's 'ours' is the host — the reverse of knomit_experiment's.
- Disjoint histories wrap ErrUnrelatedHistories (409).

UI: a block under Experiments (hidden for a subscription and while the repo mode is unknown). The confirm dialog lists facts changed since merge_base from /changes and sends that response's `head` as expected_tip, so a push landing while it is open is refused, not merged unseen. A refused merge shows BOTH versions of each fact at host_commit/peer_commit before the whole-set choice. No re-clone/lineage text (user ruling D4a): E4 trusts what an own-signed merge brought in (kb/decisions/store/verify/first-contact).

WHAT IT DOES NOT MEAN: the peer's branch is never written; the host never merges into main (on an origin-less host main follows the agent branch through AdvanceLocalUpstream); the whole-set resolution is taken against the conflicts present at the merge, which can differ from the ones the dialog showed if the HOST's agent branch changed in between (only the peer tip is pinned).
