# /git accepts a push (F11): an enrolled instance updates exactly ONE agent/* branch that is not the host's own, through knomit's own receive-pack: quarantine, new-commit walk, dot-path fast fail, mode-driven judge, one-transaction promote, registration through the chokepoint

The /git endpoint serves git's receive-pack beside upload-pack (F11). It is knomit's own code over go-git's CODEC (packp.ReferenceUpdateRequest, packfile.Parser, packp.ReportStatus, sideband), not go-git's transport/server, which writes the pack into the storer before any ref is judged, advertises every ref plus delete-refs, and ignores the command's old hash.

WHO may push is decided at the web edge, per request: `GitRemoteHandler` builds a `store.PushPolicy` and attaches it to the request context (the store's Handler() is built once and cached, so the pusher can only travel on the request). Only `Kind: instance, Via: cert` principals push; `pushPermission` (on the /git mount) records whether the principal holds `push:own`, which `CertGrants` gives every chained instance implicitly; a subscription refuses. The write gate EXEMPTS receive-pack (a push is not a fact write). No policy on the context → the store refuses (fail closed when reached without the edge). Bearer tokens never reach /git (the OAuth listener mounts no /git).

The POST, in order:
1. whole-request rules from the commands alone: exactly ONE command, not a delete, under refs/heads/agent/, not the repo's upstream, not the host's own agent branch (exact name); no rule asks whose branch the ref is; any failure refuses the whole push with an ERR pkt naming the rule (git renders `fatal: remote error: <text>`, go-git returns `<text>`), after draining the body;
2. the pack is parsed into a `quarantine` storer (memory writes, reads fall through to the host so thin-pack REF_DELTA bases resolve);
3. new commits = a walk from the new tip that STOPS at commits the host already holds (O(push), not O(repo)); in EVERY mode, refused when one's dot-path content matches NONE of its best merge bases with the upstream, i.e. matching ANY one base passes (`privatePathClosure`, early feedback only, and NOT O(push): one merge-base walk per new commit; kb/invariants/store/git-serve/receive-pack/content-closure/692bbe0d.md); then judged with `judgeCommit` plus signer = pusher (`signerIsPusher`, kb/invariants/store/git-serve/receive-pack/signer-is-pusher/0fc6cabf.md) when `verify_signatures` read at the HOST's upstream tip is log/enforce (off never reads the fleet; enforce without a fleet repository refuses);
4. under lockBranch(branch) on `context.WithoutCancel`: old-hash compare-and-swap, `storegit.PutObjects` promotes only the objects the new tip reaches in ONE transaction, `CreateBranch(branch, upstream)` seeds a first push (rows + index watermark, so the first sync is a diff), then `advanceBranchTo` (the create/FF/rewind body reconcileMainTo always ran) ends in notifyCommit.
A pushed branch is readable on the host (REST/MCP at that branch, listed in /branches), never writable there (WritableBranch false), fires no host trigger (onCommit kicks only the agent branch), and is never forwarded by the host's own origin push.

A pushed branch reaches the host's AGENT branch (which the upstream/main follows) only through two merges: the operator's web merge (`MergePushed`, kb/architecture/store/git-serve/pushed-branch-merge) and, under `consensus: auto`, the consensus merger (`MergeConsensus`). Both refuse a merge whose result would change the agent branch's dot paths (the consensus merger treats the refusal like a conflict and remembers the refused tip; the web merge answers 409 "Merge would change system files" with `private_paths`): that guard, not receive-pack, is the authority (kb/invariants/store/git-serve/pushed-branch-merge/private-path-guard/fbd12444.md).

WHAT IT DOES NOT MEAN: accepting a push is not accepting its content into the host's knowledge (a push whose tip the host already holds sends no new commits and skips the closure and the judge; the merge guard still applies); with verify_signatures off (the default) the certificate is the whole authentication of a push and NO branch is owned (PR #513 deleted the fp8-suffix rule): see kb/decisions/fleet/branch-ownership-not-identity/28db3a86.md.

## UPDATE (PR #524, verified at merge commit 9db8c106)

1. Step 3's 'STOPS at commits the host already holds' is, on the FLEET repository, 'stops at a held commit only when it is reachable from main or from a local agent/* branch'; any other held commit is judged as if new (kb/decisions/store/git-serve/receive-pack/new-commit-walk/75ab4d9f.md). So 'only new commits are judged' means 'only commits that are new or not admitted' there.
2. The judge (step 3, after the closure) is now the shared core `repoHandler.judgeIncoming` (the former body of `receivePack.verify`, which is a thin wrapper passing signer = pusher), preceded by `repoHandler.privatePathClosure`. The fleet master's fetch-time admission (store.AdmitPeerBranch / JudgePeerBranch) calls the same two over `tip ∖ main` with a non-empty selfRoot (the fleet's fact root), but with NO signer rule, since a fetch has no pusher. Rule changes in judgeCommit therefore reach the fetch entry automatically.
3. A fleet copy WITH an origin accepts no push at all: repos.Manager.FleetPushRefusal, applied at the web edge in pushPolicy (an unreadable origin row refuses; the message does not echo the origin URL). Only the hub (the master's copy with NO origin) receives pushes. This is defence in depth beside the walk rule in point 1, and applies to a member's copy too.

Misreading: 'a push to /git is how members reach the fleet' is true only for the knomit-hosted fleet; on a forge-hosted fleet members push to the forge and /git on any fleet copy refuses.
