# RelevantMethodologyForFact composite score: 0.6*vector + 0.4*tag_overlap, minScore-filtered, source vector FETCHED not re-embedded

`methodologyMatcher.RelevantMethodologyForFact(ctx, branch, factPath, sourceDomains, sourceEntities, k, minScore)` ranks methodology facts by a composite score on [0,1]: `vectorWeight*VectorScore + tagWeight*TagOverlap` with vectorWeight=0.6, tagWeight=0.4 (internal/store/methodology.go). TagOverlap = (domain_overlap + entity_overlap)/2 where each overlap = |source ∩ candidate| / max(1, |source|). The 60/40 split favours vector because tag coverage is empirically incomplete (~28% missing domain, 20% missing entities).

CRITICAL — universal markers: 'meta', 'reasoning', 'methodology' are EXCLUDED from the candidate-side domain set before intersection (isUniversalMarker in methodology.go). They sit on every methodology fact and would inflate every tag_overlap score. Filter: type='methodology' AND not deleted AND visible-on-branch (uses the facts_type index). Path is NOT part of the filter — TYPE is the canonical, schema-validated marker; kb/meta/reasoning/ is a soft path convention, not load-bearing for retrieval. An empty candidate set returns ([]MethodologyMatch, nil), not an error.

WHAT THIS DOES NOT MEAN (drift corrected 2026-07-22 — this fact previously described an API that no longer exists; if you are holding the old shape in your head, all four of these bit you):

1. The function is NOT `RelevantMethodology` and does NOT take a source BODY. It is `RelevantMethodologyForFact` and takes a `factPath`. The source vector is FETCHED from facts_vec by (branch, factPath) and is NEVER re-embedded. Consequence: the source fact must ALREADY be indexed with a vector before you call this — you cannot score an unwritten or unindexed fact by handing it prose. It also lives on the `methodologyMatcher` sub-service, reached via `Service.Methodology()`, not on the old monolithic search index (see kb/architecture/store/240a44f5.md).

2. "Returns the top k" is WRONG — it returns UP TO k, filtered to `Score >= minScore`, which is a REQUIRED caller-supplied parameter, not an internal default. A caller passing a high minScore can get zero matches even with plenty of candidates; that is success, not failure. minScore also drives a SQL-level prune (`minVec := (minScore - tagWeight) / vectorWeight`), so it is a real cutoff, not a post-filter formality.

3. There is NO truncation and NO token cap. The old '1500-token injection cap, truncate lowest-scoring first' is gone — the doc comment is explicit: "No body concatenation, no re-embedding, no truncation." Callers operating over multiple source facts invoke this once per fact and merge, keeping the highest score per methodology path (see internal/synthesize/review_strategy.go and hypothesize_strategy.go). Prompt-size control is the CALLER's job now.

4. The coefficients are `const`, not package-level `var`. They cannot be tuned at runtime or overridden by a test; changing the weighting is a code change plus a rebuild of anything that cached scores.
