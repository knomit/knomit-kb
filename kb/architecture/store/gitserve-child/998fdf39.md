# store/gitserve holds the smart-HTTP handler (upload-pack and receive-pack) over a host{*vcs.Repo, *sync.Repo}; the parent re-exports PushPolicy and WithPushPolicy, builds the handler in Service.Handler, and repoHandler does not embed a gitserve handle

Since PR 11b of the internal/ hierarchy stack (branch refactor/hier-11b-gitserve, stacked on refactor/hier-11-sync), the smart-HTTP handler is the package internal/store/gitserve: httphandler.go (the mux, upload-pack, the sideband writer), httphandler_advrefs.go (the curated advertisement and the root-commit cache), httphandler_pack.go (negotiation, the object-set build, shallow handling), httphandler_receivepack.go (PushPolicy, WithPushPolicy, receivePack: serve, judgeRequest, verify, privatePathClosure, register, heldAdmitted), receivepack_quarantine.go (the quarantine over the host's storer, the new-commit walk) plus host.go, doc.go and testseams.go. It is NOT under internal/store/internal/. It imports vcs, verify, sync, fleetrec (the Fleet a PushPolicy hands the judge) and merge (the Mode constants a branch move reports); TestLayers lists those five as same-layer edges, the last two being beyond the proposal's arrow (gitserve to vcs, verify, sync) and types only. The sync child it depends on is described in kb/architecture/store/sync-child/25664ca8.md (written in the hier-11 sync experiment).

THE HANDLE. gitserve.host is `struct{ *vcs.Repo; sy *sync.Repo }`: every `rh.Storer()`, `rh.LockBranch`, `rh.CreateBranch`, `rh.NotifyCommit` ... of the old repoHandler-typed code is the vcs handle's, and the one move receive-pack makes through reconcile code is `rp.rh.sy.AdvanceBranchTo` (was rh.advanceBranchTo). The three repoHandler wrappers the handler used (judgeIncoming, privatePathClosure, verifyModeAt in verify_seam.go) are called as verify.JudgeIncoming / verify.PrivatePathClosure / verify.VerifyModeAt with `rh.Repo`, which is exactly what the wrappers passed; the parent keeps the wrappers for Service.JudgePeerBranch. The parent builds the handler once: `gitserve.NewHandler(s.rh.Repo, s.rh.syncRepo, s.UpstreamBranch)` in Service.Handler (service_gitserve.go), the same pointers repoHandler embeds, so the lock order (branch lock, then AdvanceBranchTo, which ends in NotifyCommit) and the uncancellable registration context (kb/invariants/store/git-serve/receive-pack/ae01265e.md) are unchanged: the receive-pack body moved without an edit beyond the package qualifiers.

THE SEAM (internal/store/gitserve_seam.go): `type PushPolicy = gitserve.PushPolicy` and a one-line WithPushPolicy forward; nothing else of the child is exported to callers outside store. repoHandler gains no embedded gitserve handle: nothing in the parent calls a method of the child.

TESTS: they drive the handler through svc.Handler() and stayed in the parent. Five internals are reached through test doors in gitserve/testseams.go, each calling mustBeTest (panics outside a test binary): SetPushRegisterHookForTest, ObjectBuildsForTest, NoPushPolicyTextForTest, NewCommitsForTest, JudgeRequestForTest. No test moved; the store's top-level test count is unchanged.

CONSEQUENCE: protocol and push-judging code goes in gitserve; a new need from the Service stays a parent function that passes the handles in. MISREADING: the handler is not an override point and holds no state of its own beyond what newGitHTTPHandler caches (the root-commit cache).
