# Derived SQLite index state is regenerated from git, never data-migrated — new derived shapes ship an empty-table migration + a GraphSchemaVersion bump

CROSS-CUTTING PATTERN: every piece of SQLite-side state DERIVED from the git fact tree — facts rows, facts_vec embeddings, the cypher graph, fact_domains/fact_entities junctions, and fact_domain_tokens (PR #70) — is treated as rebuildable cache, never as a thing to migrate data into. Git is the only source of truth.

THE RECIPE for changing the shape of derived state:
1. Give the empty shape to the schema. USUALLY that is a numbered .up.sql migration creating ONLY the empty table/index — NO data backfill (migration 000008's comment: 'Derived index state: rebuilt from git, no data backfill needed here; next rebuild populates it.'). But NOT ALWAYS: a shape that must vary at runtime is code-managed — facts_vec is created by ensureFactsVec at the active embedding model's dimension, deliberately with NO static FLOAT[768] migration (search_index.go v4 note).
2. Force existing deployments to regenerate it. USUALLY a bump of searchIndex.GraphSchemaVersion (persisted in meta.graph_schema_version). But NOT ALWAYS: the embedding vectors regenerate on EMBEDDING-IDENTITY drift instead — NeedsRebuild ALSO returns true when meta.embed_model_id / meta.embed_dim no longer match the active embedder, with no version bump (search_index.go).
3. The trigger (version mismatch OR embedding-identity mismatch) is detected at startup (NeedsRebuild) and drives a full Rebuild (ON CONFLICT(path,blob_hash) DO UPDATE) that regenerates ALL derived state from the git tree + commit_log. Rowid preservation means embeddings SURVIVE a version-only heal (no re-embed) — but an embedding-identity heal recreates facts_vec empty and DOES re-embed the whole corpus.

WHY safe: because the data is reconstructable from git, a full reindex is ALWAYS a valid no-data-loss operation, so the team never writes/tests a forward data-migration for derived state — schema files carry only shape, and correctness of derived content lives in ONE place (the rebuild path). Contrast: AUTHORED state (facts.domain/entities JSON, raw immutable fact_domains rows) is NOT rebuilt-and-replaced — it round-trips from the markdown; only the CANONICAL/derived projections are regenerated.

WHAT THIS DOES NOT MEAN:
- A derived-shape change does NOT always ship a numbered .up.sql migration — a runtime-varying shape (facts_vec) is created in code by ensureFactsVec, not a migration file.
- A rebuild is NOT always gated by a GraphSchemaVersion bump — an embedding model-id/dim change forces one through the embedding-identity check with no version change.
- The derived-state set does NOT end at fact_domain_tokens — facts_vec embeddings are derived cache too, and their regeneration path differs (re-embed, not rowid-preserved).
