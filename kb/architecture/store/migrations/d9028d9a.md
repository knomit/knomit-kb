# golang-migrate's whole record is a version integer plus a dirty bit — no checksum, no body hash — and every rule of the repo migration chain follows from that: applied files are immutable, only a NEW forward migration reaches an existing DB, bodies must be re-runnable because recovery re-executes them, and a dirty stamp is healed by rewinding the integer exactly once

The migrator remembers nothing about a database except which version integer it reached and whether the last body was interrupted, so the only lever that reliably changes an existing database is appending a new version, and every recovery or safety rule is a rule about manipulating that integer rather than about the schema text.

What follows, and where each is instantiated:
- APPLIED FILES ARE IMMUTABLE; ONLY FORWARD MIGRATIONS REACH EXISTING DBs. There is no checksum re-validation, so an in-place edit to an already-applied migration is silently skipped on every persistent DB. Adding a column to `commit_log` is a NEW numbered ALTER migration with a matching down; editing 000001 would leave every on-disk repo without the column until the next `CommitLogSync` INSERT failed with 'no such column'. A forward ALTER auto-heals existing DBs with no file deletion and no `:rebuild` (which never runs migrations and never touches commit_log). Backfill of existing rows is the migration's own job — `CommitLogSync` is INSERT OR IGNORE and will not update them.
- BODIES MUST BE RE-RUNNABLE, BECAUSE RECOVERY RE-EXECUTES THEM. `dirty = 1` is set before a body and cleared after, in transactions separate from the body, so a crash in that span leaves dirty forever and `migrate.All` fails, dropping the repo from the API with a WARN. `migrate.All` self-heals: detect dirty at N, `Force(N-1)`, `Up()` again, attempted EXACTLY ONCE per call. Safe only because bodies are transactional (fully applied or fully unapplied, never torn) AND idempotent (IF NOT EXISTS / INSERT OR IGNORE).
- THE ONCE IS LOAD-BEARING. Self-heal covers INTERRUPTED migrations, not migrations that fail DETERMINISTICALLY on the data (a UNIQUE index the rows violate): those re-fail identically, so an unguarded loop would clear dirty, re-fail and re-dirty on every boot, turning a one-time manual recovery into a permanent one. On failure `migrate.All` reports the UNDERLYING migration error and leaves dirty set. Corollary: a migration that can fail on pre-existing data must repair that data itself before constraining it.
- `migrate.Core` HAS NO SELF-HEAL, by design: it runs only repo/ version 1, so a rewind on a dirty later version would migrate DOWN to 1 and destroy schema; it is only ever handed a fresh `:memory:` database (`storegit.NewMemoryStorer`), which therefore carries no `facts_vec`, no `commit_parents` and nothing from 000002 onward.

The two chains — repo/ (per-repo store, `migrate.All`) and control/ (`<home>/control.db`, `migrate.Control`) — are INDEPENDENT sequences, each numbered from 1 against a different file with its own `schema_migrations`; migration files are append-only history (a table created by one and dropped by a later one keeps both files).

WHAT THIS DOES NOT MEAN: the theoretical worry that commit_log columns must live in 000001 because Core bootstraps the git package is moot — nothing exercises the Core path for that. The ephemeral session DB is outside this rule entirely (recreated from `session_schema.sql` on every open, plain edits, no migration). And idempotency makes re-execution safe; it does not make existing data satisfy a new constraint.
