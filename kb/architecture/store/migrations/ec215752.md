# control.db's schema text has TWO appliers (the versioned migrator and migrate-registry's in-transaction replay), so the text must be IF NOT EXISTS-idempotent — and that one property constrains what a change may look like, hides drift from ordinary tests, and forces the replay to consume the whole chain

One schema text is applied by two independent appliers against homes in unknown states — a versioned migrator that records what it ran, and an operator tool that replays the text inside its own transaction because the migrator cannot join it — so the text must be safe to re-run anywhere, and that single idempotence requirement is what shapes every downstream rule: it constrains which schema changes are expressible, it makes divergence between the text and a live shape invisible to no-op and name-only tests, and it obliges the replaying applier to consume the whole chain rather than one file.

How each consequence shows up:
- EXPRESSIBILITY. New control.db state is a NEW TABLE, not a new column: `ALTER TABLE ... ADD COLUMN` has no IF NOT EXISTS form in SQLite and would break the replay. That is why a subscription is the PRESENCE of a row in `repo_subscriptions` and `Origin.Mode` is derived at read time — with the second-order effect that an origin writer which rewrites `repo_origins` without carrying Mode silently demotes a subscription to sync. A test enforces idempotence for EVERY control migration. This is specific to the CONTROL chain; the per-repo store schema is migrated differently.
- WHY IDEMPOTENT IN THE FIRST PLACE. The baseline is the pre-migrator DDL verbatim with every IF NOT EXISTS retained, so it no-ops on live homes and creates on fresh ones, needs no probe-and-Force stamping (whose failure mode is a home stamped at a version whose schema it lacks), and already satisfies the standing policy that up-migration bodies must be re-runnable because `upWithRecovery` can force them at any time. It lives in `internal/store/migrate` (`control/` beside `repo/`); `schema_migrations` records version integers only, so directory renames are safe.
- DRIFT IS INVISIBLE. An IF NOT EXISTS baseline is equally a no-op against a table whose shape has silently diverged from the text, so fresh homes and existing homes can carry different shapes forever with every package green. Only a shape-equality test catches it: build one DB from the legacy DDL pasted as a literal, one via the migrator, and compare `table_info`, `foreign_key_list` (table_info cannot see ON DELETE CASCADE), `index_list`+`index_info`, AND each index's `sqlite_master.sql` text (the only place a partial index's WHERE predicate is visible). The table's own `sqlite_master.sql` is a deliberately accepted residual. Pasting the literal is the mechanism, not a smell — importing the constant would make the test tautological.
- THE REPLAY MUST COVER THE CHAIN. A helper that extracts 'the schema' by naming ONE migration file silently pins itself to a chain length: once a 000002 exists, a home stamped at v2 by any registry open and then rebuilt by migrate-registry from v1 text carries a v1 lens shape under a v2 stamp that no migration will ever repair, with no runtime error anywhere. The resolution taken is the accessor returning the whole chain: at HEAD `migrate.ControlSchemaSQL()` globs every `control/*.up.sql`, the chain has three migrations, and the former single-file accessor and its exactly-one tripwire test are gone.

WHAT THIS DOES NOT MEAN: 'no migration needed' or 'plain edits' is NOT a property of control.db — that belongs to the ephemeral session DB; control.db keeps the numbered chain. The replay is the ONE deliberate exemption from the shared bring-up ordering in `controlUp`, and only because it drops and rebuilds the lens tables from the text inside its own transaction; every other opener must call `controlUp` rather than reproduce the sequence.
