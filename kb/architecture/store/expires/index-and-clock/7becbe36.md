# `expires` is indexed in the fact_expires SIDE TABLE (not facts columns — the migration ADD COLUMN budget is spent), backfilled by the GraphSchemaVersion 5→6 forced rebuild; every read uses ONE clock — SearchOptions.Now set once per request, and a knomit_query cursor's pages reuse the snapshot's instant stored per row (pagedRowState.AsOf)

Index: migration 000026 creates `fact_expires(fact_id INTEGER PRIMARY KEY REFERENCES facts(id) ON DELETE CASCADE, expires TEXT NOT NULL, expires_at INTEGER NOT NULL)` plus an index on expires_at. One row per DATED fact version, keyed by the immutable, content-addressed facts row (a new version of a fact gets its own row); an undated fact has no row. `expires` is the frontmatter string as written (offset kept, for display); `expires_at` is unix seconds UTC and is what every filter compares (RFC 3339 strings with different offsets do not order as text). Every read and every filter `LEFT JOIN fact_expires fe ON fe.fact_id = f.id` (search, RecentFacts and its count, GetByPath, the vector meta fetch, the highlights CTE).

WHY a side table and not facts columns: `ALTER TABLE … ADD COLUMN` is not idempotent, and the migration recovery path tolerates exactly ONE duplicate-column collision per run — which 000019 already spends whenever a head-schema database is version-rewound and re-run (what TestMigration000014/000015/017 do; 000023's header records the same limit and rebuilt its table). The first 000026 ALTERed facts and turned those three red; `facts` cannot be dropped and recreated. See conventions/store/migrations/idempotent-up-bodies for where the limit does and does not bind.

Writers: the incremental upsert does `INSERT OR IGNORE` after reading the facts row id; rebuildFacts does a second statement that re-parses (knomit_parse_fact) ONLY blobs whose bytes contain the token `expires` (instr prefilter — the token, not `expires:`, because YAML also accepts `expires : …`, which the incremental path indexes) and `INSERT OR REPLACE`s — a rebuild is the repair path. Backfill is NOT a data migration (derived state is regenerated from git): GraphSchemaVersion went 5→6, so every branch indexed by an older build reports NeedsRebuild on open and the rebuild fills the table — needed because a hand-written `expires:` could already sit in git while the old parser dropped it.

Clock: SearchOptions.Now is the read's clock, set ONCE per request (REST: the web package's `timeNow` var; MCP: the mcp package's `timeNow` var, read in parseQueryFilters), and the same value computes each row's `expired` marker, so filter and marker agree — pinned at the boundary on the first page by TestQuery_FirstPageFilterAndMarkerShareOneClock and TestREST_ExpiryFiltersAndMarkers. A knomit_query cursor snapshot stores that instant in every row's pagedRowState.AsOf; resumed pages mark against it (snapshotClock), not page-serve time, so a query run with expired=false never shows expired:true on page 3. By-path reads (explain root and summary nodes, REST fact view) and Highlights have no shared query clock and judge at the time of the call. The clock is the SERVER's; comparison is at whole seconds everywhere. Combined with a text query the expiry filter applies after the vec0 k-window (gotchas/store/vec0/k-window-precedes-where), so it can under-return; without text it is exact.

WHAT THIS DOES NOT MEAN: there is no time-travel query and no anchor-at-commit evaluation — search is HEAD-only, and commit dates are not trusted as an anchor (rebase rewrites committer time).
