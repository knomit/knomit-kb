# store/verify is the judge as a package (signatures, tree shape, CheckRange, M3, E4, validations, artifact rules, the incoming-push judge, Audit); it reads a store only through *vcs.Repo and fleetrec, the parent keeps repoHandler forwards and every public name, and verify_own.go stays in the parent driving an exported Judge

Since PR 08b of the internal/ hierarchy stack (branch refactor/hier-08b-verify, stacked on the fleetrec PR), the verify cluster is the package internal/store/verify (a sibling of git, migrate and fleetrec, not under internal/). PATH MAP for readers of older facts, which name the old files: verify_sig.go -> verify/sig.go, verify_tree.go -> verify/tree.go, verify_walk.go -> verify/walk.go, verify_range.go -> verify/range.go, verify_m3.go -> verify/m3.go, verify_e4.go -> verify/e4.go, verify_validations.go -> verify/validations.go, verify_artifacts.go -> verify/artifacts.go, verify_audit.go -> verify/audit.go, verify_incoming.go -> verify/incoming.go. Unexported names in those older facts became exported: judge -> verify.Judge (fields entry/ownOntology -> Entry/OwnOntology), newJudge/judgeCommit -> NewJudge/JudgeCommit, checkM3 -> CheckM3, verifyCommitSignature -> VerifyCommitSignature, signerIsPusher -> SignerIsPusher, branchFactsValid -> BranchFactsValid, loadMembers etc. -> fleetrec.*.

It imports only fact, pki, store/fleetrec and store/internal/vcs (TestLayers lists store/verify -> store/fleetrec and -> store/internal/vcs). It reads a store only through *vcs.Repo; the six repoHandler methods that used to live in the verify files (judgeIncoming, privatePathClosure, verifyModeAt, checkOwnLineage, plus the internal incomingValid/acceptedCommit) became functions taking the *vcs.Repo (JudgeIncoming, PrivatePathClosure, VerifyModeAt, CheckOwnLineage). The parent's verify_seam.go keeps the repoHandler methods as one-line forwards passing the embedded Repo, so receive-pack, the sync path and clone call them unchanged, and re-exports every public name (Refusal, Rule*, Verify*, CommitSigner, Err*, RangeInput/RangeVerdict, CheckRange, Audit, ...) as aliases, consts, the SAME error values and forwards.

WHAT STAYED in the parent: verify_own.go (judgeOwnRange, the publish-time judge of the master's own commits; the proposal files it under sync) and verify.go (the integrity report, fsck). verify_own.go builds three verify.Judge values and sets Entry or OwnOntology on them before calling JudgeCommit, exactly as it set the unexported fields before; no verification test moved, because every one drives a full Service or shares the parent's fixtures (namedSigner, newRangeFixture, pushHost).

CONSEQUENCE: a new rule goes in the Judge; a new caller of the judge in the parent goes through verify_seam.go or verify_own.go. verify never writes and never moves a ref, and fact_write.go and vcs/sign.go must not call it (TestVerifyIsNeverInTheWritePath matches the old and the exported spellings). MISREADING: the exported Judge is not a second entry point for acceptance; CheckRange and JudgeIncoming are, and the Entry/OwnOntology flags are set only by the incoming-push judge and the master's own-range judge.
