# repoHandler owns DB + git storage + git reads; sub-indices delegate via .rh field

repoHandler is the complete shared backend that every sub-index reaches UP into via its `rh` field. factIndex no longer owns gits/repo/configMu — it accesses fi.rh.gits, fi.rh.repo, etc. searchIndex.Sync(ctx, branch) and Rebuild(ctx, branch, progress) take NO git-reader parameter — they use si.rh directly. The 8 forwarding stubs that used to exist on Service are DELETED; factIndex retains a small set of delegation stubs for FactIndex-exposed methods (HeadCommit, ListAll, ListAllWithHash, LastCommitForPath, DiffFiles) that forward to fi.rh.

Anti-pattern: do not add new git-reader-style parameters; access via the embedded *repoHandler.

WHAT THIS DOES NOT MEAN:

1. **There is no `gitReader` interface.** This fact previously asserted `*repoHandler` satisfies `BranchIndex` and `gitReader` via `var _ gitReader = (*repoHandler)(nil)`. That interface and that assertion DO NOT EXIST at HEAD — do not search for them, and do not reintroduce a `gitReader` abstraction on the strength of this fact.

2. repoHandler is NOT a short four-field struct. "db, gits, repo, configMu" is a stale and misleadingly SHORT inventory — treating it as complete leads to re-adding state that already lives there. At HEAD (internal/store/branch.go) it carries: db, cache (*branchCache), onDrop, gits (*storegit.Storer), repo (*gogit.Repository), signer (ssh.Signer), onCommit (external observer), im (IndexManager back-ref), name, **factRoot** (the ontology root, set by Service.SetOntologyRoot, never mutated after build/swap), netTimeout, configMu, branchMu, embedder. Before adding shared state anywhere, check this struct — it is probably already here. Treat any inventory in a fact (including this one) as a pointer to the struct, not a substitute for reading it.

3. configMu is a sync.RWMutex, NOT a sync.Mutex. It is not merely a write-exclusion latch: the READ side is held across a whole fetch so a concurrent configureRemote refspec rewrite cannot race it. Taking it as a plain Mutex (or dropping the RLock on the fetch path) reintroduces that race.

4. This fact is NOT the authoritative statement of the layering rule or of the current sub-index set — it predates P1.3. See kb/architecture/store/sub-index-up-not-sideways/360ce7a5.md for the rule and the full list (including the four read-side query sub-services), and kb/architecture/store/240a44f5.md for what was carved out of searchIndex.
