# An off repository's F09 cost is tree reads only, kept small by two caches: settings memoised by the ontology paths' top-level tree entries, and the anchor's history kept in memory per upstream (knomit-kb: ~8 ms per 5-commit tick; one walk of ~130-330 ms after a restart)

Verification off (the default, and every private repo) still reads commit trees, because an off repo must notice being turned on. It never evaluates a signature or M3 (foldResult.SigChecks = 0), writes no anchor ref and counts nothing.

Two caches keep that small. Measured on knomit-kb main (2391 commits, bare clone, M-series laptop):
- `settingsAt` memoises by the root-tree entries (hash + mode) of the three ontology paths' top-level names (.knomit, .domains, the pre-dot rung). Consecutive commits share them, so a walk decodes one root tree per commit and parses each distinct ontology once: reading settings for all 2391 commits fell from ~750 ms to ~65 ms.
- `repoHandler.verifyBelow` keeps, per upstream, the set of commits reachable from the anchor (or the off-scan watermark), extended with foldResult.Advanced as the anchor moves, so a tick walks only the new commits. Steady 5-commit tick: ~8 ms. In memory only: the first tick after a restart walks the history once (~130 ms), and a first-contact root fold costs ~300 ms.

Before F09 the reconcile tick did none of this. Revisit if a repository's history grows by orders of magnitude, since the cache is one hash per commit.
