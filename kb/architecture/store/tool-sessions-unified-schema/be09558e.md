# tool_sessions/tool_seen_paths/tool_queue live in a SEPARATE ephemeral session DB (relocated from main by migration 000010); shared by knomit_explain + knomit_query

The generic tool_sessions + tool_seen_paths tables (each session row carries a `tool` field naming its consumer) plus a tool_queue table back the stateful read tools; the interface is ToolSessionIndex (interfaces.go), implemented by *toolIndex, exposed via Service.ToolSession(). Originally these were explore_sessions/explore_seen_paths, renamed when knomit_explain was added.

RELOCATION (migration 000010): these tables NO LONGER live in the main, git-derived DB. Migration 000010_relocate_session_tables DROPs tool_sessions/tool_seen_paths/tool_queue (and pipeline_sessions/pipeline_work_items) from the main DB; they now live in a SEPARATE, disposable session database defined by internal/store/session_schema.sql — which is NOT a versioned migration: the session DB is recreated empty on every Service.Open (initSessionSchema), because it holds only process-runtime state not derivable from git and not durable across restarts. (pipeline_watermarks intentionally stays in the main DB as durable progress.) So do NOT look for these tables in the numbered migrations or expect them to survive a restart.

The two remaining consumers:
- knomit_explain: a paginated BFS over a fact's provenance graph, using tool_queue for BFS state (session_id, path, commit_hash, and sort_key — the SQL-orderable consume order, formerly named `depth`; plus a per-item `state` JSON payload). The graph is a PROVENANCE SNAPSHOT frozen at the root fact's most recent commit — each ref read AT THE COMMIT WHERE THE REFERENCE EXISTED.
- knomit_query: snapshots the remainder of a result set (relevance OR sort=recent) into tool_queue (in the `state` column) and pages it via queryResume.

knomit_explore has been REMOVED (its browse-by-recency folded into knomit_query as sort=recent). The former explore-only LastCommit / WalkChangedFiles git-walk is gone.

WHAT THIS DOES NOT MEAN:
- These are NOT main-DB tables and NOT in the numbered migrations — they were relocated to a separate ephemeral session DB by migration 000010 and are (re)created from session_schema.sql on every Open.
- The queue's ordering column is NOT `depth` — it is `sort_key` (session_schema.sql: 'was depth').
- Session state does NOT survive a restart (the session DB is recreated empty each Open); only pipeline_watermarks in the main DB is durable.
