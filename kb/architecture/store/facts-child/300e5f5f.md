# store/facts holds the fact read/write cores, the system-file / template / skill readers and the trigger dispatcher's store half as facts.Index and facts.Repo; repoHandler embeds *vcs.Repo AND *factsRepo (alias of facts.Repo), and the parent keeps every public name through facts_seam.go

Since PR 09 of the internal/ hierarchy stack (PR #555, merged into dev as 6733104c), the facts cluster is the package internal/store/facts (a sibling of git, migrate, fleetrec and verify, not under internal/). Files: fact_index.go (Index: DiffFiles, ChangesUnder; NewIndex, SetAuth), fact_read.go, fact_write.go (HISTORICAL spelling as of #555: the write cores writeFileExact and BatchWriteLocked; since E2, #573, the lock-assuming core is the unexported batchWriteLocked; WriteFact and friends, ValidatePath, IsInvalidPath), fact_write_validate.go (validateWrite, FactInvalidError, WithCarriedOver), fact_record.go and fact_types.go (FactRecord, NewFactRecord, FactWithBody, ReadFact*, WriteFactResult and the ErrRepoReadOnly / ErrFactChanged / ErrInvalidPath sentinels), system_files.go, templates.go, skills.go, triggers.go (the dispatcher's store half: TriggerIndex, trigger_watermarks / trigger_fires / trigger_due_fires rows, DueCandidates, the commit readers), repo.go and testseams.go. It imports store/internal/sqlite, store/internal/vcs, store/verify, fact and pki (not store/git). THE facts-to-verify EDGE is exactly three uses, none in fact_write.go: verify.IsFactPathUnder (fact_write_validate.go, in validateWrite), verify.VerifyCommitSignature and the verify.CommitSigner type (triggers.go, CommitSignerOf). TestVerifyIsNeverInTheWritePath reads facts/fact_write.go and internal/vcs/sign.go and rejects any `verify.<name>(` call there, so a verify call added to fact_write.go fails it; the edge must stay in the validate and trigger files. TestLayers lists store/facts -> store/internal/sqlite, -> store/internal/vcs and -> store/verify as same-layer edges.

THE SEAM. The methods that used to be declared on repoHandler in these files (SkillsAt, SkillFilesAt, TemplateExistsAt, TemplateFilesAt, TemplateFactsAt, SystemFileAt, OntologyAtCommit, ScriptAt, RecipeAt, GuidanceAt, TreeReader, Toucher, CommitInfo, CommitSignerOf, BlobAt, IsAncestor, UpstreamTip, AncestorSet, the Trigger* / Record* / Due* rows, SignerFingerprint, validateWrite) are declared on facts.Repo, which is `struct{ *vcs.Repo }`. The parent's repoHandler is now `struct{ *vcs.Repo; *factsRepo }` (internal/store/vcs_seam.go; `type factsRepo = facts.Repo` in facts_seam.go gives the embedded field a name that does not collide with the embedded vcs `Repo`), and newRepoHandler builds ONE vcs.Repo and wraps the same pointer with facts.NewRepo, so a setter called on either side configures the same handle. Service keeps `fi *facts.Index` (built with facts.NewIndex(rh.factsRepo); repo.go sets credentials with fi.SetAuth). Promotion keeps every call site (rh.SkillsAt, s.Triggers() returning s.rh as a TriggerIndex) unchanged. facts_seam.go re-exports every public name as aliases, consts, the SAME error values and one-line forwards.

BOUNDARY RULES that were checked: facts.Repo declares no method with the name of a vcs.Repo method or of a parent-declared repoHandler method (HISTORICAL rationale as of #555, when facts.Repo embedded *vcs.Repo: a duplicate would silently shadow instead of failing to compile, because depth-1 selectors from two embedded fields are only ambiguous when used; since E2, #573, facts.Repo embeds nothing, so inside facts no such shadowing is possible, and the hazard survives only for the parent's repoHandler, which still embeds *vcs.Repo and *factsRepo); embedding is not virtual, so nothing in facts calls a method declared on the parent's repoHandler, and the write path (LockBranch, CommitSigner before any object is written, CommitSigs, objects, DeriveBeforeAdvance, ref move, NotifyCommit under the lock) runs unchanged.

WHAT STAYED IN THE PARENT AT #555 (HISTORICAL; the service_facts.go and triggers_testing.go parts below were superseded by parent slimming PR D, #567, see the UPDATE paragraph at the end): replay.go and consensus_branch.go (Service-level orchestration, counted as facade by the cluster fact), service_facts.go (HISTORICAL as of #555: Service.WriteSystemTree validated with facts.ValidatePath and called fi.BatchWriteLocked under rh.LockBranch / rh.NotifyCommit itself; since #567 it is a one-line forward to fi.WriteSystemTree), service_fsck.go (HISTORICAL as of #555: it called fi.WriteFile for the raw-write test; since E2, #573, WriteFile is the unexported writeFile and Service.RawWriteForTest calls fi.WriteFileExactForTest with the lowercased path), and triggers_testing.go (HISTORICAL: at #555 it held Service.TestingCommitFiles's testingTree, a test-only helper whose only caller was the parent, and stayed because exporting its tree builder would add a public test door for no consumer; the file no longer exists at #567, testingTree is in vcs/testseams.go).

TEST SEAMS. The case-preserving write core writeFileExact is reachable from parent tests only through (*facts.Index).WriteFileExactForTest, and SetBatchWriteUnlockedHookForTest now calls mustBeTest; both panic outside a test binary (testing.Testing). TestGitErrInvalidPath_Recovered moved into the child (it pins the unexported gitErrInvalidPath).

CONSEQUENCE: a new fact-file, system-file, template, skill or trigger-row reader goes in facts and, if outside callers use it, gets a line in facts_seam.go; code that needs a higher cluster (merge, index, sync) stays a method on the parent's repoHandler. MISREADING: facts.Repo is not a second git handle and is not an override point; it adds methods to the SAME vcs.Repo pointer, and a same-named method on the parent's repoHandler would shadow it only for parent callers.

UPDATE (refactor-store-slim-d-orchestration, parent slimming PR D): the body of WriteSystemTree is now facts.Index.WriteSystemTree in facts/system_files.go (the case-preserving, README.md-and-.knomit/-only door; same lock placement: branch lock, then BatchWriteLocked, then NotifyCommit under it). It was put in system_files.go on purpose and NOT in fact_write.go or triggers.go, because TestVerifyIsNeverInTheWritePath and TestFactWrite_CallsNothingFleet read facts/fact_write.go by path and the triggers allowlist reads facts/triggers.go; a new door added there would be scanned under the wrong rules. Service.WriteSystemTree in the parent's service_facts.go is a one-line forward kept for the callers in internal/repos. The test seams Service.TestingSetRef, TestingDeleteRef and TestingCommitFiles are likewise one-line forwards; their bodies are vcs.Repo.SetRefForTest, DeleteRefForTest and CommitFilesForTest (see kb/architecture/store/merge-child/4102d898.md for the pattern). triggers_testing.go is gone from the parent: its testingTree is in vcs/testseams.go.

VERIFIED at the #567 merge 07762646 (PR D, internal/store/facts/system_files.go, internal/store/service_facts.go, internal/store/internal/vcs/testseams.go): facts.Index.WriteSystemTree runs the read-only refusal, fact.TemplatePathAllowed, the case-fold duplicate check and ValidatePath, then takes fi.rh.LockBranch, calls fi.BatchWriteLocked and NotifyCommit under the lock; Service.WriteSystemTree and Service.TestingSetRef / TestingDeleteRef / TestingCommitFiles in service_facts.go are one-line forwards (to vcs.Repo.SetRefForTest, DeleteRefForTest, CommitFilesForTest; mustBeTest guards each).

UPDATE (refactor/store-e2-unembed-vcs, PR #573; verified on the branch head 08775aeb): facts.Repo is no longer `struct{ *vcs.Repo }`. It is `struct{ vr *vcs.Repo }`, a named unexported field, so none of the vcs.Repo methods (LockBranch, NotifyCommit, CommitSigs, Storer, SetRefForTest, ...) is promoted onto facts.Repo or onto anything that holds one. Inside facts every git-layer call is spelled rh.vr.X (fi.rh.vr.LockBranch, fi.rh.vr.NotifyCommit, fi.rh.vr.DeriveBeforeAdvance); lock placement and call order are unchanged. The parent's repoHandler still embeds *vcs.Repo AND *factsRepo, so the parent's rh.LockBranch resolves through *vcs.Repo and rh.SkillsAt through *factsRepo as before; the 'promotion keeps every call site' sentence above is true for the PARENT only. Consequences: (1) *facts.Repo no longer satisfies facts.TriggerIndex alone (DiffFacts is a vcs method); the TriggerIndex guard moved (from facts/triggers.go to interface_guards.go, now asserting *repoHandler, which is what Service.Triggers() returns); the TemplateIndex, SystemFileIndex and SkillIndex assertions in interface_guards.go were added by E2 (they did not exist before), and at the merge commit all four assert (*repoHandler)(nil), not *facts.Repo, so the guards do not pin what *facts.Repo alone satisfies. (2) facts.Index.BatchWriteLocked and WriteFile are unexported (batchWriteLocked, writeFile; system_files.go's WriteSystemTree calls fi.batchWriteLocked); Service.RawWriteForTest calls WriteFileExactForTest with the lowercased path. (3) The triggers allowlist keys are rh.vr.Repository, rh.vr.Storer, rh.vr.DB, rh.vr.BranchID, rh.vr.CommitSigner, (the full list in internal/store/triggers_guard_test.go is rh.vr.Repository, rh.vr.Storer, rh.vr.DB, rh.vr.BranchID, rh.vr.CommitSigner) computed by a local triggersCallKey so rh.vr.X is not folded into the anonymous ?.X; fact_write.go changed text (rh.X -> rh.vr.X) and both write-path scans still bite (proof in PR #573). TestChildRepos_DoNotEmbedVcsRepo fails if the embed returns, as a pointer (*vcs.Repo) or by value (vcs.Repo). Verified at the PR #573 merge 2a5bcadf. MISREADING: facts.Repo having no vcs methods does not mean the parent cannot reach them: they are on the parent's own *vcs.Repo embed.
