# Git objects live raw in the store's own SQLite `objects(hash, type, size, data)` table: a body by blob hash is one primary-key lookup (batchable with IN), no commit decode or tree walk; the index tables themselves hold no body

The git storer reads and writes objects in the store's SQLite file (store/git/storer.go: SELECT type,size,data FROM objects WHERE hash=?), table objects with PRIMARY KEY (hash, type) (migrate/repo/000001_schema.up.sql). So once a reader knows a version's blob hash, its content is `SELECT hash, data FROM objects WHERE type = 3 AND hash IN (...)` — one PK probe per blob, no go-git CommitObject/Tree decode. The text-less search already joins objects for every result.

Consequences: (1) the expensive part of reading a pinned version is resolving path@commit -> blob (go-git tree walks, ReadBlobHashAtCommit), never the blob read itself; anything keyed by (path, blob) — graph Fact nodes, facts rows, DERIVED_FROM targets — can read bodies cheaply. (2) The facts table has NO body column; titles/kind/type/refs are there only while that version's row exists.

What this does NOT mean: there is no public 'read blob by hash' API on the store services at dev 7db596b0 — callers go through ReadFact (tree walk). A prototype added FactQuery.BlobsByHash on branch proto/factset-streaming (unmerged).
