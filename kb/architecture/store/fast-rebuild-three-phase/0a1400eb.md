# Index rebuild is FOUR phases (0 commit log, 1 facts, 2 embeddings, 3 graph) — the 'three-phase' path slug is stale

**Rebuild runs FOUR numbered phases, not three.** This fact's path slug (`fast-rebuild-three-phase`) and its pre-2026-08 title both said THREE; the code at HEAD (internal/store/search_index.go, `func (si *searchIndex) Rebuild`) runs phases 0–3. Two in-code comments ("using three phases: facts, embeddings, graph", and "Three-phase rebuild" above rebuildFacts) are themselves stale and should not be trusted over the function body.

Each phase is wrapped in a single transaction (eliminates per-op fsync overhead — ~3000 individual fsyncs in the graph phase alone). Before phase 0, if an embedder is configured, `ensureFactsVec` runs so facts_vec exists at the active model's dimension — phase 1 can DELETE orphaned rows and fire the `facts_after_delete` trigger, which references facts_vec.

PHASE 0 (rebuildCommitLog): rewrites commit_log from git BEFORE facts, because fact indexing resolves each fact's source commit from commit_log. This is what makes `:rebuild` actually rebuild commit history (including author identity) instead of leaving stale rows a plain re-walk would skip.

PHASE 1 (rebuildFacts): the WHOLE phase runs in ONE transaction via beginTxIfNeeded. Mechanics: register knomit_parse_fact(blob BLOB)->JSON via ConnectHook (deterministic), populate a TEMP table from the go-git tree walk, then ONE bulk upsert with a CTE. CRITICAL: the facts upsert is INSERT ... ON CONFLICT(path, blob_hash) DO UPDATE — NOT INSERT OR REPLACE. facts are content-addressed by UNIQUE(path, blob_hash); ON CONFLICT refreshes parsed columns IN PLACE so the rowid is PRESERVED for unchanged blobs. This is load-bearing: INSERT OR REPLACE does DELETE+INSERT, minting a new rowid and firing facts_after_delete (which wipes the facts_vec row), so rebuildEmbeddings ('WHERE rowid NOT IN (SELECT rowid FROM facts_vec)') would re-embed the ENTIRE corpus on every rebuild. Phase 1 explicitly clears the rebuilt facts' fact_domains/fact_entities rows (scoped by `_rebuild_entries`, NOT a global wipe) before repopulating canonical/token derived state.

PHASE 2 (embeddings): ONNX inference runs OUTSIDE any transaction (`batcher.EmbedDocuments`, 32 per batch) into an in-memory slice; the finished vectors are then written in a SHORT tx. Load-bearing for concurrency (PR #82) — see kb/invariants/store/embed-outside-write-tx/8fe00fe9.md, which generalizes this to ALL inference.

PHASE 3 (graph): cursor over facts, single tx, then bump meta.graph_schema_version. Progress is reported once per embeddings batch via RebuildProgress(phase, done, total).

WHAT THIS DOES NOT MEAN:

1. **Do not infer from the path slug or from the in-code 'three phases' comments that commit_log is rebuilt elsewhere, lazily, or not at all.** Phase 0 is a real phase and its ordering before phase 1 is a correctness requirement, not an optimization.
2. There is NO `searchIndex.rebuilding` flag and NO `CachedClusterFacts` contention-avoidance path in the store. `searchIndex` carries exactly one atomic flag, `syncSuspended` (a different mechanism, for bulk Replay). The cluster_cache TABLE was dropped by migration 000013 and clustering moved in-process/scoped into internal/synthesize (PR #98); the surviving `[cluster_cache]` config-section name is a back-compat label, not storage.
3. "Rebuild holds no long lock because inference is outside the tx" does NOT mean Rebuild is non-blocking. Rebuild holds `lockBranch(branch)` for its entire duration, blocking same-branch writers AND store.Verify. The SQLite write lock and the branch lock are different locks; only the former was released.
4. `EmbedBatch` and `graphBuildSimilarityEdgesTx` were listed as entities on this fact but do NOT exist in the codebase — the batch entry point is `EmbedDocuments`. Do not search for them.
