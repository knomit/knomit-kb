# The abstraction axis is title-only embeddings in a code-managed vec0 table keyed by facts.id — content-addressing makes the cache watermark-incremental by construction

A second embedding axis alongside `facts_vec`: ONE title-only vector per fact VERSION, in a `vec0` table (`fact_titles_vec`) keyed by `facts.id`.

**The key, stated in full: `UNIQUE(path, blob_hash)`.** Both components. An edited fact is a NEW row with NO vector, so "rows lacking a vector" IS exactly the delta — the cache is watermark-incremental by construction, with no watermark column, no bookkeeping of its own, and nothing to migrate when the corpus changes shape. `LiveFactsMissingTitleVector` is the whole delta query.

**Code-managed, not migrated.** A `vec0` table fixes its dimension at CREATE and cannot be ALTERed, so like `facts_vec` it is created in code at the active model's dimension (`ensureFactTitlesVec`). Migration 000018 ships only the plain tables and the delete trigger.

**WHAT "CONTENT-ADDRESSED" DOES NOT MEAN HERE.**
- **Renames are NOT free.** `path` is part of the key, so moving a fact to a new path with byte-identical content mints a NEW `facts.id`, a new row with no title vector, and a full re-embed of that title. A bulk re-organisation of the ontology tree costs a re-embed of everything moved. Anyone reasoning "same content, so the vector is reused" has dropped `path` from the key.
- **Superseded versions are NOT self-cleaning.** The delete trigger fires on a `facts` row DELETE; while old versions persist, their vectors persist on the axis. This is load-bearing rather than cosmetic: it is exactly why `titleKNNOverfetch` exists — `TopTitleNeighbours` filters to live epistemic facts on one branch AFTER vec0 has closed its k window, so on a repo carrying many superseded revisions an un-overfetched query comes back short or empty. See `kb/gotchas/store/vec0/k-window-precedes-where/fbb0d36d.md`.
- **A missing vector is NOT an error.** During partial backfill it is the common case; `TopTitleNeighbours` returns nothing rather than failing.

**What it drifts with.** It shares `facts_vec`'s embedding identity, so an embedding-model change invalidates it and every cache derived from it — and an embedding-identity MATCH does not imply the table is structurally valid at the right width.

**EPISTEMIC-ONLY, and not by preference.** The axis covers epistemic facts alone. FORCED, not chosen: prune's decision path does not carry `Kind` through `mergedFact`, so a pragmatic fact reaching synthesis would be silently rewritten as epistemic. Lifting the restriction means fixing that first. The residual is that restatements among pragmatic facts remain unjudged by anything.
