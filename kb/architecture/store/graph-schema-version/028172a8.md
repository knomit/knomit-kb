# GraphSchemaVersion gates forced rebuilds; the persisted version is PER-BRANCH (graph_schema_version:<branch>), never global

searchIndex.GraphSchemaVersion constant (currently '5', defined in search_index.go) tracks the version of ALL forced-rebuild-on-upgrade DERIVED state — graph layout AND, despite the name, the SQLite-side derived index state (canonical fact_domains, fact_domain_tokens) AND the embedding vectors. BUMP THE CONSTANT when an indexing-logic change requires a forced reindex on existing deployments — new edge types, node identity changes, canonical/tokenised domain storage, etc.

PERSISTED PER BRANCH, in meta.graph_schema_version:<branch> (key built by schemaVersionKey), mirroring last_commit:<branch>. Rebuild bumps ONLY the branch it rebuilt. NeedsRebuild takes a branch: NeedsRebuild(ctx, branch). Migration 000016 carried the old global row onto every branch in `branches` and DROPPED the global key; a branch absent from that table has never been indexed, gets no row, and so reads stale.

Version history: v2 = DERIVED_FROM edges carry source_commit + target_commit. v3 = domain tags stored CANONICAL (NFC + case-fold + de-hyphenize) in fact_domains and tokenised into fact_domain_tokens; v2 DBs hold raw domains + an empty token table so domain search silently returns nothing until regenerated. v4 = facts_vec is code-managed (ensureFactsVec) at the active model's dimension rather than a static FLOAT[768] migration. v5 = the GraphQLite extension is gone; node/edge properties are TEXT in {node,edge}_props_text only.

A SECOND, version-independent rebuild trigger was added in v4: NeedsRebuild ALSO gates on embedding identity (meta.embed_model_id / meta.embed_dim). A model-id or dimension change invalidates every stored vector and forces a rebuild that recreates facts_vec empty and re-embeds the whole corpus — WITHOUT any GraphSchemaVersion bump. That half is deliberately still GLOBAL, and correctly so: facts_vec is corpus-wide (facts rows are shared; branch_facts is only the junction), so one branch's re-embed genuinely covers every branch. A branch that failed to rebuild still has no version row of its own, so it still reports stale.

Self-heal: repoBuilder.setupIndex asks NeedsRebuild ONCE PER BRANCH and records []healBranch{name, stale}; healIndexBranches full-Rebuilds the stale ones and incrementally SyncLocks the rest. Only the agent branch (index 0) is fatal, on both paths. NOTHING RE-ARMS A RETRY — a branch that failed simply never got its bump and reports stale again next boot, alone. setupIndex also drops an upstream whose git ref does not resolve (dropUnresolvableBranches) before scheduling work that cannot succeed; the agent branch is never dropped.

WHY PER-BRANCH — this is the load-bearing part. While the version was one global row, a partial multi-branch heal was UNREPRESENTABLE, forcing a choice between two broken options: (a) let a healthy branch's bump mark the failed branch current, masking it forever (the PR #70 bug); or (b) clear the global key on any partial heal (the PR #70 fix, IndexManager.MarkRebuildNeeded) — which turned a PERMANENT single-branch failure into an unbounded full-repo re-index on every boot, forever, while the repo still reported a healthy index (the PR #73 bug). The permanent case is real and reachable: a repo created locally (agent branch off "main") later pointed at a master-convention origin has a stored remotes.branch with no local ref, and its Rebuild fails at HeadCommit on every boot. Per-branch keys make the retry proportional and delete the dilemma. MarkRebuildNeeded NO LONGER EXISTS.

WHAT THIS DOES NOT MEAN:
- The constant is NOT '3' or '4'. It is '5' (search_index.go). Do not compare a change against an older value or revert it.
- The persisted version is NOT global. Do not read or write a bare `graph_schema_version` meta row — migration 000016 removed it, and reintroducing a global key reintroduces both bugs above.
- MarkRebuildNeeded is NOT on IndexManager. If you find yourself wanting it, the branch you want retried already retries itself.
- A version bump is NOT the only thing that forces a rebuild — an embedding model-id/dim change forces one too, with NO version change.
- 'GraphSchemaVersion' is NOT graph-only — it gates domain/token derived state AND, since v4, the facts_vec vector layout.
- "Non-fatal" and "retried aggressively" are NOT independent knobs. An upstream failure the heal declines to flag must not also trigger the most expensive recovery available; making those two decisions disagree is exactly what produced the PR #73 boot loop.
