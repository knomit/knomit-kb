# GraphSchemaVersion constant gates forced rebuilds on graph-shape changes

searchIndex.GraphSchemaVersion constant (currently '3', defined in search_index.go) tracks the version of ALL forced-rebuild-on-upgrade DERIVED state — graph layout AND, despite the name, the SQLite-side derived index state (canonical fact_domains, fact_domain_tokens). Persisted in meta.graph_schema_version (GLOBAL to the DB, not per-branch) after every successful Rebuild. BUMP THE CONSTANT when an indexing-logic change requires a forced reindex on existing deployments — new edge types, node identity changes, or (v2->v3) storing canonical/tokenised domains where older DBs hold raw values + an empty token table. Self-heal path: searchIndex.NeedsRebuild(ctx) reports stale (persisted != constant, or missing row); repoBuilder.setupIndex checks it ONCE at startup and full-Rebuilds each maintained branch instead of Sync (a plain Sync no-ops when last==HEAD and would leave domain search silently broken after a v2->v3 upgrade). The heal is cheap: Rebuild preserves facts rowids (ON CONFLICT DO UPDATE), so existing embeddings are reused — no re-embedding. searchIndex.Sync itself only WARNS on mismatch (it cannot safely escalate to a full rebuild of every branch from a single-branch call); the rebuild is driven by setupIndex. Version 2 = DERIVED_FROM edges carry source_commit + target_commit; FactVersion subsystem retired. No SQL migration needed for graph-shape changes — the version bump triggers the rebuild which reconstructs derived state from facts + commit_log (git is the source of truth).
