# Sub-indices reach UP to repoHandler; siblings NEVER reach sideways

repoHandler owns shared backend state: db, gits (*storegit.Storer), repo (*gogit.Repository), signer (ssh.Signer for commit signing), embedder, onCommit (external observer), branchMu (per-branch RWMutex map), cache (branch name→id cache), im (IndexManager back-ref), name, configMu. Sub-indices — factIndex, searchIndex, remoteIndex, pipelineIndex, toolIndex, plus the four read-side query sub-services carved out of searchIndex in P1.3 (factQuery, graphStore, historyQuery, methodologyMatcher) — each hold a back-reference `rh *repoHandler` and reach UP for git/commit primitives. Sibling subsystems NEVER reach sideways through each other. Commit signature helpers (authorSig, committerSig) and notifyCommit live on repoHandler precisely because they're shared between factIndex writes and remoteIndex.Sync merge commits. Service is a thin entry point exposing each sub-index via an accessor: Facts(), Search(), FactQuery(), GraphStore(), HistoryQuery(), Methodology(), IndexManager(), Remote(), Pipeline(), ToolSession(), Branches() — Branches() returns *repoHandler directly because repoHandler satisfies BranchIndex.

Search() returns *searchFacade, a stateless composite embedding pointers to the four query sub-services. It satisfies the SearchIndex composite purely by method promotion and holds no state of its own, so it is NOT an exception to the up-not-sideways rule: every call it promotes still reaches UP through that sub-service's own rh. searchIndex retains the index lifecycle (IndexManager) plus the write/rebuild/graph-write path, and no longer implements SearchIndex. Compile-time guards for all five types live in query_services.go.
