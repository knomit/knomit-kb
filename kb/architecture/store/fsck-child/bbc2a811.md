# store/fsck holds the integrity checker as fsck.Checker over the shared vcs.Repo and the facts and index sub-indices; Service.integrity builds one per call, the Service methods and tamper helpers stay in service_fsck.go, and fsck_seam.go re-exports the report types

Since PR 11c of the internal/ hierarchy stack (branch refactor/hier-11c-fsck, stacked on hier-11b gitserve and hier-11 sync, whose package is internal/store/remotesync), the store's integrity checker is the package internal/store/fsck (integrity.go, doc.go). verify.go of package store was renamed to fsck/integrity.go; the receiver type `integrity{rh, fi, si}` became the exported fsck.Checker, built by fsck.NewChecker(rh *vcs.Repo, fi *facts.Index, si *index.Index). It is NOT under internal/store/internal/, and it is NOT the verify child (internal/store/verify is the judge of commits; fsck is the Service-level report about the store's own consistency). It imports vcs, facts and index, and TestLayers lists those three as same-layer edges (store/fsck -> store/facts, store/index, store/internal/vcs); nothing else in the store imports it but the facade.

WHAT IS CHECKED (unchanged): git reachability, the commit log and its parents, the branches table, facts coherence, embeddings coverage and the embedding model IDENTITY, the derived tables, graph coherence, database soundness, the schema version, fact format (Deep), the generated-refs residue (PruneGeneratedRefs is the opt-in destructive half), and the orphan-objects warning (the unreachable rows a signed write or a refused batch can leave, issue 554; a warning, 'cost space only'). Verify is read-only and a snapshot: it takes the read lock of every branch it checks up front and holds them all for the whole run, so it blocks writers on those branches; that locking is documented in the package doc (fsck/doc.go, under "Verify"; the header comment moved there from above the package clause of integrity.go, where a blank line had detached it from the clause) and was moved with the code, not changed.

THE SEAM: internal/store/fsck_seam.go re-exports IntegrityIssue, IntegrityReport, PruneResult, Severity, VerifyOpts and the Severity*/Category* constants as aliases and consts. Service.Verify and Service.PruneGeneratedRefs (service_fsck.go) are one-line delegations to `s.integrity()`, which is `fsck.NewChecker(s.rh.Repo, s.fi, s.si)`. repoHandler embeds no fsck handle. The test-only tamper helpers (DeleteObjectForTest, RawDBForTest, RawWriteForTest, deleteCommitLogRowForTest, ...) stayed in service_fsck.go because they reach the Service's handles.

TESTS: the integrity tests drive a full Service and stayed in the parent. One pure unit test moved by name, TestVerify_ErrorsSortAheadOfWarningsSoTruncationCannotHideThem (it calls the unexported sortIssues), into fsck/integrity_sort_test.go; the store's top-level test count went 918 to 917 with 1 in fsck.

CONSEQUENCE: a new integrity check goes in fsck; if it needs a lock or a table another child owns, it reads it through the vcs handle or an exported accessor, never by importing a child above it (nothing is above it). MISREADING: 'verify' in this repository names two things: the judge (store/verify, the acceptance gate for commits) and this report (Service.Verify, `knomit verify`); a path or a guard named verify.go before hier-11c means this file.
