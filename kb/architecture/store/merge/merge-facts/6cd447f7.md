# A `conflicts` policy runs on the REFUSE path: the conflict set is detected, each path gets a Resolution (Body = merged bytes, Side = the consensus side, a retraction, or the site's own side-pick), and the refusing walk applies them. A key set to off keeps the site's side-pick: LocalWins on the peer sync, Refuse on the host, agent-wins on the rebase replay

Since conflict-merge PR 2 the `conflicts` setting is an object {facts, state}. It travels as a ConflictStrategy VALUE, `conflicts:<facts>/<state>` (e.g. `conflicts:merge/consensus`), built by `conflictsPolicy.strategy()` and parsed back by `conflictsPolicyOf`. No internal signature grew a parameter, and the merge commit's subject names the value. PR 1's `StrategyMergeFacts`/`StrategyMergeFactsUpstream` are gone. `conflictsStrategy(branch)` returns ok=false only when BOTH keys read off; the site then runs its own side-pick, as always.

`factMergeResolutions` (internal/store/conflict_merge.go) runs `detectConflicts` (the refusing walk). Then, for each conflicting path, in this order:
- src and dst hold the same bytes: ResolveDst, silently.
- not a fact path (`!rh.isFactPath`: outside the ontology root, or private): the STATE rule, reason=not-a-fact.
- `facts: consensus`: the consensus side's WHOLE version, as a Side. It is unparsed, and it applies to an edit, a deletion or an addition alike, so here a retraction does NOT automatically win. Recorded as Knomit-Conflict strategy=consensus.
- `facts: off`: the site's own side-pick, with no reason.
- `merge` / `merge:consensus`, one side deleted and the other edited: THE RETRACTION WINS (ruling 2). It is applied as a Side, because a Resolution Body can only SET a path, never delete it.
- otherwise fact.MergeVersions. ok gives Resolution{Body} and a Knomit-Merge strategy=merge|merge_consensus line; not ok gives the STATE rule with rec.Reason (unparsable, kind-mismatch, lossy).

THE STATE RULE: `state: consensus` takes the consensus side (Knomit-Conflict kept=<side> strategy=consensus reason=…); `state: off` takes the site's own side-pick.

WHERE A SITE'S CONSENSUS SIDE AND SIDE-PICK COME FROM:
- `mergeOpts.factConsensus`/`factFallback`. The zero value is the peer sync's: consensus = src (the consensus branch is merged INTO the agent branch), side-pick LocalWins. A LocalWins side-pick on a dual-add takes src, exactly as the LocalWins walk always overwrote.
- The host (MergePushed with no side, and MergeConsensus, via hostConflictStrategy) sets consensus = dst (its own agent branch, which the consensus branch follows) and side-pick Refuse. A path a key set to off leaves therefore refuses the WHOLE merge (atomic), naming only that path.
- The rebase replay (`replayCommit`) has an EXPLICIT arm, `conflictsPolicyOf(strategy)`, with consensus = dst (onto) and side-pick RemoteWins (the agent's commit is src). Without it the `default:` arm would silently map the strategy to agent-wins.

MISREADINGS:
- 'a conflicts setting resolves everything' is wrong: on the host whatever a key set to off leaves is refused as before. With `facts: merge` and `state: off`, a single non-fact conflict refuses the fact merge too.
- 'MergePushed always settles when conflicts is set' is wrong: an explicit `side` (the human's whole-set choice) is never overridden.
- 'consensus side = the host' is wrong at the peer: there it is the incoming consensus branch (src). Both readings name the side that is on, or will reach, the consensus branch.
