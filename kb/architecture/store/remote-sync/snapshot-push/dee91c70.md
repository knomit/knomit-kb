# remoteIndex.Push is a SNAPSHOT push: a per-branch push mutex for the whole push, the write lock only for the tip read, then the tip pushed BY HASH (+<sha>:refs/heads/<branch>) — writes never wait on the network, and a commit made mid-push goes out on the NEXT push

Push (internal/store/remote_sync.go) takes rh.lockPush(branch) (a per-branch sync.Mutex in repoHandler.pushMu, NOT the write lock) for the whole push, network included. Under rh.lockBranch(branch) it reads the branch tip S and releases the lock at once. It compares S with refs/remotes/origin/<branch> (equal → Pushed:false, no network), checks that S's commit object resolves, then pushes the refspec +<S>:refs/heads/<branch>. go-git sets the tracking ref to the pushed hash (the command's New) through the configured fetch spec, so after a push the tracking ref is S, not the current local tip.

Consequences: (1) a fact write on the branch waits at most for one ref read, never for PushContext — a hanging origin no longer stalls writes for network_timeout (this replaces the old gotcha that Push held the write lock across the network); (2) a commit landing between the snapshot and the network is NOT in this push: the next Push sees local tip != tracking ref and sends it; (3) pushes from the three callers (sync loop, fleet register/unregister, create-time push) are serialized by pushMu, so one push's snapshot is taken only after the previous push finished.

What pushMu does NOT mean: it does not guarantee the origin never applies an older tip after a newer one. A push that hits network_timeout releases pushMu while the server may still apply it; against a knomit host the guard is the host's compare-and-set on the advertised old value (receivePack.register refuses with 'moved since it was advertised'). That is unchanged from before, when the write lock was also released on timeout.

Test seam: storeHooks.afterSnapshot(branch, snap) runs after the snapshot and before any network; tests park a push there (remote_push_snapshot_test.go P1-P6).

UPDATE (PR #518, merge 537f2019): TWO MORE PUSHES TAKE A PUSH LOCK, and Push is no longer the only one that writes a ref. (1) PublishUpstream(from) pushes <tip of from>:refs/heads/<consensus branch> WITHOUT force (no '+') under the push lock of the CONSENSUS branch, reading from's tip under from's branch lock and releasing it, the same snapshot shape as Push; it is the one push that writes a consensus branch, called only for the fleet repository by the root holder; a main on the origin that is not an ancestor is refused by the origin as an ordinary push error. Push's doc names it as the exception to 'Push does NOT push main'. (2) RetractPushedBranch deletes the agent branch on the origin under the AGENT branch's push lock (kb/architecture/store/remote-sync/retract-pushed-branch). Consequence for 'only the own agent branch is ever pushed' (kb/architecture/fleet/guide/sync/7f2abf48.md): that holds for Push and for the sync loop; the fleet master's PublishUpstream is the stated exception. CORRECTION to the tracking-ref sentence above: refs/remotes/origin/<agent branch> is set by a successful push AND by every fetch (the configured fetch refspec), so 'the tracking ref' is the last tip this instance saw, which matters for anything that leases on it.

UPDATE (PR #524, verified at merge commit 9db8c106): remoteIndex.Push still never pushes main. The one writer of the origin's main is remoteIndex.PublishUpstream (added by #518, used by fleet create, and since #524 by the fleet master's every round): it pushes the tip of the local agent branch to the origin's MAIN WITHOUT force (a plain refspec, no '+'); a non-fast-forward is an ordinary error, recorded on the push status row by RemoteIndex.RecordPushError (PublishUpstream records nothing itself). The remote index also has SyncWithPeers (Sync plus the agent/* refspec for that fetch, pruning within it) and PeerTips (the fetched member tips) for the master's round. Misreading: 'the sync loop never advances the origin's main' is false for the fleet master.
