# meta.last_commit:<branch> is the store's only record of which branches the index actually maintains — graph_schema_version:<branch> is NOT, because migration 000016 backfilled it onto every known branch

# Which branches does the index maintain? Ask meta.last_commit, not graph_schema_version

The index writes `meta.last_commit:<branch>` when it syncs a branch, so the row exists exactly for branches it has actually indexed. Nothing else in the repo database records that set: `repoBuilder.setupIndex` computes it (agentBranch + upstreamMain) but does not persist it, the `branches` table records branches the store KNOWS about (a fetch can create a row for a branch that is never indexed), and `refs/heads/*` is wider still.

**The trap:** `meta.graph_schema_version:<branch>` looks like the same signal and is not. Migration 000016 carried the old GLOBAL schema-version row onto every branch known at the time, so a branch that has never been indexed can still have a `graph_schema_version` row.

**Measured on a live home, 2026-08-12** (repo `core`): branch `agent/Alexs-MacBook-Air-6.local-60def18b`, another machine's agent branch arriving by fetch, has a `graph_schema_version:` row and NO `last_commit:` row. It is unindexed — 1366 of its commits have no `branch_commits` rows. The three branches with `last_commit:` rows (`main`, and two local `agent/*`) are exactly the three that verify clean.

**Consequence for consumers:** to ask "is this branch indexed?", test for `meta.last_commit:<branch>`. Testing `graph_schema_version` instead will report unindexed branches as indexed, which for Verify means demanding SQLite/git parity for branches nothing ever populated.
