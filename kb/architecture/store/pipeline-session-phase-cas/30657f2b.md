# pipeline_sessions has phase column with CAS-based transitions

pipeline_sessions has independent columns: status (lifecycle: active|completed|abandoned), phase (workflow: work|reflect|done), and scoped (INTEGER, 1 when the session was started with a scope filter). AdvancePipelineSessionPhase(ctx, id, from, to) does an atomic UPDATE ... WHERE id=? AND phase=? returning (rowsAffected==1, nil). The CAS is what gives idempotent enqueue WITHOUT a separate dedup query: when two continuations race after the last work item is answered, exactly one wins the work->reflect transition and inserts the single reflect item; the other re-fetches and finds itself already in reflect phase. This is load-bearing once reflect has side effects: once-per-session enqueue prevents duplicate methodology proposals.

The session DB is deleted and recreated fresh from session_schema.sql on every Service.Open, so schema changes here are plain edits — NO migration (unlike the main facts DB).

WHAT THIS DOES NOT MEAN: it does NOT mean pipeline_sessions persists an effort column. Effort persistence was REMOVED (commit 6fb6a79 'drop dead session effort persistence'); pipeline_sessions has scoped, NOT effort (session_schema.sql). There is no CreatePipelineSessionWithEffort function. The discovery-dial effort is now an in-memory field on the synthesize Reviewer (NewReviewerWithEffort / Reviewer.effort in internal/synthesize/review.go) and is NOT recovered from the session row on ContinueSession.
