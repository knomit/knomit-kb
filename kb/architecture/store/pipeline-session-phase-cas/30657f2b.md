# pipeline_sessions has phase column with CAS-based transitions

pipeline_sessions has independent columns: status (lifecycle: active|completed|abandoned), phase (workflow: work|reflect|done), scoped (1 when the session was started with a scope filter), and, since PR #291, start_key (what a start must match to resume it), planning (1 until the start has rendered its first item) and advancing (1 while a won phase advance's hook runs). pipeline_work_items gained applying (1 from a claim until its apply returns).

AdvancePipelineSessionPhase(ctx, id, from, to) is ONE guarded UPDATE: it moves phase from→to and sets advancing = 1, but only WHERE id = ? AND status = 'active' AND phase = from AND advancing = 0 AND no work item of the session is unanswered or applying. It returns rowsAffected == 1. The CAS is what gives idempotent enqueue WITHOUT a separate dedup query. When two continuations race after the last work item is answered, exactly one wins the work→reflect transition and inserts the single reflect item; the other finds itself refused. The advancing mark, cleared when OnPhaseAdvance returns (and by a deferred call on a panic), stops the loser advancing reflect→done or completing the session before the reflect item exists. This is load-bearing once reflect has side effects: once-per-session enqueue prevents duplicate methodology proposals, and the guard keeps it from landing in a completed session.

The session DB is deleted and recreated fresh from session_schema.sql on every Service.Open, so schema changes here are plain edits with NO migration (unlike the main facts DB).

WHAT THIS DOES NOT MEAN: there is no effort column. Effort persistence was REMOVED (commit 6fb6a79), and there is no CreatePipelineSessionWithEffort. The discovery-dial effort is an in-memory field on the per-call Pipeline and is NOT recovered from the row on a continue. start_key does encode the effort, but only so a later START can compare it and decide whether to resume; nothing reads effort back from it to drive a session.
