# pipeline_sessions has phase column with CAS-based transitions

pipeline_sessions has independent columns: `status` (lifecycle: active|completed|abandoned), `phase` (workflow: work|reflect|done), and `effort` (discovery dial: normal|medium|high). AdvancePipelineSessionPhase(ctx, id, from, to) does an atomic UPDATE ... WHERE id=? AND phase=? returning (rowsAffected==1, nil). The CAS is what gives idempotent enqueue WITHOUT a separate dedup query: when two continuations race after the last work item is answered, exactly one wins the work->reflect transition and inserts the single reflect item; the other re-fetches and finds itself already in reflect phase. This is load-bearing once reflect has side effects (per reflect-response-schema design): once-per-session enqueue prevents duplicate methodology proposals.

The `effort` column (Plan 03) is set once at creation via CreatePipelineSessionWithEffort (empty -> 'normal'); it persists the discovery dial so a later ContinueSession recovers it without re-asking the caller. NOTE: the session DB is deleted and recreated fresh from session_schema.sql on every Service.Open, so adding this column was a plain schema edit — NO migration (unlike the main facts DB). See synthesize/discovery-integration.
