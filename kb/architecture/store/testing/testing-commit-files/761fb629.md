# store.TestingCommitFiles builds the commit's trees in ONE pass (testingTree): each blob and changed tree is written once. The per-path buildTree that the write path uses rewrites every tree on the path per file, about 5 tree objects per file, which is fine for a handful of files and ruinous for thousands

buildTree/upsertEntry (store/plumbing.go) applies ONE path: it re-encodes and stores every tree from the leaf's directory up to the root. Applying N paths one by one therefore writes roughly depth × N tree objects. For TestDispatch_Tx1Bounded's 12,000-file advance (kb/tasks/m/NNN/NNNNN.md) that was about 60,000 loose tree objects plus 12,000 blobs. It took 1.65 s locally and most of the test's 15.3 s on the Windows runner (dev run 37854454646).

Since #445 (merged a6ef5739), TestingCommitFiles groups the batch into a directory tree (testingDir) and writes each blob and each changed tree once, with entries sorted by object.TreeEntrySorter. Untouched entries of the parent tree are kept. A batch path replaces an entry of the same name the way buildTree does: file over directory, or directory over file. A path that is both a file and a directory INSIDE one batch is refused ('both a file and a directory'); the old helper let the later path win. Local commit time for 12,000 files: 0.14 s.

Guard: TestTestingCommitFiles_TreeMatchesPerPathBuild (internal/store) asserts that the root tree hash equals the per-path build over the same parent. Its fixture covers kept entries, an existing directory, new nested directories and a replaced file. Sabotages caught: dropping the parent's untouched entries; writing a sub-tree with the regular-file mode. The reviewer found one gap: its fixture has no name pair whose git tree order differs from plain name order (a directory x beside a file x.md). So a plain sort.Strings would survive the test, although the code uses the correct sorter.

Scope: test-only by contract (it panics outside a test binary). The production write path (batchWrite, WriteFact) still applies paths one by one. That is fine for the few files of a normal commit, and would be the same cost problem for a very large batch write.

A faster commit has a side effect: an observer notification armed by an earlier write can then fire after the advance and index all of it. See trap 2 of kb/gotchas/repos/triggers/testing/88a51b21.md.
