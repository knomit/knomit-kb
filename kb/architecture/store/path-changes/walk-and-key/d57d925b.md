# PathHistory is a max-heap walk over path_change_links from the entry live at the anchor; the key order_at = max(own author date, keys of what it was edited from), then gen, makes every change sort strictly above its ancestors, so the heap yields the whole history in key order and the frontier is a complete keyset cursor

Read path, per page:
1. HEAD: the entry live at the anchor (liveAtAnchor). Fast path: look up the anchor's blob for the path (case-insensitive tree walk); if exactly ONE on-branch entry introduced that blob, that is it. Otherwise nearestChangeSQL walks the anchor's first-parent line and STOPS at the first on-branch commit with a path_changes row, returning its resolves_to (a carry resolves to the write it delivered).
2. WALK: push the start set into a max-heap on (order_at desc, gen desc, commit asc); pop, emit, and push each popped entry's link targets (from_commit). Stop at `limit`; the heap's contents are the next keyset position.

Why the heap yields exact key order: a change's key is strictly above every change it was edited from (order_at >= theirs and gen > theirs). A node is pushed only when a child is popped, and every child outranks it, so all its children are popped before it. The same argument shows that a node carried in the frontier can never be re-pushed on a later page, so the frontier alone is a complete, duplicate-free position.

Why the unique-blob fast path is sound (also used at derivation in liveEntry): whoever introduced the blob found at X is in X's ancestry. If only one entry ever introduced that blob, it is that one; a second candidate (a revert, or a rebase replay of the same content) forces the first-parent walk. Branch-scoped at read time: an off-branch anchor skips the fast path entirely.

Ordering guarantee, and its limit: revisions[0] is always the live content, and a change is never listed below one it descends from, including a replay whose author date is older than its parent's (TestPathHistory_SkewedDateNeverBelowItsAncestor fails under raw-date order). On any history without concurrent edits this equals git --date-order. Across the two sides of a composing merge, a clamped (date-lifted) change stays next to its descendant rather than being re-sorted by its own date.

NAMED MISREADING: "order_at is the change's date". It is a sort key. The displayed date is author_at, the change's own author date.
