# The change live at commit X is the nearest path_changes row on X's first-parent line, found with first-parent JUMP POINTERS (commit_fp: depth + packed ups) in O(log depth) lookups; PathHistory is then a max-heap walk over path_change_links whose key (order_at, gen) puts every change strictly above its ancestors, so the frontier is a complete keyset cursor

LIVE CHANGE (vcs.LiveChange; liveChange before it was exported): the change of path P live at commit X is the nearest commit on X's first-parent line (X included) with a path_changes row for P. For an entry that is the row itself; for a carry (a PR merge) it is its resolves_to.
- Candidate rows for P are read newest first by first-parent depth, in keyset pages of 16.
- Each candidate R is tested with onFirstParentLine: jump X down depth(X)-depth(R) steps via commit_fp.ups and compare with R. ups packs the 20-byte hashes of the commits 2^k first-parent steps below, one row per commit (jumpFrom).
- That is O(log depth) indexed lookups per candidate, and the first candidate usually wins.
- No recursive walk, so at 10,000 commits the cost does not depend on how far back the last change is (review N5).
- Branch scoping at read time: candidate rows ALWAYS join branch_commits (round 4), so rows of commits on no branch, which are never garbage-collected, are not even scanned. Derivation's lookups are unscoped by design, because derivation is git-only.

Used by:
- derivation: the edited-from link at each parent
- PathHistory's first page: the head
- LiveRevision: ONLY explain's root commit

LiveRevision is pinned equal to RevisionsBefore(anchor, 1) at every commit (TestLiveRevision_EqualsRevisionsBefore), because path_changes has a row for every commit_log add/modify row of a .md path; a case-only rename is a carry. Resolution (resolveActiveCommitForPath, OutgoingAtCommit, the web as_of date) stayed on the first-parent walk in #347. PR #698 moved it onto these lookups, together with RevisionsBefore and FactLiveAtCommit, through vcs.LineEvents: commit_log candidates checked against the commit_fp jumps, with a commit_parents walk as the fallback.

WALK: push the live change into a max-heap on (order_at desc, gen desc, commit asc); pop, emit, and push each popped entry's link targets. Stop at `limit`; the heap's contents are the next keyset position. Every change's key is strictly above what it was edited from (order_at >= theirs, gen > theirs). So all of a node's children pop before it, the heap yields exact key order, and a node carried in the frontier is never re-pushed later.

ERRORS: on a continuation, ErrHistoryChanged when the anchor left the branch, or when a frontier change or a link target is not visible on it. Each of the two checks has a test that fails without it, in store and in MCP. A first page at an indexed but underived anchor is an error ("never derived"), never an empty history. Since round 6 the one legitimate way to reach it is a branch the open-time pass SKIPPED because its ref failed to resolve: nothing is served for that branch, by design (TestOpenHistory_UnresolvableBranchIsSkippedAndLogged).

ORDER guarantee and its limit: revisions[0] is always the live content, and a change is never listed below one it descends from. It equals git --date-order on histories without concurrent edits. Across the two sides of a composing merge, a date-lifted change stays next to its descendant.

MEASURED 2026-09-29, 10,000-commit repo with a revert (BenchmarkPathHistoryDeep):
- history first page at the tip 0.35 ms; cursor page 0.15 ms
- first page at an anchor 2,000 commits past the last change 0.23 ms
- LiveRevision 0.08 ms, against RevisionsBefore's walk at 15.5 ms
- explain cursor page 0.23 ms. The first call is dominated by OutgoingAtCommit's first-parent walk (about 15 ms at 10k commits) now that the resolver fast path is out of #347; its history part is sub-millisecond.

NAMED MISREADING: "order_at is the change's date". It is a sort key; the displayed date is author_at.

BOUNDARIES AND DAMAGE (round 5): below a missing parent commit (a history boundary) the child has depth 0 and no jump pointers. Neither liveChange nor LiveRevision finds anything below it, while RevisionsBefore (which walks commit_parents rows) still can. TestLiveRevision_EqualsRevisionsBeforeEdgeCases pins agreement above a boundary and the empty answer below it, alongside a composing merge and a lower -> Upper rename. A content_unavailable revision is still an entry in the walk; loadChange carries the flag into FactRevision.ContentUnavailable.

RE-MEASURED 2026-09-30 (round 6, 200 iterations): first page at the tip 0.36 ms; cursor page 0.15 ms; old anchor 0.26 ms; LiveRevision 0.08 ms against RevisionsBefore's 15.9 ms. The read path is unchanged by round 6: only derivation timing (at open) and commit_log indexing moved.

RE-DERIVATION CONSISTENCY (PR #698 review, B1). The jumps are correct only while every commit_fp row's depth and pointers agree with the rows of its first-parent ancestors. Degradation propagates only at the moment a commit is applied. So an in-place re-derivation (rederiveDegraded, run by :rebuild) that turned a degraded=1 commit A into a boundary (its first parent's commit object now missing: depth 0, no ups) left A's descendants with their old depths and degraded=0. liveChange, LiveRevision and LineEvents then trusted those descendants' jumps and silently skipped A's change, answering a superseded one. This was reproduced on dev for LiveRevision.

The fix is deriver.wouldCutDerivedLine: re-derivation never moves a row from degraded<2 to a structural row. Such a row keeps its depth, pointers and structure. Since PR #699 its content is refreshed once the blob is back (blob and diff against the stored from_blob, content_unavailable cleared, and degraded 0 when nothing is missing). With that rule, an in-place re-derivation can only do one of two things: keep a row's depth and pointers, or replace a degraded=2 row. Every descendant of a degraded=2 row is itself degraded=2 and is re-derived after it in the same parents-first pass.

RebuildCommitLog now walks git before it writes anything. It is still batched rather than one transaction, so a failure part-way leaves a consistent, partly repaired store.

LineEvents also guards on contradictions: a jump that lands on a node whose depth is not its distance from the start, or that runs out of pointers, reports incomplete, and LineEvents falls back to the walk. liveChange and LiveRevision have no such guard and no walk to fall back on. They depend on the re-derivation rule alone.

DOES NOT MEAN: degraded=1 rows can never change. Their content rows do change, by re-derivation, once the objects are back and the parents are present. Only their depth and pointers never move under derived descendants.

SNAPSHOT CONNECTION (PR #699): LineEvents holds its read transaction on one pooled *sql.Conn. If the ROLLBACK that ends it fails, the connection is marked bad (Conn.Raw returning driver.ErrBadConn). database/sql then closes it and never returns a connection still inside a transaction to the pool. TestLineEvents_FailedRollbackDiscardsTheConnection checks this.
