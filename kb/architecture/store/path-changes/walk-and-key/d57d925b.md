# The change live at commit X is the nearest path_changes row on X's first-parent line, found with first-parent JUMP POINTERS (commit_fp: depth + packed ups) in O(log depth) lookups; PathHistory is then a max-heap walk over path_change_links whose key (order_at, gen) puts every change strictly above its ancestors, so the frontier is a complete keyset cursor

LIVE CHANGE (liveChange): the change of path P live at commit X is the nearest commit on X's first-parent line (X included) with a path_changes row for P. For an entry that is the row itself; for a carry (a PR merge) it is its resolves_to.
- Candidate rows for P are read newest first by first-parent depth, in keyset pages of 16.
- Each candidate R is tested with onFirstParentLine: jump X down depth(X)-depth(R) steps via commit_fp.ups and compare with R. ups packs the 20-byte hashes of the commits 2^k first-parent steps below, one row per commit (jumpFrom).
- That is O(log depth) indexed lookups per candidate, and the first candidate usually wins.
- No recursive walk, so at 10,000 commits the cost does not depend on how far back the last change is (review N5).
- Branch scoping at read time: candidate rows ALWAYS join branch_commits (round 4), so rows of commits on no branch, which are never garbage-collected, are not even scanned. Derivation's lookups are unscoped by design, because derivation is git-only.

Used by:
- derivation: the edited-from link at each parent
- PathHistory's first page: the head
- LiveRevision: ONLY explain's root commit

LiveRevision is pinned equal to RevisionsBefore(anchor, 1) at every commit (TestLiveRevision_EqualsRevisionsBefore), because path_changes has a row for every commit_log add/modify row of a .md path; a case-only rename is a carry. Resolution (resolveActiveCommitForPath, OutgoingAtCommit, the web as_of date) stays on the first-parent walk in #347. Moving it onto these lookups is an APPROVED FOLLOW-UP (see the decision fact), to start after #347 merges and only after equivalence is proven on degraded databases.

WALK: push the live change into a max-heap on (order_at desc, gen desc, commit asc); pop, emit, and push each popped entry's link targets. Stop at `limit`; the heap's contents are the next keyset position. Every change's key is strictly above what it was edited from (order_at >= theirs, gen > theirs). So all of a node's children pop before it, the heap yields exact key order, and a node carried in the frontier is never re-pushed later.

ERRORS: on a continuation, ErrHistoryChanged when the anchor left the branch, or when a frontier change or a link target is not visible on it. Each of the two checks has a test that fails without it, in store and in MCP. A first page at an indexed but underived anchor is an error, never an empty history.

ORDER guarantee and its limit: revisions[0] is always the live content, and a change is never listed below one it descends from. It equals git --date-order on histories without concurrent edits. Across the two sides of a composing merge, a date-lifted change stays next to its descendant.

MEASURED 2026-09-29, 10,000-commit repo with a revert (BenchmarkPathHistoryDeep):
- history first page at the tip 0.35 ms; cursor page 0.15 ms
- first page at an anchor 2,000 commits past the last change 0.23 ms
- LiveRevision 0.08 ms, against RevisionsBefore's walk at 15.5 ms
- explain cursor page 0.23 ms. The first call is dominated by OutgoingAtCommit's first-parent walk (about 15 ms at 10k commits) now that the resolver fast path is out of #347; its history part is sub-millisecond.

NAMED MISREADING: "order_at is the change's date". It is a sort key; the displayed date is author_at.

BOUNDARIES AND DAMAGE (round 5): below a missing parent commit (a history boundary) the child has depth 0 and no jump pointers. Neither liveChange nor LiveRevision finds anything below it, while RevisionsBefore (which walks commit_parents rows) still can. TestLiveRevision_EqualsRevisionsBeforeEdgeCases pins agreement above a boundary and the empty answer below it, alongside a composing merge and a lower -> Upper rename. A content_unavailable revision is still an entry in the walk; loadChange carries the flag into FactRevision.ContentUnavailable.
