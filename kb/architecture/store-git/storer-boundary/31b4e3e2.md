# The storer boundary: every SQL statement lives in storegit.Storer, everything above it speaks only go-git's storage.Storer — so readers are portable across backends and any feature needing a table outside that contract must probe for it

One type owns every SQL statement and exposes itself upward only through a third-party storage interface, so code above the boundary is portable across any backend that satisfies the interface, and any feature that needs a table beyond the interface's contract must be gated by a capability probe because not every storer behind the interface carries it.

How it is instantiated here:
- `*storegit.Storer` implements go-git's full `storage.Storer` composite over a shared `*sql.DB`, with compile-time assertions per sub-interface; the objects, refs and kv tables back it, and the kv table alone serves ConfigStorer, IndexStorer, ShallowStorer and ModuleStorer under namespaced keys (`config`, `index`, `index:modtime`, `shallow`, `module:<name>`). Adding a new go-git interface assertion without backing tables is the anti-pattern: go-git will start calling it and the missing implementation panics; an un-namespaced kv key is the other.
- `git.Store` has NO `*sql.DB` field. Commit-index SQL is owned by the storer as named methods (CommitLogAvailable, CommitLogSync, CommitLogQuery, CommitLogFileCounts, CommitLogActivity); the git package keeps only the go-git walk that feeds an iterator into CommitLogSync. `CommitLogWalkChanged` does not exist, and `CommitLogActivity` takes `branchID` first — activity is branch-scoped.
- Because the interface is the whole contract, `internal/okfsource` reads a KB through a storer and nothing else — no SQLite, no Service, no repo instance — which is what lets the OKF exporter run against a plain `git clone` or an in-memory fixture. Any new read the exporter needs must be expressible against a storer; reaching back into internal/store silently re-couples the tool to a running server.
- Not every storer carries the full schema: `Storer.Module(name)` returns a per-submodule storer over a SEPARATE `:memory:` SQLite with an inline objects+refs+kv schema only, so module storers cannot call CommitLogSync and have no facts, branches or index; memory storers built module-style are in the same position. That is why commit-log work is gated by `CommitLogAvailable()`, which probes sqlite_master once per storer lifetime and caches the answer in an atomic — probing sqlite_master in a hot path is the anti-pattern.

WHAT THIS DOES NOT MEAN: the boundary says where SQL lives, not that the storer is thin — per-method design (one round-trip returning five aggregates, index-accelerated queries) is still the storer's concern, and the module storer's isolation exists for go-git interface compliance, not because users have git submodules.
