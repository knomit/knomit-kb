# Create from a template is reachable from the wizard's ontology step ("From a template": one list grouped by repo, repo name and short commit per row, empty state pointing to subscribing to a playbooks repo) and from `kb repo create <new> --template <repo>/<name> [server]`; the wire body sends the template ALONE

Wizard (web/src): the ontology step has two sources, "An ontology" (the existing editor, now OntologyDocument) and "From a template" (TemplatePicker over GET /api/v1/templates). State keeps `useTemplate` and `template` apart from `preset`/`yaml`, so switching back and forth keeps both picks; `createBodyFor` reads ONLY the side `useTemplate` names: local → `{mode: 'template', template}`, a remote branch with no ontology → `{mode: 'initialize', template, origin}`, never a preset or yaml beside it (the backend refuses two sources). The step is valid only while the picked (repo, name) is still in the fetched list. StepReview names the template instead of the ontology.

CLI (tools/bridge/repo.go): `kb repo create <new> --template <repo>/<name> [server]` POSTs mode template through the same server resolution as the proxy (knomitapi.ResolveServer / NewServerClient), polls /api/v1/repo-creates/<id> until a terminal state, and exits non-zero on a refusal (problem+json title and detail) or a failed job. `repo` is dispatched on args[0] BEFORE flag.Parse (isRepoCommand), because `-repo` is also the proxy mode's flag and a bare first positional is otherwise read as a server address. Both halves of --template are required; flags may follow the positional.

MISREADING: the wizard does not show fleet specially; a local create from `fleet` is refused by the server (409) and the error surfaces like any create failure.
