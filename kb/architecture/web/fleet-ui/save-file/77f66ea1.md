# Saving a bundle or the root key goes through saveTextFile: the desktop's NativeService.WriteFile (owner-only, 0600 on create), else the browser's save dialog, else a download, and the page says "Saved" only for an outcome it knows succeeded

Built in PR #528 (verified at merge e417fd76; web/src/saveFile.ts). Route order: (1) in the desktop app (__KNOMIT_DESKTOP__) NativeService.WriteFile through the Wails runtime by name (`main.NativeService.WriteFile`, imported by URL as eventStream.ts does, so Wails stays out of the browser bundle); it confines the name to the app's exports directory and now writes 0600 because it carries the root key; (2) in a browser with showSaveFilePicker, the dialog, whose success AND cancel are known; (3) else a plain download, which is only handed to the browser. The outcome is `saved` (with where), `downloaded`, `cancelled` or `failed`; the pages say "Saved" / "Root key saved" for `saved` alone, "...was handed to the browser as a download; check that it arrived" for a download, and "Not saved: ..." for cancel and failure, with the button label unchanged.

NOT VERIFIED: the desktop path was not run inside a real Wails webview (no desktop build in the session); the binding name and call shape match SettingsApp.tsx's Call.ByName. Known nit: 0600 applies only when the file is created, so re-saving over a file another tool made 0644 keeps 0644 (os.WriteFile keeps an existing mode).

MISREADING: a blob download is not a save; a click on <a download> in the webview is not something anyone can rely on.
