# POST /api/v1/facts/resolve turns cited fact handles into facts across the repos the caller REACHES, preferred repos first; a handle found in 2+ non-preferred repos is AMBIGUOUS and omitted; unknown, unreachable and dot-path handles are omitted, never errors

The chat's fact links resolve cited handles in ONE call: POST /api/v1/facts/resolve {handles: string[] (max 100), prefer?: string[]} -> [{handle, id, title, type, repo, branch, path, excerpt, confidence}] in the order asked, once per distinct handle. It lives in api/kb (handlers_facts_resolve.go), mounted on the API root through kb.Mount's new first argument `top`; the root HAL document links it as `facts_resolve`.

Lookup: only repos for which auth.ReachesRepo(ctx, name) holds are searched, each at its ReadBranch; the fleet repo never is. A handle naming a repo (kb://<id12, full id or name>/...) is looked for only there. Any other handle is looked for FIRST in the `prefer` repos (names, 12-hex or full repo ids, or lens names standing for write repo then reads), in the order given; the first preferred repo that holds it answers and it is not looked for again. A handle still open is then looked for in every other reachable repo: found in exactly ONE it resolves; found in TWO OR MORE it is AMBIGUOUS and OMITTED (stays code) — it is never picked by repo name order. The realistic collision is the same KB registered twice (same short ids, same paths). prefer never widens reach: a preferred repo the caller cannot read is dropped. Path handles are spelled as the store spells them (fact.NormalizePath: root prefix, .md, lowercase after the root). A done request context stops the search; what is unresolved by then is omitted. Does NOT mean a turn's binding always wins: the client must SEND it in prefer (turnPrefer), the server does not know the chat. A short id is found with index.SearchOptions.IDsIn (f.path LIKE '%/<id>.md'; only lowercase-hex ids are put into the pattern), a path with PathsIn; both set an explicit Limit because a zero Limit is a literal LIMIT 0. Only the facts that will be RETURNED are read from git (readFact, once per repo+path) for confidence and the excerpt (body minus a leading '# <title>' line, whitespace collapsed, cut at 300 runes); a hit that does not parse still resolves with its index title and type, excerpt empty and confidence 0.

Gates: isMutatingRequest treats POST to exactly httpx.APIBase+kb.FactsResolvePath as a read, so a Read-only principal (writeGate) and a ReadOnly demo server (readOnlyGate) both serve it. This does NOT exempt anything else under /facts: the match is exact, not a prefix.

Consequence: the client must leave any handle missing from the answer as plain code; the absence carries no reason (unknown vs no permission are indistinguishable by design).
