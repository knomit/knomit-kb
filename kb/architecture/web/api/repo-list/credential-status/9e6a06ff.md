# GET /repos carries credential_status ('expiring' or 'expired' only) and credential_secret (the secret's name) for a repo linked to a stored secret that needs attention; the rail draws a compact CredentialChip from them, and the Remote block's problem flag reads secret_status from GET /origin

handleHALRepos reads each live repo's injected origin once (getOrigin) for both the remote health and the credential flag; secrets metadata is listed at most once per request (secretsByID) and only when a listed repo is linked. The fields are omitted for a repo that is not linked, a secret with no expiry or status ok, and a secret that cannot be read: absence means nothing to flag, not healthy. Expiry is advisory; sync keeps using the secret. In the UI, TargetRail renders `<CredentialChip compact>` (amber expiring, red expired, title naming the secret) beside the index chip; RepoSettings marks the Remote index item (`problem`) when `origin.secret_status` is expiring or expired; RemoteCredential shows the warn box.

Not meant: credential_status is not a sync failure signal and does not drive the failing-remote red dot.

GET /repos/{repo}/origin also carries `secret_linked` (boolean, every reader). The UI decides "linked" from it (RemoteCredential, FleetSettings, RemoteConnectWizard), never from secret_name or secret_id: secret_id is sent only to admin callers (and the web GET sends no proof header), and secret_name is absent when the secret cannot be read. A linked repo with no name is shown as "Stored secret: (unreadable)" and is not offered a token replace.
