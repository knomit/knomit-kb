# The repo mount and the lens mount are parallel implementations of one surface and they diverge in BOTH directions — three verified defects, each invisible from the mount its author was testing, because the test on that mount passes

`/repos/{repo}/branches/{branch}/…` and `/lenses/{lens}/…` mirror each other: same resources, same handlers in several cases, one shared MCP dispatch closure. They are maintained as two registrations, and three verified defects show them drifting apart — in OPPOSITE directions, which is the part that makes the rule non-obvious.

THE THREE INSTANCES.

1. LENS ROUTE MISSING WHAT THE REPO ROUTE HAD. The repo-branch route registered `facts/*` as `handleHALFact(b, p.factReader, p.factSub)`; the lens route registered `handleHALLensFact(b, p.factReader)` with NO factSub. `/lenses/{lens}/facts/{path}/incoming` therefore matched the wildcard fact read with the literal path `kb/…/<uuid>.md/incoming` and 500'd `object not found` — for EVERY fact, deterministically. Fixed: handleHALLensFact now dispatches /commits, /incoming and /outgoing itself.

2. REPO ROUTE MISSING WHAT THE LENS ROUTE HAD. Only LensMiddleware calls `repos.WithBinding`. On the repo-scoped MCP mount, RepoMiddleware puts a `*RepoInstance` and BranchMiddleware the branch name, and nothing puts a `*Binding` — so `repos.BindingFromContextOpt` returns `(nil, false)` on every repo-scoped request. Code reading a binding only through the Opt form records an empty PinID for the single-repo path, the COMMON case, while working on the lens path.

3. THE SAME CONTEXT KEY MEANING DIFFERENT THINGS. Under LensMiddleware, `repos.RepoFromContext` is the lens's WRITE repo — the wrong mount for a qualified `kb://<id12>/…` path. The three fact sub-resource handlers had to stop reading it and take the resolved `*repos.RepoInstance` as a parameter instead.

WHY EACH ONE SHIPPED: the test on the author's own mount passes. A lens-route test passes while the repo route records an empty binding; a repo-route test passes while every lens fact's edges 500. Neither is a weak test — each is simply scoped to the mount its author had in mind, and a mirrored surface is exactly where that scoping is invisible.

CONSEQUENCE, and it must be stated symmetrically: when registering a route or reading ANYTHING from the request context on one mount, check what the OTHER mount puts there — the asymmetry runs both ways, so "remember the lens route too" is only half the rule. For the binding specifically: try `BindingFromContextOpt`, then fall back to `BindingFromContext` guarded by a `RepoFromContextOpt` check (it PANICS when the context holds neither), and return "" when neither is present; `bindingPin` in `internal/web/client_sessions.go` is the worked example.

CARRIED FROM THE SOURCES, because the synthesis must not smooth them away:

- The repo route is NOT missing a middleware. Synthesizing the lens-of-one binding from the context RepoInstance is DELIBERATE — it is what lets the single-repo path stay behaviour-identical without a middleware change.
- The lens sub-resource gap did NOT mean lens facts had no edges, and did NOT mean the store's edge index was broken: the same fact's edges always fetched fine through the repo route. The gap was purely the lens router surface.
- It does NOT mean every trailing segment is now handled. A fact path with some OTHER trailing segment still 500s from the go-git tree walk, on the repo route as well as the lens one. That was left alone deliberately: mapping the error to a 404 would also mask genuine object-store corruption.
- The lens-routing fix travelled in issue #178 alongside two stale-head defects, but that bundling was an accident of discovery — the fix-shape decision records the three as "small, independent, and found in one investigation". The stale-head mechanism (a dropped head notification leaving a cached anchor stale) is NOT an instance of route divergence and is not claimed here.
- Scope: three instances in this codebase, all verified. A regularity worth checking for on every mirrored route, not a proven law.
