# GET /api/v1/repos/events is a SERVER-WIDE index-state stream, held once by the app, because every other stream is scoped to the active repo while the UI renders a chip for every repo in its list

One connection carries index-state changes for EVERY repo. The route sits outside the `/repos/{repo}` subtree on purpose, and the handler carries index events ONLY — task, status, sync and push stay on the per-repo stream, where they are branch-scoped and meaningless without one. The same `IndexEvent` is also written to the per-repo stream as `event: index`, for a client watching a single repo.

WHY IT HAD TO BE NEW. The brief hedged — "add the event to whichever stream the app already holds open for all repos" — and there is no such stream. The app holds three: branches (scoped to the ACTIVE repo), sessions (Manage view only), logs (403 under read-only, and semantically unrelated). The mismatch is the whole point: the producer is per-repo, the consumer renders a chip PER REPO, so a per-repo event reaches the one chip least likely to be stale. A stream per repo was explicitly not wanted — it scales connections with the fleet.

PAYLOAD: `{repo, state, done, total}`, with `state` in the repos list's own vocabulary (`ready | indexing | error`) so a consumer patches a list entry without translating anything. The stream carries the full payload rather than the client-sessions stream's bare ping, because an index event is four small fields and a re-read per event would be a request per progress tick.

THE `ready` FRAME. One per connection, written AFTER subscribing — an event published between subscribe and announce would fall in the gap `ready` exists to close. The client refetches the repo list on a LATER `ready`, not the first: a reconnect's gap may have dropped a terminal event, so reconnect is the fallback that the removed 2 s poll used to be. The refetch is behind a GENERATION GUARD, because a reconnect during an in-flight refetch would otherwise let the older response land last.

THROTTLE: progress at most once per repo per second; entry and terminal events never throttled, and a terminal resets the window. See the publish-chokepoint invariant — that asymmetry is structural, not a timing tweak.

UI: the reducer action is `SET_INDEX`, deliberately not the existing `SET_STATUS`, which rebuilds head, branch, ontology root and embeddings from a status READ; an index event knows none of those and reusing it would either blank the fields or force a fetch per event. The stream is opened ONCE and reads the active repo through `stateRef` rather than closing over `state.repo` — depending on the repo would tear down and reopen a server-wide stream on every repo switch, and each reopen triggers the reconnect refetch. The 2 s index status poll is gone.

CONSEQUENCE, minor and measured: `/repos/events` is a static segment and `events` is a legal repo name, so `GET /api/v1/repos/events` reaches the stream rather than a repo actually named `events`. ONLY that one method+path — chi backtracks to the `{repo}` param for other methods and for deeper paths, so such a repo stays fully usable everywhere else. See the chi-backtracking gotcha; the rule stated in router.go's `creates` comment predicts a wider breakage than this route actually has.
