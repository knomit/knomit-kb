# GET /api/v1/repo-events is the server-wide stream of REPO-LEVEL events, held once by the app; `index` is its first KIND, and membership is decided by a test — about the repo as an entry in the repo list, never about content inside a branch

One connection carries repo-level events for EVERY repo. The route is top-level, deliberately outside the `/repos/{repo}` subtree. The same `IndexEvent` is also written to the per-repo branch stream as `event: index`, for a client watching a single repo.

THE SCOPE RULE, as a membership TEST rather than a list of kinds. A repo-event is about the repo AS AN ENTRY IN THE REPO LIST — its existence, its availability, or a whole-repo state. It is never about content inside a branch. Apply the test; do not extend a list.

Worked both ways, because a test that decides no cases is decoration:

- `index` BELONGS. The index chip is rendered per repo, in the list, for repos the user is not looking at. Index state is a property of the repo, not of any branch being viewed.
- A HEAD CHANGE DOES NOT. A commit is meaningful only relative to a branch — "the head moved" says nothing without naming which. Head changes, task progress and sync/push results stay on the per-branch stream at `/repos/{repo}/branches/{branch}/events`.

Future kinds follow FROM the test rather than from an enumeration, but as illustration: a repo becoming unavailable, archived, restored, appearing, or its origin failing at the repo level.

THE `created` CASE, decided so it does not acquire two homes: the PROGRESS of a creation belongs to the job stream at `/repo-creates/{id}/events`, which ENDS when the job does; a repo APPEARING in the list — or disappearing, or changing availability — is a repo-event, on a stream that does NOT end. The distinction that separates them is whether the stream terminates, not what the event is called.

THE STREAM IS GENERIC, THE KIND IS NOT. `IndexHub`→`RepoEventHub`, `Manager.IndexEvents`→`Manager.RepoEvents`, `subscribeRepoIndex`→`subscribeRepoEvents` and the route were all renamed; `IndexEvent`, the `event: index` wire name and the `TestRepoIndexEvents_*` tests deliberately were NOT. This looks like an unfinished rename and is not: `IndexEvent` names ONE kind, and renaming it generically would imply a polymorphism that does not exist; `event: index` is the wire DISCRIMINATOR, so renaming it breaks clients to buy nothing; the tests assert the index kind's behaviour, and renaming them would imply they cover the whole stream, which they do not and should not. Do not "finish" this rename.

Adding a kind is a new case in the handler's type switch plus a new entry in the OpenAPI description — NOT a new stream. The rename reached the plumbing for exactly this reason: a surface-only rename would have left a second kind needing a second hub, a second subscription and a second SSE loop.

WHY A SERVER-WIDE STREAM AT ALL. The producer is per-repo and the consumer renders a chip PER REPO, so a per-repo event reaches the one chip least likely to be stale. The app holds no other all-repo stream — branches is scoped to the ACTIVE repo, sessions is Manage-only, logs is 403 under read-only and unrelated. A stream per repo was explicitly not wanted: it scales connections with the fleet.

PAYLOAD for the `index` kind: `{repo, state, done, total}`, `state` in the repos list's own vocabulary (`ready | indexing | error`) so a consumer patches a list row without translating anything. Full payload rather than the client-sessions stream's bare ping, because a re-read per event would be a request per progress tick.

THE `ready` FRAME: one per connection, written AFTER subscribing — an event published between subscribe and announce would fall in the gap it exists to close. The client refetches the repo list on a LATER `ready`, because a reconnect's gap may have dropped a terminal event; that refetch is behind a GENERATION GUARD so a reconnect during an in-flight refetch cannot let the older response land last.

THROTTLE: `index` progress at most once per repo per second; entry and terminal events never throttled, and a terminal resets the window. See the publish-chokepoint invariant — structural, not a timing tweak.

UI: the reducer action is `SET_INDEX`, not the existing `SET_STATUS`, which rebuilds head, branch, ontology root and embeddings from a status READ that an index event knows nothing about. The stream opens ONCE and reads the active repo through `stateRef` rather than closing over `state.repo`, which would tear down and reopen a server-wide stream on every repo switch. The 2 s index status poll is gone.

HISTORY — IT SHIPPED AT THE WRONG PATH. At 594b551a this route was `GET /api/v1/repos/events`, and that shadowed a repo named `events` at `GET /api/v1/repos/events` and nowhere else (chi backtracks for other methods and deeper paths). It was moved to a top-level path in PR #222. The alternative considered and REJECTED was a reserved-name guard refusing a repo named after a static route: it taxes every future static route with a permanent, user-facing prohibition — a list of names nobody may use, growing forever — whereas moving the route removes the possibility and leaves an exclusion test that needs no maintenance. See the no-static-children invariant.

NOTE, accepted rather than overlooked: the scope rule is written in BOTH the handler comment and the OpenAPI description. That is a mild drift risk, taken deliberately — an API consumer cannot read a Go comment.
