# GET /lenses/{lens}/events sends ONE event kind, `content` {repo, id, branch, head}, per lens member (write repo included) after that member's index absorbed a write: triggered by the member's post-sync StatusEvent, head = the branch's SETTLED watermark, coalesced per member with no timers, and the stream ENDS on any lens edit; the web counts notices plus reopens into the lens list's head so #739's keep-place refresh runs

Since PR #749 (branch fix/lens-list-member-heads, merged as ab0c7906, claims re-read there; user ruling 2026-11-03: the lens list must move with ANY member's content, not only the write repo whose head state.headCommit tracks, and only when content changed).

SERVER (internal/edge/web/api/kb/handlers_lenses_events.go, handleHALLensEvents):
- Members: one per distinct (repo, branch) in Binding.Reads(). The write repo is among the reads. The branch is the one the lens binding resolved: reads[].branch, or the repo's read branch.
- Triggers: each member's TaskHub subscription, reacting ONLY to events.StatusEvent and to events.IndexEvent in state "ready" (an index job finished). The commit observer (repos/stages.go) publishes the status event only after its index sync returns. The store also syncs the COMMITTED branch itself on every commit (NotifyCommit, inside its lock), and onCommit notifies for every branch. So the settled watermark of a member pinned to a non-read branch moves too: a test pins a member on agent/side (the review's probe saw a notice in about 1.4 s).
- Head: HistoryQuery.SettledWatermark of the branch the lens reads the member at (pinned or read branch). An unsettled read (a sync or a Rebuild holding the branch) gives "" and sends nothing, but it does NOT clear the member's dirty mark (L3 of the review). The member is re-checked on the next wake: a later status event of any member, or the IndexEvent "ready" its job publishes when it ends. Before this fix, a notice could be lost for good when a Rebuild ended without a status event. A notice goes out only when the settled watermark moved past the last one sent (m.last, initialised at connect). So a commit on another branch of the member, which still fires the repo's status event, sends nothing.
- Coalescing, no timers: a status event sets dirty[i] and does a non-blocking send on a one-slot wake channel. The writer drains every dirty member. Memory is bounded at one flag per member and one pending wake. Most bursts are already collapsed upstream by the commit observer's 1 s debounce (kb/gotchas/repos/observer/debounce/4e8ac218.md), so the stream's own coalescing is the watermark dedupe plus the one-slot wake.
- Membership: the stream serves the membership resolved at connect. Right after taking LensRegistry.Changed(), it re-reads the lens and compares its (repo, branch) targets with the binding (lensReadsMatch). If they differ, the stream ends at once. This closes the race where the middleware read the lens before Changed was taken, so an edit in between would close no channel the stream holds (L1). It also ENDS when LensRegistry.Changed() closes. That is ANY lens's edit, not only this one's: every lens stream on the server reconnects once per lens edit, which was judged acceptable (L2). That channel (repos/control/lens.go) is closed after every committed Update, Rename and Delete of ANY lens; Create is excluded because it changes no open stream. The client reconnects onto the new membership.
- No event ids and no Last-Event-ID, as on every stream here (kb/gotchas/web/sse/f5afa19f.md). The stream writes one SSE comment on connect so the response starts. Without it the client's request blocks until the first 30 s keepalive: a test measured that.
- The route takes no query parameter (lensEventsParams, the #720 400). OpenAPI has it with a PLACEHOLDER description.

WEB (web/src/useLensContentRev.ts, Library.tsx):
- useLensContentRev(lensName) holds the stream only in a lens context. It counts `content` notices and every REOPEN after the first: a reopen may have missed notices, and the server ends the stream on a lens edit. Library uses `${state.headCommit}|${lensRev}` as the lens list's head in sameScopeNewHead and its deps, so a notice runs #739's quiet keep-place refresh unchanged (one in flight, trailing-edge coalescing, read-on: kb/architecture/web/library/keep-place/f5fe0d39.md).
- The write repo's branch stream stays, because it carries other status. The lens stream is the one extra connection. Repo lists open no lens stream.
- lensEventsUrl lives in useLensContentRev.ts, and apiUrl moved to web/src/apiBase.ts (api.ts re-exports it). Many tests vi.mock('./api') wholesale, and a builder in api.ts made them throw.
- Desktop: tools/desktop/uistreams.go forwards any /api/v1/ stream path (validSSEPath), so this needs no change there.

CONSEQUENCES: a new lens list dependency still goes into the effect's scope string, and the lens head now has two parts. Do not send other kinds on this stream: its one meaning is "re-read the list". Do not emit on a raw git head or before the sync: the notice promises the read will see the change. A server-wide /repo-events head kind was rejected: that stream is about repos as registry entries, never branch content (kb/architecture/web/sse/fleet-index-stream/8e878292.md).

WHAT THIS DOES NOT MEAN: the only ref moves it cannot see are those that bypass NotifyCommit, if any exist; every commit through the store syncs its own branch. It is not a replay log: notices published while the stream is down are lost, and the reopen refresh covers them.
