# A new head keeps the reader's place in the Library list (user ruling 2026-11-03, option b): a Recent or relevance list, repo or lens, re-reads exactly its loaded rows [0, n) in pages of the API's 500 ceiling, keeps the selection by path and re-anchors the scroll on a row by path; only a head-only change takes this path, any scope change reloads page 1

Since PR #739 (branch fix/list-keep-place), web/src/Library.tsx and the new web/src/listRefresh.ts handle a moved head (state.headCommit) like this:

- DETECTION: each list effect (repo Recent, repo relevance, lens union) records {scope, head} in a ref (sameScopeNewHead). The scope is every dependency except the head. Only a run where the head changed AND the scope did not, on a non-empty list, keeps the reader's place. Any scope change (text, chips, path, sort, branch, sources, ontology root) still resets to page 1, AMEND_NAV included. The ref is cleared when the effect early-returns (another sort, a lens, an empty scope), so coming back is a fresh load.
- REFETCH: refetchLoaded(n, fetchPage) re-reads rows [0, n) through the list's own route and parameters, in pages of API_MAX_LIMIT = 500 (the server's maxLimit). A relevance list is at most 500 rows, so one call. A deep Recent list makes ceil(n/500) calls. It stops at the first short page and reports `short`, which sets relExhausted/lensExhausted.
- QUIET: there is no setRows([]), no spinner, no SET_SEARCHING, no AMEND_NAV and no navigate. While a refresh runs, loadMore returns early (recentRefreshing / relRefreshing / lensRefreshing, each reset at the top of its own effect). A superseded refresh is dropped by useAsync's stale().
- PLACE: keepPlace runs just before the rows are applied. captureAnchor records the anchor row's path and its pixel offset from the scroller top: the selected row if any of it is on screen, else the top visible row. It also records a fallback list: the rows after the anchor, then the rows before it, nearest first. setSelectedIdx moves to the selected row's NEW index, found by path. A useLayoutEffect on [activeList, scrollKey] then restores the offset (restoreAnchor) and writes the new scrollTop into scrollMemory. Without that write, the passive scroll-memory restore would roll it back to the old scrollTop.
- FALLBACK: when the selected row vanished (deleted, or no longer matching), no row is selected and nothing navigates (the right panel keeps the open fact), and the nearest surviving neighbour takes the anchor's offset: the next row, else the previous one.
- The Library scroller has `overflow-anchor: none`, because the re-anchoring is manual (the double-anchoring trap: kb/architecture/web/factset-view/60d4ace8.md). Rows carry data-selected for tests.

CONSEQUENCES: a new list dependency must go into the effect's scope string as well as its deps. Otherwise a change to it would be mistaken for a head-only refresh, and the list would re-read the old scope's row count under the new filters. Do not reintroduce setRows([]) or AMEND_NAV on a head-only run. Path browse (repo and lens tree) still reloads on a new head; the ruling covers Recent and relevance only.

WHAT THIS DOES NOT MEAN: it is not a server-side snapshot. The refreshed rows are the CURRENT ranked list, so rows can shift around the anchor; only the anchor row stays put on screen. Pinned by web/src/Library.keepPlace.test.tsx (four list kinds, the deleted-row fallback, the single limit=150 refetch, scope change still resets).
