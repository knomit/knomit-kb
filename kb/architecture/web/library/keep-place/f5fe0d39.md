# A new head keeps the reader's place in the Library list (user ruling 2026-11-03, option b): once the scope's page 1 has landed, a head-only change re-reads the loaded rows [0, n) quietly, with one refresh in flight per list (trailing-edge coalescing), keeps the selection by path, re-anchors the scroll by path, retries a refused loadMore, survives a hidden list, and covers path browse

Since PR #739 (branch fix/list-keep-place, review round 2 at 7400710c), web/src/Library.tsx and web/src/listRefresh.ts handle a moved head (state.headCommit) like this.

DETECTION:
- Each list effect (repo Recent, repo relevance, lens union, repo path browse) records {scope, head} (sameScopeNewHead). The scope is every dependency except the head.
- A paged list keeps its place only when (a) the run is head-only, (b) THIS scope's page 1 has landed, and (c) the landed list is NOT EMPTY. (b) is RefreshState.loaded, set when page 1 resolves under the current scope generation, never inferred from a row count. (c) matters because an empty list has no place to keep, and a refresh of 0 rows reads nothing: before the guard, the first fact written into an empty Recent list (repo or lens) never appeared (R1 of the re-review). So an empty landed list reloads from page 1.
- H1 of the review: a head during page 1 refreshed the previous folder's 7 rows and left the spinner on. rs.loaded alone closes it. A full relevance load does NOT clear the rows (a clearing added in round 2 was removed): it brought back a false "No facts match the search." during every load. The relevance empty state waits for relLoading, as Recent's waits for loading.
- Any scope change is a full load: beginFullLoad bumps the scope generation, abandons any refresh in flight, resets to page 1, and keeps AMEND_NAV.

REFRESH (runRefresh):
- At most ONE refresh is in flight per list. A head that arrives while one runs only marks it dirty. When it completes, the pass is applied and, if dirty, exactly one more pass runs from the rows just landed (trailing edge, no timer). Every pass lands and the last head wins.
- Each pass is refetchLoaded: rows [0, n) through the list's own route, in pages of API_MAX_LIMIT = 500 (the server's maxLimit). It checks staleness (scope generation) between pages and stops at a short page (`short` sets the exhausted flag).
- READ-ON (since round 3, at c0a65974): whenever the window filled, the pass reads on [n, n + k). k is the number of new rows inserted ABOVE THE ANCHOR, the row the place hangs on (anchorPathNow: the selected row if on screen, else the top visible row; while hidden, the last-seen anchor). k is counted up to the anchor, or up to the nearest old row above it that is still listed when the anchor is gone. k = 0 means nothing was inserted above it (or it was deleted), and nothing more is read.
- WHY (the ~125px drift of round 2): re-reading exactly n rows meant every insert above the reader pushed one row out at the bottom. With the anchor within a viewport of the window's end, the scroller could not scroll far enough and clamped at scrollHeight - clientHeight, so the row came back lower by the inserted rows. Reproduced in a real browser without any Focus: 3 inserts moved the row 331 -> 472 px (3 x 47 px) with scrollTop stuck at max. The clamped offset was then remembered as the last-seen anchor, so it carried into the next FactSet round trip. Fixed by reading on, which keeps the rows below the anchor. It also subsumes the old L3 rule (read on only when the selected row fell out of the window). Pinned by 'rows inserted above keep the anchor exact, though the scroller clamps' (a clamping scrollTop emulated in jsdom). A relevance list still ends at 500 rows, so an anchor in its last viewport can clamp there, because the list really ends.
- Bounded work: ceil(n/500) calls plus at most k extra rows per pass. A relevance list (500 rows at most) is one call. A busy agent costs at most two passes per burst, not one per head.
- Quiet: no row clearing, no spinner, no SET_SEARCHING, no AMEND_NAV, no navigate. A failed pass clears the list's loading flag (L1).

PLACE:
- keepPlace runs just before a pass's rows are applied. It captures the anchor (capturePlace): the selected row if on screen, else the top visible row, by path, with its offset and a fallback list (the rows below it, then above it, nearest first). The selection moves to the selected row's new index by path.
- A layout effect on [activeList, scrollKey] restores the anchor (restoreAnchor) and writes the new scrollTop into scrollMemory. Without that write, the passive scroll-memory restore would put the old scrollTop back.
- FALLBACK: a vanished selected row (deleted, or no longer matching) leaves nothing selected, nothing navigates (the right panel keeps the open fact), and its nearest surviving neighbour takes its offset.
- HIDDEN LIST (M3): while the FactSet view holds Focus, the Library is display:none, so getClientRects() is empty and every rect is 0. isRendered() gates every read. A refresh then anchors on lastAnchor: the last place read on screen, refreshed in that layout effect and once per animation frame on scroll. It writes nothing into scrollMemory and keeps the anchor pending. A ResizeObserver on the scroller re-anchors when the list shows again.
- LOADMORE RETRY (M2): a loadMore refused while a refresh runs sets loadMoreBlocked. After the refresh's rows render, it is called again if the sentinel is still in view (sentinelInView), because the IntersectionObserver reports only changes.
- PATH BROWSE (L2): the repo and lens tree also re-read their folder in place on a head-only change. Rows are replaced, never cleared, and re-anchored the same way. Native scroll anchoring could not do it: the scroll-memory restore put the old scrollTop back, and a real browser showed a 3-row shift. `overflow-anchor: none` is on the one Library scroller for every sort (the double-anchoring trap: kb/architecture/web/factset-view/60d4ace8.md).

CONSEQUENCES: a new list dependency must go into the effect's scope string as well as its deps. Otherwise a change to it is mistaken for a head-only refresh. Do not reintroduce row clearing or AMEND_NAV on a head-only run. Do not restart a refresh per head: coalesce. Mark `loaded` only for the current scope generation.

WHAT THIS DOES NOT MEAN: it is not a snapshot. Each pass reads the CURRENT list, so rows shift around the anchor; only the anchor stays put on screen. A lens list moves only with its write member's head (state.headCommit): a write to a read member does not trigger a refresh, the same as before #739.
