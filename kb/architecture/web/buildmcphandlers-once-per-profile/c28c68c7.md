# Server.buildMCPHandler constructs exactly ONE MCP server, shared across all repos and lenses — the 'once-per-profile' path slug is stale

`Server.buildMCPHandler()` (SINGULAR) constructs exactly ONE MCP server instance and wraps it in `mcpserver.NewStreamableHTTPServer`, stored in the scalar field `s.mcpHandler http.Handler`. It is built once lazily inside `Server.Handler()` when `s.mcpHandler == nil`, then never rebuilt.

The single server is shared across ALL repos and lenses. Each request resolves its repo from context via `repos.RepoFromContext(ctx)` (populated by RepoMiddleware), and the authoring profile is resolved per-repo at session start by `profileFor(mgr, ri)` → `settings.Profile(ri.ID())` against the `repo_settings` table in control.db, defaulting to "code" whenever the manager, settings store, repo identity, or row is unavailable (the default must never error a session).

`mcp.NewServer(defaultOntologyRoot, mgr, readOnly, embedders...)` takes s.OntologyRoot as the default fallback, the repo manager, the read-only flag, and the optional embedder (for learn-dedup batching).

WHAT THIS DOES NOT MEAN:
- **There is no map of handlers and no profile key.** `s.mcpHandlers` (plural, `map[string]http.Handler` keyed by profile) and `Server.buildMCPHandlers` (plural) DO NOT EXIST. This fact's path slug still says "once-per-profile" — ignore it; the three profile-keyed instances (code, chat, generic) were collapsed to one by lenses RFC decision 12. See kb/decisions/mcp/profile-per-repo/f192649f.md for the rationale.
- **Profile is NOT a constructor parameter.** Do not look for it in the `mcp.NewServer` signature. Adding or changing a profile means editing the `profileAddenda` map in internal/mcp/instructions.go — there is no profiles slice to extend.
- `?profile=` on the MCP endpoint is DEPRECATED: router.go accepts it, logs a debug line, and ignores it. Bridge `--profile` is likewise accepted and ignored.
