# The FactSet UI: Library builds the FsSearch from the SAME listSearch builders its list calls use, a module store (factsetOptions.factsetView) carries it to RightPanel, FactSetView renders ONE run from FactSetStream (seek replaces it), and shared parts live in materializeParts.tsx

As built in #710 (merged at c785c88e; web/src, flat):
- listSearch.ts: listSearchParams (repo /search, /facts) and lensListSearchParams (lens /search, /facts) return exactly what a results list sends minus paging; api.search, api.recent, lensSearch and listLensFacts call them, and Library builds the FactSet's FsSearch {target repo|lens, sort relevance|recent, params} from the same builders with the ONE listFilters object its list calls use. They live outside api.ts because many tests vi.mock('./api') wholesale; a builder in api.ts made those suites throw on render. The lens /facts list now sends its text as q (the handler reads query or q).
- LibraryHeader: the entry control sits beside the count on every search list (absent in the path tree, disabled when !isLive). A lens of any size uses the lens route.
- factsetOptions.ts: the open flag and options in the query string (factset=1, fs_depth, fs_refs, fs_cross_kb, fs_unpin; replaceState); the frozen search in memory in factsetView (useSyncExternalStore). Since #713 the list's search and its context are in the URL too (listUrl.ts: ctx_* and l_* keys), so a reload RE-CREATES the FactSet: load() keeps factset=1 as pending 'wait'. useListUrl restores the list (RESTORE_LIST), then arm()s it to 'ready', and Library's effect then opens the FactSet from its own factsetSearch, a new first call from the same builders. Where nothing can be re-created (factsetSearch null in the path tree, !isLive in history, or the URL context gone: abandon), dropPending() removes the flag and keeps the fs_* options in memory. The old L5 clear-on-load is gone. The URL still never carries a FactSet id or cursor.
- RightPanel renders FactSetView (keyed by searchKey) before any other branch when factsetView holds a search. The view exists only in Focus (decision kb/decisions/web/factset-view/focus-exit/8f74df50.md): Back, the Exit focus toggle and Esc outside a text field all close it (useMatFocus(onExit)); the stream's dispose then DELETEs the FactSet and the URL flag is cleared.
- useFactSetStream.ts FactSetStream: one run on screen (loadMore appends, loadBefore prepends a whole unit across pages, seek replaces); one call in flight under a generation counter; any option change restarts and seeks back to the reported top unit; 503 retried per Retry-After (clamped to MAX_RETRY_AFTER_S = 10 s) at most MAX_BUSY_RETRIES (3); a 404 on a CURSOR call re-creates the same search, seeks back and raises notice 'FactSet refreshed' (Q-UI13), at most once in a row: the re-creating first call (and the seek right after it) is not recoverable, so a 404 there (the repo or lens is gone) is shown as an error instead of looping, and the bound resets only when a CURSOR call succeeds (loadMore, loadBefore, reach, seek, the seek inside a restart), never on a first call's own page, so a FactSet whose cursor calls always 404 (another server without sticky routing, an owner mismatch) is re-created once and then shows the 404 where it happened; Retry on an expired tail or head error (the reader's act, so it cannot loop) resets the bound, so the 404 it meets re-creates the FactSet once more; a seek, and reach() for a unit already in the run, read on inside the unit (readOn) until the target anchor or section n has arrived or the cursor passes the unit, so a link or builds-on click lands on its target, not the unit root; a loadBefore failure is headError, shown at the top; a superseded FactSet is closed with DELETE, but a FactSet known to be gone (a cursor call answered 404, or the export did: it calls recover(cursor), and recover marks gone BEFORE its once-in-a-row bound, so the mark holds even when no re-creation follows; markGone records the FactSet id, the cursor minus its last two dot parts) is never closed, so the re-creation after a 404 sends no DELETE for the dead cursor while Back, Exit focus, Esc and a superseded live FactSet still do (since #726). Pages are section-limited (limit 5) and can split a unit, so loadBefore reads until the cursor's unit passes the target.
- FactSetView (since #726): the top sentinel is armed per run (armedEpoch === epoch) and ONLY by the reader's move UP in that run: an upward scroll event, or a wheel with deltaY < 0 / an upward touchmove while scrollTop is 0 (a seek to a unit root lands clamped at 0, where an upward wheel fires no scroll event). A scroll DOWN never arms it, so the observer rebuilt after a loadMore cannot prepend while the reader reads down. Scroll events are ignored until the run has settled (settledEpoch === epoch, set in a requestAnimationFrame scheduled after the landing effect), so the browser's clamp on a run swap and the landing's own scroll cannot arm it; later scrolls the view makes (setScrollTop: a link scroll, keeping the place on a prepend) are recognised by their scrollTop. The reader's move up also calls loadBefore directly when the sentinel is already in range, since the observer reports only changes (Q-UI9). The settle gate and the at-top wheel are browser reasoning: jsdom tests drive them with a mocked scrollTop, not real layout. The progress line 'unit X of N' shows topUnit, the unit at the top of the pane that the Unit stepper also shows, updated on scroll and after every landing; it is NOT env.unit_to (the last unit loaded).
- materializeParts.tsx: Stepper, Switch, Body, Disclosure, Section, NESTING moved out of MaterializeView (useMatFocus lives in useMatFocus.ts: react-refresh keeps hooks out of component files; its optional onExit makes Esc leave the view, used by the FactSet view only); Section takes an optional fs extra (unit, link, repoName, unavailable) plus onLink; a 'Related, not included' entry with reason lens_repo reads the repo_name, a space, then the fact path with its kb://<id12>/ prefix stripped inside a <code> element, and no reason code (ruling S2: the same repo name and path render_agent.go omissionText writes into the export, where the path is in markdown backticks instead); every other reason still reads 'title || id || path (reason)' (MatOmission.repo_name since #726); a stub has no data-anchor and its own heading id, so only the written section is a scroll target.

CONSEQUENCE: a new list filter must be added in listSearch.ts (and Library's listFilters) to reach both the list and its FactSet; never build FactSet params separately.

LANDING (since #726 at 7aa62463): the stream's `land` stays set for the whole run, and the landing effect's inputs (byUnitN) are rebuilt on every append and prepend, so FactSetView records the land object it acted on (landed ref) and lands each request EXACTLY ONCE. Before that, after any jump (Unit stepper seek, link-click seek, reach, re-creation after a 404) every new page snapped the reader back to the landing target and overwrote a prepend's place-keeping (scrollTop + the prepended height). A new landing is a new land object (seek, reach, restart each commit one), so do not reuse or mutate a land to re-trigger it, and never key the landing on node arrays. Since #736 a land can carry `back` (seek(unit, undefined, n, true)): the Back pill's re-seek to an origin whose run a jump dropped. The landing effect handles it first. It hands the origin to restoreStep, which puts the section (unit, n) back at its saved offset, never follows it even if it is a stub, and does not flash. restoreStep re-runs on each change of the run and reads units above (loadBefore) or below (loadMore) until the offset fits without clamping. The stream keeps the pending Back target, so recover() after a 404 re-creates the FactSet at the origin rather than at topUnit, and Retry after a failed Back seek retries the Back. A landing on a link or builds-on anchor flashes the target (FLASH_MS); a landing on a unit alone does not. Decision: kb/decisions/web/factset-view/back-pill/d6245a58.md.

PLACE-KEEPING (since #726 at 0b0a85d0): the view's own layout effect is the ONLY place-keeping on the FactSet scroller, and `.k-fs-scroll { overflow-anchor: none; }` in materialize.css keeps the browser's native scroll anchoring off there. Both on at once is the double-anchoring trap: native anchoring already holds the reader's place on a prepend, the manual scrollTop + (scrollHeight - before) then adds the height again, and the view jumps by twice the prepended unit (measured in a real browser: a 458px unit moved scrollTop 299 -> 1215). The manual path is kept rather than native anchoring because it is deterministic in every engine, including the desktop app's WebKit webview. So never remove that rule while the manual adjustment exists, and never add manual place-keeping to a scroller that still has native anchoring on. The rule is scoped to this scroller: the single-fact view never prepends. The head skeleton is part of the place-keeping too: when it mounts above the run, its height is added to scrollTop; the prepend then adds the net change (the reader ends at scrollTop + the prepended height); a failure gives the skeleton's height back, so the head error shows at the top. Tests read materialize.css ?raw (vite.config test.css include matches ?raw ids only) to assert the rule, because jsdom runs no native anchoring.

BACK TO TOP (since #736): the arrow (fs-top) goes to the START of the FactSet, never to scrollTop 0 of the loaded run. When nodes[0].unit === 1, nothing can be prepended above it, so it scrolls to 0 (smooth). Otherwise it calls seek(1), which lands on unit 1's root. The old scrollTop = 0 reached only the top of the run. After a seek that run starts near the target, and landing at its top armed a prepend whose place-keeping left the reader somewhere new on each click (the user saw 338, then 336.x). Do not reintroduce a bare scrollTop = 0 on this scroller. The single-fact view's top button is unchanged (it never prepends).
