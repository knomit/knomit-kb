# Tool calls carry started_ms and ended_ms (Unix ms, server clock) in the snapshot's tool_call items and on the live tool_call events; the activity line shows wall time = last ended_ms minus first started_ms, and nothing while any call is running or lacks timestamps

The running tool_call event carries started_ms; the done event repeats started_ms and adds ended_ms; the snapshot item (viewItem) holds both, so a page that joins late shows the same line as one that watched (the snapshot is authoritative). Both come from the server's clock at LoopToolUse and LoopToolResult, so client clock skew cannot matter. The client's wallDurationMs(calls) = max(ended_ms) - min(started_ms), and 0 (no time shown) if any call has no endedMs or no startedMs. It is NOT the sum of duration_ms: overlapping calls would count twice and the model's thinking between calls would be missed (a looping local model showed 2m 2s wall against about 9ms of summed tool time). duration_ms stays, for the per-row time. A call declined at an approval still gets both stamps (its span includes the wait). Guarded by Go test TestChat_ToolCallEventCarriesDetail-style assertions in waiting_test.go (events equal snapshot) and the ChatWaiting tests for overlap and for a gap.
