# api/chat routes: /chat-providers, /chats and /chats/{id}/{events,turns,cancel,approvals/{callId},grants (GET lists, DELETE revokes one),calls/{callId}}; a chat belongs to the principal that created it and any other principal gets 404; the id is chat-<32 hex> everywhere

internal/edge/web/api/chat exports only Mount(ctx, r, mcpServer, repoManager, registry, sessionsDir, logDir, released). Server.chatRouter builds it ONCE per Server (the plain and OAuth listeners share one set of live chats, as with origin sessions) and apiRouter registers each (method, pattern) the shared mux holds, so the route golden lists exactly them. The chats are not mounted on a ReadOnly server; without a provider registry they ARE mounted: GET /chat-providers answers an empty list and POST /chats answers 422 'Cannot start the chat' ('no chat providers are configured'; TestChat_NoProviderRegistry).

Ownership: every /chats/{id} route resolves {id} against the caller's principal string and answers 404 for any other principal, including events, approvals, calls and DELETE (TestChat_OtherPrincipalGets404 answers a pending approval as the other principal and reads a call that exists, so the 404 comes from ownership); GET /chats lists only the caller's. The id (chat- and 32 hex) is the MCP session id registered in clientsessions, the endpoint /api/v1/chats/<id> (the cursor owner), the Knomit-Trace value chat:<id> and the session log's file stem.

POST /chats takes the registry's judgement first: 400 for a provider or model outside the allowlist (llm.ErrUnknownModel), 422 for a provider that cannot be used (no key, no tool support). Read-only principals may chat; the permission gate decides per tool.

Consequence: a new chat route needs an api/chat entry in the OpenAPI file, a regenerated route golden and a paramClass entry for any new {param}. It does NOT mean chat state is durable: the chat list is the live set and a restart ends every chat.

Revoke: DELETE /chats/{id}/grants takes a grantInfo body {target, kind, tool, action} (all four required, else 400), answers 204, or 404 for a grant the chat does not hold. It is the owner's alone (chatOf, so another principal gets 404) and it passes the write gate because readonly.go's chatRoutePattern exempts everything under /chats; it changes the chat's approvals, never a knowledge base. The usage SSE event also carries `seq`, the chat's request counter (1, 2, ...), so a client can count a repeated frame once. It counts responses, so a pause_turn continuation inside one turn gets the next seq (TestChat_UsageEventsCarryAnIncreasingSeq, TestChat_UsageSeqIncreasesAcrossAPauseTurnContinuation).
