# api/chat routes: /chat-providers, /chats and /chats/{id}/{events,turns,cancel,approvals/{callId},grants,calls/{callId}}; a chat belongs to the principal that created it and any other principal gets 404; the id is chat-<32 hex> everywhere

internal/edge/web/api/chat exports only Mount(ctx, r, mcpServer, repoManager, registry, sessionsDir, logDir, released). Server.chatRouter builds it ONCE per Server (the plain and OAuth listeners share one set of live chats, as with origin sessions) and apiRouter registers each (method, pattern) the shared mux holds, so the route golden lists exactly them. The chats are not mounted on a ReadOnly server; without a provider registry they ARE mounted (empty provider list, creation refused).

Ownership: every /chats/{id} route resolves {id} against the caller's principal string and answers 404 for any other principal, including events, calls and DELETE; GET /chats lists only the caller's. The id (chat- and 32 hex) is the MCP session id registered in clientsessions, the endpoint /api/v1/chats/<id> (the cursor owner), the Knomit-Trace value chat:<id> and the session log's file stem.

POST /chats takes the registry's judgement first: 400 for a provider or model outside the allowlist (llm.ErrUnknownModel), 422 for a provider that cannot be used (no key, no tool support). Read-only principals may chat; the permission gate decides per tool.

Consequence: a new chat route needs an api/chat entry in the OpenAPI file, a regenerated route golden and a paramClass entry for any new {param}. It does NOT mean chat state is durable: the chat list is the live set and a restart ends every chat.
