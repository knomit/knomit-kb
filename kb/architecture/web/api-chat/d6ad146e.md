# api/chat routes: /chat-providers, /chats, GET /chats/events (the ONE page events stream) and /chats/{id}/{turns,cancel,approvals/{callId},context,grants (GET lists, DELETE revokes one),calls/{callId}}; a chat belongs to the principal that created it and any other principal gets 404 (and never sees its events); the id is chat-<32 hex> everywhere

internal/edge/web/api/chat exports only Mount(ctx, r, mcpServer, repoManager, registry, sessionsDir, logDir, released). Server.chatRouter builds it ONCE per Server (the plain and OAuth listeners share one set of live chats, as with origin sessions) and apiRouter registers each (method, pattern) the shared mux holds, so the route golden lists exactly them. The chats are not mounted on a ReadOnly server; without a provider registry they ARE mounted: GET /chat-providers answers an empty list and POST /chats answers 422 'Cannot start the chat' ('no chat providers are configured'; TestChat_NoProviderRegistry).

Ownership: every /chats/{id} route resolves {id} against the caller's principal string and answers 404 for any other principal, including approvals, calls and DELETE; the page stream GET /chats/events is not per chat: it carries only the CALLER's chats (the manager keys page streams by owner), so another principal's stream never sees them (TestChat_OtherPrincipalGets404 answers a pending approval as the other principal and reads a call that exists, so the 404 comes from ownership); GET /chats lists only the caller's, each row carrying the chat's identity plus its rowState, in id order (recency is the client's job). The id (chat- and 32 hex) is the MCP session id registered in clientsessions, the endpoint /api/v1/chats/<id> (the cursor owner), the Knomit-Trace value chat:<id> and the session log's file stem.

POST /chats takes the registry's judgement first: 400 for a provider or model outside the allowlist (llm.ErrUnknownModel), 422 for a provider that cannot be used (no key, no tool support). It then takes an optional message, trimmed (a blank message is no message and the chat is created empty): with one, the first turn starts exactly as POST /chats/{id}/turns would start it, and the 201 carries turn. If that first turn is refused (the chat ended in the instant after creation) the handler ends the chat and answers 503, so no chat is left behind. Read-only principals may chat; the permission gate decides per tool.

Consequence: a new chat route needs an api/chat entry in the OpenAPI file, a regenerated route golden and a paramClass entry for any new {param}. It does NOT mean chat state is durable: the chat list is the live set and a restart ends every chat.

Revoke: DELETE /chats/{id}/grants takes a grantInfo body {target, kind, tool, action} (all four required, else 400), answers 204, or 404 for a grant the chat does not hold. It is the owner's alone (chatOf, so another principal gets 404) and it passes the write gate because readonly.go's chatRoutePattern exempts everything under /chats; it changes the chat's approvals, never a knowledge base. The usage SSE event also carries `seq`, the chat's request counter (1, 2, ...), so a client can count a repeated frame once. It counts responses, so a pause_turn continuation inside one turn gets the next seq (TestChat_UsageEventsCarryAnIncreasingSeq, TestChat_UsageSeqIncreasesAcrossAPauseTurnContinuation).

GET /chats/{id} is the authoritative transcript: its `items` are user | assistant | tool_call rows, and each user item (a turn header) also carries that turn's `usage` (summed over its requests), `cost_usd` (summed, absent without a price card), `warning` (the worded price-tier warning, once per chat, on the turn it fired in) and `error` with `cancelled` (how the turn ended when it did not succeed; cancelled marks the person's Stop). The view is append-only, so turn indices are stable, and the user item is appended before POST /turns answers 202. `usage_seq` is the seq of the last usage event the items include (TestChat_SnapshotCarriesEachTurnsUsageCostWarningAndEnd). A client that holds a snapshot ignores live usage events at or below usage_seq.

Turn index on the wire: text_delta, tool_call (running and done), approval, usage, warning, turn_done and turn_error all carry `turn`, the view index of the turn's user item, and POST /turns answers 202 with `{turn, _links}` (the user item is already in the view). finishTurn captures the index before it sets running=false, because the next send moves it (TestChat_EventsAndTheAcceptedTurnNameTheirTurnIndex). Concurrency: the per-turn summary a view item points at (the usage struct) is IMMUTABLE: onLoopEvent allocates a new turnUsage on every update (CostUSD already did), because GET /chats/{id} copies the items under the chat lock but encodes them after releasing it; updating it in place is a data race that `go test -race` reports (TestChat_SnapshotDuringATurnDoesNotRaceTheUsageSummary, many pause_turn responses in one turn while four goroutines GET).

Events (one stream per page): GET /chats/events replaced the per-chat GET /chats/{id}/events, which no longer exists (the chat links no longer carry an `events` rel; the client builds the URL). Every event's data is an object with `chat` (the chat id) first; `ready` is page-level and carries none. Besides the events above it carries thinking_delta, chat_state (the rail row, the same rowState GET /chats embeds in each list row: title, state idle|running|awaiting_approval|error, turns, cost_usd, last_activity, started_at; sent only when it changes, last_activity aside) and chat_end (the stream stays open). Callers checked: the web client (chatEvents.ts is the only opener), the desktop's Wails transport (accepts any /api/v1/ GET path, so it carries the new route unchanged), OpenAPI and the route golden; no e2e spec touched the per-chat route.

POST /chats/{id}/turns and POST /chats/{id}/cancel take an optional send_id, at most 64 bytes (400 otherwise). A cancel naming a send_id the chat has not accepted yet withdraws it: a POST /turns with that send_id then answers 409 'Send withdrawn' and starts no turn. A cancel with no body still ends the running turn. Each user item of GET /chats/{id} echoes the send_id of the POST that started it (absent when there was none).

GET /chats/{id} and GET /chats/{id}/context carry prompt_tokens: the size of the last request's prompt (input plus cache read plus cache write), which is what the context meter shows as used; 0 before a request. GET /chats/{id} also carries expected_first_token_ms, and each model in GET /chat-providers carries it too: the slowest time to a first reply that model took in this server run, absent until one is observed. It is in-memory and resets with the server.
