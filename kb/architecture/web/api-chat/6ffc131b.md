# POST /chats accepts an optional message and starts the first turn exactly as POST /chats/{id}/turns would; the 201 carries turn (the view index) only when a message was sent

handleCreate trims req.Message (strings.TrimSpace); a message that is empty or only whitespace is no message and the chat is created empty with no turn. Otherwise it starts the first turn with the trimmed text through startFirstTurn (c.startTurn), and the response is the chat item plus turn (pointer, omitted without a message; turn 0 is a real value). If the first turn is refused (the chat ended in the instant after creation) the handler ends the chat and answers 503, so no chat is left behind. The create body limit is 1 MiB like /turns. The start screen relies on this: nothing exists until Enter or Start, then one call creates the chat with its first message. Does NOT mean the SSE stream has seen the turn's early events: the client attaches after create, so it re-reads the snapshot on ready (see the turn-end gotcha); a failure of the turn itself (context full, provider down) is asynchronous, a turn_error on the already-created chat, as for /turns. Enforced by TestChat_CreateWithMessageStartsTurn, TestChat_CreateTrimsTheMessage and TestChat_CreateWithRefusedFirstTurnLeavesNoChat.
