# The session log of an adaptive chat adds adaptive, tools and preload records and a projection field on request records: preload is written once per turn at the turn's END with the hit set, error fields hold a class, and turn records stay whole while tool_call records stay cut at 8 KiB

Same file, same id as before (the chat id is the file stem, every line's session_id, the MCP session id and the trace id). An adaptive chat writes, besides the existing records: `adaptive` once at open ({ranker: the one it starts with (blended, or lexical with no embedder), tools: catalogue size, preload_budget: P}); `tools` for every change to the loaded set ({turn, reason: preload|model|stale_call|pressure, loaded, evicted, loaded_now, tokens, ranker_error?}); `preload` once per turn the ranker ran, written when the turn ENDS ({turn, ranker: blended|lexical (the guess that was made; lexical when the embedder failed that turn), ranked: the best 5 with fused scores, picks: [{name, score}] of what was loaded (never a core tool), budget: P, loaded, hits, picked, called, embedding_error? (why the embedding ranker was passed over), ranker_error? (the loop swallowed it)}); and each `request` record gains projection {stubbed_results: tool results of ended turns sent as stubs, saved_tokens_est: stored view minus sent view in bytes/4, net of the loader's own definition and counting the reasoning of ended turns that was left out}. The request record's items and tokens are what was SENT (the projected view). The core tools are in loaded_now from the first change on, and the opening itself writes no tools record. These `tools` records are the ONLY record of the window's changes: the page gets no tools event and no tools field (kb/gotchas/web/chat/adaptive-tools/ff6fa124.md), so a question about what was loaded when is answered from the log.

ranker_error and embedding_error hold the CLASS of the failure (timeout, canceled or error, from rankErrorClass), never the error's text: an embedder's error can carry model paths and other local detail, and a session log is the file people attach to bug reports.

A loader call is a tool_call record with the loader's name and an approval record with decision `auto` and tool load_tools; it raises no approval event and is never in pending_approvals. Every call to a loaded MCP tool still gets its own approval record from the gate. A call answered by the no-progress guard is a tool_call record too, with the earlier result and the note, and gets no approval record (it was not run).

What this does not change: `turn` records hold the whole stored entries (reasoning included), and `tool_call` records still cut a result at maxLoggedResult (8 KiB) with truncated=true and the full byte count, so a result over 8 KiB is whole only in the turn record (TestSessionLog_ToolsPreloadAndProjectionRecords). A static chat's log has none of the new records and no projection field. Reading `hits` against `picks` is how the preload hit rate is measured; it is per turn, not per chat.
