# An adaptive chat keeps every tool in the Builder's hook 1 and puts the catalogue in the loader's description: Registry.Adaptive alone decides, hook 2 and hook 3 are byte-identical to a static chat, the window opens with the core tools loaded, and a catalogue that cannot fit refuses to open the chat

chat.manager.create asks Registry.Adaptive(provider, model, caps) and nothing else; when it is true the chat gets a Loop.Window built by mcp.NewChatToolWindow, otherwise Window is nil and the chat is the static path (Anthropic, or an Ollama provider with adaptive_tools = "off"). The Builder is built the same way in both modes: mcp.AddPrefix puts EVERY tool in hook 1, ChatSystemPrompt in hook 2 and the server instructions in hook 3. The adaptive loop sends Window.Project(Builder.Snapshot()), so the request carries the loader, the core tools (mcp.ChatCoreTools: knomit_bind and knomit_query, loaded from the opening) and the tools loaded since, while the Builder still holds all of them.

The catalogue ("- name: purpose", sorted, built from exactly the tools the principal was shown, core tools included) is the loader tool's DESCRIPTION: llm.LoaderDescription, a newline, the catalogue. It is not in the system prompt, so hook 2 and hook 3 are the same bytes for adaptive and static chats and a read-only principal's catalogue holds no write tool. A tool with a row in mcp's toolPurposes table uses that approved line; a tool with none (a script tool) gets the first sentence of its description cut to its share of the budget. The catalogue's budget is the preload budget P (usable room / PreloadDivisor); over it the lines degrade to names only; over it again mcp returns *CatalogueTooBigError and the chat does not open: create fails (HTTP 422) with llm.OpeningTooBigError(adaptive=true, ...), the catalogue-flavoured opening-too-big sentence with the same sizes and Ollama hint as the loop's own refusal. A server tool named like the loader (load_tools) also refuses to open, with llm.ReservedToolNameMessage.

What this does NOT mean: adaptive mode does not shrink the Builder's hook 1 (stored history and the tool list stay whole; only the sent view is projected), and the chat package holds no list of tool names and no kind check: the capability is Caps.StablePrefix, read through Registry.Adaptive (the core list lives in mcp, not in chat). Anthropic chats get no Window and their request prefix is byte-identical to the static prefix builder's (TestChat_AnthropicRequestPrefixBytesAreTheStaticPrefix). chat.Mount gained an embedder parameter (the server's), so the fact kb/architecture/web/api-chat/d6ad146e.md names a Mount signature that is now out of date.
