# Origin-session apply/commit are RUNS: the POST waits for the run's first event, then answers 202 + events link (or the refusal the run recorded); one run per session (409 Session busy); a per-run event log replays from the start, resumes on Last-Event-ID, ends with 204, and outlives the session for 10 min

Since #509 (PR #754), internal/edge/web/api/origins/runs.go.

POST /apply and /commit: beginRun first checks the session exists, RESERVES a run in the manager's runRegistry (409 problem 'Session busy' with `_links.events` of the running run when the session already has a BUSY apply or commit: one that has neither finished NOR logged its done/error; a run past its outcome but still releasing the session does not block, the new POST's Use waits for the release), then takes the session's use with r.Context() (a request that ends while waiting answers 404 and drops the reservation). The handler's own validation still answers plain problems. Then startRun hands the use to a goroutine running the operation under context.WithoutCancel(r.Context()) (request VALUES kept, e.g. RepoFromContext; its cancellation is not), cancelled when the manager's lifetime (Mount's ctx) ends.

THE POST WAITS FOR THE FIRST EVENT. It answers only when the run has logged an event (then 202, body {session_id, run, _links: {events, session}}, Location = events href) or has ended without one (then the refusal the run recorded with runLog.refuse, else a 500). This is how the commit machine's pre-change refusals (isCommitRefusal: Knowledge base already local, Different knowledge base, Origin not attached, ...) that arrive from rm.Send INSIDE the run still come back as HTTP problems on the POST, exactly as lazyStream did. A refused run is dropped from the registry (its link 404s and it blocks nothing). That does NOT make the commit retryable on the same session: a refusal from the machine's guards inside the run comes after the clone was closed, so re-POSTing answers 409 'session has no remote store' (as before #509); only the indexing 409, decided in the POST before the clone is closed, is retried with cancel_indexing.

THE LOG. Every event is JSON-appended to a runLog. GET .../{apply,commit}/events (handleRunEvents) replays from the start, then follows live (wake channel), keepalive every 30 s, and RETURNS after the run's last event. Each event is `id: <n>`, increasing but NOT contiguous: progress events (those carrying `current`, i.e. replay per fact and indexing) are COALESCED, one replacing the log's last entry when that is progress of the same phase, under a new id; every phase event is kept. So a 100k-fact replay logs a handful of entries, and a live reader still sees each progress event it is awake for. Last-Event-ID n resumes with the entries whose id is past n; an id this run never issued (from an earlier run of the same kind) replays from the start. 204 ONLY for a reader that has already seen everything of an ended run (its Last-Event-ID is the last id); a first reader of an ended run gets a 200 replay. No run of that kind for the session: 404. A run that ends without a done/error event gets a synthetic error event (finish), and a panic is recovered into one, so a reader never waits forever. Finished runs are kept runRetention (= sessionExpiry, 10 min) in the registry, counted from the run's END, independent of the session (commit deletes its own session at its end, and its outcome must stay readable). The retention ends early when the manager's lifetime ends, or when a new run of the same kind starts on the session (it replaces the entry).

CANCELLATION. Dropping the session (Delete, replace, idle expiry, lifetime end) calls retire, which calls the session's cancelRun: set only for APPLY (cancelOnDrop), so an apply is cancelled; a COMMIT is not (a store swap must not stop half-way) and runs to its end. Both are cancelled at manager lifetime end. For a commit that is safe: repos.Manager.Send uses the caller's ctx only for ResolveOrigin before queueing, and Machine.Send only to bound queueing and the wait for the reply; a queued swap runs on the machine's goroutine under its own context (guardContext(m.root)), so cancelling stops the narration, never the swap half-way. Before #509 a client disconnect cancelled both via r.Context(); now a disconnect cancels nothing. The apply sets the session's state BEFORE logging done.

CONSEQUENCE: a client may POST the commit as soon as it SEES the apply's done event (the wizard does: streamApply resolves on done); the commit's POST then waits for the apply's release and runs. A POST while the other run has not yet logged its outcome gets 409 Session busy. (Test: TestApply_CommitPostedOnSeeingDoneIsNotBusy; PR #754 review fixed a 409 here.) A test that needs to stall the run's reader hooks sessionManager.runEventHook (called on the run goroutine after each append), not the response writer.

WHAT THIS DOES NOT MEAN: /test and /preview are NOT runs; they still stream on their own GET response (beginSSE). The registry is not a job system: no ids beyond (session, kind), no listing, nothing persisted, gone at shutdown.
