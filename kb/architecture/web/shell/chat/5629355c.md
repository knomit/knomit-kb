# The chat side panel shows one entry at a time (a tool result by callId, a fact by repo, branch and path, or a commit by repo, branch and hash), with no back stack; the reader selects from the chat, closing empties it, and its width is remembered under knomit.chatPanelWidth

chatPanelState.ts owns the panel: PanelState {entry}. open(entry) replaces what is shown and close empties it; there is no history, no back or forward and no count (user decision, kb/decisions/ui/chat/panel-browse-chrome/64aa3076.md: the reader selects from the chat). ChatFacet derives the highlighted timeline step from the shown entry (selectedId = callId of a result entry), so a fact entry highlights no step. A third kind, {kind:'commit', repo, branch, commit}, shows ChatCommitView (a commit link opens it; its crumb is repo / short hash). A commit or a tool result has a 40px header (crumb and ×); a fact has none, because its band holds the path and the ×. A fact entry may carry commit (read at that commit, the band showing that version) and removed (the commit retracted it: read with ?fallback=before). From a fact reached through a commit, the way back to the commit is its chip, and the panel's memo of commits (ChatSidePanel, by repo, branch and hash) returns to the same scroll without a second read while the panel stays open; the panel's state is not persisted, so a reload starts closed. The footer holds only the Esc hint. A fact entry is complete by itself: ChatFactView fetches api.fact and api.explain (VersionWalker reads the versions) from {repo, branch, path, commit?}, so a fact link only has to dispatch open; a load failure shows the server's sentence (the text after fetchJSON's '<url> → <status> ') in a blocked NoticeLine, never the request URL. Width: default 470px, min 320, max PANEL_MAX_FRACTION (0.6) of the CHAT BODY's width (the row holding column and panel, not the window; App.css `.k-chat-result` max-width is the same 60% of the same box and a test pins the two). It reaches the stylesheet as the CSS variable --k-panel-w (width: var(--k-panel-w, 470px)), so no inline width fights the phone-width rule. A splitter drag starts from the width the panel is SHOWN at (offsetWidth), not the stored value, and is clamped by clampPanelWidth(w, container); persisted to knomit.chatPanelWidth only on mouse release, like the Library width. A materialize result's crumb reads `file` (path or kb://<store>/<path>, the real argument shape; `binding` is an opaque handle) and takes the target from repo/lens/target else the binding in force when the call ran (boundBeforeCall in chatState.ts). The header crumb is repo / path / dir when the call names a file, else the repo then the tool's label; for a bind call the repo is the bind's own target (bindTarget in chatState.ts: lens, repo, name, target), not the binding in force before it ran. The module is chatPanelState.ts, NOT chatSidePanel.ts: on a case-insensitive filesystem that collides with ChatSidePanel.tsx and tsc -b fails with TS1149. Narrow windows (<=640px): the panel stacks above the chat, full width, max-height 50%, splitter hidden; those rules sit AFTER the base .k-chat-result rule in App.css so source order wins without !important (an earlier media block ABOVE it lost to the base max-width: 60% and showed a 225px panel at 375). Answer tables sit in a .k-chat-table-scroll box (overflow-x: auto) so a wide table scrolls instead of being cut off by the panel.
