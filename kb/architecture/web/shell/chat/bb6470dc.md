# A chat is a PinnedTarget {kind:'chat', id} whose backing list is GET /chats (useChats); onChatCreated adds it and pins it in one batched update, and the chat pins over the browse context

A chat is a pinned target, not a browse context: facets.ts PinnedTarget gains {kind:'chat', id}, DraftKind gains 'chat' (DRAFT_NAME 'New chat'), and a rail pick or a finished start form SELECT_PINNEDs it OVER the browse context, so picking a repo row returns to the repo's Browse (the facet rule restores the remembered facet).

Its BACKING LIST is useChats (GET /chats, merged with local add/remove that happened while a read was in flight, re-read on window focus). Under pin-backing-list, App's auto-unpin effect drops a pinned chat that is not in `chats` once `chatsLoaded` is true. So App.onChatCreated calls addChat(chat) and dispatches DRAFT_REGISTERED and SELECT_PINNED in the SAME event handler: React batches them into one render, and the effect never sees a pin without its row. Do not 'refresh then pin': a refetch between the two is exactly the gap the invariant forbids. A chat leaves the list when its stream sends chat_end or its transcript read answers 404 (ChatFacet.onGone -> removeChat), and the effect then unpins it.

Consequences: (1) every live chat stays MOUNTED in App (hidden unless displayed) so its stream and transcript survive a look at a repository; a chat lives as long as its tab. (2) Leaving a chat does not end it. (3) The Chats rail group is absent, not disabled, unless chat is served (not read-only AND at least one provider from GET /chat-providers).

NOT meant: the chat is not a BrowseContext and never goes into AppState or the nav stack.
