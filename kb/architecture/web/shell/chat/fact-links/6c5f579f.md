# Chat fact links: the FINISHED turns' inline-code candidates are resolved in one POST /facts/resolve per mount (per distinct preference list), cached per handle+preference for the page's life; remarkFactLinks marks code spans data-fact / data-repo and collapses multi-fact table cells to first link + "+N"; chatComponents' code/span overrides draw them from FactLinkContext

Pipeline (web/src/chatFactLinks.ts, ChatFactChip.tsx, ChatPanel.tsx, chatTableBars.tsx):
1. factCandidates(answer) reads INLINE code only (fenced blocks are stripped first, prose is never read): an 8-hex short id, a slash path ending in .md or in an 8-hex segment, or kb://<store>/<path>. Bare repo names and kb://<store> without a path are NOT resolve candidates; they become repo chips from the page's repo list (ChatFacet's `repos` prop, from App) via repoChipName.
2. useTurnFacts(answers, prefers) sends ONE resolveFactHandles per effect run per distinct preference list (normally one: a chat stays bound to one target), carrying every candidate of every FINISHED turn not already in the module-level cache or in flight. The cache is keyed by preference list + handle and lives for the page, so a remounted chat asks nothing it has asked, and a turn that finishes later gets one call for its NEW handles only. A turn still streaming (the last turn while state.running) passes null and is never asked. A failed call caches its handles as null: they stay code and are NOT retried, on this mount or the next (until a reload). An answer arriving after unmount fills the cache but sets no state. prefers[i] = turnPrefer(turns, i): what turn i's SUCCESSFUL calls acted on (a bind's target; a call the server marks in_base, the server's target, else the binding in force; a call without in_base adds nothing) and the store of a kb:// file they named, latest call first, then the binding in force when the turn began. A call that failed adds nothing, whichever tool it was: kb/decisions/web/chat/prefer-failed-calls/3abb79be.md (user decision, with its accepted cost). callTarget and the activity line still see failed calls; the binding in force is kept, and a failed bind does not move it (boundAfter). Tool RESULTS are not in the transcript, so a kb:// inside a result does not count. A kb://<id> repo chip needs the server's id lengths (12 hex or the full id).
3. ChatPanel builds remarkFactLinks(turnFacts[ti], repos) per turn and APPENDS it after chatPlugins/chatLivePlugins (order vs remarkCaret does not matter: it only touches inlineCode and tableCell). It wraps each turn in FactLinkContext.Provider.
4. chatComponents.code renders FactLink for data-fact and RepoLink for data-repo, otherwise a plain <code>; chatComponents.span renders FactLinksMore for data-fact-more and passes every other span (the caret) through.

Click dispatches the side panel's existing `open` with {kind:'fact', repo, branch, path} (branch is the resolver's, i.e. the repo's read branch); ChatFacet derives openKey from the shown entry, so EVERY link to the open fact is highlighted (data-open, .k-fact-link--open), in any turn. Cmd/Ctrl-click calls onBrowseFact(chatId, {repo, branch, path}), with the resolver's branch, which lands in Browse by the reveal path; Back there returns to the chat. The hover card has no Open in Browse (user decision): cmd-click is the way. The hover card is position:fixed at the chip's rect so a table's .k-chat-table-scroll does not clip it.

Gotcha: non-component exports (context, factKey, the hook) live in chatFactLinks.ts, not ChatFactChip.tsx, because react-refresh/only-export-components fails lint otherwise. Hover card (user rule: REUSE Browse's pieces, not a custom rendering): it renders Browse's FactMetaLine (kind flag, type, origin, 'conf 0.92', sources, and the repo drawn as a lens mount with its branch, via lensMeta) and FactBand's path row (FactBandPath, extracted from FactBand) from the resolver's fields; it is createPortal'ed to document.body because the link sits inside a <p> that may not hold FactMetaLine's <div>. Do NOT hand-write type badges, confidence labels or path lines in the card. Copy of its own: only factLinksMore ('+N').

Commit links: a code span the resolver answered with `commit` is marked data-commit and drawn by CommitLink as TimelineNav's own CommitHash component inside a button. Click dispatches the side panel's `open` with {kind:'commit', repo, branch, commit}; repo and branch are the resolver's item (ri.Name(), ri.ReadBranch()), so the read goes to the repo's read branch. It is never a lens: prefer may name a lens, but the resolver expands it to its members and answers a hash only when exactly one repo is preferred, naming that repo. openKey carries commitKey for a shown commit, so the chip stays highlighted while its commit is on screen. Why the panel: kb/decisions/ui/chat/commit-link-target/2c5e5366.md.

The commit view (ChatCommitView) reads api.commitDetail and mounts the timeline's own block (CommitBlock in TimelineNav.tsx), open, with the label 'Facts affected'; the timeline keeps 'Files affected'. What a row does is the other input. The server lists only paths under the ontology root, so .knomit/ and artifacts/ never arrive; the client also drops kb/ paths with a dot segment and non-markdown files, whose rows would open nothing. A commit with no facts shows the block with 'Facts affected · 0', and that includes an empty commit: a commit on branch_commits with no commit_log rows is known empty (the invariant kb/invariants/store/three-table-commit-index/0d26d859.md: the tables are written in one transaction), so CommitDetail answers from the commit object (hash, date, message, author, no files) rather than 404. A commit the repo does not hold, or holds without having recorded it, is still 404. A row's title is its title AT THAT COMMIT (commitDetail reads the file at the commit), and only a row the commit deleted takes its last title before the commit: any other row whose read fails stays untitled. The timeline's detail card reads the same rows. A fact row opens {kind:'fact', repo, branch, path, commit}. A fact the commit deleted is read as Browse reads any anchored fact, with ?fallback=before (edges too), so it shows the last version and the 'retracted at <hash>' badge. How the fact itself is drawn, and what its controls do, is in kb/decisions/ui/chat/panel-browse-chrome/64aa3076.md.

LIMITS of the cache (useTurnFacts, as merged): an entry is keyed by preference list + handle only, never by the repo's head, and is never invalidated while the page lives. So a handle that resolved to nothing (not a fact yet, ambiguous, or the call failed) stays plain code in every later turn with the same preference list, even after a later turn writes that fact; and a resolved link keeps the title, excerpt and branch it was first answered with. Only a reload asks again. Does NOT mean a click shows that snapshot: the panel reads the fact afresh (FactView), so the card and the panel can disagree after a change.
