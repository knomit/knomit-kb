# Chat fact links: the FINISHED turns' inline-code candidates are resolved in one POST /facts/resolve per mount (per distinct preference list), cached per handle+preference for the page's life; remarkFactLinks marks code spans data-fact / data-repo and collapses multi-fact table cells to first link + "+N"; chatComponents' code/span overrides draw them from FactLinkContext

Pipeline (web/src/chatFactLinks.ts, ChatFactChip.tsx, ChatPanel.tsx, chatTableBars.tsx):
1. factCandidates(answer) reads INLINE code only (fenced blocks are stripped first, prose is never read): an 8-hex short id, a slash path ending in .md or in an 8-hex segment, or kb://<store>/<path>. Bare repo names and kb://<store> without a path are NOT resolve candidates; they become repo chips from the page's repo list (ChatFacet's `repos` prop, from App) via repoChipName.
2. useTurnFacts(answers, prefers) sends ONE resolveFactHandles per effect run per distinct preference list (normally one: a chat stays bound to one target), carrying every candidate of every FINISHED turn not already in the module-level cache or in flight. The cache is keyed by preference list + handle and lives for the page, so a remounted chat asks nothing it has asked, and a turn that finishes later gets one call for its NEW handles only. A turn still streaming (the last turn while state.running) passes null and is never asked. A failed call caches its handles as null: they stay code and are NOT retried, on this mount or the next (until a reload). An answer arriving after unmount fills the cache but sets no state. prefers[i] = turnPrefer(turns, i): what turn i's calls acted on (bind target, repo/lens argument, else the binding in force) and the store of a kb:// file argument, latest call first, then the binding in force when the turn began. A failed bind counts for nothing (failedBind, boundAfter's own rule): a failed bind to a second reachable repo would otherwise make two preferred repos and stop a commit chip from resolving. Any other failed call still counts. Tool RESULTS are not in the transcript, so a kb:// inside a result does not count. A kb://<id> repo chip needs the server's id lengths (12 hex or the full id).
3. ChatPanel builds remarkFactLinks(turnFacts[ti], repos) per turn and APPENDS it after chatPlugins/chatLivePlugins (order vs remarkCaret does not matter: it only touches inlineCode and tableCell). It wraps each turn in FactLinkContext.Provider.
4. chatComponents.code renders FactLink for data-fact and RepoLink for data-repo, otherwise a plain <code>; chatComponents.span renders FactLinksMore for data-fact-more and passes every other span (the caret) through.

Click dispatches the side panel's existing `open` with {kind:'fact', repo, branch, path} (branch is the resolver's, i.e. the repo's read branch); ChatFacet derives openKey from the shown entry, so EVERY link to the open fact is highlighted (data-open, .k-fact-link--open), in any turn. Cmd/Ctrl-click and the hover card's Open in Browse call onOpenInBrowse(repo, path). The hover card is position:fixed at the chip's rect so a table's .k-chat-table-scroll does not clip it.

Gotcha: non-component exports (context, factKey, the hook) live in chatFactLinks.ts, not ChatFactChip.tsx, because react-refresh/only-export-components fails lint otherwise. Hover card (user rule: REUSE Browse's pieces, not a custom rendering): it renders Browse's FactMetaLine (kind flag, type, origin, 'conf 0.92', sources, and the repo drawn as a lens mount with its branch, via lensMeta) and FactBand's path row (FactBandPath, extracted from FactBand) from the resolver's fields; it is createPortal'ed to document.body because the link sits inside a <p> that may not hold FactMetaLine's <div>. Do NOT hand-write type badges, confidence labels or path lines in the card. Copy of its own: only 'Open in Browse' and factLinksMore ('+N').

Commit links: a code span the resolver answered with `commit` is marked data-commit and drawn by CommitLink as TimelineNav's own CommitHash component inside a button. Click dispatches the side panel's `open` with {kind:'commit', repo, branch, commit}; repo and branch are the resolver's item (ri.Name(), ri.ReadBranch()), so the read goes to the repo's read branch. It is never a lens: prefer may name a lens, but the resolver expands it to its members and answers a hash only when exactly one repo is preferred, naming that repo. openKey carries commitKey for a shown commit, so the chip stays highlighted while its commit is on screen. Why the panel: kb/decisions/ui/chat/commit-link-target/2c5e5366.md.

The commit view (ChatCommitView) reads api.commitDetail and draws TimelineNav's parts (CommitHash, CommitAuthorLine, CommitFilesLabel, CommitFileRow). The server lists only paths under the ontology root, so .knomit/ and artifacts/ never arrive; the client also drops kb/ paths with a dot segment and non-markdown files, whose rows would open nothing. A commit with no facts shows no label and no rows. A row's title is the fact's title at the branch's head when it still exists there (commitDetail reads the current index first), so a fact retitled later shows its newer title in the row and its older one once opened. A fact row opens {kind:'fact', repo, branch, path, commit}. Action 'deleted' adds removed:true: the plain read at that commit is 404 by design, so ChatFactView reads with ?fallback=before (edges too), shows the last version and a 'retracted at <hash>' line. With commit set the band shows that version's hash, date and vN (its place in the fact's history, not the history's length; left out when the commit is not in it). A commit with no commit_log rows (an empty commit) is on branch_commits, so its chip resolves, yet commitDetail answers 404 'commit not found in history index': the panel shows that sentence in its error line.
