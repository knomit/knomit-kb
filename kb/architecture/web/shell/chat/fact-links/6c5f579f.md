# Chat fact links: the FINISHED turns' inline-code candidates are resolved in one POST /facts/resolve per mount (per distinct preference list), cached per handle+preference for the page's life; remarkFactLinks marks code spans data-fact / data-repo and collapses multi-fact table cells to first link + "+N"; chatComponents' code/span overrides draw them from FactLinkContext

Pipeline (web/src/chatFactLinks.ts, ChatFactChip.tsx, ChatPanel.tsx, chatTableBars.tsx):
1. factCandidates(answer) reads INLINE code only (fenced blocks are stripped first, prose is never read): an 8-hex short id, a slash path ending in .md or in an 8-hex segment, or kb://<store>/<path>. Bare repo names and kb://<store> without a path are NOT resolve candidates; they become repo chips from the page's repo list (ChatFacet's `repos` prop, from App) via repoChipName.
2. useTurnFacts(answers, prefers) sends ONE resolveFactHandles per effect run per distinct preference list (normally one: a chat stays bound to one target), carrying every candidate of every FINISHED turn not already in the module-level cache or in flight. The cache is keyed by preference list + handle and lives for the page, so a remounted chat asks nothing it has asked, and a turn that finishes later gets one call for its NEW handles only. A turn still streaming (the last turn while state.running) passes null and is never asked. A failed call caches its handles as null: they stay code and are NOT retried, on this mount or the next (until a reload). An answer arriving after unmount fills the cache but sets no state. prefers[i] = turnPrefer(turns, i): what turn i's calls acted on (bind target, repo/lens argument, else the binding in force) and the store of a kb:// file argument, latest call first, then the binding in force when the turn began. Tool RESULTS are not in the transcript, so a kb:// inside a result does not count. A kb://<id> repo chip needs the server's id lengths (12 hex or the full id).
3. ChatPanel builds remarkFactLinks(turnFacts[ti], repos) per turn and APPENDS it after chatPlugins/chatLivePlugins (order vs remarkCaret does not matter: it only touches inlineCode and tableCell). It wraps each turn in FactLinkContext.Provider.
4. chatComponents.code renders FactLink for data-fact and RepoLink for data-repo, otherwise a plain <code>; chatComponents.span renders FactLinksMore for data-fact-more and passes every other span (the caret) through.

Click dispatches the side panel's existing `open` with {kind:'fact', repo, branch, path} (branch is the resolver's, i.e. the repo's read branch); ChatFacet derives openKey from the shown entry, so EVERY link to the open fact is highlighted (data-open, .k-fact-link--open), in any turn. Cmd/Ctrl-click and the hover card's Open in Browse call onOpenInBrowse(repo, path). The hover card is position:fixed at the chip's rect so a table's .k-chat-table-scroll does not clip it.

Gotcha: non-component exports (context, factKey, the hook) live in chatFactLinks.ts, not ChatFactChip.tsx, because react-refresh/only-export-components fails lint otherwise. Copy: only 'Open in Browse' (PANEL_OPEN_IN_BROWSE) and factLinksMore ('+N') are text; the card shows confidence as the bare number because a 'confidence' label was not approved copy.
