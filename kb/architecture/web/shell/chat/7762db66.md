# The rail is live from the page's one events stream: useChats watches it through watchChatStates and applies every chat's chat_state to its row; add() reads the hub's per-chat record (latestChatState); a reconnect re-reads GET /chats; a new answer is client-side (completed turns beyond the last seen)

useChats watches the page's single GET /chats/events stream through watchChatStates (chatEvents.ts), a page-level watcher that sees ready and every chat's chat_state whether or not that chat is listed or has a ChatFacet mounted, and that keeps the stream open even when no chat is listed. Each chat_state (title, state, turns, cost_usd, last_activity, started_at) is applied to that chat's row. The hub also keeps the latest chat_state per chat id (latestChatState; bounded by the owner's own chats, dropped on chat_end, cleared on each connect); add() reads it, so a chat created in this page starts with the state and first-message title the server already sent, and nothing is re-read for it. The connect-time ready is not a change (the list was just read); a later ready is a reconnect and re-reads GET /chats (the one watcher answers it, not one per chat). A chat_state that arrives while such a read is in flight is recorded per read and re-applied over the older answer when it lands, so an older list never undoes a newer event; a chat added after a read began keeps its added row over that read's row. The list is also read at load and on window focus. A chat created in another tab is unknown until the next read. A chat is 'new answer' when it is idle, not on screen, and completedTurns(row) (turns minus the running one) exceeds the value useSeenTurns last recorded; first sight sets the baseline so a reload shows nothing as new. Not meant: chat_state does not announce a chat this page has never listed (the record keeps its row for a later add(); the list gains no row from it).
