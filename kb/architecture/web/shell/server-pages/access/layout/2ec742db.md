# The Access server page is three Browse-like columns — SectionRail (Secrets, Authorizations), an item list, a detail panel — with the selection kept PER SECTION in AccessPage, the section overview when nothing is picked, and the Authorizations data read once (AuthProvider/useAuthData) and only while that section shows

web/src/AccessPage.tsx lays Access out as: sections (SectionRail at the target rail's 236px, glyphs only below ACCESS_MEDIUM_PX=960 of page width; an underlined SectionStrip tablist below ACCESS_NARROW_PX=640) -> list (SecretsList in SecretsTab.tsx, AuthList in ManageOAuth.tsx grouped Waiting / Approved) -> detail (SecretDetail / SecretCreate / SecretsOverview, PendingDetail / GrantDetail / RequestGone / AuthOverview). Width is the page's own, measured with useWidth (ResizeObserver), so jsdom (width 0, no ResizeObserver) renders the wide layout unless a test stubs clientWidth and ResizeObserver.

INVARIANT: ONE element tree at every width. The section slot, the list slot (data-testid access-list) and the detail slot (access-detail) keep their positions; a breakpoint only restyles them (narrow with an item open hides the list with display:none; narrow with nothing open stacks list over overview). Do NOT render a different tree per width: that remounts the columns and drops in-progress state (subject and scopes, a new secret draft, a hosts edit, the list search, a notice), which is what review of PR #795 caught. Consequence for tests: in narrow mode the list is hidden, not absent (assert not.toBeVisible, not toBeNull).

WHICH section shows is App's (accessTabsFor, useOAuthAvailability): AccessPage only reports picks through onTab. The PICKED ITEM is AccessPage state keyed by section; null means the section's overview. Secrets are read by AccessPage (the rail counts them and shows an expiry dot); the Authorizations queue and approved logins are read by AuthProvider via useAuthData, polling every 5 s ONLY while the auth section shows. AuthProvider also holds the Authorizations NOTICE as {at, text, tone}: `at` is the list key it is about (null = overview); it is shown only there and an effect in AuthSection.Detail drops it as soon as the selection moves elsewhere, so 'Revoked A' never shows above login B. Approve, Deny and Revoke all return to the overview with their notice; a re-approval that left the subject's grants unchanged (approvalNotice in oauthAccess.ts) is tone 'warn' (role alert), a first approval 'ok'. The Approved group is drawn only when api.listOAuthGrants answers non-null (404 -> null); a failed grants read keeps the last list. List ids: pendingKey 'p:<id>' and grantKey 'g:<id>' share one selection.

Keyboard (listKeys in accessUtil.ts): wide, ArrowUp/Down and j/k SELECT the next row, ArrowLeft focuses the rail, ArrowRight/Enter the detail. Narrow (focusOnly), selecting replaces the list with the detail, so arrows move FOCUS only and Enter is left to the focused row's own click. Each list has one Tab stop, tabStop(ids, selected): the selected row if listed, else the first, so a list with nothing picked is reachable by Tab. The rail's ArrowUp/Down picks the next section (wrapping), ArrowRight focuses the list. Tests drive Secrets and Authorizations THROUGH AccessPage; there is no standalone SecretsTab or AuthPage component. After Approve the approved login only appears under Approved once the client's browser collects the approval and it has a live code or a token.
