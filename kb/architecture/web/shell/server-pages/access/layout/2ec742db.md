# The Access server page is three Browse-like columns — SectionRail (Secrets, Authorizations), an item list, a detail panel — with the selection kept PER SECTION in AccessPage, the section overview when nothing is picked, and the Authorizations data read once (AuthProvider/useAuthData) and only while that section shows

web/src/AccessPage.tsx lays Access out as: SectionRail (AccessParts.tsx; at the target rail's 236px, glyphs only below ACCESS_MEDIUM_PX=960 of page width, an underlined SectionStrip tablist and one column at a time below ACCESS_NARROW_PX=640, measured from the page's own width with useWidth, so jsdom (width 0) always renders the wide layout) -> list (SecretsList in SecretsTab.tsx, AuthList in ManageOAuth.tsx grouped Waiting / Approved) -> detail (SecretDetail / SecretCreate / SecretsOverview, PendingDetail / GrantDetail / RequestGone / AuthOverview). WHICH section shows is still App's (accessTabsFor, useOAuthAvailability): AccessPage only reports picks through onTab. The PICKED ITEM is AccessPage state keyed by section, so switching sections and back returns to the same item; null means the section's overview. Secrets are read by AccessPage itself (so the rail can count them and show an expiry dot); the Authorizations queue and the approved logins are read by AuthProvider via useAuthData, polling every 5 s ONLY while the auth section is the one shown, and reporting the waiting count up through onAuthCount for the rail and the server tab. The Approved group is drawn only when api.listOAuthGrants answers non-null: a 404 (no issuer) is null, the same rule as listOAuthPending; a failed grants read keeps the last list. List ids: pendingKey 'p:<id>' and grantKey 'g:<id>' share one selection. Keyboard: listKeys (accessUtil.ts) ArrowUp/Down and j/k step the list, ArrowLeft focuses the rail, ArrowRight/Enter focuses the detail; the rail's own ArrowUp/Down picks the next section (wrapping), ArrowRight focuses the list. Tests drive Secrets and Authorizations THROUGH AccessPage (SecretsTab.test.tsx, ManageOAuth.test.tsx); there is no standalone SecretsTab or AuthPage component any more. After Approve the page goes back to the overview with a notice: the approved login only appears under Approved once the client's browser collects the approval (that is when the family is created).
