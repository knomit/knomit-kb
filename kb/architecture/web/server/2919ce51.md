# web.Server holds process-wide dependencies exactly once (LLM adapter, embedder, ONE MCP handler shared by every repo and lens) and nothing repo-scoped; everything repo-scoped is resolved per request from context through the narrowest injectable provider interface — so no per-repo object lives on the server and no process-wide dependency is threaded through repos

Process-wide dependencies are held once on the server object and repo-scoped state is resolved per request from the request context through narrow, injectable interfaces, so the two lifetimes never mix: a per-request resolution cannot be cached on the server, and a process-wide dependency is never carried inside a repo instance.

The three instantiations:
- PROVIDERS ARE PER-REQUEST SEAMS. The server carries a dozen-plus pluggable provider fields, each an interface; production fills a nil field with a default provider that reaches the store through the repo instance's scoped read (`ri.WithRead`), tests inject mocks, and the router applies `if provider == nil { provider = default }` before handing the provider to a handler factory closure. Handlers depend on the NARROWEST provider they need, never on the repo manager or the store service directly; reaching into the manager inline from a handler is the anti-pattern because it defeats mocking.
- ONE MCP HANDLER FOR ALL REPOS. `buildMCPHandler` (singular) constructs exactly one MCP server, built lazily inside `Server.Handler()` and never rebuilt; each request resolves its repo from context, and the authoring profile is resolved per repo at session start from the settings table, defaulting to 'code' whenever the manager, settings store, repo identity or row is unavailable — the default must never error a session. There is no map of handlers keyed by profile, profile is not a constructor parameter, and the `?profile=` query and bridge flag are accepted and ignored.
- PROCESS-WIDE STATE STAYS ON THE SERVER. The LLM adapter and embedder are constructed and held by the server; the synthesis-run handler is a package-level function taking ONLY the adapter, resolving the repo from context and creating the reviewer on demand per request from that repo instance. The former bundle that carried the reviewer and LLM through the repo instance was deleted, and the handler no longer takes the manager.

WHAT THIS DOES NOT MEAN: it does not say the server holds no per-request-resolved objects at all — it holds the seams that resolve them; the stale 'once-per-profile' path slug on the MCP fact does not describe HEAD; and the synth handler's 503 when the adapter is nil and 409 when a job is already running are its contract, not incidental.
