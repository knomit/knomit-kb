# Two knomit dependencies resolve by an IMPLICIT, layout-dependent mechanism that the shipped packaging happens to satisfy — so both look configured, work in dist/ and the .app, and fail only off that layout, where one surface keeps working and misdirects the diagnosis

Two independently-found gotchas instantiate one mechanism, and naming it is what makes the next instance findable before it bites.

THE SHAPE. A runtime dependency is located by an implicit resolver keyed to WHERE THE BINARY SITS — an exe-directory probe, or bare `$PATH` — rather than by anything the project declares. The shipped packaging satisfies that resolver as a side effect of its layout. So the dependency appears configured, works for everyone running the shipped artifact, and breaks only for someone running off that layout: a scratch `go build -o /tmp/…`, a Linux dev container, a code-server checkout, a test harness.

THE TWO INSTANCES.

1. ONNX runtime library. `initORT` resolves it two ways only — `os.Getenv("ORT_LIB_PATH")`, else a probe of `<exe dir>/lib/libonnxruntime.{so,dylib}` plus platform fallbacks. It never consults the loaded config. Meanwhile `config.ONNXLibPath` exists with TOML key `onnx_lib_path` and env overlay `ONNXRUNTIME_SHARED_LIBRARY`, is tilde-expanded, and is read by NOTHING: setting it has no effect. Off `dist/<platform>/` the probe fails and, because embeddings are mandatory, the boot DIES rather than degrading. The Dockerfile, the Makefile run targets and tools/calibrate all set `ORT_LIB_PATH`; they are the models to copy.

2. knomit-bridge for Claude Code hooks. `.claude/settings.json` wires SessionStart, PostToolUse (Edit|Write|MultiEdit, AskUserQuestion) and PreCompact as the bare command `knomit-bridge claude hook <name>`, resolved only via `$PATH`. Nothing puts it there: `make dist` builds `dist/<goos-goarch>/knomit-bridge` and refreshes the `dist/knomit-bridge` symlink, but never touches `$PATH`. On macOS the gap is invisible because Knomit.app symlinks `Contents/MacOS/knomit-bridge` into `<home>/bin` on every launch, specifically for a stable MCP command path; no container or code-server environment plays that role, because no desktop app is running. Fix: symlink the built binary somewhere already on `$PATH`.

WHY IT MISDIRECTS, which is the part worth carrying. The failure is PARTIAL, and the surface that still works argues against the real cause. For the bridge, `.mcp.json` wires the MCP server by EXPLICIT path (`${CLAUDE_PROJECT_DIR:-.}/dist/knomit-bridge`), so `mcp__knomit__*` tools work perfectly while the four hooks fail silently — two surfaces of one binary resolving it differently, which reads as an inconsistent integration rather than a PATH problem. For ONNX, a config key that LOOKS like the knob is sitting right there, so the natural first move — set `ONNXRUNTIME_SHARED_LIBRARY` — changes nothing and appears to rule the library path out.

CONSEQUENCE when adding any new external dependency: state how it resolves when the binary is NOT in the packaged layout, and make the declared configuration surface either operative or absent. A config key that is parsed but unread is worse than no key — it is a wrong answer that looks like the right one.

CARRIED FROM THE SOURCES, because the synthesis must not smooth them away:

- The ONNX config field is DEAD WEIGHT, not an alternative spelling. Either wire it into `initORT` or delete it — but do not document it as a knob.
- The bridge gap does NOT mean the knomit MCP integration is broken: `mcp__knomit__*` calls work independently of `$PATH`, via the explicit `.mcp.json` path.
- Scope: two instances, both verified on this repo. This is a named regularity worth checking for, not a proven law of the codebase.
