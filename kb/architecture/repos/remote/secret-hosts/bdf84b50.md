# A stored secret's hosts list is the ONE guard on where it is sent: checked at link time, at every resolution, and on every edit of the list itself; the URL scheme is not a second guard

Mechanism: a credential's permitted destinations are an explicit, operator-written allowlist that is re-checked at every point where a binding to a destination is created, used, or where the allowlist itself changes, so no single later change can route the credential to an unlisted destination.

The three enforcement points, all using control.HostAllowed (an entry equal to the remote host, or a bare-host entry equal to the remote's host name; a host:port entry allows only that port):
1. Link time: the repo's remote host must be on the secret's hosts list when it is linked.
2. Every resolution: the host is checked again at every git operation, so a later URL change to an unlisted host makes resolution fail as a sync error and the secret is never sent.
3. Edits of the list: Secrets.SetHosts / Secrets.Update refuses (HostInUseError, 409 naming the repos, writing nothing) a host-list change that would stop a linked repo's remote host from matching; at least one host must remain. Unlinking is the way to free a repo from a host.

Because the hosts list decides every send, the scheme is deliberately not a second policy: token and basic secrets are accepted on http:// and https:// alike (ssh_key needs an ssh URL), per checkSecretFits.

Host binding is necessary but not sufficient: linking, unlinking and URL changes on a linked repo also require admin plus the local-or-same-origin gate (requireLocalOrSameOriginAdmin); operator alone is not enough for any link-related action.

WHAT THIS DOES NOT MEAN: the host check at resolution is not optional or link-time only; allowing http does not loosen host binding and does not make plain http safe against an on-path observer (that risk is the operator's, by naming an http host); and it says nothing about fleet origins, which require https on their own (refuseFleetOrigin).
