# Cluster-cache refresh is deduped by an in-flight marker, not just singleflight

The cluster-cache `clusterSF` singleflight collapses concurrent Louvain COMPUTE for a key, but it does NOT dedup the DISPATCH or the staleness LOGGING. Because a long Louvain compute leaves the cache row stale for its whole duration, the 5s background checker (`checkBranchClusters`) and the read path both re-fired a refresh and re-logged `cluster cache: triggering refresh` / `stale, returning cached + async refresh` on every tick — ~18 log pairs per ~90s compute.

Fix: `searchIndex.clusterRefreshing` is a `sync.Map` holding the SET of cluster keys (`clusterCacheKey` = branch|resolution|minCommunitySize) with a refresh in flight. It is keyed, NOT a single atomic flag, because one `searchIndex` is per-repo and serves MANY branches that refresh concurrently (refreshClustersAsync detaches each compute into its own goroutine + context, and per-key singleflight does not collapse across branches) — a single flag would let one branch's ~90s compute suppress every other branch's refresh. `LoadOrStore(key, struct{}{})` is the atomic test-and-claim; `Delete` releases; `Load` is the read.

Both compute paths set the marker:
- STALE async: `refreshClustersAsync` does `LoadOrStore`; if already present returns `started=false` so the caller skips launching a goroutine AND skips the log; the goroutine `Delete`s on done.
- COLD sync: `CachedClusterFacts` !found path `LoadOrStore`s best-effort; if it was absent it `defer Delete`s, else it still computes via the singleflight (no cached row to return) and lets the acquirer clear.

New `Searcher.ClusterRefreshInFlight(branch,resolution,minCommunitySize)` (a `Load`) lets `checkBranchClusters` `continue` (no dispatch, no log) while EITHER path's compute runs. Net: exactly one trigger + one stale/cold + one refreshed per staleness window.

History: first implemented with `map[string]struct{}` + `sync.Mutex` + tryMark/clear helpers; simplified to `sync.Map` (commit 8d8e3b6) — same semantics, LoadOrStore replaces the explicit lock.

Separately, `ClusterFacts` logs `cluster compute: louvain timing` (probe/louvain/postfilter durations + `attempts` + nodes/communities), DEBUG normally and WARN when louvain ≥ `slowClusterLouvainThreshold` (5s) — diagnostic for the slow-louvain investigation. See [[louvain-slow-under-write-contention]].
