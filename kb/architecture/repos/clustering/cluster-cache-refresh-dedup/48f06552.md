# Cluster-cache refresh is deduped by an in-flight marker, not just singleflight

The cluster-cache `clusterSF` singleflight collapses concurrent Louvain COMPUTE for a key, but it does NOT dedup the DISPATCH or the staleness LOGGING. Because a long Louvain compute leaves the cache row stale for its whole duration, the 5s background checker (`checkBranchClusters`) and the read path both re-fired a refresh and re-logged `cluster cache: triggering refresh` / `stale, returning cached + async refresh` on every tick — ~18 log pairs per ~90s compute.

Fix: `searchIndex` holds `clusterRefreshing map[string]struct{}` guarded by `clusterRefreshMu`. `refreshClustersAsync` atomically check-and-sets the key (returns `started bool`; false ⇒ a refresh is already running, so the caller skips launching a goroutine AND skips the log). The marker is held for the goroutine's whole lifetime (compute included). New `Searcher.ClusterRefreshInFlight(branch,resolution,minCommunitySize)` lets `checkBranchClusters` `continue` without dispatching/logging while a compute runs. Net: exactly one trigger + one stale + one refreshed per staleness window.

IMPORTANT: this covers the STALE path only. The COLD sync path (`CachedClusterFacts` computing on a missing row) does NOT set the marker, so a slow first-ever compute on a branch could still re-log per tick. The singleflight key and the in-flight key share `clusterCacheKey(branch,resolution,minCommunitySize)`.
