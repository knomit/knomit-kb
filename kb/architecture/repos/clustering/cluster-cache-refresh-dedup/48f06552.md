# Cluster-cache refresh is deduped by an in-flight marker, not just singleflight

The cluster-cache `clusterSF` singleflight collapses concurrent Louvain COMPUTE for a key, but it does NOT dedup the DISPATCH or the staleness LOGGING. Because a long Louvain compute leaves the cache row stale for its whole duration, the 5s background checker (`checkBranchClusters`) and the read path both re-fired a refresh and re-logged `cluster cache: triggering refresh` / `stale, returning cached + async refresh` on every tick — ~18 log pairs per ~90s compute.

Fix: `searchIndex` holds `clusterRefreshing map[string]struct{}` guarded by `clusterRefreshMu`, with helpers `tryMarkClusterRefreshing(key) bool` / `clearClusterRefreshing(key)`. BOTH compute paths set the marker:
- STALE async: `refreshClustersAsync` check-and-sets and returns `started bool` (false ⇒ already running ⇒ caller skips launching a goroutine AND skips the log); goroutine clears on done.
- COLD sync: `CachedClusterFacts` !found path marks best-effort (`tryMarkClusterRefreshing`; if already held it still computes via the singleflight since there is no cached row to return — only the acquirer clears via defer).

New `Searcher.ClusterRefreshInFlight(branch,resolution,minCommunitySize)` lets `checkBranchClusters` `continue` (no dispatch, no log) while EITHER path's compute runs. Net: exactly one trigger + one stale/cold + one refreshed per staleness window. Singleflight key and in-flight key share `clusterCacheKey(branch,resolution,minCommunitySize)`.

Separately, `ClusterFacts` now logs `cluster compute: louvain timing` (probe/louvain/postfilter durations + `attempts` + nodes/communities), DEBUG normally and WARN when louvain ≥ `slowClusterLouvainThreshold` (5s) — diagnostic for the slow-louvain investigation. See [[louvain-slow-under-write-contention]].
