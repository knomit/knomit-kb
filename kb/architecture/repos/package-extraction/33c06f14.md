# internal/repos owns lifecycle, internal/web is pure HTTP — repos NEVER imports web (no import cycle)

internal/repos owns repo lifecycle management: RepoInstance, TaskHub, Manager, the background reconcile loop, context helpers (RepoFromContext / RepoFromContextOpt / WithRepoInstance in context.go), ResolveLensBinding, SwapStore. internal/web is pure HTTP — router, handlers, SSE, git remote, AND all middleware.

CRITICAL INVARIANT (verified at HEAD): internal/repos NEVER imports internal/web (no import cycle); internal/web imports internal/repos for types; cmd imports both via the internal/app package. Anti-pattern (FORBIDDEN): adding HTTP-aware code to internal/repos — a handler needing repo state accesses it via ri.WithRead / accessor methods through *repos.Manager. Why the boundary matters: the HTTP layer stays testable in isolation and the lifecycle layer is reusable by other entry points.

MIDDLEWARE NOW LIVES IN WEB (changed by P1.4, 2026-07-21). RepoMiddleware moved from internal/repos/middleware.go to internal/web/repo_middleware.go, and internal/repos/middleware.go no longer exists. This move HAPPENED IN ORDER TO PRESERVE this fact's own invariant, which is the opposite of what a casual reading suggests: the middleware had to emit RFC 9457 problem+json to match the 34 hand-written repo lookups it was replacing, and problem+json lives in internal/web/hal — so keeping the middleware in repos would have forced repos to import web. Moving it to web was the only option that did not break the cycle rule. BranchMiddleware already lived in web while using repos.WithBranch, so this follows existing precedent rather than inventing one.

THE LENS MIDDLEWARE WAS SPLIT, NOT MOVED — and the reason is a trap worth knowing. internal/mcp/lens_endtoend_test.go is `package mcp` (not mcp_test) and drives the lens middleware directly. Since internal/web imports internal/mcp, moving the lens middleware wholesale into web would have created an import cycle THROUGH A TEST FILE — an easy thing to miss, because the production dependency graph alone does not show it. Resolution: repos.ResolveLensBinding (internal/repos/lens_resolve.go) owns registry lookup and binding minting and returns a classified *LensResolveError; web.LensMiddleware (internal/web/lens_middleware.go) owns status/title/problem+json rendering. Domain resolution in repos, HTTP rendering in web. Apply the same seam if another middleware ever needs to move.

WHAT THIS DOES NOT MEAN: this fact was seeded from the extraction PLAN and several plan-era symbol names are STALE — do not rely on them. The lifecycle entrypoint is Manager.Start() (manager.go), NOT Boot(). Sync is ONE goroutine, runReconcileLoop (sync.go), doing Sync-then-Push — NOT separate runSyncLoop/runPushLoop. There is NO setupMCP in this package. cmd/serve.go reaches the Manager through internal/app (app.New -> a.Manager()), it does NOT call repos.New/m.Boot inline. Only the package-boundary invariant (no cycle; repos=lifecycle, web=HTTP) is load-bearing; verify any symbol name against code before relying on it.
