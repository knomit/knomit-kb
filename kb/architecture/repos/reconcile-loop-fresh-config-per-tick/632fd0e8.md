# runReconcileLoop re-reads remote config FRESH every tick; 5 consecutive failures escalate WARN→ERROR

runReconcileLoop re-reads svc.Remote().GetRemote('origin') FRESH on every tick so DB-stored config changes (auth update, interval change) are picked up on the NEXT tick without restarting the loop. The initial config read at loop start is only for log context — the actual sync uses the fresh record. Failure escalation: reconcileFailureEscalateThreshold = 5 consecutive failures escalate the log line from Warn to Error (a repo stuck on revoked credentials otherwise looks identical to a healthy one after log rotation drops the early warns). The counter resets to 0 on first success after failures, with an 'after_failures' log line so operators can see recovery. Order within a tick: Sync runs FIRST, then Push. On sync success with mainChanged OR agentChanged, hub.broadcastSyncOK fires with the full SyncResult including Mode discriminators. syncFails and pushFails are INDEPENDENT counters — each escalates on its own consecutive-failure streak.

WHAT THIS DOES NOT MEAN: a Sync error does NOT skip the Push. The sync-error branch (sync.go:131) logs and increments syncFails but does NOT return — execution falls through and Push still runs, gated ONLY by pushAllowed(readOnly) (sync.go:156). Do not assume a failed pull suppresses the push attempt. The single early-return that skips BOTH Sync and Push is an AUTH-RESOLUTION failure (sync.go:112); a local-origin policy block (sync.go:104) and a nil/failed fresh remote read also skip the tick before sync/push.
