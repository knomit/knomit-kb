# consensus: auto merges every pushed peer branch into the HOST's AGENT branch (never the consensus branch), asynchronously, and only on a no-origin, writable, non-subscribed repo. Under auto an absent `conflicts` defaults to facts: merge / state: consensus, so a conflict is settled with the host's branch as the consensus side; only a key explicitly set to off leaves a conflict refused, warned once per (branch, tip) and left for a human UI merge

F08 PR B (ruling R5). The root ontology attribute `consensus` (`off` | `auto`, absent = off, scope root; registry entry AttrConsensus in internal/fact/ontology.go) is read by `fact.ReadConsensus` from the ontology at the tip of the repo's CONSENSUS branch, resolved with `svc.UpstreamBranch()` and read through `store.Service.OntologyAt` — never at the agent branch and never at a hardcoded "main". Any value other than off/auto reads as OFF with one WARN per ontology blob (safe: off only means 'leave it to a human'), so a later value such as a recipe reference is ignored by this binary.

The merger (`consensusMerger`, internal/repos/consensus.go) is built in `Manager.newInstance` under the same guard as the trigger dispatcher — agent branch non-empty (a subscription has none), not `cfg.ReadOnly`. Its lifetime is the Serve stage's Life (issue #411): Serve.Enter calls life.Go("consensus", c.run); it exposes run(ctx) only (one round is runOnce) and stops when the Serve life is cancelled, which happens before Open's Exit closes the store. It runs under Options.Synchronous too.

Kick: `ri.onCommit` sends one non-blocking kick for every commit on a branch that is NOT the agent branch and NOT `exp/*` (`consensusKicks`). That covers a peer's push (receive-pack's register → notifyCommit on the peer branch) and the consensus branch advancing (N2: turning auto on takes effect without a new push). onCommit never reads the store (it runs under the writer's branch lock); the merge runs on the merger goroutine, so the push POST never waits for it (T-B7).

Run: not auto → nothing. Repo has an origin (GetRemote("origin") != nil) → nothing, WARN once naming the origin URL (the origin owns the consensus branch). Otherwise, for every branch `isPushedBranch` accepts, `Service.MergeConsensus(peer, agentBranch, tip)`: StrategyRefuse with NO side, host-signed merge commit [agent tip, peer tip] (MergePushed's record semantics). Conflict / unrelated histories / no signer → the (branch, tip) is memoised and not retried until that branch's tip moves, WARN once, the branch stays in the Pushed branches list. ErrBranchMoved → ignored (the new push kicked again). Other errors → WARN once per (branch, tip, error), retried at the next kick. After any merge it calls `ri.wakeSync()`, so the local reconcile fast-forwards the consensus branch within the push countdown instead of the interval.

Why the agent branch: AdvanceLocalUpstream only fast-forwards and skips when the consensus branch is not an ancestor of the agent branch; a merge written into the consensus branch would freeze it for the host's own facts forever (T-B1's sabotage).

Consequence: once merged, a peer's fact fires the HOST's triggers with change.source = "merged" (T-B6), including `do: run` recipes — F11's 'host triggers do not fire on pushed branches' still holds for the pushed branch itself, not for what the merger brings into the host's own branch.

Misreading to avoid: 'auto merges into main' is false. SINCE CONFLICT-MERGE PR 2, 'auto never picks a side' is false. Under `consensus: auto` an ABSENT `conflicts` (an object {facts, state}) reads `facts: merge` / `state: consensus`. MergeConsensus therefore merges a conflicting fact field by field (fact.MergeVersions), keeps a fact one side retracted retracted, and gives every other conflicting path, and any fact it cannot merge losslessly, the host's version (the host's own agent branch is the consensus side). The merger refuses and memoises only what a key set to off leaves: `conflicts: {facts: off, state: off}` restores the PR B behaviour (and the F1 gotcha). Other values: `merge:consensus` makes a field both changed take the host's value, and `facts: consensus` takes the host's whole version. MergeConsensus reads the setting itself at svc.UpstreamBranch()'s tip, the same place autoAt reads `consensus`.

## UPDATE (PR #524, verified at merge commit 9db8c106): the fleet repository is the exception to everything above

The description above (the `consensus: auto` gate, no origin, the `conflicts` auto-default) holds for every repository EXCEPT the fleet repository. In consensusMerger.runOnce, `if m.ri.IsFleet()` takes a different gate: the merge runs only where `RepoInstance.isFleetMaster(svc)` holds (fleet door, fleet repo, Manager master predicate: root key file here AND its certificate is the root on main), on every hosting, with or without an origin; the origin is not read and `consensus` is not read (the built-in fleet ontology declares none). The non-fleet gate moved unchanged into consensusMerger.mayMerge. A member's fleet copy merges nothing.

On the fleet repository the merger also re-judges each local agent/* branch against the CURRENT main before merging it (`fleetPeers.mayMerge`, memo on (branch, tip, main)): a branch admitted before main moved (a revocation) and now refused is recorded (`last_refusal`) and DEMOTED (its local refs/heads/agent/<x> dropped, only while still at the judged tip) instead of merged. This holds on a knomit-hosted hub too. On a forge the branches reach the host through the master's own fetch (AdmitPeerBranch), not through a push; the merger merges them the same way.

The conflict behaviour changes with it: the fleet ontology no longer declares `consensus: auto`, so the `conflicts` auto-default (facts: merge / state: consensus) does not apply to a fleet created or refreshed after #524, and a conflicting member branch is refused and left behind. A fleet created before #524 keeps the old default until the master's ontology refresh rewrites main's ontology (harmless, self-healing).
