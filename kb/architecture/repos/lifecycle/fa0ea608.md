# Repo open serves immediately; heavy index runs in the background with per-repo IndexStatus

Manager.openOne builds the RepoInstance with a LIVE store first (openStore->openGit->loadOntology->ensureBranch->setupIndex->seedWatermarks->build), then runs the heavy index heal (healIndexBranches: Rebuild when schema-stale, else Sync) in a BACKGROUND goroutine — so the HTTP server / web UI come up immediately at startup and after a clone, instead of blocking ListenAndServe until indexing finishes (the prior synchronous open was why the API/UI 'didn't come up' during a startup rebuild). build() is SPLIT: it constructs ri + the startSync closure + closeFn but DEFERS recoverFromOrigin + startSyncLoops to b.activate(), which the background goroutine calls only AFTER the index completes — so the reconcile loop and commit observer never race the initial index build (two writers on one SQLite). The goroutine watches b.syncCtx (cancelled by shutdown/Archive and Manager.Close), so a close mid-index aborts the heal and skips activation.

RepoInstance.IndexStatus() reports ready|indexing|error + done/total, surfaced in the branch/status response (which also computes index_percent: 0-100, 100 when ready). The web UI shows an 'indexing' banner (and an 'error' banner) and reads return partial results progressively until ready (git is source of truth; the index is a warmable cache). DisableBackgroundSync (test harnesses) takes the SYNCHRONOUS path (heal + activate inline) so the open->index-ready contract holds.

ERROR-STATE SEMANTICS (PR #82 review fix): healIndexBranches now RETURNS ok bool — false when a Rebuild of any branch fails OR the initial Sync of the AGENT branch (index 0, the one local reads depend on) fails. An upstream-only Sync failure (index > 0) is logged but NON-fatal (reconcile loop owns upstream convergence), so it does NOT flip to error. The caller marks the index 'error' only when ok==false; on syncCtx cancellation it marks NOTHING (a clean shutdown is not a failure — the prior code wrongly marked failed on cancel and never on a real heal failure, so 'error' was effectively inverted/dead). On a failed heal it STILL calls activate() so the sync/push loops can retry and recover; the error state reflects only that the INITIAL heal did not fully complete and is not reset by later loop activity (re-heals on next startup).
