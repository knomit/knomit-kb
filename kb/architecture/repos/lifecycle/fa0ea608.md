# Repo open serves immediately; heavy index runs in the background with per-repo IndexStatus

Manager.openOne builds the RepoInstance with a LIVE store first (openStore->openGit->loadOntology->ensureBranch->setupIndex->seedWatermarks->build), then runs the heavy index heal (healIndexBranches: Rebuild when schema-stale, else Sync) in a BACKGROUND goroutine — so the HTTP server / web UI come up immediately at startup and after a clone, instead of blocking ListenAndServe until indexing finishes (the prior synchronous open was why the API/UI 'didn't come up' during a startup rebuild). build() is SPLIT: it constructs ri + the startSync closure + closeFn but DEFERS recoverFromOrigin + startSyncLoops to b.activate(), which the background goroutine calls only AFTER the index completes — so the reconcile loop and commit observer never race the initial index build (two writers on one SQLite). The goroutine watches b.syncCtx (cancelled by shutdown/Archive and Manager.Close), so a close mid-index aborts the heal and skips activation. RepoInstance.IndexStatus() reports ready|indexing|error + done/total, surfaced in the branch/status response; the web UI shows an 'indexing' banner and reads return partial results progressively until ready (git is source of truth; the index is a warmable cache). DisableBackgroundSync (test harnesses) takes the SYNCHRONOUS path (heal + activate inline) so the open->index-ready contract holds.
