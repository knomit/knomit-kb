# TaskHub runs no work and holds at most one running and one last-terminal event per op; tasks enter only via TaskPublisher.PublishTask, which records a terminal before publishing it and overwrites a running entry (there is no single-flight)

TaskHub (internal/corpus/repos/events/hub.go) runs no work. It holds two maps under h.mu: `active` (op to latest running TaskEvent) and `lastDone` (op to last terminal TaskEvent). Nothing older is kept, and nothing survives a restart.

RECORDING. A task enters the hub only through TaskPublisher.PublishTask(ev), and the publisher is held only by the repos parent (kb/decisions/repos/events/hub-publisher-split/f6d5c104.md). In production the one caller is the lifecycle machine's manual index rebuild (op `rebuild`, ids chosen by the machine). PublishTask with status `running` sets active[op] = ev, OVERWRITING any running entry of that op. With status `done` or `error` it deletes active[op] only when that entry's ID equals ev.ID, then sets lastDone[op] = ev. Both happen under h.mu BEFORE h.ob.Publish(ev). Publishing first let a Subscribe see the task running and never receive its end, which hung a per-job events stream (PR #623 F1; regression TestTaskHub_SubscribeRacingATerminalNeverMissesIt, a 2000-iteration stress loop racing a terminal PublishTask against repeated Subscribes). An event with any other status is published but not recorded.

READING. Subscribe(ctx) registers the subscription AND collects a snapshot under the same lock: every active event, plus each lastDone event whose op is not active, so a reconnecting SSE client renders the right state at once. Task(id) returns the running or last terminal event with that id. Tasks(op) returns the running one first, then the last terminal one: at most two, none before the op's first run. These are what the web job routes read (kb/decisions/web/jobs/taskhub-is-the-only-job-record/c514ec1b.md).

MISREADINGS.
- "The hub refuses a second running task of an op (single-flight, 409)": no. That was TaskHub.Start, which PR #791 deleted along with the `<op>-<counter>` ids, the emit closure and its idempotent termination, the panic recovery, the cancels map and TaskHub.Cancel. PublishTask simply overwrites active[op], so single-flight for the rebuild is the lifecycle machine's job.
- "A terminal clears the op's running entry": only when the ids match. A terminal for another id sets lastDone and leaves active[op] as it was.
- "The hub can cancel a task": no. It holds no task contexts; a rebuild is cancelled through the machine's CancelIndex.

HISTORY. This fact's path names the per-op single-flight that TaskHub.Start enforced from PR #623 until PR #791 (merged as 02d41850) deleted Start. The path cannot change; the claims above are what holds at that merge, re-read there.
