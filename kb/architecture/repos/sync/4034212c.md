# Sync reacts to a stored secret's VALUE and LINKS only, never to its metadata: expiry is a UI flag that neither gates sync nor resets breakers, while a value replace, link, unlink or pasted-token swap resets the breakers and wakes sync

Mechanism: the sync loop's behaviour is driven only by changes to what is actually sent to the forge (the credential value and which credential a repo is linked to); descriptive metadata about the credential is surfaced to people and never fed back into sync control.

Metadata side (advisory only): the server computes a secret's status (ok, expiring, expired, none; expiring = within control.ExpiringWithin, 14 days). Sync keeps using an expired secret; expiry does not gate, disable or deprioritise sync, and nothing calls forges in the background to verify tokens. The UI flags the secret and every linked repo (GET /repos credential_status 'expiring'/'expired' only, drawn as CredentialChip; the Remote block's problem flag from GET /origin secret_status). Absence of credential_status means nothing to flag, not healthy. credential_status is not a sync failure signal and does not drive the failing-remote red dot. No notifications outside the UI.

Value/link side (acts on sync): replacing a secret's value, linking or unlinking a repo, and the light pasted-token swap reset the fetch and push circuit breakers of every affected repo and then wake its sync. This is a deliberate, scoped exception to the breaker decision; nothing else resets breakers.

WHAT THIS DOES NOT MEAN: the breaker reset is not a general license to reset breakers on other events such as renames, expiry changes or URL edits; and an 'expired' flag is not evidence the token fails (the forge is the authority).
