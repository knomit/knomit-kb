# internal/corpus/repos/control owns the control.db registries (Registry, LensRegistry, Origins, VerifyAccepts, ArchiveReason, the lens re-key migration, ErrRepoExists); consumers import control directly and the repos parent re-exports nothing

At 6c0f1a78 (PR #595, step 14a of the internal/ hierarchy) package internal/corpus/repos/control holds the control.db registries: Registry, LensRegistry (Lens, LensRead), Origins, VerifyAccepts, ArchiveReason, the lens re-key migration (lens_migrate.go) and ErrRepoExists. Consumers import control directly; the repos parent re-exports nothing (no-facades rule 44ec3b17). Methods whose receiver is *Manager or *RepoInstance stayed in the parent. control imports only engine/store.

NEWLY EXPORTED, the only new exports of the split: ControlUp (the ordered bring-up, see 52a6318e; called by Manager.Start after OpenRegistryNoSchema) and TableExists (used by the parent's read-only fleet_identity.go probe, which deliberately does NOT go through ControlUp). Both were unexported while the files shared a package. Review follow-up (a5a54428): ErrInvalidProfile, ErrLensNameEmpty and ErrRegistryNotFound had no outside user and were UNEXPORTED (errRegistryNotFound is still returned, wrapped, by registry.go, so it was unexported rather than deleted). ProfileGeneric (keeps the Profile enum whole) and ArchiveSource (type of the exported ArchiveReason.Source field) stay exported on purpose.

LAYERING: no sameLayerEdges entry was needed for corpus/repos -> corpus/repos/control: parent<->child imports are always allowed (isFamily), and every outside importer of control is in edge/, cmd/ or test/ (downward). No archtest guard named a moved file (the repos guards already walked the tree), so no guard key changed; the review sabotaged a WriteSystemTree selector in a throwaway control file and TestStoreSystemTreeDoor_OnlyFromRepos caught it, so the child stays covered.

CONSEQUENCE: a test that needs a Manager (newLifecycleManagerWithRoot, m.LensRegistry()) stays in the parent; the child's tests use only control.db handles. Parent tests that also need control's helpers use copies in control_fixtures_test.go in the parent (seedMember, openTestOrigins, testCrypt), because exporting test helpers from control would add speculative public API; the review accepted the ~25 duplicated lines. DOES NOT MEAN: control has no tests needing a store (control_durability_test runs there but only checks pragmas), nor that the control.db migrator lives in control (it is internal/engine/store/migrate).

SIBLING (14b, PR #631, merge 37dc65d5): the next child, internal/corpus/repos/events, follows the same handle-getter shape (Manager.RepoEventHub() beside LensRegistry(), Origins(), Repos()) but adds a rule control did not need: the hubs' publishing halves are separate publisher values the parent keeps private (kb/architecture/repos/events-child/e2f5bc64.md). A child that publishes events gets its publisher as a parameter, never a getter.

SIBLING CHILDREN (PR #632, merged as ee850fd6): the repos parent now has three children, control (this fact), events (kb/architecture/repos/events-child/e2f5bc64.md) and trigger (the dispatcher, kb/architecture/repos/triggers/dispatcher/a01f40fc.md). Unlike control, which consumers import directly, trigger is reached through the parent's RepoInstance.Triggers() handle, and its run loop is a capability held only by the parent (kb/decisions/repos/triggers/run-func-capability/03d92e7a.md). The 14c step completes the internal/ restructure.
