# A recipe runs BESIDE the dispatcher: phase B only resolves, takes a `concurrent` slot WITHOUT blocking (full → `busy` row, no queue), mints run-<32 hex>, records `started` and starts a goroutine; the result row comes back through a mutex-guarded late inbox (d.lateIn) that only the dispatcher goroutine drains into pending.late, and pendingFlush.empty() counts it — else a result with no new commit is never written

internal/corpus/repos/trigger_recipe.go startRecipe/runJob/addLate/drainLate and internal/corpus/repos/triggers.go (F07 PR 5, rev 2.1 M1, D4, D6).

Flow: phase B's `case p.trig.Do == fact.TriggerDoRun` (its own case, ahead of the emit default arm) calls startRecipe: resolve → rc.tryTake(name, limits.Concurrent) → newRunID() → d.rc.wg.Add(1); go d.runJob(d.runCtx, job). The fire's row is `started` (counted in fires) / `busy` / `recipe-error`, carrying recipe_source, recipe_rev, run_id. runJob: jitter (after the slot), fact.RunRecipe under context.WithTimeout(runCtx, limits.Timeout) with the binding and the fire's trailers, slot released, result row (same run_id, the fire's range copied, duration_ms = the recipe's wall time; the result text in `message` for done/spawned/delivered and in `error` only for failures — store.IsRecipeFailure, migration 000033, kb/architecture/repos/triggers/recipes/run-rows/c4520572.md) → addLate → triggerKick.

Late rows [M1]: the runner NEVER touches d.pending (flush ends with resetPending and would drop a concurrent append). run() calls drainLate(svc) right after its Acquire (before phase A, which may return early); flushOnStop drains too. empty() includes len(p.late), so settle flushes them after the 20 ms grace with no new commit; flush writes them with RecordTriggerResults (no run row, own range, prune in the same tx). A failed or cross-generation flush, or a crash, loses them (stated, D4).

Stop: the loop's ctx.Done arm waits d.rc.wg FIRST (every recipe derives from runCtx, so it is interrupted and its process group/job killed), then flushOnStop — that is how the `recipe-error … stopped` rows reach the table (TestRun_StopKillsAndRecords). knomit.run from a script returns at once and adds its start row to the fire's rows (scriptHost.onRow → rows appended after the `ran` row); from inside a recipe, onRow is addLate.

At-most-once after the flush: a clean stop/restart never re-runs a recipe; a CRASH before the fire's phase C is flushed re-fires the range and runs it once more (TestRun_CrashBeforeFlushReRunsOnce pins the window with the skipFlushOnStop hook).

A second narrow re-run window sits beside the crash one (reviewer n2): a stop that cancels phase B after a recipe has already started loses the `started` row (an aborted phase B records nothing), so the range re-fires on restart and the recipe runs again; the killed recipe's own `stopped` result row is still written by the final flush.
