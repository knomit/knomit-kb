# The script rate cap is script RUNS per trigger per minute — a sliding window of run instants (the run's clock) kept in memory per trigger — from `[triggers].script_rate_per_minute` in knomit.toml (env KNOMIT_TRIGGERS_SCRIPT_RATE_PER_MINUTE; default 60; Load refuses < 1; a literal Config with 0 falls back to config.DefaultScriptRatePerMinute); fires beyond it are DROPPED as `rate-limited` rows, never retried, with one WARN per cap episode; there is NO per-trigger ontology key

Ruling D-rate (2026-09-28): "keep the brake per minute, per trigger"; the default "with default but should be configurable in toml"; "Toml is enough" — no `rate:` entry key (an older binary would have marked such an ontology invalid). Implementation: `triggerDispatcher.sc.rate` from `newScriptState(tools, cfg.Triggers.ScriptRatePerMinute)`; `rateAllows(name, rs.now)` trims entries older than one minute and refuses when the window holds `rate` entries; it is checked in `runScript` AFTER `if` held and the script is loaded, so only runs that would start are counted (an `if-false` costs nothing, an emit trigger is never capped). A dropped fire is a `store.TriggerFire` row with outcome `rate-limited`, counted in `TriggerStatsView.RateLimited`, and the bookmark moves past it — the burst is gone on this machine; only the rows and the counter say so. The WARN ("trigger script rate cap reached") is logged once per (trigger, blob) cap episode; a run that goes through resets it.

The window uses the RUN's clock (rs.now, the `now` test hook, UTC at whole seconds), so tests move time with the fake clock (parkDispatcher keeps the installed hooks, clock included); the cap test's burst is one BatchWriteFacts commit, the realistic shape of a merged burst.

This is the only brake on two scripts feeding each other (60 + 60 commits a minute by default until someone fixes a script). Validation lives in config.Validate ("triggers.script_rate_per_minute must be >= 1"): there is no unlimited setting.

EXCEPTION FOR `due` (F08 PR A, M3): a DUE fire that the cap drops is not lost. Its due mark is not written (runState.dueRetry), so the next sweep — the next tick or write — fires it again, bounded by the tick, never a hot loop. "Never retried" above holds for learn/update/retract fires only. See kb/invariants/repos/triggers/due-marks/db770fa9.md.
