# `do: push` / knomit.push() is ONE non-blocking send on ri.syncWake (a 1-slot channel on the RepoInstance, not the loop, so it survives ActivateSync's restart); both sync loops gain a wake arm that runs a FIXED 1 s countdown from the first wake (pushWakeWindow, not a debounce), drains the slot, then runs ONE ordinary tick — one round running, one pending

F07 PR 4 (user rulings D-local, D-window, D-report, 2026-09-28).

Send side. Phase B has its OWN `case p.trig.Do == fact.TriggerDoPush` ahead of `default:` (the emit arm): it calls d.wakeSync() → ri.wakeSync(), a `select { case ri.syncWake <- struct{}{}: default: }`, and records outcome `kicked` (counted as a fire; no SSE event, no commit, no trailer, one Debug line). scriptHost.push does the same send and returns `{ok: true, status: "kicked"}`; it ignores its arguments (nothing can name a branch) and the fire stays `ran`. The send carries nothing: the loop pushes only its own agent branch with the unchanged refspec, so a wake can never publish a peer's branch, main or exp/*.

Receive side (sync.go). runReconcileLoop and runLocalReconcile take `wake <-chan struct{}` (nil in unit tests: never ready). On a wake the loop calls awaitPushWindow: it waits pushWakeWindow (1 s, a const) WITHOUT listening to the channel, so later fires only fill the slot and cannot restart or extend the countdown; then it drains the slot (those fires are this round) and runs one ordinary doTick (fetch, merge, push of the branch head as it is at that moment). A fire that lands during the round stays in the slot and opens the NEXT countdown when the round returns — exactly one follow-up, never a queue. The countdown for such a fire starts when the running round ends, not at the fire's own instant.

Start and restart. Both loops drain the slot once before their first tick (that tick covers every earlier commit). runReconcileLoop also checks ctx.Err() at the top of every iteration, so a loop that ActivateSync is cancelling exits before its select and never consumes a wake it would not act on; the new loop's first tick drains it. The slot lives on the RepoInstance (built in build()); startSyncLoops passes b.ri.syncWake (nil without an instance) and the ActivateSync closure passes ri.syncWake.

No origin (D-local): the local loop's wake arm runs exactly the ticker body — kickTriggers(), ownsMain() with its exit on a definite origin (the two loops stay mutually exclusive), then AdvanceLocalUpstream only when it owns main. main follows only this machine's agent branch, so a wake never publishes peers' facts sooner.

D-report: the fire never learns whether the round succeeded; that is the remote's last_sync/last_push status, the banner and the log. A `kicked` row means 'asked', not 'pushed'.

Misreading to avoid: the kick SEND never blocks and the tick never runs on the dispatcher goroutine — that does NOT mean phase B is free of the network: see the agent-branch-lock gotcha (Push holds lockBranch across the network push).

Accepted as merged (user, 2026-09-28, verbatim: "343 will be merged as is."): the countdown for a fire that lands during a round opens when that round ends, not at the fire's instant.

**Since F21 S2:** a third sender shares the slot. Under `sync: {push: realtime}` (read by the loop at the consensus branch's tip and cached in `ri.realtimePush`), `ri.onCommit`'s agent-branch arm calls `ri.wakeSync()` for EVERY commit on this instance's agent branch — no trigger needed. It coalesces with `do: push` fires in the same 1-slot channel (one countdown). The local loop's fixed ticker became a per-round timer (`loopWait`), so the wait can follow `pull: realtime`; the wake arm is unchanged. See kb/architecture/repos/sync/sync-mode/c125223d.md.
