# The `on: due` sweep is a phase-A step of the SAME dispatcher run as the advances: candidates are the index's liveness join (branch_facts of the agent branch ⋈ fact_expires, expires_at <= the run's clock), filtered glob → marks → confirmed against the HEAD tree → one `change` per path; every run sweeps, tick-kicked or write-kicked, and the sweep has no timer of its own

F07 PR 2 (branch feat/f07-due). Where the sweep runs: inside triggerDispatcher.phaseA, after the tree-episode half (`advance`), as `sweepDue` — so a due fire shares the run's Acquire, phase B (`if` + emit, no store held), the write-behind phase C buffer, the statistics and the slow-trigger detector with the advances. It runs on EVERY run (D4 (i)): a write-kicked run and a tick-kicked run both sweep. It has NO schedule of its own: the reconcile tick kicks the dispatcher (sync.go), that is all.

What one sweep does, IN THIS ORDER (M1, cheap filters first, so a processed or unmatched due fact never costs a blob read on any run):
1. `tr.DueCandidates(ctx, branch, now.Unix())` — ONE indexed query: `SELECT bf.path, fe.expires_at FROM fact_expires fe JOIN branch_facts bf ON bf.fact_id = fe.fact_id WHERE bf.branch_id = (SELECT id FROM branches WHERE name = ?) AND fe.expires_at <= ?` (plan: covering-index range on fact_expires_at, then a branch_facts_fact probe per row; linear in the number of PAST-DATED fact versions in the table, independent of KB size). A run with a due trigger but nothing due costs this query and nothing else.
2. the glob of the ACTIVE triggers whose `on` lists due (`ct.Matches(rel)`, rel = path minus the ontology root) — no match → the row is dropped;
3. the marks (`tr.DueMarks`, read ONCE per run and only when step 2 matched something, with the write-behind buffer's pending marks overlaid by overlayPending): a trigger whose mark for (trigger, path) holds the candidate's expires_at is done; a DIFFERENT instant is a re-arm;
4. the HEAD tree is the truth: `cr.trees.BlobAt(head, path)` + ParseFact; absent, unparseable, undated or `expires > now` at the head → skipped. The index is the FINDER; the tree DECIDES. This closes the window between a writer moving the ref and the index Sync and makes 'a removed fact never fires' hold by construction. The mark is then re-checked against the HEAD's instant (not the candidate row's), and candidate rows are deduplicated per path, so a stale or duplicate candidate row can never produce a second fire;
5. `buildChange` once per path with episode `due`: `source = "due"`, `before = null`, `commit` = the toucher at the head (the commit that introduced the content the path carries), `trace` from its trailer, `author.verified` per the 1b rule; one pendingFire and one DueMark{trigger, path, expires_at = the HEAD's instant, fired_at = the run's clock} per surviving trigger.

The run's clock is read ONCE per run (`triggerDispatcher.clock`: `time.Now().UTC().Truncate(time.Second)`, or the `now` test hook) and compared with `<=` at whole seconds — F03's inclusive rule (`expires_at == now` is due). It is the ONE clock comparison in F07; a wrong system clock fires early or late on that machine only, and two machines each fire on their own clock and tick (no cross-machine coordination is claimed).

Run-row rule (M1): the run row and stats.recordRun happen when `rs.paths > 0 || len(rs.dueMarks) > 0` (runState.didWork); `paths` on the row includes the distinct due paths evaluated; a tick-only run has range_from = range_to = the head it read. An idle 30 s tick on a repo whose due facts are all processed writes NO run row and is not counted (otherwise 2,880 rows a day would enter a 10,000-row log).

What a `due` trigger is: `due` is in activeTriggerOn since PR 2 (internal/fact/triggers.go), so `[learn, due]` and `[due]` triggers are `active`; the tree side keeps the 1b bookmark rules; a fact learned already past its date fires learn AND due in the same run (D3, two rows, `change.episode` tells them apart); `[update, due]` fires update and due together when the date is moved to another past instant. First appearance: no seeding — the currently overdue set is processed once on the first sweep (D2 (a), maintainer ruling 'the feature was never live'), and the same after a store swap, a rename or a remove-and-re-add (all detected only by a missing bookmark row).

What it is NOT: nothing else happens on expiry — the sweep emits and marks; it never writes, hides, deletes or retracts a fact (F03's ruling stands); `.knomit/` and other dot paths are never candidates (not indexed, glob refuses dot segments); exp/*, main, read-only servers and subscriptions never fire (the join is on the agent branch's id; there is no dispatcher on the last two).

Misreading to avoid: 'the sweep reads fact_expires' — it never reads fact_expires ALONE; the table is per fact VERSION and shared by every branch (see the gotcha on fact_expires liveness). Tests: internal/repos/triggers_due_test.go (T1–T27), internal/store/triggers_due_test.go.
