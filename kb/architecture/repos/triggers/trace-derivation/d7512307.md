# A fire's `trace` is DERIVED and never empty since F07 PR 3 (`deriveTrace`): the toucher's Knomit-Trace copied forward; else, when the firing fact is an F01 task (pragmatic `signal` with exactly one entity), that entity; else the firing commit's own hash — so one cause is one story on every machine and on a re-fire, and `git log --all --grep='^Knomit-Trace: <C>'` lists a story's descendants below its root C

`buildChange` (internal/repos/triggers.go) sets `pf.trace = deriveTrace(m.trace, pf.factMap, pf.commit)` after the fact map is read; `change.trace`, the fire-log `trace` column, the SSE `trigger` event and the Knomit-Trace a script's writes carry are all this value. Only script writes are STAMPED in PR 3 (ruling D-mint: "agreed, no" — human, session, REST and synthesize commits get no trailer); a story rooted in a human write is found by that write's hash, which the first script commit names as both its trace and its cause.

Why a derived id, not a random one: the same firing commit on two machines, or a re-fire after a crash (at-least-once), yields the SAME story id; a random id would split one cause into two stories per re-fire. The three id kinds (40-hex commit, `task-…` entity, and later PR 5's minted ids) never collide by construction.

Consequence for an old expectation: TestDispatch_TraceFromTrailer's "without a trailer → empty" became "→ the commit hash".
