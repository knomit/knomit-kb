# A ref's meaning is split on the HEAD-independence line: KIND (syntax + repo identity) is computed once by a pure leaf, while RESOLUTION is commit-dependent and is only ever recorded per ref-event at the referrer's commit — never evaluated at HEAD, never server-reported as a status

A reference's meaning is split into a part that is invariant across history — its kind, a function of syntax plus repo identity — and a part that depends on the referrer's commit — whether and to what it resolves — and the system computes the first part once in a pure leaf while the second part is only ever recorded or resolved pinned to a specific commit, so no reader is ever handed a HEAD-time answer to a commit-time question.

How the split is enforced:
- KIND lives in `internal/fact` as `fact.ClassifyRef(raw, localRepoID) -> fact.Ref`, pure and I/O-free; every classifier call site consumes it (edge builder, knomit_explain, web UI, federate's qualified-path parsing delegates DOWN to it) and a completeness test fails the build if any file outside internal/fact re-derives classification from raw scheme checks. This replaced three divergent implementations that disagreed on a typo'd local path.
- RESOLUTION lives in `internal/refs` (formerly refgate), which may import store because resolving needs corpus access and repo identity; `internal/fact` may not, and `TestFactStaysPure` enforces that direction. The boundary is stated in the package doc as 'resolution, NOT classification'. Nothing catches gratuitous migration INTO refs, so keeping pure helpers (parsing, shape validation, kind) out of it is on the author.
- In the graph, resolution is recorded as one immutable `DERIVED_FROM` edge per ref-event carrying (source_commit, target_commit): 'at source_commit, this version of the source pointed at the version of the target active then'. Edges accumulate across a fact's history, are written POST-COMMIT through the single unexported writer (no public add-edge API), and are NEVER deleted on retraction; the query layer hides deleted endpoints instead. They must be written through `graphInsertEdgeReturningID` (plain INSERT) — routing them through the OR IGNORE helper silently swallows every ref-event after the first for a pair.
- In the UI, clickability is gated on kind alone and the hop is handed to the commit-anchored time-travel machinery, which pins the version the referrer reasoned over.

WHAT THIS DOES NOT MEAN: a fact's DERIVED_FROM out-edges are NOT a mirror of its current refs — read the fact record for current refs, never the graph. Retracting or updating a fact does NOT clean its edges; that is by design. Adding a server-computed `status` field to the fact API re-introduces the HEAD-time bug this split removed: a fact opened at an older commit whose target was later retracted would be labelled broken although its ref resolves at the referrer's commit. 'Put anything ref-related in internal/refs' is the named misreading of the package rename; a pure helper there forces every parser to link the store closure.
