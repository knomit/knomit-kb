# A fact may ref a FILE under .knomit/ — `.knomit/<path>` or `kb://<id>/.knomit/<path>` classify as local_system_file / foreign_system_file (path verbatim, case kept); the write gate refuses one whose file is not at the branch tip; explain pins it at the referrer's own commit with NO graph edge

Built on branch feat/system-file-reads (#428); synthesize gates and symlinks added in #437 (merge 4c716446) (user ruling 2026-10-06: "if we cannot get to the js file now because it's not a fact, let's fix it"; decision 3: a file ref pins the file at the referrer's commit).

CLASSIFICATION (internal/domain/fact/ref.go, still the single authority). A ref whose repo-relative path starts with the exact, lowercase `.knomit/` — bare, or after `kb://<12-hex>/` — is a SYSTEM FILE, not a fact: `local_system_file` when bare or the id is the caller's own, `foreign_system_file` otherwise. Path is kept VERBATIM (SKILL.md ≠ skill.md); fact paths are still lowercased. Malformed (RefMalformed, refused by ValidateRefs at write): the bare root, an empty segment (`//`, trailing `/`), a `.` or `..` segment. Dot segments BELOW the root are allowed (`.knomit/templates/mission/.knomit/triggers/claims.js`). `.KNOMIT/x`, `.github/x`, `kb/.drafts/x.md` stay fact-kind refs exactly as before (and the gate refuses them as missing facts). RefIdentity keys them as `file|<path>` (plus repo id when foreign).

WRITE GATE (internal/refs). `Gate.WithFiles(resolver)`: a NEWLY ADDED local system-file ref must name a FILE (not a directory, not a symlink) in the tree at the tip of the branch the write lands on — `refs.FromSystemFiles(files *facts.Repo, branch)` (it took the store.SystemFileIndex interface until PR #575 deleted it) — or the whole write is refused in the same one-error list, its own section with the fix line "does not exist under .knomit/ at the tip of the branch this write lands on". Carried refs are not re-judged (prior), keyed apart from fact paths. A gate built WITHOUT a file resolver refuses a newly added one ("cannot check refs to .knomit/ files") rather than letting it through. Wired: knomit_learn, knomit_update, REST POST/PUT (writerGate), experiment resolutions (resolveGate: either side), and every synthesize gate (#428 follow-ups). In internal/synthesize ONE constructor, writeGate(localRepoID, idx, files, branch), builds all six gates (reflect, distill, prune merge, dedup merge, discovery, reinforce) with the fact resolver and the file resolver at the SAME branch, the session's. `files` is the *facts.Repo of the Service the caller writes through (Service.FactsRepo()): Pipeline.storeIndices hands the fact resolver (store.FactQuery) and the *facts.Repo out of one Service under one read lock, and synthesize carries it as Deps.Files. (Until PR #575 this was the store.FactIndex, which embedded store.SystemFileIndex; both types are deleted.) Only reflect (all-or-nothing: one bad ref aborts the whole reflect), distill (warn and skip that fact) and the prune merge (warn and skip that merge; a ref no member carried is new) can meet a NEW .knomit/ ref, because the model writes their refs; the other three add only fact paths or carry refs as prior. TestSynthesize_OneRefGateConstructor fails the build on any refs.New in internal/synthesize outside ref_gate.go. Before this, those gates refused EVERY new .knomit/ ref ("cannot check refs to .knomit/ files"), including refs to files that exist. Foreign system-file refs are never checked. Canonicalize stores a local one as `kb://<own-id>/.knomit/<path>`, case kept.

READING (knomit_explain). There is NO DERIVED_FROM edge and no index change: because the pin is the referrer's own commit, the child is a pure function of (fact version, ref), so explain derives it from the fact's parsed refs at the node's commit (`systemFileChildren`, first call and resume). .knomit/ never enters the graph or the index. This deliberately deviates from design v3 §2 item 3 (an index edge); it keeps the refs→DERIVED_FROM invariant (kb/invariants/store/refs-to-derived-from-edges/eb438c74.md) untouched.

WHAT THIS DOES NOT MEAN: a ref does not make .knomit/ writable, listable or queryable; a `system_file` ref is not "broken" for want of a fact (REST ref views give it kind `system_file`, path, no link); and the gate's tip check is a one-time write check — a file later removed from .knomit/ does not invalidate the fact (explain then shows the node `deleted: true`). SYMLINKS (user ruling 2026-10-08, "we do NOT want to follow symlinks, so 404"): facts.Repo.SystemFileAt (formerly store.SystemFileAt) reads a symlink entry as absent (found=false, not an error), like a directory. It needs an explicit symlink clause because go-git's Mode.IsFile is true for a symlink. So the gate refuses a new ref to one as "does not exist", REST GET is 404 and explain shows a cited one `deleted: true`. An executable (+x) file is still a file.

RE-VERIFIED at the PR #575 merge f41adda1: refs.FromSystemFiles(sf *facts.Repo, branch string) ResolveFunc is in internal/refs/refs.go and calls sf.SystemFileAt(ctx, branch, "", path, 0); synthesize's writeGate(localRepoID, idx store.FactQuery, files *facts.Repo, branch) in internal/synthesize/ref_gate.go adds the file resolver only when files is non-nil, so a nil files still REFUSES a new .knomit/ ref. facts.Index.SystemFileAt (a forward) was deleted; the reader is facts.Repo.SystemFileAt in internal/store/facts/system_files.go.
