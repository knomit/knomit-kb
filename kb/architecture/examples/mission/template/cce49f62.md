# examples/mission/ is a copyable mission repo built from generic primitives only: ontology (consensus: auto + conflicts {facts: merge, state: consensus} + sync {push: realtime, pull: realtime} written out, no do: push triggers), one file script per take pattern (claims.js: offer/decide/dup-check; awards.js: bid/award/take-award), inline js: expiry, two skills, and a recipe that tells the session to call knomit_skill work-task

F08 PR D. The template ships under examples/mission/ and is copied with `cp -R examples/mission/. <repo>/` (the trailing /. matters: `cp -r mission/*` drops .knomit/).

Layout (paths under the ontology root):
- tasks/<lane>/ (claim/wait/take), claims/<task-id>/<agent-id>/, inbox/<agent-id>/working/ (the queue) and inbox/<agent-id>/active/ (copies a session took), acks/<task-id>/;
- offers/<awarder-agent-id>/<lane>/, bids/<awarder>/<task-id>/<bidder>/, awards/<winner>/ (host-awarded).
Every topic is signal-only by validation and learn_dedup: off. Triggers are per topic (the Ontology root has no triggers field): inline `js:` for expiry (`expire`, `expire-offer`, and the block-scalar `withdraw-bid`), `script: claims` for offer/decide/dup-check, `script: awards` for bid/award/take-award, `do: run recipe: work-task` for wake (on: learn, match inbox/{agent}/working/**) and, since #388 (feat/mission-drain-inbox, merged at 56da0d0e), for lease (on: due, match inbox/{agent}/**). 11 triggers (10 before), all active on a real host (TestMissionTemplate_LoadsAsIs, and the cmd route test on host, peer and restarted host).

Since #383 (feat/mission-template-realtime, merged at c6c2625b, 2026-10-01): the root attributes also write out `sync: {push: realtime, pull: realtime}` (F21 S2), and the four `do: push` triggers (push-claim, push-take, push-bid, push-award) were REMOVED: realtime push already opens the 1 s push countdown for every commit on the instance's own agent branch. TestMissionTemplate_Settings fails if the sync object is missing, if either key is not realtime, or if any trigger is `do: push`. CONSEQUENCE: an operator who drops `sync` (e.g. on GitHub, for the request cost) gets NO fast path at all — every write waits for the 300 s round — and must raise X back to the 300 s rule.

Pattern 1 (claims.js): rank = FNV-1a 32-bit of `task|agent-id`, ties broken by the agent id string (total order, TestMissionTemplate_RankIsTotal). The winner takes with ONE knomit.learn(workingCopy, {retract: [task, own claims, dead claims]}); losers re-arm their claim's expires by knomit.update; a claim more than 2X past its expires no longer ranks (the re-offer). dup-check makes the lower-ranked holder of a second working copy retract its own. The claim window WINDOW_SECONDS is 15 s (was 360 s before realtime sync): see the timing-rule fact in kb/decisions/fleet/f08/claim-window-realtime/.

Pattern 2 (awards.js): the award trigger matches bids/{agent}/**, so it runs on the awarder only; each award is the F04 move 'write awards/<bidder>/..., retract the offer', so a second award is refused by the retract precondition under the awarder's branch lock: exactly one award per offer (TestMission_HostAwardedExactlyOnce).

The recipe passes the working copy by PATH only (task_path). Since feat/mission-drain-inbox the session it starts is UNBOUND and drains the whole queue: see kb/architecture/examples/mission/session/unbound/111ffc86.md, kb/architecture/examples/mission/queue/take-lock/98a83215.md and kb/invariants/examples/mission/queue/lease/ed443981.md. No template file names a branch (TestMissionTemplate_Settings greps for main/master/trunk/develop).

MISREADING: the template's `conflicts` block is NOT behaviourally load-bearing under consensus: auto (F20's auto default is the same values); only the static settings test pins that it is written out. CONSEQUENCE: an operator who deletes it gets the same behaviour on a knomit host, but the GitHub variant (consensus removed) MUST keep it, or conflicts fall back to off.

ADDRESSED by feat/mission-drain-inbox (the session drains working/, and the `lease` due trigger re-wakes a session for a copy whose wake was dropped as busy; TestMission_LeaseWakesDroppedCopy reproduces the busy drop and its recovery). The original note, kept for history — OPEN (reviewer N3 on #383, live check): in one run, one of two tasks assigned to the HOST did not wake the fake claude. Likely cause, not yet confirmed: the recipe busy-drop (D6). work-task.js declares `concurrent: 1`, and a recipe at its limit DROPS the fire with a `busy` row — there is no queue (trigger_recipe.go tryTake; kb/architecture/repos/triggers/recipes/runner/e3a210c6.md). Two working copies landing while the first session still runs would leave the second unwoken. CHECK IN THE FIRST REAL MISSION RUN: look for a `busy` outcome on the `wake` trigger in the trigger fires; if that is the cause, either raise `concurrent` or make the work-task skill pick up every working copy in inbox/<agent>/working/ rather than only the one it was woken for.
