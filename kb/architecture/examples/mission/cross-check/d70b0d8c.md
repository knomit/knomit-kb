# Mission cross-checks never update shared facts and make no commit on the target KB: each writes one annotation per check: path into the MISSION repo (annotations/<its task id>/, context.kind: verdict, kb:// ref to the checked fact), and ONE fold task, posted after the round's acks, reads them by path plus context and is the only writer of the hypotheses, inside one experiment on the target KB

Since the F26 template follow-up PR (branch feat/f26-mission-shape, against dev), replacing #410's verdicts/<task id>/ topic in the companion examples/mission-kb/ (deleted). The problem is unchanged: parallel tasks that knomit_update the same fact in per-task experiments cannot all land as written (kb/gotchas/missions/experiments/parallel-updates-conflict/1133a108.md). The template splits a cross-check round in two:
- Cross-checks, in parallel, each assigned to one checker: the post-task skill's `cross-check-task` block goes in the body (with the exact `check: <path>` lines, kept from #410: they fixed F-R4). For each checked fact the session writes ONE annotation with knomit_learn on the MISSION handle: topic annotations, category <task id>, type observation, context {kind: verdict, verdict: corroborate|contradict, confidence: what the fact deserves}, refs = kb://<target repo id>/<path> first, then evidence. It never updates what it checks and writes NOTHING to the target KB. The work-task skill's Call shapes carry this call (TestMissionTemplate_SkillCallShapes asserts binding <mission>, category <task id>, context.kind verdict, first ref kb://).
- The fold: ONE task, ONE agent, posted only after every cross-check acked (Done or Failed). The `fold-task` block: knomit_query on the mission handle with path <root>/annotations/<id>/ and context {kind: verdict} per cross-check, FOLLOWING the cursor until has_more is false (with include_body one page holds at most 5, so a fold over a nine-fact cross-check that reads one page silently misses four, contradictions included; review R1 finding 1, pinned by TestMissionAnnotations_FoldReadsEveryPage with the work-task skill's own first-page and cursor skeletons); group by the kb:// ref; then, inside this task's ONE experiment on the target KB (the work-task loop opens it), per fact ONE change: knomit_update (confidence, evidence added to refs since updates.refs REPLACES the list, a sentence in the body summarising the verdicts), a merge (update one, retract the other) or knomit_retract; a strong contradiction adds a counter-hypothesis via knomit_learn with distinct_from naming what it counters (honoured by learn's dedup since #412; not stored, so knomit_review can still merge them later). It never refs the annotations from the KB: nothing in the target points at the mission repo. The fold block carries no hypothesis format (there is none since F26). Coordinator discipline, not enforced: an early fold is safe (single writer), only incomplete.
- Paths, not 'not your own': the coordinator picks check: paths from git authorship on the TARGET KB: writer = `git log --diff-filter=A --format=%an -1 <consensus branch> -- <path>`; a checker's own name = the author who added a fact its earlier task wrote, or `git log --no-merges -1 --format=%an <its agent branch>` (a plain -1 can be a sync merge carrying another author).

Verified on two instances by TestMission_CrossCheckAnnotatesFoldWrites (internal/repos): the work-task skill's own annotation skeleton, routed by its binding placeholder, is run on H and on P; both land at two paths under kb/annotations/ and every branch tip of the target KB is unchanged; the fold's read (the skill's query skeleton) returns exactly each task's verdict; the fold's update waits in its experiment and, after the commit, every new target commit carries Mission-Task: <fold task>; knomit_explain shows the hypothesis's earlier revision and the fold's change. Sabotage: pointing the skeleton at <kb>, or filing it under a shared category, turns it red.
