# The mission template's trace is mission/task/session: Knomit-Trace = the mission repo's name, Mission-Task = the task id, Knomit-Run = the run (one session); the task cannot ride in Knomit-Cause because the trace argument accepts Knomit-Cause only as a full lowercase commit hash

Built by the F26 template follow-up PR (feat/f26-mission-shape), on the user's 2026-10-06 rule 'trace = mission, cause = task, run = session'. Before it, examples/mission/.knomit/recipes/work-task.js stamped Knomit-Trace = the waking commit's trace (the task id) and Knomit-Cause = the waking commit.

Why not Knomit-Cause = task id: internal/mcp/trace.go parseTrace refuses a Knomit-Cause that is not ^[0-9a-f]{40}$|^[0-9a-f]{64}$ and a Knomit-Run that is not run-<32 hex>, and refuses any other Knomit-* key; the brief forbade Go changes. So the task travels in an agent-owned key, Mission-Task (keys: letters/digits/hyphens <= 32 chars; value one line <= 128 bytes). The session's trace carries NO Knomit-Cause. This mapping was the worker's call within that constraint and was flagged for the user in the PR.

Who sets what:
- recipe: {Knomit-Trace: missionRepo(), Knomit-Run: run.id, Mission-Task: fact.entities[0]} — Mission-Task left out unless the id matches ^[A-Za-z0-9._:-]{1,128}$.
- work-task skill: every write (take, results, experiment open/commit/rollback, ack) passes that trace; for other copies it drains, the same Knomit-Trace and Knomit-Run with that copy's Mission-Task.
- post-task skill's posting skeleton: {Knomit-Trace: <mission repo name>, Mission-Task: <task id>}, and the skill says the trace is REQUIRED on a post (review R1 finding 3; TestMissionTemplate_SkillCallShapes pins both). knomit's deriveTrace (internal/repos/trigger_script.go) copies the firing commit's Knomit-Trace forward onto trigger-script writes, so claims/takes for a task posted this way carry the mission too; a task posted WITHOUT a trace gets the task id as its scripts' Knomit-Trace (deriveTrace's F01 fallback), while the session still stamps the mission.

Reading back: git log --all --grep='^Knomit-Trace: <mission repo name>' (the whole mission, mission repo and target KB, provided every post carried the trace), --grep='^Knomit-Run: <run id>' (one session). --grep='^Mission-Task: <task id>' finds ONLY the poster's and the sessions' writes: trigger-script writes (claims, the take into working/, dup-check back-offs, offers/bids/awards) carry knomit's own set (Knomit-Trace copied forward, Knomit-Cause = the firing commit, Knomit-Trigger), never Mission-Task. MISREADING to avoid: a Mission-Task grep showing no claims does NOT mean nobody claimed the task; find claims by path (kb/claims/<task id>/, inbox copies whose one entity is the task id) or through Knomit-Cause (review R1 finding 2). Before F26, Knomit-Trace: <task id> returned the whole task story; one grep per task again needs the parseTrace change the PR flags. Pinned by TestMission_RecipeStartsUnboundStrictInTempDir (exact map), TestMission_OneTaskTwoClaimersOneTakes, and TestMission_CrossCheckAnnotatesFoldWrites (every new target-KB commit carries Mission-Task of the fold).
