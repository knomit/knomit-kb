# The mission recipe starts claude UNBOUND, strict and sandboxed: one MCP server `kb` with args [] built by the recipe (not mcp.config), --strict-mcp-config, --allowedTools mcp__knomit,WebFetch,WebSearch, --max-budget-usd MAX_BUDGET_USD, cwd = a fresh `mktemp -d` removed in a finally; the session knomit_binds the mission repo and the task's KB itself and opens one experiment per task on the KB handle

examples/mission/.knomit/recipes/work-task.js since feat/mission-drain-inbox (user ruling 2026-10-01: "the recipe in claude's case should run in a temporary folder, with knomit available, but not bound to any repo - use dynamic binding. The recipe can also use experiments to make sure the work is doing is atomic").

- MCP: {"mcpServers":{"knomit":{"command":"kb","args":[]}}} as a JSON string to --mcp-config. kb with no --repo/--lens serves the unscoped mount; the KNOMIT_SERVER knomit puts in the recipe env (its own local socket, or its TCP address when that socket is not its own) makes it reach THIS knomit, and Claude Code passes its environment on to the stdio MCP servers it starts (measured, Claude Code 2.1.287), so the MCP config names no address. CORRECTION (2026-10-02, first-mission rehearsal): this used to say KNOMIT_HOME in the recipe env did it. It did not: `kb` took its server from its argument or the desktop lockfile, never from KNOMIT_HOME, so with a rehearsal instance beside the main one the session reached the MAIN instance. --strict-mcp-config keeps the user's own MCP servers out (without it claude -p loads them, the personal lens included).
- Mission repo name: no recipe global names the repo (globals: fact, agent, change, payload, task_path, mcp, run), so the recipe reads it from knomit's own entry for this repo: JSON.parse(mcp.config).mcpServers[mcp.server].args after "--repo". Never hardcode it (TestMission_RecipeStartsUnboundStrictInTempDir runs the peer as repo `crew-ops`).
- Prompt: an instruction (knomit_bind the mission repo, knomit_skill work-task with that binding) plus ONE JSON literal of data: mission_repo, working_copy, experiment, lease, trace. No task text.
- The recipe skips claude when the woken copy is gone AND working/ is empty, and starts it whenever either holds work (TestMissionTemplate_RecipeStartsOnlyWhenQueued runs the shipped recipe in goja with stub globals, both ways).
- Session side (work-task skill): two handles — mission (copies, acks, the skill) and the KB the task names in its body (`knowledge base: repo <name>` / `lens <name>`). Per task: open experiment <kebab(task id)> on the KB handle (strict kebab-case: lowercase, runs of non [a-z0-9] -> '-', trimmed, <= 64, the same rule as the recipe's experimentName), work there with trace, commit, then ack on the mission handle; a refused open or commit -> rollback + 'Failed:' ack. On the unscoped mount the experiment rides on the handle, so the mission handle keeps writing the agent branch.

KNOWN LIMITS (README): an unbound session can bind ANY repo or lens its knomit serves — the skill binds only what the task names, a hard limit needs the session's knomit to serve only the mission's repos; knomit_experiment takes no trace, so the experiment's merge commit is untraced (its fact commits keep theirs); mktemp and rm must be on knomit's PATH (Windows: Git Bash).

Tests stand in for every external program: the recipe helper acts as mktemp / rm by argv[0] and reports its cwd (internal/repos/triggers_run_helper_test.go).
