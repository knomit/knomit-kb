# Server and bridge compute the local listener path INDEPENDENTLY, so every input one process evaluates on its own (environment, cwd, executable location, validation scope) is a silent divergence channel — each known channel is excluded, isolated, routed through one function, or recorded as an accepted gap

Two processes that must arrive at the same rendezvous by computing it separately will diverge whenever any input to that computation is evaluated per-process rather than shared, and because the fallback on a miss (TCP) succeeds, the divergence costs the verified identity without raising any error; so the design rule is that the rendezvous may depend only on inputs both processes are guaranteed to see identically, computed by one function, and every per-process input must be deliberately excluded, isolated, normalised, or documented as a known gap.

How each channel is handled today (details and evidence are in the members):
- EXCLUDED — environment variables an MCP host may filter from the bridge: the long-root fallback uses the LITERAL /tmp/knomit-<euid>, never TMPDIR, XDG_RUNTIME_DIR or os.TempDir (long-home-fallback decision).
- ISOLATED — failures unrelated to the socket: config.SocketPath deliberately does NOT call config.Load, because Load's Validate and every other KNOMIT_* parse would turn an unrelated config problem, or a bridge launched with a different environment, into a silent TCP fallback (socket-path-not-load gotcha). Misreading to avoid: 'the bridge should just call Load to be sure it agrees' — agreement comes from the shared functions, not from sharing Load.
- ONE FUNCTION — the layering itself: config.socketFor (KNOMIT_SOCKET > knomit.toml socket > localListenerName of the tilde-expanded home) is reached by both config.Load and config.SocketPath, both starting from config.homeAndConfig; the bridge resolves no layer itself (listener-layering invariant). A new layer goes into socketFor at both call sites, never into one resolver.
- ACCEPTED GAPS — findConfigFile checks beside os.Executable() before <home>/knomit.toml, and a relative KNOMIT_HOME or socket path resolves against each process's own cwd, so a knomit.toml beside only one binary, or a relative path, can still split the two sides (toml-beside-executable gotcha). These are knowingly unfixed, safe only because the binaries ship side by side, and tracked in knomit#274 together with the unexpanded `~` in a socket value and the hooks client's per-dial re-read.

CONSEQUENCE: when adding any input to how the listener is located, first ask whether BOTH processes evaluate it identically; if not, it must fall into one of the four treatments above before it ships. A single-process test cannot see this class; only an agreement test that computes both sides (Load().Socket == SocketPath()) under the varied input can.

WHAT THIS DOES NOT MEAN:
- Not that the chosen socket value is tilde-expanded: `socket = "~/x.sock"` stays literal on both sides; they agree, and the missing expansion is a pre-existing bug.
- Not full parity today: the accepted gaps above are real and open.
- Not that the server and bridge must share a process or a config object; they share functions and inputs, deliberately not Load.
