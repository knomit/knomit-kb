# materialize: BFS to depth decides the included set, a pre-order DFS in refs order decides reading order; one version per path; MCP pages are MEASURED against the 32 KiB cap and the agent pages concatenate byte-for-byte to the REST document

internal/corpus/materialize (Plan) builds one Document; both surfaces render it. Since PR #696 (dev f04bc8d6) Plan runs on the FactSet planner (internal/corpus/materialize/factset_plan.go): a single fact is planned as ONE unit with no FactSet around it (no reservation, no links), reading only the index in batches (index.LevelReader: per BFS level the ref_edges rows of the level's blobs, then the facts rows and dates of unseen targets), with no per-fact git read and no OutgoingAtCommit call. walk.go keeps Plan/PlanStats, the Document/Node types and the root resolution (index.HistoryQuery.LiveAt at the anchor; an empty anchor is the write mount's index watermark).

WALK:
- Inclusion: BFS from the root to Options.Depth (shortest distance), cut at MaxNodes in BFS order. Every included node's refs are resolved, the ones at the depth limit too, so a ref cut by depth still has a title.
- Order: pre-order DFS in the order each fact's refs are WRITTEN (the author's refs order, ref_edges.ord; the planner classifies refs in that order), writing each included node at its first visit.
- One version per path: the version it was first reached at in the BFS. A version is its BLOB (a root: the blob live at the anchor; a pinned ref: its ref_edges target_blob; unpinned and cross-KB: the blob live at the anchor or frozen tip). A later citation of a different version is a back-reference marked different_version, decided by BLOB identity (user ruling Q3): ANY change to the cited blob counts (body, title, refs, confidence, whitespace), so it is NOT a body comparison; the same blob at two commits (commit inequality alone) is never a change. Code: the builds_on link in factset_plan.go sets DifferentVersion = r.blob != t.blob.
- Back-references are Link entries (builds_on) to the written node's ordinal, never a second copy and never a separate stream entry.
- A 'not included' ref is `size` when the cap cut it (the target was reached) and `depth` otherwise; Truncated counts distinct cut paths per reason. Under unpin a gone target is neither listed nor counted.
- Frames: a frame's parents are the frames it refs, each read at the commit its edge pins; ancestors (upward closure over ANY frame ref, each at its pinned commit, cross-KB frames too when cross_kb and reach allow; see kb/decisions/materialize/rulings/16ccefe6.md) are adopted before the BFS by a breadth-first pass (inclusion only: closest first against the cap). Their ORDER is a depth-first POST-ORDER from the starting frame over its frame refs in refs order: walk back to the top, write top-down, so every parent precedes every frame that cites it. A ref to a frame already visited (the start included) is a back-reference: it settles a mutual pair (the frame you are at is the child) and keeps the walk from looping, with no cycle detection. (An earlier discovery-number edge filter plus Kahn sort was removed: it dropped edges to parents reached earlier and wrote a child before its parent, review B3: U; T->U; C->T; F->T,C must give U, T, C, F.) They are terminal and their blocks list no omissions.
- Agent rendering: body headings shift to min(level+3, 6) (markdown has no level 7); ``` and ~~~ fences are skipped.

PAGING (knomit_materialize): one tool_queue item per node (sort_key = ordinal, state = envelope + node without body; tool = 'materialize:<audience>:<limit>', the first call's page limit frozen with the snapshot, so a resume knows its page size before it dequeues and refuses other tools' cursors). Bodies are re-read per page by the stored (repo, blob) (materialize.ReadBodies in reader.go), so a commit landing between pages changes nothing. Each page is filled while json.Marshal of the whole page stays <= 32 KiB (a single larger fact goes alone); nodes that did not fit are re-enqueued. With cursor, any document argument is REFUSED, not ignored.

PARITY: the agent document is header + one block per node, each block starting with a blank line, so page texts concatenate exactly to RenderAgent(doc), which is what GET .../facts/<path>/materialize returns.

FACTSET EXCEPTION: in a FactSet unit that is not a frame, every node at BFS distance 1 stays a child of the unit's root in the reading order, in refs order, never under a sibling (pinDirect in factset_plan.go), because a FactSet fixes those numbers ('<unit>.<k>') before any unit is walked. A single materialization (Plan) keeps the plain pre-order DFS.

WHAT THIS DOES NOT MEAN: it is not explain: explain is BFS, summaries only, and dedups by path@commit; materialize writes full bodies and dedups by path.

MOVED (feat/materialize-rest-cursor): the paging above (envelope, measured fill, snapshot, resume) now lives in internal/corpus/materialize/pages.go (FirstPage, NextPage, Page, PageEnv, PageCap = the old materializePageCap) and is shared by knomit_materialize and the REST pages route GET .../facts/<path>/materialize/pages, which serves the human page byte for byte (kb/architecture/materialize/rest-pages/contract/626080c2.md). The mcp package keeps only argument parsing and its expiry text.
