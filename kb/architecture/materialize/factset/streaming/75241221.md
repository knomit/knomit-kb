# FactSet streaming: frozen inputs in ONE session row owned by the principal (many per principal, explicit close), state in an in-memory cache holding a first-appearance prefix (any unit re-planned alone, never replayed) under a memory budget, the reading position in the cursor token, and every level of every unit one batched index read with no per-fact git

internal/corpus/materialize serves a materialized SEARCH (FactSet) as follows, built on ref_edges (PR B):

- FROZEN INPUTS, written ONCE at the first call in ONE transaction (sessions.ToolIndex.CreateFactSet, BEGIN IMMEDIATE): a tool_sessions row (owner = the principal ALONE, materialize.FactSetOwner, no endpoint or route; binding pin; read set) plus factsets.frozen = JSON of the search, options, anchor, the frozen tips of every repo the caller reaches (only when cross_kb is on), and the roots as (path, commit, blob, title, date). CreateFactSet ONLY inserts: a principal holds any number of FactSets at once, and a first call never ends another (the book-era one-per-owner replace was dropped, user ruling 2026-11-01; PR #701, merged at 73753c1f).
- ANCHOR = the write mount's INDEX WATERMARK (meta last_commit:<branch>, HistoryQuery.Watermark), read with the sync_pending marker (HistoryQuery.SettledWatermark) before and after the search; while the watermark is unsettled (a sync in flight, an empty watermark mid-Rebuild) or moves across the search, the first call waits and searches again, bounded by the request context and session.factset_anchor_wait (default 5s), then ErrIndexMoved (503, Retry-After). Never git HEAD. branch_facts describes the watermark only when no sync is rewriting it (gotcha 68218e91), so only then is each hit's (commit, blob) its version at the anchor.
- PLANNER (factset_plan.go) is the ONE walk for a single fact (Plan) and every FactSet unit: per BFS level ONE read per KB through index.LevelReader (one per call, two prepared statements: the ref_edges rows of the level's blobs, then the facts rows and commit_log dates of ONLY the targets the unit has not seen, keyed by (path, blob, commit) so one blob pinned at two commits keeps each commit's date), so a unit costs at most Depth+2 index reads beyond the read-ahead (root metadata + Depth+1 levels; the depth-limit level is read for the titles of cut refs). A FactSet call also READS AHEAD (fsCall.readAhead): windows of 6 units, roots then level by level speculatively to the unit's depth within a max_nodes-per-unit budget, in parallel chunks, pipelined behind the planner (pages only: the export makes its PLANNING reads while it holds its per-unit planning reservation, never in a background window; its body and RULE 1 reads, inflate's BlobsByHash and CurrentBlobs, run after it gives the reservation back, exportChunk sections at a time); a unit whose data was not read ahead reads it itself with the same answer. UNPIN reads no ref_edges rows at all: the targets are the fact's frontmatter refs (local fact refs in ord order, each once, self skipped), each versioned by HistoryQuery.LiveAt at the anchor, so a ref that had no row at write time (cited before its target existed) still resolves; reserve() takes the N.k targets the same way so the reservation mirrors the planner. Cross-KB versions also come from LiveAt, at the frozen tips. Bodies are read by blob (FactQuery.BlobsByHash) only for the sections a page emits.
- STATE (since PR #702, merged at 233a5404) lives in a process cache (factset_cache.go): results and reserved map as frozen sorted 24-byte tables, and the planned PREFIX (units 1..planned): per written fact the unit that FIRST wrote it (a uint16 per frozen-table entry, plus an extra set of 32-byte entries carrying the unit), each planned unit's section count, and an LRU of 8 kept unit plans. A fact is written at most once in a FactSet, so 'written before unit u' = 'first unit < u' and ONE growing prefix answers every u <= planned (invariant 479400a8): a unit within it is re-planned alone (lookup bounded by u), never by replaying units 1..u-1; extending it is done by the one call holding the entry's extension token (fsCall.acquireToken; others wait on their own context holding no planning memory; reads of planned units never touch the token and run concurrently: there is no per-FactSet mutex). The export plans on the same prefix (extending or re-planning). Eviction drops the entry; the next call plans again up to what it needs. A frozen row with more than MaxFactSetFacts roots reads as ErrCursorExpired. Store close drops that store's entries (ToolIndex.OnClose hook run by Service.Close).
- BUDGET: session.factset_memory_mib (default 64 MiB) bounds cached entries PLUS a planning reservation every call that must plan takes BEFORE the token (fsPlanReserve: two read-ahead windows at about 4 KiB per node, or while the tables are unbuilt 128 bytes per depth-1 entry, both measured on synth B). Over budget idle LRU entries are evicted; an entry in use is not, but it is CHARGED as it grows (after its tables are built and after every unit an extension applies), so an export or far seek holding it stays visible to the budget. A call that still does not fit WAITS (granted at once when no other reservation is in flight, so the budget is SOFT by one reservation plus the entries in use), bounded by its context and config.FactSetStallLimit, then ErrFactSetBusy (503). Admission is not FIFO: a large reservation can be overtaken by small ones (unmeasured follow-up). The old caps (4 planning slots, 8 export slots, ErrFactSetExportsBusy) are gone. A page reserves only when it must plan; the export reserves per unit and releases before it writes, and keeps only the edge's 1-minute per-write stall limit, no overall deadline.
- PAGE FIELDS: UnitsWalked/Sections are the highest unit the page itself walked and the sections of units 1..it (what sequential paging reports), never the cache's extent.
- CURSOR = "<id>.<unit>.<section>": the position after the page. Pages write nothing; two calls with one cursor return the same bytes (no CAS, no 409), in any order and concurrently (TestFactSet_RandomAccessIsByteIdentical) WHILE THE CALLER'S REACH IS UNCHANGED (see REACH QUALIFIER). The ROW decides ownership on every call; a position past the factset's last unit is ErrInvalid (400) (a position past the planned prefix is valid: it extends the prefix); another owner or an unknown id is ErrCursorExpired (404). The only later writes are the heartbeat, at most once per tool_idle_ttl/4 (SetFactSetIdleTTL, wired in internal/app because repos cannot import materialize), and the explicit CLOSE.
- LIFETIME: a FactSet ends by (a) CLOSE — materialize.CloseFactSet, reached by knomit_materialize `close: true` + any cursor of it, and by REST DELETE …/search/factset?cursor= (204); sessions.ToolIndex.CloseFactSet deletes in ONE statement only a row matching id AND pin AND read set AND owner (unknown, foreign, closed: ErrCursorExpired alike, nothing deleted), then the cache entry is dropped; a cursor that is not factset syntax is ErrInvalid; the REST DELETE is exempt from the write and read-only gates (isMutatingRequest, factsetClosePattern) AND from the fleet-repository gate (httpx.FleetRepoRefused via isRepoFactSetResource: DELETE on exactly …/repos/{repo}/branches/{branch}/search/factset, nothing below it) because it deletes the caller's transient session data, never repository data (user ruling 2026-11-01; pinned by TestFleetRepo_FactSetCloseIsNotRefused, which also asserts every other fleet-repo mutation is still 409 fleet_repository); (b) the idle reaper (session.tool_idle_ttl); (c) the session DB wipe on store open (no restart persistence, by ruling). A page already being served when a close lands finishes; its cursor then reads expired.

CONSEQUENCE: never add a per-page or per-fact session write, a git read, or OutgoingAtCommit to this path; F13 and F14 (factset_engine_test.go) fail on each.

WHAT THE MANY-PER-PRINCIPAL RULE DOES NOT MEAN: there is still no count cap, but nothing frees a FactSet early except close, the reaper and restart, so a client that opens FactSets in a loop holds them until it closes them or they go idle; and the cache budget still evicts state (the next call plans it again), never rows.

WHAT THIS DOES NOT MEAN: the single-fact pages route still pages through its tool_queue snapshot (its wire contract is unchanged); only its walk and bodies moved onto the planner.

RESUME REACH (PR #700, merged at 737bcf75): resuming a FactSet cursor does NOT re-check reach of the frozen tips. openFactSet used to loop every repo in fr.Tips through reader.target and answer ErrCursorExpired (404) if any was unreachable, so one archived or removed repo the FactSet never cited failed the whole FactSet. Reach is now enforced per content read: reader.foreign applies target + mayRead (89b26b07) whenever planning enters a repo, and fsCall.inflate serves a section of a foreign repo the caller can no longer read as an unavailable heading (written false, no body, numbering kept) instead of a 500; an unplanned ref into such a repo reads kb_unavailable in not_included. CONSEQUENCES: a re-read can differ from bytes sent earlier; after cache eviction, or when a unit is re-planned alone (#702), it is planned without the gone repo, so a cursor position inside a unit can lie past the re-planned unit's end, and fsCall.page then continues at the next unit's first section (never a 400); past the last unit is the normal end-of-FactSet 400. Only positions that were never valid (malformed, unit outside 1..units, extra args) are 400.

WHAT RESUME REACH DOES NOT MEAN: access is not unchecked on resume. The id, owner (the principal), pin and read-set checks are unchanged and an unknown, foreign or closed cursor is still the one identical ErrCursorExpired 404, so no gone-repo answer exists to probe. A narrower credential resuming a wider caller's cursor is served, minus the content it cannot read. Pinned by TestFactSet_ResumeIgnoresAnUnrelatedUnreachableRepo, TestFactSet_ResumeAfterACitedRepoIsGone, TestFactSet_ResumeInsideAShrunkUnitContinuesAtTheNextUnit, TestFactSet_ResumeUnknownAndForeignCursorsStay404 and TestFactSet_F11_UnreachableRepoIsUnavailable.

REACH QUALIFIER (#702 on top of #700): 'a page is a pure function of (FactSet id, position)' and 'same bytes in any order, concurrently' hold ONLY while the caller's reach is unchanged. Both directions change bytes: a repo LOST since a unit was planned reads as kb_unavailable when that unit is re-planned or first planned (extension); a WIDENED reach can make a fact appear in full TWICE (the prefix records its first write in a later unit w because unit u could not reach it; unit u re-planned with the wider reach writes it too, since firstUnit = w >= u is not a back link). This is ACCEPTED per the user's no-reach-re-check ruling (#700): resume does not re-check reach and the prefix is not re-planned when reach changes. Nothing crashes and the prefix is not corrupted: re-planning never applies to the prefix, lookups stay bounded by the unit, and extension still plans strictly in order.

SEAM (PR #705, merged at 01319df2): FactSetFirstPage is now search + anchor followed by the pinned seam freezePinned/startPinned/createPinned with home = wire = the write repo; the frozen row's write_repo is the HOME and an omitempty wire_repo is set only for a lens sub-FactSet.
