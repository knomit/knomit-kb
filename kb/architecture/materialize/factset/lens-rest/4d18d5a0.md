# REST lens FactSet routes (F4): GET /lenses/{lens}/search/factset, …/export and DELETE …/search/factset?cursor= are the repo FactSet handlers over the lens binding (factsetSurface), plus the lens list's repeatable repo= and its wiring (lensEmbed + lensMotifClusters); errors map as the repo route, except an unknown repo= is the lens list's 422 "Unknown repo"

Since feat/lens-factset-rest (F4 of the lens FactSet plan), internal/edge/web/api/kb registers the factset routes on BOTH subtrees (kb.Mount): the branch router (/repos/{repo}/branches/{branch}/search/factset, /export, DELETE) and the lens router inside LensMiddleware (/lenses/{lens}/search/factset, /export, DELETE). The SAME three handlers serve both; a factsetSurface says where the binding comes from (repoFactSets: repos.NewBindingOfRepo(RepoFromContext, httpx.BranchFromContext); lensFactSets: repos.BindingFromContext, the lens LensMiddleware resolved) and whether the first call is a lens call.

LENS-ONLY on the first call (factsetRequest with sf.lens):
- repo= (repeatable, member repo names), named exactly as GET /lenses/{lens}/search names it, goes to FactSetSearch.Repos. On the repo route repo= is still the generic 400 "unknown parameter".
- When the binding IsLens (two or more members): req.Embed = lensEmbed(emb) and req.Clusters = lensMotifClusters, the lens list's own embedder and motif cluster reader, so the query is embedded ONCE per fan-out and motif terms widen over the full read set. A ONE-member lens is NOT IsLens: it gets the repo route's wiring (emb.EmbedQuery when emb is set) and the engine serves it on the repository path with the write repo's units and sections (pin lens:<uid>), but AS A LENS (user ruling 2026-11-02, kb/decisions/materialize/factset/one-member-lens/0ae658c1.md): cross_kb=true is the lens 400 and its no-filter title is "All in lens <lens>".
- since_fork reads experimentChangedPaths(b.Write(), b.WriteMountBranch()) on both routes (on a repo route that IS ri/branch). On a lens it works only when the lens pins its write member to an exp/... branch; otherwise it is the repo route's 400 "Not an experiment".

ERROR MAPPING (writeFactSetError, shared):
- *federate.UnknownRepoError anywhere in the chain -> 422 "Unknown repo" with the error's own text (byte-equal to the lens list's StageRepos answer, instance path aside). Checked BEFORE ErrInvalid. This needed an ENGINE change: planLensSearch and checkRepoNarrowing now wrap with "%w: %w" (were "%w: %v", which broke the chain); the text is unchanged.
- ErrCursorExpired (unknown, foreign principal, closed, idle, membership changed, lens cursor on a repo route and the reverse) -> the repo route's 404 "Cursor not found".
- ErrInvalid (cross_kb=true on a lens of ANY size, a one-member lens included; past-the-end; bad sort ...) -> 400 "Invalid request" with the ENGINE's text passed through (no edge-side copy of engine strings).
- ErrFactSetBusy / ErrStoreBusy / ErrIndexMoved / ErrNotReady -> 503 "Busy" with Retry-After, as the repo route.
- Malformed parameters are the handlers' own 400s, identical on both surfaces.

GATES: factsetClosePattern (readonly.go, used by readOnlyGate AND writeGate through isMutatingRequest) matches `(?:/repos/[^/]+/branches/[^/]+|/lenses/[^/]+)/search/factset$`, so the lens close needs only read and works on a read-only instance. The fleet gate (httpx.FleetRepoRefused) is mounted on /repos/{repo} only (route golden: lens routes run writeGate > lensMiddleware, no fleetRepoRefused), so isRepoFactSetResource needed no lens arm; a lens holding the fleet repository as a read member closes its FactSet with 204.

OWNERSHIP: unchanged engine rule (owner = principal alone, pin + read set): an MCP lens-endpoint cursor pages, seeks, exports and closes over the REST lens route for the same principal and the reverse; a lens cursor on the write repo's REST route, and a repo cursor on the lens route, are the unknown cursor's 404.

CONSEQUENCES: a new factset route or parameter goes into the shared handlers with a factsetSurface switch, never a copied lens handler. A new engine error the edge must classify must be wrapped with %w all the way down; %v silently turns it into the generic 400.

WHAT THIS DOES NOT MEAN: the lens routes are not behind the fleet gate because the lens is trusted; they are outside it because the gate is keyed on {repo}, and the close deletes only session data. And repo= on a lens FactSet is not new engine behaviour: the engine accepted search.repo since F3 (MCP); F4 only exposes it on REST.
