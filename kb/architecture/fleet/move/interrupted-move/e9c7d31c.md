# An interrupted move: GET /fleet `interrupted_move` (record_is_here or move_back_to) on the MASTER whose forge copy does not follow the host record; the repairs are Host here or Move back, re-sending the forge it stopped on is `unchanged`, and a moved member reads `last_error_fleet_moved`

Verified at the merge of PR #529 (60ddfb1c). A move (kb/invariants/fleet/move/onto-forge/d83bd272.md) is atomic against a FAILED host-record write, but a process death after the attach is stored and before the record lands is not undone: the master's copy syncs from the new forge while main's host record still names the old host. fleetHostRound runs only on a copy with NO origin, so nothing self-heals it; the state persists across restarts and rounds until repaired (staged for real in review by killing the master the moment the attach was stored).

GET /fleet reports it as `interrupted_move`, set only when this instance is the master, has a non-cert (forge) origin, and follows_host is false: `record_is_here: true` when the record names this instance's own hub URLs (the move started at the hub), else `move_back_to: <first record URL>` (the move started on another forge). Both are credential-free.

REPAIRS (Fleet -> Settings card 'The move to the forge did not finish'): record_is_here -> 'Host the fleet here' only (no Point at, no Move back); move_back_to -> 'Move the fleet back to <forge>...' (the move flow prefilled with the forge the record names) or 'Host the fleet here'. The master never gets 'Point at the new host' and never has its own hub URL prefilled.

N-4: re-sending the forge the move stopped on is `unchanged` (the stored URL), so there is no 'finish the move' by re-submitting; repair goes back or hosts here, then moves again.

MEMBERS HAVE NOTHING TO DO: members follow the host record on main, and an interrupted move never changed it. So the move-back Review and Host-here on `record_is_here` say 'Members have nothing to do' (web: the membersUnaffected prop, testids fleet-move-members and fleet-host-members). EXCEPTION: Host here on `move_back_to` DOES rewrite the record (main still named the old forge), so members become stale there and must re-point; that screen keeps 'tell every member the new URL' and drops only the false 'the old master points its copy here too'.

last_error_fleet_moved: on a MEMBER (follows_host false), true when the recorded last_error contains the old host's push refusal for a copy with an origin (FleetPushRefusalHasOrigin). The page then says 'The fleet has moved: the old host no longer takes this copy's pushes. Use Point at the new host; nothing this copy wrote is lost' instead of the raw error and 'Retrying', and 'Hosted by' names the record's URL.

TESTS. TestFleetStatus_AnInterruptedMove (both variants), TestFleetStatus_LastErrorFleetMoved, vitest FleetSettings.config.test.tsx ('an interrupted move offers Host the fleet here, or moving back', 'the repairs of an interrupted move tell the operator members have nothing to do', 'a member refused by the old host is told the fleet moved').

MISREADINGS. (1) 'The hub self-heals this': the hub does, a forge copy does not. (2) 'Host here always means members need not move': only on record_is_here.
