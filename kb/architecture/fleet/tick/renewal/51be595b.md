# The acting fleet master's round re-signs main's CRL and renews main's leaves in the FINAL THIRD of each one's own lifetime, for that same lifetime, and every copy installs its renewed leaf from main in its own tick; no day count and no constant validity is read

WHAT (fleet PR8b, branch feat/fleet-tick-renewal). `fleetRenewRound` runs in the master's round on BOTH hostings, after the leave duty and before the round moves main (hub: `fleetHostRound`; forge: `fleetMasterDuty`), and checks `actsAsFleetMaster` itself; fleetOpMu is held by the caller.
- CRL re-sign (`resignFleetCRL`): when main's CRL is due (`pki.CRLNeedsResign`: less than a third of NextUpdate-ThisUpdate left) AND the master's agent branch holds the same CRL bytes as main (nothing unpublished; a revocation's fresh CRL needs no re-sign), `pki.ReissueCRL` signs the same entries with Number + 1 for the CRL's own lifetime from now; committed as crl.pem, copied to <home>/fleet (`pki.RecordCRL`). It is NOT installed by the duty: the master's own tick installs it from main next round (installCRLCallers stays tick + revoke).
- Leaf renewal (`renewFleetLeaves` / `leafRenewalDue`): for every leaf on main that is due (`pki.NeedsRenewal`), when the agent branch holds the same leaf bytes as main (not renewed and unpublished) AND, on BOTH main and the master's agent branch (`renewableAt`, since the round publishes the agent branch): a CRL exists and does not list the leaf; exactly ONE member record is filed for the id; that record is not `left`; the record's key is the leaf's key. (Main-only checks let two reachable cases re-certify: a revoke whose publish failed, and a `left` record admitted in the very round the leaf fell due; the round then published the revocation or the left record together with a fresh unrevoked leaf, and leftLeafDue never revokes it because the record names the OLD serial. PR #537 review B1/B2, regression tests TestFleetRenew_AnUnpublishedRevokeIsNotUndoneByARenewal and TestFleetRenew_ALeaveOnTheAgentBranchIsNotRenewedBeforeMain.) Re-issued with `pki.IssueLeaf(root, same key, same agent email, pki.RenewalValidity(old), renewalIssueTime)` and committed with issued/<serial>.pem; the master's own leaf included; the local issued.jsonl gets the line.
- `pki.RenewalValidity(cert) = Lifetime - clockSkew`, because IssueLeaf back-dates NotBefore by clockSkew: passing Lifetime grew each renewal by 5 minutes (found by the test).
- Every commit reaches main through the master's own-commit judge (leaf-renewal and crl-newer hold by construction).
- The tick then installs the renewal: `Manager.installMainLeaf` takes main's certs/<own id>.pem when its NotBefore is later than the installed certificate's and calls `pki.InstallLeaf` (CRL first, then the leaf).

TEST SEAM. `fleetNow` (decision clock only; `SetFleetClockForTest` for other packages). Signing always uses time.Now, so a moved clock still yields valid artifacts. A moved clock left in place renews every round (the fresh leaf is again 'due' at the fake time): restore it.

CONSEQUENCES.
- An id enrolled but never joined (no record), a left member, a revoked leaf and a re-keyed record are never renewed: they expire.
- A hub member whose leaf EXPIRED can no longer fetch, so it never installs a renewal: renewal must land before expiry (the final third is the window).
- Proven: internal/repos TestFleetRenew_ForgeMasterRenewsDueLeavesAndResignsTheCRL and one test per guard in fleet_renew_guards_test.go (two records, another key, an unpublished renewal, an unpublished CRL re-sign, B1, B2); cmd TestFleetE2E_KnomitHosted (which asserts the hub sees the renewed client serial and serves its own renewed leaf) and TestFleetE2E_Forge.
- MISREADING: "the judge would catch a bad renewal": leaf-renewal checks only NotBefore, one record and the key; it admits a renewal for a revoked or departed id (by design, for the rejoin), so the duty itself must refuse it.

MISREADING. "Renewal pushes a new bundle to members": nothing is sent; each copy pulls main and installs its own leaf.
