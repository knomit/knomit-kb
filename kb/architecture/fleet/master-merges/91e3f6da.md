# The fleet master merges members' branches on EVERY hosting, and the origin is transport only: the merger is gated by RepoInstance.isFleetMaster alone (never by an origin or by `consensus`), and the master's origin round fetches agent/*, judges tip∖main, promotes, merges and publishes main without force

WHAT (PR #524, verified at merge commit 9db8c106). On the fleet repository the consensus merger runs only where `RepoInstance.isFleetMaster` holds (fleet door AND fleet repo AND Manager.isFleetMaster: the root key file is here and its certificate is the root on main), on every hosting. The origin is not read for the fleet repository and `consensus` is not read; the built-in fleet ontology (ontology_fleet.yaml) declares no `consensus`. A non-master copy (a member) merges nothing. For every other repository the gate is unchanged (`consensus: auto` at the consensus branch AND no origin, consensusMerger.mayMerge).

TWO HOSTINGS, ONE MERGER:
- knomit-hosted fleet (the master's copy has NO origin, the hub): members push their agent branch into receive-pack; the merger merges it into the master's agent branch; main follows through the local reconcile. None of the origin-round steps below run.
- forge-hosted fleet (the master's copy HAS an origin): nobody pushes to the master (FleetPushRefusal, see the push-refusal invariant). The master's ordinary origin round, only while isFleetMaster holds, does three more things: (1) its fetch adds every agent/* branch (store SyncWithPeers; refspec +refs/heads/agent/*:refs/remotes/origin/agent/*, see the peer-refspec fact); (2) each fetched tip whose (tip, main) was not judged yet is judged over EVERY commit of tip∖main with the receive-pack judge core (see the fetch-judge invariant), and an admitted tip becomes the local refs/heads/agent/<x> exactly as receive-pack's register leaves a pushed branch (promotePeer: seed, advance, notifyCommit), which kicks the merger; a refused tip is left behind as a remote-tracking ref nobody reads; (3) after its own agent-branch push, if that push did not fail, it publishes main: PublishUpstream of the agent branch to the origin's main WITHOUT force, then local main follows. This runs on EVERY round of a publishing instance, whether or not the own push sent anything, so a main that create or an earlier round failed to publish goes out next round. A non-fast-forward refusal is an ordinary push error (recorded on the push status row by RecordPushError, handed to onPush, charged to the push breaker); the next round fetches the newer main, merges it into the agent branch and pushes again.

ONE PUBLISH PATH (covers #518): publishFleetMainOn = PublishUpstream then local main follows. Callers: fleet create (publishFleetMainNow), FleetRetry (pushFleet) and the loop round (fleetPeers.publish). RepoInstance.publishesFleetMain = isFleetMaster OR (the root holder before main holds the root). Manager.fleetPushed only reads the outcome (kb/invariants/fleet/registration/registering-needs-main-published/f035a93a.md).

LAST_REFUSAL: the master's refusal of a branch (fetch judge or merger re-judge) is a PeerRefusal{branch, tip, reason, at} held IN MEMORY (Manager.FleetRefusals). GET /fleet/members shows it as `last_refusal` on the member whose record's `branch` matches. A refused first join has no record on main, so it has no member row: visible only in the master's log and in FleetRefusals. A restart forgets refusals and judges each fetched branch once more.

MEMBERS: a member's round fetches main and its own branch, pushes its own branch and never merges.

MISREADINGS: 'the master merges only when the fleet is knomit-hosted' is false (a forge master merges after fetching); 'consensus: auto turns the fleet merge on' is false (the setting is not read for the fleet; a pre-#524 fleet keeps a stale `consensus: auto` line on main until the master's ontology refresh, harmless); 'the forge's PR merge is how a member lands' is false. Two masters at once is unsupported (see the two-masters decision) and the forge's main is trusted as fetched (see the trust-the-forge decision).

UPDATE (PR #527, verified at merge commit c6e282db) — the LAST_REFUSAL claim above that a refused first join has no member row and is visible only in the log NO LONGER HOLDS. Refusals now have THREE writers: the hub's receive-pack (PushPolicy.Judged -> Manager.FleetPushJudged -> fleetPeers.pushed, told after the private-path closure and verify, and with "" after a successful registration; whole-request refusals and a copy-with-origin's FleetPushRefusal are not verdicts and are never told), the forge fetch judge, and the merger's re-judge. PeerRefusal gained `agent`: the agent id of the REFUSED TIP's author (store.CommitAgent, the address the judge reads; "" when not an agent address). Every refusal also goes into an in-memory ring (the last 200; fleetPeers.ring, RefusalLog newest first) that GET /fleet/activity shows as `refused`; the same branch refused again at the same tip for the same reason is one entry. A refused first join is therefore an Activity `refused` event with its agent, and `last_refusal` on its `enrolled` Members row (see the activity and members-route facts).
