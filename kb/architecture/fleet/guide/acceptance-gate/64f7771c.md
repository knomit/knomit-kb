# Fleet guide — the acceptance gate: a change is verified ONCE, where it advances a KB's main, against the fleet repository's member records; verify_signatures (off | log | enforce, read at that main's tip) switches it; the same judge runs in receive-pack on a knomit host and in `knomit verify ci` on a forge; nothing re-verifies history on fetch, clone or merge, and `knomit verify audit` is the forensic tool

Part of the fleet guide (kb/architecture/fleet/guide/). Describes merged dev at 3e2e83b0 (PR #514).

THE SWITCH. Root ontology attribute verify_signatures: exactly "off", "log" or "enforce"; absent = off. It is read through fact.ReadVerifySettings, which reads ONLY the root attributes block, at the tip of the main the change is about to advance (receive-pack: the HOST's upstream tip; verify ci: the --main checkout's tip). An unknown value is never read as off: the gate cannot run (exit 2 in verify ci, refusal in receive-pack). Anyone who can merge to the KB's main can change it; there is no special role.

THE JUDGE (store.CheckRange / judgeCommit). Off: verdict off, the fleet is never read. On: load the fleet repository's member records (the checkout or mount must have the fleet ontology; a malformed record is skipped and logged once); for every commit in candidate minus main (PR #523 order): FIRST its tree and every parent's tree must be well formed (malformed-tree); then every two-parent merge runs M3 and a merge that adds nothing beyond its parents (M3: its tree equals the three-way merge of its parents, every entry including gitlinks) is admitted unsigned, signed, or with a present-but-invalid signature (user ruling: no content of its own); a merge that fails M3 is refused `merge` if unsigned and judged like any commit if signed; otherwise the SSHSIG must verify (signature); the author address <id>[+op]@agents.knomit.io yields the OPAQUE agent id; exactly one record at that id (no-record / ambiguous); the signing key must equal that record's CURRENT key by full wire bytes (key-mismatch) and be no other record's current key (duplicate-key); the record's state must be active (inactive). On a knomit host receive-pack adds signer = pusher (not-pusher). enforce refuses, log reports only.

WHERE IT RUNS. (a) Knomit host: in receive-pack, for each pushed new commit, against Manager.FleetMembers (the fleet repository's records at its consensus branch). (b) Forge: `knomit verify ci --fleet <fleet checkout>` over plain checkouts in the merge job; exit 0 off/clean/log, 1 enforce with refusals, 2 could not run. Nothing else gates: the decision acceptance-only removed every re-verification on fetch, clone, reconcile or merge.

NEIGHBOURS. E4 first contact: when an instance clones or re-attaches, it adopts origin's copy of its OWN agent branch only if every commit beyond origin's main is signed by an own key (chain of trust: commits an own-signed merge brought in are adopted). `knomit verify accept <commit>` records an operator's acceptance in control.db (an instance-level accept list). `knomit verify audit` re-checks a whole branch against EVERY version of the member records (rotated keys and departed agents are attributed, not flagged). The trigger field change.author.verified means the change already passed this gate (verification on at the observed head AND the commit already on upstream main).

TRUST MODEL. Transitive, like git: repository access is the trust boundary; a breach is handled forensically with audit, not prevented by host hardening.

CONSEQUENCES. With verify_signatures off (the default for every non-fleet preset; the embedded fleet preset now declares enforce, but a fleet repository that already existed keeps its stored ontology) a knomit host accepts any enrolled instance's push unjudged and a forge accepts whatever its access rules accept. After a key rotation the OLD key is refused at the gate (current key only). A revoked certificate affects the gate through rule B: once the CRL listing its serial is on the fleet repository at the revision the judge reads, that member's commits are refused (rule revoked) even while its record is active.

MISREADINGS. 'Find the record by the signing key': wrong; the record is found by the author id and must hold the key. 'Every fetch verifies': no, only the main-advancing gate does. 'An invalid verify_signatures value is off': no, it stops the gate.

UPDATE (PR #514, verified at the merge commit): THE JUDGE reads, at ONE fleet revision, the member records AND the certificate artifacts the fleet ontology's artifacts section declares (root, CRL, leaves), so records and CRL never come from different commits. With PKI present (the declared root file exists) the judge FAILS CLOSED. RULE B: a commit by an active member with a matching record is admitted only if the leaf file for its id names the record's key, chains to the root, and is not on a CRL the root signed; otherwise no-cert (no leaf, a leaf the root did not sign, or an unreadable root/CRL/leaf), key-mismatch (the leaf is for another key) or revoked. With no root file, the rules are as before. RULE A: a commit refused for no-record, key-mismatch or inactive is ADMITTED as a self-registration when the id has no active record, the signing key is not the current key of a record for a DIFFERENT id, the commit keeps the record-owner rule (not-owner: against every parent, every path it changes outside declared artifact paths is under members/<id>/, nothing there deleted, every record written there has agent == id), a valid unrevoked leaf for the id carries the SIGNING key and chains to the root, and the folder it leaves holds exactly one record, for that id, state active, with that key. Only a join or rejoin can be admitted this way; leaving is an ordinary change. Rule A exists only where the judged KB is itself the fleet repository. ARTIFACT RULES: every admitted commit (signed, or an unsigned M3 merge) must also keep every rule of the artifacts section of the judged repository's ontology at the main being advanced (see kb/architecture/fact/ontology/guide/artifact-rules); they run only under log/enforce. REFUSAL RULES a user sees: signature, no-record, ambiguous, key-mismatch, duplicate-key, inactive, merge, revoked, no-cert, not-pusher, artifact-write-once, artifact-append-only, artifact-replace, artifact-size, artifact-pki, artifact-rules, artifact-not-a-file. Nothing is derived from an id's text (D18): it is a lookup key for a record or a leaf file name and is compared for equality (byte for byte, ids are lower case) with the certificate's email SAN id. NO MERGE-TIME RE-JUDGE (user ruling): a commit accepted before a CRL landed may still merge after it (kb/decisions/store/verify/no-merge-time-rejudge/f0c6232e.md). MISREADING: 'revoking a certificate stops signing everywhere': only for a gate whose fleet revision already holds the newer CRL; the CRL must be committed to the fleet repository's main by a commit that itself satisfies crl-newer and superset.

UPDATE (PR #523, verified at merge commit 3ac59b57): the rule list gains `malformed-tree` (first; every repository; also in receive-pack's closure in every verify_signatures mode) and `not-owner` (fleet repository only; also required of a certified active member after rule B). Details: kb/decisions/store/verify/m3-first/b3bb33da.md, kb/invariants/store/verify/record-owner/74b64ef6.md, kb/invariants/store/verify/tree-shape/fc07357f.md. A malformed tree already on main wedges the gate (kb/gotchas/store/verify/malformed-main-recovery/0cbaf27d.md). MISREADINGS: 'an unsigned merge passes only if M3 is clean' is now 'a clean merge passes in ANY signature state'; 'a member can merge main into its branch and settle a conflict' is false: a merge that settles a conflict fails M3 and is refused not-owner.

## UPDATE (PR #524, verified at merge commit 9db8c106): the gate for the FLEET repository on a forge is the master's fetch-time judge, not `verify ci`

The sentence 'the same judge runs in receive-pack on a knomit host and in `knomit verify ci` on a forge' describes user knowledge bases. For the fleet repository: on a knomit-hosted fleet the gate is receive-pack on the hub (plus the merger's re-judge against the current main); on a forge-hosted fleet it is the master's FETCH-TIME judge (store.AdmitPeerBranch: the same judgeIncoming core after privatePathClosure, over every commit of `tip ∖ main`, non-empty selfRoot, NO signer = pusher) plus the same re-judge before each merge. A member's branch that the judge refuses is never merged and never reaches main, so the fleet's acceptance does not depend on a `verify ci` job on the forge (running one is not what gates the fleet's main). All rules (record rules, A/B, record-owner `not-owner`, `malformed-tree`, artifact rules) therefore apply at fetch too. The verdict is memoised per (branch, tip, main) because the judge reads the fleet at main: a leaf issued on main admits a join refused before it; a revocation refuses a branch admitted before it. Verification of history is still not repeated on fetch/clone/merge: the fetch judge looks at `tip ∖ main` of a branch BEFORE it is admitted, not at main.

Not covered: the forge's own main. The master trusts it as fetched (stated assumption, user ruling on #524); see kb/decisions/fleet/trust-the-forge-main/3a19b2d3.md and kb/invariants/fleet/fetch-judge/88eb5593.md.
