# Fleet guide — push and merge: on a knomit host a peer pushes its agent branch over mTLS into receive-pack (one agent/* ref, never the host's own, dot-path fast-fail, judged per verify_signatures), and it reaches the host's main only by a merge into the host's AGENT branch — the operator's web merge, or the consensus merger (`consensus: auto` on a user KB; on the fleet repository, the fleet MASTER on any hosting) — which the local reconcile then fast-forwards main onto; on a forge-hosted fleet nobody pushes to the master: it FETCHES agent/*, judges tip∖main, merges and publishes main WITHOUT force

Part of the fleet guide (kb/architecture/fleet/guide/). Describes merged dev at c9c599de.

TWO HOSTINGS. A knowledge base's git lives either on a FORGE (GitHub: peers push their agent branches with forge credentials, a pull request or workflow merges into main, `knomit verify ci` is the gate) or on a KNOMIT HOST: one instance holds the repository with NO origin and serves /git over the mTLS listener; peers mount it with a plain https:// origin that classified as a fleet peer when it was set (stored with auth method cert since PR #526; the fleet go-git transport behind it is reached through an internal scheme that only pki.GitURL spells: kb/decisions/repos/remote/plain-https-origins/07cc1cef.md). Everything below is the knomit-host path.

1. PUSH (receive-pack, F11, knomit's own code over go-git's codec). Who: only a principal of Kind instance authenticated Via a certificate holding push:own (implicit for every instance certificate chaining to the fleet root); a subscription refuses. What: exactly ONE command, not a delete, under refs/heads/agent/, not the upstream, not the host's own agent branch; NO rule asks whose branch it is (any enrolled pusher may push any other agent/* ref; branch ownership is not identity). The pack goes into a quarantine; new commits are those the host does not hold; in EVERY verify mode a new commit whose dot-path content (.knomit/, any segment beginning with '.') matches none of its best merge bases with the upstream is refused (early feedback only). Then, when verify_signatures read at the HOST's upstream tip is log or enforce, each new commit is judged against the fleet repository's records (judgeCommit, the acceptance gate's rules) plus signer = pusher (the SSHSIG key must be the pusher's certificate key, full fingerprint); enforce refuses, log only logs, off never reads the fleet (enforce with no fleet repository refuses). Accepted objects are promoted in one transaction under the branch lock. The pushed branch is readable on the host, never writable there, fires no host trigger and is never forwarded by the host.

2. MERGE into the host's AGENT branch — never main, never a caller-chosen target. Two routes only: the operator's web merge (POST /repos/{repo}/branches/{branch}/merge {expected_tip, resolution?} -> store.MergePushed; requires the `operator` permission; resolution host|peer settles every conflicting path) and, when the ontology at the consensus branch's tip says `consensus: auto` on a no-origin, writable, non-subscribed repo, the consensus merger (store.MergeConsensus, asynchronous, kicked by any commit on a non-agent, non-exp branch). Both write one host-signed merge commit and both REFUSE a merge whose result would change any dot path of the host's agent branch (PrivatePathMergeError; 409 "Merge would change system files") — this merge-time guard, not receive-pack, is the authority that a peer cannot change the host's .knomit/. Conflicts on paths both sides changed are settled by the root attribute `conflicts` {facts, state} read at the consensus branch's tip (absent under consensus: auto reads facts: merge / state: consensus; a key set to off refuses and leaves the branch for a human).

3. MAIN FOLLOWS. On the host (no origin) the local reconcile loop (AdvanceLocalUpstream, every [git].local_reconcile_interval, default 30 s, sooner after a merge's wakeSync) only FAST-FORWARDS main to the agent branch. Peers fetch main on their sync round and merge it into their own agent branches, settling conflicts with the same `conflicts` setting (the incoming consensus branch is the consensus side there).

CONSEQUENCES. A push being accepted is not its content being accepted: nothing reaches main until a merge. Once merged, a peer's facts fire the HOST's triggers (change.source = merged). A GitHub-hosted KB gets the same conflict settlement because it runs in the peer's sync before its push.

MISREADINGS. 'consensus: auto merges into main': false, it merges into the host's agent branch. 'receive-pack protects .knomit/': only as a fast-fail; the merge guard is the authority. 'With verify_signatures off a pushed branch is owned by its pusher': no branch is owned (PR #513 removed the fp8-suffix rule); the certificate is the whole authentication of a push.

## UPDATE (PR #524, verified at merge commit 9db8c106): 'a forge host does all of this with its own push and PR merge' is no longer how a fleet works

For the FLEET repository on a forge, the master does it, inside its ordinary origin round and only while `RepoInstance.isFleetMaster` holds:
1. its fetch adds every `agent/*` branch (refspec +refs/heads/agent/*:refs/remotes/origin/agent/*, added to THAT fetch only, not written to the git config; a copy of the key in or out of the instance takes effect on the next round); the strict fetch also prunes tracking refs within that wildcard, and a refusal for a branch gone from the forge is forgotten;
2. each fetched tip whose (tip, main) was not judged yet is judged over EVERY commit of `tip ∖ main` by the receive-pack judge core (`judgeIncoming` after `privatePathClosure`, non-empty selfRoot so rule A / record-owner run, no signer = pusher): admitted, it is promoted to a local agent/<x> (like register does), which kicks the merger; refused (`not-owner`, `malformed-tree`, `no-cert` ...), it is left behind, remembered in memory only (`last_refusal` on GET /fleet/members for the member whose record's branch matches) until the tip or main moves;
3. after its own push it publishes main WITHOUT force (store PublishUpstream, then local main follows), on every round whose own push did not fail. A non-fast-forward refusal is an ordinary push error; the next round fetches, merges and retries.
On a knomit-hosted fleet (the master's copy has no origin, the hub) none of 1 to 3 runs: members push into receive-pack and main follows through the local reconcile as described above. Members never merge; a member fetches only main and its own branch.

TRUST THE FORGE (stated assumption, user ruling on #524 S1): the master adopts the forge's `main` as fetched, rewinds included, without judging it; a direct write to the forge's main is the forge admin's business (branch protection). The fetch-time judge covers `agent/*` tips only, not main.
TWO MASTERS AT ONCE are unsupported (the user's responsibility): knomit never elects itself, and nothing detects or fences it.

## UPDATE (PR #525, verified at merge commit fd991d4f): the operator's web merge on the fleet repository

Route 1 of step 2 (the operator's POST /repos/{repo}/branches/{branch}/merge) is, on the FLEET repository only, no longer a free operator action: it is refused with 409 `not_master` on an instance that is not the fleet's master, and on the master it re-judges the branch against main NOW (tip minus main, the same core as the master's merger) and refuses with 409 `judge_refused` when the judge would. So 'an operator can merge any pushed branch by hand' holds for user KBs, not for the fleet repository; and a branch the master's merger would demote cannot be merged by hand in the window before the demotion. The same release made the fleet repository's origin DETACH (a member's: 409 `member_keeps_origin`; the master's needs the mTLS listener and external_addresses) and upstream change (409 `fleet_upstream_fixed`) refused.
