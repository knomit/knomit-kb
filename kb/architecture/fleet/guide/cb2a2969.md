# Fleet guide (start here): a fleet is several knomit instances sharing knowledge bases through git, each writing only its own signed agent branch, with ONE fleet repository (reserved ontology id `fleet`, built into knomit) whose member records decide who may sign and an operator-held fleet root CA that admits instances to each other's mTLS listeners; built on dev through PR #525 (fd991d4f): membership, the baked reserved-id fleet ontology, fleet create, the membership routes (enroll, join, leave, revoke, decommission, the root move; all local-listener only), push and merge with the master's merger, the signature gate with judge rules A/B and trust-file rules (P3), OAuth approvals — NOT built: the master and member duties that issue, renew, revoke and install certificates AUTOMATICALLY through the fleet repository (P5/P6), the fleet UI (P7)

Entry point of the fleet guide. Read the components in this order; each explains one mechanism end to end and links the detailed facts. Everything here describes merged dev at 3e2e83b0, the merge of PR #514 (2026-10-14), plus the baked-ontology changes of PR #520 (merge commit 1a6c03f7, 2026-10-15) and the fleet create of PR #518 (merge commit 537f2019, 2026-10-15) where it says so; the design document for what comes next is intent, not truth.

VOCABULARY. INSTANCE: one knomit server with an opaque, persisted agent id and an ssh-ed25519 instance key; it signs every commit it authors (author <id>+<op>@agents.knomit.io). AGENT BRANCH: the one branch per knowledge base that this instance writes; no one else writes it. CONSENSUS BRANCH (main/upstream): what every instance merges from; its name is recorded per repo. HOST: where a knowledge base's git lives, either a forge (GitHub) or a knomit instance that holds the repo with no origin and serves /git over mTLS. FLEET REPOSITORY: the repo whose ontology id is `fleet`; its member records are the signing policy. FLEET ROOT: an X.509 CA whose key an operator keeps as a plain owner-only file, <home>/fleet/root.key, like an SSH key (no OS keychain, no passphrase, no export/import; PR #519, 72919aa0); it signs instance/operator certificates and OAuth approval statements.

READING ORDER.
1. Membership — kb/architecture/fleet/guide/membership: the fleet repository, member records, join / leave / enroll / revoke / decommission (kb/architecture/fleet/membership-routes/7f87bdd5.md), create (kb/architecture/fleet/create/sequence), the opaque agent id.
2. PKI and transport — kb/architecture/fleet/guide/pki: fleet root custody (the plain root.key file), enroll/join/revoke through the local-only routes (PR #525; the `knomit identity enroll|install|revoke` verbs are gone), CRL watermark, the mTLS listener, principals and CertGrants, and the fleet transport (peers are plain https origins that classify as fleet peers; PR #526).
3. Push and merge — kb/architecture/fleet/guide/push-and-merge: receive-pack, the merge-time dot-path guard, the operator's web merge, consensus: auto and conflicts, main following the agent branch.
4. The acceptance gate — kb/architecture/fleet/guide/acceptance-gate: verify_signatures, CheckRange/judgeCommit, verify ci on forges, E4, audit, transitive trust.
5. Sync and triggers — kb/architecture/fleet/guide/sync: loops, intervals, realtime push/pull, triggers across instances.
6. OAuth approvals — kb/architecture/fleet/guide/oauth-approvals: parked requests, local and root-signed approvals.
Repository-level switches (verify_signatures, consensus, conflicts, sync) are ontology root attributes, and the fleet's trust-file rules are the root `artifacts:` section: see the ontology guide, kb/architecture/fact/ontology/guide/.

ONE WRITE'S JOURNEY (knomit host). An agent writes a fact on its instance's agent branch (signed) -> the sync loop pushes that branch over the fleet transport (mTLS; the origin is a plain https URL stored with auth method cert) -> receive-pack accepts it into agent/<peer> on the host (dot-path fast-fail; judged against the fleet repository's records when verify_signatures at the host's main is log/enforce) -> the operator's web merge or consensus: auto merges it into the HOST's agent branch (never main), refusing dot-path changes and settling conflicts per `conflicts` -> the host's local loop fast-forwards main -> every other instance's sync fetches main and merges it into its own agent branch. On a FORGE the push uses forge credentials, a PR/workflow merges into main, and `knomit verify ci --fleet` is the gate in that job.

BUILT on dev (with the PRs that carried the latest piece): fleet repository recognised by its ontology id and member records (F09/F10); since PR #520 that ontology is built into knomit (not a preset or template), the id `fleet` is reserved at every generic create/clone/subscribe/restore/connect door, boot admits only the repository recorded in control.db instance_fleet_repo, the fleet repository is read-only for MCP and the fact REST routes, and only the master (root.key plus a matching root.crt) refreshes its ontology (kb/invariants/fleet/baked-ontology/); REST/CLI/UI registration and durable unregistration (#334/#336); receive-pack (F11) with content closure and signer = pusher (P1, #511); the merge-time dot-path guard (#511); operator web merge and consensus: auto with conflict merging (F08, conflict-merge PRs); the acceptance gate in receive-pack and `verify ci`, `verify audit`, E4 first contact (F09); fleet root with pure issuance/revocation (its key first in the OS keychain with export/import, #512; since #519 a plain owner-only root.key file and no keychain, export or import), CRL-only install primitive with per-root watermark (P2, #512); the mTLS listener with connection re-judging, CertGrants, the fleet git transport (the internal scheme knomit+https, never typed by users since PR #526); OAuth approvals signed by the fleet root; no identity inferred from names (D18, #513); P3 (#514): judge rule A (a self-registration admitted by a leaf certificate file for the author id), rule B (a commit by a member whose leaf is revoked, missing or for another key is refused), and the fleet repository's trust files under artifacts/fleet/ (root.crt, crl.pem, certs/<id>.pem, one issued/ file per issuance, one revocations/ file per revocation) enforced by ontology-declared artifact rules (kb/architecture/fact/ontology/guide/artifact-rules). FLEET CREATE (PR #518): POST /api/v1/fleet/create, local listener only and no CLI verb, founds a fleet with a fresh root, this instance as its master and first member, hosted here (no origin) or on a forge, root first, with a state-driven total rollback for a failed step or a crash (kb/architecture/fleet/create/sequence, kb/invariants/fleet/create/). A certificate names its holder by ONE email SAN <agent-id>@agents.knomit.io (any other address is an operator); agent ids are lower case everywhere and compared exactly.

NOT BUILT on dev (design only, phases of the decentralized-membership design; the fleet JOIN, P4, IS built since PR #525 as POST /api/v1/fleet/join, see the UPDATE at the end): (fleet CREATE is built, PR #518; the reserved-id chokepoint on every mount path is built, PR #520; any join path must record its uid in instance_fleet_repo, as RegisterFleet and CreateFleet do); 'master duties' issuing, renewing and revoking certificates and re-signing the CRL as fleet-repository artifacts on each tick — P5 (since PR #525 IssueLeaf and RevokeSerial are called by the enroll and revoke ROUTES, on an operator's request; NeedsRenewal and CRLNeedsResign still have no caller, and nothing issues, renews or revokes on a tick); 'member duties' installing a newer certificate, the CRL and pinning the root from the fleet repository — P6 (InstallCRL's one production caller is the master's own revoke route, installing the CRL it just built; no member installs a newer CRL from the fleet repository yet); fleet enroll/bundle UI — P7 (the enroll and join API is built, PR #525; a browser cannot call it, it is local-listener only); multi-instance end-to-end tests — P8. Also postponed: F12 librarian, F13 leader lease (a human does both).

CONSEQUENCES. Today every certificate operation (enroll, renewal before the 90-day default expiry, revocation, CRL delivery to listeners) is an operator-requested step (enroll, revoke) through the local-only REST routes since PR #525, not an automatic one, and the fleet repository CAN hold the certificate, CRL and root as artifacts and the judge enforces their rules, but nothing writes them there automatically (the issuing and installing duties, P5/P6, are not built). Leaving a fleet does not yet revoke the leaf (that is a P5 duty). Signing policy (records) and network admission (certificates) are independent switches: a complete removal changes the record AND installs a CRL on every host. The built-in fleet ontology declares verify_signatures: enforce (and consensus: auto), so a NEW fleet repository judges every change that enters main; on the MASTER the boot replaces an EXISTING fleet repository's stored ontology wholesale with the built-in one, and members never write it (before PR #520 an existing fleet repository kept its stored ontology because the preset refresh was blocked by root attributes and artifacts). Set a fleet up root first: commit root.crt and crl.pem when the repository is created, members afterwards (fleet create does exactly that, in code).

MISREADINGS. 'Fleet create makes the fleet run itself': it issues ONE certificate (the founder's own) and publishes main; enrolling others, renewal, revocation and CRL delivery stay manual. 'The fleet runs itself': no; acceptance of a member record, certificate issuance and CRL delivery need a human on dev. 'consensus: auto merges into main': no, into the host's agent branch. 'The design document describes the system': it describes P4–P8, which are not on dev (P3 is).
