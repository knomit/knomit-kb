# Fleet guide — PKI and transport: an operator-held fleet root (its key a plain owner-only file root.key: no OS keychain, no passphrase, no export/import) signs instance certificates over each instance's EXISTING ssh-ed25519 key; since PR #525 enrollment, join, revocation and the root move are local-listener-only REST routes (POST /fleet/enroll -> bundle -> POST /fleet/join; POST /fleet/revoke; GET|PUT|DELETE /fleet/root), issued and revoked when the master is ASKED (nothing renews, re-signs or delivers on a tick); the certificate admits a peer to the mTLS listener with implicit read and push:own, and it carries no signing authority

Part of the fleet guide (kb/architecture/fleet/guide/). Describes merged dev at 3e2e83b0 (PR #514), except the ROOT paragraph, which describes the root key as of 72919aa0 (PR #519).

ROOT (fleet root side, the operator's machine, default <home>/fleet). POST /api/v1/fleet/create creates root.crt and an initial crl.pem (PR #525 deleted `knomit identity init-root`; enroll and revoke append the master's LOCAL audit logs issued.jsonl / revoked.jsonl there and revoke replaces crl.pem there; the fleet repository holds no ledger); the root KEY is the plain, unencrypted OpenSSH-format file <dir>/root.key (mode 0600, in an owner-only directory; PR #519, merge 72919aa0), like an SSH key: no OS keychain, no passphrase, no prompt, and no export-root/import-root (they were deleted; `knomit identity import-root x` is an unknown-command error). Every root operation (create, enroll, revoke, `oauth approve --sign`) reads the file through pki.LoadRoot, which refuses a directory that is not private to the user or a key that is a symlink or wider than 0600; whoever can read the file can sign for the fleet, and a lost or replaced key is a fresh fleet (kb/decisions/pki/root-custody/plain-key-file/781b626f.md). The RootID (SHA-256 of the root key's SSH wire encoding) is returned as `root_fingerprint` by enroll, join and GET /fleet/root (the `knomit identity root-fingerprint` verb was removed in #525, its only purpose was the value `install --root` took).

ISSUE (built; a route since PR #525). POST /api/v1/fleet/enroll {agent_id, public_key} (master only, local listener only; it replaced `knomit identity enroll`, and the `--operator` operator-certificate form has NO route now) signs the instance's existing ssh-ed25519 key into a bundle (leaf + root.crt + CURRENT CRL from main) and, since PR #526, wraps it in a `# knomit fleet bundle v1` document whose header names the fleet repository URL, the agent, the root fingerprint and the serial (an optional `address` picks which external address the URL uses: kb/architecture/fleet/enroll/bc7f6c5f.md); validity is the create's fleetLeafValidity. The answer also carries `serial`, `root_fingerprint` and `published`/`publish_error`. A certificate names its holder with ONE email SAN <agent-id>@agents.knomit.io (the committer's form; the id is compared for equality, never parsed); there is no URI SAN and no role field. pki.IdentityOf: exactly one email SAN that is an agent address = an INSTANCE certificate (implicit read + push:own); anything else (another address, no email, several emails) = an OPERATOR (grants rows only). Agent ids are lower case everywhere; ValidAgentID refuses an upper-case letter, '+', '@', white space or control characters where an id is minted, read back at boot, or certified, and nothing is case folded (certs/Vic.pem can hold no leaf). Certificates issued before #514 (URI SAN only) read as operators until re-issued. internal/pki splits signing from placement (IssueLeaf, RevokeSerial, SignCRL return bytes; the leaf PEM is the fleet repository's issuance record, RevokeSerial also returns a root-signed revocation statement and builds the new CRL from the CURRENT CRL) so a future fleet reconcile can write them as fleet-repository artifacts; on dev (PR #525) the enroll route calls IssueLeaf (then RecordIssuance after the commit) and the revoke route calls RevokeSerial and RecordRevocation, each on an operator's request; the fleet create calls IssueInstance and IssueCRL once each for the founder; NeedsRenewal / CRLNeedsResign have no caller.

INSTALL (instance side). POST /api/v1/fleet/join (since PR #525; `knomit identity install` is gone) (which, since #526, takes the bundle document alone and reads the fleet URL from it; POST /fleet/join:check previews it without installing: kb/architecture/fleet/join-check/6fba2b2c.md) and the desktop Settings Fleet page's binding (kept until PR 7; it may still pass a bare PEM bundle) call pki.InstallBundle: the leaf must be for this instance's key and chain to the bundle's root under its CRL; the join refuses while any of root.crt, crl.pem, instance.crt is already installed (`trust_installed`), and supplying the bundle is the operator's consent to its root (the answer prints the root fingerprint); the decision is taken against the root the caller saw, under a cross-process lock. The inverse is pki.Uninstall (leave, decommission, a refused join's undo): it removes instance.crt, crl.pem and root.crt and keeps crl.number and the key. Files land in [tls].dir (default <home>/pki): instance.crt, root.crt, crl.pem, crl.number. Trust material changes ONLY through the local-listener routes (join, leave, decommission, create, revoke's CRL), the desktop's window-gated bindings, never through a route a network peer or a browser page can reach.

REVOKE (a route since PR #525; `knomit identity revoke` is gone). POST /api/v1/fleet/revoke {agent_id, reason} (master only) finds the agent's serial through certs/<id>.pem on main, builds a new CRL from main's CURRENT CRL plus that serial (higher Number), commits crl.pem and revocations/<serial>.txt, copies them locally (RecordRevocation: revoked.jsonl line, atomic crl.pem), installs the CRL here (InstallCRL, its one production caller) and publishes. Refusals: not_enrolled, already_revoked, own_id. A listener honours a revocation only once IT holds a CRL listing the serial; members do not fetch a newer CRL from the fleet repository on dev (P6 is unbuilt). A CRL past NextUpdate is enforced and warned.

TRANSPORT. The mTLS listener ([tls].addr; off until set AND a certificate is installed) is a separate http.Server over the same handler; it requires a client certificate and judges it with pki.VerifyInstanceChain (chain to the installed root, not revoked); open connections are re-judged at first track, after each adoption and on a 10 s ticker. A verified certificate becomes a principal (Kind instance or operator decided by its email SAN, Via cert, ID = the full 64-hex key fingerprint). auth.CertGrants gives every chained INSTANCE read and push:own implicitly and nothing else; anything more, and everything an operator certificate holds, is a grants row (`knomit grants add <principal> <permission>`). Permissions: read, write, push:own, merge:main, operator, admin. Peers dial another instance with an https origin that classified as a peer when it was set (pki.ClassifyOrigin, stored as auth method cert; kb/decisions/repos/remote/plain-https-origins/07cc1cef.md) over the fleet go-git transport on pki.HTTPClient (the internal scheme is spelled only by pki.GitURL); there is no plaintext fallback.

CONSEQUENCES. Certificates gate the NETWORK (who may connect, fetch and push to a knomit host); member records gate SIGNING (whose commits a main accepts). They are independent on dev: removing an agent needs both a record change (signing) and a revocation installed on hosts (network).

MISREADINGS. 'The fleet repository distributes certificates and the CRL by itself': it can STORE them under rules the judge enforces, but issuing into it and installing from it are manual or unbuilt (P5/P6). 'openssl's certificate fingerprint is the root fingerprint': no, install --root takes the key's SSH-wire SHA-256. 'A certificate lets a peer write': an instance certificate holds only read and push:own; writing facts needs a grants row.

UPDATE (PR #514): THE FLEET REPOSITORY'S TRUST FILES. Under artifacts/fleet/ the built-in fleet ontology (not a preset since PR #520) declares: root.crt (write-once), crl.pem (replaced only by a root-signed CRL with a strictly greater Number that keeps every previously listed serial), certs/<id>.pem (an agent's current leaf; replaced only by a renewal for the member record's current key with a later NotBefore), issued/*.pem (ONE write-once file per issuance: the issued leaf's PEM, whose root signature is the record), revocations/*.txt (ONE write-once file per revocation: a statement knomit-revoke/v1 + root fingerprint + serial + time + reason, signed by the root). These per-operation files REPLACE the old append-only issued.jsonl / revoked.jsonl ledgers in the fleet repository: there is no ledger to append to there (kb/decisions/fleet/pki/per-operation-records/235c9dd9.md). A file NAME means nothing (uniqueness and readability only); order and meaning come from the signed content (D18). The root key signs X.509, CRLs and revocation statements; the statement's tag makes the three unforgeable as each other. The judge enforces these rules (kb/architecture/fact/ontology/guide/artifact-rules). Commit root.crt and crl.pem FIRST when creating the fleet repository, then members. MISREADING: 'a revocation file revokes': no; only the CRL the judge reads at the fleet revision revokes. A revocation file is a signed, judged record. Nothing writes these files automatically yet (P5).

UPDATE (PR #520, merge commit 1a6c03f7): WHO IS THE MASTER. The directory <home>/fleet is the one constant pki.FleetRootDirName (shared by internal/repos and cmd/identity.go). An instance counts as the fleet's master only when <home>/fleet/root.key is a regular file AND the root.crt beside it equals artifacts/fleet/root.crt on the fleet repository's main; a root.key alone, or one from another root, does not make an instance the master, and the key is not opened for the test. The master is the only instance that refreshes the fleet ontology (kb/invariants/fleet/baked-ontology/master-refresh/d62746d2.md).

UPDATE (PR #518, merge 537f2019): FLEET CREATE. POST /api/v1/fleet/create (local listener only, no CLI verb) is a second way to make a fleet root. With a fresh root it mints root.key, root.crt, an empty CRL (Number 1) and this instance's own leaf (via IssueInstance, so one line lands in issued.jsonl) into <home>/fleet.creating, commits root.crt + crl.pem first and then the leaf and its one issued/<serial>.pem to the new fleet repository, installs the bundle (leaf, root, CRL) into [tls].dir through InstallBundle, and moves the staging directory to <home>/fleet. It refuses (pre-flights) if any of root.crt, crl.pem or instance.crt is already installed, or <home>/fleet is not empty. The creator is the master from then on (kb/invariants/fleet/baked-ontology/master-refresh/d62746d2.md). Enrolment of OTHER instances, renewal, revocation and CRL delivery are still manual and unbuilt as described above; the create issues exactly one certificate. Details: kb/architecture/fleet/create/sequence, kb/invariants/fleet/create/preflights. (PR #525 note: `identity init-root` no longer exists; fleet create is the only way to make a root, and a new master receives an existing root through PUT /fleet/root.)
