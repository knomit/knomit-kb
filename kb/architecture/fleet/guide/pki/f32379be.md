# Fleet guide — PKI and transport: an operator-held fleet root (OS keychain, passphrase file fallback) signs instance and operator certificates over each instance's EXISTING ssh-ed25519 key; enrollment, renewal, revocation and CRL delivery are MANUAL CLI/desktop steps on dev (`knomit identity enroll` -> bundle -> `install`); the certificate admits a peer to the mTLS listener with implicit read and push:own, and it carries no signing authority

Part of the fleet guide (kb/architecture/fleet/guide/). Describes merged dev at c9c599de.

ROOT (fleet root side, the operator's machine, default <home>/fleet). `knomit identity init-root` creates root.crt, an initial crl.pem and the ledgers issued.jsonl / revoked.jsonl; the root KEY goes into the OS keychain (service "knomit", account fleet-root/<RootID>, RootID = SHA-256 of the root key's SSH wire encoding) or, without a keychain, a passphrase-encrypted root.key. `export-root` moves the key into an encrypted file (--keep copies it), `import-root` loads it on another machine: that is how the fleet root changes hands. `root-fingerprint` prints the RootID that installers confirm.

ISSUE (built, manual). `knomit identity enroll --pubkey <instance key line> [--role instance|operator]` signs the instance's existing key into a bundle (leaf + root.crt + current CRL); default validity 90 days. The role travels in the certificate's URI SAN knomit://<role>/<label> on dev. internal/pki splits signing from placement (IssueLeaf, RevokeSerial, SignCRL return bytes and the exact ledger line) so a future fleet reconcile can write them as fleet-repository artifacts; on dev nothing outside internal/pki calls them, and NeedsRenewal / CRLNeedsResign have no caller.

INSTALL (instance side). `knomit identity install` or the desktop Settings Fleet page call pki.InstallBundle: the leaf must be for this instance's key and chain to the bundle's root under its CRL; a first install or a root change (--replace-root) needs the root fingerprint confirmed out of band; the decision is taken against the root the caller saw, under a cross-process lock. Files land in [tls].dir (default <home>/pki): instance.crt, root.crt, crl.pem, crl.number. Trust material changes ONLY through the CLI or the desktop's window-gated bindings, never an HTTP route.

REVOKE. `knomit identity revoke --serial|--fingerprint` appends revoked.jsonl and reissues crl.pem with a higher Number. A listener honours a revocation only once IT holds a CRL listing the serial; on dev the only wired installer is InstallBundle (InstallCRL, the CRL-only install with a per-root, strictly-increasing Number watermark, exists for design P6 and has no caller outside internal/pki). A CRL past NextUpdate is enforced and warned.

TRANSPORT. The mTLS listener ([tls].addr; off until set AND a certificate is installed) is a separate http.Server over the same handler; it requires a client certificate and judges it with pki.VerifyInstanceChain (chain to the installed root, not revoked); open connections are re-judged at first track, after each adoption and on a 10 s ticker. A verified certificate becomes a principal (Kind instance or operator, Via cert, ID = the full 64-hex key fingerprint). auth.CertGrants gives every chained INSTANCE read and push:own implicitly and nothing else; anything more, and everything an operator certificate holds, is a grants row (`knomit grants add <principal> <permission>`). Permissions: read, write, push:own, merge:main, operator, admin. Peers dial a host through the knomit+https:// go-git scheme over pki.HTTPClient; there is no plaintext fallback.

CONSEQUENCES. Certificates gate the NETWORK (who may connect, fetch and push to a knomit host); member records gate SIGNING (whose commits a main accepts). They are independent on dev: removing an agent needs both a record change (signing) and a revocation installed on hosts (network).

MISREADINGS. 'The fleet repository distributes certificates and the CRL': not on dev (design P5/P6). 'openssl's certificate fingerprint is the root fingerprint': no, install --root takes the key's SSH-wire SHA-256. 'A certificate lets a peer write': an instance certificate holds only read and push:own; writing facts needs a grants row.
