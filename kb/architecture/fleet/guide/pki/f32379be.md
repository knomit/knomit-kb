# Fleet guide (start here): a fleet is several knomit instances sharing knowledge bases through git, each writing only its own signed agent branch, with ONE fleet repository (ontology id `fleet`) whose member records decide who may sign and an operator-held fleet root CA that admits instances to each other's mTLS listeners; built on dev c9c599de: membership, push and merge, the signature gate, manual PKI, OAuth approvals — NOT built: certificates/CRL/root kept and distributed through the fleet repository, judge rules A/B, local fleet create, fleet UI (design phases P3–P8)

Entry point of the fleet guide. Read the components in this order; each explains one mechanism end to end and links the detailed facts. Everything here describes merged dev at c9c599de (2026-10-14); the design document for what comes next is intent, not truth.

VOCABULARY. INSTANCE: one knomit server with an opaque, persisted agent id and an ssh-ed25519 instance key; it signs every commit it authors (author <id>+<op>@agents.knomit.io). AGENT BRANCH: the one branch per knowledge base that this instance writes; no one else writes it. CONSENSUS BRANCH (main/upstream): what every instance merges from; its name is recorded per repo. HOST: where a knowledge base's git lives, either a forge (GitHub) or a knomit instance that holds the repo with no origin and serves /git over mTLS. FLEET REPOSITORY: the repo whose ontology id is `fleet`; its member records are the signing policy. FLEET ROOT: an X.509 CA whose key an operator keeps in an OS keychain; it signs instance/operator certificates and OAuth approval statements.

READING ORDER.
1. Membership — kb/architecture/fleet/guide/membership: the fleet repository, member records, register / unregister, the opaque agent id.
2. PKI and transport — kb/architecture/fleet/guide/pki: fleet root custody, manual enroll/install/revoke, CRL watermark, the mTLS listener, principals and CertGrants, knomit+https.
3. Push and merge — kb/architecture/fleet/guide/push-and-merge: receive-pack, the merge-time dot-path guard, the operator's web merge, consensus: auto and conflicts, main following the agent branch.
4. The acceptance gate — kb/architecture/fleet/guide/acceptance-gate: verify_signatures, CheckRange/judgeCommit, verify ci on forges, E4, audit, transitive trust.
5. Sync and triggers — kb/architecture/fleet/guide/sync: loops, intervals, realtime push/pull, triggers across instances.
6. OAuth approvals — kb/architecture/fleet/guide/oauth-approvals: parked requests, local and root-signed approvals.
Repository-level switches (verify_signatures, consensus, conflicts, sync) are ontology root attributes: see the ontology guide, kb/architecture/fact/ontology/guide/.

ONE WRITE'S JOURNEY (knomit host). An agent writes a fact on its instance's agent branch (signed) -> the sync loop pushes that branch over knomit+https/mTLS to the host -> receive-pack accepts it into agent/<peer> on the host (dot-path fast-fail; judged against the fleet repository's records when verify_signatures at the host's main is log/enforce) -> the operator's web merge or consensus: auto merges it into the HOST's agent branch (never main), refusing dot-path changes and settling conflicts per `conflicts` -> the host's local loop fast-forwards main -> every other instance's sync fetches main and merges it into its own agent branch. On a FORGE the push uses forge credentials, a PR/workflow merges into main, and `knomit verify ci --fleet` is the gate in that job.

BUILT on dev (with the PRs that carried the latest piece): fleet repository recognised by preset id and member records (F09/F10); REST/CLI/UI registration and durable unregistration (#334/#336); receive-pack (F11) with content closure and signer = pusher (P1, #511); the merge-time dot-path guard (#511); operator web merge and consensus: auto with conflict merging (F08, conflict-merge PRs); the acceptance gate in receive-pack and `verify ci`, `verify audit`, E4 first contact (F09); fleet root in the OS keychain with export/import, pure issuance/revocation, CRL-only install primitive with per-root watermark (P2, #512); the mTLS listener with connection re-judging, CertGrants, knomit+https; OAuth approvals signed by the fleet root; no identity inferred from names (D18, #513).

NOT BUILT on dev (design only, phases of the decentralized-membership design): judge rules A (a self-registration admitted by a certificate artifact for the author id) and B (a revoked serial refused at the gate) — P3; fleet preset root attributes, local (no-origin) fleet creation and a one-fleet chokepoint on every mount path — P4; 'master duties' issuing, renewing and revoking certificates and re-signing the CRL as fleet-repository artifacts on each tick — P5 (IssueLeaf/RevokeSerial/NeedsRenewal have no caller outside internal/pki); 'member duties' installing a newer certificate, the CRL and pinning the root from the fleet repository — P6 (InstallCRL has no caller outside internal/pki); fleet enroll/bundle UI and API — P7; multi-instance end-to-end tests — P8. Also postponed: F12 librarian, F13 leader lease (a human does both).

CONSEQUENCES. Today every certificate operation (enroll, renewal before the 90-day default expiry, revocation, CRL delivery to listeners) is a manual operator step through `knomit identity` or the desktop Settings Fleet page, and the fleet repository holds no certificate, CRL or root. Signing policy (records) and network admission (certificates) are independent switches: a complete removal changes the record AND installs a CRL on every host. A fleet repository created from the preset has verify_signatures off; turning it on is a commit to that KB's main.

MISREADINGS. 'The fleet runs itself': no; acceptance of a member record, certificate issuance and CRL delivery need a human on dev. 'consensus: auto merges into main': no, into the host's agent branch. 'The design document describes the system': it describes P3–P8, which are not on dev.
