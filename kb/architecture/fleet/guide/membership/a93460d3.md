# Fleet guide — membership: the fleet repository is the ONE mounted repo whose ontology id is `fleet`; its member records (kb/members/<agent-id>/, one per agent, current values only) are the only thing that says who may sign; an instance joins by writing its own record on its own agent branch, and it counts only once a merge puts that record on the fleet repository's main

Part of the fleet guide (kb/architecture/fleet/guide/). Describes merged dev at c9c599de (2026-10-14).

RECOGNITION. A repository IS the fleet repository when its ontology id is `fleet` (fact.FleetOntologyID, fact.IsFleetOntology); Manager.fleetRepo() finds the one mounted repo with that ontology. No repo name, URL, flag or config key marks it. The embedded fleet preset (internal/fact/ontology_fleet.yaml) declares one topic, `members`, with one JS validation `members-are-policy` (a member record must be kind pragmatic, type policy) and NO root attributes: a fleet repository created from the preset has verify_signatures and consensus absent, i.e. off, unless its creator writes them.

THE MEMBER RECORD. Path: <ontology root>/members/<lowercased agent id>/<first 8 hex of sha256(agent id)>.md (memberRecordPath). The body starts with `field: value` lines: agent, state (active | left | revoked), key (the current ssh-ed25519 public key line) are required; host, branch, addresses, git, capabilities are optional and informational; free text follows. A record holds only CURRENT values: an earlier key or state is an earlier version of the same fact (knomit_explain history). Records are never deleted; leaving is a state change. addresses come only from the operator's knomit.toml external_addresses, copied verbatim.

THE AGENT ID. Opaque, computed once at first boot and persisted in control.db; every authored commit has author <id>+<operation>@agents.knomit.io and committer <id>@agents.knomit.io and is SSHSIG-signed with the instance key. Since PR #513 (design D18) nothing derives a fingerprint or any identity from an agent id, a branch name, an author email, a certificate SAN or a file name: identity comes from keys and records only.

JOIN (built). `knomit fleet register <url>` or PUT /api/v1/fleet (the CLI is a thin client of the running server; the web/desktop Fleet tab uses the same API) mounts the fleet repository as a CLONE with an agent branch, refuses it unless its ontology is the fleet preset (not_a_fleet, the mount is removed), writes this instance's own record (state active) on its agent branch and pushes to the fleet repository's origin. control.db walks standalone -> registering -> registered; a failed push is retried by the sync loop (onPush -> fleetPushed). A second fleet with a different URL is refused (409 already_registered). ACCEPTANCE is a merge of that agent branch into the fleet repository's main by a human (a forge pull request) or, where a knomit instance hosts the fleet repository with `consensus: auto`, by that host's consensus merger. At boot, fleetBootReconcile/refreshOwnRecord rewrites the own record once when the advertised fields (addresses, git, capabilities) differ from it; it does not run per tick.

LEAVE (built). DELETE /api/v1/fleet or `knomit fleet unregister` writes state `left` on the agent branch and pushes; the state stays `unregistering` and the push is retried until it succeeds or the fleet repository is archived by hand, and only a successful push unmounts it. A new registration is refused meanwhile.

CREATING a fleet repository on dev: from a template whose ontology id is `fleet`, only in mode "initialize" onto the fleet's git URL and only when this instance has no fleet (ErrTemplateFleetLocal / ErrTemplateFleetPresent); a local, origin-less fleet repository from a template is refused. A fleet repository therefore always has an origin that registration pushes to.

CONSEQUENCES. To admit, suspend or remove a signer, change that agent's record and get the change merged into the fleet repository's main; there is no other switch. Every reader of the records reads them at the fleet repository's main/upstream tip (receive-pack via Manager.FleetMembers, `knomit verify ci` via its --fleet checkout).

MISREADINGS. 'Registering makes me a member': no, the merge onto the fleet repository's main does. 'The fleet repository stores certificates, a CRL or the root': not on dev; no KB or commit carries a key list, certificate, CRL or root key (kb/decisions/fleet/source-of-truth). 'Revoking an instance certificate removes it from the fleet': no, the signature gate reads records only; a revoked certificate stops mTLS, not signing.
