# Fleet guide — membership: the fleet repository is the ONE mounted repo whose ontology id is `fleet`; its member records (kb/members/<agent-id>/, one per agent, current values only) are the only thing that says who may sign; an instance joins by writing its own record on its own agent branch, and it counts only once a merge puts that record on the fleet repository's main

Part of the fleet guide (kb/architecture/fleet/guide/). Describes merged dev at 3e2e83b0, PR #514 (2026-10-14), except the RECOGNITION, JOIN, LEAVE and CREATING passages, which describe 1a6c03f7 (PR #520).

RECOGNITION. A repository IS the fleet repository when its ontology id is `fleet` (fact.FleetOntologyID, fact.IsFleetOntology); Manager.fleetRepo() finds the one mounted repo with that ontology. No repo name, URL, flag or config key marks it. The built-in fleet ontology (internal/fact/ontology_fleet.yaml; fact.FleetOntology; NOT a preset, and the id `fleet` is reserved, see kb/invariants/fleet/baked-ontology/reserved-id/4cdcf99e.md) declares one topic, `members`, with one JS validation `members-are-policy` (a member record must be kind pragmatic, type policy), the root attributes verify_signatures: enforce and consensus: auto, and a root `artifacts:` section declaring the trust files under artifacts/fleet/ (root.crt, crl.pem, certs/*.pem, issued/*.pem, revocations/*.txt; see kb/architecture/fact/ontology/guide/artifact-rules). Being recognised by id is not enough to be THIS instance's fleet at boot: only the repository recorded in control.db instance_fleet_repo is admitted, any other fleet-id repo is unavailable with cause fleet_conflict. An existing fleet repository's ontology is replaced wholesale by the built-in one on the MASTER only (kb/invariants/fleet/baked-ontology/master-refresh/d62746d2.md); the preset refresh never touches it.

THE MEMBER RECORD. Path: <ontology root>/members/<agent id>/<first 8 hex of sha256(agent id)>.md (memberRecordPath; the id is used EXACTLY, nothing is lowercased, because ids are lower case by construction). The body starts with `field: value` lines: agent, state (active | left | revoked), key (the current ssh-ed25519 public key line) are required; host, branch, addresses, git, capabilities are optional and informational; free text follows. A record holds only CURRENT values: an earlier key or state is an earlier version of the same fact (knomit_explain history). Records are never deleted; leaving is a state change. addresses come only from the operator's knomit.toml external_addresses, copied verbatim.

THE AGENT ID. Opaque, computed once at first boot and persisted in control.db; every authored commit has author <id>+<operation>@agents.knomit.io and committer <id>@agents.knomit.io and is SSHSIG-signed with the instance key. Since PR #513 (design D18) nothing derives a fingerprint or any identity from an agent id, a branch name, an author email, a certificate SAN or a file name: identity comes from keys and records only.

JOIN (built; POST /api/v1/fleet/join since PR #525, which replaced `knomit fleet register` and PUT /api/v1/fleet; local listener only). The master first enrolls this instance's key (POST /fleet/enroll, which returns the bundle: leaf + root + CRL); the joiner posts the bundle with the fleet URL. JoinFleet checks the bundle is for THIS instance's key and agent id, installs it, mounts the fleet repository as a CLONE through the fleet door with an agent branch, refuses it unless its ontology is the fleet ontology (not_a_fleet) and its root on main is the bundle's (root_differs), records its uid in control.db instance_fleet_repo (recordFleetRepo; without it the fleet would not mount after a restart), writes this instance's own record (state active) on its agent branch and pushes it ONCE. control.db goes standalone -> registered (a member never enters `registering`); a refused join, the push's refusal included, undoes the clone, the install and the record and leaves the state standalone: nothing is retried by the sync loop. A second fleet is refused (409 fleet_present, and trust_installed while any trust material is installed). Full list of codes: kb/invariants/fleet/join/a0225037.md; the other routes: kb/architecture/fleet/membership-routes/7f87bdd5.md. ACCEPTANCE is a merge of that agent branch into the fleet repository's main: by a person on the forge for a forge-hosted fleet, or, where a knomit instance hosts the fleet repository, by the master's consensus merger (consensus: auto is declared by the fleet ontology itself). The product text says the fleet's master merges, not a human. At boot, fleetBootReconcile/refreshOwnRecord rewrites the own record once when the advertised fields (addresses, git, capabilities) differ from it; it does not run per tick.

LEAVE (built; POST /api/v1/fleet/leave since PR #525, which replaced DELETE /api/v1/fleet and `knomit fleet unregister`; local listener only). It writes state `left` on the agent branch, makes ONE push attempt (answer `pushed` / `push_error`), then WHATEVER the push did it drops the repository from every lens, deletes it, runs pki.Uninstall and returns the state to standalone, so it works offline. The durable retry-until-pushed unregistration (the `unregistering` state, kb retracted decision adb65151) is gone; guardFleetRemoval still refuses archive and delete of the fleet repository in every state (409 fleet_repository) but now points at leave and decommission. The master is refused (`is_master`): it decommissions, or hands the root on and stands down first. CONSEQUENCE: a leave whose push failed leaves NO `left` record on the fleet; the master's revoke (POST /fleet/revoke) is the authoritative half.

CREATING a fleet repository: no generic door can. A fleet-id ontology is refused by preset, custom YAML, initialize, template, clone, subscribe, restore and connect (ErrFleetOntologyReserved, 422); the fleet template and its ErrTemplateFleet* sentinels are gone. A fleet repository is mounted only by two fleet-door routes (PR #518 and #525): POST /fleet/create (a fresh root; a copy with no origin is the hub) and POST /fleet/join (a clone of an existing fleet's URL, which always has an origin); both record their uid (reserved-id invariant).

CONSEQUENCES. To admit, suspend or remove a signer, change that agent's record and get the change merged into the fleet repository's main; there is no other switch. Every reader of the records reads them at the fleet repository's main/upstream tip (receive-pack via Manager.FleetMembers, `knomit verify ci` via its --fleet checkout).

MISREADINGS. 'Registering makes me a member': no, the merge onto the fleet repository's main does. 'The fleet repository stores certificates, a CRL or the root': it CAN, as judged artifacts under artifacts/fleet/ (PR #514), but the member records still say who may sign, and nothing writes the certificate files automatically yet (P5); no KB carries a key list (kb/decisions/fleet/source-of-truth). 'Revoking an instance certificate removes it from the fleet': no. A revoked certificate stops mTLS on a host that has installed the CRL, and, once the CRL is on the fleet repository at the revision a gate reads, rule B refuses that member's commits (revoked); the member's record is still active until changed. Leaving a fleet (state left) does not revoke the leaf: the master must call POST /fleet/revoke (a manual step until the P5 reconcile).

UPDATE (PR #514): agent ids are lower case everywhere (pki.ValidAgentID refuses an upper-case id at minting and boot), so the members/<id>/ folder, the record's `agent:` field, the commit author address, the certificate's email SAN id and the leaf file certs/<id>.pem are all the same string, compared by EQUALITY only; nothing is parsed out of an id and nothing is case folded. A self-registration (judge rule A) may touch only members/<id>/ for its own id. MISREADING: 'an id with + or @ or a capital is a different id': it is refused as an id.

UPDATE (PR #523, verified at merge commit 3ac59b57): (1) A member writes only its own folder: the record-owner rule refuses (not-owner) any commit that changes a path outside members/<id>/ and DECLARED artifact paths, deletes anything under its own folder, or writes a record there whose agent: is not <id>; so 'records are never deleted' is enforced, and a member's merge that settles a conflict with main is refused (kb/invariants/store/verify/record-owner/74b64ef6.md). (2) The loader counts a record only if its agent: equals its folder, and a malformed fleet tree fails the load (kb/invariants/fleet/member-loader/folder-binding/07d6a7a2.md). (3) The state `revoked` is derived for the readers (FleetStatus.record_state, GET /fleet/members) from the CRL at the same main and is never written; the judge reads records as written (kb/decisions/fleet/derived-revoked/504782ff.md). Revised misreading: 'the record on main says revoked once the leaf is on the CRL' is false; the readers say so, the record still says what its owner wrote.

## UPDATE (PR #524, verified at merge commit 9db8c106): who merges the record

'It counts only once a merge puts that record on the fleet repository's main' is done by the fleet's MASTER on EVERY hosting (RepoInstance.isFleetMaster: the root key file here and its certificate the root on main), automatically: on a knomit-hosted fleet the member pushes its agent branch to the hub (no origin), receive-pack judges it and the master's merger merges it; on a forge-hosted fleet the master FETCHES the member's agent/<id> branch, judges `tip ∖ main` (a first join is judged as a joiner: rule A and the record-owner rule), promotes it and merges it, and publishes main without force. A member never merges. A refused FIRST join (no record on main yet) has no row on GET /fleet/members to hang `last_refusal` on; its refusal is visible only in the master's log (and in memory, Manager.FleetRefusals). `last_refusal` appears on the member whose record's `branch` matches the refused branch. Refusals are in memory only: a restart judges each fetched branch once more.

UPDATE (PR #527, verified at merge commit c6e282db). A first join the master REFUSED no longer has 'no row': the id the master enrolled but whose record is not on main is an `enrolled` row of GET /fleet/members (derived from a leaf on main and no record, never written to a record), and a refusal whose refused tip's author is that id hangs on that row as `last_refusal` (matching is by the tip's author, because an enrolled id has no record and so no `branch`; a record row still matches by its `branch`). Refusals also go into the master's 200-entry in-memory ring that GET /fleet/activity shows as `refused`. FleetStatus.record_state never reads `enrolled`. See kb/architecture/fleet/members-route/528a3e8e.md and kb/architecture/fleet/activity/d66f9e08.md.
