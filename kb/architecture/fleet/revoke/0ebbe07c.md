# POST /api/v1/fleet/revoke builds the new CRL from MAIN's current CRL (pki.RevokeSerial), commits crl.pem and revocations/<serial>.txt, copies them locally with pki.RecordRevocation (revoked.jsonl line and an ATOMIC crl.pem), installs the CRL here (installSignedCRL -> pki.InstallCRL, one of two production callers) and publishes; refusals not_enrolled, already_revoked, own_id

SEQUENCE (PR #525, verified at merge commit fd991d4f, RevokeFleetMember in internal/corpus/repos/fleet_membership.go; master only, under fleetOpMu). (1) own_id (409) for the master's own agent id (decommission instead). (2) Read main (fleetAtMain): its CRL must exist; the agent's leaf is certs/<id>.pem on main, none = 404 `not_enrolled`. (3) pki.RevokeSerial(root, MAIN's CURRENT CRL, serial, ...) builds the new CRL (Number + 1, a superset of the current list) and the root-signed revocation statement; a serial already listed is 409 `already_revoked`, any other failure 422 `revoke_failed`. (4) writeFleetArtifacts commits crl.pem and revocations/<serial>.txt on the master's agent branch. (5) pki.RecordRevocation copies locally: appends the revoked.jsonl audit line and replaces <home>/fleet/crl.pem through writeFileAtomic, so a crash never leaves a torn crl.pem (the file GET /fleet/root hands the next master); a failure is a WARN. (6) pki.InstallCRL(here, root, CRL) installs the CRL on this instance (a failure is `install_error` in the answer and does not undo the revoke). (7) publish (hub: local main fast-forward; forge: push agent branch, then main). The answer is 200 {agent_id, serial, crl_number, published, publish_error, install_error}.

AUTHORITY. MAIN's CRL is the authority and the base of the new CRL; the local crl.pem and revoked.jsonl are COPIES. The old pki.Revoke refused to build from a crl.pem that lagged revoked.jsonl or was missing; that check is gone with the function, so nothing verifies that the local crl.pem lists every logged serial. The artifact rule `revoked_set: superset` (kb/decisions/fleet/pki/per-operation-records/235c9dd9.md) judges main's CRL. Revoking a lost-key leaf needs the leaf to be the one at certs/<id>.pem (see the enroll invariant).

REACH. Revoke reaches other members only when THEY hold the new CRL: each copy installs main's CRL in its own sync round (fleet_tick.go, PR #536; kb/architecture/fleet/tick/crl-install/f5806529.md), and the revoked member's own listener keeps admitting it until its round has installed the CRL. The gate (judge rule B) refuses the revoked member's commits once the CRL is on main at the revision it reads, and readers show `revoked` (derived).

PINNED BY the repos forge e2e (TestFleetMembership_ForgeEnrollJoinAdmitLeaveRevokeDecommission: statement on main, CRL #2 installed, revoked.jsonl one line, the local crl.pem equals main's new CRL) and the cmd knomit-hosted e2e; sabotage that skips InstallCRL or RecordRevocation turns them red.

MISREADINGS. 'Revoke deletes the member's record or removes it from the fleet': it only lists the serial. 'Revoke needs the member online': it does not.

UPDATE (PR #532, squash commit a1b0ca5d on dev, verified there): steps (3) to (6) are now one function, Manager.revokeLeaf(ctx, ri, root, baseCRL, agentID, leaf, reason) in fleet_membership.go: it builds the CRL from the base it is GIVEN, commits crl.pem and revocations/<serial>.txt on the master's agent branch, records locally and installs the CRL, and returns the new CRL; it does NOT publish and the caller holds fleetOpMu. RevokeFleetMember calls it with main's current CRL, then publishes (step 7). The master's leave duty (revokeLeftMembers, fleet_leave.go; kb/invariants/fleet/leave/master-revokes-left/d2132d6b.md) is the second caller: it chains the base across several leavers, reason "left the fleet", and leaves the publish to the round that ran it. MISREADING: 'the leave duty is a second InstallCRL caller that the archtest should list': it goes through revokeLeaf, which has the one InstallCRL call of the membership side. (The PR #532 wording that pki.InstallCRL had ONE production caller file, fleet_membership.go, and that no member installs main's CRL, was superseded by PR #536 and is corrected by the next paragraph.)

UPDATE (step 15a, PR #609, merged as 786b0ce7; re-read there): fleet_membership.go was split by operation. The sequence above now lives in internal/corpus/repos/fleet_revoke.go: RevokeFleetMember (steps 1-2, 7), revokeLeaf (steps 3-6, still does not publish) and installSignedCRL, which is the function that calls pki.InstallCRL on the membership side. pki.InstallCRL has TWO production caller files: fleet_revoke.go (installSignedCRL, from revokeLeaf, MASTER only) and fleet_tick.go (installMainCRL, every copy's tick duty, from #536); test/archtest installCRLCallers lists exactly those two and pins FILES, not functions. The file references to fleet_membership.go in the SEQUENCE paragraph are historical (as of fd991d4f); fleet_membership.go now holds only shared helpers (masterFleet, publishMasterWrite, RebuildFleetIndex). The enroll and join operations are in fleet_enroll.go and fleet_join.go. MISREADING: 'only the master ever installs a CRL': the master installs the CRL it just signed; every copy (master included) also installs main's CRL in its own round.
