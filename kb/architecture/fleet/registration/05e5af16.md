# Fleet membership is REST on the running server's LOCAL listener (POST /api/v1/fleet/create | join | leave | enroll | revoke | decommission, GET|PUT|DELETE /fleet/root; GET /fleet and /fleet/members are readable by any admitted principal) driving the control.db state machine standalone -> registered (join, or a create with no origin) | standalone -> registering -> registered (a create with an origin whose publish is pending); leave and decommission go straight back to standalone; the push that completes a pending create step is retried by the repo's own reconcile loop (onPush -> Manager.fleetPushed)

repos.Manager: fleetRepo() = the one mounted repo whose ontology id is `fleet` (the built-in fleet ontology, reserved id; no name, no URL stored in the repo; WHICH repo the fleet is IS stored since PR #520, in control.db instance_fleet_repo, and boot admits that uid, plus the repository NAMED by an unfinished create's marker so the boot rollback can open it: kb/invariants/fleet/create/marker-and-rollback).

WAYS IN AND OUT (PR #525, merge fd991d4f, replaced the PUT/DELETE /api/v1/fleet registration; `Manager.RegisterFleet`, `UnregisterFleet`, `registerOwnRecord`, the same-URL refresh, the `unregistering` state and the durable-unregistration retry are all GONE, and so are `knomit fleet register|unregister`; the CLI keeps `knomit fleet status`):
- JOIN (POST /fleet/join, `Manager.JoinFleet`; since PR #526 its request is {bundle, auth?} and the fleet URL comes from the bundle document, with POST /fleet/join:check as the read-only look first: kb/decisions/fleet/bundle-document/0c5cf18a.md): installs the bundle, clones through the fleet door, records the uid with recordFleetRepo, writes the own record (persisted agent id, CURRENT key, state active, host, branch; memberRecordPath members/<id>/<sha256(id)[:4] hex>.md) and pushes ONCE. On success the state is `registered`: a member NEVER enters `registering` any more. Any refusal undoes everything (state stays standalone). Details and the refusal codes: kb/invariants/fleet/join/a0225037.md.
- LEAVE (POST /fleet/leave): `left` record, one push, then repository, lens mounts and installed material are removed whatever the push did, state standalone. The push is not retried by anything: a leave whose push failed (offline) is not durable, the master revokes by hand.
- CREATE (POST /fleet/create, PR #518): founds a fleet with a fresh root. Its state is set only at its END, in the transaction that also deletes the instance_fleet_create marker (registered with no origin, registering with an origin), so a fleet being created is still `standalone` to fleetPushed and FleetStatus until it is done. `registering` therefore means ONLY a forge-hosted create whose publish of main is pending.
- DECOMMISSION (POST /fleet/decommission, master): back to standalone.

Retry: runReconcileLoop takes onPush(repo, err); the Manager wires Manager.fleetPushed, which ignores non-fleet repos, records fleet_last_attempt/fleet_last_error (cleared on success), and on success completes registering -> registered (only a create's pending step: on the instance that holds the fleet root only after main is published: kb/invariants/fleet/registration/registering-needs-main-published). It no longer has an unregistering arm; a member's registered state does not wait for a later push. FleetRetry pushes once on demand. Guards (PR #520, merge commit 1a6c03f7): Archive/DeleteRepo of the fleet repo answer 409 fleet_repository in EVERY state; the text (PR #525) names POST /api/v1/fleet/leave and POST /api/v1/fleet/decommission. A fleet-id repo that is NOT the recorded one is not the fleet repository (it is unavailable with cause fleet_conflict) and archives normally; see kb/invariants/fleet/baked-ontology/reserved-id/4cdcf99e.md.

Clients: web handlers (problem+json with code; declared in openapi.yaml, contract-tested), the Fleet rail target (PR #528: Members, Activity and Settings tabs; ManageFleet.tsx and the Fleet server page behind the gear are gone; every mutation control is drawn only when GET /fleet says `local`, kb/invariants/web/fleet-ui/local-gate/b27d49db.md), and `knomit fleet status` as a thin local-socket client (localAPIClient/localCall, never app.New). record_state is read from the fleet repo's local upstream (pending until the master merges the agent branch).

BOOT RECONCILE (F10). Manager.Start ends by launching startFleetBootReconcile: one goroutine (which FIRST runs recoverFleetCreate under fleetOpMu, rolling back a fleet create that did not finish, then fleetBootReconcile), tracked by fleetBootWg (Close waits on it before releasing control.db), that NEVER blocks or fails Start. fleetBootReconcile does nothing unless control.db fleet_state is `registered` (standalone and registering are skipped) and the instance is not read-only (INFO line; a read-only instance never pushes). A missing/unopenable fleet repo or a missing own record is one WARN (its text now says to leave and join again), retried at the next boot. Otherwise refreshOwnRecord reads the own record at the agent branch HEAD (not main), diffs the advertised fields against advertised() (config external_addresses verbatim, git only when git.serve && !read_only, os/arch from runtime via hostPlatform, version.String(), read_only, hostname, key, branch) and writes at most ONE version via WriteFactIfUnchanged(expectBlob = the blob it read), keeping state and notes verbatim; logs INFO `fleet record current` or `fleet record updated: <fields>`. The ordinary sync loop pushes it; the master merge publishes it on main. This is the only AUTOMATIC fleet write (the routes above are operator actions); TestFleetRecordWriters_OnlyFleetCallers pins the exact call sites of the record writers, and no KB write path reaches it. A same-URL re-registration used to refresh the record too; that path is gone, so a changed advertised field reaches the fleet at the next boot only (or via leave + join).

STATUS (F10). FleetStatus adds external_addresses ([] never null), notice (while empty), record (own record at agent head), record_current (agent head == advertised now), and record_pending_update = the own record's BLOB differs between agent head and main while main has one. MISREADING: pending update is NOT 'agent branch ahead of main' — the sync loop merges main into the agent branch, so the branch is routinely ahead by merge commits with nothing to accept. PR #525 also added `master`, `hosting` and `root_dir` (kb/architecture/fleet/membership-routes/7f87bdd5.md).

UPDATE (PR #524, verified at merge commit 9db8c106): `Manager.fleetPushed` (the onPush hook) does NOT publish main; it records the attempt and, on a nil push error, advances the state. The publish of main happens in the push round itself (the sync loop's fleetPeers.publish, or Manager.pushFleet for FleetRetry), for the fleet master or the root holder, and a failed publish arrives here as the push error. GET /fleet/members additionally carries `last_refusal` (the master's in-memory refusal of the branch of the member whose record matches). Details: kb/invariants/fleet/registration/registering-needs-main-published/f035a93a.md.

MISREADING: 'registered' on a root holder means main is published; on a member it means its record reached the origin (the join's one push), NOT that the master has admitted it: a member counts only once the master merges its record into main.
