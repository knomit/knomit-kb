# mcp-go v0.45.0 client.NewInProcessClient registers NO server-side session unless sampling, elicitation or roots handlers are set, so recordClientInfo would record nothing; the chat uses its own transport that registers a server.InProcessSession under the supplied id

At mcp-go v0.45.0, client/transport/inprocess.go InProcessTransport.Start creates and registers a server.InProcessSession ONLY when a sampling, elicitation or roots handler is configured; otherwise the transport has no session and SendRequest hands HandleMessage a context with no ClientSession. knomit's AfterInitialize hook (recordClientInfo) returns early when the context has no session id, so a plain NewInProcessClient chat would leave no client_sessions row and no marker.

knomit therefore has its own transport.Interface in internal/edge/mcp/inprocess.go. Start registers server.NewInProcessSession(<supplied id>, nil) with MCPServer.RegisterSession; every request runs under a context built by requestContext, and after HandleMessage the request is recorded through clientsessions.Store.RecordRequest. Session id: the caller-supplied canonical chat id (chat-<32 hex>), also the clientsessions row id. Endpoint: /api/v1/chats/<id>, so the endpoint owner is per chat. Endpoint kind: unscoped (repos.WithSessionScoped plus a fresh repos.PinRecorder), so every tool call needs a knomit_bind handle. clientInfo: name knomit-chat, version <provider>/<model>.

Consequence: a second OpenInProcessSession with a live id fails (RegisterSession returns ErrSessionExists); Close ends the row and unregisters, after which the id is free. Do NOT switch to client.NewInProcessClient to save code; the Sessions marker and binding set would silently vanish. Version-dependent: re-check Start when mcp-go is upgraded.
