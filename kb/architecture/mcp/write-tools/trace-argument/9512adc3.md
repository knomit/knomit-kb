# The MCP write tools (knomit_learn, knomit_update, knomit_retract, knomit_review, knomit_hypothesize) take an optional `trace` object of `Key: value` entries that applyTrace validates and attaches to the call's ctx BEFORE anything is written, so every commit THAT CALL makes ends with them; nothing is kept between calls (#349)

Built for #349 (PR feat/agent-trace -> dev). internal/mcp/trace.go owns it: traceArg() is the schema property (an object whose additionalProperties are strings), declared on all five write tools — it MUST be in review's and hypothesize's schemas because those two refuse undeclared arguments (rejectUnknownArguments). applyTrace(ctx, req) runs in each handler right after the moment_name checks (learn/update/retract) or right after rejectUnknownArguments (review/hypothesize), i.e. before any store read for the write: absent `trace` -> ctx unchanged (D-mint: no paragraph); present -> parseTrace, then store.WithAgentTrace(ctx, set), which puts the set on the ctx the handler hands to every write. Because the set rides the ctx, ONE call stamps ALL its commits: learn's atomic move (facts + retract in one commit), a review ANSWER's applied decisions, and a review START's planning-time dedup merges and removals (synthesize Plan -> dedupCluster run on the start call's ctx), and a hypothesize discover proposal. The server stores no trace per session, binding or connection: two tasks interleaved on ONE MCP session carry their own traces write by write (TestAgentTrace_E2E_ParallelTasksOnOneSession). Consequences for a consumer: (1) an agent must pass the same `trace` on EVERY write of a task — a write without it is untraced (the accepted 'agent forgets' gap); (2) passing `trace` on a review start stamps the corpus-wide dedup commits of that start into the task's story; (3) an OLDER server ignores `trace` on learn/update/retract (they do not reject unknown arguments) and REFUSES the call on review/hypothesize. Misreading to avoid: the trace is not session state and there is no 'set my trace' call — it is per write, by design (user, on rev 1: 'what if the session is long running and does multiple tasks in parallel').
