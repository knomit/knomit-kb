# knomit_explain of a .knomit/ path returns ONE `system_file` node with the raw content (depth 0); deeper in a walk a file is a SUMMARY (path, commit, blob, size, superseded, deleted) — drill in with path AND commit; REST GET of the same path returns the raw bytes, PUT/DELETE stay 400

Built on branch feat/system-file-reads (user rulings 2026-10-06; decision 1: content only when the file is explained directly; decision 2: REST GET reopened, PUT/DELETE refused).

ROUTING. resolveExplainTarget tests `fact.IsSystemFilePath(rel)` BEFORE NormalizePath (which would lowercase and append .md). Bare → the binding's write mount; `kb://<id>/.knomit/…` → that mount (lens read mounts included). Every other dot path, and a malformed `.knomit/…` one, still reaches closedToFactTools and is refused "closed to the fact tools".

DEPTH 0 (file named directly). One node, no history, no children, no session/cursor: `{path, commit, depth: 0, kind: "system_file", blob, size, content, superseded, deleted}`. No title/type/confidence/refs/history/motifs — it is a file. `commit` optional (full 40-hex; reads the file as of that commit; superseded = blob differs at the tip, deleted = gone at the tip). Non-UTF-8 → `encoding: "base64"`. Over 256 KiB (explainFileContentMax) → `content_truncated: true`, no content. Missing / wrong case / a directory / a symlink (never followed) → error "<path> not found at the tip of branch <b>" (or "at commit … on branch …"). `history_cursor` with a file → refused ("has no history_cursor").

IN A WALK. A fact node's local system-file refs are enqueued at the FACT's own commit (root: its live revision; others: the edge's target commit) and come back as `system_file` summaries — blob and size, no content — with superseded/deleted against the tip. To read one: explain {file: node.path, commit: node.commit}. Leaves: no children. A cited file that is NOT a file at the fact's own commit (absent, a directory or a symlink) is still EMITTED (#428 follow-up N2; it used to be dropped silently): `deleted: true`, `superseded: false`, blob "" and size 0. It stays deleted even when the file exists at the tip, because what the fact cited is the pin, and no pinned version exists to compare with the tip. This is how a ref that an experiment resolution accepted against the OTHER side's tree shows up. A store READ ERROR still drops the child, as fact children are dropped on a read error, so that a transient failure is never reported as a deletion; it is logged at debug.

REST. GET /repos/{r}/branches/{b}/facts/.knomit/<path> and …/commits/{sha}/facts/.knomit/<path> return the RAW bytes (text/plain; charset=utf-8, or application/octet-stream when not UTF-8), headers X-Knomit-Commit and X-Knomit-Blob, 404 when absent or a symlink (never followed; user ruling 2026-10-08), 413 over 4 MiB. Judged percent-decoded. No sub-resources: `.knomit/x.md/commits` names a file (404). The LENS GET route /lenses/{lens}/facts/.knomit/<path> serves it raw too (one read rule across REST): bare = the write mount at its read branch, kb://<id12>/.knomit/<path> = that mount; an unmounted id, a mount without the file and a missing file all get the lens's single 404 "Fact not found" with no branch named (no mount-topology oracle). The lens has no write route. PUT/DELETE of .knomit/ stay 400.

WHAT THIS DOES NOT MEAN: knomit_query by a .knomit/ path is still refused ("is private") and .knomit/ is never indexed or listed; explain of `.github/x` or `kb/.drafts/x.md` is still refused.
