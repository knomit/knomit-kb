# knomit_explain history paging: the first call shows 3 revisions; history_cursor pages return history only (20), from a KEYSET position bound to the binding, mount and normalized fact path. The root's `commit` stays the first-parent resolved version and can differ from history.revisions[0]

Shape:
- `history` holds revisions (commit, date = the change's own author date, message, action added|modified, diff against the content it was EDITED FROM), more_available, and history_cursor (present only when more_available).
- A revision carries content_unavailable: true when its content, or the content it was edited from, is missing from the repository. Its diff is then empty, and the tool text tells agents not to read that commit for content. Damage itself is reported by Verify, not by explain.
- The first explain call shows explainHistoryDisplay = 3 revisions next to the body and graph.
- A call with `file` + `history_cursor` returns {path, history} only: no body, no facts, no graph walk. It holds up to explainHistoryPageSize = 20 revisions.
- The diffs are PRECOMPUTED in path_changes (store.RevisionDiff), so a page reads no blob at all.

The cursor is opaque base64url JSON of historyCursor: the binding's PinID and read-set fingerprint, the mount ("" for the write repo, else its 12-hex id), the NORMALIZED path, the anchor, the keyset frontier (store.PathHistoryCursor), and whether the anchor was on the branch when it was issued. It is NOT signed. A hand-edited cursor naming on-branch commits, even ones newer than its anchor, returns a page of those commits' history. That grants nothing beyond explain at HEAD, but a cursor is not a tamper-proof position. Pages check readability with readFactVersion (one blob read), not readNode (no HEAD-liveness lookup).

Refused, each as a distinct error, never as a short or empty page:
- "unknown history_cursor": it cannot be decoded, was issued to another binding, or the fact is not readable at its anchor.
- "history changed": the anchor left the branch, or a frontier change is no longer on it or no longer indexed (a rewind, or a :rebuild that dropped commits; both swap the branch atomically, so a page never sees one half-done). Restart without history_cursor.
- "not a fact path": the file is neither .md under the ontology root nor a .knomit/<area>/ slot (fact.IsFactFilePath; the first call applies the same rule).
- "belongs to another fact": the normalized path or mount differs. kb/x, x and kb/x.md are the SAME fact to it.
- a cursor combined with `commit` or `cursor`.

The ROOT's `commit` is NOT history.revisions[0].commit. It stays the first-parent resolved version, because seen-keys and edge pins are first-parent commits. It is computed by LiveRevision, which is pinned equal to RevisionsBefore(anchor, 1) at every commit but uses jump pointers instead of a 15 ms walk at 10k commits. For a merge-delivered fact the root commit is the PR merge, and revisions[0] is the write behind it.

Measured on 2026-09-29, review round 4 (BenchmarkExplainHistory on the fixture; medians of 20 calls elsewhere):
- first explain call: 1.6 ms on the 25-change fixture, 2.2 ms on crawl-state (36 changes), 5.8 ms on a knomit-kb fact (round 5).
- On a synthetic 10,000-commit repo the first call is 17 ms. That is dominated by OutgoingAtCommit's first-parent walk (graph edges, not history), whose fast path was taken out of #347; its history part is sub-millisecond.
- history_cursor page: 1.7 ms, 1.7 ms, 1.8 ms and 0.29 ms respectively.
- A cold first call after open: 6-16 ms. On the 10k repo it is 237 ms, which is RepoInstance.ID's one-time walk to the root commit (cached afterwards, and not history code).

NAMED MISREADING: "to page history, re-call with commit = the oldest revision". That re-anchors the whole explain, re-sends the body, and on a branching history skips the other side's revisions. history_cursor is the paging mechanism.
