# client_session_bindings is the SET of handles one MCP session has presented, keyed by (session_id, handle) so two handles on one repo are two rows — client_sessions.binding stays as the LAST-seen pin, and ?binding= matches any row via EXISTS and returns the session once

SCHEMA (control.db, migration `000006_client_session_bindings.up.sql`):
`client_session_bindings(session_id, handle, binding, branch, first_seen_at, last_seen_at, request_count)`, PRIMARY KEY `(session_id, handle)`, plus an index on `binding`.

WHY IT EXISTS. Since binding became a per-call handle, one `Mcp-Session-Id` can serve several independent callers at once. `client_sessions.binding` holds the LAST pin seen, so it stopped describing a session and became a snapshot of whichever call landed most recently. This table is the set.

KEYED BY HANDLE, NOT BY PIN. Two handles naming the same repo are TWO ROWS, because they are two callers; collapsing them by pin would discard exactly the distinction the handle exists to make. The PK is what enforces it.

HOW IT IS STAMPED. `recordClientSession` reads `repos.ResolvedBindingFromContext` ONCE (handle, pin, branch) and uses it twice: the pin goes to `Store.Touch` for `client_sessions.binding`, and the whole triple goes to `Store.RecordSessionBinding` — an upsert that inserts at count 1 and afterwards bumps `last_seen_at` and the count while leaving `first_seen_at` alone. Reading the context twice could DISAGREE, because a task-augmented tool call may still be writing into the recorder while this runs; that is also why `PinRecorder` is mutex-guarded.

ONLY A REQUEST THAT RESOLVED A HANDLE ADDS A ROW. A URL-scoped request has a pin but no handle, so it stamps `client_sessions.binding` as before and contributes NOTHING here. That asymmetry is correct rather than an omission: the set answers "which handles has this session presented", and a URL-scoped caller presented none. Such a session's `bindings` array is empty, and the API serialises it as `[]`, never `null`.

READING IT. `Store.SessionBindings(ctx, sids)` returns every row for a page of sessions in ONE query, most-recently-used first within each session. One query for the same reason the handler builds one `bindingNames` index: control.db runs at `SetMaxOpenConns(1)`, so a lookup per row would serialise the whole response behind a single connection. A failure DEGRADES — the handler logs, drops the sets and still serves the rows, because the last-seen pin is on the row itself and losing the page over the richer view would be the worse trade.

FILTERING. `?binding=` matches a session if ANY binding it has presented is that pin: `binding = ? OR EXISTS (SELECT 1 FROM client_session_bindings b WHERE b.session_id = client_sessions.id AND b.binding = ?)`. Two halves, both load-bearing. EXISTS rather than a JOIN because a session with three handles on one pin is ONE session — a join would return it three times and corrupt every count built on the list. And the legacy `binding = ?` half is what keeps a session recorded only on the old column matching, so the filter does not regress for rows written before this table existed.

LIFETIME. The set belongs to its session and dies with it: `Store.Purge` deletes rows whose `session_id` is no longer in `client_sessions`. That is deliberately UNLIKE `binding_handles`, which is routing state a live caller may still present and therefore ages on its own `last_used_at`.

WHAT THIS DOES NOT MEAN. These rows are OBSERVATIONAL, exactly like every column of `client_sessions` and for the same reason — inferred from request traffic, never to be gated on. Routing was decided by the handle argument on the call itself. A row here says only "this session was seen presenting this handle". It is also NOT the routing table: that is `binding_handles`, which maps a handle to its target and is what the gate reads.
