# knomit_reason's ONLY deadline is the asker's `budget` (seconds, default 10 min) applied inside Engine.Run — it deliberately skips the 30 s / 60 s handler timeout every other MCP handler wraps its ctx in; an expired budget returns outcome `interrupted`, not a tool error

ReasonHandler follows the handler prologue (rejectUnknownArguments, RequireBinding, validate, execute) EXCEPT step 1 of kb/conventions/mcp/handler-template: no context.WithTimeout(30s|60s). A run takes minutes, nothing above the handler limits it (listeners have WriteTimeout 0, the MCP mount no per-call limit; E02 §10), so a handler timeout would be the only thing ending a run early. Engine.Run applies context.WithTimeout(ctx, budget); the goja interrupt is armed on that ctx and every host call (the tool handlers derive their own deadlines from the earlier one; the model HTTP request uses it) is bounded by it. The per-endpoint slot wait also counts against the budget. On expiry the result is outcome `interrupted` with the chain the host logged so far, and no answer facts.

The tool is registered in toolRegistrationsWith as a WRITE tool (it opens an experiment and writes there) with gateRequired, so the binding and permission gates wrap it at registration; arguments are exactly question, budget, binding.

Consequence: do not 'fix' knomit_reason by adding the usual 30 s wrapper; a client that times out first needs its own tool timeout raised. Misreading to avoid: this is not a precedent for other handlers dropping their timeouts.

What pins it (since 4900270a): TestReason_DeadlineIsExactlyTheBudget wraps the tool set and records the deadline the first tool call's ctx carries; with budget 600 s it must be within (590 s, 600 s]. Any handler-side WithTimeout shorter than the budget fails it — a 1 s wrapper added to ReasonHandler passed every other test at 69be5c98 and fails this one. TestReason_DeadlineComesFromBudget covers the other direction (a 1 s budget ends a 5 s model call as `interrupted`).
