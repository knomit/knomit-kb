# binding_handles maps an opaque per-bind handle to a pin plus a branch ('' meaning the target's own read branch); handles coexist, age out on their own last_used_at, and the PinRecorder carries the resolved pin back out for client_sessions

SCHEMA (control.db, migration `000005_binding_handles.up.sql`):
`binding_handles(handle TEXT PRIMARY KEY, binding TEXT NOT NULL, branch TEXT NOT NULL DEFAULT '', created_at INTEGER NOT NULL, last_used_at INTEGER NOT NULL)` plus an index on `last_used_at`.

- `handle` is 24 crypto/rand bytes as unpadded base64url — 32 characters, 192 bits, no structure. It is deliberately not derivable from a repo or lens name, so a model cannot conjure a valid one from a name it has seen.
- `binding` is the uid PIN (`repo:<uid>` / `lens:<uid>`), never a name, so a rename cannot strand a live handle.
- `branch` is the read branch the handle names. `''` means "the target's own read branch" and resolves through the very same `NewBindingOfRepo(ri, branch)` the URL-scoped mounts use — the agent branch for a normal repo, the followed upstream for a subscription. `knomit_bind` does not accept a branch yet and always writes `''`, so the column is inert today; it exists so per-handle branch switching becomes a behaviour change rather than a migration. A non-empty branch on a LENS pin is REFUSED, not ignored: a lens pins a branch per mount at resolve time, so one branch names nothing coherent across its members.

HANDLES COEXIST. `MintBindingHandle` is an INSERT, never an upsert. Every `knomit_bind` call mints a fresh handle and old handles stay valid, so two callers on one connection each hold a handle that names what it named when minted. An agent that binds twice by mistake ends up holding two working handles rather than one silently retargeted one — which is exactly the difference from the session-keyed upsert this replaced.

PURGE. `Store.BindingHandle` stamps `last_used_at` on every successful resolve, and `Store.Purge` deletes handles whose `last_used_at` is older than the retention window (`session.client_retention`, default 168h — a SETTING, not a constant). Handles age on their OWN last-used time, NOT with any session: they are not keyed by session id, so no session row's death can collect them, and a handle a long-lived caller keeps using stays alive indefinitely.

THE PinRecorder SEAM. `client_sessions.binding` is still stamped, and the value has to travel BACKWARDS to do it: on this mount the binding is named by an argument inside the request body, so nothing knows it until the tool gate runs, and a handler cannot alter its caller's context. So `SessionBindingMiddleware` installs a mutex-guarded `repos.PinRecorder` in the request context, the gate records the resolved pin into it, and `recordClientSession` — which runs AFTER the response — reads it out via `BindingPinFromContext`. The mutex is not decoration: a task-augmented tool call keeps running after the response is written, so the write and the read genuinely race. The body is deliberately NOT peeked: the old bounded peek was 4 KB and `knomit_learn` bodies routinely exceed it, so a `binding` key ordered after a large body would fall outside the window.

WHAT THIS DOES NOT MEAN. `client_sessions.binding` remains OBSERVATIONAL — a trail of what a session was seen doing, which must never gate anything; routing was already decided, by the handle. And the old `session_bindings` table still EXISTS in the schema: it is abandoned, not dropped, because `knomit migrate-registry` replays the whole control chain as one concatenated script and therefore admits idempotent `CREATE ... IF NOT EXISTS` only. Nothing reads or writes it; its rows carry no value. Do not read its presence as evidence that session-keyed binding is still live.
