# knomit registers 9 MCP tools (4 in read-only mode) on ONE shared server; mounted per-branch, per-lens, AND session-bound

The MCP surface is NINE tools, listed in `toolRegistrations` (internal/mcp/server.go) in registration order with their write flags:

| tool | write? |
|---|---|
| knomit_learn (write facts in one commit) | yes |
| knomit_query (paginated snippet search) | no |
| knomit_explain (walk versioned provenance) | no |
| knomit_update (revise in place) | yes |
| knomit_retract (commit a removal) | yes |
| knomit_hypothesize (generate hypothesis facts; user-initiated) | yes |
| knomit_review (work-stealing prune/distill/reflect) | yes |
| knomit_repos (THE discovery tool: every repo and lens on the server, plus this session's binding) | no |
| knomit_bind (bind this session to a repo or lens by name) | no |

knomit_bind arrived with the session-bound mount (PR #209). A tenth tool, knomit_catalog, was built and then FOLDED INTO knomit_repos before it shipped (PR #210) — so a reader who finds knomit_catalog referenced anywhere is looking at something written mid-flight; it never existed on dev.

knomit_repos needs NO BINDING and returns `{repos, lenses | lenses_error, bound?}`: every repo on the server; every lens (the `lenses` key is always present on success, `[]` when the server has none); and — only when the session points at something — a `bound` section carrying the binding name and mount table it used to return at the top level, or `status: "unresolvable"` with the reason when the session's stored pin no longer resolves. When the lens registry lookup FAILS, the `lenses` key is ABSENT and `lenses_error` carries the text while `repos` and `bound` are still returned, so a caller never loses its own mount table over an unrelated control-plane error and can never read a failure as "no lens exists" (the field is a `*[]T` with omitempty for exactly that reason: a plain slice would marshal zero lenses and nil identically). The shape is fixed PER STATE, not per session: each key's presence reports a fact about the world (is the session bound; did the lens lookup succeed), never a mode the tool is in, so the name never means two things.

knomit_bind returns that same `bound` object ALONE plus the bound base's instructions — never the catalogue. Both tools build the mount table through one shared function so they cannot drift.

`knomit_update` list fields (domain, entities, refs) replace WHOLESALE: send the complete new list; omit the field to leave it unchanged (internal/mcp/update.go: `updates.Refs != nil` → `fact.Refs = refs`).

**readOnly GATES the tool set.** `NewServer(defaultOntologyRoot, mgr, readOnly, embedders...)` runs `enabledTools(toolRegistrations(mgr, embedders...), readOnly)`: when readOnly=true every write tool is dropped and only the FOUR read tools register — knomit_query, knomit_explain, knomit_repos, knomit_bind. So a read-only ('demo') instance exposes 4 tools, not 9. knomit_repos and knomit_bind are write=false deliberately: without them nothing on the unscoped mount could be discovered, bound, and therefore read.

**MOUNT POINTS — there are THREE**, all dispatching to the same handler (`mcpDispatch`, internal/web/router.go), each accepting `/mcp` and `/mcp/*`:
- repo+branch-scoped: `/api/v1/repos/{repo}/branches/{branch}/mcp`
- lens-scoped: `/api/v1/lenses/{lens}/mcp`
- session-bound (unscoped): `/api/v1/mcp` — no repo or lens in the URL; the session picks one with knomit_bind and the choice is stored per Mcp-Session-Id.

WHAT THIS DOES NOT MEAN:
- **Profile does NOT key servers and does NOT gate tools.** There is exactly ONE MCP server instance (`s.mcpHandler`), not three. Profile is a per-repo setting in control.db that changes ONLY the per-session instruction addendum; it never adds or removes a tool — readOnly does. `?profile=` on the endpoint is accepted, logged at debug, and IGNORED. See kb/decisions/mcp/profile-per-repo/f192649f.md.
- '9 tools' is the read-WRITE count. Do not assume a client can call learn/update/retract/review/hypothesize against a read-only instance — those 5 write tools are absent from its catalog entirely.
- **Every tool fails closed on an unbound session EXCEPT knomit_repos.** Seven return a tool error naming knomit_bind; knomit_repos answers, because it is how an agent learns the names knomit_bind accepts. Do not 'restore consistency' by making it fail too.
- The tool list is NOT filtered by the binding's write eligibility. A session bound to a subscription (a read-only follower) still SEES the write tools listed; they fail at call time on Binding.WriteOK(). tools/list is per server, not per session.
- The lens mount is not a second server; a lens authors under its WRITE repo's profile.
- The session-bound mount is not an authorization boundary. Any repo is already reachable by URL, so binding grants nothing new; the network remains the boundary.

Clients usually reach this via knomit-bridge (stdio). With neither --repo nor --lens the bridge connects to the session-bound mount.
