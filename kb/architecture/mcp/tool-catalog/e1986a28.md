# knomit registers 10 MCP tools (5 in read-only mode) on ONE shared server; mounted per-branch, per-lens, AND session-bound

The MCP surface is TEN tools, listed in `toolRegistrations` (internal/mcp/server.go) in registration order with their write flags:

| tool | write? |
|---|---|
| knomit_learn (write facts in one commit) | yes |
| knomit_query (paginated snippet search) | no |
| knomit_explain (walk versioned provenance) | no |
| knomit_update (revise in place) | yes |
| knomit_retract (commit a removal) | yes |
| knomit_hypothesize (generate hypothesis facts; user-initiated) | yes |
| knomit_review (work-stealing prune/distill/reflect) | yes |
| knomit_repos (list the mounts behind THIS BINDING) | no |
| knomit_bind (bind this session to a repo or lens by name) | no |
| knomit_catalog (list EVERY repo and lens this server serves) | no |

knomit_bind and knomit_catalog arrived with the session-bound mount (PR #209, PR for Task 9). Both are registered write=false deliberately: a read-only instance still needs them, or nothing on the unscoped mount could be bound and therefore nothing read.

knomit_repos and knomit_catalog answer DIFFERENT questions and neither was overloaded into the other — knomit_repos describes the CURRENT binding's mounts, knomit_catalog describes the whole server and needs no binding at all.

`knomit_update` list fields (domain, entities, refs) replace WHOLESALE: send the complete new list; omit the field to leave it unchanged (internal/mcp/update.go: `updates.Refs != nil` → `fact.Refs = refs`).

**readOnly GATES the tool set.** `NewServer(defaultOntologyRoot, mgr, readOnly, embedders...)` runs `enabledTools(toolRegistrations(mgr, embedders...), readOnly)`: when readOnly=true every write tool is dropped and only the FIVE read tools register — knomit_query, knomit_explain, knomit_repos, knomit_bind, knomit_catalog. So a read-only ('demo') instance exposes 5 tools, not 10.

**MOUNT POINTS — there are THREE**, all dispatching to the same handler (`mcpDispatch`, internal/web/router.go), each accepting `/mcp` and `/mcp/*`:
- repo+branch-scoped: `/api/v1/repos/{repo}/branches/{branch}/mcp`
- lens-scoped: `/api/v1/lenses/{lens}/mcp`
- session-bound (unscoped): `/api/v1/mcp` — no repo or lens in the URL; the session picks one with knomit_bind and the choice is stored per Mcp-Session-Id. Every other tool fails closed until it does.

WHAT THIS DOES NOT MEAN:
- **Profile does NOT key servers and does NOT gate tools.** There is exactly ONE MCP server instance (`s.mcpHandler`), not three. Profile is a per-repo setting in control.db that changes ONLY the per-session instruction addendum; it never adds or removes a tool — readOnly does. `?profile=` on the endpoint is accepted, logged at debug, and IGNORED. See kb/decisions/mcp/profile-per-repo/f192649f.md.
- '10 tools' is the read-WRITE count. Do not assume a client can call learn/update/retract/review/hypothesize against a read-only instance — those 5 write tools are absent from its catalog entirely.
- The tool list is NOT filtered by the binding's write eligibility. A session bound to a subscription (a read-only follower) still SEES the write tools listed; they fail at call time on Binding.WriteOK(). tools/list is per server, not per session.
- The lens mount is not a second server; a lens authors under its WRITE repo's profile.
- The session-bound mount is not an authorization boundary. Any repo is already reachable by URL, so binding grants nothing new; the network remains the boundary.

Clients usually reach this via knomit-bridge (stdio). With neither --repo nor --lens the bridge connects to the session-bound mount.
