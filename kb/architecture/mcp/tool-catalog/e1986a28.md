# knomit registers 10 MCP tools (4 in read-only mode) on ONE shared server; mounted per-branch, per-lens, per-lens-experiment, and unscoped — where the target is named per CALL by a `binding` handle, not by the session

The MCP surface is TEN tools, listed in `toolRegistrations` (internal/mcp/server.go) in registration order with their write flags:

| tool | write? |
|---|---|
| knomit_learn (write facts in one commit) | yes |
| knomit_query (paginated snippet search) | no |
| knomit_explain (walk versioned provenance) | no |
| knomit_update (revise in place) | yes |
| knomit_retract (commit a removal) | yes |
| knomit_hypothesize (generate hypothesis facts; user-initiated) | yes |
| knomit_review (work-stealing prune/distill/reflect) | yes |
| knomit_experiment (list/open/commit/rollback/sync an exp/<name> branch) | yes |
| knomit_repos (THE discovery tool: every repo and lens on the server, plus what a given handle points at) | no |
| knomit_bind (mint a handle naming a repo or lens) | no |

knomit_experiment arrived with experiments (PR #236) and is write=TRUE even though it authors no fact: `open` forks a branch, `commit` merges one into the agent branch and `rollback` deletes one, so a read-only instance must not expose it. knomit_bind arrived with the unscoped mount (PR #209). A tool called knomit_catalog was built and then FOLDED INTO knomit_repos before it shipped (PR #210) — a reader who finds it referenced anywhere is looking at something written mid-flight; it never existed on dev.

**THE `binding` ARGUMENT (PR #215, merged b3cebeb4).** On the unscoped mount every tool EXCEPT knomit_repos and knomit_bind takes a REQUIRED `binding` argument: the opaque handle knomit_bind returns. knomit_repos takes it optionally; knomit_bind takes none, since it is where handles come from. On a URL-scoped mount the argument is refused. Nothing is keyed on Mcp-Session-Id — see kb/invariants/mcp/session-binding/handle-is-the-only-router. The gate that enforces it wraps each handler AT REGISTRATION rather than as middleware, for reasons in kb/invariants/mcp/binding-gate/registration-seam.

knomit_repos needs NO BINDING and returns `{repos, lenses | lenses_error, bound?}`: every repo on the server; every lens (the `lenses` key is always present on success, `[]` when the server has none); and — only when the call carried a handle that resolved — a `bound` section carrying the target's NAME and mount table, or `status: "unresolvable"` with the reason when the handle's pin no longer resolves. Since PR #236 the write mount row also carries `experiment` (the name, when the binding is inside one) and the bound section carries `lapsed_experiment` when a stored experiment could not be honoured. NOTE the key: `bound.name` is the repo or lens name; the key `binding` means the opaque HANDLE everywhere on this surface and never a name (it was `bound.binding` before #215). When the lens registry lookup FAILS, the `lenses` key is ABSENT and `lenses_error` carries the text while `repos` and `bound` are still returned, so a caller never loses its own mount table over an unrelated control-plane error and can never read a failure as "no lens exists" (the field is a `*[]T` with omitempty for exactly that reason: a plain slice would marshal zero lenses and nil identically). The shape is fixed PER STATE, not per session: each key's presence reports a fact about the world, never a mode the tool is in.

knomit_bind returns `{binding, name, mounts}` — the handle FIRST — plus the bound base's instructions; never the catalogue. It takes an optional `experiment` that RESUMES an existing one (it never creates; that is knomit_experiment open). It and knomit_repos build the mount table through one shared function so they cannot drift.

`knomit_update` list fields (domain, entities, refs) replace WHOLESALE: send the complete new list; omit the field to leave it unchanged (internal/mcp/update.go: `updates.Refs != nil` → `fact.Refs = refs`).

**readOnly GATES the tool set.** `NewServer(defaultOntologyRoot, mgr, readOnly, embedders...)` runs `enabledTools(toolRegistrations(mgr, embedders...), readOnly)`: when readOnly=true every write tool is dropped and only the FOUR read tools register — knomit_query, knomit_explain, knomit_repos, knomit_bind. So a read-only ('demo') instance exposes 4 tools, not 10 — the read-only count did NOT change when knomit_experiment was added, because it is a write tool. knomit_repos and knomit_bind are write=false deliberately: without them nothing on the unscoped mount could be discovered, bound, and therefore read.

**MOUNT POINTS — there are FOUR since PR #236**, all dispatching to the same handler (`mcpDispatch`, internal/web/router.go), each accepting `/mcp` and `/mcp/*`:
- repo+branch-scoped: `/api/v1/repos/{repo}/branches/{branch}/mcp` — which reaches an experiment as `branches/exp:<name>`
- lens-scoped: `/api/v1/lenses/{lens}/mcp`
- lens-experiment-scoped: `/api/v1/lenses/{lens}/experiments/{name}/mcp`, which re-pins ONLY the lens's write member (architecture/web/lens-experiment-mount)
- unscoped: `/api/v1/mcp` — no repo or lens in the URL; a caller mints a handle with knomit_bind and names it on every subsequent call. Formerly called the 'session-bound' mount, which is now a misnomer: several independent callers may share one connection and hold different handles at the same time.

WHAT THIS DOES NOT MEAN:
- **Profile does NOT key servers and does NOT gate tools.** There is exactly ONE MCP server instance (`s.mcpHandler`), not four. Profile is a per-repo setting in control.db that changes ONLY the per-session instruction addendum; it never adds or removes a tool — readOnly does. `?profile=` on the endpoint is accepted, logged at debug, and IGNORED. See kb/decisions/mcp/profile-per-repo/f192649f.md.
- '10 tools' is the read-WRITE count. Do not assume a client can call learn/update/retract/review/hypothesize/experiment against a read-only instance — those 6 write tools are absent from its catalog entirely.
- **Every tool fails closed without a valid handle EXCEPT knomit_repos.** Eight return a tool error naming knomit_bind; knomit_repos answers, because it is how an agent learns the names knomit_bind accepts, and it REPORTS a bad handle under `bound` rather than raising. Do not 'restore consistency' by making it fail too.
- The tool list is NOT filtered by the binding's write eligibility. A caller whose handle names a subscription (a read-only follower) still SEES the write tools listed; they fail at call time on Binding.WriteOK(). tools/list is per server, not per session.
- The lens mount is not a second server; a lens authors under its WRITE repo's profile.
- The unscoped mount is not an authorization boundary. Any repo is already reachable by URL, so a handle grants nothing new; the network remains the boundary. The handle is unguessable so that a model cannot conjure a valid one from a name, not to keep anyone out.

Clients usually reach this via knomit-bridge (stdio). With neither --repo nor --lens the bridge connects to the unscoped mount and forwards the `binding` argument untouched.
