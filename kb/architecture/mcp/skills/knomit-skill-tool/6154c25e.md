# knomit_skill is the MODEL-invocable face of repo skills: read-only, gated like knomit_query (unscoped mount needs a binding handle and then serves that binding's write repo), same source as the prompts — no name lists name+description, a name returns body + bundled files or a named error

User, on F08 PR C: "add the knomit_skill tool too" — MCP prompts are slash commands a user types and a model cannot see or run, so a session told "follow the work-task skill" (including a recipe-started `claude -p` session) needs a tool.

internal/edge/mcp/skill_tool.go, registered in toolRegistrationsWith as {skillTool(), SkillHandler(skills), write=false, gateRequired}. It shares the server's one skillSource with the prompt layer (same parse cache, same WARN-once record), so every rule is identical: binding's write repo (lens → write repo only), tip of UpstreamBranch(), malformed skipped, 256 KiB TOTAL inline cap.

- knomit_skill {} → {repo, branch, commit, skills:[{name, description}]}.
- knomit_skill {name} → {repo, branch, commit, name, description, body (raw; $ARGUMENTS left in place), files:[{path, uri, mime_type, text, size}], not_inlined:[{path, uri, size, reason: binary|over-cap}]}; absent → tool error "no skill <name> in repo <repo> (skills are read from the tip of <branch>…)".
- Unscoped mount: like knomit_query — no handle is the gate's "requires a `binding` argument … knomit_bind" error; with a handle it serves that binding. (The prompts on that mount still list none: a prompt request carries no handle.)
- Read-only servers keep it (not a write tool); the writable catalog is now 12 tools.

What this does NOT mean: there is no `knomit.skill(name)` on the recipe/script host; that fallback was named in the RCA and is not built without a user ruling.
