# Ollama v2 adapter sends each tool call's knomit id as tool_calls[].id and tool_call_id (plus tool_name); the server's own call id is not stored

Ollama's api types accept ids on tool calls: ToolCall.ID (json id) and Message.ToolCallID (json tool_call_id), both present at v0.30.0 and later (checked v0.30.0, v0.35.0, v0.40.14, api/types.go); the server assigns its own ids to the calls it parses (server/routes.go toolCallId, v0.40.14); those ids are opaque and their format varies (the source suggests 'call_<8 chars>' but Ollama 0.40.14 live returned a 32-character mixed-case id such as X9kKkGmlFqRVsSAlK2yPLXzc5Ua5wC4k), so never depend on a server id's format and the native path forwards tool_call_id to llama-server (llm/llama_server.go). The adapter (renderOllamaChecked, ollamaAssistant) walks hook 6 then hook 7, records for each assistant tool_use its tool name and a wire id under the knomit id (tu_<n>), and renders (a) the replayed call as tool_calls[] with id, and (b) each tool_result as {role:tool, tool_name, tool_call_id, content} with the same id and the name of the call it answers. The wire id is ALWAYS the knomit id (ToolUse.ID); an id the server put on a streamed call is not stored (there is no ToolUse.ProviderID: kb/decisions/llm/ollama-v2/e4ebd61a.md). The neutral history never takes Ollama's id as its key, so a later provider switch still works. tool_name is still sent, so a server that ignores ids still gets name-plus-order matching: that is the fallback, not the mechanism. Consequence: two parallel calls to the SAME tool in one turn are told apart by id (tested with and without server ids, results answered in reverse order, asserting the server's own ids are not sent). A tool_result whose id answers no tool_use earlier in the snapshot makes Stream return an error BEFORE any HTTP request (renderOllama, the test variant, emits empty ids/name instead). The ids sit in hooks 6 and 7, never in the shared prefix, so byte-stability is unaffected. Confirmed live on Ollama 0.40.14, 2026-11-04, model qwen35 (hf.co/unsloth/Qwen3.5-4B-GGUF:Q4_K_M): the adapter did not store the server id; Ollama accepted the knomit id tu_1 in both tool_calls[].id and tool_call_id, and the model used the tool result. Not tested live: two parallel calls to the same tool (that behaviour rests on the unit tests only). knomit's tu_<n> ids are always what is sent. Does NOT mean Ollama requires ids: matching by name remains what older servers do. Supersedes the earlier claim that Ollama matches by name and not by id, which was a statement about the adapter, not about Ollama.
