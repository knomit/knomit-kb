# Ollama v2 adapter maps knomit tool_use ids to tool NAMES on every render; the tu_ id never reaches Ollama and a result with no matching call refuses the request

Ollama's /api/chat matches a tool result to its call by tool name (a {role:"tool", tool_name, content} message), not by id. renderOllamaChecked walks hook 6 then hook 7 in order, records each assistant tool_use's name under its knomit id (tu_<n>), and renders each tool_result block as a tool message carrying that name. The tu_ id is never sent. A tool_result whose id answers no tool_use earlier in the snapshot makes Stream return an error BEFORE any HTTP request (renderOllama, the exported-for-tests variant, silently emits an empty tool_name instead). Consequence: two parallel calls to the SAME tool in one assistant turn are indistinguishable on the wire; results are matched by order, which Ollama does not document. Does NOT mean the neutral history changes: it keeps knomit ids so a later provider switch still works. Reasoning from another provider is dropped on replay (Entry.ReplayFor); Ollama's own reasoning goes back in the message thinking field. API shape from the Ollama API docs (docs/api.md, main branch read 2026-11-04).
