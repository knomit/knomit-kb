# A script fire runs in a FRESH goja runtime with the compiled Program cached per trigger by the script BLOB hash (loaded in phase A through TriggerIndex.ScriptAt at the head), `Date` pinned to the run's UTC clock through SetTimeSource for `if` AND scripts, the interrupt armed by context.AfterFunc on the host ctx (budget expiry OR dispatcher cancel), and a Go panic inside a host call recovered by the host — never left to reach safeRun

internal/fact/script.go: `CompileScript(name, src)` (strict), `RunScript(ctx, prog, name, globals, host, now)` builds `newSandboxVM(now)` — goja.New(), process/require deleted (defensive: goja has no host bindings), `SetTimeSource(func() time.Time { return now })` — binds the frozen JSON globals (shared `sandboxGlobals` with EvalIf, which now also takes `now`), binds the frozen `knomit` object, and runs the program with `stop := context.AfterFunc(ctx, vm.Interrupt)`. A Program is not tied to a runtime; a runtime is never reused (sticky interrupt flag, shared prototypes).

The dispatcher's cache (`scriptState.scripts`, keyed by trigger NAME, staleness by blob) is refreshed in phase A by `loadScripts` for every ACTIVE `do: script` trigger — one tree-entry lookup per script per run (`ScriptAt` in internal/store/triggers.go, modelled on OntologyAtCommit, returns ErrNoScriptAtCommit when absent) — so a changed `.knomit/triggers/<name>.js` takes effect on the next run with no restart, and a missing or uncompilable script is known BEFORE any fire: the endpoint overlays `invalid` + the error on the trigger, ERROR is logged once per (trigger, blob), and every fire is a `script-error` row while the bookmark keeps advancing (no catch-up burst when fixed). A script commit is never an episode (`.knomit/` is private to the diff).

Why the ctx arms the interrupt [M1]: goja's Interrupt does not interrupt a native Go call, so the budget bounds the JavaScript and the NUMBER of host calls; the same hostCtx (WithTimeout(runCtx, budget)) is what every handler receives, so a blocking call returns DeadlineExceeded at the budget rather than the handler's own 60 s/30 s, and `stop()` (d.cancel) interrupts a spinning script within the interrupt latency. After the run: runCtx cancelled → the run aborts (re-fires later, at-least-once); hostCtx deadline exceeded or *goja.InterruptedError → `script-timeout`; any other error → `script-error`. Note that an interrupted script never runs its `catch`: the interrupt lands on the very next instruction after a host call returns.

Why the host recovers [M2]: a Go panic inside a host closure escapes RunProgram as a Go panic; in the dispatcher that reaches safeRun, which drops the write-behind buffer and RE-RUNS the range on every kick — a deterministic handler panic would loop forever. `scriptHost.call` recovers, crashdumps once per (trigger, blob, tool), and returns an error the fact layer throws to the script.

Consequence for TESTS: a busy loop written as `while (Date.now() - s < 90) {}` never ends under the pinned clock, and an iteration-count spin is CPU time, which shrinks under contention (review F1: it flaked the detector tests on loaded CI). A test that needs a trigger slow in real wall time uses the test-only hook `triggerHooks.evalDelay` (repos helper `slowIf`), which sleeps INSIDE the trigger's timed section before its `if` — the `changeDelay` shape; the detector tests keep their original 90 ms / 80–85 ms thresholds and passed 40/40 with every core pinned.
