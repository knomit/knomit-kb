# Ontology guide — the other per-node blocks: `triggers` (rules fired by learn/update/retract/due changes under a topic: emit, script, push or run a recipe), `context` (typed keys a fact under the topic may or must carry) and `guidance` (paths to .knomit/guidance/*.md fed to the hypothesize and review prompts); all three inherit or scope by the topic tree, none is ever fatal to an existing repo, and each makes a preset repo diverge

Part of the ontology guide (kb/architecture/fact/ontology/guide/). Describes merged dev at c9c599de.

TRIGGERS (F07/F08; on a topic or child node). Each entry: name (kebab-case; its bookmark is keyed by it), match (a glob relative to the ontology root, starting with the topic's path; * ? **, {agent} and {host} placeholders; never a dot path; absent = everything under the topic), on (learn | update | retract | due, one or a list; due fires once when a matching live fact's `expires` has passed), if (optional JavaScript over fact, agent, change), do: emit (log + SSE), script (inline `js:` or .knomit/triggers/<script>.js read from the agent branch head; host API query, explain, learn, update, retract, emit, push, run; writes stamped Knomit-Trace/-Cause/-Trigger), push (a 1 s countdown then one sync round), run (start the recipe .knomit/recipes/<name>.js from the tip of the repo's main, else <home>/recipes, without waiting). States: active, invalid (a warning, logged once, bookmark frozen, never fatal) or unsupported (valid syntax this version does not act on; none today: emit, script, push and run are all active). Triggers run asynchronously on the dispatcher, never in the write path, and only on this instance's own agent branch. The script rate cap is per instance (knomit.toml [triggers].script_rate_per_minute), not per trigger.

CONTEXT (F22; on a topic or child node, inherited, nearest declaration wins). `context: {<key>: {type: string|number|bool|enum|time, values (enum), required, pattern (string), min/max (number), max_len (string)}}`. A fact's `context:` map (snake_case keys, scalar values, at most 16) is refused on write if a key is undeclared for its topic, a value has the wrong type, or a required key is missing (ValidateContext, before the JS rules; REST update runs it too). knomit_query filters by it. It is data: nothing acts on a value.

GUIDANCE (F23; on the root or any node, nearest wins). Two keys only, hypothesize and review, each a path `guidance/<file>.md` relative to .knomit/. The synthesis prompts receive the text read at ONE consensus-tip commit (never the agent branch or an experiment). There is no per-call instructions argument. A refused value fails closed (it shadows the parent, no guidance).

STRICTNESS. Every trigger, context or guidance problem is a WARNING on the open path (the repo keeps opening) and, for context and guidance, fatal for a NEW ontology; a bad trigger only disables that trigger.

CONSEQUENCES. These blocks are how a repository is programmed (queues, leases, expiry scripts, mission workflows) without knomit code changes. Any of them on a preset-derived repo is divergence (reasons triggers, context, guidance) and stops preset upgrades. Trigger declarations, scripts and recipes are re-read by blob from the branch they come from, so a committed change takes effect at the next dispatcher run; context declarations use the mount-time ontology snapshot.

MISREADINGS. 'Triggers fire on facts pushed by peers': not on the pushed branch; only once a merge brings them into this instance's agent branch. 'Context values steer knomit': no, they are labels for finding facts.
