# Ontology guide — JS validations: `validations: [{name, message, rule}]` on the root or any node are JavaScript boolean expressions over a frozen `fact` object, compiled at parse and run root -> topic -> each declared child; since PR #533 they run at EVERY writer (the store's two write cores: MCP, triggers, REST with 422, the review pipeline) and at every entry path (receive-pack, the fetch judge, `knomit verify ci`, the master's own range, merge results), in every verify_signatures mode

Part of the ontology guide (kb/architecture/fact/ontology/guide/). Describes merged dev at c9c599de.

WHAT A RULE IS. A Validation {name, message, rule} on the document root or on any topic/child node. `rule` is a JavaScript expression compiled ONCE when the ontology parses (goja, strict); a rule that does not compile makes the whole ontology fail to parse. Evaluation: a FRESH goja runtime per rule, `process`/`require` deleted, one non-enumerable global `fact`, a 100 ms interrupt; the truthiness of the result is pass/fail.

WHAT IT SEES. `fact` carries every Fact field by its json name: kind, type, domain, entities, motifs, refs, title, body, path, confidence, sources, origin, evidence_weight, expires, context ({} when absent). origin and motifs are the RESOLVED values that will land on disk (the type's default origin; subject-restating motifs stripped), not the raw input. ref_warnings is deliberately hidden. A rule cannot see other facts, the repository, the network, the author or the commit.

WHAT IT CAN DO. Pass or fail one fact: required kinds/types for a topic (`fact.kind === 'pragmatic' && fact.type === 'policy'`, the fleet preset's members-are-policy), minimum refs or confidence, title/body shape, required entities or domains, context values (after the typed context gate already passed). The first failing rule returns a ValidationError naming rule, topic path and message; the write is refused.

ORDER ON A WRITE. ValidateContext (the F22 typed context gate) FIRST, then root rules, then the topic's rules, then each declared child down the topic path, stopping at the first undeclared segment (a deeper undeclared category gets the rules of its deepest declared ancestor and above). Segments are lowercased for lookup. A nil ontology runs no rules but still refuses any context.

WHERE IT RUNS (fact.ValidateFact callers): the knomit_learn handler (each fact, and the merged fact when learn's dedup folds into an existing one) and the knomit_update handler — including when a `do: script` trigger calls knomit.learn/update, because the script host goes through those UNCHANGED handlers — and experiment commits whose resolutions supply a {body} (MCP knomit_experiment and the REST experiment route, through internal/resolutions). (SUPERSEDED by PR #533, see the UPDATE below: the 'NEVER' list that stood here, REST create/update, review writes, merges and receive-pack, no longer holds.)

CONSEQUENCES. (Before #533: a write-time guard on the MCP write path only. See the UPDATE.) Rules use the mount-time ontology snapshot. Adding a rule to a preset-derived repo stops preset upgrades (a validation name the preset lacks is shape divergence).

MISREADINGS. 'Every fact in the repo satisfies the ontology's rules': still false (untouched legacy facts are never judged). 'A rule can query the KB or check the writer': no, it sees only the one fact.

UPDATE (PR #533, squash commit 6f241959 on dev, verified there; user ruling kb/decisions/fact/validation/enforced-everywhere/338656ce.md): the header and the 'WHERE IT RUNS' list above describe the MCP write path only. Validations now ALSO run (1) at the SOURCE for every in-process writer, in both store write cores under the branch lock before any object is written: REST create and update (refused 422 with the rule's message), the review pipeline (distill, prune/subsume, reflect, dedup, discovery: refused as warns, the file unchanged), fleet code and trigger scripts (kb/invariants/store/fact-write/validate-write); and (2) at every ENTRY path, on the branch's NET change, in every verify_signatures mode including off and in every repository: receive-pack, the fleet fetch judge, `knomit verify ci`, the master's own range, with the merge RESULT validated by MergePushed, MergeConsensus and verify ci's merge-tree check (kb/invariants/store/verify/validation-net-change, kb/invariants/store/verify/ci-merge-result). So a topic rule now binds every fact a writer or an entering branch ADDS OR CHANGES. It does NOT bind untouched legacy facts (kb/gotchas/fact/validation/legacy-invalid-facts), deletes, byte-identical copies (Replay), a branch whose ontology does not parse (writers skip, entry paths refuse everything: kb/gotchas/store/verify/unparseable-ontology) or reconcileMain following an origin's main (trust-the-forge). CONSEQUENCE for a template or mission author: a `validations:` block IS now a guarantee for new and changed facts under a path, including review output, so a rule you add can make the review pipeline's writes to that topic fail; test review's behaviour on the topic before adding a rule that distilled or merged facts cannot meet.
