# Ontology guide — artifact rules: the root `artifacts:` section maps path patterns under artifacts/ to closed-value keys (pki root|crl|leaf|issuance|revocation, change write-once|append-only|replace, replace_when crl-newer|leaf-renewal, revoked_set superset, max_size) that the commit judge enforces as Go primitives on every commit entering main, only under verify_signatures log/enforce; a bad value is fatal, an unknown key a warning on open, and an undeclared path has no rule

Part of the ontology guide (kb/architecture/fact/ontology/guide/). Describes PR #514 (feat/fleet-judge-rules) as merged at 3e2e83b0. The root `artifacts:` section declares rules for FILES under artifacts/. It exists because topic attributes cannot reach artifacts/ (the topic walk covers only the ontology root, kb/). It is a map: path pattern (relative to artifacts/) -> a flow block of keys. Every key and value below is the complete set; the sets are CLOSED.

Example (the built-in fleet ontology):
  fleet/root.crt: { pki: root, change: write-once, max_size: 16KiB }
  fleet/crl.pem: { pki: crl, change: replace, replace_when: crl-newer, revoked_set: superset }
  fleet/certs/*.pem: { pki: leaf, change: replace, replace_when: leaf-renewal, max_size: 16KiB }
  fleet/issued/*.pem: { pki: issuance, change: write-once, max_size: 16KiB }
  fleet/revocations/*.txt: { pki: revocation, change: write-once, max_size: 4KiB }

KEYS AND VALUES (each value names a Go primitive; the refusal rule is what a user sees):
change — what may happen to a matching file that already exists.
- write-once: may be ADDED; never modified, never deleted. Refusal rule artifact-write-once. It does NOT mean the file must exist, and it does not stop the first add.
- append-only: the new blob must hold the old blob as an exact byte prefix AND be strictly longer; never deleted. Refusal rule artifact-append-only.
- replace: may be modified only when replace_when holds; never deleted. Needs replace_when. Refusal rule artifact-replace.
replace_when (only with change: replace):
- crl-newer (needs pki: crl): the new file is a CRL signed by the declared pki: root, and its CRL Number is strictly greater than the old one's; an old CRL with no readable Number cannot be replaced this way. Refusal artifact-replace.
- leaf-renewal (needs pki: leaf): the new leaf chains to the root, is not on the CRL, its email SAN agent id EQUALS the id the file name stands for, its key equals the CURRENT key of the one member record for that id in the commit's tree, and its NotBefore is strictly later than the old leaf's. Refusal artifact-replace.
revoked_set:
- superset (needs pki: crl): a replacing CRL must also list every serial the CRL it replaces lists, so a reissue never un-revokes. It is its own key because a new behaviour is a new key, never a new value of crl-newer. Refusal artifact-replace.
pki — the file's role; a pki file that is ADDED must hold as its role or the add is refused with artifact-pki.
- root: a CA certificate; needs change: write-once; one literal path; at most one per ontology.
- crl: an X.509 CRL the root signed; needs change: replace + replace_when: crl-newer; one literal path; at most one.
- leaf: an agent's certificate; needs change: replace + replace_when: leaf-renewal; the pattern is literal except its last segment, which holds exactly one '*' standing for the agent id. On add it must chain to the root, not be revoked by the CRL in the commit's tree, and have an email SAN agent id equal to the id in the file name. At most one leaf pattern.
- issuance: an issued leaf's PEM, ONE FILE PER ISSUANCE; needs change: write-once; checked with pki.CheckIssuance (the root issued it, and the file is exactly ONE canonical CERTIFICATE PEM block: byte-equal to its own PEM encoding, so junk before or after, a second block, headers, CRLF or a missing final newline are refused).
- revocation: a root-signed revocation statement (tag knomit-revoke/v1, root fingerprint, serial, time, reason), ONE FILE PER REVOCATION; needs change: write-once; checked with pki.VerifyRevocation (canonical bytes rebuilt from the fields).
Declaring crl, leaf, issuance or revocation without a pki: root is an error. The reader (store.FleetAt) finds the fleet's root, CRL and leaves from these declarations, never from fixed paths.
max_size — a positive integer of bytes, or <n>B, <n>KiB, <n>MiB, at most 1 GiB; anything else (16KB, 1.5MiB, 0, negative) is a bad value. A larger blob is refused with artifact-size. Never put it on a file that only grows (the CRL): a legitimate update would become a permanent refusal. Without max_size a non-CRL pki file is still read only up to 64 KiB and a CRL up to 64 MiB (a reader guard, refused as artifact-rules when exceeded); a non-pki file with no cap is unbounded.

HOW PATTERNS MATCH. Patterns are relative to artifacts/ and use the trigger glob syntax: '*' and '?' inside one segment, '**' as a whole segment for any number of segments, everything else literal, matched ASCII case-INSENSITIVELY (a rule covers every case spelling of its path). No segment may begin with '.'. An undeclared path has no rule at all.
HOW OVERLAPPING PATTERNS COMBINE. max_size: the SMALLEST any matching pattern declares (every cap applies). pki, and change together with replace_when and revoked_set: from the MOST SPECIFIC matching pattern that declares them (fewer '**' segments first, then fewer wildcard segments, then more segments). Two equally specific patterns that declare different values for the same path make that path ambiguous and the judge refuses any commit that changes it (artifact-rules) rather than guess.

NOT A FILE (artifact-not-a-file). A declared path must hold a regular file. A tree, symlink or submodule AT a declared path is refused, and so is any entry UNDER a directory that a pattern declares a FILE (a directory squatting a file's name, e.g. certs/<id>.pem/x). Under directory d, the entry p is a squat only when some pattern matches d but NOT p (fact.Ontology.ArtifactFileAt): a family pattern such as fleet/** matches both and squats nothing, while fleet/* declares fleet/issued a file and refuses adds beneath it.
DELETION. A file whose matching rules carry a change rule is never deleted (the refusal rule is that change's: artifact-write-once, -append-only or -replace). A file matched only by max_size or by patterns without a change may be deleted.
BOOTSTRAP. A first ADD of any declared file is allowed whatever its change rule. A pki file must still hold as its role when added, and its role checks read the root and CRL from the commit's OWN tree: commit root.crt and crl.pem first (same commit or earlier), then members, leaves and records.

STRICTNESS. A bad value, a malformed pattern or an inconsistent block (replace without replace_when, a pki file without its required change rule, revoked_set without pki: crl, a second root/crl/leaf pattern, a root/crl pattern with wildcards, a bad leaf pattern) is FATAL on every path, open or create: guessing a security rule is worse than a repository that refuses writes until fixed. An UNKNOWN key is a warning on open (a newer knomit may have written it; it is preserved on write-back and has no effect) and fatal for a NEW ontology (ParseNewOntology). Because a bad value is fatal and the gate must parse the ontology, a gate with verification on cannot run (push refused / verify ci exit 2) until the ontology at main is fixed.

WHERE IT IS READ AND ENFORCED. Read from the ontology at the tip of the main being advanced, the same revision and reader path as verify_signatures (receive-pack: the host's upstream tip; verify ci: --main). Enforced by the commit judge (store.judgeCommit) on EVERY commit it admits, signed or an unsigned M3 merge, for each artifacts/ path the commit changes diffed against EVERY parent (the empty tree for a root commit). It runs ONLY when verify_signatures is log (reported) or enforce (refused); with off the ontology is not even read. The built-in fleet ontology declares verify_signatures: enforce, so a NEW fleet repository judges these rules from its first push; on the master, the boot replaces an existing fleet repository's stored ontology with the built-in one (kb/invariants/fleet/baked-ontology/master-refresh/d62746d2.md). The section is generic, but only fleet-style readers consume the pki roles.
REFUSAL RULE NAMES a user sees: artifact-write-once, artifact-append-only, artifact-replace, artifact-size, artifact-pki, artifact-rules (ambiguous rules, an unreadable blob, or a blob over the read bound), artifact-not-a-file. They sit beside the signer rules signature, no-record, ambiguous, key-mismatch, duplicate-key, inactive, merge, revoked, no-cert, not-pusher.
BOOT REFRESH (as of PR #520, merge commit 1a6c03f7). The fleet ontology is not a preset and is refreshed only wholesale, on the master (see the master-refresh invariant). For the embedded PRESETS (default, code), Ontology.SubsetDivergence counts the section (artifactsNotSubset): a stored artifacts: rule the preset does not declare identically reports `attributes` and the refresh is skipped. fact.ArtifactRulesEqual and its refreshDivergence arm no longer exist, so nothing blocks a preset that would ADD an artifacts: section; none does today, because neither preset declares one.

WHAT A REPOSITORY CAN AND CANNOT EXPRESS. It can combine the closed Go primitives above per path pattern. It cannot declare a custom check, a JS rule, a regex over content, a per-writer exception, a different size unit, or a new role or condition: a new behaviour is a code change plus a NEW key. These rules are not facts: validations never see artifacts/.

CONSEQUENCES. To change a trust-file rule, commit the ontology to the KB's main; the next judged commit sees it. When adding a primitive, add a key (closed-value rule) and a refusal rule.

MISREADINGS. 'write-once means the file must exist': no, it only forbids modification and deletion after the first add. 'A file name carries order or meaning': never; issuance and revocation names are for uniqueness and readability only, order and meaning come from signed content. 'The leaf pattern's * is parsed': no, it is a lookup key compared for equality. 'More specific wins for everything': no, max_size takes the smallest of all matches. 'An unknown key is ignored harmlessly': only on open; on create it is refused. 'artifacts: rules apply when verify_signatures is off': no. 'An undeclared path is protected': no, an undeclared path has no rule. 'Any pattern matching a directory makes it a file': no, only one that does not also match the path beneath it.

UPDATE (PR #523, verified at merge commit 3ac59b57): the artifacts: patterns also define which paths a member of the FLEET repository may write outside its own folder: the record-owner rule exempts only paths under artifacts/ that a pattern matches (same ArtifactAttrs match, same ASCII case-insensitive globbing), and refuses (not-owner) a member's change to any other path, an undeclared artifacts/ path included. 'An undeclared path has no rule' therefore holds for the ARTIFACT rules only; in the fleet repository the owner rule still refuses it (kb/invariants/store/verify/record-owner/74b64ef6.md). Every admitted commit also passes the tree-shape check first, so these rules never judge a prefix of a tree (the artifact diff is a DiffTree).
