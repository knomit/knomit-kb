# Ontology guide — what can be customised, and where: per REPOSITORY (the ontology root block, root attributes, root validations and guidance, .knomit/ scripts, recipes, skills, templates), per TOPIC (children, validations, learn_dedup, triggers, context declarations, guidance), per INSTANCE (knomit.toml: ontology_root, sync intervals, trigger rate) and per CHANGE (context values, expires, trace trailers, retract-as-move, experiments and their resolutions, merge resolution) — and what cannot be customised at all

Part of the ontology guide (kb/architecture/fact/ontology/guide/). Describes merged dev at 3e2e83b0 (PR #514).

PER REPOSITORY (in .knomit/, changed by a git commit). The ontology document: id, name, description, topics, root validations (run on every fact), root guidance, the root attributes verify_signatures, consensus, conflicts, sync, and the `artifacts:` section (per-path rules for files under artifacts/: pki role, change write-once|append-only|replace, replace_when, revoked_set, max_size; enforced by the acceptance gate under verify_signatures log/enforce). Files: .knomit/triggers/<script>.js, .knomit/recipes/<name>.js, .knomit/skills/<name>/SKILL.md (served by knomit_skill and as MCP prompts, from the consensus tip), .knomit/guidance/<file>.md, .knomit/templates/<name>/ (seeds for new repos).

PER TOPIC (any topic or child node, inherited down the tree where noted). children (the declared category skeleton; deeper paths are freeform), validations (cumulative root -> leaf), attributes: learn_dedup (inherited), triggers (scoped to the node's match), context declarations (inherited), guidance (inherited, nearest wins).

PER INSTANCE (knomit.toml, not in the repository). ontology_root (default kb), [git].local_reconcile_interval and realtime_pull_interval, [triggers].script_rate_per_minute, [tls] and [oauth] listeners, external_addresses advertised in the fleet record. Grants (`knomit grants`) are per instance too.

PER CHANGE (arguments of one write). knomit_learn/update: topic + category (placement), kind/type, context values (typed by the topic's declarations), expires (a date knomit never acts on, except `on: due` triggers), motifs, distinct_from (opt out of one dedup merge), retract (an atomic move on one branch), trace (Knomit-Trace / -Cause / -Run and free keys as commit trailers), if_commit (optimistic concurrency on update), path (an artifacts/ file instead of a fact). knomit_experiment: an isolated exp/<name> branch committed or rolled back as a unit, with per-path resolutions. The operator's pushed-branch merge: resolution host|peer.

NOT CUSTOMISABLE. The fact format and the kind/type taxonomy (13 leaf types) — code, not ontology. The set of attribute keys and their values (registry). Where repository settings are read (fixed per key). Who may sign (member records in the fleet repository, never a KB's ontology). Per-call prompt instructions (refused by design: guidance is by path only). Triggers on pushed peer branches or on dot paths. Writing .knomit/ through any fact tool. Changing an existing ontology through knomit: no editor, no migration; renaming a topic orphans its facts.

CONSEQUENCES. When a behaviour needs to vary, check this list from the narrowest scope up: a per-change argument, then a topic block, then a repository file or root attribute; if none fits, it is a code change (and, for a new switch, a new registry key).

MISREADING. 'A topic can turn signature verification on': no, verify_signatures is repository-scoped; on a topic it is a wrong-scope warning and ignored.

UPDATE (PR #514): WHAT artifacts: CAN AND CANNOT DO. A repository can choose, per path pattern, among the fixed Go primitives (see kb/architecture/fact/ontology/guide/artifact-rules/e544cf71.md). It cannot add a new check, a content regex, a JS rule, a per-writer exception, a new role or condition, or a different size unit; that is a code change plus a new key. It cannot loosen a rule for one path by a more general pattern: the most specific wins for pki/change, and the SMALLEST max_size of all matches applies.
