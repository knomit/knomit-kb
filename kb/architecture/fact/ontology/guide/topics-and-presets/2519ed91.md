# Ontology guide — topics, presets and the ontology's lifecycle: an ontology is chosen once at create time (preset `default`/`code`/`fleet`, custom YAML, or a repo template), lives at .knomit/ontology.yaml, is snapshotted per repo at mount from its read branch, and changes afterwards only by git commits or the boot refresh that rewrites a preset-derived file when it is a strict subset of the newer embedded preset

Part of the ontology guide (kb/architecture/fact/ontology/guide/). Describes merged dev at 3e2e83b0 (PR #514).

SHAPE. Document root: id, name, description, topics (required, at least one), validations, attributes (repository-level), artifacts (rules for files under artifacts/, PR #514), guidance. Topic/child node: description, children, validations, attributes (topic-level), triggers, context, guidance. Topic and child keys are lowercase kebab-case. A bare key (`alpha:` with nothing under it) is a nil node that is still declared. Unknown fields are reported (warnings) and preserved by Serialize so a newer knomit's keys survive.

PRESETS (embedded in internal/fact). Three: name "default" -> id general (ontology_default.yaml), "code" -> id source-code (ontology_code.yaml: invariants, architecture, conventions, decisions, gotchas, incidents, meta, principles), "fleet" -> id fleet (ontology_fleet.yaml: one `members` topic, the root attribute verify_signatures: enforce, and an artifacts: section for artifacts/fleet/). The create wizard lists default and code (GET /api/v1/ontologies/presets); fleet is reached by preset name or a fleet-id template. EmbeddedPresetByID maps a stored id back to its preset.

CREATE. resolveOntology: mode custom (and initialize with YAML) parses with ParseNewOntology (strict: warnings that the open path tolerates are refused); a preset name otherwise; the default preset when nothing is given. Templates: a folder .knomit/templates/<name>/ (README.md + .knomit/** only) at an active mounted repo's consensus tip; its ontology must parse as a NEW ontology, may carry a preset id only if it IS that preset, and a fleet-id template only initializes a remote and only when this instance has no fleet. Clone and subscribe take the remote's ontology.

LOAD. At the lifecycle Identify stage, RepoInstance.loadOntology reads the READ branch (agent branch when hosted, upstream when subscribed) and NEVER substitutes a default: missing, empty or unparsable means the repo opens readable but unwritable; a symlink refuses the repo. That snapshot drives every write-time check (ValidatePath, validations, context, learn_dedup) until the repo is re-identified; an ontology commit arriving by sync is not seen until then.

REFRESH. If the stored id is a preset's and the repo is not a subscription: when refreshDivergence finds nothing (SubsetDivergence = "" AND root attributes identical AND artifact rules identical) and the bytes differ, the preset is written over the file (a signed commit on the read branch). Divergence reasons, by priority: shape (a topic, child or validation name the preset lacks), attributes (a topic attribute the preset does not carry identically, ANY root-attribute difference, or ANY artifacts: difference in either direction), triggers, context, guidance. A diverged repo keeps its file and forgoes upgrades, with a warning naming the reason. Validations match by NAME only, so a preset can fix a rule's body.

CONSEQUENCES. A preset repo that sets learn_dedup, any root attribute, a trigger, a context key or guidance stops receiving preset upgrades. Removing or renaming a topic orphans facts: there is no editor and no migration. A new topic attribute added to an embedded preset reaches existing subset repos at their next boot; a new ROOT attribute or artifact rule in a preset never does (and blocks refresh for every repo that lacks it), so the fleet preset's verify_signatures: enforce and artifacts: section reach NEW fleet repositories only.

MISREADINGS. 'Immutable after create' means no knomit editor and no tool write; the file is still a git file that a human commit can change, and root attributes are routinely changed that way. 'The repo validates against the consensus tip': no, against its mount-time snapshot of the read branch.

UPDATE (PR #514): an artifacts: difference between stored and preset (a pattern missing or with different keys, in either direction) is reported as divergence reason `attributes` (SubsetDivergence via artifactsNotSubset; refreshDivergence via ArtifactRulesEqual); there is no separate reason name. A stored ontology that declares an artifact rule the preset lacks, or lacks one the preset adds, is never refreshed. See kb/architecture/fact/ontology/guide/artifact-rules/e544cf71.md.
