# Ontology guide — adding a new ontology attribute: declare ONE registry entry (accepts, valid, absent, scope) with a CLOSED value set, give it a named reader (Ontology.Attr helper for a topic key; a ReadX over only the root block, with a decided bad-value reading, for a root key), decide which branch tip it is read at, and accept that older binaries warn on the unknown key while a NEW value for an existing key would make them refuse writes

Part of the ontology guide (kb/architecture/fact/ontology/guide/). Steps as the code on dev c9c599de requires them; follow the existing keys (learn_dedup for topic scope; verify_signatures, consensus, conflicts, sync for root scope) as templates.

1. DECLARE. Add a constant AttrX and one entry in attributeRegistry (internal/fact/ontology.go): accepts (human text), valid (accept exact strings or a mapping with known inner keys; reject YAML bools), absent (the value that behaves as leaving it out, or nil when absence depends on something else, as for conflicts and sync), scope (scopeTopic or scopeRoot). That is the ONLY declaration point: diagnostics, wrong-scope warnings, IsSubsetOf comparison and RootAttributesEqual all read it.

2. CLOSE THE VALUE SET. A bad value for a known TOPIC key is fatal on open; a new value added later would make every older binary refuse writes to the repo. So new behaviour ships as a NEW key, never a new value of an existing one. (Root keys are softer: a bad value is a warning on open, but each reader must still decide what it means.)

3. READ IT. Topic key: through Ontology.Attr / a named helper like LearnDedupOff, which returns the nearest declared value from the cache built at parse; never read OntologyNode.Attributes directly. Root key: a ReadX(data []byte) in internal/fact that unmarshals ONLY the root `attributes:` node, validates through the registry, and returns {value, Valid}; decide and document what an invalid value means — UNKNOWN and refuse (verify_signatures: a safety gate must not fail open) or a safe default with one warning per ontology blob (consensus, conflicts, sync). Add TestReadX and a registry test like the existing *_settings_test.go files.

4. CHOOSE WHERE IT IS READ. Repository policy is read from the ontology at a branch tip at each use (consensus branch for consensus/conflicts/sync; the main being advanced for verify_signatures), not from the repo's mount-time snapshot, which only write-time validation uses. Two instances should read one value, which is why the consensus branch is the usual choice.

5. PRESET INTERPLAY. Attributes are compared by value in SubsetDivergence (the `absent` value compares as absent). A topic attribute added to an embedded preset reaches existing subset repos at their next boot refresh; a ROOT attribute added to an embedded preset is never written by the refresh and makes refreshDivergence report attributes for every stored ontology that lacks it, so those repos stop receiving preset upgrades.

6. DOCUMENT. Update the field docs served to the ontology editor (fact/schema.go: the `attributes` entries of Ontology and OntologyNode), the AttrX doc comment, and spec/mbekg.md section 3.

CONSEQUENCES. An older knomit opening a repo that uses the new key warns ('unknown attribute ... ignored'), keeps the key on write-back, and behaves as if it were absent: make the absent behaviour safe. Serialize writes attribute blocks with sorted keys, so new keys round-trip.

MISREADING. 'Extend learn_dedup with a third value': that is exactly what the closed-set rule forbids.
