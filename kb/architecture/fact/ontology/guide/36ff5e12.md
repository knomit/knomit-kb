# Ontology guide (start here): a repository's ontology (.knomit/ontology.yaml) is its schema AND its program — topics and children place facts; validations, topic attributes, context declarations, triggers and guidance shape writes per topic; root attributes set repository policy (signature gate, consensus merging, conflict settlement, sync cadence) — and each piece is read from a DIFFERENT place at a different time, which is the first thing to know before changing one

Entry point of the ontology guide. Describes merged dev at c9c599de (2026-10-14). Read the components in this order; each links the detailed facts.

READING ORDER.
1. The three roots — kb/architecture/fact/ontology/guide/roots: kb/ (facts), .knomit/ (the system, git-only writes), artifacts/ (agents' untyped files), and the private dot-path rule.
2. Topics, presets and lifecycle — kb/architecture/fact/ontology/guide/topics-and-presets: the document shape, the three embedded presets (default/general, code/source-code, fleet/fleet), create modes and templates, the mount-time snapshot, the boot preset refresh and its divergence reasons.
3. Topic attributes — kb/architecture/fact/ontology/guide/topic-attributes: the registry, inheritance, learn_dedup, strictness.
4. Root attributes — kb/architecture/fact/ontology/guide/root-attributes: verify_signatures, consensus, conflicts, sync — values, readers, bad-value readings.
5. JS validations — kb/architecture/fact/ontology/guide/validations: what a rule sees and can do, and the write paths that run (and never run) it.
6. Triggers, context and guidance — kb/architecture/fact/ontology/guide/node-blocks.
7. Adding an attribute — kb/architecture/fact/ontology/guide/adding-an-attribute.
8. What can be customised per repository, topic, instance and change — kb/architecture/fact/ontology/guide/customisation.
For how root attributes drive the fleet, see the fleet guide, kb/architecture/fleet/guide/.

WHERE EACH PIECE IS READ (the map most mistakes come from):
- topics/children, validations, topic attributes (learn_dedup), context declarations, ValidatePath: the repo's ONE ontology snapshot, loaded at the lifecycle Identify stage from the READ branch (agent branch when hosted, upstream when subscribed); unchanged until the repo is re-identified.
- trigger declarations, `if` programs, trigger scripts: the observed (agent) branch's head, re-read by blob at each dispatcher run.
- recipes, skills, guidance files: the tip of the repo's CONSENSUS branch.
- consensus, conflicts, sync: the ontology at the CONSENSUS branch's tip, read by their components at each use.
- verify_signatures: the tip of the main being advanced (the host's upstream in receive-pack; --main in verify ci).
- the ontology file itself: never written by a fact tool; changed by a git commit, or by the boot refresh for a preset-derived repo that is a strict subset of its newer preset.

STRICTNESS IN ONE LINE. Opening an existing repo is lenient (unknown keys and most problems are warnings so the repo keeps opening; only a malformed document, a bad topic-attribute value or an uncompilable rule refuses writes); creating one is strict (ParseNewOntology refuses the warnings too).

CONSEQUENCES. Before changing behaviour, find which reader you need to reach: an edit to validations or context takes effect only after a remount, a root-attribute edit only once it is on the consensus/main tip, a trigger edit at the next dispatcher run on the agent branch. Any customisation of a preset-derived repo stops its preset auto-upgrades.

MISREADINGS. 'The ontology is one live config read everywhere': no, see the map above. 'The ontology is immutable': no editor or tool can change it, but a git commit can, and repository policy is changed exactly that way. 'Validations are invariants of the corpus': they guard only the MCP write path.

UPDATE (PR #514): the document root may carry an `artifacts:` section (path patterns relative to artifacts/ -> keys pki, change, replace_when, revoked_set, max_size). READING ORDER item 9: Artifact rules — kb/architecture/fact/ontology/guide/artifact-rules/e544cf71.md: every key and value, how patterns match and combine, the artifact-not-a-file rule, strictness, where enforced, refusal rule names. WHERE READ: artifact rules are read, like verify_signatures, from the ontology at the tip of the main being advanced and enforced by the commit judge only under verify_signatures log/enforce; they are NOT part of the mount-time snapshot's behaviour and no write path of a fact tool consults them. STRICTNESS: a bad value in artifacts: is fatal on open AND create (a security rule is never guessed); an unknown key is a warning on open and fatal on create. The boot refresh treats the section like a root attribute (never added, changed or dropped; a difference stops preset upgrades). CONSEQUENCE: topic attributes cannot reach artifacts/, so file rules for artifacts/ live ONLY here.
