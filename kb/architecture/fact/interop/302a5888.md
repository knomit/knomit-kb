# Current knomit kb/ trees are conformant OKF v0.1 bundles — SerializeFact writes `type` unconditionally

Google's Open Knowledge Format (OKF v0.1, GoogleCloudPlatform/knowledge-catalog, released ~July 2026) requires exactly three things for bundle conformance: (1) every non-reserved `.md` file has parseable YAML frontmatter, (2) that frontmatter has a non-empty `type` field, (3) reserved `index.md`/`log.md` files follow the spec's shape *when present*. A current knomit `kb/` tree satisfies all three: every fact is frontmatter+body markdown, `SerializeFact` writes `type` unconditionally (unlike `kind`/`evidence_weight`/`origin`, which are elided at defaults), and knomit creates no `index.md`/`log.md`. Consequence: knomit can claim "every knomit repo is an OKF bundle" with zero format changes; an exporter only needs to ADD optional niceties (generated per-directory `index.md`, `log.md` from git history, frontmatter `refs` materialized as body links so OKF graph viewers see edges). WHAT THIS DOES NOT MEAN: legacy kbs written before the `type` field (e.g. the personal ~/.knomit kb, whose fact files have no `type` key) are NOT conformant — the guarantee holds only for facts written by the current serializer.
