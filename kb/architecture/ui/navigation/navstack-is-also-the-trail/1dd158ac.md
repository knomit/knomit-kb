# state.navStack is BOTH the back stack and the time-travel trail's source — selectTrail walks it and jumpTrail pops it, so NAV_BACK cannot become non-destructive without changing breadcrumbs

There is ONE navigation stack, and the time-travel breadcrumb is a derived VIEW of it — not a second structure. Anyone reading TrailBreadcrumb and the back button as independent subsystems will design something that breaks one of them.

THE COUPLING, concretely:
- `pushNav(s)` appends the state being LEFT (not the state being entered) on NAVIGATE, GO_UP, ADD_FILTER, REMOVE_FILTER, CLEAR_FILTERS and APPLY_NAV. So navStack is "places you can go back to"; the current view is never in it.
- `NAV_BACK` restores `navStack[last]` and TRUNCATES (`slice(0, -1)`). It does not call pushNav, so there is no re-push trap.
- `selectTrail(s)` walks `s.navStack` backwards collecting fact-bearing entries until it hits a live one. The breadcrumb IS the stack, filtered AND COLLAPSED (see below).
- `jumpTrail(i)` in App implements a crumb jump as N × NAV_BACK — pops, not an index move. N is the crumb's `pops` count, not its index distance.

CRUMBS ARE NOT ONE-TO-ONE WITH STACK ENTRIES (since PR #506 / #486): entering a fact's timeline pushes the fact's live entry (kb/invariants/ui/navigation/set-as-of-pushes-on-entry), so navStack can hold two adjacent entries for the same fact. `selectTrail` collapses an adjacent same-fact run into ONE crumb (a run containing the current view keeps the current view; any other run keeps its OLDEST entry, which lands live; see kb/decisions/ui/temporal/trail-crumb-landing) and each `TrailCrumb` carries `pops`, the NAV_BACK count that lands on it (current = 0). `jumpTrail` (App.tsx) and `planTrailHop` (state.ts) use `pops`; they fall back to index distance only for hand-built crumbs without `pops` (tests). The misreading: 'crumb i needs depth - i pops' is false once a fact has been opened in its timeline.

THE CONSEQUENCE THAT CONSTRAINS FUTURE WORK: a browser-style forward button requires a non-destructive cursor. If NAV_BACK stops truncating, selectTrail walks entries the user has already gone back past and the breadcrumb grows crumbs for places they left. If it keeps truncating, forward has nothing to return to. You cannot add forward without deciding what happens to the trail, and 36 assertions in state.test.ts sit on the current semantics.

THE CHOICE MADE: back only. The Library header renders a single chevron driven by `canGoBack(s) = navStack.length > 0`; there is no navIndex, no GO_FORWARD, no RESTORE_NAV. A design handoff proposed all three on the premise that the trail and the nav stack were already separate — they never were.

WHAT THIS DOES NOT MEAN:
- Not "the trail and the back button are the same feature". They read the same array through different rules: the trail only shows fact-bearing entries and only in history mode; back restores any entry in any mode.
- Not "navStack is append-only history". It is a stack of DEPARTURE states, so navStack[last] is where you were before the current view, not the current view.
- Not a claim that adding forward is impossible — only that it is a change to breadcrumb semantics, not an additive feature, and must be costed as one.
