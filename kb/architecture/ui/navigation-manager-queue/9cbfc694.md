# useNavigationManager serializes nav requests; APPLY_NAV applies full nav state atomically

useNavigationManager hook serialises all navigation requests through a queue, resolves async data BEFORE dispatching, and applies the full nav position atomically in ONE APPLY_NAV action. Components are dumb callers: they say 'navigate here' via navigate(NavRequest); the manager figures out what to fetch. Example: a history request with factPath=null is partial — the manager calls api.commitDetail, finds files[0].path, then dispatches APPLY_NAV with the resolved factPath. Fully-specified requests dispatch synchronously, no API call. STALE-CLOSURE PROTECTION: state and dispatch are stored in refs (stateRef/dispatchRef) so async callbacks in resolve() always read CURRENT values — prevents a repo change while a request is in-flight from dispatching APPLY_NAV against the wrong repo. PROBLEM SOLVED: prior tree→history transition caused a flash summary→fact→summary because SET_VIEW cleared state and two separate effect chains raced to re-establish it. Three new explicit state fields replace ambiguous leftSelection/rightSelection: historyCommit, factPath, factCommit. SET_VIEW for tree/chrono clears historyCommit + factCommit but PRESERVES factPath so right panel keeps showing the same fact in the new mode.
