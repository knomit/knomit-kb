# pageEnvelopeReserveBytes is a MEASURED transport budget, not a tuning knob — every prompt edit spends it, and a test re-measures it because the reserve had silently drifted to 103 bytes of headroom

The delivered-page budget is three constants, and the middle one is the trap: `maxDeliveredItemBytes` (32 KiB, the client's MCP tool-result cap) minus `pageEnvelopeReserveBytes` gives `maxPageFactBytes`. The reserve covers everything on a page that is NOT facts — the prompt, the response schema, the paging fields, the ReviewResult envelope. So the whole page-budget guarantee rests on the reserve actually being big enough, and NOTHING in the pager controls what fills it.

THE CONSEQUENCE A PROMPT AUTHOR MUST ACT ON: editing a prompt file spends a transport budget. This is not obvious from either side — the prompt file has no size limit in view, and the constant lives in `types.go` next to code that never mentions prompts.

MEASURED DRIFT, which is why this is written down. The constant's own comment recorded a worst case of 5,893 bytes against an 8 KiB reserve. By PR #188 the real figure was 8,089 — leaving 103 bytes of headroom, one prompt edit from over-promising — and the comment had been stale for long enough that nobody would have caught it by reading. The reserve moved to 12 KiB and the measured worst case is now recorded and dated in the comment. Re-measure and update that figure on any change that touches prompt text or the response schema; treat the recorded number as evidence, not decoration.

COST OF RAISING IT: `maxPageFactBytes` is the subtraction, so +4 KiB of reserve is −4 KiB of facts per page (24 KiB → 20 KiB), and items page more often. Correctness is unaffected because `completion_token` paging already covers multi-page items — this is a throughput cost, not a behaviour change. `maxDeliveredItemBytes` is the MCP output cap and a SEPARATE concern; do not raise it to buy prompt room.

ENFORCED BY `TestDeliveredPage_EnvelopeFitsItsReserve`, which renders each paging step type with a full-size methodology section and fails when the envelope outgrows the reserve. It measures the artifact via `deliveredFactsLen` rather than predicting it, because `json.MarshalIndent` expands per JSON TOKEN, so the expansion factor is a function of how MANY facts a page holds, not how large each one is.

WATCH THE WORST CASE WHEN THE PROMPT GAINS A BRANCH. Once distill grew a remainder variant, that branch became the larger ask, and a caller passing the cluster branch would have left the true worst case unmeasured while the test stayed green — the exact stale-reserve failure the test exists to prevent. It now runs a subtest per branch. The same reasoning applies to `TestDistillWorkItem_EveryPageFitsDeliveredCap`, whose page 1 carries the prompt.
