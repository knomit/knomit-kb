# pageEnvelopeReserveBytes is a MEASURED transport budget, not a tuning knob — every prompt edit spends it, and a test re-measures it because the reserve had silently drifted to 103 bytes of headroom

The delivered-page budget is three constants, and the middle one is the trap: `maxDeliveredItemBytes` (32 KiB, the client's MCP tool-result cap) minus `pageEnvelopeReserveBytes` gives `maxPageFactBytes`. The reserve covers everything on a page that is NOT facts: the prompt, the response schema, the paging fields, and the ReviewResult envelope. So the whole page-budget guarantee rests on the reserve actually being big enough, and NOTHING in the pager controls what fills it.

THE CONSEQUENCE A PROMPT AUTHOR MUST ACT ON: editing a prompt file spends a transport budget. This is not obvious from either side: the prompt file has no size limit in view, and the constant lives in `types.go` next to code that never mentions prompts. The same holds for any field added to the result envelope, including fields the MCP handler sets after the engine returns.

MEASURED DRIFT, which is why this is written down. The constant's own comment recorded a worst case of 5,893 bytes against an 8 KiB reserve. By PR #188 the real figure was 8,089, leaving 103 bytes of headroom, and the comment had been stale long enough that nobody would have caught it by reading. The reserve moved to 12 KiB.

The review-session fix (PR #291) then found the test measured a narrower envelope than real page-1 START results. As measured now, page 1 carries the following, and the test sets every one of them at realistic lengths:
- the repo identity: repo, repo_id, write_branch;
- the abandoned_session / abandoned_session_created_by pair (`resumed` is left out: it and that pair never share a result, and the pair is the larger);
- the `next` line in its longest form, the unscoped endpoint's;
- on a multi-page item, also page, pages, more_available, the item's own paging line, and the "read on" form of `next`.
Measured with all of those, the worst case is page 1 of a MULTI-PAGE distill remainder at 12,432 bytes (single-page: 12,302), over 12 KiB. The reserve is now 12.5 KiB, leaving 368 bytes. Re-measure and update the figure in the constant's comment on any change that touches prompt text, the response schema, or the envelope.

COST OF RAISING IT: `maxPageFactBytes` is the subtraction, so every byte of reserve is a byte less of facts per page (12.5 KiB of reserve leaves 19.5 KiB for facts), and items page more often. Correctness is unaffected because `completion_token` paging already covers multi-page items; this is a throughput cost, not a behaviour change. `maxDeliveredItemBytes` is the MCP output cap and a SEPARATE concern; do not raise it to buy prompt room.

ENFORCED BY `TestDeliveredPage_EnvelopeFitsItsReserve`. It renders each paging step type, single-page and multi-page, with a full-size methodology section plus the start-result and `next` fields, and fails when the envelope outgrows the reserve. It measures the artifact via `deliveredFactsLen` rather than predicting it, because `json.MarshalIndent` expands per JSON TOKEN: the expansion factor is a function of how MANY facts a page holds, not how large each one is.

WATCH THE WORST CASE WHEN THE PROMPT OR ENVELOPE GAINS A BRANCH. Once distill grew a remainder variant, that branch became the larger ask; now the multi-page form of it is. A test that skips the worst branch stays green while the reserve goes stale, which is the exact failure it exists to prevent. The same reasoning applies to `TestDistillWorkItem_EveryPageFitsDeliveredCap`, whose page 1 carries the prompt.
