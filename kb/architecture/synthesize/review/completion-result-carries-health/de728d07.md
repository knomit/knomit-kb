# Session-end facts can ONLY be reported on the completion result, because sess.Health is in-memory and rides the FIRST result — and the only work-item listing method returns the unanswered half

BEFORE PR #190 the completion result carried `Summary` and `Progress` and NO health lines at all. Every descriptor was recorded during Plan and rode the FIRST result of a session. That is a real constraint on what a health line can ever report, and two plausible-sounding designs are foreclosed by it. Both were written into a plan and both are false of the code; this fact exists so the next person does not re-derive them.

FALSE PREMISE 1 — "keep a running tally on the session in memory". `store.PipelineSession.Health` is documented IN MEMORY ONLY, "written and read inside the same StartSession call", deliberately not a column. `recordStats` states the general rule outright: the engine is rebuilt per call, so nothing kept in memory survives to completion — which is why running totals live on the session ROW. Anything that only becomes knowable as later turns answer work items therefore has NO turn on which an in-memory tally is both populated and still alive.

FALSE PREMISE 2 — "recompute from the store; it already returns items by session". It returns the wrong half. `PendingPipelineWorkItems` selects `response IS NULL` BY DEFINITION, so it is exactly the set with no answers in it. Before #190 there was no read path back out of an answer at all, which is easy to miss because a listing method by session visibly exists.

THE SHAPE THAT WORKS: the response column was already the durable record and simply had no reader, so add the narrowest one — `AnsweredDistillResponses(ctx, sessionID)`, response strings only, one step type, one session — and compute at `completeSession`. Prefer a narrow reader over handing back whole work items: the claim protocol has opinions about those, and a general method invites reads that bypass it.

CONSEQUENCE TO EXPECT AND NOT MISTAKE FOR A BUG: the completion result now carries a Health line where it carried none. That is wire-visible on the turn an agent reads when a session ends. It is the point rather than a side effect — completion is the ONLY turn on which a session-end tally can exist — but treat adding one as a deliberate interface change, not an implementation detail. Append, never assign (`TestHealthRecorders_NeverDestroyExistingLines`).

ONE PARSING DEPENDENCY WORTH KNOWING: for distill, `Decode` returns the agent's text unchanged as `normalized`, so the response column holds RAW text and `parseDistillResponse` applies to it directly. A future normalisation of distill responses would silently break any tally reading that column.

TESTING LIMIT, stated rather than papered over: the engine reaches its indices through a concrete `*store.Service`, so there is no seam to fault the real store mid-session — `pipeline.go` records the same limitation for the answer-write path and marks that branch UNCOVERED. A store-failure path is therefore testable only by calling the helper with an injected `Deps`, not end-to-end.
