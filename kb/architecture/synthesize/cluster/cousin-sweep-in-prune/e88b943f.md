# Cousins reach the prune judge via a SECOND unfenced neighbour search over prune clusters only — and it sweeps outward from facts ALREADY in a prune cluster, so a pair with neither half in one is not reached

`ScopedCluster` expands each seed's neighbourhood with `Path: categoryDir(seed.File)`, applied as a raw path PREFIX (`AND f.path LIKE cat||'%'`). Siblings meet; descendants of a shallow-filed seed meet (which is why prune clusters LOOK cross-category from outside — a shallow-filed fact acts as a hub); COUSINS, in different directories under a shared ancestor, do not.

#149 (PR #164) fixes this by AUGMENTING rather than replacing. `joinCousinsForPrune` runs dedupCluster's own search — `QueryByPath`, the model's calibrated dedup floor, bounded KNN — with two differences: no `Path` filter, and the membership rule INVERTED. dedupCluster keeps only hits already inside the cluster; this keeps only hits outside it. A cousin in no prune cluster is ATTACHED; a cousin in a different prune cluster JOINS the two.

THREE CONSTRAINTS ON THE FIX, all load-bearing, all about WHERE it runs rather than what it does:

1. **It sweeps outward from facts ALREADY IN A PRUNE CLUSTER.** That is the origin constraint, and it is the fix's boundary: a cousin pair with NEITHER half in a prune cluster has no origin to search from and is NOT reached. This covers the measured population — in all six confirmed pairs on the live corpus one half was served in a prune item and the other sat in the leftover bucket — but it is a real limit, pinned by `TestCousins_BothHalvesLeftoverIsNotReached`. Widening the origin to every seed would also CREATE prune items where there were none, which is a scope change, not a bug fix.

2. **It runs AFTER `dedupCluster`, never before.** Before it, a newly-met cousin above the floor would be merged MECHANICALLY with no judge — strictly larger than what was ruled. The ruling is that cousins should MEET so the prune JUDGE sees them.

3. **It operates on a SEPARATE prune-cluster slice and never mutates `clusters`.** That slice has five consumers in `reviewStrategy.Plan`: dedupCluster, the prune items, the shortlist's co-membership, `distillGroups`, and `clusterResultFromGroups` (both bridge axes and discover). The ruling scopes the fix to prune, so the other four must see exactly what they saw before.

COUPLED CONSEQUENCE: the restatement shortlist's co-membership input is now `clusters` PLUS the cousin-joined prune clusters. The exclusion means "prune already sees this pair", so it must be read off the clusters prune is ACTUALLY given — otherwise the shortlist spends a judge slot on a pair the cousin sweep just put in front of the same judge.

WHAT THIS DOES NOT MEAN. It does not remove the category fence, and it does not change what distill, either bridge axis, or discover cluster — those still see the fenced partition. It also does not mean the fence is the ONLY thing separating two cousins: `SubgraphEdges` (Step 2) is unfenced, so when both cousins are seeds an A↔B SIMILAR_TO edge can exist and Louvain can co-cluster them in principle; what the fence guarantees is narrower — a NON-SEED cousin can never enter the subgraph at all, at any cosine. The sweep is indifferent to which mechanism missed the pair, which is why it is stated as "reach the cousin" rather than "defeat the fence".

`maxCousinSearches` (64) is a RESOURCE budget bounding the added work, not a claim about how many cousins a corpus has; when it truncates the sweep the health line names how many prune facts went unswept, so "no cousins found" cannot be read as "cousins do not exist" for facts nobody looked at.
