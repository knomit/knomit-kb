# Pipeline work is two channels — edge-triggered seeding from the watermark diff, and a standing-pairs restatement shortlist — and the standing one needs its OWN trigger, because the empty-seed early return short-circuits before Plan

Edge-triggered channel: dirtyFacts seeds review from the watermark's commit diff — only facts changed since the last run. Standing-state channel: the cross-cluster restatement shortlist (motif phase 0, PR #99) reads standing `restatement_pairs` each session — corpus-wide detection, no watermark, no scope.

Why the second channel exists: two unchanged facts that restate the same claim are STRUCTURALLY invisible to edge-triggered review — once the watermark passes them, neither is ever dirty again unless edited, so per-cluster review can never re-surface the pair. The standing-state channel is the repair loop for exactly that debt, budget-bounded, not a rescan.

THE TRAP, and it recurs. `planRestatementShortlist` is called inside `reviewStrategy.Plan`, and `pipeline.go`'s empty-seed early return completes the session BEFORE reaching Plan. So on a session with an empty dirty set the shortlist was NOT planned: a quiet, caught-up corpus did not drain its standing backlog, and the sweep advanced only while the corpus kept changing — the exact opposite of the population it serves. The backfill rip-out (dev 97f54077, PR #161) removed the level-triggered trio that used to guard this and left a warning at that early return naming the trap in advance: "a pass whose trigger is corpus state cannot be planned from an edge-triggered seed scan, and this early return is where it would be silently starved again."

RESOLVED for the structural sweep (#155, PR #164) by giving the standing channel its own trigger: a `standingWorkStrategy` hook the empty-seed branch calls before completing. Four properties of that hook are load-bearing, and each answers a way the previous machinery went wrong:
- ONE method, not a trio. The removed `HasLevelTriggeredWork` + `planLevelTriggered` pair asked "is there work?" and then separately planned it — two statements that can drift apart. The hook plans, then reports what it planned, so the health line and the queue cannot disagree.
- It reads the QUEUE, not the selection count, to decide whether anything was planned. selected != served is the source of two separate defects in this area (knomit#117a, #130).
- It plans the STANDING channel only — not the full `Plan`. The rest of Plan is edge-triggered and correctly empty on an empty seed pool; running it anyway widens what a quiet session can break for nothing.
- A SCOPED session never plans standing work (knomit#128 review, MEDIUM-2, reinstated). The standing pools are corpus-wide by construction, so consulting them on a scoped run turns a scope that matched nothing into a whole-corpus session nobody asked for.

CONSEQUENCE a reader must act on: any corpus-state-triggered work must be planned from corpus state, not from inside the edge-triggered Plan — or it silently starves on exactly the corpora that are caught up. The hook above is the place to add the next one; do not re-route a standing pass through Plan.

WHAT THIS DOES NOT MEAN: it does not mean the watermark gates DETECTION (pair detection remains corpus-wide when it runs), and it does not mean shortlist pairs are unrelated facts — pair members are related TO EACH OTHER (path identity, shared rare token, title cosine); they are merely unrelated to the current session's changes. Growth of `restatement_pairs` is still detection INVENTORY, not an offer queue: the offer rate is capped by the budget and the structural allowance.
