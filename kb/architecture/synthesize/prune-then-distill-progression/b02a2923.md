# Distill is PROMOTED by the prune verdict, not planned beside it — an acted-on cluster stops, a strict all-KEEP promotes in the SAME session, and the enqueue-after-answer machinery this needs already shipped with RAPTOR

Distill items used to be planned ALONGSIDE prune at session start, so every cluster was reasoned over twice in one session — once to decide whether its facts overlap, then again to synthesize upward from them as though they did not.

The sharp end is not the wasted slot. When a prune verdict MERGED two facts, the distill item still held the PRE-MERGE grouping, so synthesis saw two facts saying the same thing and read them as two independent sources. That is fabricated corroboration manufactured out of one claim recorded twice (knomit#135).

THE FIX IS AN ORDERING, AND THE GATE IS A CLASSIFIER YOU ALREADY PAID FOR. Every cluster goes to prune first; its distill item exists only if the verdict earns it:
- acted on (merge / retract / update) → the facts overlapped. The cluster STOPS this session. The action dirties the changed facts, so they re-seed through the watermark and are re-clustered NEXT session, on settled material.
- strict all-KEEP → the judge certified them distinct, which is synthesis's legitimate input. Promoted IN THE SAME SESSION.

SAME-SESSION IS LOAD-BEARING, and it is why this is not "plan distill next session for KEEPed clusters": an all-KEEP changes nothing, so nothing is dirty, so the watermark never re-seeds those facts and the promotion is a promise the pipeline cannot keep.

NO NEW MACHINERY WAS NEEDED, and that was the surprise. Enqueue-after-answer already ships: Strategy.Apply runs after the claim CAS is won, NextPipelineWorkItem filters on NEITHER step type NOR phase, handlePhase advances only once the queue returns nil, and enqueueRaptorFollowups has enqueued same-session follow-ups from the distill arm since RAPTOR landed. So there is no dependency column, no schema change, no stored state. Ordering is free too: prune items carry priority = cluster size (positive), distill items 0.0, queue is `priority DESC`, so a promoted item lands behind every prune item still queued.

STRICT ALL-KEEP HAS FOUR CONDITIONS, and the fourth is the one that surprises: no merges; at least one decision; every decision `keep`; AND the decisions COVER every fact in the item. `validatePrunePaths` accepts a PARTIAL decision list — it checks that decisions name known paths, never that known paths have decisions — so "all the decisions were keep" is satisfied by a judge that classified one fact out of five. Empty and partial are both NON-ANSWERS, and promoting on either would plan synthesis on silence.

WHAT THIS DOES NOT MEAN. (1) The REMAINDER is not gated. distillGroups' remainder is the seeds that landed in no multi-seed cluster; they never become a prune item, so they have no verdict to be classified by, and gating them would gate them on nothing and silently drop them. (2) Shortlist (`restate-N`) items do not promote — their all-KEEP means "these two restatements are distinct", not "this group is worth synthesizing over". (3) Promoted payloads are WHOLE-CLUSTER, not seeds-only: the seed set is a plan-time value gone by Apply time and there is nowhere to persist it, so promoted items carry neighbours the seed scan never returned and any cross-category cousin attached by knomit#149. That also widens the population slightly to clusters that were prune items but never distill groups. Both consequences are stated in the health line rather than left to be discovered, and neither reintroduces the redundancy this fix removes — that redundancy was distill firing on prune-ACTED, overlapping clusters, which promotion-gating blocks outright.
