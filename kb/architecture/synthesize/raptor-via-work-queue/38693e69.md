# RAPTOR multi-depth distill runs through the SAME work item queue; priority orders depth

RAPTOR (multi-depth distill) doesn't have its own pipeline — it runs through the SAME pipeline_work_items queue as everything else. When a distill work item completes: (1) apply distill decisions (write new synthesized facts to git); (2) if response produced new facts AND depth < maxRaptorDepth (3): `enqueueRaptorFollowups` builds factForLLM rows from the facts just written, runs ScopedCluster over them, and enqueues new distill items at depth+1 (chunked by maxItemBytes, ClusterKey `raptor-d<depth>-c<n>-<chunk>`) — it does NOT embed or upsert the new facts into the index first (an earlier version of this fact said it did; see the 2026-10-12 note); (3) return next work item, or complete session if queue empty. PRIORITY ORDERING: prune items first (priority = cluster size, highest first). Distill items use Priority = -nextDepth directly (depth 0 = 0, depth 1 = -1, depth 2 = -2) so SQLite ORDER BY priority DESC drains shallow distill before deeper RAPTOR layers — NOT the fixed -1/-2/-3 tiers an earlier version of this fact described. The depth column on pipeline_work_items is needed by ContinueSession to decide whether to enqueue deeper RAPTOR items. ScopedCluster (after removing the allFacts param) uses idx.Search to find neighbors and cluster.

Updated 2026-10-12 (drift sweep against HEAD 2104fd6d): step (2) previously claimed the new facts were upserted to the index with embeddings (embedder.Embed + idx.Upsert) before re-clustering. At HEAD `enqueueRaptorFollowups` (internal/synthesize/review_strategy.go:1042-1103) contains no Embed or Upsert call: it clusters the in-memory written facts with ScopedCluster(ctx, newFacts, d.Search, ...) and inserts the deeper distill items, logging and swallowing every failure (the distill decisions are already committed, so a lost follow-up costs depth, not correctness). maxRaptorDepth is still 3 (line 1035) and the guard is `item.Depth >= maxRaptorDepth` (line 1049). Priority is still `-nextDepth` (line 1091), so shallow distill still drains before deeper layers. CONSEQUENCE: do not rely on the new facts being searchable through the embedding index at the moment the follow-up clusters are formed; whatever makes them findable later is the normal commit/sync path, not this function. Misreading to avoid: this does not say RAPTOR clusters without embeddings in general; ScopedCluster still takes d.Search. The refs below pointing at the March 2026 plan doc and review.go@77f70cf are historical; the HEAD ref is the authority.
