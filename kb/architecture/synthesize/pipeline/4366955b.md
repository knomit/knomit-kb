# Because the pipeline engine is rebuilt on every call and continuations can race, every once-only step is decided by a conditional UPDATE whose row count is the verdict, everything that must outlive a call lives in the session DB, and only values re-derivable from config stay in memory

The engine is rebuilt on every call and two continuations of the same session may race, so every once-only transition is decided by a conditional UPDATE whose affected-row count is the verdict (a lost race is a benign no-op, never an error), every datum that must outlive a call is written to the session DB row or the response column rather than held in memory, and the only state deliberately kept in memory is what can be re-derived from config or arguments at the start of each call.

The three faces of the same constraint:
- ONCE-ONLY TRANSITIONS ARE CAS. `AdvancePipelineSessionPhase(ctx, id, from, to)` is `UPDATE ... WHERE id=? AND phase=?`; when two continuations race after the last work item, exactly one wins work→reflect and enqueues the single reflect item, the other re-fetches and finds itself already there — once-per-session enqueue with no separate dedup query, load-bearing because reflect has side effects. Work items are claimed the same way: PEEK, DECODE + VALIDATE (a failure here leaves the item unclaimed and retryable), then `UPDATE pipeline_work_items SET response=? WHERE id=? AND response IS NULL` via `AnswerPipelineWorkItem`, and APPLY only on a won claim. Applying twice mints duplicate synthesized facts because distill and merge generate a fresh UUID filename per apply, so apply-before-claim is corpus corruption.
- DURABLE MEANS A ROW. `PipelineSession.Health` is in-memory only and rides the FIRST result, so a session-end tally can only be computed at completion from the response column, through a narrow reader (`AnsweredDistillResponses`); `PendingPipelineWorkItems` returns the unanswered half by definition and cannot supply it. Running totals live on the session row for the same reason.
- RE-DERIVABLE MEANS IN MEMORY, NOT PERSISTED. Discovery effort is resolved from config/args at session start onto the Reviewer and never read back from a session row; there is NO `pipeline_sessions.effort` column and NO `CreatePipelineSessionWithEffort` — both were removed as dead persistence. `CreatePipelineSession(ctx, tool, branch, createdBy)` is the only constructor.

The session DB itself is ephemeral: recreated empty from `session_schema.sql` on every Service.Open, so schema changes there are plain edits with no numbered migration; only `pipeline_watermarks` in the main DB is durable across restarts.

WHAT THIS DOES NOT MEAN: the CAS is not a lock and takes no lease — no reclaim path, no expiry, a consumed item never returns to the queue. A hard failure DURING apply loses that one item's decisions and is not retried; this is the ACCEPTED failure mode (corpus un-maintained, never invalid) and a claim-lease with retry must NOT be added, because retry is only safe when apply is idempotent and it is not. 'No migration needed' is a property of the ephemeral session tables only; main-DB tables keep the numbered up/down discipline.
