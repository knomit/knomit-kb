# internal/corpus/synthesize/graph holds louvain.go, cluster.go (ScopedCluster) and cluster_result.go; it imports only synthesize/step and store/index, and the parent reaches it through exported names with a real production user

The graph child package (PR 604) owns Louvain community detection, the category-fenced ScopedCluster and the ClusterResult type. It imports only synthesize/step plus engine/store/index and nothing from the parent.

The parent reaches it through ScopedCluster, ClusterResult/ClusterOf, ClusterResultFromGroups (bridge, bridge_report, bridge_motif_report, review_strategy) and RequireNeighborKinds (cousins.go); the last two were unexported before the move and renamed on export, and each has a production caller. louvainCommunities, categoryDir, groupByCategory, subgraphFacts and filterSmallClusters stay unexported, and their tests moved into the child. There is no parent alias, var or wrapper for a graph name (TestParents_NoForwardsIntoChildren).

Guards that follow the move: (1) TestLayers lists the new edge 'corpus/synthesize/graph -> corpus/synthesize/step' as the only new same-layer edge; deleting the entry fails the test. (2) The MN6 keys in internal/domain/fact/motif_conformance_test.go are graph/cluster.go and graph/louvain.go; a stale key fails loudly ('MN6 target ... is missing'), so a future move cannot silently narrow the guard. Facts a408264a (category fence) and 7e16b659 (ScopedCluster determinism) describe code that now lives in graph/cluster.go.

Does NOT mean: the category fence, the neighbor-kind filter or Louvain seeding changed. The review confirmed the move is behaviour-neutral apart from the package clause and the two export renames.
